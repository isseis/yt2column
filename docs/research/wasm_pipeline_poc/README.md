# Go の WASM 版のパイプラインを拡張のページで動かす PoC の調査記録

記事を作る Go のパイプラインを WASM（WebAssembly）にビルドし、ブラウザ拡張のページで動かした PoC（概念実証）の測定の記録である。拡張だけの構成の設計（[#772](https://github.com/isseis/yt2column/issues/772)）が、構成を決める根拠として引用するために残す。タスクは [0084](../../tasks/0084_wasm_pipeline_poc/01_requirements.md)（[#771](https://github.com/isseis/yt2column/issues/771)）である。

0084 の測定は 2026-11-12 の 1 日に行い、タスク 0090 の追加の測定（「0090 の追加の測定」）は 2026-11-12〜13 に行った。どちらも時点の記録として扱う。ブラウザ・Go・API は変わるので、ここに書いた振る舞いが今も成り立つとは限らない。

本書は、API キー・ワークスペース ID・記事の本文・字幕の本文を含まない。

## 3 つの問いへの答え

問い 1〜3 は、要件書の背景の 3 つの問いである。答え方の規則は要件書 AC-24 による。

### 問い 1：Go の WASM 版のパイプラインは、拡張のページで現実的に動くか

-   **仕組みとして動くか：はい（生成と検証・推敲の 2 つの工程で確かめた。字数の調整の工程は走らなかった）。** WASM の入口から `net/http`（`fetch` に変換されたもの）で Claude API を呼び、記事の生成が完了した。Haiku の 7 回（Chrome 5 回・Brave 2 回。「測った値」の測定 3・4）と、Chrome で本番の構成の 3 回（測定 6）が成功した。
    -   ただし、字数の調整の工程は、どの回でも走らなかった（`skipped`）。CLI と同じ条件で、生成した本文が長すぎなかったためである。字数の調整は生成と同じクライアント（同じ HTTP の経路）を使うが、この工程の API の呼び出しそのものは観測していない（「確かめていない事項」）。
-   **現実的かどうか：** 値だけを挙げ、判断は #772 に委ねる（要件書 §4.1）。
    -   WASM のサイズは 17,300,194 バイト、`gzip -9` で 4,138,823 バイトである。
    -   ページの読み込みの開始から、入口を呼べるようになるまでの時間は、Chrome で 62.4〜171.2 ms、Brave で 49.9〜206.5 ms である（各 7 回）。
-   拡張のページから API を呼ぶのに要ったのは、次の 2 つである（「CSP・権限・ヘッダの試行」）。CSP は Chrome と Brave で確かめた。ヘッダと権限の組み合わせは Chrome だけで試し、Brave では権限なし・ヘッダありで通ることだけを確かめた。
    -   CSP の `'wasm-unsafe-eval'`。
    -   `anthropic-dangerous-direct-browser-access` のヘッダ。
-   `fetch` を通した送信では、アダプタの守りの一部が、ネイティブのビルドと同じには働かなかった（「プローブ」）。
    -   リダイレクトを拒否する守りは、効かなかった。
    -   期限とキャンセルは、本文の途中では効かなかった。

### 問い 2：記事の生成をビューアのタブで実行できるか

**はい。** 問い 2 の失敗（要件書 AC-17 の最後の段落）は 1 つもなかった。

-   背面のままの試行は、Chrome と Brave の両方で、記事の生成・長い応答・メモリセーバーを有効にした記事の生成のすべてが完走した（測定 4・5）。
-   Chrome での本番の構成の 3 本も、すべて背面のまま完成した（測定 6）。
-   メモリセーバーを有効にした試行で、ブラウザはタブを破棄しなかった。人が破棄を強制する操作でも、拡張のページのタブは破棄されなかった（測定 4 の 4-3・4-4）。
-   どちらのブラウザでも、タブを閉じると、送信中の要求は中止された（測定 4 の 4-5）。

### 問い 3：ストリーミングは要るか

**測った範囲では要らない。** 次のものを、ストリーミングなしで受け取りきれた。

-   長い応答（Haiku、`max_tokens` 40,000）の 2 回。出力は 37,555 トークンと 37,673 トークンで、どちらも打ち切りではなく完了した。所要時間は約 203〜205 秒で、背面のままだった。
-   本番の構成の 3 本の、走ったすべての工程（生成と検証・推敲）。

応答の受け取りそのもの（`fetch` の失敗や期限切れ）で受け取れなかったものはない。

**Opus で 40,000 トークンを出力する長さの応答。** この長さの応答は確かめていない。見積もりでは期限の内に収まるが、背面のタブで受け取れるかは未確認で、#772 で扱う。根拠は次のとおりである。

-   本番の 3 本で観測した Opus（effort `high`）の出力の速さは、約 98〜128 トークン/秒である。工程の所要時間の全体で割った値で、入力の処理の時間を含むので、速さとしては低めに出る。
-   この速さで 40,000 トークンを出力すると、約 313〜408 秒（約 5.2〜6.8 分）かかる見積もりになる。
-   これは、Haiku の長い応答の所要時間（約 203〜205 秒）の約 1.5〜2 倍で、呼び出しごとの期限（15 分）の半分以下である。
-   ただし、この長さの応答を背面のタブで受け取れるかは、実測していない。

## 測った値

### 測定 1：プローブ（アダプタの守り）

PoC の入口から、`llmhttp.Post` を、ダミーのキーを付けた要求で localhost のプローブ用サーバへ送った。本物の API キーは使っていない。ブラウザは Chrome と Brave で、コミットは `5bcc3c4b` である。

| ケース | Chrome | Brave | サーバの記録 |
|---|---|---|---|
| `redirect_same`（`host_permissions` の内の先へ 307） | 成功（11 バイト、18 ms） | 成功（11 バイト、9 ms） | リダイレクトの先に、ダミーのキーと本文が届いた |
| `redirect_foreign`（`host_permissions` の外の先へ 307、事前の確認を拒む） | `transport`（`Failed to fetch`）、16 ms | `transport`、6 ms | 先には `OPTIONS` だけが届いた（`Origin` は `null`、キーと本文はなし）。本番の要求は届かなかった |
| `redirect_foreign`（同上、事前の確認を許す） | 成功（11 バイト、10 ms） | 成功（11 バイト、13 ms） | `OPTIONS` の後に本番の要求が届き、ダミーのキーと本文が付いていた |
| `redirect_manual`（`js.fetch:redirect: manual` を付けた `redirect_foreign`） | `http_status`（状態 0）、4 ms | `http_status`（状態 0）、5 ms | 元だけに届き、先には何も届かなかった |
| `large_body`（9,437,184 バイトの本文） | `invalid_response`（8 MiB の上限）、29 ms | `invalid_response`、28 ms | サーバは送りきった。クライアントは上限で読むのをやめた |
| `stall_header`（応答ヘッダの前で止まる、期限 3 秒） | `timeout`、3,006 ms | `timeout`、3,001 ms | クライアントが約 3,000 ms で接続を閉じた |
| `cancel_header`（応答ヘッダの前で止まる、2 秒でキャンセル） | `canceled`、2,004 ms | `canceled`、2,003 ms | クライアントが約 2,000 ms で接続を閉じた |
| `stall_body`（本文の途中で止まる、期限 3 秒） | 返らない | 返らない | 期限の 3 秒を過ぎても接続は閉じられなかった。閉じられたのは 20 秒以上後で、人がページを読み込み直した時刻と見られる |
| `cancel_body`（本文の途中で止まる、2 秒でキャンセル） | 返らない | 返らない | 同上 |

-   **リダイレクト。** `fetch` がリダイレクトに従い、アダプタの `CheckRedirect` による拒否は効かなかった（[security.md](../../dev/security.md) §3 の守り）。
    -   リダイレクトの先が `host_permissions` の内なら、API キーのヘッダと本文がそのまま転送された。
    -   `host_permissions` の外の先でも、その先が事前の確認を許せば、ヘッダと本文が転送された。CORS は、転送を防がない。
    -   `js.fetch:redirect: manual` を付けると、どの先へも送られず、状態 0 の失敗になった。
-   **本文の上限。** 8 MiB の上限は効いた。
-   **期限とキャンセル。** 応答ヘッダの前では効いた。本文の途中では、期限もキャンセルも効かなかった。`llmhttp.Post` の「期限は本文の読み込みまで覆う」という前提は、`js` のビルドでは成り立たない。
-   **期限の遅れ。** 背面のタブが長く隠れると、ブラウザはタイマーを間引く。Go の期限は `setTimeout` で発火するので、背面では期限切れの時刻が遅れうる。背面での期限の遅れは測っていない。

### 測定 2：読み込みと CSP、サイズと読み込みの時間

-   CSP を manifest に書かない状態（`f016d7c7`）では、Chrome も Brave も WASM を読み込めなかった。ページには次の理由が表示された。

    ```text
    WebAssembly.instantiateStreaming(): Compiling or instantiating WebAssembly module violates the following Content Security policy directive because neither 'wasm-eval' nor 'unsafe-eval' is an allowed source of script in the following Content Security Policy directive: "script-src 'self'".
    ```

    MV3 の拡張のページの既定の CSP は、`'wasm-unsafe-eval'` を含まない。Chrome では、DevTools のコンソールには何も出なかった。
-   `content_security_policy.extension_pages` を `script-src 'self' 'wasm-unsafe-eval'; object-src 'self'` にした状態（`5bcc3c4b`）では、どちらも読み込めた。
-   サイズは、`yt2column.wasm` が 17,300,194 バイト、`gzip -9` で 4,138,823 バイトである（`5bcc3c4b`。`f016d7c7` では、圧縮しないもので同じ大きさ、`gzip -9` で 4,138,817 バイト）。
-   読み込みの時間は、ページの読み込みの開始（`performance.timeOrigin`）から、入口を呼べるようになったと知らせるまでである。`WebAssembly.instantiateStreaming` で読み込んだ。単位は ms。

| 回 | 条件 | Chrome | Brave |
|---|---|---|---|
| 1 | 拡張を読み込み直した後、ページを開き直した | 152.2 | 114.7 |
| 2〜4 | 同じタブで読み込み直した | 89.9 / 93.5 / 62.4 | 51.3 / 81.0 / 49.9 |
| 5〜7 | ブラウザを終了して起動し直した直後 | 171.2 / 168.7 / 130.7 | 189.7 / 206.5 / 123.1 |

### 測定 3：CSP・権限・ヘッダの試行（Chrome、Haiku）

`anthropic-dangerous-direct-browser-access` のヘッダと、`host_permissions` の `https://api.anthropic.com/*` の組み合わせを、記事の生成で 1 回ずつ試した。

| 組み合わせ | 結果 | DevTools の Network |
|---|---|---|
| 権限なし・ヘッダあり（3-a、`5bcc3c4b`） | 成功 | 事前の確認（`OPTIONS`）が 1 本、`POST /v1/messages` が 2 本で、すべて 200。Anthropic は事前の確認を許した |
| 権限あり・ヘッダなし（3-b、`a7b09d81`） | 失敗（`http_status` 401、551 ms） | `POST` が 1 本で 401。事前の確認はなかった |
| 権限あり・ヘッダあり（3-c、`a7b09d81`） | 成功 | `POST` が 2 本で、どちらも 200。事前の確認はなかった |

-   **ヘッダは必須で、`host_permissions` は必須ではない。**
    -   権限がないと、拡張のページからの送信は CORS の対象になり、事前の確認が 1 往復増える。それでも、事前の確認は Anthropic に許されて通った。
    -   権限があると、事前の確認は省かれる。
-   3-b と 3-c は、同じページで、同じ入力欄の値のまま、ヘッダを送るかどうかだけを変えた。そのため、3-b の 401 はキーの誤りではなく、ヘッダがなかったことによると判断した。DevTools の Headers で、`x-api-key` に正しいキーが入っていることも人が見た（値は記録していない）。
-   3-b の応答の本文は読めなかった。アダプタは 200 以外の応答の本文を読まないので、DevTools でも「failed to load response data」となり、エラーの type と message は得られなかった。
-   3-b の失敗の文とページの記録に、API キーとワークスペース ID は出なかった。
-   Haiku 5.5 は、effort の `medium` を受け付けた（200）。`medium` 以外の値は試していない。

各回の工程ごとの値は、下の「工程ごとの値」にある。

### 測定 8：Worker からの送信の守り（プローブ、ダミーのキー）

-   上限を超える書き込みは、黙って切り詰められず、値を書かずに失敗した。
