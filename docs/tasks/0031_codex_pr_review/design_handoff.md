# 設計への申し送り（0031 codex_pr_review）

要件の起草で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目をどう扱ったか（または扱わない理由）を記録する。

## H-01: Codex のレビュー済みを判定する手段

F-003（AC-10・AC-11）。候補は、`chatgpt-codex-connector[bot]` の PR レビューの `commit_id` と head の一致（issue #403）。指摘が 0 件のときの完了の印は、F-001 の観測（AC-01 の 1）で決める。PR レビューのオブジェクトが投稿されない場合（リアクションだけなど）、依頼のコメントとレビューの対応づけ、および依頼の後に head が動いた場合の扱いを決める。今の `LAST_REVIEWED`（`runpr.md:179-185`）を、Codex の印からどう求めるかも含める。

## H-02: 比較の期間かどうかを、コマンドがどこから知るか

F-004・F-005。`_context.md` の値（待つ PR レビュアーを 2 つ持つ形）にするか、別の値にするかを決める。比較の期間を終える変更（AC-20）が、その値と `.coderabbit.yaml` の変更で済む形にする。

## H-03: REST の名前の作り方

AC-22。#395 の設計（H-02）の「GraphQL の `login` に `[bot]` を付けて REST の名前を作る」規則が、Codex でも成り立つかを、F-001 の観測（AC-03）で確かめる。成り立たなければ、#405 の設計と合わせて決める。

## H-04: `@codex` のメンションを誰が使えるか

4.2 セキュリティ。公開リポジトリで、書き込み権限のないアカウントが `@codex review` などのメンションで Codex を動かせるかを、F-001 の試験運用の際に、公式文書か設定の画面で確かめる。動かせる場合、そのレビューの著者は `chatgpt-codex-connector` になるので、判定（AC-11）と `/fixpr` の信頼の判定（#405）への影響を検討する。

## H-05: Codex のステータスコンテキスト・チェックラン

AC-01 の 4 の観測の結果に応じて、レビュー済みの判定に使うか、`gh pr checks --watch` の待ちに影響するか、branch protection の設定を変える必要があるかを決める。

## H-06: 観測と比較の記録の文書

F-001・F-004・F-005。文書の名前と形式（表の列）を決める。観測の記録（設計の入力）と比較の記録（継続の判断の入力）を同じ文書にするか分けるかも決める。
