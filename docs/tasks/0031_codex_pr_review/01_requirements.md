## 1. 概要 (Overview)

**目的:** 本書は、PR レビュー（GitHub の PR 上で自動レビュアーが行うレビュー）を CodeRabbit から Codex の GitHub 連携に切り替えるための要件を定義する（[#403](https://github.com/isseis/yt2column/issues/403)）。切り替えの前に試験運用で Codex の振る舞いを観測し、その結果に基づいてレビュー済みの判定を設計する。ローカルの CLI レビュー（`coderabbit review`）は、CodeRabbit のまま残す。

**背景:**

CodeRabbit の PR レビューには、時間あたりの上限がある。Essentials のプランでは、1 開発者あたり 1 時間に 5 回である。手動の `@coderabbitai review` も数える（issue #403）。この上限のため、PR レビューは PR を開いたときの 1 回だけにし、`.coderabbit.yaml` で増分レビューを止めている（`.coderabbit.yaml:9-14`）。以後の変更はローカルの CLI でレビューする（`CLAUDE.md:99-104`）。2 回目以降の PR レビューは、エスカレーションの判断か利用者の依頼があったときだけ依頼する（`.claude/commands/_lib/pr-review-escalation.md:14-18`）。それでも、CodeRabbit の PR レビューは頻繁にレート制限に当たり、実際には機能していない（利用者の報告。2026-10-21）。

現在の `/runpr` は、PR レビューを CodeRabbit 専用の方法で扱う。

-   **依頼:** `gh pr comment <number> --body "@coderabbitai review"` で依頼する（`runpr.md:187-196`）。PR を開くコマンドも、約 2 分待ってもレビューが始まらないときだけ、同じ方法で依頼する（`_lib/task-pr-handoff.md:116-121`）。
-   **レビュー済みの判定:** 次の 2 つがそろったとき、そのコミットをレビュー済みとする（`runpr.md:153-185`）。1 つは、PR の `StatusContext` のうち `CodeRabbit` のものが `SUCCESS` であること。もう 1 つは、CodeRabbit の PR レビューの本文か要約コメントに「between `<sha>` and `<headRefOid>`.」の行があることである。応答がなければ、依頼から約 15 分で止めて報告する（`runpr.md:192-196`）。
-   **ラウンド上限:** `/fixpr` のラウンド上限は、スレッドの最初のコメントの著者が `Bot` である場合だけに働く（`fixpr.md:42-49`・`fixpr.md:183`）。

Codex の GitHub 連携の公式文書から分かったことは、次のとおりである（issue #403）。

-   手動の依頼は PR コメントの `@codex review` で行う。
-   自動でレビューするタイミングは、Codex の設定で「PR 作成時のみ」「push する度に」「スマート検出（試験的機能）」から選ぶ。今の設定は「PR 作成時のみ」である（利用者の報告。2026-10-21）。
-   設定の「徹底的なコードレビュー」を有効にすると、新しい問題を検出しなくなるまで指摘を探し続ける（利用者の報告。2026-10-21）。
-   投稿者は `chatgpt-codex-connector` ボットである。ファイル・行に紐づくコメントを、標準の GitHub レビューとして投稿する。
-   GitHub には P0 と P1 の指摘だけを投稿する。
-   レビューの規則は `AGENTS.md` で変えられる。
-   ChatGPT のプランが必要で、API キーの契約では使えない。
-   GitHub 経由のレビューの割り当て（6 節）の数値は、公式文書に記載がない。

`AGENTS.md` はすでにリポジトリにあり、`## Review guidelines` の節を持つ（`AGENTS.md:5`）。一方、issue は `AGENTS.md` を新規に作り、`## Code Review Rules` の節を置くとしている。

このリポジトリは公開されている（`docs/tasks/0030_fixpr_untrusted_threads/01_requirements.md` の 1 節。2026-10-21 に確かめた）。GitHub のアカウントを持つ人なら誰でも、PR にコメントを書ける。

対応 issue: [#403](https://github.com/isseis/yt2column/issues/403)（前提: [#405](https://github.com/isseis/yt2column/issues/405)、その前提: [#395](https://github.com/isseis/yt2column/issues/395)（タスク `0030_fixpr_untrusted_threads`）。関連: [#394](https://github.com/isseis/yt2column/issues/394)）

**前提の関係:** #395 は、信頼する自動レビュアーを `_context.md` の 1 つの名前で判定する（`docs/tasks/0030_fixpr_untrusted_threads/01_requirements.md` の AC-01・AC-35）。その名前は `coderabbitai` の予定である（同 `02_architecture.md` 3.3。#395 は実装中で、`_context.md` にはまだその項目がない）。このままでは Codex が開いたスレッドは信頼されず、`/fixpr` は自動では処理しない。名前を複数持てるようにする対応は #405 で行う。依存関係は #395 → #405 → #403 である。本書の F-002 から F-006 は、#405 の完了を前提にする。F-001（試験運用での観測）は、#405 を待たずに行える。#405 は、F-001 の観測値（AC-03）をもとに設計する。

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。具体的には、何を観測して記録するか、いつどの Bot にレビューを依頼するか、何をもってレビュー済みとするか、である。「切り替えの PR」「完了を待つ PR レビュアー」「完了の印」「レビュー済み」は 6 節で定義する。次の事項は設計（`02_architecture.md`）で決める。設計は、F-001 の観測の記録がそろってから始める（2.4）。

-   Codex のレビュー済みを判定する具体的な方法（どの API のどの値を見るか）と、待つ時間の上限。
-   コマンドの文書のどこに何を書くか。

要件の起草とレビューで挙がった設計の事項は、[design_handoff.md](design_handoff.md) に申し送る。

**issue #403 で決めたこと:**

-   **切り替えるのは PR レビューだけ:** ローカルの CLI レビューは CodeRabbit のまま残す。CLI の割り当ては PR レビューの割り当てと別であり、`--base-commit`・構造化出力・`findings --clear` など、今の手順がそのまま使えるためである。
-   **エスカレーションの方針は残す:** PR レビューは PR を開いたときの 1 回だけとし、2 回目以降はエスカレーションの判断か利用者の依頼で行う。Codex の割り当てを実測するまでは、割り当てに余裕があると見なせないためである。
-   **先に試験運用で観測する:** issue #403 の未確認項目 1〜5（AC-01 の 1〜5 に当たる）を観測して記録してから、コマンドを変える。判定の方法が観測の結果で決まるためである。
-   **CodeRabbit の PR レビューを止める:** `.coderabbit.yaml` で CodeRabbit の自動レビューを止める（`auto_review.enabled: false`）。両方が同じ PR をレビューして割り当てを二重に使うのを防ぐためである（AC-22）。
-   **スレッドの著者の値を記録する:** GraphQL の `author.__typename` と `author.login`、REST の `user.type` と `user.login` を記録する。CodeRabbit では、GraphQL の `login`（`coderabbitai`）と REST の `login`（`coderabbitai[bot]`）の形が違ったためである。#405 は、この値をもとに設計する。
-   **完了を待つ PR レビュアーを信頼の一覧と分ける:** どの Bot の PR レビューを待つかは、信頼する自動レビュアーの一覧（#405）とは別に定める。REST の名前は直接書かず、`_context.md` から作る（0030 の AC-35 に合わせる）。役割が違うためである。信頼の一覧は「誰のスレッドを処理するか」を決め、完了を待つ PR レビュアーは「何をもってレビュー済みとするか」を決める。

issue は、CodeRabbit との比較（進め方 4）と、比較の結果に基づく継続の判断を完了条件に含めている。本書はこれをスコープ外とする（下記の最初の決定）。

**要件定義の際に決めたこと（2026-10-21）:**

-   **比較をせずに切り替える:** Codex への切り替えを既定の方針とし、CodeRabbit との比較と、継続するかの判断はスコープ外とする（2.3）。CodeRabbit の PR レビューは頻繁にレート制限に当たって機能しておらず、同じ PR で両方を並べて比べることができないためである。比較のための期間（両方のレビューを待つ処理）と、継続しない場合に revert で戻す要件も設けない。
-   **観測は設計の前に行う:** 要件では、観測の項目と記録の内容を定める。観測そのものは、`02_architecture.md` を書く前に済ませる（F-001・2.4）。試験運用はまだ行っていない。判定の方法は観測の結果で決まるので、観測の前に設計すると書き直しになるためである。
-   **書き込み権限のない人が Codex を動かせるなら、切り替えを進めない:** 判定の範囲は、観測の後に次の項目で絞った。試験運用で確かめ、動かせると分かったら、観測の記録に残して止め、設計に進まない（AC-01 の 8・AC-05）。切り替えを既定の方針にしても、この条件は残す。公開リポジトリでは誰でもコメントを書けるので、外部の人が利用者の割り当てを消費できる。さらに、Codex に修正やブランチの作成を依頼できるおそれがあるためである。
-   **ゲートは、Codex のアカウントを接続していない外部のアカウントで判定する（2026-10-21、観測の後）:** 試験運用で、Codex のアカウントを接続していない、書き込み権限のないアカウントの `@codex review` では、Codex が断りのコメントを返すだけで実行されず、利用者の割り当ても消費されないことを確かめた（[observations.md](observations.md) の項目 8）。Codex のアカウントを接続している外部のアカウントは確かめていない。そのような人の `@codex` はその人のアカウントと割り当てで実行されると考えられ、利用者の割り当ては消費されない。残るのは、App の書き込み権限（`code`・`workflows` など）を使う依頼ができるかであり、これを残るリスクとして記録して（4.2）、ゲートは確かめた範囲で判定する。確かめるには、Codex の契約を持つ別のアカウントが要り、費用に見合わないためである。
-   **レビューのタイミングは「PR 作成時のみ」にする:** Codex は PR を開いたときに自動でレビューし、push ではレビューしない。2 回目以降は `@codex review` で依頼する（F-002）。PR を開いたときの 1 回だけという方針に、そのまま合うためである。「push する度に」は採らない。修正を push するたびにレビューが走り、割り当てを消費するためである。「スマート検出」も採らない。試験的な機能で、いつ走るかを `/runpr` から予測できず、レビュー済みの判定（F-003）を組めないためである。
-   **徹底的なコードレビューは使わない:** 設定の「徹底的なコードレビュー」は有効にしない（5 節）。`/fixpr` は、指摘が尽きるまでではなく方針で止める設計（`fixpr.md` の Convergence policy）であるためである。また、所要時間が延びると待つ時間の上限（AC-13）に響き、割り当ての消費も分かっていない。
-   **自動レビューが始まらなければ依頼する:** PR を開いた後、Codex がレビューを始めていなければ、PR を開くコマンドが `@codex review` で依頼する（AC-06）。始まっていれば依頼しない。自動レビューと依頼が重なると、割り当てを二重に使うためである。今の CodeRabbit の扱い（`_lib/task-pr-handoff.md:116-121`）と同じ形である。
-   **`AGENTS.md` は既存のものを更新する:** 新規には作らない。Codex が読む節の見出しは、試験運用で確かめてから決める（F-001・F-006）。`AGENTS.md` はすでにあり、`## Review guidelines` の節を持つ（`AGENTS.md:5`）が、issue は `## Code Review Rules` としているためである。
-   **Codex のレビューが届かないときは止めて報告する:** レート制限の通知や、依頼の後に応答がない場合は、レビュー済みとせず、止めて報告する（F-003）。CodeRabbit に自動で切り替える案は採らない。CodeRabbit の PR レビューは機能しておらず、両方の判定の方法を保守することにもなるためである。
-   **再実行では、応答を待つ依頼があれば再び依頼しない:** 止まった後に `/runpr` を再実行したとき、そのコミットについて、完了を待つ PR レビュアーへの依頼が応答を待っていれば、再び依頼しない。レート制限やエラーの通知を受けた依頼と、待つ時間の上限（AC-13）を過ぎても完了の印がない依頼は終わったものとし、新しく依頼する（AC-15）。再実行のたびに割り当てを消費せず、回復の後や応答がなかった後には依頼し直せるようにするためである。完了の印がないまま上限を過ぎた依頼を終わったものとしないと、再実行しても同じ依頼を待って止まり続け、マージに進む手段がなくなる。
-   **作業の順序と #403 を閉じる PR:** 作業の順序は 2.4 のとおりとし、切り替えの PR で #403 を閉じる。試験運用の `@codex review` の投稿は、利用者が行う。PR へのコメントはネットワークの操作であり、`CLAUDE.md` の「Tool Execution Safety」で承認が要るためである。
-   **観測の記録はタスクのディレクトリに置く:** 本タスクのディレクトリの下の文書に記録する（F-001）。設計と同じ PR の流れでレビューでき、判断の根拠がリポジトリに残るためである。
-   **依頼したコミットは、依頼の時点の head とその子孫とする（2026-10-22、設計の際）:** Codex は、依頼から 12〜25 秒後にレビューを始めたときの head をレビューする（observations.md の項目 9）。この間に `/fixpr` などの push があると、依頼の時点の head ちょうどの完了の印は届かず、待つ時間の上限で止まって割り当ても無駄に使う。また、PR を開いたときの自動レビューと、前回の実行の依頼では、依頼の時点の head を GitHub から確実に求められない（push の時刻を返す API がない）。完了の印は示すコミットだけをレビュー済みにするので、範囲を広げても、レビューしていないコミットをレビュー済みにすることはない（AC-10）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   Codex の PR レビューの振る舞い（AC-01 の 1〜5 など）を観測して記録し、判定の方法を観測の結果に基づいて決められるようにする。
-   PR レビューを Codex で行い、`/runpr` が初回のレビューの完了を正しく判定できるようにする。

### 2.2. スコープ (In Scope)

-   試験運用での観測と、その記録（F-001）。
-   Codex への PR レビューの依頼（F-002）。
-   Codex のレビュー済みの判定と、レビューが届かないときの停止（F-003）。
-   CodeRabbit の PR レビューの停止（F-004）。
-   文書: `AGENTS.md`・`CLAUDE.md`・`.coderabbit.yaml`・`docs/translation_glossary.md`、および `.claude/commands/` の下のコマンドの文書のうち、PR レビューを行う Bot を名指しするもの（`_context.md`・`runpr.md`・`_lib/task-pr-handoff.md`・`_lib/pr-review-escalation.md`・`fixpr.md`・`mkreq.md` など）（F-006）。

### 2.3. スコープ外 (Out of Scope)

-   CodeRabbit との比較と、比較の結果に基づく継続の判断（issue #403 の進め方 4 と完了条件の 3 つめ）。1 節の最初の決定のとおり、CodeRabbit の PR レビューが機能しておらず、比べられないためである。
-   ローカルの CLI レビュー（`_lib/coderabbit-local-review.md`）。issue で CodeRabbit のまま残すと決めたためである。
-   信頼する自動レビュアーを複数の名前にすること（`_context.md` の一覧、`fixprguard` の `--reviewer`、文書のガードのテスト）。#405 で行う。
-   CodeRabbit のレート制限の通知を、CodeRabbit のレビュー済みと数えない修正（#394）。切り替えの後は、`/runpr` が CodeRabbit の PR レビューを待たなくなるためである。#394 をどう閉じるかは、本タスクでは決めない。
-   Codex CLI の導入、`codex login`、リポジトリの Codex 連携とコードレビューの有効化。リポジトリの外の設定であり、利用者が行う（issue #403 の「進め方 1」）。
-   エスカレーションの方針の見直し（初回のみの方針をやめること）。Codex の割り当てを実測した後に、別の issue で扱う。

### 2.4. 作業の順序

本タスクは、試験運用という運用の作業を含む。そのため、通常の要件 → 設計 → 計画 → 実装の流れに、次の段階を加える。

1.  本書の承認。
2.  試験運用（F-001）。利用者が Codex の連携を設定し（レビューのタイミングは「PR 作成時のみ」）、PR を開いたときの自動レビューと、`@codex review` による依頼の両方を観測する。観測の記録は、本タスクのディレクトリの下の文書として PR にし、マージする。観測の結果が AC-05 に当たれば、本書を `draft` に戻して見直す。
3.  #405 の完了。
4.  設計（`02_architecture.md`）と実装計画（`03_implementation_plan.md`）。
5.  切り替えの PR（F-002・F-003・F-004・F-006 の変更）。#403 を閉じる。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 試験運用での観測と記録

実際の PR を開いたときの自動レビューと、`@codex review` の依頼の両方で、Codex の振る舞いを観測して記録する。この記録が設計の入力になる。

**Acceptance Criteria**:
- **AC-01**: 次の観測の結果が、本タスクのディレクトリの下の文書に記録されている。記録の項目は AC-01〜AC-03 で定める（文書の名前は問わない）。
    1.  指摘が 0 件のとき、Codex が何を投稿するか（PR レビュー、コメント、リアクションだけ、など）。レビューの途中に何かを投稿するか（受け付けを示すリアクションなど）も含める。
    2.  依頼していない push で、Codex が再びレビューするか（レビューのタイミングが「PR 作成時のみ」のとき）。
    3.  Codex のスレッドの著者の値（AC-03）。
    4.  ステータスコンテキストやチェックランが付くか。付く場合は、名前と状態の値、branch protection に影響するか。
    5.  1 時間あたりに受け付けるレビューの回数と、上限に達したときに投稿される通知の文面。上限に達するまで観測できなければ、観測した範囲の回数と、上限に達しなかったことを記録する。公式文書に通知の文面があれば、URL とともに引用する。
    6.  Codex のレビューの規則として読まれる、`AGENTS.md` の節の見出し。
    7.  依頼からレビューの完了までの時間。
    8.  Codex のアカウントを GitHub に接続していない、書き込み権限のないアカウントのコメント（`@codex review` など）で、Codex が動くか、利用者の割り当てが消費されるか。あわせて、Codex の GitHub App をインストールしたリポジトリの範囲と、App の権限。動くかどうかは、公式文書（URL 付きの引用）、Codex の設定の画面、書き込み権限のないアカウントでの実際の試行のいずれかで確かめ、記録にはそのどれによったかを書く。実際に試行した場合は、試行のコメントと、試行のために加えた権限や設定を片付けたことも記録する。
    9.  観測したときの Codex の設定（レビューのタイミング、徹底的なコードレビューの有無）と、PR を開いたときの自動レビューが始まったことを示す印（受け付けのリアクションなど。1 の途中の投稿と合わせて観測する）と、PR を開いてからその印が現れるまでの時間。
- **AC-02**: 各観測の記録に、日付と根拠が含まれている。根拠は、API の応答の該当部分、PR の画面で見た内容、公式文書の引用（URL 付き）のいずれかである。PR での観測には、PR の番号と、依頼したコミットの SHA も含める。
- **AC-03**: 指摘が 1 件以上あるレビューについて、スレッドの最初のコメントの著者の値として、GraphQL の `author.__typename` と `author.login`、REST の `user.type` と `user.login` が記録されている。
- **AC-04**: 指摘が 0 件のレビューと 1 件以上のレビューを、それぞれ 1 回以上観測している。
- **AC-05**: 次のいずれかに当たる場合は、その点が記録に挙げられ、本書の該当する要件が見直されて再び承認されるまで、設計を始めない。
    -   観測の結果が本書の要件と矛盾する（例: タイミングが「PR 作成時のみ」でも push のたびにレビューされる。Codex のスレッドの著者が `Bot` でない）。
    -   指摘が 0 件のレビューの完了を、レビューがない状態と区別できる印がない。または、その印をコミットと対応づけられない（AC-09 を満たせない）。
    -   指摘が 0 件のレビューか、1 件以上のレビューを観測できなかった（AC-04 を満たせない）。
    -   Codex のアカウントを接続していない、書き込み権限のないアカウントのコメントで、Codex が動くか、利用者の割り当てが消費される（AC-01 の 8）。
    -   PR を開いたときの自動レビューが始まったことを示す印がない（AC-06 を満たせない）。

#### F-002: Codex への PR レビューの依頼

PR レビューは、PR を開いたときの Codex の自動レビューで行う。自動レビューが始まらないときと、2 回目以降は、`@codex review` で依頼する。

**Acceptance Criteria**:
- **AC-06**: PR を開くと、Codex が自動でレビューする（AC-07）。PR を開いた後、設計で定めた時間（AC-01 の 9 の観測をもとに決める）だけ待つ。その間に Codex がレビューを始めた印（AC-01 の 9）が現れなければ、PR を開くコマンドが `@codex review` のコメントで依頼する。印が現れれば依頼しない。PR を開くのは、`/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2`・`/runplan` と、単独の変更で PR を作るときの `/runpr` である。
- **AC-07**: Codex のレビューのタイミングの設定は「PR 作成時のみ」で、徹底的なコードレビューは無効である。PR を開いたとき以外は、依頼していない push で Codex のレビューは走らない。
- **AC-08**: `/runpr` が 2 回目以降の PR レビューを依頼するとき（エスカレーションの判断が `request` のとき、または利用者が依頼を選んだとき）は、`@codex review` で Codex に依頼する。

#### F-003: Codex のレビュー済みの判定

`/runpr` は、Codex が依頼されたコミットのレビューを完了したことを確かめてから、そのコミットをレビュー済みとする。

**Acceptance Criteria**:
- **AC-09**: あるコミットに対して Codex が完了の印を投稿したときだけ、そのコミットはレビュー済みと判定される。完了の印は、指摘のあるレビューのものでも、指摘が 0 件のレビューのものでもよい。指摘が 0 件のときに何を完了の印とするかは、AC-01 の 1 の観測で決める。
- **AC-10**: レビュー済みの判定は、依頼したコミットについて行う。依頼したコミットは、依頼の時点の head と、その後に push されたコミットのうち依頼の時点の head を祖先に持つものである。依頼の時点の head が分からない依頼（PR を開いたときの自動レビュー、前回までの `/runpr` の実行や利用者が投稿した依頼）では、PR に含まれるコミット（PR の今の head とその祖先）を依頼したコミットとする。PR を開いたときの自動レビューの依頼の時点は、PR を開いた時点とする。依頼の後に `/fixpr` の push で head が動いても、依頼したコミットに完了の印があれば、その依頼はレビュー済みになる。完了の印は、それが示すコミットだけをレビュー済みにする。LAST_REVIEWED（`runpr.md:181-185`）は、Codex がレビュー済みのコミットのうち、ほかのすべてを祖先に持つものである。
- **AC-11**: 次のものは、レビュー済みの判定に使われない。
    -   著者の種類が `Bot` でないか、`login` が `_context.md` に定めた完了を待つ PR レビュアー（AC-25）と一致しない投稿。名前が同じ `User` のアカウントの投稿も含む。
    -   依頼したコミット（AC-10 の範囲）以外のコミットに対する完了の印。
    -   レート制限の通知とエラーの通知（AC-01 の 5 で観測した文面、または公式文書の文面）。
- **AC-12**: 待っている依頼の時点（AC-10）より後に、完了を待つ PR レビュアーが次の 4 種のいずれにも当たらない投稿をしたとき、`/runpr` はレビュー済みとせず、待ち続けずに止めて、投稿の URL と内容の要約を報告する。4 種とは、依頼したコミットに対する完了の印、AC-01 の 1 でレビューの途中の投稿と確かめたもの、すでに受け入れたレビューに属するコメントや返信、ほかのコミットに対する完了の印（AC-11 のとおり使わない）である。レート制限の通知とエラーの通知は、いずれにも当たらない投稿の例である。
- **AC-13**: 依頼から設計で定めた時間（AC-01 の 7 の観測をもとに決める）がたっても、依頼したコミットがレビュー済みにならなければ、`/runpr` は止め、Codex が最後に投稿したもの（なければ、投稿がないこと）を報告する。
- **AC-14**: AC-12・AC-13 で止まったとき、`/runpr` はマージの質問に進まない。
- **AC-15**: 止まった後に `/runpr` を再実行したとき、そのコミットについて、完了を待つ PR レビュアーへの依頼（PR を開いたときの自動レビュー、または利用者（`gh` で認証したアカウント）のコメント）がすでにあり、その依頼が応答を待っていれば、再び依頼しない。その依頼に対する完了の印を待つ。その依頼の後、次の依頼より前に、完了を待つ PR レビュアーがレート制限の通知かエラーの通知（AC-11・AC-12）を投稿していれば、その依頼は終わったものとし、新しく依頼する。依頼の時点から AC-13 の時間を過ぎても、その依頼に対する完了の印がない場合も（途中の投稿があってもよい）、同じく終わったものとし、新しく依頼する。
- **AC-17**: LAST_REVIEWED、エスカレーション（`_lib/pr-review-escalation.md`）、マージの質問の「PR レビュー」（`runpr.md:282-286`）は、Codex のレビューをもとにする。

#### F-004: CodeRabbit の PR レビューの停止

CodeRabbit の PR レビューを止め、PR レビューを Codex だけで行う。両方が同じ PR をレビューして割り当てを二重に使わないためである。ローカルの CLI レビューは止めない。

**Acceptance Criteria**:
- **AC-22**: PR を開いても、CodeRabbit の PR レビューは走らない（`.coderabbit.yaml` で自動レビューを止める）。`.claude/commands/` の下のコマンドの文書には、`@coderabbitai review` の依頼も、CodeRabbit の PR レビューを待つ手順も残らない。`.coderabbit.yaml` のコメントは、PR レビューを行わない理由を説明する。

#### F-006: 文書

PR レビューを行う Bot を説明する文書と、Codex が読むレビューの規則を、切り替えの後の状態に合わせる。完了を待つ PR レビュアーは `_context.md` の 1 か所で定め、コマンドの投稿が Codex を意図せず動かさないようにする。

**Acceptance Criteria**:
- **AC-24**: `.claude/commands/` の下のコマンドの文書（コマンドの `description` を含む）と `CLAUDE.md` は、PR レビューを行う Bot を Codex として説明する。ローカルの CLI レビューを CodeRabbit と呼ぶ記述は残る。
- **AC-25**: `/runpr` がどの Bot の PR レビューを待つかは、`.claude/commands/_context.md` の 1 か所で定められている。この値は、信頼する自動レビュアーの一覧（#405）とは別の項目である。`runpr.md` と `_lib/task-pr-handoff.md` は、REST の名前（例: `chatgpt-codex-connector[bot]`）を直接書かず、その値を参照する。
- **AC-26**: `AGENTS.md` の、Codex がレビューの規則として読む節（AC-01 の 6 で確かめた見出し）に、レビューの規則がある。その節は、`CLAUDE.md` の規則を写さず、参照する。
- **AC-27**: `docs/translation_glossary.md` に、本書で用いる「割り当て」（quota）・「指摘」（finding）・「スレッド」（thread）が載っている。
- **AC-28**: `make test`・`make lint` と、CI の `doc-guard` のジョブが通る。
- **AC-29**: コマンドが PR に投稿する文面（`/fixpr` の返信、PR のコメントなど）は、レビューの依頼そのもの（AC-06・AC-08）を除いて、`@codex` のメンションを含まない。スレッドの本文を引用する返信でも同じである。利用者のアカウントで投稿された `@codex` のメンションは、Codex に修正やブランチの作成をさせうるためである。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   N/A。PR レビューを待つ時間の上限は、観測（AC-01 の 7）をもとに設計で決める（AC-13）。

### 4.2. セキュリティ (Security)

本タスクは、ネットワークへの送信（Codex の GitHub 連携がリポジトリの内容を読む）と、信頼できない入力（GitHub API が返す、Codex やほかのアカウントの投稿）の扱いに関わる。`docs/dev/security.md` の観点から、次を要件とする。

-   **外部の人が Codex を動かせるなら進めない:** Codex のアカウントを接続していない、書き込み権限のないアカウントのコメントで Codex が動くか、利用者の割り当てが消費されると分かったら、切り替えに進まない（AC-01 の 8・AC-05）。
-   **残るリスク:** Codex のアカウントを接続している外部のアカウントが、`@codex` で修正やブランチの作成を依頼し、App の書き込み権限（`code`・`workflows` など）で変更させられるかは、確かめていない（1 節の決定）。他のリポジトリの報告では、修正の依頼には「create an environment for this repo」と返信しており、依頼する人が自分の環境を用意する必要がある（observations.md の項目 8）。
-   **外部の人の `@codex` への返信:** 外部の人が `@codex` と書くと、Codex は断りのコメントを返す（observations.md の項目 8）。この返信を、待っている依頼への想定外の投稿（AC-12）と取り違えると、外部の人が `/runpr` を止められる。どの投稿がどの依頼への応答かの対応づけは、設計で決める（design_handoff.md の H-01）。
-   **コマンドの投稿で Codex を動かさない:** コマンドが PR に投稿する文面のうち、`@codex` のメンションを含むのはレビューの依頼だけである（AC-29）。`/fixpr` の返信は、信頼できないスレッドの本文をもとに書かれるので、本文に含まれるメンションを写すと、利用者のアカウントから Codex に修正やブランチの作成を依頼することになるためである。
-   **Codex のスレッドの本文は信頼できないデータとして扱う:** Codex のスレッドは、#395（タスク 0030）の対策と同じく、信頼できない入力として扱う。本文はデータとしてプロンプトに渡し、変更の範囲を確かめる。Codex を信頼する自動レビュアーに加えるのは #405 で行い、本タスクでは信頼の判定を変えない。
-   **完了の印の受け入れ:** レビュー済みの判定は、GitHub API の応答という信頼できない入力を読む。境界の要件は次のとおりである。
    -   **受け入れる形:** 著者の種類が `Bot` で、`login` が完了を待つ PR レビュアー（AC-25）と一致する投稿のうち、AC-01 の 1 で定めた完了の印の形をとり、対象のコミットの SHA（40 桁の 16 進数）が依頼したコミット（AC-10 の範囲）のどれかの SHA と一致するものだけを受け入れる（AC-09〜AC-11）。
    -   **それ以外:** 値の欠け、形の違い、想定外の投稿は、補って受け入れず、「レビュー済みでない」とする。完了を待つ PR レビュアーの想定外の投稿があれば、止めて報告する（AC-12）。ほかのアカウントの投稿は、完了の印に似た文面を含んでいても使わない。公開リポジトリでは誰でもコメントを書けるためである。
    -   **ページ送り:** 判定に使う一覧（PR レビュー、コメント）は、ページを最後まで読む。途中のページで打ち切ると、完了の印や通知を見落とすためである。
    -   **使うメンバーと上限:** 使うのは、投稿の著者（種類と `login`）、完了の印の形、対象のコミットの SHA だけである。応答のほかのメンバーは、GitHub が増やしうるので拡張可能として無視する。件数とサイズの上限は N/A とする。読むのは 1 つの PR の一覧で、今の `runpr.md:167-178` と同じく GitHub のページ送りに従うためである。
    -   **センチネルエラー:** N/A。判定はコマンドの文書（エージェントへの手順）で行い、Go のコードを持たないためである。拒否の結果は、「レビュー済みでない」とすることか、止めて報告することである。
-   **送るのは公開されている内容だけ:** Codex の GitHub 連携が読むのは、公開リポジトリの PR の内容である。秘密（`DEEPSEEK_API_KEY`・`ANTHROPIC_API_KEY`・`SLACK_WEBHOOK_URL`）をコミットしない規則（`CLAUDE.md` の「Development Notes」）は変わらない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   Codex のレビューが届かないときは、レビュー済みとせず止めて報告する（AC-12〜AC-14）。CodeRabbit への自動の切り替えはしない。
-   再実行で依頼を重ねない（AC-15）。
-   Codex の割り当てが尽きて止まったとき、利用者は割り当ての回復を待って `/runpr` を再実行する。再実行では、通知を受けた依頼を終わったものとし、新しく依頼する（AC-15）。

### 4.4. 互換性 (Compatibility)

-   ローカルの CLI レビュー（`coderabbit review`）の手順は変えない。
-   `/fixpr` のラウンド上限（`fixpr.md:42-49`）は、Codex のスレッドにも同じく働く。これは、Codex のスレッドの著者が `Bot` であることを前提にする（AC-01 の 3 で確かめる。違えば AC-05）。

### 4.5. 保守性 (Maintainability)

-   完了を待つ PR レビュアーは 1 か所で定める（AC-25）。
-   判定の方法は Codex 用の 1 つだけにする。CodeRabbit の PR レビューの依頼と待ちは、コマンドの文書から消す（AC-22）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   F-002 から F-006 は #405 の完了を前提にする。F-001 は前提なしに行える（2.4）。
-   Codex の GitHub 連携には ChatGPT のプランが必要である。API キーの契約では使えない（issue #403）。Codex の割り当ては、利用者のほかの Codex の利用（CLI など）と共有されうる。
-   Codex の連携と設定は、リポジトリの外の設定であり、利用者が行う。リポジトリの連携、コードレビューの有効化、レビューのタイミングを「PR 作成時のみ」にすること、徹底的なコードレビューを無効のままにすることである（AC-07）。
-   エスカレーションの方針（`_lib/pr-review-escalation.md`）は、Codex の割り当てを実測するまで残す（issue #403）。

## 6. 用語集 (Glossary)

-   **PR レビュー**: 自動レビュアーが GitHub の PR 上で行うレビュー。ローカルの CLI レビューと区別する。
-   **ローカルの CLI レビュー**: `coderabbit` CLI でローカルの差分をレビューすること（`_lib/coderabbit-local-review.md`）。本タスクでは変えない。
-   **割り当て**: 自動レビュアーが一定時間に受け付けるレビューの回数の上限（英語では quota）。`docs/translation_glossary.md` の「枠」（slot）は localhost サーバの同時処理数の単位であり、別の概念なので本書では使わない。
-   **指摘**: レビューが挙げる個々の問題。スレッドとして投稿されるものと、レビューの本文にだけ書かれるものがある。
-   **スレッド**: PR のファイル・行に紐づくレビューコメントの連なり。`/fixpr` が処理する単位である。
-   **依頼**: 完了を待つ PR レビュアーにレビューを求めること。`@codex review` のコメントと、PR を開いたときの自動レビュー（AC-10）の両方を指す。
-   **完了の印**: 完了を待つ PR レビュアーが、あるコミットのレビューを完了したことを示す投稿（AC-09）。何を印とするかは、AC-01 の 1 の観測で決める。
-   **レビュー済み**: 完了を待つ PR レビュアーが、依頼されたコミットについて完了の印を投稿した状態（`runpr.md` の「Reviewed」）。
-   **完了を待つ PR レビュアー**: `/runpr` がレビュー済みの判定に使う Bot。承認を待つのではなく、レビューがそのコミットまで完了したことを待つ。信頼する自動レビュアーの一覧（#405）とは別に定める（AC-25）。
-   **切り替えの PR**: F-002・F-003・F-004・F-006 の変更を入れる PR（2.4 の 5）。
-   用語は `docs/translation_glossary.md` と統一する。
