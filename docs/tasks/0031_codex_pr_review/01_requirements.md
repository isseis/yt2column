## 1. 概要 (Overview)

**目的:** 本書は、PR レビュー（GitHub の PR 上で自動レビュアーが行うレビュー）を CodeRabbit から Codex の GitHub 連携に切り替える案を評価し、評価の結果に従って切り替えるための要件を定義する（[#403](https://github.com/isseis/yt2column/issues/403)）。評価は 3 段階で行う。試験運用での観測、同じ PR での CodeRabbit との比較、継続するかの判断である。ローカルの CLI レビュー（`coderabbit review`）は、CodeRabbit のまま残す。

**背景:**

CodeRabbit の PR レビューには、時間あたりの上限がある。Essentials のプランでは、1 開発者あたり 1 時間に 5 回である。手動の `@coderabbitai review` も数える（issue #403）。この上限のため、PR レビューは PR を開いたときの 1 回だけにし、`.coderabbit.yaml` で増分レビューを止めている（`.coderabbit.yaml:9-14`）。以後の変更はローカルの CLI でレビューする（`CLAUDE.md:99-104`）。2 回目以降の PR レビューは、エスカレーションの判断か利用者の依頼があったときだけ依頼する（`.claude/commands/_lib/pr-review-escalation.md:14-18`）。それでも、PR レビューの割り当て（6 節）そのものがボトルネックである点は変わらない。

現在の `/runpr` は、PR レビューを CodeRabbit 専用の方法で扱う。

-   **依頼:** `gh pr comment <number> --body "@coderabbitai review"` で依頼する（`runpr.md:187-196`）。PR を開くコマンドも、同じ方法で依頼する（`_lib/task-pr-handoff.md:116-121`）。
-   **レビュー済みの判定:** 次の 2 つがそろったとき、そのコミットをレビュー済みとする（`runpr.md:153-185`）。1 つは、PR の `StatusContext` のうち `CodeRabbit` のものが `SUCCESS` であること。もう 1 つは、CodeRabbit の PR レビューの本文か要約コメントに「between `<sha>` and `<headRefOid>`.」の行があることである。応答がなければ、依頼から約 15 分で止めて報告する（`runpr.md:192-196`）。
-   **ラウンド上限:** `/fixpr` のラウンド上限は、スレッドの最初のコメントの著者が `Bot` である場合だけに働く（`fixpr.md:42-49`・`fixpr.md:183`）。

Codex の GitHub 連携の公式文書から分かったことは、次のとおりである（issue #403）。

-   手動の依頼は PR コメントの `@codex review` で行う。個人設定で自動レビュー（Automatic review）を有効にすることもできる。
-   投稿者は `chatgpt-codex-connector` ボットである。ファイル・行に紐づくコメントを、標準の GitHub レビューとして投稿する。
-   GitHub には P0 と P1 の指摘だけを投稿する。
-   レビューの規則は `AGENTS.md` で変えられる。
-   ChatGPT のプランが必要で、API キーの契約では使えない。
-   GitHub 経由のレビューの割り当ての数値は、公式文書に記載がない。

`AGENTS.md` はすでにリポジトリにあり、`## Review guidelines` の節を持つ（`AGENTS.md:5`）。一方、issue は `AGENTS.md` を新規に作り、`## Code Review Rules` の節を置くとしている。

このリポジトリは公開されている（`docs/tasks/0030_fixpr_untrusted_threads/01_requirements.md` の 1 節。2026-10-21 に確かめた）。GitHub のアカウントを持つ人なら誰でも、PR にコメントを書ける。

対応 issue: [#403](https://github.com/isseis/yt2column/issues/403)（前提: [#405](https://github.com/isseis/yt2column/issues/405)、その前提: [#395](https://github.com/isseis/yt2column/issues/395)（タスク `0030_fixpr_untrusted_threads`）。関連: [#394](https://github.com/isseis/yt2column/issues/394)）

**前提の関係:** #395 は、信頼する自動レビュアーを `_context.md` の 1 つの名前で判定する（`docs/tasks/0030_fixpr_untrusted_threads/01_requirements.md` の AC-01・AC-35）。その名前は `coderabbitai` の予定である（同 `02_architecture.md` 3.3。#395 は実装中で、`_context.md` にはまだその項目がない）。このままでは Codex が開いたスレッドは信頼されず、`/fixpr` は自動では処理しない。名前を複数持てるようにする対応は #405 で行う。依存関係は #395 → #405 → #403 である。本書の F-002 から F-006 は、#405 の完了を前提にする。F-001（試験運用での観測）は、#405 を待たずに行える。#405 は、F-001 の観測値（AC-03）をもとに設計する。

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。具体的には、何を観測して記録するか、いつどの Bot にレビューを依頼するか、何をもってレビュー済みとするか、比較の期間に何をするか、継続するかの判断をどう記録し、その後どうするか、である。「比較の期間」「切り替えの PR」「判断の PR」「待つ PR レビュアー」「完了の印」「レビュー済み」は 6 節で定義する。次の事項は設計（`02_architecture.md`）で決める。設計は、F-001 の観測の記録がそろってから始める（2.4）。

-   Codex のレビュー済みを判定する具体的な方法（どの API のどの値を見るか）と、待つ時間の上限。
-   比較の期間かどうかを、コマンドがどこから知るか。
-   観測と比較の記録の文書の名前と形式。
-   コマンドの文書のどこに何を書くか。

要件の起草とレビューで挙がった設計の事項は、[design_handoff.md](design_handoff.md) に申し送る。

**issue #403 で決めたこと:**

-   **切り替えるのは PR レビューだけ:** ローカルの CLI レビューは CodeRabbit のまま残す。CLI の割り当ては PR レビューの割り当てと別であり、`--base-commit`・構造化出力・`findings --clear` など、今の手順がそのまま使えるためである。
-   **エスカレーションの方針は残す:** PR レビューは PR を開いたときの 1 回だけとし、2 回目以降はエスカレーションの判断か利用者の依頼で行う。Codex の割り当てを実測するまでは、割り当てに余裕があると見なせないためである。
-   **先に試験運用で観測する:** issue #403 の未確認項目 1〜5（AC-01 の 1〜5 に当たる）を観測して記録してから、コマンドを変える。判定の方法が観測の結果で決まるためである。
-   **CodeRabbit と比べてから継続を決める:** 指摘の質（見落とし・誤検知）、所要時間、割り当ての消費を比べる。
-   **スレッドの著者の値を記録する:** GraphQL の `author.__typename` と `author.login`、REST の `user.type` と `user.login` を記録する。CodeRabbit では、GraphQL の `login`（`coderabbitai`）と REST の `login`（`coderabbitai[bot]`）の形が違ったためである。#405 は、この値をもとに設計する。
-   **待つ PR レビュアーを信頼の一覧と分ける:** どの Bot の PR レビューを待つかは、信頼する自動レビュアーの一覧（#405）とは別に定める。REST の名前は直接書かず、`_context.md` から作る（0030 の AC-35 に合わせる）。役割が違うためである。信頼の一覧は「誰のスレッドを処理するか」を決め、待つ PR レビュアーは「何をもってレビュー済みとするか」を決める。

issue の「変更の見込み」は、`.coderabbit.yaml` で CodeRabbit の自動レビューを止める（`auto_review.enabled: false`）変更を、切り替えと同時に行うとしている。本書は、この変更を比較の期間の後に移す（AC-22）。比較の期間は、同じ PR を CodeRabbit にもレビューさせる（下記の決定）ためである。

**要件定義の際に決めたこと（2026-10-21）:**

-   **観測は設計の前に行う:** 要件では、観測の項目と記録の内容を定める。観測そのものは、`02_architecture.md` を書く前に済ませる（F-001・2.4）。試験運用はまだ行っていない。判定の方法は観測の結果で決まるので、観測の前に設計すると書き直しになるためである。
-   **書き込み権限のない人が Codex を動かせるなら、切り替えを進めない:** 試験運用で確かめ、動かせると分かったら、観測の記録に残して止め、設計に進まない（AC-01 の 8・AC-05）。公開リポジトリでは誰でもコメントを書けるので、外部の人が利用者の割り当てを消費できる。さらに、Codex に修正やブランチの作成を依頼できるおそれがあるためである。
-   **比較は同じ PR で両方にレビューさせて行う:** 比較の期間は、同じ PR を CodeRabbit と Codex の両方にレビューさせる（F-004）。同じ変更に対する指摘を並べなければ、見落としを直接比べられないためである。切り替えの後の Codex と過去の CodeRabbit を比べる案と、PR ごとに交互に使う案は採らない。どちらの案も割り当てを二重に使わずに済むが、PR が違うので見落としを比べられないためである。
-   **比較の期間は、マージの前に両方のレビューを待つ:** 比較の期間の `/runpr` は、CodeRabbit と Codex の両方の初回のレビューが済み、両方のスレッドを処理してからマージの質問に進む（F-004）。Codex だけを待つ案は採らない。CodeRabbit の指摘がマージの後に届くと、処理されないまま残るためである。
-   **比較する PR は 5 件:** そのうち、文書だけを変える PR とコードを変える PR を、それぞれ 1 件以上含める（F-004）。種類によって指摘の傾向が違いうるためである。
-   **head を実際にはレビューしなかった PR は、5 件に数えない:** どちらかの Bot がレート制限などで head をレビューしなかった PR は数えず、別の PR で補う（AC-19）。CodeRabbit のレート制限の通知をレビュー済みと数える問題（#394）は残るので、そのような PR を数えると「指摘 0 件」と記録され、比較が歪むためである。
-   **継続は記録を読んで人が判断する:** 比較の記録を読んで人が継続するかを判断し、判断とその理由を記録する（F-005）。数値の基準は事前に決めない。5 件では、基準の値を決める根拠が乏しいためである。
-   **継続しないときは、切り替えの PR を revert して戻す:** 判定の方法は Codex 用の 1 つだけにし、両方の判定の方法を残して切り替えられるようにはしない（F-005）。使わない経路を `runpr.md` に残して保守し続けることになるためである（`CLAUDE.md` の YAGNI）。要件としては戻した後の状態を定め（AC-23）、revert で戻せない部分（その後の変更と衝突する部分）は手で直す。
-   **Codex の自動レビューは使わない:** Codex の個人設定の Automatic review は有効にしない。レビューは `@codex review` の依頼でだけ行う（F-002）。自動レビューが push のたびに走ると（AC-01 の 2）、「PR を開いたときの 1 回だけ」の方針と割り当ての節約が崩れるためである。
-   **`AGENTS.md` は既存のものを更新する:** 新規には作らない。Codex が読む節の見出しは、試験運用で確かめてから決める（F-001・F-006）。`AGENTS.md` はすでにあり、`## Review guidelines` の節を持つ（`AGENTS.md:5`）が、issue は `## Code Review Rules` としているためである。
-   **Codex のレビューが届かないときは止めて報告する:** レート制限の通知や、依頼の後に応答がない場合は、レビュー済みとせず、止めて報告する（F-003）。CodeRabbit に自動で切り替える案は採らない。両方の判定の方法が必要になり、継続しないときの戻し方（revert）の決定と矛盾するためである。
-   **再実行では、依頼済みなら再び依頼しない:** 止まった後に `/runpr` を再実行したとき、そのコミットについて、待つ PR レビュアーへの依頼がすでにあれば、再び依頼しない（AC-15）。再実行のたびに割り当てを消費しないためである。比較の期間に CodeRabbit のレビューだけが届かないときは、利用者が「Codex だけで進め、その PR を比較から外す」を選べる（AC-16）。CodeRabbit を待ち続けるだけでは、マージに進む手段がなくなるためである。
-   **#403 は、判断とその変更の PR で閉じる:** 作業の順序は 2.4 のとおりとし、継続するかの判断と、判断に従う変更（AC-22 か AC-23）を含む PR で #403 を閉じる。issue の完了条件が、比較の結果と継続の判断の記録を含むためである。試験運用の `@codex review` の投稿は、利用者が行う。PR へのコメントはネットワークの操作であり、`CLAUDE.md` の「Tool Execution Safety」で承認が要るためである。
-   **観測と比較の記録はタスクのディレクトリに置く:** 本タスクのディレクトリの下の文書に記録する（F-001・F-004・F-005）。設計と同じ PR の流れでレビューでき、判断の根拠がリポジトリに残るためである。
-   **2 回目以降の PR レビューは、比較の期間も Codex にだけ依頼する:** LAST_REVIEWED（`runpr.md:181-185`）、エスカレーション、マージの質問の「PR レビュー」も、Codex のレビューだけをもとにする（AC-08・AC-17）。比較の対象は、PR を開いたときの同じ head に対する初回のレビューである。2 回目以降まで両方に依頼すると、CodeRabbit の割り当てを使ううえ、比較の対象が PR ごとにそろわなくなるためである。この決定は、issue の「PR レビューを Codex に切り替える」と上の決定から導いたものであり、PR で、レビュアーに確認してもらう点として挙げる。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   Codex の PR レビューの振る舞い（AC-01 の 1〜5 など）を観測して記録し、判定の方法を観測の結果に基づいて決められるようにする。
-   PR レビューを Codex で行い、`/runpr` が初回のレビューの完了を正しく判定できるようにする。
-   同じ PR での CodeRabbit との比較の結果を記録し、継続するかを判断する。

### 2.2. スコープ (In Scope)

-   試験運用での観測と、その記録（F-001）。
-   Codex への PR レビューの依頼（F-002）。
-   Codex のレビュー済みの判定と、レビューが届かないときの停止（F-003）。
-   比較の期間の振る舞いと、比較の記録（F-004）。
-   継続するかの判断の記録と、判断の後の変更（F-005）。
-   文書: `AGENTS.md`・`CLAUDE.md`・`.coderabbit.yaml`・`docs/translation_glossary.md`、および `.claude/commands/` の下のコマンドの文書のうち、PR レビューを行う Bot を名指しするもの（`_context.md`・`runpr.md`・`_lib/task-pr-handoff.md`・`_lib/pr-review-escalation.md`・`fixpr.md`・`mkreq.md` など）（F-006）。

### 2.3. スコープ外 (Out of Scope)

-   ローカルの CLI レビュー（`_lib/coderabbit-local-review.md`）。issue で CodeRabbit のまま残すと決めたためである。
-   信頼する自動レビュアーを複数の名前にすること（`_context.md` の一覧、`fixprguard` の `--reviewer`、文書のガードのテスト）。#405 で行う。
-   CodeRabbit のレート制限の通知を、CodeRabbit のレビュー済みと数えない修正。#394 で行う。比較の期間に CodeRabbit のレビューを待つときは、今の CodeRabbit の判定（`runpr.md:153-185`）をそのまま使う。この問題が比較に与える影響は、AC-19 で抑える。
-   Codex CLI の導入、`codex login`、リポジトリの Codex 連携とコードレビューの有効化。リポジトリの外の設定であり、利用者が行う（issue #403 の「進め方 1」）。
-   エスカレーションの方針の見直し（初回のみの方針をやめること）。Codex の割り当てを実測した後に、別の issue で扱う。

### 2.4. 作業の順序

本タスクは、試験運用と比較という運用の作業を含む。そのため、通常の要件 → 設計 → 計画 → 実装の流れに、次の段階を加える。

1.  本書の承認。
2.  試験運用（F-001）。利用者が Codex の連携を設定し、`@codex review` を依頼して観測する。観測の記録は、本タスクのディレクトリの下の文書として PR にし、マージする。観測の結果が AC-05 に当たれば、本書を `draft` に戻して見直す。
3.  #405 の完了。
4.  設計（`02_architecture.md`）と実装計画（`03_implementation_plan.md`）。
5.  切り替えの PR（F-002・F-003・F-004・F-006 の変更）。マージした時点で、比較の期間が始まる。
6.  比較（F-004）。本タスク以外の PR で行い、比較の記録に追記する。
7.  判断の PR（F-005）。継続するかの判断の記録と、判断に従う変更（AC-22 か AC-23）を含め、#403 を閉じる。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 試験運用での観測と記録

実際の PR で `@codex review` を依頼し、Codex の振る舞いを観測して記録する。この記録が設計の入力になる。

**Acceptance Criteria**:
- **AC-01**: 次の観測の結果が、本タスクのディレクトリの下の文書に記録されている。
    1.  指摘が 0 件のとき、Codex が何を投稿するか（PR レビュー、コメント、リアクションだけ、など）。レビューの途中に何かを投稿するか（受け付けを示すリアクションなど）も含める。
    2.  依頼していない push で、Codex が再びレビューするか（自動レビューが無効のとき）。
    3.  Codex のスレッドの著者の値（AC-03）。
    4.  ステータスコンテキストやチェックランが付くか。付く場合は、名前と状態の値、branch protection に影響するか。
    5.  1 時間あたりに受け付けるレビューの回数と、上限に達したときに投稿される通知の文面。上限に達するまで観測できなければ、観測した範囲の回数と、上限に達しなかったことを記録する。公式文書に通知の文面があれば、URL とともに引用する。
    6.  Codex のレビューの規則として読まれる、`AGENTS.md` の節の見出し。
    7.  依頼からレビューの完了までの時間。
    8.  書き込み権限のないアカウントのコメント（`@codex review` など）で、Codex が動くか。あわせて、Codex の GitHub App をインストールしたリポジトリの範囲と、App の権限。
- **AC-02**: 各観測の記録に、日付と根拠が含まれている。根拠は、API の応答の該当部分、PR の画面で見た内容、公式文書の引用（URL 付き）のいずれかである。PR での観測には、PR の番号と、依頼したコミットの SHA も含める。
- **AC-03**: 指摘が 1 件以上あるレビューについて、スレッドの最初のコメントの著者の値として、GraphQL の `author.__typename` と `author.login`、REST の `user.type` と `user.login` が記録されている。
- **AC-04**: 指摘が 0 件のレビューと 1 件以上のレビューを、それぞれ 1 回以上観測している。
- **AC-05**: 次のいずれかに当たる場合は、その点が記録に挙げられ、本書の該当する要件が見直されて再び承認されるまで、設計を始めない。
    -   観測の結果が本書の要件と矛盾する（例: 自動レビューが無効でも push のたびにレビューされる。Codex のスレッドの著者が `Bot` でない）。
    -   指摘が 0 件のレビューの完了を、レビューがない状態と区別できる印がない。または、その印をコミットと対応づけられない（AC-09 を満たせない）。
    -   指摘が 0 件のレビューか、1 件以上のレビューを観測できなかった（AC-04 を満たせない）。
    -   書き込み権限のないアカウントのコメントで Codex が動く（AC-01 の 8）。

#### F-002: Codex への PR レビューの依頼

PR レビューは、Codex に `@codex review` で依頼する。

**Acceptance Criteria**:
- **AC-06**: PR を開いた後、Codex に `@codex review` のコメントでレビューが依頼される。PR を開くのは、`/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2`・`/runplan` と、単独の変更で PR を作るときの `/runpr` である。
- **AC-07**: 依頼していない push で、Codex のレビューは走らない。Codex の個人設定の Automatic review は有効にしない。
- **AC-08**: `/runpr` が 2 回目以降の PR レビューを依頼するとき（エスカレーションの判断が `request` のとき、または利用者が依頼を選んだとき）は、`@codex review` で Codex に依頼する。比較の期間も、2 回目以降の依頼は Codex にだけ行う。

#### F-003: Codex のレビュー済みの判定

`/runpr` は、Codex が依頼されたコミットのレビューを完了したことを確かめてから、そのコミットをレビュー済みとする。

**Acceptance Criteria**:
- **AC-09**: あるコミットに対して Codex が完了の印を投稿したときだけ、そのコミットはレビュー済みと判定される。完了の印は、指摘のあるレビューのものでも、指摘が 0 件のレビューのものでもよい。指摘が 0 件のときに何を完了の印とするかは、AC-01 の 1 の観測で決める。
- **AC-10**: レビュー済みの判定は、依頼したコミットについて行う。依頼の後に `/fixpr` の push で head が動いても、依頼したコミットに完了の印があれば、その依頼はレビュー済みになる。LAST_REVIEWED（`runpr.md:181-185`）は、Codex がレビュー済みのコミットのうち、ほかのすべてを祖先に持つものである。
- **AC-11**: 次のものは、レビュー済みの判定に使われない。
    -   著者の種類が `Bot` でないか、`login` が `_context.md` に定めた待つ PR レビュアー（AC-25）と一致しない投稿。名前が同じ `User` のアカウントの投稿も含む。
    -   依頼したコミット以外のコミットに対する完了の印。
    -   レート制限の通知とエラーの通知（AC-01 の 5 で観測した文面、または公式文書の文面）。
- **AC-12**: 待っている依頼のコメントより後に、待つ PR レビュアーが次の 4 種のいずれにも当たらない投稿をしたとき、`/runpr` はレビュー済みとせず、待ち続けずに止めて、投稿の URL と内容の要約を報告する。4 種とは、依頼したコミットに対する完了の印、AC-01 の 1 でレビューの途中の投稿と確かめたもの、すでに受け入れたレビューに属するコメントや返信、ほかのコミットに対する完了の印（AC-11 のとおり使わない）である。レート制限の通知とエラーの通知は、いずれにも当たらない投稿の例である。
- **AC-13**: 依頼から設計で定めた時間（AC-01 の 7 の観測をもとに決める）がたっても、依頼したコミットがレビュー済みにならなければ、`/runpr` は止め、Codex が最後に投稿したもの（なければ、投稿がないこと）を報告する。
- **AC-14**: AC-12・AC-13 で止まったとき、`/runpr` はマージの質問に進まない。
- **AC-15**: 止まった後に `/runpr` を再実行したとき、そのコミットについて、待つ PR レビュアーへの依頼が利用者（`gh` で認証したアカウント）のコメントとしてすでにあれば、再び依頼しない。その依頼に対する完了の印を待つ。

#### F-004: 比較の期間

比較の期間は、同じ PR を CodeRabbit と Codex の両方にレビューさせ、結果を比較の記録に残す。

**Acceptance Criteria**:
- **AC-16**: 比較の期間に開いた PR では、CodeRabbit と Codex の両方が、PR を開いたときの head をレビューする。CodeRabbit が自動でレビューしなければ、PR を開くコマンドが `@coderabbitai review` で依頼する（今の `_lib/task-pr-handoff.md:116-121` と同じ）。比較の期間の `/runpr` は、両方の初回のレビューが済み、両方が開いたスレッドの処理が済むまで、マージの質問に進まない。CodeRabbit のレビューが届かずに止まったときは（`runpr.md:192-196` と同じ）、再実行の際に、利用者が「Codex だけで進め、その PR を比較から外す」を選べる。
- **AC-17**: LAST_REVIEWED、エスカレーション（`_lib/pr-review-escalation.md`）、マージの質問の「PR レビュー」（`runpr.md:282-286`）は、比較の期間も、Codex のレビューだけをもとにする。
- **AC-18**: 比較の期間は、切り替えの PR のマージで始まり、判断の PR（F-005）のマージで終わる。判断の PR は、AC-19 の条件を満たす 5 件の PR がマージされた後に開く。比較の期間の後は、`/runpr` は CodeRabbit の PR レビューを待たない。
- **AC-19**: 比較の記録は、比較の期間にマージした 5 件の PR を含む。そのうち、文書だけを変える PR とコードを変える PR が、それぞれ 1 件以上ある。次の PR は 5 件に数えない。どちらかの Bot が、PR を開いたときの head を実際にはレビューしなかった PR（レート制限、エラー、AC-16 で比較から外した PR）と、マージせずに閉じた PR である。本タスクの PR（判断の PR を含む）も数えない。比較の期間に開き、比較の期間の後にマージした PR も数えない。記録には、数えなかった PR とその理由も残す。
- **AC-20**: 比較の対象は、PR を開いたときの head に対する、各 Bot の初回のレビューの指摘だけである。指摘には、スレッドの指摘と、スレッドにならずにレビューの本文にだけ書かれた指摘（CodeRabbit の nitpick など）の両方を含め、両者を分けて数える。比較の記録は、PR ごとに次のものを含む。
    -   PR の番号と種類（文書かコードか）。
    -   Bot ごとの指摘の数と、その内訳。内訳は、`/fixpr` で修正したもの、`/fixpr` で妥当でないと返信したもの（誤検知）、保留（deferred）にしたもの、その他である。レビューの本文にだけ書かれた指摘は、記録を書く人が同じ区分で判定する。
    -   片方の Bot だけが挙げた、修正したか保留にした指摘（もう片方の見落とし）の一覧。各項目に、指摘の URL と重大度（CodeRabbit の重大度、または Codex の P0・P1）を付ける。Codex は P0・P1 しか投稿しないので、CodeRabbit の指摘のうち P0・P1 に当たらないものは、Codex の見落としと数えない。CodeRabbit の重大度と P0・P1 の対応は、設計で決める。
    -   Bot ごとの、PR を開いてから初回のレビューが完了するまでの時間。
    -   Bot ごとの、依頼の回数と、レート制限に達したかどうか。

#### F-005: 継続の判断と、その後の変更

比較の記録を読んで人が継続するかを判断し、判断に従って比較の期間を終える。

**Acceptance Criteria**:
- **AC-21**: 継続するかの判断、判断した人、日付、理由が、本タスクのディレクトリの下の文書に記録されている。理由は、比較の記録（AC-20）の項目を根拠に挙げる。比較の記録のうち、記録を書いた人が判定した箇所（同じ指摘かどうか、誤検知かどうか、レビューの本文にだけ書かれた指摘の区分）は、判断した人が確かめている。
- **AC-22**: 継続すると判断した後は、PR を開いても CodeRabbit の PR レビューは走らない（`.coderabbit.yaml` で自動レビューを止める）。`.claude/commands/` の下のコマンドの文書には、`@coderabbitai review` の依頼も、CodeRabbit の PR レビューを待つ手順も残らない。`.coderabbit.yaml` のコメントは、PR レビューを行わない理由を説明する。
- **AC-23**: 継続しないと判断した後は、PR レビューの依頼と待ちが CodeRabbit だけで行われる。`.claude/commands/` の下のコマンドの文書・`CLAUDE.md`・`AGENTS.md` は、Codex を PR レビューを行う Bot として名指ししない。`_context.md` の待つ PR レビュアー（AC-25）は CodeRabbit である。

#### F-006: 文書

**Acceptance Criteria**:
- **AC-24**: 判断の PR のマージまで、`.claude/commands/` の下のコマンドの文書（コマンドの `description` を含む）と `CLAUDE.md` は、PR レビューを行う Bot を Codex として説明する（比較の期間は Codex と CodeRabbit の両方）。判断の PR の後は、AC-22 か AC-23 に従う。ローカルの CLI レビューを CodeRabbit と呼ぶ記述は残る。
- **AC-25**: `/runpr` がどの Bot の PR レビューを待つかは、`.claude/commands/_context.md` の 1 か所で定められている。この値は、信頼する自動レビュアーの一覧（#405）とは別の項目である。`runpr.md` と `_lib/task-pr-handoff.md` は、REST の名前（例: `chatgpt-codex-connector[bot]`）を直接書かず、その値を参照する。
- **AC-26**: `AGENTS.md` の、Codex がレビューの規則として読む節（AC-01 の 6 で確かめた見出し）に、レビューの規則がある。その節は、`CLAUDE.md` の規則を写さず、参照する。この変更は切り替えの PR に含め、比較の期間の途中では `AGENTS.md` のレビューの規則を変えない。CodeRabbit も `AGENTS.md` を読むので、期間の途中で変えると、比較の条件が PR ごとにそろわなくなるためである。
- **AC-27**: `docs/translation_glossary.md` に、本書で用いる「割り当て」（quota）・「指摘」（finding）・「スレッド」（thread）が載っている。
- **AC-28**: `make test`・`make lint` と、CI の `doc-guard` のジョブが通る。
- **AC-29**: コマンドが PR に投稿する文面（`/fixpr` の返信、PR のコメントなど）は、レビューの依頼そのもの（AC-06・AC-08・AC-16）を除いて、`@codex` のメンションを含まない。スレッドの本文を引用する返信でも同じである。利用者のアカウントで投稿された `@codex` のメンションは、Codex に修正やブランチの作成をさせうるためである。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   N/A。比較の期間に、待つ時間が CodeRabbit と Codex のうち遅い方に合わせて長くなることは、F-004 で受け入れる。

### 4.2. セキュリティ (Security)

本タスクは、ネットワークへの送信（Codex の GitHub 連携がリポジトリの内容を読む）と、信頼できない入力（GitHub API が返す、Codex やほかのアカウントの投稿）の扱いに関わる。`docs/dev/security.md` の観点から、次を要件とする。

-   **外部の人が Codex を動かせるなら進めない:** 書き込み権限のないアカウントのコメントで Codex が動くと分かったら、切り替えに進まない（AC-01 の 8・AC-05）。
-   **コマンドの投稿で Codex を動かさない:** コマンドが PR に投稿する文面のうち、`@codex` のメンションを含むのはレビューの依頼だけである（AC-29）。`/fixpr` の返信は、信頼できないスレッドの本文をもとに書かれるので、本文に含まれるメンションを写すと、利用者のアカウントから Codex に修正やブランチの作成を依頼することになるためである。
-   **Codex のスレッドの本文は信頼できないデータとして扱う:** Codex のスレッドは、#395（タスク 0030）の対策と同じく、信頼できない入力として扱う。本文はデータとしてプロンプトに渡し、変更の範囲を確かめる。Codex を信頼する自動レビュアーに加えるのは #405 で行い、本タスクでは信頼の判定を変えない。
-   **完了の印の受け入れ:** レビュー済みの判定は、GitHub API の応答という信頼できない入力を読む。境界の要件は次のとおりである。
    -   **受け入れる形:** 著者の種類が `Bot` で、`login` が待つ PR レビュアー（AC-25）と一致する投稿のうち、AC-01 の 1 で定めた完了の印の形をとり、対象のコミットの SHA（40 桁の 16 進数）が依頼したコミットの SHA と一致するものだけを受け入れる（AC-09〜AC-11）。
    -   **それ以外:** 値の欠け、形の違い、想定外の投稿は、補って受け入れず、「レビュー済みでない」とする。待つ PR レビュアーの想定外の投稿があれば、止めて報告する（AC-12）。ほかのアカウントの投稿は、完了の印に似た文面を含んでいても使わない。公開リポジトリでは誰でもコメントを書けるためである。
    -   **ページ送り:** 判定に使う一覧（PR レビュー、コメント）は、ページを最後まで読む。途中のページで打ち切ると、完了の印や通知を見落とすためである。
    -   **使うメンバーと上限:** 使うのは、投稿の著者（種類と `login`）、完了の印の形、対象のコミットの SHA だけである。応答のほかのメンバーは、GitHub が増やしうるので拡張可能として無視する。件数とサイズの上限は N/A とする。読むのは 1 つの PR の一覧で、今の `runpr.md:167-178` と同じく GitHub のページ送りに従うためである。
    -   **センチネルエラー:** N/A。判定はコマンドの文書（エージェントへの手順）で行い、Go のコードを持たないためである。拒否の結果は、「レビュー済みでない」とすることか、止めて報告することである。
-   **送るのは公開されている内容だけ:** Codex の GitHub 連携が読むのは、公開リポジトリの PR の内容である。秘密（`DEEPSEEK_API_KEY`・`ANTHROPIC_API_KEY`・`SLACK_WEBHOOK_URL`）をコミットしない規則（`CLAUDE.md` の「Development Notes」）は変わらない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   Codex のレビューが届かないときは、レビュー済みとせず止めて報告する（AC-12〜AC-14）。CodeRabbit への自動の切り替えはしない。
-   再実行で依頼を重ねない（AC-15）。
-   Codex の割り当てが尽きて止まったとき、利用者は割り当ての回復を待って `/runpr` を再実行する。待たずに手でマージした PR は、比較の期間なら 5 件に数えない（AC-19）。
-   比較の期間には、CodeRabbit の判定の既知の問題（レート制限の通知をレビュー済みと数える。#394）が残る。比較の期間の `/runpr` は CodeRabbit のレビューも待つので、この問題の影響を受ける。比較の記録への影響は AC-19 で抑え、#394 の修正は本タスクの範囲外とする（2.3）。

### 4.4. 互換性 (Compatibility)

-   ローカルの CLI レビュー（`coderabbit review`）の手順は変えない。
-   `/fixpr` のラウンド上限（`fixpr.md:42-49`）は、Codex のスレッドにも同じく働く。これは、Codex のスレッドの著者が `Bot` であることを前提にする（AC-01 の 3 で確かめる。違えば AC-05）。

### 4.5. 保守性 (Maintainability)

-   待つ PR レビュアーは 1 か所で定める（AC-25）。
-   判定の方法は Codex 用の 1 つだけにする。CodeRabbit の PR レビューの依頼と待ちは、比較の期間が終われば、コマンドの文書から消える（AC-22）。継続しないときは revert で戻す（AC-23）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   F-002 から F-006 は #405 の完了を前提にする。F-001 は前提なしに行える（2.4）。
-   Codex の GitHub 連携には ChatGPT のプランが必要である。API キーの契約では使えない（issue #403）。Codex の割り当ては、利用者のほかの Codex の利用（CLI など）と共有されうる。そのため、比較の記録では、割り当ての消費を依頼の回数で表す（AC-20）。
-   Codex の連携と設定（リポジトリの連携、コードレビューの有効化、Automatic review を無効のままにすること）は、リポジトリの外の設定であり、利用者が行う。
-   エスカレーションの方針（`_lib/pr-review-escalation.md`）は、Codex の割り当てを実測するまで残す（issue #403）。

## 6. 用語集 (Glossary)

-   **PR レビュー**: 自動レビュアーが GitHub の PR 上で行うレビュー。ローカルの CLI レビューと区別する。
-   **ローカルの CLI レビュー**: `coderabbit` CLI でローカルの差分をレビューすること（`_lib/coderabbit-local-review.md`）。本タスクでは変えない。
-   **割り当て**: 自動レビュアーが一定時間に受け付けるレビューの回数の上限（英語では quota）。`docs/translation_glossary.md` の「枠」（slot）は localhost サーバの同時処理数の単位であり、別の概念なので本書では使わない。
-   **指摘**: レビューが挙げる個々の問題。スレッドとして投稿されるものと、レビューの本文にだけ書かれるものがある。
-   **スレッド**: PR のファイル・行に紐づくレビューコメントの連なり。`/fixpr` が処理する単位である。
-   **完了の印**: 待つ PR レビュアーが、あるコミットのレビューを完了したことを示す投稿（AC-09）。何を印とするかは、AC-01 の 1 の観測で決める。
-   **レビュー済み**: 待つ PR レビュアーが、依頼されたコミットについて完了の印を投稿した状態（`runpr.md` の「Reviewed」）。
-   **待つ PR レビュアー**: `/runpr` がレビュー済みの判定に使う Bot。信頼する自動レビュアーの一覧（#405）とは別に定める（AC-25）。
-   **比較の期間**: 同じ PR を CodeRabbit と Codex の両方にレビューさせる期間。切り替えの PR のマージで始まり、判断の PR のマージで終わる（AC-18）。
-   **切り替えの PR**: F-002・F-003・F-004・F-006 の変更を入れる PR（2.4 の 5）。
-   **判断の PR**: 継続するかの判断の記録と、判断に従う変更を入れる PR（2.4 の 7）。
-   用語は `docs/translation_glossary.md` と統一する。
