# 設計への申し送り：ブラウザ拡張からサーバへの送信と結果の表示

本書は、[01_requirements.md](01_requirements.md) の起草（とレビュー）で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 送信を行う場所と、送信中にポップアップを閉じた場合

-   **事項:** ポップアップの送信のボタンから送るとき、`fetch` をポップアップで行うか、service worker に依頼するかを決める。送信中に利用者がポップアップを閉じた場合（ポップアップはほかの場所をクリックすると閉じる）に、送信を続けるか、結果をどこに示すかを決める。
-   **理由:** ポップアップを閉じるとそのページは破棄され、ポップアップの中の `fetch` も中断される。本文を送り終えた後に中断された場合、サーバはジョブを続けるが、拡張は結果を示せない。service worker で送れば閉じても送信は続くが、結果を示す場所（結果のウィンドウ、アイコンのバッジなど）が別に要る。どちらの場合も、自動で再送してはならない（F-005）。0007 §3.12.1 の観測では、service worker とポップアップのどちらから送っても `Origin` は同じだった。
-   **候補の方針:** 右クリックメニューの経路は service worker から送るので、ポップアップも service worker に依頼して送信の処理を 1 つにする（AC-21）。ポップアップが開いている間は結果をポップアップに示し、閉じられていれば結果のウィンドウ（右クリックメニューの経路と同じ）に示す。service worker が送信中に停止しないことも確かめる（Manifest V3 の service worker は、拡張の API のイベントや `fetch` が続いている間の扱いに注意が要る）。
-   **関連:** F-003、F-005、AC-20、AC-21、AC-22

## H-02: 「結果が分からない」の検出と区別

-   **事項:** `fetch` の失敗（`TypeError`）、時間の上限（`AbortSignal.timeout` など）、応答の本文の読み込みの失敗を、どう検出して「結果が分からない」に分類するかを決める。接続の拒否（サーバが起動していない）と、送信後の切断を区別できるかを確かめる。
-   **理由:** ブラウザの `fetch` は、接続の拒否も送信途中の切断も同じ `TypeError`（`Failed to fetch`）にする。区別できないなら、「サーバに接続できない」と表示すると、実際には処理されている場合に利用者が再送して二重に投稿する。要件（F-007）は区別しないことを既定とする。
-   **候補の方針:** 区別しない。表示では「サーバが起動していない可能性」と「処理されている可能性」を両方示し、送り直す前に Slack を確かめるよう案内する。区別できる手段が見つかった場合は、`02_architecture.md` に観測の結果を書いて、要件の変更として扱う。
-   **関連:** F-003、F-007、AC-26、AC-27

## H-03: 送信の時間の上限

-   **事項:** 送信の時間の上限の値を決める。
-   **理由:** サーバは本文の読み込み（`ReadTimeout` 30 秒）・検査・#107 の解析の後に応答を書き、全体を `WriteTimeout` 60 秒で抑える（API の設計書 §3.5.1）。拡張の上限が短すぎると、受理されたリクエストを「結果が分からない」として示し、利用者の再送を招く。長すぎると、応答のないサーバを長く待つ。
-   **候補の方針:** サーバの `WriteTimeout`（60 秒）より少し長い値にする。サーバの応答は、本文の解析が終わり次第返る（生成を待たない）ので、通常は 1 秒以内である。
-   **関連:** F-003、4.3

## H-04: 応答の本文の厳格な解析

-   **事項:** 応答の本文を、要件 3.2 の受理する形（メンバの重複・無効な UTF-8・対になっていないサロゲートのエスケープ・余分なメンバ・型の違いを拒否）で検査する方法と、本文の大きさの上限の値と適用の方法を決める。
-   **理由:** `JSON.parse` は重複したメンバを後の値で黙って上書きし、`Response.text()` は無効な UTF-8 を U+FFFD に置き換える（エラーにしない）。応答は本物のサーバが返すとは限らない（API の設計書 §5.4）。サーバの Go 側は `internal/strictjson` で同じ問題を扱っているが、拡張は Go のコードを使えない。
-   **候補の方針:** `Response.arrayBuffer()` で読み、上限（数 KiB。正当な応答は 100 バイト程度）を超えたら想定外の応答とする。`TextDecoder` の `fatal: true` で無効な UTF-8 を拒否する。重複したメンバは、`JSON.parse` の結果からも `reviver` からも検出できない（`JSON.parse` は重複した名前の前の値を、`reviver` に渡す前に捨てる。そのため `{"status":"accepted","status":"rejected",...}` は受理されてしまう）。受理する形は 2〜3 個の文字列のメンバだけを持つ平らなオブジェクトなので、復号した本文の文字列を小さな厳格な字句の走査で調べ、同じメンバ名が 2 回現れたら拒否する方法を、`JSON.parse` の結果の形の検査と組み合わせて使う。上限を超える応答の読み込みを打ち切る方法（ストリームで読むか）も決める。
-   **関連:** F-006、F-007、3.2、AC-25、AC-28、AC-29

## H-05: 結果のウィンドウと表示用の値の受け渡し

-   **事項:** 右クリックメニューの経路で、送信中の表示と送信の結果をどう示すか（結果のウィンドウを送信の前に開いて状態を更新するか、送信の後に開くか）と、`chrome.storage.session` で結果のウィンドウへ渡す値の形（0007 の `OutcomeSummary` を拡張するか、別の型にするか）を決める。
-   **理由:** 0007 の結果のウィンドウは、収集した内容の要約を受け取って表示する。#111 では送信の結果を表示する（F-005）。送る値の全体（選択範囲の全文）や共有トークンを、表示のために保存先へ渡してはならない（AC-32）。送信の前にウィンドウを開くと送信中を示せるが、状態の更新の仕組みが要る。
-   **候補の方針:** 表示用の値は、結果の分類・`requestId`・状態コード・収集した内容の要約だけを持つ型にし、0007 の `parseSummary` と同じく、読み出す側で形を厳格に検査する。
-   **関連:** F-005、F-006、AC-18、AC-22、AC-32

## H-06: 設定の保存と読み出しの形

-   **事項:** `chrome.storage.local` のキーの名前、保存する値の形（トークンとポートを 1 つのオブジェクトにまとめるか、別のキーにするか）、読み出した値の検査、オプションページの入力欄の表示の形（`type="password"` など）を決める。
-   **理由:** 保存先は、オプションページ以外（開発者のコンソール、将来の版の拡張）から書き換えられうる。読み出した値を補正せずに検査し、合わなければ送らない（F-004、AC-15、AC-15b）。
-   **候補の方針:** 読み出しは、オプションページの入力の検証と同じ関数で検査する。ポートが欠落していれば `8765`、存在して形が合わなければ「ポートの設定が正しくない」として送らない（F-004）。
-   **関連:** F-001、F-004、AC-01〜AC-06、AC-15、AC-15a、AC-15b

## H-07: manifest の変更と既存のガードのテスト

-   **事項:** `host_permissions` と `options_ui`（または `options_page`）の宣言の形、`minimum_chrome_version` を上げる必要があるか、既存の manifest のガードのテスト（`extension/test/manifest.test.ts`）と `security.md` の権限の記述の同期を決める。
-   **理由:** 0007 の AC-26 は、manifest の権限が設計書に挙げたものと一致することをテストで確かめている。権限を加えると、テストと文書を同時に改める必要がある。0007 の設計書 3.1 は `options_ui` を「#111 で宣言する」としている。
-   **候補の方針:** `host_permissions: ["http://127.0.0.1/*"]` と `options_ui`（`open_in_tab` の要否を含む）を宣言し、ガードのテストの期待値を改める。
-   **関連:** 4.2、AC-31
