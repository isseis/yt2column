## 1. 概要 (Overview)

**目的:** 本書は、ブラウザ拡張が、収集した字幕と動画ページの URL を localhost のサーバへ送り、サーバの応答を利用者に示す部分の要件を定義する。共有トークンとポートの設定画面と保存も含む。

**背景:**
`yt-dlp` による字幕の取得は、YouTube から HTTP 429 を繰り返し受けることがある。そこで、利用者が YouTube の「文字起こしを表示」パネルで選択した字幕を、ブラウザ拡張が localhost のサーバへ送り、サーバが記事を生成して Slack へ投稿する（[#43](https://github.com/isseis/yt2column/issues/43)）。

ブラウザ拡張（[#105](https://github.com/isseis/yt2column/issues/105)）は、API に依存しない骨格と入力の収集（[#110](https://github.com/isseis/yt2column/issues/110)、タスク `0007_browser_extension_skeleton`、完了）と、本タスク（[#111](https://github.com/isseis/yt2column/issues/111)）に分かれている。サーバと HTTP API は [#109](https://github.com/isseis/yt2column/issues/109)（タスク `0011_localhost_server`）が定義し、実装した。本タスクは、`0011_localhost_server/02_architecture.md`（以下「API の設計書」）の §3.4 と §9 に従って送信する。

現在の拡張は、右クリックメニューとツールバーのアイコン（ポップアップ）の 2 つの起動の手段を持ち、選択範囲の文字列・タブの URL・タブのタイトルを収集して表示するだけで、ネットワークにアクセスしない。0007 の要件書は、#111 での振る舞いを次のように定めている。

-   **右クリックメニュー:** 送る意図がはっきりしているので、確認を挟まずに送る。
-   **ツールバーのアイコン:** ポップアップに送信のボタンを加え、内容を確かめてから送る。

API の設計書 §9 は、拡張に次を求めている。

-   `POST http://127.0.0.1:8765/articles` に、`Origin`・`Authorization: Bearer <共有トークン>`・`Content-Type: application/json`（完全一致）を付けて送る。
-   manifest の `host_permissions` に `http://127.0.0.1/*` を宣言する（宣言しないと preflight になり、サーバは `OPTIONS` を `405` で拒否する）。
-   オプションページでトークンを受け取るとき、`^[0-9a-f]{64}$` に一致することを確かめ、前後の空白・改行を含む値を保存しない。
-   応答を受け取れないネットワークの誤りは「結果が分からない」として表示し、自動で再送しない。サーバは `202` が届かなくてもジョブを続けるので、再送すると記事が二重に投稿される。
-   送信中は送信のボタンを無効にする。
-   応答の `requestId` を表示する。利用者がサーバのログと Slack の通知を照合するのに使う。

本タスクで次のことを決める。

-   **生成・投稿の結果の表示（#111 の「決めること」）:** 拡張は、サーバが受け付けたこと（`202`）までを表示する。生成と投稿の結果（成功・失敗）は Slack だけで知らせ、拡張は表示しない。サーバは `202` の後の結果を返す API（ポーリング、進捗の通知）を持たない（API の要件書 2.3）。拡張は、受け付けたときに「結果は Slack に届く」ことと `requestId` を示す。
-   **共有トークンの受け渡しと保存先:** 利用者がサーバの起動時に表示されたトークンを拡張のオプションページに貼り付け、拡張は `chrome.storage.local` に保存する（0007 §3.12.3 の候補のうち、ブラウザを再起動しても貼り直さずに済むもの）。`chrome.storage.sync` は使わない（トークンがブラウザの外へ出るため）。
-   **送る値:** `videoUrl` に収集したタブの URL を、`transcript` に収集した選択範囲の文字列を、どちらも補正せずに入れる。タブのタイトルは `title` に入れない。API の `title` は動画タイトルで、タブのタイトルではないためである（API の要件書 F-002）。任意の 3 フィールド（`title`・`channelName`・`description`）は、本タスクでは値を持たないので送らない。値を DOM から取る処理は [#170](https://github.com/isseis/yt2column/issues/170) が加える。#170 が送信のクライアントを変更せずに済むよう、送信のクライアントは任意の 3 フィールドを受け取れる形にする（F-002）。
-   **ポート:** 既定値はサーバと同じ `8765` とし、オプションページで変更できるようにする。サーバは `YT2COLUMN_SERVER_PORT` でポートを変えられ（API の設計書 §3.2.2）、拡張に別のポートを設定する手段は #111 で決めることになっている。

**本書の記述範囲:** 本書は、観測できる振る舞い（何を送り、何を送らず、利用者に何を示すか）を定める。実現の手段（送信を行う場所、モジュールの分け方、表示の正確な文言と書式、タイムアウトの値、テストの手段など）は設計（`02_architecture.md`）で決める。要件のレビューで挙がった、設計で決める事項は [design_handoff.md](design_handoff.md) に申し送る。

対応 issue: #111（親: #105、#43）

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   YouTube の動画ページで字幕を選択し、右クリックメニューまたはポップアップの送信のボタンから送ると、サーバが記事を生成して Slack へ投稿する。
-   サーバに接続できないとき、サーバが拒否したときに、利用者がその理由と次の操作を知ることができる。
-   応答を受け取れなかった場合に、拡張が自動で再送せず、利用者にも「結果が分からない」ことを示して、記事の二重の投稿を避ける。
-   共有トークンを、利用者が一度貼り付ければ使い続けられる。トークンは拡張の外へ、サーバへの送信以外で出ない。
-   拡張が API キーと Webhook URL を持たず、扱わない。

### 2.2. スコープ (In Scope)

-   API の設計書 §3.4 に従ったリクエストの組み立てと送信（F-002・F-003）。
-   送る前の確認の追加: 共有トークンの未設定、送る本文の大きさの上限（F-004）。
-   右クリックメニューからの送信と、ポップアップの送信のボタン（F-005）。
-   応答の解釈と表示: 受付、拒否の理由ごとの表示、結果が分からない場合、想定外の応答（F-006・F-007）。
-   オプションページ: 共有トークンとポートの入力・検証・保存（F-001）。
-   manifest への `host_permissions`（`http://127.0.0.1/*`）とオプションページの追加（4.2）。
-   文書: README（オプションページの設定、送信の使い方）、`security.md` §8 の拡張に関する記述（F-008）。

### 2.3. スコープ外 (Out of Scope)

-   生成・投稿の結果（成功・失敗）の拡張での表示、結果のポーリング、進捗の通知。結果は Slack だけで知らせる（1. 概要）。
-   任意の 3 フィールド（`title`・`channelName`・`description`）の値を DOM から取ること（#170）。
-   サーバと API の変更（#109 で完了）。本タスクは API の設計書 §3.4 に従い、サーバ側を変更しない。
-   収集と既存の送る前の確認（0007 F-005）の変更。拒否の理由（対象外のページ、収集の失敗、選択範囲が空、タイトルが空）と、その順序はそのまま使う。タブのタイトルは送らないが、確認の対象として残す（収集の部分を変更しない。0007 4.5）。
-   応答を受け取れなかった場合の自動の再送と、送った内容の再送のための保存。
-   同じ動画を二重に送ることの検出（サーバにもその仕組みはない。API の設計書 §5.4）。
-   サーバの認証（サーバが本物であることの確認）。同じマシンの他の利用者がポートを先に使うリスクは、API の設計書 §5.4 のとおり受け入れる。
-   `127.0.0.1` 以外のホスト（`localhost`・`[::1]`・他のマシン）への送信。
-   サーバの起動・停止の拡張からの操作、サーバの状態の常時の表示。
-   送信の履歴の保存と表示。
-   表示する文言の多言語化。Chrome と Brave 以外のブラウザ（0007 2.3 と同じ）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: オプションページ（共有トークンとポートの設定）

-   拡張にオプションページを設ける。利用者は、拡張の管理ページ（またはポップアップの案内、F-004）から開く。
-   オプションページで、共有トークンとポートを入力して保存できる。
-   **共有トークン:** 入力値が `^[0-9a-f]{64}$` に完全に一致するときだけ保存する。前後の空白・改行を含む値、大文字の 16 進、長さの異なる値は、取り除いたり変換したりせずに拒否し、理由を示す（CLAUDE.md「Reject, don't normalize」）。
-   **ポート:** 10 進の数字だけからなり、先頭が `0` でない、`1024`〜`65535` の整数のときだけ保存する（サーバの `YT2COLUMN_SERVER_PORT` の受理する形と同じ。API の設計書 §3.2.2）。未設定のときは `8765` を使う。
-   拒否した入力は保存せず、それまでに保存した値を変更しない。
-   保存した共有トークンは、オプションページを開き直したときに値そのものを表示しない。設定済みかどうかだけを示す。入力中の値も、画面の共有などで読み取られにくい形で表示する（具体的な形は設計で決める）。
-   保存した共有トークンを消去できる。
-   共有トークンとポートは `chrome.storage.local` に保存する。`chrome.storage.sync` には保存しない。

**Acceptance Criteria**:
- **AC-01**: 小文字の 16 進 64 文字のトークンを入力して保存すると、保存される。オプションページを開き直すと、トークンが設定済みであることが示され、トークンの値は表示されない（ユニットテストで保存と表示を、手動で開き直しを確かめる）。
- **AC-02**: 次のトークンの入力はそれぞれ拒否され、保存されず、それまでに保存した値が変わらない: 空文字列、63 文字、65 文字、大文字を含む 64 文字、`g` を含む 64 文字、前に空白を付けた 64 文字、末尾に改行を付けた 64 文字、全角の英数字を含むもの（ユニットテスト）。
- **AC-03**: 次のポートの入力はそれぞれ拒否され、保存されない: 空文字列、`0`、`80`、`1023`、`65536`、`08765`、`+8765`、` 8765`、`8765 `、`0x2235`、`8765.0`。`1024`・`8765`・`65535` は保存される（ユニットテスト）。
- **AC-04**: ポートを保存していない状態で送ると、`8765` へ送る（ユニットテスト）。
- **AC-05**: 保存した共有トークンを消去すると、次の送信は F-004 の「共有トークンが未設定」で止まる（ユニットテスト）。
- **AC-06**: 共有トークンが `chrome.storage.local` に保存され、`chrome.storage.sync` に書き込まれない（ユニットテストで fake の保存先を確かめる）。

#### F-002: 送る本文の組み立て

-   本文は、API の要件書 F-002 の JSON のオブジェクト 1 つとする。
-   `videoUrl` は、収集した URL（0007 F-005）を補正せずに入れる。`t`・`list` などのパラメータもそのまま残し、正規化はサーバに任せる。
-   `transcript` は、収集した選択範囲の文字列を補正せずに入れる。改行、前後の空白、空行を保つ。
-   送信のクライアントは、任意の 3 フィールド（`title`・`channelName`・`description`）の値を受け取れる。値がない、または空文字列のフィールドは、本文から省略する（`null` も空文字列も送らない）。本タスクでは呼び出し側が値を渡さないので、本文は `videoUrl` と `transcript` の 2 つのメンバだけになる。
-   タブのタイトルを本文に入れない。
-   本文に、宣言したメンバ以外のメンバを入れない。共有トークンを本文に入れない。
-   本文は、`collect`（0007）の確認を通った入力からだけ組み立てられる（確認を通っていない値を送れないことを型で保証する。0007 の設計書 3.2）。

**Acceptance Criteria**:
- **AC-07**: 収集した入力から組み立てた本文を JSON として解析すると、ちょうど `videoUrl` と `transcript` の 2 つのメンバを持ち、それぞれの値が収集した URL・選択範囲の文字列と一致する。選択範囲の前後の空白・空行・`\r\n` の改行・全角空白・サロゲートペアの文字が保たれる。URL の `t`・`list` のパラメータとフラグメントが保たれる（ユニットテスト）。
- **AC-08**: 任意の 3 フィールドに値を渡すと本文に含まれ、空文字列を渡す、または渡さないと本文に含まれない（`null` のメンバも現れない）（ユニットテスト）。
- **AC-09**: 本文に、タブのタイトルと共有トークンが含まれない（ユニットテスト。タイトルとトークンに識別できる文字列を使い、本文の文字列に現れないことを確かめる）。

#### F-003: リクエストの送信

-   送信先は `http://127.0.0.1:<ポート>/articles` とする。ポートは F-001 で保存した値、なければ `8765`。
-   メソッドは `POST`、ヘッダは `Content-Type: application/json`（引数を付けない）と `Authorization: Bearer <共有トークン>` とする。`Origin` はブラウザが付ける。
-   リダイレクトを辿らない。リダイレクトの応答は、F-007 の「想定外の応答」として扱う。
-   cookie などの資格情報を送らない。
-   送信には有限の時間の上限を設ける。上限までに応答が完了しない場合は、送信を打ち切り、F-007 の「結果が分からない」として扱う。上限の値は設計で決める（サーバの `WriteTimeout` 60 秒との関係を考える。[design_handoff.md](design_handoff.md) H-03）。
-   応答を受け取れなかった場合（接続の拒否、接続の切断、時間の上限）に、自動で再送しない。
-   送信 1 回につき、リクエストは 1 つだけ送る。

**Acceptance Criteria**:
- **AC-10**: 送信すると、`http://127.0.0.1:<保存したポート>/articles` へ `POST` で、`Content-Type` がちょうど `application/json`、`Authorization` がちょうど `Bearer <保存したトークン>` のリクエストが 1 つ送られる（ユニットテスト。送信の API を fake に置き換えて引数を確かめる）。
- **AC-11**: 送信の API が失敗した場合（ネットワークの誤り、時間の上限）、リクエストは 1 つだけで、再送されない（ユニットテスト）。
- **AC-12**: リダイレクトを辿らない設定で送る（ユニットテストで送信の API に渡す設定を確かめる）。リダイレクトの応答は「想定外の応答」として表示される（ユニットテスト）。
- **AC-13**: 実際のサーバ（#109）に送ると、`Origin` が `chrome-extension://clfmbbcdpnjcefbdihdoahomaifbabkk` のリクエストとして受理され、preflight（`OPTIONS`）が送られない（手動確認。Chrome と Brave。サーバのログで確かめる）。

#### F-004: 送る前の確認（追加分）

既存の確認（0007 F-005: 対象外のページ、収集の失敗、選択範囲が空、タイトルが空）を通った後、送る前に次を確かめる。どれかに当たる場合は送らず、理由を利用者に示す。

-   **共有トークンが未設定:** 共有トークンが保存されていない。オプションページを開いてトークンを貼り付ける手順を示す。保存された値が F-001 の受理する形に合わない場合（保存先が別の手段で書き換えられた場合など）も、未設定と同じく送らない。理由は区別して示してよい（設計で決める）。
-   **送る内容が大きすぎる:** 組み立てた本文を UTF-8 で表したバイト数が、サーバの本文の上限 4 MiB（4,194,304 バイト。API の設計書 §3.5.3）を超える。送れば `413` で拒否されるか、送る途中で接続を切られて「結果が分からない」になるので、送る前に止める。
-   **設定を読み込めない:** 保存先からトークン・ポートを読み込めなかった。

確認の順序は、既存の確認、設定を読み込めない、共有トークンが未設定、送る内容が大きすぎる、の順とする。

ポップアップでは、これらの確認をポップアップを開いた時点で行い、当たる場合は送信のボタンを押せない状態にして理由を示す。右クリックメニューでは、送る直前に行う。

**Acceptance Criteria**:
- **AC-14**: 共有トークンが未設定の場合、リクエストを送らず、「共有トークンが未設定」の理由とオプションページを開く手順が表示される（ユニットテストで送信が呼ばれないことと表示を確かめ、手動でも右クリックメニューとポップアップのそれぞれで確かめる）。
- **AC-15**: 保存されたトークンの値が `^[0-9a-f]{64}$` に一致しない場合、リクエストを送らない（ユニットテスト）。
- **AC-16**: 本文のバイト数がちょうど 4,194,304 の場合は送り、4,194,305 の場合は送らずに「送る内容が大きすぎる」が表示される。バイト数は、UTF-16 の長さや文字数ではなく UTF-8 で数える（ユニットテスト。多バイト文字を含む本文で境界を確かめる）。
- **AC-17**: 既存の確認で拒否される場合（対象外のページなど）、設定の読み込みも送信も行わない（ユニットテスト）。

#### F-005: 起動の手段ごとの送信の流れ

-   **右クリックメニュー:** 項目を選ぶと、収集・確認（0007 F-005 と F-004）の後、確認を挟まずに送る。送信中であることと、送信の結果（F-006・F-007）を利用者に示す。表示の手段は、0007 で設けた結果のウィンドウなどから設計で選ぶ。0007 で収集した内容を表示していた結果のウィンドウは、送信の結果の表示に置き換える。
-   **ポップアップ:** 開いたときの収集した内容の表示（0007 F-006）に、送信のボタンを加える。ボタンを押すと送る。
    -   送信中は、送信のボタンを押せない状態にし、送信中であることを示す（二重のクリックの防止）。
    -   送信が終わった後（結果によらず）、同じポップアップから再び送ることはできない。もう一度送るには、ポップアップを開き直す。送信の結果を確かめずに続けて送ることによる二重の投稿を避けるためである。
    -   送信中に利用者がポップアップを閉じた場合の扱い（送信を続けるか、結果をどこに示すか）は設計で決める（[design_handoff.md](design_handoff.md) H-01）。どの場合も自動で再送しない。
-   どちらの起動の手段でも、本文の組み立て（F-002）、送信（F-003）、送る前の確認（F-004）、応答の解釈（F-006・F-007）は同じ処理を使い、複製しない。

**Acceptance Criteria**:
- **AC-18**: 右クリックメニューから起動すると、確認を通った場合に、利用者の操作を待たずにリクエストが 1 つ送られ、その結果が表示される（ユニットテストと手動確認）。
- **AC-19**: ポップアップを開いただけでは、リクエストを送らない。送信のボタンを押すと 1 つ送られる（ユニットテスト）。
- **AC-20**: ポップアップの送信のボタンは、送信中と送信の後に押せない状態になる。送信中にボタンのクリックを繰り返しても、リクエストは 1 つだけ送られる（ユニットテスト）。
- **AC-21**: 右クリックメニューとポップアップのそれぞれから、同じ fake の入力・設定・応答で、同じ本文が送られ、同じ結果の分類になる（ユニットテスト）。
- **AC-22**: 送信中であることが、右クリックメニューとポップアップのそれぞれで示される（手動確認）。

#### F-006: 応答の解釈と表示

サーバの応答（API の設計書 §3.4.2・§3.4.3）を次のように解釈し、表示する。

-   **受付:** 状態コード `202` で、本文が `{"status":"accepted","requestId":"<小文字の 16 進 16 文字>"}`。受け付けたこと、生成と投稿の結果は Slack に届くこと、`requestId` を示す。
-   **拒否:** 状態コードが `4xx`・`5xx` で、本文が `{"status":"rejected","reason":"<固定値>","requestId":"<小文字の 16 進 16 文字>"}`、かつ `reason` と状態コードの組が API の設計書 §3.4.3 の表にあるもの。拒否されたことと理由ごとの文言、`requestId` を示す。理由ごとの表示は次のとおりとし、互いに区別できる文言にする。

    | `reason` | 状態コード | 利用者に示すこと |
    |---|---|---|
    | `unauthorized` | 401 | 共有トークンがサーバと一致しない。サーバのトークンを確かめ、オプションページに貼り直す手順 |
    | `forbidden_origin` | 403 | サーバが拡張を認めなかった（読み込んだ拡張の ID が想定と違う可能性） |
    | `forbidden_host` | 403 | サーバが送信先のホストを認めなかった |
    | `too_many_requests` | 429 | サーバが別の記事を処理中。しばらく待ってから送り直す |
    | `body_too_large` | 413 | 送る内容が大きすぎる |
    | `invalid_body` | 400 | サーバが本文の形を受理しなかった（拡張の誤りの可能性） |
    | `invalid_video_url` | 400 | 動画の URL を受理しなかった |
    | `invalid_transcript` | 400 | 選択した文字列が文字起こしパネルの字幕の形でない。文字起こしパネルを開いて字幕の行を選択し直す手順 |
    | `internal_error` | 500 | サーバの内部の誤り。サーバのログを確かめる |
    | `not_found`・`method_not_allowed`・`unsupported_media_type` | 404・405・415 | 送信先が想定のサーバでない、または拡張の誤り。ポートの設定を確かめる |

-   拒否の理由のうち、サーバが Slack にも失敗を通知するもの（`body_too_large`・`invalid_body`・`invalid_video_url`・`invalid_transcript`、枠を取った後の `internal_error`）では、Slack にも通知が届きうることを示してよい（設計で決める）。
-   `requestId` は、受付と拒否の両方で、利用者が選択してコピーできる形で表示する。
-   応答の値（`reason`・`requestId`）は、受理する形に合うものだけを表示に使う。応答の本文の文字列をそのまま表示しない（`reason` は固定の文言に置き換える）。

**Acceptance Criteria**:
- **AC-23**: `202` と受理する形の本文の応答で、「受け付けた」ことと、結果が Slack に届くこと、`requestId` が表示される（ユニットテストと手動確認）。
- **AC-24**: 上の表の `reason` と状態コードの組のそれぞれについて、互いに区別できる文言と `requestId` が表示される（ユニットテストで組と表示の対応を確かめる。`unauthorized`・`invalid_transcript`・`too_many_requests` は手動でも確かめる）。
- **AC-25**: 応答の `reason` の値や `requestId` に `<img src=x onerror=alert(1)>` のような文字列を含む応答は「想定外の応答」となり、その文字列は表示されない、または要素として解釈されない（ユニットテスト）。

#### F-007: 結果が分からない場合と想定外の応答

-   **結果が分からない:** 応答を受け取れなかった場合（サーバに接続できない、接続が切れた、時間の上限、応答の本文を読み切れない）。拡張は、サーバが起動していない可能性と、リクエストがサーバに届いて処理されている可能性の両方を示し、送り直す前に Slack を確かめるよう案内する。拡張は、サーバに接続できなかった場合と処理されている可能性がある場合を区別しない（ブラウザの API が区別できる情報を与えないため。区別できる場合の扱いは設計で決める。[design_handoff.md](design_handoff.md) H-02）。
-   **想定外の応答:** 応答は受け取ったが、F-006 の受理する形に合わない場合。次を含む。
    -   状態コードが `202` でも、本文が受付の形に合わない。
    -   状態コードが `2xx`・`3xx` で `202` 以外。
    -   本文が JSON として解析できない、オブジェクトでない、メンバが欠けている・余分にある・型が違う、`status` の値が状態コードと合わない。
    -   `reason` が F-006 の表にない値、または `reason` と状態コードの組が表にない。
    -   `requestId` が小文字の 16 進 16 文字でない。
    -   本文が有限の上限（設計で決める）を超える。
    -   サーバが本文を JSON で返さない応答（API の設計書 §3.4.2 の「ハンドラに届かない応答」: `400`・`431`・`417`）。
-   想定外の応答では、状態コードを示し、サーバの版が拡張と合っているか、ポートの設定が正しいかを確かめるよう案内する。応答の本文は表示しない。リクエストは処理されていないとは限らないので、「結果が分からない」と同じく、送り直す前に Slack を確かめるよう案内する。
-   「結果が分からない」と「想定外の応答」のどちらでも、自動で再送しない。

**Acceptance Criteria**:
- **AC-26**: 送信の API がネットワークの誤りで失敗した場合と、時間の上限に達した場合に、「結果が分からない」の表示になり、Slack を確かめる案内が含まれる（ユニットテスト）。
- **AC-27**: サーバを起動していない状態で送ると、「結果が分からない」の表示になる（手動確認。右クリックメニューとポップアップのそれぞれで確かめる）。
- **AC-28**: 次の応答のそれぞれで「想定外の応答」の表示になり、状態コードが示される: `202` で本文が空、`202` で `status` が `rejected`、`200` で受付の形の本文、`401` で本文が受付の形、本文が JSON の配列、余分なメンバを持つ本文、`requestId` が大文字を含む・15 文字・17 文字、`reason` が表にない値、`reason` が `unauthorized` で状態コードが `403`、本文が JSON でない `400`、上限を超える本文（ユニットテスト）。この例は網羅を意図しない。
- **AC-29**: 「想定外の応答」の表示に、応答の本文の文字列が現れない（ユニットテスト）。

#### F-008: 文書

-   README: 拡張のオプションページを開いて共有トークン（とポートを変えた場合はポート）を設定する手順、右クリックメニューとポップアップからの送信の使い方、「結果が分からない」の表示のときは送り直す前に Slack を確かめること、`requestId` でサーバのログと Slack の通知を照合できること。README の「拡張は #111 で送信するようになる」旨の記述を、送信する現在の振る舞いに改める。
-   `security.md` §8・§8.1: 拡張が送信するようになったことを反映する。追加の権限（`host_permissions` の `http://127.0.0.1/*`）とその理由、共有トークンの保存先（`chrome.storage.local`）とその理由と残余のリスク（0007 §3.12.3）、トークンをログ・表示・本文に出さないこと、拡張が API キーと Webhook URL を持たないこと、応答を受け取れない場合に自動で再送しないこと、応答を受理する形で検査し、本文の文字列を表示しないこと。§8 の「トークンの受け渡しと保存先は #109・#111 で決める」と §8.2 の「確定は #111」を、決まった内容に改める。
-   0007 と 0011 の文書のうち、#111 で決めるとした記述は、それぞれのタスクの記録として残し、変更しない。

**Acceptance Criteria**:
- **AC-30**: 上記の各文書に、上記の内容が記載されている（静的な確認）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

| 境界 | 受理する形 | 上限 | 拒否時の扱い | 主な AC |
|---|---|---|---|---|
| オプションページのトークンの入力 | `^[0-9a-f]{64}$` に完全に一致する文字列。補正しない | 64 文字（形で決まる） | 保存せず理由を示す | AC-02 |
| オプションページのポートの入力 | 10 進の数字だけ、先頭が `0` でない、`1024`〜`65535` | 5 文字（形で決まる） | 保存せず理由を示す | AC-03 |
| 保存したトークン・ポート（`chrome.storage.local` から読んだ値） | 上の 2 つと同じ形。ポートは欠落なら `8765` | 同上 | 送らない（F-004） | AC-04・AC-15 |
| サーバの応答 | F-006 の受付・拒否の形。状態コード・`status`・`reason`・`requestId` の組が一致する。オブジェクトのメンバは宣言したものだけで、重複を許さない | 応答の本文に有限の上限（設計で決める） | 想定外の応答（F-007） | AC-25・AC-28・AC-29 |

-   サーバの応答は、本物のサーバが返すとは限らない。サーバが停止している間に同じマシンの他のプロセスがポートを使うことがある（API の設計書 §5.4）。そのため、応答を信頼できない入力として扱い、受理する形に合わない応答を「想定外の応答」とする。
-   応答の本文について、標準の JSON の解析が黙って修復・破棄・無視すれば受理できてしまう入力（重複したメンバ、無効な UTF-8 の置き換え、対になっていないサロゲートのエスケープなど）は受理しない。応答のオブジェクトは拡張可能と宣言しない。宣言していないメンバを持つ応答は想定外の応答とする（サーバの API の設計書 §3.4.2 は、応答のメンバを 3 つに固定している）。具体的な検出の手段は設計で決める（[design_handoff.md](design_handoff.md) H-04）。
-   本タスクの送る値（選択範囲の文字列、タブの URL）は、0007 の境界をそのまま使う。送る前に新たに確かめるのは、本文の大きさ（F-004）だけである。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   送信の処理（本文の組み立て、大きさの確認、応答の解釈）は、送信そのものに比べて無視できる時間で終わればよい。性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。

### 4.2. セキュリティ (Security)
-   **権限:** 追加する権限は、`host_permissions` の `http://127.0.0.1/*` と、オプションページの宣言だけとする。ほかのホストへの権限、`tabs` などの閲覧内容全般に及ぶ権限を加えない。追加する権限ごとに、必要な理由を `02_architecture.md` に書く（0007 4.2 と同じ）。
-   **秘密の扱い:** 共有トークンを、本文、開発者向けのログ、利用者への表示（オプションページの保存後の表示を含む）、結果のウィンドウへ渡す値、エラーメッセージに出さない。送信の `Authorization` ヘッダと保存先だけに置く。
-   **API キーと Webhook URL:** 拡張はこれらを持たず、入力も保存も表示もしない。
-   **表示:** 応答から得た値も、収集した値と同じく、HTML やほかのマークアップとして解釈せずにテキストとして表示する（0007 F-006）。応答の本文の文字列は表示しない（F-006・F-007）。
-   **送信先:** `127.0.0.1` だけに送る。送信先のホストを利用者が設定する手段を設けない。
-   **再送しない:** 応答を受け取れない場合と想定外の応答の場合に、自動で再送しない（F-003・F-007）。
-   **既存の制約の維持:** `content_scripts` を宣言しない、利用者が起動するまでページを読まない、Manifest V3 の既定の Content Security Policy を緩めない、`eval`・`new Function` を使わない（0007 4.2）。オプションページも同じ制約に従う。

**Acceptance Criteria**:
- **AC-31**: manifest の権限（ホストの権限を含む）が、0007 の権限に `http://127.0.0.1/*` の `host_permissions` とオプションページの宣言を加えたものと一致し、`02_architecture.md` に理由とともに挙げたものと一致する（静的な確認。既存の manifest のガードのテストを改める）。
- **AC-32**: 送信の経路の開発者向けのログ、結果のウィンドウへ渡す値、利用者への表示に、共有トークンの値が現れない（ユニットテスト。識別できるトークンの値を使い、fake のロガー・保存先・描画した DOM のテキストに現れないことを確かめる）。
- **AC-33**: 拡張のソースと manifest に、API キーと Webhook URL を扱う設定・入力欄・保存先がない（静的な確認）。
- **AC-34**: 視聴中の YouTube ページで字幕を選択し、拡張から送ると、記事が Slack に投稿される（手動確認。右クリックメニューとポップアップのそれぞれで、Chrome で確かめる。#43・#105・#111 の完了条件）。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   送信の失敗（結果が分からない、想定外の応答、設定の読み込みの失敗）は、利用者への表示として扱い、拡張の service worker を止めない。失敗した後も、次の起動は通常どおり動作する（0007 4.3 と同じ）。
-   送信には時間の上限を設け、応答のないサーバを待ち続けない（F-003）。

### 4.4. 互換性 (Compatibility)
-   利用時: macOS 上の Chrome と Brave の、本タスクの作業時点の安定版で動作すること（0007 4.4 と同じ）。manifest の最小の Chrome の版を上げる必要がある場合は、理由を `02_architecture.md` に書く。
-   API: API の設計書 §3.4 の API（サーバの現在の実装）と組み合わせて動作すること。

### 4.5. 保守性 (Maintainability)
-   本文の組み立て、送る前の確認、応答の解釈、理由と表示の文言の対応、トークンとポートの入力の検証は、ブラウザの API から分離し、ブラウザなしでユニットテストできるようにする。送信（`fetch`）と保存先はテストで fake に置き換えられるようにする（0007 4.5 と同じ）。
-   応答の分類（受付、拒否の理由ごと、結果が分からない、想定外の応答）と、拒否の理由は、文字列の内容から推し量らずに型で表す。応答の `reason` の文字列は、解釈の境界で型の値に変換し、それ以降は型で扱う。理由の追加に表示の文言の追加が漏れると型検査が失敗するようにする（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」、0007 の `rejectionMessage` と同じ）。
-   #170 が任意の 3 フィールドの値を渡すときに、送信のクライアント（本文の組み立て・送信・応答の解釈と表示）を変更せずに済むこと（F-002）。
-   収集と既存の確認（0007 の `collect`）を変更しない。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。
-   API の設計書 §3.4・§9 に従う。サーバ側（Go のコード、API）を変更しない。
-   拡張の実行時に読み込むコードは、本リポジトリで書いたコードだけとする。npm の依存パッケージを実行時に加えない（0007 F-001）。
-   ユニットテストは、実際のブラウザも実際のサーバも起動しない。送信と保存先は fake に置き換える。実際のサーバとの組み合わせは手動で確認する。
-   手動確認で LLM API と Slack Webhook を実際に呼ぶのは、AC-34 と、記事の生成に至る確認だけとする。拒否の確認（AC-24 の手動分、AC-27）は、記事の生成に至らない入力で行う。

## 6. 用語集 (Glossary)

-   **API の設計書**: `docs/tasks/0011_localhost_server/02_architecture.md`。本書の「API の設計書 §N」はその節を指す。「API の要件書」は同じタスクの `01_requirements.md` を指す。
-   **0007**: ブラウザ拡張の骨格のタスク（`docs/tasks/0007_browser_extension_skeleton/`）。「0007 F-NNN」はその要件書の項番、「0007 §N」はその設計書の節を指す。
-   **共有トークン**: サーバが初回の起動時に生成し、拡張が `Authorization: Bearer` で送る、小文字の 16 進 64 文字の値（API の設計書 §3.3）。
-   **オプションページ**: 拡張の設定の画面。拡張の管理ページから開く拡張のページで、ほかの拡張とウェブページはその入力欄にも保存した値にも触れられない（0007 §3.12.3）。
-   **リクエスト ID（`requestId`）**: サーバがリクエストごとに生成する小文字の 16 進 16 文字の識別子。応答・サーバのログ・失敗の通知に同じ値が載る。秘密ではない（API の設計書 §3.4.2）。
-   **受付**: サーバが `202 Accepted` を返したこと。記事の生成と投稿が成功したことは意味しない。
-   **結果が分からない**: 応答を受け取れなかったため、サーバがリクエストを処理したかどうかを拡張が判断できない状態（F-007）。
-   **想定外の応答**: 応答を受け取ったが、F-006 の受理する形に合わない状態（F-007）。
-   **送信のクライアント**: 本文の組み立て（F-002）、送信（F-003）、応答の解釈（F-006・F-007）を行う部分。#170 はこれを変更しない。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
