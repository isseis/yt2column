## H-01: `fetch` を通した送信で、リダイレクトの拒否が効かない

**懸念:** アダプタは、`http.Client` の `CheckRedirect` でリダイレクトを拒否する（`internal/llm/llmhttp/llmhttp.go:65`）。WASM のビルドでは `net/http` が `fetch` に変換され、`fetch` がリダイレクトに従うので、この拒否は効かなかった。リダイレクトの先が `host_permissions` の内か、事前の確認を許す先なら、API キーのヘッダと本文がそのまま転送された（[調査記録](../../research/wasm_pipeline_poc/README.md)「測定 1：プローブ（アダプタの守り）」）。

**理由:** [security.md](../../dev/security.md) §3 は、リダイレクトに従わないことを定める。拡張だけの構成でこれが働かないと、API キーが Anthropic のほかの先へ送られうる。

**候補:** 要求に `js.fetch:redirect: manual` のヘッダを付ける。PoC では、どの先へも送られず、状態 0 の失敗になった（同上）。TypeScript に一本化するなら、`fetch` の `redirect: "manual"` か `"error"` を指定する。

**関連:** F-002、AC-19。

## H-02: `fetch` を通した送信で、応答の本文の途中の期限とキャンセルが効かない

**懸念:** 期限とキャンセルは、応答ヘッダの前では効いたが、本文の途中では効かなかった。`llmhttp.Post` の「期限は本文の読み込みまで覆う」という前提は、WASM のビルドでは成り立たない。背面のタブではブラウザがタイマーを間引くので、期限切れの時刻が遅れうる。背面での遅れは測っていない（調査記録「測定 1：プローブ（アダプタの守り）」と「確かめていない事項」）。

**理由:** 応答の本文の途中で止まった呼び出しが、期限を過ぎても終わらないと、利用者には生成が進まないまま見える。security.md §3 は、呼び出しに期限を設けることを定める。

**候補:** ページの側で、呼び出しの全体を覆う期限を別に持ち、過ぎたら `AbortController` で中止して失敗として示す。または、このリスクを受け入れ、利用者がページを閉じて止める手順を示す。

**関連:** F-002、AC-19。

## H-03: Anthropic API を呼ぶのに要るヘッダと、`host_permissions` の要否

**懸念:** 拡張のページから Anthropic API を呼ぶには、`anthropic-dangerous-direct-browser-access` のヘッダが要った。`host_permissions` の `https://api.anthropic.com/*` は必須ではなく、ないと事前の確認が 1 往復増えるだけだった（調査記録「測定 3：CSP・権限・ヘッダの試行（Chrome、Haiku）」）。ヘッダが Brave でも必須かは、確かめていない（調査記録「確かめていない事項」）。

**理由:** 権限を加えるかどうかは、Web Store での権限の説明と、リダイレクトの転送の範囲（H-01）に関わる。権限がなければ、`host_permissions` の内の先への転送は起きない。

**候補:** `host_permissions` を加えず、ヘッダだけを付ける（PoC の測定 4〜6 の組み合わせ）。

**関連:** F-002、AC-15・AC-20。

## H-04: WASM を採るときの Content Security Policy、成果物、ビルド

**懸念:** WASM を読み込むには、拡張のページの Content Security Policy に `'wasm-unsafe-eval'` が要った。成果物には、Go のツールチェーンの `wasm_exec.js` とビルドした WASM が入る。WASM は 17,300,194 バイト（`gzip -9` で 4,138,823 バイト）である（調査記録「測定 2：読み込みと CSP、サイズと読み込みの時間」）。

**理由:** security.md §8.1 は既定の Content Security Policy を緩めないと定める。[ADR-0026](../../dev/adr/0026-extension-platform.md) は、成果物を本リポジトリで書いたコードだけにし、Go の手順が拡張のディレクトリを含まず Node.js を呼ばないと定める。WASM を採ると、この 3 つが変わる。WASM でビルドできることを守る検査（`make wasm-check`、`Makefile:320`）は、#772 が決めるまでの規則である（[ADR-0019](../../dev/adr/0019-pipeline-component-interfaces.md)）。

**候補:** WASM を採るなら、Content Security Policy に `'wasm-unsafe-eval'` だけを加え、`wasm_exec.js` を成果物の検査の例外として宣言し、`make wasm-check` を残す。TypeScript に一本化するなら、3 つの方針は変えず、`make wasm-check` を外す。PoC は WASM をページのメインスレッドで動かした。Web Worker で動かす案は検討に残っている（[0084 設計書](../0084_wasm_pipeline_poc/02_architecture.md)）。

**関連:** F-002、AC-15。

## H-05: API キーの保存の手段と、読める文脈の限定

**懸念:** API キーを、ブラウザの再起動の後も残る形で保存する（AC-05）。保存した値を読める文脈が広いと、LLM の出力を描画するビューアや、ページに注入したスクリプトから API キーに届きうる。Go の側では、API キーを `secret.Secret` で持つ（[ADR-0031](../../dev/adr/0031-secret-closure.md)）。拡張のページと記事を作る処理の間で、API キーを受け渡す形も決める必要がある。

**理由:** API キーは、拡張だけの構成で新しく守る資産になる（AC-17）。AC-06 は、API キーがリクエストのほかに出ないことを求める。

**候補:** `chrome.storage.local` に保存し、`chrome.storage.sync` は使わない。読める文脈を拡張のページに限る（`setAccessLevel`）。API キーを入力する画面を、記事を描画するビューアと分ける。記事は今と同じく自前の描画だけで表示し、HTML として解釈しない（[ADR-0017](../../dev/adr/0017-viewer-markdown-rendering.md)）。

**関連:** F-001・F-002、AC-06・AC-15・AC-17。

## H-06: 完成した記事をブラウザの終了まで持つ手段と、記事を指す値

**懸念:** 完成した記事を、ブラウザを終了するまで持ち、ディスクに書かない（AC-09）。今の記事のキーは、サーバのプロセスごとの秘密を鍵とする HMAC で作る（[ADR-0027](../../dev/adr/0027-article-job-api.md)）。サーバがなくなるので、記事を指す値の作り方と、ビューアの URL に持つ値を決め直す必要がある。処理中の記事は、生成を実行するページだけが持つので、同じ動画の照会が処理中の記事を見つける手段も要る（AC-10）。

**理由:** 持ち方によって、再読み込みと閉じたタブの復元の後に記事を表示できるか、件数の上限をどう守るかが変わる。

**候補:** `chrome.storage.session` に持つ。ブラウザの終了で消え、ディスクに書かれない。容量に上限があるので、件数の上限と大きさの合計の上限（AC-09）の値と、超えたときに古い記事から捨てる規則を決める。処理中の記事は、今のビューアの探し方（`BroadcastChannel`）で探す。今のサーバは、同じ動画の記事を探すことと生成を始めることを、1 回の排他制御の中で行う（ADR-0027）。探すことと始めることが分かれると、同時に押された 2 つの開始がどちらも記事を見つけず、同じ動画の記事を二重に生成しうる。この競合を防ぐ手段も決める。

**関連:** F-001・F-002、AC-09・AC-10・AC-15。

## H-07: 記事の生成を実行する場所と、一度も前面にならなかった背面のタブ

**懸念:** 今のビューアは、生成の開始と同時に背面のタブで開き、一度も前面にならないことがある（[ADR-0009](../../dev/adr/0009-viewer-opening.md)）。PoC では、人が前面でボタンを押してから背面にしたので、この開き方は試していない（調査記録「確かめていない事項」）。ブラウザが自動で行う破棄を受けたときの振る舞いも、観測していない。

**理由:** ビューアのタブで生成を実行するなら、この開き方で生成が完走することが前提になる。完走しないなら、生成を実行する場所か、ビューアの開き方を変えることになる。

**候補:** 設計の前に、背面で開いたタブで生成が完走するかを確かめる。完走するなら、ビューアのタブで実行する。完走しないなら、Offscreen Document で実行するか、ビューアを前面で開く。

**関連:** F-002・F-003、AC-15・AC-21。

## H-08: 開発用の fake の LLM の、拡張だけの構成での使い方

**懸念:** fake の LLM は、開発用のサーバから使う構成要素として決めた（[ADR-0045](../../dev/adr/0045-dev-fake-llm.md)）。サーバがなくなると、拡張の画面を料金をかけずに動かす手段がなくなる。

**理由:** 拡張の開発と手動の確認のたびに、本番の構成で 1 本あたり約 0.33〜0.46 USD（調査記録「測定 6：本番の構成（Chrome、`83ef12bd`、背面のまま）」）がかかるのは、現実的でない。ADR-0045 は、本番の成果物が fake の LLM に依存しないことも定める。開発用のサーバのタスク（0086、[#687](https://github.com/isseis/yt2column/issues/687)）は、承認済みだが実装はまだで、廃止するサーバの上に作る計画である。その扱いも決める必要がある。

**候補:** 開発用のビルドだけが fake の LLM を含み、公開する成果物は含まない。成果物の検査で、公開する成果物に fake が入らないことを確かめる。

**関連:** F-002、AC-15・AC-24。

## H-09: manifest の `key` と、Web Store が割り当てる ID

**懸念:** 今は manifest の `key` で拡張の ID を固定している。理由は、ホストの `allowed_origins` が ID を指定するからである（ADR-0026）。ホストを廃止すると、この理由はなくなる。Web Store は、公開する拡張に ID を割り当てる。

**理由:** `key` を残すかどうかで、開発用に読み込んだ拡張と、Web Store から導入した拡張の ID が同じになるかが変わる。ID が変わると、保存した値（API キー）は引き継がれない。

**候補:** Web Store の条件を確かめたうえで、`key` を除くか、Web Store の公開鍵に合わせる。

**関連:** F-002、AC-15・AC-20。

## H-10: プロバイダの追加を妨げない形

**懸念:** 拡張が使うプロバイダは Claude だけだが、将来 OpenAI などを選べるようにすることを妨げない構成にする（AC-04）。そのために今の構成を過度に複雑にはしない。

**理由:** 保存する値の形や、記事を作る処理の入口の形を Claude だけに合わせて決めると、プロバイダを足すときに、保存した値の移行や入口の作り直しが要る。

**候補:** 保存する値の名前に、プロバイダを区別できる名前を使う。記事を作る処理の入口は、CLI と同じ設定の値の文法（[ADR-0003](../../dev/adr/0003-llm-config-contract.md)）を受け取り、拡張は固定の値を渡す。プロバイダを選ぶ設定と、複数の API キーの保存は作らない。

**関連:** F-001、AC-04。

## H-11: サーバとホストを前提にした項目を持つ ADR の洗い出し

**懸念:** issue #772 が挙げた ADR（ADR-0005・0006・0008・0010・0018・0026・0027・0031）のほかにも、サーバとホストを前提にした項目を持つ有効な ADR がある。要件定義のレビューで挙がった候補は、ADR-0003・0004・0007・0017・0024・0033・0034・0038・0043 である。[ADR-0029](../../dev/adr/0029-extension-ui-languages.md) は、言語の設定を持たない理由を「拡張は設定を持たず、何も保存しない」としており、要件の PR が改めた [ADR-0010](../../dev/adr/0010-extension-stores-nothing.md) の決定と合わない。ADR-0010 の「背景」「採らなかった案」「結果」にも、改めた決定と合わない記述が残っている。

**理由:** AC-24 は、設計書がこれらをすべて挙げ、設計の PR のマージの後に残らないことを求める。挙げ漏らすと、有効な ADR が、なくなったサーバやホストの規則を述べ続ける。

**候補:** `docs/dev/adr/` の有効な ADR を、サーバ、ホスト、ソケット、設定ファイル、ジョブの API の語で検索し、該当する項目を表にする。項目ごとに、改める、別の ADR に移す、ADR を廃止する、のどれかを決める。

**関連:** F-004、AC-24。
