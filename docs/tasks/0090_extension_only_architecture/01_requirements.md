## 1. 概要 (Overview)

**目的:** 本書は、記事をブラウザ拡張だけで作る構成（以下、拡張だけの構成）を設計し、その決定を ADR に記録するタスクの要件を定める。本タスクの成果は文書である。製品のコードは変えない。実装は [#773](https://github.com/isseis/yt2column/issues/773) が行う。

**背景:**

今の主経路は、拡張が集めた字幕を Native Messaging のホストが localhost サーバへ中継し、サーバが記事を作る構成である（[project_overview.md](../../dev/project_overview.md)「決定済みの方針」の実行形式）。この構成は、利用者にネイティブのバイナリの導入、ホストの manifest の登録、サーバの起動を求める。拡張を Chrome Web Store で公開することを見据えると、導入の障壁が大きい（[#769](https://github.com/isseis/yt2column/issues/769)）。

品質の目標は `claude-opus-5-5` を要するので（[production_profile.md](../../dev/production_profile.md)）、ブラウザの中で推論する形は採れない。一方、推論はせずに拡張のページから Claude API を直接呼ぶ構成なら、サーバとホストを廃止できる。

この構成が成り立つかは、タスク 0084 の PoC（概念実証）で測った（[#771](https://github.com/isseis/yt2column/issues/771)）。結果は[調査記録](../../research/wasm_pipeline_poc/README.md)にある。要点は次のとおりである。

-   Go のパイプラインを WASM（WebAssembly）にビルドしたものは、拡張のページから Claude API を呼んで記事を完成させた。本番の構成の 3 本は、背面のタブのまま完成した（調査記録「3 つの問いへの答え」）。
-   ストリーミングは、測った範囲では要らなかった（同上）。
-   `fetch` を通した送信では、アダプタの守りの一部が働かなかった。リダイレクトを拒否する守りは効かず、期限とキャンセルは応答の本文の途中では効かなかった（調査記録「測定 1：プローブ（アダプタの守り）」）。
-   確かめていない事項が残っている（調査記録「確かめていない事項」）。

今の拡張とサーバの決定のうち、拡張だけの構成で変わるものは、次のとおりである。

-   拡張は何も保存せず、API キーを持たず、ネットワークへ要求を送らない。権限は `activeTab`・`scripting`・`nativeMessaging` の 3 つである（`extension/static/manifest.json:16`、[security.md](../../dev/security.md) §8.1）。
-   記事の生成と状態の正しい値は、サーバが持つ。完成した記事は、サーバがメモリに持ち、サーバの再起動で失う（[development.md](../../dev/guides/development.md)「ジョブの API」、security.md §8.2「localhost サーバ」の「メモリに持つ記事」）。
-   ビューアは、完成した記事の推定の料金を示す。失敗した生成の料金は示さない。状態の取得の応答で `cost` を持つのは、状態が `done` のジョブの `article` だけで、`failed` のジョブが持つのは `steps` と `failure` である（`docs/dev/guides/development.md:138-140`）。
-   API キーは、CLI では環境変数から、サーバでは設定ファイルからだけ読む（security.md §2）。

対応 issue: [#772](https://github.com/isseis/yt2column/issues/772)（親: [#769](https://github.com/isseis/yt2column/issues/769)、前提: [#771](https://github.com/isseis/yt2column/issues/771)、後続: [#773](https://github.com/isseis/yt2column/issues/773)、関連: [#770](https://github.com/isseis/yt2column/issues/770)）

**本書の記述範囲:** 本書は、次の 4 つを定める。

-   拡張だけの構成が満たす、製品上の要件（F-001）。
-   設計（`02_architecture.md`）が決める事項と、その決め方（F-002・F-003）。
-   決定を ADR に記録する規則（F-004）。
-   本タスクと #773 の範囲の境界（F-005）。

構成の手段（記事の生成を実行する場所、保存の手段、権限、ビルドの方式など）は、設計で決める。要件定義の過程で挙がった手段の候補と注意点は、[design_handoff.md](design_handoff.md) に申し送る。

**issue #769・#772 で決めたこと:**

-   **記事の生成は拡張だけで行い、localhost サーバと Native Messaging のホストを廃止する（#769）。** 拡張のページから LLM の API を直接呼ぶ。利用者にネイティブのバイナリの導入を求めないためである。ADR: [ADR-0047](../../dev/adr/0047-extension-only-generation.md) を作った。サーバの構成と設定ファイルの主題が終わるので、[ADR-0005](../../dev/adr/0005-server-architecture.md) と [ADR-0018](../../dev/adr/0018-server-config-file.md) を廃止した。
-   **利用者は、自分の Anthropic API キーを拡張に設定する（#769）。** 開発者は、API キーも、API を中継するサーバも提供しない。ADR: ADR-0047 に記録した。
-   **生成のジョブの寿命は、それを実行する拡張のページの寿命とする（#769）。** ブラウザやそのページを閉じれば、生成は止まる。サーバの寿命が効くのは、生成を頼んだ後にブラウザを閉じ、起動し直して同じページで頼み直す経路だけで、現実には起きにくいためである。ADR: ADR-0047 に記録した。
-   **CLI は開発用の経路として残し、記事を作る処理を拡張と共有する（#769）。** 共有の方法は、Go のコアを WASM にビルドする案を推奨とし、TypeScript に一本化する案と比べて設計で決める（#772）。ADR: CLI を残すことは ADR-0047 に記録した。共有の方法は、設計の PR で記録する。
-   **新旧の経路を併存させず、一括で切り替える（#769）。** 利用者が開発者 1 人で、互換の仕組みの費用に見合わないためである。ADR: ADR-0047 に記録した。
-   **Slack の Incoming Webhook への投稿の機能は廃止する（#769）。** タスク 0083（#770）が決めて実装するので、本タスクは扱わない。ADR: なし（[ADR-0043](../../dev/adr/0043-copy-mention-neutralization.md) などに記録済みである）。
-   **構成は、PoC の結果をもとに決める（#772）。** 測った値を根拠にする決定は、調査記録を引用する。ADR: なし（決め方の規則で、本タスクの中で閉じる）。
-   **設計が決める事項と、改める ADR の見込み（#772）。** issue は、決める事項の案と、改める見込みの ADR（ADR-0005・0006・0008・0010・0018・0026・0027・0031）を挙げた。本書は、これを F-002 と F-004 に取り込んだ。ADR: 各事項の決定を、設計の PR で記録する。

**要件定義の際に決めたこと（2026-11-12）:**

-   **進め方は通常の進め方（`full`）とする。** 変更は、拡張、記事を作る処理の共有、セキュリティの方針に及ぶ。決めることが多く、多くの ADR の決定を変えるためである。簡易な進め方から除外する変更に当たるかの判断は「当たる」とした。脅威モデル（[ADR-0006](../../dev/adr/0006-threat-model.md)）と、security.md §8 の前提（拡張は API キーを持たず、ネットワークへ送らない）を変えるためである。人は通常の進め方を選び、この判断を覆していない。ADR: なし（このタスクの進め方の決定で、タスクの外に及ばない）。
-   **仕様の文書は、#773 がコードと一緒に書き換える（F-005）。** 対象は、security.md・project_overview.md・README などである。これらは今のコードの仕様の正本で、#773 より前に書き換えると、サーバとホストが動いている間、文書がコードと食い違うためである。issue #772 は、改める見込みのものに security.md §8 を挙げたが、本タスクでは書き換えない。本タスクは、新しい規則を要件書・設計書と ADR に記録し、ADR に食い違いの注記を置く。ADR: なし（タスクの間の範囲の分け方である）。
-   **拡張が使うプロバイダは Claude だけとし、3 つの工程とも本番の構成に固定する（F-001）。** 拡張の設定は、API キーと任意のワークスペース ID だけである。品質の目標が本番の構成を要し、設定の画面と権限を最小にできるためである。将来は OpenAI などを選べるようにするつもりなので、それを妨げない構成にする。ただし、そのために今の構成を過度に複雑にはしない。CLI は、今までどおり 3 つのプロバイダを選べる。ADR: ADR-0047 に記録した。
-   **API キーは、ブラウザを再起動しても残る形で保存する（F-001）。** 利用者が API キーを 1 回入力すれば済むようにするためである。値はプロファイルのディスクに平文で残り、同じ OS ユーザーのプロセスは読める。これは、CLI の `.envrc` やサーバの設定ファイルと同じ水準として受け入れる。ブラウザの終了で消す案と、利用者が選べるようにする案は採らなかった。ADR: [ADR-0010](../../dev/adr/0010-extension-stores-nothing.md) を更新した。
-   **完成した記事は、ブラウザを終了するまで持ち、ディスクに書かない。同じ動画の照会を続ける（F-001）。** 今の「サーバのメモリにだけ置き、再起動で失う」に最も近い振る舞いである。料金のかかった記事を、再読み込みやタブを閉じる操作で失わないためである。タブが開いている間だけ持つ案と、ディスクに保存する案は採らなかった。ADR: [ADR-0027](../../dev/adr/0027-article-job-api.md) と ADR-0010 を更新した。
-   **ビューアは、失敗した実行の料金も示す（F-001）。** 利用者が自分の API キーで支払うので、失敗した実行で使った額も分かるようにするためである。ページを閉じるか読み込み直して中止した生成の料金は、示さない。生成のジョブの寿命をページの寿命とする決定（#769）の帰結で、その使用量を受け取るページが残らないためである。今の表示を保つ案と、生成の前に概算を示す案は採らなかった。ADR: [ADR-0022](../../dev/adr/0022-cost-estimate.md) を更新した。
-   **Web Store への対応は、構成に関わる方針だけを本タスクで決める（F-002・F-005）。** 構成を縛る条件（権限とその理由、扱うデータと送り先、プライバシーポリシーの要否と書くべき内容、リモートのコードを読み込まないこと）を設計で挙げ、構成がそれを満たすことを記録する。掲載の文面、プライバシーポリシーの本文、申請は、別の issue にする。構成が決まる前の文面は、実装の後に直すことになりうるためである。ADR: 範囲の決定は、なし。構成が Web Store で公開できる形であることは ADR-0047 に記録した。条件の中身は、設計の PR で記録する。
-   **サーバとホストを前提にした残りの ADR は、設計の PR で改める（F-004）。** 主題が終わる ADR-0005 と ADR-0018 は、本書の PR で廃止した。ADR-0006・0008・0009・0026・0028・0031 と、ADR-0010・0027 の残りの項目は、置き換える決定が設計で決まるので、設計の PR で 1 回だけ書き換える。それまでは、ADR-0047 に、これらを設計で改める旨の注記を置く。ADR: なし（記録の手順の決定で、本タスクの中で閉じる）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   拡張だけの構成を、#773 が実装できる水準まで設計する。
-   構成の決定を、理由、採らなかった案、根拠とした測定とともに ADR に記録する。
-   サーバとホストを前提にした ADR の決定を、拡張だけの構成の決定に改める。

### 2.2. スコープ (In Scope)

-   拡張だけの構成の設計（F-001・F-002）。`02_architecture.md` に書く。
-   調査記録の「確かめていない事項」の扱いの決定と、設計が先に確かめると決めた事項の実測（F-003）。
-   ADR の新設、更新、廃止（F-004）。
-   #773 への引き継ぎと、Web Store の掲載の文面を扱う issue の作成（F-005）。

設計書の承認の後に残る作業（F-003 の実測のうち設計の後に行うもの、F-005 の issue の更新と作成）は、`03_implementation_plan.md` が扱う。

### 2.3. スコープ外 (Out of Scope)

-   拡張だけの構成の実装と、サーバとホストの撤去。#773 が行う。本タスクは、`cmd/`・`internal/`・`extension/` を変えない。
-   仕様の文書（security.md・project_overview.md・production_profile.md・README・`README.en.md`・development.md・package_reference.md・CLAUDE.md）の書き換え。要件定義の際に決めたとおり、#773 がコードと一緒に行う。
-   画面の文言、画面の配置、アクセシビリティの受け入れ基準。#773 の要件定義で決める。本タスクの設計は、画面が示す状態の種類までを決める。
-   Web Store の掲載の文面、プライバシーポリシーの本文、申請。要件定義の際に決めたとおり、別の issue にする。
-   Claude のほかのプロバイダを拡張で選べるようにすること、拡張でモデルと effort を選べるようにすること。要件定義の際に決めたとおりである。
-   Slack の Incoming Webhook への投稿の廃止。タスク 0083（#770）が行う。
-   CLI の振る舞いの変更。

## 3. 機能要件 (Functional Requirements)

本タスクの成果は文書なので、受け入れ基準は、設計書と ADR が何を定め、何を記録するかを述べる。F-001 の基準は、設計書が定める構成が満たす性質である。その性質をコードが満たすことは、#773 の受け入れ基準で確かめる。

### 3.1. 機能一覧

#### F-001: 拡張だけの構成が満たす製品上の要件

設計書が定める構成は、次の基準を満たす。

**Acceptance Criteria**:

-   **AC-01**: 構成は、記事の生成のために、拡張のほかに利用者のマシンへ何も導入させない。ネイティブのバイナリ、Native Messaging のホストの manifest、常駐するプロセスを要さない。
-   **AC-02**: 構成では、拡張は、利用者が拡張に設定した Anthropic API キーで LLM の API を呼ぶ。API キーが設定されていないときは、生成を始めず、LLM の API を呼ばず、API キーの設定が要ることを利用者に示す。
-   **AC-03**: 構成では、拡張が使うプロバイダは Claude だけで、3 つの工程とも本番の構成（`claude-opus-5-5`、effort `high`）を使う。拡張の設定の項目は、API キーと任意のワークスペース ID だけである。
-   **AC-04**: 設計書は、将来プロバイダを 1 つ足すときに変える箇所を挙げる。構成は、Claude のほかのプロバイダのための設定、権限、コードを含まない。
-   **AC-05**: 構成では、設定した API キーとワークスペース ID は、ブラウザを再起動した後も残る。
-   **AC-06**: 構成では、API キーは、Anthropic の API へのリクエストを除き、どこにも出ない。出ない先は、少なくとも、ログ、エラーの表示、ビューアの URL、保存するファイル、コピーする文章、LLM に送るプロンプト、ブラウザの外への同期である。
-   **AC-07**: 構成では、料金のかかる生成は、利用者がポップアップのボタンを押したときだけ始まる。拡張のページを開くこと、再読み込み、閉じたタブの復元、履歴からの表示では始まらない。失敗した生成と、結果の分からない生成を、自動では送り直さない。
-   **AC-08**: 構成では、生成を実行するページを閉じると、その生成は止まり、ほかの場所で続かない。途中で止まった生成は、完成した記事として残らない。
-   **AC-09**: 構成では、完成した記事は、ブラウザを終了するまで、再読み込みと閉じたタブの復元の後も表示できる。ブラウザを終了した後は、ビューアは記事が失われたことを示す。完成した記事は、ディスクに書かない。
-   **AC-10**: 構成では、同じ動画の照会が、今と同じ範囲で働く。照会付きの生成の開始は、同じ動画の処理中か完了の記事があれば、生成を始めずにその記事を示す。対象は、ブラウザを終了するまでに拡張が持つ記事である。
-   **AC-11**: 構成では、ビューアは、完成した記事の推定の料金と、失敗した実行の推定の料金を示す。料金が分からないときは、0 を含め推測の値を出さず、不明と示す。ページを閉じるか読み込み直して中止した生成の料金は、示さない。
-   **AC-12**: 構成は、CLI を残し、CLI と拡張が同じ記事を作る処理を使う。設計書は、CLI の引数、環境変数、出力を変える決定を含まない。
-   **AC-13**: 構成は、サーバとホストを使う経路と拡張だけの経路を併存させる仕組みも、版の食い違いを見分ける仕組みも持たない。
-   **AC-14**: 構成は、本書と設計書が改めると挙げた決定のほかの、有効な ADR の決定を変えない。設計の途中で、ほかの決定を変える必要が分かったときは、設計の際に人と決めて記録する。

#### F-002: 設計が決める事項

設計書は、構成を決めるのに要る事項を、理由と採らなかった案とともに決める。

**Acceptance Criteria**:

-   **AC-15**: 設計書は、次の各事項の決定を、理由と、採らなかった案とその理由とともに記録する。
    -   記事の生成を実行する場所（ビューアのタブ、Offscreen Document など）と、ポップアップ、Service Worker、ビューアの役割。
    -   生成の状態の正しい値の置き場所と、ポップアップとビューアがそれを表示する方法。
    -   ストリーミングを使うかどうか。
    -   CLI と記事を作る処理を共有する方法（Go のコアを WASM にビルドするか、TypeScript に一本化するか）。あわせて、ビルドの方式と、WASM でビルドできることを守る検査（`make wasm-check`）を残すかどうか。
    -   API キーの保存の手段、設定・変更・削除の操作、API キーを LLM の出力を描画するページと同じオリジンに置くことへの対策。
    -   完成した記事の持ち方、件数や大きさの上限と、上限を超えたときに捨てる記事の選び方、記事を指す値（今の記事のキー）の作り方。
    -   拡張が要求する権限と Content Security Policy。加えるものと除くものを、それぞれ理由とともに挙げる。
    -   manifest の `key` による ID の固定を続けるかどうか。
    -   利用者に示す状態の種類。少なくとも、API キーが設定されていない、API が API キーを拒んだ、生成が失敗した、生成がページとともに止まった、記事が失われた、の 5 つを含む。
    -   開発と手動の確認で、料金をかけずに拡張を動かす方法。
    -   対象のブラウザと、拡張が要求する Chrome の最小の版。
-   **AC-16**: 設計書は、測った値を根拠にする決定で、調査記録の節の名前を挙げて引用する。調査記録にない値を根拠にするときは、F-003 に従って確かめた結果を引用する。
-   **AC-17**: 設計書は、拡張だけの構成の脅威モデルを定める。守る資産（API キーを含む）、信頼する相手、排除する相手とその根拠、受け入れるリスクを挙げる。相手には、少なくとも、ウェブページ、ほかの拡張、ページに注入したスクリプト、同じ OS ユーザーのプロセス、プロンプトインジェクションで操作された LLM の出力を含む。
-   **AC-18**: 設計書は、構成が受け取る信頼できない入力ごとに、受理する形、拒否の理由、大きさの上限を定める（§3.2）。
-   **AC-19**: 設計書は、[security.md](../../dev/security.md) §3 の規則（リダイレクトに従わない、応答の本文の大きさに上限を設ける、呼び出しに期限を設ける）のそれぞれを、拡張からの送信でどう満たすかを定める。満たせない規則は、受け入れるリスクとして、理由とともに記録する。
-   **AC-20**: 設計書は、構成を縛る Chrome Web Store の条件を、出典（公式の文書の URL と、確かめた日付）とともに挙げ、構成が各条件を満たすことを示す。条件には、少なくとも、権限とその理由、扱うデータと送り先、プライバシーポリシーの要否と書くべき内容、リモートのコードを読み込まないことを含む。

#### F-003: 確かめていない事項の扱い

調査記録の「確かめていない事項」には、構成の前提になるものがある。たとえば、一度も前面にならなかった背面のタブでの記事の生成と、Opus で 40,000 トークンを出力する長さのストリーミングなしの応答である。設計は、これらを確かめないまま前提にしない。

**Acceptance Criteria**:

-   **AC-21**: 設計書は、調査記録の「確かめていない事項」の各項目について、構成の決定に関わるかどうかを判定する。関わる項目は、先に確かめるか、確かめずに受け入れるかを、理由とともに記録する。受け入れる項目は、見込みが外れたときに変わる決定も記録する。
-   **AC-22**: 先に確かめると決めた事項は、確かめた結果を、測った日と条件とともに調査記録に追記する。追記は、その結果を引用する文書の PR か、それより前の PR で `main` に入れる。確かめるためのコードは、`main` に入れない。

#### F-004: ADR への記録

**Acceptance Criteria**:

-   **AC-23**: 設計の PR は、設計書の主要な決定を、新しい ADR か既存の ADR の更新で記録する。各 ADR の「決定」は、設計書の決定と一致する。ADR と索引は、[adr.md](../../dev/conventions/adr.md) の形に従う。
-   **AC-24**: 設計の PR のマージの後、有効な ADR の「決定」に、localhost サーバまたは Native Messaging のホストがあることを前提にした規則が残らない。食い違いの注記の中の記述は除く。対象は、少なくとも ADR-0006・0008・0009・0010・0026・0027・0028・0031 である。あわせて、[ADR-0019](../../dev/adr/0019-pipeline-component-interfaces.md) の「#772 が決めるまで」の検査の規則と、[ADR-0045](../../dev/adr/0045-dev-fake-llm.md) の開発用のサーバの規則を、設計の決定に合わせて改める。
-   **AC-25**: 設計の PR は、ADR-0047 の、残りの ADR を設計の PR で改める旨の段落を除く。
-   **AC-26**: 決定がコードや仕様の文書とまだ食い違う ADR は、食い違いの注記を持ち、注記は #773 にリンクする。issue #773 の本文は、それらの ADR の番号を挙げる。

#### F-005: 範囲の境界と引き継ぎ

**Acceptance Criteria**:

-   **AC-27**: 本タスクの PR の差分は、`docs/tasks/0090_extension_only_architecture/`、`docs/dev/adr/`、`docs/translation_glossary.md`、`docs/research/` に限る。
-   **AC-28**: 設計書は、#773 が実装するものと、#773 が書き換える仕様の文書を挙げ、文書ごとに、書き換える内容の要点を示す。
-   **AC-29**: Web Store の掲載の文面、プライバシーポリシーの本文、申請を扱う issue を作り、設計書からリンクする。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

本タスクは、コードを書かないので、入力を受け取る実装を持たない。境界の規則は、設計書が構成の一部として定め（AC-18）、#773 が実装する。設計書が定める境界は、少なくとも次の 4 つである。

-   **コピーした字幕と動画メタデータ。** 拡張が動画のページから集め、記事を作る処理に渡す値である。今はサーバが生成の開始の本文として検査する（security.md §8.2「受け取る入力の境界」）。構成は、今のサーバが拒否する入力を、補正して受理しない。
-   **LLM の API の応答。** 応答の大きさの上限、空の応答、打ち切りの扱いは、今のアダプタと同じにする（security.md §3、[CLAUDE.md](../../../CLAUDE.md)「Empty is an error」）。
-   **利用者が入力する API キーとワークスペース ID。** 受理する形に合わない値は、補正せずに拒否する（CLAUDE.md「Reject, don't normalize」）。
-   **拡張が保存した場所から読み戻す値。** API キー、ワークスペース ID、完成した記事である。受理する形に合わない値を、補正して使わない。

各境界の受理する形、拒否したときに利用者に示すもの、上限の値は、設計書が定める。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   本書は、WASM のサイズと読み込みの時間に閾値を設けない。設計書は、調査記録の値（「測定 2：読み込みと CSP、サイズと読み込みの時間」）を引用し、記事を作る処理を共有する方法の決定（AC-15）で、その値を受け入れるかどうかを理由とともに記録する。

### 4.2. セキュリティ (Security)

[security.md](../../dev/security.md) を当てはめる。拡張だけの構成は、API キーを扱い、LLM の API へデータを送り、字幕と動画メタデータ（信頼できないテキスト）をプロンプトに入れるので、条件つきのガイドの対象である。

-   **保つ規則。** 構成は、次の規則を保つ。
    -   API キーを、送信先へのリクエストを除くどの出力にも出さない（security.md §2、[ADR-0031](../../dev/adr/0031-secret-closure.md)、AC-06）。
    -   LLM に送るデータは今と同じにし、API キーをプロンプトに入れない（security.md §4）。
    -   記事と動画メタデータを、信頼できないテキストとして扱う（security.md §6・§8.1、[ADR-0017](../../dev/adr/0017-viewer-markdown-rendering.md)、ADR-0043）。
    -   料金のかかる生成を、利用者の明示の操作のときだけ始め、自動では送り直さない（[ADR-0008](../../dev/adr/0008-launch-path.md)・[ADR-0028](../../dev/adr/0028-no-automatic-resend.md)、AC-07）。
-   **変える方針。** 構成は、次の方針を変える。どれも、サーバとホストを廃止し、拡張が API を直接呼ぶこと（#769）の帰結である。仕様の文書は、#773 が書き換える。
    -   security.md §2：API キーは、CLI では環境変数から、サーバでは設定ファイルからだけ読む。構成では、拡張が API キーを保存して使う（AC-05）。
    -   security.md §8.1「API キーと Webhook URL を持たない」：構成では、拡張が API キーを入力させ、保存する。
    -   security.md §8.1「設定を保存しない」と ADR-0010：構成では、拡張が API キー、ワークスペース ID、完成した記事を保存する（AC-05・AC-09）。
    -   security.md §8.1「送る相手は固定のホストだけ」：構成では、拡張が LLM の API へ要求を送る。
    -   security.md §8 の脅威モデルと ADR-0006：サーバのソケットとホストを前提にした規則がなくなり、拡張が持つ API キーが守る資産に加わる（AC-17）。
-   **設計で決まる方針の変更。** security.md §8.1 の「Manifest V3 の既定の Content Security Policy を緩めない」と、[ADR-0026](../../dev/adr/0026-extension-platform.md) の「成果物は本リポジトリで書いたコードだけにする」は、記事を作る処理を共有する方法によっては変わる。変えるかどうかは設計で決め、変えるときは理由を記録する（AC-15）。
-   **`fetch` を通した送信の守り。** リダイレクトの拒否と、応答の本文の途中での期限とキャンセルは、PoC では働かなかった。設計は、これを確かめないまま今と同じに働くとは前提にしない（AC-19）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   構成は、失敗を成功として扱わない。空の応答と打ち切りは失敗である（CLAUDE.md「Empty is an error」、AC-08）。
-   生成の途中でページが閉じられると、その生成は失われる。これは受け入れる（#769）。設計は、失われたことを利用者にどう示すかを決める（AC-15）。

### 4.4. 互換性 (Compatibility)

-   サーバとホストを使う経路との互換の仕組みは設けない（AC-13）。
-   対象のブラウザと Chrome の最小の版は、設計で見直す（AC-15）。今の決定は、Chrome と Brave だけを対象とし（ADR-0026）、最小の版を 110 とする（[ADR-0030](../../dev/adr/0030-minimum-chrome-version.md)）。

### 4.5. 保守性 (Maintainability)

-   記事を作る処理は、CLI と拡張で 1 つにする（AC-12）。同じ規則を、Go と TypeScript の両方に書かない。
-   構成が外部の依存（Go のモジュール、拡張の npm のパッケージ、成果物に入れる外部のファイル）を加えるときは、設計書が、標準ライブラリや今の依存では足りない理由を記録する（CLAUDE.md「Dependencies」）。

## 6. 用語集 (Glossary)

用語は [docs/translation_glossary.md](../../translation_glossary.md) と統一する。

-   **拡張だけの構成:** localhost サーバと Native Messaging のホストを使わず、ブラウザ拡張が LLM の API を直接呼んで記事を作る構成。
-   **PoC:** 概念実証（proof of concept）。本書では、タスク 0084 の、`main` にマージしない測定のための実装を指す。
-   **調査記録:** タスク 0084 の測定の結果の文書（`docs/research/wasm_pipeline_poc/README.md`）。
-   **WASM:** WebAssembly。本書では、Go のコードを `GOOS=js GOARCH=wasm` でビルドしたものを指す。
-   **本番の構成:** 3 つの工程とも `claude-opus-5-5`、effort `high` の構成（[production_profile.md](../../dev/production_profile.md)）。
-   **3 つの工程:** 生成、字数の調整、検証・推敲（[ADR-0002](../../dev/adr/0002-post-generation-steps.md)）。
-   **記事の生成:** 3 つの工程を通して記事を作る一連の処理。工程の 1 つの「生成」とは区別する。
-   **仕様の文書:** 今のコードの仕様の正本である文書。security.md・project_overview.md・production_profile.md・README・`README.en.md`・development.md・package_reference.md・CLAUDE.md を指す。
-   **食い違いの注記:** ADR の決定が、仕様の文書やコードとまだ食い違っていることを述べ、それを解消する issue にリンクする記述（[adr.md](../../dev/conventions/adr.md)「Writing an ADR」）。
-   **設計の PR:** 本タスクの `02_architecture.md` を加える PR。
