## 1. 概要 (Overview)

**目的:** 本書は、記事をブラウザ拡張だけで作る構成（以下、拡張だけの構成）を設計し、その決定を ADR に記録するタスクの要件を定める。本タスクの成果は文書である。製品のコードは変えない。実装は [#773](https://github.com/isseis/yt2column/issues/773) が行う。

**背景:**

今の主経路は、拡張が集めた字幕を Native Messaging のホストが localhost サーバへ中継し、サーバが記事を作る構成である（[project_overview.md](../../dev/project_overview.md)「決定済みの方針」の実行形式）。この構成は、利用者にネイティブのバイナリの導入、ホストの manifest の登録、サーバの起動を求める。拡張を Chrome Web Store で公開することを見据えると、導入の障壁が大きい（[#769](https://github.com/isseis/yt2column/issues/769)）。

品質の目標は `claude-opus-5-5` を要するので（[production_profile.md](../../dev/production_profile.md)）、ブラウザの中で推論する形は採れない。一方、ブラウザの中では推論せず、拡張のページから Claude API を直接呼ぶ構成なら、サーバとホストを廃止できる。

この構成が成り立つかは、タスク 0084 の PoC（概念実証）で測った（[#771](https://github.com/isseis/yt2column/issues/771)）。結果は[調査記録](../../research/wasm_pipeline_poc/README.md)にある。要点は次のとおりである。

-   Go のパイプラインを WASM（WebAssembly）にビルドしたものは、拡張のページから Claude API を呼んで記事を完成させた。本番の構成で試した 3 本の動画の記事は、背面のタブのまま完成した（調査記録「3 つの問いへの答え」）。
-   ストリーミングは、測った範囲では要らなかった（同上）。
-   `fetch` を通した送信では、アダプタの守りの一部が働かなかった。リダイレクトを拒否する守りは効かず、期限とキャンセルは応答の本文の途中では効かなかった（調査記録「測定 1：プローブ（アダプタの守り）」）。
-   確かめていない事項が残っている（調査記録「確かめていない事項」）。

今の拡張とサーバの決定のうち、拡張だけの構成で変わるものは、次のとおりである。

-   拡張は何も保存せず、API キーを持たず、ネットワークへリクエストを送らない。権限は `activeTab`・`scripting`・`nativeMessaging` の 3 つである（`extension/static/manifest.json:16`、[security.md](../../dev/security.md) §8.1）。
-   記事の生成と状態の正しい値は、サーバが持つ。完成した記事は、サーバがメモリに持ち、サーバの再起動で失う（[development.md](../../dev/guides/development.md)「ジョブの API」、security.md §8.2「localhost サーバ」の「メモリに持つ記事」）。
-   ビューアは、完成した記事の推定の料金を示す。失敗した実行の料金は示さない。状態の取得の応答で `cost` を持つのは、状態が `done` のジョブの `article` だけで、`failed` のジョブが持つのは `steps` と `failure` である（`docs/dev/guides/development.md:138-140`）。
-   API キーは、CLI では環境変数から、サーバでは設定ファイルからだけ読む（security.md §2）。

対応 issue: [#772](https://github.com/isseis/yt2column/issues/772)（親: [#769](https://github.com/isseis/yt2column/issues/769)、前提: [#771](https://github.com/isseis/yt2column/issues/771)、後続: [#773](https://github.com/isseis/yt2column/issues/773)、関連: [#770](https://github.com/isseis/yt2column/issues/770)）

**本書の記述範囲:** 本書は、次の 4 つを定める。

-   拡張だけの構成が満たす、製品上の要件（F-001）。
-   設計（`02_architecture.md`）が決める事項と、その決め方（F-002・F-003）。
-   決定を ADR に記録する規則（F-004）。
-   本タスクと #773 の範囲の境界（F-005）。

構成の手段（記事の生成を実行する場所、保存の手段、権限、ビルドの方式など）は、設計で決める。本書が使う用語（実行、要件の PR、設計の PR、仕様の文書、食い違いの記述、記事を作る処理など）は、§6 に定義する。要件定義の過程で挙がった手段の候補と注意点は、[design_handoff.md](design_handoff.md) に申し送る。

**issue #769・#772 で決めたこと:**

-   **記事の生成は拡張だけで行い、localhost サーバと Native Messaging のホストを廃止する（#769）。** 拡張のページから LLM の API を直接呼ぶ。利用者にネイティブのバイナリの導入を求めないためである。ADR: [ADR-0047](../../dev/adr/0047-extension-only-generation.md) を作った。サーバの構成と設定ファイルの主題が終わるので、[ADR-0005](../../dev/adr/0005-server-architecture.md) と [ADR-0018](../../dev/adr/0018-server-config-file.md) を廃止した。
-   **利用者は、自分の Anthropic API キーを拡張に設定する（#769）。** 開発者は、API キーも、API を中継するサーバも提供しない。今は API キーをサーバの設定ファイルに置いており（security.md §2）、サーバを廃止すると、API キーを置ける場所が拡張だけになるためである。利用者の Claude のサブスクリプション（Pro・Max）を API キーの代わりに使う案は、採らなかった。Anthropic は、事前の承認がない限り、サードパーティの製品が claude.ai のログインやサブスクリプションの利用枠を提供することを認めていない（[Agent SDK の概要](https://code.claude.com/docs/en/agent-sdk/overview)、2026-11-12 に確認）。claude.ai の画面を拡張から操作する方法はこの方針に反するうえ、画面の変更で壊れる。利用者の Claude Code（`claude -p`）を呼ぶ方法は、ローカルのプロセスが要り、AC-01 に反する。ADR: ADR-0047 に記録した。
-   **生成のジョブの寿命は、それを実行する拡張のページの寿命とする（#769）。** ブラウザやそのページを閉じれば、記事の生成は止まる。サーバの寿命が効くのは、記事の生成を頼んだ後にブラウザを閉じ、起動し直して同じページで頼み直す経路だけである。この経路は現実には起きにくいので、ページの寿命に合わせる。ADR: ADR-0047 に記録した。
-   **CLI は開発用の経路として残し、記事を作る処理を拡張と共有する（#769）。** CLI は開発・検証用の経路で（project_overview.md の冒頭）、実行ごとに設定を変えて試す使い方があるためである（ADR-0018）。共有の方法は、Go のコアを WASM にビルドする案を推奨とし、TypeScript に一本化する案と比べて設計で決める（#772）。ADR: CLI を残すことは ADR-0047 に記録した。共有の方法は、設計の PR で記録する。
-   **新旧の経路を併存させず、一括で切り替える（#769）。** 利用者が開発者 1 人で、互換の仕組みの費用に見合わないためである。ADR: ADR-0047 に記録した。
-   **Slack の Incoming Webhook への投稿の機能は廃止する（#769）。** タスク 0083（#770）が決めて実装するので、本タスクは扱わない。ADR: なし（[ADR-0043](../../dev/adr/0043-copy-mention-neutralization.md) などに記録済みである）。
-   **構成は、PoC の結果をもとに決める（#772）。** 測った値を根拠にする決定は、調査記録を引用する。ADR: なし（決め方の規則で、本タスクの中で閉じる）。
-   **設計が決める事項と、改める ADR の見込み（#772）。** issue は、決める事項の案と、改める見込みの ADR（ADR-0005・0006・0008・0010・0018・0026・0027・0031）を挙げた。本書は、これを F-002 と F-004 に取り込んだ。ADR: 各事項の決定を、設計の PR で記録する。

**要件定義の際に決めたこと（2026-11-12）:**

-   **進め方は通常の進め方（`full`）とする。** 変更は、拡張、記事を作る処理の共有、セキュリティの方針に及ぶ。決めることが多く、多くの ADR の決定を変えるためである。簡易な進め方から除外する変更に当たるかの判断は「当たる」とした。脅威モデル（[ADR-0006](../../dev/adr/0006-threat-model.md)）と、security.md §8 の前提（拡張は API キーを持たず、ネットワークへ送らない）を変えるためである。人は通常の進め方を選び、この判断を覆していない。ADR: なし（このタスクの進め方の決定で、タスクの外に及ばない）。
-   **仕様の文書は、#773 がコードと一緒に書き換える（F-005）。** 対象は、security.md・project_overview.md・README などである。これらは今のコードの仕様の正本で、#773 より前に書き換えると、サーバとホストが動いている間、文書がコードと食い違うためである。issue #772 は、改める見込みのものに security.md §8 を挙げたが、本タスクでは書き換えない。本タスクは、新しい規則を要件書・設計書と ADR に記録し、ADR に食い違いの記述を置く。ADR: なし（タスクの間の範囲の分け方である）。
-   **拡張が使うプロバイダは Claude だけとし、3 つの工程とも本番の構成に固定する（F-001）。** 拡張の設定は、API キーと任意のワークスペース ID だけである。品質の目標が本番の構成を要し、設定の画面と権限を最小にできるためである。将来は OpenAI などを選べるようにするつもりなので、それを妨げない構成にする。ただし、そのために今の構成を過度に複雑にはしない。CLI は、今までどおり 3 つのプロバイダを選べる。モデルと effort を選べるようにする案は、設定の画面と検証が増え、品質の目標を満たさない構成を利用者が選べるようになるので、採らなかった。複数のプロバイダを選べるようにする案は、拡張のページから直接呼べることを確かめたのが Claude だけなので、採らなかった。ADR: ADR-0047 に記録した。
-   **API キーは、ブラウザを再起動しても残る形で保存する（F-001）。** 利用者が API キーを 1 回入力すれば済むようにするためである。値はプロファイルのディスクに平文で残り、同じ OS ユーザーのプロセスは読める。これは、CLI の `.envrc` やサーバの設定ファイルと同じ水準として受け入れる。ブラウザの終了で消す案は、利用者がブラウザを起動するたびに API キーを貼り直すことになるので、採らなかった。利用者が選べるようにする案は、設定の画面と保存の経路が 2 つになるので、採らなかった。ADR: [ADR-0010](../../dev/adr/0010-extension-stores-nothing.md) を更新した。
-   **完成した記事は、ブラウザを終了するまで持ち、ディスクに書かない。同じ動画の照会を続ける（F-001）。** 今の「サーバのメモリにだけ置き、再起動で失う」に最も近い振る舞いである。料金のかかった記事を、再読み込みやタブを閉じる操作で失わないためである。タブが開いている間だけ持つ案は、再読み込みやタブを閉じる操作で記事を失い、作り直すと料金がもう一度かかるので、採らなかった。ディスクに保存する案は、見た動画の記事が端末に残り、削除の操作と上限の設計が要るので、採らなかった。持ち続ける記事の記録には、今のサーバと同じく、コピーした字幕を持たない。字幕は最大で 4 MiB になりうるうえ、記事の表示にも同じ動画の照会にも要らないためである。上限は、件数に加えて大きさの合計にも設ける。記事 1 本の大きさは、今のサーバが状態の応答を 256 KiB までに抑える規則のもとで、ふつうは数十 KB だが最大で約 256 KiB になり、件数だけでは持つ量の上限が決まらないためである。ADR: [ADR-0027](../../dev/adr/0027-article-job-api.md) と ADR-0010 を更新した。
-   **ビューアは、記事が完成しなかった実行の料金を、一律に不明と示す（F-001）。** 対象は、失敗した実行と、記事の生成を実行するページが閉じられるか再読み込みされて止まった実行である。利用者が自分の API キーで支払うので、記事が完成しなくても料金がかかりうることを示すためである。金額は、工程ごとにも合計でも示さない。失敗した実行では、料金が分かる工程と分からない工程が混ざり（失敗した呼び出しは使用量を返さないことがある。project_overview.md「パイプライン」の `LLMClient`）、工程ごとに示すと画面が複雑になるためである。今の表示を保ち、失敗した実行の料金を示さない案は、料金がかかったかもしれないことが利用者に分からないので、採らなかった。料金が分かった工程の金額を示し、分からない工程を不明と示す案は、画面が複雑になるので、採らなかった。記事の生成の前に概算を示す案は、字幕の長さから料金を見積もる仕組みを新しく作ることになり、実際の値との差も出るので、採らなかった。ADR: [ADR-0022](../../dev/adr/0022-cost-estimate.md) を更新した。
-   **Web Store への対応は、構成に関わる方針だけを本タスクで決める（F-002・F-005）。** 構成を縛る条件（権限とその理由、扱うデータと送り先、プライバシーポリシーの要否と書くべき内容、リモートのコードを読み込まないこと）を設計で挙げ、構成がそれを満たすことを記録する。掲載の文面、プライバシーポリシーの本文、申請は、別の issue にする。構成が決まる前の文面は、実装の後に直すことになりうるためである。ADR: 範囲の決定は、なし。構成が Web Store で公開できる形であることは ADR-0047 に記録した。条件の中身は、設計の PR で記録する。
-   **サーバとホストを前提にした残りの ADR は、設計の PR で改める（F-004）。** 主題が終わる ADR-0005 と ADR-0018 は、要件の PR で廃止した。ADR-0006・0008・0009・0026・0028・0031 と、ADR-0010・0027 の残りの項目は、置き換える決定が設計で決まるので、設計の PR で 1 回だけ書き換える。ほかの有効な ADR にも該当する項目がありうるので、設計書がすべて挙げる（AC-24）。それまでは、ADR-0047 に、これらを設計で改める旨の段落を置く。これは、決定を変える PR が同じ PR で ADR を改めるという規則（[CLAUDE.md](../../../CLAUDE.md)「Design decisions (ADR)」）の例外である。範囲は、サーバとホストを前提にした項目を、設計の PR まで元のまま残すことに限る。同じ ADR を、要件の PR と設計の PR で 2 回書き換えないためである。ADR: なし（記録の手順の決定で、本タスクの中で閉じる）。
-   **設計が決める事項に、issue の案にない事項を加えた（F-002・F-003）。** 加えたのは、脅威モデル、信頼できない入力の境界、`fetch` を通した送信の守り、「確かめていない事項」の扱い、利用者に示す状態の種類、料金をかけずに拡張を動かす方法、対象のブラウザと Chrome の最小の版、同時に走る記事の生成の数である。どれも、サーバとホストの廃止で前提が変わるか、PoC が未解決のまま残した事項で、設計が決めないと #773 が実装できないためである。issue の案は、決める事項の案であり、網羅を意図していない。ADR: なし（設計が決める範囲の決定で、各事項の決定は設計の PR で記録する）。

## 3. 機能要件 (Functional Requirements)

本タスクの成果は文書なので、受け入れ基準は、設計書と ADR が何を定め、何を記録するかを述べる。F-001 の基準は、設計書が定める構成が満たす性質である。その性質をコードが満たすことは、#773 の受け入れ基準で確かめる。

### 3.1. 機能一覧

#### F-001: 拡張だけの構成が満たす製品上の要件

設計書が定める構成は、次の基準を満たす。

**Acceptance Criteria**:

-   **AC-01**: 構成は、記事の生成のために、拡張のほかに利用者のマシンへ何も導入させない。ネイティブのバイナリ、Native Messaging のホストの manifest、常駐するプロセスを要さない。
-   **AC-02**: 構成では、拡張は、利用者が拡張に設定した Anthropic API キーで LLM の API を呼ぶ。API キーが設定されていないときは、記事の生成を始めず、LLM の API を呼ばず、API キーの設定が要ることを利用者に示す。
-   **AC-03**: 構成では、拡張が使うプロバイダは Claude だけで、3 つの工程とも本番の構成（[production_profile.md](../../dev/production_profile.md)）を使う。拡張の設定の項目は、API キーと任意のワークスペース ID だけである。
-   **AC-04**: 設計書は、将来プロバイダを 1 つ足すときに変える箇所を挙げる。構成は、プロバイダを選ぶ設定と、Claude のほかの送り先への権限を持たない。
-   **AC-05**: 構成では、設定した API キーとワークスペース ID は、ブラウザを再起動した後も残る。
-   **AC-06**: 構成では、API キーは、拡張が保存する場所と、Anthropic の API へのリクエストを除き、どこにも出さない。出さない先には、少なくとも、ログ、エラーの表示、ビューアの URL、保存するファイル、コピーする文章、LLM に送るプロンプト、ブラウザの外への同期を含む。
-   **AC-07**: 構成では、料金のかかる記事の生成は、利用者がポップアップのボタンを押したときだけ始まる。拡張のページを開くこと、再読み込み、閉じたタブの復元、履歴からの表示では始まらない。失敗した実行と、結果の分からない実行を、自動ではやり直さない。
-   **AC-08**: 構成では、記事の生成は、それを実行する拡張のページが閉じられると止まり、ほかの場所で続かない。どのページが実行するかは、設計で決める（AC-15）。途中で止まった記事の生成は、完成した記事として残らない。
-   **AC-09**: 構成では、完成した記事は、ブラウザを終了するまで、再読み込みと閉じたタブの復元の後も表示できる。設計が定める上限で捨てた記事は除く。ブラウザを終了した後と、記事を捨てた後は、ビューアは記事が失われたことを示す。完成した記事は、ディスクに書かない。持ち続ける記事の記録は、コピーした字幕を持たない。持ち続ける記事には、件数の上限と、大きさの合計の上限の両方を設ける。
-   **AC-10**: 構成では、同じ動画の照会が、今と同じ範囲で働く。照会付きの生成の開始は、同じ動画の記事が処理中か完了していれば、記事の生成を始めずにその記事を示す。対象は、ブラウザを終了するまでに拡張が持つ記事である。
-   **AC-11**: 構成では、ビューアは、完成した記事の推定の料金を示す。記事が完成しなかった実行（失敗した実行と、記事の生成を実行するページが閉じられるか再読み込みされて止まった実行）を示すときは、料金を一律に不明と示す。その実行では、0 を含め、金額を工程ごとにも合計でも出さない。
-   **AC-12**: 構成は、CLI を残し、CLI と拡張が同じ記事を作る処理を使う。設計書は、CLI の引数、環境変数、出力を変える決定を含まない。
-   **AC-13**: 構成は、サーバとホストを使う経路と拡張だけの経路を併存させる仕組みも、版の食い違いを見分ける仕組みも持たない。
-   **AC-14**: 構成は、本書が変えると定めたもののほか、利用者から見えるポップアップとビューアの機能と、有効な ADR の決定を変えない。設計書は、構成が変える有効な ADR の決定をすべて挙げる。本書が挙げていない決定を変えるときは、設計の際に人と決めて記録する。

#### F-002: 設計が決める事項

設計書は、構成を決めるのに要る事項を、理由と採らなかった案とともに決める。

**Acceptance Criteria**:

-   **AC-15**: 設計書は、次の各事項の決定を、理由と、採らなかった案とその理由とともに記録する。
    -   記事の生成を実行する場所（ビューアのタブ、Offscreen Document など）と、ポップアップ、Service Worker、ビューアの役割。
    -   記事の生成の状態の正しい値の置き場所と、ポップアップとビューアがそれを表示する方法。
    -   ストリーミングを使うかどうか。
    -   CLI と記事を作る処理を共有する方法（Go のコアを WASM にビルドするか、TypeScript に一本化するか）。あわせて、ビルドの方式と、WASM でビルドできることを守る検査（`make wasm-check`）を残すかどうか。
    -   API キーの保存の手段、設定・変更・削除の操作、保存した API キーを画面に再び表示するかどうか、API キーを LLM の出力を描画するページと同じオリジンに置くことへの対策。
    -   完成した記事の持ち方、件数の上限と大きさの合計の上限の値（AC-09）と、上限を超えたときに捨てる記事の選び方、記事を指す値（今の記事のキー）の作り方。拡張の再読み込みと更新のときに記事が残るかどうかも決める。
    -   同時に走る記事の生成の数の上限と、同じ入力でもう一度頼まれたときの扱い。今は、サーバが同時に走る記事の生成の数に上限を設け、同じ入力では作り直さない（security.md §8.2、ADR-0027）。
    -   CLI と共有する処理の範囲。メンションの無効化、保存するファイルの中身、完了の時点の記事の検査を、共有する処理に含めるかどうかを決める。
    -   拡張が要求する権限と Content Security Policy。加えるものと除くものを、それぞれ理由とともに挙げる。
    -   manifest の `key` による ID の固定を続けるかどうか。
    -   利用者に示す状態の種類。少なくとも、API キーが設定されていない、API が API キーを拒んだ、記事の生成が失敗した、記事の生成がページとともに止まった、記事が失われた、の 5 つを含む。失敗した実行の状態を、再読み込みの後も示すかどうかも決める。
    -   開発と手動の確認で、料金をかけずに拡張を動かす方法。
    -   対象のブラウザと、拡張が要求する Chrome の最小の版。
-   **AC-16**: 設計書は、測った値を根拠にする決定で、調査記録の節の名前を挙げて引用する。調査記録にない値を根拠にするときは、F-003 に従って確かめた結果を引用する。
-   **AC-17**: 設計書は、拡張だけの構成の脅威モデルを定める。守る資産（API キーを含む）、信頼する相手、排除する相手とその根拠、受け入れるリスクを挙げる。相手には、少なくとも、ウェブページ、ほかの拡張、ページに注入したスクリプト、同じ OS ユーザーのプロセス、プロンプトインジェクションで操作された LLM の出力を含む。
-   **AC-18**: 設計書は、構成が受け取る信頼できない入力ごとに、受理する形、拒否の理由、大きさの上限、拒否したときに利用者に示すものを定める（§3.2）。構造を持つ入力では、使うメンバと、知らないメンバと重複したメンバの扱いも定める。どの境界でも、受理する形に合わない値を補正して使わない。
-   **AC-19**: 設計書は、LLM の API への送信の守り（リダイレクトに従わない、応答の本文の大きさに上限を設ける、呼び出しに期限を設ける。[security.md](../../dev/security.md) §3 と `internal/llm/llmhttp`）のそれぞれを、拡張からの送信でどう満たすかを定める。構成は、API キーを、リダイレクトの先を含め、Anthropic の API のほかの先へ送らない（AC-06）。これは、受け入れるリスクにしない。このほかの守りのうち、拡張からの送信で満たせないものは、受け入れるリスクとして、理由とともに記録する。
-   **AC-20**: 設計書は、構成を縛る外部の条件を、出典（公式の文書の URL と、確かめた日付）とともに挙げ、構成が各条件を満たすことを示す。Chrome Web Store の条件には、少なくとも、権限とその理由、扱うデータと送り先、プライバシーポリシーの要否と書くべき内容、リモートのコードを読み込まないことを含む。Anthropic の条件には、拡張のページから API を直接呼ぶことと、利用者が自分の API キーを設定して使う拡張を配布することを含む。設計書は、これらの条件が変わったときに変わる決定も記録する。

#### F-003: 確かめていない事項の扱い

調査記録の「確かめていない事項」には、構成の前提になるものがある。たとえば、一度も前面にならなかった背面のタブでの記事の生成と、Opus が 40,000 トークンを出力するほど長い、ストリーミングなしの応答である。設計は、これらを確かめないまま前提にしない。前提にする事項は、設計の PR のマージより前に確かめる。確かめない事項は、見込みが外れたときの決定を用意して受け入れる。

**Acceptance Criteria**:

-   **AC-21**: 設計書は、調査記録の「確かめていない事項」の各項目について、構成の決定に関わるかどうかを判定する。関わる項目は、設計の PR のマージより前に確かめるか、確かめずに受け入れるかを、理由とともに記録する。受け入れる項目は、見込みが外れたときに変わる決定も記録する。
-   **AC-22**: 確かめると決めた事項は、確かめた結果を、測った日と条件とともに調査記録に追記し、設計書がそれを引用する。追記は、設計の PR か、それより前の PR で `main` に入れる。確かめるためのコードは、`main` に入れない。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

本タスクは、コードを書かないので、入力を受け取る実装を持たない。境界の規則は、設計書が構成の一部として定め（AC-18）、#773 が実装する。設計書が定める境界は、少なくとも次の 5 つである。

-   **コピーした字幕と動画メタデータ。** 拡張が動画のページから集め、記事を作る処理に渡す値である。今はサーバが生成の開始の本文として検査する（security.md §8.2「受け取る入力の境界」）。構成は、今のサーバが拒否する入力を、補正して受理しない。
-   **LLM の API の応答。** 応答の大きさの上限、空の応答、打ち切りの扱いは、今のアダプタと同じにする（security.md §3、[CLAUDE.md](../../../CLAUDE.md)「Empty is an error」）。
-   **利用者が入力する API キーとワークスペース ID。** 受理する形に合わない値は、補正せずに拒否する（CLAUDE.md「Reject, don't normalize」）。
-   **拡張が保存した場所から読み戻す値。** API キー、ワークスペース ID、完成した記事である。受理する形に合わない値を、補正して使わない。
-   **拡張のページの間で受け渡す値。** ビューアの URL が持つ値と、ポップアップ、Service Worker、ビューアの間のメッセージである。送り手の検査は今の規則を保つ（security.md §8.1「生成の開始は、拡張自身のポップアップからだけ受け付ける」）。

各境界の受理する形、拒否したときに利用者に示すもの、上限の値は、設計書が定める。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   本書は、WASM のサイズと読み込みの時間に閾値を設けない。設計書は、調査記録の値（「測定 2：読み込みと CSP、サイズと読み込みの時間」）を引用し、記事を作る処理を共有する方法の決定（AC-15）で、その値を受け入れるかどうかを理由とともに記録する。

### 4.2. セキュリティ (Security)

[security.md](../../dev/security.md) を当てはめる。拡張だけの構成は、API キーを扱い、LLM の API へデータを送り、字幕と動画メタデータ（信頼できないテキスト）をプロンプトに入れるので、条件つきのガイドの対象である。

-   **保つ規則。** 構成は、次の規則を保つ。
    -   API キーを、送信先へのリクエストを除くどの出力にも出さない（security.md §2、[ADR-0031](../../dev/adr/0031-secret-closure.md)、AC-06）。
    -   LLM に送るデータは今と同じにし、API キーをプロンプトに入れない（security.md §4）。
    -   記事と動画メタデータを、信頼できないテキストとして扱う（security.md §6・§8.1、[ADR-0017](../../dev/adr/0017-viewer-markdown-rendering.md)、ADR-0043）。
    -   料金のかかる記事の生成を、利用者の明示の操作のときだけ始め、自動では送り直さない（[ADR-0008](../../dev/adr/0008-launch-path.md)・[ADR-0028](../../dev/adr/0028-no-automatic-resend.md)、AC-07）。
-   **変える方針。** 構成は、次の方針を変える。どれも、サーバとホストを廃止し、拡張が API を直接呼ぶこと（#769）の帰結である。仕様の文書は、#773 が書き換える。
    -   security.md §2：API キーは、CLI では環境変数から、サーバでは設定ファイルからだけ読む。構成では、拡張が API キーを保存して使う（AC-05）。
    -   security.md §8.1「API キーと Webhook URL を持たない」：構成では、拡張が API キーを入力させ、保存する。
    -   security.md §8.1「設定を保存しない」と ADR-0010：構成では、拡張が API キー、ワークスペース ID、完成した記事を保存する（AC-05・AC-09）。
    -   security.md §8.1「送る相手は固定のホストだけ」と「要求する権限」：構成では、拡張が LLM の API へリクエストを送り、`nativeMessaging` の権限を持たない。加える権限は設計で決める（AC-15）。
    -   project_overview.md「決定済みの方針」の実行形式と、「前提・制約」の、サーバが記事をメモリに持つこと：構成では、サーバとホストがなく、完成した記事は拡張が持つ（AC-01・AC-09）。
    -   security.md §8 の脅威モデルと ADR-0006：サーバのソケットとホストを前提にした規則がなくなり、拡張が持つ API キーが守る資産に加わる（AC-17）。
-   **設計で決まる方針の変更。** security.md §8.1 の「Manifest V3 の既定の Content Security Policy を緩めない」と、[ADR-0026](../../dev/adr/0026-extension-platform.md) の「成果物は本リポジトリで書いたコードだけにする」は、記事を作る処理を共有する方法によっては変わる。変えるかどうかは設計で決め、変えるときは理由を記録する（AC-15）。
-   **`fetch` を通した送信の守り。** リダイレクトの拒否と、応答の本文の途中での期限とキャンセルは、PoC では働かなかった。設計は、これらが今と同じに働くことを前提にしない（AC-19）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   構成は、失敗を成功として扱わない。空の応答と打ち切りは失敗である（CLAUDE.md「Empty is an error」、AC-08）。
-   記事の生成の途中でページが閉じられると、その記事の生成は失われる。これは受け入れる（#769）。設計は、失われたことを利用者にどう示すかを決める（AC-15）。

### 4.4. 互換性 (Compatibility)

-   サーバとホストを使う経路との互換の仕組みは設けない（AC-13）。
-   対象のブラウザと Chrome の最小の版は、設計で見直す（AC-15）。今の決定は、Chrome と Brave だけを対象とし（ADR-0026）、最小の版を 110 とする（[ADR-0030](../../dev/adr/0030-minimum-chrome-version.md)）。

### 4.5. 保守性 (Maintainability)

-   記事を作る処理は、CLI と拡張で 1 つにする（AC-12）。同じ規則を、Go と TypeScript の両方に書かない。
-   構成が外部の依存（Go のモジュール、拡張の npm のパッケージ、成果物に入れる外部のファイル）を加えるときは、設計書が、標準ライブラリや今の依存では足りない理由を記録する（CLAUDE.md「Dependencies」）。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。本書が変える方針は、§4.2 の「変える方針」に挙げた。
-   本タスクは、製品のコードと仕様の文書を変えない（AC-27）。
-   実 API の呼び出しと、ネットワークを使う操作（Web Store の公式の文書の取得、issue の作成と更新）は、その都度、人の承認を得る（CLAUDE.md「Tool Execution Safety」）。

-   受け入れ基準の多くは、文書の内容を定める。これらは、PR のレビューで文書を読んで確かめる（[requirements_process.md](../../dev/conventions/requirements_process.md) §4）。AC-27 は差分で、AC-23 のうち ADR と索引の形は既存の検査で確かめる。

## 6. 用語集 (Glossary)

用語は [docs/translation_glossary.md](../../translation_glossary.md) と統一する。

-   **拡張だけの構成:** localhost サーバと Native Messaging のホストを使わず、ブラウザ拡張が LLM の API を直接呼んで記事を作る構成。
-   **PoC:** 概念実証（proof of concept）。本書では、タスク 0084 の、`main` にマージしない測定のための実装を指す。
-   **調査記録:** タスク 0084 の測定の結果の文書（`docs/research/wasm_pipeline_poc/README.md`）。
-   **WASM:** WebAssembly。本書では、Go のコードを `GOOS=js GOARCH=wasm` でビルドしたものを指す。
-   **本番の構成:** 3 つの工程とも `claude-opus-5-5`、effort `high` の構成（[production_profile.md](../../dev/production_profile.md)）。
-   **3 つの工程:** 生成、字数の調整、検証・推敲（[ADR-0002](../../dev/adr/0002-post-generation-steps.md)）。
-   **記事の生成:** 3 つの工程を通して記事を作る一連の処理。工程の 1 つの「生成」とは区別する。
-   **実行:** 記事の生成の 1 回。完成するか、失敗するか、途中で止まる。
-   **記事を作る処理:** コピーした字幕と動画メタデータから、表示・保存・コピーする記事を作るまでの処理。今は `internal/` のパッケージにあり、CLI とサーバが共有する。拡張と共有する範囲は、設計で決める（AC-15）。
-   **仕様の文書:** 今のコードの仕様の正本である文書。security.md・project_overview.md・production_profile.md・README・`README.en.md`・development.md・package_reference.md・CLAUDE.md を指す。
-   **食い違いの記述:** ADR の決定が、仕様の文書やコードとまだ食い違っていることを述べ、それを解消する issue にリンクする記述（[adr.md](../../dev/conventions/adr.md)「Writing an ADR」）。
-   **要件の PR:** 本書を加える PR。
-   **設計の PR:** 本タスクの `02_architecture.md` を加える PR。
