## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

本タスクの成果は文書である（要件書 1 章）。設計書と ADR の変更は、設計の PR（#871）で `main` に入った。本計画は、設計書の承認の後に残る作業を扱う（要件書 §2.2）。残る作業は次の 2 つである。

-   issue [#773](https://github.com/isseis/yt2column/issues/773) の本文が挙げる ADR の番号の誤りを 1 つ直す（AC-26）。
-   本文が挙げる ADR の番号と、本タスクの PR の差分の範囲を、`_checks/` のスクリプトで確かめて記録する（AC-26・AC-27）。

### 1.2. 実装の原則

-   **実装の PR が変えるのは、本タスクのディレクトリの下のファイルだけである。** ADR、調査記録、用語集は変えない。製品のコードと仕様の文書も変えない（要件書 §2.3・AC-27）。
-   **新しい恒久のテストは足さない。** スクリプトは 1 回走らせて結果を記録するもので、`make test` にも CI にも組み込まない（`requirements_process.md` §4「`diff` verification」）。
-   **issue の本文の編集は、ネットワークを使う操作として、その場で人の承認を得てから行う**（CLAUDE.md「Tool Execution Safety」、要件書 5 章）。

### 1.3. 計画の際に決めたこと（2026-11-14）

-   **#773 の本文は、要件の PR の段落の `ADR-0047` を `ADR-0048` に直すだけにする。** 今の本文の 2 つの段落（要件の PR の段落と設計の PR の段落）で、食い違いの記述を持つ 25 本の ADR はすべて挙がっている。誤りは、要件の PR（#862）が食い違いの記述を置いた ADR-0048 を ADR-0047 と書いた 1 か所だけである（§1.4）。2 つの段落を今の 25 本の 1 つの一覧にまとめ直す案は採らなかった。直しが大きくなり、PR ごとの経緯が本文から消えるためである。ADR: なし（issue の本文の直し方で、本タスクの中で閉じる）。
-   **AC-26 と AC-27 は、`_checks/` のシェルのスクリプトで確かめ、その出力を本計画 §7 に記録する。** AC-26 は ADR の番号という値を述べるので、読んで確かめるだけでは足りない（`requirements_process.md` §4）。スクリプトは番号の集合とファイルの一覧を機械的に比べる。採らなかった案は、コマンドの出力を本計画に貼ってレビューで読み比べる案である。25 本の番号を目で比べることになり、見落としうる。ADR: なし（確かめ方の決定で、本タスクの中で閉じる）。
-   フェーズは 1 つで、実装の PR は 1 本である。PR の作成ポイントは置かない。ADR: なし。

## 2. 実装の手順 (Implementation Steps)

-   [ ] **ステップ 1-1**: 確認のスクリプトを `_checks/check.sh` に書く。引数は、比べる 2 つのコミット（変更の前と後）と、#773 の本文を書き出したファイルである。後のコミットの内容で、次を確かめる。
    -   状態が `有効` で「決定」の節に #773 の URL（`issues/773` の後に数字が続かないもの）を持つ ADR の番号の集合が、本文のファイルに現れる ADR の番号（`ADR-NNNN`）の集合と等しい（AC-26）。等しくないときは、片方にだけある番号を出す。
    -   2 つのコミットの間で追加・削除・変更されたファイルが、すべて `docs/tasks/0090_extension_only_architecture/`・`docs/dev/adr/`・`docs/translation_glossary.md`・`docs/research/` の下にある（AC-27）。外にあるファイルを出す。

    違反があれば 0 でない終了コードで終わる。どの場合も、2 つのコミットの完全な ID、本文のファイルの SHA-256、`check.sh` の blob の ID を出す。コメントと文字列リテラルは英語で書く。
-   [ ] **ステップ 1-2**: スクリプトの各確認が、少なくとも 1 つの壊し方で失敗することを確かめる。壊し方は、本文のファイルの写しを変えるか、使い捨てのブランチの一時的なコミットで作る。使い捨てのブランチは push せず、確かめた後に消す。壊し方ごとの結果は、ステップ 1-4 のコミットのメッセージに書く。
-   [ ] **ステップ 1-3**: #773 の本文を直す。人の承認を得てから、`gh issue view 773 --json body --jq .body` で本文をスクラッチパッドのファイルに書き出す。次の文がちょうど 1 回現れることを確かめる。
    -   直す前：`タスク 0090 の要件の PR（#862）で決定を改め、実装まで食い違いの記述を置いた ADR：ADR-0010・ADR-0022・ADR-0027・ADR-0047。実装の PR で、それぞれの記述を除く。`
    -   直した後：`タスク 0090 の要件の PR（#862）で決定を改め、実装まで食い違いの記述を置いた ADR：ADR-0010・ADR-0022・ADR-0027・ADR-0048。実装の PR で、それぞれの記述を除く。`

    この 1 か所のほかは変えずに、`gh issue edit 773 --body-file <file>` で書き戻す。書き戻す前に、ファイルが `_context.md` の「PR review request」の言及を含まないことを、`_lib/task-pr-handoff.md` の mention check で確かめる。文が見つからないか 2 回以上現れるときは、書き戻さずに止まって人に報告する。
-   [ ] **ステップ 1-4**: 直した後の本文を、`gh issue view 773 --json body --jq .body` でもう一度書き出す。確認のスクリプトを、次の 4 組のコミットと、その本文のファイルで実行する。
    -   要件の PR #862 のスカッシュのコミットの親とそのコミット（`28358348`）。
    -   設計の PR #871 のスカッシュのコミットの親とそのコミット（`63ee516a`）。
    -   本計画の PR のスカッシュのコミットの親とそのコミット。
    -   実装の PR の merge-base（`git merge-base origin/main HEAD`。`git fetch origin main` の後）と `HEAD`。

    どの組でも AC-26 の確認は後のコミットの ADR を読むので、組ごとにその時点の ADR と今の本文を比べることになる。各組の出力・終了コード・完全なコミットの ID を本計画 §7 に書き、本計画の進み具合とともにコミットする。`make test` と `make lint` を通す。

**PR を作る直前の確かめ直し。** ステップ 1-4 の後で `_checks/` か `docs/dev/adr/` を変えるコミットが入ったとき、または `main` を取り込んだときは、ステップ 1-4 の実装の PR の組をやり直して §7 の記録を改める。`_checks/` を変えたときは、ステップ 1-2 もやり直す。対象は、`/runplan` のレビューの後、PR を作る前のコミットで、`.claude/commands/_lib/task-pr-handoff.md` Part B の手順 1・2 の修正も含む。`/runplan` がこれを実装のまとまりとして拾わないよう、チェックボックスにはしない。

**完了の条件:** #773 の本文の `ADR-0047` が `ADR-0048` になり、ほかが変わっていない。確認のスクリプトが 4 つの組のすべてで終了コード 0 で終わり、その記録が本計画 §7 にある。壊し方ごとの結果が、ステップ 1-4 のコミットのメッセージにある。`make test` と `make lint` が通る。
