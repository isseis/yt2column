## 1. 概要 (Overview)

**目的:** 本書は、ポップアップの主ボタンを押したときに、同じ動画の記事がサーバのキャッシュにあれば、生成を始める前にそのことを示し、利用者が「現在の選択範囲で記事を生成する」か「既存の記事を表示する」かを選べるようにするための要件を定義する。

**背景:**

本書の用語（「照会付きの生成の開始」「同じ動画の応答」「選択の状態」など）は 6 章で定義する。

タスク `0050_viewer_tab`（[#503](https://github.com/isseis/yt2column/issues/503)）の後、拡張はサーバのジョブの API（[#502](https://github.com/isseis/yt2column/issues/502)、タスク `0044_article_job_api`）で記事を生成する。今の振る舞いは次のとおりである。

-   記事のキーは、生成の開始の入力の検査を通った後の 5 つの値（`videoUrl`・`transcript`・`title`・`channelName`・`description`）のすべてから、サーバのプロセスごとの秘密を鍵とする HMAC-SHA256 で計算する（`internal/articlecache/key.go:55-69`、`0044` F-001、`0044` `02_architecture.md` §3.2）。`videoUrl` は、`https://www.youtube.com/watch?v=<動画 ID>` の形に正規化した値である（`internal/transcript/video_id.go:13-16`・`:55-70`）。
-   キャッシュは、キーごとに 1 つの記録を持ち、キーだけで記録を引く（`internal/articlecache/cache.go:29-39`）。記録は動画 ID を持たない。件数の上限は 100 件で（`cache.go:13`）、サーバを再起動するとすべて失われる（`0044` F-004）。
-   生成の開始は、キーの記録が処理中か完了なら、生成を始めずにそのキーを返し、LLM を呼ばない。失敗なら生成をやり直す（`cache.go:86-88`、`0044` F-001）。受け付けの応答は、生成を始めたか既存のキーを返したかを区別しない（`internal/server/response.go:189-191`）。
-   字幕は、ページで選択された文字列をそのまま使う（`extension/src/core/collect.ts:31`）。このため、5 つの値がすべて同じまま（同じページで同じ選択範囲のまま）押し直せば同じキーが返り、二重には生成されない。一方、選択し直して範囲が 1 文字でも変われば、別の入力として記事を生成し直す（LLM を再び呼ぶ）。概要欄を開いてから送り直した場合も同じである。
-   主ボタンを押すと、Service Worker がビューアのタブを背面で開き、それと同時に生成の開始を 1 回だけ送る（`extension/src/startCoordinator.ts:1-9`、`0050` F-001・F-002）。生成の開始の結果は、ビューアとポップアップの両方に届く。ポップアップを閉じても結果を失わないためである（`0050` 1. 概要の決定）。

キーを入力のすべての値から計算するという今の仕様には筋が通っている。範囲が変われば記事の材料が変わるからである。ただ、利用者が同じ動画の記事を誤って二度依頼しても、そのことに気づきにくい。

対応 issue: [#593](https://github.com/isseis/yt2column/issues/593)（前提: [#503](https://github.com/isseis/yt2column/issues/503)（タスク `0050`）、関連: [#502](https://github.com/isseis/yt2column/issues/502)（タスク `0044`）・[#507](https://github.com/isseis/yt2column/issues/507)（タスク `0046`）・[#501](https://github.com/isseis/yt2column/issues/501)（親）・[#526](https://github.com/isseis/yt2column/issues/526)）

**本書の記述範囲:** 本書は、利用者から見える振る舞いと、サーバとホストの外から見える振る舞いを定める。対象は、照会付きの生成の開始に対するサーバの振る舞い、版の食い違いのときの振る舞い、ポップアップの選択の状態とその操作、ビューアの表示、受理する入力の形、文書である。照会の指定を置く場所（ホストのメッセージか生成の開始の入力か）とその名前と値、応答の形・状態コード・結果のコード、記録に動画 ID を持たせる方法、ポップアップの状態の構造、ビューアの URL に加える値の形、文言（英語と日本語）、受け入れ基準の検証の手段は、設計（`02_architecture.md`）と実装計画で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る（本書は、その項目を H-01 などの番号で示す）。

**issue #593 で決めたこと:**

-   **同じ動画の記事があれば、生成を始める前にポップアップで示す:** 利用者は「現在の選択範囲で記事を生成する」と「既存の記事を表示する」（その記事のビューアを開く）のどちらかを選ぶ。同じ動画の記事がなければ、今と同じく生成を始める。利用者が同じ動画の記事を誤って二度依頼したことに気づけるようにするためである。
-   **「既存の記事がない」は保証ではないので、文言で断定しない:** キャッシュは件数に上限があり、再起動すると消える（`0044` F-004）ためである。
-   **ポップアップに状態を 1 つ加える:** `0046` のセクションの構成と、`0050` の生成中・生成済み・失敗の状態との関係を、本書で決める（F-003）。
-   **アクセシビリティ:** 2 つの選択肢について、[CLAUDE.md](../../../CLAUDE.md)「Accessibility」の各項目の受け入れ条件を定める（4.6）。
-   **プライバシーとログ:** 動画単位の照会がサーバのログや通知に何を残すかを決める（4.2）。
-   **スコープ外:** 字幕の差分の比較や選択範囲の近さによる判定、拡張に記事の履歴を保存すること（`0050` の `chrome.storage` を使わない方針を保つ）、最近の記事の一覧の画面（2.3）。

**要件定義の際に決めたこと（2026-11-03）:**

-   **API は、生成の開始に「同じ動画の記事があれば生成せずに知らせる」指定（照会の指定）を加える形にする（issue の論点 1 の (b)）:** 利用者が「現在の選択範囲で生成する」を選んだら、照会の指定を付けずに送り直す。動画単位の問い合わせの操作を加える案（(a)）は採らない。(b) なら送るのが 1 回で済み、照会と開始の間に競合がなく、振る舞いを送り手が指定した値で選ぶ（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）ためである。照会の指定を置く場所と名前と値は設計で決める（H-01）。
-   **同じ動画は、正規化した `videoUrl` の動画 ID が同じことで判定する（issue の論点 2）:** タイトル・チャンネル名・概要欄・字幕の違いは問わない。issue のスコープ外（字幕の差分や選択範囲の近さによる判定をしない）に合わせるためである。
-   **選択の状態を示すのは、同じ動画の記事（今の入力とキーが違い、処理中か完了のもの）があるときだけにする（issue の論点 4）:** 今の入力と同じキーの記録が処理中か完了なら、今と同じく選択を示さずにそのキーを返す。この場合は二重に生成されず（`0044` F-001）、利用者が選ぶ理由がないためである。失敗した記録は「既存の記事」として示さない。開いても記事がなく、選ぶ意味がないためである。
-   **同じ動画の記事が複数あれば、最新の 1 件だけを示す（issue の論点 3）:** 最新とは、その記録の今の生成の開始を受け付けた時刻（失敗の後のやり直しでは、やり直しの受け付けの時刻。`0044` AC-14）が最も新しいことである。最近の記事の一覧の画面は issue のスコープ外であり、一覧を示すと実質的にその画面になるためである。
-   **照会付きで送ったときに開いたビューアのタブは、既存の記事を表示する:** 同じキーを表示しているビューアがほかにあれば、`0050` F-002 の再利用と同じく、新しいタブは閉じ、先に開いていたビューアが引き継ぐ。ポップアップを閉じていても、費用のかからない方（既存の記事）が手元に残り、`0050` の「ポップアップを閉じても結果は失われない」を保てるためである。タブを閉じてポップアップだけに選択を示す案は、ポップアップを閉じていた場合に何も残らないので採らない。
-   **動画単位で記事の有無とキーが分かることを受け入れ、`0044` の脅威 T-10 を再評価する:** `0044` `02_architecture.md` §3.2 は、キーの計算に秘密を使う理由の 1 つを、生成を始めずに記事の有無を知る手段を作らないこととし、同書の脅威 T-10 とした。照会付きの生成の開始は、検査を通る入力を送れば、その動画の記事の有無とキーを、生成を始めずに返す。T-10 の攻撃者はソケットに接続できる同じ利用者の権限のプロセスで、そのプロセスは信頼する（`docs/dev/security.md` §8、`0044` の T-07）。そのプロセスは、生成の開始でキーを得て投稿を求められ、ブラウザの履歴も読めるので、記事の有無の照会で新しく知ることはない。このため T-10 の記事の有無の照会を、排除する脅威ではなく、信頼の境界の内側で受け入れるリスクとする（5. 制約条件）。キーを秘密から計算することは、キーを不透明に保つ（計算方法に依存させない）ために変えない。秘密を使う目的は、攻撃に対する防御ではなく、公開しないキーの計算方法に依存させないこと（Hyrum's Law）である。
-   **選択の状態の主ボタンは「既存の記事を表示する」にし、「現在の選択範囲で生成する」を副次のボタンにする:** 費用がかからず、誤って二度依頼した場合に安全な方を既定の操作にするためである。
-   **選択の状態は、既存の記事があることと、その状態（生成中か生成済みか）を示す:** 生成中の記事を待つか、選択範囲を変えて生成し直すかを、利用者が決められるようにするためである。
-   **失敗・不明の後の「やり直す」は、やり直す対象の送信と同じ種類で送る:** 照会付きの送信をやり直すときは照会の指定を付け、「現在の選択範囲で生成する」による送信をやり直すときは付けない。利用者がすでに選んだことを、やり直しで覆さないためである。
-   **選択の状態の間に既存の記事が失敗か不明になったら、選択の状態を終え、主ボタンを元の「記事を生成する」（照会付き）に戻す:** 既存の記事が使えなくなったことを示す。押すと照会付きで送るので、同じ動画のほかの記事があれば再び選択の状態になり、なければ生成する。「最新」は受け付けの時刻で選ぶので、新しい処理中の記事が選ばれ、古い完了した記事が示されないことがある。照会なしの「現在の選択範囲で生成する」を主ボタンにすると、完了した記事が残っていても費用のかかる生成へ導くためである（セルフレビューで、照会なしにする当初の案から改めた）。
-   **照会の指定を知らないホストやサーバに送っても、黙って生成しない:** 拡張だけを新しくし、ホストやサーバが本タスクの前の版のままの場合、照会付きの生成の開始は生成を始めず、受け付けにも同じ動画の応答にもならない。今のサーバは、生成の開始の入力にある宣言していないメンバを無視して受理する（`0044` 3.2、`internal/server/request.go:67`）ので、照会の指定の置き方によっては、古いサーバが選択を示さずに生成し、LLM の料金がかかるためである。
-   **版の食い違いでは、専用の表示を出す:** 生成していないことと、拡張・ホスト・サーバの版をそろえる手順を示す。`0050` の想定外の応答の表示（`extension/src/core/native.ts:73-74` がホストの `protocol_error` を想定外の応答にする）は、サーバが生成しているかもしれないことと、同じ入力の送り直しを示すが、版の食い違いでは何も生成されておらず、送り直しても毎回同じ結果になるためである。
-   **ビューアの「既存の記事を表示している」ことの表示は、再読み込み・閉じたタブの復元・履歴からの表示の後も残す:** ビューアの URL に、既存の記事を表示していることを示す値を持たせる。ポップアップを閉じた利用者が、表示された記事を自分の選択範囲から生成したものと誤解しないための表示だからである。
-   **既存の記事を表示しているビューアは、処理中の経過時間を示さない:** 工程の表示だけを示す。サーバは処理中の経過時間を返さず（`0050` 1. 概要の決定）、ビューアの送信の時刻から数えると、既存の記事の生成が実際に続いている時間より短く見えるためである。完了した後は、今と同じくサーバが返す所要時間を示す。

上の決定から導いた振る舞いとして、次の点を要件に含める（レビュアーは PR で確かめる）。

-   **照会付きの生成の開始は、同じ動画の応答を返すとき、何も変えない:** 生成を始めず、LLM を呼ばず、キャッシュの記録を加えも捨てもせず、失敗した同じキーの記録をやり直さない。生成の枠も使わないので、生成の枠に空きがなくても同じ動画の応答を返す（F-001）。
-   **照会なしの生成の開始の振る舞いは変えない:** `0044` F-001 のとおりとする。「現在の選択範囲で生成する」は、この振る舞いで送る。
-   **「既存の記事を表示する」は、`0050` の「ビューアを開く」と同じ順でタブを前面に出し、何も送らない:** この送信の表示を受け持つビューアのタブ、なければ同じキーのほかのビューアのタブ、どちらもなければ新しいタブ、の順である（`0050` F-004）。
-   **ビューアは、既存の記事を表示していることと、現在の選択範囲で生成する手順を示す:** ポップアップを閉じていた場合は、ポップアップの選択の状態を見ないためである（F-004）。
-   **ビューアの見出しは、現在の収集の値から作る:** ビューアの URL の見出し・チャンネル名・動画タイトルは、`0050` F-002 のとおりポップアップの収集の値から作る。同じ動画なので多くは既存の記事と同じだが、動画メタデータが違えば、見出しと記事の中のタイトルが違いうる。これを受け入れる。キャッシュは既存の記事の入力を持たない（`0044` F-004）ので、既存の記事の入力から見出しを作ることはできないためである。
-   **「既存の記事がない」と読める表示をしない:** 照会付きの生成の開始が受け付けられた（同じ動画の記事が見つからなかった）場合の表示は、`0050` の生成中・生成済みの表示のままとし、同じ動画の記事がないことに触れない（F-003、AC-22・AC-30）。
-   **版の食い違いのままでは、主ボタンから生成できない:** 主ボタンは照会付きで送るので、版をそろえるまで、照会付きの生成の開始は毎回通らない。専用の表示がこのことと手順を示す（F-002）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   同じ動画の記事がサーバにあるとき、利用者が生成の前にそれに気づき、既存の記事を開くか、現在の選択範囲で生成し直すかを選べるようにする。
-   照会と生成の開始の間に競合がなく、照会のための送信で記事を生成しないようにする。
-   ホストやサーバの版が古い場合にも、選択を示さずに黙って生成しないようにする。

### 2.2. スコープ (In Scope)

-   照会付きの生成の開始に対するサーバの振る舞い（F-001）。
-   照会の指定を知らないホストやサーバに送った場合の振る舞いと表示（F-002）。
-   ポップアップの選択の状態と、その 2 つの操作、選択の状態の後の状態の移り方、「やり直す」の送り方（F-003）。
-   照会付きの送信で開いたビューアと、既存の記事を表示するビューアの表示（F-004）。
-   文書: README（`README.md` と英語版の `README.en.md`）の「ブラウザ拡張」節と、ジョブの API の説明、`docs/dev/guides/development.md` の「ジョブの API」「ジョブの API のコード」と拒否の理由の表、`docs/dev/security.md` §8、`docs/translation_glossary.md`（F-005）。

### 2.3. スコープ外 (Out of Scope)

-   字幕の差分の比較や、選択範囲の近さによる判定: issue のスコープ外。同じ動画かどうかだけで判定する。
-   拡張に記事の履歴を保存すること: issue のスコープ外。`0050` の `chrome.storage` を使わない方針を保つ。
-   最近の記事の一覧の画面、同じ動画の記事の一覧: issue のスコープ外。1. 概要の決定により、最新の 1 件だけを示す。
-   既存の記事の入力（字幕・動画メタデータ）を示すことや、今の選択範囲との違いを示すこと: 上の 1 件目（字幕の差分の比較）と同じ理由による。キャッシュはコピーした字幕を保持しない（`0044` F-004）。
-   CLI と `/articles` の振る舞い: CLI はキャッシュを使わない。`/articles` の削除は #526 で扱い、本タスクは変えない。
-   キャッシュの永続化と、件数の上限の変更: 1. 概要の決定により、照会はベストエフォートとする。
-   既存の記事を取り消す・削除する操作: issue が求めていない（サーバも利用者の操作による取り消しを持たない。`0044` 2.3）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 照会付きの生成の開始（サーバ）

生成の開始に照会の指定を付けて送ると、サーバは、同じ動画の記事があれば生成を始めずにそのことを返す。

-   照会をするかどうかは、送り手が指定した値で決める。サーバは、入力の中身（字幕の長さや範囲など）から照会の要否を推し量らない。照会なしの生成の開始の振る舞いは、`0044` F-001 のとおりで変えない。
-   **同じ動画:** 検査を通った `videoUrl` の動画 ID が同じこと。タイトル・チャンネル名・概要欄・字幕の違いは問わない（字幕は今と同じく検査するが、同じ動画の判定には使わない）。
-   **同じ動画の記事:** キャッシュにある、同じ動画の記録のうち、今の入力のキーと違うキーで、ジョブの状態が処理中か完了のもの。失敗の記録は含めない。複数あれば、今の生成の開始を受け付けた時刻が最も新しい 1 件とする。
-   照会付きの生成の開始の検査の順序は、照会なしの場合と同じく、パスとメソッドの検査、本文の読み込みと検査の同時実行の上限、本文の読み込みと検査（拒否の理由も同じ）とし、その後に次の表で振る舞いを決める。

| キャッシュの状態 | 振る舞い |
|---|---|
| 今の入力のキーの記録が処理中か完了 | 今と同じく、生成を始めずに、受け付けの応答でそのキーを返す（同じ動画の記事があっても同じ動画の応答にしない） |
| 上に当たらず、同じ動画の記事がある | 生成を始めず、LLM を呼ばず、キャッシュを変えずに、同じ動画の応答を返す。同じ動画の応答は、同じ動画の記事があることと、その記事のキーを持ち、受け付けの応答と区別できる。生成の枠に空きがなくても、キャッシュが件数の上限に達していても、拒否しない |
| どちらにも当たらない | 照会なしの生成の開始と同じ（`0044` F-001 の表。生成を始める、失敗した記録をやり直す、`too_many_requests` で拒否する） |

-   今の入力のキーの記録が失敗で、同じ動画の記事があるときは、同じ動画の応答を返し、失敗した記録をやり直さない。
-   同じ動画の記事を探すことと、生成を始めることは、間にほかの処理を挟まない 1 つの処理として行う。同じ動画の記事がない状態で、同じ動画の違う入力の照会付きの生成の開始が同時に届いたときは、生成を始めるのは 1 つだけとし、ほかは、始めた記録のキーを持つ同じ動画の応答を受け取る。
-   同じ動画の応答を返す処理は、Webhook へ通知しない（新しい API の方針。`0044` F-001）。
-   同じ動画の応答の形（状態コード、`status` などのメンバの値、結果のコード）は設計で決める（H-02）。応答は、`0044` F-005 と同じく、文言・コピーした字幕・URL・動画メタデータ・秘密の値を含まず、コードとキーと `requestId` だけを持つ。
-   照会付きの生成の開始の処理の途中の panic は、今の生成の開始と同じく回復し、`internal_error` で拒否し、サーバは動き続ける（`internal/server/jobs_api.go:46-69`）。

**Acceptance Criteria**:
- **AC-01**: 同じ動画（違う URL の書き方を含む。例: `https://youtu.be/<ID>` と `https://www.youtube.com/watch?v=<ID>`）の別の入力で完了した記事があるとき、選択範囲（`transcript`）だけが違う入力を照会付きで送ると、同じ動画の応答が返り、そのキーは完了した記事のキーである。LLM は呼ばれず、キャッシュの記録の数と各記録の状態は変わらない。
- **AC-02**: 同じ動画の別の入力が処理中のときに照会付きで送ると、同じ動画の応答が返り、そのキーは処理中の記録のキーである。タイトル・チャンネル名・概要欄だけが違う入力でも同じである。
- **AC-03**: 同じ動画の記録が失敗だけのとき、または別の動画の記事だけがあるとき、照会付きで送ると、照会なしの場合と同じく生成が始まり、受け付けの応答が返る。
- **AC-04**: 今の入力と同じキーの記録が処理中か完了のとき、同じ動画のほかの記事があっても、照会付きで送ると、受け付けの応答でそのキーが返り、LLM は呼ばれない。
- **AC-05**: 今の入力と同じキーの記録が失敗で、同じ動画のほかの記事が完了しているとき、照会付きで送ると、同じ動画の応答でその記事のキーが返り、失敗した記録はやり直されず、失敗のままである。
- **AC-06**: 同じ動画の記事が 2 つ以上あるとき、同じ動画の応答のキーは、生成の開始を受け付けた時刻が最も新しい記録のキーである。失敗の後にやり直した記録は、やり直しの受け付けの時刻で比べる。
- **AC-07**: 生成の枠に空きがないとき、またはキャッシュが件数の上限に達して捨てられる記録がないときでも、同じ動画の記事があれば、照会付きの生成の開始は同じ動画の応答を返し、`too_many_requests` で拒否されない。
- **AC-08**: 同じ動画の記事がないとき、同じ動画の違う入力の照会付きの生成の開始を同時に送ると、生成（LLM の呼び出し）は 1 回分だけ始まり、ほかのすべての送信は、始まった記録のキーを持つ同じ動画の応答を受け取る。
- **AC-09**: 照会なしの生成の開始は、同じ動画の記事があっても、`0044` F-001 と同じく振る舞う（今の入力の記事を生成する）。
- **AC-10**: 同じ動画の応答は、エラーの文言、コピーした字幕、URL、動画メタデータ、秘密の値を含まず、同じ動画の応答を返しても Webhook への通知は行われない。
- **AC-11**: 照会付きの生成の開始の処理の途中で panic が起きると、`internal_error` で拒否され、サーバはその後のリクエストに応答する。

#### F-002: 照会の指定を知らないホストやサーバ

拡張が照会付きの生成の開始を送った経路のホストかサーバが本タスクの前の版である場合、生成は始まらず、拡張は版の食い違いの表示を出す。

-   本タスクの前の版とは、コミット `54bca194`（本書の作成の時点の `main`）のホストとサーバである。
-   次の版の組み合わせのそれぞれで、照会付きの生成の開始は、LLM を呼ばず、キャッシュに記録を加えず、受け付けにも同じ動画の応答にもならない（拡張・ホスト・サーバの順）。
    -   新しい拡張・前の版のホスト・前の版のサーバ
    -   新しい拡張・前の版のホスト・新しいサーバ
    -   新しい拡張・新しいホスト・前の版のサーバ
-   このとき、ポップアップとビューアは、`0050` の想定外の応答などの表示の代わりに、版の食い違いの表示を出す。表示は、記事を生成していないことと、拡張・ホスト・サーバを同じ版に更新する手順を示し、同じ入力の送り直しを手順として示さない。版の食い違いをどう見分けるかは設計で決める（H-01）。
-   版をそろえるまで、主ボタン（照会付き）からは生成できない（1. 概要の「導いた振る舞い」）。README にこのことを書く（F-005）。
-   前の版の拡張（`0050` の拡張）が新しいホストとサーバに送る生成の開始は、照会の指定を持たないので、照会なしの生成の開始として `0044` F-001 のとおり受け付けられる（選択の状態は示さない）。

**Acceptance Criteria**:
- **AC-12**: 上の 3 つの版の組み合わせのそれぞれで、照会付きの生成の開始を送ると、LLM は呼ばれず、キャッシュに記録は加わらず、受け付けの応答も同じ動画の応答も返らない（前の版の振る舞いの確かめ方は、設計と実装計画で決める。H-01）。
- **AC-13**: AC-12 の場合、ポップアップとビューアは版の食い違いの表示を出し、想定外の応答の表示は出さない。前の版の拡張が送る、照会の指定のない生成の開始は、新しいホストとサーバで受け付けられる。
- **AC-14**: 版の食い違いの表示は、記事を生成していないことと、拡張・ホスト・サーバを同じ版に更新する手順を、英語と日本語の両方で示し、同じ入力を送り直す手順を含まない（文言を PR のレビューで読む。`manual`）。

#### F-003: ポップアップの選択の状態

主ボタン（「記事を生成する」）を押すと、拡張は照会付きの生成の開始を送る。同じ動画の応答を受け取ると、ポップアップは選択の状態を表示する。

-   主ボタンを押したときの送信（Service Worker が送ること、1 回の押下につき 1 回だけ送ること、ビューアのタブを背面で開くこと、送り手の検査）は、`0050` F-001・F-002 のとおりとし、生成の開始に照会の指定を付ける。
-   **選択の状態の表示:** 動画のセクションと詳細はそのまま残し、確認のセクションの位置に、このサーバに同じ動画の記事があることと、その記事の状態（生成中か生成済みか）を示す。記事の状態は、ポップアップが同じ動画の応答のキーで状態の取得を繰り返して知る（`0050` F-003 と同じ規則で続け、止める）。選択の状態の文言は、ほかに同じ動画の記事がないことや、この記事が今後も残ることを断定しない。
-   **2 つの操作:** 操作のセクションに、主ボタン「既存の記事を表示する」と、副次のボタン「現在の選択範囲で生成する」を置く。どちらも、選択の状態になった時点から押せる。英語の名前は設計で決める（H-04）。2 つのボタンは、`0046` AC-17 と同じ条件で、スクロールせずに全体が見える。
-   **「既存の記事を表示する」:** `0050` F-004 の「ビューアを開く」と同じ順で、同じ動画の応答のキーのビューアのタブを前面に出す（この送信の表示を受け持つビューアのタブ、なければ同じキーのほかのビューアのタブ、どちらもなければ新しいタブ）。生成の開始は送らない。新しいタブで開くビューアの URL は、そのキー、現在の収集の値から作る見出しなど（`0050` F-002）、送信の時刻（押した時刻）、既存の記事を表示していることを示す値（F-004）を持つ。押した後もポップアップが開いていれば、選択の状態のまま変わらない。
-   **「現在の選択範囲で生成する」:** 主ボタンを押したときと同じ入力で、照会なしの生成の開始を送る。送信は `0050` F-001・F-002 と同じく、Service Worker が 1 回だけ送り、ビューアのタブを背面で新しく開く。押した後、ポップアップは `0050` F-004 の送信中・キーを受け取れなかった・処理中・完了・失敗・不明の状態に移る。既存の記事を表示しているビューアのタブは閉じない。
-   **同じ動画の応答を受け取っても、拡張は自動では何も送らない:** 照会なしの生成の開始を送るのは、利用者が「現在の選択範囲で生成する」か、その後の「やり直す」を押したときだけである。
-   **選択の状態での状態の取得の結果:** 次の表のとおりとする。通知の文言と出し方は、`0050` F-004 の通知に合わせて設計で決める（H-03）。

| 状態の取得の結果 | 選択の状態の扱い | ボタン | 状態の取得の繰り返し |
|---|---|---|---|
| 最初の結果を受け取る前 | 保つ。既存の記事の状態は、取得中であることを示す | 2 つとも押せる | 続ける |
| 処理中・完了 | 保つ。生成中か生成済みかを示す（生成中から完了に変わったら、生成済みにする） | 2 つとも押せる | `0050` F-003 と同じ（完了で止める） |

**Acceptance Criteria**:
- **AC-15**: 主ボタンを押すと、ホストは照会付きの生成の開始のメッセージを 1 つだけ受け取る。その入力は、`0050` AC-01 と同じ収集の値から作る値である。
- **AC-16**: 同じ動画の応答を受け取ると、ポップアップは動画のセクションと詳細を残したまま、同じ動画の記事があることと、その記事の状態（生成中か生成済みか）を示し、主ボタンは「既存の記事を表示する」、副次のボタンは「現在の選択範囲で生成する」になる。生成中の記事が完了すると、生成済みの表示に変わる。2 つのボタンは、`0046` AC-17 と同じ条件で、スクロールせずに全体が見える。
- **AC-17**: 同じ動画の応答を受け取った後、どのボタンも押さなければ、ホストが受け取る生成の開始のメッセージは最初の 1 つのままである（状態の取得のメッセージだけが加わる）。
- **AC-18**: 選択の状態で「既存の記事を表示する」を押すと、同じ動画の応答のキーのビューアのタブが、`0050` AC-21 と同じ順で前面に出る。生成の開始は送られない。同じキーのビューアがどこにもなければ、新しいタブで開いたビューアは、既存の記事を表示していることを示す（AC-25）。
- **AC-19**: 選択の状態で「現在の選択範囲で生成する」を押すと、ホストは照会の指定のない生成の開始のメッセージを 1 つだけ受け取り、その入力は最初の送信と同じである。新しいビューアのタブが 1 つ背面で開き、既存の記事を表示しているタブは閉じない。ポップアップは送信中の状態に移り、その後は `0050` F-004 の状態を表示する。
- **AC-20**: 選択の状態で、既存の記事の状態の取得が失敗か不明を返すと、ポップアップは選択の状態を終えて、同じ動画の記事が使えなくなったことを示し、主ボタンは「記事を生成する」になり、副次のボタンはなくなる。押すと、照会付きの生成の開始が 1 回だけ送られる。

#### F-004: 既存の記事を表示するビューア

照会付きの送信で開いたビューアは、同じ動画の応答を受け取ると、既存の記事を表示し、そのことを示す。

-   同じ動画の応答を受け取ったビューアは、同じ動画の応答のキーを受け付けの応答のキーと同じように扱う。URL にそのキーと、既存の記事を表示していることを示す値を加え、状態を取得して表示する（`0050` F-002・F-003）。同じキーを表示しているビューアがほかにあれば、`0050` F-002 の再利用と同じく、新しいビューアは自分のタブを閉じ、先に開いていたビューアが引き継ぐ。引き継いだビューアも、自分の URL に既存の記事を表示していることを示す値を加える。
-   引き継いだビューアの送信の時刻とポーリングは、`0050` F-002 のとおりとする。引き継いだビューアが処理中か完了を表示していれば、そのまま表示とポーリングを続け、送信の時刻を変えない。失敗か不明を表示していた場合、または状態を取得できずにポーリングを止めていた場合は、送信の時刻を送り直した時刻に改め、ポーリングを再び始める。
-   URL に既存の記事を表示していることを示す値を持つビューア（再読み込み・閉じたタブの復元・履歴からの表示の後を含む。以下、既存の記事のビューア）は、次を示す。

    -   処理中のときは、工程ごとの状態を示し、経過時間を示さない。完了したときは、`0050` と同じく、サーバが返す所要時間を示す。
-   既存の記事のビューアのそのほかの表示と操作（記事の表示、投稿・保存・コピー、失敗・不明の表示）は、`0050` のとおりとする。

**Acceptance Criteria**:
- **AC-25**: 照会付きの送信で開いたビューアが同じ動画の応答を受け取ると、その URL は同じ動画の応答のキーと、既存の記事を表示していることを示す値を持ち、ビューアはそのキーの状態を表示し、同じ動画の既存の記事を表示していることと、現在の選択範囲で生成する手順を示す。照会付きの送信が受け付けられた場合（同じ動画の応答でない場合）のビューアは、これを示さない。

- **AC-27**: 既存の記事のビューアは、再読み込み、閉じたタブの復元、履歴からの表示の後も、AC-25 の表示を示す。処理中のときは工程ごとの状態を示し、経過時間を示さない。完了したときは所要時間を示す。
- **AC-28**: AC-25 の表示は、同じ動画の既存の記事を表示していて、現在の選択範囲からは生成していないことと、現在の選択範囲で生成する手順を、英語と日本語の両方で示す（文言を PR のレビューで読む。`manual`）。

-   `docs/translation_glossary.md` に、新しい用語（同じ動画の照会、照会付きの生成の開始、同じ動画の応答、選択の状態、既存の記事、既存の記事のビューア、副次のボタン、現在の選択範囲）を加え、既存の用語の定義を改める（主ボタン: 選択の状態の「既存の記事を表示する」と、選択の状態を終えた後の「記事を生成する」を加える。送信の時刻: 「現在の選択範囲で生成する」・選択の状態を終えた後の「記事を生成する」・「既存の記事を表示する」（新しいタブを開く場合）を押した時刻を加える。ビューアの URL: 既存の記事を表示していることを示す値を加える）。

**Acceptance Criteria**:
- **AC-29**: README（両方）・`development.md`・`security.md`・`translation_glossary.md` の記述が、F-001 から F-004 の振る舞いと合っている（PR のレビューで読む。`manual`）。拒否の理由やコードを加えた場合、README と `development.md` の表の値の集合は、サーバと拡張が定義する値の集合と一致する。
- **AC-30**: ポップアップ・ビューア・README のどの表示と記述も、同じ動画の記事がサーバにないことを断定しない（照会付きの送信が受け付けられたときの表示は、同じ動画の記事がなかったことに触れない）。README は、照会がベストエフォートであることを示す（英語と日本語の文言を PR のレビューで読む。`manual`）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

サーバと同じ利用者の権限で動くプロセスは信頼する（`security.md` §8）。境界の検査は、`0044` 3.2 と `0050` 3.2 と同じ厳しさで行う。照会の指定は振る舞いを選ぶ値なので、受理する形でない照会の指定を、照会の指定がないものとして扱わない（無視して生成しない）。

- **AC-32**: 同じ動画の応答で、`0050` AC-41 が挙げる形の誤り（メンバの重複、対になっていないサロゲートのエスケープ、正しくない UTF-8、先頭の BOM、宣言していないメンバ、足りないメンバ、閉じた集合にないコード、状態コードと `status` の組が合わないもの、後続のデータ、上限の超過）を持つもの、キーが空か文字列でないものは、いずれも想定外の応答になり、ポップアップは選択の状態を表示せず、ビューアはそのキーを使わない。
- **AC-33**: 拡張自身のポップアップ以外の送り手からの生成の開始の求め（照会付き・照会なし）では、Service Worker はホストに何も送らず、タブも開かない。ビューアの URL の、既存の記事を表示していることを示す値が、決めた形でない、重複する、またはキーを持たない URL にあるとき、ビューアはリンクが正しくないことを表示し、状態の取得を送らない。拡張自身のページ以外からの、生成の開始の結果と引き継ぎのメッセージは無視される。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   同じ動画の記事を探す処理は、キャッシュの件数の上限（100 件。`cache.go:13`）の記録をたどるだけで、LLM の呼び出しに比べて無視できる時間である。索引などの探す処理を速める仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   同じ動画の応答は LLM と Webhook を待たずに返る。ホストの 20 秒の打ち切り（`internal/nmhost/relay.go:31`）の中に収まればよい。

### 4.2. セキュリティ (Security)

本タスクは、LLM API への送信（生成）を始めるかどうかを変え、記録に動画 ID を持たせ、ログに残す値を変えるので、`docs/dev/security.md` を適用する。

-   **動画単位で記事の有無とキーが分かること:** 照会付きの生成の開始は、検査を通る入力を送れば（字幕は検査を通る形であれば中身を問わない）、その動画の記事の有無とキーを、生成を始めずに返す。キーを知れば、状態の取得でその記事を読み、投稿の操作で Webhook へ投稿を求められる。これを受け入れる理由は、ソケットに接続できるのは同じ利用者の権限のプロセスだけで、そのプロセスは信頼する（`security.md` §8）ことである。そのプロセスは、今も `.envrc` を読んで LLM API と Webhook を直接使える（`security.md` §8）ので、守る資産は変わらない。他ユーザーのプロセスとウェブページは、今と同じく UDS とその権限で排除する（`security.md` §8.2）。記事の有無の照会は、このプロセスにとって新しい手段にならない。生成の開始でキーを得られ（`0044` の T-10 の残るリスク）、キーがあれば投稿を求められ（`0044` の T-07）、ブラウザの履歴も読めるためである。このため `0044` の T-10 は、排除する脅威ではなく、信頼の境界の内側で受け入れるリスクとして再評価する（5. 制約条件）。
-   **待ち受けの範囲とホストの制約:** 今と同じく、Unix ドメインソケットの上だけで受け、TCP を待ち受けない。ホストの起動の制約（拡張の origin の検査、`HOME` だけを読む、プロキシを使わない、再送しない。`security.md` §8.2）を保つ。拡張に任意のパスを指定させない（`0044` F-008）。
-   **メモリに持つ値:** 記録は、同じ動画の判定のために動画 ID を持つ。動画 ID は記録が捨てられるか、サーバが再起動するまでメモリにあり、ディスクには書かれない。完了した記録は、今も記事のファイルの中身（`0044` F-002）のフロントマターに出典の URL（動画 ID を含む）を持つ（`internal/publisher/file_render.go:49`）。処理中と失敗の記録が動画 ID を持つことは新しいが、キャッシュの記録の寿命（`0044` F-004）を超えない。コピーした字幕は、今と同じく生成の後に持たない（`0044` F-004）。
-   **ログと通知:** 照会付きの生成の開始のログも、今の方針（`0044` 4.2）に従う。1 つの出来事を 1 行で、固定の属性だけを出し、`redact.Writer` を通す。今の生成の開始のログはキー・動画 ID・結果のコードを出す（`internal/server/jobs_api.go:132`）。同じ動画の応答を返したことは、結果のコードの新しい値として出し、本文、コピーした字幕、`videoUrl` の文字列、動画メタデータ、記事の本文、秘密の値を出さない。同じ動画の応答で返した既存の記事のキーをログに出すかは設計で決める（H-06）。Webhook への通知は行わない（F-001）。拡張の開発者向けのログは、今の方針（`security.md` §8.1）に従い、キーと動画メタデータの値を出さない。
-   **権限を広げない:** 拡張の manifest の権限は今のまま（`activeTab`・`scripting`・`nativeMessaging`）とし、`storage`・`tabs` などを加えない（`0050` 4.2）。
-   **自動で再送しない:** 同じ動画の応答を受け取っても、拡張は生成の開始を自動では送らない（F-003、AC-17）。
-   **ビューアの URL:** 既存の記事を表示していることを示す値は、ブラウザの履歴に残る。値は、そのビューアが既存の記事を表示していることだけを表し、入力や既存の記事の値を含まない。
-   **プロンプトへの埋め込み:** コピーした字幕と動画メタデータを記事生成のプロンプトに埋め込むことは変えない。同じ動画の応答を返す場合は、プロンプトを作らない。

**Acceptance Criteria**:
- **AC-34**: 同じ動画の応答を返した生成の開始は、ログに 1 行で記録され、その行は固定の属性と、同じ動画の応答を示す結果のコードの値を持ち、本文、コピーした字幕、`videoUrl` の文字列、動画メタデータ、秘密の値を含まない。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   照会はベストエフォートである。同じ動画の記事がキャッシュの件数の上限で捨てられた後、またはサーバの再起動の後は、選択を示さずに生成する（`0044` F-004・4.3）。README にこのことを書く（F-005）。
-   同じ動画の応答を返した後、既存の記事が捨てられるか失敗する場合がある。そのときのポップアップの表示は F-003（選択の状態を終える）、ビューアの表示は `0050` F-003（記事が失われた・失敗）に従う。
-   照会付きの生成の開始の処理の途中の panic は、今と同じく回復する（F-001、AC-11）。

### 4.4. 互換性 (Compatibility)
-   照会なしの生成の開始、状態の取得、投稿の操作、`/articles` の振る舞いは変えない（F-001・F-002）。
-   本タスクの後の版の拡張は、本タスクの後の版のホストとサーバを必要とする。版が食い違った場合は、黙って生成せずに版の食い違いの表示を出し、版をそろえるまで主ボタンから生成できない（F-002）。README に、拡張・ホスト・サーバを同じ版に更新するよう書く（F-005）。
-   ポップアップの送る前の画面（`0046`）と、`0050` の各状態の表示は、選択の状態と版の食い違いの表示を加えるほかは変えない。

### 4.5. 保守性 (Maintainability)
-   照会の指定の有無、同じ動画の応答、ポップアップの選択の状態、「やり直す」が送る種類は、閉じた集合の値で表し、その値で振る舞いを選ぶ（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。照会の指定がないことの解釈は照会なしの送信とする。入力について最も仮定の少ない解釈（生成しない）にしないのは、前の版の拡張が照会の指定を持たない生成の開始を送り、それを今と同じく受け付ける必要がある（F-002）ためである。
-   同じ動画の判定に使う動画 ID は、今の `videoUrl` の検査が返す値を使い、URL の解析を別に実装しない（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   「既存の記事を表示する」のタブの探し方と前面に出し方は、`0050` の「ビューアを開く」の処理を使い、二重に実装しない。

### 4.6. アクセシビリティ (Accessibility)

ポップアップの選択の状態、選択の状態を終えた後の表示、版の食い違いの表示、既存の記事のビューアの新しい表示は、[CLAUDE.md](../../../CLAUDE.md)「Accessibility」に従い、WCAG 2.2 のレベル AA を満たす（押せる要素の大きさと動きはレベル AAA の値）。この節の各 AC の検証は、実装計画で `test` または `static` の検証を割り当てる（色のコントラストは色の変数から計算するなど）。ブラウザでの見え方の確認は、それに加えて行う。

**Acceptance Criteria**:
- **AC-35**（キーボード）: 選択の状態の「既存の記事を表示する」と「現在の選択範囲で生成する」、選択の状態を終えた後の「記事を生成する」は、Tab・Shift+Tab・Enter・Space だけで操作できる。フォーカスの順序は見た目の順序に従い、フォーカスを閉じ込めない。キーボードで押した主ボタンが選択の状態の主ボタンに変わったとき、フォーカスの扱いは `0050` の主ボタンの扱い（どの要素にもフォーカスがないとき、押せるようになった主ボタンにフォーカスを戻す）と同じである。副次のボタンにフォーカスがある間に選択の状態を終えて副次のボタンがなくなったときは、フォーカスを主ボタンに移す。
- **AC-36**（見えるフォーカス）: 2 つのボタンのフォーカスは、隣り合う色に対して 3:1 以上のコントラストの印で示される。ライトとダークの両方で満たす。
- **AC-37**（名前・役割・状態）: 2 つのボタンはネイティブの `<button>` で作り、見える名前と一致する名前を持つ。押せないボタンは、押せないことが支援技術に伝わる。主ボタンと副次のボタンの違いは、見た目の重みだけでなく、名前と位置でも分かる。
- **AC-38**（状態のメッセージ）: 選択の状態になったこと、既存の記事の状態（生成中か生成済みか）とその変化、選択の状態を終えたこと（既存の記事が使えなくなったこと）、状態を取得できないことの通知、版の食い違い、ビューアの「既存の記事を表示している」ことは、フォーカスを動かさずに支援技術に伝わる。
- **AC-39**（コントラスト・色だけに頼らない）: 新しい表示の文字は、背景に対して 4.5:1 以上、意味のある図形は 3:1 以上で、ライトとダークの両方で満たす。既存の記事の状態（生成中か生成済みか）は、色だけでなく文字でも区別できる。
- **AC-40**（言語）: ポップアップとビューアの `lang` は、表示の言語と一致する（`0050` AC-49 と同じ。新しい文言にも当てはまる）。
- **AC-41**（押せる大きさ）: 2 つのボタンと、選択の状態を終えた後の「記事を生成する」は、それぞれ 44×44 CSS ピクセル以上である。
- **AC-42**（動き）: 選択の状態で既存の記事の生成中を示す動きがあれば、`prefers-reduced-motion` が `reduce` のとき止まる。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。
-   **以前のタスクの判断の再評価:** `0044` `02_architecture.md` §3.2「秘密を使う理由」と、同書の脅威 T-10 は、秘密を使わないハッシュだと、生成の開始を呼ばずに状態の取得で記事の有無を調べる手段になるとして、キーを生成の開始の応答からしか得られないようにした。本タスクは、この記事の有無の照会を、排除する脅威ではなく、信頼の境界の内側で受け入れるリスクとして再評価する。T-10 の攻撃者は同じ利用者の権限のプロセスで、`0044` はそのプロセスを信頼する（T-07、`security.md` §8）。そのプロセスは生成の開始でキーを得られ（T-10 の残るリスク）、ブラウザの履歴も読めるので、記事の有無の照会で新しく知ることはない（1. 概要の決定、4.2）。この再評価により、本タスクの照会付きの生成の開始が、動画単位で、生成を始めずに記事の有無とキーを返すことは、`0044` の方針の例外ではない。キーを秘密から計算すること（同じ入力のキーを、生成の開始を呼ばずに計算できないこと）と、キーが不透明であることは、キーの計算方法に依存させないために変えない。秘密を使う目的は、攻撃に対する防御ではなく、公開しないキーの計算方法に依存させないこと（Hyrum's Law）である。承認済みの `0044` `02_architecture.md` は当時の決定の記録として変えず、再評価は本書と `security.md` §8 に書く（F-005）。
-   **以前のタスクの方針の例外:**
    -   `0044` F-001「応答は、生成を始めたか、既存のジョブまたは記事を返したかを区別しない」は、区別して返すかを設計に任せていた。本タスクは、照会付きの生成の開始で同じ動画の記事を返す場合を、同じ動画の応答として区別する。照会なしの生成の開始の応答は変えない。方針の変更ではなく、`0044` が残した選択である。
    -   `0050` F-001「1 回の押下につき生成の開始を 1 回だけ送る」と「自動では送り直さない」は保つ。「現在の選択範囲で生成する」と、選択の状態を終えた後の「記事を生成する」は、利用者の別の押下である。
    -   `0050` 1. 概要の決定「処理中の経過時間は、そのビューアを開いた送信の時刻から数える」は、既存の記事のビューアには当てはめない。既存の記事のビューアは、処理中の経過時間を示さない。理由は 1. 概要の決定のとおり、送信の時刻から数えると既存の記事の生成の時間より短く見えることである。
-   **ホストの判定の例外（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」の例外の 1 つ）:** ホストが今の形と新しい形を見分ける判定（`internal/nmhost/relay.go` の `route`）は、#526 で取り除く予定の例外である。照会の指定をホストのメッセージに置く場合（H-01）も、新しい形の中の判定は、指定した値による分岐で行い、例外の範囲を広げない。
-   ユニットテストは、実際のブラウザ・ホスト・サーバ・LLM を呼ばない。ブラウザの API と LLM は fake に置き換える（[CLAUDE.md](../../../CLAUDE.md)「Testing Strategy」）。
-   外部のライブラリと npm のパッケージを加えない（[CLAUDE.md](../../../CLAUDE.md)「Dependencies」）。

## 6. 用語集 (Glossary)

-   **0044・0046・0050**: それぞれ、サーバとホストに新しい API を加えたタスク（`docs/tasks/0044_article_job_api/`）、ポップアップの画面を再設計したタスク（`docs/tasks/0046_popup_redesign/`）、拡張を新しい API に移しビューアを加えたタスク（`docs/tasks/0050_viewer_tab/`）。
-   **同じ動画:** 検査を通った `videoUrl` の動画 ID が同じこと。
-   **同じ動画の記事:** キャッシュにある同じ動画の記録のうち、今の入力のキーと違うキーで、ジョブの状態が処理中か完了のもの（F-001）。
-   **同じ動画の照会:** 生成の開始で、同じ動画の記事があれば生成せずに知らせるよう求めること。そのための値を**照会の指定**と呼ぶ。置く場所と名前は設計で決める。
-   **照会付きの生成の開始:** 照会の指定を付けた生成の開始。主ボタン（「記事を生成する」）を押したとき、選択の状態を終えた後の「記事を生成する」を押したとき、それらの送信をやり直したときに送る。**照会なしの生成の開始**は、照会の指定のない生成の開始で、`0044` F-001 のとおり振る舞う。
-   **同じ動画の応答:** 照会付きの生成の開始に、同じ動画の記事があるときにサーバが返す応答。生成を始めず、その記事のキーを持つ。受け付けの応答とは区別する。
-   **選択の状態:** 同じ動画の応答を受け取った後のポップアップの状態。「既存の記事を表示する」と「現在の選択範囲で生成する」を選べる。`0046` の確認のセクション（送る前に選択範囲や概要欄を確かめる行を並べるセクション）とは別のものである。
-   **既存の記事:** 同じ動画の応答のキーの記事。
-   **既存の記事のビューア:** URL に、既存の記事を表示していることを示す値を持つビューア（F-004）。
-   **副次のボタン:** 選択の状態で主ボタンの隣に置く「現在の選択範囲で生成する」のボタン。
-   **現在の選択範囲:** ポップアップを開いたときに集めた選択範囲（`0050` の収集の値）。押した時点で集め直したものではない。
-   **版の食い違い:** 本タスクの後の版の拡張と、本タスクの前の版のホストかサーバを組み合わせて使うこと（F-002）。
-   **主ボタン・確認のセクション・ビューア・ビューアの URL・送信の時刻・やり取りの結果・結果不明・記事のキー・ジョブの状態:** `0046`・`0050` と [translation_glossary.md](../../translation_glossary.md) の定義による（F-005 で改める定義を含む）。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
