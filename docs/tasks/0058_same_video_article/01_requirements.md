## 1. 概要 (Overview)

**目的:** 本書は、ポップアップの主ボタンを押したときに、同じ動画の記事がサーバのキャッシュにあれば、生成を始める前にそのことを示し、利用者が「現在の選択範囲で記事を生成する」か「既存の記事を表示する」かを選べるようにするための要件を定義する。

**背景:**

本書の用語（「宣言付きの生成の開始」「同じ動画の記事」など）は 6 章で定義する。

タスク `0050_viewer_tab`（[#503](https://github.com/isseis/yt2column/issues/503)）の後、拡張はサーバのジョブの API（[#502](https://github.com/isseis/yt2column/issues/502)、タスク `0044_article_job_api`）で記事を生成する。今の振る舞いは次のとおりである。

-   記事のキーは、生成の開始の入力の検査を通った後の 5 つの値（`videoUrl`・`transcript`・`title`・`channelName`・`description`）のすべてから、サーバのプロセスごとの秘密を鍵とする HMAC-SHA256 で計算する（`internal/articlecache/key.go:55-69`、`0044` F-001、`0044` `02_architecture.md` §3.2）。`videoUrl` は、`https://www.youtube.com/watch?v=<動画 ID>` の形に正規化した値である（`internal/transcript/video_id.go:13-16`・`:55-70`）。
-   キャッシュは、キーごとに 1 つの記録を持ち、キーだけで記録を引く（`internal/articlecache/cache.go:29-39`）。記録は動画 ID を持たない。件数の上限は 100 件で（`cache.go:13`）、サーバを再起動するとすべて失われる（`0044` F-004）。
-   生成の開始は、キーの記録が処理中か完了なら、生成を始めずにそのキーを返し、LLM を呼ばない。失敗なら生成をやり直す（`cache.go:88-90`、`0044` F-001）。受け付けの応答は、生成を始めたか既存のキーを返したかを区別しない（`internal/server/response.go:189-191`）。
-   字幕は、ページで選択された文字列をそのまま使う（`extension/src/core/collect.ts`）。このため、同じ選択範囲で押し直せば同じキーが返り、二重には生成されない。一方、選択し直して範囲が 1 文字でも変われば、別の入力として記事を生成し直す（LLM を再び呼ぶ）。概要欄を開いてから送り直した場合も同じである。
-   主ボタンを押すと、Service Worker がビューアのタブを背面で開き、それと同時に生成の開始を 1 回だけ送る（`extension/src/startCoordinator.ts:1-9`、`0050` F-001・F-002）。生成の開始の結果は、ビューアとポップアップの両方に届く。ポップアップを閉じても結果を失わないためである（`0050` 1. 概要の決定）。

キーを入力のすべての値から計算するという今の仕様には筋が通っている。範囲が変われば記事の材料が変わるからである。ただ、利用者が同じ動画の記事を誤って二度依頼したとき、それを見逃しやすい。

対応 issue: [#593](https://github.com/isseis/yt2column/issues/593)（前提: [#503](https://github.com/isseis/yt2column/issues/503)（タスク `0050`）、関連: [#502](https://github.com/isseis/yt2column/issues/502)（タスク `0044`）・[#507](https://github.com/isseis/yt2column/issues/507)（タスク `0046`）・[#501](https://github.com/isseis/yt2column/issues/501)（親）・[#526](https://github.com/isseis/yt2column/issues/526)）

**本書の記述範囲:** 本書は、利用者から見える振る舞いと、サーバとホストの外から見える振る舞いを定める。対象は、宣言付きの生成の開始に対するサーバの振る舞い、版の食い違いのときの振る舞い、ポップアップの確認の状態とその操作、ビューアの表示、受理する入力の形、文書である。宣言を置く場所（ホストのメッセージか生成の開始の入力か）とその名前と値、応答の形と状態コードとコード、記録に動画 ID を持たせる方法、ポップアップの状態の構造、文言（英語と日本語）、受け入れ基準の検証の手段は、設計（`02_architecture.md`）と実装計画で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #593 で決めたこと:**

-   **同じ動画の記事があれば、生成を始める前にポップアップで示す:** 利用者は「現在の選択範囲で記事を生成する」と「既存の記事を表示する」（その記事のビューアを開く）のどちらかを選ぶ。同じ動画の記事がなければ、今と同じく生成を始める。利用者が同じ動画の記事を誤って二度依頼したことに気づけるようにするためである。
-   **「既存の記事がない」は保証ではないので、文言で断定しない:** キャッシュは件数に上限があり、再起動すると消える（`0044` F-004）ためである。
-   **確認の状態を、ポップアップの状態の 1 つとして加える:** `0046` のセクションの構成と、`0050` の生成中・生成済み・失敗の状態との関係を、本書で決める（F-003）。
-   **アクセシビリティ:** 2 つの選択肢について、[CLAUDE.md](../../../CLAUDE.md)「Accessibility」の各項目の受け入れ条件を定める（4.6）。
-   **プライバシーとログ:** 動画単位の照会がサーバのログや通知に何を残すかを決める（4.2）。
-   **スコープ外:** 字幕の差分の比較や選択範囲の近さによる判定、拡張に記事の履歴を保存すること（`0050` の `chrome.storage` を使わない方針を保つ）、最近の記事の一覧の画面（2.3）。

**要件定義の際に決めたこと（2026-11-03）:**

-   **API は、生成の開始に「同じ動画の記事があれば生成せずに知らせる」宣言を加える形にする（issue の論点 1 の (b)）:** 利用者が「現在の選択範囲で生成する」を選んだら、宣言を付けずに送り直す。動画単位の問い合わせの操作を加える案（(a)）は採らない。(b) なら送るのが 1 回で済み、問い合わせと開始の間に競合がなく、振る舞いを宣言した値で選ぶ（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）ためである。宣言を置く場所と名前と値は設計で決める（H-01）。
-   **同じ動画は、正規化した `videoUrl` の動画 ID が同じことで判定する（issue の論点 2）:** タイトル・チャンネル名・概要欄・字幕の違いは問わない。issue のスコープ外（字幕の差分や選択範囲の近さによる判定をしない）に合わせるためである。
-   **確認を出すのは、今の入力とキーが違う、処理中か完了の同じ動画の記事があるときだけにする（issue の論点 4）:** 今の入力と同じキーの記録が処理中か完了なら、今と同じく確認を出さずにそのキーを返す。この場合は二重に生成されない（`0044` F-001）ので、確認する理由がないためである。失敗した記録は「既存の記事」として示さない。開いても記事がなく、選ぶ意味がないためである。
-   **同じ動画の記事が複数あれば、最新の 1 件だけを示す（issue の論点 3）:** 最新とは、その記録の今の生成の開始を受け付けた時刻（失敗の後のやり直しでは、やり直しの受け付けの時刻。`0044` AC-14）が最も新しいことである。最近の記事の一覧の画面は issue のスコープ外であり、一覧を示すと実質的にその画面になるためである。
-   **宣言付きで送ったときに開いたビューアのタブは、既存の記事を表示する:** 同じキーを表示しているビューアがほかにあれば、`0050` F-002 の再利用と同じく、新しいタブは閉じ、既存のビューアが引き継ぐ。ポップアップを閉じていても、費用のかからない方（既存の記事）が手元に残り、`0050` の「ポップアップを閉じても結果は失われない」を保てるためである。タブを閉じてポップアップだけに確認を出す案は、ポップアップを閉じていた場合に何も残らないので採らない。
-   **動画単位で記事の有無とキーが分かることを、`0044` の設計の理由の例外として受け入れる:** `0044` `02_architecture.md` §3.2 は、キーの計算に秘密を使う理由の 1 つを、生成を始めずに記事の有無を知る手段を作らないこととした。宣言付きの生成の開始は、正しい形の入力（字幕の中身は問わない）を送れば、その動画の記事の有無とキーを、生成を始めずに返す。同じ利用者の権限のプロセスは信頼する（`docs/dev/security.md` §8）ので、守る資産は変わらないためである（5. 制約条件）。
-   **確認の状態の主ボタンは「既存の記事を表示する」にし、「現在の選択範囲で生成する」を副次のボタンにする:** 費用がかからず、誤って二度依頼した場合に安全な方を既定の操作にするためである。
-   **確認の状態は、既存の記事があることと、その状態（生成中か生成済みか）を示す:** 生成中の記事を待つか、選択範囲を変えて生成し直すかを、利用者が決められるようにするためである。
-   **失敗・不明の後の「やり直す」は、やり直す対象の送信と同じ種類で送る:** 宣言付きの送信をやり直すときは宣言を付け、「現在の選択範囲で生成する」による送信をやり直すときは宣言を付けない。利用者がすでに選んだことを、やり直しで覆さないためである。
-   **確認を表示している間に既存の記事が失敗か不明になったら、確認の状態を終える:** 既存の記事が使えなくなったことを示し、主ボタンを「現在の選択範囲で生成する」（宣言を付けない送信）にする。「既存の記事を表示する」を残しても、開いた先には失敗か不明が表示されるだけであり、ポップアップは既存の記事の入力を持たないので、その記事をやり直すことはできないためである。
-   **宣言を知らないホストやサーバに送っても、黙って生成しない:** 拡張だけを新しくし、ホストやサーバが本タスクの前の版のままの場合、宣言付きの生成の開始は生成を始めず、拡張には受け付け以外の結果（拒否・想定外の応答など）として現れる。今のサーバは生成の開始の入力の宣言していないメンバを無視して受理する（`0044` 3.2、`internal/server/request.go:67`）ので、宣言の置き方によっては、古いサーバが確認をせずに生成し、LLM の料金がかかるためである。

上の決定から導いた振る舞いとして、次の点を要件に含める（レビュアーは PR で確かめる）。

-   **宣言付きの生成の開始は、確認の応答では何も変えない:** 生成を始めず、LLM を呼ばず、キャッシュの記録を加えも捨てもせず、失敗した同じキーの記録をやり直さない。生成の枠も使わないので、生成の枠に空きがなくても確認の応答を返す（F-001）。
-   **宣言を付けない生成の開始の振る舞いは変えない:** `0044` F-001 のとおりとする。「現在の選択範囲で生成する」は、この振る舞いで送る。
-   **「既存の記事を表示する」は、`0050` の「ビューアを開く」と同じ順でタブを前面に出し、何も送らない:** この送信の表示を受け持つビューアのタブ、なければ同じキーのほかのビューアのタブ、どちらもなければ新しいタブ、の順である（`0050` F-004）。生成の開始は送らない。
-   **ビューアは、既存の記事を表示していることと、現在の選択範囲で生成する手順を示す:** 宣言付きの送信で開いたビューアが既存の記事を表示したとき、利用者は自分の選択範囲から生成された記事だと誤解しうる。ポップアップを閉じていた場合は、ポップアップの確認も見ない。このため、ビューアは、同じ動画の既存の記事を表示していること（現在の選択範囲からは生成していないこと）と、現在の選択範囲で生成する手順（ポップアップから送り、「現在の選択範囲で生成する」を選ぶ）を示す（F-004）。
-   **経過時間の起点は `0050` の規則に従う:** 既存の記事が処理中のとき、宣言付きの送信で開いた新しいビューアは、その送信の時刻から経過時間を数える。既存のビューアが引き継いだ場合は、そのビューアの送信の時刻を変えない（`0050` F-002・1. 概要の決定）。`0050` で同じ入力を送り直した場合と同じ規則である。
-   **「既存の記事がない」と読める表示をしない:** 宣言付きの生成の開始が受け付けられた（同じ動画の記事が見つからなかった）場合の表示は、`0050` の生成中・生成済みの表示のままとし、同じ動画の記事がないことに触れない（F-003、AC-24）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   同じ動画の記事がサーバにあるとき、利用者が生成の前にそれに気づき、既存の記事を開くか、現在の選択範囲で生成し直すかを選べるようにする。
-   確認と生成の開始の間に競合がなく、確認のための送信で記事を生成しないようにする。
-   ホストやサーバの版が古い場合にも、確認をせずに黙って生成しないようにする。

### 2.2. スコープ (In Scope)

-   宣言付きの生成の開始に対するサーバの振る舞い（F-001）。
-   宣言を知らないホストやサーバに送った場合の振る舞い（F-002）。
-   ポップアップの確認の状態と、その 2 つの操作、確認の後の状態の移り方、「やり直す」の送り方（F-003）。
-   宣言付きの送信で開いたビューアの表示（F-004）。
-   文書: README（`README.md` と英語版の `README.en.md`）の「ブラウザ拡張」節と、ジョブの API の説明、`docs/dev/guides/development.md` の「ジョブの API」「ジョブの API のコード」と拒否の理由の表、`docs/dev/security.md` §8、`docs/translation_glossary.md`（F-005）。

### 2.3. スコープ外 (Out of Scope)

-   字幕の差分の比較や、選択範囲の近さによる判定: issue のスコープ外。同じ動画かどうかだけで判定する。
-   拡張に記事の履歴を保存すること: issue のスコープ外。`0050` の `chrome.storage` を使わない方針を保つ。
-   最近の記事の一覧の画面、同じ動画の記事の一覧: issue のスコープ外。1. 概要の決定により、最新の 1 件だけを示す。
-   既存の記事の入力（字幕・動画メタデータ）を示すことや、今の選択範囲との違いを示すこと: 1 件目のスコープ外による。キャッシュはコピーした字幕を保持しない（`0044` F-004）。
-   CLI と `/articles` の振る舞い: CLI はキャッシュを使わない。`/articles` の削除は #526 で扱い、本タスクは変えない。
-   キャッシュの永続化と、件数の上限の変更: 1. 概要の決定により、確認はベストエフォートとする。
-   既存の記事を取り消す・削除する操作: issue が求めていない（サーバも利用者の操作による取り消しを持たない。`0044` 2.3）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 宣言付きの生成の開始（サーバ）

生成の開始に「同じ動画の記事があれば生成せずに知らせる」宣言を付けて送ると、サーバは、同じ動画の記事があれば生成を始めずにそのことを返す。

-   宣言の有無は、送り手が宣言する値で決める。サーバは、入力の中身（字幕の長さや範囲など）から宣言の有無を推し量らない。宣言を付けない生成の開始の振る舞いは、`0044` F-001 のとおりで変えない。
-   **同じ動画:** 検査を通った `videoUrl` の動画 ID が同じこと。タイトル・チャンネル名・概要欄・字幕の違いは問わない。
-   **同じ動画の記事:** キャッシュにある、同じ動画の記録のうち、今の入力のキーと違うキーで、ジョブの状態が処理中か完了のもの。失敗の記録は含めない。複数あれば、今の生成の開始を受け付けた時刻が最も新しい 1 件とする。
-   宣言付きの生成の開始の検査の順序は、宣言を付けない場合と同じく、パスとメソッドの検査、本文の読み込みと検査の同時実行の上限、本文の読み込みと検査（拒否の理由も同じ）とし、その後に次の表で振る舞いを決める。

| キャッシュの状態 | 振る舞い |
|---|---|
| 今の入力のキーの記録が処理中か完了 | 今と同じく、生成を始めずに、受け付けの応答でそのキーを返す（同じ動画の記事があっても確認の応答にしない） |
| 上に当たらず、同じ動画の記事がある | 生成を始めず、LLM を呼ばず、キャッシュを変えずに、確認の応答を返す。確認の応答は、同じ動画の記事があることと、その記事のキーを持ち、受け付けの応答と区別できる。生成の枠と件数の上限に空きがなくても、拒否しない |
| どちらにも当たらない | 宣言を付けない生成の開始と同じ（`0044` F-001 の表。生成を始める、失敗した記録をやり直す、`too_many_requests` で拒否する） |

-   「今の入力のキーの記録が失敗」で、同じ動画の記事があるときは、確認の応答を返し、失敗した記録をやり直さない。
-   同じ動画の記事を探すことと、生成を始めることは、1 つの判断として行う。同じ動画の違う入力の宣言付きの生成の開始が同時に来て、同じ動画の記事がない場合、生成を始めるのは 1 つだけで、ほかは、始めた記録のキーを持つ確認の応答を受け取る。
-   確認の応答を返す処理は、Webhook へ通知しない（新しい API の方針。`0044` F-001）。
-   確認の応答の形（状態コード、`status` などのメンバの値、コード）は設計で決める（H-02）。応答は、`0044` F-005 と同じく、文言・コピーした字幕・URL・動画メタデータ・秘密の値を含まず、コードとキーと `requestId` だけを持つ。

**Acceptance Criteria**:
- **AC-01**: 同じ動画（違う URL の書き方を含む。例: `https://youtu.be/<ID>` と `https://www.youtube.com/watch?v=<ID>`）の別の入力で完了した記事があるとき、選択範囲（`transcript`）だけが違う入力を宣言付きで送ると、確認の応答が返り、そのキーは完了した記事のキーである。LLM は呼ばれず、キャッシュの記録の数と各記録の状態は変わらない（ユニットテスト）。
- **AC-02**: 同じ動画の別の入力が処理中のときに宣言付きで送ると、確認の応答が返り、そのキーは処理中の記録のキーである。タイトル・チャンネル名・概要欄だけが違う入力でも同じである（ユニットテスト）。
- **AC-03**: 同じ動画の記録が失敗だけのとき、または別の動画の記事だけがあるとき、宣言付きで送ると、宣言を付けない場合と同じく生成が始まり、受け付けの応答が返る（ユニットテスト）。
- **AC-04**: 今の入力と同じキーの記録が処理中か完了のとき、同じ動画のほかの記事があっても、宣言付きで送ると、受け付けの応答でそのキーが返り、LLM は呼ばれない（ユニットテスト）。
- **AC-05**: 今の入力と同じキーの記録が失敗で、同じ動画のほかの記事が完了しているとき、宣言付きで送ると、確認の応答でその記事のキーが返り、失敗した記録はやり直されず、失敗のままである（ユニットテスト）。
- **AC-06**: 同じ動画の記事が 2 つ以上あるとき、確認の応答のキーは、生成の開始を受け付けた時刻が最も新しい記録のキーである。失敗の後にやり直した記録は、やり直しの受け付けの時刻で比べる（ユニットテスト）。
- **AC-07**: 生成の枠に空きがないとき、またはキャッシュが件数の上限に達して捨てられる記録がないときでも、同じ動画の記事があれば、宣言付きの生成の開始は確認の応答を返し、`too_many_requests` で拒否されない（ユニットテスト）。
- **AC-08**: 同じ動画の記事がないとき、同じ動画の違う入力の宣言付きの生成の開始を同時に送ると、生成（LLM の呼び出し）は 1 回分だけ始まり、ほかのすべての送信は、始まった記録のキーを持つ確認の応答を受け取る（ユニットテスト）。
- **AC-09**: 宣言を付けない生成の開始は、同じ動画の記事があっても、`0044` F-001 と同じく振る舞う（今の入力の記事を生成する）（ユニットテスト）。
- **AC-10**: 確認の応答は、エラーの文言、コピーした字幕、URL、動画メタデータ、秘密の値を含まず、確認の応答を返しても Webhook への通知は行われない（ユニットテスト）。

#### F-002: 宣言を知らないホストやサーバ

拡張が宣言付きの生成の開始を送った相手のホストかサーバが本タスクの前の版である場合、生成は始まらない。

-   本タスクの前の版のホストかサーバが宣言付きの生成の開始を受け取った場合、LLM は呼ばれず、拡張には、受け付けでも確認でもないやり取りの結果（拒否・想定外の応答のいずれか。どれになるかは宣言の置き方による。H-01）が表示される。表示は、`0050` のそのやり取りの結果の表示と同じとする。
-   拡張・ホスト・サーバを同じ版に更新する必要があることは、README に書く（`0050` 4.4 と同じ。F-005）。
-   本タスクの後の版の拡張が宣言を付けずに送る生成の開始（「現在の選択範囲で生成する」）は、本タスクの前の版のホストとサーバでも、`0044` F-001 のとおり受け付けられる。

**Acceptance Criteria**:
- **AC-11**: 本タスクの前の版のホスト（本書の作成の時点の `main` の `internal/nmhost`）と、本タスクの前の版のサーバ（同じく `internal/server`）のそれぞれに、本タスクの後の版の拡張が作る宣言付きの生成の開始を送ると、生成は始まらず（LLM は呼ばれず、キャッシュに記録は加わらず）、受け付けの応答は返らない（検証の手段は実装計画で決める。H-01）。

#### F-003: ポップアップの確認の状態

主ボタン（「記事を生成する」）を押すと、拡張は宣言付きの生成の開始を送り、確認の応答を受け取ると、ポップアップは確認の状態を表示する。

-   主ボタンを押したときの送信（Service Worker が送ること、1 回の押下につき 1 回だけ送ること、ビューアのタブを背面で開くこと、送り手の検査）は、`0050` F-001・F-002 のとおりとし、生成の開始に宣言を付ける。
-   **確認の状態の表示:** 動画のセクションと詳細はそのまま残し、確認のセクションの位置に、このサーバに同じ動画の記事があることと、その記事の状態（生成中か生成済みか）を示す。記事の状態は、ポップアップが確認の応答のキーで状態の取得を繰り返して知る（`0050` F-003 と同じ規則で続け、止める）。最初の状態を取得するまでの表示と、状態を取得できないときの表示は、`0050` F-004 の読み込み中と通知に合わせて設計で決める（H-03）。確認の状態の文言は、サーバにほかの記事がないことや、今後も同じ動画の記事がないことを断定しない。
-   **2 つの操作:** 操作のセクションに、主ボタン「既存の記事を表示する」と、副次のボタン「現在の選択範囲で生成する」を置く。英語の名前は設計で決める（H-04）。
-   **「既存の記事を表示する」:** `0050` F-004 の「ビューアを開く」と同じ順で、確認の応答のキーのビューアのタブを前面に出す（この送信の表示を受け持つビューアのタブ、なければ同じキーのほかのビューアのタブ、どちらもなければ新しいタブ）。生成の開始は送らない。
-   **「現在の選択範囲で生成する」:** 主ボタンを押したときと同じ入力で、宣言を付けない生成の開始を送る。送信は `0050` F-001・F-002 と同じく、Service Worker が 1 回だけ送り、ビューアのタブを背面で新しく開く。押した後、ポップアップは `0050` F-004 の送信中・キーを受け取れなかった・処理中・完了・失敗・不明の状態に移る。既存の記事を表示しているビューアのタブは閉じない。
-   **確認の状態を終える場合:** 確認を表示している間に、状態の取得が既存の記事の失敗か不明を返したら、確認の状態を終え、同じ動画の記事が使えなくなったことを示し、主ボタンを「現在の選択範囲で生成する」（宣言を付けない送信。上と同じ振る舞い）にする。生成中だった記事が完了したら、確認の状態のまま、生成済みの表示に変える。
-   **宣言付きの送信の、確認以外の結果:** 受け付けの応答なら `0050` F-004 の処理中・完了などの状態、キーを受け取れなかったなら `0050` F-004 のそれぞれの状態を、今と同じく表示する。同じ動画の記事がなかったことには触れない。
-   **「やり直す」:** `0050` F-004 の失敗・不明の状態の「やり直す」は、やり直す対象の送信と同じ種類で送る。宣言付きの送信をやり直すときは宣言を付け、「現在の選択範囲で生成する」による送信（または、その送信をやり直した送信）をやり直すときは宣言を付けない。
-   ポップアップを開き直すと、今と同じく送る前の状態から始まり、確認の状態は残らない（`0050` F-004）。

**Acceptance Criteria**:
- **AC-12**: 主ボタンを押すと、ホストは宣言付きの生成の開始のメッセージを 1 つだけ受け取る。その入力は、`0050` AC-01 と同じ収集の値から作る値である（ユニットテスト）。
- **AC-13**: 確認の応答を受け取ると、ポップアップは動画のセクションと詳細を残したまま、同じ動画の記事があることと、その記事の状態（生成中か生成済みか）を示し、主ボタンは「既存の記事を表示する」、副次のボタンは「現在の選択範囲で生成する」になる。生成中の記事が完了すると、生成済みの表示に変わる（ユニットテスト）。
- **AC-14**: 確認の状態で「既存の記事を表示する」を押すと、確認の応答のキーのビューアのタブが、`0050` AC-21 と同じ順で前面に出る。生成の開始は送られない（ユニットテスト）。
- **AC-15**: 確認の状態で「現在の選択範囲で生成する」を押すと、ホストは宣言を付けない生成の開始のメッセージを 1 つだけ受け取り、その入力は最初の送信と同じである。ビューアのタブが新しく 1 つ背面で開き、既存の記事を表示しているタブは閉じない。ポップアップは送信中の状態に移り、その後は `0050` F-004 の状態を表示する（ユニットテスト）。
- **AC-16**: 確認の状態で、既存の記事の状態の取得が失敗か不明を返すと、ポップアップは確認の状態を終えて、同じ動画の記事が使えなくなったことを示し、主ボタンは「現在の選択範囲で生成する」になる。押すと、AC-15 と同じく宣言を付けない生成の開始が 1 回だけ送られる（ユニットテスト）。
- **AC-17**: 宣言付きの送信が受け付けられたとき、または受け付けられなかったとき（拒否・未送信・結果不明）、ポップアップは `0050` F-004 と同じ表示をする（ユニットテスト）。
- **AC-18**: 宣言付きの送信の後の失敗か不明の状態で「やり直す」を押すと、宣言付きの生成の開始が送られる。「現在の選択範囲で生成する」の後の失敗か不明の状態で「やり直す」を押すと、宣言を付けない生成の開始が送られる。その送信の後の失敗か不明でもう一度「やり直す」を押しても、宣言を付けない（ユニットテスト）。
- **AC-19**: 確認の状態のポップアップを閉じて開き直すと、送る前の状態が表示され、拡張は何も送らない（ユニットテスト）。

#### F-004: 宣言付きの送信で開いたビューア

宣言付きの送信で開いたビューアは、確認の応答を受け取ると、既存の記事を表示する。

-   確認の応答を受け取ったビューアは、確認の応答のキーを受け付けの応答のキーと同じように扱う。URL にそのキーを加え、状態を取得して表示する（`0050` F-002・F-003）。同じキーを表示しているビューアがほかにあれば、`0050` F-002 の再利用と同じく、新しいビューアは自分のタブを閉じ、既存のビューアが引き継ぐ。
-   この送信の表示を受け持つビューア（新しいビューアか、引き継いだ既存のビューア）は、同じ動画の既存の記事を表示していること（現在の選択範囲からは生成していないこと）と、現在の選択範囲で生成する手順（ポップアップを開いて主ボタンを押し、「現在の選択範囲で生成する」を選ぶ）を示す。この表示を、再読み込みや履歴から開いた後も残すかは設計で決める（H-05）。
-   経過時間の起点は、`0050` の規則に従う（1. 概要の「導いた振る舞い」）。

**Acceptance Criteria**:
- **AC-20**: 宣言付きの送信で開いたビューアが確認の応答を受け取ると、その URL は確認の応答のキーを持ち、ビューアはそのキーの状態（処理中なら工程と経過時間、完了なら記事）を表示する。同じキーのビューアがほかにあれば、新しいタブは閉じ、既存のビューアがそのまま表示を続ける（`0050` AC-08 と同じ）（ユニットテスト）。
- **AC-21**: AC-20 のビューア（新しいビューア、または引き継いだ既存のビューア）は、同じ動画の既存の記事を表示していることと、現在の選択範囲で生成する手順を示す。宣言付きの送信が受け付けられた場合（確認の応答でない場合）のビューアは、これを示さない（ユニットテスト）。
- **AC-22**: AC-21 の表示は、同じ動画の既存の記事を表示していて、現在の選択範囲からは生成していないことと、現在の選択範囲で生成する手順を、英語と日本語の両方で示す（文言を PR のレビューで読む。`manual`）。

#### F-005: 文書

-   README（`README.md` を変え、`/mktrans` で `README.en.md` に移す）の「ブラウザ拡張」節に、主ボタンを押したときに同じ動画の記事があれば確認を示すこと、2 つの選択肢、同じ動画の判定の基準（動画 ID）、確認がベストエフォートであること（キャッシュの件数の上限と再起動で記事が消え、そのときは確認なしに生成すること）、拡張・ホスト・サーバを同じ版に更新する必要があることを書く。
-   README と `docs/dev/guides/development.md` のジョブの API の説明に、宣言、確認の応答の形とコード、宣言付きの生成の開始の振る舞い（F-001 の表）を加える。拒否の理由やコードを加える場合は、表に加える。
-   `docs/dev/security.md` §8 に、宣言付きの生成の開始が動画単位で記事の有無とキーを返すこと、それを受け入れる理由（4.2）、記録が動画 ID を持つこと、ログに残す値を書く。
-   `docs/translation_glossary.md` に、新しい用語（宣言付きの生成の開始、確認の応答、同じ動画の記事など）を加える。

**Acceptance Criteria**:
- **AC-23**: README（両方）・`development.md`・`security.md`・`translation_glossary.md` の記述が、F-001 から F-004 の振る舞いと合っている（PR のレビューで読む。`manual`）。拒否の理由やコードの表に値を加えた場合は、今のガード（`extension/test/serverReasons.test.ts` と、`development.md` の値を突き合わせる Go のテスト）が、加えた値を含めて通る（ユニットテスト）。
- **AC-24**: ポップアップ・ビューア・README のどの表示と記述も、同じ動画の記事がサーバにないことを断定しない（宣言付きの送信が受け付けられたときの表示は、同じ動画の記事がなかったことに触れない）。README は、確認がベストエフォートであることを示す（英語と日本語の文言を PR のレビューで読む。`manual`）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

サーバと同じ利用者の権限で動くプロセスは信頼する（`security.md` §8）。境界の検査は、`0044` 3.2 と `0050` 3.2 と同じ厳しさで行う。宣言は振る舞いを選ぶ値なので、受理する形でない宣言を、宣言がないものとして扱わない（無視して生成しない）。

| 境界 | 受理する形 | 上限 | 失敗・拒否時の扱い | 主な AC |
|---|---|---|---|---|
| 宣言（ホストのメッセージか生成の開始の入力のどちらかに置く。H-01） | 設計で決めた名前と、閉じた集合の値。値の型が違う、集合にない値、重複する宣言は拒否し、補正しない。宣言がないことは、宣言を付けない送信として受理する | 置く場所の今の上限（ホスト 32 MiB、生成の開始の本文 4 MiB） | 置く場所の今の拒否の理由（ホストなら、サーバにリクエストを送らずに `protocol_error`。`0044` F-008。生成の開始の本文なら `invalid_body`。`0044` 3.2）。生成を始めず、キャッシュに何も加えない | AC-25 |
| 拡張が受け取る確認の応答 | `0050` 3.2 の「サーバの応答の本文」と同じ全体の規則（正しい UTF-8、BOM なし、1 つの JSON オブジェクト、どの階層でもメンバの重複なし、対になっていないサロゲートのエスケープなし、後続のデータなし）。メンバの集合は、`development.md` に書く確認の応答の形と過不足なく一致する（拡張可能と宣言するメンバはない）。コードは閉じた集合に限る。キーは空でない JSON の文字列で、形は検査しない（`0044` 3.2）。状態コードと `status` の組は `development.md` の表に合う | `0050` の生成の開始の応答の上限と同じ | 想定外の応答（`0050` 3.2）。キーを使わず、確認の状態を表示しない | AC-26 |
| Service Worker が受け取る、宣言を付けない生成の開始の求め（「現在の選択範囲で生成する」と、その後の「やり直す」） | `0050` 3.2 の生成の開始の求めと同じく、拡張自身のポップアップからの、設計で決めた形の求め（H-01・H-03） | `0050` と同じ 4 MiB | 何も送らず、タブも開かずに無視する（`0050` AC-05） | AC-27 |

-   受理する形でない宣言の例: 真偽値の宣言に `"true"`・`1`・`null` を書いたもの、宣言の名前を 2 回書いたもの。これは例であり、網羅ではない。
-   確認の応答のキーは、受け付けの応答のキーと同じく、拡張とホストにとって不透明な値である。拡張は、キーから動画や入力について何も導かない。

**Acceptance Criteria**:
- **AC-25**: 宣言の値の型が違う、集合にない値の、または宣言が重複する生成の開始は、置く場所の拒否の理由で拒否され、生成は始まらず、キャッシュは変わらない。宣言を持たない生成の開始は、宣言を付けない送信として受け付けられる（ユニットテスト）。
- **AC-26**: 確認の応答で、メンバが重複するもの、宣言していないメンバを持つもの、メンバが足りないもの、コードが閉じた集合にないもの、キーが空か文字列でないもの、状態コードと `status` の組が合わないもの、後続のデータを持つものは、いずれも想定外の応答になり、ポップアップは確認の状態を表示せず、ビューアはそのキーを使わない（ユニットテスト）。
- **AC-27**: 拡張自身のポップアップ以外の送り手からの、宣言を付けない生成の開始の求めでは、Service Worker はホストに何も送らず、タブも開かない（ユニットテスト）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   同じ動画の記事を探す処理は、キャッシュの件数の上限（100 件。`cache.go:13`）の記録をたどるだけで、LLM の呼び出しに比べて無視できる時間である。索引などの探す処理を速める仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   確認の応答は LLM と Webhook を待たずに返る。ホストの 20 秒の打ち切り（`internal/nmhost/relay.go:31`）の中に収まればよい。

### 4.2. セキュリティ (Security)

本タスクは、LLM API への送信（生成）を始めるかどうかを変え、記録に動画 ID を持たせ、ログに残す値を変えうるので、`docs/dev/security.md` を適用する。

-   **動画単位で記事の有無とキーが分かること:** 宣言付きの生成の開始は、正しい形の入力（字幕の中身は問わない）を送れば、その動画の記事の有無とキーを、生成を始めずに返す。キーを知れば、状態の取得でその記事を読み、投稿の操作で Webhook へ投稿を求められる。これを受け入れる理由は、ソケットに接続できるのは同じ利用者の権限のプロセスだけで、そのプロセスは信頼する（`security.md` §8）ことである。そのプロセスは、今も `.envrc` を読んで LLM API と Webhook を直接使えるので、守る資産は変わらない。他ユーザーのプロセスとウェブページは、今と同じく UDS とその権限で排除する（`security.md` §8.2）。これは `0044` の設計の理由の例外である（5. 制約条件）。
-   **待ち受けの範囲とホストの制約:** 今と同じく、Unix ドメインソケットの上だけで受け、TCP を待ち受けない。ホストの起動の制約（拡張の origin の検査、`HOME` だけを読む、プロキシを使わない、再送しない。`security.md` §8.2）を保つ。拡張に任意のパスを指定させない（`0044` F-008）。
-   **メモリに持つ値:** 記録は、同じ動画の判定のために動画 ID を持つ。動画 ID は記録が捨てられるか、サーバが再起動するまでメモリにあり、ディスクに書かない。完了した記事は、今もファイルの中身に出典の URL（動画 ID を含む）を持つので、新しい種類の値をメモリに持つことにはならない。コピーした字幕は、今と同じく生成の後に持たない（`0044` F-004）。
-   **ログと通知:** 宣言付きの生成の開始のログも、今の方針（`0044` 4.2）に従う。1 つの出来事を 1 行で、固定の属性だけを出し、`redact.Writer` を通す。今の生成の開始のログはキー・動画 ID・結果のコードを出す（`internal/server/jobs_api.go:132`）。確認の応答を返したことは、結果のコードの新しい値として出し、本文、コピーした字幕、`videoUrl` の文字列、動画メタデータ、記事の本文、秘密の値を出さない。確認の応答で返した既存の記事のキーをログに出すかは設計で決める（H-06）。Webhook への通知は行わない（F-001）。拡張の開発者向けのログは、今の方針（`security.md` §8.1）に従い、キーと動画メタデータの値を出さない。
-   **権限を広げない:** 拡張の manifest の権限は今のまま（`activeTab`・`scripting`・`nativeMessaging`）とし、`storage`・`tabs` などを加えない（`0050` 4.2）。
-   **自動で再送しない:** 確認の応答を受け取っても、拡張は宣言を付けない生成の開始を自動では送らない。送るのは、利用者が「現在の選択範囲で生成する」か「やり直す」を押したときだけである（F-003）。
-   **プロンプトへの埋め込み:** コピーした字幕と動画メタデータを記事生成のプロンプトに埋め込むことは変えない。確認の応答を返す場合は、プロンプトを作らない。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   確認はベストエフォートである。同じ動画の記事がキャッシュの件数の上限で捨てられた後、またはサーバの再起動の後は、確認を示さずに生成する（`0044` F-004・4.3）。README にこのことを書く（F-005）。
-   確認の応答を返した後、既存の記事が捨てられるか失敗する場合がある。そのときのポップアップの表示は F-003（確認の状態を終える）、ビューアの表示は `0050` F-003（記事が失われた・失敗）に従う。
-   宣言付きの生成の開始を処理する途中の panic は、今の生成の開始と同じく回復し、`internal_error` で拒否し、サーバは動き続ける（`internal/server/jobs_api.go:46-69`）。

### 4.4. 互換性 (Compatibility)
-   宣言を付けない生成の開始、状態の取得、投稿の操作、`/articles` の振る舞いは変えない（F-001・F-002）。
-   本タスクの後の版の拡張は、本タスクの後の版のホストとサーバを必要とする。版が食い違った場合は、黙って生成せずに受け付け以外の結果になる（F-002）。README に、拡張・ホスト・サーバを同じ版に更新するよう書く（F-005）。
-   ポップアップの送る前の画面（`0046`）と、`0050` の各状態の表示は、確認の状態を加えるほかは変えない。

### 4.5. 保守性 (Maintainability)
-   宣言の有無、確認の応答、ポップアップの確認の状態、「やり直す」が送る種類は、型（列挙・判別共用体）で表し、`switch` の網羅性で欠けを型の検査が知らせる形にする（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。宣言の零値は、最も多くを仮定しない解釈（設計で決める。H-01）とする。
-   同じ動画の判定に使う動画 ID は、今の `videoUrl` の検査（`transcript.ValidateVideoURL`）が返す値を使い、URL の解析を別に実装しない（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   「既存の記事を表示する」のタブの探し方と前面に出し方は、`0050` の「ビューアを開く」の処理を使い、二重に実装しない。

### 4.6. アクセシビリティ (Accessibility)

ポップアップの確認の状態と、ビューアの新しい表示は、[CLAUDE.md](../../../CLAUDE.md)「Accessibility」に従い、WCAG 2.2 のレベル AA を満たす（押せる要素の大きさと動きはレベル AAA の値）。各 AC の検証は、実装計画で `test` または `static` の検証を割り当てる（色のコントラストは色の変数から計算するなど）。ブラウザでの見え方の確認は、それに加えて行う。

**Acceptance Criteria**:
- **AC-28**（キーボード）: 確認の状態の「既存の記事を表示する」と「現在の選択範囲で生成する」、確認の状態を終えた後の「現在の選択範囲で生成する」は、Tab・Shift+Tab・Enter・Space だけで操作できる。フォーカスの順序は見た目の順序に従い、フォーカスを閉じ込めない。キーボードで押した主ボタンが確認の状態の主ボタンに変わったとき、フォーカスの扱いは `0050` の主ボタンの扱い（何もフォーカスを持たないとき、押せるようになった主ボタンにフォーカスを戻す）と同じである。
- **AC-29**（見えるフォーカス）: 2 つのボタンのフォーカスは、隣り合う色に対して 3:1 以上のコントラストの印で示される。ライトとダークの両方で満たす。
- **AC-30**（名前・役割・状態）: 2 つのボタンはネイティブの `<button>` で作り、見える名前と一致する名前を持つ。押せないボタンは、押せないことが支援技術に伝わる。主ボタンと副次のボタンの違いは、見た目の重みだけでなく、名前と位置でも分かる。
- **AC-31**（状態のメッセージ）: 確認の状態になったこと、既存の記事の状態（生成中か生成済みか）とその変化、確認の状態を終えたこと（既存の記事が使えなくなったこと）、ビューアの「既存の記事を表示している」ことは、フォーカスを動かさずに支援技術に伝わる。
- **AC-32**（コントラスト・色だけに頼らない）: 確認の状態とビューアの新しい表示の文字は、背景に対して 4.5:1 以上、意味のある図形は 3:1 以上で、ライトとダークの両方で満たす。既存の記事の状態（生成中か生成済みか）は、色だけでなく文字でも区別できる。
- **AC-33**（言語）: ポップアップとビューアの `lang` は、表示の言語と一致する（`0050` AC-49 と同じ。新しい文言にも当てはまる）。
- **AC-34**（押せる大きさ）: 2 つのボタンは、それぞれ 44×44 CSS ピクセル以上である。
- **AC-35**（動き）: 確認の状態で既存の記事の生成中を示す動きがあれば、`prefers-reduced-motion` が `reduce` のとき止まる。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。
-   **以前のタスクの方針の例外:**
    -   `0044` `02_architecture.md` §3.2「秘密を使う理由」は、秘密を使わないハッシュだと、生成の開始を呼ばずに状態の取得で記事の有無を調べる手段になるとして、キーを生成の開始の応答からしか得られないようにした。本タスクの宣言付きの生成の開始は、動画単位で、生成を始めずに記事の有無とキーを返す。理由は、issue の目的（同じ動画の記事を生成の前に示すこと）がこの情報を返すことそのものであり、ソケットに接続できる同じ利用者の権限のプロセスは信頼する（`security.md` §8）ので、守る資産が変わらないことである（1. 概要の決定、4.2）。キーを秘密から計算すること（同じ入力のキーを、生成の開始を呼ばずに計算できないこと）と、キーが不透明であることは変えない。
    -   `0044` F-001「応答は、生成を始めたか、既存のジョブまたは記事を返したかを区別しない」は、区別して返すかを設計に任せていた。本タスクは、宣言付きの生成の開始で同じ動画の記事を返す場合を、確認の応答として区別する。宣言を付けない生成の開始の応答は変えない。方針の変更ではなく、`0044` が残した選択である。
    -   `0050` F-001「1 回の押下につき生成の開始を 1 回だけ送る」と「自動では送り直さない」は保つ。「現在の選択範囲で生成する」は、利用者の別の押下である。
-   **ホストの判定の例外（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」の例外の 1 つ）:** ホストが今の形と新しい形を見分ける判定（`internal/nmhost/relay.go` の `route`）は、#526 で取り除く予定の例外である。宣言をホストのメッセージに置く場合（H-01）も、新しい形の中の判定は、宣言した値による `switch` で行い、例外の範囲を広げない。
-   ユニットテストは、実際のブラウザ・ホスト・サーバ・LLM を呼ばない。ブラウザの API と LLM は fake に置き換える（[CLAUDE.md](../../../CLAUDE.md)「Testing Strategy」）。
-   外部のライブラリと npm のパッケージを加えない（[CLAUDE.md](../../../CLAUDE.md)「Dependencies」）。

## 6. 用語集 (Glossary)

-   **0044・0046・0050**: それぞれ、サーバとホストに新しい API を加えたタスク（`docs/tasks/0044_article_job_api/`）、ポップアップの画面を再設計したタスク（`docs/tasks/0046_popup_redesign/`）、拡張を新しい API に移しビューアを加えたタスク（`docs/tasks/0050_viewer_tab/`）。
-   **同じ動画:** 検査を通った `videoUrl` の動画 ID が同じこと。
-   **同じ動画の記事:** キャッシュにある同じ動画の記録のうち、今の入力のキーと違うキーで、ジョブの状態が処理中か完了のもの（F-001）。
-   **宣言:** 生成の開始に付ける、「同じ動画の記事があれば生成せずに知らせる」ことを求める値（F-001）。置く場所と名前は設計で決める。
-   **宣言付きの生成の開始:** 宣言を付けた生成の開始。主ボタン（「記事を生成する」）を押したときと、その送信をやり直したときに送る。
-   **確認の応答:** 宣言付きの生成の開始に、同じ動画の記事があるときにサーバが返す応答。生成を始めず、その記事のキーを持つ。受け付けの応答とは区別する。
-   **確認の状態:** 確認の応答を受け取った後のポップアップの状態。「既存の記事を表示する」と「現在の選択範囲で生成する」を選べる。
-   **既存の記事:** 確認の応答のキーの記事。
-   **主ボタン・ビューア・送信の時刻・やり取りの結果・結果不明・記事のキー・ジョブの状態:** `0050` と [translation_glossary.md](../../translation_glossary.md) の定義による。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
