## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

規則（`docs/dev/conventions/requirements_process.md`）の移し替えを、変更履歴のないすべての文書に広げる。承認済みの文書なら、状態表の `Review date` と `Reviewer` から写した承認の行を変更履歴に置く。あわせて、移し替えを参照する 5 つのコマンドの定義を新しい節に合わせ、`/fixpr` の Migration check を広げる。何をどう書くかは設計書 3〜6 章で決まっている。本書は、それをどのステップで行い、どう確かめるかを定める。

### 1.2. 実装の原則

-   設計書 8 章のフェーズの順（1 → 3）で実装する。本書のフェーズ 1〜3 は、設計書 8 章のフェーズ 1〜3 に対応する。PR は 1 つにまとめる（設計書 8 章「PR の分け方」）。
-   行の形・手順・確かめは規則の 1 か所にだけ書き、コマンドの定義は規則の節を名指しして参照する（設計書 1.1 節、AC-11）。写した承認の行の印の文言や、写せない条件を、コマンドの定義に書き写さない。
-   規則とコマンドの定義の文言は、PR のレビューで読んで確かめる（`manual`）。文言を照合する恒久のテストは加えない（設計書 7.1 節、`CLAUDE.md`「Document tests check values, structure, and executable examples, never prose」）。規則に書いた手順 1 と手順 7 の確かめが記述どおりに行えることは、ステップ 3-1 の試行で一度確かめる（設計書 7.2 節）。
-   規則とコマンドの定義の本文は英語で書く。写した承認の行の形と例は、タスク文書に書く日本語の値をそのままコードブロックで示す（設計書 3.1 節）。
-   フェーズごとに 1 つ以上のコミットにし、規則の変更とコマンドの定義の変更を別のコミットで読めるようにする。

### 1.3. 計画の際に決めたこと（2026-11-02）

-   計画の段階で利用者に問うべき未決の選択はなかった。PR の分け方とフェーズの順は設計書 8 章が、確かめの方法は設計書 7 章が決めている。
