## 1. 概要 (Overview)

**目的:** 本書は、変更履歴のないタスク文書に、新しい規則で最初の状態の遷移を書くときの移し替えの要件を定義する（用語は §3 の冒頭と §6 で定義する）。その文書が承認済みなら、状態表にある過去の承認（承認日と承認者）も変更履歴に残す（[#621](https://github.com/isseis/yt2column/issues/621)）。

**背景:**

タスク 0053（[#596](https://github.com/isseis/yt2column/issues/596)、PR #613・#617）で、タスク文書の状態の遷移を文書の末尾の変更履歴（`## 変更履歴`）に記録する規則を入れた（`docs/dev/conventions/requirements_process.md:139-201`）。この規則は承認も毎回変更履歴に書くと定めている。`draft` に戻すと `Review date` と `Reviewer` が `-` になる（同書 22-24 行）ので、変更履歴に承認の記録がなければ過去の承認が消えるためである（`docs/tasks/0053_status_comments_policy/01_requirements.md`「要件定義の際に決めたこと」）。

ところが、この規則より前に承認された文書には変更履歴がない。そうした文書を決定の変更で `draft` に戻すと、過去の承認が文書から消える。

-   規則は、移し替えの対象（旧規則で書かれた文書）を「変更履歴がなく、`Comments` が `-` でない文書」と定めている（`requirements_process.md:205-208`、0053 の AC-17）。そのため `Comments` が `-` の承認済み文書では移し替えが行われず、`draft` への戻しの行だけが書かれる。
-   移し替えの対象の文書でも、移すのは `Comments` の文だけである（`requirements_process.md:211-217`、0053 の AC-18）。状態表の `Review date` と `Reviewer` は写さないので、旧 `Comments` に承認の経緯がなければ、やはり承認が消える。

2026-11-02 時点の `origin/main`（`cbb5d84e`）には、変更履歴のない承認済みの文書が 155 件ある。うち 52 件は `Comments` が `-`、103 件は `Comments` に文がある。数え方：`docs/tasks/*/0[123]_*.md` のうち、状態表の `Status` が `approved` で、行全体が `## 変更履歴` である行を持たない文書を数えた。承認の事実は git の履歴には残る。状態表の `Reviewer` を書き換えた squash コミット（件名に `(#N)` を持つ）を `git log -S` でたどれば分かる。ただし、文書を読む人がそこまでたどるとは期待しにくい。

この問題は PR #617 のレビューのスレッド（https://github.com/isseis/yt2column/pull/617#discussion_r4437831154 ）で指摘された。承認済みの 0053 の AC-17・AC-18 を変える内容なので、PR #617 では変えず、本タスクで扱う。

対応 issue: [#621](https://github.com/isseis/yt2column/issues/621)
前提のタスク: 0053（[#596](https://github.com/isseis/yt2column/issues/596)）

**本書の記述範囲:** 本書は、移し替えの対象、承認の行を作る条件と行に書く内容、変更履歴の中での並び、値を写せないときの振る舞いを定める。次の事項は設計（`02_architecture.md`）で決める：写した承認の行の正確な書式と印の文言、規則の英語の本文のどの節をどう書き換えるか、旧規則で書かれた文書という用語と節の見出しの扱い、写した値を機械的に確かめるかどうかとその方法、コマンドの定義の参照の書き換え、受け入れ基準の確かめ方。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #621 で決めたこと:**

-   **承認済みの文書なら、遷移の前に状態表の値から写した承認の行を作る:** 変更履歴のない文書に新しい規則で最初の状態の遷移を書くとき、その文書が `approved` なら、遷移の行の前に、状態表の `Review date` と `Reviewer` の値から写した承認の行を 1 行作る。値は状態表から機械的に写せるので、文書を読む人が git の履歴をたどらずに過去の承認を読めるようにできる。
-   **写した承認の行は PR 番号を求めない例外とする:** 状態表からは、承認を記録した PR の番号が分からない。そこで、旧 `Comments` を移した項目と同じく、PR 番号を求めない例外とする。0053 では「変更履歴の行は、どれもその行を加えた PR の番号を持つ」と決め（`docs/tasks/0053_status_comments_policy/01_requirements.md`「要件定義の際に決めたこと」）、規則は移した項目を唯一の例外としている（`requirements_process.md:182-183`）。この決定は、そこに 2 つ目の例外を加える。
-   **移し替えの対象を変更履歴のない文書に広げる:** 対象を「変更履歴がなく `Comments` が `-` でない文書」から「変更履歴のない文書」に広げる。旧 `Comments` を移す手順は、`Comments` が `-` でないときだけ行う。`Comments` が `-` の承認済み文書でも承認を残すためである。
-   **規則は 1 か所で定め、コマンドの定義は食い違う箇所だけを直す:** 規則を参照するコマンドの定義（`runpr.md` の PRE_MERGE、`fixpr.md` の Phase 3、`runplan.md`、`mkarch.md`、`mkplan2.md`）は、参照の文言を確かめ、規則と食い違う箇所だけを直す。規則を 1 か所で定める 0053 の方針（0053 の AC-20）を保つためである。
-   **新しいタスクとして扱う:** 承認済みの 0053 の AC-17・AC-18 を変える要件の変更なので、`/mkreq` から始める。

**要件定義の際に決めたこと（2026-11-02）:**

-   **写した承認の行は、`approved` の文書からのどの遷移でも作る:** 状態の遷移のうち、`approved` の文書から起こりうるのは `draft` への戻し、セッション中の再承認、`withdrawn` の 3 種類である。写した承認の行は、このどの遷移が最初の遷移でも作る。過去の承認を実際に消すのは `draft` への戻しだけである（セッション中の再承認と `withdrawn` で `Review date` と `Reviewer` を更新する手順は、規則にもコマンドの定義にもない。`requirements_process.md:34-41`・`:267`、`.claude/commands/runplan.md:64`）。それでも条件を「`approved` かどうか」の 1 つにすれば規則が単純になる。また、どの文書の変更履歴でも、過去の承認が後の遷移の行より前に並ぶ。
-   **値はそのまま写し、写せないときは止まる:** 写した承認の行の日付と承認者には、状態表の `Review date` と `Reviewer` の値を、内容を変えずに写す。誤記と思われる値も直さない（`origin/main` には `Reviewer` が `isesis` の文書が 2 件ある）。`CLAUDE.md` の「Reject, don't normalize」に従い、写す側で値を推測して直さないためである。`approved` の文書で `Review date` か `Reviewer` が `-` または空のときは、遷移を書かずに止まって報告する。推測で写した承認の行を作ったり、行を省いて過去の承認を黙って失ったりしないためである。`origin/main` の変更履歴のない承認済みの文書 155 件は、どれも両方の値を持つので、今この停止に当たる文書はない。止まった後にどう続けるか（状態表をどう直すか）は、報告を受けた利用者が決める。本タスクではその手順を定めない。
-   **並びは、移した項目、写した承認の行、遷移の行の順とする:** 旧 `Comments` を移した項目があるときは、それを変更履歴の先頭に置く（0053 の規則のまま。`requirements_process.md:198-201`）。その後に写した承認の行、最後に遷移の行を置く。移した項目を先頭に置く規則を変えずに済むためである。旧 `Comments` に承認の経緯が書かれていれば、写した承認の行と内容が重なる。これは許容する。
-   **既存のタスク文書は変えない:** 本タスクの PR では、変更履歴のない既存の文書に写した承認の行を一括して書き足さない。0053 の要件定義書の AC-17・AC-18 も書き換えない。新しい規則は、各文書に最初の状態の遷移を書くときに当てはめる（0053 の「既存のタスク文書の `Comments` は、本タスクでは改訂しない」と同じ扱い）。規則は `requirements_process.md` の 1 か所で定め、0053 からの変更とその理由は本書に記録する。0053 の要件定義書を書き換えると、それ自体が決定の変更になってその文書が `draft` に戻り、新たに決める内容のない再承認が必要になるためである。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   変更履歴のない承認済みの文書に状態の遷移を書いても、状態表にある直近の承認（承認日と承認者）が文書から消えないようにする。それより前の承認は、旧 `Comments` に書かれていれば、移した項目に残る。
-   規則（`requirements_process.md`）と、規則を参照するコマンドの定義を矛盾させない。

### 2.2. スコープ (In Scope)

-   `docs/dev/conventions/requirements_process.md` の変更履歴の規則（「Change history」の PR 番号と移した項目の例外。同書 182-201 行）と、旧規則で書かれた文書の移し替えの規則（「Documents written under the old rule」。同書 203-226 行）。これらを参照する同書の箇所（同書 32、41、46、144、267 行）も含む。
-   移し替えを参照するコマンドの定義（本書でいう「対象のコマンドの定義」）：`.claude/commands/runpr.md`（PRE_MERGE の承認の記録。224 行）、`.claude/commands/fixpr.md`（Phase 3 の R3 の指示と移し替えの確かめ。469-470 行・502-512 行）、`.claude/commands/runplan.md`（64 行）、`.claude/commands/mkarch.md`（72 行）、`.claude/commands/mkplan2.md`（107 行）。

### 2.3. スコープ外 (Out of Scope)

-   **既存のタスク文書の書き換え:** 本タスクの PR では、`docs/tasks/` 以下の既存の文書に写した承認の行を書き足さず、0053 の要件定義書も変えない（「要件定義の際に決めたこと」）。
-   **状態表の誤記の訂正:** `Reviewer` の `isesis` のような値は、写した承認の行にそのまま写す。状態表の値を直すことは本タスクで扱わない。
-   **承認の PR 番号を git の履歴から探すこと:** 写した承認の行には PR 番号を書かない（issue #621 で決めたこと）。squash コミットから PR 番号をたどることはしない。たどれば、移し替えのたびに履歴の検索と GitHub への問い合わせ（`requirements_process.md:190-194` の手順）が要るうえ、状態表から機械的に写せる、という issue の前提も崩れるためである。
-   **コマンドを実行した結果を確かめること:** 新しい規則に従った遷移の結果は、本タスクの後の PR で分かる。本タスクでは規則とコマンドの定義の記述を確かめる（0053 と同じ扱い）。

## 3. 機能要件 (Functional Requirements)

本書の用語は 0053 の要件定義書に従う。「規則」は `docs/dev/conventions/requirements_process.md` を指す。「状態の遷移」は承認、`draft` への戻し、セッション中の再承認、`withdrawn` の 4 種類を指す（同書「Document Status Format」）。「対象のコマンドの定義」は 2.2 に挙げた 5 ファイルを指す。「移した項目」は、旧 `Comments` の文を変更履歴の先頭に移して作る項目（`旧規則の Comments：` で始まる項目）を指す。「状態表から写した承認の行」（以下「写した承認の行」）は、F-002 で状態表の値から作る承認の行を指す。

### 3.1. 機能一覧

#### F-001: 移し替えの対象を変更履歴のない文書に広げる

変更履歴のない文書に、新しい規則で最初の状態の遷移を書くときは、`Comments` の値によらず移し替えの手順を行う。

**Acceptance Criteria**:
- **AC-01**: 規則が、移し替えの手順の対象を、変更履歴のセクションがない文書と定めている。`Comments` が `-` かどうかは、対象かどうかの条件に含まれない。
- **AC-02**: 規則が、旧 `Comments` を移した項目にする手順を、`Comments` が `-` でないときだけ行うと定めている。`Comments` が `-` のときは移した項目を作らない。
- **AC-03**: 規則が、編集上の訂正だけを加えるときは移し替えを行わず、`Comments` と変更履歴を変えないと定めている（0053 の AC-18 の後半のまま）。
- **AC-04**: 規則のもとで、作ったばかりの `draft` の文書（変更履歴がなく、`Comments` が `-`）を初めて承認したときに書かれる変更履歴は、承認の行 1 行だけである。移した項目も写した承認の行も作られない。

#### F-002: 過去の承認を変更履歴に残す

変更履歴のない `approved` の文書に最初の状態の遷移を書くときは、遷移の行の前に、状態表の値から写した承認の行を 1 行作る。

**Acceptance Criteria**:
- **AC-05**: 規則が次を定めている。変更履歴のない `approved` の文書に、新しい規則で最初の状態の遷移（`draft` への戻し、セッション中の再承認、`withdrawn` のどれでも）を書くときは、遷移を書く前の状態表にある `Review date` と `Reviewer` の値から写した承認の行を 1 行作る。前の文書の決定の変更に伴って `draft` に戻す文書にも当てはまる。
- **AC-06**: 規則が、写した承認の行の内容を次のとおり定めている。日付は `Review date` の値、承認者は `Reviewer` の値で、どちらも内容を変えずに写す（誤記と思われる値も直さない）。PR 番号の代わりに、状態表から写した承認であることを示す印を書く。
- **AC-07**: 規則が、写した承認の行を、移した項目と並んで PR 番号を求めない例外と定めている。写した承認の行は、PR 番号が未記入であることを示す印（`#未記入`）を持たない。
- **AC-08**: 規則が、変更履歴の中の並びを、移した項目（あるとき）、写した承認の行、遷移の行の順と定めている。
- **AC-09**: 規則が、遷移の前の状態が `approved` でない文書（`draft` または `withdrawn`）には、写した承認の行を作らないと定めている。
- **AC-10**: 規則と、対象のコマンドの定義のうち移し替えを行うものが次を定めている。`approved` の文書で `Review date` か `Reviewer` の行がない、または値が `-` か空のときは、遷移を書かずに止まる。止まるときは、その遷移を含む変更（決定の変更による本文の書き換えと、それに伴って `draft` に戻すほかの文書を含む）を、どの文書についてもコミットしない。利用者には、その文書のパスと、写せなかった項目の名前（`Review date` か `Reviewer`）を報告する。止まったときに作業ツリーをどの状態で残すかは設計で決める。

#### F-003: 規則とコマンドの定義を矛盾させない

移し替えの対象と手順は規則の 1 か所で定め、規則の中のほかの箇所と対象のコマンドの定義はそれを参照する。

**Acceptance Criteria**:
- **AC-11**: 規則の中で移し替えと PR 番号の例外を参照する箇所（2.2 に挙げた行）と、対象のコマンドの定義の参照（2.2 に挙げた行）が、次を満たす。どの箇所も、移し替えの対象を変更履歴のない文書として述べるか、移し替えを定める節を参照するだけである。「`Comments` が `-` でない」を移し替えの対象の条件として述べる箇所がない。PR 番号の例外を「移した項目だけ」と述べる箇所がない。

#### F-004: 既存のタスク文書を変えない

本タスクの PR では、既存のタスク文書に新しい規則を当てはめない。

**Acceptance Criteria**:
- **AC-12**: 本タスクの PR は、`docs/tasks/` 以下の既存のタスク文書（`docs/tasks/0056_legacy_approval_history/` 以外）を変えない。

## 6. 用語集 (Glossary)

-   **変更履歴:** 文書の最後に置く、状態の遷移を 1 件 1 行で記録するセクション（0053 の F-003、規則「Change history」）。
-   **変更履歴のない文書:** 変更履歴のセクションがない文書。本タスクの後は、移し替えの対象になる（F-001）。
-   **移し替え:** 変更履歴のない文書に新しい規則で最初の状態の遷移を書くとき、その前に行う手順。変更履歴を作り、`Comments` が `-` でなければ移した項目を、`approved` なら写した承認の行を書く。
-   **承認の行:** `/runpr` が承認を記録するときに書く、PR 番号を持つ行（規則「Change history」）。写した承認の行とは区別する。
-   **移した項目:** 旧 `Comments` の文を、`旧規則の Comments：` の印を付けて変更履歴の先頭に置いた項目（規則「Change history」の Migrated item）。
