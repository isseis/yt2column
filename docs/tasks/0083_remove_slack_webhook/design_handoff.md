# 設計への申し送り：0083 Slack の Webhook への投稿の廃止とコピーでのメンションの無効化

`01_requirements.md` を書くときに挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目について採った方法か、当てはまらない理由を記録する。

## H-01: 無効化をどの部品で行うか

**懸念:** コピーする文章の無効化を、サーバ（Go）で行うか、拡張（TypeScript）で行うかが決まっていない。サーバで行うなら、状態の取得の応答に、コピーする文章（と、無効化したかどうか）を加えることになる。拡張で行うなら、対象の `@` の定義とコードの範囲の判定（`writer.ProseRanges`）を TypeScript に書き直し、Go の規則と二重になる。

**なぜ重要か:** 規則が 2 か所にあると、`docs/dev/security.md` §6 の正本と食い違いうる。issue #770 は、規則が Go の `internal/publisher` にあり、拡張だけの構成（#769）への移行の後は WASM の中でそのまま使えることを挙げている。

要件はビューアの表示も同じ規則で無効化すると決めた（AC-16）ので、表示とコピーが同じ無効化の結果を使うようにする。

**候補:** サーバが `DisplayMarkdown` と同じ記事から、無効化した文字列と、無効化したかどうかを作り、状態の取得の `done` の応答に入れる（`markdown` の値を無効化した文字列にする案を含む）。拡張は、それを表示にも使い、コピーではそのまま書く。応答の大きさの上限（`maxStatusResponseBytes`、`internal/server/status.go:19`）と、完了の時点の大きさの検査（`article_too_large`）への影響を確かめる。

**関連:** F-002、F-003、AC-03、AC-10、AC-18

## H-02: 無効化したかどうかの渡し方

**懸念:** AC-18 の通知は、コピーする文章に U+200B を 1 つ以上入れたかどうかで決まる。拡張が文章の中に U+200B があるかで判定する方法では、表示用の Markdown がもともと U+200B を含む記事で判定を誤る。

**なぜ重要か:** 無効化していない記事で、無効化したと通知してしまう。

**候補:** 無効化を行う部品が、無効化したかどうかを値として返す（H-01 でサーバに置くなら、応答のメンバにする）。

**関連:** F-003、AC-18、AC-19

## H-03: 本文の UTF-8 の検査の置き場所

**懸念:** 要件は、本文が正しい UTF-8 でない記事を完了の時点の検査で `article_invalid` にすると決めた（AC-09a）。いまは送る前の検査だけが本文の UTF-8 を検査し（`internal/publisher/slack_message.go:30`〜`35`）、`CheckPublishable` は検査しない。どこに検査を置けば、サーバの完了の時点の検査と CLI の `--out` の両方に効くかが決まっていない。

**なぜ重要か:** 置き場所を誤ると、片方の経路だけが検査し、もう片方で JSON への書き出しやルーンへの変換が黙って U+FFFD に置き換える。

**候補:** `writer.Article.CheckPublishable` に本文の UTF-8 の検査を加え、両方の経路が同じ検査を通るようにする。

**関連:** AC-09a、AC-10、AC-16

## H-04: 無効化の規則のコードとテストの置き場所

**懸念:** 対象の `@` の判定（`mentionAts`・`mentionAtsOf`・見た目の似た文字の置き換え）と無効化（`insertAfterAts`）は、`slack_message.go`・`slack_render.go` にあり、Webhook の拒否と分割のコードと同じファイルにある。投稿のコードを消すときに、残す規則と消すコードを分ける必要がある。

**なぜ重要か:** 残す規則のテスト（いまは `slack_render_test.go` などにある）を消すと、F-002 の振る舞いが確かめられなくなる。消すテストは coverage-compare で確かめる（`CLAUDE.md`「Testing Strategy」）。

**候補:** 残す規則を Webhook に依存しない名前のファイル（またはパッケージ）へ移すコミットと、投稿のコードとテストを消すコミットを分ける。移すコミットはテストを消さず、消すコミットだけを coverage-compare で確かめる。

**関連:** F-001、F-002、§5

## H-05: 拡張の状態の取得の応答の検査と、投稿の状態に依存するポーリング

**懸念:** 拡張は状態の取得の応答の形を検査し（`extension/src/core/response.ts`）、投稿中の記事ではポーリングを続ける（`extension/src/core/poll.ts:57`）。`publish`・`webhookConfigured` のメンバをなくすと、応答の検査とポーリングの止め方を改める必要がある。

**なぜ重要か:** 応答の検査が古い形を求めたままだと、すべての状態の取得が想定外の応答になる。

**候補:** 拡張とサーバを同じ PR で改め、応答の検査から 2 つのメンバを除く。`done` の記事ではポーリングを止める。

**関連:** AC-01、AC-03

## H-06: URL とコードの範囲の判定を、Mattermost の扱いと比べる

**懸念:** 要件は、コードの範囲の中の `@` と URL のパスの `/@` を変えないと決めた（AC-12）。こちらの判定（コードの範囲は `writer.ProseRanges`、URL のパスの `/@` は要件 §3.1 の定義）と、Mattermost の判定が食い違う書き方では、こちらが変えなかった `@` がメンションになる（要件 §4.2 の残るリスク 4・5）。候補として、`~~~` のフェンス（実機では Mattermost もコードとして扱った）、閉じていないフェンス、リストの中のフェンス、長さの違うバッククォート、URL の末尾の `)`・`>`・`.`・`,` がある。過去の読解は `docs/tasks/0028_output_layout/02_architecture.md` §6.5 にある。

**なぜ重要か:** 食い違いは通知になり、利用者のチャンネルの全員に届きうる。

**候補:** 判定の細部を、Mattermost のソースの読解（またはテスト用のチャンネルでの確かめ）と比べ、食い違う形は、こちらを狭める（無効化する側に倒す）。比べた形と結果を設計書に記録する。

**関連:** AC-11、AC-12、AC-13、AC-17、§4.2

## H-07: タイトル・チャンネル名・本文の切り分け

**懸念:** AC-11 は、タイトルの行・チャンネル名の行・本文で規則が違う。拡張が受け取るのは表示用の Markdown の 1 つの文字列で、チャンネル名がないときは、本文の最初の行とチャンネル名の行を見分けられない。表示用の Markdown の全体に `ProseRanges` をかけると、タイトルのバッククォートが本文のバッククォートと対になるなど、本文だけにかけたときとコードの範囲が変わりうる。

**なぜ重要か:** 範囲を誤ると、無効化すべき `@` を残すか、変えない `@` を変える。

**候補:** 無効化を、記事の値（タイトル・チャンネル名・本文）を別々に持つ部品で行う（H-01）。拡張で行うなら、切り分けに要る値を応答から受け取る。

**関連:** AC-03、AC-11、AC-13、H-01
