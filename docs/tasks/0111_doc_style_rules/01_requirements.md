## 1. 概要 (Overview)

**目的:** 本書は、日本語の文書の太字の使い方と、項目の多い節の組み立て方の規則を定め、ADR などが読みづらくなるのを防ぐ要件を定める。

**背景:**

PR #1009 のレビューで、ADR-0013 の「決定」「採らなかった案」「結果」が読みづらいと指摘された（issue #1011「きっかけ」）。原因は 2 つあった。

-   太字が多すぎた。今の ADR は、「決定」の各項目の先頭の文を太字にする書き方が慣習になっている（例：`docs/dev/adr/0039-adr-writing-criteria.md` の「決定」）。
-   1 項目に、規則・理由・正本が 1 段落で詰め込まれていた。

PR #1009（本書を書いた時点で未マージ）は、ADR-0013 だけを組み直す案を出している。まとめを先に書き、`###` の小見出しと入れ子の箇条書きで構造化した形である。

今のリポジトリには、この 2 点を定める規則がない。

-   `CLAUDE.md` の「Documents」（`CLAUDE.md:27-41`）は、文書の置き場所・言語・形式（Markdown）・Mermaid の規約へのリンクだけを持つ。
-   ADR の規約の「Writing an ADR」（`docs/dev/conventions/adr.md:128-191`）は、各節に何をどの粒度で書くかを定める。太字と、節の組み立て方は定めない。
-   日本語の文章の点検 `japrose`（`.claude/commands/japrose.md:90-98`）の基準にも、太字の項目はない。

書式の規約には先例がある。Mermaid の書式の規則は `docs/dev/conventions/mermaid_reference.md` にあり、`CLAUDE.md` はそこへのリンクを置くだけである（`CLAUDE.md:34-37`）。

対応 issue: [#1011](https://github.com/isseis/yt2column/issues/1011)

**本書の記述範囲:** 本書は、規則の中身・置き場所・当てる範囲と、`japrose` が太字を確かめる振る舞いを定める。各ファイルのどこに何を書くかは `02_architecture.md` で、確かめ方は `03_implementation_plan.md` で定める。

**issue #1011 で決めたこと:**

-   太字は、見出しと、本文の中で本当に強調が必要な箇所だけに使う。
    -   理由：太字が多いと、どこが大事かが分からなくなるため（issue「きっかけ」）。
-   項目が多い節は、最初に 1〜2 文でまとめを書き、詳細は小見出しや箇条書きで構造化する。
    -   理由：1 項目に規則・理由・正本を 1 段落で詰め込むと読みにくいため（issue「きっかけ」）。
-   短い ADR では、構造化せずに箇条書きでもよい（issue のコメント、2026-11-19）。
    -   理由は記録されていない。

**要件定義の際に決めたこと（2026-11-19）:**

人に確かめて決めたことは、進め方、規則の置き場所と ADR、規則の中身、当てる範囲、`japrose` の確認の 5 つに分かれる。

### 進め方

-   進め方は簡易な進め方（`simple`）とする。
    -   理由：変わるのは文書だけで、届く先は新しい規約・`CLAUDE.md`・`adr.md`・`japrose.md`・ADR-0039 の数か所である。新しい仕組みは作らない。未決の判断も少ない。
    -   除外の判断：除外される変更に当たらない（`docs/dev/conventions/requirements_process.md`「Simple Process」の「Excluded changes」）。`docs/dev/security.md` の規則と前提、開発の道具の信頼境界（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）、外部依存のどれも変えない。`japrose` が新たに読むのは手元の `git` の出力だけで、レビューのスレッドや Bot への依頼の扱いは変えない。
    -   ADR：なし。本タスクの中で閉じる、進め方の選択である。

### 規則の置き場所と ADR

-   規則の正本は、新しい規約 `docs/dev/conventions/document_formatting.md` に置く。`CLAUDE.md` の「Documents」と `adr.md` の「Writing an ADR」には、規約へのリンクを置く（F-001・F-002）。
    -   理由：書式の規則は Mermaid の規約と同じ種類のもので、同じ形にそろえる。同じ規則を 2 か所に書かずに済む。エージェントが従う規約なので、英語で書く（`CLAUDE.md`「Document language」の原則 (b)）。
    -   採らなかった案：一般の規則を `CLAUDE.md` に、ADR への当てはめを `adr.md` に書く案。初めはこれを選んだが、人の指示で見直した。`CLAUDE.md` は長く、書式の細部を持つ置き場所ではない。Mermaid の先例とも形が分かれる。
    -   採らなかった案：`adr.md` だけに置く案。対象が ADR に限られる。
    -   ADR：規約そのものには ADR を作らない（次の項目）。ADR への当てはめは [ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) を更新する（その次の項目）。
-   書式の規約には、新しい ADR を作らない。
    -   理由：日本語の文書一般の書式の規則で、取り消すときも規約の 1 ファイルとそれを指す数行を変えるだけで済む。Mermaid の書式の規約にも ADR はない。理由と採らなかった案は、本書のこの節に残す。
    -   採らなかった案：後のすべての文書を縛る開発プロセスの方針として、規約を要約してリンクする ADR を作る案。初めはこれを選んだが、人の指示で見直した。ADR の「決定」が規約の要約とリンクだけになる。
-   [ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) を更新し、ADR の書式は書式の規約に従うこと、既存の ADR を規約に合わせる書き直しは編集上の訂正として行ってよいことを、「決定」に 1 項目足す（F-002）。
    -   理由：`adr.md` の「Writing an ADR」は ADR-0039 の主題（ADR の書き方の基準）で、1 つの主題は 1 つの有効な ADR が持つ（`docs/dev/conventions/adr.md:45-47`）。書式の規則への参照をそこに足すことは、ADR-0039 の決定を変える。
    -   採らなかった案：ADR-0039 を変えず、書式は ADR-0039 の主題の外とする案。「Writing an ADR」の基準が変わるのに、ADR-0039 の「決定」と食い違う。
    -   この PR の時点では `adr.md` と書式の規約がまだこの決定を持たないので、ADR-0039 の項目は、そのずれの記述を [#1011](https://github.com/isseis/yt2column/issues/1011) へのリンクとともに持つ（`docs/dev/conventions/adr.md:171-175`）。実装の PR が、その記述を消す。
    -   ADR：ADR-0039 を更新する。

### 規則の中身

-   規則の対象は、日本語の文書とする（`CLAUDE.md`「Document language」の原則 (a)：タスク文書・ADR・ガイドなど）。英語の文書（`CLAUDE.md`・コマンドの定義・規約）は対象にしない（F-001）。
    -   理由：issue の問題は日本語の文書で起きた。
    -   採らなかった案：ADR だけに当てる案。タスク文書やガイドでも、同じ読みにくさが起こりうる。
    -   採らなかった案：英語の文書を含むすべての文書に当てる案。範囲が英語の指示文書の書式の見直しに広がる。
    -   ADR：なし（書式の規約に ADR を作らない理由による。以下の項目も同じ）。
-   太字について、次のとおりとする（F-001）。
    -   太字にしてよいもの：項目や段落の頭のラベル（`理由:`・`正本:` のようにコロンで終わるもの、`状態。` のように句点で終わる短い見出し）と、本文の中で読み落とすと誤解を招く語句（否定、例外など）。
    -   太字にしないもの：文全体、または文より長いまとまり。今の ADR の「決定」の項目の先頭の文の書き方は使わない。
    -   規則の外にあるもの：テンプレート・規約・道具が形を決めている固定のラベル（計画書の `**実装モデル要件**:`、受け入れ基準の `**AC-01**`、handoff の `**扱った箇所:**` など）。決められた形のまま書く。
    -   理由：issue の「見出し」は、項目の頭のラベルを指すものとして扱う（2026-11-19 に人が選んだ）。句点で終わる短い見出しもラベルに含めるのは、今のガイドとタスク文書がこの形を多く使っているためである（2026-11-19 に人が選んだ）。固定のラベルは道具や規約が読むので、規則で変えてはならない。
    -   採らなかった案：項目の頭のラベルも太字にしない案（PR #1009 が ADR-0013 に出している書き方）。
    -   採らなかった案：ラベルをコロンで終わるものに限り、句点で終わる短い見出しを認めない案。今のガイドの書き方の多くが規則に合わなくなる。
-   まとめを先に書いて構造化する規則は、日本語の文書のうち項目の多い節すべてに当てる。テンプレートが形を決めている箇所（受け入れ基準の一覧、状態の表など）は、テンプレートの形に従う（F-001）。
    -   理由：issue は ADR の 3 つの節を例に挙げ、「など」と書いている。対象を日本語の文書とした決定とそろえる。
    -   採らなかった案：ADR の「決定」「採らなかった案」「結果」に限る案。
-   短い節は、まとめも構造化も求めず、箇条書きのままでよい。短いかどうかは、数値の閾値を設けず、書き手が判断する。当てはまるかは PR のレビューで読んで確かめる（F-001）。
    -   理由：issue のコメントは「短い ADR」について述べている。対象を日本語の文書の節に広げたので、同じ扱いを「短い節」に広げる。項目の数で決めると、1 項目が長いときの読みにくさを拾えない。
    -   採らなかった案：短い節でも、まとめの 1〜2 文は書く案。
    -   採らなかった案：項目の数で決める案（例：5 つ以下なら構造化しなくてよい）。
-   規約は、項目の中の形（内容・理由・正本のラベルの並べ方など）を決めない（F-001）。
    -   理由：issue は「小見出しや箇条書きで構造化する」とだけ書いている。形を決めると、短い項目にも余分なラベルが要る。ADR の項目に理由と正本の場所を書くことは、すでに `adr.md` の「What 決定 holds」（`docs/dev/conventions/adr.md:163-175`）が定めている。
    -   採らなかった案：規則の行の下に `理由:`・`正本:` を入れ子で置く形を定める案。

### 当てる範囲

-   規則は、新しく書く文書と、変更が項目の中身を足すか書き換える節に当てる。そうした節は、節全体を規則に合わせる。変更が触れない節を書き直すことは求めない（F-001）。
    -   理由：規則に合わない節に項目を足すとき、足す項目だけを合わせると、1 つの節の中で書き方が混ざる（2026-11-19 に人が選んだ）。全体の書き直しは範囲とレビューの負担が大きい。
    -   節全体を合わせるきっかけは、節の項目の中身を足すか書き換える変更だけとする。リンク・名前・見出しの直し、ずれの記述の削除、誤字の直しは、きっかけにしない。これらは、`docs/dev/conventions/adr.md`「Editorial corrections」の 2〜4 種目にあたる直しである。中身を変えない小さな直しのたびに節全体の書き直しを求めると、直しの差分とレビューが大きくなるためである。
    -   ADR にも、書式は節全体に合わせる規則を当てる。基準ができる前の ADR の決定を変える PR は変える部分だけを基準に合わせる、という規則（`docs/dev/conventions/adr.md:339-340`）は、各節に何を書くかという中身の基準について、今のまま残す（2026-11-19 に人が選んだ）。書式と中身で、合わせる範囲が分かれる。
    -   この PR で ADR-0039 に足す項目は、今の ADR-0039 の書き方（先頭の文を太字にする）のままにする（2026-11-19 に人が選んだ）。この PR の時点では書式の規約がまだないためである。実装の PR がその項目のリンクを規約へ替える直しは、上のとおり節全体を合わせるきっかけにしない。
    -   採らなかった案：足す項目だけを合わせ、まとめと構造化は節を新しく書くか大半を書き直すときだけ求める案。
    -   採らなかった案：ADR では、書式も `adr.md:339-340` に従い、変える部分だけを合わせる案。
    -   採らなかった案：この PR で ADR-0039 の「決定」の節全体を新しい書式に組み直す案。規約がまだなく、範囲が広がる。
    -   採らなかった案：本タスクで既存の ADR を組み直す案。範囲が広がる。
    -   採らなかった案：新しく書く文書だけに当てる案。決定を変える PR が足した部分も古い書き方になる。
-   既存の ADR を規約に合わせる書き直しは求めないが、編集上の訂正（`docs/dev/conventions/adr.md`「Editorial corrections」の 1 種目、基準に合わせる書き直し）として、どの PR も行ってよい（F-002）。
    -   理由：訂正としてコミットと PR の説明に記録するので、レビュアーが確かめられる。ADR-0001〜0030 の見直し（[#729](https://github.com/isseis/yt2column/issues/729)）にも使える。
    -   採らなかった案：認めず、PR が変える部分だけにする案。
    -   ADR：ADR-0039 の更新に含める。

### `japrose` の確認

-   `japrose` の基準に、太字の項目を 1 つ加える。確かめるのは、そのブランチで足した行と変えた行だけである。これらの行は、`origin/main` と `HEAD` の merge-base と、対象の文書との差分から決める。まとめを先に書いて構造化する規則は、`japrose` では確かめない（F-003）。
    -   理由：`japrose` は、タスク文書を書くコマンド（`/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2`）が書いた文書にかけ、`/mkreq`・`/mkarch`・`/mkplan` と簡易な進め方では ADR の変更にもかける（`.claude/commands/mkreq.md`・`mkarch.md`・`mkplan.md`・`mkplan2.md`・`_lib/simple-process.md`）。そこで太字の使いすぎを書いた直後に直せる。構造化は、`japrose` の「構造・見出しを変えない」という制約（`.claude/commands/japrose.md:101`）と合わない。確かめる行を限るのは、変更が触れない節の太字まで外さないためである。範囲の決め方は、2026-11-19 に人が選んだ選択肢（merge-base との差分を読んで限る）による。
    -   太字の項目は、`japrose` が直しを入れる前の 1 回目の確認でだけ確かめる。人が選んだのは「ブランチで足した行と変えた行」で、`japrose` 自身の表現の直しが変えた行は含まないためである。各回の前に行を決め直すと、`japrose` が前の回に直した、変更が触れない節の行まで太字の確認がかかる。
    -   採らなかった案：`japrose` に加えず、PR のレビューで読むだけにする案。初めに勧めたが、人が太字の項目を加える案を選んだ。
    -   採らなかった案：新しく作った文書だけを確かめる案。決定を変える PR が既存の ADR に足した部分を見落とす。
    -   採らなかった案：文書全体を確かめる案。変更が触れない節の太字まで外す。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   日本語の文書の太字を、ラベルと本当に強調が必要な語句に絞る。
-   項目の多い節を、まとめから読めるようにする。
-   エージェントが文書を書くときに、規則を見つけて従えるようにする。

### 2.2. スコープ (In Scope)

-   書式の規約 `docs/dev/conventions/document_formatting.md` の新設（F-001）。
-   `CLAUDE.md` の「Documents」と、`adr.md` の「Writing an ADR」からの参照と、ADR-0039 の更新（F-002）。
-   `japrose` の太字の確認（F-003）。

### 2.3. スコープ外 (Out of Scope)

-   既存の文書の、変更が触れない節の書き直し。理由は 1 章の「要件定義の際に決めたこと」にある。ADR については、編集上の訂正として行ってよい（F-002）。
-   英語の文書（`CLAUDE.md`・コマンドの定義・規約）の書式。理由は同じく 1 章にある。
-   まとめを先に書いて構造化する規則の、`japrose` やテストでの確認。PR のレビューで読んで確かめる。
-   テンプレート（`docs/tasks/0000_template/` など）の書き換え。テンプレートが決めている形は規則の外とする。
-   書式の規約のための新しい ADR。理由は 1 章にある。
-   `japrose` を呼ばない経路（`/runplan`・`/fixpr`・人の手による変更）での太字の確認。これらの経路で書いた文の書式は、PR のレビューで読んで確かめる。`japrose` を呼ぶコマンドを増やすと、範囲が文書の点検の流れの見直しに広がる。
-   `.claude/commands/_context.md` と、`/mkarch` などの読む文書の一覧への規約の追加。`CLAUDE.md` はどのセッションでも読まれるので、そこからのリンクで足りる。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 書式の規約

日本語の文書の太字と、項目の多い節の組み立て方を、1 つの規約に定める。

**Acceptance Criteria**:
- **AC-01**: `docs/dev/conventions/document_formatting.md` があり、英語で書かれている。規約の対象は、`CLAUDE.md`「Document language」の原則 (a) の日本語の文書であると述べ、英語の文書と、原則 (c) の README（`README.md`・`README.en.md`）は対象でないと述べる。
- **AC-02**: 規約は、規則を当てる範囲を次のとおり述べる。
    -   新しく書く文書と、変更が項目の中身を足すか書き換える節に当て、そうした節は節全体を規則に合わせる。
    -   リンク・名前・見出しの直し、ずれの記述の削除、誤字の直しだけの変更は、節全体を合わせるきっかけにしない。
    -   変更が触れない節を書き直すことは求めない。
- **AC-03**: 規約は、太字の規則を次のとおり述べる。
    -   太字にしてよいもの：項目や段落の頭のラベルと、本文の中で読み落とすと誤解を招く語句。ラベルは、項目や段落の頭にある、述語を持たない短い句（名詞で終わる句）の太字で、コロン（`:` か `：`）か句点（`。` か `.`）で終わる（終わりの記号は太字の内でも直後でもよい）。
    -   太字にしないもの：文全体、または文より長いまとまり。
    -   規則の外にあるもの：テンプレート・規約・道具が形を決めている固定のラベル。決められた形のまま書く。
- **AC-04**: 規約は、項目の多い節の規則を次のとおり述べる。
    -   最初に 1〜2 文でまとめを書く。
    -   詳細は、小見出しか入れ子の箇条書きで構造化する。1 項目の規則・理由・正本が長くなるときは、1 段落に詰め込まず、分けて書く。どれも短いときは 1 段落でよく、どちらに当たるかは書き手が判断する。
    -   項目の中の形は、書き手に任せる。
- **AC-05**: 規約は、次の 2 つを述べる。
    -   短い節は、まとめも構造化も求めず、箇条書きのままでよい。短いかどうかは、数値の閾値なしに書き手が判断する。
    -   テンプレートか規約が形を決めている箇所（ADR の「経緯」の項目など）は、その形に従う。

#### F-002: 規約への参照

エージェントと書き手が、規約を見つけられるようにする。

**Acceptance Criteria**:
- **AC-06**: `CLAUDE.md` の「Documents」の箇条書きに、日本語の文書の書式は `docs/dev/conventions/document_formatting.md` に従う、という項目があり、規約へリンクする。
- **AC-07**: `docs/dev/conventions/adr.md` の「Writing an ADR」は、ADR の書式は書式の規約に従うと述べ、規約へリンクする。書式は節全体に合わせ、中身の基準は今までどおり変える部分だけを合わせる（`adr.md:339-340`）と述べる。項目が多くなりやすい節として「決定」「採らなかった案」「結果」を挙げ、短い節は箇条書きのままでよいと述べる。
- **AC-15**: `adr.md` の「Writing an ADR」は、既存の ADR を書式の規約に合わせる書き直しは求めないが、編集上の訂正の 1 種目（基準に合わせる書き直し）として行ってよいと述べる。

#### F-003: japrose の太字の確認

`japrose` が、ブランチで足した行と変えた行の太字を、規約に照らして確かめ、直す。

**Acceptance Criteria**:
- **AC-08**: `japrose` の文章の基準（Prose-quality checklist）に、規約の太字の規則に合わない太字がないことを確かめる項目が 1 つある。`japrose` は、レビューのサブエージェントに書式の規約を読ませる。
- **AC-09**: `japrose` は、太字の項目を、対象の文書のうち、ブランチで足した行と変えた行にだけ当てる。
    -   足した行と変えた行は、`origin/main` と `HEAD` の merge-base と、作業ツリーの対象の文書との差分から決める。`git` は、リポジトリの最上位を作業ディレクトリにして、最上位からのパスで呼ぶ。
    -   merge-base に対象の文書のパスがなく、ブランチがほかのファイルを消しても動かしてもいないときは、文書のすべての行を足した行とみなす。
    -   行は、`japrose` が直しを入れる前に 1 回だけ決め、太字の項目は 1 回目の確認でだけ確かめる。`japrose` 自身の直しが変えた行は、足した行にも変えた行にも含まない。
    -   レビューのサブエージェントには、行の範囲と差分の各ハンクを渡す。変えた行のうち、変更がリンク・名前・見出し・誤字の直しだけの行の太字は、指摘しない。
    -   それ以外の行の太字は、指摘も変更もしない。
- **AC-10**: 足した行と変えた行を決められないとき、`japrose` は太字の項目を確かめない。確かめなかったことと理由を報告に書き、ほかの項目の確認は続ける。決められないときは次のとおりである。
    -   この手順の `git` が 0 以外の終了状態で終わったか、手順が想定しない形の出力を出したとき。
    -   対象の文書がリポジトリの作業ツリーの外にあるとき。
    -   merge-base に対象の文書のパスがなく、ブランチがほかのファイルを消すか動かしているとき（その文書が動かした先かどうかを確かめられないため）。
- **AC-17**: `japrose` の報告は、太字の項目で確かめた行の数を述べる。0 行のときは、確かめる行がなかったと述べる。
- **AC-11**: `japrose` が太字の指摘を直すときは、太字の印だけを外し、文字は変えない。規則の外にある固定のラベルの太字は外さない。
