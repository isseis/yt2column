## 1. 概要 (Overview)

**目的:** 本書は、日本語の文書の太字の使い方と、項目の多い節の組み立て方の規則を定め、ADR などが読みづらくなるのを防ぐ要件を定める。

**背景:**

PR #1009 のレビューで、ADR-0013 の「決定」「採らなかった案」「結果」が読みづらいと指摘された（issue #1011「きっかけ」）。原因は 2 つあった。

-   太字が多すぎた。今の ADR は、「決定」の各項目の先頭の文を太字にする書き方が慣習になっている（例：`docs/dev/adr/0039-adr-writing-criteria.md` の「決定」）。
-   1 項目に、規則・理由・正本が 1 段落で詰め込まれていた。

PR #1009 は ADR-0013 だけを組み直した。まとめを先に書き、`###` の小見出しと入れ子の箇条書きで構造化した形である。

今のリポジトリには、この 2 点を定める規則がない。

-   `CLAUDE.md` の「Documents」（`CLAUDE.md:27-41`）は、文書の置き場所・言語・形式（Markdown）・Mermaid の規約へのリンクだけを持つ。
-   ADR の規約の「Writing an ADR」（`docs/dev/conventions/adr.md:128-183`）は、各節に何をどの粒度で書くかを定める。太字と、節の組み立て方は定めない。
-   日本語の文章の点検 `japrose`（`.claude/commands/japrose.md:90-98`）の基準にも、太字の項目はない。

書式の規約には先例がある。Mermaid の書式の規則は `docs/dev/conventions/mermaid_reference.md` にあり、`CLAUDE.md` はそこへのリンクを置くだけである（`CLAUDE.md:34-37`）。

対応 issue: [#1011](https://github.com/isseis/yt2column/issues/1011)

**本書の記述範囲:** 本書は、規則の中身・置き場所・当てる範囲と、`japrose` が太字を確かめる振る舞いを定める。各ファイルのどこに何を書くかは `02_architecture.md` で、確かめ方は `03_implementation_plan.md` で定める。

**issue #1011 で決めたこと:**

-   太字は、見出しと、本文の中で本当に強調が必要な箇所だけに使う。
    -   理由：太字が多いと、どこが大事かが分からなくなるため（issue「きっかけ」）。
-   項目が多い節は、最初に 1〜2 文でまとめを書き、詳細は小見出しや箇条書きで構造化する。
    -   理由：1 項目に規則・理由・正本を 1 段落で詰め込むと読みにくいため（issue「きっかけ」）。
-   短い ADR では、構造化せずに箇条書きでもよい（issue のコメント、2026-11-19）。
    -   理由は記録されていない。

**要件定義の際に決めたこと（2026-11-19）:**

-   進め方は簡易な進め方（`simple`）とする。
    -   理由：変わるのは文書だけで、届く先は新しい規約・`CLAUDE.md`・`adr.md`・`japrose.md` の数か所である。新しい仕組みは作らず、どの ADR の決定も変えない。未決の判断も少ない。
    -   除外の判断：除外される変更に当たらない（`docs/dev/conventions/requirements_process.md`「Simple Process」の「Excluded changes」）。`docs/dev/security.md` の規則と前提、開発の道具の信頼境界（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）、外部依存のどれも変えない。`japrose` はレビューの文書を読むが、信頼できない入力の扱いは変えない。
    -   ADR：なし。本タスクの中で閉じる、進め方の選択である。
-   規則の正本は、新しい規約 `docs/dev/conventions/document_formatting.md` に置く。`CLAUDE.md` の「Documents」と `adr.md` の「Writing an ADR」には、規約へのリンクを置く（F-001・F-002）。
    -   理由：書式の規則は Mermaid の規約と同じ種類のもので、同じ形にそろえる。同じ規則を 2 か所に書かずに済む。エージェントが従う規約なので、英語で書く（`CLAUDE.md`「Document language」の原則 (b)）。
    -   採らなかった案：一般の規則を `CLAUDE.md` に、ADR への当てはめを `adr.md` に書く案。初めはこれを選んだが、人の指示で見直した。`CLAUDE.md` は長く、書式の細部を持つ置き場所ではない。Mermaid の先例とも形が分かれる。
    -   採らなかった案：`adr.md` だけに置く案。対象が ADR に限られる。
    -   ADR：なし。下の項目の理由による。
-   ADR は作らない。
    -   理由：この規則は文書の書式で、後の変更が守る設計上の決定（構造・境界・プロトコル・セキュリティの前提など）ではない。取り消すときも、規約の 1 ファイルとそれを指す数行を変えるだけで済む。Mermaid の書式の規約にも ADR はない。理由と採らなかった案は、本書のこの節に残す。
    -   採らなかった案：後のすべての文書を縛る開発プロセスの方針として、規約を要約してリンクする ADR を作る案。初めはこれを選んだが、人の指示で見直した。ADR の「決定」が規約の要約とリンクだけになる。
-   規則の対象は、日本語の文書とする（`CLAUDE.md`「Document language」の原則 (a)：タスク文書・ADR・ガイドなど）。英語の文書（`CLAUDE.md`・コマンドの定義・規約）は対象にしない（F-001）。
    -   理由：issue の問題は日本語の文書で起きた。英語の指示文書は、今は太字のラベルを多用する書式を前提にしている。
    -   採らなかった案：ADR だけに当てる案。タスク文書やガイドでも、同じ読みにくさが起こりうる。
    -   採らなかった案：英語の文書を含むすべての文書に当てる案。範囲が広がり、英語の指示文書の書式の見直しになる。
    -   ADR：なし。
-   規則は、新しく書く文書と、変更が足すか変える部分にだけ当てる。既存の文書の、変えない部分を書き直すことは求めない（F-001）。
    -   理由：全体の書き直しは範囲とレビューの負担が大きい。決定を変える PR が古い ADR のうち自分が変える部分だけを基準に合わせる、という [ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) の扱いとそろえる。
    -   採らなかった案：本タスクで既存の ADR を編集上の訂正として組み直す案。範囲が広がる。
    -   採らなかった案：新しく書く文書だけに当てる案。決定を変える PR が足した部分も古い書き方になる。
    -   ADR：なし。
-   構造化しなくてよい「短い節」かどうかは、数値の閾値を設けず、書き手が判断する。当てはまるかは PR のレビューで読んで確かめる（F-001）。
    -   理由：項目の数で決めると、1 項目が長いときの読みにくさを拾えない。簡易な進め方を採るかどうかと同じく、人が読んで決める。
    -   採らなかった案：項目の数で決める案（例：5 つ以下なら構造化しなくてよい）。
    -   ADR：なし。
-   まとめを先に書いて構造化する規則は、日本語の文書のうち項目の多い節すべてに当てる。テンプレートが形を決めている箇所（受け入れ基準の一覧、状態の表など）は、テンプレートの形に従う（F-001）。
    -   理由：issue は ADR の 3 つの節を例に挙げ、「など」と書いている。対象を日本語の文書とした決定とそろえる。
    -   採らなかった案：ADR の「決定」「採らなかった案」「結果」に限る案。
    -   ADR：なし。
-   太字について、次のとおりとする（F-001）。
    -   太字にしてよいもの：項目や段落の頭のラベル（`理由:`・`正本:` など）と、本文の中で読み落とすと誤解を招く語句（否定、例外など）。
    -   太字にしないもの：文全体、または文より長いまとまり。今の ADR の「決定」の項目の先頭の文の書き方は使わない。
    -   規則の外にあるもの：テンプレート・規約・道具が形を決めている固定のラベル（計画書の `**実装モデル要件**:`、受け入れ基準の `**AC-01**`、handoff の `**扱った箇所:**` など）。決められた形のまま書く。
    -   理由：issue の「見出し」は、項目の頭のラベルを指すものとして扱う（2026-11-19 に人が選んだ）。固定のラベルは道具や規約が読むので、規則で変えてはならない。
    -   採らなかった案：項目の頭のラベルも太字にしない案（PR #1009 の ADR-0013 の書き方）。
    -   ADR：なし。
-   `japrose` の基準に、太字の項目を 1 つ加える。確かめるのは、そのブランチで足した行と変えた行に限る。まとめを先に書いて構造化する規則は、`japrose` では確かめない（F-003）。
    -   理由：エージェントが書く文書には必ず `japrose` がかかるので、太字の使いすぎを書いた直後に直せる。構造化は、`japrose` の「構造・見出しを変えない」という制約（`.claude/commands/japrose.md:101`）と合わない。確かめる行を限るのは、既存の部分の太字まで外すと、上の「変える部分だけに当てる」決定と食い違うためである。`japrose` は ADR の変更にもかかり、ADR のファイル全体を見る（`.claude/commands/mkreq.md` の step 7）。
    -   採らなかった案：`japrose` に加えず、PR のレビューで読むだけにする案。初めに勧めたが、人が太字の項目を加える案を選んだ。
    -   採らなかった案：新しく作った文書だけを確かめる案。決定を変える PR が既存の ADR に足した部分を見落とす。
    -   採らなかった案：文書全体を確かめる案。既存の部分の太字まで外す。
    -   ADR：なし。
-   規約は、項目の中の形（内容・理由・正本のラベルの並べ方など）を決めない（F-001）。
    -   理由：issue は「小見出しや箇条書きで構造化する」とだけ書いている。形を決めると、短い項目にも余分なラベルが要る。ADR の項目に理由と正本の場所を書くことは、すでに `adr.md` の「What 決定 holds」（`docs/dev/conventions/adr.md:163-176`）が定めている。
    -   採らなかった案：規則の行の下に `理由:`・`正本:` を入れ子で置く形を定める案。
    -   ADR：なし。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   日本語の文書の太字を、ラベルと本当に強調が必要な語句に絞る。
-   項目の多い節を、まとめから読めるようにする。
-   エージェントが文書を書くときに、規則を見つけて従えるようにする。

### 2.2. スコープ (In Scope)

-   書式の規約 `docs/dev/conventions/document_formatting.md` の新設（F-001）。
-   `CLAUDE.md` の「Documents」と、`adr.md` の「Writing an ADR」からの参照（F-002）。
-   `japrose` の太字の確認（F-003）。

### 2.3. スコープ外 (Out of Scope)

-   既存の文書の、変えない部分の書き直し。理由は 1 章の「要件定義の際に決めたこと」にある。必要になったら、別の issue で扱う。
-   英語の文書（`CLAUDE.md`・コマンドの定義・規約）の書式。理由は同じく 1 章にある。
-   まとめを先に書いて構造化する規則の、`japrose` やテストでの確認。PR のレビューで読んで確かめる。
-   テンプレート（`docs/tasks/0000_template/` など）の書き換え。テンプレートが決めている形は規則の外とする。
-   ADR の作成と変更。理由は 1 章にある。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 書式の規約

日本語の文書の太字と、項目の多い節の組み立て方を、1 つの規約に定める。

**Acceptance Criteria**:
- **AC-01**: `docs/dev/conventions/document_formatting.md` があり、英語で書かれている。規約の対象は、`CLAUDE.md`「Document language」の原則 (a) の日本語の文書であると述べ、英語の文書は対象でないと述べる。
- **AC-02**: 規約は、規則を当てる範囲を次のとおり述べる。
    -   新しく書く文書と、変更が足すか変える部分に当てる。
    -   既存の文書の、変えない部分を書き直すことは求めない。
- **AC-03**: 規約は、太字の規則を次のとおり述べる。
    -   太字にしてよいもの：項目や段落の頭のラベルと、本文の中で読み落とすと誤解を招く語句。
    -   太字にしないもの：文全体、または文より長いまとまり。
    -   規則の外にあるもの：テンプレート・規約・道具が形を決めている固定のラベル。決められた形のまま書く。
- **AC-04**: 規約は、項目の多い節の規則を次のとおり述べる。
    -   最初に 1〜2 文でまとめを書く。
    -   詳細は、小見出しか入れ子の箇条書きで構造化する。1 項目に規則・理由・出典を 1 段落で詰め込まない。
    -   項目の中の形は、書き手に任せる。
- **AC-05**: 規約は、次の 2 つを述べる。
    -   短い節は、構造化せずに箇条書きにしてよい。短いかどうかは、数値の閾値なしに書き手が判断する。
    -   テンプレートが形を決めている箇所は、テンプレートの形に従う。

#### F-002: 規約への参照

エージェントと書き手が、規約を見つけられるようにする。

**Acceptance Criteria**:
- **AC-06**: `CLAUDE.md` の「Documents」の箇条書きに、日本語の文書の書式は `docs/dev/conventions/document_formatting.md` に従う、という項目があり、規約へリンクする。
- **AC-07**: `docs/dev/conventions/adr.md` の「Writing an ADR」は、ADR の書式は書式の規約に従うと述べ、規約へリンクする。項目が多くなりやすい節として「決定」「採らなかった案」「結果」を挙げ、短い ADR は箇条書きでよいと述べる。

#### F-003: japrose の太字の確認

`japrose` が、ブランチで足した行と変えた行の太字を、規約に照らして確かめ、直す。

**Acceptance Criteria**:
- **AC-08**: `japrose` の文章の基準（Prose-quality checklist）に、規約の太字の規則に合わない太字がないことを確かめる項目が 1 つある。
- **AC-09**: `japrose` は、太字の項目を、対象の文書のうち、ブランチで足した行と変えた行にだけ当てる。
    -   足した行と変えた行は、`origin/main` と `HEAD` の merge-base と、作業ツリーの対象の文書との差分から決める。
    -   merge-base に対象の文書がないときは、文書のすべての行を足した行とみなす。
    -   それ以外の行の太字は、指摘も変更もしない。
- **AC-10**: 足した行と変えた行を決められないとき（`git` が失敗したときなど）、`japrose` は太字の項目を確かめない。確かめなかったことを報告に書き、ほかの項目の点検は続ける。
- **AC-11**: `japrose` が太字の指摘を直すときは、太字の印だけを外し、文字は変えない。規則の外にある固定のラベルの太字は外さない。

#### F-004: 変更の範囲

**Acceptance Criteria**:
- **AC-12**: 実装の PR の差分のうち、次の 4 つのファイル以外の変更は、本タスクのディレクトリ（`docs/tasks/0111_doc_style_rules/`）の中に限る。
    -   `docs/dev/conventions/document_formatting.md`
    -   `CLAUDE.md`
    -   `docs/dev/conventions/adr.md`
    -   `.claude/commands/japrose.md`
- **AC-13**: 既存の 3 つのファイルの差分は、次に限る。
    -   `CLAUDE.md`：「Documents」の箇条書きに 1 項目を足すこと。
    -   `adr.md`：「Writing an ADR」に 1 段落を足すこと。
    -   `japrose.md`：太字の項目を足すことと、足した行と変えた行を決める手順を足すこと。
- **AC-14**: `go test -tags test ./cmd/yt2column` が通る（文書のリンクの先があることと、ADR の記録の形を確かめるガードを含む）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   N/A。文書と、文書の点検の手順の変更だけである。

### 4.2. セキュリティ (Security)
-   N/A。`docs/dev/security.md` の条件（外部コマンドの起動、API キー、キャッシュ、ネットワーク、信頼できない文字列の埋め込み）のどれにも当たらない。`japrose` が新たに実行するのは、手元のリポジトリを読む `git` だけで、ネットワークに触れない。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   `japrose` は、足した行と変えた行を決められないとき、太字の確認だけを飛ばし、そう報告する（AC-10）。文書全体の太字を外す側には倒さない。

### 4.4. 互換性 (Compatibility)
-   既存の文書は、変えない部分を書き直さなくてよい（AC-02）。今の書き方のまま読める。

### 4.5. 保守性 (Maintainability)
-   規則の正本は規約の 1 か所に置き、`CLAUDE.md` と `adr.md` はリンクと当てはめだけを持つ（AC-06・AC-07）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   規約とコマンドの定義は英語で書く（`CLAUDE.md`「Document language」の原則 (b)）。`japrose` の基準の項目は、今の基準と同じく日本語で書く（`.claude/commands/japrose.md:90-98`）。
-   文書のテストは文の意味を確かめない（`CLAUDE.md`「Testing Strategy」）。規約の中身は PR のレビューで読んで確かめる。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。
-   **書式の規約:** `docs/dev/conventions/document_formatting.md`。本タスクで新しく作る。
-   **固定のラベル:** テンプレート・規約・道具が形を決めている太字のラベル。計画書の `**実装モデル要件**:`、受け入れ基準の `**AC-01**`、handoff の `**扱った箇所:**` など。
-   **項目の多い節:** 箇条書きの項目が多いか、1 項目が長いために、まとめなしでは全体をつかみにくい節。当てはまるかは書き手が判断する。
