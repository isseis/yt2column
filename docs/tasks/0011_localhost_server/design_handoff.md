# 設計への申し送り：localhost サーバ本体と拡張との HTTP API

本書は、[01_requirements.md](01_requirements.md) のレビュー（と起草）で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 本文のサイズ上限の値と、ヘッダの検査の後に本文を読む方法

-   **事項:** リクエスト本文の上限の具体値と、上限を超える本文を全量バッファリングせずに拒否する読み込みの方法を決める。本文は、ヘッダだけで行える検査（メソッド・`Content-Type`・`Host`・`Origin`・共有トークン）をすべて通過した後にだけ読む（F-003、AC-12）。
-   **理由:** 認証のないリクエストもサーバに届く（[security.md](../../dev/security.md) §8、0007 §3.12.1）。共有トークンはヘッダで受け取るので、本文を読まずに認証できる。本文を先に読むと、未認証のリクエストが 1 件ごとに上限までのメモリと読み込みの時間を消費させる。F-006 の同時実行数の上限は認証後の処理に効くので、未認証のリクエストの同時の数は制限されない。`io.ReadAll` のような上限なしの読み込みは、認証済みのリクエストでも使わない。
-   **候補の方針:** ハンドラの先頭でヘッダの検査を行い、失敗したら本文に触れずに拒否する。通過後、`http.MaxBytesReader` で読み、上限を超えたら拒否する。`Content-Length` が上限を超えていれば読む前に拒否できるが、`Content-Length` のない（チャンク転送の）リクエストもあるので、`MaxBytesReader` は省略しない。ハンドラが本文を読まずに返ると、`net/http` が接続の再利用のために本文の一部を読み捨てることがある。必要なら、拒否の応答で接続を閉じる（`Connection: close`）。AC-12 の「本文を読まない」は、読み込みを記録する `io.Reader` を本文に差し込んだテストで確かめる。上限は、字幕が埋め込まれるプロンプトの上限（`internal/writer` の `maxPromptBytes` = 1 MiB）と #107 のパーサの入力の大きさを基準に決める。時刻の行を含む生の字幕は、解析後の本文より大きい点に注意する。
-   **関連:** F-002、F-003、AC-12

## H-02: 共有トークンの生成・受け渡し・比較

-   **事項:** 共有トークンの生成方法（暗号学的に安全な乱数、長さ、文字の表現）、トークンのファイルのパス・権限・形式と、その検査、リクエストで受け取るヘッダの名前、比較の方法（定数時間）、生成時の表示の形式を決める。
-   **理由:** 共有トークンは省略できない認証要素である（security.md §8、0007 §3.12.1）。`Origin` は認証にならない。共有トークンは再起動をまたいで同じ値を使う（F-001）。起動のたびに作り直すと、拡張の `chrome.storage.local` に保存した値がサーバの再起動のたびに無効になり、利用者が毎回貼り付け直すことになるためである。
-   **候補の方針:**
    -   生成: `crypto/rand` で 32 バイトを生成し、16 進または base64url で表す。
    -   パス: `$XDG_CONFIG_HOME/yt2column/`（未設定なら `$HOME/.config/yt2column/`）の下のファイル。導出に必要な環境変数がない場合は、待ち受けを開始せずに終了する（H-08 の既定のキャッシュディレクトリの扱いと揃える）。
    -   作成: ディレクトリは `0700`、ファイルは `0600` とし、`O_CREATE|O_EXCL` で作る。2 つのサーバが同時に初回の起動をしても、片方が他方のトークンを上書きしない。
    -   読み込み時の検査: 通常ファイルであること（シンボリックリンクを辿らない）、権限が `0600` より広くないこと、所有者が実行中の利用者であること、内容が規定の長さと文字の表現に一致すること。末尾の改行も補正せずに拒否するかは、ファイルの形式と合わせて決める。不一致なら終了し、修復も再生成もしない（AC-03）。
    -   比較: `crypto/subtle.ConstantTimeCompare` を使う。
    -   ヘッダ: `Authorization: Bearer <token>` などを候補とする。
    -   受け渡し: 生成時の標準出力の表示、拡張のオプションページへの貼り付け、`chrome.storage.local` への保存とする（0007 §3.12.3）。確定は #111。
    -   ログとの分離: 共有トークンを表示する標準出力と、ログの出力先（標準エラー出力など）を分け、ログの経路にトークンが流れないようにする（AC-02）。
    -   再表示: 2 回目以降の起動では表示しない。利用者が値を再び必要とするとき（ブラウザのプロファイルを作り直したときなど）は、ファイルを読む手順を README に記す。
-   **関連:** F-001、F-004、AC-02、AC-03、AC-16

## H-03: エンドポイントとエラー応答のスキーマ

-   **事項:** エンドポイントのパスとメソッド（`POST` のみ）、応答の JSON のスキーマ、理由の種別ごとの状態コードの割り当てを決める。
-   **理由:** API は要件で振る舞いを定めたが、実際のインターフェースは設計で固定する。拡張（#111）がこれに従う。
-   **候補の方針:** 理由の種別を型または固定の値で表し、`switch` で状態コードに対応させる（CLAUDE.md「Declare, don't infer」）。状態コードの候補: `Content-Type` の不一致は `415`、`Host`・`Origin`・共有トークンの不一致は `403`（`Origin` の欠落も含む）、動画 URL の不正・字幕書式の不正・本文のサイズ超過は `400`（サイズ超過は `413` も候補）、同時実行数の超過は `429` または `503`。
-   **関連:** F-002、F-006、F-008

## H-04: #107 の `TranscriptSource` の使い方とメタデータの載せ方

-   **事項:** #107 の `TranscriptSource` をどう呼ぶか（入力は `transcript` の文字列と `videoUrl`）、`Title`・`ChannelName`・`Description` をどのように `Transcript` に載せるかを決める。
-   **理由:** #107 の `TranscriptSource` は `Fetch(ctx, videoURL)` の形（タスク `0002`）とは入出力が異なる。生の字幕の文字列から `Transcript` を作る新しい実装になる。メタデータ（`title` 等）はサーバが受け取るので、#107 の実装に渡すか、サーバで `Transcript` に詰めるかを決める必要がある。
-   **候補の方針:** #107 の実装が動画 ID と字幕の文字列を受け取り、`Transcript` を返す形にする。サーバがメタデータを詰める場合、`transcript.Transcript` の exported フィールドを変更する必要はない。
-   **関連:** F-005、AC-19

## H-05: 非同期処理のライフサイクルと同時実行数の計上

-   **事項:** `202` を返した後の非同期処理（goroutine）のライフサイクル、サーバのグレースフルシャットダウン、context の伝播、同時実行数の計上の方法を決める。
-   **理由:** F-005 は非同期、F-006 は同時実行数の上限を求める。サーバの終了時に処理中のリクエストをどう扱うかを決める必要がある。
-   **候補の方針:** 同時実行数をセマフォ（バッファ付きチャネル）で計上し、上限に達したら拒否する。シャットダウン時は処理中のリクエストの完了を待つ（または待つ時間に上限を設ける）。
-   **関連:** F-005、F-006、AC-22

## H-06: 同時実行の上限超過の状態コードと `Retry-After`

-   **事項:** 同時実行数の上限を超えたリクエストの状態コード（`429` か `503` か）と、`Retry-After` を付けるかを決める。
-   **理由:** F-006 と F-008 の応答の設計。
-   **関連:** F-006、F-008、AC-22、AC-27

## H-07: リクエストの型を `transcript.Transcript` と別にする判断

-   **事項:** リクエストの型を `transcript.Transcript`（`internal/pipeline` の `TestCommonTypesFieldSets` が固定する）と別にするかを決める。
-   **理由:** リクエストは生の字幕の文字列を持ち、`Transcript` は解析済みの `Segments` を持つ。`transcript.Transcript` を変更すると、`internal/pipeline/pipeline_test.go` の guard を同じ変更で更新する必要がある。
-   **候補の方針:** 別の型にする。この場合、`transcript.Transcript` と `transcript.Segment` は変更しない。
-   **関連:** F-002、F-005、保守性

## H-08: 待ち受けのポートの設定と、サーバが使わない設定の検査

-   **事項:** 待ち受けのポートを与える設定（変数名、既定値の有無、受理する範囲）を決める。あわせて、`config.Load` がサーバの使わない設定を検査することをどう扱うかを決める。
-   **理由:** F-001 はポートを設定で固定するが、`internal/config` にポートの変数はない。また、`config.Load` は `YT2COLUMN_CACHE_DIR`・`YT2COLUMN_YTDLP_PATH` と既定のキャッシュディレクトリ（`HOME`・`XDG_CACHE_HOME` から導出）を常に検査する。そのままでは、サーバが使わない変数の不備（相対パスの `YT2COLUMN_CACHE_DIR`、`HOME` の欠落など）でサーバが起動できない（F-009）。
-   **候補の方針:** ポートは `internal/config` に変数を加え、既存の規則（補正しない、空の値はエラー）で検査する。使わない変数の検査は、入口ごとに読み込む項目を分ける（例: CLI 用とサーバ用の読み込み関数）か、サーバでも検査を受け入れて文書に記すかを選ぶ。サーバは共有トークンのファイルのパスを `XDG_CONFIG_HOME`・`HOME` から導出する（H-02）。キャッシュディレクトリの導出と同じ規則で扱えるか、あわせて決める。
-   **関連:** F-001、F-009、AC-29、AC-30、H-02

## H-09: #107・#108 との依存の順序

-   **事項:** #107（コピーした字幕のパーサと `TranscriptSource`）、#108（失敗を Slack へ投稿する仕組み）、本タスク（サーバ本体）の依存関係が双方向に見え、開発の着手の順序を決めにくい。依存の向きを整理し、各段階の前提を明確にする。
-   **理由:** 本タスクは #107・#108 の成果を使う（要件 2.3・§5）ので両者に依存する。一方で #108 は、本タスクが新設する `internal/failure` の型（`Kind`・`Notice`・`Notifier`、§3.9）を実装するため、本タスクにも依存するように見える。循環しているように見えると、どの作業から着手できるかが決まらない。
-   **候補の方針:** 契約（interface と型）と実装を分ける。契約を葉として先に凍結し、#107・#108 は契約にだけ依存させる。#107 と #108 は互いに依存しないので並行できる。本タスクのサーバは、ユニットテストでは fake の `Notifier` を使うので #108 の実装を待たず、#108 の実物が要るのは統合テストだけにする。
-   **関連:** F-005、F-007、§5、AC-11、AC-23
