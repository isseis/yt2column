## 1. 概要 (Overview)

**目的:** 本書は、ブラウザ拡張から字幕を受け取り、記事を生成して Slack へ投稿する localhost サーバ本体と、拡張との HTTP API の要件を定義する。

**背景:**
`yt-dlp` による字幕の取得は、YouTube から HTTP 429 を繰り返し受けることがある（[#43](https://github.com/isseis/yt2column/issues/43)）。そこで、字幕の取得を利用者に任せ、利用者が YouTube の「文字起こしを表示」パネルで選択した字幕の文字列を、ブラウザ拡張が localhost のサーバへ送り、サーバが記事を生成して Slack へ投稿する（[#104](https://github.com/isseis/yt2column/issues/104)）。

#104 は、コピーした字幕のパーサと `TranscriptSource`（[#107](https://github.com/isseis/yt2column/issues/107)）、失敗を Slack へ投稿する仕組み（[#108](https://github.com/isseis/yt2column/issues/108)）、本タスク（サーバ本体と API、[#109](https://github.com/isseis/yt2column/issues/109)）に分かれている。拡張側は、API に依存しない骨格と入力の収集（[#110](https://github.com/isseis/yt2column/issues/110)、タスク `0007_browser_extension_skeleton`）と、API に従った送信と結果の表示（[#111](https://github.com/isseis/yt2column/issues/111)）に分かれている。本タスクは、#107・#108 と CLI 版の完了を前提に、API を定義する。

`0007_browser_extension_skeleton/02_architecture.md` の §3.12 が、#109 の API の定義に必要な調査（拡張 ID、`Origin` ヘッダ、チャンネル名・概要欄の取得、共有トークンの受け渡し）を記録している。本タスクはその記録を参照する。

対応 issue: #109（親: #104、#43）

要件レビューの過程で挙がった、設計で決める事項は [design_handoff.md](design_handoff.md) に申し送る。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   拡張（#111）と、将来さらに拡張する拡張とが使う HTTP API を定義する。API は、拡張が容易に取得できる情報を必須、YouTube のサイトの DOM に依存する情報を任意として受け取る（F-002）。
-   拡張から受け取った字幕を検証・解析し、既存のパイプライン（`ArticleWriter`・`Publisher`）で記事を生成して Slack へ投稿する。CLI と同じコアロジックを共有する。
-   loopback の外からのアクセス、拡張以外からのアクセス、過大な入力、不正な入力を拒否する（F-003・F-004）。
-   認証済みのリクエストの失敗（字幕の書式、LLM の失敗、空の応答）を Slack へ投稿する（F-007、#108 の仕組みを使う）。
-   API とサーバの起動方法を文書化する（F-010）。

### 2.2. スコープ (In Scope)

-   `cmd/` の新しい入口としてのサーバ。`ArticleWriter`・`Publisher`・パイプラインを CLI と共有する（配置は設計で決める）。
-   拡張との HTTP API の定義（エンドポイント、リクエスト・応答の JSON、エラーの返し方、認証）（F-002・F-004・F-008）。
-   localhost からのアクセスだけを受け付ける安全対策（loopback への bind、`Host`・`Origin`・`Content-Type` の検査、共有トークン）（F-001・F-004）。
-   入力の検証（本文のサイズ上限、URL・動画 ID の検証、字幕書式の検証）と、同時実行数の制限（F-003・F-006）。
-   受け取った字幕の文字列から `Transcript` を作る `TranscriptSource`（#107）を使った記事の生成（F-005）。
-   失敗の Slack への投稿（F-007、#108）。
-   設定の読み込み（F-009、`internal/config` の再利用）。
-   文書: CLAUDE.md（「将来 Slack bot や定期実行の裏側にする」前提の見直し）、`project_overview.md`、`security.md`、README のサーバの起動手順（F-010）。

### 2.3. スコープ外 (Out of Scope)

-   ブラウザ拡張側の送信、共有トークンの設定画面と保存、サーバの応答の表示（#111）。
-   字幕書式のパーサと `TranscriptSource` の実装そのもの（#107）。本タスクは #107 の成果を使う。
-   失敗を Slack へ投稿する仕組みそのもの（#108）。本タスクは #108 の成果を使う。
-   `yt-dlp` の呼び出しと字幕・info.json のキャッシュ（`internal/transcript` の `YtDlpSource`）。本タスクのサーバは字幕を拡張から受け取るので、`yt-dlp` も `YT2COLUMN_YTDLP_PATH` も `YT2COLUMN_CACHE_DIR` も使わない。
-   サーバの起動の自動化（launchd など）。起動は手動とする（F-001）。
-   同時実行の上限を超えたリクエストの待ち行列（キュー）。上限を超えたリクエストは拒否する（F-006）。
-   API のバージョニング、複数のエンドポイント、共有トークンの自動のローテーション。漏洩時の作り直しは、利用者がトークンのファイルを削除してサーバを再起動する手動の手順とし、README に記す（F-001・F-010）。
-   生成した記事の全文を拡張へ返すこと、生成の進捗の通知、結果のポーリング（#111 の範囲、または将来）。
-   コラム生成プロンプトと記事の形式（タスク `0008_column_prompt`、`0010_post_generation_review`）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: サーバの起動と待ち受け

-   サーバは `cmd/` の新しい入口として実装し、`make build` でビルドできる。
-   サーバは `127.0.0.1` と `::1` だけに bind し、外部インターフェースのアドレスには bind しない。
-   ポートは設定で固定し、起動時に待ち受ける URL（ホストとポート）を利用者に示す。拡張は同じポートを使う（受け渡しは #111）。
-   共有トークンは、サーバの再起動をまたいで同じ値を使う。拡張への貼り付けは最初の 1 回で済む。
    -   サーバは起動時に、設定ディレクトリにあるトークンのファイルを読む（パスは設計で決める。[design_handoff.md](design_handoff.md) H-02）。
    -   ファイルがない場合、暗号学的に安全な乱数で共有トークンを生成し、所有者だけが読み書きできる権限でファイルに保存する。拡張へ貼り付けるために、生成したときだけ標準出力に表示する。
    -   ファイルがあるが、所有者以外に読み書きを許す権限である、または内容が規定の形式でない場合、待ち受けを開始せずに終了する。ファイルを修復も再生成もしない（CLAUDE.md「Reject, don't normalize」）。
    -   共有トークンは、生成時の表示とファイルを除き、応答・ログ・エラーメッセージに現れない。
    -   作り直すときは、利用者がファイルを削除してサーバを再起動する。
-   起動は手動とする。ログイン時の自動起動は行わない。
-   待ち受けを開始する前に設定を読み込み、必要な設定（プロバイダ、モデル、API キー、Slack Webhook URL）が欠けている場合は待ち受けを開始せず、値を出力せずに分かるエラーで終了する（F-009）。

**Acceptance Criteria**:
- **AC-01**: サーバを起動すると loopback（`127.0.0.1` と `::1`）で待ち受ける。外部インターフェースのアドレスからは接続できない（手動確認）。
- **AC-02**: トークンのファイルがない状態で起動すると、共有トークンが生成されて表示され、所有者だけが読み書きできる権限のファイルに保存される。同じ値で API の認証が通る。サーバを再起動しても、新しいトークンを表示せず、同じ共有トークンで認証が通る。共有トークンは、生成時の表示を除き、応答・エラーメッセージ・ログに現れない（F-004・F-008）。
- **AC-03**: 必要な設定が欠けている場合、またはトークンのファイルが不正（所有者以外に読み書きを許す権限、規定の形式でない内容）な場合、サーバは待ち受けを開始せず、終了する。トークンのファイルを修復も再生成もしない。その出力に、欠けている設定の値・API キー・Webhook URL・共有トークンが現れない。

#### F-002: HTTP API のリクエスト

-   サーバは、記事の生成を要求する 1 つのエンドポイントを設け、`POST` だけを受理する（`Origin` を検査するため。0007 §3.12.1）。エンドポイントのパスは設計で決める。
-   リクエストの `Content-Type` は `application/json` とする。それ以外は拒否する。
-   リクエストの本文は、次のメンバを持つ JSON のオブジェクト 1 つとする。

    | メンバ | 型 | 必須 | 内容 |
    |---|---|---|---|
    | `videoUrl` | string | 必須 | 動画ページの URL。拡張が起動したタブの URL |
    | `transcript` | string | 必須 | 利用者がコピーした字幕の文字列（生。時刻の行と本文の行を含む。補正しない） |
    | `title` | string | 任意 | 動画タイトル（動画ページの DOM から取る。タブのタイトルではない） |
    | `channelName` | string | 任意 | チャンネル名（動画ページの DOM から取る） |
    | `description` | string | 任意 | 概要欄（動画ページの DOM から取る。折りたたみ時は冒頭のみ） |

-   必須は、拡張がブラウザの安定な API（タブの URL、選択の API）から常に取得でき、サーバが記事の生成に欠かせない `videoUrl` と `transcript` の 2 つとする。
-   任意は、YouTube のサイトの DOM に依存し、サイトの変更で取得できなくなりうる `title`・`channelName`・`description` とする。拡張は取得できたときに送り、取得できなければ省略する。これらの任意フィールドを実際に取得する拡張の拡張は [#170](https://github.com/isseis/yt2column/issues/170) で扱う。
-   任意のメンバが欠落または空の場合も受理し、記事の生成を続行する。その場合、`Transcript` の該当フィールドは空文字列とする（F-005）。任意のメンバが存在し、その値が文字列でない（`null` を含む）場合は、欠落とみなさずに拒否する（CLAUDE.md「Reject, don't normalize」）。
-   リクエストのオブジェクトは拡張可能と宣言する。宣言していないメンバ（将来の拡張が加えるメンバを含む）は、値の種類を問わず無視して受理する。ただし、本文全体の検査（有効な UTF-8、対になっていないサロゲートのエスケープがないこと、JSON の構文、F-003）は宣言していないメンバにも及ぶ。宣言したメンバが重複する場合は拒否する。
-   リクエストの本文の大きさには有限の上限を設け、超える入力を拒否する（F-003）。

**Acceptance Criteria**:
- **AC-04**: `videoUrl` と `transcript` を含み、`Content-Type` が `application/json` の `POST` を受理する（F-005 の 202 を返す）。
- **AC-05**: `videoUrl` または `transcript` が欠落している、型が文字列でない、または空もしくは空白のみの場合、拒否し、記事の生成を開始しない。
- **AC-06**: `title`・`channelName`・`description` のそれぞれが欠落または空の場合でも受理し、`Transcript` の該当フィールドを空文字列として記事の生成を続行する。値が文字列でない（`null` を含む）場合は拒否する。
- **AC-07**: 宣言していないメンバを含むリクエストを受理する（値を無視する）。
- **AC-08**: `Content-Type` が `application/json` でないリクエストと、`POST` 以外のメソッドのリクエストを拒否する。

#### F-003: 入力の検証

-   `videoUrl` は、既存の YouTube の URL の検証（タスク `0002_ytdlp_transcript_source` の受理する URL と動画 ID の規則）に従って検証する。動画 ID は 11 文字の `[A-Za-z0-9_-]` とする。`t`・`list` などの `v` 以外のクエリは受理し、正規化した URL と動画 ID はサーバが導出する。
-   `transcript` は、有効な UTF-8 であり、空白文字以外の文字を 1 つ以上含むこととする。
-   字幕の書式の検証は #107 のパーサが行う。書式に合わない入力は補正せずに拒否する。
-   リクエストの本文には有限のサイズ上限を設ける。上限を超える本文は拒否する。上限は、本文を読み込む時点で適用し、上限を超える本文を全量バッファリングしない。
-   本文は、ヘッダだけで行える検査（F-002 のメソッド・`Content-Type`、F-004 の `Host`・`Origin`・共有トークン）をすべて通過した後にだけ読み込む。ヘッダの検査に失敗したリクエストの本文は読まない（認証のないリクエストにメモリと読み込みの時間を消費させないため）。
-   上限の具体値と適用方法は設計で決める（[design_handoff.md](design_handoff.md) H-01）。上限は、`internal/writer` のプロンプトの上限（`maxPromptBytes`）と整合させる。

**Acceptance Criteria**:
- **AC-09**: 受理しない `videoUrl`（スキームが `http`・`https` 以外、ホストが `www.youtube.com`・`youtube.com`・`m.youtube.com`・`youtu.be` 以外、`watch`・`embed`・`shorts`・`live` 以外のパス、`v` が複数、userinfo を含む、前後に空白がある、動画 ID が 11 文字の `[A-Za-z0-9_-]` でない、など。受理する形は `transcript.ValidateVideoURL` と同じ）を拒否し、記事の生成を開始しない。
- **AC-10**: `transcript` が空文字列、または空白文字だけの場合は拒否する。
- **AC-11**: `transcript` が #107 の字幕書式に合わない場合、拒否し（パーサのエラー）、補正しない。
- **AC-12**: 本文が上限を超えるリクエストは拒否する。上限を超える本文を全量バッファリングしない。ヘッダの検査（F-002 のメソッド・`Content-Type`、F-004）に失敗したリクエストでは、本文を 1 バイトも読まない。そのため、本文が上限を超え、かつ共有トークンが誤っているリクエストは、サイズ超過ではなく共有トークンの不一致として拒否される。
- **AC-13**: 本文のどこかに無効な UTF-8 または対になっていないサロゲートのエスケープ（`\ud800` など）を含む場合、拒否する（宣言していないメンバの中を含む）。

#### F-004: アクセスの制限（安全対策）

-   サーバは loopback だけに bind する（F-001）。これは防御の層であり、認証ではない（[security.md](../../dev/security.md) §8）。
-   `Host` ヘッダが loopback のホストと一致することを検査する。受理するのは `127.0.0.1:<ポート>`・`[::1]:<ポート>`・`localhost:<ポート>` とし、それ以外を拒否する（DNS rebinding への対策）。
-   `Origin` ヘッダが、固定した拡張のオリジン `chrome-extension://clfmbbcdpnjcefbdihdoahomaifbabkk`（0007 §3.12.1）であることを検査する。`Origin` がないリクエストと、一致しないリクエストを拒否する。`Origin` は送り元の認証ではない（拡張 ID は公開の `key` から決まる）ため、これだけに頼らない。
-   共有トークンを必須とする。共有トークンはリクエストのヘッダで受け取り（ヘッダの名前は設計で決める）、正しいときだけ受理する。共有トークンがない、または誤っているリクエストを拒否する。比較は定数時間で行う。
-   共有トークンその他の検証より前に、記事の生成・Slack への投稿などの副作用を起こさない（security.md §8）。

**Acceptance Criteria**:
- **AC-14**: `Host` ヘッダが loopback のホスト（`127.0.0.1:<ポート>`・`[::1]:<ポート>`・`localhost:<ポート>`）でないリクエストを拒否する。
- **AC-15**: `Origin` ヘッダがない、または `chrome-extension://clfmbbcdpnjcefbdihdoahomaifbabkk` でないリクエストを拒否する。
- **AC-16**: 共有トークンがない、または誤っているリクエストを拒否し、記事の生成を開始せず、Slack へも投稿しない。
- **AC-17**: F-004 の検査（`Host`・`Origin`・共有トークン）、F-002 の `Content-Type`・メソッドの検査のいずれかに失敗したリクエストでは、記事の生成も Slack への投稿も行わない（ローカルのログにだけ記録する）。F-007 の失敗の投稿も行わない。

#### F-005: 記事の生成と投稿

-   認証（F-004）と入力の検証（F-003）を通過したリクエストに対し、サーバは `202 Accepted` を返し、記事の生成と Slack への投稿を非同期で行う（LLM の呼び出しに数十秒かかるため、拡張を待たせない）。
-   記事の生成は、受け取った字幕の文字列から `Transcript` を作る `TranscriptSource`（#107）と、既存のパイプライン（`internal/writer` の `ArticleWriter`、`internal/publisher` の `SlackWebhookPublisher`）を使う。CLI と同じ実装を共有する。
-   `Transcript` の `VideoID` と `VideoURL` は、`videoUrl` を検証して導出した値とし、リクエストの URL 文字列をそのまま使わない。`VideoURL` は `VideoID` から導出した正規化 URL と一致させる。
-   `Transcript` の `Title`・`ChannelName`・`Description` は、任意のメンバの値とする。欠落または空の場合は空文字列とする。
-   `Transcript` の `Segments` は、#107 のパーサが `transcript` を解析して作る。
-   生成した記事は Slack Webhook へ投稿する（CLI と同じ `Publisher`）。File への出力は行わない。

**Acceptance Criteria**:
- **AC-18**: 認証と入力の検証を通過したリクエストに対して、サーバは `202 Accepted` を返し、記事の生成と Slack への投稿を行う。
- **AC-19**: 生成に使う `Transcript` の `VideoID` は `videoUrl` から導出した動画 ID と一致し、`VideoURL` はその動画 ID の正規化 URL と一致する。リクエストの `videoUrl` の文字列が `VideoURL` にそのまま入ることはない。
- **AC-20**: 記事の投稿先は Slack Webhook であり、CLI と同じ `Publisher` の実装を使う。
- **AC-21**: `202` の応答本文に、`transcript`・`title`・`channelName`・`description` の値、API キー、Webhook URL が含まれない。

#### F-006: 同時実行数の制限

-   サーバは、同時に処理するリクエストの数に有限の上限を設ける。
-   同時実行数が上限に達しているときに届いた新しいリクエストは、待ち行列に積まずに拒否する。処理中のリクエストは継続する。
-   上限の具体値と、拒否の状態コード（例: `429`・`503`）は設計で決める（[design_handoff.md](design_handoff.md) H-06）。

**Acceptance Criteria**:
- **AC-22**: 同時実行数が上限に達している状態で新しいリクエストを送ると、拒否され、記事の生成を開始しない。処理中のリクエストは継続し、完了する。

#### F-007: 失敗の Slack への投稿

-   認証済みのリクエストの処理が失敗した場合、その失敗を Slack へ投稿する（#108 の仕組みを使う）。対象は、入力の拒否（`videoUrl` の検証、字幕の書式、本文のサイズ超過）、LLM の失敗（通信の失敗、タイムアウト、空の応答、打ち切られた応答）、Slack への投稿の失敗とする。
-   失敗の Slack への投稿に、秘密情報（API キー、Webhook URL）と、受け取った字幕の本文（`transcript`・`title`・`channelName`・`description` の値）を含めない。
-   F-004 の検査と、F-002 のメソッド・`Content-Type` の検査に失敗したリクエスト（認証前）では、Slack へ投稿しない（AC-17）。認証のないリクエストに Slack を消費させないためである。
-   失敗の投稿そのものが失敗した場合、サーバは動作を続け、その失敗をローカルのログに記録する。応答は既に `202` を返しているので、利用者へ返せるものはない。

**Acceptance Criteria**:
- **AC-23**: 認証済みのリクエストの処理が失敗した場合（`videoUrl` の検証に失敗する、本文がサイズの上限を超える、字幕の書式が合わない、LLM がエラーを返す、LLM が空の応答を返す、Slack への投稿が失敗する）、失敗が Slack に投稿される。
- **AC-24**: 失敗の Slack への投稿に、API キー、Webhook URL、`transcript`・`title`・`channelName`・`description` の値が含まれない。例外のスタックトレースや内部のパスも含めない。
- **AC-25**: F-004 の検査に失敗したリクエストでは、Slack へ投稿しない。
- **AC-26**: 失敗の投稿自体が失敗した場合、サーバは動作を続ける。その失敗がローカルのログに記録される。

#### F-008: 応答とエラーの返し方

-   受理したリクエストには `202 Accepted` を返す（F-005）。
-   拒否したリクエストには `4xx` を返す。理由の種別（メソッドの不一致、`Content-Type` の不一致、`Host`・`Origin`・共有トークンの不一致、本文の形の不一致（JSON の構文、必須メンバの欠落・型の不一致、無効な UTF-8）、動画 URL の不正、字幕書式の不正、サイズ超過、同時実行数の超過）ごとに、対応する状態コードを返す。
-   応答の本文は JSON とし、理由の種別を表す固定の値だけを含める。応答の本文に、秘密情報と受け取った字幕の本文を含めない。
-   サーバ内部のエラー（生成・投稿の失敗）は、`202` を返した後の非同期処理で起きるため、応答として返らない。その失敗は Slack（F-007）とローカルのログに記録する。

**Acceptance Criteria**:
- **AC-27**: 拒否の理由の種別ごとに、対応する状態コードを返す。応答の本文に、API キー、Webhook URL、`transcript`・`title`・`channelName`・`description` の値が含まれない。
- **AC-28**: サーバ内部のエラーの応答（返す場合）にも、API キー、Webhook URL、字幕の本文が含まれない。

#### F-009: 設定の読み込み

-   サーバは、`internal/config` を再利用して設定を読み込む。値の扱い（補正しない、空の値はエラー、選んだプロバイダに関係しない変数は検査しない）は、既存の規則に従う。
-   必要な設定は、`YT2COLUMN_LLM_PROVIDER`（既定 `deepseek`）、`YT2COLUMN_MODEL`、プロバイダの API キー、`SLACK_WEBHOOK_URL`、待ち受けのポート（F-001。変数名と既定値の有無は設計で決める。[design_handoff.md](design_handoff.md) H-08）とする。`YT2COLUMN_REVIEW_PROVIDER`・`YT2COLUMN_REVIEW_MODEL` は、既存の規則どおりに反映する。
-   サーバは `yt-dlp` を呼ばないので、`YT2COLUMN_YTDLP_PATH` と `YT2COLUMN_CACHE_DIR` を使わない。現在の `config.Load` はこれらと既定のキャッシュディレクトリ（`HOME`・`XDG_CACHE_HOME` から導出）を常に検査するので、サーバがこれらの不備で起動できなくならないようにする方法は設計で決める（H-08）。

**Acceptance Criteria**:
- **AC-29**: サーバは `internal/config` の規則に従って設定を読み込む。`YT2COLUMN_MODEL` が未設定または空なら、待ち受けを開始せず、`errors.Is(err, config.ErrMissing)` が真になるエラーで終了する（利用者へ示す）。
- **AC-30**: `SLACK_WEBHOOK_URL` が未設定または空の場合、サーバは待ち受けを開始せず、終了する（Slack への投稿が必須のため）。`SLACK_WEBHOOK_URL` が不正な場合も同様に終了する。これらの出力に値が現れない。

#### F-010: 文書

-   CLAUDE.md: 「将来 Slack bot や定期実行の裏側にする」という前提を見直し、サーバを新しい入口として加える。サーバのビルド・起動・検査の手順を記す。
-   `project_overview.md`: 実行形式（CLI と localhost サーバ）と、サーバのパイプラインの入力元（拡張が送る字幕）を加える。
-   `security.md` §8: サーバの節に、loopback への bind、`Host`・`Origin`・共有トークンの検査、認証前の副作用の禁止、秘密情報の扱い、受け取る入力の境界を記す。共有トークンのファイルの場所と権限、拡張への受け渡しと拡張側の保存先（0007 §3.12.3）を記す。
-   README: サーバの起動手順、初回の起動時に示される共有トークンの拡張への貼り付け、トークンのファイルを削除して作り直す手順、`curl` による動作確認の例を記す。

**Acceptance Criteria**:
- **AC-31**: 上記の各文書に、上記の内容が記載されている（静的な確認）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

拡張が送る値と、その他のリクエストの要素は、信頼できない入力である。

| 境界 | 受理する形 | 上限 | 拒否時の理由 | 主な AC |
|---|---|---|---|---|
| リクエスト本文 | `application/json` のオブジェクト 1 つ。宣言したメンバ（`videoUrl`・`transcript`・`title`・`channelName`・`description`）を持ち、宣言していないメンバは無視する | 有限のバイト数（設計で決める）。ヘッダの検査（認証を含む）を通過した後、本文の読み込み時に適用 | `Content-Type` の不一致、サイズ超過、本文の形の不一致 | AC-08・AC-12 |
| `videoUrl` | 受理する YouTube の URL。導出した動画 ID が 11 文字の `[A-Za-z0-9_-]` | なし（本文の上限に含む） | 動画 URL の不正 | AC-09 |
| `transcript` | 有効な UTF-8。空白文字以外を 1 つ以上含む。#107 の字幕書式に合う | 本文の上限に含む | 字幕書式の不正、空 | AC-10・AC-11・AC-13 |
| `title`・`channelName`・`description` | 有効な UTF-8（空を許す） | 本文の上限に含む | 無効な UTF-8 | AC-06・AC-13・AC-24 |
| `Host` ヘッダ | loopback のホスト | - | `Host` の不一致 | AC-14 |
| `Origin` ヘッダ | `chrome-extension://clfmbbcdpnjcefbdihdoahomaifbabkk` | - | `Origin` の欠落・不一致 | AC-15 |
| 共有トークン | トークンのファイルに保存した値と一致するヘッダ | - | 共有トークンの欠落・不一致 | AC-16 |

本文の形について、標準ライブラリが黙って修復・破棄・無視すれば受理できてしまう入力は、受理せず拒否する。ただし、リクエストのオブジェクトの宣言していないメンバは拡張可能と宣言しており、無視して受理する（F-002）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   サーバは、認証と入力の検証を通過した時点で `202` を返す。記事の生成（LLM の呼び出し）を待たない。
-   本文の読み込みと検証は、記事の生成より前に行う。過大な入力と不正な入力を、LLM と Slack の前に落とす。

### 4.2. セキュリティ (Security)

-   `security.md` §8 に従う。loopback への bind は認証ではない。`Host`・`Origin`・`Content-Type`・共有トークンを併用する。
-   共有トークンを検証する前に、副作用（記事の生成、Slack への投稿）を起こさない。
-   API キー・Webhook URL・共有トークン・字幕の本文を、応答・ログ・エラーメッセージ・失敗の Slack への投稿に含めない。
-   トークンのファイルは、所有者だけが読み書きできる権限とする。同じ OS の利用者として動くプロセスから読める点は、`.envrc` に置く秘密情報と同じ信頼の範囲である（0007 §3.12.3）。
-   受け取った字幕・メタデータは、プロンプトに埋め込まれる信頼できない入力として扱う（security.md §6）。生成結果を他のコマンドやコードとして実行しない。
-   エンドポイントは `POST` に限る。`host_permissions` がなくても preflight の不要な `POST` は届きうるので、認証前に副作用を起こさない（0007 §3.12.1）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   1 つのリクエストの失敗（入力の拒否、LLM の失敗、Slack の失敗）でサーバは停止しない。次のリクエストを処理し続ける。
-   認証済みの失敗は Slack へ投稿し、失敗の投稿も失敗した場合はローカルのログに残す（F-007）。
-   記事の投稿が途中で失敗した場合、成功として扱わない。失敗として Slack へ投稿する（#108・F-007）。

### 4.4. 互換性 (Compatibility)

-   利用時: macOS 上の Chrome と Brave の、作業時点の安定版から送られるリクエストを受理する（拡張 ID は固定、0007 §3.12.1）。
-   サーバは Go のシングルバイナリとしてビルドでき、外部ライブラリを追加しない（標準ライブラリの `net/http` を使う）。

### 4.5. 保守性 (Maintainability)

-   記事の生成と投稿は、CLI と同じパイプライン・`ArticleWriter`・`Publisher` を共有する。サーバ固有のコードは、HTTP の受け口、入力の検証、認証、応答に限る。
-   リクエストの型は、`transcript.Transcript`（`internal/pipeline` の `TestCommonTypesFieldSets` が固定する）と別にする（設計で決める。[design_handoff.md](design_handoff.md) H-07）。
-   拒否の理由は、文字列の内容から推し量らず、型または固定の値で表す（CLAUDE.md「Declare, don't infer」）。
-   本文、字幕、メタデータは補正しない。合わない入力を修復せずに拒否する（CLAUDE.md「Reject, don't normalize」）。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。外部ライブラリは追加しない。
-   依存: 字幕のパーサと `TranscriptSource`（#107）、失敗を Slack へ投稿する仕組み（#108）、`SlackWebhookPublisher`（#7）、CLI 版の完了（#3〜#8）。
-   `internal/config` を再利用する。設定の読み込みの規則を変えない。
-   `internal/pipeline` の `TestCommonTypesFieldSets` が `transcript.Transcript` と `transcript.Segment` の exported フィールドを固定している。本タスクでこれらの型を変更する場合、同じ変更で guard を更新する。リクエストの型を別にすれば、これらの型は変更しない。
-   サーバは `yt-dlp` を呼ばない。字幕は拡張から受け取る。
-   共有トークンの受け渡しは、拡張のオプションページに利用者が貼り付ける方法を候補とし、拡張側の保存先は `chrome.storage.local` を候補とする（0007 §3.12.3）。共有トークンはサーバの再起動をまたいで変わらないので、ブラウザの再起動をまたいで保持する `local` に意味がある。確定は #111 で行う。
-   ユニットテストは、実際のブラウザを起動せず、LLM の API も Slack の Webhook も呼ばない。HTTP の受け口は `net/http/httptest` で試す。
-   [project_overview.md](../../dev/project_overview.md) と CLAUDE.md の文書を更新する（F-010）。

## 6. 用語集 (Glossary)

-   **サーバ:** 本タスクで作る、loopback で待ち受ける localhost サーバ。拡張から字幕を受け取り、記事を生成して Slack へ投稿する。
-   **API:** 拡張とサーバの間の HTTP の取り決め（エンドポイント、リクエスト・応答の JSON、エラーの返し方、認証）。
-   **共有トークン:** サーバが初回の起動時に生成してファイルに保存し、正しい拡張だけが使えるようにリクエストに付ける値。サーバの再起動をまたいで同じ値を使う。`Origin` は認証にならないため、これで補う。
-   **loopback:** 同じマシンの中だけで使えるアドレス（`127.0.0.1`・`::1`・`localhost`）。
-   **生の字幕:** 利用者が「文字起こしを表示」パネルでコピーした、時刻の行と本文の行を含む文字列。補正しない。
-   **メタデータ:** `title`・`channelName`・`description`。動画ページの DOM に依存する任意の情報。
-   **2 つの起動の経路:** 右クリックメニューとツールバーのアイコン（0007）。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
