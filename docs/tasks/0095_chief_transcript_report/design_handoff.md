# 設計への申し送り：0095 chief が Claude Code の pane の最後の報告を transcript から読む

要件定義（[01_requirements.md](01_requirements.md)）の段階で挙がった、設計（`02_architecture.md`）で決める事項。設計書は、各項目をどう扱ったか、または扱わない理由を記録する。

## H-01: 「最後に終わった応答」を transcript のどの行と項目から見分けるか

**懸念:** 要件（AC-01〜AC-04、4.2）は、最後に終わった応答の本文を報告とすることと、使う項目の種類と値の扱いだけを定めている。2026-11-16 に手元の transcript で確かめたところ、次のとおりだった。

-   応答は `type` が `assistant` の行に書かれる。
-   1 つの応答（同じ `message.id`）は、本文の部分ごとに複数の行に分かれる（`thinking`・`text`・`tool_use`）。同じ `message.id` の思考だけの行と文字の行の両方に `stop_reason` が `end_turn` と書かれていた。
-   ターンを終えた応答は、`message.stop_reason` が `end_turn` である。
-   その後に `type` が `system`（`subtype` が `turn_duration`）の行などが続く。
-   サブエージェントの行は `isSidechain` で見分けられる。

ただし、これはサンプルとして採ったものではない。

**なぜ重要か:** 見分け方を誤ると、途中の応答（ツールを呼ぶ前の文）、サブエージェントの応答、Claude Code が自ら書いた記録（API のエラーの知らせ、compact の要約、recap、Stop フックの返事、task-notification や peer の入力に応えた応答）を報告と読む。そうすると、①の照合や④の確かめが誤った報告で通る。

**候補:**

-   実際の `/mkarch` などの実行の終わりと、`/runpr` の報告の終わりの transcript をサンプルとして採る。サンプルは、採った人を特定できる値を置き換えてから `internal/chief/testdata/transcript/` に置く（要件書 4.2 の「サンプルの取り扱い」）。
-   そのサンプルで、次の規則を確かめる。
    -   `stop_reason` と `message.id` で応答の終わりとまとまりを決める。
    -   `text` の部分だけを本文とする。
    -   最後に終わった応答の後に、人の入力の行（今の `readLastHumanInput` の規則で人の入力と見分ける行）か、新しい `assistant` の行があれば、報告はないものとする（AC-02）。
    -   Claude Code が自ら書いた記録を、どの項目で見分けるか（AC-04）。
-   `/runpr` の報告のサンプルで、NEXT の行が Markdown のままどう書かれるかを確かめ、要件書 AC-07 の文法（今の画面の文法）で読めることを確かめる。読めなければ、要件に戻って文法を決め直す。

**関係する ID:** F-001、AC-01〜AC-04、AC-06、AC-07、4.2

## H-02: transcript を読む量の上限の値と、読む回数

**懸念:** 要件は有限の上限を求め、値を設計に委ねている。今は、`/model` の後の確かめに 1 MiB（`internal/chief/transcript.go:29` の `transcriptLimit`）、リセットに 64 MiB（同 30 行の `resetTranscriptLimit`）を使う。PR を作ったコマンドのセッションは、0088 のサンプルで数 MB になった（同 24〜27 行のコメント）。

**なぜ重要か:** 上限が小さいと、長い実行の後の報告が読めず、③④が今と同じく働かない。大きすぎると、①で workspace の Claude Code の pane ごとに大きなファイルを読む。

**候補:**

-   報告の読み取りにはリセットと同じ 64 MiB を使う。
-   ①で workspace の Claude Code の pane ごとに transcript を読む時間を測り、実害がないことを確かめる（CLAUDE.md の「Performance」）。
-   ④では、人の最後の入力、PR の記録、最後の報告を、1 回の読み取りからまとめて読む。
-   末尾から読む方法は、最後の人の入力が先頭にありうること（同 24〜27 行のコメント）と、全体の形の確かめ（要件書 4.2）を満たすかを確かめてから選ぶ。

**関係する ID:** AC-12、4.1、4.2

## H-03: Herdr がセッションを報告しない Claude Code の pane と、/clear の後の pane

**懸念:** 要件（AC-12・AC-14）は、セッションの報告がない Claude Code の pane を「transcript を読めない」とし、①ではその workspace に送らない。今の①は、画面を読めれば、セッションの有無に関わらず照合できる。一方、セッションの報告があってファイルがないときは「報告がない」とする（AC-02）。

**なぜ重要か:** 起動した直後や `/clear` の直後に、Herdr がセッションを報告しない Claude Code の pane がよくあると、`/runplan` を OpenCode へ送るときにも、自動送信が止まる。chief 自身が `/clear` で空にした pane（④）が、次のマージの①でこの状態になりうる。

**候補:**

-   0088 の採取と chief の待ち受けの記録で、入力を受け付ける状態の Claude Code の pane にセッションの報告がないことがあるかを確かめる。`/clear` → 入力を待つ状態 → 次のマージ、という流れで、Herdr のセッションの報告と transcript のファイルがどうなるかを確かめる。
-   セッションの報告がないことがよくあるなら、要件書の AC-12 を変えるかを人に尋ねる（要件の変更なので、設計では決めない）。

**関係する ID:** AC-02、AC-07、AC-12、AC-14

## H-04: 示す本文の上限と無害化の部品

**懸念:** 今の報告は、画面の上限（`CapScreen`）で切って控える（`internal/chief/detail.go:453`）。transcript から読んだ報告は画面より長くなりうる。上限と切り方を、画面の部品のまま使うか、報告用に分けるかが決まっていない。

**なぜ重要か:** 上限が画面の行数を前提にしていると、長い報告の要約の材料が足りなくなるか、chief のセッションへ渡す量が大きくなりすぎる。

**候補:** 今の `CapScreen` の上限の値と単位を確かめ、報告に合わなければ報告用の上限を設ける。制御文字と見えない文字の置き換え（`internal/chief/sanitize.go`）は同じものを使う。

**関係する ID:** AC-09、4.2

## H-05: 使われなくなる Claude Code の報告の画面の読み取り

**懸念:** この変更の後、Claude Code の画面から最後のメッセージを切り出す部品（`claudeLastMessage` と、その `※ recap:` の読み飛ばし、`internal/chief/screen_report.go`）と、そのサンプル（`internal/chief/testdata/screens/claude-command-report*.ansi`）は、報告の読み取りに使われなくなる。

**なぜ重要か:** 使われない関数は `make deadcode` で失敗する。テストを消すときは、CLAUDE.md の「Testing Strategy」のとおり、消すコミットを分けて `make coverage-compare` で確かめる必要がある。画面の読み取りをまとめて消すのは #908 の範囲である。

**候補:**

-   このタスクで使われなくなる関数とそのテストを消す（消すコミットを分け、coverage-compare の結果を残す）。
-   画面のサンプルがほかのテスト（入力欄の判定など）で使われていれば残す。

**関係する ID:** AC-06、2.3（スコープ外の #908）

## H-06: PR の記録（`pr-link` の行）がいつ書かれるか

**懸念:** 要件（AC-05・AC-09・AC-10）は、セッションが作った PR を、transcript の PR の記録で見分ける。2026-11-16 に手元の transcript で、`type` が `pr-link` の行（`prNumber`・`prUrl`・`prRepository`・`timestamp`）を確かめた。ただし、サンプルとしては採っておらず、どの操作で書かれるか（`gh pr create` を走らせたときか、PR の URL を出力したときか、ほかのリポジトリの PR でも書かれるか）は確かめていない。

**なぜ重要か:** PR を作ったコマンドの実行で記録が書かれなければ、③④は働かない。PR を作っていないセッションでも書かれるなら（たとえば PR の URL を示しただけで書かれるなら）、宣言された値で見分ける利点が薄れる。

**候補:**

-   `/mkarch` などが PR を作った実行の transcript をサンプルとして採り、記録が書かれることと、その位置（最後に終わった応答との前後）を確かめる。
-   PR を作らずに URL を示しただけのセッションで記録が書かれるかも確かめる。
-   PR を作ったコマンドの実行で記録が書かれないと分かったら、要件に戻って決め直す（要件書「要件定義の際に決めたこと」）。
-   `prRepository` がこのリポジトリと違う記録を、その PR の記録とみなさないかどうかを決める。

**関係する ID:** AC-05、AC-09、AC-10、4.2

## H-07: Herdr の状態と transcript の書き込みの間の遅れ

**懸念:** Claude Code は、コマンドの記録を少し遅れて transcript に書く（`internal/chief/transcript.go:33-35` のコメント。`/model` の記録について）。Herdr が入力を待つ状態を報告した時点で、最後の応答がまだ書かれていないことがありうる。③の控えは PR の head ごとに 1 回作って残す（`internal/chief/detail.go:430-438`）。最後の応答が書かれる前に読むと、③はその head の間ずっと PR の説明を示し、④はその pane を空にしない（`internal/chief/reset.go:118`）。

**なぜ重要か:** 安全側の失敗ではあるが、この変更で直したい「③④が働かない」が、別の理由で残る。

**候補:** 遅れがあるかを確かめる。あれば、報告がないときは控えを作らずに次の周で読み直すか、短い間を置いて読み直す（`/model` の後の確かめと同じ形）。

**関係する ID:** AC-09、AC-10、4.3
