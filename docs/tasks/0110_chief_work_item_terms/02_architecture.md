## 1. 設計の全体像

本タスクは文書だけを変える。用語集に 3 つの語を足し（[01_requirements.md](01_requirements.md) F-001）、その語で、chief のガイドの 3.1 を書き直す（F-002）。ADR-0046・ADR-0035・サンプルの説明（F-003）と、0102・0105 の承認済みの文書（F-004）の古い用語は、編集上の訂正として直す。chief の道具、`/chief` の定義、protocol 番号は変えない（F-005）。

**設計原則:**

-   **語の置き換えは、決まった対応の表に従う（3.2 節）。** 文書ごとに言い換えを考えると、同じ概念が文書ごとに違う語になるためである。文の言い回しは、置き換えた語が日本語として自然に読める範囲でだけ変える。
-   **意味は変えない。** 値の集合、各値の決まり方、表示する文字列、決定は変えない。変えるのは呼び名だけである。

**設計の際に決めたこと（2026-11-19）:**

-   なし。人に聞くべき未決の判断はなかった。変える文書とその範囲は、要件定義で人が選んだ（要件書 1 章の「要件定義の際に決めたこと」）。英語の訳語（3.1 節）は、用語集の既存の訳語と重ならないものを選んだ。置き換えの対応（3.2 節）は、要件書の F-001 の定義から決まる。
    -   ADR: なし。本タスクの中で閉じる。

本書の行番号は、コミット `910bb12b`（`origin/main`）で確かめた。

概念モデルとシステム構成の Mermaid の図は省く。文書の用語を変えるだけで、コンポーネントの関係は変わらない（`docs/dev/conventions/requirements_process.md`「Simple Process」の「May be omitted」）。

### 3.1. 用語集に足す語

`docs/translation_glossary.md` の chief の語（「ラウンド」、`docs/translation_glossary.md:144`）の後に、次の 3 行を足す（AC-01〜AC-04）。

| 日本語 | English | 備考に書くこと |
|---|---|---|
| タスクの進行 | task progression | タスクは、決まった順の作業項目を 1 つずつ進む。通常の進め方の順は、要件定義書の作成 → 設計書の作成 → 計画書の作成 → 計画書の PR-1 → PR-2 → … である。簡易な進め方では、3 つの文書を 1 つの作業項目（3 つの文書の作成）で作り、計画書の PR が続く。旧称：進行の位置（chief の状況の表の行が示す、今の作業項目と作業項目の状態の組） |
| 作業項目 | work item | タスクの進行の 1 つの単位。まだ終わっていない最初の作業項目を「今の作業項目」と呼び、chief の状況の表は「文書」の列に示す（0102 の後は「タスク」の列の 2 行目）。-・なし・要確認は作業項目ではなく、今の作業項目がないか決められないことを示す値である。旧称：進行の位置の文書、文書の段 |

-   英語の訳語は、用語集の「ステージ」（stage）・「工程」（step）・「フェーズ」（phase）・「工程の状態」（step state）と重ならない（AC-04）。
-   「作業項目の状態」の値の一覧は、今の値（ガイドの 3.1）の例として挙げる。値の集合を定めるのはガイドなので、0102 が値の文字列を縮めても（「作業中」など）、用語集を直さずに済むように「など」で結ぶ。

### 3.2. 古い用語の置き換えの対応

すべての文書で、次の対応で置き換える（AC-10・AC-11〜AC-13・AC-15）。

| 古い用語（chief の状況の表の意味） | 新しい用語 |
|---|---|
| 進行の位置（組） | 今の作業項目とその状態。文脈によっては、今の作業項目と作業項目の状態 |
| 進行の位置の文書、文書の段、行の「文書」（例：`Row.Position.Document` を指す「行の文書」） | 今の作業項目。値の種類を述べるときは作業項目 |
| 進み具合 | 作業項目の状態 |
| 英語（CLAUDE.md など）で、上を訳した語（例：document stage） | work item、work item state |

-   表の列の見出し「文書」「状態」は、表の見出しの文字列なので置き換えない（要件書 1 章）。「『文書』の列」のように列を名指す箇所も、そのまま残す。
-   コードの名前と出力の項目（`PositionDocument`・`position.document` など）は置き換えない（F-005）。
-   「進み具合」は、chief の状況の表の意味の箇所だけを置き換える。計画書の PR の進み具合のチェックボックス（`docs/dev/adr/0013-review-setup.md:24` など）や、拡張の工程の進み具合は置き換えない（要件書 2.3 節）。
-   「文書」も、chief の行の値を指す箇所だけを置き換える。タスクの文書（要件定義書など）を指す「文書」はそのまま残す。

### 3.3. ガイドの 3.1 の書き直し

`docs/dev/guides/chief_guide.md` の 3.1「状況の表の見方」を、次のように変える（AC-05〜AC-10）。

| 今の箇所 | 変え方 |
|---|---|
| `:57` の「急ぎの度合い・進行の位置と行の並び」 | 「急ぎの度合い・今の作業項目とその状態・行の並び」 |
| `:63` の「文書」の行の中身「タスクがどの文書の段にあるか」 | 「今の作業項目（タスクの進行のどこにいるか）」 |
| `:64` の「状態」の行の中身「進み具合。…」 | 「作業項目の状態。…」（後半の「行の状態を、…細かくしたもの」は残す） |
| `:82` の段落「**進行の位置。**」 | 次の 3 つの段落に替える |
| `:92` の段落「**調べ方。**」 | 出力の項目の対応を 1 文足す |

`:82` に替える段落の中身：

1.  **タスクの進行。** タスクは、決まった順の作業項目を 1 つずつ進む。通常の進め方では、要件定義書の作成 → 設計書の作成 → 計画書の作成 → 計画書の PR-1 → PR-2 → … と進む。簡易な進め方では、3 つの文書を 1 つの作業項目で作り、その後に計画書の PR が続く。PR マーカーのない計画書の PR は PR-1 である（AC-05）。
2.  **今の作業項目。** まだ終わっていない最初の作業項目で、`origin/main` のタスクの文書から決まる。「文書」の列は、要件定義書・設計書・計画書・PR-N（計画書の PR のうち、まだマージされていない最初のもの）のどれかを示す。作業項目でない値が 3 つある。-（タスクのないブランチ）、なし（すべての作業項目が終わった）、要確認（今の作業項目を決められない。fetch や文書の読み取りに失敗した、HEAD が detached など）である（AC-06）。簡易な進め方のタスクは、3 つの文書の PR がマージされるまで「要件定義書」と示される。`origin/main` の文書からは、マージの前に進め方が分からないためである（AC-07）。
3.  **作業項目の状態。** 今の作業項目がどこまで進んだかで、行の状態と実行中のコマンドから決まる。値は今の `:82` の後半と同じ（作成待ち（表では「次を提案」と示す）・作成中・`/runpr` 実行中・実行中・マージの確認待ち・質問で停止・レビュー待ち・タスク完了・要確認）である（AC-08）。

「調べ方」に足す文：今の作業項目は出力の `position.document`（PR-N の N は `position.plan_pr`）に、作業項目の状態は `position.progress` に入る（AC-09）。

段落の言い回しは実装で整えてよい。ただし、値の集合と各値の決まり方は今の `:82` から変えない（AC-06・AC-08）。

**先に変わったときの扱い（AC-10・AC-18）。** 実装の PR を作るときに、0102 の PR-3（ガイドの 3.1 と 8 章）か 0105 の実装（AC-12 の書き足し）が先にマージされていれば、上の行番号は合わない。そのときは、その時点の 3.1 に同じ内容（タスクの進行、今の作業項目、作業項目の状態、出力の項目の対応）を入れ、3.2 節の対応で古い用語を置き換える。0102 が書いた表の形（5 つの列と 2 行目）や 0105 が書き足した 4 点は、用語だけを替えて残す。

## 7. テスト戦略

-   恒久のテストは足さない。古い用語が残っていないことを確かめるテストは、`CLAUDE.md`「Testing Strategy」の「assert that an old name is absent from a document」に当たるためである。

-   用語集・ガイドの中身（AC-01〜AC-09・AC-11〜AC-13）は、PR のレビューで読む。
-   文書を読む既存のガード（`doc-guard` のジョブ）は、ガイドの値と ADR の形を読む。`make test` で通ることを確かめる。
