## 1. 概要 (Overview)

**目的:** 本書は、テストを削除する変更の前と後の 2 つのコミットでカバレッジを取り、関数ごとに比べる常設の道具の要件を定義する。対象は Go のコードとブラウザ拡張のコードの両方である（[#618](https://github.com/isseis/yt2column/issues/618)）。あわせて、[CLAUDE.md](../../../CLAUDE.md)「Deleting a test is a claim that must be checked」を、この道具を使う手順に書き換える。

**背景:**

[CLAUDE.md](../../../CLAUDE.md)「Testing Strategy」の「Deleting a test is a claim that must be checked」は、テストを削除した後に `go tool cover -func` の結果が関数ごとに変わらないことを確かめ、そう書くよう求めている（`CLAUDE.md:490-491`）。この確認には常設の道具がない。`make` の対象にある `go tool cover -func` の呼び出しは、CI 向けの `make test-ci` が全体の網羅率の 1 行を出すものだけである（`Makefile:101-103`）。そのため、テストを削除するタスクのたびに、比べる手順を設計し直し、一度きりの道具を作ってきた。

-   0027：拡張の lcov の行・分岐・関数を、ソースの差分（`git diff`）で前後の行を対応づけて比べた。行番号のずれもこの対応で扱った（0027 `02_architecture.md` 3.11）。
-   0038：BASE と HEAD の作業用のチェックアウトを作り、`go test -tags test -count=1 -coverpkg=./... -coverprofile=<file> ./...` の `go tool cover -func` の出力が同じであることを確かめるスクリプトを作った（`docs/tasks/0038_doc_test_pruning/check_pruning.sh:480-505`、0038 `02_architecture.md` 7.1）。`-coverpkg=./...` を付けたのは、`cmd/yt2column` のテストが `internal/` のパッケージのコードも実行するので、パッケージごとに測ると、削除で起きる別のパッケージの網羅率の低下を見落とすからである。
-   0046：拡張の lcov の関数の実行回数が 0 にならないことを、CLAUDE.md の規則の拡張での読み替えとして確かめた（0046 `03_implementation_plan.md` 1.2）。
-   0052：2 つの `go tool cover -func` の出力を比べる Go の道具を作った（`docs/tasks/0052_doc_test_pruning/_checks/coverage/main.go`）。比べる対象を製品のコード（`_test.go` でも、ビルドの制約が `test` で始まるファイルでもない Go のファイル）に限った（0052 `01_requirements.md` AC-11）。
-   0054：拡張の lcov の関数の実行回数が 0 にならないことを、CLAUDE.md の規則の方針の例外として要件で承認を得たうえで確かめた（0054 `01_requirements.md` 1 章「方針の例外」、`02_architecture.md` 3.2）。最終的な変更は 2 ファイル・16 行の削除だったのに対し、ローカルのレビューの指摘の多くは、この一度きりの比較の手順の頑健さに集中していた（issue #618）。

0054 の設計で分かった、拡張の lcov を比べるときの注意点は次のとおりである（0054 `02_architecture.md` 3.2）。

-   名前のない関数の `anonymous_<番号>` は、同じコミットでも実行のたびに変わる。名前のある関数でも、1 つのファイルに同じ名前が複数あることがある（`<instance_members_initializer>`）。そのため、関数は (ファイル, `FN` の行) で識別する。
-   1 つの `FN` の行から複数の関数が始まることがある（入れ子のアロー関数）。
-   カレントディレクトリやテストの指定を誤ると、テストが 1 つも動かずに報告が空になり、比較が通ってしまう。
-   テストが失敗した実行の報告は使えない。失敗したテストが実行させるはずの関数が、報告から欠けるからである。

後続の [#619](https://github.com/isseis/yt2column/issues/619)（軽量プロセスの定義）は、類型 D「削除」の確かめ方として、本タスクの道具を使う予定である。

対応 issue: [#618](https://github.com/isseis/yt2column/issues/618)（関連: [#560](https://github.com/isseis/yt2column/issues/560)・[#619](https://github.com/isseis/yt2column/issues/619)）

**本書の記述範囲:** 本書は、道具の入口、比べる対象と合格の基準、止まる場合とそのときの報告、合格したときに出す結果、道具が自分自身を確かめるテスト、CLAUDE.md の手順の書き換えを定める。道具を書く言語と置き場所、カバレッジの報告の取り方（コマンドとその引数）、前後の行の対応と関数の範囲の求め方、作業用のチェックアウトの作り方、結果の行の正確な書式、テストの手段は、設計（`02_architecture.md`）で決める。0038・0052 の道具を再利用するかどうかも設計で決める。要件の作成で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #618 で決めたこと:**

-   **対象は Go と拡張の両方:** Go は `go tool cover -func` の関数ごとの網羅率を、拡張は `node --test --experimental-test-coverage --test-reporter=lcov` の `FN`・`FNDA` を比べる。0054 の注意点は道具の中で扱う。それぞれのタスクで比べる手順を設計し直さずに済むようにするためである。
-   **比べるのは 2 つのコミット:** 削除の前と後の 2 つのコミットでカバレッジを取る。
-   **基準は「削除の前に実行された関数が、削除の後も実行されている」こと:** あわせて、削除した関数だけが消えたことも確かめる。
-   **合格とせずに止まる場合:** 何も測れていない場合、テストが失敗した場合、関数の対応が取れない場合は止まる。この止まり方を、壊した報告で確かめるテストを道具の側に持たせる。測れていない比較が通るのを防ぐためである。
-   **CLAUDE.md の書き換え:** 「Deleting a test is a claim that must be checked」を、この道具を使う手順に書き換える。これで、拡張での比較は方針の例外ではなくなる。
-   **CI では自動実行しない:** 道具は、テストを削除する変更で人や agent が実行する。

**要件定義の際に決めたこと（2026-11-02）:**

この節で使う「製品のコード」「残る関数」「削除した関数」「対応が取れない」「停止の種類」は、6 章で定義する。

-   **比べる細かさ:** Go は、関数ごとの網羅率が削除の前より下がらないことを確かめる。拡張は、削除の前に実行回数が 1 以上だった関数が、削除の後も 1 以上であることを確かめる。どちらも行と分岐の単位では比べない。Go は関数ごとの網羅率をそのまま出せるため、比べる手間を増やさずに、関数の中の文の網羅率の低下まで見つけられる。拡張の lcov の関数の記録は実行回数だけを持つので、issue の基準どおりに比べる（F-003）。
    -   今の CLAUDE.md と 0038・0052 は「関数ごとに変わらない」ことを求めた（`CLAUDE.md:490-491`、0038 `02_architecture.md` 7.1）。本書の基準「下がらない」は、字義の上ではそれより緩い。ただし、残る関数の中身が変わる変更は止める（下の「削除以外の変更で対応が付かなければ止める」）ので、網羅率の分母は前後で変わらない。テストを削除して網羅率が上がるのは、テストの順序などで実行が変わる場合に限られ、それは削除の確認の失敗ではない。CLAUDE.md の書き換え（F-008）は、この基準に改める。
-   **削除した関数は差分から求める:** 前後のソースの差分で削除された行から始まる関数を、削除した関数とする。利用者は削除した関数を指定しない。行番号のずれに対応を付けるために差分はどのみち使うので、指定の誤りという新しい失敗を増やさないためである（F-004）。
-   **Go はモジュール全体で測る:** Go の関数は、モジュールのどのパッケージのテストから実行されても数える（0038 の `-coverpkg=./...` と同じ範囲）。理由は 0038 と同じで、パッケージごとに測ると、ほかのパッケージのテストだけが実行させていた関数が実行されなくなること（網羅率の低下）を見落とすからである。拡張の lcov も、どのテストからの実行も数える（F-003）。
-   **比べる時点は BASE と HEAD:** 削除の前は利用者が指定したコミット（BASE）、削除の後は今のコミット（HEAD）とする。コミットしていない変更があれば止める。測った内容とコミットした内容が同じであることを保つためである（0054 `02_architecture.md` 3.2 と同じ前提。F-001）。
-   **BASE は HEAD の祖先に限る:** BASE が HEAD の祖先でなければ止める。無関係なコミットや子孫のコミットとの比較は、削除の確認にならないためである。テストの数が減っていなくても止めず、前後の数を結果に出す。テストの中の確認を一部だけ消す変更では、テストの数が減らないためである（F-001・F-005）。
-   **削除以外の変更で対応が付かなければ止める:** 残る関数の始まりの行が書き換わっている場合、残る関数の範囲の中に差分の行（追加・書き換え・削除）がある場合、HEAD にだけある関数がある場合は、どれも「関数の対応が取れない」として止める。Go と拡張の両方に当てはめる。この道具は削除を確かめるためのものであり、中身が変わった関数や新しい関数は、前後で同じ条件で比べられないためである（F-004）。
-   **比べるのは製品のコードだけ:** Go は、ビルドの制約が `test` のタグを求める、または `test` のタグで成り立つファイル（`//go:build test`、`//go:build test || integration` など。0052 AC-11 と同じ）を比べない。拡張は `extension/src/` と `extension/scripts/` の下のファイルだけを比べ、`extension/test/` の下のファイルは比べない。テストを削除すると、テストの補助のコードの網羅率が下がるのは自然なことであり、製品のコードに影響のない削除でも不合格になってしまうためである（F-003）。
-   **入口は Go と拡張で 2 つ:** Go 用と拡張用の、2 つの `make` の対象を設ける。拡張だけのテストを削除するときに、Go の全テストを 2 回走らせずに済むためである。名前は issue の例のとおり `make coverage-compare BASE=<commit>` と `make ext-coverage-compare BASE=<commit>` とする。CLAUDE.md の「Commands」にも載せる。CLAUDE.md は `make` の対象の一覧を持つので、載せないと agent が道具を見つけられないためである（F-001・F-008）。
-   **結果にはツリーの ID も出し、コミットメッセージと PR の説明に書く:** 結果を書くには、削除をコミットしてから道具を実行し、そのコミットのメッセージを直すことになる。メッセージを直すとコミットの ID は変わるが、ツリーの ID は変わらない。そこで道具は、HEAD のコミットの ID とツリーの ID の両方を出す。PR は squash merge され、ブランチのコミットメッセージは `main` に残らない（`.claude/commands/_context.md`「PR merge method」）。そのため、PR の説明にも書く。PR の説明に書く点は 0052 AC-11 と同じである（F-005・F-008）。
-   **同じ行から始まる拡張の関数は、実行された数で比べる:** 1 つの行から複数の関数が始まるとき、その行から始まる関数の数が前後で違えば、対応が取れないとして止める。数が同じなら、その行で実行回数が 1 以上の関数の数を前後で比べ、同じなら合格、減れば不合格、増えれば対応が取れないとして止める。BASE で実行回数 0 の関数がその行にあっても止めない。lcov の `FN` は列を持たないので、その行のどの関数が実行されたかは区別できない。0054 は、BASE で実行回数 0 の関数を含む行があれば止めた（0054 `02_architecture.md` 3.2）。しかし常設の道具でそうすると、`a => b => ...` のように内側が呼ばれない関数を持つファイルで、削除と関係なく毎回止まってしまい、利用者が先に進めなくなる。
    -   **残る制限:** BASE で 0 だった関数が実行されるようになり、同時に 1 以上だった別の関数が 0 になると、実行された関数の数は変わらないので、道具はこれを見逃す。テストを削除するだけでは、それまで実行されなかった関数が実行されるようにはならないので、この入れ替わりが起きるのは、同じ変更でテストを加えたか書き換えた場合に限られる（F-003）。
-   **結果は短く保つ:** 道具はテストの出力やカバレッジの報告の全文を出さない。結果をコミットメッセージと PR の説明にそのまま書けるようにするためである（F-005）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   テストを削除する変更で、削除の前に実行されていた製品の関数が削除の後も実行されていることを、1 つのコマンドで確かめられるようにする。Go と拡張で同じ形の確かめ方にする。
-   何も測れていない比較、テストが失敗した比較、関数の対応が取れない比較を、合格として報告しない。
-   テストを削除するタスクのたびに比べる手順を設計し直す手間と、拡張での比較を方針の例外として承認を得る手間をなくす。

### 2.2. スコープ (In Scope)

-   Go のコードの比較の入口（`make coverage-compare`）と、拡張のコードの比較の入口（`make ext-coverage-compare`）。
-   比べる対象と合格の基準、止まる場合と、そのときの報告。
-   道具が読む入力（カバレッジの報告、テストの実行の結果、ソースの差分）の受け入れる形と、受け入れない場合の扱い。
-   合格したときに出す結果（コミットメッセージと PR の説明に書くもの）。
-   止まり方を、壊した報告で確かめる道具のテスト。
-   [CLAUDE.md](../../../CLAUDE.md)「Deleting a test is a claim that must be checked」の書き換えと、CLAUDE.md の「Commands」への 2 つの入口の追加。

### 2.3. スコープ外 (Out of Scope)

-   **行と分岐の単位の比較:** 比べない。関数の単位の比較で、テストの削除で関数が実行されなくなることは見つけられる。Go は関数ごとの網羅率まで比べるので、関数の中の文の網羅率の低下も見つけられる（1 章「要件定義の際に決めたこと」）。
-   **CI での自動実行:** しない（issue #618）。道具のテスト（F-007）は、既存のテストの一式の中で動く。
-   **追加や書き換えを含む変更の比較:** 残る関数の中身の変更や、新しい関数の追加を含む変更は比べずに止まる（F-004）。これらの変更は、削除を確かめるという道具の目的の外にある。
-   **テストの補助のコードの比較:** Go のテストのタグのファイルと、拡張の `extension/test/` の下のファイルは比べない（1 章「要件定義の際に決めたこと」）。
-   **`integration` のタグだけのファイル:** `//go:build integration` のように `test` のタグで成り立たないファイルは、`-tags test` の測り方ではビルドされず、報告に出ないので比べない。
-   **削除したテストが確かめていた内容の行き先:** カバレッジはコードが実行されたことを示すだけで、何を確かめたかは示さない（0027 `02_architecture.md` 3.10.2）。確認の内容の行き先をたどることは、この道具の外にある。
-   **過去のタスク文書と一度きりの道具:** 0027・0038・0046・0052・0054 のタスク文書の比べ方の記述は書き換えない。各タスクの時点の決定の記録だからである。0038・0052 の道具を再利用するか、そのまま残すかは設計で決める（[design_handoff.md](design_handoff.md) H-01）。
-   **#619 の軽量プロセス:** 軽量プロセスの定義と、そこからこの道具を呼ぶ手順は #619 で扱う。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

本章の用語は 6 章の定義に従う。

#### F-001: 比較の入口と、比べる 2 つの時点

利用者は、リポジトリのルートで `make coverage-compare BASE=<commit>`（Go）または `make ext-coverage-compare BASE=<commit>`（拡張）を実行する。道具は、BASE と HEAD のそれぞれのコミットの内容でテストを実行してカバレッジの報告を取り、比べる。

**Acceptance Criteria**:
- **AC-01**: `make coverage-compare BASE=<commit>` は Go の製品のコードを、`make ext-coverage-compare BASE=<commit>` は拡張の製品のコードを、BASE と HEAD のコミットの内容で測って比べる。合格のときは終了コード 0 で終わり、合格でないとき（不合格と止まった場合）は 0 以外で終わる。
- **AC-02**: 次のどれかに当たるときは、テストを実行する前に止まり、当たった理由を出す。
    -   BASE の指定がない、または BASE がコミットとして解決できない（停止の種類 `usage`）。
    -   BASE と HEAD が同じコミットである、または BASE が HEAD の祖先でない（`not-ancestor`）。
    -   作業ツリーまたはインデックスに、コミットしていない変更がある。追跡されていないファイルも、git が無視するものでなければ数える（`dirty`）。
- **AC-03**: 道具の実行の前と後で、利用者の作業ツリーの追跡されているファイル、インデックス、今のブランチ、HEAD のコミット、git に登録された作業ツリーの一覧は変わらない。道具が作った一時的なファイルとチェックアウトは、合格・不合格・止まった場合と、SIGINT・SIGTERM で中断された場合のどれでも、終わるときに残らない。
- **AC-04**: `make ext-coverage-compare` は、ほかの `ext-*` の対象と同じ前提の確認を通る。`node` と `npm` の版が `extension/.node-version` と `extension/package.json` の `packageManager` の版と一致しないとき、または `extension/node_modules` がないときは、テストを実行する前に止まり（停止の種類 `toolchain`）、当たった理由を出す（`Makefile:309-332` の `ext_check_versions`・`ext_preflight`）。依存パッケージを入れたり、ネットワークを使ったりはしない。
- **AC-05**: `make coverage-compare` は、BASE と HEAD のどちらかの `go.mod` が、入っている go と別の版の go を求めるときは、go の版を取りに行かずに止まる（停止の種類 `toolchain`）。道具の実行は、ネットワークを使わない。
- **AC-06**: BASE と HEAD は、同じ go（拡張では同じ node と同じ `extension/node_modules`）で、同じ機械で続けて測る。結果に、使った go または node の版を出す。

- **AC-07**: 実装の後に、それぞれの入口を、テストを削除した実際のコミットの組で一度ずつ実行し、合格することと、結果（AC-24）が実際の値を示すことを確かめる。Go では、ほかのパッケージのテストからだけ実行される関数が比べる対象に含まれる組を選ぶ（AC-11）。この実行は手動で行い、使った組と結果を実装計画に記す。

#### F-002: 測れていることの確認

BASE と HEAD のどちらの実行も、テストがすべて通り、比べる関数が報告に含まれていなければ、比較に使わない。

**Acceptance Criteria**:
- **AC-08**: BASE と HEAD のどちらかの実行で、テストが 1 つでも失敗した場合、パッケージやテストのファイルのビルドや読み込みが失敗した場合、またはテストの実行が 0 以外で終わった場合は、比べずに止まる（停止の種類 `test-failed`）。止まるときは、どちらの時点で失敗したかと、失敗したテストの名前（テストの名前がない失敗では、失敗したパッケージまたはファイル）を出す。
- **AC-09**: BASE と HEAD のどちらかの実行で、実行されたテストの数が 0 の場合、または比べる対象のファイルの関数の数が 0 の場合は、比べずに止まる（停止の種類 `nothing-measured`）。

#### F-003: 関数ごとの比較

前後で対応が付いた関数（F-004）について、削除の前に実行されていた関数が削除の後も実行されていることを確かめる。

**Acceptance Criteria**:
- **AC-10**: Go では、BASE で網羅率が 0% より大きかった残る関数は、どれも HEAD での網羅率が BASE での網羅率以上である。網羅率は、表示のための丸めをせずに比べる（`go tool cover -func` は小数第 1 位に丸めて出すが、丸めた値では小さな減少が見えなくなるため）。下がった関数があれば不合格とし、その関数の (ファイル, 行, 名前) と前後の網羅率を出す。
- **AC-11**: Go の網羅率は、モジュールのどのパッケージのテストから実行された文も数える。あるパッケージの関数が、ほかのパッケージのテストからだけ実行されている場合も、その関数は実行されたものとして比べる。
- **AC-12**: 拡張では、BASE で実行回数が 1 以上だった残る関数は、どれも HEAD での実行回数が 1 以上である。0 になった関数があれば不合格とし、その関数の (ファイル, 行) と、報告にある名前を出す。拡張では、実行回数の増減は比べない（1 以上かどうかだけを比べる）。
- **AC-13**: 拡張で、HEAD のソースにある製品のコードのファイルが、HEAD の報告にない（どのテストも読み込まなかった）場合は、そのファイルの関数の HEAD での実行回数を 0 として AC-12 で比べる。BASE の報告にない製品のコードのファイルの関数は、BASE で実行されていなかったものとして扱い、比べない。
- **AC-14**: 拡張で、1 つの (ファイル, `FN` の行) から複数の関数が始まる場合は、その行の関数を名前で対応させず、その行で実行回数が 1 以上の関数の数で比べる。BASE と HEAD でその行から始まる関数の数が違う場合は、対応が取れないとして止まる。数が同じ場合は、その行で実行回数が 1 以上の関数の数を BASE と HEAD で比べ、HEAD で同じなら合格、少なければ不合格、多ければ対応が取れないとして止まる。ただし、ファイルが HEAD の報告にない場合（AC-13）は、HEAD の関数の数を BASE と同じとし、実行回数をすべて 0 として比べる。BASE でその行に実行回数 0 の関数があることは、それだけでは止める理由にならない（1 章「要件定義の際に決めたこと」）。
- **AC-15**: Go で、同じ (ファイル, 行) から始まる関数が報告に複数ある場合は、対応が取れないとして止まる。
- **AC-16**: 比べるのは製品のコードの関数だけである。比べないファイルの関数の網羅率や実行回数が下がっても、不合格にはしない。
- **AC-17**: 関数は (ファイル, 始まりの行) で識別し、名前では識別しない。名前のない関数の名前が実行のたびに変わる場合（拡張の `anonymous_<番号>`）や、同じファイルに同じ名前の関数が複数ある場合も、比較の結果は名前によらない。

#### F-004: 前後の関数の対応と、削除した関数

BASE と HEAD の製品のコードの差分から、残る関数の前後の行を対応させ、削除した関数を求める。

**Acceptance Criteria**:
- **AC-18**: BASE の製品の関数で、その範囲のすべての行が BASE から HEAD への差分で削除された行（書き換えられた行でない）に当たるものを、削除した関数とする。ファイルごと削除された場合は、そのファイルのすべての関数が削除した関数である。削除した関数は比較の対象にせず、結果（F-005）に一覧として出す。
- **AC-19**: 残る関数（削除した関数でないもの）は、HEAD の報告にある関数と対応させる。対応の相手は、残る関数の始まりの行（差分で変わらない行）の HEAD での位置から始まる関数である。削除で後ろの行番号がずれた関数も、この対応で比べる。
- **AC-20**: 次のどれかに当たるときは、対応が取れないとして止まり（停止の種類 `unmatched`）、当たった関数の (ファイル, 行) を出す。
    -   BASE の製品の関数の範囲の中に、差分で書き換えられた行がある、または一部の行だけが削除された。
    -   残る関数の範囲の中に、HEAD で追加された行がある。
    -   残る関数の HEAD での位置から始まる関数が、HEAD の報告にない（拡張の AC-13 の場合を除く）。
    -   HEAD の製品の関数で、BASE のどの残る関数にも対応しないもの（HEAD にだけある関数）がある。
    -   ファイルの名前の変更や移動がある。この場合は、BASE のファイルの削除と HEAD のファイルの追加として扱うので、移したファイルの関数は HEAD にだけある関数になり、上の項目に当たる。
- **AC-21**: 関数の範囲の外の変更（import、パッケージの変数や定数、トップレベルの式など）は、止める理由にならず、比べる対象にもならない。

- **AC-22**: 削除した関数のうち、BASE で実行されていなかった（Go で網羅率 0%、拡張で実行回数 0）ものがあっても、それだけを理由に不合格にはしない。結果の一覧に、実行されていなかったことを添えて出す。

#### F-005: 結果の報告

合格のときも不合格のときも止まったときも、どれであったかが出力から一意に分かる形で、比べた内容を出す。

**Acceptance Criteria**:
- **AC-23**: 出力の最後の行は、合格・不合格・止まった場合のどれであったかを示す決まった行である。止まった場合は、停止の種類（`usage`・`not-ancestor`・`dirty`・`toolchain`・`test-failed`・`nothing-measured`・`unreadable`・`unmatched` のどれか）も示す。行の正確な書式は設計で決める。止まる理由と不合格の理由が複数あるときは、この順で最初に当たったものを示す：`usage`・`not-ancestor`・`dirty`・`toolchain`（テストの実行の前）、`test-failed`、`unreadable`、`nothing-measured`、`unmatched`、不合格。
- **AC-24**: 合格のときは、次のものを出す。
    -   実行した入口（`make` の対象と BASE の指定）。
    -   BASE のコミットの ID、HEAD のコミットの ID とツリーの ID。
    -   使った go または node の版。
    -   BASE と HEAD のそれぞれでの、実行されたテストの数・比べたファイルの数・比べた関数の数。
    -   削除した関数の一覧（(ファイル, 行, 名前) と、BASE で実行されていなかったか）。
    -   比べた関数で網羅率が下がった（拡張では実行回数が 0 になった）ものがないこと。
- **AC-25**: 不合格のとき（AC-10・AC-12・AC-14）と止まったときは、AC-24 の「網羅率が下がったものがないこと」を出さない。止まった理由と、それに当たった関数・テスト・時点を出す。
- **AC-26**: 道具の出力に、テストの出力やカバレッジの報告の全文を含めない。出すのは AC-23〜AC-25 に挙げたものだけである。
- **AC-27**: 出力で、ファイルはリポジトリのルートからの相対パスで示す（Go の報告のモジュールのパスも、この形に直して示す）。

#### F-006: 入力の境界

道具が読むカバレッジの報告、テストの実行の結果、ソースの差分は、道具が実行した go・node・git のコマンドの出力である。これらを受け入れる形を定め、外れたものは修復せずに止まる（停止の種類 `unreadable`。止まるときは、どの時点のどの入力の、どの行が読めなかったかを出す）。読めない部分を飛ばして、残りの部分だけで比べることはしない。

**Acceptance Criteria**:
- **AC-28**: Go のカバレッジの報告は、関数ごとに (ファイル, 行, 名前) と、丸めない網羅率（AC-10）が得られる形のものを読む。どの出力を読み、それぞれをどの文法で受け入れるかは設計で決める。設計は、読むそれぞれの出力に次を当てはめる。全体の集計の行（`go tool cover -func` の `total:` の行など）は決まった位置に 1 つだけあるものとし、ない・2 つ以上ある・別の位置にある場合は受け入れない。行番号・文の数・網羅率が数として読めない（負、範囲外、網羅率が 100% を超える）場合と、モジュールの外のファイルの場合は受け入れない。
- **AC-29**: 拡張の lcov は、ファイルのまとまり（`SF` から `end_of_record` まで）の並びだけを受け入れる。道具が読むのは `SF`・`FN`・`FNDA`・`end_of_record` のレコードである。`TN`・`FNF`・`FNH`・`DA`・`LF`・`LH`・`BRDA`・`BRF`・`BRH` は、読み飛ばしてよいレコードとして受け入れる。次のどれかに当たるものは受け入れない。それ以外の種類のレコード。閉じていないまとまり。まとまりの外のレコード。同じ `SF` のまとまりが 2 つ以上ある。1 つのまとまりの中で、`FN` と `FNDA` の数が違う、または出現の順で組にした `FN` と `FNDA` の名前が違う。行や実行回数が負でない整数として読めない（符号、小数、範囲外を含む）。
- **AC-30**: テストの実行の結果からは、テストの数と、失敗したテストの名前を読む。Go のテストの数はトップレベルのテスト関数の実行の数（サブテストは数えない）、拡張のテストの数は node のテストランナーが実行の終わりに報告するテストの数とする。この数を読めない場合は受け入れない。
- **AC-31**: ソースの差分は、追跡されているテキストのファイルの、行の単位の差分だけを受け入れる。製品のコードの範囲にバイナリのファイルの差分がある場合や、差分を行の対応として読めない場合は受け入れない。
- **AC-32**: 入力の大きさに上限は設けない。どの入力も、利用者の機械で、リポジトリのテストの一式と git が出すものに限られるためである。

#### F-007: 道具のテスト

道具の判定は、壊した報告を与えるテストで確かめる。

**Acceptance Criteria**:
- **AC-33**: 道具のテストは、少なくとも次の入力のそれぞれで、道具が合格とせず、止まるか不合格にすることを確かめる。止まる場合は、AC-23 の停止の種類が正しいことも確かめる。
    -   テストの数が 0 の報告と、関数の数が 0 の報告（それぞれ別に）。
    -   テストが失敗した実行。
    -   `FN` と `FNDA` の数が違うまとまり、名前が違うまとまり、閉じていないまとまり、重複した `SF`。
    -   形の崩れた Go の出力の行と、`total:` の行がない、または最後でない出力。
    -   網羅率が下がった Go の関数と、丸めると同じになる小さな減少。
    -   実行回数が 0 になった拡張の関数と、HEAD の報告から消えたファイル。
    -   同じ行から始まる関数で、実行された数が減った場合、増えた場合、関数の数が変わった場合。
    -   範囲の中が書き換えられた残る関数、範囲の中に行が追加された残る関数、HEAD にだけある関数。
- **AC-34**: 道具のテストは、合格する入力でも確かめる。ファイルの途中の関数を削除して後ろの関数の行番号がずれた場合と、ファイルごと削除した場合と、同じ行から始まる関数に BASE で実行回数 0 のものがあり前後で変わらない場合で、道具が合格とし、削除した関数を正しく一覧に出すことを確かめる。
- **AC-35**: 道具のテストは、実際の Go や拡張のテストの一式を実行しない。道具のテストは、既存の `make test` または `make ext-test` の中で動く。
- **AC-36**: 入口の前提の確認（AC-02・AC-04・AC-05）、後始末（AC-03）、同じ条件での測定（AC-06）、出力の範囲（AC-26・AC-27）も、道具のテストまたは実装計画に記す手動の手順で確かめる。

#### F-008: 手順の書き換え

CLAUDE.md の「Deleting a test is a claim that must be checked」を、この道具を使う手順に書き換える。

**Acceptance Criteria**:
- **AC-37**: [CLAUDE.md](../../../CLAUDE.md)「Deleting a test is a claim that must be checked」は、次の手順を求める。
    -   テストを削除する変更を、それだけで 1 つのコミットにする。
    -   その親のコミットを BASE として、Go のテストを削除したときは `make coverage-compare BASE=<親のコミット>` を、拡張のテストを削除したときは `make ext-coverage-compare BASE=<親のコミット>` を実行する。両方を削除したときは両方を実行する。
    -   合格の結果（AC-24）を、そのコミットのメッセージ（メッセージだけを直す）と PR の説明に書く。
    -   基準は「関数ごとに変わらない」ではなく、Go では網羅率が下がらないこと、拡張では実行回数が 0 にならないことである。
    -   拡張の比較を方針の例外として扱う記述はない。
- **AC-38**: CLAUDE.md の「Commands」に、`make coverage-compare BASE=<commit>` と `make ext-coverage-compare BASE=<commit>` が、それぞれの説明とともに載っている。`make ext-coverage-compare` は、拡張の `ext-*` の対象の一覧（「Extension Commands」）に載っている。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   1 回の実行で、Go または拡張のテストの一式を 2 回（BASE と HEAD）走らせる。それ以上の時間の上限は定めない。テストを削除する変更で、人や agent が一度実行するものだからである（CLAUDE.md「Performance」の、絶対的な予算で判断する方針）。

### 4.2. セキュリティ (Security)

-   N/A。この道具は `yt-dlp` を呼ばず、API キーや Webhook URL を扱わず、キャッシュのディレクトリを読み書きせず、ネットワークで送信せず（AC-04・AC-05）、信頼できない文字列をプロンプトや記事に埋め込まない（`docs/dev/security.md` の適用条件に当たらない）。BASE は HEAD の祖先のコミットに限り（AC-02）、そのテストを実行するのは、`make test`・`make ext-test` を実行するのと同じ範囲の操作である。テストの一式は、今の `make test` と同じく、`yt-dlp`・LLM API・Webhook を呼ばない（CLAUDE.md「Testing Strategy」）。
-   道具が読む入力の境界は F-006 が定める。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   道具は、合格の判定の根拠にならない状態（テストの失敗、空の報告、読めない入力、対応の取れない関数）では、合格としない（F-002・F-004・F-006）。
-   途中で止まった場合と中断された場合も、利用者の作業ツリーとブランチは変わらない（AC-03）。

### 4.4. 互換性 (Compatibility)

-   既存の `make` の対象（`make test`・`make test-ci`・`make ext-test` など）の振る舞いは変えない。
-   拡張の比較は、ほかの `ext-*` の対象と同じ版の node と npm で動く（AC-04）。
-   macOS と Linux で動く（開発に使う環境）。

### 4.5. 保守性 (Maintainability)

-   依存は増やさない。Go の道具ならば標準ライブラリだけを使い、`.golangci.yml` の `depguard` に module を加えない。拡張の側に置くならば、npm のパッケージを加えない（CLAUDE.md「Dependencies」）。
-   道具の出力の文言、識別子、コメントは英語である（CLAUDE.md「Language」「Go Idioms」）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   CLAUDE.md「Tool Execution Safety」に従う。道具はネットワークを使わない。`extension/node_modules` がないときは自分で入れず、止まる（AC-04）。
-   道具の判定に使う値は、道具が実行したテストの報告から読む。テストの数・関数の数・削除した関数を利用者が申告する形にはしない（1 章「要件定義の際に決めたこと」）。

## 6. 用語集 (Glossary)

-   **カバレッジの報告:** テストの一式を実行したときに、関数ごとの実行の記録を出したもの。Go は設計が選ぶ関数ごとの網羅率の出力（`go tool cover -func` の出力など）、拡張は node のテストランナーが出す lcov の形式のもの（0027・0054 と同じ用語）。
-   **網羅率:** Go の関数ごとの、その関数の文のうちテストで実行された文の割合。
-   **実行回数:** 拡張の lcov の中で、関数ごとに記録される、テストの実行中にその関数が呼ばれた回数（`FNDA` の値。0054 と同じ用語）。
-   **BASE:** 削除の前の時点として、利用者が `BASE=<commit>` で指定するコミット。HEAD の祖先に限る。
-   **HEAD:** 削除の後の時点。道具を実行したときの今のコミット。
-   **製品のコード:** 比べる対象のファイル。Go では、`_test.go` でなく、ビルドの制約が `test` のタグを求めることも `test` のタグで成り立つこともないファイル（0038・0052 と同じ用語）。拡張では `extension/src/` と `extension/scripts/` の下のファイル。
-   **製品の関数:** 製品のコードのファイルにある関数。
-   **関数の範囲:** 関数の始まりの行から終わりの行まで。
-   **削除された行・書き換えられた行・追加された行:** BASE から HEAD への差分で、HEAD に対応する行がない BASE の行が削除された行、BASE に対応する行がない HEAD の行が追加された行である。変わらない行をはさまずに続く変更の行のまとまりが、削除された行と追加された行の両方を持つとき、その削除された行を書き換えられた行とする（差分の前後に付ける文脈の行の数によらない）。
-   **削除した関数:** BASE の製品の関数のうち、範囲のすべての行が削除された行（書き換えられた行でない）に当たるもの（AC-18）。
-   **残る関数:** BASE の製品の関数のうち、範囲のどの行も削除されていないもの（AC-19）。範囲の一部だけが削除・書き換えられた関数は、どちらでもなく、対応が取れない（AC-20）。
-   **対応が取れない:** BASE の関数と HEAD の関数を、差分の変わらない行で 1 対 1 に結べない状態（AC-14・AC-15・AC-20）。
-   **停止の種類:** 道具が止まった理由の分類（AC-23）。
-   用語は `docs/translation_glossary.md` と統一する。
