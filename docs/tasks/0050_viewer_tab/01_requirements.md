## 1. 概要 (Overview)

**目的:** 本書は、ブラウザ拡張の送信をサーバの新しい API（生成の開始・状態の取得・投稿の操作）に移し、生成した記事を拡張のページ（ビューア）に表示し、ビューアから Slack への投稿、`.md` ファイルへの保存、Markdown のコピーを行えるようにするための要件を定義する。

**背景:**

本書の用語（「新しい API」「ビューア」「やり取りの結果」など）は 6 章で定義する。

今の拡張は、ポップアップの主ボタンを押すと、収集した値から作ったリクエストの本文を、今の形のメッセージとして Native Messaging のホストに 1 回だけ送る（`extension/src/send.ts:28-55`、本文は `extension/src/core/prepare.ts:25-42`）。ホストはそれを `POST /articles` へ中継し（`internal/nmhost/relay.go:55`）、サーバは受け付けると `202` を返して、記事の生成から Slack への投稿までを非同期に行う（`0011_localhost_server` F-005）。

-   拡張は受け付けの応答を表示するだけで、記事は Slack にだけ届く。受け付けの文言は「生成と投稿の結果は Slack に届く」と案内する（`extension/src/core/i18n/en.ts:92`）。
-   結果不明のとき（応答がない、ホストが失敗した、想定外の応答）は、送り直す前に Slack を確かめるよう案内し、自動では再送しない。送信中の文言も、ポップアップを閉じたら Slack を確かめるよう案内する（`en.ts:95-122`、`docs/dev/security.md` §8.1）。送り直すと、同じ記事が二重に生成・投稿されうるためである（`security.md` §8.2）。
-   送信中にポップアップを閉じると、結果は表示されない（README「ブラウザ拡張」）。
-   拡張は、サーバの応答を `/articles` の形（`status` と `requestId`、拒否なら `reason`）だけ受理し、本文の上限は 1,024 バイトである（`extension/src/core/response.ts:57`・`:158-223`）。
-   拡張の権限は `activeTab`・`scripting`・`nativeMessaging` だけで（`extension/static/manifest.json:12`）、manifest は Service Worker（`background`）を宣言しない（`manifest.json:1-13`）。拡張は何も保存しない（`security.md` §8.1）。

タスク `0044_article_job_api`（[#502](https://github.com/isseis/yt2column/issues/502)）は、サーバとホストに新しい API を加えた。ホストは、版のメンバ `v` を持つ新しい形のメッセージ（`{"v":1,"op":"start"|"status"|"publish",...}`）を、操作ごとに決めた送り先（`POST /jobs`・`GET /jobs/{key}`・`POST /jobs/{key}/publish`）へ中継する（`internal/nmhost/relay.go:389-394`・`:466-510`）。状態の取得は、ジョブの状態・工程の状態・投稿の状態・失敗の理由をコードで返す（`docs/dev/guides/development.md`「ジョブの API」「ジョブの API のコード」）。状態の取得の応答の本文は最大 256 KiB で（`internal/server/status.go:20`）、ホストは 512 KiB までの応答を中継する（`relay.go:43`）。記事のキーは、生成の開始の入力の検査を通った後の値（`videoUrl`・`transcript`・`title`・`channelName`・`description`）のすべてから計算する（`0044` F-001）。拡張がこの API に移るまで、サーバは `/articles` を残している（`0044` F-007）。

タスク `0046_popup_redesign`（[#507](https://github.com/isseis/yt2column/issues/507)）は、ポップアップを動画のセクション・確認のセクション・操作のセクション・詳細の構成に作り直した。生成中・生成済み・失敗の状態は本タスクで加える前提で、画面の内容の種類として加えられる構造にしてある（`docs/tasks/0046_popup_redesign/02_architecture.md` 9 章）。

対応 issue: [#503](https://github.com/isseis/yt2column/issues/503)（親: [#501](https://github.com/isseis/yt2column/issues/501)、前提: [#502](https://github.com/isseis/yt2column/issues/502)・[#507](https://github.com/isseis/yt2column/issues/507)、関連: [#504](https://github.com/isseis/yt2column/issues/504)・[#506](https://github.com/isseis/yt2column/issues/506)・[#526](https://github.com/isseis/yt2column/issues/526)）

**本書の記述範囲:** 本書は、利用者から見える振る舞いを定める。対象は、送信の経路、ビューアを開く時機と開き方、ポップアップとビューアが表示する状態と文言の種類、投稿・保存・コピーの操作、拡張が受け取る値の受理する形である。拡張の内部の構成（Service Worker・ポップアップ・ビューアの間のメッセージの形、ポーリングをどこで行うか）、ビューアの URL の形、ポーリングの間隔、各上限の値、ファイル名に使えない文字の集合、受け入れ基準の検証の手段は、設計（`02_architecture.md`）と実装計画で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #503 で決めたこと（親 issue #501・#507 の決定を含む）:**

-   **記事は必ずブラウザに表示する:** 生成と投稿を分け、Slack への投稿と `.md` ファイルへの保存は、ビューアでの利用者の操作で行う（#501）。
-   **送信は Service Worker が行う:** ポップアップで主ボタンを押すと、Service Worker が生成の開始を呼ぶ。ポップアップを閉じても結果は失われない。
-   **送る前の確認はポップアップに残す:** 料金がかかるので、送る前に確かめられることを保つ。
-   **ビューアのタブ:** 送信と同時に拡張のページ（`viewer.html`）を新しいタブで開き、動画メタデータ、処理中の表示、経過時間を表示する。状態の取得をポーリングし、完了したら同じタブで記事を表示する。
-   **記事はプレーンテキストで表示する:** Markdown の描画は #504 で行う。
-   **状態の正しい値はサーバに置く:** Service Worker は停止しうるので、ビューアと Service Worker はサーバに照会するだけにする。
-   **ビューアの操作:** 元動画へのリンク、生成の料金と所要時間の表示、Slack への投稿（キーで投稿の操作を呼ぶ。投稿済みなら押せない）、`.md` での保存（サーバが返すファイルの中身を、ブラウザのダウンロードで保存する）、Markdown のコピー。
-   **同じ入力の再送:** サーバが既存のキーを返したら、同じ記事のビューアを開く。
-   **失われた記事:** サーバの再起動で記事が失われたら、ビューアはその旨と、送り直す手順を表示する。
-   **常時の host permission は加えない。**
-   **ポップアップの状態（#507 の決定）:** 生成中（工程ごとのチェックリストと経過時間。プログレスバーは使わない。実行中の工程はアニメーションで示し、`prefers-reduced-motion` では止める）・生成済み・失敗を、ポップアップの同じ 3 つのセクションの構成の中で切り替える。
-   **多言語（#506 の決定）:** 文言は英語と日本語の両方を持つ。数と日時は `Intl.NumberFormat` と `Intl.DateTimeFormat` を、選んだ言語で使う。

**要件定義の際に決めたこと（2026-10-29）:**

-   **ビューアは背面のタブで開き、ポップアップは開いたまま状態を表示する:** 主ボタンを押すと、ビューアを新しいタブで、作業中のタブを切り替えずに開く。ポップアップは閉じずに、生成中・生成済み・失敗の状態を表示し、ビューアのタブを前面に出す操作を持つ。前面で開くとポップアップがすぐに閉じ、#507 で決めたポップアップの状態が表示されないためである。ポップアップとビューアの両方が状態を取得することになるが、状態の取得は LLM を呼ばず、サーバのログにも残らない（`docs/dev/guides/development.md`「ジョブの API」）ので許容する。
-   **ビューアは送信と同時に開き、生成の開始の結果も表示する:** キーを受け取れなかった場合（拒否・未送信・結果不明）も、ビューアに理由と手順を表示する。キーを受け取ってから開くと、応答（最大で約 20 秒。`relay.go:31`）を待つ間にポップアップを閉じた場合、拒否の理由がどこにも表示されず、issue の「ポップアップを閉じても結果は失われない」を満たせないためである。
-   **ビューアの URL に記事のキーと表示に使う値を持たせ、拡張は何も保存しない:** ビューアを再読み込みしても、閉じたタブを復元しても、履歴から開いても、同じ記事を表示する。ビューアのタブを閉じた後に開き直す手段は、閉じたタブの復元・履歴と、ポップアップから同じ入力を送り直す（キャッシュに当たれば LLM を呼ばない）ことである。拡張は `chrome.storage` を使わない。「設定を保存しない」という今の性質（`security.md` §8.1）を保ち、権限を加えずに済ませるためである。最近の記事の一覧は設けない。
-   **権限を加えない:** 権限は今の `activeTab`・`scripting`・`nativeMessaging` のままとする。`.md` の保存は拡張のページからのダウンロードで、コピーは利用者の操作の中のクリップボードへの書き込みで行い、`downloads`・`clipboardWrite`・`tabs`・`storage`・host permission を加えない。権限の範囲を今より広げないためである。権限なしで実現できるかは設計で確かめる（H-05・H-06・H-07）。
-   **送信を新しい API に全面的に移し、自動で再送しない:** 拡張は今の形のメッセージ（`/articles` の経路）を送らない。生成の開始と投稿の操作を、拡張が自動で送り直すことはしない。状態の取得は、ポーリングとして繰り返す（F-003）。生成の開始の結果不明では、Slack を確かめる手順を示さず、同じ入力を送り直しても、その記事が処理中か完了していれば、二重には生成されないことを示す。新しい API の生成の開始は、処理中または完了したキーを返すだけで LLM を呼ばない（`0044` F-001）ためである。サーバの `/articles` の削除は #526 で行う。
-   **処理中の経過時間は、そのビューアを開いた送信の時刻から数える:** 送信の時刻をビューアの URL に持たせ、再読み込みでも保つ。完了した後は、サーバが返す所要時間（`durationMs`）を表示する。状態の取得は、処理中には経過時間を返さないためである（`docs/dev/guides/development.md`「ジョブの API」）。同じ入力の送り直しで既存のビューアを再利用した場合（下の決定）、そのビューアは、処理中か完了を表示していれば最初の送信の時刻から数え続け、失敗か不明を表示していれば、送り直した時刻から数え直す。前者は同じ生成が続いており、後者はサーバが生成をやり直すためである。
-   **`.md` のファイル名は動画タイトルから作る:** ファイル名に使えない文字を `_` に置き換え、長さに上限を設ける。動画タイトルがないとき、または空のときは `<動画 ID>.md` にする。動画 ID は、収集した URL の `v` の値である。使えない文字の集合と長さの上限は設計で決める（H-05）。
-   **「Markdown をコピー」は表示用の Markdown をコピーする:** 状態の取得が返す表示用の Markdown（`article.markdown`。見出し・チャンネル名・本文）を、変えずにコピーする。フロントマター付きのファイルの中身は、`.md` の保存で手に入るためである。
-   **やり直しはポップアップから行い、ビューアにはやり直しのボタンを置かない:** 生成の失敗・記事が失われた場合・キーを受け取れなかった場合、ビューアは、理由に応じた手順（送り直しで解決する場合は、ポップアップから送り直す手順）を表示する。ビューアは入力（コピーした字幕）を持たず、拡張は何も保存しないためである。ポップアップは選択範囲を持っているので、失敗の状態でやり直しの操作を持つ（#507 のモックアップの「Try again」）。
-   **同じ入力を送り直したときは、同じキーのビューアがあればそのタブを再利用する（2026-10-30 の PR のレビューで変更）:** 送信と同時に新しいビューアを開くことは変えない。生成の開始の応答でキーを受け取ったとき、同じキーを表示しているビューアがほかにあれば、新しいビューアは自分のタブを閉じ、既存のビューアがその送信の表示を引き継ぐ。同じ記事のタブが送り直すたびに増えないようにするためである。キーはサーバだけが知る秘密から計算するので（`0044` `02_architecture.md` §3.2）、拡張はキーを受け取るまで同じ記事かどうか分からない。このため、背面で開いたタブは、閉じるまでの短い間だけ現れる。既存のビューアを探すことは、`tabs` の権限を加えずに、ビューア同士のやり取りで行う（H-01・H-07）。

上の決定から導いた振る舞いとして、次の点を要件に含める（レビュアーは PR で確かめる）。

-   **送り直しで二重に生成されない範囲を正しく示す:** キーは入力のすべての値から計算するので、同じ選択範囲でも、動画メタデータが違えば（概要欄を開いてから送った、ページから読めた値が変わった）別の記事として生成し直す。前の生成が失敗していた場合、サーバが再起動した場合、記事のキャッシュから捨てられた場合も、生成し直す。結果不明の文言は、二重に生成されないのは同じ入力の記事が処理中か完了している場合であることを、断定しすぎずに示す。
-   **ポップアップを開き直したときは、送る前の状態から始まる:** ポップアップは送った記事を覚えていない（拡張は何も保存しない）。開き直したポップアップで同じ入力を送ると、キャッシュに当たった記事の状態（処理中または生成済み）を表示する。
-   **投稿の操作の結果不明でも、自動では送り直さない:** 投稿の操作は、投稿中または投稿済みの記事には投稿し直さずに受け付けの応答を返す（`0044` F-003）。このため、利用者がもう一度押しても二重には投稿されないことを示し、状態の取得で投稿の状態を確かめる。
-   **状態の取得は、送り直しで直らない結果では止める:** ポーリングはホストのプロセスを毎回起動する（`security.md` §8.2）。キーが受理されない（`invalid_key`）、想定外の応答など、繰り返しても変わらない結果ではポーリングを止め、繰り返せば直りうる結果（サーバが動いていない、応答がない、ホストの失敗）でだけ続ける（F-003）。
-   **ビューアが生成の開始の結果を受け取れないまま待ち続けない:** 1 回のやり取りの上限（25 秒。`send.ts:21`）から決めた時間のうちに結果を受け取れなければ、ビューアは結果不明を表示する（F-002）。
-   **表示した記事は、後で失われても保存とコピーができる:** 完了した記事を表示した後に、状態の取得が `unknown` を返した場合も、ビューアは表示中の記事を残し、保存とコピーを使えるようにする。投稿は、サーバに記事がないのでできない（F-003・F-006）。
-   **記事が失われた場合の送り直しは、二重の投稿になりうることを示す:** 再起動の後に生成し直して投稿すると、前に届いた投稿と重複しうる（`security.md` §8.2、`0044` 4.3）。失われた記事の手順はこのことを示す。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   生成した記事を、Slack ではなくブラウザ（ビューア）で読めるようにする。
-   送信の後にポップアップを閉じても、生成の開始の結果と記事が失われないようにする。
-   Slack への投稿と `.md` ファイルへの保存を、ビューアで利用者が選んで行う操作にする。
-   結果が分からないときに同じ入力を送り直しても、処理中または完了した記事を二重に生成せず、記事を二重に投稿しないようにする。

### 2.2. スコープ (In Scope)

-   ポップアップからの送信を Service Worker に移し、新しい API の生成の開始を使うこと（F-001）。
-   ビューアのタブを開くこと、同じキーのビューアの再利用、ビューアの URL が持つ値（F-002）。
-   ビューアの状態の表示とポーリング（F-003）。
-   ポップアップの生成中・生成済み・失敗の状態（F-004）。
-   ビューアでの記事の表示（F-005）。
-   ビューアからの Slack への投稿（F-006）。
-   `.md` ファイルへの保存（F-007）。
-   Markdown のコピー（F-008）。
-   新しい API のコードと拒否の理由ごとの文言（英語と日本語。F-009）。
-   文書: README（`README.md` と英語版の `README.en.md`）の「ブラウザ拡張」節・「localhost サーバ」節・拒否の理由の表、`docs/dev/guides/development.md` の「ジョブの API」と拒否の理由の表、`docs/dev/security.md` §8、`docs/dev/project_overview.md`、`CLAUDE.md` の「Architecture Overview」、`docs/translation_glossary.md`（F-010）。

### 2.3. スコープ外 (Out of Scope)

-   Markdown の描画（見出し・強調・リストなどの整形）と、描画のためのリンクの扱い: #504 で扱う。本タスクは記事をプレーンテキストで表示する。
-   サーバの `/articles` の削除と、ホストの今の形の中継の削除: #526 で扱う。本タスクは、拡張が `/articles` を使わなくなるところまでを行う。
-   サーバとホストの変更: 新しい API は `0044` で完成している。本タスクは、拡張と文書だけを変える。設計で新しい API に欠けがあると分かった場合は、そのときにレビュアーと扱いを決める。
-   ビューアでの概要欄の表示: 概要欄は長くなりうるのでビューアの URL に持たせず（1. 概要の決定）、ビューアは動画メタデータのうち見出しとチャンネル名を表示する。概要欄の状態は、送る前にポップアップで確かめる（`0046`）。
-   最近の記事の一覧と、記事や入力の保存: 1. 概要の決定により設けない。
-   ビューアからの生成のやり直し: 1. 概要の決定により、ポップアップから送り直す。
-   キーを受け取る前に既存のビューアを見分けること: 拡張はキーを受け取るまで同じ記事かどうか分からない（1. 概要の決定）。送信と同時に開いたタブは、同じキーのビューアがあると分かった後に閉じる（F-002）。
-   生成の途中での取り消し: issue が求めていない（サーバも利用者の操作による取り消しを持たない。`0044` 2.3）。
-   ツールバーのバッジ、動画の切り替えの検知: #501 の「対象外」（常時の host permission と content script が要る）。
-   生成の統計とダッシュボード: #505 で扱う。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 送信（ポップアップから Service Worker を経て生成の開始へ）

ポップアップの主ボタンを押すと、Service Worker が生成の開始の操作をホストに送る。

-   送る前の確認（収集、動画メタデータの読み込み、4 MiB の検査、主ボタンを押せる条件）は、今のポップアップ（`0046`）のとおりとする。
-   生成の開始の入力は、今のリクエストの本文と同じ値とする（`videoUrl`・`transcript` と、空でない `title`・`channelName`・`description`。`prepare.ts:25-42`）。拡張は今の形のメッセージを送らない。
-   Service Worker は、1 回の押下につき生成の開始を 1 回だけ送り、自動では送り直さない。ポップアップを閉じても、送信は続き、その結果はビューアに届く（F-002・F-003）。
-   生成の開始の結果は、今の送信の結果と同じ分類（受け付け・拒否・未送信・応答なし・ホストの失敗・想定外の応答）とする。受け付けはキーを持つ。
-   結果不明（応答なし・ホストの失敗・想定外の応答）の文言は、同じ入力を送り直しても、その記事が処理中か完了していれば二重には生成されないことを示し、Slack を確かめる手順を含まない。送信中・未送信・拒否の文言も、Slack に触れない。ポップアップの送信中の文言は、ポップアップを閉じてもよいことと、結果がビューアのタブに表示されることを示す（F-004）。ビューアの表示は、ポップアップを閉じることに触れない。
-   Service Worker は、生成の開始の求めを、拡張自身のポップアップからだけ受け付ける。ほかの送り手（拡張のほかのページ、ページに注入したスクリプト、ほかの拡張）からの生成の開始の求めは、何も送らず、タブも開かずに無視する。

**Acceptance Criteria**:
- **AC-01**: 主ボタンを押すと、ホストは新しい形の生成の開始のメッセージを 1 つだけ受け取る。その入力は、同じ収集の値から今のポップアップが作る本文と同じメンバと値を持つ。拡張は、どの操作でも今の形のメッセージ（版のメンバ `v` を持たないメッセージ）を送らない。
- **AC-02**: 主ボタンを押した直後にポップアップを閉じても、生成の開始は 1 回だけ送られ、その結果はビューアに表示される。
- **AC-03**: 生成の開始の結果が、拒否・未送信・応答なし・ホストの失敗・想定外の応答のいずれでも、拡張は生成の開始を送り直さない（ホストが受け取るメッセージは 1 つのまま）。
- **AC-04**: 生成の開始の結果不明の表示は、同じ入力の記事が処理中か完了していれば、送り直しても二重に生成されないことを示す。ポップアップの送信中の表示は、ポップアップを閉じてもよいことと、結果がビューアのタブに表示されることを示す。ビューアの表示は、ポップアップを閉じることに触れない。送信中と、生成の開始のどの結果の表示も、Slack を確かめる手順を含まない（英語と日本語の文言を PR のレビューで読む。`manual`）。
- **AC-05**: 拡張自身のポップアップ以外の送り手からの生成の開始の求めでは、Service Worker はホストに何も送らず、タブも開かない。

#### F-002: ビューアのタブを開く

主ボタンを押すと、送信と同時にビューアを新しいタブで開く。

-   ビューアのタブは、作業中のタブを切り替えずに（背面で）開く。ポップアップは閉じない。
-   押すたびに新しいビューアのタブを開く。同じ入力の送り直し（キャッシュに当たる場合）も、まず新しいタブを開く。
-   生成の開始が受け付けられたとき、同じキーを表示しているビューアがほかにあれば、新しいビューアは自分のタブを閉じる。既存のビューアはそのまま残り、タブを前面に出さない（作業中のタブを切り替えない）。同じキーのビューアが 2 つ以上あるときに、どれが引き継ぐかは設計で決める（H-01）。
-   引き継いだ既存のビューアは、処理中か完了を表示していれば、そのまま表示とポーリングを続け、送信の時刻を変えない。失敗か不明を表示していた場合、または状態を取得できずにポーリングを止めていた場合は、URL の送信の時刻を送り直した時刻に改め、ポーリングを再び始める（F-003）。
-   同じキーのビューアがあるかを決めた時間のうちに確かめられない場合（既存のタブがブラウザに破棄されて応答しないなど）は、新しいビューアは閉じずに表示を続ける。この場合、同じキーのビューアが 2 つ残る。
-   キーが違えば（動画メタデータが違う、サーバの再起動の後など）、別の記事として新しいビューアが表示を続ける。
-   ビューアの URL は、記事のキー（受け付けの後）、見出し（ポップアップの動画のセクションの見出しと同じ文字列。動画タイトル、なければタブのタイトル）、チャンネル名（あれば）、動画タイトル（あれば。ファイル名に使う。F-007）、収集した URL、送信の時刻を持つ。コピーした字幕と概要欄は持たない。
-   生成の開始の結果を受け取ると、ビューアはその結果を表示する。受け付けなら、URL にキーを加える。
-   キーを持つ URL のビューアは、再読み込み、閉じたタブの復元、履歴からの表示で、同じ記事の状態を表示する（F-003）。
-   キーを持たない URL のビューアが生成の開始の結果を待つ時間は、1 回のやり取りの上限（25 秒）から設計で決める（H-01）。その時間のうちに結果を受け取れなかった場合（Service Worker の停止、結果を受け取る前の再読み込みを含む）は、結果不明と、ポップアップから送り直す手順を表示し、状態の取得を送らない。その後に届いた生成の開始の結果の扱いは設計で決める（H-01）。
-   キーを受け取る前にビューアのタブを閉じ、ポップアップも閉じていた場合、その生成の開始の結果は表示されない。生成の開始が受け付けられていれば、同じ入力の送り直しはキャッシュに当たる。この手順は、README に書く（F-010）。

**Acceptance Criteria**:
- **AC-06**: 主ボタンを押すと、ビューアのページを持つタブが 1 つ、作業中のタブを切り替えずに開く。ポップアップは、その後も状態を表示し続ける。
- **AC-07**: 生成の開始が受け付けられた後のビューアの URL はキーを持つ。その URL を開き直したビューアは、同じキーの状態を取得して表示する。
- **AC-08**: 主ボタンで送り、処理中か完了の間にポップアップを開き直して同じ入力で再び送ると、2 回目の送信で開いたタブは、キーを受け取った後に閉じる。最初のビューアのタブだけが残り、作業中のタブは切り替わらず、最初のビューアの経過時間は最初の送信の時刻から数え続ける。同じキーのビューアがあるかを決めた時間のうちに確かめられない場合は、2 回目の送信で開いたタブは閉じずに、そのキーの状態を表示する。キーが違う送信で開いたタブは閉じない。
- **AC-09**: ビューアの URL は、コピーした字幕と概要欄の文字列を含まない。
- **AC-10**: キーを持たない URL のビューアは、決めた時間のうちに生成の開始の結果を受け取れなければ、結果不明とポップアップから送り直す手順を表示し、状態の取得を送らない。どのキーの状態も表示しない。

#### F-003: ビューアの状態の表示とポーリング

ビューアは、生成の開始の結果と、キーの状態を表示する。

-   見出し・チャンネル名・元動画へのリンク（F-005）は、どの状態でも表示する。ページのタイトル（タブの名前）は、見出しを含む。
-   表示する状態は次のとおりとする。

| 状態 | 表示 |
|---|---|
| 送信中（生成の開始の結果を待っている） | ロード中の表示と、送信中であること |
| 読み込み中（キーを持つビューアが、状態の取得の最初の結果を待っている） | ロード中の表示と、記事の状態を読み込んでいること |
| キーを受け取れなかった（拒否・未送信・結果不明） | やり取りの結果と理由、理由に応じた手順（送り直しで解決する場合は、ポップアップから送り直す手順） |
| 処理中（`running`） | 3 つの工程（`draft`・`shorten`・`review`）のチェックリスト（各工程の `pending`・`running`・`done`・`skipped` を区別する）と経過時間 |
| 完了（`done`） | 記事（F-005）、推定の料金、所要時間、投稿の状態と操作（F-006）、保存（F-007）とコピー（F-008）の操作 |
| 失敗（`failed`） | 失敗の理由の文言、`failed` の工程（状態の取得が示す場合）、理由に応じた手順 |
| 不明（`unknown`） | 記事が失われたこと（サーバの再起動、または記事のキャッシュからの破棄）、ポップアップから送り直す手順と、送り直して投稿すると前の投稿と重複しうること |

-   ロード中の表示は、文言と、動きのある印を組み合わせたものとする。状態は印だけでなく文言でも伝え、印の動きは `prefers-reduced-motion` が `reduce` のとき止める（4.6）。印の形は設計で決める（H-12）。結果を受け取ると、ロード中の表示は、その結果の状態の表示に替わる。読み込み中は、再読み込み・閉じたタブの復元・履歴からの表示・「ビューアを開く」で新しいタブを開いたときに当たる。2 回目以降の状態の取得（ポーリング）の間は、直前に表示した状態を残し、ロード中の表示に戻さない。
-   完了した記事を表示した後に状態の取得が `unknown` を返したときは、記事が失われたことを表示し、表示中の記事と保存・コピーの操作を残す。投稿の操作はできなくする。
-   経過時間は、ビューアの URL が持つ送信の時刻から数える。経過時間は、表示した時点までの経過を示し、タブが見えている間は 1 秒ごとに更新する。所要時間は、状態の取得が返す `durationMs` を表示する。
-   推定の料金は、分かる場合は USD の金額を、分からない場合はそのことを表示する。
-   受け付けの後、ビューアは状態の取得を繰り返す（ポーリング）。ジョブの状態が `running` の間と、投稿の状態が `posting` の間は続ける。投稿の状態が `posting` になった理由（このビューアの操作、ほかのビューアの操作、再読み込みの前の操作）は問わない。それ以外の完了・失敗・不明では止める。投稿の操作の後は、投稿の状態が `posting` でなくなるまで続ける（F-006）。1 つのページが同時に送る状態の取得は 1 つまでとする。
-   状態の取得のやり取りの結果に応じて、次のように振る舞う。どの場合も、直前に表示した状態を残す。状態の取得は生成も投稿も始めないので、繰り返しても二重の生成や投稿は起きない。

| 状態の取得のやり取りの結果 | 振る舞い |
|---|---|
| 未送信（サーバが動いていない）・応答なし・ホストの失敗 | 状態を取得できないことと手順（サーバが動いていない場合はサーバを起動する手順）を表示し、ポーリングを続ける |
| 拒否（`invalid_key`）・想定外の応答・そのほかの拒否 | 状態を取得できないことと手順（拡張・ホスト・サーバを同じ版にそろえる、ポップアップから送り直す）を表示し、ポーリングを止める |

-   状態や工程が変わったことは、フォーカスを動かさずに支援技術に伝える（4.6）。

**Acceptance Criteria**:
- **AC-11**: 処理中のキーでは、ビューアは 3 つの工程を、状態の取得が返す工程の状態（`pending`・`running`・`done`・`skipped`）に合わせて、互いに区別できる表示で示す。状態の取得の結果が変わると表示も変わる。
- **AC-12**: 処理中の経過時間は、URL が持つ送信の時刻からの時間で、再読み込みの後も同じ時刻から数える。
- **AC-13**: 完了したキーでは、ビューアは記事、`durationMs` に基づく所要時間、推定の料金（`known` なら金額、`unknown` なら分からないこと）を表示し、投稿の状態が `posting` でなければポーリングを止める。
- **AC-14**: 失敗したキーでは、ビューアは失敗の理由のコードごとに決めた文言と手順を表示し、ポーリングを止める。状態の取得が `failed` の工程を示す場合はその工程を示し、示さない場合（`article_invalid`・`article_too_large` など）は工程を失敗として示さない。失敗の理由のコード（`internal`・`transcript_too_long`・`llm_timeout`・`llm_empty`・`llm_truncated`・`llm_failed`・`article_invalid`・`article_too_large`）のそれぞれで、表示する文言は互いに違う。
- **AC-15**: `unknown` のキーでは、ビューアは記事が失われたこと、ポップアップから送り直す手順、送り直して投稿すると前の投稿と重複しうることを表示し、ポーリングを止める。完了した記事を表示した後に `unknown` になった場合は、表示中の記事と保存・コピーの操作を残し、投稿の操作をできなくする。
- **AC-16**: 状態の取得が未送信・応答なし・ホストの失敗になったとき、ビューアは直前の状態の表示を残し、状態を取得できないことと手順を表示し、その後も状態の取得を続ける。`invalid_key` の拒否・ほかの拒否・想定外の応答になったときは、直前の状態の表示を残し、状態を取得できないことと手順を表示し、状態の取得を止める。どちらでも、生成の開始と投稿の操作は送らない。
- **AC-17**: 生成の開始が拒否・未送信・結果不明になったとき、ビューアはその結果と理由と手順を表示し、状態の取得を送らない。
- **AC-18**: 完了した記事を表示したときに投稿の状態が `posting` なら、ビューアはこのビューアで投稿の操作をしていなくても状態の取得を続け、`posting` でなくなったら結果を表示して止める。
- **AC-19**: 1 つのページで、前の状態の取得の結果を受け取る前に、次の状態の取得は送られない。
- **AC-52**: 生成の開始の結果を待つ間（送信中）と、キーを持つビューアが状態の取得の最初の結果を待つ間（読み込み中）、ビューアはロード中の表示を、どちらの待ちかを示す文言とともに出す。結果を受け取ると、ロード中の表示はその結果の状態の表示に替わる。2 回目以降の状態の取得の間は、直前の状態の表示を残し、ロード中の表示を出さない。

#### F-004: ポップアップの状態

主ボタンを押した後、ポップアップは開いている間、生成の開始の結果とキーの状態を表示する。

-   動画のセクションと詳細はそのまま残し、確認のセクションの位置に状態を表示し、操作のセクションの主ボタンを状態に応じた操作にする（`0046` `02_architecture.md` 9 章）。
-   送信中: 主ボタンは押せず、送信中であることと、ポップアップを閉じてもよいこと、結果がビューアのタブに表示されることを示す。ポップアップは、ページやほかのタブをクリックするとブラウザが閉じるので、開いたままにすることを利用者に求めない。
-   キーを受け取れなかった（拒否・未送信・結果不明）: やり取りの結果と理由と手順を示す（文言は F-001）。主ボタンは押せないままで、送り直すにはポップアップを開き直す（今と同じ。README「ブラウザ拡張」）。
-   処理中: 3 つの工程のチェックリストと経過時間を示す。経過時間は、この送信の時刻から数える。主ボタンは「ビューアを開く」操作になり、ポップアップを閉じてもよいことと、結果がビューアのタブに表示されることを示す。
-   完了: 記事ができたことと、推定の料金と所要時間を示す。主ボタンは「ビューアを開く」操作になる。
-   失敗・不明: 理由（失敗の理由、または記事が失われたこと）と、理由に応じた手順を示す。主ボタンは「やり直す」操作になり、押すと、同じ入力で生成の開始を送り直す。タブの開き方と、同じキーのビューアの再利用は、F-001・F-002 と同じ振る舞いとする。
-   「ビューアを開く」は、次の順に、最初に当てはまるタブを前面に出す。前面に出すとは、そのタブを選び、そのタブのウィンドウを前面に出すことである。
    1.  この送信の表示を受け持つビューアのタブ（この送信で開いたタブか、それが閉じた後に引き継いだ既存のタブ）が残っていれば、そのタブ。
    2.  そのタブがもうなければ、同じキーを表示しているほかのビューアのタブ（履歴から開いたタブなど）。探し方は、F-002 の再利用と同じビューア同士のやり取りとし、`tabs` の権限を加えない。同じキーのビューアが 2 つ以上あるときに選ぶタブは設計で決める（H-01）。
    3.  どちらもなければ（決めた時間のうちに答えがない場合を含む）、同じキーのビューアを新しいタブで開き、前面に出す。
-   ポップアップの状態の取得は、F-003 と同じ規則で続け、止める。ポップアップが閉じたら止まる。ポップアップを開き直すと、送る前の状態から始まる（1. 概要の「導いた振る舞い」）。

**Acceptance Criteria**:
- **AC-20**: 生成の開始が受け付けられた後、ポップアップは動画のセクションを残したまま、処理中なら 3 つの工程のチェックリストと送信の時刻からの経過時間を、完了なら推定の料金と所要時間を示し、主ボタンは「ビューアを開く」操作になる。
- **AC-21**: 「ビューアを開く」を押すと、この送信の表示を受け持つビューアのタブ（AC-08 で既存のタブが引き継いだ場合は、そのタブ）が前面に出る。そのタブを閉じた後に押すと、同じキーを表示しているほかのビューアがあればそのタブが前面に出て、新しいタブは開かない。同じキーのビューアがどこにもなければ、同じキーのビューアが新しいタブで開き、前面に出る。どの場合も、生成の開始は送られない。
- **AC-22**: 失敗または不明のとき、ポップアップは理由と手順を示し、主ボタンは「やり直す」操作になる。押すと、同じ入力の生成の開始が 1 回だけ送られ、新しいビューアのタブが開く。同じキーで失敗か不明を表示していたビューアがあれば、新しいタブはキーを受け取った後に閉じ、そのビューアが送り直した時刻からの経過時間で処理中の表示に戻り、状態の取得を再び始める。
- **AC-23**: キーを受け取れなかったとき、ポップアップはやり取りの結果と理由と手順を示し、主ボタンは押せないままである。
- **AC-24**: ポップアップを開き直すと、送る前の状態（`0046` の画面）が表示され、拡張は何も送らない。

#### F-005: 記事の表示

ビューアは、完了した記事を表示する。

-   記事は、状態の取得が返す表示用の Markdown（`article.markdown`）を、変えずにプレーンテキストとして表示する。改行を保つ。Markdown の記法は解釈せず、記事の中の HTML のタグやリンクの記法は、文字としてそのまま表示する。描画は #504 で行う。
-   見出しとチャンネル名は、ビューアの URL が持つ値を表示する（どの状態でも表示できるようにするため。F-003）。
-   元動画へのリンクは、ビューアの URL が持つ収集した URL が、拡張が受け付ける動画ページの URL（`extension/src/core/acceptedUrl.ts:7-25`）である場合だけ表示する。リンクは新しいタブで開き、開いたページにビューアを参照させず、参照元も送らない。
-   記事とメタデータの文字列は、右から左に書く文字を含んでも、周りの表示の向きを変えない（今のポップアップと同じ扱い）。

**Acceptance Criteria**:
- **AC-25**: 完了した記事の表示用の Markdown が HTML のタグ（例: `<img src=x onerror=alert(1)>`、`<a href="javascript:...">`）や Markdown のリンクを含んでも、ビューアはその文字列をそのまま文字として表示し、記事の内容から要素や属性を作らない。表示した文字列は表示用の Markdown と一致する。
- **AC-26**: 収集した URL が受け付ける動画ページの URL なら、ビューアは元動画へのリンクを、新しいタブで開き、開いたページにビューアを参照させず、参照元を送らない形で表示する。受け付けない URL（`javascript:` のスキーム、ほかのホストなど）なら、リンクを表示しない。
- **AC-27**: ビューアは、どの状態でも、URL が持つ見出しとチャンネル名を表示し、ページのタイトルは見出しを含む。

#### F-006: Slack への投稿

ビューアは、完了した記事を Slack へ投稿する操作を持つ。

-   投稿のボタンの状態は、次の表の行を上から順に見て、最初に当てはまる行で決める。

| 順 | 条件 | 投稿のボタン | 表示 |
|---|---|---|---|
| 1 | 記事が失われた（`unknown`、`article_not_found`） | 押せない | 記事が失われたこと（F-003） |
| 2 | 投稿の状態が `posted` | 押せない | 投稿したこと |
| 3 | 投稿の状態が `posting` | 押せない | 投稿中であること |
| 4 | 投稿の状態が `unpostable` | 押せない | 投稿できない理由（`mention`・`other` ごとの文言） |
| 5 | `webhookConfigured` が `false` | 押せない | Webhook が設定されていないこと、`SLACK_WEBHOOK_URL` を設定してサーバを起動し直す手順 |
| 6 | 投稿の状態が `failed` | 押せる（やり直し） | 投稿の失敗の理由（`webhook`・`internal` ごとの文言）と、やり直すと届かなかったメッセージから送ること |
| 7 | 投稿の状態が `not_posted` | 押せる | - |

-   押すと、記事のキーで投稿の操作を 1 回だけ送る。受け付けられたら、投稿の状態が `posting` でなくなるまで状態の取得を繰り返し、結果を表示する。
-   投稿の操作の結果が拒否（`webhook_not_configured`・`article_not_postable`・`article_not_found`・`article_not_ready`・`invalid_key` など）のときは、その理由の文言を表示する。`article_not_found` は、記事が失われたこと（F-003 の `unknown` と同じ）として表示する。
-   投稿の操作の結果不明（応答なし・ホストの失敗・想定外の応答）のときは、自動で送り直さない。もう一度押しても二重には投稿されないことを示し、状態の取得で投稿の状態を確かめる。
-   投稿の操作を送っている間は、ボタンを押せない。

**Acceptance Criteria**:
- **AC-28**: 投稿のボタンは、上の表の行を上から順に見て最初に当てはまる行のとおりに押せる・押せないが決まり、押せないときはその行の表示をする。2 つ以上の行の条件が同時に当てはまる組み合わせ（`webhookConfigured` が `false` で `posted`、`unpostable` で `webhookConfigured` が `false` など）でも、上の行が決める。
- **AC-29**: `not_posted` の記事で投稿のボタンを押すと、ホストは記事のキーを持つ投稿の操作を 1 つだけ受け取り、その後の状態の取得の結果に合わせて、ビューアは投稿中を経て投稿したことを表示する。
- **AC-30**: 投稿の状態が `failed` になると（`webhookConfigured` が `true` のとき）、ビューアは理由の文言を表示し、投稿のボタンを押せるようにする。押すと投稿の操作が 1 つ送られる。
- **AC-31**: 投稿の操作が拒否されたときは理由の文言を、結果不明のときは二重に投稿されないことを示す文言を表示し、どちらでも投稿の操作を自動で送り直さない。
- **AC-32**: 投稿のボタンが押せない行に当たるとき、投稿の操作を送る手段はなく、投稿の操作は送られない。

#### F-007: `.md` ファイルへの保存

ビューアは、完了した記事を `.md` ファイルとして保存する操作を持つ。

-   保存する中身は、状態の取得が返すファイルの中身（`article.file`）を UTF-8 で符号化したバイト列そのものとする。BOM を付けず、改行を変えない。
-   保存はブラウザのダウンロードで行う。保存先と、保存のダイアログを出すかどうかは、ブラウザの設定に従う。
-   ファイル名は、動画タイトルの、ファイル名に使えない文字を `_` に置き換え、長さの上限で切り詰め、`.md` を付けたものとする（1. 概要の決定）。動画タイトルがないとき、空のとき、または空白だけのときは `<動画 ID>.md` とする。ファイル名は、パスの区切り（`/`・`\`）と制御文字を含まず、`.` で始まらず、`.md` で終わる。使えない文字の集合と長さの上限は設計で決める（H-05）。
-   保存の操作は、完了した記事を表示しているときだけ使える（後で失われた記事を含む。F-003）。ビューアの URL が受理する形でない場合は、記事を表示しないので、保存の操作もない（3.2）。

**Acceptance Criteria**:
- **AC-33**: 保存したファイルのバイト列は、状態の取得が返したファイルの中身を UTF-8 で符号化したものと一致する（BOM なし。改行を含む記事で確かめる）。
- **AC-34**: 動画タイトルが `a/b:c` のようにファイル名に使えない文字を含むとき、ファイル名はそれらを `_` に置き換えた名前に `.md` を付けたものになる。長さの上限を超えるタイトルは切り詰められる。動画タイトルがないとき、または空白だけのとき、ファイル名は `<動画 ID>.md` になる。どの場合も、ファイル名はパスの区切りと制御文字を含まず、`.` で始まらず、`.md` で終わる。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

拡張は、ホストの応答とサーバの応答を信頼できない入力として扱う（`security.md` §8.1「応答を受理する形で検査し」）。本タスクは、受理する応答を新しい API の応答に広げ、拡張のページの URL と、拡張の中のメッセージを新しく入力として読む。拒否は、拡張の分類の「想定外の応答」（今の `unexpected`。`response.ts:91-104`）として扱うか、境界ごとに下の表で決めた表示にする。

| 境界 | 受理する形 | 上限 | 失敗・拒否時の扱い | 主な AC |
|---|---|---|---|---|
| ホストの応答（外側の形） | 今と同じ（`v` が 1、`kind` が `response` か `error`、`kind` ごとのメンバの集合と型、本文は正規の標準の base64。`extension/src/core/native.ts:114-171`） | ブラウザの 1 MiB（ホストのフレームの上限） | 想定外の応答。今と同じ | AC-41 |
| サーバの応答の本文（生成の開始・状態の取得・投稿の操作） | 先頭に BOM を持たない正しい UTF-8 で、後続のデータのない 1 つの JSON オブジェクト。どの階層でもメンバの重複がなく、対になっていないサロゲートのエスケープを含まない。メンバの集合は、操作と `status`・`job.state`・投稿の状態ごとに `docs/dev/guides/development.md`「ジョブの API」の形と過不足なく一致する（拡張可能と宣言するメンバはない）。コードの値は `docs/dev/guides/development.md`「ジョブの API のコード」の閉じた集合に限る。`requestId` は 16 進 16 文字。`durationMs` は、符号・小数点・指数を持たない 10 進の整数の表記で、2^53−1 以下。`cost.usd` は、数字の並び・`.`・4 桁の数字の形（`internal/publisher/format.go:26-31`）。`article.markdown` と `article.file` は空でない文字列（[CLAUDE.md](../../../CLAUDE.md)「Empty is an error」）。状態コードと `status`・`reason` の組は `docs/dev/guides/development.md` の表に合う。キーは空でない JSON の文字列で、形は検査しない（`0044` 3.2） | サーバの状態の取得の上限（256 KiB。`status.go:20`）を下回らず、ホストの中継の上限（512 KiB。`relay.go:43`）を超えない値（設計で決める。H-03） | 想定外の応答。記事・コード・数値の一部だけを表示に使うことはしない | AC-41・AC-42 |

| Service Worker が受け取る生成の開始の求め | 拡張自身のポップアップからの、設計で決めた形の求め（H-01） | 今のリクエストの本文の 4 MiB | 何も送らず、タブも開かずに無視する | AC-05 |
| ビューアが受け取る生成の開始の結果 | 拡張自身の Service Worker からの、そのビューアのタブに宛てた、設計で決めた形の結果（H-01） | - | 無視する。決めた時間のうちに受理できる結果がなければ、結果不明を表示する（F-002） | AC-10 |

**Acceptance Criteria**:
- **AC-41**: 状態の取得の応答で、どの階層かでメンバが重複するもの、対になっていないサロゲートのエスケープを含むもの、正しくない UTF-8 を含むもの、先頭に BOM を持つもの、宣言していないメンバを持つもの、メンバが足りないもの、コードが閉じた集合にないもの、`durationMs` が負・小数・`1.0`・`1e3`・`-0` の表記・2^53−1 を超えるもの、`cost.usd` が決めた形でないもの、`article.markdown` か `article.file` が空のもの、状態コードと `status` の組が合わないもの、後続のデータを持つもの、上限を超えるものは、いずれも想定外の応答になり、記事もコードも表示に使われない。
- **AC-42**: サーバの状態の取得の上限（256 KiB）いっぱいの完了した記事の応答を、拡張は受理して記事を表示する。
- **AC-43**: ビューアの URL で、宣言していない値を持つもの、値が重複するもの、必須の値が欠けるもの、不正なパーセントエンコーディングや正しくない UTF-8 になる値を持つもの、受け付けない動画ページの URL を持つもの、送信の時刻が整数でないか負かページを読み込んだ時刻より後のもの、キーが空のもの、長さの上限を超える値を持つものは、ビューアのリンクが正しくないことの表示になり、記事は表示されず、状態の取得は送られない。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   ポーリングの間隔は設計で決める固定の値とし、1 秒より短くしない（H-04）。状態の取得は LLM を呼ばず、サーバのログにも残らない（`docs/dev/guides/development.md`「ジョブの API」）。1 回の状態の取得でホストのプロセスが 1 つ起動し（`security.md` §8.2）、ポップアップと開いているビューアのそれぞれがポーリングするが、1 つのページが同時に送る状態の取得は 1 つまでで（F-003）、繰り返しても直らない結果では止める。これに加えて、間隔を広げる仕組みや、取得を省く仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   1 回のホストとのやり取りの上限は、今と同じ 25 秒（`extension/src/send.ts:21`）とする。

### 4.2. セキュリティ (Security)

本タスクは、データをホスト経由でサーバへ送り（LLM API と Webhook に届く）、プロンプトインジェクションで操作されうる記事（untrusted なテキスト）を拡張のページに表示するので、`docs/dev/security.md` を適用する。

-   **権限を広げない:** manifest の権限は `activeTab`・`scripting`・`nativeMessaging` のままとする。`host_permissions`・`content_scripts`・`web_accessible_resources`・`storage`・`tabs`・`downloads`・`clipboardWrite` を加えない。ビューアのページは、ウェブページから開けない（`web_accessible_resources` に含めない）。
-   **記事を HTML として解釈しない:** ビューアは記事を文字として表示し、記事の中身から要素・属性・URL を作らない（AC-25）。拡張のページの既定のコンテンツセキュリティポリシーを緩めない。ビューアは `nativeMessaging` を呼べるページであり、記事からスクリプトが動くと、ホストへの任意の送信につながるためである。
-   **リンクは受け付ける動画ページの URL だけ:** 元動画へのリンクは、収集の時点と同じ検査を通った URL だけにする（AC-26）。記事の中のリンクは、本タスクではリンクにしない（#504）。
-   **送り先は固定のホストだけ:** ネットワークへの要求（`fetch`・`XMLHttpRequest`・`WebSocket`・`EventSource`）を持たず、固定のホスト名にだけ送ることは今と同じとする。操作は新しい形のメッセージの `op` で指定し、パスを指定しない（`0044` F-008）。
-   **生成の開始の求めは拡張自身のポップアップからだけ受け付ける**（F-001、AC-05）。
-   **保存しない:** 拡張は `chrome.storage` を使わない。ビューアの URL に持たせる値は、ブラウザの履歴に残る。値は、見出し・チャンネル名・動画タイトル・動画の URL・送信の時刻と、記事のキーである。動画の URL とタイトルは、動画のページを開いた時点ですでに履歴に残る値である。キーはサーバのプロセスごとの秘密を鍵とする HMAC で（`0044` `02_architecture.md` §3.2）、サーバの再起動の後は使えない。コピーした字幕と概要欄は URL に持たせない（AC-09）。
-   **開発者向けのログに値を出さない:** Service Worker・ポップアップ・ビューアの開発者向けのログは、今のログの方針（`security.md` §8.1。項目の名前・理由・検査の種類だけを出し、値を出さない）に従い、コピーした字幕・記事・動画メタデータの値・キーを出さない。
-   **API キーと Webhook の URL を持たない:** 拡張は今と同じく持たない。投稿できるかは、サーバが返す `webhookConfigured` だけで知る。
-   **自動で再送しない:** 生成の開始と投稿の操作を自動で送り直さない（F-001・F-006）。状態の取得だけを繰り返す。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   Service Worker が停止しても、キーを受け取った後のビューアと記事は失われない。ビューアは、URL のキーで状態を取得し直す。状態の正しい値はサーバにある（issue の決定）。キーを受け取る前に停止した場合は、ビューアは決めた時間の後に結果不明を表示する（F-002）。
-   サーバが再起動するか、記事がキャッシュから捨てられると、状態の取得は `unknown` を返し、ビューアは記事が失われたことを表示する（F-003）。これは #501 で受け入れた仕様である。
-   状態の取得の一時的な失敗（サーバが止まっている、応答がない）では、表示中の状態を消さずに、取得を続ける。繰り返しても直らない結果では止める（F-003、AC-16）。

### 4.4. 互換性 (Compatibility)
-   拡張は、新しい API を持つサーバとホスト（`0044` の版以降）を必要とする。古いホストは新しい形のメッセージを今の形として `/articles` へ中継するので、拡張を更新するときはサーバとホストも同じ版に更新するよう、README に書く。
-   ブラウザの最小の版（`minimum_chrome_version` の 103）は、設計で Service Worker と使う API が動くことを確かめ、必要なら上げる（H-10）。上げる場合は README に書く。
-   ポップアップの送る前の画面（`0046`）は変えない。

### 4.5. 保守性 (Maintainability)
-   新しい API のコード、拒否の理由、ポップアップとビューアの状態は、型（判別共用体と閉じた集合）で表し、`switch` の網羅性で欠けを型の検査が知らせる形にする（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。
-   ホストの応答の外側の検査（`native.ts`）は、生成の開始・状態の取得・投稿の操作で共有する（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   拡張が使わなくなった `/articles` のためのコード（`/articles` の応答の解釈、Slack を案内する文言）は、本タスクで取り除く。
-   Markdown のライブラリを加えない。npm のパッケージは開発用に限る（[CLAUDE.md](../../../CLAUDE.md)「Dependencies」）。

### 4.6. アクセシビリティ (Accessibility)

ビューアと、ポップアップの新しい状態は、[CLAUDE.md](../../../CLAUDE.md)「Accessibility」に従い、WCAG 2.2 のレベル AA を満たす（押せる要素の大きさと動きはレベル AAA の値）。各 AC の検証は、実装計画で `test` または `static` の検証を割り当てる（色のコントラストは色の変数から計算するなど）。ブラウザでの見え方の確認は、それに加えて行う。

**Acceptance Criteria**:
- **AC-44**（キーボード）: ビューアの投稿・保存・コピーのボタンと元動画へのリンク、ポップアップの「ビューアを開く」「やり直す」は、Tab・Shift+Tab・Enter・Space だけで操作でき、フォーカスの順序は見た目の順序に従い、フォーカスを閉じ込めない。
- **AC-45**（見えるフォーカス）: フォーカスのある要素は、隣り合う色に対して 3:1 以上のコントラストの印で示される。ライトとダークの両方で満たす。
- **AC-46**（名前・役割・状態）: ビューアとポップアップの操作は、ネイティブの要素（`<button>`・`<a>`・見出し）で作り、見える名前と一致する名前を持つ。押せないボタンは、押せないことが支援技術に伝わる。工程のチェックリストの各工程の状態は、記号だけでなく文字でも伝わる。
- **AC-47**（状態のメッセージ）: 状態の変化（ロード中になったこととロード中が終わったこと、工程の変化、完了、失敗、投稿の結果、コピーの結果、状態を取得できないこと）は、フォーカスを動かさずに支援技術に伝わる。経過時間の毎秒の更新は、読み上げを繰り返させない。
- **AC-48**（コントラスト・色だけに頼らない）: 文字は背景に対して 4.5:1 以上、意味のある図形は 3:1 以上で、ライトとダークの両方で満たす。工程・投稿の状態は、色だけでなく形と文字でも区別できる。
- **AC-49**（言語）: ビューアのページの `lang` は、表示の言語と一致する。
- **AC-50**（押せる大きさ）: ビューアとポップアップの押せる要素は、44×44 CSS ピクセル以上である。
- **AC-51**（動き）: 実行中の工程のアニメーションと、ロード中の表示の印の動きは、`prefers-reduced-motion` が `reduce` のとき止まる。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。本タスクは同書のツールの説明と `extension/` の説明を変えるので、F-010 で同書を更新する（親 issue #501「project_overview の方針の変更」）。
-   **以前のタスクと文書の方針の変更:**
    -   `docs/dev/security.md` §8.1「送れなかった場合と結果が分からない場合を分け、自動で再送しない」は、結果不明のときに送り直す前に Slack を確かめるよう案内するとした。本タスクは、生成の開始の結果不明では、同じ入力の記事が処理中か完了していれば二重には生成されないことを示し、Slack に触れない。理由は、新しい API の生成の開始が、同じ入力に対して処理中または完了したキーを返し、LLM を呼ばないこと（`0044` F-001）と、投稿が利用者の操作になったこと（#501）である。自動で再送しないことは保つ。
    -   `docs/dev/security.md` §8.1「応答を受理する形で検査し、本文の文字列を表示しない」は、応答の本文の文字列を表示に使わない（`reason` は固定の文言に、`requestId` は 16 進 16 文字に限る）とした。本タスクは、状態の取得が返す記事（表示用の Markdown とファイルの中身）を、文字として表示し、保存し、コピーする。理由は、記事をビューアに表示することが issue の目的そのものだからである。記事のほかの文字列は、検査を通った推定の料金の金額（`cost.usd`）を除き、今と同じく表示に使わない。記事は HTML として解釈せず（4.2）、リンクにしない。
    -   `docs/dev/security.md` §8.1「送る相手は固定のホストだけ」の「1 回の送信でホストを 1 回起動し、ジョブの完了を待たずに受付の応答で終わる」は、状態の取得を繰り返すことで、1 回の送信の後にもホストを起動するようになる。1 回の起動で 1 つのメッセージを送ることは変えない。理由は、#501 が状態をポーリングで取得すると決めたことである。
    -   `0046_popup_redesign` `01_requirements.md` 1 章は、送信の経路と、送信中・送信の結果の文言を変えないとした。これは本タスクで変える前提の決定であり（同書 2.3）、方針の変更ではない。
-   **CLAUDE.md「Reject, don't normalize」は、ファイル名を作る処理には当てはめない:** 方針は、呼び出し側の不正な入力を補正せずに拒否することである（[CLAUDE.md](../../../CLAUDE.md)「Key Design Patterns」）。動画タイトルにファイル名に使えない文字があることは不正な入力ではなく、正しいタイトルである。ファイル名は、そのタイトルから作る出力であり、使えない文字の置き換えは、決めた規則による変換である（F-007）。拒否すると、そのようなタイトルの記事を保存できなくなるためである。
-   拡張は外部のフォントやライブラリを使わず、値は `textContent` だけで設定する（`0046` の「今のまま保つこと」）。
-   ユニットテストは、実際のブラウザ・ホスト・サーバを呼ばない。ブラウザの API は fake に置き換える。テストの組み立て方は設計で決める（H-13）。
-   サーバとホストのコードは、2.3 の条件のほかは変えない。

## 6. 用語集 (Glossary)

-   **0044**: サーバとホストに新しい API を加えたタスク（`docs/tasks/0044_article_job_api/`）。
-   **0046**: ポップアップの画面を再設計したタスク（`docs/tasks/0046_popup_redesign/`）。
-   **新しい API**: `0044` で加えた 3 つの操作（生成の開始・状態の取得・投稿の操作）。拡張は、ホストの新しい形のメッセージ（`v`・`op`）で指定する。
-   **今の形のメッセージ**: 版のメンバ `v` を持たない、ホストが `POST /articles` へ中継するメッセージ（`0044` F-008）。
-   **同じ入力**: 生成の開始の入力の値（選択範囲・URL・動画メタデータ）がすべて同じであること。サーバは同じ入力に同じキーを返す（`0044` F-001）。
-   **Service Worker**: Manifest V3 の拡張のバックグラウンドの処理を行うスクリプト。ブラウザが必要なときに起動し、使われないと停止する。
-   **ビューア**: 記事の状態と記事を表示する拡張のページ（`viewer.html`）。タブで開く。
-   **ビューアの URL**: ビューアのタブの URL。記事のキー・見出し・チャンネル名・動画タイトル・収集した URL・送信の時刻を持つ。
-   **送信の時刻**: 利用者が主ボタン（または「やり直す」）を押して、生成の開始を送った時刻。処理中の経過時間の起点。
-   **ポーリング**: 状態の取得を、決めた間隔で繰り返すこと。
-   **やり取りの結果**: 生成の開始・状態の取得・投稿の操作の 1 回のホストとのやり取りの結果。受け付け・拒否・未送信・応答なし・ホストの失敗・想定外の応答のいずれか。応答なし・ホストの失敗・想定外の応答をまとめて結果不明と呼ぶ。ジョブの状態の `不明`（`unknown`。サーバに記録がない）とは別のものである。
-   **推定の料金**: 状態の取得が返す記事 1 本の料金（`cost`）。`internal/pricing` の単価の表から算出した推定値である。
-   **主ボタン**: ポップアップの操作のセクションのボタン。送る前は送信を始め、本タスクの状態では「ビューアを開く」「やり直す」の操作になる。
-   **記事のキー・ジョブの状態・工程・工程の状態・投稿の状態**: `0044` と [translation_glossary.md](../../translation_glossary.md) の定義による。工程は `draft`（下書き）・`shorten`（本文の短縮）・`review`（検証・推敲）の 3 つである。
-   **見出し**: ポップアップの動画のセクションの見出しと同じ文字列（動画タイトル、なければタブのタイトル。`0046`）。
-   **動画 ID**: 収集した URL の `v` の値。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
