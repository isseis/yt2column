# 設計への申し送り：DeepSeek アダプタ

## 本書の位置づけ

[01_requirements.md](01_requirements.md) の作成とレビューの過程で挙がった事項のうち、要件（観測できる振る舞い）ではなく、設計・実装の段階で決める、または注意すべき事項をまとめる。

-   要件書は「何を送り、何を受理し、何をどの番兵で拒否するか」だけを定める。本書の項目は、その振る舞いを実現する手段の候補と、既知の落とし穴である。
-   `02_architecture.md` は、本書の各項目について、採用した手段または扱わない理由を記録する（要件書 §5）。本書の手段は候補であり、設計で別の手段を選んでもよい。ただし、対応する AC を満たすこと。
-   本書は承認対象の文書ではない。設計の作成時に参照し、項目を追加してよい。

## H-01: タイムアウトを `context.DeadlineExceeded` として報告する

-   `http.Client.Timeout` による打ち切りは `*url.Error`（`Timeout()` が真）として返り、`errors.Is(err, context.DeadlineExceeded)` が真になるとは限らない。AC-17 は構築時のタイムアウトでも `context.DeadlineExceeded` を要求する。
-   候補: 構築時のタイムアウトを `context.WithTimeout` で `ctx` に重ね、その `ctx` でリクエストを作る。本文の読み取りも同じ `ctx` の下で行い、読み取りの途中で期限が来た場合も `context.DeadlineExceeded` として報告する。
-   `http.Client.Timeout` を併用する場合は、どちらが先に発火しても AC-17 を満たすことを確認する。

## H-02: リダイレクトに従わない

-   `http.Client` は既定で最大 10 回のリダイレクトに従う。別ドメインへのリダイレクトでは `Authorization` ヘッダーを落とすが、同じドメインの別パスや、`http` へのダウングレードの扱いに依存したくない。
-   候補: `http.Client.CheckRedirect` で `http.ErrUseLastResponse` を返し、3xx の応答をそのまま受け取って `ErrHTTPStatus` にする。

## H-03: 標準ライブラリのエラーに含まれる値

-   `*url.Error` は、メソッド・URL・下位のエラーを文字列に含める。API キーは `Authorization` ヘッダーで送り URL には含めないため、通常は API キーは現れない。ただし、送信先 URL にクエリやユーザー情報を含める設計にすると漏れうる。
-   `http.Request` を `%+v` で出力すると、ヘッダーが含まれる。エラーの型に `*http.Request` や `http.Header` を保持しない。
-   API キーの `Reveal()` は、ヘッダーを設定する直前の 1 か所だけで呼ぶ。取り出した文字列を構造体のフィールドやクロージャの外に保持しない。
-   AC-20 は、エラーの各書式（`Error()`・`%v`・`%+v`・`%#v`）で確認する。`%#v` は、エラーの型が保持するフィールドをすべて表示するためである。

## H-04: 応答本文のサイズの上限と超過の検出

-   `io.LimitReader(r, n)` は n バイトで読み取りを止めるだけで、超過したかどうかを知らせない。上限ちょうどの応答と、上限を超える応答の先頭 n バイトを区別できない。
-   候補: 上限 + 1 バイトまで読み、上限を超えて読めたら `ErrInvalidResponse` とする。
-   上限値は、想定する生成の長さ（40 分前後の動画のコラム記事）と、`reasoning_content` を含む応答全体の大きさから決める。`reasoning_content` は本文より長くなりうる。
-   読み取りを上限で止めた後の接続は再利用できないことがある。本ツールは 1 回の実行で 1 回しか呼ばないため、接続の再利用は考慮しなくてよい。

## H-05: `encoding/json` が黙って補正する入力

要件書 3.2 の「標準ライブラリのデコーダが黙って置換・切り捨て・無視しうる入力も拒否する」を具体化する。既知のものは次のとおり。検出の手段は設計で決める。

-   **不正な UTF-8:** `json.Unmarshal` は不正なバイト列を U+FFFD に置き換えて成功する。応答本文全体を `utf8.Valid` で検査する。
-   **対になっていないサロゲートのエスケープ:** `"\ud800"` は `utf8.Valid` を通過し、デコード時に U+FFFD に置き換えられる。消費しないメンバー（`reasoning_content` など）にあるものも拒否する（AC-30）ため、消費するフィールドのデコード結果だけでなく、本文全体の文字列トークンを検査する必要がある。
-   **後続データ:** `json.Decoder.Decode` は最初の値だけを読んで成功する。デコード後に EOF まで空白しか残っていないことを確認する。`json.Unmarshal` は後続データを拒否するが、他の検査との組み合わせで選ぶ。
-   **重複したメンバー:** `encoding/json` は後に現れた値を採る。消費するメンバーの重複を検出するには、トークン単位で読むか、`map[string]json.RawMessage` へのデコードでは検出できない（後勝ちになる）ことに注意する。
-   **`null` の文字列へのデコード:** `"content":null` を `string` のフィールドへデコードすると、エラーにならずゼロ値（空文字列）のままになる。そのまま進むと `ErrEmptyResponse` になり、AC-27 が求める `ErrInvalidResponse` にならない。ポインタ型や `json.RawMessage` で受けて、存在と種類を確かめる。
-   **欠落したフィールド:** 欠落したフィールドもゼロ値のままになる。`null` と同様に、存在を確かめる。
-   **配列の要素の `null`:** `[null]` を構造体のスライスへデコードすると、ゼロ値の要素になる（AC-28）。

`0002_ytdlp_transcript_source` の json3・info.json のパーサが同種の検査を実装している。共通化できる部分があれば再利用を検討する（CLAUDE.md の DRY）。ただし、パッケージ間の依存の向き（`internal/llm/deepseek` が `internal/transcript` に依存しないこと）に注意し、共通化する場合は共通のパッケージへ移す。

## H-06: 送信先の差し替え

-   ユニットテストは `httptest` のサーバーを送信先にする（AC-25）。`httptest.NewServer` は `http` の URL を返す。
-   本番の送信先は `https://api.deepseek.com/chat/completions` に固定し、利用者の設定（#6）からは変えられないようにしたい。送信先を任意に変えられると、API キーを任意のホストへ送れるためである。
-   候補:
    -   送信先を非公開のフィールドにし、同じパッケージのテストだけが設定できるようにする。
    -   `http.Client`（または `http.RoundTripper`）を差し替え可能にし、テストでは `httptest.Server.Client()` と、リクエストの送信先を書き換える `RoundTripper` を使う。
-   どの手段でも、テストのために公開した差し替え口を本番のコードから使えないことを確認する。

## H-07: `200` 以外の応答の本文の扱い

-   要件書は、`200` 以外の応答の本文をエラーに含めないと定める（F-003）。応答本文は信頼できない入力であり、端末の制御文字などを含みうるためである。
-   DeepSeek は `400`（形式不正）・`401`（認証失敗）・`402`（残高不足）・`422`（パラメータ不正）・`429`（レート制限）・`500`・`503`（過負荷）を返す。ステータスコードだけで原因の見当はつく。
-   デバッグに本文が必要になった場合は、本文の `error.message` を検証したうえで切り詰めて含める、などの拡張を別途検討する。本タスクでは行わない。
-   本文を読み捨てる場合も、H-04 と同じ上限を超えて読まない。

## H-08: thinking モードと `max_tokens`

-   thinking モードでは、`max_tokens` が推論過程（`reasoning_content`）のトークンを含むかどうかで、`ArticleWriter`（#5）が与えるべき `MaxOutputTokens` が変わる。含む場合、推論が長いと本文が短く打ち切られ、`ErrTruncated` が増える。
-   事前調査（要件書 §5）で確認し、結果を `02_architecture.md` に記録して #5 に引き継ぐ。
-   AC-24 の「生成に十分でない小さな `MaxOutputTokens`」は、この調査結果を踏まえて値を決める。

## H-09: 番兵エラーの配置

-   `ErrTruncated`・`ErrEmptyResponse` は、どのプロバイダでも起こりうる概念である。`internal/llm` に置けば、`ArticleWriter`（#5）や CLI（#6）がプロバイダに依存せず判別できる（例: 打ち切りなら `MaxOutputTokens` を増やすよう案内する）。
-   `ErrHTTPStatus`・`ErrInvalidResponse`・`ErrTransport` は HTTP の API に共通だが、将来の SDK ベースのプロバイダ（Gemini・Claude）では SDK のエラーを変換することになる。どこに置くかは、`ErrUnexpectedFinishReason`・`ErrInvalidRequest` とあわせて設計で決める。
-   `internal/llm` に番兵を追加する場合、`llm.LLMClient` の契約（doc コメント）にもその番兵で報告することを書く。

## H-10: リクエスト本文の組み立て

-   リクエスト本文は、構造体を `json.Marshal` して作る。プロンプトを文字列連結で JSON に埋め込まない（エスケープ漏れでリクエストの構造が変わるため）。
-   `max_tokens` を省略するには、`omitempty` か、ポインタ型を使う（AC-05）。
-   `json.Marshal` は既定で `<`・`>`・`&` を `<` などにエスケープする。JSON として等価なので API の解釈は変わらないが、AC-04 のテストはエスケープの有無ではなく、デコードした文字列が元のプロンプトと一致することで確認する。
-   `json.Marshal` は不正な UTF-8 を含む文字列を U+FFFD に置き換え、エラーを返さない。要件書は不正な UTF-8 のプロンプトを `ErrInvalidRequest` で拒否すると定める（F-002・AC-07）ため、`json.Marshal` の前に `utf8.ValidString` で検査する。
