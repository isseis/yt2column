# 設計への申し送り：ADR の規約に、背景と決定に書く内容と詳細度の基準を足す

要件定義書（[01_requirements.md](01_requirements.md)）のレビューで挙がった、設計で決めることを記録する。`02_architecture.md` は、各項目をどう扱ったかを記す。

## H-01: 基準を置く場所と、CLAUDE.md とそろえる指示

規約の「Writing an ADR」は、ADR と正本の文書の分担を述べる「決定」の項目について、同じ分担を CLAUDE.md も持つので変えるときは両方をそろえる、と述べる（`docs/dev/conventions/adr.md:138-141`）。新しい基準をその分担の文の中に置くと、文字どおりには CLAUDE.md もそろえる必要が生じ、AC-20（CLAUDE.md を変えない）と食い違う。基準を分担の文の外に置くか、分担の文の意味を変えない形で足すかを、設計で決める。

## H-02: 「正本の文書かコードの場所」の粒度

AC-04 は「決定」の各項目に正本の文書かコードの場所を添えることを求め、AC-06 は呼び出し箇所の列挙を禁じ、規約の「Links」は行番号を使わないと定める。場所をどの粒度（文書と節、パッケージ、ファイル）で書くかを、規約の文面で示すかどうかを設計で決める。

## H-03: ずれの記述の見つけ方

AC-14 は、ずれを直す PR に、そのずれを述べる ADR の記述を消すことを求める。ずれの記述は扱う issue へリンクするので、PR が対応する issue へのリンクを `docs/dev/adr/` で探せば見つかる。この探し方を規約に書くか、どのコマンドの手順にも入れずに PR を作る人に任せるかを、設計で決める（コマンドの定義は本タスクで変えない。要件定義書 2.3）。

## H-04: 「背景」に残す数字の例

AC-03 の、決定の根拠になる数字の例（ADR-0038 の約 23〜31 倍）を規約に添えるかどうかを決める。例は基準を読み取りやすくするが、ADR-0038 が変わると古くなりうる。

## H-05: 後から `main` に入る ADR の PR が、ずれが直ったことに気づく手がかり

AC-14 は、ずれを直す PR より後に、ずれの記述を持つ ADR が `main` に入るときは、その ADR の PR が `main` を取り込んだときに消すことを求める。git はこの場合に衝突を起こさないので、PR がそれに気づく手がかり（ずれの記述がリンクする issue が閉じたことを、`main` を取り込むときに確かめるなど）と、その規則を規約のどの節（「Taking in `main`」など）に置くかを、設計で決める。
