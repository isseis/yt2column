## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

規約の「Writing an ADR」に「背景」と「決定」の基準を足す（F-001・F-002）。また、決定を変えない編集上の訂正の扱いを、規約の訂正の節と、「Approval and the PR」「History entries」「Taking in `main`」に足す（F-003）。同じ PR で、ADR-0039 の「決定」から、規則がまだ規約にないと述べる記述を消し、規約の節へのリンクに置き換える（F-004 の AC-23）。変えないことを求める AC は、`_checks/` の 1 回限りの確認のプログラムで確かめる。

### 1.2. 実装の原則

-   **変えるファイルは、規約、ADR-0039、このタスクのディレクトリの下だけにする。** `CLAUDE.md`、`.claude/commands/` の下、`requirements_process.md`、ADR の索引、ADR-0036 は変えない（設計書 2.2、AC-20）。
-   **規約の文面は、設計書 3.1〜3.5 の英語の案を使う。** 言い回しは、案の意味を変えない範囲で整えてよい。意味を変えるときは、実装を止めて設計書を改める（設計書 3 章の冒頭）。
-   **変えない部分は 1 バイトも変えない。** 分担の文、3 つのそろえる段落、「Template」「Status」「Index」の節などは、設計書 7.2 の表のとおりである。改める文が変えない文と同じ行から始まるとき（本計画 §1.4）は、変えない文の後ろだけを書き換え、その行の前半と改行の位置を保つ。
-   **ADR-0039 の変更は、編集上の訂正として、PR を作る前のコミットに入れる**（設計書 3.6）。
-   **新しい恒久的なテストは足さない**（設計書 1.1・7.1）。

### 1.3. 計画の際に決めたこと（2026-11-09）

人間のレビュアーに諮るべき未決の判断はなかった。設計書が、PR の数、コミットの順序、差分の確認で確かめることとその性質まで決めているためである。次の点は計画で決めたことであり、理由とともに記す。PR のレビューで異論があれば改める。どれも本タスクの中で閉じるので、ADR は作らない（`CLAUDE.md`「Design decisions (ADR)」の基準で major ではない）。

-   **フェーズは 1 つにし、PR の作成ポイントは置かない。** 設計書 8 章は PR を 1 本と決めている。フェーズが 1 つの計画には PR の作成ポイントを置かず、`/runplan` がフェーズの完了の後に PR を作る（`.claude/commands/runplan.md:231`）。
-   **確認のプログラムは Go で書き、ビルドした実行ファイルを走らせる。** 置き場所は `docs/tasks/0070_adr_writing_criteria/_checks/main.go` とし、先頭に `//go:build test` を置く。`go build -tags test -o <scratchpad の中のパス> ./docs/tasks/0070_adr_writing_criteria/_checks/` でビルドし、`[<base> <head>]` の引数で走らせる。引数を省くと、`origin/main` と `HEAD` のマージベースと、`HEAD` を比べる。理由は次のとおりである。
    -   節と段落の切り出しを Go で書けば、シェルと `awk` の方言（macOS の BSD 版と GNU 版）の違いに左右されない。
    -   `go run` は、プログラムの終了コードが 0 でなければ、値によらず 1 で終わる。そのため、違反（1）と読み取りの失敗（2）を区別できない。タスク 0067 の計画が確かめた（`docs/tasks/0067_stage_terminology/03_implementation_plan.md:34`）。
    -   `-tags test` を付けると、`internal/doctestutil` の見出しと節の読み取り（`HeadingsOutsideBlocks`・`SectionOutsideBlocks`、`internal/doctestutil/markdown.go:31`・`:44`）を再利用できる。引数の形、git でファイルを読む関数、終了コードの決め方は、タスク 0069 の `_checks/main.go` にならう。
-   **確認のプログラムが使う日本語の文字列は、プログラムの横の `data.json` に置く。** ADR-0039 の `## 決定` の見出し、規約の「背景」の箇条の始まり（`- **背景:**`）、置き換え前後の文は日本語を含む。`_checks/` には guard-test literal exception（`CLAUDE.md`「Go Idioms」）が及ばないので、Go のソースの文字列は英語に保つ。データのファイルは、比べるコミットの中ではなく作業ツリーから読む（ステップ 1-4 で、データのファイルを含まない一時的なコミットを先頭にして走らせるため）。先例はタスク 0069 の `_checks/data.json` である。
-   **変えない部分は、基点で切り出し、先頭の同じ節にそのまま 1 回だけ現れることで確かめる。** 部分の切り出しは、節の見出しと、部分の始まりと終わりの文字列（`data.json`）で行い、行番号を使わない。目印が見つからないか、2 回以上見つかるときは、読み取りの失敗にする。節の並びの確認（設計書 7.2 の「節の構成」の行）と合わせると、部分の中身と節の位置の両方を確かめられる。
-   **AC-23 の確認は、`決定` の各項目を置き換えの対で確かめる。** `data.json` に、項目ごとの置き換え前の文と置き換え後の文の対を置く。確認のプログラムは、変更前の `決定` の各項目の置き換え前の文を置き換え後の文に替えたものが、変更後の項目に等しいことを確かめる。あわせて、変更後の `決定` が `issues/728`・`#728`・`に足すことは` を含まないことを確かめる。設計書 7.2 の「#728 で扱う」は、Markdown のソースでは `[#728](https://…/issues/728) で扱う` と書かれ、そのままの文字列では現れないので、ソースに現れる形で探す。
-   **AC-23 の記録の形（AC-12 の訂正の行）も、同じプログラムで確かめる。** 設計書 7.2 にない項目だが、プログラムは比べる範囲のコミットを読むので、追加の手間なく機械で確かめられる。比べる範囲のマージでないコミット（`--no-merges`）のうち ADR-0039 を変えるものについて、次の 3 つを確かめる。(a) 1 つ以上ある。(b) どれも ADR-0039 のほかのファイルを変えない。(c) どれも、メッセージに ADR-0039 の訂正の行（`Editorial correction: docs/dev/adr/0039-adr-writing-criteria.md: ` で始まり `; no decision changed` で終わり、`@` と `<` を含まない行）を 1 行以上持つ。行の数（項目ごとに 1 行）と内容は、PR のレビューで読む。マージのコミットを除くのは、`main` を取り込むと、そのマージのコミットがほかのタスクの `docs/dev/adr/` の変更を含むためである。先例はタスク 0069 の計画の §1.3 である。

## 2. 実装のステップ (Implementation Steps)

### フェーズ 1: 規約の変更と ADR-0039 の訂正（全 AC）

設計書 8 章の優先順位 1〜4 を、この順で行う。優先順位 5（PR の作成）は、フェーズの完了の後に `/runplan` が行う。

-   [ ] **ステップ 1-4（コミット 3）**: 確認のプログラムが違反と読み取りの失敗を検出できることを確かめる。PR のブランチから `git worktree` で使い捨てのブランチを作り、壊し方を 1 件ずつ別の一時的なコミットとして作る。それぞれを先頭として、ビルドした実行ファイルを PR のブランチの作業ツリーから走らせる。壊した項目だけが失敗し、ほかの項目は通ることと、終了コード（違反は 1、読み取りの失敗は 2）を確かめる。
    -   **壊す対象:** ステップ 1-3 の各項目について、その項目の失敗の経路を 1 件以上の壊し方で確かめる。変えない部分の項目では、部分ごと（分担の文、3 つのそろえる段落のそれぞれ、「背景」以外の箇条、「**Links.**」からの部分、「Approval and the PR」の最初の 3 文、「History entries」の今ある箇条とコードブロック、「Taking in `main`」の手順、ガードの失敗の段落の最初の 2 文、「Template」「Status」「Index」の各節）に 1 バイトの変更を加える。範囲の項目では、`CLAUDE.md`、`.claude/commands/` の下のファイル、`requirements_process.md`、それ以外の範囲外のファイルをそれぞれ変える。節の構成の項目では、見出しの追加・名前の変更・入れ替えを試す。AC-23 の項目では、`#728` へのリンクを 1 つ残すこと、項目のほかの文を変えること、「経緯」に行を足すことを試す。訂正の行の項目では、行がないこと、行の終わりがないこと、ADR-0039 を変えるコミットがほかのファイルも変えることを試す。
    -   **読み取りの失敗:** 目印（見出しか、部分の始まりと終わりの文字列）がないこと、2 回現れること、基点と先頭を入れ替えて渡すこと（基点が先頭の祖先でない）を試す。終了コードが 2 であることを確かめ、ほかの項目の結果は問わない。
    -   **作り方:** ADR-0039 に関する壊し方は、使い捨てのブランチで、コミット 1 の上にコミット 2 を作り直して作る。こうすると、訂正の行の項目が巻き添えで失敗しない。作り直すコミット 2 には、正しい訂正の行を残す（訂正の行の項目を壊すときを除く）。狙った項目のほかが失敗するときは、壊し方を直す。
