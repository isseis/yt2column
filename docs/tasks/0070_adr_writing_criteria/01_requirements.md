## 1. 概要 (Overview)

**目的:** 本書は、ADR の規約 `docs/dev/conventions/adr.md` に、ADR の「背景」と「決定」に何をどの詳細度で書くかの基準を足すための要件を定義する。あわせて、決定を変えずに ADR の書き方だけを直す PR の扱いを定める（[#728](https://github.com/isseis/yt2column/issues/728)）。

**背景:**

ADR は、後の開発者が、変えようとしている主題の決定とその理由を知るために読む文書である。規約の「Writing an ADR」は、各節の用途を 1 行ずつ述べるだけである。「背景」は、主題に決定が要る理由と、決定を縛る前提とだけ述べる（`docs/dev/conventions/adr.md:122-123`）。「決定」は、今効いている決定だけを書き、正本の文書がある主題では仕様を書き写さずに要約してリンクする、と述べる（`docs/dev/conventions/adr.md:124-130`）。どちらの節にも、何をどの詳細度で書くかの基準はない。そのため、背景には過去の規則の経緯や調査の数字が時系列で並びやすく、決定には正本の文書の一覧の写しや、腐りやすい実装の細部が入りやすい。

タスク 0065 の最後の PR（[#727](https://github.com/isseis/yt2column/pull/727)）では、レビュアーと基準を決め、ADR-0031〜0038 の「背景」と「決定」をそれに合わせて書き直した。その基準は、PR の説明にだけ記録され、規約には入っていない。

規約の「Approval and the PR」は、ADR を追加・変更するのは、その決定を下すか変える PR だけだと述べる（`docs/dev/conventions/adr.md:215-219`）。そのため、決定を変えずに書き方だけを直す PR は、文字どおりには認められない。ところが、そうした変更はすでに必要になっている。

-   タスク 0068 は、ADR-0020 の「決定」にある、`package_reference.md` の一覧に 4 つのパッケージがないことを #713 で扱うとする記述（以下「ずれの記述」）を扱った。当初は「本タスクの PR は ADR に触れず、0065 の側が消す」と決めた（`docs/tasks/0068_strictjson_package_reference/01_requirements.md:44`）。
-   タスク 0069 は、ADR-0029 のずれの記述を、README を直す実装の PR が消すことにした。これは規約の例外として、本タスクの 1 回の削除に限っている。決定を変えないので、経緯の項目は足さず、編集上の修正としてコミットメッセージと PR の説明に記す（ブランチ `isseis/0069-readme-display-language-01` の `docs/tasks/0069_readme_display_language/01_requirements.md:57-63`、AC-10）。
-   後続の [#729](https://github.com/isseis/yt2column/issues/729) は、ADR-0001〜0030 を本タスクの基準で見直す。見直しは決定を変えない書き直しなので、今の規約では行えない。

タスク文書については、決定を変えない編集上の訂正を、コミットメッセージと PR の説明に記録し、変更履歴には記録しないことが定まっている（`docs/dev/conventions/requirements_process.md`「Editing an approved document」の「Editorial correction」）。ADR の「経緯」は、決定を下したときと変えたときに 1 項目ずつ足す、と定まっている（`docs/dev/conventions/adr.md:167-169`「History entries」）。

ADR の仕組みそのもの（タスク 0060 が決めた、生きた文書としての ADR、状態、規約）を主題とする ADR はない（`docs/dev/adr/README.md` の表）。0060 の決定は、0060 のタスク文書にだけ記録されている（`docs/tasks/0060_adr_records/01_requirements.md`「要件定義の際に決めたこと（2026-11-04）」）。

**軽量プロセスを取らない理由:** この変更は `docs/dev/conventions/` の規則を足し、意味を変える。`docs/dev/conventions/` では誤字の修正だけが軽量プロセスに当たり、ほかの変更は通常プロセスになる（`docs/dev/conventions/requirements_process.md`「Changes that always take the normal process」）。

対応 issue: [#728](https://github.com/isseis/yt2column/issues/728)（関連: [#729](https://github.com/isseis/yt2column/issues/729)、タスク 0065 の [#666](https://github.com/isseis/yt2column/issues/666) と [#727](https://github.com/isseis/yt2column/pull/727)、[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md)（ADR の背景と決定の書き方と、決定を変えない書き直し））

**本書の記述範囲:** 本書は、規約が述べる基準の内容と、決定を変えない書き直しの扱いを定める。規約の英語の文面と、基準を「Writing an ADR」のどこにどう置くか（項目の中の箇条書きにするか、節を分けるかなど）は、`02_architecture.md` で決める。

**issue #728 で決めたこと:**

-   **背景と決定の基準は、PR #727 でレビュアーと決め、ADR-0031〜0038 に当てはめたものとする:** 内容は 3 章の F-001・F-002 のとおりである。すでに 8 本の ADR に当てはめ、レビューを経ているためである。ADR：作る（[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md)。要件定義の際に決めたことの 3 つ目の項目）。
-   **基準の観点は、後の開発者が、変えようとしている主題の決定とその理由を知ることとする:** ADR が読まれる目的がそれだからである。ADR：ADR-0039 に含める。
-   **規約の「Writing an ADR」を変え、必要なら「Approval and the PR」も変える:** ADR の書き方を定める文書が規約だからである。ADR：ADR-0039 に含める。
-   **CLAUDE.md の「Design decisions (ADR)」と規約が同じ文で持つ部分を変えるときは、両方をそろえる:** 規約の指示である（`docs/dev/conventions/adr.md:138-141`・`:221-222`）。ADR：なし。規約の既存の規則を当てはめるだけで、新しい決定ではない。
-   **決定を変えない書き直しを認めるか、認めるならどう記録するかを、本 issue で決める:** 要件定義の際に決めたことの 1 つ目と 2 つ目の項目で決めた。
-   **既存の ADR の見直しは、後続の issue で行う:** [#729](https://github.com/isseis/yt2column/issues/729) が ADR-0001〜0030 を見直す。本タスクの範囲を規約に限るためである。ADR：なし。作業の範囲の決定で、本タスクの中で閉じる。

**要件定義の際に決めたこと（2026-11-09）:**

-   **決定を変えない ADR の書き直しを、編集上の訂正として認める:** 決定を下しも変えもしない PR も、ADR に編集上の訂正を加えてよい。訂正は、コミットメッセージと PR の説明に記録し、「経緯」に項目を足さない。どの PR が行ってもよい。ずれの記述は、正本の文書かコードのずれを直す PR が、同じ PR で消す（F-003）。
    -   **理由:** タスク文書の編集上の訂正の扱い（`requirements_process.md`「Editorial correction」）と同じ記録の置き場所になる。0068 と 0069 が 1 回ずつ作った例外も、この形だった。「経緯」は決定を下したときと変えたときの記録で（`adr.md`「History entries」）、決定を変えない訂正はそれに当たらない。ずれを直す PR が同じ PR で消せば、ずれの記述が事実でない期間が生じない。
    -   **採らなかった案:** 訂正にも「経緯」の項目を足す案は、「経緯」の定義を変え、決定の変遷の中に書き方の直しが混ざるので採らない。書き直しを認めず、タスクごとの例外で扱い続ける案は、#729 のような見直しのたびに例外が要るので採らない。
    -   ADR：[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) を作る。ADR を変える PR の条件という、開発のプロセスの方針で、後のすべての PR を縛るため、`CLAUDE.md`「Design decisions (ADR)」の基準で major である。
-   **編集上の訂正は 3 種類とする:** (1) 「Writing an ADR」の基準に合わせる書き直し、(2) ずれが直った後のずれの記述の削除、(3) 古くなったリンク・名前・見出しへの参照の訂正である（F-003）。
    -   **理由:** (1) は #729 の見直しに、(2) は 0068・0069 が扱った場面に要る。(3) は、名前や見出しが変わるたびに、決定を下す PR を待たずに直せるようにするためである。どれも決定の内容を変えない。
    -   **採らなかった案:** (1) と (2) だけに限る案は、古くなったリンクを直すのにも決定を下す PR が要り、ADR に誤った参照が残るので採らない。
    -   ADR：[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) に含める。
-   **この主題の ADR として、ADR-0039 を新しく作る:** 主題は、ADR の「背景」と「決定」の書き方と、決定を変えない書き直しに限る。ADR の仕組み全体（0060 の決定）は、主題に含めない。
    -   **理由:** 書き方の基準は、後に ADR を書くすべてのタスクを縛るので、major である。主題を本 issue の範囲に限り、0060 の決定全体を ADR にする作業を持ち込まない。
    -   **採らなかった案:** ADR の仕組み全体の ADR を作る案は、issue の範囲を超えるので採らない。規約そのものが正本の文書なので ADR を作らない案は、正本の文書がある主題でも ADR が理由・採らなかった案・経緯を持つという規約の分担（`adr.md:124-130`）と合わないので採らない。
-   **CLAUDE.md は変えない:** 基準と書き直しの扱いは、規約だけに書く（F-004）。
    -   **理由:** CLAUDE.md「Design decisions (ADR)」は、決定を下す PR だけが ADR を変えるという文（`adr.md:218-219`）を持たない（`CLAUDE.md:124-130`）。ADR と正本の文書の分担の文（`CLAUDE.md:148-150`）は、ADR が正本を要約してリンクするとだけ述べ、新しい基準と食い違わない。規約が両方をそろえるよう求める文の意味は変わらないので、CLAUDE.md を変える理由がない。
    -   **採らなかった案:** CLAUDE.md の「Rule」の項目にも、書き直しを認める文を足す案は、同じ規則を 2 か所で持つことになり、そろえる手間が増えるので採らない。
    -   ADR：なし。規約の既存の分担を当てはめるだけで、本タスクの中で閉じる。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   ADR を書くエージェントと人が、規約だけを読んで、「背景」と「決定」に何を書き、何を書かないかを判断できるようにする。
-   決定を変えずに ADR の書き方を直す変更を、規約の例外を作らずに行えるようにする。

### 2.2. スコープ (In Scope)

-   `docs/dev/conventions/adr.md` の「Writing an ADR」に、「背景」と「決定」の基準を足すこと（F-001・F-002）。
-   `docs/dev/conventions/adr.md` の「Approval and the PR」と「History entries」に、決定を変えない編集上の訂正の扱いを足すこと（F-003）。
-   この主題の ADR として、ADR-0039 と索引の行を本書の PR で足すこと（`.claude/commands/_lib/settle-decisions.md` の手順による）。

### 2.3. スコープ外 (Out of Scope)

-   **既存の ADR の見直し。** ADR-0001〜0030 は [#729](https://github.com/isseis/yt2column/issues/729) で見直す。ADR-0031〜0038 は、PR #727 でこの基準に合わせて書かれたので、本タスクでは見直さない。
-   **CLAUDE.md の変更。** 1 章の「要件定義の際に決めたこと」の 4 つ目の項目のとおりである。
-   **ADR の仕組み全体（0060 の決定）を ADR にすること。** 同じく 3 つ目の項目のとおりである。
-   **0068・0069 のタスク文書の変更。** 両タスクが規約の例外として決めたことは、タスク文書の変わらない記録として残す。
-   **「Writing an ADR」の、「状態」「採らなかった案」「結果」「経緯」の項目と、「Links」の段落の内容の変更。** issue が求めるのは「背景」と「決定」の基準だからである。ただし、F-003 が求める「History entries」への追記は含む。
-   **`requirements_process.md` の変更。** 編集上の訂正の記録の形は、同書「Recording in the PR description」をそのまま参照する。
-   **基準に合っているかを確かめるテスト。** 基準は文の意味についての規則で、文書のテストは文の意味を確かめない（`CLAUDE.md`「Testing Strategy」の「Document tests check values, structure, and executable examples, never prose」、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。

## 3. 機能要件 (Functional Requirements)

本章の「規約」は `docs/dev/conventions/adr.md` を指す。各受け入れ基準は、規約が述べる内容を定め、PR のレビューで規約を読んで確かめる。

### 3.1. 機能一覧

#### F-001: 「背景」の基準

規約の「Writing an ADR」が、「背景」に書くものと書かないものを述べる。

**Acceptance Criteria**:
- **AC-01**: 規約は、「背景」には、決定が答えている問題と、決定を縛る前提だけを書く、と述べる。
- **AC-02**: 規約は、前の規則の中身、調査の数字、規則の由来を、決定の根拠そのものでない限り「背景」に書かない、と述べる。前の決定は「経緯」に、退けた形は「採らなかった案」に置く、と述べる。
- **AC-03**: 規約は、決定の根拠になる数字は「背景」に残す、と述べる。ADR-0038 の「背景」の、`-race` 付きのビルドで解析が約 23〜31 倍遅くなるという数字のような例を、規約が添えるかどうかは設計で決める。

#### F-002: 「決定」の基準

規約の「Writing an ADR」が、「決定」に書くものと書かないものを述べる。今の「決定」の項目が述べる 2 つの規則（今効いている決定だけを書き、前の決定は「経緯」に置くこと、正本の文書がある主題では要約してリンクすること）は、意味を変えずに残す。

**Acceptance Criteria**:
- **AC-04**: 規約は、「決定」には、後の変更が守るべき規則を 1 項目ずつ書く、と述べる。各項目には、短い理由と、正本の文書かコードの場所を添える、と述べる。
- **AC-05**: 規約は、正本の文書が持つ一覧（構文の一覧、例外の一覧など）を「決定」に書き写さない、と述べる。
- **AC-06**: 規約は、腐りやすい実装の細部（関数の呼び出しの順序、呼び出し箇所の列挙、手順の細部など）を「決定」に書かない、と述べる。
- **AC-07**: 規約は、正本の文書とコードのずれの記述と、そのずれを扱う issue へのリンクは「決定」に残す、と述べる。
- **AC-08**: 規約の「決定」の項目は、今効いている決定だけを書き、前の決定は「経緯」に置くことと、正本の文書がある主題では仕様を書き写さずに要約してリンクすることを、今と同じ意味で述べ続ける。

#### F-003: 決定を変えない編集上の訂正

規約の「Approval and the PR」と「History entries」が、決定を変えずに ADR を直す変更の扱いを述べる。

**Acceptance Criteria**:
- **AC-09**: 規約は、ADR の決定を下しも変えもしない PR も、ADR に編集上の訂正を加えてよい、と述べる。編集上の訂正は、次の 3 種類だけである、と述べる。
  1.  「Writing an ADR」の基準に合わせる書き直し。
  2.  ずれが直った後の、ずれの記述の削除。
  3.  古くなったリンク・名前・見出しへの参照の訂正。
- **AC-10**: 規約は、編集上の訂正が ADR の決定の内容を変えない、と述べる。「決定」の意味を変える変更は編集上の訂正ではなく、決定を下すか変える PR だけが行う、という今の規則がそのまま効く、と述べる。
- **AC-11**: 規約は、編集上の訂正を、その変更を行うコミットのメッセージと PR の説明に記録する、と述べる。記録の形は、`docs/dev/conventions/requirements_process.md` の「Recording in the PR description」の訂正の行と訂正の段落とし、何を何に変えたかと、決定を変えないことを記す、と述べる。PR のレビュアーが分類に異を唱えられるように、PR の説明で編集上の訂正であると明示する、と述べる。
- **AC-12**: 規約の「History entries」は、編集上の訂正では「経緯」に項目を足さない、と述べる。
- **AC-13**: 規約は、ずれの記述を、正本の文書かコードのずれを直す PR が、同じ PR で消す、と述べる。
- **AC-14**: 規約の「Approval and the PR」の、ADR は決定を下すか変える PR 以外では追加も変更もされない、という文は、AC-09 の編集上の訂正を除く形に改まっている。ADR の追加は、決定を下す PR だけが行う、という意味は変わらない。

#### F-004: 変えないもの

**Acceptance Criteria**:
- **AC-15**: 本タスクの実装の PR は、`CLAUDE.md` を変えない。
- **AC-16**: 本タスクの実装の PR の後も、規約の「Template」「Status」「Index」の節は、見出しと、それぞれが持つ 1 つのコードブロックか表を変えずに持つ。`TestADRRecords` がこれらの節を見出しで探して読むためである（`docs/dev/conventions/adr.md:17-21`）。
- **AC-17**: 規約の「Writing an ADR」と「Approval and the PR」は、CLAUDE.md と同じ文で持つ部分を変えたときは両方をそろえる、という指示（`docs/dev/conventions/adr.md:138-141`・`:221-222`）を、今と同じ意味で持ち続ける。

## 6. 用語集 (Glossary)

用語は `docs/translation_glossary.md` と統一する。

-   **正本の文書:** ある主題の今の仕様を持つ文書（`CLAUDE.md`「Design decisions (ADR)」の "a document that holds the current specification"）。例は `docs/dev/security.md` と `docs/dev/production_profile.md` である。
-   **ずれの記述:** ADR の「決定」にある、正本の文書とコードが食い違っていることと、それを扱う issue を述べる記述。例は ADR-0029 の「決定」の最後の項目（`docs/dev/adr/0029-extension-ui-languages.md:24`）である。
-   **編集上の訂正:** 決定の内容を変えずに ADR を直す変更。F-003 の 3 種類に限る。タスク文書の editorial correction（`requirements_process.md`「Editorial correction」）と同じ語を使う。
-   **腐りやすい実装の細部:** コードの変更で、決定が変わらなくても古くなる記述。関数の呼び出しの順序、呼び出し箇所の列挙、手順の細部などである。
