## 1. 概要 (Overview)

**目的:** 本書は、ADR の規約 `docs/dev/conventions/adr.md` に、ADR の「背景」と「決定」に何をどの詳細度で書くかの基準を足すための要件を定義する。あわせて、決定を変えずに ADR を直す PR の扱いを定める（[#728](https://github.com/isseis/yt2column/issues/728)）。

**背景:**

ADR は、後の開発者が、変えようとしている主題の決定とその理由を知るために読む文書である。規約の「Writing an ADR」は、各節の用途を 1 行ずつ述べるだけである。「背景」は、主題に決定が要る理由と、決定を縛る前提とだけ述べる（`docs/dev/conventions/adr.md:122-123`）。「決定」は、今効いている決定だけを書き、正本の文書がある主題では仕様を書き写さずに要約してリンクする、と述べる（`docs/dev/conventions/adr.md:124-130`）。どちらの節にも、何をどの詳細度で書くかの基準はない。issue #728 は、そのために背景には過去の規則の経緯や調査の数字が時系列で並びやすく、決定には正本の文書の一覧の写しや、腐りやすい実装の細部が入りやすいと述べる。

タスク 0065 の最後の PR（[#727](https://github.com/isseis/yt2column/pull/727)）では、レビュアーと基準を決め、ADR-0031〜0038 の「背景」と「決定」をそれに合わせて書き直した。この基準を記録しているのは、その PR の説明（「レビュアーと決めた書き直し（PR を作った後）」）と issue #728 だけで、規約には入っていない。

規約の「Approval and the PR」は、ADR を追加・変更するのは、その決定を下すか変える PR だけだと述べる（`docs/dev/conventions/adr.md:215-219`）。そのため、決定を変えずに ADR を直すだけの PR は、文字どおりには認められない。そうした変更は、すでに次のように必要になっている。

-   タスク 0068 は、ADR-0020 の「決定」にある、`package_reference.md` の一覧に 4 つのパッケージがないことを #713 で扱うとする記述（以下「ずれの記述」）を、一覧を直す実装の PR で消すと決めた。その PR は「結果」に 1 文と「経緯」に 1 項目を足して ADR-0020 を変えるので、「Approval and the PR」に収まると判断している（`docs/tasks/0068_strictjson_package_reference/01_requirements.md:44`、AC-13〜AC-15）。
-   タスク 0069 は、ADR-0029 のずれの記述を、README を直す実装の PR が消すと決めた。その PR は ADR の決定を変えないので、規約の例外とし、その 1 回の削除に限っている。経緯の項目は足さず、編集上の修正としてコミットメッセージと PR の説明に記す（`docs/tasks/0069_readme_display_language/01_requirements.md:57-63`、AC-10）。
-   後続の [#729](https://github.com/isseis/yt2column/issues/729) は、ADR-0001〜0030 を本タスクの基準で見直す。見直しは決定を変えないので、今の規約では行えない。

規約には、すでに 1 つ、ADR の編集上の訂正がある。`main` を取り込んで番号だけがぶつかったときの ADR の番号の付け替えで、コミットメッセージに編集上の訂正として記録する（`docs/dev/conventions/adr.md:232-238`「Taking in `main`」の手順 2）。また、`main` の上で `TestADRRecords` が失敗したときの直しは、その直しだけの PR で行う。関係のない PR のレビュアーは、ADR の変更を承認する立場にないからである（`docs/dev/conventions/adr.md:244-248`。0060 の設計による。`docs/tasks/0060_adr_records/02_architecture.md:260`）。

タスク文書については、決定を変えない編集上の訂正を、コミットメッセージの訂正の行と PR の説明の訂正の段落に記録し、変更履歴には記録しないことが定まっている（`docs/dev/conventions/requirements_process.md:49-61`「Editorial correction」、同書 377 行からの「Recording in the PR description」）。その記録の形と、それを運ぶコマンドの定義（`.claude/commands/fixpr.md:484-486`、`.claude/commands/_lib/local-cli-review.md:234`）は、タスク文書だけを対象にしている。ADR の「経緯」は、決定を下したときと変えたときに 1 項目ずつ足す、と定まっている（`docs/dev/conventions/adr.md:167-169`「History entries」）。

ADR の仕組みそのもの（タスク 0060 が決めた、生きた文書としての ADR、状態、規約）を主題とする ADR はない（`docs/dev/adr/README.md` の表）。0060 の決定は、0060 のタスク文書に記録されている（`docs/tasks/0060_adr_records/01_requirements.md`「要件定義の際に決めたこと（2026-11-04）」）。そのうち、ADR についての記録の置き場所は、[ADR-0036](../../dev/adr/0036-task-document-status-records.md) の「決定」の 1 つ目の項目が扱う。

**軽量プロセスを取らない理由:** この変更は `docs/dev/conventions/` の規則を足し、意味を変える。`docs/dev/conventions/` では誤字の修正だけが軽量プロセスに当たり、ほかの変更は通常プロセスになる（`docs/dev/conventions/requirements_process.md`「Changes that always take the normal process」）。

対応 issue: [#728](https://github.com/isseis/yt2column/issues/728)（関連: [#729](https://github.com/isseis/yt2column/issues/729)、タスク 0065 の [#666](https://github.com/isseis/yt2column/issues/666) と [#727](https://github.com/isseis/yt2column/pull/727)、[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md)（ADR の背景と決定の書き方と、決定を変えない編集上の訂正）、[ADR-0036](../../dev/adr/0036-task-document-status-records.md)）

**本書の記述範囲:** 本書は、規約が述べる基準の内容と、決定を変えない編集上の訂正の扱いを定める。規約の英語の文面と、基準を「Writing an ADR」のどこにどう置くかは、`02_architecture.md` で決める（[design_handoff.md](design_handoff.md)）。

**要件定義の際に決めたこと（2026-11-09）:**

-   **決定を変えずに ADR を直すことを、編集上の訂正として認める:** ADR に編集上の訂正を加えてよい PR を、決定を下すか変える PR に限らない。決定を下しも変えもしない PR も、ほかの ADR の決定を変える PR も、加えてよい。訂正は、コミットメッセージと PR の説明に記録し、「経緯」に項目を足さない。ずれの記述は、ずれを直す PR が同じ PR で消す（F-003）。
    -   **理由:** タスク文書の編集上の訂正（`requirements_process.md`「Editorial correction」）と、ADR の番号の付け替え（`adr.md`「Taking in `main`」の手順 2）と同じ記録の置き場所になる。0069 が作った例外も、この形だった。「経緯」は決定を下したときと変えたときの記録で（`adr.md`「History entries」）、決定を変えない訂正はそれに当たらない。ずれを直す PR が同じ PR で消せば、ずれの記述が事実でない期間が生じない。
    -   **採らなかった案:** 訂正にも「経緯」の項目を足す案は、「経緯」の定義を変え、決定の変遷の中に書き方の直しが混ざるので採らない。決定を変えない直しを認めず、タスクごとの例外で扱い続ける案は、#729 のような見直しのたびに例外が要るので採らない。
    -   ADR：[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) を作る。ADR を変える PR の条件という、開発のプロセスの方針で、後のすべての PR を縛るため、`CLAUDE.md`「Design decisions (ADR)」の基準で major である。
-   **編集上の訂正は 3 種類とする:** (1) 「Writing an ADR」の基準に合わせる書き直し、(2) ずれが直った後のずれの記述の削除か、一部が直った後の残りのずれへの書き換え、(3) 古くなったリンク・名前・見出しへの参照の訂正である（F-003）。`main` を取り込むときの番号の付け替えは、「Taking in `main`」の手順 2 が定める別の訂正として、今のまま残す。
    -   **理由:** (1) は #729 の見直しに、(2) は 0068・0069 が扱った場面に要る。(3) は、名前や見出しが変わるたびに、決定を下す PR を待たずに直せるようにするためである。どれも決定の内容を変えない。
    -   **採らなかった案:** (1) と (2) だけに限る案は、古くなったリンクを直すのにも決定を下す PR が要り、ADR に誤った参照が残るので採らない。
    -   ADR：[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) に含める。
-   **この主題の ADR として、ADR-0039 を新しく作り、ADR-0036 から ADR-0039 へリンクする:** ADR-0039 の主題は、ADR の「背景」と「決定」の書き方と、ADR を変えてよい PR の条件（決定を下すか変える PR と、編集上の訂正）に限る。0060 の決定のうち、ADR の状態、置き場所と名前、索引、経緯の書き方、廃止と取り下げは、主題に含めない。ADR-0036 は、ADR についての記録の置き場所を述べる項目に、ADR の編集上の訂正の記録が ADR-0039 にあることを 1 文足し、「経緯」に 1 項目足す（ADR の判断：ADR-0036 を更新する）。
    -   **理由:** 書き方の基準は、後に ADR を書くすべてのタスクを縛るので、major である。主題を本 issue の範囲に限り、0060 の決定全体を ADR にする作業を持ち込まない。ADR-0036 は ADR の記録の置き場所に触れるので、重なる主題として互いにリンクする（`adr.md:38-40`）。
    -   **採らなかった案:** ADR の仕組み全体の ADR を作る案は、issue の範囲を超えるので採らない。規約そのものが正本の文書なので ADR を作らない案は、正本の文書がある主題でも ADR が理由・採らなかった案・経緯を持つという規約の分担（`adr.md:124-130`）と合わないので採らない。
-   **CLAUDE.md は変えない:** 基準と編集上の訂正の扱いは、規約だけに書く（F-004）。
    -   **理由:** CLAUDE.md「Design decisions (ADR)」は、決定を下す PR だけが ADR を変えるという文（`adr.md:218-219`）を持たない（`CLAUDE.md:124-129`）。ADR と正本の文書の分担の文（`CLAUDE.md:148-150`）は、ADR が正本を要約してリンクするとだけ述べ、新しい基準と食い違わない。規約が両方をそろえるよう求める文の意味は変わらないので、CLAUDE.md を変える理由がない。
    -   **採らなかった案:** CLAUDE.md の「Rule」の項目にも、編集上の訂正を認める文を足す案は、同じ規則を 2 か所で持つことになり、そろえる手間が増えるので採らない。
    -   ADR：なし。規約の既存の分担を当てはめるだけで、本タスクの中で閉じる。
-   **コマンドの定義と `requirements_process.md` は変えない:** ADR の編集上の訂正の記録は、規約が、`requirements_process.md`「Recording in the PR description」の訂正の行と訂正の段落の形を ADR のパスにも当てはめると述べ、エージェントがその形で書く。`/fixpr`・`/runplan`・ローカルの CLI レビューの記録の手順を ADR に広げることは、別の issue にする（2.3）。
    -   **理由:** 本タスクの範囲を規約に保つためである。コマンドの定義には文書のテストがあり、広げると変更とレビューの範囲が大きくなる。
    -   **採らなかった案:** 本タスクでコマンドの定義と `requirements_process.md` も変える案は、範囲が広がるので採らない。
    -   ADR：ADR-0039 の「結果」に、コマンドがまだ ADR の訂正を運ばないことを書く。
-   **`main` の上のガードの失敗の直しは、今のまま、その直しだけの PR で行う:** 規約の該当の段落（`adr.md:244-248`）は、番号を付け替える直しを対象とすることを明示する。編集上の訂正は、番号も決定も変えないので、どの PR でも行えることと矛盾しない（F-003）。
    -   **理由:** 番号の付け替えは ADR の識別子を変え、ほかの文書の参照にも及ぶ。編集上の訂正では、レビュアーが確かめるのは決定が変わらないことだけである。
    -   **採らなかった案:** 番号の付け替えの直しもどの PR でも行えるようにする案は、0060 の設計の理由を覆すので採らない。
    -   ADR：ADR-0039 に含める。
-   **基準に合わせる書き直しは、ADR の中で記述を別の節へ移すことを含む:** ADR かその出典の文書にすでにある内容を、別の節（「経緯」「採らなかった案」「結果」など）へ移してよい。新しい事実は足さない。出典に理由がない「決定」の項目には、「採らなかった案」と同じく `理由は記録されていない` と書く。題名の意味を変えない書き直しは認め、索引の行を同じ PR でそろえる（F-003）。
    -   **理由:** #729 の見直しでは、「背景」から前の決定を除くと、それを「経緯」か「採らなかった案」へ移す必要がある。理由を補って書くと、出典にない決定の根拠を作ることになる。
    -   **採らなかった案:** 同じ節の中の書き直しだけに限り、節をまたぐ移動と題名の変更を認めない案は、#729 で基準に合わせられない ADR が残るので採らない。
    -   ADR：ADR-0039 に含める。
-   **紛らわしい場合の扱い:** 同じ PR が ADR の決定を変え、同じ ADR に編集上の訂正も加えるときは、決定の変更を「経緯」に、訂正をコミットメッセージと PR の説明に記録する。PR のレビュアーが分類に異を唱えたときは、その変更を決定の変更として扱い、「経緯」の項目と ADR の判断を加える。`廃止` の ADR にも同じ規則を当てはめる。決定を変える PR が基準より前に書かれた ADR に触れるとき、その PR が基準に合わせるのは、自分が変える部分だけでよい（F-003）。
    -   **理由:** 記録の置き場所を、変更ごとの性質で決めるためである。分類を争う変更は、決定の変更として扱うほうが記録を失わない。ADR の全体の見直しは #729 のような作業で行い、決定を変える PR の範囲を広げない。
    -   **採らなかった案:** 決定を変える PR が、触れた古い ADR の全体を基準に合わせる案は、その PR の範囲とレビューを広げるので採らない。
    -   ADR：ADR-0039 に含める。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

-   **ADR-0039 の経緯は、0060・0065・0070 の 3 項目とする:**
    -   0060 は、「決定」は正本を要約してリンクし、ADR を作るか更新する PR はその決定を下すか変える PR であると決めた（2026-11-04。0060 の要件定義書の「要件定義の際に決めたこと（2026-11-04）」と F-003）。
    -   0065 は、ADR の「決定」に正本の表・列挙・規則の一覧を書き写さないことと、正本とコードのずれを issue にしてリンクすることを、設計原則とした（2026-11-06。0065 の設計書の「1.1. 設計原則」。節の見出しに日付がないので、承認の日付による）。
    -   本タスクは、基準と編集上の訂正の扱いを規約に足す（2026-11-09）。
    -   PR #727 でレビュアーと決めた基準は、PR の説明にだけ記録されている。本書の「issue #728 で決めたこと」がその記録になるので、本タスクの項目に含める。ADR-0039 の 2026-11-09 の項目の出典は、この扱いによる。
-   **ずれの記述の扱いの細部:**
    -   ずれを直す PR より後に、ずれの記述を持つ ADR が `main` に入るときは、その ADR の PR が `main` を取り込んだときに消す。
    -   ずれの一部だけが直ったときは、残りのずれを述べる形に書き換える。
    -   ずれの記述は扱う issue へリンクするので、ずれを直す PR は、その issue へのリンクを `docs/dev/adr/` で探して見つける（探し方は設計で決める。[design_handoff.md](design_handoff.md) H-03）。後から `main` に入る ADR の PR が、ずれが直ったことに気づく手がかりも設計で決める（H-05）。
-   **ADR-0039 自身のずれ:** ADR-0039 は本書の PR で `有効` になるが、規約は実装の PR まで基準も編集上の訂正の規則も述べない。ADR-0039 の「決定」の、規則を規約に足すことを #728 で扱うとする各項目の記述がこのずれで、実装の PR がそれらを規約の節へのリンクに置き換える（F-004 の AC-23）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   ADR を書くエージェントと人が、規約だけを読んで、「背景」と「決定」に何を書き、何を書かないかを判断できるようにする。
-   決定を変えずに ADR を直す変更を、規約の例外を作らずに行えるようにする。

### 2.2. スコープ (In Scope)

-   `docs/dev/conventions/adr.md` の「Writing an ADR」に、「背景」と「決定」の基準を足すこと（F-001・F-002）。
-   `docs/dev/conventions/adr.md` の「Approval and the PR」「History entries」「Taking in `main`」に、決定を変えない編集上の訂正の扱いを足し、`main` の上のガードの失敗の段落の対象を明示すること（F-003）。どの節に何を置くかは設計で決める。
-   この主題の ADR として、ADR-0039 と索引の行を足し、ADR-0036 から ADR-0039 へリンクすること。本書の PR で行う（`.claude/commands/_lib/settle-decisions.md` の手順による）。
-   実装の PR で、ADR-0039 のずれの記述を消すこと（F-004）。

### 2.3. スコープ外 (Out of Scope)

-   **既存の ADR の見直し。** ADR-0001〜0030 は [#729](https://github.com/isseis/yt2column/issues/729) で見直す。ADR-0031〜0038 は、PR #727 でこの基準に合わせて書かれたので、本タスクでは見直さない。
-   **CLAUDE.md の変更。** 1 章の「要件定義の際に決めたこと」のとおりである。
-   **コマンドの定義（`.claude/commands/`）と `requirements_process.md` の変更。** 同じく 1 章のとおりである。ADR の編集上の訂正を `/fixpr`・`/runplan`・ローカルの CLI レビューの記録の手順に広げることは、本書の PR を開くときに別の issue にする。
-   **ADR の仕組み全体（0060 の決定）を ADR にすること。** 同じく 1 章のとおりである。
-   **0068・0069 のタスク文書の変更。** 両タスクが決めたことは、タスク文書の変わらない記録として残す。
-   **「Writing an ADR」の、「状態」「採らなかった案」「結果」「経緯」の項目と、「Links」の段落の内容の変更。** issue が求めるのは「背景」と「決定」の基準だからである。ただし、F-003 が求める「History entries」への追記は含む。
-   **軽量プロセスの条件の変更。** ADR の編集上の訂正が軽量プロセスを取れるかどうかは、今の条件（`requirements_process.md`「Lightweight Process」）のとおりに決まる。
-   **基準に合っているかを確かめるテスト。** 基準は文の意味についての規則で、文書のテストは文の意味を確かめない（`CLAUDE.md`「Testing Strategy」の「Document tests check values, structure, and executable examples, never prose」、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。

## 3. 機能要件 (Functional Requirements)

本章の「規約」は `docs/dev/conventions/adr.md` を指す。各受け入れ基準は、実装の PR の後に規約が述べる内容を定め、PR のレビューで規約を読んで確かめる。

### 3.1. 機能一覧

#### F-001: 「背景」の基準

規約の「Writing an ADR」が、「背景」に書くものと書かないものを述べる。

**Acceptance Criteria**:
- **AC-01**: 規約は、「背景」には、決定が答えている問題と、決定を縛る前提だけを書く、と述べる。
- **AC-02**: 規約は、前の規則の中身、調査の数字、規則の由来を、決定の根拠そのものでない限り「背景」に書かない、と述べる。前の決定は「経緯」に、退けた形は「採らなかった案」に置く、と述べる。
- **AC-03**: 規約は、決定の根拠になる数字は「背景」に残す、と述べる。ADR-0038 の「背景」の、`-race` 付きのビルドで解析が約 23〜31 倍遅くなるという数字のような例を規約が添えるかどうかは、設計で決める（[design_handoff.md](design_handoff.md) H-04）。

#### F-002: 「決定」の基準

規約の「Writing an ADR」が、「決定」に書くものと書かないものを述べる。

**Acceptance Criteria**:
- **AC-04**: 規約は、「決定」には、後の変更が守るべき規則を 1 項目ずつ書く、と述べる。各項目には、短い理由と、正本の文書かコードの場所を添える、と述べる。出典に理由がない項目には `理由は記録されていない` と書き、理由を補わない、と述べる。
- **AC-05**: 規約は、正本の文書が持つ一覧（構文の一覧、例外の一覧など）を「決定」に書き写さない、と述べる。
- **AC-06**: 規約は、腐りやすい実装の細部（関数の呼び出しの順序、呼び出し箇所の列挙、手順の細部など）を「決定」に書かない、と述べる。
- **AC-07**: 規約は、正本の文書とコードのずれの記述と、そのずれを扱う issue へのリンクは「決定」に残す、と述べる。
- **AC-08**: 規約の「決定」の項目は、今効いている決定だけを書き、前の決定は「経緯」に置くことと、正本の文書がある主題では仕様を書き写さずに要約してリンクすることを、今と同じ意味で述べ続ける。

#### F-003: 決定を変えない編集上の訂正

規約の「Approval and the PR」と「History entries」が、決定を変えずに ADR を直す変更の扱いを述べる。

**Acceptance Criteria**:
- **AC-09**: 規約は、どの PR も（ADR の決定を下しも変えもしない PR を含む）、ADR に編集上の訂正を加えてよい、と述べる。その編集上の訂正は、次の 3 種類だけである、と述べる。「Taking in `main`」の手順 2 の番号の付け替えは、この 3 種類とは別の訂正として残る、と述べる（AC-19）。
  1.  「Writing an ADR」の基準に合わせる書き直し。
  2.  ずれが直った後のずれの記述の削除と、一部が直った後の、残りのずれを述べる形への書き換え。
  3.  古くなったリンク・名前・見出しへの参照の訂正。
- **AC-10**: 規約は、1 つ目の書き直しが、ADR かその出典の文書にすでにある内容を別の節へ移すことを含み、新しい事実を足さないと述べる。題名の意味を変えない書き直しを含み、そのときは索引の行を同じ PR でそろえる、と述べる。
- **AC-11**: 規約は、編集上の訂正が ADR の決定の内容を変えない、と述べる。「決定」の意味を変える変更は編集上の訂正ではなく、決定を下すか変える PR だけが行う、という今の規則がそのまま効く、と述べる。
- **AC-12**: 規約は、編集上の訂正を、その変更を行うコミットのメッセージと PR の説明に記録する、と述べる。記録の形は、`docs/dev/conventions/requirements_process.md` の「Recording in the PR description」の訂正の行と訂正の段落とし、その形を ADR のパスにも当てはめる、と述べる。訂正の行には、何を何に変えたかと、決定を変えないことを記す。PR のレビュアーが分類に異を唱えられるように、PR の説明で編集上の訂正であると明示する、と述べる。
- **AC-13**: 規約の「History entries」は、編集上の訂正では「経緯」に項目を足さない、と述べる。
- **AC-14**: 規約は、ずれの記述を、ずれを直す PR が同じ PR で消す（一部だけを直すときは、残りのずれを述べる形に書き換える）、と述べる。ずれを直す PR より後に、ずれの記述を持つ ADR が `main` に入るときは、その ADR の PR が `main` を取り込んだときに消す、と述べる。
- **AC-15**: 規約は、同じ PR が ADR の決定を変え、同じ ADR に編集上の訂正も加えるときは、決定の変更を「経緯」に、訂正をコミットメッセージと PR の説明に記録する、と述べる。
- **AC-16**: 規約は、PR のレビュアーが編集上の訂正という分類に異を唱えたときは、その変更を決定の変更として扱い、「経緯」の項目と ADR の判断を加える、と述べる。
- **AC-17**: 規約は、`廃止` の ADR にも同じ規則を当てはめる、と述べる。決定を変える PR が基準より前に書かれた ADR に触れるとき、その PR が基準に合わせるのは自分が変える部分だけでよい、と述べる。
- **AC-18**: 規約の「Approval and the PR」の、ADR は決定を下すか変える PR 以外では追加も変更もされない、という文は、編集上の訂正を除く形に改まっている。ADR の追加は、決定を下す PR だけが行う、という意味は変わらない。
- **AC-19**: 規約の「Taking in `main`」の手順 2 の番号の付け替えは、今と同じ意味で、編集上の訂正として記録する、と述べ続ける。同じ節の、`main` の上で `TestADRRecords` が失敗したときの段落は、番号の重複か欠けを直すその直しを、その直しだけの PR で行うと述べ続け、それが ADR の番号を付け替える直しを対象とし、AC-09 の編集上の訂正を対象としないことを明示する。

#### F-004: 変えないものと、ADR-0039 のずれ

**Acceptance Criteria**:
- **AC-20**: 本タスクの実装の PR は、`CLAUDE.md`、`.claude/commands/` の下のファイル、`docs/dev/conventions/requirements_process.md` を変えない。
- **AC-21**: 本タスクの実装の PR の後も、規約の「Template」「Status」「Index」の節は、見出しと、それぞれが持つ 1 つのコードブロックか表を変えずに持つ。`TestADRRecords` がこれらの節を見出しで探して読むためである（`docs/dev/conventions/adr.md:17-21`）。
- **AC-22**: 規約の「Writing an ADR」と「Approval and the PR」は、CLAUDE.md と同じ文で持つ部分を変えたときは両方をそろえる、という指示（`docs/dev/conventions/adr.md:138-141`・`:221-222`）を、今と同じ意味で持ち続ける。
- **AC-23**: 実装の PR の後、ADR-0039 の「決定」は、その規則のどれか（背景と決定の基準、編集上の訂正、ずれの記述の削除）が規約にまだないと述べる記述と、それを扱う issue として #728 へリンクする記述を持たない。規則の置き場所は、規約の節へのリンクで示す。この削除は、AC-14 のずれの記述の削除として、AC-12 の形で記録する。

## 6. 用語集 (Glossary)

用語は `docs/translation_glossary.md` と統一する。

-   **正本の文書:** ある主題の今の仕様を持つ文書（`CLAUDE.md`「Design decisions (ADR)」の "a document that holds the current specification"）。例は `docs/dev/security.md` と `docs/dev/production_profile.md` である。
-   **ずれの記述:** ADR の「決定」にある、正本の文書とコードが食い違っていることと、それを扱う issue を述べる記述。例は、ADR-0029 の「決定」の最後の項目の 2 文目以降（`docs/dev/adr/0029-extension-ui-languages.md:24`）である。
-   **編集上の訂正:** 決定の内容を変えずに ADR を直す変更（英語では editorial correction。タスク文書の `requirements_process.md`「Editorial correction」と同じ語）。決定を下しも変えもしない PR が加えてよいものは、F-003 の 3 種類に限る。0069 の文書は「編集上の修正」と呼ぶが、同じものを指す。
-   **基準に合わせる書き直し:** 編集上の訂正の 1 つ目の種類。「書き直し」は、本書ではこの意味だけに使う。
-   **腐りやすい実装の細部:** コードの変更で、決定が変わらなくても古くなる記述。関数の呼び出しの順序、呼び出し箇所の列挙、手順の細部などである。
