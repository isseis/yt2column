# 設計への申し送り

要件定義の過程で挙がった、設計（`02_architecture.md`）で扱う事項である。`02_architecture.md` は、各項目の扱い（採った手段、または当たらない理由）を記録する。

## H-01: 0090 設計書を正本として参照し、本タスクの設計は差分だけを決める

**懸念:** 0090 設計書は、記事生成モジュールの関数、ジョブの記録、SW の調停、権限と CSP、状態の種類、撤去するものまで決めている。本タスクの `02_architecture.md` が同じ内容を写すと、2 つの設計書が食い違いうる。

**重要な理由:** 写した内容のどちらかだけが直されると、実装の正本が分からなくなる。

**候補の手段:** 0090 設計書の節を正本として参照し、本タスクの設計は、0090 設計書が決めていない事項（ファイルの分け方、PR の区切りの前提になる依存、ビルドタグの付け方、本書で決めたポップアップのリンクとページのタイトルの置き場所）と、0090 設計書の手段を変える箇所だけを決める。変える箇所は、0090 設計書の節と、変える理由を挙げる。

**関連:** 01_requirements.md §5（0090 設計書を手段と値の正本とする制約）

## H-02: `internal/config` を WASM でビルドできるようにする方法

**懸念:** 今の `internal/config` は、`//go:build unix` だけの `internal/privatefile` を import するので、`GOOS=js` でビルドできない（0090 設計書 §8 の 1）。0090 設計書は、サーバとホストの設定の読み込みのファイルに `!js` のビルドタグを付ける案と、記事生成モジュール用の関数を `privatefile` に依存しない場所に置く案を挙げ、どちらにするかを決めていない。

**重要な理由:** サーバを撤去する前の PR で記事生成モジュールをビルドするには、どちらかが要る。撤去の PR でタグを外し忘れると、使われないビルドタグが残る。

**候補の手段:** 撤去の前の PR でタグを付け、撤去の PR でサーバとホストの読み込みとともにタグを除く。撤去の PR の完了の条件に、タグが残らないことを入れる。

**関連:** AC-27・AC-30

## H-03: 今のサーバと同じ値を返すことを、サーバを撤去する前に確かめる

**懸念:** AC-19 は、無効化した表示用の Markdown、保存するファイルのバイト列、推定の料金が、今のサーバと同じ値になることを求める。サーバを撤去した後は、比べる相手がない。

**重要な理由:** 撤去と同じ PR で比べるテストを書くと、今のサーバのテストの行を引き継いだかどうかを、レビューで確かめにくい。

**候補の手段:** `internal/server` の `request_test.go`・`status_test.go` の行を、サーバを撤去する前の PR で `internal/extjob` のテストに写し、両方が同じ行で通ることを確かめてから、撤去の PR でサーバのテストを削除する。削除はカバレッジの比較の手順に従う。

**関連:** AC-19・AC-27・AC-30

## H-04: ポップアップのオプションページへのリンクの置き場所と名前

**懸念:** ポップアップは、いつもオプションページへのリンクを持つ（AC-06）。今のポップアップは、動画、確認、拒否、操作、詳細の節を持つ（`extension/static/popup.html:10-18`）。リンクをどこに置くか、主ボタンとの関係、アクセシブルな名前を決めていない。

**重要な理由:** 押せる領域の大きさ（44×44 CSS ピクセル）とフォーカスの順（AC-18）を満たしつつ、主ボタンの操作と紛れないようにする必要がある。API キーがないときの目立つ操作と、いつもあるリンクが二重に並ぶことにもなる。

**候補の手段:** リンクを詳細の節の後に置き、`chrome.runtime.openOptionsPage` で開く。API キーがないときの操作は、状態の表示の中に置く。

**関連:** AC-06・AC-18

## H-05: 記録がないビューアのページのタイトル

**懸念:** AC-16 は、ブラウザを起動し直してビューアを復元した後も、履歴の項目の動画のタイトルが失われないことを求める。復元したビューアはジョブの記録を持たない（記事が失われた状態）ので、固定のタイトルを出すと、履歴の項目のタイトルを上書きしうる（0090 設計書 §3.13）。

**重要な理由:** 上書きされるかどうかは確かめていない。上書きされると、履歴から記事を作り直す手がかりが失われる。

**候補の手段:** `viewer.html` の静的なタイトル（今は `yt2column`。`extension/static/viewer.html:5`）を空にするか除き、記録がないときはページのタイトルを書き換えない（0090 設計書 §3.13 の「空のままにするなど」）。手動の確認で上書きされると分かったら、同じ節の「見込みが外れたときに変わる決定」に従う。

**関連:** AC-16

## H-06: 開発用のビルドで出せない状態を、単体テストで出す方法

**懸念:** 結果不明（60 秒たっても予約の結果がない）、入力を受け取れなかった、完成したが保持できなかった（`chrome.storage.session` への書き込みの失敗）、開始が拒否された（上限、Worker の読み込みの失敗）は、fake の LLM のシナリオでは出せない（AC-29）。

**重要な理由:** これらの状態の表示と文言（AC-14・AC-15）を確かめる手段が、単体テストだけになる。

**候補の手段:** SW とビューアのテストで、`chrome.storage`・`chrome.tabs`・Port・Worker の fake に、書き込みの失敗、応答の遅れ、読み込みの失敗を注入できるようにする。

**関連:** AC-14・AC-15・AC-29

## H-07: Worker から受け取る JSON の文字列の、重複したメンバの拒否

**懸念:** 記事生成モジュールの結果と進み具合は JSON の文字列で受け取る（0090 設計書 §3.1.2）。`JSON.parse` は重複したメンバを黙って後の値で上書きする。今の厳格な解析は、撤去する `extension/src/core/response.ts` が使っている。

**重要な理由:** 重複したメンバを拒否する規則（01_requirements.md §3.2）が、`JSON.parse` では満たせない。

**候補の手段:** 拡張に残る厳格な解析（`extension/src/core/strictJson.ts`）を使い、結果と進み具合とジョブの記録の読み戻しの検査に当てる。

**関連:** AC-20・01_requirements.md §3.2

## H-08: 予約の後に API キーがなかった記録の、料金の示し方

**懸念:** 予約の後、`generate` を呼ぶ前に API キーが消されていたときは、記録が `failed`（`api_key_missing`）になる（0090 設計書 §6.2）。この記録では LLM の API を呼んでいないが、0090 設計書 §3.8 の「API キーが設定されていない」の行は料金の示し方を書いていない。AC-11 が料金を不明と示す 3 つの状態にも当たらない。

**重要な理由:** 料金がかかっていないのに不明と示すか、何も示さないかで、表示が変わる。

**候補の手段:** API を呼んでいないので、料金に触れず、API キーの設定が要ることだけを示す。

**関連:** AC-06・AC-11
