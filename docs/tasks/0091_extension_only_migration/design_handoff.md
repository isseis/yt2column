# 設計への申し送り

要件定義の過程で挙がった、設計（`02_architecture.md`）で扱う事項である。`02_architecture.md` は、各項目の扱い（採った手段、または当たらない理由）を記録する。

## H-01: 0090 設計書を正本として参照し、本タスクの設計は差分だけを決める

**懸念:** 0090 設計書は、記事生成モジュールの関数、ジョブの記録、SW の調停、権限と CSP、状態の種類、撤去するものまで決めている。本タスクの `02_architecture.md` が同じ内容を写すと、2 つの設計書が食い違いうる。

**重要な理由:** 写した内容のどちらかだけが直されると、実装の正本が分からなくなる。

**候補の手段:** 0090 設計書の節を正本として参照し、本タスクの設計は、0090 設計書が決めていない事項（ファイルの分け方、PR の区切りの前提になる依存、ビルドタグの付け方、本書で決めたポップアップのリンクとページのタイトルの置き場所）と、0090 設計書の手段を変える箇所だけを決める。変える箇所は、0090 設計書の節と、変える理由を挙げる。本書が 0090 設計書から変えた点は、01_requirements.md §1 の「0090 設計書から変える点」の表にある。設計は、表の各行の扱いを記録する。

**関連:** 01_requirements.md §1（0090 設計書から変える点）・§5（0090 設計書を手段と値の正本とする制約）

## H-02: `internal/config` を WASM でビルドできるようにする方法

**懸念:** 今の `internal/config` は、`//go:build unix` だけの `internal/privatefile` を import するので、`GOOS=js` でビルドできない（0090 設計書 §8 の 1）。0090 設計書は、サーバとホストの設定の読み込みのファイルに `!js` のビルドタグを付ける案と、記事生成モジュール用の関数を `privatefile` に依存しない場所に置く案を挙げ、どちらにするかを決めていない。

**重要な理由:** サーバを撤去する前の PR で記事生成モジュールをビルドするには、どちらかが要る。撤去の PR でタグを外し忘れると、使われないビルドタグが残る。

**候補の手段:** 撤去の前の PR でタグを付け、撤去の PR でサーバとホストの読み込みとともにタグを除く。撤去の PR の完了の条件に、タグが残らないことを入れる。

**関連:** AC-27・AC-31

## H-03: 今のサーバと同じ値を返すことを、サーバを撤去する前に確かめる

**懸念:** AC-19 は、無効化した表示用の Markdown、保存するファイルのバイト列、推定の料金が、今のサーバと同じ値になることを求める。サーバを撤去した後は、比べる相手がない。

**重要な理由:** 撤去と同じ PR で比べるテストを書くと、今のサーバのテストの行を引き継いだかどうかを、レビューで確かめにくい。

**候補の手段:** `internal/server` の `request_test.go`・`status_test.go`・`generation_test.go` の行を、サーバを撤去する前の PR で `internal/extjob` のテストに写し、両方が同じ行で通ることを確かめてから、撤去の PR でサーバのテストを削除する。削除はカバレッジの比較の手順に従う。

**関連:** AC-19・AC-27・AC-31

## H-04: ポップアップのオプションページへのリンクの置き場所と名前

**懸念:** ポップアップは、いつもオプションページへのリンクを持つ（AC-06）。今のポップアップは、動画、確認、拒否、操作、詳細の節を持つ（`extension/static/popup.html:10-18`）。リンクをどこに置くか、主ボタンとの関係、アクセシブルな名前を決めていない。

**重要な理由:** 押せる領域の大きさ（44×44 CSS ピクセル）とフォーカスの順（AC-18）を満たしつつ、主ボタンの操作と紛れないようにする必要がある。API キーがないときの目立つ操作と、いつもあるリンクが二重に並ぶことにもなる。

**候補の手段:** リンクを詳細の節の後に置き、`chrome.runtime.openOptionsPage` で開く。API キーがないときの操作は、状態の表示の中に置く。

**関連:** AC-06・AC-18

## H-05: 記録がないビューアのページのタイトルと、履歴の項目の上書き

**懸念:** AC-16 は、記録がないビューアも空でない固定のタイトルを持ち、かつブラウザを再起動してビューアを復元した後も、履歴の項目の動画のタイトルが失われないことを求める。Chrome が同じ URL を開き直したときに履歴の項目のタイトルを書き換えるなら、固定のタイトルが動画のタイトルを上書きする（0090 設計書 §3.13）。上書きされるかどうかは確かめていない。

**重要な理由:** 上書きされるなら、AC-16 を満たすには、短く切った動画のタイトルを URL に加える必要がある（01_requirements.md §1「要件定義の際に決めたこと」）。これは 0090 設計書 §1.2 と ADR-0010 の決定（URL から動画のタイトルを除く）を変え、ビューアの URL の形（AC-16 と §3.2 の「ビューアの URL」の行）も変わる。実装の途中で分かると、作り直しになる。

**候補の手段:** ページのタイトルを実装する PR より前に、開発用のビルドか小さな試作で、記録がないビューアが固定のタイトルを出したときに履歴の項目のタイトルが書き換わるかを、Chrome と Brave で手で確かめる。上書きされなければ、`viewer.html` の静的なタイトル（今は `yt2column`。`extension/static/viewer.html:5`）を、状態の分かる固定のタイトルにする。上書きされるなら、人と決めたうえで URL に短く切った動画のタイトルを加え、その PR で ADR-0010 を改める。切る長さと、URL のクエリの名前と検査の規則を設計で決める。

**関連:** AC-16・01_requirements.md §3.2（ビューアの URL）

## H-06: 開発用のビルドで出せない状態を、単体テストで出す方法

**懸念:** 結果不明（60 秒たっても予約の結果がない）、入力を受け取れなかった、「完成したが保持できなかった」（`chrome.storage.session` への書き込みの失敗）、「開始が拒否された」のうち内部の失敗（Worker の読み込みの失敗など）、予約の後の `api_key_missing`、オプションページの検査できない場合と書き込みの失敗は、fake の LLM のシナリオでもブラウザの操作でも出せない（AC-29）。

**重要な理由:** これらの状態の表示と文言（AC-14・AC-15）を確かめる手段が、単体テストだけになる。

**候補の手段:** SW とビューアのテストで、`chrome.storage`・`chrome.tabs`・Port・Worker の fake に、書き込みの失敗、応答の遅れ、読み込みの失敗を注入できるようにする。

**関連:** AC-02・AC-06・AC-14・AC-15・AC-29

## H-07: Worker から受け取る JSON の文字列の、重複したメンバの拒否と、読み戻す記録の形の検査

**懸念:** 記事生成モジュールの結果と進み具合は JSON の文字列で受け取る（0090 設計書 §3.1.2）。`JSON.parse` は重複したメンバを黙って後の値で上書きする。今の厳格な解析は、撤去する `extension/src/core/response.ts` が使っている。一方、`chrome.storage.session` から読み戻すジョブの記録と開始の文脈は、JSON の文字列ではなくオブジェクトとして返るので、重複したメンバは起きず、閉じたメンバの集合と型の検査が要る。

**重要な理由:** 重複したメンバを拒否する規則（01_requirements.md §3.2）が、`JSON.parse` では満たせない。記録の検査を JSON の文字列の解析と同じものだと考えると、記録の検査が抜ける。

**候補の手段:** Worker からの JSON の文字列には、拡張に残る厳格な解析（`extension/src/core/strictJson.ts`）を使う。読み戻す記録と開始の文脈には、`version`、閉じたメンバの集合、状態ごとのメンバを確かめる検査の関数を置く。

**関連:** 01_requirements.md §3.2

## H-08: 失敗の値 `settings_invalid` の追加と、ワークスペース ID の指定なしの扱い

**懸念:** 本書は、保存した設定が形に合わないときの失敗の値 `settings_invalid` を加え、ワークスペース ID の空の文字列を指定なしとした（01_requirements.md §1）。0090 設計書の値の集合（§4.1）、`config.LoadExtension` に渡す名前を引く関数（§3.1.3）、`generate` の結果の形（§3.1.2）は、この値と空の文字列を前提にしていない。

**重要な理由:** 記事生成モジュールが LLM の API を呼ぶ前の設定の検査を、ほかの `internal` の失敗と分けて返さないと、ビューアは設定し直す手順を示せず、料金に触れない側（AC-11）にも入れられない。ワークスペース ID の空の文字列を形の検査に渡すと、`claudeparam.ParseWorkspaceID` が空を拒否する。

**候補の手段:** `WasmFailure`・`RecordFailure` と Go の `internal/extjob` の `Failure` に `settings_invalid` を加え、`generate` の設定の読み込みの失敗をこの値にする。名前を引く関数は、ワークスペース ID の空の文字列を未設定として答える（0090 設計書 §3.1.3 の「保存されていないとき（空のとき）」と同じ扱い）。オプションページは、保存と削除で `chrome.storage.local` の `set` と `remove` をそれぞれ 1 回だけ呼ぶ。

**関連:** AC-02・AC-04・AC-06・AC-11・01_requirements.md §3.2

## H-09: オプションページの検査の期限

**懸念:** AC-02 は、Models API の呼び出しの期限切れを「確かめられなかった」として保存し、記事生成モジュールか Worker を読み込めないときは保存しないとする。Models API の呼び出しの期限は、記事の生成と同じ送信の守りの期限（0090 設計書 §5.3 の 15 分）を通る。オプションページが Worker の読み込みと検査の全体に別の期限を持つなら、その値を決めていない。

**重要な理由:** ページの期限が呼び出しの期限より短いと、通信が止まったときに「検査できなかった」として保存しないことになり、0090 設計書 §3.6 が避けた「一時的な失敗で利用者が先へ進めない」状態になる。15 分の期限は、保存のボタンを押した利用者が待つには長い。

**候補の手段:** Worker の読み込みには実行するビューアと同じく 30 秒の期限を持ち（0090 設計書 §3.4）、Models API の呼び出しには、記事の生成より短い専用の期限を Go の側で持たせる。ページの側の全体の期限は、Worker の読み込みの期限と呼び出しの期限の和より長くする。

**関連:** AC-02

## H-10: fake の 401 と、設定の検査の fake の差し込み口

**懸念:** API キーが拒まれる結果（`api_key_rejected`）は、Claude アダプタの `HTTPStatusError`（`internal/llm/claude/errors.go`）の状態 401 から決まる（0090 設計書 §4.1）。fake の LLM（`internal/llm/devfake`）は `internal/llm` と標準ライブラリだけに依存する。設定の検査の結果を fake で出すには、公開用の記事生成モジュールに開発用の分岐を入れずに、検査の関数を差し替える口が要る（ADR-0045）。

**重要な理由:** fake が `internal/llm/claude` を import すると、fake の依存が広がる。公開用の記事生成モジュールに fake を選ぶ分岐が入ると、ADR-0045 の決定（公開する成果物は fake を含まない）に反する。

**候補の手段:** 失敗の分類を、プロバイダに依存しない形（たとえば `internal/llm` の型）で表すか、`internal/extjob` の分類が fake の失敗も 401 と見分けられるようにする。設定の検査は、公開用と開発用の記事生成モジュールの `main` で関数を差し込み、`internal/extjob` は差し込まれた関数を呼ぶだけにする。どちらも ADR-0045 の `go list -deps` の検査で確かめる。開発用の記事生成モジュールは Claude のクライアントを作らないが、保存した設定の検査（`settings_invalid`、AC-29）は公開用と同じく行う。

**関連:** AC-02・AC-25・AC-26・AC-29

## H-11: `chrome.storage` の変更の知らせに API キーが載ること

**懸念:** `chrome.storage.onChanged` は、`local` と `session` の両方の変更を、変わった値とともに知らせる。ポップアップ、表示するビューア、SW がこれを受け取ると、オプションページが保存した API キーの値を受け取る（AC-20）。0090 設計書 §7.3 の lint とソースの検査は、この経路を見ていない。

**重要な理由:** 同じオリジンのページなので、脅威モデルの上の害はないが、AC-20 が定める API キーの経路の外に値が出る。

**候補の手段:** ジョブの記録の変更は `chrome.storage.session.onChanged` だけで受け取り、`chrome.storage.onChanged` と `chrome.storage.local.onChanged` を使わない。lint かソースの検査で、これらの使用を拒否する。

**関連:** AC-20

## H-12: 文字を伏せた入力の欄と、支援技術

**懸念:** API キーの欄は `type="text"` に `-webkit-text-security: disc` で文字を伏せる（0090 設計書 §3.6）。支援技術は、この欄をパスワードの欄として扱わず、入力した文字を読み上げうる。

**重要な理由:** AC-03 は文字を伏せることを、AC-18 は支援技術で使えることを求める。読み上げで API キーが周りに聞こえうる。

**候補の手段:** スクリーンリーダー（VoiceOver など）で、欄の名前と、入力した文字の読み上げを確かめる。読み上げるなら、欄の説明に、入力した文字が読み上げられうることを添えるかを、設計で決める。

**関連:** AC-03・AC-18
