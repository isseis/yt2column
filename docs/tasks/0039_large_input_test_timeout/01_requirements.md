## 1. 概要 (Overview)

**目的:** 本書は、`internal/transcript` のテスト `TestParseCopiedLargeInputs` が CI の `Test` ジョブで時間の上限を超える原因を調べ、テストが CI で安定して通るようにするための要件を定義する（[#463](https://github.com/isseis/yt2column/issues/463)）。

**背景:**

`TestParseCopiedLargeInputs` は、コピーした字幕のパーサに 4 MiB 以下の合成の入力を 7 つ与え、それぞれについて次の 3 つを確かめる（`internal/transcript/copied_format_test.go:1036-1092`）。

-   解析が成功し、セグメント数が期待どおりである。
-   解析の時間が上限 `copiedParseDeadline`（15 秒。`copied_format_test.go:1033`）未満である。
-   メモリの確保量（`runtime.MemStats.TotalAlloc` の増分）が、入力 1 バイトあたり `copiedParseAllocPerByte` 以下である。この値はビルドごとに定める。`-race` 付きのビルドでは 8192（`copied_format_race_test.go:16`）、`-race` なしのビルドでは 128（`copied_format_norace_test.go:9`）である。

このテストは、タスク 0015 の AC-08（4 MiB の入力で解析が完走し、時間とメモリが入力の長さに比例する。`docs/tasks/0015_copied_transcript_source/01_requirements.md:115`）と、タスク 0024 の AC-20（0015 AC-08 を維持する。`docs/tasks/0024_copied_transcript_panel_lines/01_requirements.md:229`）を確かめている。0015 の設計は、解析の時間の予算を 30 秒未満とし、4 MiB の入力を 1 秒未満で解析することを目標にしている（`docs/tasks/0015_copied_transcript_source/02_architecture.md:732`）。時間の上限 15 秒は、`-race` 付きの実測（約 3 秒）に余裕を持たせて決めた（同 `:735`）。0015 の実装計画は、`-race` 付きの `make test` でこの上限を満たすことを求めている（`docs/tasks/0015_copied_transcript_source/03_implementation_plan.md:184`）。

CI の `Test` ジョブは、`make test-ci` でテストを `-race` 付きで 1 回だけ実行する（`.github/workflows/ci.yml` の `test` ジョブ、`Makefile:87-89`）。`-race` なしでテストを実行するジョブはない。

PR #461 の CI で、`shortest_form_A_lines` の解析が 4 回中 3 回、上限を超えて失敗した（15.44 秒・15.25 秒・15.02 秒。issue #463）。PR #461 は `internal/transcript` を変えていない。

2026-10-23 に手元（12 コアの macOS）で `6022d4b` を計測した結果は次のとおりである。

| 入力 | `-race` 付き・単独 | `-race` 付き・並行 | `-race` なし・単独 |
|---|---|---|---|
| `shortest_form_A_lines` | 2.66 秒、1 バイトあたり 1,710 バイト | 3.01 秒、1 バイトあたり 1,715 バイト | 0.116 秒、1 バイトあたり 18.7 バイト |
| `textless_form_B_timestamps` | 2.88 秒、1 バイトあたり 1,875 バイト | 3.22 秒、1 バイトあたり 1,868 バイト | 0.093 秒、1 バイトあたり 12.8 バイト |
| `form_A_headings_between_segments` | 1.11 秒、1 バイトあたり 591 バイト | 1.20 秒、1 バイトあたり 588 バイト | 0.045 秒、1 バイトあたり 6.6 バイト |

「単独」は `go test -tags test -race -count=1 -run TestParseCopiedLargeInputs ./internal/transcript`（`-race` なしは `-race` を除いたもの）、「並行」は `internal/transcript` を、`fixprguard` のテストを含む重いパッケージ（`./internal/fixprguard ./cmd/fixprguard ./cmd/yt2column ./internal/job`）と 1 回の `go test -race` で並行に実行したときの値である。残りの 4 つの入力は、いずれの条件でも 0.5 秒未満だった。

この計測から次のことが分かる。

-   `-race` なしのビルドでは、どの入力も 0015 の目標（1 秒未満）と `-race` なしのメモリの確保量の上限（128）の中に収まる。
-   `-race` 付きのビルドでは、時間が約 23 倍、メモリの確保量が約 92 倍になる。
-   手元では、並行の負荷で時間が約 13% 増えるだけだった。CI の失敗した実行の時間は手元の並行の約 5 倍であり、その差が CI の runner の速さによるのか、CI での並行の負荷によるのかは、手元の計測では分からない。

本番の `yt2column-server` は `-race` なしでビルドされる（`make build`）。

対応 issue: [#463](https://github.com/isseis/yt2column/issues/463)（関連: タスク 0015・0024、PR #461）

**本書の記述範囲:** 本書は、調べて記録すること、時間とメモリの確保量をどのビルドで何に照らして確かめるか、CI で安定して通ることの確かめ方を定める。時間の上限の値、`-race` なしの確認を CI と手元でどう実行するか、CI での比較の手順、パーサを改善するかどうかとその方法は、設計（`02_architecture.md`）で決める。要件の段階で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #463 で決めたこと:**

-   **原因を調べる:** 上限を超える原因が、パーサの処理そのもの（メモリの確保量を含む）か、CI の並行の負荷かを調べる。手元で、単独で実行した時間と `make test` の中での時間を比べる。原因が分からないまま上限だけを変えると、本当の劣化を見逃すおそれがあるためである。
-   **プロファイルで確かめる:** 1 バイトあたり約 1,715 バイトのメモリの確保量が妥当かを、プロファイルで確かめる。`CLAUDE.md`「Performance」の「Profile before optimizing」に従うためである。
-   **上限と測り方を見直す:** `-race` の下での上限と、並行の負荷の影響を受けない測り方を検討する。
-   **完了の条件:** 原因を特定し、パーサの改善か、テストの上限・測り方の見直しのどちらか（または両方）を行う。CI の `Test` ジョブで安定して通る。

**要件定義の際に決めたこと（2026-10-23）:**

-   **時間は `-race` なしのビルドで確かめる:** 解析の時間の上限は、`-race` なしのビルドで確かめ、CI でも実行する。`-race` 付きのビルドでは時間を確かめない。0015 の時間の予算が守るのは本番のサーバの解析であり、本番は `-race` なしでビルドされる。`-race` 付きの時間は、データ競合の検出器の負担と runner の速さで大きく揺れ、パーサの性能を表さないためである（F-002）。
-   **`-race` 付きのビルドでは成功とメモリの確保量を確かめ続ける:** `-race` 付きのビルドでも、7 つの入力について解析の成功・セグメント数・メモリの確保量の上限を確かめる。これらは負荷で揺れず、非線形の増加を検出できるためである（F-003）。
-   **時間の上限の値は設計で決める:** 上限の値は、CI での実測に余裕を持たせて設計で決める。要件は、0015 の解析の予算（30 秒未満）より十分小さいことだけを定める。CI の runner の速さと負荷は計測するまで分からず、0015 の目標の 1 秒をそのまま上限にすると余裕が小さすぎるおそれがあるためである（F-002）。
-   **原因は CI で比べて確かめる:** CI の runner で、`TestParseCopiedLargeInputs` を単独で実行したときと、ほかのパッケージと並行に実行したときの時間を比べ、記録する。手元の計測では CI の失敗を再現できず、原因を区別できないためである（F-001）。
-   **パーサを改善するかどうかはプロファイルで決める:** パーサを改善するかどうかは、プロファイルの結果を見て設計で決める。手元の計測では `-race` なしのビルドが予算の中に収まっているが、`-race` 付きのメモリの確保量が約 92 倍になる理由はまだ分かっていないためである（F-004）。
-   **安定は 3 回連続の成功で確かめる:** CI の `Test` ジョブで安定して通ることは、再実行を含めて 3 回続けて成功することで確かめる。PR #461 では 4 回中 3 回失敗しており、1 回の成功では安定とはいえないためである（F-005）。
-   **ほかの時間の上限を持つテストは扱わない:** 本タスクは `TestParseCopiedLargeInputs` だけを扱う。`internal/transcript/exec_test.go` などのほかの時間の上限は、今回失敗していないためである。失敗したら別の issue で扱う。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `TestParseCopiedLargeInputs` が CI の時間の上限を超える原因を特定し、記録する。
-   解析の時間の確認を、本番のビルドの性能を表し、CI の負荷で揺れない形にする。
-   0015 AC-08・0024 AC-20 が確かめる性質（4 MiB の入力の完走と、時間とメモリの確保量の線形性）を確かめ続ける。

### 2.2. スコープ (In Scope)

-   原因の調査と記録: 手元と CI での単独・並行の時間の比較、`-race` 付きと `-race` なしのプロファイル（F-001）
-   時間の上限の確認を `-race` なしのビルドに移し、CI で実行すること（F-002）
-   `-race` 付きのビルドでの、解析の成功・セグメント数・メモリの確保量の確認（F-003）
-   プロファイルの結果に応じたパーサの改善（F-004。改善しない場合はその判断と理由の記録）
-   CI の `Test` ジョブでの安定の確認（F-005）

### 2.3. スコープ外 (Out of Scope)

-   `TestParseCopiedLargeInputs` 以外の、時間の上限を持つテスト（`internal/transcript/exec_test.go:27`・`:429` など）。今回失敗していないため。
-   コピーした字幕の書式の受理と拒否の規則（0015・0024 が定める）。パーサを改善する場合も変えない（F-004）。
-   サーバの本文の上限（4 MiB。`internal/server/request.go:18`）と、サーバのタイムアウト（`internal/server/server.go:32` など）。
-   0015 の解析の予算（30 秒未満）と目標（1 秒未満）。本タスクはこれを変えず、確かめ方だけを変える。
-   CI の runner の種類やジョブの並列度の変更。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 原因の調査と記録

`TestParseCopiedLargeInputs` が CI で時間の上限を超える原因を調べ、本タスクの文書に記録する。

**Acceptance Criteria**:
- **AC-01**: 手元で、`TestParseCopiedLargeInputs` の 7 つの入力の時間とメモリの確保量を、`-race` 付きで単独に実行したときと `make test` の中で実行したときについて計測した値が、計測した環境とコミットとともに記録されている。
- **AC-02**: CI の runner で、`TestParseCopiedLargeInputs` を `-race` 付きで単独に実行したときと、ほかのパッケージと並行に実行したとき（`make test-ci` と同じ条件）の時間が、CI の実行の URL とともに記録されている。
- **AC-03**: `shortest_form_A_lines` の解析について、`-race` 付きと `-race` なしのそれぞれで CPU とメモリの確保のプロファイルを取った結果が記録されている。記録には、メモリの確保量の大きい箇所と、1 バイトあたり約 1,715 バイト（`-race` 付き）の確保量が妥当かどうかの判断とその理由が含まれる。
- **AC-04**: AC-01〜AC-03 の結果から、上限を超えた原因（パーサの処理、`-race` の負担、CI の runner の速さ、CI での並行の負荷のうち、どれがどの程度効いているか）の結論が記録されている。

#### F-002: `-race` なしのビルドでの時間の確認

`TestParseCopiedLargeInputs` の 7 つの入力について、解析の時間を `-race` なしのビルドで上限と照らして確かめる。

**Acceptance Criteria**:
- **AC-05**: `-race` なしのビルドのテストで、7 つの入力のそれぞれについて、解析の時間が上限を超えるとテストが失敗する。上限は 0015 の解析の予算（30 秒未満。`docs/tasks/0015_copied_transcript_source/02_architecture.md:732`）より十分小さい。
- **AC-06**: 上限の値と、その根拠（CI での実測と、持たせた余裕）が記録されている。
- **AC-07**: CI の `Test` ジョブが走る PR では、`-race` なしのビルドでの AC-05 の時間の確認が実行され、その成否がジョブの成否に反映される。
- **AC-08**: `-race` 付きのビルドのテストは、解析の時間で失敗しない。

#### F-003: `-race` 付きのビルドでの成功とメモリの確保量の確認

`-race` 付きのビルドでも、時間以外の性質を確かめ続ける。

**Acceptance Criteria**:
- **AC-09**: `-race` 付きのビルドのテスト（`make test`・`make test-ci`）で、7 つの入力のそれぞれについて、解析の成功、期待するセグメント数、1 バイトあたりのメモリの確保量の上限を確かめる。どれかを満たさないとテストが失敗する。
- **AC-10**: `-race` なしのビルドのテストでも、7 つの入力について AC-09 と同じ 3 つを確かめる。メモリの確保量の上限は `-race` なしのビルドの値である。

#### F-004: プロファイルに応じたパーサの改善

AC-03 のプロファイルの結果を見て、パーサを改善するかどうかを設計で決める。

**Acceptance Criteria**:
- **AC-11**: パーサを改善するかどうかの判断と、その理由が記録されている。理由は、`CLAUDE.md`「Performance」に従い、実際の実行の絶対的な予算（0015 の解析の予算）に照らして述べる。
- **AC-12**: パーサを改善した場合、コピーした字幕のどの入力についても、受理か拒否か、受理したときのセグメント（`StartMs`・`Text`）、拒否したときのエラー（`ErrCopiedTranscriptFormat` と理由の番兵）が改善の前と変わらない。0015・0024 の受け入れ基準を確かめる既存のテストがすべて通る。
- **AC-13**: パーサを改善した場合、改善の前と後の、AC-01 と同じ条件での時間とメモリの確保量が記録されている。

#### F-005: CI での安定の確認

**Acceptance Criteria**:
- **AC-14**: 本タスクの実装の最後の PR で、CI の `Test` ジョブが、再実行を含めて 3 回続けて成功する。3 回の実行の URL が記録されている。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   本番のビルドでの解析の予算（4 MiB の入力を 30 秒未満、目標は 1 秒未満。0015 §7.3）は変えない。
-   CI の `Test` ジョブに加わる実行時間は、`-race` なしで `TestParseCopiedLargeInputs` を実行する分（手元の計測で 1 秒未満）に、ビルドの時間を加えた程度に収める。

### 4.2. セキュリティ (Security)
-   N/A。本タスクは、外部コマンドの呼び出し、秘密、キャッシュ、ネットワーク、信頼できない文字列のプロンプトへの埋め込みのどれも変えない。パーサを改善する場合も、信頼できない入力（コピーした字幕）の受理の形・拒否の番兵・大きさの上限は 0015・0024 のまま変えない（AC-12）。新しい信頼できない入力の境界は加わらない。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   時間の確認は、CI の並行の負荷で失敗しない余裕を持つ（AC-06・AC-14）。

### 4.4. 互換性 (Compatibility)
-   `make test` と `make test-ci` は、これまでどおり `-race` 付きで全パッケージのテストを実行する。
-   テストを実行する環境（macOS と CI の Linux）で、テストの結果が変わらない。

### 4.5. 保守性 (Maintainability)
-   時間の上限とメモリの確保量の上限について、値と根拠をテストのコードの近くか本タスクの文書から辿れるようにする（AC-06）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   `CLAUDE.md`「Performance」に従う。パーサの最適化は、ベンチマークの相対的な差ではなく、実際の実行の絶対的な予算で正当化する。最適化は、それを動機づけた振る舞いの変更とは別のコミットにする。
-   **先行タスクの決定の変更:** 0015 の設計は、時間の上限を `-race` 付きの実測から 15 秒と決め（`docs/tasks/0015_copied_transcript_source/02_architecture.md:735`）、実装計画は `-race` 付きの `make test` でこの上限を満たすことを求めた（`docs/tasks/0015_copied_transcript_source/03_implementation_plan.md:184`）。本タスクはこの決定を変え、時間の上限を `-race` なしのビルドで確かめる（F-002）。理由は §1「要件定義の際に決めたこと」の 1 項目めのとおりである。0015 AC-08 と 0024 AC-20 が確かめる性質は変えない。

## 6. 用語集 (Glossary)

-   **`-race` 付きのビルド / `-race` なしのビルド:** Go のデータ競合の検出器を有効にしてテストをビルドする（`go test -race`）か、しないか。`make test`・`make test-ci` は `-race` 付きである。
-   **メモリの確保量:** 解析の間の `runtime.MemStats.TotalAlloc` の増分。用語集の「割り当て」（quota。自動レビュアーのレビューの回数の上限）と区別するため、本書ではこの語を使う。
-   **単独 / 並行:** テストを、対象のパッケージだけで実行するか、ほかのパッケージとともに 1 回の `go test` で並行に実行するか。
-   **プロファイル:** Go の CPU プロファイルとメモリのプロファイル（`go test -cpuprofile`・`-memprofile` などで得るもの）。
