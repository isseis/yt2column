## 1. 概要 (Overview)

**目的:** 本書は、`internal/transcript` のテスト `TestParseCopiedLargeInputs` が CI の `Test` ジョブで時間の上限を超える原因を調べ、テストが CI で安定して通るようにするための要件を定義する（[#463](https://github.com/isseis/yt2column/issues/463)）。

**背景:**

`TestParseCopiedLargeInputs` は、コピーした字幕のパーサに 4 MiB 以下の合成の入力を 7 つ与え、それぞれについて次の 3 つを確かめる（`internal/transcript/copied_format_test.go:1036-1092`）。

-   解析が成功し、セグメント数が期待どおりである。
-   解析の時間が上限 `copiedParseDeadline`（15 秒。`copied_format_test.go:1033`）未満である。
-   メモリの確保量（`runtime.MemStats.TotalAlloc` の増分）が、入力 1 バイトあたり `copiedParseAllocPerByte` 以下である。この値はビルドごとに定める。`-race` 付きのビルドでは 8192（`copied_format_race_test.go:16`）、`-race` なしのビルドでは 128（`copied_format_norace_test.go:9`）である。

このテストは、タスク 0015 の AC-08（4 MiB の入力で解析が完走し、時間とメモリが入力の長さに比例する。`docs/tasks/0015_copied_transcript_source/01_requirements.md:115`）と、タスク 0024 の AC-20（0015 AC-08 を維持する。`docs/tasks/0024_copied_transcript_panel_lines/01_requirements.md:229`）を確かめている。0015 の設計は、解析の時間の予算を 30 秒未満とし、4 MiB の入力を 1 秒未満で解析することを目標にしている（`docs/tasks/0015_copied_transcript_source/02_architecture.md:732`）。時間の上限 15 秒は、`-race` 付きの実測（約 3 秒）に余裕を持たせて決めた（同 `:735`）。0015 の実装計画は、`-race` 付きの `make test` でこの上限を満たすことを求めている（`docs/tasks/0015_copied_transcript_source/03_implementation_plan.md:184`）。

CI の `Test` ジョブは、`make test-ci` で全パッケージのテストを `-race` 付き・カバレッジ付き（`-coverprofile`）で 1 回実行する（`.github/workflows/ci.yml` の `test` ジョブ、`Makefile:87-89`）。`internal/transcript` を `-race` なしで実行するジョブはない。`-race` なしでテストを実行するジョブは `doc-guard` だけで、その対象は `./cmd/yt2column ./cmd/yt2column-server ./cmd/fixprguard ./internal/pipeline` である（`.github/workflows/ci.yml:184`）。そのため、`-race` なしのメモリの確保量の上限（128）は、今は CI で確かめられていない。

PR #461 の CI で、`shortest_form_A_lines` の解析が 4 回中 3 回、上限を超えて失敗した（15.44 秒・15.25 秒・15.02 秒。issue #463）。PR #461 は `internal/transcript` を変えていない。

2026-10-23 に手元（12 コアの macOS）で `6022d4b` を計測した結果は次のとおりである。カバレッジはどの条件でも付けていない。

| 入力 | `-race` 付き・単独 | `-race` 付き・並行（代用） | `-race` なし・単独 |
|---|---|---|---|
| `shortest_form_A_lines` | 2.66 秒、1 バイトあたり 1,710 バイト | 3.01 秒、1 バイトあたり 1,715 バイト | 0.116 秒、1 バイトあたり 18.7 バイト |
| `textless_form_B_timestamps` | 2.88 秒、1 バイトあたり 1,875 バイト | 3.22 秒、1 バイトあたり 1,868 バイト | 0.093 秒、1 バイトあたり 12.8 バイト |
| `form_A_headings_between_segments` | 1.11 秒、1 バイトあたり 591 バイト | 1.20 秒、1 バイトあたり 588 バイト | 0.045 秒、1 バイトあたり 6.6 バイト |

「単独」は `go test -tags test -race -count=1 -run TestParseCopiedLargeInputs ./internal/transcript`（`-race` なしは `-race` を除いたもの）である。「並行（代用）」は、`make test` の代わりに、`internal/transcript` を重いパッケージ（`./internal/fixprguard ./cmd/fixprguard ./cmd/yt2column ./internal/job`）と 1 回の `go test -race` で並行に実行したときの値である。`make test` の中での値ではない（`make test` での計測は AC-01 で行う）。残りの 4 つの入力は、いずれの条件でも 0.5 秒未満だった。

この計測から次のことが分かる。

-   `-race` なしのビルドでは、どの入力も 0015 の目標（1 秒未満）を満たし、メモリの確保量も `-race` なしの上限（128）以下に収まる。
-   上の 3 つの入力では、`-race` 付きのビルドの時間は `-race` なしの約 23〜31 倍、メモリの確保量は約 90〜146 倍である。
-   手元の代用の条件では、並行の負荷で時間が約 8〜13% 増えた。CI の失敗した実行の時間は手元の並行の約 5 倍であり、その差が CI の runner の速さ、CI での並行の負荷、カバレッジのどれによるのかは、手元の計測では分からない。

本番の `yt2column-server` は `-race` なしでビルドされる（`make build`。`Makefile:60-64`）。

対応 issue: [#463](https://github.com/isseis/yt2column/issues/463)（関連: タスク 0015・0024、PR #461）

**本書の記述範囲:** 本書は、調べて記録すること、時間とメモリの確保量をどのビルドで何に照らして確かめるか、CI で安定して通ることの確かめ方を定める。時間の上限の値、`-race` なしの確認を CI と手元でどう実行するか、CI での比較の手順、パーサを改善するかどうかとその方法、各記録をどの文書に置くか（AC-16 を除く）は、設計（`02_architecture.md`）で決める。要件の段階で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。本書で「AC-NN」とだけ書くものは本書の受け入れ基準を指し、先行タスクの受け入れ基準は「0015 AC-08」のようにタスクの番号を付けて書く。

**issue #463 で決めたこと:**

-   **原因を調べる:** 上限を超える原因が、パーサの処理そのもの（メモリの確保量を含む）か、CI の並行の負荷かを調べる。手元で、単独で実行した時間と `make test` の中での時間を比べる。原因が分からないまま上限だけを変えると、本当の劣化を見逃すおそれがあるためである。
-   **プロファイルで確かめる:** 1 バイトあたり約 1,715 バイトのメモリの確保量が妥当かを、プロファイルで確かめる。`CLAUDE.md`「Performance」の「Profile before optimizing」に従うためである。
-   **上限と測り方を見直す:** `-race` の下での上限と、並行の負荷の影響を受けない測り方を検討する。検討の結果は、下の「時間は `-race` なしのビルドで確かめる」で決めた。
-   **完了の条件:** 原因を特定し、パーサの改善か、テストの上限・測り方の見直しのどちらか（または両方）を行う。CI の `Test` ジョブで安定して通る。

**要件定義の際に決めたこと（2026-10-23）:**

-   **時間は `-race` なしのビルドで確かめる:** 解析の時間の上限は、`-race` なしのビルドで確かめ、CI でも実行する。`-race` 付きのビルドでは時間を確かめない。0015 の時間の予算が守るのは本番のサーバの解析であり、本番は `-race` なしでビルドされる。`-race` 付きのビルドでは、データ競合の検出器の負担のため、手元の計測で `-race` なしの約 23〜31 倍の時間がかかり、本番のパーサの性能を表さないためである（F-002）。この決定は、原因の調査（F-001）の結論が F-002 の前提に合わない場合に見直す（AC-05）。
-   **`-race` 付きのビルドでは成功とメモリの確保量を確かめ続ける:** `-race` 付きのビルドでも、7 つの入力について解析の成功・セグメント数・メモリの確保量の上限を確かめる。手元の計測では、メモリの確保量は単独と並行（代用）で 1% 未満しか違わず、0015 が確かめようとした性質（メモリの確保量が入力の長さに比例すること。0015 AC-08）を、時間の上限を持たずに確かめ続けられるためである（F-003）。
-   **時間の上限の値は設計で決める:** 上限の値は、CI での実測に余裕を持たせて設計で決める。要件は、0015 の解析の予算（30 秒）未満であることと、根拠を記録することだけを定める。CI の runner の速さと負荷は計測するまで分からず、0015 の目標の 1 秒をそのまま上限にすると余裕が小さすぎるおそれがあるためである（F-002）。
-   **原因は CI で比べて確かめる:** CI の runner で、`TestParseCopiedLargeInputs` を単独で実行したときと、ほかのパッケージと並行に実行したときの時間を比べ、記録する。手元の計測では CI の失敗を再現できず、原因を区別できないためである（F-001）。
-   **パーサを改善するかどうかはプロファイルで決める:** パーサを改善するかどうかは、プロファイルの結果を見て設計で決める。手元の計測では `-race` なしのビルドが予算の中に収まっているが、`-race` 付きのメモリの確保量が約 90〜146 倍になる理由はまだ分かっていないためである（F-004）。
-   **安定は 3 回連続の成功で確かめる:** CI の `Test` ジョブで安定して通ることは、同じコミットで再実行を含めて 3 回続けて成功することで確かめる。テストの結果をキャッシュから再利用した実行は数えない。PR #461 では 4 回中 3 回失敗しており、1 回の成功では安定とはいえないためである（F-005）。
-   **ほかの時間の上限を持つテストは扱わない:** 本タスクは `TestParseCopiedLargeInputs` だけを扱う。`internal/transcript/exec_test.go` などのほかの時間の上限は、今回失敗していないためである。失敗したら別の issue で扱う。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `TestParseCopiedLargeInputs` が CI の時間の上限を超える原因を特定し、記録する。
-   解析の時間の確認を本番のビルドの性能に照らした形にし、上限を、確認を実行する条件での CI の実測に対して余裕のある値にする。
-   0015 AC-08・0024 AC-20 のために確かめてきたこと（4 MiB の入力の完走と、時間とメモリの確保量が上限の中に収まること）を確かめ続ける。

### 2.2. スコープ (In Scope)

-   原因の調査と記録: 手元と CI での単独・並行の時間の比較、`-race` 付きと `-race` なしのプロファイル（F-001）
-   時間の上限の確認を `-race` なしのビルドに移し、CI で実行すること（F-002）
-   `-race` 付きのビルドでの、解析の成功・セグメント数・メモリの確保量の確認（F-003）
-   プロファイルの結果に応じたパーサの改善（F-004。改善しない場合はその判断と理由の記録）
-   CI の `Test` ジョブでの安定の確認（F-005）

### 2.3. スコープ外 (Out of Scope)

-   `TestParseCopiedLargeInputs` 以外の、時間の上限を持つテスト（`internal/transcript/exec_test.go:27`・`:429` など）。今回失敗していないため。
-   コピーした字幕の書式の受理と拒否の規則（0015・0024 が定める）。パーサを改善する場合も変えない（F-004）。
-   サーバの本文の上限（4 MiB。`internal/server/request.go:18`）と、サーバのタイムアウト（`internal/server/server.go:32` など）。
-   0015 の解析の予算（30 秒未満）と目標（1 秒未満）。本タスクはこれを変えず、確かめ方だけを変える。
-   CI の runner の種類やジョブの並列度の変更。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 原因の調査と記録

`TestParseCopiedLargeInputs` が CI で時間の上限を超える原因を調べ、本タスクの文書に記録する。

**Acceptance Criteria**:
- **AC-01**: 手元で、`TestParseCopiedLargeInputs` の 7 つの入力の時間とメモリの確保量を計測した値が、計測した環境とコミットとともに記録されている。条件は次の 4 つである。(a) `-race` 付きで単独、(b) `make test` の中、(c) (a) にカバレッジ（`make test-ci` と同じ `-coverprofile`）を付けたもの、(d) `make test-ci` と同じ条件（全パッケージを並行に、`-race` 付き・カバレッジ付き）。
- **AC-02**: CI の runner で、`TestParseCopiedLargeInputs` の 7 つの入力の時間を計測した値が、CI の実行の URL とともに記録されている。条件は次の 4 つである。(a) `-race` 付き・カバレッジ付きで単独、(b) `-race` 付き・カバレッジなしで単独、(c) `make test-ci` と同じ条件（全パッケージを並行に、`-race` 付き・カバレッジ付き）、(d) `-race` なし・カバレッジなしで単独。この計測は F-002 の実装より前に行う。各条件の実行の回数は設計で決め、複数回のときは最小・中央・最大を記録する。
- **AC-03**: `shortest_form_A_lines` と `textless_form_B_timestamps` の解析について、`-race` 付きと `-race` なしのそれぞれで CPU とメモリの確保のプロファイルを取った結果が記録されている。記録には、メモリの確保量の大きい箇所と、`-race` 付きの 1 バイトあたり約 1,710〜1,875 バイト（手元の単独の計測）の確保量が妥当かどうかの判断とその理由が含まれる。判断は、同じ入力の `-race` なしの確保量と、0015 の解析の予算に照らして述べる。
- **AC-04**: AC-01〜AC-03 の結果から、上限を超えた原因の結論が記録されている。結論は、パーサの処理、`-race` の負担、カバレッジの負担、CI の runner の速さ、CI での並行の負荷のそれぞれが、どの程度効いているかを述べる。

#### F-002: `-race` なしのビルドでの時間の確認

`TestParseCopiedLargeInputs` の 7 つの入力について、解析の時間を `-race` なしのビルドで上限と照らして確かめる。

**Acceptance Criteria**:
- **AC-05**: 次のどちらかに当たる場合、実装は F-002 に進まず、要件の変更として人間のレビュアーに判断を求める。(a) AC-02 (d) の 7 つの入力の時間のうち最大のもの（複数回計測したときは、全計測を通した最大）が 1 秒以上になり、0015 の目標（1 秒未満）を満たさない。目標を満たさないことは、時間の確認を `-race` なしのビルドに移すだけでは解決しないためである。(b) `-race` なしのビルドにも現れる劣化が原因に含まれ、AC-13 でパーサを改善しないと判断した。
- **AC-06**: CI の runner で、`-race` なしのビルドの時間の確認を、CI で実行するときと同じ条件（並行に走るほかのテストの有無とカバレッジの有無を含む）で実行した 7 つの入力の時間が、CI の実行の URL とともに記録されている。
- **AC-07**: `-race` なしのビルドのテストで、7 つの入力のそれぞれについて、解析の時間が上限を超えるとテストが失敗する。上限は 0015 の解析の予算（30 秒）未満である。
- **AC-08**: 上限の値と、その根拠が記録されている。根拠には、AC-06 の最大の時間、それに対する上限の倍率、上限と 0015 の目標（1 秒）・予算（30 秒）との比が含まれる。
- **AC-09**: CI の `Test` ジョブが走る PR では、AC-07 の時間の確認が CI のいずれかのジョブで実行され、その成否がその PR の CI の成否に反映される。
- **AC-10**: `-race` 付きのビルドのテストは、解析の時間で失敗しない。

#### F-003: 時間以外の性質の確認

`-race` 付きと `-race` なしの両方のビルドで、時間以外の性質を確かめ続ける。

**Acceptance Criteria**:
- **AC-11**: `-race` 付きのビルドのテスト（`make test`・`make test-ci`）で、7 つの入力のそれぞれについて、解析の成功、期待するセグメント数、1 バイトあたりのメモリの確保量の上限を確かめる。どれかを満たさないとテストが失敗する。
- **AC-12**: `-race` なしのビルドのテストでも、7 つの入力について AC-11 と同じ 3 つを確かめる。メモリの確保量の上限は `-race` なしのビルドの値である。この確認は AC-07 と同じく CI で実行される。

#### F-004: プロファイルに応じたパーサの改善

AC-03 のプロファイルの結果を見て、パーサを改善するかどうかを設計で決める。

**Acceptance Criteria**:
- **AC-13**: パーサを改善するかどうかの判断と、その理由が記録されている。理由は、`CLAUDE.md`「Performance」に従い、実際の実行の絶対的な予算（0015 の解析の予算）に照らして述べる。
- **AC-14**: パーサを改善した場合、0015・0024 の受け入れ基準を確かめる既存のテスト（fuzz のテストの種を含む）がすべて、変更なしで通る。受理か拒否か、受理したときのセグメント（`StartMs`・`Text`）、拒否したときのエラー（`ErrCopiedTranscriptFormat`・理由の番兵・行番号・メッセージ）は、改善の前と変わらない。
- **AC-15**: パーサを改善した場合、改善の前と後の、AC-01 と同じ条件での時間とメモリの確保量が記録されている。

#### F-005: CI での安定の確認

本タスクの変更の後、CI でテストが安定して通ることを、同じコミットでの繰り返しの成功で確かめる。

**Acceptance Criteria**:
- **AC-16**: 本タスクの実装の PR のうち、時間・メモリの確保量の確認か CI の手順を最後に変える PR を対象とする。この PR をマージする直前のヘッドのコミットについて、CI の `Test` ジョブと、AC-07 の時間の確認を実行するジョブ（`Test` ジョブと異なる場合）が、再実行を含めて 3 回続けて成功する。途中で失敗したら、数え直す。各実行では、数える両ジョブが `TestParseCopiedLargeInputs` を実際に実行する。以前の実行の結果をキャッシュから再利用し、テストを実行しなかった実行は数えない。ヘッドが変わったら（記録のためのコミットを含む）、新しいヘッドで数え直す。3 回の実行の URL は、この PR のマージの後に、`docs/` だけを変える別の PR で `03_implementation_plan.md` に記録する。

### 3.2. エラーと境界の振る舞い

-   時間の上限を超えたとき（AC-07）、開発者には、`go test` の失敗として、入力の名前・バイト数・かかった時間・上限が見える（今の `copied_format_test.go:1080-1082` の形を保つ）。
-   `-race` 付きのビルドでは時間の上限がないため、解析が止まらないときは、`go test` のパッケージのタイムアウト（既定 10 分。`make test`・`make test-ci`・CI のジョブはタイムアウトを指定していない。`Makefile:83-89`、`.github/workflows/ci.yml`）で失敗する。時間の劣化は `-race` なしのビルドの確認（AC-07）で検出する。
-   原因の調査の結論が F-002 の前提に反するとき（AC-05）は、実装を進めずに要件の変更として扱う（`docs/dev/developer_guide/requirements_process.md`「Editing an approved document」）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   本番のビルドでの解析の予算（4 MiB の入力を 30 秒未満、目標は 1 秒未満。0015 §7.3）は変えない。

### 4.2. セキュリティ (Security)

## 6. 用語集 (Glossary)

-   **`-race` 付きのビルド / `-race` なしのビルド:** Go のデータ競合の検出器を有効にしてテストをビルドする（`go test -race`）か、しないか。`make test`・`make test-ci` は `-race` 付きである。
-   **メモリの確保量:** 解析の間の `runtime.MemStats.TotalAlloc` の増分。翻訳用語集（`docs/translation_glossary.md`）の「割り当て」（quota。自動レビュアーのレビューの回数の上限）と区別するため、本書ではこの語を使う。
-   **単独 / 並行:** テストを、対象のパッケージだけで実行するか、ほかのパッケージとともに 1 回の `go test` で並行に実行するか。
-   **カバレッジ付き:** `go test -coverprofile` でカバレッジを取りながらテストを実行すること。`make test-ci` はカバレッジ付きである。
-   **プロファイル:** Go の CPU プロファイルとメモリのプロファイル（`go test -cpuprofile`・`-memprofile` などで得るもの）。
