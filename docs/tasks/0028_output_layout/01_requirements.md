## 1. 概要 (Overview)

**目的:** 本書は、生成した記事の出力（`--out` のファイルと Slack の投稿）の構成を見直す要件を定義する。読者が知りたい情報を先頭に置き、開発・デバッグ用の情報は、Slack では末尾に、ファイルではフロントマターに移す（[#345](https://github.com/isseis/yt2column/issues/345)）。本書が参照する `H-NN` は、同じ `docs/tasks/0028_output_layout/` の `design_handoff.md` の項目番号である。

**背景:**

現在の出力は、ファイルと Slack で共通の `renderArticle`（`internal/publisher/file.go`）が作る。

```text
# タイトル

- Model: …
- Model version: …
- Shorten model: …            （字数の調整が LLM を呼んだときだけ）
- Shorten model version: …
- Review model: …             （推敲が走ったときだけ）
- Review model version: …
- Estimated cost: 0.0208 USD  （算出できないときは unknown）

本文

出典: <https://www.youtube.com/watch?v=…>
```

末尾の「出典: <URL>」は、publisher ではなく `internal/writer` の `newArticle` が本文に連結する。URL は検証済みの動画 ID から組み立て、生成テキストは使わない。

この構成には、次の問題がある。

-   読者が知りたいこと（何の記事か、どのチャンネルか）より前に、開発・デバッグ用のモデル情報が並び、本文までの距離が長い。
-   チャンネル名は、すでに取得している（`transcript.Transcript.ChannelName`。プロンプトにも渡している）が、出力に含まれない。`writer.Article` にも持たせていない。
-   現在の出力（`# タイトル` と `- Model: …`）は、実機の Slack では記号のままではなく、見出しと箇条書きとして描画される（2026-10-19 に確認）。このため、Markdown の記法は投稿先で解釈されることを前提とする。値に含まれる記号が描画を壊しうる点は、設計で扱う（H-02）。
-   モデルの版は、`e72d3c7f…` のように提供元ごとに形が違い、中身から意味を読み取れない文字列である。読者には意味がなく、再現性の確認にしか使わない。

情報の仕分けを、次のとおりとする。

| 情報 | 読者 | 開発・デバッグ | 置き場所 |
|---|---|---|---|
| タイトル、チャンネル名 | ◎ | | 先頭 |
| 本文 | ◎ | | 先頭の直後 |
| 出典 URL | ◎（元動画へ移るため） | | 本文の直後 |
| モデル名 | △ | ◎ | Slack は末尾の脚注、ファイルはフロントマター |
| モデルの版 | × | ◎ | Slack には出さない。ファイルはフロントマター |
| 推定コスト | △ | ◎ | Slack は末尾の脚注、ファイルはフロントマター |

出力の形は次のとおりとする（議論で決定済み。[#345](https://github.com/isseis/yt2column/issues/345)）。

-   **Slack:** plain text のままにし、Block Kit へは移行しない。Slack は折りたたみに対応しない。`context` ブロックは使えるが、`section` ブロックの上限（1 つ 3,000 文字）に合わせて分割処理（`splitSlackText`）を作り直す必要がある。現状の分割は `text` の上限 16,383 文字を前提としているため、見送る。
-   **ファイル:** YAML のフロントマターにメタデータを入れる。Slack とは形が異なるので、`renderArticle` の共有をやめ、publisher ごとに整形する。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   Slack の投稿を、タイトルとチャンネル名で始め、すぐ後に本文を置き、モデルとコストを末尾の短い脚注にする。
-   ファイルの出力を、メタデータをフロントマターに集め、読者向けの部分（見出しと本文）をその後ろに置く形にする。
-   チャンネル名を、出力で使えるように `writer.Article` に持たせる。

### 2.2. スコープ (In Scope)

-   `--out` のファイルの出力の構成（フロントマターの導入）。
-   Slack の投稿の構成（先頭の見出し行、末尾の脚注、複数メッセージに分かれるときの扱い）。CLI からの投稿と localhost サーバからの投稿の両方。
-   チャンネル名の経路（`Transcript` から `Article` まで、`--after` で再開した実行を含む）と、その検査。
-   Slack の投稿のメンションの扱いの変更。`@` の直前が文字・数字の `@` を受理し、見出し行・脚注・本文（コードの外）の対象の `@`（定義は AC-14）を U+200B で無効化する（AC-14〜AC-14d）。拒否する場合の失敗の理由を、CLI とサーバの失敗の通知で示す（AC-14e、AC-14f）。`0006_slack_webhook_publisher` の規則 M2（`@` の直後に名前の文字が続く並びをすべて拒否する）の変更になる。
-   出力の形を固定しているテストと、出力の形を説明する文書（`README.md`、`docs/dev/project_overview.md`、`docs/dev/security.md`）の更新。

### 2.3. スコープ外 (Out of Scope)

-   Slack の Block Kit への移行。
-   本文の Markdown を別の記法へ変換すること。本文は従来どおり Markdown のまま投稿する。
-   記事の本文・タイトルの生成（プロンプト、後処理）の変更。末尾の出典のブロック（`出典: <URL>`）の書式の変更。
-   料金の算出（`internal/pricing`）の変更。金額の値と、桁数（小数点以下 4 桁）、不明の扱いは変えない。
-   通貨表記の国際化（i18n。[#298](https://github.com/isseis/yt2column/issues/298)）。
-   `--review-log` のファイルの書式。
-   CLI の標準エラーの要約の行（モデル名、トークン数、料金の行）。
-   完了したタスクの文書（`0010`・`0022` など）の書き換え。これらは当時の決定の記録として残す。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: チャンネル名を記事に持たせる

`writer.Article` がチャンネル名を持ち、publisher が使えるようにする。チャンネル名は任意の値である。空文字のとき（localhost サーバへの要求で `channelName` が省略または空文字のときを含む）は、「チャンネル名なし」として扱う。

-   チャンネル名は、`Transcript` の `ChannelName` から `Article` まで、生成の実行でも、`--after` で再開した実行でも、同じ値が届く。
-   空文字でないチャンネル名は、表示用の文字列として、タイトルと同じ規則（空白だけでない、制御文字を含まない）で検査する。この規則に違反する記事は公開しない（`ErrInvalidArticle`）。

**Acceptance Criteria**:
- **AC-01**: チャンネル名が `"Example Channel"` の入力から作った `Article` は、`Example Channel` を持つ。生成の実行（`--after` なし）と、`--after generation`・`--after shorten`・`--after review` で再開した実行のどれでも同じである。
- **AC-02**: チャンネル名が空文字の入力から作った `Article` は、チャンネル名を持たず、公開の検査（`CheckPublishable`）を通る。
- **AC-03**: チャンネル名が空白だけの文字列、制御文字（タブ、改行、ESC を含む）または双方向の制御文字（U+202A〜U+202E、U+2066〜U+2069）を含む文字列、不正な UTF-8 の文字列、または 200 コードポイントを超える文字列である記事は、`CheckPublishable` が `ErrInvalidArticle` で拒否する。拒否の理由は値の内容を含まない。
- **AC-04**: 検査に通らないチャンネル名の記事は、ファイルにも Slack にも書き出されない。ファイルの場合、書き出しの前に失敗し、一時ファイルを残さない。Slack の場合、通信の前に失敗する。

#### F-002: Slack の投稿の構成

Slack の投稿（plain text。CLI と localhost サーバの両方）を、次の並びにする。以下、「投稿」は 1 回の記事の投稿の全体を、「メッセージ」は Slack に送る 1 通を指す。

1.  **見出し行:** タイトル。チャンネル名があるときは、同じ行にチャンネル名を続ける。
2.  空行。
3.  **本文:** `Article.Body`。末尾に従来どおり出典のブロック（`出典: <URL>`）が付く。
4.  空行。
5.  **脚注:** モデルとコストの情報（英語の固定の語。後述）。

脚注は、次の内容を 1 行で示す。

-   **モデル:** 生成・字数の調整・推敲の各段階のうち、LLM を実際に呼んだ段階と中間生成物を再利用した段階について、モデル名を示す。同じモデル名の段階は 1 つにまとめ、そのモデル名を使った段階を併記する。モデルの版は出さない。
-   **コスト:** 記事 1 本の推定コストを、現在と同じ値と書式（小数点以下 4 桁の米ドル、または `unknown`）で示す。

脚注の例（記号や強調の細部は設計で決める。H-02）:

```text
Models: deepseek-flash (generation, shorten, review) · Estimated cost: 0.0208 USD
Models: deepseek-flash (generation, shorten) · claude-haiku-5-5 (review) · Estimated cost: unknown
```

Slack の見出し行の例（記号や強調の細部は設計で決める。H-02）:

```text
タイトル（チャンネル名）
```

脚注の語は、開発者向けの情報なので英語とする。現在のメタデータの行（`- Model:`、`- Estimated cost:`）が英語であり、Go の文字列リテラルを英語とする規則（CLAUDE.md）にも合うためである。出典のラベル（`出典: `）は記事の本文の一部で、日本語のままとする。

投稿が複数のメッセージに分かれる場合も、見出し行は先頭のメッセージに 1 回だけ、脚注は最後のメッセージに 1 回だけ現れる。

**Acceptance Criteria**:
- **AC-05**: 1 通に収まる投稿は、先頭の行がタイトルで、チャンネル名があるときは同じ行にチャンネル名を含む。チャンネル名がないときは、区切り記号なども含めず、タイトルだけの行になる。
- **AC-06**: 投稿のうち本文より前にある部分は、見出し行と空行だけである。モデル名、モデルの版、コストの行は、本文より前に現れない。
- **AC-07**: 投稿の最終行は脚注で、本文のあと、出典のブロックの後ろに置く。脚注は 1 行である。複数のメッセージに分かれる場合は、最後のメッセージの最終行が脚注である。
- **AC-08**: 脚注は、モデルの版（`Model version` に当たる値）を含まない。モデルの版が空の場合と空でない場合で、脚注は変わらない。
- **AC-09**: 生成・字数の調整・推敲が同じモデル名のとき、脚注にそのモデル名は 1 回だけ現れ、3 つの段階が併記される。字数の調整が LLM を呼ばなかった（`Article.Shorten` が nil の）とき、または推敲が走らなかった（`Article.Review` が nil の）ときは、その段階を併記しない。
- **AC-10**: 段階によってモデル名が異なるとき、脚注はモデル名ごとにまとめ、各モデル名にそれを使った段階を併記する。段階の並びは、生成・字数の調整・推敲の順である。
- **AC-11**: コストが算出できるとき、脚注のコストは `Estimated cost: <小数点以下 4 桁> USD` で、値は現在の見出しのメタデータの行と同じである。算出できないとき、脚注は `Estimated cost: unknown` で、数値を出さない。
- **AC-12**: 16,383 文字を超えて複数のメッセージに分かれる記事では、見出し行は最初のメッセージにだけ、脚注は最後のメッセージにだけ現れ、どちらも 1 回だけである。脚注だけ（または空白と脚注だけ）のメッセージは作られない（その場合は従来どおり `ErrSlackUnsplittable`）。
- **AC-13**: 脚注と見出し行の文字数も、1 通あたりの上限（16,383 文字）と、メッセージ数の上限（10 通）の計算に含まれる。`SlackMessageCount` の結果は、実際に送るメッセージの数と一致する。
- **AC-14**: 「対象の `@`」を、「`@` の直後に名前の文字（文字・数字・`_`・`.`・`-`）が続き、`@` の直前が文字でも数字でもない（または先頭の）`@`」と定める（例: `@everyone`、`(@name)`、`_@here`、`x_@here`）。全角の `＠`（U+FF20）などの見た目の似た文字も、判定では `@` として扱う。見出し行（タイトルとチャンネル名）、脚注（モデル名）、本文のコードスパンとフェンス付きコードブロックの外にある対象の `@`（`＠` を含む）は、元の文字の直後に U+200B を 1 つ入れて、メンションとして扱われない形にして投稿する（拒否しない）。ただし、直前が `/` の `@`（URL の一部の可能性がある。`＠` を含む）は、無効化せず、AC-14b のとおり拒否する。ファイルの出力と `Article` の値は変えない。
- **AC-14a**: `@` の直前が文字または数字の並び（語の途中の `@`。例: チャンネル名 `Tech@Work`、タイトルや本文の `user@example.com`、`さん@xxx`）は、Mattermost のメンションにならないので、拒否もせず、変更もしない。この受理は、見出し行・脚注・本文を含む投稿の全体に適用する。
- **AC-14b**: 本文（`Article.Body`）のコードスパンとフェンス付きコードブロックの中にある対象の `@`、および直前が `/` の対象の `@` は、従来どおり、通信の前に拒否される（`ErrSlackMention`）。本文のそれ以外の中身（コードの断片を含む）は、AC-14 の U+200B を除いて変えない。
- **AC-14c**: 見出し行・脚注・本文のどこかに、メンションとして扱われうる `@` 以外の並び（`<!`・`<@`、文字参照、`<a|b>` の形）を含む記事は、従来どおり、通信の前に拒否される（`ErrSlackMention`）。拒否の判定は、見出し行と脚注を含む投稿の全体に対して行う。見出し行と脚注に使う記法の記号が値に含まれる場合の扱いは、設計で決める（H-02）。
- **AC-14d**: 複数のメッセージに分かれる投稿で、分割の位置が、`@` の直前が文字・数字の `@` を断片の先頭にしない（`x@here` を `x` と `@here` に分けない）。切る位置を動かしてもそのような並びを避けられない場合は、投稿しない（`ErrSlackUnsplittable`）。
- **AC-14e**: 対象の `@` が原因の `ErrSlackMention` の拒否で、CLI の案内は、原因が「`@` の直後に名前の文字が続く並び」であること、拒否する位置（Slack に送る形の投稿での行と列。1 行目は見出し行で、`--out` のファイルとは行がずれる）、再実行すると別の記事が生成されること、`--out` で記事を確かめられることを示す。値（`@` の後の文字列）は含めない。
- **AC-14f**: localhost サーバは、`ErrSlackMention` による拒否を、一般の投稿の失敗（`KindPublish`）とは別の失敗の種類として分類し、Slack の失敗の通知に、「記事の一部がメンションとして扱われうる形だったので投稿しなかった。送り直すと別の記事が生成される」と示す。通知は、サーバが選んだ固定の値だけで組み立てる（要求の値を含めない）。

#### F-003: ファイルの出力の構成

`--out` のファイルを、YAML のフロントマター、見出し、本文の順にする。

```text
---
channel: "Example Channel"
source: "https://www.youtube.com/watch?v=…"
model: "deepseek-flash"
model_version: "e72d3c7f…"
shorten_model: "deepseek-flash"
shorten_model_version: "e72d3c7f…"
review_model: "deepseek-flash"
review_model_version: "e72d3c7f…"
estimated_cost_usd: "0.0208"
---

# タイトル

Example Channel

本文

出典: <https://www.youtube.com/watch?v=…>
```

-   ファイルの先頭の行は `---` で、フロントマターは次の `---` の行で終わる。その後に空行、`# タイトル`、空行が続く。チャンネル名があるときは、その後にチャンネル名だけの行と空行が続く。その後に本文が続く。本文の末尾の出典のブロックは従来どおり本文の一部である。
-   チャンネル名は、フロントマターの `channel` と、見出しの下の行の両方に出す。Markdown のビューアがフロントマターを隠しても、チャンネル名が読めるようにするためである。チャンネル名がないときは、見出しの下の行も出さない。
-   キーは、上の例のとおりで、この順に並べる。`channel` は、チャンネル名があるときだけ出す。`shorten_model`・`shorten_model_version` は `Article.Shorten` があるときだけ、`review_model`・`review_model_version` は `Article.Review` があるときだけ出す。
-   値は、すべて YAML の二重引用符の文字列とする。数値として読める `estimated_cost_usd` も文字列である。引用符・バックスラッシュ・`:`・`#` などを含む値でも、フロントマターの構造は変わらず、YAML として読み戻すと元の値になる。
-   モデルの版が空のとき、値は `"(none)"` とする（現在の `(none)` の表記を引き継ぐ）。
-   推定コストは、算出できるときは小数点以下 4 桁の数値を表す文字列（例: `"0.0208"`）とし、算出できないときは `"unknown"` とする。単位は米ドルで、キー名 `estimated_cost_usd` が示す。
-   `source` は、記事の出典の URL（`Article.SourceURL`）である。

**Acceptance Criteria**:
- **AC-15**: ファイルは `---` の行で始まり、次の `---` の行までがフロントマターである。フロントマターの後は、空行をはさんで `# <タイトル>` の行が来る。チャンネル名があるときは、空行をはさんでチャンネル名の行が来る（描画した行がチャンネル名と一致する。ブロックの記法で始まる名前は、行頭をエスケープする）。その後、空行をはさんで本文が来る。フロントマターの前に、BOM や空行などの文字がない。
- **AC-16**: フロントマターのキーは、F-003 の例の名前と順序のとおりである。条件付きのキー（`channel`、`shorten_*`、`review_*`）は、条件を満たさないとき、キーごと出ない。
- **AC-17**: フロントマターの値は、すべて二重引用符の文字列である。`"` や `\` や `:` や `#` や `---` を含む値（チャンネル名・モデル名・モデルの版）を入れても、フロントマターの行数とキーの並びは変わらず、値は元の文字列に戻る（YAML の二重引用符の文字列の規則）。
- **AC-18**: モデルの版が空のとき、対応する `*_version` の値は `"(none)"` である。
- **AC-19**: 推定コストが算出できるとき `estimated_cost_usd` は `"0.0208"` のように小数点以下 4 桁で、値は現在のファイルの `- Estimated cost:` の行と同じ算出と丸めである。算出できないとき `"unknown"` である。
- **AC-20**: 見出しの下に、モデル名・モデルの版・コストの行がない（これらはフロントマターにだけある）。チャンネル名がないときは、見出しの下にチャンネル名の行も、その代わりの空行もない。
- **AC-21**: 従来の動作が変わらない: 既存のファイルを上書きしない、一時ファイルを経由して書く、書く前に `CheckPublishable` で検査する、検査に通らないときはファイルを作らない。
- **AC-22**: タイトルとチャンネル名は、従来の検査を通った値だけが書かれる（制御文字を含む値を拒否する）。

#### F-004: 文書の更新

出力の形を説明する文書を、新しい構成に合わせる。

**Acceptance Criteria**:

- **AC-25**: `docs/dev/security.md` に、チャンネル名がタイトルと同じく外部由来の表示用の文字列であり、制御文字の拒否とメンションの扱い（無効化と拒否）の対象であることを書く。メンションの拒否の規則（74 行）も、AC-14〜AC-14f に合わせて更新する。フロントマターの値が引用符で囲まれ、エスケープされることを書く。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

本タスクはチャンネル名を出力に含める。そのため、外部由来の値が出力の構造に入る境界が 1 つ増える。

| 境界 | 受理する形 | 拒否の場合 | 備考 |
|---|---|---|---|
| チャンネル名（`Article`） | 空文字（なし）、または 200 コードポイント以下で、空白だけでなく制御文字（Unicode の Cc）を含まない文字列 | `ErrInvalidArticle` | タイトルと同じ規則に、長さの上限を加える。不正な UTF-8 も拒否する。上限の根拠は設計書 §3.1。双方向の制御文字（U+202A〜U+202E、U+2066〜U+2069）は、表示の順序を入れ替えて名前を偽って見せられるので拒否する。ほかの書式制御文字（ZWJ など）は、絵文字などに正当に使われるので拒否しない。タイトルとモデル名は従来どおり拒否しない（既知のリスク。設計書 §5） |
| Slack の投稿に入る値（見出し行のタイトル・チャンネル名、脚注のモデル名、本文のコードの外） | 対象の `@`（AC-14）は U+200B で無効化する。それ以外のメンションとして扱われうる並び（`<!`・`<@`、文字参照、`<a\|b>`）は含まない。本文のコードの中と、直前が `/` の対象の `@` は含まない | `ErrSlackMention`（無効化しない `@` と、`@` 以外の並び） | 既存の `rejectMention` の対象に含める。`@` の判定は Mattermost の語の分け方を踏まえた保守的な規則とする（設計書 §3.7） |
| フロントマターの値 | 必ず二重引用符の文字列に変換できる文字列 | 変換できない値は、上の検査で先に拒否する | 変換で値を黙って変えない（制御文字の除去なども行わない） |

-   チャンネル名の長さの上限は 200 コードポイントとする。Slack の 1 通あたりの上限とメッセージ数の上限は、見出し行と脚注を含めて従来どおり適用する（AC-13）。
-   チャンネル名の検査を、LLM を呼ぶ前に行えるかは、設計で決める（H-03）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   性能に関する要件はない。出力の整形にかかる時間は、LLM の呼び出しに比べて無視できる。

### 4.2. セキュリティ (Security)

-   外部由来の値（チャンネル名、タイトル、モデル名）が、Slack の投稿の見出し行・脚注、またはファイルのフロントマターの構造を壊さない。§3.2 を参照する。
-   出典のブロックは、従来どおり、検証済みの動画 ID から作り、生成テキストにも、チャンネル名にも依存しない。
-   Webhook の URL や API キーを、出力に出さない。この扱いは変えない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   ファイルの書き出しは、従来の保証（一時ファイル、`link(2)`、上書きしない、書く前の検査）を保つ。
-   Slack の投稿の分割・再送の振る舞い（部分的な送信の扱いを含む）は、見出し行と脚注が加わることと、AC-14d の規則が加わること以外は変えない。

### 4.4. 互換性 (Compatibility)

-   ファイルの形式は、破壊的に変わる（見出しの下のメタデータの行がなくなり、フロントマターが先頭に来る）。このリポジトリの外に出力の利用者はいない（CLAUDE.md の「Declare, don't infer」と同じ前提）ので、旧形式は残さない。
-   `0006_slack_webhook_publisher` の規則 M2 は、本タスクの完了後は、語の途中の `@` を拒否しなくなる。本文を含む投稿の全体が対象で、メールアドレスなどを含む記事の拒否が減る。0006 の文書は書き換えず、設計書 §6.2 に置き換えの関係を記録する。
-   `0022_cost_estimate` の AC-23・AC-24（見出しのメタデータの料金の行）は、本タスクの完了後は当てはまらない。料金の値、丸め、不明の扱いの部分は本タスクが引き継ぐ。0022 の文書は書き換えず、本タスクの文書に置き換えの関係を記録する。

### 4.5. 保守性 (Maintainability)

-   Slack の整形とファイルの整形は、publisher ごとに分け、共通にするのは、段階ごとのモデルの一覧を作る部分など、実際に共通の部分だけとする（CLAUDE.md の DRY と YAGNI）。
-   `Article` にフィールドを追加するときは、そのフィールドが `CheckPublishable` の検査の対象になるようにする。検査をしないまま出力に出すフィールドは作らない。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   `docs/dev/security.md` の Slack への投稿の規則（メンションの拒否、分割の上限）に従う。ただし、規則 M2 は AC-14 で置き換える。
-   YAML のライブラリを追加しない（標準ライブラリだけを使う。CLAUDE.md の「Dependencies」）。フロントマターの値は二重引用符の文字列だけなので、標準ライブラリで書き出せる。
-   「出典: <URL>」のブロックは、記事の本文に連結された状態（`Article.Body`）のまま扱う。

## 6. 用語集 (Glossary)

-   **フロントマター:** Markdown のファイルの先頭にある、`---` で囲んだ YAML のメタデータ。
-   **脚注:** Slack の投稿の末尾にある、モデルとコストを示す 1 行。
-   **見出し行:** Slack の投稿の先頭にある、タイトルとチャンネル名の行。ファイルの `# タイトル` の行は、単に「見出し」と呼ぶ。
-   **出典のブロック:** 本文の末尾に付く `出典: <URL>`。
-   (その他の用語は `docs/translation_glossary.md` と統一する)
