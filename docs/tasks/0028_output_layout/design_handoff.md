# 設計への申し送り：出力の構成の見直し

本書は、[01_requirements.md](01_requirements.md) の起草で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 整形の分担と共通部分

-   **事項:** `renderArticle` の共有をやめた後の、Slack の整形・ファイルの整形・共通部分の置き場所を決める。
-   **理由:** `renderArticle` はファイルと Slack の両方が使い、`cmd/yt2column` と `internal/server` から同じ経路で呼ばれる。モデルの行の並び（生成・字数の調整・推敲）の組み立て、`modelVersionOrNone`、`articleCostLine` が共有されている。`--review-log`（`reviewlog.go`）は `modelVersionOrNone` を使う。
-   **候補の方針:** 共通にするのは、段階ごとのモデルの一覧を作る部分と、コストの文字列を作る部分に限る。ファイルの整形と Slack の整形は、それぞれの publisher のファイルに置く。
-   **関連:** F-002、F-003、§4.5

## H-02: Slack の見出し行と脚注の記法

-   **事項:** Slack の見出し行（Markdown の見出し `# タイトル` など）、チャンネル名との区切り、脚注の弱めた表示（`_…_` など）に使う記法を決める。ファイルの見出しの下のチャンネル名の行（F-003）の記法も同じ方針で決める。
-   **理由:** タイトル・チャンネル名・モデル名は、外部由来または LLM 由来の文字列で、記法の記号（`*`、`_`、`&`、`<`、`>`）を含みうる。実機の確認（01_requirements.md §1）で、投稿先は Markdown の見出しと箇条書きを描画する。そのため、記号が強調の組を壊したり、リンクや特殊な並びとして解釈されたりすると、投稿の構造が崩れる。`# ` や `- ` で始まるチャンネル名は、ファイルの見出しの下の行で見出しや箇条書きとして描画される。既存の `rejectMention` は、メンションとして扱われうる並び（M1・M2）と、書き換えられうる並び（M3・M4）だけを見ている。
-   **候補の方針:** 記法を使わない案（タイトルとチャンネル名を `—` で区切るだけ、脚注も記号なし）を、まず検討する。記法を使うなら、値に含まれる記号を拒否する（`Reject, don't normalize`）か、Slack の仕様のエスケープ（`&amp;`・`&lt;`・`&gt;`）で処理するかを決める。新しい見出し行と脚注の候補は、実機で描画を確かめてから決める。
-   **関連:** AC-05、AC-14、AC-15

## H-03: チャンネル名の検査の位置

-   **事項:** チャンネル名の検査を、`CheckPublishable`（公開の直前）だけで行うか、LLM を呼ぶ前にも行うかを決める。
-   **理由:** 公開の直前で拒否すると、LLM の費用（課金）を使った後に、記事を出せない。チャンネル名は入力の側の値で、`--after` による再開でも同じ値が使われる。localhost サーバは `channelName` を任意の文字列として受け取る。
-   **候補の方針:** 生成の前に同じ規則で検査できるなら、そちらを主とし、`CheckPublishable` は最後の砦として残す。入力の境界で検査するときの拒否の理由（サーバの `reason` の表）と、README の拒否の理由の表との整合（`serverReasons.test.ts` が README の表を読む）に注意する。
-   **関連:** AC-03、AC-04、§3.2

## H-04: フロントマターの値の書き出しと検証

-   **事項:** 二重引用符の YAML 文字列を、標準ライブラリだけで書き出す方法と、テストでの検証方法を決める。
-   **理由:** プロジェクトは YAML のライブラリを許可していない。`strconv.Quote` の出力は Go の文字列リテラルの規則で、YAML の二重引用符の規則と一致しない場合がある（例: `\x` や `\U` の形式、非 ASCII の扱い）。テストで YAML を読み戻す手段がない。
-   **候補の方針:** 検査済みの値（制御文字を含まない UTF-8）だけを対象にし、エスケープを `\\` と `\"` の 2 つに限る小さな関数を書く。テストは、その関数の出力を同じ規則の小さな読み戻しの関数で戻し、元の値と一致することを、`:`・`#`・`---`・引用符・バックスラッシュ・日本語を含む値で確かめる。
-   **関連:** AC-17

## H-05: 分割のときの見出し行と脚注の扱い

-   **事項:** `splitSlackText` が分割する対象を、本文だけにするか、見出し行と脚注を含めた全体にするかを決める。
-   **理由:** 現在は `renderArticle` の出力全体（見出しのメタデータを含む）を分割する。脚注が最後のメッセージにだけ付き、脚注だけのメッセージができないこと（AC-12）、位置の記号 `(n/m)` との関係、`slackDisplayMaxRunes` の計算を保つ必要がある。
-   **候補の方針:** 組み立てた全体の文字列を従来どおり分割し、脚注が末尾にあることで AC-12 を満たす。脚注が単独のメッセージになる境界の入力（本文の最後の改行の直後で切れる場合）を、テストで確かめる。
-   **関連:** AC-12、AC-13

## H-06: 古い文書とガードのテスト

-   **事項:** 出力の形を固定している既存のテストと、文書を読むガードのテストを洗い出し、更新する範囲を決める。
-   **理由:** `file_test.go`・`slack_message_test.go`・`slack_articles_test.go`・`cmd/yt2column/run_test.go`・`cost_test.go`・`docs_test.go` が出力の形を固定している。`0022_cost_estimate` の AC-23・AC-24 は、本タスクの完了後に当てはまらない。タスクの記録を読むガード（CLAUDE.md の「the task records」）が 0022 の記述を読んでいないかを確かめる。
-   **候補の方針:** 実装の前に `grep` で出力の形を参照するテストを列挙し、実装計画に載せる。完了したタスクの文書は書き換えない。
-   **関連:** F-004、§4.4
