## 1. 概要 (Overview)

**目的:** 本書は、localhost サーバと Native Messaging のホストに、記事の生成・状態の取得・Slack への投稿を別々の操作として加え、生成した記事をサーバのメモリに保持するための要件を定義する。拡張がこの API を使って Viewer タブ（6. 用語集で定義）に記事を表示する部分は、[#503](https://github.com/isseis/yt2column/issues/503) で扱う。

**背景:**

今のサーバの API は `POST /articles` の 1 つだけである（`internal/server/handler.go:13`）。サーバは受け付けると `202` を返し、記事の生成から Slack への投稿までを非同期に行う（`0011_localhost_server` F-005）。結果を返す API はない（`docs/dev/security.md` §8.1）。このため、拡張は結果を表示できない。結果が分からないまま利用者が送り直すと、同じ記事を 2 回生成・投稿するおそれがある（`security.md` §8.2 の残るリスク）。サーバは同じ入力の送信を区別しない（`internal/server/job.go:19` の `maxInFlight = 2` は同時実行の数を限るだけである）。

親 issue [#501](https://github.com/isseis/yt2column/issues/501) は、記事を必ずブラウザに表示し、Slack への投稿は Viewer からの利用者の操作で行う、と決めた。本タスクはそのサーバとホストの側を担う。

ホストは、拡張から受け取ったメッセージを解析せず、そのまま `POST http://yt2column/articles` へ中継する（`internal/nmhost/relay.go:45`・`:232`）。送り先は固定で、1 回の中継は 20 秒で打ち切る（`relay.go:27`）。拡張に新しい操作を使わせるには、ホストのメッセージを変える必要がある（`0026_native_messaging_relay` `02_architecture.md` §9）。

対応 issue: [#502](https://github.com/isseis/yt2column/issues/502)（親: [#501](https://github.com/isseis/yt2column/issues/501)、関連: [#503](https://github.com/isseis/yt2column/issues/503)・[#504](https://github.com/isseis/yt2column/issues/504)・[#506](https://github.com/isseis/yt2column/issues/506)）

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。対象は、各操作が何を受け取って何を返すか、状態の値、拒否の理由、キャッシュの保持と破棄、ホストが拡張の指定した操作をどの送り先に対応づけるかである。HTTP のパスとメソッド、リクエストと応答の JSON の正確な形、キーの符号化とハッシュ、コードの綴り、キャッシュのデータ構造、各上限の値、ホストのメッセージの版の表し方、テストの手段は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #502 で決めたこと（親 issue #501 の決定を含む）:**

-   **生成と投稿を分ける:** 記事は必ずブラウザに表示する。Slack への投稿は Viewer からの利用者の操作で行う（#501）。
-   **生成の開始の入力は今の `/articles` と同じ:** 拡張が送る入力（`videoUrl`・`transcript`・`title`・`channelName`・`description`）を、今と同じ規則で検査する（`internal/server/request.go:57-110`）。
-   **記事のキーは、検査を通った宣言済みのメンバから計算したハッシュとする:** 受信したバイト列からは計算しない。宣言していないメンバは今もサーバが無視するので（`request.go:62`）、キーにも含めない。符号化は、フィールドの並びや区切りに曖昧さのない形にする。処理中と完了で同じキーを使う（#501）。
-   **同じ入力では LLM を呼ばない:** 同じキーのジョブが処理中、または完了していれば、LLM を呼ばずにそのキーを返す。
-   **生成に失敗した記事はキャッシュに残さない:** 同じ入力を送り直せば、生成をやり直せる（失敗の状態と理由だけは残す。後述の「要件定義の際に決めたこと」）。
-   **状態の取得:** キーを指定して、処理中・完了・失敗・不明（再起動で失われた場合を含む）のいずれかを返す。完了なら記事も返す。拡張はこれをポーリングする。
-   **記事の中身:** 表示用の Markdown と、`--out` と同じ形式（フロントマター付き）のファイルの中身を返す。ファイル向けの整形は Go 側で行う（今の `renderFileArticle`、`internal/publisher/file_render.go:35-65`）。生成の料金と所要時間も返す（`RunUsage` と `internal/pricing` の値）。
-   **Slack への投稿はキーで指定する:** 本文は受け取らない。Slack 向けの整形は今の Go の実装に残す（#501）。同じ記事を 2 回投稿しないように、投稿済みかどうかを記事ごとに持つ。投稿だけが失敗した場合は、やり直せる。
-   **キャッシュはオンメモリ:** サーバの再起動でリセットする。コピーした字幕そのものは持たない。再生成のフラグは設けない。同じ入力で作り直したいときは、サーバを再起動する（#501）。
-   **ホストは操作を enum で受け取る:** 拡張が操作を enum で指定し、ホストがそれを送り先に対応づける。拡張に任意のパスを指定させない。
-   **状態をコードで返す（2026-10-25 の追記）:** ジョブの状態、失敗の理由、処理中の工程（issue の「段階」。下書き／本文の短縮／検証・推敲）を、文言ではなくコード（enum）で返す。拡張は、コードを見て表示する文言を選ぶ（#506）。本文の短縮は本文が 4,000 字を超えたときだけ行う（`internal/writer/length.go:9`）ので、「省略」も区別できるようにする。

**要件定義の際に決めたこと（2026-10-27）:**

-   **今の `/articles` は、今の振る舞いのまま残す:** #503 で拡張が新しい API に移るまで、今の拡張が使えなくならないようにするためである（issue の条件）。`/articles` は新しいキャッシュと関係させない。同じ入力を `/articles` に送れば、今までどおり毎回生成して投稿する。`/articles` は #503 の後に削除する。
-   **旧 API に関わるリファクタリングを issue にする:** 拡張が新しい API に移った後（#503 の後）に、`/articles` とそれだけが使うコードの削除と、新旧の API の両方に対応するために複雑になったコードの簡素化が要る。具体的な項目は本タスクの設計で決まるので、設計で項目を挙げ、実装計画の最初の作業として issue に起票する（[design_handoff.md](design_handoff.md) H-12）。削除と簡素化を忘れないようにするためである。
-   **キーは、検査を通った後の値から計算する:** 省略した任意のメンバ（`title`・`channelName`・`description`）は空文字列と同じ値とし、`videoUrl` は今の検査が正規化した後の URL（`request.go:22-27`・`:92-95`）を使う。今の検査は、省略した任意のメンバと空文字列のメンバを同じ値にする（`request.go:112-125`）。プロンプトと記事に届く値が同じ入力を、同じキーにするためである。受け取った文字列から計算すると、同じ記事になる入力を 2 回生成しうる。
-   **投稿の操作は、受け付けた時点で応答する:** 投稿の結果（投稿中・投稿済み・投稿の失敗）は、状態の取得で返す。記事は 16,383 コードポイントごとのメッセージに分けて 1 秒の間隔で送られ、1 通ごとに 30 秒で打ち切られる（`internal/publisher/slack.go:23`・`:28`）。投稿の完了を待つと、ホストの 20 秒の打ち切り（`relay.go:27`）を超えることがあるためである。
-   **`SLACK_WEBHOOK_URL` を、サーバでは任意にする:** 未設定でもサーバは起動する。投稿の操作と `/articles` は、新しい拒否の理由で拒否する。状態の取得は、投稿できるかどうかも返す。Viewer が投稿のボタンを無効にできるようにするためである。親 issue #501 の「`SLACK_WEBHOOK_URL`: サーバでは必須 → 任意」に従う。
-   **Webhook が未設定のサーバに今の拡張が送った場合の表示は、#503 までの振る舞いとして受け入れる:** 今の拡張は新しい拒否の理由を知らないので、「想定外の応答」として扱い、送り直す前に Slack を確かめるよう案内する（`extension/src/core/response.ts:22-29`、`security.md` §8.1）。Webhook を設定していない利用者は、今の拡張の経路を使えない。この案内は README に書く。既存の拒否の理由に振り替えると、その理由の意味が崩れるためである。
-   **新しい API では、失敗を Webhook へ通知しない:** 生成と投稿の失敗は、状態の取得で返す。`/articles` の失敗の通知（`failure.Notifier`）は、`/articles` を削除するまで今のまま残す。Viewer が失敗を表示できるので、Webhook への通知は重複になるためである。`/articles` の通知を止めると、今の拡張では失敗が見えなくなる。
-   **キャッシュに有限の件数の上限を設け、上限を超えたら完了または失敗した時刻の古い記録から捨てる:** 捨てる対象は、生成が完了した記事と失敗の記録である。完了または失敗した時刻の古いものから捨てる。処理中の記事と投稿中の記事は捨てない。捨てた記事のキーは「不明」になる（再起動で失われた場合と同じ）。上限の値は、記事の大きさを測ったうえで設計で決める。長く動かし続けたときにメモリが増え続けないようにするためである。
-   **分割した投稿の一部だけが失敗した場合、やり直しは届かなかった最初のメッセージから送る:** 届いたメッセージは送り直さない。失敗したメッセージは、実は届いていた可能性がある（応答を受け取れなかった場合）。その 1 通だけは重複しうることを許容する。最初から送り直すと、届いた分がすべて重複するためである。
-   **生成の同時実行の上限は、今の 2 を `/articles` と合算する:** 新しいキーの生成の開始が上限を超えたら、待ち行列に入れずに `too_many_requests` で拒否する（今の `/articles` と同じ。`0011` `02_architecture.md` §3.8.2）。処理中または完了したキーなら、上限にかかわらずそのキーを返す。新しい API のために同時に走る LLM の呼び出しを増やさないためである。
-   **生成の開始のリクエストの本文の読み込みと検査に、別の有限の上限を設ける:** 処理中または完了したキーを生成の同時実行の上限にかかわらず返すには、キーが分かるまで本文（最大 4 MiB）を読んで検査する必要がある。今の `/articles` は、枠を取ってから本文を読む（`handler.go:56-63`）。同時に読み込みと検査を行うリクエストの数を限り、超えたら本文を読まずに `too_many_requests` で拒否する。値は設計で決める。本文の読み込みと解析が際限なく並ばないようにするためである。
-   **生成に失敗したキーには、記事を持たない「失敗」の状態と失敗の理由だけを残す:** ポーリングしている Viewer が、失敗とその理由を表示できるようにするためである。同じ入力の生成の開始が来たら、生成をやり直す（issue の「キャッシュに残さない」は、再送で生成をやり直せることを指すと解釈した）。
-   **投稿中または投稿済みの記事への投稿の操作には、投稿し直さずに、受け付けたときと同じ応答を返す:** 応答を受け取れずに拡張が送り直しても、二重に投稿されないようにするためである（冪等）。
-   **生成が完了していない記事への投稿の操作は、拒否する:** 処理中なら「まだ完了していない」、失敗または不明なら「投稿できる記事がない」の拒否の理由で返す。完了したら自動で投稿する予約は設けない。
-   **ホストは、版のメンバの有無で今の形と新しい形のメッセージを区別する（CLAUDE.md「Declare, don't infer」の例外）:** 今の拡張が送るメッセージは何も宣言していないので、宣言だけでは区別できない。ホストは最上位のメンバ名だけを見て、版のメンバがあれば新しい形として検査し、なければ今の形として本文を変えずに `POST /articles` へ中継する。1 つの JSON オブジェクトとして読めないメッセージは、今の形として扱う（F-008）。例外の範囲と理由は 5. 制約条件に書く。今の拡張を変えずに動かし続けるためであり、#503 の後に今の形を削除するまでの一時的な例外である。別のホスト名を使う案は、利用者に manifest の登録をやり直させるので採らなかった。

上の決定から導いた振る舞いとして、次の 2 点を要件に含める（レビュアーは PR で確かめる）。

-   **送る前の検査で投稿を拒否される記事は、生成の完了の時点で「投稿できない」とする:** 今の投稿は、記事を送る前に、公開できる形か、本文を分割できるか、メンションを含まないかを確かめ、合わなければ 1 通も送らずに拒否する（`internal/publisher/slack_message.go:26-58`）。この検査の結果は記事だけで決まるので、何度やり直しても変わらない。新しい API では、同じ入力の生成の開始はキャッシュの記事を返し、再生成のフラグもない。このため、そのような記事は再起動して生成し直すまで投稿できない（#501 の決定の帰結）。生成の完了の時点でこの検査を行い、投稿の状態を `投稿できない` にする。Viewer が、必ず失敗する投稿のボタンを有効にしないようにするためである。記事そのものは `完了` として返し、表示とファイルへの保存はできる。
-   **生成が終わっても公開できない記事は、生成の失敗とする:** 今の `Publisher` は、記事が公開できる形か（タイトル・チャンネル名・モデル名などの表示用の文字列）を、整形の前に確かめる（`internal/writer/article.go:16`、`internal/publisher/file.go:106`）。ファイルの中身を返せない記事を「完了」としないためである。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   拡張が、生成した記事をサーバから受け取って表示できるようにする（表示そのものは #503）。
-   同じ入力の再送で、記事を 2 回生成しない。同じ記事を 2 回投稿しない。
-   Slack への投稿を、利用者が選んで行う操作にする。投稿だけが失敗した場合にやり直せるようにする。
-   状態・工程・失敗の理由をコードで返し、拡張が言語ごとの文言を選べるようにする（#506）。
-   #503 が終わるまで、今の拡張（`/articles` の経路）を今のまま使えるようにする。

### 2.2. スコープ (In Scope)

-   生成の開始の操作と、記事のキーの計算（F-001）。
-   状態と記事の取得の操作（F-002）。
-   Slack への投稿の操作と、投稿の状態の保持（F-003）。
-   オンメモリのキャッシュの保持・破棄・件数の上限（F-004）。
-   新しい拒否の理由と、状態・工程・失敗の理由のコード（F-005）。
-   `SLACK_WEBHOOK_URL` を任意にすることと、その場合の振る舞い（F-006）。
-   今の `/articles` の維持（F-007）。
-   ホストが拡張の指定した操作を送り先に対応づけること（F-008）。
-   文書: README の「Localhost server」節と設定の表、`docs/dev/security.md` §8、`docs/dev/project_overview.md`、`docs/translation_glossary.md`（F-009）。
-   旧 API に関わるリファクタリングの issue の起票（実装計画の最初の作業。1. 概要の決定）。

### 2.3. スコープ外 (Out of Scope)

-   拡張の変更（Service Worker からの送信、Viewer タブ、Viewer からの投稿と保存、新しい形の応答の検査）: #503 で扱う。本タスクの後も、拡張は `/articles` の経路を使い続ける。
-   `/articles` の削除と、新旧の API の両対応のために加えたコードの簡素化: #503 で拡張が新しい API に移った後に行う。本タスクは、その作業を issue に起票するまでを行う（[design_handoff.md](design_handoff.md) H-12）。
-   拡張の UI の多言語化: #506 で扱う。本タスクは、拡張が言語ごとに文言を選べるように、値をコードで返すだけである。
-   Markdown の描画と、描画の安全性（返した記事の中のリンクやマークアップの扱い）: #503・#504 で扱う。
-   キャッシュの永続化と、再起動をまたいだ記事と投稿の状態の保持: 親 issue #501 で、永続化しないと決めた。
-   再生成のフラグ: 親 issue #501 で、設けないと決めた。作り直すにはサーバを再起動する。
-   利用者の操作による生成の途中での取り消し: issue が求めていない（シャットダウンでの取り消しは 4.3 で定める）。
-   `.md` ファイルへの保存の操作: サーバはファイルの中身を返すだけで、ファイルを書かない。保存は拡張がブラウザのダウンロードで行う（#503）。
-   CLI（`cmd/yt2column`）の変更: CLI は `--slack` で Webhook を必須とする今の振る舞いを保つ。
-   生成の統計とダッシュボード: #505 で扱う。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 生成の開始

拡張が送る入力を受け取り、記事のキーを返す。キーの記事がまだなければ、生成を始める。

-   入力の宣言済みのメンバと検査の規則は、今の `/articles` と同じとする（`internal/server/request.go:57-110`）。拒否の理由も今と同じ（`invalid_body`・`invalid_video_url`・`invalid_transcript`・`body_too_large`・`internal_error`）。
-   キーは、検査を通った後の値（1. 概要の決定。省略した任意のメンバは空文字列、`videoUrl` は正規化した URL）から計算する。この値が 1 つでも違えばキーも違い、すべて同じならキーも同じである。メンバの順序、JSON の空白、エスケープの書き方、宣言していないメンバの有無と値、正規化で同じになる URL の書き方の違いは、キーを変えない。
-   検査の順序は次のとおりとする。パスとメソッドの検査、本文の読み込みと検査の同時実行の上限（超えたら本文を読まずに `too_many_requests`）、本文の読み込みと検査、キーの状態による振る舞い（次の表）。

| キーの状態 | 振る舞い |
|---|---|
| キャッシュにない（初めての入力、捨てた記録、再起動の後） | 生成の同時実行の上限に空きがあれば生成を始め、キーを返す。空きがなければ `too_many_requests` で拒否し、生成を始めず、キャッシュに何も加えない |
| 処理中 | 新しい生成を始めず、LLM を呼ばずにキーを返す |
| 完了 | 新しい生成を始めず、LLM を呼ばずにキーを返す。投稿の状態は変えない |
| 失敗 | 生成の同時実行の上限に空きがあれば、生成をやり直し（キーの状態は処理中になる）、キーを返す。空きがなければ `too_many_requests` で拒否し、失敗の記録はそのまま残す |

-   同じキーの生成の開始が同時に来ても、生成は 1 回だけ行う。
-   応答は、生成を始めたか、既存のジョブまたは記事を返したかを区別しない（拡張はどちらの場合も、キーの状態を取得する）。区別して返すかは設計で決めてよい。
-   新しい API の失敗は、Webhook へ通知しない（1. 概要の決定）。

**Acceptance Criteria**:
- **AC-01**: 正しい入力を送ると、キーを含む受け付けの応答が返り、そのキーの状態の取得が `処理中` または `完了` を返す（ユニットテスト）。
- **AC-02**: 同じ入力を、生成の処理中と完了の後にそれぞれ送り直すと、同じキーが返り、LLM の呼び出しの回数は 1 回の生成の分から増えない（ユニットテスト）。
- **AC-03**: メンバの順序、JSON の空白、文字のエスケープの書き方（例: `"あ"` と `"\u3042"`）、宣言していないメンバの有無と値、正規化で同じ URL になる `videoUrl` の書き方（例: `https://youtu.be/<ID>` と `https://www.youtube.com/watch?v=<ID>`）だけが違う 2 つの入力は、同じキーになる。任意のメンバを省略した入力と、そのメンバに空文字列を入れた入力も、同じキーになる（ユニットテスト）。
- **AC-04**: 検査を通った後の値のうち 1 つだけが違う 2 つの入力は、どのメンバについても違うキーになる（ユニットテスト）。
- **AC-05**: 2 つのメンバの値の境目だけを動かした入力（例: `title` が `"ab"`・`channelName` が `"c"` の入力と、`title` が `"a"`・`channelName` が `"bc"` の入力）は、違うキーになる（ユニットテスト）。
- **AC-06**: 生成が失敗したキーと同じ入力を、生成の同時実行の上限に空きがあるときに送ると、生成がやり直され（LLM の呼び出しが新たに行われ）、同じキーが返る。空きがないときに送ると `too_many_requests` で拒否され、状態の取得は `失敗` と同じ失敗の理由を返し続ける（ユニットテスト）。
- **AC-07**: 生成中のジョブが生成の同時実行の上限（`/articles` のジョブとの合計）に達しているとき、新しいキーの入力は `too_many_requests` で拒否され、生成は始まらず、そのキーの状態の取得は `不明` を返す。同じときに、処理中または完了したキーの入力は拒否されず、そのキーが返る（ユニットテスト）。
- **AC-08**: 入力の検査に失敗した場合の拒否の理由は、同じ入力を今の `/articles` に送った場合と同じであり、キャッシュには何も加わらない（ユニットテスト）。
- **AC-09**: 新しい API の生成の失敗では、Webhook への失敗の通知が行われない（ユニットテスト）。
- **AC-09a**: 本文の読み込みと検査の同時実行の上限に達しているとき、生成の開始は本文を読まずに `too_many_requests` で拒否される（ユニットテスト）。
- **AC-09b**: 同じ新しいキーの生成の開始を同時に送ると、すべてに同じキーが返り、生成（LLM の呼び出し）は 1 回分だけ行われる。失敗したキーについても同じである（ユニットテスト）。
- **AC-09c**: 完了し、投稿の状態が `投稿済み` の記事と同じ入力を送っても、投稿の状態は `投稿済み` のまま変わらない（ユニットテスト）。

#### F-002: 状態と記事の取得

キーを指定して、そのキーの状態を返す。完了していれば記事も返す。

-   状態は、`処理中`・`完了`・`失敗`・`不明` のいずれかをコードで返す（F-005）。キャッシュにないキー（再起動の後、捨てた記録、一度も使っていないキー）は `不明` であり、拒否ではない。
-   工程は `下書き`（生成）／`本文の短縮`／`検証・推敲` の 3 つで、各工程の状態は `未着手`・`実行中`・`完了`・`省略` のいずれかをコードで返す。`本文の短縮` は、下書きが完了した時点で本文が 4,000 字以下なら `省略` になる。サーバは本文の短縮と検証・推敲を常に有効にして生成する（`cmd/yt2column-server/run.go:93-98`）ので、`検証・推敲` は `省略` にならない。
-   `処理中` のときは、工程ごとの状態を返す。
-   `完了` のときは、次を返す。
    -   表示用の Markdown: 記事のタイトル、チャンネル名、本文を含む。形は設計で決める（H-05）。
    -   ファイルの中身: 同じ記事を CLI の `--out` で書き出したときと、バイト単位で同じ文字列（フロントマター・見出し・チャンネル名の行・本文。`internal/publisher/file_render.go:35-65`）。
    -   料金: 記事 1 本の料金（`internal/pricing` の `article` の合計。`pricing.go:127-140`）。料金が分からない場合は、分からないことをコードで示す。
    -   所要時間: 完了した生成を始めた受け付け（失敗の後のやり直しでは、やり直しの受け付け）から、生成が完了するまでの時間。
    -   工程ごとの状態（`完了` か `省略` だけ）。
    -   投稿の状態（F-003）。
-   `失敗` のときは、失敗の理由をコードで返す（F-005）。記事は返さない。工程ごとの状態も返し、失敗した工程が分かるようにする（失敗した工程は `実行中` のまま止まった形で示すか、別の値にするかは設計で決める。H-07）。
-   どの状態でも、このサーバで投稿の操作ができるか（`SLACK_WEBHOOK_URL` が設定されているか）を返す（F-006）。
-   状態の取得は、生成も投稿も始めない。
-   キーが受理する形でない場合は拒否する（3.2）。

**Acceptance Criteria**:
- **AC-10**: 生成の開始の直後から完了までの間、状態の取得は `処理中` を返し、工程ごとの状態が、各工程の開始と終了に合わせて `未着手`→`実行中`→`完了` と変わる。本文の短縮を行わない記事では、`本文の短縮` は下書きの完了の後に `省略` になる（ユニットテスト）。
- **AC-11**: 下書きの出力が 4,000 字以下の場合、`本文の短縮` の状態は `省略` になり、4,000 字を超える場合は `省略` にならない（ユニットテスト）。
- **AC-12**: 完了した記事の状態の取得が返すファイルの中身は、同じ記事を CLI の `--out` で書き出したファイルとバイト単位で同じである（ユニットテスト）。
- **AC-13**: 完了した記事の状態の取得は、表示用の Markdown にタイトル・チャンネル名・本文を含み、料金として `internal/pricing` の `article` の合計を返す。料金が分からない記事では、分からないことを示すコードを返す（ユニットテスト）。
- **AC-14**: 完了した記事の状態の取得が返す所要時間は、完了した生成を始めた受け付けから生成の完了までの時間である。失敗した後にやり直した記事では、やり直しの受け付けから数える（ユニットテスト）。
- **AC-15**: 一度も生成の開始に使っていないキーと、サーバの再起動の後のキーは、`不明` を返し、拒否の理由を返さない（ユニットテスト）。
- **AC-16**: 生成が失敗したキーの状態の取得は、`失敗` と、失敗の理由のコードと、失敗した工程が分かる工程ごとの状態を返し、記事を返さない（ユニットテスト）。
- **AC-17**: 状態の取得は、LLM と Webhook を呼ばない（ユニットテスト）。
- **AC-17a**: 生成が終わっても公開できない記事（今の公開が整形の前に拒否する記事）は、`失敗` と、そのことを示す失敗の理由のコードになり、記事を返さない（ユニットテスト）。

#### F-003: Slack への投稿

キーを指定して、そのキーの記事を Slack 互換の Incoming Webhook へ投稿する。本文は受け取らない。

-   投稿は受け付けた時点で応答し、投稿そのものは非同期に行う。投稿の結果は状態の取得で返す。
-   記事ごとに投稿の状態を持つ。値は `未投稿`・`投稿中`・`投稿済み`・`投稿の失敗`・`投稿できない` のいずれかで、コードで返す（F-005）。`投稿の失敗` と `投稿できない` のときは、理由もコードで返す。
-   `投稿できない` は、送る前の検査（本文の分割・メンションなど。`internal/publisher/slack_message.go:26-58`）で記事が拒否される場合で、生成の完了の時点で決まる（1. 概要の「上の決定から導いた振る舞い」）。公開できる形でない記事は、生成の `失敗` になるので `完了` にならない（F-002）。`SLACK_WEBHOOK_URL` が未設定のサーバでも、この判定は同じく行う。`投稿の失敗` は、送り始めた後の失敗（Webhook が成功を返さない、時間切れ、通信の失敗、投稿のジョブの異常終了）で、やり直せる。
-   投稿の内容（見出し・本文・脚注、分割、`silent`、メンションの扱い）は、今の `/articles` の投稿と同じとする（`internal/publisher/slack.go:158-190`・`slack_render.go:66-87`）。
-   投稿の状態とキーの状態に応じて、次のように振る舞う。

| 状態 | 振る舞い |
|---|---|
| `SLACK_WEBHOOK_URL` が未設定 | キーの状態にかかわらず、「Webhook が設定されていない」の拒否の理由で拒否する（F-006） |
| 完了・`未投稿` | 投稿を始め、受け付けの応答を返す。投稿の状態は `投稿中` になる |
| 完了・`投稿中` または `投稿済み` | 投稿し直さず、受け付けの応答を返す |
| 完了・`投稿の失敗` | まだ届いていない最初のメッセージから投稿を再開し、受け付けの応答を返す。1 通も届いていなければ、最初のメッセージから送る |
| 完了・`投稿できない` | Webhook を呼ばず、「この記事は投稿できない」の拒否の理由で拒否する。投稿の状態は変えない |
| 処理中 | 「まだ完了していない」の拒否の理由で拒否する |
| 失敗・不明 | 「投稿できる記事がない」の拒否の理由で拒否する |

-   メッセージが届いたとみなすのは、今の投稿と同じく、Webhook が成功を返した場合である（`slack.go:192-237`）。成功を返さなかったメッセージは、届いていないとみなして、やり直しで送る。そのメッセージは実は届いていた可能性があり、その 1 通だけは重複しうる（1. 概要の決定）。
-   同じキーへの投稿の操作が同時に来ても、投稿は 1 回だけ行う。
-   状態の取得は、`投稿できない` の記事について、投稿の操作ができないことを返す。
-   投稿の失敗は、Webhook へ通知しない（1. 概要の決定）。

**Acceptance Criteria**:
- **AC-18**: 完了・`未投稿` の記事への投稿の操作は、受け付けの応答を返し、その後の状態の取得は `投稿中` を経て `投稿済み` を返す。Webhook が受け取ったメッセージは、同じ記事を今の `/articles` が投稿した場合と同じである（ユニットテスト）。
- **AC-19**: 投稿の操作の応答は、Webhook が応答を返すのを待たずに返る（ユニットテスト）。
- **AC-20**: `投稿中` と `投稿済み` の記事への投稿の操作は、受け付けの応答を返し、Webhook へのメッセージの数を増やさない。同じキーへの投稿の操作を同時に送っても、Webhook が受け取るメッセージは 1 回の投稿の分だけである（ユニットテスト）。
- **AC-21**: N 通に分かれる記事で k 通目（1 ≤ k ≤ N）の投稿が失敗した場合、状態の取得は `投稿の失敗` と失敗の理由のコードを返す。その後の投稿の操作で Webhook が受け取るのは k 通目から N 通目までであり、1 通目から k−1 通目までは送り直されない（ユニットテスト。k = 1 の場合と 1 < k の場合）。
- **AC-22**: 処理中の記事への投稿の操作は「まだ完了していない」の拒否の理由で、失敗のキーと不明のキーへの投稿の操作は「投稿できる記事がない」の拒否の理由で拒否され、Webhook は呼ばれない（ユニットテスト）。
- **AC-23**: 送る前の検査で拒否される記事（メンションを含む記事、分割できない本文の記事）は、生成の完了の時点で、状態の取得が `完了` と記事を返し、投稿の状態として `投稿できない` とその理由のコードを返し、投稿の操作ができないことを返す。その記事への投稿の操作は「この記事は投稿できない」の拒否の理由で拒否され、Webhook は呼ばれない（ユニットテスト）。
- **AC-24**: 新しい API の投稿の失敗では、Webhook への失敗の通知が行われない（ユニットテスト）。

#### F-004: キャッシュ

生成した記事と、そのジョブの状態を、サーバのメモリに保持する。

-   保持するのは、キー、ジョブの状態、工程ごとの状態、完了した記事（表示用の Markdown・ファイルの中身・料金・所要時間を返せるだけの値と、投稿に必要な値）、投稿の状態、失敗の理由である。コピーした字幕そのもの（`transcript` の文字列と、解析したセグメント）は、生成が終わった後に保持しない。
-   ディスクに書かない。サーバの再起動で、すべて失われる。
-   件数に有限の上限を設ける。値は設計で決める（H-06）。上限を超えるときは、完了と失敗の記録のうち、完了または失敗した時刻の古いものから捨てる。処理中の記事と、`投稿中` の記事は捨てない。`投稿の失敗` の記事は捨てうる。捨てた後に同じ入力で生成し直して投稿すると、前に届いたメッセージも重複して投稿されうる。これは件数の上限の決定の帰結として受け入れる。
-   捨てられる記録がなく、新しいキーを加えると上限を超える場合は、生成の開始を `too_many_requests` で拒否する。
-   捨てた記録のキーは、状態の取得で `不明` を返す。同じ入力の生成の開始は、新しい生成として扱う。

**Acceptance Criteria**:
- **AC-25**: 上限の件数まで記事を完了させた後に新しいキーで生成を始めると、完了の時刻が最も古い記事が捨てられ、そのキーの状態の取得は `不明` を返す。ほかの記事は残る（ユニットテスト）。
- **AC-26**: 上限に達したとき、処理中の記事と `投稿中` の記事は、完了の時刻が古くても捨てられない（ユニットテスト）。
- **AC-26a**: 上限に達し、捨てられる記録がないとき、新しいキーの生成の開始は `too_many_requests` で拒否され、既存の記録は変わらない（ユニットテスト）。
- **AC-27**: 生成が終わった後のキャッシュの記録は、送られたコピーした字幕の文字列を含まない（ユニットテスト）。
- **AC-28**: サーバを再起動すると、前のサーバで完了した記事のキーは `不明` を返す（ユニットテスト）。

#### F-005: 状態・工程・理由のコード

新しい API の応答に含める状態・工程・理由は、文言ではなく固定のコード（enum）で返す（#506）。

-   コードの集合は閉じた集合とし、各値を README に表で示す。コードの綴りは設計で決める（H-07）。応答に文言（自然言語の文）を入れない。
-   ジョブの状態: `処理中`・`完了`・`失敗`・`不明`。
-   工程: `下書き`／`本文の短縮`／`検証・推敲`。工程の状態: `未着手`・`実行中`・`完了`・`省略`。
-   投稿の状態: `未投稿`・`投稿中`・`投稿済み`・`投稿の失敗`・`投稿できない`。
-   生成の失敗の理由: 今の失敗の通知の分類（`internal/server/job.go:109-155` の `classify`）と同じ粒度で区別する。コピーした字幕が長すぎる、LLM の時間切れ、LLM の空の応答、LLM の打ち切り、その他の LLM の失敗、内部の失敗、に加えて、公開できない記事（F-002）を区別する。
-   `投稿できない` の理由: メンションを含む、それ以外の送る前の検査で拒否される（#506 の表示の粒度に合わせて分けるかは設計で決める。H-07）。
-   投稿の失敗の理由: Webhook への送信の失敗（今の `SlackPostError` にあたる）と、内部の失敗（投稿のジョブの異常終了）。
-   新しい拒否の理由: 「まだ完了していない」、「投稿できる記事がない」、「この記事は投稿できない」、「Webhook が設定されていない」、キーが受理する形でない（既存の `invalid_body` を使うか、新しい理由にするかは設計で決める。H-07）。HTTP の状態コードも設計で決める。
-   既存の拒否の理由（`internal/server/response.go:17-72`）は、意味と状態コードを変えない。

**Acceptance Criteria**:
- **AC-29**: 新しい API の応答の状態・工程・理由の値は、README の表に挙げた値のいずれかであり、README の表はサーバが定義する値の集合と過不足なく一致する（ユニットテスト）。
- **AC-30**: 生成の失敗の分類（コピーした字幕が長すぎる・LLM の時間切れ・空の応答・打ち切り・その他の LLM の失敗・内部の失敗・公開できない記事）のそれぞれで、状態の取得は互いに違う失敗の理由のコードを返す（ユニットテスト）。
- **AC-31**: 新しい API の応答は、エラーの文言、コピーした字幕、URL、メタデータ、秘密の値を含まない。例外は、完了した記事として返す値（表示用の Markdown とファイルの中身。記事は出典の URL とタイトル・チャンネル名を含む）だけである（ユニットテスト）。

#### F-006: `SLACK_WEBHOOK_URL` を任意にする

サーバは `SLACK_WEBHOOK_URL` が未設定でも起動する。

-   未設定のとき:
    -   生成の開始と状態の取得は、設定されているときと同じく動く。
    -   状態の取得は、投稿の操作ができないことを返す。
    -   投稿の操作は、「Webhook が設定されていない」の拒否の理由で拒否する。
    -   `/articles` は、パスとメソッドの検査の後、枠を取る前に、本文を読まずに同じ拒否の理由で拒否する。ジョブを始めず、失敗の通知もしない（通知の送り先がない）。今の拡張は、これを「想定外の応答」として表示する（1. 概要の決定）。
-   設定されているとき、値の検査（`https` の URL であることなど。`internal/config/config.go:747-764`）は今と同じとする。空の値や不正な値は、今と同じく起動を止める（project_overview の「値は補正せず、空の値は未設定ではなくエラーとして扱う」方針を保つ）。
-   CLI の `--slack` が `SLACK_WEBHOOK_URL` を必須とすることは変えない。

**Acceptance Criteria**:
- **AC-32**: `SLACK_WEBHOOK_URL` が未設定で、ほかのサーバの設定が正しいとき、サーバは設定のエラーを出さずに起動する（ユニットテスト）。
- **AC-33**: `SLACK_WEBHOOK_URL` が空の値または不正な値のとき、サーバの設定の読み込みは今と同じエラーを返す（ユニットテスト）。

#### F-007: 今の `/articles` を残す

#### F-008: ホストの操作の対応づけ

ホストは、拡張が指定した操作を、サーバの送り先に対応づけて中継する。

-   拡張は、操作を閉じた集合（生成の開始・状態の取得・投稿の操作）の値で指定する。ホストは、値ごとに決めた送り先（パスとメソッド）へ中継する。拡張が送り先のパスやメソッドを指定する手段は設けない。
-   ホストは、次の順に形を決める（1. 概要の決定。5. 制約条件の例外）。まず、メッセージが 1 つの JSON オブジェクトとして読めるか（正しい UTF-8、JSON として正しい、オブジェクトである、後続のデータがない）を確かめる。読めなければ今の形とする。読めれば、最上位のメンバ名をエスケープを解いた後の名前で比べ、版のメンバがあれば新しい形、なければ今の形とする。読めるオブジェクトで版のメンバが重複する場合は、新しい形として拒否する。今の形のメッセージは、今と同じく変えずに `/articles` へ中継する。今のホストはメッセージを解析せずに中継し、読めない本文はサーバが `invalid_body` で拒否する（`0026`）ので、読めないメッセージを今の形とすれば、今の拡張から見た振る舞いは変わらない。
-   今の形のメッセージは、今と同じく、本文のバイト列を変えずに `POST /articles` へ中継する。今の拡張は 5 つの宣言済みのメンバだけを送る（`extension/src/core/prepare.ts:26-42`）ので、版のメンバを含まない。今の形の本文の中身（最上位のメンバ名を除く）は解析しない。
-   新しい形のメッセージは、版の値、操作の値、その操作に要る値（生成の開始なら入力、状態の取得と投稿の操作ならキー）だけを持つ。ホストは、版の値が知らない値の場合、操作の値が集合にない場合、メンバが足りない場合、重複する場合、宣言していないメンバがある場合、形が合わない場合、サーバにリクエストを送らずに、拡張に `protocol_error` を返す（今のホストのエラーの値の 1 つ。`internal/nmhost/relay.go:59-82`）。キーについては、ホストは JSON の文字列であることだけを確かめ、形（長さや文字の種類）は検査しない（3.2）。新しいホストのエラーの値を加えるかは、設計で決めてよい。
-   生成の開始の入力は、ホストが中身を検査せずにサーバへ渡す。入力の検査はサーバが行う（F-001。宣言していないメンバを無視して受理する規則を含む）。
-   ホストが受け取るメッセージの大きさの上限は、今と同じ 32 MiB（`relay.go:34`）とする。生成の開始の入力の上限はサーバの 4 MiB で、ホストの上限はそれより大きい。新しい形の上限を小さくするかは設計で決めてよい（H-09）。
-   中継の時間の上限（20 秒）、1 回の起動で 1 つのリクエストを中継して再送しないこと、ホストの起動の制約（拡張の origin の検査、`HOME` だけを読む、プロキシを使わない。`security.md` §8.2）は、今と同じとする。
-   ホストが中継できるサーバの応答の大きさは、完了した記事の状態の取得の応答が収まる大きさにする（H-09）。それでも上限を超える応答は、今と同じく切り詰めずに `protocol_error` を返す。

**Acceptance Criteria**:
- **AC-38**: 新しい形のメッセージで指定した 3 つの操作のそれぞれで、ホストは、その操作に決めた送り先へ、1 回だけリクエストを送る（ユニットテスト）。
- **AC-39**: 今の拡張が送る形のメッセージと、1 つの JSON オブジェクトとして読めないメッセージ（版のメンバらしい文字列を含んでいても、不正な UTF-8 や後続のデータがあるもの）は、今と同じく `POST /articles` へ、本文を変えずに中継される（ユニットテスト）。
- **AC-40**: 版のメンバの名前をエスケープで書いたメッセージは、新しい形として扱われる。新しい形のメッセージで、版の値が知らない値の場合、版のメンバが重複する場合、操作の値が集合にない場合、メンバが足りない場合、重複する場合、宣言していないメンバがある場合、ホストはサーバにリクエストを送らずに、`protocol_error` を返す（ユニットテスト）。
- **AC-40a**: 新しい形のメッセージのキーが文字列であれば、ホストは形（長さや文字の種類）にかかわらず、その文字列を変えずにサーバへ渡す。キーが文字列でなければ `protocol_error` を返す（ユニットテスト）。
- **AC-41**: 状態の取得で、設計で決めた最大の大きさの記事（完了の状態）を返す応答を、ホストは切り詰めずに中継する（ユニットテスト）。
- **AC-41a**: 新しい形のメッセージの中継でも、中継の時間の上限（20 秒）を超えると `server_timeout` を返し、リクエストを再送しない（ユニットテスト）。

#### F-009: 文書

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

サーバと同じ利用者の権限で動くプロセスは信頼する（`security.md` §8）。ただし、生成の開始の入力のコピーした字幕とメタデータは、プロンプトに埋め込まれる untrusted なテキストである（`security.md` §6）。境界の検査は、今の `/articles` と同じ厳しさで行う。

| 境界 | 受理する形 | 上限 | 失敗・拒否時の扱い | 主な AC |
|---|---|---|---|---|
| 生成の開始の本文 | 今の `/articles` と同じ（1 つの JSON オブジェクト、正しい UTF-8、対になっていないサロゲートのエスケープを含まない、後続のデータがない。宣言済みのメンバは `videoUrl`・`transcript`・`title`・`channelName`・`description` で、宣言済みのメンバの重複は拒否する。宣言していないメンバは今と同じく無視して受理する。`request.go:57-110`） | 今と同じ 4 MiB（`request.go:18`） | 今と同じ拒否の理由（`invalid_body`・`invalid_video_url`・`invalid_transcript`・`body_too_large`・`internal_error`）。キャッシュに何も加えない | AC-03・AC-08 |
| 状態の取得と投稿の操作のキー | 設計で決めた形（ハッシュの値の固定長の文字列など）だけを受理する。大文字と小文字の違い、前後の空白、余分な文字を補正しない | 形で決まる | キーが受理する形でない場合の拒否の理由（F-005、H-07）。キャッシュを変えない | AC-44 |
| 状態の取得と投稿の操作のリクエストの、キーのほかの部分（本文・クエリ） | 設計で決める形だけを受理する。本文を使わない操作に本文やクエリがあれば拒否する。本文を使う場合は、宣言済みのメンバを閉じた集合とし、宣言していないメンバと重複するメンバを拒否し（新しい操作には、今の拡張との互換のために未知のメンバを許す理由がない）、生成の開始と同じ全体の検査（UTF-8・単一の値・後続のデータなし）を行う | 設計で決める（生成の開始より小さい上限） | `invalid_body`（または H-07 で決める理由） | AC-44 |
| ホストが受け取る新しい形のメッセージ | 版の値、操作の値（閉じた集合）、その操作に要る値だけを持つ形。1 つの JSON オブジェクトとして読めること（F-008 の最初の判定）を前提に、最上位では、宣言していないメンバと重複するメンバを拒否する（拡張可能と宣言しない）。生成の開始の入力の中身はホストでは検査せず、サーバの境界（1 行目）に任せる | 今と同じ 32 MiB（`relay.go:34`） | サーバにリクエストを送らずに `protocol_error`（F-008） | AC-40 |
| ホストが受け取る今の形のメッセージ | 最上位に版のメンバを持たない JSON オブジェクトと、JSON オブジェクトとして読めないメッセージ。最上位のメンバ名のほかは解析せず、バイト列を変えずに中継する（`0026`） | 今と同じ 32 MiB | サーバの検査が境界である（今と同じ） | AC-39 |

-   キーは、生成の開始の応答でサーバが返した値を、拡張がそのまま送り返すものである。拡張とホストは、キーを不透明な値として扱う。形を検査せず、中身から何も導かず、計算方法に依存しない。キーの形と計算方法はサーバの内部の事柄であり、変えても拡張とホストは変わらない。キーの形を検査するのはサーバだけである（AC-44）。サーバは、受け取ったキーを、キャッシュを引く値としてだけ使い、ファイルのパスやログの書式などに埋め込まない。

**Acceptance Criteria**:
- **AC-44**: 状態の取得と投稿の操作で、受理する形でないキー（短すぎる・長すぎる・受理しない文字を含む・大文字と小文字だけが違う・前後に空白がある）は拒否され、キャッシュは変わらない。本文を使わない操作に本文やクエリがあるリクエスト、本文を使う操作で宣言していないメンバ・重複するメンバ・不正な UTF-8・後続のデータを含む本文も拒否される（ユニットテスト）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   状態の取得と投稿の操作の受け付けは、LLM と Webhook を待たずに応答する（F-002・F-003）。ホストの 20 秒の打ち切りの中に収まればよく、性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   キーの計算は、生成の開始のたびに検査を通った値の全体に対して行う。LLM の呼び出しに比べて無視できる時間であり、計算を省く仕組みは設けない。

### 4.2. セキュリティ (Security)

本タスクは、ネットワークへの送信（LLM API・Webhook）、Webhook の URL、プロンプトに埋め込む untrusted なテキストを扱うので、`docs/dev/security.md` を適用する。

-   **待ち受けの範囲:** 新しい操作も、今と同じ Unix ドメインソケットの上だけで受ける。TCP を待ち受けない（`security.md` §8.2）。
-   **固定の値だけを返す:** 新しい API の応答は、完了した記事として返す値（表示用の Markdown とファイルの中身）を除き、コードとして定めた固定の値、キー、数値だけを含む。エラーの文言、Webhook の URL、API キーを含まない（F-005、AC-31。今の `0011` F-008 と同じ方針）。
-   **返す記事は untrusted なテキスト:** 表示用の Markdown とファイルの中身は、LLM が生成した文章であり、コピーした字幕とメタデータへのプロンプトインジェクションで操作されうる（`security.md` §6）。サーバは、公開できる記事か（F-002）を確かめるほかは、記事を変えずに返す。受け取った側での描画の安全性（リンク、HTML、スクリプトの扱い）は、#503・#504 で扱う。
-   **ログ:** 新しい操作のログも、今の方針（`0011` `02_architecture.md` §3.10）に従う。1 つの出来事を 1 行で、固定の属性だけを出す。本文、コピーした字幕、`videoUrl` の文字列、メタデータ、記事の本文、秘密の値を出さない。ログは今と同じく `redact.Writer` を通す。キーをログに出すかどうかは設計で決める（H-10）。
-   **メモリに持つ値:** キャッシュは、記事（コピーした字幕から作られ、その内容を含みうる）を、サーバの再起動まで、または捨てられるまでメモリに持つ。コピーした字幕そのものは持たない（F-004）。ディスクに書かないので、`project_overview.md` の「処理を終えた動画の文字起こしをローカルに残し続けない」方針に反しない。
-   **投稿の操作は利用者の操作:** 同じ利用者の権限のプロセスはキーを知れば投稿を求められるが、そのプロセスは今も `/articles` で投稿を求められる。信頼の境界は今と変わらない（`security.md` §8）。
-   **資源の上限:** 本文の読み込みと検査、生成、キャッシュの件数のそれぞれに有限の上限を設ける（F-001・F-004）。
-   **二重の投稿の防止:** 投稿の操作は冪等にし（F-003）、`security.md` §8.2 の残るリスク（再送による二重の生成と投稿）を、新しい API の経路では、分割した投稿の失敗したメッセージ 1 通の重複と、捨てた記録や再起動の後の投稿し直しに減らす。`/articles` の経路のリスクは、削除するまで残る。
-   **ホスト:** 拡張に任意のパスを指定させない（F-008）。ホストの起動の制約（origin の検査、`HOME` だけを読む、プロキシを使わない、再送しない）を保つ。
-   **プロンプトへの埋め込み:** コピーした字幕とメタデータを記事生成のプロンプトに埋め込むことは変えない。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   サーバの再起動で、キャッシュと投稿の状態はすべて失われる。再起動の後、状態の取得は `不明` を返す。投稿済みかどうかも失われるので、再起動の前に投稿した記事を、再起動の後に同じ入力で生成し直して投稿すれば、同じ内容の記事がもう一度投稿されうる。これは親 issue #501 で受け入れた仕様（キャッシュを永続化しない）の帰結として受け入れる。
-   キャッシュの件数の上限（F-004）で、長く動かし続けてもメモリが増え続けない。
-   シャットダウンでは、新しい API の処理中の生成のジョブを取り消す。記事のキャッシュはサーバの終了で失われ、シャットダウンの後に完了した記事は誰も受け取れないので、待っても LLM の料金と再起動の遅れが生じるだけであるため（2026-10-27、設計の際の決定）。`/articles` の処理中のジョブは、今と同じく取り消さずに完了まで待つ（`0011` `02_architecture.md` §3.8.3）。処理中の投稿のジョブも完了まで待つ。待つ時間の上限は設計で決める（H-11）。上限を超えて終わった投稿では、最後に送ったメッセージが届いたかどうかが分からないまま記録が失われるので、再起動の後に同じ記事を投稿し直すと、届いたメッセージが重複しうる。
-   生成のジョブの中の panic は、今と同じく回復し、そのキーを `失敗`（内部の失敗）にする。投稿のジョブの中の panic も回復し、投稿の状態を `投稿の失敗`（内部の失敗）にする。届いたメッセージの記録は残し、やり直しは届かなかった最初のメッセージから送る。サーバは動き続ける。

**Acceptance Criteria**:
- **AC-45**: 生成のジョブの中で panic が起きると、そのキーの状態の取得は `失敗` と内部の失敗の理由を返し、サーバはその後のリクエストに応答する（ユニットテスト）。
- **AC-45a**: 投稿のジョブの中で panic が起きると、投稿の状態は `投稿の失敗` と内部の失敗の理由になり、その後の投稿の操作は届かなかった最初のメッセージから投稿を再開する（ユニットテスト）。
- **AC-46**: シャットダウンを始めたとき、新しい API の処理中の生成のジョブは取り消され、LLM の呼び出しが打ち切られる。処理中の投稿のジョブと `/articles` のジョブは取り消されず、完了してからサーバが終わる（ユニットテスト）。

### 4.4. 互換性 (Compatibility)
-   今の拡張（`/articles` の経路）は、本タスクの後も、変更なしで動く（F-007・F-008）。拡張のコードとテストは変えない。例外は、`SLACK_WEBHOOK_URL` が未設定のサーバでは今の拡張の送信が「想定外の応答」になることで、#503 までの振る舞いとして受け入れた（1. 概要の決定）。今の版のサーバは Webhook が未設定では起動しないので、今の設定のまま動いている利用者には影響しない。
-   CLI の振る舞い（`--slack` での `SLACK_WEBHOOK_URL` の必須を含む）は変えない。
-   ホストの今の形のメッセージ、ホストの応答の形（`{"v":1,"kind":"response",...}`・`{"v":1,"kind":"error",...}`）、ホストのエラーの値は、今の拡張が受け取る範囲で変えない。新しい形のメッセージの応答の形を変えるかは設計で決める（H-08）。

### 4.5. 保守性 (Maintainability)
-   ジョブの状態・工程の状態・投稿の状態・失敗の理由・拒否の理由・ホストの操作は、型（列挙）で表す。応答とログは、その型で振る舞いを選び、エラーの文言から推し量らない（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。各列挙の零値は、最も多くを仮定しない解釈にする（どの値かは設計で決める。H-07）。
-   ファイルの中身と Slack の投稿の整形は、今の `internal/publisher` の関数を使い、新しいコードで整形を二重に実装しない（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   `/articles` の削除が、新しい API の振る舞いを変えずにできるように、`/articles` に固有の振る舞い（自動の投稿、失敗の通知、今の形のメッセージの中継）を新しい API から分ける。削除の項目は設計で挙げる（H-12）。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。本タスクは、同書の次の記述を変えるので、F-009 で同書を更新する（親 issue #501「project_overview の方針の変更」）。
    -   「決定済みの方針」の「実行形式」: localhost サーバは「記事を生成して Slack へ投稿する」→「記事を生成して保持し、求めに応じて返す・投稿する」（`/articles` は削除するまで残る）。
    -   「設定（環境変数）」の `LoadServer` の段落: 「`SLACK_WEBHOOK_URL` を必須とする」→「任意とし、未設定なら投稿の操作と `/articles` を拒否する」。
    -   「前提・制約」のキャッシュの段落: 字幕・info.json のディスクのキャッシュとは別に、サーバが記事をメモリに持つこと。
-   **CLAUDE.md「Declare, don't infer」の例外（ホストのメッセージの形の区別）:**
    -   方針: 呼び出し側が渡した文字列の中身を調べて振る舞いを選ばない（[CLAUDE.md](../../../CLAUDE.md)「Key Design Patterns」）。
    -   範囲: ホスト（`internal/nmhost`）が、拡張から受け取ったメッセージが 1 つの JSON オブジェクトとして読めるかどうかと、その最上位に版のメンバがあるかどうかで、今の形と新しい形を選ぶ箇所だけとする（F-008）。新しい形の中では、操作は宣言した値（列挙）で選ぶ。
    -   理由: 今の拡張が送るメッセージは何も宣言しておらず、本タスクでは拡張を変えない（2.3）。今の形を区別するには、宣言がないことを見るしかない。
    -   境界: 読めるオブジェクトに版のメンバがあれば、新しい形として厳格に検査し、合わなければ拒否する（今の形として扱い直さない）。読めないメッセージは、今と同じくサーバが拒否する。今の形は #503 の後に削除し、この例外もそのときに取り除く（H-12）。
-   以前のタスクの方針の変更:
    -   `0011_localhost_server` `01_requirements.md` §2.3 は、記事・進み具合を返すこととポーリングをスコープ外とし、F-007 は認証の後の失敗を Slack に通知するとした。本タスクは、新しい API で記事と進み具合を返し、新しい API の失敗を Slack に通知しない。理由は、親 issue #501 が、記事をブラウザに表示し、失敗の通知先を Viewer にすると決めたことである。`/articles` の通知は残す。
    -   `0011` `02_architecture.md` §3.8.2 は、枠を取ってから本文を読むとした。新しい API の生成の開始は、キーが分かるまで本文を読む必要があるので、枠の前に本文を読み、その読み込みに別の上限を設ける（1. 概要の決定）。
    -   `0026_native_messaging_relay` `01_requirements.md` §2.3 は、ポーリングと、拡張での成功・失敗の表示をスコープ外とした。`02_architecture.md` §9 は、ホストが `POST /articles` だけを送るとした。本タスクは、ホストが操作の値を送り先に対応づけるようにする。理由は同じく #501 の決定である。
-   外部ライブラリを加えない。ハッシュは標準ライブラリで計算する（[CLAUDE.md](../../../CLAUDE.md)「Dependencies」）。
-   ユニットテストは、LLM API・Webhook・実際のブラウザを呼ばない。`ArticleWriter`・`LLMClient`・Webhook は fake に置き換える。テストの組み立て方は設計で決める（H-13）。
-   拡張のコードとテストを変えない（#503 で変える）。

## 6. 用語集 (Glossary)

-   **0011**: localhost サーバのタスク（`docs/tasks/0011_localhost_server/`）。
-   **0026**: Native Messaging のホストのタスク（`docs/tasks/0026_native_messaging_relay/`）。
-   **新しい API**: 本タスクで加える 3 つの操作（生成の開始・状態の取得・投稿の操作）。`/articles` を含まない。
-   **生成の開始**: 拡張が送る入力を受け取り、記事のキーを返し、必要なら生成のジョブを始める操作。
-   **状態の取得**: キーを指定して、ジョブの状態・工程の状態・投稿の状態と、完了なら記事を返す操作。
-   **投稿の操作**: キーを指定して、その記事を Slack 互換の Incoming Webhook へ投稿する操作。
-   **記事のキー**: 生成の開始の入力の、検査を通った後の値からサーバが計算するハッシュ。新しい API で記事を指す値。拡張とホストにとっては不透明な値で、形にも計算方法にも依存しない（3.2）。
-   **記事のキャッシュ**: サーバがメモリに持つ、キーごとのジョブの状態と記事。`translation_glossary.md` の「キャッシュ」（ディスクの字幕・info.json の保存）とは別のものなので、本書では「キャッシュ」と書いたときも、記事のキャッシュを指す。
-   **ジョブの状態**: `処理中`・`完了`・`失敗`・`不明`。
-   **工程**: `ArticleWriter` の中の 3 つの処理（下書き／本文の短縮／検証・推敲）。コードの `step` にあたる。issue は「段階」と書くが、`translation_glossary.md` の「段階」（パイプラインの段階）と区別するため、本書では「工程」と書く。
-   **工程の状態**: 工程ごとの `未着手`・`実行中`・`完了`・`省略`。
-   **投稿の状態**: `未投稿`・`投稿中`・`投稿済み`・`投稿の失敗`・`投稿できない`。
-   **コピーした字幕**: 拡張が送る `transcript` の文字列（`translation_glossary.md`）。
-   **Viewer**: #503 で拡張に加える、記事を表示するタブ（`viewer.html`）。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
