## 1. 概要 (Overview)

**目的:** 本書は、localhost サーバと Native Messaging のホストに、記事の生成・状態の取得・Slack への投稿を別々の操作として加え、生成した記事をサーバのメモリに保持するための要件を定義する。拡張がこの API を使って Viewer タブに記事を表示する部分は、[#503](https://github.com/isseis/yt2column/issues/503) で扱う。

**背景:**

今のサーバの API は `POST /articles` の 1 つだけである（`internal/server/handler.go:13`）。サーバは受け付けると `202` を返し、記事の生成から Slack への投稿までを非同期に行う（`0011_localhost_server` F-005）。結果を返す API はない（`docs/dev/security.md` §8.1）。このため、拡張は結果を表示できない。結果が分からないまま利用者が送り直すと、同じ記事を 2 回生成・投稿するおそれがある（`security.md` §8.2 の残るリスク）。サーバは同じ入力の送信を区別しない（`internal/server/job.go:19` の `maxInFlight = 2` は同時実行の数を限るだけである）。

親 issue [#501](https://github.com/isseis/yt2column/issues/501) は、記事を必ずブラウザに表示し、Slack への投稿は Viewer からの利用者の操作で行う、と決めた。本タスクはそのサーバとホストの側を担う。

ホストは、拡張から受け取ったメッセージを解析せず、そのまま `POST http://yt2column/articles` へ中継する（`internal/nmhost/relay.go:45`・`:232`）。送り先は固定で、1 回の中継は 20 秒で打ち切る（`relay.go:27`）。拡張に新しい操作を使わせるには、ホストのメッセージを変える必要がある（`0026_native_messaging_relay` `02_architecture.md` §9）。

対応 issue: [#502](https://github.com/isseis/yt2column/issues/502)（親: [#501](https://github.com/isseis/yt2column/issues/501)、関連: [#503](https://github.com/isseis/yt2column/issues/503)・[#506](https://github.com/isseis/yt2column/issues/506)）

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。対象は、各操作が何を受け取って何を返すか、状態の値、拒否の理由、キャッシュの保持と破棄、ホストが拡張の指定した操作をどの送り先に対応づけるかである。HTTP のパスとメソッド、リクエストと応答の JSON の正確な形、キーの計算に使うハッシュと符号化、キャッシュのデータ構造、件数の上限の値、ホストのメッセージの版の表し方、応答の大きさの上限、テストの手段は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #502 で決めたこと（親 issue #501 の決定を含む）:**

-   **生成と投稿を分ける:** 記事は必ずブラウザに表示する。Slack への投稿は Viewer からの利用者の操作で行う（#501）。
-   **生成の開始の入力は今の `/articles` と同じ:** 拡張が送る入力（`videoUrl`・`transcript`・`title`・`channelName`・`description`）を、今と同じ規則で検査する（`internal/server/request.go:57-110`）。
-   **記事のキーは、検査を通った宣言済みのメンバから計算したハッシュとする:** 受信したバイト列からは計算しない。宣言していないメンバは今もサーバが無視するので（`request.go:62`）、キーにも含めない。符号化は、フィールドの並びや区切りに曖昧さのない形にする。処理中と処理済みで同じキーを使う（#501）。
-   **同じ入力では LLM を呼ばない:** 同じキーのジョブが処理中、または記事が処理済みなら、LLM を呼ばずにそのキーを返す。
-   **生成に失敗した記事はキャッシュに残さない:** 同じ入力を送り直せば、生成をやり直せる。
-   **状態の取得:** キーを指定して、処理中・完了・失敗・不明（再起動で失われた場合を含む）のいずれかを返す。完了なら記事も返す。拡張はこれをポーリングする。
-   **記事の中身:** 表示用の Markdown と、`--out` と同じ形式（フロントマター付き）のファイルの中身を返す。ファイル向けの整形は Go 側で行う（今の `renderFileArticle`、`internal/publisher/file_render.go:35-65`）。生成の料金と所要時間も返す（`RunUsage` と `internal/pricing` の値）。
-   **Slack への投稿はキーで指定する:** 本文は受け取らない。Slack 向けの整形は今の Go の実装に残す（#501）。同じ記事を 2 回投稿しないように、投稿済みかどうかを記事ごとに持つ。投稿だけが失敗した場合は、やり直せる。
-   **キャッシュはオンメモリ:** サーバの再起動でリセットする。字幕そのものは持たない。再生成のフラグは設けない。同じ入力で作り直したいときは、サーバを再起動する（#501）。
-   **ホストは操作を enum で受け取る:** 拡張が操作を enum で指定し、ホストがそれを送り先に対応づける。拡張に任意のパスを指定させない。
-   **状態をコードで返す（2026-10-25 の追記）:** ジョブの状態、失敗の理由、処理中の段階（下書き・本文の短縮・字幕との照合）を、文言ではなくコード（enum）で返す。拡張は、コードを見て表示する文言を選ぶ（#506）。本文の短縮は本文が 4,000 字を超えたときだけ行う（`internal/writer/length.go:9`）ので、「省略」も区別できるようにする。

**要件定義の際に決めたこと（2026-10-27）:**

-   **今の `/articles` は、今の振る舞いのまま残す:** #503 で拡張が新しい API に移るまで、今の拡張が使えなくならないようにするためである（issue の条件）。`/articles` は新しいキャッシュと関係させない。同じ入力を `/articles` に送れば、今までどおり毎回生成して投稿する。`/articles` は #503 で削除する。
-   **投稿の操作は、受け付けた時点で応答する:** 投稿の結果（投稿中・投稿済み・投稿の失敗）は、状態の取得で返す。記事は 16,383 コードポイントごとのメッセージに分けて 1 秒の間隔で送られ、1 通ごとに 30 秒で打ち切られる（`internal/publisher/slack.go:23`・`:28`）。投稿の完了を待つと、ホストの 20 秒の打ち切り（`relay.go:27`）を超えることがあるためである。
-   **`SLACK_WEBHOOK_URL` を、サーバでは任意にする:** 未設定でもサーバは起動する。投稿の操作と `/articles` は、新しい拒否の理由で拒否する。状態の取得は、投稿できるかどうかも返す。Viewer が投稿のボタンを無効にできるようにするためである。親 issue #501 の「`SLACK_WEBHOOK_URL`: サーバでは必須 → 任意」に従う。
-   **新しい API では、失敗を Webhook へ通知しない:** 生成と投稿の失敗は、状態の取得で返す。`/articles` の失敗の通知（`failure.Notifier`）は、`/articles` を削除するまで今のまま残す。Viewer が失敗を表示できるので、Webhook への通知は重複になるためである。`/articles` の通知を止めると、今の拡張では失敗が見えなくなる。
-   **キャッシュに有限の件数の上限を設け、上限を超えたら完了の古い記事から捨てる:** 捨てる対象は、生成が完了した記事と失敗の記録である。完了または失敗した時刻の古いものから捨てる。処理中の記事と投稿中の記事は捨てない。捨てた記事のキーは「不明」になる（再起動で失われた場合と同じ）。上限の値は、記事の大きさを測ったうえで設計で決める。長く動かし続けたときにメモリが増え続けないようにするためである。
-   **分割した投稿の一部だけが失敗した場合、やり直しは届かなかった最初のメッセージから送る:** 届いたメッセージは送り直さない。失敗したメッセージは、実は届いていた可能性がある（応答を受け取れなかった場合）。その 1 通だけは重複しうることを許容する。最初から送り直すと、届いた分がすべて重複するためである。
-   **生成の同時実行の上限は、今の 2 を `/articles` と合算する:** 新しいキーの生成の開始が上限を超えたら、待ち行列に入れずに `too_many_requests` で拒否する（今の `/articles` と同じ。`0011` `02_architecture.md` §3.8.2）。処理中または処理済みのキーなら、上限にかかわらずそのキーを返す。新しい API のために同時に走る LLM の呼び出しを増やさないためである。
-   **生成に失敗したキーには、記事を持たない「失敗」の状態と失敗の理由だけを残す:** ポーリングしている Viewer が、失敗とその理由を表示できるようにするためである。同じ入力の生成の開始が来たら、生成をやり直す（issue の「キャッシュに残さない」は、再送で生成をやり直せることを指すと解釈した）。
-   **投稿中または投稿済みの記事への投稿の操作には、投稿し直さずに、受け付けたときと同じ応答を返す:** 応答を受け取れずに拡張が送り直しても、二重に投稿されないようにするためである（冪等）。
-   **旧 API に関わるリファクタリングを issue にする:** 拡張が新しい API に移った後（#503 の後）に、`/articles` とそれだけが使うコードの削除と、新旧の API の両方に対応するために複雑になったコードの簡素化が要る。具体的な項目は本タスクの設計で決まるので、設計で項目を挙げ、実装計画の最初の作業として issue にしてファイルする（[design_handoff.md](design_handoff.md) H-12）。削除と簡素化を忘れないようにするためである。
-   **生成が完了していない記事への投稿の操作は、拒否する:** 処理中なら「まだ完了していない」、失敗または不明なら「投稿できる記事がない」の拒否の理由で返す。完了したら自動で投稿する予約は設けない。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   拡張が、生成した記事をサーバから受け取って表示できるようにする（表示そのものは #503）。
-   同じ入力の再送で、記事を 2 回生成しない。同じ記事を 2 回投稿しない。
-   Slack への投稿を、利用者が選んで行う操作にする。投稿だけが失敗した場合にやり直せるようにする。
-   状態・段階・失敗の理由をコードで返し、拡張が言語ごとの文言を選べるようにする（#506）。
-   #503 が終わるまで、今の拡張（`/articles` の経路）を今のまま使えるようにする。

### 2.2. スコープ (In Scope)

-   生成の開始の操作と、記事のキーの計算（F-001）。
-   状態と記事の取得の操作（F-002）。
-   Slack への投稿の操作と、投稿の状態の保持（F-003）。
-   オンメモリのキャッシュの保持・破棄・件数の上限（F-004）。
-   新しい拒否の理由と、状態・段階・失敗の理由のコード（F-005）。
-   `SLACK_WEBHOOK_URL` を任意にすることと、その場合の振る舞い（F-006）。
-   今の `/articles` の維持（F-007）。
-   ホストが拡張の指定した操作を送り先に対応づけること（F-008）。
-   文書: README の「Localhost server」節と設定の表、`docs/dev/security.md` §8、`docs/dev/project_overview.md`（F-009）。

### 2.3. スコープ外 (Out of Scope)

-   拡張の変更（Service Worker からの送信、Viewer タブ、Viewer からの投稿と保存）: #503 で扱う。本タスクの後も、拡張は `/articles` の経路を使い続ける。
-   `/articles` の削除と、新旧の API の両対応のために加えたコードの簡素化: #503 で拡張が新しい API に移った後に行う。本タスクは、その作業を issue にしてファイルするまでを行う（実装計画の最初の作業。[design_handoff.md](design_handoff.md) H-12）。
-   拡張の UI の多言語化: #506 で扱う。本タスクは、拡張が言語ごとに文言を選べるように、値をコードで返すだけである。
-   Markdown の描画: #504 で扱う。
-   キャッシュの永続化と、再起動をまたいだ記事の保持: 親 issue #501 で、永続化しないと決めた。
-   再生成のフラグ: 親 issue #501 で、設けないと決めた。作り直すにはサーバを再起動する。
-   生成の途中での取り消し: issue が求めていない。
-   `.md` ファイルへの保存の操作: サーバはファイルの中身を返すだけで、ファイルを書かない。保存は拡張がブラウザのダウンロードで行う（#503）。
-   CLI（`cmd/yt2column`）の変更: CLI は `--slack` で Webhook を必須とする今の振る舞いを保つ。
-   生成の統計とダッシュボード: #505 で扱う。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 生成の開始

拡張が送る入力を受け取り、記事のキーを返す。キーの記事がまだなければ、生成を始める。

-   入力の宣言済みのメンバと検査の規則は、今の `/articles` と同じとする（`internal/server/request.go:57-110`）。拒否の理由も今と同じ（`invalid_body`・`invalid_video_url`・`invalid_transcript`・`body_too_large`・`internal_error`）。
-   キーは、検査を通った宣言済みのメンバの値から計算する。宣言済みのメンバの値が 1 つでも違えば、キーも違う。メンバの順序、JSON の空白、エスケープの書き方、宣言していないメンバの有無と値が違っても、宣言済みのメンバの値が同じならキーは同じである。省略した任意のメンバ（`title`・`channelName`・`description`）と、空文字列を入れた同じメンバは、違う入力として扱う（今の検査は、空文字列の任意のメンバを受理する。`request.go:112-125`）。
-   キーに使う `videoUrl` の値は、今の検査が正規化した後の URL か、受け取った文字列か、を設計で決める（H-02）。どちらにしても、F-001 の他の規則は変わらない。
-   キーの状態に応じて、次のように振る舞う。

| キーの状態 | 振る舞い |
|---|---|
| キャッシュにない（初めての入力、捨てた記事、再起動の後） | 同時実行の上限に空きがあれば生成を始め、キーを返す。空きがなければ `too_many_requests` で拒否し、生成を始めない |
| 処理中 | 新しい生成を始めず、LLM を呼ばずにキーを返す |
| 完了 | 新しい生成を始めず、LLM を呼ばずにキーを返す。投稿の状態は変えない |
| 失敗 | 失敗の記録を消して生成をやり直し、キーを返す（同時実行の上限の扱いは「キャッシュにない」と同じ） |

-   応答は、生成を始めたか、既存のジョブまたは記事を返したかを区別しない（拡張はどちらの場合も、キーの状態を取得する）。区別して返すかは設計で決めてよい。
-   新しい API の失敗は、Webhook へ通知しない（F-006）。

**Acceptance Criteria**:
- **AC-01**: 正しい入力を送ると、キーを含む受け付けの応答が返り、そのキーの状態の取得が「処理中」または「完了」を返す（ユニットテスト。fake の `ArticleWriter`）。
- **AC-02**: 同じ宣言済みのメンバの値を持つ入力を、生成の処理中と完了の後にそれぞれ送り直すと、同じキーが返り、LLM（fake）の呼び出しの回数は 1 回の生成の分から増えない（ユニットテスト）。
- **AC-03**: メンバの順序、JSON の空白、文字のエスケープの書き方（例: `"あ"` と `"あ"`）、宣言していないメンバの有無と値だけが違う 2 つの入力は、同じキーになる（ユニットテスト）。
- **AC-04**: 宣言済みのメンバのうち 1 つの値だけが違う 2 つの入力は、どのメンバについても違うキーになる。任意のメンバを省略した入力と、そのメンバに空文字列を入れた入力も、違うキーになる（ユニットテスト）。
- **AC-05**: 2 つのメンバの値の境目だけを動かした入力（例: `title` が `"ab"`・`channelName` が `"c"` の入力と、`title` が `"a"`・`channelName` が `"bc"` の入力）は、違うキーになる（ユニットテスト）。
- **AC-06**: 生成が失敗したキーと同じ入力を送ると、生成がやり直され（LLM の呼び出しが新たに行われ）、同じキーが返る（ユニットテスト）。
- **AC-07**: 生成中のジョブが同時実行の上限（`/articles` のジョブとの合計）に達しているとき、新しいキーの入力は `too_many_requests` で拒否され、生成は始まらない。同じときに、処理中または完了したキーの入力は拒否されず、そのキーが返る（ユニットテスト）。
- **AC-08**: 入力の検査に失敗した場合の拒否の理由は、同じ入力を今の `/articles` に送った場合と同じであり、キャッシュには何も加わらない（ユニットテスト。今の `/articles` の検査のテストの入力を使う）。
- **AC-09**: 新しい API の生成の失敗では、`failure.Notifier`（fake）が呼ばれない（ユニットテスト）。

#### F-002: 状態と記事の取得

キーを指定して、そのキーの状態を返す。完了していれば記事も返す。

-   状態は、`処理中`・`完了`・`失敗`・`不明` のいずれかをコードで返す（F-005）。キャッシュにないキー（再起動の後、捨てた記事、一度も使っていないキー）は `不明` であり、拒否ではない。
-   `処理中` のときは、段階ごとの進み具合を返す。段階は `下書き`（生成）・`本文の短縮`・`字幕との照合`（検証・推敲）の 3 つで、各段階の状態は `未着手`・`実行中`・`完了`・`省略` のいずれかをコードで返す。本文の短縮を行わなかった（本文が 4,000 字以下だった）場合は `省略` になる。
-   `完了` のときは、次を返す。
    -   表示用の Markdown: 記事のタイトル、チャンネル名、本文を含む。形は設計で決める（H-05）。
    -   ファイルの中身: 同じ記事を CLI の `--out` で書き出したときと、バイト単位で同じ文字列（フロントマター・見出し・チャンネル名の行・本文。`internal/publisher/file_render.go:35-65`）。
    -   料金: 記事 1 本の料金（`internal/pricing` の `article` の合計。`pricing.go:127-140`）。料金が分からない場合は、分からないことをコードで示す。
    -   所要時間: 生成の開始の受け付けから、生成が完了するまでの時間。
    -   段階ごとの状態（`処理中` と同じ形。完了の後は `完了` か `省略` だけ）。
    -   投稿の状態（F-003）。
-   `失敗` のときは、失敗の理由をコードで返す（F-005）。記事は返さない。
-   どの状態でも、このサーバで投稿の操作ができるか（`SLACK_WEBHOOK_URL` が設定されているか）を返す（F-006）。
-   キーが受理する形でない場合は拒否する（拒否の理由は F-005）。

**Acceptance Criteria**:
- **AC-10**: 生成の開始の直後から完了までの間、状態の取得は `処理中` を返し、段階ごとの状態が、各段階の開始と終了に合わせて `未着手`→`実行中`→`完了` と変わる（ユニットテスト。各段階の途中で止められる fake の `LLMClient`）。
- **AC-11**: 生成の出力が 4,000 字以下の場合、`本文の短縮` の段階は `省略` を返し、4,000 字を超える場合は `省略` を返さない（ユニットテスト）。
- **AC-12**: 完了した記事の状態の取得は、ファイルの中身として、同じ `writer.Article` を `FilePublisher` が書き出すファイルとバイト単位で同じ文字列を返す（ユニットテスト）。
- **AC-13**: 完了した記事の状態の取得は、表示用の Markdown にタイトル・チャンネル名・本文を含み、料金として `internal/pricing` の `article` の合計を返し、料金が分からない記事では分からないことを示すコードを返す（ユニットテスト）。
- **AC-14**: 完了した記事の状態の取得は、所要時間を返し、その値は生成の開始の受け付けから生成の完了までの時間である（ユニットテスト。時刻を差し替えられる時計）。
- **AC-15**: 一度も生成の開始に使っていないキーと、サーバの再起動の後のキーは、`不明` を返し、拒否の理由を返さない（ユニットテスト。再起動は新しいサーバの値で表す）。
- **AC-16**: 生成が失敗したキーの状態の取得は、`失敗` と、失敗の理由のコードを返し、記事を返さない（ユニットテスト）。
- **AC-17**: 状態の取得は、生成も投稿も始めず、LLM（fake）と Webhook（fake）を呼ばない（ユニットテスト）。

#### F-003: Slack への投稿

キーを指定して、そのキーの記事を Slack 互換の Incoming Webhook へ投稿する。本文は受け取らない。

-   投稿は受け付けた時点で応答し、投稿そのものは非同期に行う。投稿の結果は状態の取得で返す。
-   記事ごとに投稿の状態を持つ。値は `未投稿`・`投稿中`・`投稿済み`・`投稿の失敗` のいずれかで、コードで返す（F-005）。`投稿の失敗` のときは、失敗の理由もコードで返す。
-   投稿の内容（見出し・本文・脚注、分割、`silent`、メンションの扱い）は、今の `/articles` の投稿と同じとする（`internal/publisher/slack.go:158-190`・`slack_render.go:66-87`）。
-   投稿の状態とキーの状態に応じて、次のように振る舞う。

| 状態 | 振る舞い |
|---|---|
| 完了・`未投稿` | 投稿を始め、受け付けの応答を返す。投稿の状態は `投稿中` になる |
| 完了・`投稿中` または `投稿済み` | 投稿し直さず、受け付けの応答を返す |
| 完了・`投稿の失敗` | まだ届いていない最初のメッセージから投稿を再開し、受け付けの応答を返す |
| 処理中 | 「まだ完了していない」の拒否の理由で拒否する |
| 失敗・不明 | 「投稿できる記事がない」の拒否の理由で拒否する |
| `SLACK_WEBHOOK_URL` が未設定 | キーの状態にかかわらず、「投稿先が設定されていない」の拒否の理由で拒否する（F-006） |

-   メッセージが届いたとみなすのは、今の投稿と同じく、Webhook が成功を返した場合である（`slack.go:192-237`）。成功を返さなかったメッセージは、届いていないとみなして、やり直しで送る。そのメッセージは実は届いていた可能性があり、その 1 通だけは重複しうる（1. 概要の決定）。
-   同じキーへの投稿の操作が同時に来ても、投稿は 1 回だけ行う。
-   投稿の失敗は、Webhook へ通知しない（F-006 の決定）。

**Acceptance Criteria**:
- **AC-18**: 完了・`未投稿` の記事への投稿の操作は、受け付けの応答を返し、その後の状態の取得は `投稿中` を経て `投稿済み` を返す。Webhook（fake）が受け取ったメッセージは、同じ記事を今の `/articles` が投稿した場合と同じである（ユニットテスト）。
- **AC-19**: 投稿の操作の応答は、Webhook（fake）が応答を返す前に返る（ユニットテスト。応答を止めておける fake の Webhook）。
- **AC-20**: `投稿中` と `投稿済み` の記事への投稿の操作は、受け付けの応答を返し、Webhook（fake）へのメッセージの数を増やさない。同じキーへの投稿の操作を同時に送っても、Webhook が受け取るメッセージは 1 回の投稿の分だけである（ユニットテスト）。
- **AC-21**: N 通に分かれる記事で k 通目（1 < k ≤ N）の投稿が失敗した場合、状態の取得は `投稿の失敗` と失敗の理由のコードを返す。その後の投稿の操作で Webhook（fake）が受け取るのは k 通目から N 通目までであり、1 通目から k−1 通目までは送り直されない（ユニットテスト）。
- **AC-22**: 処理中の記事への投稿の操作は「まだ完了していない」の拒否の理由で、失敗のキーと不明のキーへの投稿の操作は「投稿できる記事がない」の拒否の理由で拒否され、Webhook（fake）は呼ばれない（ユニットテスト）。
- **AC-23**: メンションを含むために投稿できない記事（今の `publisher.ErrSlackMention`）への投稿は、`投稿の失敗` と、メンションを理由とする失敗のコードになる（ユニットテスト）。
- **AC-24**: 新しい API の投稿の失敗では、`failure.Notifier`（fake）が呼ばれない（ユニットテスト）。

#### F-004: キャッシュ

生成した記事と、そのジョブの状態を、サーバのメモリに保持する。

-   保持するのは、キー、ジョブの状態、段階ごとの状態、完了した記事（表示用の Markdown・ファイルの中身・料金・所要時間を返せるだけの値と、投稿に必要な値）、投稿の状態、失敗の理由である。字幕そのもの（`transcript` の文字列と、解析したセグメント）は、生成が終わった後に保持しない。
-   ディスクに書かない。サーバの再起動で、すべて失われる。
-   件数に有限の上限を設ける。値は設計で決める（H-06）。上限を超えるときは、完了と失敗の記録のうち、完了または失敗した時刻の古いものから捨てる。処理中の記事と、`投稿中` の記事は捨てない。
-   捨てられる記録がなく、新しいキーを加えると上限を超える場合は、生成の開始を `too_many_requests` で拒否する（同時実行の上限が 2 なので、上限の値を十分に大きくすれば通常は起きない）。
-   捨てた記事のキーは、状態の取得で `不明` を返す。同じ入力の生成の開始は、新しい生成として扱う。

**Acceptance Criteria**:
- **AC-25**: 上限の件数まで記事を完了させた後に新しいキーで生成を始めると、完了の時刻が最も古い記事が捨てられ、そのキーの状態の取得は `不明` を返す。ほかの記事は残る（ユニットテスト。上限をテスト用に小さくできる場合はその値で行い、できない場合は実際の上限の値で行う）。
- **AC-26**: 上限に達したとき、処理中の記事と `投稿中` の記事は、完了の時刻が古くても捨てられない（ユニットテスト）。
- **AC-27**: 生成が終わった後のキャッシュの記録は、送られた字幕の文字列を含まない（ユニットテスト。字幕にだけ現れる目印の文字列が、記録のどの値にも含まれないことを確かめる）。
- **AC-28**: サーバはキャッシュの内容をファイルに書かない（ユニットテスト。サーバの実行の間に一時ディレクトリと作業ディレクトリへファイルが作られないことを確かめる。またはサーバのコードがファイルを書く API を呼ばないことの静的な確認）。

#### F-005: 状態・段階・理由のコード

新しい API の応答に含める状態・段階・理由は、文言ではなく固定のコード（enum）で返す（#506）。

-   コードの集合は閉じた集合とし、各値を README に表で示す。コードの綴り（例: `running`・`succeeded`）は設計で決める（H-07）。応答の文言（自然言語の文）を返さない。
-   ジョブの状態: `処理中`・`完了`・`失敗`・`不明`。
-   段階: `下書き`・`本文の短縮`・`字幕との照合`。段階の状態: `未着手`・`実行中`・`完了`・`省略`。
-   投稿の状態: `未投稿`・`投稿中`・`投稿済み`・`投稿の失敗`。
-   生成の失敗の理由: 今の失敗の通知の分類（`internal/server/job.go:109-155` の `classify`）と同じ粒度で区別する。字幕が長すぎる、LLM の時間切れ、LLM の空の応答、LLM の打ち切り、その他の LLM の失敗、内部の失敗、である。
-   投稿の失敗の理由: メンションを含むために投稿できない、その他の投稿の失敗、である。
-   新しい拒否の理由: 生成が「まだ完了していない」、「投稿できる記事がない」、「投稿先が設定されていない」、キーが受理する形でない（既存の `invalid_body` を使うか、新しい理由にするかは設計で決める。H-07）。HTTP の状態コードも設計で決める。
-   既存の拒否の理由（`internal/server/response.go:17-72`）は、意味と状態コードを変えない。

**Acceptance Criteria**:
- **AC-29**: 新しい API の応答の状態・段階・理由の値は、README の表に挙げた値のいずれかであり、README の表はサーバのコードが定義する値の集合と過不足なく一致する（ユニットテスト。今の `cmd/yt2column-server/docs_test.go` の拒否の理由の表のガードと同じ種類の確認）。
- **AC-30**: 生成の失敗の分類（字幕が長すぎる・LLM の時間切れ・空の応答・打ち切り・その他の LLM の失敗・内部の失敗）のそれぞれで、状態の取得は互いに違う失敗の理由のコードを返す（ユニットテスト。今の `classify` のテストと同じ失敗を fake で起こす）。
- **AC-31**: 新しい API の応答は、エラーの文言、字幕、URL、メタデータ、秘密の値を、コードとして定めた値の外では含まない（ユニットテスト。fake のエラーの文言と秘密の値に目印を入れ、応答の本文に現れないことを確かめる。記事そのものを返すメンバは除く）。

#### F-006: `SLACK_WEBHOOK_URL` を任意にする

サーバは `SLACK_WEBHOOK_URL` が未設定でも起動する。

-   未設定のとき:
    -   生成の開始と状態の取得は、設定されているときと同じく動く。
    -   状態の取得は、投稿の操作ができないことを返す。
    -   投稿の操作は、「投稿先が設定されていない」の拒否の理由で拒否する。
    -   `/articles` は、本文を読む前に同じ拒否の理由で拒否する。ジョブを始めず、失敗の通知もしない（通知の送り先がない）。
    -   起動のログに、投稿先が設定されていないことを 1 行で示す（URL の値は、設定されているときも出さない）。
-   設定されているとき、値の検査（`https` の URL であることなど。`internal/config/config.go:747-764`）は今と同じとする。空の値や不正な値は、今と同じく起動を止める（「値は補正せず、空の値は未設定ではなくエラーとして扱う」という project_overview の方針を保つ）。
-   CLI の `--slack` が `SLACK_WEBHOOK_URL` を必須とすることは変えない。

**Acceptance Criteria**:
- **AC-32**: `SLACK_WEBHOOK_URL` が未設定で、ほかのサーバの設定が正しいとき、`LoadServer` はエラーを返さず、サーバは起動する（ユニットテスト）。
- **AC-33**: `SLACK_WEBHOOK_URL` が空の値または不正な値のとき、`LoadServer` は今と同じエラーを返す（ユニットテスト。今のテストを保つ）。
- **AC-34**: `SLACK_WEBHOOK_URL` が未設定のサーバで、生成の開始と状態の取得は設定されているときと同じ結果を返し、状態の取得は投稿できないことを返す。投稿の操作は「投稿先が設定されていない」で拒否され、`/articles` も同じ理由で拒否され、どちらでもジョブは始まらない（ユニットテスト）。
- **AC-35**: `SLACK_WEBHOOK_URL` が設定されたサーバでは、状態の取得は投稿できることを返す（ユニットテスト）。

#### F-007: 今の `/articles` を残す

`POST /articles` は、#503 で削除するまで、今の振る舞いを保つ。

-   リクエストの検査、応答（`202` と `{"status":"accepted","requestId":"…"}`、拒否の形）、非同期の生成と投稿、失敗の通知、同時実行の上限は、今と同じとする（`0011`・`0026` の要件）。例外は、`SLACK_WEBHOOK_URL` が未設定の場合の拒否（F-006）と、同時実行の上限を新しい API の生成と合算すること（1. 概要の決定）だけである。
-   `/articles` の生成は、新しいキャッシュを読まず、書かない。

**Acceptance Criteria**:
- **AC-36**: `SLACK_WEBHOOK_URL` が設定されたサーバで、今の `/articles` のテストが、テストを変えずに通る。ただし、同時実行の上限の数え方と、F-006 の拒否を確かめるテストは除く（ユニットテスト）。
- **AC-37**: 同じ入力を `/articles` に送っても、新しい API の同じキーの状態は変わらず（`不明` のまま）、`/articles` は同じ入力を送るたびに LLM（fake）を呼んで投稿する（ユニットテスト）。

#### F-008: ホストの操作の対応づけ

ホストは、拡張が指定した操作を、サーバの送り先に対応づけて中継する。

-   拡張は、操作を閉じた集合（生成の開始・状態の取得・投稿）の値で指定する。ホストは、値ごとに決めた送り先（パスとメソッド）へ中継する。拡張が送り先のパスやメソッドを指定する手段は設けない。
-   今の拡張が送るメッセージ（入力の JSON をそのまま送る形）は、今と同じく `POST /articles` へ中継する。今の拡張の振る舞いは変えない。新しい形と今の形の区別は、メッセージの中で宣言した値で行い、メッセージの中身から推し量らない（CLAUDE.md「Declare, don't infer」）。区別の手段（版の値など）は設計で決める（H-08）。
-   新しい形のメッセージで、操作の値が集合にない場合、操作の値が重複する場合、形が合わない場合、ホストはサーバに接続せず、拡張に `protocol_error` を返す（今のホストのエラーの値の 1 つ。`internal/nmhost/relay.go:59-82`）。新しいホストのエラーの値を加えるかは、設計で決めてよい。
-   中継の時間の上限（20 秒）と、1 回の起動で 1 つのリクエストを中継する振る舞いは、今と同じとする。
-   ホストが中継できるサーバの応答の大きさは、完了した記事の状態の取得の応答が収まる大きさにする。今の上限（`relay.go:36` の 64 KiB）で足りるかは、設計で記事の大きさの上限から確かめる（H-09）。
-   ホストは、ホストの起動の制約（拡張の origin の検査、`HOME` だけを読む、プロキシを使わない、再送しない。`security.md` §8.2）を保つ。

**Acceptance Criteria**:
- **AC-38**: 新しい形のメッセージで指定した 3 つの操作のそれぞれで、ホストは、その操作に決めた送り先へ、1 回だけリクエストを送る（ユニットテスト。fake のサーバ）。
- **AC-39**: 今の拡張が送る形のメッセージは、今と同じく `POST /articles` へ、本文を変えずに中継される（ユニットテスト。今の中継のテストを保つ）。
- **AC-40**: 新しい形のメッセージで、操作の値が集合にない場合、重複する場合、メッセージの形が合わない場合、ホストはサーバに接続せず、`protocol_error` を返す（ユニットテスト）。
- **AC-41**: 状態の取得で、設計で決めた最大の大きさの記事（完了の状態）を返す応答を、ホストは切り詰めずに中継する（ユニットテスト）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

サーバと同じ利用者の権限で動くプロセスは信頼する（`security.md` §8）。ただし、生成の開始の入力の字幕とメタデータは、プロンプトに埋め込まれる untrusted なテキストである（`security.md` §6）。境界の検査は、今の `/articles` と同じ厳しさで行う。

| 境界 | 受理する形 | 上限 | 失敗・拒否時の扱い | 主な AC |
|---|---|---|---|---|
| 生成の開始の本文 | 今の `/articles` と同じ（1 つの JSON オブジェクト、正しい UTF-8、対になっていないサロゲートのエスケープを含まない、後続のデータがない。宣言済みのメンバは `videoUrl`・`transcript`・`title`・`channelName`・`description` で、宣言済みのメンバの重複は拒否する。宣言していないメンバは今と同じく無視して受理する。`request.go:57-110`） | 今と同じ 4 MiB（`request.go:18`） | 今と同じ拒否の理由（`invalid_body`・`invalid_video_url`・`invalid_transcript`・`body_too_large`）。キャッシュに何も加えない | AC-03・AC-08 |
| 状態の取得と投稿の操作のキー | 設計で決めた形（ハッシュの値の固定長の文字列など）だけを受理する。大文字と小文字の違い、前後の空白、余分な文字を補正しない | 形で決まる | キーが受理する形でない場合の拒否の理由（F-005、H-07）。キャッシュを変えない | AC-44 |
| 状態の取得と投稿の操作のリクエストの本文（本文を使う場合） | 設計で決める。使う場合は、宣言済みのメンバを閉じた集合とし、宣言していないメンバと重複するメンバを拒否する（新しい操作には、今の拡張との互換のために未知のメンバを許す理由がない）。生成の開始と同じ全体の検査（UTF-8・単一の値・後続のデータなし）を行う | 設計で決める（生成の開始より小さい上限） | `invalid_body`（または H-07 で決める理由） | AC-44 |
| ホストが受け取る新しい形のメッセージ | 操作の値（閉じた集合）と、その操作に要る値だけを持つ形。宣言していないメンバと重複するメンバを拒否する。JSON の全体の検査（UTF-8・単一の値・後続のデータなし）を行う | 今と同じ 32 MiB（`relay.go:34`） | サーバに接続せず `protocol_error`（F-008） | AC-40 |

-   キーは、生成の開始の応答でサーバが返した値を、拡張がそのまま送り返すものである。サーバは、受け取ったキーを、キャッシュを引く値としてだけ使い、ファイルのパスやログの書式などに埋め込まない。
-   ホストの今の形のメッセージ（`/articles` へ中継する形）は、今と同じく解析せずに中継する。サーバの検査が境界である（`0026`）。

**Acceptance Criteria**:
- **AC-44**: 状態の取得と投稿の操作で、受理する形でないキー（短すぎる・長すぎる・受理しない文字を含む・大文字と小文字だけが違う・前後に空白がある）は拒否され、キャッシュは変わらない。リクエストの本文を使う場合は、宣言していないメンバ・重複するメンバ・不正な UTF-8・後続のデータを含む本文も拒否される（ユニットテスト）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   状態の取得と投稿の操作の受け付けは、LLM と Webhook を待たずに応答する（F-002・F-003）。ホストの 20 秒の打ち切りの中に収まればよく、性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   キーの計算は、生成の開始のたびに入力の全体（最大 4 MiB）に対して行う。LLM の呼び出しに比べて無視できる時間であり、計算を省く仕組みは設けない。

### 4.2. セキュリティ (Security)

本タスクは、ネットワークへの送信（LLM API・Webhook）、Webhook の URL、プロンプトに埋め込む untrusted なテキストを扱うので、`docs/dev/security.md` を適用する。

-   **待ち受けの範囲:** 新しい操作も、今と同じ Unix ドメインソケットの上だけで受ける。TCP を待ち受けない（`security.md` §8.2）。
-   **固定の値だけを返す:** 新しい API の応答は、記事そのもの（表示用の Markdown とファイルの中身）を除き、コードとして定めた固定の値、キー、数値だけを含む。エラーの文言、Webhook の URL、API キーを含まない（F-005、AC-31。今の `0011` F-008 と同じ方針）。
-   **ログ:** 新しい操作のログも、今の方針（`0011` `02_architecture.md` §3.10）に従う。1 つの出来事を 1 行で、固定の属性だけを出す。本文、字幕、`videoUrl` の文字列、メタデータ、記事の本文、秘密の値を出さない。ログは今と同じく `redact.Writer` を通す。キーをログに出すかどうかは設計で決める（H-10）。
-   **メモリに持つ値:** キャッシュは、記事（LLM が生成した文章。字幕から作られ、字幕の内容を含みうる）を、サーバの再起動まで、または捨てられるまでメモリに持つ。字幕そのものは持たない（F-004）。ディスクに書かないので、`project_overview.md` の「処理を終えた動画の文字起こしをローカルに残し続けない」方針に反しない。
-   **投稿の操作は利用者の操作:** 同じ利用者の権限のプロセスはキーを知れば投稿を求められるが、そのプロセスは今も `/articles` で投稿を求められる。信頼の境界は今と変わらない（`security.md` §8）。
-   **二重の投稿の防止:** 投稿の操作は冪等にし（F-003）、`security.md` §8.2 の残るリスク（再送による二重の生成と投稿）を、新しい API の経路では、分割した投稿の失敗したメッセージ 1 通の重複だけに減らす。`/articles` の経路のリスクは、#503 で削除するまで残る。
-   **ホスト:** 拡張に任意のパスを指定させない（F-008）。ホストの起動の制約（origin の検査、`HOME` だけを読む、プロキシを使わない、再送しない）を保つ。
-   **プロンプトへの埋め込み:** 字幕とメタデータを記事生成のプロンプトに埋め込むことは変えない。プロンプトインジェクションによって記事の内容が操作されうることを前提とする（`security.md` §6）。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   サーバの再起動で、キャッシュと投稿の状態はすべて失われる。再起動の後、状態の取得は `不明` を返す。投稿済みかどうかも失われるので、再起動の前に投稿した記事を、再起動の後に同じ入力で生成し直して投稿すれば、同じ内容の記事がもう一度投稿されうる。これは親 issue #501 で受け入れた仕様（キャッシュを永続化しない）の帰結として受け入れる。
-   キャッシュの件数の上限（F-004）で、長く動かし続けてもメモリが増え続けない。
-   シャットダウンでは、今の `/articles` と同じく、処理中の生成のジョブと投稿の完了を待つ（`0011` `02_architecture.md` §3.8.3）。投稿のジョブも待つかどうかと、その上限は設計で決める（H-11）。
-   ジョブの中の panic は、今と同じく回復し、そのキーを `失敗`（内部の失敗）にする。サーバは動き続ける。

### 4.4. 互換性 (Compatibility)
-   今の拡張（`/articles` の経路）は、本タスクの後も、変更なしで動く（F-007・F-008）。拡張のコードとテストは変えない。
-   CLI の振る舞い（`--slack` での `SLACK_WEBHOOK_URL` の必須を含む）は変えない。
-   ホストの今の形のメッセージ、ホストの応答の形（`{"v":1,"kind":"response",...}`・`{"v":1,"kind":"error",...}`）、ホストのエラーの値は、今の拡張が受け取る範囲で変えない。新しい形のメッセージの応答の形を変えるかは設計で決める（H-08）。
-   `/articles` の、`SLACK_WEBHOOK_URL` が設定されたときの振る舞いは変えない。未設定のときは、今はサーバが起動しないので、互換の問題はない。

### 4.5. 保守性 (Maintainability)
-   ジョブの状態・段階の状態・投稿の状態・失敗の理由・拒否の理由・ホストの操作は、型（列挙）で表す。応答とログは、その型で振る舞いを選び、エラーの文言から推し量らない（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。列挙の零値は、最も多くを仮定しない解釈（例: 不明・内部の失敗）とする。
-   キャッシュは interface か小さな型の後ろに置き、サーバのテストで、時刻と上限を差し替えて確かめられるようにする。
-   ファイルの中身と Slack の投稿の整形は、今の `internal/publisher` の関数を使い、拡張や新しいコードで整形を重ねて書かない（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   `/articles` の削除（#503）が、新しい API のコードを変えずにできるように、`/articles` に固有のコード（自動の投稿、失敗の通知）を新しい API のコードから分ける。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。本タスクは、同書の次の記述を変えるので、F-009 で同書を更新する（親 issue #501「project_overview の方針の変更」）。
    -   「決定済みの方針」の「実行形式」: localhost サーバは「記事を生成して Slack へ投稿する」→「記事を生成して保持し、求めに応じて返す・投稿する」（`/articles` は #503 まで残る）。
    -   「設定（環境変数）」の `LoadServer` の段落: 「`SLACK_WEBHOOK_URL` を必須とする」→「任意とし、未設定なら投稿の操作と `/articles` を拒否する」。
    -   「前提・制約」のキャッシュの段落: 字幕・info.json のディスクのキャッシュとは別に、サーバが記事をメモリに持つこと。
-   以前のタスクの方針の変更:
    -   `0011_localhost_server` `01_requirements.md` §2.3 は、記事・進み具合を返すこととポーリングをスコープ外とし、F-007 は認証の後の失敗を Slack に通知するとした。本タスクは、新しい API で記事と進み具合を返し、新しい API の失敗を Slack に通知しない。理由は、親 issue #501 が、記事をブラウザに表示し、失敗の通知先を Viewer にすると決めたことである。`/articles` の通知は残す。
    -   `0026_native_messaging_relay` `01_requirements.md` §2.3 は、ポーリングと、拡張での成功・失敗の表示をスコープ外とした。`02_architecture.md` §9 は、ホストが `POST /articles` だけを送るとした。本タスクは、ホストが操作の値を送り先に対応づけるようにする。理由は同じく #501 の決定である。
-   外部ライブラリを加えない。ハッシュは標準ライブラリで計算する（[CLAUDE.md](../../../CLAUDE.md)「Dependencies」）。
-   ユニットテストは、LLM API・Webhook・実際のブラウザを呼ばない。`ArticleWriter`・`LLMClient`・Webhook は fake に置き換える。
-   拡張のコードとテストを変えない（#503 で変える）。

## 6. 用語集 (Glossary)

-   **0011**: localhost サーバのタスク（`docs/tasks/0011_localhost_server/`）。
-   **0026**: Native Messaging のホストのタスク（`docs/tasks/0026_native_messaging_relay/`）。
-   **新しい API**: 本タスクで加える 3 つの操作（生成の開始・状態と記事の取得・Slack への投稿）。`/articles` を含まない。
-   **生成の開始**: 拡張が送る入力を受け取り、記事のキーを返し、必要なら生成のジョブを始める操作。
-   **状態の取得**: キーを指定して、ジョブの状態・段階の状態・投稿の状態と、完了なら記事を返す操作。
-   **投稿の操作**: キーを指定して、その記事を Slack 互換の Incoming Webhook へ投稿する操作。
-   **記事のキー**: 生成の開始の入力の、検査を通った宣言済みのメンバの値から計算するハッシュ。新しい API で記事を指す値。
-   **キャッシュ（記事の）**: サーバがメモリに持つ、キーごとのジョブの状態と記事。ディスクの字幕・info.json のキャッシュ（`translation_glossary.md` の「キャッシュ」）とは別のもので、文脈が曖昧なときは「記事のキャッシュ」と書く。
-   **ジョブの状態**: `処理中`・`完了`・`失敗`・`不明`。
-   **段階の状態**: 生成の 3 つの段階（下書き・本文の短縮・字幕との照合）ごとの `未着手`・`実行中`・`完了`・`省略`。「段階」は `translation_glossary.md` の「段階」（パイプラインの段階）とは粒度が違い、`ArticleWriter` の中の処理を指す。
-   **投稿の状態**: `未投稿`・`投稿中`・`投稿済み`・`投稿の失敗`。
-   **Viewer**: #503 で拡張に加える、記事を表示するタブ（`viewer.html`）。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
