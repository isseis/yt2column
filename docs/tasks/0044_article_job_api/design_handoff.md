# 設計への申し送り：サーバとホストに、生成と投稿を分けた API と記事のオンメモリのキャッシュを加える

本書は、[01_requirements.md](01_requirements.md) の起草（とレビュー）で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 新しい API の HTTP のパス・メソッド・リクエストと応答の形

-   **事項:** 3 つの操作（生成の開始・状態の取得・投稿の操作）のパスとメソッド、キーを渡す場所（パスか本文か）、応答の JSON の形を決める。今の `checkHeaders` は `r.RequestURI` を `/articles` と完全に照合する（`internal/server/handler.go:119-127`）ので、パスにキーを入れる場合の照合の方法も決める。
-   **理由:** 要件は観測できる振る舞いだけを定め、形は設計に任せた（要件書 §1「本書の記述範囲」）。キーをパスに入れると、照合が完全一致ではなくなる。
-   **関連:** F-001、F-002、F-003、AC-44

## H-02: キーの符号化とハッシュ

-   **事項:** 検査を通った後の値（要件書 1. 概要の決定。省略した任意のメンバは空文字列、`videoUrl` は正規化した URL）を曖昧さなく並べる符号化（長さを前に置く形など）、ハッシュの関数（標準ライブラリの SHA-256 など）、キーの文字列の形（固定長の小文字の 16 進など）を決める。
-   **理由:** 境目の曖昧さ（AC-05）は要件で禁じた。キーの文字列の形は、状態の取得と投稿の操作の境界の受理する形になる（要件書 3.2）。
-   **関連:** F-001、AC-03、AC-04、AC-05、AC-44

## H-03: 工程の進み具合を知る手段

-   **事項:** サーバが `ArticleWriter` の工程（下書き／本文の短縮／検証・推敲）の開始・終了・省略を知る手段を決める（コールバック、進み具合を受け取る interface など）。
-   **理由:** 今の `writer.Write` は、工程の進み具合を呼び出し側に知らせない。CLI と共有する `ArticleWriter` の振る舞いを変えずに加える必要がある。
-   **関連:** F-002、AC-10、AC-11

## H-04: 同時実行の上限の数え方と値

-   **事項:** 新しい API の生成と `/articles` を合算して 2 とする上限（要件書 1. 概要の決定）を、今の枠（`internal/server/job.go:19`・`server.go:100`）とどう共有するかを決める。投稿の操作のジョブ（Webhook への送信）を上限に数えるか、数えるなら別の上限にするかを決める。今の `/articles` は失敗の通知も枠を持ったまま行う（`server.go:69-72`）。
-   本文の読み込みと検査の同時実行の上限（要件書 1. 概要の決定）の値と、その上限と生成の枠の関係を決める。
-   **理由:** 要件は生成の上限と本文の読み込みの上限を定めた。投稿は LLM を呼ばないが、Webhook への送信が並ぶと Webhook の側の制限に当たりうる。
-   **関連:** F-001、F-003、AC-07

## H-05: 表示用の Markdown の形

-   **事項:** 表示用の Markdown が何を含むか（タイトルの見出し、チャンネル名の行、本文、出典のリンク）を決める。`docs/dev/project_overview.md` の `ArticleWriter` の項は「出力先ごとに別の関数で整形し、共有するのは料金などの値の書式だけ」とするので、表示用の Markdown も別の関数で整形する。今の `renderFileArticle`（`internal/publisher/file_render.go:35-65`）の一部を共有する場合は、同書の方針の例外として、方針・範囲・理由を `02_architecture.md` に書く。
-   **理由:** 要件は、タイトル・チャンネル名・本文を含むことだけを定めた（AC-13）。#504 で拡張が Markdown を描画するので、その入力として扱いやすい形にする。
-   **関連:** F-002、AC-13

## H-06: キャッシュの件数の上限の値

-   **事項:** 件数の上限の値を決める。完了した記事 1 件が持つ大きさ（表示用の Markdown・ファイルの中身・投稿に必要な値）を測り、上限の件数を掛けたメモリの量を記録する。
-   **理由:** 要件は有限の上限を設けることだけを定め、値は設計に任せた（要件書 1. 概要の決定）。上限が小さいと、Viewer が開いている記事が捨てられ、`不明` になりうる。
-   捨てられない記録（処理中と `投稿中`）だけで上限が埋まると、新しい生成がすべて拒否される（要件書 AC-26a）。上限は、生成の同時実行の上限と、同時に走りうる投稿のジョブの数（H-04）の和より十分に大きくする。
-   **関連:** F-004、AC-25、AC-26

## H-07: コードの綴り、新しい拒否の理由と HTTP の状態コード

-   **事項:** ジョブの状態・工程・工程の状態・投稿の状態・失敗の理由・新しい拒否の理由のコードの綴りを決める。新しい拒否の理由（まだ完了していない、投稿できる記事がない、この記事は投稿できない、Webhook が設定されていない）の HTTP の状態コードを決める。失敗した工程を工程の状態でどう示すか（要件書 F-002）と、各列挙の零値（要件書 4.5。今の `failure.Kind` の零値は `KindUnknown`）を決める。キーが受理する形でない場合に、既存の `invalid_body` を使うか、新しい理由にするかを決める。
-   **理由:** README の拒否の理由の表は、Go のガード（`cmd/yt2column-server/docs_test.go:81-107`）と拡張のガード（`extension/test/serverReasons.test.ts`）の両方が読む。今の拡張が知らない理由の行は、3 列目を `fixed message` 以外にする（要件書 F-009）。生成の失敗の理由は、今の `failure.Kind`（`internal/failure/failure.go:14-28`）と対応づけられる綴りにすると、`classify`（`internal/server/job.go:109-155`）を共有しやすい。
-   **関連:** F-005、AC-29、AC-30、AC-42

## H-08: ホストのメッセージの新しい形

-   **事項:** 新しい形のメッセージの形（版のメンバの名前と値、操作の値、生成の開始の入力とキーの持ち方）、最上位のメンバ名だけを見る手段（エスケープを解いた名前で比べる。読めないメッセージは今の形として扱う。要件書 F-008）、新しい形の応答の形を変えるかを決める。生成の開始の入力を、ホストがサーバへ渡すときのバイト列（受け取った入力の部分をそのまま渡すか、組み立て直すか）を決める。
-   **理由:** 区別は版のメンバの有無で行う（要件書 1. 概要の決定、5. 制約条件の例外）。今のホストはメッセージを解析しない（`internal/nmhost/frame.go:1-4`・`relay.go:232`）。今の形の中継では、最上位のメンバ名を見るために本文を読んでも、中継するバイト列を変えてはならない（AC-39）。今の `forward` はメッセージをためずに流し、`Expect: 100-continue` で送る（`relay.go:215-255`）。形を決めるにはメッセージ全体を接続の前に読む必要があるので、その読み込みの時間（20 秒の上限の中での配分）と、標準入力が止まった場合の振る舞い（`relay.go:23-27` の注釈）も決める。`0026` `02_architecture.md` §9 は、新しいパスには「ホストのメッセージの変更（`v` を上げる）」が要るとした。
-   **関連:** F-008、AC-38、AC-39、AC-40

## H-09: 応答の大きさの上限

-   **事項:** 完了した記事の状態の取得の応答の最大の大きさを、記事の本文の上限から見積もり、ホストのサーバの応答の上限（`internal/nmhost/relay.go:36` の 64 KiB）と、ホストの応答のフレームの上限（`frame.go:21` の 1 MiB。本文は base64 で 4/3 倍になる）に収まるかを確かめる。拡張の今の上限（`extension/src/core/response.ts:57` の 1,024 バイト）は `/articles` の応答のためのもので、新しい形の応答の上限は #503 で決めることを記す。新しい形のメッセージの大きさの上限を、今の 32 MiB（`relay.go:34`）より小さくするかも決める（生成の開始の入力の上限はサーバの 4 MiB で、ホストは最上位のメンバ名を見るためにメッセージを読む必要がある）。
-   **理由:** 本文は 4,000 字を超えると短縮されるが、短縮の後と検証・推敲の後の本文の長さに上限が保証されているかを確かめる必要がある。表示用の Markdown とファイルの中身の 2 つを返すので、本文がほぼ 2 回含まれる。
-   **関連:** F-002、F-008、AC-41

## H-10: キーをログに出すか

-   **事項:** 新しい操作のログに、キー（またはその一部）を出すかを決める。
-   **理由:** キーは字幕とメタデータのハッシュで、内容は復元できないが、同じ入力を送ったことを照合できる。今のログは request ID と動画 ID を出す（`internal/server/job.go:180-207`）。開発者がジョブを追うには、キーか、キーに対応づけた ID が要る。
-   **関連:** 4.2 セキュリティ

## H-11: シャットダウンと投稿のジョブ

-   **事項:** シャットダウンのときに、処理中の投稿のジョブの完了を待つ時間の上限を決める（待つことは要件書 4.3 で決めた）。今のシャットダウンは、生成と失敗の通知のジョブを取り消さずに待つ（`internal/server/server.go:143-180`）。
-   **理由:** 投稿の途中でサーバが止まると、届いたメッセージの記録が失われ、再起動の後のやり直しで重複する。
-   **関連:** 4.3 信頼性

## H-12: 旧 API に関わるリファクタリングの issue をファイルする

-   **事項:** 拡張が新しい API に移った後（#503 の後）に要る作業を、設計の段階で具体的な項目として挙げる。対象は、`/articles`（旧 API）とそれだけが使うコードの削除、新旧の API の両方に対応するために複雑になったコードの簡素化である。挙げた項目を、実装計画（`03_implementation_plan.md`）の最初の作業として、GitHub の issue に起票する。
    -   `02_architecture.md` は、旧 API だけが使うコード（例: `/articles` のハンドラ、自動の投稿、`failure.Notifier` とその実装、ホストの今の形のメッセージの中継、README の `/articles` の節と拒否の理由の表の行）と、新旧の両対応のために加えたもの（例: 同時実行の上限の合算、ホストのメッセージの形の区別）を一覧にする。
    -   `03_implementation_plan.md` の最初の手順は、その一覧を本文に書いた issue をファイルすることとする。issue は #501 の子とし、#503 にブロックされる関係を記す。
-   **理由:** 要件は `/articles` を #503 まで今のまま残すと決めた（要件書 F-007）。新旧の両対応のコードは、削除の時期が来るまで残る。具体的な項目は設計で初めて決まるので、設計の後、実装の前にファイルし、削除と簡素化を忘れないようにする（2026-10-27、レビュアーの指示）。
-   **関連:** F-007、F-008、4.5 保守性

## H-13: テストの組み立て

-   **事項:** 要件書の AC を確かめるテストの組み立てを決める。候補: 各工程の途中で止められる fake の `LLMClient`（AC-10）、応答を止めておける fake の Webhook（AC-19・AC-20）、差し替えられる時計（AC-14・AC-25）、テスト用に小さくできるキャッシュの上限（AC-25・AC-26・AC-26a）、再起動を新しいサーバの値で表すこと（AC-15・AC-28）、コピーした字幕にだけ現れる目印の文字列（AC-27）、fake のエラーの文言と秘密の値に入れた目印（AC-31）、今の `cmd/yt2column-server/docs_test.go` の拒否の理由の表のガードと同じ種類の確認（AC-29）、今の `/articles` のテストの入力と期待値の再利用（AC-36）、送る前の検査を生成の完了の時点で行うための `internal/publisher` の関数の分け方（AC-23）。
-   **理由:** 要件は観測できる振る舞いだけを定め、テストの手段は設計に任せた（要件書 5. 制約条件）。
-   **関連:** F-001〜F-008
