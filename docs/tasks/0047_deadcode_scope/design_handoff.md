# 設計への申し送り：`make deadcode` の解析の範囲

要件定義（[01_requirements.md](01_requirements.md)）の作成中に挙がった設計事項を記す。`02_architecture.md` は、各項目にどう対応したか、または対応しない理由を記録する。

## H-01: 出力からの判定方法

-   **背景:** `deadcode` は、到達できない関数を報告しても終了コード 0 で終わる。報告は標準出力に、エラーのメッセージは標準エラーに出る（本書の作成時、`golang.org/x/tools` v0.47.0 で確かめた）。F-002 は、`deadcode` が終了コード 0 で終わり、何も出力しなかった場合だけを成功とする。
-   **注意点:**
    -   パイプ（`deadcode ... | tee` など）を使うと、`sh` は最後のコマンドの終了コードを返す。そのため、`deadcode` 自身の失敗（AC-12）が失われる。POSIX の `sh` では `pipefail` を使えるとは限らない。
    -   報告とエラーのメッセージを、どちらも表示する（AC-11・AC-12）。標準出力と標準エラーをどう扱うか（分けたままにするか）を決める。
    -   失敗の理由（報告があった、解析が失敗した）を示す要約の行を加えるかどうかを決める。
    -   F-002 は標準エラーへの出力も失敗とする。害のない出力（例: 初めての環境での `go: downloading ...`）が標準エラーに出る場合があるかを確かめ、扱いを決める。
    -   レシピが外部コマンドの出力を読んで振る舞いを選ぶことと、`CLAUDE.md` の「Declare, don't infer」との関係を整理する。この方針は呼び出し側が渡す文字列についてのものだが、設計で扱いを記す。

## H-02: `make -n` の検査との両立

-   **背景:** `extension/test/repository.test.ts:230-258` は、`node` と `npm` のない `PATH` で `make -n build test lint deadcode` を実行する。そして、終了コードが 0 であることと、標準エラーが空であることを確かめる。
-   **注意点:** 判定や `deadcode` の有無の確認（AC-13）を `$(shell ...)` のように解析時に評価される形で書くと、`make -n` でも `deadcode` が実行される。すると、`deadcode` が `PATH` にないときに標準エラーへ出力が出る。判定と確認はレシピの中に置く（`check_gofumpt`、`Makefile:20-26` と同じ）。`Makefile` を変えるので、実装では `make ext-test` も実行する（`CLAUDE.md`、Development Notes）。

## H-03: 受け入れ基準の確かめ方

-   **背景:** AC-02・AC-05〜AC-09・AC-11〜AC-13 は、関数やコンパイルエラーをわざと加えた作業ツリーでの振る舞いを述べている。
-   **候補:** 一時的な変更を加えて手で実行し、結果を実装計画に記録する。または、一時ディレクトリに小さなモジュールを作り、`make deadcode` のレシピを走らせるテストを書く。後者では、`deadcode` が `PATH` にない環境（CI）での扱いを決める必要がある（テストが黙ってスキップしないか）。
-   **入力の分離:** 「到達できると数える」AC（AC-02・AC-03・AC-04・AC-08・AC-09）は、確かめたい起点だけが届く入力で確かめる（`CLAUDE.md` の Testing Strategy、「A layered path needs inputs only one layer can handle」）。たとえば AC-02 では、次の 2 点を先に確かめる。その関数に `main` 以外のどのテストからも届かないこと、今のレシピ（`deadcode -test -tags test ./cmd/yt2column`）ではその関数が報告されること。本書の作成時の木には、ほかの `main` パッケージからだけ届き、テストから届かない関数が見当たらなかった（例として挙げた `internal/nmhost` の `Install` も、`internal/nmhost/manifest_test.go` から呼ばれている）。そのため、確かめるための関数を作る必要がある。

## H-04: `deadcode` の版とインストール方法

-   **背景:** `deadcode` は `PATH` にあるものを使い、版は固定されていない（要件のスコープ外）。版によって、報告の形や判定が変わりうる。
-   **注意点:** 設計で前提にする版を記録する。本書の作成時に手元で確かめたのは `golang.org/x/tools` v0.47.0 である。AC-13 で表示するインストール方法（`go install golang.org/x/tools/cmd/deadcode@...`）で、どの版を指すかも決める。
