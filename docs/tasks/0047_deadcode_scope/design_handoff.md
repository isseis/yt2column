# 設計への申し送り：`make deadcode` の解析の範囲

要件定義（[01_requirements.md](01_requirements.md)）の作成中に挙がった設計事項を記す。`02_architecture.md` は、各項目にどう対応したか、または対応しない理由を記録する。

## H-01: 報告の有無の判定方法

-   **背景:** `deadcode` は、到達できない関数を報告しても終了コード 0 で終わる（本書の作成時、`deadcode` v0.47.0 の `golang.org/x/tools`、`Makefile:245` の現在のレシピ）。そのため AC-08 を満たすには、レシピが出力から報告の有無を判定する必要がある。
-   **注意点:**
    -   パイプ（`deadcode ... | tee` など）を使うと、`sh` は最後のコマンドの終了コードを返す。そのため `deadcode` 自身の失敗（AC-09）が失われる。`pipefail` は POSIX の `sh` で使えるとは限らない。
    -   報告とエラーのメッセージが標準出力と標準エラーのどちらに出るかを確かめる。報告はすべて端末に表示する（AC-08）。
    -   判定にどの出力を数えるか（報告の行だけか、空でない出力すべてか）を決める。報告の形が変わった版の `deadcode` で黙って 0 件と判定しないほうを選ぶ。

## H-02: `make -n` の検査との両立

-   **背景:** `extension/test/repository.test.ts:230-258` は、`node` と `npm` のない `PATH` で `make -n build test lint deadcode` を実行し、終了コード 0 と空の標準エラーを確かめる。
-   **注意点:** レシピの判定を `$(shell ...)` などの解析時に評価される形で書くと、`make -n` でも `deadcode` が実行され、`PATH` にないときに標準エラーへ出力が出る。判定はレシピの中に置く。`Makefile` を変えるので、実装では `make ext-test` も実行する（`CLAUDE.md`、Development Notes）。

## H-03: 受け入れ基準の確かめ方

-   **背景:** AC-02〜AC-06・AC-08・AC-09 は、到達できない関数やコンパイルエラーをわざと加えた作業ツリーでの振る舞いを述べている。
-   **候補:** 一時的な関数を加えて手で実行し、結果を実装計画に記録する。または、一時ディレクトリに小さなモジュールを作って `make deadcode` のレシピを走らせるテストを書く。後者は `deadcode` が `PATH` にない環境（CI）での扱いを決める必要がある（要件のスコープ外である CI の導入とは別に、テストが黙ってスキップしないか）。
-   AC-02〜AC-04 は、`cmd/yt2column` だけを起点にしていた今のレシピなら報告される関数を例に選ぶ（AC-02〜AC-04 に挙げた例）。今のレシピとの違いが確かめられるようにするためである。

## H-04: `deadcode` の版

-   **背景:** `deadcode` は `PATH` にあるものを使い、版は固定されていない（要件のスコープ外）。版によって報告の形や判定が変わりうる。
-   **注意点:** 設計で前提にする版（本書の作成時に手元で確かめたのは `golang.org/x/tools` v0.47.0）を記録する。
