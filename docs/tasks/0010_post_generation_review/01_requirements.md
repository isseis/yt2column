## 1. 概要 (Overview)

**目的:** 本書は、`ArticleWriter` が記事を生成した後に加える 2 つの段階（字数の調整と、根拠の検証・推敲）と、それらを設定・評価するための要件を定義する。

**背景:**
タスク `0008_column_prompt` では、記事を 1 回の LLM 呼び出しで生成するテンプレートを 5 版まで調整したが、合格条件を満たせず、評価を保留した（[0008 の 02_evaluation.md](../0008_column_prompt/02_evaluation.md) §5.6）。残った問題は次の 3 種類で、いずれもテンプレートの指示を足すだけでは収束しなかった。

-   **根拠のずれ:** 記事 1 本につき 1〜2 か所、素材にない知識の補足や、意味の変わる言い換えが入る（例: 「ポートレート」に「接写」を足す、「地球サイズ」を「地球ほどの質量」と言い換える、「可視光線以外の電磁波も」の「も」が落ちる、評した人と評された人を取り違える）。版を重ねても、別の箇所に別のずれが出た。
-   **誤認識の写し:** 字幕の音声認識の誤り（「後退」が「交代」）を、5 版続けて記事に写した。意味の取れない文も残った。
-   **字数の超過:** 32 分の動画で、本文が 4,000 字の上限（0008 の F-004・AC-10）を毎回超えた（6,349〜4,743 字）。

一方、0008 の採点では、生成とは別の LLM が記事と字幕を突き合わせて、根拠のずれと誤認識の写しを見つけられた。字数は機械的に数えられる。そこで、生成の後に、字数を数えて超過したときだけ縮める段階と、記事を素材と突き合わせて直す段階を加える。2 つの段階は、0008 のテンプレート（v5）と組み合わせて評価し、0008 の評価を再開する。

対応 issue: #145

要件レビューの過程で挙がった、設計で決める事項は [design_handoff.md](design_handoff.md) に申し送る。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   生成した記事の本文が字数の上限を超えたときだけ、LLM で上限以内に縮める。
-   生成した記事を、字幕・概要欄・動画タイトル・チャンネル名と突き合わせ、根拠のない記述、意味の変わる言い換え、話者の取り違え、字幕の誤認識の写し、意味の取れない文を直すか削る。
-   検証に使うプロバイダとモデルを、生成とは別に設定で選べる。
-   どの段階が何を変えたかを、利用者と評価者が確かめられる。
-   いずれかの段階が失敗した記事を、成功として返さない。
-   0008 の評価を、v5 のテンプレートとこれらの段階の組み合わせで再開できる。

### 2.2. スコープ (In Scope)

-   `ArticleWriter` の生成の後に、字数の調整の段階と、検証・推敲の段階を加えること（どのパッケージに置くかは設計で決める）。
-   2 つの段階のプロンプトテンプレートの既定の文面（`prompts/` に置き、埋め込む）と、その上書き。
-   検証・推敲の段階のプロバイダとモデルの設定（環境変数）。
-   段階を無効にする CLI のフラグと、検証・推敲の段階が直した箇所の一覧を書き出す CLI のフラグ。
-   `Article` に、各段階で使ったモデル名とモデルの版の識別子を記録すること、`--out` の出力にそれを書くこと。
-   2 つの段階の評価（0008 の評価の動画と観点を使う）。

### 2.3. スコープ外 (Out of Scope)

-   生成のテンプレート（`prompts/system.tmpl`・`prompts/user.tmpl`）の変更。0008 の評価の再開と、最終の版の `prompts/` への反映（0008 の F-007）は 0008 で行う。
-   生成の前に字幕を整形する（句読点を付ける、誤認識を直す）段階。#145 の「代わりの案」に当たる。本タスクの評価で、生成後の段階では誤認識の写しが直らないと分かった場合は、別の issue にする。
-   話者の区別が難しい動画を検出して、生成を上位のモデルに回すこと（#146）。
-   字数の下限（2,500 字）に満たない記事を長くすること。0008 の F-004 は、素材が少ない動画で下限を下回ることを認めており、水増しを避けるため、本タスクは下限を扱わない。
-   各段階を複数回繰り返すこと（検証して直した記事をさらに検証する、など）。各段階の呼び出しは、1 本の記事につき最大 1 回とする（F-002・F-003）。
-   Claude アダプタそのもの（タスク `0009_claude_llm_client`、#9）。本タスクは、設定で選べるプロバイダの 1 つとして使う。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 段階の順序と入出力

記事の生成は、次の順で進める。

1.  **生成:** 現行の `ArticleWriter` の生成（テンプレートの展開、LLM の呼び出し、生成テキストの検証）。
2.  **字数の調整:** 本文の字数を数え、上限を超えていれば、LLM で上限以内に縮める（F-002）。上限以内なら何もしない。
3.  **検証・推敲:** 記事を素材と突き合わせて直す（F-003）。
4.  **最終の字数の確認:** 検証・推敲の後の本文の字数を数え、上限を超えていればエラーにする（F-002）。
5.  **出典の付与:** 現行どおり、出典のブロックを本文の末尾に付ける。

字数の調整を検証・推敲より前に置くのは、縮める際に混入した根拠のずれも、検証・推敲の段階で直せるようにするためである。

本文の字数は、0008 の `check_article.py` と同じく、LLM が書いた Markdown のうちタイトルの行を除いた部分（出典のブロックを含まない）の、改行を除いたコードポイントの数とする。Markdown の記号（`## `・`**` など）も数える。上限は 4,000 字とする（0008 の F-004）。

字数の調整の LLM の生成テキストは、現行の生成と同じ形（1 行目が `# ` で始まるタイトル、2 行目以降が Markdown の本文）とし、現行の生成テキストと同じ検証（タスク `0004_article_writer` の F-005 と §3.2）を通す。検証・推敲の LLM は、記事ではなく直した箇所の一覧だけを返し、直した記事は `ArticleWriter` が一覧を当てはめて作る（F-003）。作った記事も、同じ検証を通す。

**Acceptance Criteria**:
- **AC-01**: 生成した本文が上限以内で、検証・推敲の段階が記事を変えない場合、`ArticleWriter` は生成の LLM を 1 回、検証・推敲の LLM を 1 回呼び、字数の調整の LLM を呼ばない。返る記事のタイトルと本文（出典のブロックを除く）は、生成した記事と同じである。
- **AC-02**: 生成した本文が上限を超える場合、`ArticleWriter` は生成、字数の調整、検証・推敲の順に LLM を 1 回ずつ呼ぶ。検証・推敲の LLM に渡る記事は、字数の調整の後の記事である。
- **AC-03**: 字数の調整の LLM の生成テキスト、または検証・推敲の一覧を当てはめて作った記事が、現行の生成テキストの検証（0004 の AC-22〜AC-25・AC-27・AC-29・AC-31）で拒否される形である場合、`ArticleWriter` は `errors.Is(err, ErrMalformedOutput)` が真になるエラーを返し、返る `Article` はゼロ値である。
- **AC-04**: 本文の字数は、F-001 の数え方で数える。タイトルの行、改行、出典のブロックは数えず、Markdown の記号は数える。字数がちょうど 4,000 の本文は上限以内、4,001 の本文は上限を超えるものとして扱う。

#### F-002: 字数の調整

生成した本文が上限を超えたときだけ、LLM に記事と上限を渡し、主な論点を残して上限以内に縮めさせる。縮める段階に渡す入力は記事だけとし、字幕は渡さない（縮めるときに新しい内容を足さないようにするため）。

縮めた後の本文がなお上限を超える場合は、もう一度縮めず、エラーにする。検証・推敲の後の本文が上限を超えた場合も、エラーにする。どちらのエラーも、超過した記事を成功として返さないためである。

縮める段階には、生成と同じプロバイダとモデルを使う（記事を書き直す作業であり、検証とは性質が違うため）。

**Acceptance Criteria**:
- **AC-05**: 生成した本文が上限を超える場合、字数の調整の LLM に渡るプロンプトには、生成した記事のタイトルと本文と上限の値が含まれ、字幕（`Segment.Text`）は含まれない。
- **AC-06**: 字数の調整の後の本文がなお上限を超える場合、`ArticleWriter` は `errors.Is(err, ErrTooLong)` が真になるエラーを返し、検証・推敲の LLM を呼ばず、返る `Article` はゼロ値である。エラーには、上限と、超過した本文の字数が含まれる。
- **AC-07**: 検証・推敲の後の本文が上限を超える場合、`ArticleWriter` は `errors.Is(err, ErrTooLong)` が真になるエラーを返し、返る `Article` はゼロ値である。
- **AC-08**: 字数の調整の LLM は、生成と同じ `LLMClient` を使う。

#### F-003: 検証・推敲

記事と素材（動画タイトル・チャンネル名・概要欄・字幕）を LLM に渡し、次の箇所を見つけて、素材どおりに直すか削らせる。

-   素材に根拠のない記述（知識による補足、素材が結び付けていない因果を含む）
-   意味の変わる言い換えや省略（話者が付けた条件・留保の脱落、助詞の脱落による意味の変化を含む）
-   話者の割り当ての誤り（評した人と評された人の取り違えを含む）
-   字幕の誤認識の写し（文脈から正しい語が明らかなもの）
-   意味の取れない文

直す範囲はこれらの箇所に限る。構成（節の分け方と順序、見出し）、文体、ほかの記述は変えさせない。素材にない内容を足させない。

検証・推敲の LLM は、直した箇所の一覧だけを返す。一覧の各項目は、次の 4 つを含む。

-   直す前の記述（検証の対象の記事からの、一字一句そのままの引用）
-   直した後の記述（削った場合はそのことを示す）
-   直した理由の種類（上の 5 つのいずれか）
-   根拠となる素材の箇所（字幕の該当部分の引用など）

直した記事は、`ArticleWriter` が、検証の対象の記事の各項目の「直す前の記述」を「直した後の記述」に置き換えて（削った項目は取り除いて）作る。各項目が置き換えるのは、検証の対象の記事の中で「直す前の記述」が現れる 1 か所だけであり、ある項目が入れた文字列を、別の項目が探したり置き換えたりすることはない。そのため、直した記事は、項目の順序によらず同じになる。LLM に記事を書き直させないのは、一覧に載っていない書き換えを起こさせないためである。直す箇所がなければ、一覧は空であり、記事は変えない。

一覧を記事に当てはめられるのは、次の条件をすべて満たすときだけとする。満たさない項目が 1 つでもあれば、一覧全体を拒否する。

-   「直す前の記述」は、検証の対象の記事（タイトルの行と本文。出典のブロックは含まない）の中に、ちょうど 1 回だけ現れる。
-   異なる項目の「直す前の記述」が、記事の中で重ならない。
-   「直す前の記述」と「直した後の記述」は、改行を含まない（段落と行の構成を変えさせないため）。
-   一覧を当てはめた後の記事の見出し（`## ` で始まる行）は、検証の対象の記事の見出しと、数・文言・順序のすべてが同じである（構成を変えさせないため）。したがって、項目は見出しの中を直すことも、見出しを作ることや消すこともできない。タイトルの行の中にある項目は認める。

検証・推敲の LLM の応答は、信頼できない入力である。応答は、次の規則をすべて満たすときだけ受理し、満たさなければ拒否する。

-   応答は、0 件以上の項目を持つ一覧 1 つだけからなる。
-   一覧の各項目は、宣言した 4 つの要素（直す前の記述、直した後の記述または削ったことを示す印、理由の種類、根拠の箇所）をちょうど 1 つずつ持つ。理由の種類は、上の 5 つのいずれかである。
-   応答の形は拡張できない。項目の中の未知の要素や重複した要素、一覧の外にある内容（末尾に続く内容を含む）は拒否する。
-   黙って修復、破棄、無視すれば受理できてしまう入力は、受理せず拒否する。
-   応答全体の大きさと項目の数には、それぞれ有限の上限を設ける。いずれかの上限を超える応答は拒否する。

応答の拒否も、一覧を当てはめられない場合も、`errors.Is(err, ErrMalformedOutput)` が真になるエラーとし、返る `Article` はゼロ値とする。応答の具体的な構文（項目と要素の表し方）と上限の値は、設計で決める（[design_handoff.md](design_handoff.md) H-01）。

**Acceptance Criteria**:
- **AC-09**: 検証・推敲の LLM に渡るプロンプトには、検証の対象の記事（タイトルと本文）と、動画タイトル・チャンネル名・概要欄・字幕のすべてが含まれる。字幕は、生成のプロンプトに埋め込む字幕と同じ文字列である。
- **AC-10**: 検証・推敲の LLM が、当てはめの条件を満たす 1 件以上の項目を持つ一覧を返した場合、`ArticleWriter` が返す記事は、検証の対象の記事の各項目の「直す前の記述」を「直した後の記述」に置き換えた（削った項目は取り除いた）ものと一致し、ほかの部分は変わらない。各項目が置き換えるのは検証の対象の記事の中の 1 か所だけで、ある項目が入れた文字列を別の項目が置き換えることはなく、結果は項目の順序によらない（例: 記事の `甲乙` に、`甲` を `乙` にする項目と、`乙` を `丙` にする項目を当てはめた結果は `乙丙` である）。一覧を `ArticleWriter` の結果から取り出せ（取り出し方は設計で決める）、各項目は直す前の記述・直した後の記述（または削ったこと）・理由の種類・根拠の箇所を持つ。
- **AC-11**: 検証・推敲の LLM が空の一覧を返した場合、`ArticleWriter` が返す記事のタイトルと本文は検証の対象の記事と同じであり、一覧は空である。
- **AC-12**: 検証・推敲の LLM の応答が、F-003 の受理の規則のいずれかを満たさない場合、`ArticleWriter` は `errors.Is(err, ErrMalformedOutput)` が真になるエラーを返し、返る `Article` はゼロ値である。少なくとも次の応答をそれぞれ拒否する: 一覧がない、一覧の項目に 4 つの要素のいずれかが欠ける、項目に未知の要素または重複した要素がある、理由の種類が 5 つのいずれでもない、一覧の後に内容が続く、応答全体の大きさまたは項目の数が上限を超える。
- **AC-13**: 一覧のいずれかの項目について、「直す前の記述」が検証の対象の記事の中に現れない、または 2 回以上現れる場合、`ArticleWriter` は `errors.Is(err, ErrMalformedOutput)` が真になるエラーを返し、返る `Article` はゼロ値である。異なる項目の「直す前の記述」が記事の中で重なる場合も同じである。
- **AC-14**: 一覧のいずれかの項目について、「直す前の記述」または「直した後の記述」が改行を含む場合、「直す前の記述」が見出し（`## ` で始まる行）の中にある場合、または当てはめると見出しの行ができる場合（行の先頭にある「直す前の記述」を、`## ` で始まる「直した後の記述」に置き換える場合など）、すなわち当てはめた後の記事の見出しが検証の対象の記事の見出しと異なる一覧の場合、`ArticleWriter` は `errors.Is(err, ErrMalformedOutput)` が真になるエラーを返し、返る `Article` はゼロ値である。「直す前の記述」がタイトルの行の中にある項目は受理し、返る記事のタイトルは置き換えた後のものである。

#### F-004: 検証・推敲のプロバイダとモデルの設定

検証・推敲の段階のプロバイダとモデルは、生成とは別の環境変数で指定できる。

-   `YT2COLUMN_REVIEW_PROVIDER`: 検証・推敲のプロバイダ。受理する値は `YT2COLUMN_LLM_PROVIDER` と同じ（`deepseek`。タスク 0009 の完了後は `claude` も）。未設定なら、`YT2COLUMN_LLM_PROVIDER` と同じプロバイダを使う。
-   `YT2COLUMN_REVIEW_MODEL`: 検証・推敲のモデル名。`YT2COLUMN_REVIEW_PROVIDER` を設定した場合は必須とする（プロバイダと合わないモデル名を既定で使わないため）。どちらも未設定なら、`YT2COLUMN_MODEL` と同じモデルを使う。
-   API キーなどのプロバイダ固有の設定は、プロバイダごとの既存の環境変数（`DEEPSEEK_API_KEY`、0009 の `ANTHROPIC_API_KEY` など）を共有する。

値の扱い（補正しない、空の値はエラー、選んだプロバイダに関係しない変数は検査しない）は、既存の設定の規則（タスク 0009 の F-006）に従う。

**Acceptance Criteria**:
- **AC-15**: `YT2COLUMN_REVIEW_PROVIDER` と `YT2COLUMN_REVIEW_MODEL` がどちらも未設定の場合、検証・推敲の LLM は、生成と同じプロバイダとモデルで構築される。
- **AC-16**: `YT2COLUMN_REVIEW_PROVIDER` と `YT2COLUMN_REVIEW_MODEL` を設定した場合、検証・推敲の LLM は、そのプロバイダとモデルで構築され、生成の LLM は `YT2COLUMN_LLM_PROVIDER`・`YT2COLUMN_MODEL` のままである。検証・推敲のプロバイダが生成と異なる場合、そのプロバイダの API キーの環境変数が未設定または空なら、読み込みは `errors.Is(err, config.ErrMissing)` が真になるエラーになる。
- **AC-17**: `YT2COLUMN_REVIEW_PROVIDER` を設定し、`YT2COLUMN_REVIEW_MODEL` が未設定または空の場合、読み込みは `errors.Is(err, config.ErrMissing)` が真になるエラーになる。`YT2COLUMN_REVIEW_PROVIDER` が受理する値以外の場合は、`errors.Is(err, config.ErrInvalid)` が真になるエラーになり、拒否した値はエラーのメッセージに現れない。
- **AC-18**: `YT2COLUMN_REVIEW_MODEL` だけを設定した場合、検証・推敲の LLM は、生成と同じプロバイダと、`YT2COLUMN_REVIEW_MODEL` のモデルで構築される。

#### F-005: CLI のフラグと出力

-   `--no-shorten`: 字数の調整の段階を行わない。最終の字数の確認（F-001 の 4）も行わない。
-   `--no-review`: 検証・推敲の段階を行わない。
-   `--review-log <path>`: 検証・推敲の段階が直した箇所の一覧を、Markdown のファイルとして書き出す。一覧が空なら、直した箇所がないことを書く。`--no-review` と同時には指定できない。
-   2 つの段階のプロンプトテンプレートは、生成のテンプレートと同じく、既定の文面を埋め込み、ファイルで上書きできる（`--shorten-system-prompt`・`--shorten-user-prompt`・`--review-system-prompt`・`--review-user-prompt`）。上書きファイルの検証の規則は、生成のテンプレートと同じとする（0004 の F-001）。テンプレートで参照できる値は設計で決める。
-   `--out` の出力の先頭のモデルの行に、生成に加えて、実際に呼んだ段階のモデル名とモデルの版の識別子を書く。

2 つの段階を無効にするフラグは、評価で段階の効果を比べるため（段階なしの記事と比べる）と、費用を抑えたい場合のために設ける。既定では 2 つの段階を行う。

**Acceptance Criteria**:
- **AC-19**: `--no-review` を指定した場合、検証・推敲の LLM は呼ばれない。`--no-shorten` を指定した場合、字数の調整の LLM は呼ばれず、本文が上限を超えても `ErrTooLong` にならない。両方を指定した場合の出力は、本タスクの導入前の CLI の出力と同じである（`--out` のモデルの行を含む）。
- **AC-20**: `--review-log` を指定した場合、記事の書き出しまたは投稿が成功した後に、一覧のファイルが書き出される。一覧の各項目について、直す前の記述・直した後の記述・理由の種類・根拠の箇所が読める。記事の生成に失敗した場合は、一覧のファイルを書き出さない。記事の書き出しまたは投稿が済んだ後に、一覧のファイルの書き出しに失敗した場合、CLI はエラーで終わる。このエラーのメッセージから、記事が書き出し済み（投稿済み）であることが分かる。
- **AC-21**: `--review-log` と `--no-review` を同時に指定した場合、CLI は LLM を呼ぶ前に、使い方の誤りとしてエラーで終わる。
- **AC-22**: `--out` の出力のモデルの行には、生成、字数の調整（呼んだ場合）、検証・推敲（呼んだ場合）のそれぞれのモデル名とモデルの版の識別子が、どの段階のものか分かる形で書かれる。呼ばなかった段階の行は書かない。
- **AC-23**: 2 つの段階の上書きテンプレートは、生成のテンプレートと同じ規則で検証され、規則に反するファイルを与えた場合、CLI は LLM を呼ぶ前にエラーで終わる。埋め込まれた既定のテンプレートは、同じ規則の検証を通る（既定のテンプレートを規則に反する形に編集するとテストが失敗する）。

#### F-006: 失敗の報告

いずれかの段階の LLM の呼び出しが失敗した場合（通信の失敗、タイムアウト、キャンセル、空の応答、打ち切られた応答）、記事を成功として返さない。前の段階の結果（検証していない記事など）に戻して返すこともしない。

**Acceptance Criteria**:
- **AC-24**: 字数の調整または検証・推敲の LLM が、`llm.ErrTruncated`・`llm.ErrEmptyResponse`・`context.DeadlineExceeded`・テスト用の独自の番兵のそれぞれをラップしたエラーを返す場合、`ArticleWriter` が返すエラーは、元の番兵を `errors.Is` で判定でき、返る `Article` はゼロ値である。どの段階で失敗したかが、エラーのメッセージから分かる。
- **AC-25**: 字数の調整または検証・推敲の段階に入る前に `ctx` がキャンセルされていた場合、その段階の LLM を呼ばずに `errors.Is(err, context.Canceled)` が真になるエラーを返す。

#### F-007: テスト可能性

**Acceptance Criteria**:
- **AC-26**: 2 つの段階のユニットテストは、LLM の API もネットワークも呼ばない。生成、字数の調整、検証・推敲のそれぞれに fake の `LLMClient` を使い、F-001〜F-006 の各 AC を検証する。
- **AC-27**: 既存の `ArticleWriter`・CLI のテストのうち、2 つの段階を無効にした構成で実行するものは、本タスクの後もそのまま通る。

#### F-008: 評価

2 つの段階の効果を、0008 の評価の動画（5 本）と観点（0008 の F-006）で評価する。生成のテンプレートは 0008 の v5 とする。評価の手順と記録は `02_evaluation.md`（本タスク）に置く。評価の結果、2 つの段階を含めた構成で 0008 の合格条件を満たせる見込みが立ったら、0008 の評価を再開する。

評価では、段階の効果を次の 2 つの面から確かめる。

-   **直したこと:** 段階なしの記事にあった根拠のずれ・誤認識の写し・字数の超過が、段階の後に残っていないか。
-   **壊したこと:** 段階が、新しい根拠のずれを入れていないか、直す必要のない記述を変えていないか、構成を変えていないか。

検証・推敲に使うモデルは、少なくとも生成と同じモデル（deepseek-flash）で評価する。タスク 0009 の Claude アダプタが使えるようになっていれば、Claude でも評価し、比べる。

**Acceptance Criteria**:
- **AC-28**: `02_evaluation.md` に、0008 の評価の 5 本の動画について、v5 のテンプレートで生成し、2 つの段階を通した記事の、0008 の F-006 の観点ごとの判定が記録されている。判定の方法（スクリプト・LLM・人の分担、人の確認）は 0008 と同じとする。
- **AC-29**: `02_evaluation.md` に、各記事の検証・推敲の一覧（`--review-log`）の各項目について、直したことが正しかったか（素材に照らして直す必要があり、直した後の記述が素材どおりか）の判定と、段階が入れた新しいずれの有無が記録されている。
- **AC-30**: `02_evaluation.md` に、検証・推敲に使ったプロバイダとモデル、2 つの段階の呼び出しの回数、生成から出力までにかかった時間が、記事ごとに記録されている。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   2 つの段階は、1 本の記事につき LLM の呼び出しを最大 2 回増やす（字数の調整が 1 回、検証・推敲が 1 回）。検証・推敲の呼び出しは字幕全体を入力にするので、入力のトークン数は生成とほぼ同じになる。40 分前後の動画で、生成から出力までの時間がどれだけ増えるかを、評価で記録する（AC-30）。

### 4.2. セキュリティ (Security)

-   2 つの段階のプロンプトに埋め込む記事と素材は、信頼できない入力として扱う。テンプレートでは、埋め込んだ文章を指示として扱わないよう、生成のテンプレートと同じく区画を分けて示す（[security.md](../../dev/security.md) §6）。
-   API キーの扱いは、各プロバイダのアダプタの既存の規則に従う。検証・推敲のプロバイダを生成と別にしても、API キーをエラーやログ、`--review-log` のファイルに出力しない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   いずれかの段階の失敗は、記事全体の失敗とする（F-006）。検証していない記事を、検証した記事として公開しないためである。

### 4.4. 互換性 (Compatibility)

-   `--no-shorten --no-review` を指定した CLI の振る舞いは、本タスクの前と同じである（AC-19）。
-   既定で 2 つの段階を行うので、フラグを指定しない CLI の振る舞いは変わる（LLM の呼び出しが増え、記事が直されることがある）。

### 4.5. 保守性 (Maintainability)

-   2 つの段階の後処理（応答の検証、一覧の当てはめ、字数の数え方）は、プロバイダに依存しない。プロバイダを追加しても、2 つの段階のコードを変更せずに済む。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。外部ライブラリは追加しない。
-   空の応答、打ち切られた応答、形の不正な応答は、どの段階でもエラーとし、成功として返さない（CLAUDE.md「Empty is an error」）。
-   検証・推敲の段階で Claude を使うには、タスク 0009 の Claude アダプタの実装が必要である。本タスクは 0009 の完了を前提にしない（既定は生成と同じプロバイダ）。
-   評価で LLM の API を呼ぶ実行は、実行のたびに人が承認する。DeepSeek の料金が 2 倍になる時間帯（日本時間の平日 10〜13 時と 15〜19 時）は避ける（0008 の 02_evaluation.md §2.3）。
-   [project_overview.md](../../dev/project_overview.md) のパイプラインの説明と設定の表を更新する（2 つの段階の追加、`YT2COLUMN_REVIEW_PROVIDER`・`YT2COLUMN_REVIEW_MODEL`）。

## 6. 用語集 (Glossary)

-   **字数の調整:** 本文の字数が上限を超えたときだけ、LLM で上限以内に縮める段階（F-002）。
-   **検証・推敲:** 記事を素材と突き合わせ、根拠のない記述・意味の変わる言い換え・話者の取り違え・誤認識の写し・意味の取れない文を直す段階（F-003）。
-   **一覧（直した箇所の一覧）:** 検証・推敲の LLM が返す、直す箇所ごとの、直す前と後の記述、理由の種類、根拠の箇所の一覧。`ArticleWriter` は、これを記事に当てはめて直した記事を作る（F-003）。
-   **素材:** 動画タイトル・チャンネル名・概要欄・字幕（0008 の用語と同じ）。
-   **本文の字数:** タイトルの行と出典のブロックを除いた本文の、改行を除いたコードポイントの数（F-001）。
