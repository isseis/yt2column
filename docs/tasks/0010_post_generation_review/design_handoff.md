# 設計への申し送り：生成後の検証・推敲と字数の調整

本書は、[01_requirements.md](01_requirements.md) のレビューで挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 検証・推敲の応答の構文、上限の値、不正な入力の検出方法

-   **事項:** 検証・推敲の段階の LLM の応答（直した箇所の一覧だけからなる）について、次の 3 つを決める。
    -   具体的な構文。一覧の項目と、項目の 4 つの要素（直す前の記述、直した後の記述または削ったことを示す印、理由の種類、根拠の箇所）をどう表すか。
    -   上限の値。応答全体の大きさと、項目の数のそれぞれ。
    -   不正な入力の検出方法。形に合わない応答、未知の要素や重複した要素、末尾に続く内容、標準ライブラリが黙って修復・破棄・無視する入力を、どう見つけて拒否するか。
-   **理由:** この応答は、信頼できない LLM の出力を受け取る境界である（[requirements_process.md](../../dev/developer_guide/requirements_process.md) の「Untrusted input boundaries」）。要件は受理の規則と拒否の番兵（`ErrMalformedOutput`）を定めたが、構文と値が決まらなければ、規則を実装もテストもできない。
-   **候補の方針:** 一覧は JSON で表し、`internal/strictjson` を再利用して、未知のキー・重複したキー・末尾のデータを拒否する。上限の値は、現行の生成テキストの上限を基準に決める。「直す前の記述」の照合は、要件どおり一字一句の一致とする（空白の違いなどを許す照合にするなら、要件の変更として扱う）。
