## 1. 概要 (Overview)

**目的:** 本書は、単純な変更を、要件・設計・計画の文書を作らずに 1 本の PR で進める軽量プロセスの要件を定義する。定めるのは次のことである。

-   軽量プロセスの対象になる条件
-   `/mkreq` での振り分け
-   軽量プロセスの仕様の記録と承認
-   実装のコマンド `/runissue`
-   マージと issue の扱い
-   更新する文書

**背景:**

タスク 0054（#560）の最終的な変更は、拡張の使われなくなった関数 1 つとそのテスト 1 つの削除だった（2 ファイル、−16 行）。issue #619 の記録によれば、これに対して、通常のプロセスで次のものを作った。

-   要件・申し送り・設計・計画の文書、計約 600 行
-   `_checks/removal_only.ts` 254 行
-   4 本の PR（#609・#611・#614・#615）と 17 件のコミット

最初の PR からマージまで約 9 時間かかった。Codex の PR レビューの指摘は、4 本とも 0 件だった。ローカルの CLI レビューの指摘の多くは、そのタスクのために作った確認の仕組みについてのものだった。このように、変更の大きさに対して、文書の量とレビュー・マージの手間が釣り合っていない。

今は、どの変更も、要件定義書・アーキテクチャ設計書・実装計画書が承認されるまで実装を始めない（`docs/dev/conventions/requirements_process.md:11-14`）。また、各タスクは `docs/tasks/NNNN_<name>/` に置く（`CLAUDE.md:33`）。`/mkreq` は、issue を読むと必ず要件定義書を作る（`.claude/commands/mkreq.md:12-15`・`34-112`）。

対応 issue: [#619](https://github.com/isseis/yt2column/issues/619)

関連: [#560](https://github.com/isseis/yt2column/issues/560)（タスク 0054。本 issue のきっかけ）、[#618](https://github.com/isseis/yt2column/issues/618)（テストの削除の前後でカバレッジを比べる道具。タスク 0055 で `make coverage-compare`・`make ext-coverage-compare` として実装済み。`CLAUDE.md:140`。後述の類型 D の確かめ方の前提になる）

**本書の記述範囲:** 本書は、次のことを定める。

-   軽量プロセスの対象になる条件と、行数・ファイル数の数え方
-   `/mkreq` が提案し、利用者が選ぶ流れ
-   仕様のコメントとラベル
-   `/runissue` の入口の確認と、実装・確認・PR の作成
-   確かめ直しで条件を満たさなかったときの扱いと、途中で失敗したときの扱い
-   `/runpr` でのマージと、issue を閉じること
-   各文書に書かれていること

次のことは設計（`02_architecture.md`）で決める。

-   条件の確かめ直しの方法（スクリプトか、手順か）
-   除外するパスの正確な一覧と、その置き場所
-   仕様のコメントの目印の行と書式
-   `/runpr` が軽量プロセスの PR を見分ける方法と、閉じる issue を知る方法
-   ブランチ名、PR のタイトルとコミットの接頭辞、記録の書式
-   コマンドの定義のどの手順をどう書き換えるか

要件のレビューで挙がった設計事項は、[design_handoff.md](design_handoff.md) に申し送る。

**issue #619 で決めたこと:**

-   **変更を 3 つの類型に分け、類型ごとに分量の上限を設ける:** 類型は W（文言）・D（削除）・M（機械的なリファクタ）である。どれか 1 つの類型に収まり、全体の上限（PR 1 本、手で変更したファイル 10 個まで）も満たす変更を、軽量プロセスの対象とする。全体の上限は、人が 15 分でレビューできる大きさを目安にしている。
-   **分量にかかわらず、決まった種類の変更は通常のプロセスとする:** 機械的に確かめられない範囲を含むためである（F-001 の AC-05）。
-   **振り分けは `/mkreq` が issue を読んだ直後に行う:** LLM が条件に当たるかを判断し、当たる場合は、類型・見込みの変更量・理由を示して軽量プロセスを提案する。迷うときと当たらないときは、通常のプロセスで進める。
-   **軽量プロセスでは要件定義書を作らない:** 代わりに、issue に「軽量プロセスの仕様」（やること・やらないこと・類型・確かめ方）をコメントで書き、ラベルを付ける。これを要件の承認に当たるものとする。
-   **実装は新しいコマンドで行い、`docs/tasks/` の下は作らない:** コマンドは、ブランチの作成、実装、ビルドの確認、サブエージェントによるレビュー 1 回、ローカルの CLI レビュー、コミットメッセージへの確かめた結果の記録、`Closes #N` 付きの PR の作成を行う。
-   **実装の後に、実際の diff で条件を確かめ直す:** 満たさなければ PR を作らずに止まり、通常のプロセスに戻すよう報告する。
-   **PR を作った後は、今の `/runpr` に、タスクのない単独の変更として渡す。**
-   **0054 で役に立ったものは残す:** 事実の確認、スコープの宣言、テストを削除するときのカバレッジの確認、確かめた結果をコミットメッセージに残すことである。

**要件定義の際に決めたこと（2026-11-04）:**

-   **実装のコマンドの名前は `/runissue` とする:** 既存のコマンド（`/runplan`・`/runpr`）の `run<対象>` の形に合わせ、issue を入力に取ることを名前で示すためである。
-   **ラベルの名前は `lightweight` とする:** リポジトリの既存のラベル（2026-11-04 に `gh label list` で確かめた。`devenv`・`refactor`・`accessibility` など）に合わせて英語にする。
-   **軽量プロセスの PR のマージの後は、`/runpr` が issue を閉じる:** リポジトリの「Auto-close issues with merged linked pull requests」の設定は off である（`.claude/commands/_lib/task-pr-handoff.md:111-113`）。そのため、PR の本文の `Closes #N` だけでは issue は閉じない。今の `/runpr` が issue を閉じるのは、タスクの最後のプランの PR のマージの後だけである（`.claude/commands/runpr.md:809-827`）。設定を on にすると、タスクの issue が最初の PR のマージで閉じてしまうので、採らない。手作業で閉じる案も採らない。閉じ忘れると、issue の状態と実際の状態が食い違うためである。
-   **仕様は、`/mkreq` が文面を示して尋ね、利用者がそれを選んだことで承認とする:** 承認の後に `/mkreq` が仕様を issue に投稿し、ラベルを付ける。先に投稿して、`/runissue` の実行を承認とみなす案は採らない。承認の時点がはっきりせず、文面を読まずに実行されうるためである。
-   **行数は、diff の追加行と削除行を別々に数える:** 1 行を書き換えると、追加 1 行・削除 1 行になる。issue #619 の上限の書き方（「削除 100 行まで、追加 10 行まで」）と合い、機械的に確かめられる。
-   **確かめ直しで条件を満たさなかったときは、ラベルを外し、満たさなかった条件を issue にコメントし、実装のコミットを push しない:** 後で `/mkreq` を実行したとき、通常のプロセスで進むためである。会話の中で報告するだけにすると、issue の状態と実際の進め方が食い違う。
-   **実装の途中で判断が必要になったときも、止まって通常のプロセスへ戻す:** 扱いは、確かめ直しで条件を満たさなかったときと同じにする。issue #619 は「issue のコメントで判断を求める」としていた。しかし、設計上の選択肢が残る変更は、もともと軽量プロセスの対象外である（issue #619 の「やること」の 1）。途中で判断が要ったことは、その前提が外れたことを示す。issue で尋ねて再開する案と、その場で尋ねて仕様に追記する案は、承認の後に仕様を変える流れを足すことになるので採らない。
-   **仕様とみなすのは、認証済みの利用者（AC-17）が書いた、仕様のコメントであることを示す決まった 1 行（目印の行）で始まるコメントのうち、最新の 1 件だけとする:** 公開リポジトリでは、issue には誰でもコメントできる。他人が書いた「仕様」を `/runissue` が実装しないようにするためである。ラベルがない issue では、`/runissue` は止まる。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

以下は、レビュアーと個別には確認していない。上の決定と現行の規則から導いたもので、PR のレビューで異論があれば改める。

-   **`/mkreq` に `[task]` を渡したときは、振り分けない:** 既存のタスクのディレクトリに書くことを、利用者がすでに選んでいるためである。ただし、ラベルか仕様のコメントがすでにある issue では止まる（AC-15 が優先する）。同じ issue に 2 つの進め方が並ばないようにするためである。
-   **ラベルか仕様のコメントがすでにある issue に `/mkreq` を実行したときは、要件定義書を作らずに止まる:** 両方がそろっていれば `/runissue <N>` を案内し、片方だけなら直し方を案内する（AC-15）。仕様が承認済みの issue に要件定義書を作ると、同じ issue に 2 つの進め方が並ぶためである。また、2 件目の仕様を投稿しないためでもある。
-   **一度通常のプロセスへ戻した issue には、`/mkreq` は軽量プロセスを提案しない（AC-32）:** 戻した理由は、変更が条件を外れたことである。もう一度提案すると、同じ変更がまた軽量プロセスで進みうる。
-   **`README.md` の変更に伴う `README.en.md` の変更も、行数とファイル数に数える:** `/mktrans` が書く行は、再実行しても同じ diff になる道具が生成した行（類型 M の例外）に当たらない。また、数える対象から外すと、確かめ直しが単純でなくなる。この結果、類型 W で直せる README の行は、およそ半分（追加・削除とも 15 行ほど）になる。
-   **確かめる対象のタスク文書は、承認済みのものに限らず、`docs/tasks/` の下のすべてとする（AC-05）:** issue #619 は「承認済みのタスク文書の編集」を除くとしていた。`draft` のタスク文書は、その文書の PR で直すものであり（`.claude/commands/mkreq.md:47-49`）、軽量プロセスの PR で直すと、同じ文書に 2 つの PR が並ぶ。パスで機械的に確かめられる形にもなる。
-   **`make ext-check` は、`extension/` を変えたときだけ行う（AC-22）:** issue #619 は `make test`・`make lint`・`make ext-check` を並べていた。CLAUDE.md の「Development Notes」は、`make ext-check` を拡張の変更の後に行うとしている（`CLAUDE.md:560`）。README と `docs/dev/guides/development.md` を変えたときは、同じ節のとおり `make ext-test` を行う。`make fmt` は、Go のファイルを変えたときの CLAUDE.md の手順（同節）である。
-   **サブエージェントによるレビューの観点は、issue の範囲ではなく、仕様の範囲とする（AC-24）:** 承認されたのは仕様のコメントであり、issue の本文は誰でも書けるためである（AC-18）。
-   **`/runissue` は、要件定義書、リンクされた開いている PR、軽量プロセスのブランチのどれかがすでにあれば止まる（AC-16）:** 要件定義書か PR があれば、同じ issue に 2 つの進め方が並ぶためである。ブランチがあるときは、途中で止まった実行を自動で再開しない。再開すると、前の実行の途中の状態を確かめる手順が要るためである。
-   **通常のプロセスへ戻すときは、コメントを投稿してからラベルを外す（AC-30）:** 先にラベルを外すと、コメントの投稿に失敗したとき、戻したことの記録もラベルも残らず、後の `/mkreq` が戻した issue を見分けられない（AC-32）。コメントが残っていれば、ラベルの外し忘れは利用者が直せる。
-   **通常のプロセスへ戻すとき、実装のコミットはローカルのブランチに残す（AC-30）:** 利用者が、どこで条件を外れたかを確かめられるようにするためである。`origin` には実装のコミットを置かない。
-   **PR の作成の後の修正（`/runpr` から行う `/fixpr`）では、条件を確かめ直さない:** PR のレビューで、レビュアーが判断する。確かめ直すと、`/runpr` と `/fixpr` にも軽量プロセスの条件を持ち込むことになる。
-   **軽量プロセスの PR にも、Codex の PR レビューは今のとおり 1 回付く:** PR は開いたときに 1 回レビューされる（`CLAUDE.md:178-181`）。`/runpr` の単独の変更の扱いを変えない（issue #619 の「やること」の 3）。

**方針の例外:**

-   **`requirements_process.md` の「Do not begin writing any implementation code until the status of `03_implementation_plan.md` is `approved`」（同書 13 行）と、CLAUDE.md の「Each task lives in `docs/tasks/NNNN_<name>/`」（`CLAUDE.md:33`）:** 軽量プロセスの対象になる変更は、タスク文書を作らず、仕様のコメントの承認だけで実装を始める。理由は「背景」のとおりで、例外の範囲は F-001 の条件に限る。例外は `requirements_process.md` と CLAUDE.md に明記する（AC-38）。
-   **`/mkreq` が必ず要件定義書を作るという前提（`.claude/commands/mkreq.md:12-15`）と、CLAUDE.md の「Each task PR is handled by two commands」の段落（`CLAUDE.md:166`）:** 軽量プロセスでは、`/mkreq` は要件定義書を作らず、PR を作るのは `/runissue` である。両方の記述を改める（AC-37・AC-43）。
-   **タスクの PR の本文には closing keyword を書かない規則（`.claude/commands/_lib/task-pr-handoff.md:244`）:** この規則はタスクの PR についてのものである。軽量プロセスの PR はタスクの PR ではないので、本文に `Closes #N` を書く（issue #619 の「やること」の 3）。例外ではないが、混同しないよう、`/runissue` の定義にその旨を書く。
-   **PR のタイトルの `<scope>`（`.claude/commands/_context.md` の「PR title and squash subject」）:** コマンドが書く PR のタイトルは `<scope>` を持つ。軽量プロセスの PR にはタスクの番号がないので、何を `<scope>` にするかを設計で決める（[design_handoff.md](design_handoff.md) の H-06）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   条件に当てはまる単純な変更を、文書を作らずに、PR 1 本で進められるようにする。
-   0054 で役に立った確認（事実の確認、スコープの宣言、テストを削除するときのカバレッジの確認、確かめた結果の記録）は、軽量プロセスでも残す。
-   条件を外れた変更が軽量プロセスのまま PR になることを、実際の diff での確かめ直しで防ぐ。

### 2.2. スコープ (In Scope)

-   軽量プロセスの条件の定義（`docs/dev/conventions/requirements_process.md`）
-   `.claude/commands/mkreq.md`：振り分け、仕様の提示と投稿、ラベルの付与、「Authorization」
-   新しいコマンドの定義 `.claude/commands/runissue.md`
-   `.claude/commands/runpr.md`：軽量プロセスの PR のマージの後に issue を閉じること、「Authorization」
-   `.claude/commands/_context.md`：ラベル名、ブランチ名、PR のタイトルとコミットの接頭辞など、コマンドが参照する値
-   CLAUDE.md：概要、例外、コマンドの一覧への `/runissue` の追加
-   軽量プロセス用の issue テンプレート（`.github/ISSUE_TEMPLATE/` の下）
-   リポジトリへの `lightweight` ラベルの作成

### 2.3. スコープ外 (Out of Scope)

-   **通常のプロセスの手順の変更:** 要件・設計・計画の文書とその PR の流れは変えない。
-   **リポジトリの、issue を自動で閉じる設定の変更:** off のままにする（「要件定義の際に決めたこと」）。
-   **PR の作成の後の修正での確かめ直し:** 「上の決定から導いたこと」のとおり。
-   **既存の issue の振り分け直し:** 本タスクの後に `/mkreq` を実行した issue から適用する。すでに要件定義書がある issue は対象外である（`/mkreq` は、要件定義書がある issue では止まる。`.claude/commands/mkreq.md:42-49`）。
-   **本タスク自身への適用:** 本タスクは、コマンドの定義と `docs/dev/conventions/` の内容を変えるので、軽量プロセスの対象外であり、通常のプロセスで進める。
-   **Codex の PR レビューの扱いの変更:** 「上の決定から導いたこと」のとおり。
-   **途中で止まった `/runissue` の再開:** 「上の決定から導いたこと」のとおり、止まって報告する（AC-16）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 軽量プロセスの対象になる条件

変更が軽量プロセスの対象になるかを、類型、分量、除外する変更の 3 つで決める。

**Acceptance Criteria**:
- **AC-01**: `docs/dev/conventions/requirements_process.md` が、次の 3 つの類型を定めている。
  - **W（文言）:** コメントや文書の、誤字・表記ゆれ・言い回しの修正で、意味を変えないもの。確かめ方は、diff を読むことである。README は、`/mktrans` と既存の document test で確かめる。
  - **D（削除）:** 到達できないことが道具（`make deadcode`・`tsc`・`git grep`）で示されたコードと、それだけを確かめるテストの削除。確かめ方は、`make test`・`make lint` と、`extension/` を変えたときの `make ext-check` である。テストを削除するときは、CLAUDE.md の「Deleting a test is a claim that must be checked」（`CLAUDE.md:504`）の比較も行う。
  - **M（機械的なリファクタ）:** 誤りがあれば、コンパイラ・型検査・linter・既存のテストが必ず検出する変更。例は、参照がコードの中だけにある識別子の名前の変更、`golangci-lint run --fix` の適用、コードやファイルの移動である。確かめ方は、D と同じ確認に加えて、道具の再実行である。
- **AC-02**: 同じ文書が、類型ごとの分量の上限を次のとおり定めている。行は、diff の追加行と削除行を別々に数える。
  - **W:** 追加行・削除行とも 30 行まで。
  - **D:** 削除行 100 行まで、追加行 10 行まで。
  - **M:** 手で書いた追加行が 50 行まで。道具が生成した行は、使ったコマンドを記録し（AC-26）、そのコマンドを変更の前の状態で再実行して同じ diff になる場合に限り、この上限に数えない。
- **AC-03**: 同じ文書が、全体の上限を定めている。PR は 1 本で、手で変更したファイルは 10 個までである。AC-02 の例外で道具が生成した変更だけを含むファイルは、手で変更したファイルに数えない。`README.md` の変更に伴う `README.en.md` の変更は、行数にもファイル数にも数える。
- **AC-04**: 同じ文書が、対象になる変更は、ちょうど 1 つの類型に収まり、その類型の上限と全体の上限を満たすものだと定めている。2 つ以上の類型にまたがる変更は対象にならない。
- **AC-05**: 同じ文書が、分量にかかわらず次の変更は通常のプロセスとする、と定めている。
  - 意味が変わる文言の変更。`CLAUDE.md`・`.claude/commands/`・`docs/dev/conventions/` の変更は、誤字の修正だけを軽量プロセスの対象とし、それ以外は通常のプロセスとする。
  - 文字列で参照されるものの名前の変更。例は、JSON のタグ、プロトコルのメンバー、ストレージのキー、メッセージカタログのキー、`chrome.*` の名前、document test のリテラル、文書が名前で参照する識別子である。
  - 利用者に見える文言の、誤字の修正を超える変更。
  - `docs/dev/security.md` の適用条件に当たるもの。
  - 信頼境界に触れるもの。信頼境界は、`fixprguard`・`codexreview`・`mergepr`、秘密情報、`yt-dlp` の呼び出し、キャッシュである。
  - 依存パッケージの追加。
  - 方針の例外を伴うもの。
  - 設計上の選択肢が残るもの。
  - タスク文書（`docs/tasks/` の下）の編集。
  - 振る舞いを変える変更（バグの修正を含む）。
- **AC-06**: 同じ文書が、AC-02〜AC-05 のうち、実際の diff から機械的に確かめられる条件を示している。具体的には、類型ごとの行数、手で変更したファイルの数、AC-05 のうちパスで決まるもの（除外するパス）である。それ以外の条件は、サブエージェントによるレビュー（AC-24）が確かめる、と書いている。
- **AC-07**: 同じ文書の「Review Flow」（同書 63〜78 行）が、通常のプロセスの流れに加えて、軽量プロセスの流れを示している。流れは、`/mkreq` の振り分けから、仕様の承認、`/runissue`、`/runpr` によるマージと issue を閉じることまでである。

#### F-002: `/mkreq` での振り分け

`/mkreq` は、issue を読んだ直後に、軽量プロセスの条件に当たるかを判断し、当たるときだけ利用者に提案する。

**Acceptance Criteria**:
- **AC-08**: `/mkreq <issue>` を `[task]` なしで実行し、次のすべてに当たる場合を考える。issue が開いている。要件定義書がない（`.claude/commands/mkreq.md:42-49` の確認を通った）。AC-15 にも AC-32 にも当たらない。このとき `/mkreq` は、ブランチを作る前に、issue の内容が F-001 の条件に当たるかを判断する。
- **AC-09**: 当たると判断したときは、`AskUserQuestion` で軽量プロセスを提案する。問いの前の説明では、次のものを示す。
  - 類型
  - 見込みの変更量（追加・削除の行数とファイル数）
  - 当たると判断した理由
  - 投稿する仕様の文面の全文（AC-11）

  問いの選択肢は、示した文面のとおりに軽量プロセスで進むか、通常のプロセスで進むかである。利用者が文面を直す答え（選択肢にない答え）をしたときは、直した全文を示して、もう一度尋ねる。承認とするのは、示した全文のとおりに進む選択肢を選んだときだけである。
- **AC-10**: 迷うとき、当たらないと判断したとき、利用者が軽量プロセスを選ばなかったとき、`[task]` を渡したとき（AC-15 に当たる場合を除く）は、今の通常のプロセスのまま進む（ブランチの作成、要件定義書の作成）。この場合、`/mkreq` は issue にコメントせず、ラベルも付けない。
- **AC-11**: 利用者が軽量プロセスを選んだときは、`/mkreq` は要件定義書もブランチも作らない。issue に仕様のコメントを 1 件投稿し、その後に `lightweight` ラベルを付ける。仕様のコメントは日本語で、目印の行から始まり、やること・やらないこと・類型・確かめ方を含む。投稿する文面は、AC-09 で承認された全文と同じである。
- **AC-12**: 投稿の前に、コメントの文面に、PR レビューの依頼のメンションが含まれていないことを確かめる（`.claude/commands/_context.md` の「PR review request」の行が定める規則）。含まれていれば、投稿もラベルの付与もせずに止まり、報告する。
- **AC-13**: 投稿とラベルの付与が終わったら、`/mkreq` は、次に利用者が実行するコマンドとして `/runissue <N>` を示して終わる。`/mkreq` は `/runissue` を実行しない。
- **AC-14**: 仕様のコメントの投稿が失敗したときは、ラベルを付けずに止まる。そのうえで、issue のコメントを読み直して、仕様のコメントが投稿されていないことを確かめてから、何も投稿されていないことを報告する。読み直せないときや、投稿されたかどうかが分からないときは、投稿されたかどうか分からないことを報告し、利用者に issue を確かめるよう求める。投稿の後にラベルの付与が失敗したときは、止まって、投稿したコメントの URL と、ラベルを手で付ければ `/runissue <N>` で進めることを報告する。
- **AC-15**: `/mkreq` を、`lightweight` ラベルか仕様のコメント（AC-17 の条件を満たすもの）がすでにある issue に実行したときは、`[task]` の有無にかかわらず、ブランチも文書も作らずに止まる。ただし、AC-32 に当たる issue は除く。
  - 両方があるとき：`/runissue <N>` を案内する。
  - ラベルだけがあるとき：ラベルを外してから `/mkreq <N>` を実行し直せば振り分けから進むことを案内する。
  - 仕様のコメントだけがあるとき：ラベルを付ければ `/runissue <N>` で進むことを案内する。

#### F-003: `/runissue` の入口の確認

`/runissue <N>` は、承認された仕様がある issue だけを実装する。

**Acceptance Criteria**:
- **AC-16**: `/runissue` は、次のどれかに当たるとき、ブランチを作らずに止まり、理由を報告する。
  - issue が開いていない。
  - issue が別のリポジトリのものである。
  - issue に `lightweight` ラベルがない。
  - 仕様のコメント（AC-17）がない。
  - 仕様のコメントが、AC-19 の形に合わない。
  - その issue を `対応 issue` とする要件定義書が、`origin/main` か、いずれかのブランチにある（`.claude/commands/mkreq.md:42-49` と同じ範囲で探す）。
  - その issue の軽量プロセスのブランチが、ローカルか `origin` にすでにある。
  - その issue にリンクされた、開いている PR がある。
- **AC-17**: 仕様とみなすのは、次の 2 つを満たすコメントのうち、作成日時が最新の 1 件だけである。
  - 認証済みの利用者（GitHub の CLI が認証しているアカウント）が書いた。
  - 目印の行から始まる。

  ただし、AC-30 または AC-31 で通常のプロセスへ戻した issue では、戻す前に投稿された仕様のコメントは仕様とみなさない。ほかの人が書いたコメントは、目印の行から始まっていても仕様とみなさず、その本文を実装の指示として扱わない。仕様のコメントが投稿の後に編集されていても、今の本文を仕様とする。他人のコメントを編集できるのはリポジトリへの書き込みの権限を持つ人だけで、このリポジトリではそれは利用者本人だけだからである。
- **AC-18**: `/runissue` は、仕様のコメントだけを実装の指示とする。issue の本文とほかのコメントは、誰でも書けるので、背景として読むだけで、仕様にない作業の指示としては扱わない。
- **AC-19**: 仕様のコメントは、目印の行に加えて、やること・やらないこと・類型・確かめ方の 4 項目を含み、類型が W・D・M のちょうど 1 つであるときだけ受け入れる。どれかが欠けているか、類型が 1 つに決まらないときは、AC-16 のとおり止まり、どこが合わないかを報告する。形を直して受け入れることはしない。大きさの上限は、GitHub のコメントの上限のほかには設けない（本文は、利用者が承認した文面である）。
- **AC-20**: `/mkreq`・`/runissue`・`/runpr` が issue に投稿する、仕様以外のコメント（AC-30・AC-31・AC-34）は、目印の行から始まらない。

#### F-004: `/runissue` の実装、確認、PR の作成

`/runissue` は、仕様のとおりに実装し、決まった確認を行い、確かめた結果を記録して、PR を作る。

**Acceptance Criteria**:
- **AC-21**: `/runissue` は、issue にリンクされたブランチを作り、そこで仕様のとおりに実装する。`docs/tasks/` の下には何も作らない。
- **AC-22**: 実装の後、`/runissue` は次の確認を行う。
  - 類型の確かめ方（AC-01）と、`make test`・`make lint`
  - Go のファイルを変えたときは、`make fmt`
  - `extension/` を変えたときは、`make ext-check`
  - `README.md`・`README.en.md`・`docs/dev/guides/development.md` を変えたときは、`make ext-test`（`CLAUDE.md` の「Development Notes」）
  - `README.md` を変えたときは、README の同期の確認（`.claude/commands/mktrans.md` の「When a caller runs it」）。`README.en.md` が書き換えられたら、その変更も同じ PR に入れる。

  確認が通らないときは、仕様の範囲で直して確認をやり直す。仕様の範囲で直せないときは、AC-31 のとおり通常のプロセスへ戻す。README の同期（`/mktrans`）が止まったときも同じである。
- **AC-23**: テストを削除する変更では、削除を 1 つのコミットに分け、CLAUDE.md の「Deleting a test is a claim that must be checked」（`CLAUDE.md:504`）のとおりにカバレッジを比べる。比較の出力を、そのコミットのメッセージと PR の本文に書く。結果ごとの扱いは次のとおりである。
  - `PASS`：続ける。
  - `FAIL`：削除したテストがほかのコードも確かめていたことを示すので、類型 D の条件を外れたものとして、AC-30 のとおり通常のプロセスへ戻す。
  - `STOP <kind>`：比較ができなかったことを示すので、issue を変えずに止まり、`STOP` の種類を報告する。
- **AC-24**: `/runissue` は、サブエージェントによるレビューを 1 回行う。観点は、変更が F-001 の条件を満たすことと、仕様の範囲（やること・やらないこと）を超えないことである。条件を外れているという指摘があれば、AC-30 のとおり通常のプロセスへ戻す。それ以外の指摘は、仕様の範囲で直し、AC-22 の確認をやり直す。レビューをもう一度行うことはしない。
- **AC-25**: `/runissue` は、ローカルの CLI レビュー（`.claude/commands/_lib/local-cli-review.md`）を行う。
- **AC-26**: コミットメッセージには、確かめた結果を書く。書くのは、類型、実際の行数とファイル数、行った確認とその結果である。D の場合は、到達できないことを示した道具とその結果、M の場合は、道具が行を生成したコマンドも書く。PR の本文にも同じものを書く。squash merge のコミットメッセージには、今と同じく `/mergepr` が、CLAUDE.md がコミットメッセージに求める記録を書く（`.claude/commands/_context.md:51`）。
- **AC-27**: PR の本文は日本語で、次のものを含む。
  - 仕様のコメントへのリンク
  - 類型
  - 確かめた結果（AC-26）
  - レビュアーが確かめる点
  - `Closes #<N>`

  PR のタイトルは、`.claude/commands/_context.md` の「PR title and squash subject」の形に従う。タイトルと本文には、PR レビューの依頼のメンションを含めない（AC-12 と同じ確認）。
- **AC-28**: PR を作った後、`/runissue` は、Codex の PR レビューが始まったかを確かめ、始まらなかったときだけ依頼する（`.claude/commands/_lib/task-pr-handoff.md` の Part B 手順 5 と同じ扱い）。そしてレビュアーに知らせ、次の操作として、PR のレビューと `/runpr <PR>` を示して終わる。待つこともマージもしない。

#### F-005: 条件の確かめ直しと、通常のプロセスへの戻し

実際の diff が条件を外れたとき、または実装の途中で判断が必要になったときは、PR を作らずに通常のプロセスへ戻す。

**Acceptance Criteria**:
- **AC-29**: `/runissue` は、最後のコミットの後、push の直前に、ブランチの実際の diff（`origin/main` から分かれた点から、最後のコミットまで）で、AC-06 の機械的に確かめられる条件を確かめ直す。確かめるのは、類型の行数の上限、手で変更したファイルの数、除外するパスへの変更がないことである。AC-22・AC-25 の後に修正のコミットが増えたときも、最後のコミットで確かめ直す。
- **AC-30**: AC-29 の条件を 1 つでも満たさないとき、またはサブエージェントによるレビュー（AC-24）が条件を外れていると判断したときは、`/runissue` は次のことをこの順に行う。
  1. 実装のコミットを push せず、PR も作らない。
  2. 満たさなかった条件と実際の値（たとえば、追加行 42 行で上限 30 行）を、日本語で issue にコメントする。投稿の前に AC-12 と同じ確認をする。このコメントは、issue を通常のプロセスへ戻したことの記録になる（AC-32）。
  3. issue から `lightweight` ラベルを外す。
  4. `origin` にブランチがあり、そこに実装のコミットがなければ、そのブランチを消す。実装のコミットは、ローカルのブランチに残す。`origin` のブランチに実装のコミットがあるとき（手順 1 のとおりなら起きない）は、消さずに止まり、そのことを報告する。
  5. 通常のプロセス（`/mkreq <N>`）で進めるよう報告して止まる。

  コメントの投稿に失敗したとき（メンションの確認で止まったときを含む）は、ラベルを外さずに、その後の手順を行わずに止まり、通常のプロセスへ戻したことを記録できなかったことと、ラベルが残っていることを報告する。ラベルを外すことに失敗したときは、その後の手順を行わずに止まり、コメントで戻したことを記録したことと、ラベルを手で外すよう報告する。
- **AC-31**: 実装の途中で、仕様が決めていない判断が必要になったときも、AC-30 と同じことを行う。issue へのコメントには、必要になった判断を書く。
- **AC-32**: AC-30 または AC-31 で通常のプロセスへ戻した issue に `/mkreq <N>` を実行すると、`/mkreq` は振り分けをせず、通常のプロセスで進む。

#### F-006: `/runpr` でのマージと、issue を閉じること

軽量プロセスの PR は、今の `/runpr` が単独の変更として扱い、マージの後に issue を閉じる。

**Acceptance Criteria**:
- **AC-33**: `/runpr` は、軽量プロセスの PR を、今の単独の変更と同じ手順で扱う。手順は、Codex の PR レビューと CI を待つこと、`/fixpr`、1 つの問い、`/mergepr` でのマージである。NEXT（マージの後に案内する次のコマンド）はない。
- **AC-34**: 軽量プロセスの PR をマージした後、`/runpr` は、その PR の元になった issue が開いていれば、マージした PR を示す日本語のコメントを付けて閉じる。コメントの投稿の前に、AC-12 と同じ確認をする。
- **AC-35**: マージの後に実行が止まったあと、すでにマージされた軽量プロセスの PR に `/runpr` を実行したときも、その issue が開いていれば、AC-34 のとおり閉じる。
- **AC-36**: 軽量プロセスでない単独の変更の PR と、タスクの PR では、`/runpr` が issue を閉じる条件は今と変わらない（`.claude/commands/runpr.md:809-827`）。

#### F-007: 文書の更新

軽量プロセスとそのコマンドを、エージェントと人が読む文書に書く。

**Acceptance Criteria**:
- **AC-37**: CLAUDE.md が、軽量プロセスの概要と、F-001 の条件を定めた文書へのリンクを書いている。また、「Claude Commands」の一覧に `/runissue <N>` を載せ、「Each task PR is handled by two commands」の段落（`CLAUDE.md:166`）が、軽量プロセスでは `/mkreq` が要件定義書を作らず、`/runissue` が PR を作ることを述べている。
- **AC-38**: CLAUDE.md の「Each task lives in `docs/tasks/NNNN_<name>/`」（`CLAUDE.md:33`）と、`requirements_process.md` の「LLM Constraints」（同書 7〜14 行）が、軽量プロセスの例外とその範囲を述べている。範囲は、F-001 の条件を満たし、仕様が承認された変更である。
- **AC-39**: `.claude/commands/_context.md` が、ラベル名 `lightweight` と、`/runissue` が使うブランチ名、PR のタイトルとコミットの接頭辞の形を定めている。コマンドの定義は、その値を名前で参照する。
- **AC-40**: `.github/ISSUE_TEMPLATE/` の下に、軽量プロセス用の issue テンプレートがある。テンプレートは、背景・やること・やらないこと・確かめ方の見出しを置く。
- **AC-41**: リポジトリに `lightweight` ラベルがある。
- **AC-42**: `.claude/commands/runissue.md` が英語で書かれている。また、F-003〜F-005 の手順と、「Authorization」（承認されるネットワークの操作）を書いている。
- **AC-43**: `.claude/commands/mkreq.md` が、F-002 の手順を書いている。その「Authorization」（今は読み取りの操作だけを承認している。同書 26〜30 行）が、仕様のコメントの投稿とラベルの付与を承認している。
- **AC-44**: `.claude/commands/runpr.md` の「Authorization」が、軽量プロセスの PR の issue について、issue の読み取り、コメント、issue を閉じることを承認している。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   N/A（コマンドの手順と文書の変更であり、実行時の性能に関わらない）。

### 4.2. セキュリティ (Security)

-   `docs/dev/security.md` の適用条件（`.claude/commands/_context.md` の「Conditional-guide trigger」）は、製品のパイプライン（`yt-dlp` の呼び出し、API キー・Webhook の URL、キャッシュ、LLM API・Webhook への送信、LLM のプロンプトや記事への字幕・メタ情報の埋め込み）についてのものである。本タスクはそのどれにも触れないので、N/A とする。
-   一方、`/mkreq` と `/runissue` は、誰でも書ける issue の本文とコメントを、エージェントの文脈に読み込む。この危険には、`security.md` ではなく、次の機能要件で対処する。
    -   認証済みの利用者が書いた仕様のコメントだけを仕様とする（AC-17）。
    -   仕様のコメントだけを実装の指示とする（AC-18）。
    -   形に合わない仕様は直さずに拒否する（AC-19）。
    -   コマンドが投稿するほかのコメントは目印の行から始めない（AC-20）。
    -   投稿する文面にメンションを含めない（AC-12・AC-27・AC-30・AC-34）。
-   軽量プロセスは、信頼境界に触れる変更を対象にしない（AC-05）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   条件を満たさないとき、または判断が必要になったときは、実装のコミットを push せず、PR を作らない。issue のラベルとコメントを変え、実装のコミットのない `origin` のブランチを消して、通常のプロセスへ戻す（AC-30・AC-31）。
-   GitHub への書き込みが途中で失敗したときに、利用者が何をすれば進めるかを報告する（AC-14・AC-15・AC-30）。

### 4.4. 互換性 (Compatibility)

-   通常のプロセスの流れ、既存のタスク文書、タスクの PR での `/runpr` の振る舞いは変えない（AC-10・AC-36）。

### 4.5. 保守性 (Maintainability)

-   条件は `requirements_process.md` の 1 か所で定め、コマンドの定義はそれを参照する。コマンドが参照する値（ラベル名など）は `_context.md` の 1 か所で定める（AC-39）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   CLAUDE.md の「Document language」に従う。`.claude/commands/` と `docs/dev/conventions/` は英語、GitHub に書くもの（仕様のコメント、PR、issue のコメント、テンプレート）は日本語とする。
-   CLAUDE.md の「Tool Execution Safety」に従う。GitHub への書き込み（コメント、ラベル、PR、issue を閉じること）は、各コマンドの「Authorization」が承認する範囲で行う（AC-42〜AC-44）。
-   外部のライブラリは足さない（CLAUDE.md の「Dependencies」）。

## 6. 用語集 (Glossary)

-   **軽量プロセス:** F-001 の条件を満たす変更を、タスク文書を作らずに、仕様のコメントの承認と PR 1 本で進めるプロセス。
-   **通常のプロセス:** 要件定義書・アーキテクチャ設計書・実装計画書を作り、それぞれの承認を経て実装するプロセス（`requirements_process.md`）。
-   **類型:** W（文言）・D（削除）・M（機械的なリファクタ）のいずれか。
-   **仕様のコメント:** `/mkreq` が issue に投稿する、軽量プロセスの仕様（やること・やらないこと・類型・確かめ方）のコメント。目印の行から始まる。
-   **手で書いた行・手で変更したファイル:** 道具が生成した行（AC-02 の例外）を除いた、diff の行とファイル。
-   **確かめ直し:** 実装の後に、実際の diff で F-001 の機械的に確かめられる条件を確かめること。
-   用語は `docs/translation_glossary.md` と統一する。
