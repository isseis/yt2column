## 1. 概要 (Overview)

**目的:** 本書は、単純な変更を、要件・設計・計画の文書を作らずに 1 本の PR で進める軽量プロセスの要件を定義する。定めるのは次のことである。

-   軽量プロセスの対象になる条件
-   `/mkreq` での振り分け
-   軽量プロセスの仕様の記録と承認
-   実装のコマンド `/runissue`
-   マージと issue の扱い
-   更新する文書

**背景:**

タスク 0054（#560）の最終的な変更は、拡張の使われなくなった関数 1 つとそのテスト 1 つの削除だった（2 ファイル、−16 行）。これに対して、通常のプロセスで次のものを作った。

-   要件・申し送り・設計・計画の文書、計約 600 行
-   `_checks/removal_only.ts` 254 行
-   4 本の PR（#609・#611・#614・#615）と 17 のコミット

最初の PR からマージまで約 9 時間かかった。Codex の PR レビューの指摘は、4 本とも 0 件だった。ローカルのレビューの指摘の多くは、そのタスクのために作った確認の仕組みに向いていた。このように、変更の大きさに対して、文書の量とレビュー・マージの手間が釣り合っていない。

今は、どの変更も、要件定義書・設計書・実装計画が承認されるまで実装を始めない（`docs/dev/conventions/requirements_process.md:11-14`）。また、各タスクは `docs/tasks/NNNN_<name>/` に置く（`CLAUDE.md:33`）。`/mkreq` は、issue を読むと必ず要件定義書を作る（`.claude/commands/mkreq.md:34-112`）。

対応 issue: [#619](https://github.com/isseis/yt2column/issues/619)

関連: [#560](https://github.com/isseis/yt2column/issues/560)（タスク 0054。本 issue のきっかけ）、[#618](https://github.com/isseis/yt2column/issues/618)（テストの削除の前後でカバレッジを比べる道具。タスク 0055 で `make coverage-compare`・`make ext-coverage-compare` として実装済み。類型 D の確かめ方の前提）

**本書の記述範囲:** 本書は、次のことを定める。

-   軽量プロセスの対象になる条件と、行数・ファイル数の数え方
-   `/mkreq` が提案し、利用者が選ぶ流れ
-   仕様のコメントとラベル
-   `/runissue` の入口の確認と、実装・確認・PR の作成
-   確かめ直しで条件を満たさなかったときの扱い
-   `/runpr` でのマージと issue のクローズ
-   各文書に書かれていること

次のことは設計（`02_architecture.md`）で決める。

-   条件の確かめ直しの方法（スクリプトか、手順か）
-   除外するパスの正確な一覧と、その置き場所
-   仕様のコメントの目印の行と書式
-   `/runpr` が軽量プロセスの PR を見分ける方法
-   ブランチ名、コミットの接頭辞、コミットメッセージへの記録の書式
-   コマンドの定義のどの手順をどう書き換えるか

要件のレビューで挙がった設計事項は、[design_handoff.md](design_handoff.md) に申し送る。

**issue #619 で決めたこと:**

-   **変更を 3 つの類型に分け、類型ごとに分量の上限を設ける:** 類型は W（文言）・D（削除）・M（機械的なリファクタ）である。どれか 1 つの類型に収まり、全体の上限（PR 1 本、手作業で変更するファイル 10 個まで）も満たす変更を、軽量プロセスの対象とする。全体の上限は、人が 15 分でレビューできる大きさを目安にしている。
-   **分量にかかわらず、決まった種類の変更は通常のプロセスとする:** 機械的に把握できない範囲を含むためである（F-001 の AC-05）。
-   **振り分けは `/mkreq` が issue を読んだ直後に行う:** LLM が条件に当たるかを判断し、当たる場合は、類型・見込みの変更量・理由を示して軽量プロセスを提案する。迷うときと当たらないときは、通常のプロセスで進める。
-   **軽量プロセスでは要件定義書を作らない:** 代わりに、issue に「軽量プロセスの仕様」（やること・やらないこと・類型・確かめ方）をコメントで書き、ラベルを付ける。これを要件の承認に当たるものとする。
-   **実装は新しいコマンドで行い、`docs/tasks/` の下は作らない:** コマンドは、ブランチの作成、実装、ビルドの確認、サブエージェントによるレビュー 1 回、ローカルの CLI レビュー、コミットメッセージへの確認結果の記録、`Closes #N` 付きの PR の作成を行う。
-   **実装の後に、実際の diff で条件を確かめ直す:** 満たさなければ PR を作らずに止まり、通常のプロセスに戻すよう報告する。
-   **PR を作った後は、今の `/runpr` に、タスクのない単独の変更として渡す。**
-   **0054 で役に立ったものは残す:** 事実の確認、スコープの宣言、テストを削除するときのカバレッジの確認、確かめた結果をコミットメッセージに残すことである。

**要件定義の際に決めたこと（2026-11-04）:**

-   **実装のコマンドの名前は `/runissue` とする:** 既存のコマンド（`/runplan`・`/runpr`）の `run<対象>` の形に合わせ、issue を入力に取ることを名前で示すためである。
-   **ラベルの名前は `lightweight` とする:** 既存のラベル（`devenv`・`refactor`・`accessibility` など）に合わせて英語にする。
-   **軽量プロセスの PR のマージの後は、`/runpr` が issue を閉じる:** リポジトリの「Auto-close issues with merged linked pull requests」の設定は off である（`.claude/commands/_lib/task-pr-handoff.md:111-113`）。そのため、PR の本文の `Closes #N` だけでは issue は閉じない。今の `/runpr` が issue を閉じるのは、タスクの最後の計画 PR のマージの後だけである（`.claude/commands/runpr.md:809-827`）。設定を on にすると、タスクの issue が最初の PR のマージで閉じてしまうので、採らない。手作業で閉じる案も採らない。閉じ忘れると、issue の状態と実際の状態が食い違うためである。
-   **仕様は、`/mkreq` の問いの中で文面を示し、利用者がそれを選んだことで承認とする:** 承認の後に `/mkreq` が仕様を issue に投稿し、ラベルを付ける。先に投稿して、`/runissue` の実行を承認とみなす案は採らない。承認の時点がはっきりせず、文面を読まずに実行されうるためである。
-   **行数は、diff の追加行と削除行を別々に数える:** 1 行を書き換えると、追加 1 行・削除 1 行になる。issue の上限の書き方（「削除 100 行まで、追加 10 行まで」）と合い、機械的に確かめられる。
-   **確かめ直しで条件を満たさなかったときは、ラベルを外し、満たさなかった条件を issue にコメントし、ブランチのコミットを push しない:** 後で `/mkreq` を実行したとき、ラベルが残っていなければ、通常のプロセスで進むためである。会話の中で報告するだけにすると、issue の状態と実際の進め方が食い違う。
-   **実装の途中で判断が必要になったときも、止まって通常のプロセスへ戻す:** 扱いは、確かめ直しで条件を満たさなかったときと同じにする。issue は「issue のコメントで判断を求める」としていた。しかし、設計上の選択肢が残る変更は、もともと軽量プロセスの対象外である（issue の 1）。途中で判断が要ったことは、その前提が外れたことを示す。issue で尋ねて再開する案と、その場で尋ねて仕様に追記する案は、承認の後に仕様を変える流れを足すことになるので採らない。
-   **仕様とみなすのは、認証済みの利用者が書いた、目印の行で始まるコメントのうち最新の 1 件だけとする:** 公開リポジトリでは、issue には誰でもコメントできる。他人が書いた「仕様」を `/runissue` が実装しないようにするためである。ラベルがない issue では、`/runissue` は止まる。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

以下は、レビュアーと個別には確認していない。上の決定と現行の規則から導いたもので、PR のレビューで異論があれば改める。

-   **`/mkreq` に `[task]` を渡したときは、振り分けない:** 既存のタスクのディレクトリに書くことを、利用者がすでに選んでいるためである。
-   **ラベルがすでに付いた issue に `/mkreq` を実行したときは、止まって `/runissue <N>` を案内する:** 仕様が承認済みなので、要件定義書を作ると、同じ issue に 2 つの進め方が並ぶ。
-   **`README.md` の変更に伴う `README.en.md` の変更も、行数とファイル数に数える:** `/mktrans` が書く行は、道具が決まった diff を生成する行（類型 M の例外）に当たらない。また、数える対象から外すと、確かめ直しが単純でなくなる。
-   **PR の作成の後の修正（`/runpr` から行う `/fixpr`）では、条件を確かめ直さない:** PR のレビューで、レビュアーが判断する。確かめ直すと、`/runpr` と `/fixpr` にも軽量プロセスの条件を持ち込むことになる。
-   **軽量プロセスの PR にも、Codex の PR レビューは今のとおり 1 回付く:** `/runpr` の単独の変更の扱いを変えない（issue の 3）。

**方針の例外:**

-   **`requirements_process.md` の「Do not begin writing any implementation code until the status of `03_implementation_plan.md` is `approved`」（同書 13 行）と、CLAUDE.md の「Each task lives in `docs/tasks/NNNN_<name>/`」（`CLAUDE.md:33`）:** 軽量プロセスの対象になる変更は、タスク文書を作らず、仕様のコメントの承認だけで実装を始める。理由は「背景」のとおりで、例外の範囲は F-001 の条件に限る。例外は `requirements_process.md` と CLAUDE.md に明記する（F-007）。
-   **タスクの PR の本文には closing keyword を書かない規則（`.claude/commands/_lib/task-pr-handoff.md:244`）:** この規則はタスクの PR についてのものである。軽量プロセスの PR はタスクの PR ではないので、本文に `Closes #N` を書く（issue の 3）。例外ではないが、混同しないよう、`/runissue` の定義にその旨を書く。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   条件に当てはまる単純な変更を、文書を作らずに、PR 1 本で進められるようにする。
-   0054 で役に立った確認（事実の確認、スコープの宣言、テストを削除するときのカバレッジの確認、コミットメッセージへの記録）は、軽量プロセスでも残す。
-   条件を外れた変更が軽量プロセスのまま PR になることを、実際の diff での確かめ直しで防ぐ。

### 2.2. スコープ (In Scope)

-   軽量プロセスの条件の定義（`docs/dev/conventions/requirements_process.md`）
-   `.claude/commands/mkreq.md`：振り分け、仕様の提示と投稿、ラベルの付与
-   新しいコマンドの定義 `.claude/commands/runissue.md`
-   `.claude/commands/runpr.md`：軽量プロセスの PR のマージの後の、issue のクローズ
-   `.claude/commands/_context.md`：ラベル名、ブランチ名、コミットの接頭辞など、コマンドが参照する値
-   CLAUDE.md：概要と、コマンドの一覧への `/runissue` の追加
-   軽量プロセス用の issue テンプレート（`.github/ISSUE_TEMPLATE/` の下）
-   リポジトリへの `lightweight` ラベルの作成

### 2.3. スコープ外 (Out of Scope)

-   **通常のプロセスの手順の変更:** 要件・設計・計画の文書とその PR の流れは変えない。
-   **リポジトリの自動で閉じる設定の変更:** off のままにする（「要件定義の際に決めたこと」）。
-   **PR の作成の後の修正での確かめ直し:** 「上の決定から導いたこと」のとおり。
-   **既存の issue の振り分け直し:** 本タスクの後に `/mkreq` を実行した issue から適用する。すでに要件定義書がある issue は対象外である（`/mkreq` は、要件定義書がある issue では止まる。`.claude/commands/mkreq.md:42-49`）。
-   **本タスク自身への適用:** 本タスクは、コマンドの定義と `docs/dev/conventions/` の意味を変えるので、軽量プロセスの対象外であり、通常のプロセスで進める。
-   **Codex の PR レビューの扱いの変更:** 「上の決定から導いたこと」のとおり。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 軽量プロセスの対象になる条件

変更が軽量プロセスの対象になるかを、類型、分量、除外する変更の 3 つで決める。

**Acceptance Criteria**:
- **AC-01**: `docs/dev/conventions/requirements_process.md` が、次の 3 つの類型を定めている。
  - **W（文言）:** コメントや文書の、誤字・表記ゆれ・言い回しの修正で、意味を変えないもの。確かめ方は、diff を読むことである。README は `/mktrans` と既存の document test で確かめる。
  - **D（削除）:** 到達できないことが道具（`make deadcode`・`tsc`・`git grep`）で示されたコードと、それだけを確かめるテストの削除。確かめ方は、`make test`・`make lint`・`make ext-check` である。テストを削除するときは、CLAUDE.md の「Deleting a test is a claim that must be checked」（`CLAUDE.md:504`）の比較も行う。
  - **M（機械的なリファクタ）:** 誤りがあれば、コンパイラ・型検査・linter・既存のテストが必ず検出する変更。例は、参照がコードの中だけにある識別子の名前の変更、`golangci-lint run --fix`、移動である。確かめ方は、D と同じ確認に加えて、道具の再実行である。
- **AC-02**: 同じ文書が、類型ごとの分量の上限を次のとおり定めている。行は、diff の追加行と削除行を別々に数える。
  - **W:** 追加行・削除行とも 30 行まで。
  - **D:** 削除行 100 行まで、追加行 10 行まで。
  - **M:** 手で書いた追加行が 50 行まで。道具が生成した行は、使ったコマンドをコミットメッセージに書き、そのコマンドを変更の前の状態で再実行して同じ diff になる場合に限り、この上限に数えない。
- **AC-03**: 同じ文書が、全体の上限を定めている。PR は 1 本で、手作業で変更するファイルは 10 個までである。AC-02 の例外で道具が生成した変更だけを含むファイルは、手作業で変更するファイルに数えない。
- **AC-04**: 同じ文書が、対象になる変更は、ちょうど 1 つの類型に収まり、その類型の上限と全体の上限を満たすものだと定めている。2 つ以上の類型にまたがる変更は対象にならない。
- **AC-05**: 同じ文書が、分量にかかわらず次の変更は通常のプロセスとする、と定めている。
  - 意味が変わる文言の変更。`CLAUDE.md`・`.claude/commands/`・`docs/dev/conventions/` の変更は、誤字の修正だけを対象とする。
  - 文字列で参照されるものの名前の変更。例は、JSON のタグ、プロトコルのメンバー、ストレージのキー、メッセージカタログのキー、`chrome.*` の名前、document test のリテラル、文書が名前で参照する識別子である。
  - 利用者に見える文言の、誤字の修正を超える変更。
  - `docs/dev/security.md` の適用条件に当たるもの。
  - 信頼境界に触れるもの。信頼境界は、`fixprguard`・`codexreview`・`mergepr`、秘密情報、`yt-dlp` の呼び出し、キャッシュである。
  - 依存パッケージの追加。
  - 方針の例外。
  - 設計上の選択肢が残るもの。
  - タスク文書（`docs/tasks/` の下）の編集。
  - 振る舞いを変える変更（バグの修正を含む）。
- **AC-06**: 同じ文書が、AC-02〜AC-05 のうち、実際の diff から機械的に確かめられる条件を挙げている。挙げるのは、類型ごとの行数、手作業で変更するファイルの数、AC-05 のうちパスで決まるもの（除外するパス）である。それ以外の条件は、サブエージェントによるレビュー（AC-17）が確かめる、と書いている。
- **AC-07**: 同じ文書の「Review Flow」（同書 63〜78 行）が、通常のプロセスの流れに加えて、軽量プロセスの流れを示している。流れは、`/mkreq` の振り分けから、仕様の承認、`/runissue`、`/runpr` によるマージと issue のクローズまでである。

#### F-002: `/mkreq` での振り分け

`/mkreq` は、issue を読んだ直後に、軽量プロセスの条件に当たるかを判断し、当たるときだけ利用者に提案する。

**Acceptance Criteria**:
- **AC-08**: `/mkreq <issue>` を `[task]` なしで実行し、issue が開いていて、`lightweight` ラベルがなく、要件定義書もない場合を考える（`.claude/commands/mkreq.md:42-49` の確認を通った場合）。このとき `/mkreq` は、ブランチを作る前に、issue の内容が F-001 の条件に当たるかを判断する。
- **AC-09**: 当たると判断したときは、`AskUserQuestion` で軽量プロセスを提案する。問いの前の説明では、類型、見込みの変更量（追加・削除の行数とファイル数）、当たると判断した理由を示す。問いの選択肢には、投稿する仕様の文面（AC-11）を示す。
- **AC-10**: 迷うとき、当たらないと判断したとき、利用者が軽量プロセスを選ばなかったとき、`[task]` を渡したときは、今の通常のプロセスのまま進む（ブランチの作成、要件定義書の作成）。この場合、`/mkreq` は issue にコメントせず、ラベルも付けない。
- **AC-11**: 利用者が軽量プロセスを選んだときは、`/mkreq` は要件定義書もブランチも作らない。issue に仕様のコメントを 1 件投稿し、`lightweight` ラベルを付ける。仕様のコメントは日本語で、目印の行から始まり、やること・やらないこと・類型・確かめ方を持つ。投稿する文面は、AC-09 で示した文面と同じである。
- **AC-12**: 投稿の前に、コメントの文面に、PR レビューの依頼のメンションが含まれていないことを確かめる（`.claude/commands/_context.md` の「PR review request」の行が定める規則）。含まれていれば、投稿もラベルの付与もせずに止まり、報告する。
- **AC-13**: 投稿とラベルの付与が終わったら、`/mkreq` は次のコマンドとして `/runissue <N>` を示して終わる。`/runissue` を実行するのは、利用者が実行を選んだときだけである。
- **AC-14**: `lightweight` ラベルがすでに付いた issue に `/mkreq` を実行したときは、ブランチも文書も作らずに止まり、`/runissue <N>` を案内する。

#### F-003: `/runissue` の入口の確認

`/runissue <N>` は、承認された仕様がある issue だけを実装する。

**Acceptance Criteria**:
- **AC-15**: `/runissue` は、次のどれかに当たるとき、ブランチを作らずに止まり、理由を報告する。
  - issue が開いていない。
  - issue が別のリポジトリのものである。
  - issue に `lightweight` ラベルがない。
  - 仕様のコメント（AC-16）がない。
  - その issue を `対応 issue` とする要件定義書が、`origin/main` か、いずれかのブランチにある（`.claude/commands/mkreq.md:42-49` と同じ範囲で探す）。
  - その issue にリンクされた、開いている PR がある。
- **AC-16**: 仕様とみなすのは、認証済みの利用者（`gh api user` のログイン名）が書いたコメントで、目印の行から始まるもののうち、最新の 1 件だけである。ほかの人が書いたコメントは、目印の行から始まっていても仕様とみなさない。また、その本文を実装の指示として扱わない。

#### F-004: `/runissue` の実装、確認、PR の作成

`/runissue` は、仕様のとおりに実装し、決まった確認を行い、確認の結果を記録して、PR を作る。

**Acceptance Criteria**:
- **AC-17**: `/runissue` は、issue にリンクされたブランチを作り、そこで仕様のとおりに実装する。`docs/tasks/` の下には何も作らない。
- **AC-18**: 実装の後、`/runissue` は、類型の確かめ方（AC-01）と、`make test`・`make lint` を行う。`extension/` を変えたときは、`make ext-check` も行う。Go のファイルを変えたときは、`make fmt` も行う。どれかが通らなければ PR を作らない。
- **AC-19**: テストを削除する変更では、削除を 1 つのコミットに分け、CLAUDE.md の「Deleting a test is a claim that must be checked」（`CLAUDE.md:504`）のとおりにカバレッジを比べる。比較の出力を、そのコミットのメッセージと PR の本文に書く。比較が `PASS` でなければ、PR を作らない。
- **AC-20**: `/runissue` は、サブエージェントによるレビューを 1 回行う。観点は、変更が F-001 の条件を満たすことと、仕様の範囲（やること・やらないこと）を超えないことである。
- **AC-21**: `/runissue` は、ローカルの CLI レビュー（`.claude/commands/_lib/local-cli-review.md`）を行う。
- **AC-22**: コミットメッセージには、確かめた結果を書く。書くのは、類型、実際の行数とファイル数、行った確認とその結果である。D の場合は、到達できないことを示した道具とその結果、M の場合は、道具が生成した行を生んだコマンドも書く。
- **AC-23**: PR の本文は日本語で、次のものを持つ。
  - 仕様のコメントへのリンク
  - 類型
  - 確かめた結果
  - レビュアーが確かめる点
  - `Closes #<N>`

  PR の題名は、`.claude/commands/_context.md` の「PR title and squash subject」の形に従う。題名と本文には、PR レビューの依頼のメンションを含めない（AC-12 と同じ確認）。
- **AC-24**: PR を作った後、`/runissue` は、Codex の PR レビューが始まるようにし、レビュアーに知らせる。そして、次の操作として、PR のレビューと `/runpr <PR>` を示して終わる。待つこともマージもしない。

#### F-005: 条件の確かめ直しと、通常のプロセスへの戻し

実際の diff が条件を外れたとき、または実装の途中で判断が必要になったときは、PR を作らずに通常のプロセスへ戻す。

**Acceptance Criteria**:
- **AC-25**: PR を作る前に、`/runissue` は、ブランチの実際の diff（`origin/main` との merge-base から HEAD まで）で、AC-06 の機械的に確かめられる条件を確かめ直す。確かめるのは、類型の行数の上限、手作業で変更するファイルの数、除外するパスへの変更がないことである。
- **AC-26**: AC-25 の条件を 1 つでも満たさないとき、またはサブエージェントによるレビュー（AC-20）が条件を外れていると判断したときは、`/runissue` は次のことを行う。
  - ブランチのコミットを push せず、PR も作らない。
  - issue から `lightweight` ラベルを外す。
  - 満たさなかった条件と実際の値（たとえば、追加行 42 行で上限 30 行）を、日本語で issue にコメントする。投稿の前に AC-12 と同じ確認をする。
  - 通常のプロセス（`/mkreq <N>`）で進めるよう報告して止まる。ブランチは、ローカルに残す。
- **AC-27**: 実装の途中で、仕様が決めていない判断が必要になったときも、AC-26 と同じことを行う。issue へのコメントには、必要になった判断を書く。
- **AC-28**: AC-26 または AC-27 の後、同じ issue に `/mkreq <N>` を実行すると、ラベルがないので、AC-08 の判断から進む。

#### F-006: `/runpr` でのマージと issue のクローズ

軽量プロセスの PR は、今の `/runpr` が単独の変更として扱い、マージの後に issue を閉じる。

**Acceptance Criteria**:
- **AC-29**: `/runpr` は、軽量プロセスの PR を、今の単独の変更と同じ手順で扱う。手順は、Codex の PR レビューと CI を待つこと、`/fixpr`、1 つの問い、`/mergepr` でのマージである。NEXT はない。
- **AC-30**: 軽量プロセスの PR をマージした後、`/runpr` は、その PR が `Closes #<N>` で示す issue が開いていれば、マージした PR を示す日本語のコメントを付けて閉じる。コメントの投稿の前に、AC-12 と同じ確認をする。
- **AC-31**: 軽量プロセスでない単独の変更の PR と、タスクの PR では、`/runpr` が issue を閉じる条件は今と変わらない（`.claude/commands/runpr.md:809-827`）。

#### F-007: 文書の更新

軽量プロセスとそのコマンドを、エージェントと人が読む文書に書く。

**Acceptance Criteria**:
- **AC-32**: CLAUDE.md が、軽量プロセスの概要と F-001 の条件を定めた文書へのリンクを持っている。また、「Claude Commands」の一覧に `/runissue <N>` を持っている。
- **AC-33**: CLAUDE.md の「Each task lives in `docs/tasks/NNNN_<name>/`」（`CLAUDE.md:33`）と、`requirements_process.md` の「LLM Constraints」（同書 7〜14 行）が、軽量プロセスの例外とその範囲を述べている。範囲は、F-001 の条件を満たし、仕様が承認された変更である。
- **AC-34**: `.claude/commands/_context.md` が、ラベル名 `lightweight` と、`/runissue` が使うブランチ名とコミットの接頭辞の形を定めている。コマンドの定義は、その値を名前で参照する。
- **AC-35**: `.github/ISSUE_TEMPLATE/` の下に、軽量プロセス用の issue テンプレートがある。テンプレートは、背景・やること・やらないこと・確かめ方の見出しを持つ。
- **AC-36**: リポジトリに `lightweight` ラベルがある。
- **AC-37**: `.claude/commands/runissue.md` が英語で書かれている。また、F-003〜F-005 の手順と、「Authorization」（承認されるネットワークの操作）を持っている。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   N/A（コマンドの手順と文書の変更であり、実行時の性能に関わらない）。

### 4.2. セキュリティ (Security)

-   `docs/dev/security.md` の適用条件（`.claude/commands/_context.md` の「Conditional-guide trigger」）には当たらないので、N/A とする。本タスクは、`yt-dlp` の呼び出し、API キー・Webhook の URL、キャッシュ、LLM API・Webhook への送信、プロンプトや記事へのテキストの埋め込みのどれにも触れない。
-   ただし、issue のコメントはエージェントが読むテキストであり、誰でも書ける。他人のコメントを仕様とみなさないこと（AC-16）と、投稿する文面にメンションを含めないこと（AC-12・AC-23・AC-26・AC-30）を、機能要件として定めた。
-   軽量プロセスは、信頼境界に触れる変更を対象にしない（AC-05）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   条件を満たさないとき、または判断が必要になったときは、実装のコミットを push せず、PR を作らない。issue のラベルとコメントだけを変え、通常のプロセスへ戻す（AC-26・AC-27）。

### 4.4. 互換性 (Compatibility)

-   通常のプロセスの流れ、既存のタスク文書、タスクの PR での `/runpr` の振る舞いは変えない（AC-10・AC-31）。

### 4.5. 保守性 (Maintainability)

-   条件は `requirements_process.md` の 1 か所で定め、コマンドの定義はそれを参照する。コマンドが参照する値（ラベル名など）は `_context.md` の 1 か所で定める（AC-34）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   CLAUDE.md の「Document language」に従う。`.claude/commands/` と `docs/dev/conventions/` は英語、GitHub に書くもの（仕様のコメント、PR、issue のコメント、テンプレート）は日本語とする。
-   CLAUDE.md の「Tool Execution Safety」に従う。GitHub への書き込み（コメント、ラベル、PR）は、コマンドの「Authorization」が承認する範囲で行う。
-   外部のライブラリは足さない（CLAUDE.md の「Dependencies」）。

## 6. 用語集 (Glossary)

-   **軽量プロセス:** F-001 の条件を満たす変更を、タスク文書を作らずに、仕様のコメントの承認と PR 1 本で進めるプロセス。
-   **通常のプロセス:** 要件定義書・設計書・実装計画を作り、それぞれの承認を経て実装するプロセス（`requirements_process.md`）。
-   **類型:** W（文言）・D（削除）・M（機械的なリファクタ）のいずれか。
-   **仕様のコメント:** `/mkreq` が issue に投稿する、軽量プロセスの仕様（やること・やらないこと・類型・確かめ方）のコメント。目印の行から始まる。
-   **確かめ直し:** 実装の後に、実際の diff で F-001 の機械的に確かめられる条件を確かめること。
-   用語は `docs/translation_glossary.md` と統一する。
