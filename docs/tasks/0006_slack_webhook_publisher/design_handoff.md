# 設計への申し送り：Slack Webhook への投稿

## 本書の位置づけ

[01_requirements.md](01_requirements.md) の作成とレビューの過程で挙がった事項のうち、要件（観測できる振る舞い）ではなく、設計の段階で決める事項をまとめる。

-   `02_architecture.md` は、本書の各項目について、採用した手段または扱わない理由を記録する。本書の手段は候補であり、設計で別の手段を選んでもよい。ただし、対応する AC を満たすこと。
-   本書は承認対象の文書ではない。設計の作成時に参照し、項目を追加してよい。

## H-01: Slack の公式文書で確認する値

-   **事項:** 次を Slack の公式文書で確認し、出典（URL と確認日）とともに `02_architecture.md` に記す。
    -   `markdown` ブロックのテキストの文字数の上限。1 つのブロックの上限か、1 つのペイロードのすべての `markdown` ブロックの合計の上限か。
    -   文字数の数え方の単位（Unicode のコードポイント、UTF-16 の符号単位、バイトなど）。公式文書に記載がない場合は、どの解釈でも上限を超えない安全側の数え方（例: UTF-16 の符号単位で数える、または UTF-8 のバイト数で数える）を選び、その理由を記す。日本語の記事では、UTF-8 のバイト数で数えると 1 つのメッセージに入る文字数がおよそ 3 分の 1 になる。分割の数が増えることとの兼ね合いを示す。
    -   Incoming Webhook の成功の応答（ステータスと本文）と、主なエラーの応答（`invalid_payload`・`no_service`・`channel_is_archived` など）。
    -   Incoming Webhook のレート制限。分割したメッセージを続けて送るとき、間に待つ必要があるか。
    -   通知（プッシュ通知やチャンネル一覧の表示）に使われるトップレベルの `text` を、`markdown` ブロックと併せて送るべきか。
-   **理由:** 上限の値と数え方を誤ると、Slack がペイロードを拒否する（`invalid_blocks` など）か、表示が途中で切れる。
-   **関連:** F-003・F-004

## H-02: メンションの通知を抑止する手段

-   **事項:** `markdown` ブロックで送ったテキストのうち、Slack がメンションとして解釈する記法を、公式文書と実際の Slack のテスト用チャンネルへの投稿で確認する。対象は少なくとも `<!channel>`・`<!here>`・`<!everyone>`・`<@U…>`・`<!subteam^…>`・平文の `@channel`・`@here`・`@everyone` とする。そのうえで、抑止の手段を選ぶ。
-   **手段の候補:**
    -   (a) 解釈される記法を含む記事を、最初のメッセージを送る前に拒否する。[CLAUDE.md](../../../CLAUDE.md)「Reject, don't normalize」に沿う。ただし、記事が正当な文脈で `@here` などの文字列を含む場合（例: Slack の使い方を解説する動画）にも、その記事を投稿できない。
    -   (b) 解釈される記法を、通知として解釈されない形に変換して送る（Slack の `&lt;`・`&gt;` のエスケープ、ゼロ幅の文字の挿入など）。記事の表示が変わらないことを確認する必要がある。また、`markdown` ブロックが HTML の文字参照をどう表示するかを確かめる必要がある。
    -   (c) ペイロードのオプション（`link_names` など）で解釈を止める。`markdown` ブロックに効くかを確認する必要がある。
-   (b) は記事の入力を補正するものではなく、Slack への出力のための符号化である。採用する場合は、その区別と、変換の対象を漏れなく列挙できる根拠を `02_architecture.md` に示す。
-   **関連:** F-006・AC-21・AC-22

## H-03: Webhook URL の検証の規則の共有

-   **事項:** `internal/config` の `validSlackWebhook` と同じ規則を、`SlackWebhookPublisher` の構築でも適用する（F-001）。規則を 2 か所に書くと、一方だけが変わったときに食い違う。
-   **手段の候補:**
    -   (a) 検証済みの Webhook URL を表す型（非公開のフィールドと、検証するコンストラクタだけを持つ型）を設け、`internal/config` がそれを返し、`SlackWebhookPublisher` がそれを受け取る（[CLAUDE.md](../../../CLAUDE.md)「Enforce invariants with the type, not with convention」）。型を置くパッケージ（`internal/secret`・`internal/publisher` など）は、`internal/config` から `internal/publisher` への依存を作るかどうかを含めて決める。
    -   (b) 検証の関数を 1 つのパッケージに置き、両方から呼ぶ。
-   テスト用のループバックの送信先は、この規則を満たさない。テスト用のビルドでだけ使える構築の手段（既存の `deepseek.NewForLoopbackTest` と同じ考え方）で、規則を迂回する範囲をループバックアドレスに限る。
-   **関連:** F-001・AC-03

## H-04: 投稿先の選択の表し方

-   **事項:** `internal/job` の `Request.OutPath` は現在必須であり、`job.Run` は `--out` の事前確認（`precheckOutput`）を常に行う。`--slack` では `OutPath` がない。`OutPath` が空かどうかで事前確認の有無を決めると、文字列の内容から振る舞いを推し量ることになる（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。
-   **手段の候補:** 投稿先の種類を列挙した型（ゼロ値はどの投稿先でもなく、拒否される）を `job.Request` に持たせ、`switch` で事前確認の有無を決める。または、事前確認を `Publisher` の側の任意の interface（例: 実行前に確認できる投稿先が実装するもの）として表す。CLI のフラグの解析でも、`--out` と `--slack` の組み合わせを同じ列挙値に変換してから使う。
-   **関連:** F-007・AC-23・AC-24

## H-05: 統合テストのオプトインの変数と make のターゲット

-   **事項:** F-008 の 2 つの統合テストのオプトインの変数と make のターゲットを決める。既存のターゲット（`make test-integration-deepseek`・`make test-integration-cli`）と同じく、各ターゲットは自分のオプトインだけをエクスポートする。
-   CLI の統合テストを、既存の `make test-integration-cli`（ファイル出力まで）に加えるか、別のターゲットにするかを決める。加える場合、既存のターゲットの実行にテスト用の Webhook URL が必須になる。
-   実行条件の判定は、既存の `internal/llm/deepseek/testutil` の `SettingsFrom` と共有するか、同じ考え方で設けるかを決める。テスト用の Webhook URL がない場合は失敗する（AC-29）。
-   テスト用の Webhook URL の形式の検証は、本番と同じ規則（H-03）で行う。
-   **関連:** F-008・AC-29〜AC-31

## H-06: Webhook URL を含まないエラーの作り方

-   **事項:** `http.Client.Do` が返す `*url.Error` は、`Error()` に URL を含む。`errors.Unwrap` でたどれるすべてのエラーから URL を除く（F-005）には、`*url.Error` を返さずに、その `Err`（内側のエラー）だけを包む必要がある。ただし、内側のエラーも URL を含みうる。
    -   `CheckRedirect` が返したエラーは、`*url.Error` の内側に入る。リダイレクトを止めるために返すエラーは、URL を含まない固定の値にする。
    -   `net.OpError` などは接続先のアドレス（ホストとポート）を含む。ホスト（`hooks.slack.com`）は秘密ではないが、パスを含まないことを確かめる。
    -   `http.ErrUseLastResponse` を使ってリダイレクトの応答をそのまま受け取る方法もある。この場合、3xx は通常の応答として扱える。
    -   `http.Client.Timeout` による打ち切りのエラーが `context.DeadlineExceeded` に対して `errors.Is` で真になるかは、Go の版によって異なりうる。AC-16 を満たすために、タイムアウトを `context.WithTimeout` で与えるか、`http.Client.Timeout` を使うかを決める。
-   **理由:** 内側のエラーまで URL を除かないと、呼び出し元が `errors.AsType` で内側のエラーを取り出して出力したときに、Webhook URL が漏れる。CLI は既存の仕組みで秘密の値を伏せる（0005 の F-008）が、`SlackWebhookPublisher` は CLI 以外からも使われうる。
-   **関連:** F-005・AC-19

## H-07: エラーの分類の番兵と、応答の本文の検出

-   **事項:** 要件定義書 3.2 は、拒否をどの分類で報告するかを仮称で定めている。次を設計で決める。
    -   各分類の番兵エラー（または型）の名前と置き場所。`internal/publisher` に置くか、`internal/llm/deepseek` の同種の番兵（`ErrHTTPStatus`・`ErrInvalidResponse`・`ErrTransport`）と共有するか。共有する場合は、パッケージの依存の向きを含めて示す。
    -   応答の本文が `ok` と一致しないことと、上限を超えることの検出の手段。候補は、上限まで読んだうえで 1 バイト多く読めるかを確かめる方法（上限ちょうどの本文と上限を超える本文を区別できる）。
    -   応答の本文の上限値。Slack のエラーの理由（`invalid_payload` など）を読める長さとする。
-   **理由:** 番兵を共有するかどうかでパッケージの依存が変わる。上限を超えたことを検出しないと、切り詰めた本文を `ok` と比べてしまい、拒否の分類を取り違えうる。
-   **関連:** F-003・F-004・F-005・AC-11・AC-13〜AC-15・AC-35
