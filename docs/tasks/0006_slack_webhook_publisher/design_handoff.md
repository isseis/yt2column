# 設計への申し送り：Slack 互換の Webhook への投稿

## 本書の位置づけ

[01_requirements.md](01_requirements.md) の作成とレビューの過程で挙がった事項のうち、要件（観測できる振る舞い）ではなく、設計の段階で決める事項をまとめる。

-   `02_architecture.md` は、本書の各項目について、採用した手段または扱わない理由を記録する。本書の手段は候補であり、設計で別の手段を選んでもよい。ただし、対応する AC を満たすこと。
-   本書は承認対象の文書ではない。設計の作成時に参照し、項目を追加してよい。
-   2026-10-07: 検証の対象を Mattermost の Slack 互換の Incoming Webhook とし、Slack を best effort としたことに合わせて、全項目を改めた（要件定義書 2.2 の「対応の範囲」）。

## H-01: Mattermost の公式文書で確認する値

-   **事項:** 次を Mattermost の公式文書（記載がなければサーバのソース）で確認し、出典（URL と確認日、ソースならその版）とともに `02_architecture.md` に記す。
    -   1 つの投稿の `text` の文字数の上限（公式文書の Incoming Webhook の頁は、サーバ v5.0 以降で 16383 文字とする）と、上限を超えた場合の扱い（自動で複数の投稿に分けるか）。
    -   文字数の数え方の単位（Unicode のコードポイント、UTF-16 の符号単位、バイトなど）。確かめられない場合は、どの解釈でも上限を超えない安全側の数え方を選び、その理由を記す。日本語の記事で分割の数が増えることとの兼ね合いを示す。
    -   Incoming Webhook の成功の応答（ステータスと本文）と、エラーの応答の形（ステータスと本文。JSON か平文か、どの項目にエラーの理由が入るか）。
    -   レート制限（サーバの設定による制限の有無と、超えた場合の応答）。分割したメッセージを続けて送るとき、間に待つ必要があるか。
    -   `silent` が使えるサーバの版と、対応しない版のサーバに `silent` を送った場合の扱い（無視されるか、拒否されるか）。
    -   Slack は best effort なので確認の対象ではない。ただし、Mattermost に合わせて選んだ上限と数え方が Slack で明らかに不都合な場合（Slack の `text` の上限が Mattermost の上限より小さいことが公式文書で分かる場合など）は、その旨と、Slack の上限に合わせるかどうかの判断を記す。
-   **理由:** 上限の値と数え方を誤ると、サーバが投稿を拒否するか、自動で分割して分割の位置の表示と食い違う。`silent` を拒否する版のサーバでは、すべての投稿が失敗する。
-   **関連:** F-003・F-004・F-006

## H-02: 拒否するメンションの記法の範囲と、検出の手段

-   **事項:** F-006 は、`silent` の指定と、通知の記法を含む記事の拒否を併用すると定めている。拒否について、次を決める。
    -   対象の記法。少なくとも要件定義書 F-006 に挙げた Mattermost と Slack の記法（`@channel`・`@all`・`@here`・`@everyone`・`@ユーザー名`・`@グループ名`・`<!channel>`・`<!here>`・`<!all>`・`<!everyone>`・`<@U…>`・`<!subteam^…>`）とする。大文字と小文字の違い（`@Channel` など）を含めるか。
    -   変形の扱い。Markdown のバックスラッシュのエスケープ（`\@here`）、HTML の文字参照（`&#64;here`）、見た目の似た文字（全角の `＠`）、表示されない文字（U+200B）を挟んだ形を、拒否の対象に含めるか。
    -   名前の形をした `@` の並びをすべて拒否する場合の、正当な記事への影響（YouTube のハンドル、メールアドレス、プログラミングの注釈など）と、それを許すかどうか。
-   **理由:** `silent` だけでは、対応しない版の Mattermost のサーバと Slack で通知を防げない。拒否だけでは、検出の漏れで通知を防げない。両方の層が働く範囲を設計で明確にする。
-   **関連:** F-006・AC-21・AC-22

## H-03: Webhook URL の検証の規則の共有

-   **事項:** `internal/config` が `SLACK_WEBHOOK_URL` に適用する規則（URL として解析できる、スキームが `https`、ホストが空でない）を、`SlackWebhookPublisher` の構築でも適用する（F-001）。規則を 2 か所に書くと、一方だけが変わったときに食い違う。
-   **手段の候補:**
    -   (a) 検証済みの Webhook URL を表す型（非公開のフィールドと、検証するコンストラクタだけを持つ型）を設け、`internal/config` がそれを返し、`SlackWebhookPublisher` がそれを受け取る（[CLAUDE.md](../../../CLAUDE.md)「Enforce invariants with the type, not with convention」）。ただし、要件定義書 F-001 は構築の引数を `secret.Secret` と定めている。
    -   (b) 検証の関数を 1 つのパッケージに置き、両方から呼ぶ。
-   テスト用のループバックの送信先は `http` であり、この規則を満たさない。テスト用のビルドでだけ使える構築の手段（既存の `deepseek.NewForLoopbackTest` と同じ考え方）で、規則を迂回する範囲をループバックアドレスに限る。
-   既存の `config.validSlackWebhook` と、それを確かめるテストは、この規則に置き換える。
-   **関連:** F-001・AC-03・AC-03a

## H-04: 投稿先の選択の表し方

-   **事項:** `internal/job` の `Request.OutPath` は現在必須であり、`job.Run` は `--out` の事前確認（`precheckOutput`）を常に行う。`--slack` では `OutPath` がない。`OutPath` が空かどうかで事前確認の有無を決めると、文字列の内容から振る舞いを推し量ることになる（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。
-   **手段の候補:** 投稿先の種類を列挙した型（ゼロ値はどの投稿先でもなく、拒否される）を `job.Request` に持たせ、`switch` で事前確認の有無を決める。または、事前確認を `Publisher` の側の任意の interface（例: 実行前に確認できる投稿先が実装するもの）として表す。CLI のフラグの解析でも、`--out` と `--slack` の組み合わせを同じ型の値に変換してから使う。
-   **関連:** F-007・AC-23・AC-24

## H-05: 統合テストのオプトインの変数と make のターゲット

-   **事項:** F-008 の 2 つの統合テストのオプトインの変数と make のターゲットを決める。既存のターゲット（`make test-integration-deepseek`・`make test-integration-cli`）と同じく、各ターゲットは自分のオプトインだけをエクスポートする。
-   CLI の統合テストを、既存の `make test-integration-cli`（ファイル出力まで）に加えるか、別のターゲットにするかを決める。加える場合、既存のターゲットの実行にテスト用の Webhook URL が必須になる。
-   実行条件の判定は、既存の `internal/llm/deepseek/testutil` の `SettingsFrom` と共有するか、同じ考え方で設けるかを決める。テスト用の Webhook URL がない場合は失敗する（AC-29）。
-   テスト用の Webhook URL の形式の検証は、本番と同じ規則（H-03）で行う。
-   **関連:** F-008・AC-29〜AC-31

## H-06: Webhook URL を含まないエラーの作り方

-   **事項:** `http.Client.Do` が返す `*url.Error` は、`Error()` に URL を含む。`errors.Unwrap` でたどれるすべてのエラーから URL を除く（F-005）には、`*url.Error` を返さずに、その `Err`（内側のエラー）だけを使う必要がある。ただし、内側のエラーも URL を含みうる。
    -   `CheckRedirect` が返したエラーは、`*url.Error` の内側に入る。リダイレクトを止めるために返すエラーは、URL を含まない固定の値にする。
    -   `net.OpError` などは接続先のアドレス（ホストとポート）を含む。Mattermost のサーバのホストは秘密ではないが、パスを含まないことを確かめる。
    -   `http.ErrUseLastResponse` を使ってリダイレクトの応答をそのまま受け取る方法もある。この場合、3xx は通常の応答として扱える。
    -   `http.Client.Timeout` による打ち切りのエラーが `context.DeadlineExceeded` に対して `errors.Is` で真になるかは、Go の版によって異なりうる。AC-16 を満たすために、タイムアウトを `context.WithTimeout` で与えるか、`http.Client.Timeout` を使うかを決める。
-   **理由:** 内側のエラーまで URL を除かないと、呼び出し元が `errors.AsType` で内側のエラーを取り出して出力したときに、Webhook URL が漏れる。CLI は既存の仕組みで秘密の値を伏せる（0005 の F-008）が、`SlackWebhookPublisher` は CLI 以外からも使われうる。
-   **関連:** F-005・AC-19

## H-07: エラーの分類の番兵と、応答の本文の検出

-   **事項:** 要件定義書 3.2 は、拒否をどの分類で報告するかを仮称で定めている。次を設計で決める。
    -   各分類の番兵エラー（または型）の名前と置き場所。`internal/publisher` に置くか、`internal/llm/deepseek` の同種の番兵（`ErrHTTPStatus`・`ErrInvalidResponse`・`ErrTransport`）と共有するか。共有する場合は、パッケージの依存の向きを含めて示す。
    -   応答の本文が `ok` と一致しないことと、上限を超えることの検出の手段。候補は、上限まで読んだうえで 1 バイト多く読めるかを確かめる方法（上限ちょうどの本文と上限を超える本文を区別できる）。
    -   応答の本文の上限値。Mattermost のエラーの応答（H-01）を読める長さとする。
    -   `200` 以外の応答の本文から、エラーの理由として何を読み取ってエラーに含めるか（JSON の識別子の項目だけか、説明の文も含めるか）。本文は信頼できない値なので、Webhook URL の一部や制御文字が入りうることを前提に、含める形を限る。
-   **理由:** 番兵を共有するかどうかでパッケージの依存が変わる。上限を超えたことを検出しないと、切り詰めた本文を `ok` と比べてしまい、拒否の分類を取り違えうる。
-   **関連:** F-003・F-004・F-005・AC-11・AC-13〜AC-15・AC-20・AC-35
