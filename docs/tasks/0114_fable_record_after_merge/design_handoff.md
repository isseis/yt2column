# 設計への引き継ぎ：Fable の部分レビューの記録の後、push の前にできた commit を、PR を開く前に確かめる

`02_architecture.md` が扱う項目。どれも、要件定義（[01_requirements.md](01_requirements.md)）で出た、手段の選択である。

## H-01: push の直前の再判定を、手順のどこに、どの入口として置くか

**懸念:** 再判定（AC-01〜AC-06）は、`_lib/task-pr-handoff.md` Part B の step 2（CHECKS）と step 3（push）の間に置くのが自然である。ただし、`fable-review.md` に新しい入口（たとえば「pre-push」）を足すか、チェックポイントの入口（Entry 3）を広げて使うかは決まっていない。チェックポイントの入口は、有効なら印の commit を作る。push の直前に印を作ると、commit が 1 つ増える。

**なぜ大事か:** 入口の数と、それぞれが何を作るかは、有効かの判定の規則（`fable-review.md`「The validity decision」）と、判定のスクリプトの `<ENTRY>` の引数に響く。

**案:** 新しい入口を足し、有効なら何も作らず、有効でなければ単独の経路（`fable-review.md`「The standalone path」）を走らせて、もう一度判定する。単独の経路の後に CHECKS を走らせ直すかも、合わせて決める。単独の経路の直しは文書や実装を変えうるので、CHECKS を走らせ直す必要がある。

**関連:** F-001、AC-01〜AC-06

## H-02: タスク文書の PR の Part B step 2 の直しを、記録を無効にしない commit と見分ける方法

**懸念:** `/runplan` では、チェックポイントの印の後の commit を、判定のスクリプトの規則 3 が無効にしない（`review-records.sh:104-108`）。タスク文書の PR には印がないので、Part B step 2 の直しは、今の規則では記録を無効にする。

**なぜ大事か:** 見分け方を誤ると、Part B step 2 の直しでない中身のある commit まで無効にしない側に入り（AC-11）、Fable を飛ばして PR が開きうる。判定の関門で誤って有効と判定する側の誤りである。

**案:** 次の 2 つから選ぶ。
- **(a)** タスク文書の PR でも、Part B step 2 の前に印の commit を作る（チェックポイントの入口と同じ形）。規則 3 を、`<ENTRY>` によらず、印があれば効くように広げる。
- **(b)** 記録の commit から Part B step 2 の前までに作られた commit がないことを、セッションが確かめてから印を作る。

印の後に merge commit があるときに無効のままとなること（AC-08）は、今の「merge commit はどの規則にも当たらない」で満たされる。これを判定のスクリプトのテストで確かめる。印の後に phase group の実装の記録があるときに印を使わない、今の除外とも整合させる。

**関連:** F-002、AC-07、AC-08、AC-11

## H-03: 判定のスクリプトを変えるかと、そのテスト

**懸念:** H-02 の案 (a) は、`review-records.sh` の規則 3 を変える。スクリプトは `origin/main` から取り出して走るので、変更がスクリプトに効くのは、本タスクの PR のマージ後である。本タスクの実装の PR 自身の判定には、変更の前のスクリプトが使われる。

**なぜ大事か:** 実装の PR の順序や、本タスク自身の PR で何を確かめられるかに響く。

**案:** スクリプトの変更は、ほかの手順の変更より前の PR に分けるか、同じ PR で、マージ前の確かめを使い捨てのクローンで行う。スクリプトのテスト（`.claude/commands/_lib` のテスト）に、次の形のブランチを足す。
- 記録 → 印 → 直し（有効）
- 記録 → 印 → merge commit（有効でない）
- 記録 → 中身のある commit → 印 → 直し（有効でない）

**関連:** AC-07、AC-08、AC-10、AC-11

## H-04: PR の説明の「どちらの CLI もレビューしなかった commit」を、記録の後の commit について求める方法

**懸念:** AC-12〜AC-14 は、記録の後の commit のうち中身のあるものを挙げる。中身のない commit の定義は、判定のスクリプトの中にある（`review-records.sh` の `checkbox_only` など）。セッションが手順の文に従って手で判定すると、`fable-review.md` の規則と食い違いうる。

**なぜ大事か:** 一覧の誤りは、人が PR レビューを追加で頼むかの判断を誤らせる。ただし、PR を開く関門ではない。

**案:** 判定のスクリプトの `coverage` モードを使えるかを検討する。`coverage` は、中身のない commit と見た範囲の行の範囲を「見た」とし、merge commit を「見ていない」とする（`review-records.sh:28-45`）。LAST_REVIEWED に `none` を渡せば、`origin/main..HEAD` の見ていない commit の一覧が得られる。それが、セッションのレビューの SUMMARY による今の規則（`task-pr-handoff.md:250-260`）とどう合わさるかを決める。

**関連:** F-003、AC-12〜AC-14
