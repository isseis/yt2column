## 1. 概要 (Overview)

**目的:** 本書は、ブラウザ拡張と localhost サーバの通信を、HTTP（loopback）と共有トークンから、Native Messaging ホスト（以下、ホスト）と Unix ドメインソケット（UDS）に移行する要件を定義する。ジョブ（1 件のリクエストに対する記事の生成と Slack への投稿の処理）はサーバが持ったまま、ブラウザとの境界だけを置き換える。

**背景:**
現在の拡張は、収集した字幕と動画ページの URL を、`127.0.0.1` のサーバへ HTTP で送る（`0011_localhost_server`・`0020_extension_send`）。サーバは loopback への bind に加えて、`Host`・`Origin`・`Content-Type`・共有トークンを検査し、認証前に副作用を起こさないようにしている（`docs/dev/security.md` §8・§8.2）。共有トークンは利用者が拡張のオプションページに貼り付ける必要があり、その表示は #266（`0021_shared_token_display`）で見直した。

[#272](https://github.com/isseis/yt2column/issues/272) は、この通信を Native Messaging に移行するかどうかを検討し、次の 3 案を記録した。

1. フル移行: Native Messaging のホストに処理をすべて持たせる。
2. 中間案: 常駐サーバは残し、待ち受けを TCP から UDS に変える。Native Messaging のホストは、受け取ったメッセージをソケットへ転送するだけにする。
3. 移行しない。

議論の結果、**中間案を採用する**。この案なら、フル移行の最大の論点であるジョブの寿命（ブラウザを閉じたとき、拡張を再読み込みしたとき）の問題を避けられる。秘密情報と設定の読み方（ブラウザが起動するプロセスはシェルの環境変数を引き継がない問題）とログの出力先（標準出力が通信路になる問題）も、サーバ側に残せる。サーバは引き続き手動で起動する。

**決定事項:**

- サーバは TCP をやめ、UDS だけを待ち受ける。ソケットは `0700` のディレクトリに置き、`0600` にする。
- 共有トークン、ポート設定（`YT2COLUMN_SERVER_PORT`）、拡張の `host_permissions`、オプションページのトークン/ポートを削除する。
- Native Messaging のホストは中継役に徹し、記事の JSON を解釈しない。接続できる拡張は manifest の `allowed_origins` で固定の拡張 ID に限定する。
- ジョブはサーバ側で動かし、ホストは受付応答（`202` 相当）を返したら終了する。ブラウザを閉じてもジョブは続く。
- タスクは 3 つに分けず、`0026_native_messaging_relay` の 3 フェーズ（サーバの UDS 化、ホスト、拡張）とする。
- UDS 上のプロトコル（HTTP/1.1 の再利用か、4 バイト長 + JSON のフレームか）は `02_architecture.md` で決める。本書は、1 メッセージ 1 リクエスト、上限、固定の応答、応答がジョブの完了を待たないことだけを定める。

**セキュリティ上の前提:**
共有トークンは「拡張の認証」ではなく、**トークンのファイルを読める相手だけが示せる秘密の値（capability）で、ファイルを読めない相手を排除するもの**だった。同一ユーザーでファイルを読めるプロセスは、トークンのファイルも `.envrc` も読める。したがって、同一ユーザーのフル権限プロセス（AI Agent を含む）は信頼する。それ以外の相手を排除する根拠は、相手ごとに異なる。他ユーザーは、UDS のディレクトリ `0700` とソケット `0600` で排除する。ウェブページは、ブラウザがページから UDS へ接続する手段を持たないことで排除する。サンドボックス化された Agent は、サンドボックスのポリシーが Unix ソケットへの接続を禁じている場合にだけ排除され、UDS の権限では排除できない（ファイルのモードは同じ uid のプロセスを区別しない）。UDS 化によって、この点が後退することはない。残余リスク（同一ユーザーによるソケットの `unlink`/再 bind、ホストのバイナリ/manifest の置き換え、`.envrc` の秘密の読み取り）は `security.md` に明記し、受け入れる（§4.2）。

対応 issue: [#272](https://github.com/isseis/yt2column/issues/272)（関連: [#43](https://github.com/isseis/yt2column/issues/43)、[#104](https://github.com/isseis/yt2column/issues/104)、[#109](https://github.com/isseis/yt2column/issues/109)、[#110](https://github.com/isseis/yt2column/issues/110)、[#111](https://github.com/isseis/yt2column/issues/111)、[#266](https://github.com/isseis/yt2column/issues/266)）

**本書の記述範囲:** 本書は、観測できる振る舞い（何を送り、どこで待ち受け、何を表示するか）を定める。ソケットパスの具体値、UDS 上のフレーム、ホストの起動方法、表示の正確な文言、タイムアウトの値、テストの手段は設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は `design_handoff.md` に申し送る。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

- 共有トークンの生成・表示・貼り付け・保存をなくす。利用者は、ホストを一度インストールした後、トークンを貼り付けずに拡張を使える。
- ウェブページから localhost のサーバへリクエストが届く経路をなくす。サーバは UDS だけを待ち受け、接続できる相手を同一ユーザーに限定する。
- サーバの停止中に、同じマシンの別のプロセスが同じ TCP ポートで待ち受けて字幕を受け取るリスク（`security.md` §8.2）をなくす。同一ユーザーが UDS のパスを先に bind する残余リスクは残る（§4.2）。
- ブラウザを閉じたとき、拡張を再読み込みしたとき、service worker が止められたときに、受け付けたジョブが失われないようにする。ジョブはサーバ側で続ける。
- ホストがサーバに接続できない場合、サーバが拒否した場合、応答が想定外の場合（「想定外の応答」。F-004 で定義）を、利用者が区別できる固定の表示で示す。
- 既存の入力の検証（本文の上限、`videoUrl`、字幕書式）、同時実行数の上限、`requestId`、失敗の Slack 通知、結果ウィンドウ（0020 で設けた、送信の結果を表示するウィンドウ）の振る舞いを保つ。
- 文書と静的なガードを更新し、トークン・TCP・`host_permissions` の記述とコードを残さない。

### 2.2. スコープ (In Scope)

- **フェーズ 1: サーバの UDS 化**
    - 待ち受けを TCP から UDS に変える。`0700` のディレクトリ、`0600` のソケット、所有者と権限の検査、stale socket（接続を受け付けないまま残ったソケット。§6）の扱い、単一起動。
    - 共有トークン、`YT2COLUMN_SERVER_PORT`、`internal/authtoken`、トークンの表示を削除する。
    - 起動ログ、終了コード、シャットダウン時にジョブの完了を待つ動作を、UDS でも保つ。
- **フェーズ 2: Native Messaging ホスト**
    - ブラウザが起動するホストのバイナリ。stdin/stdout 上で Native Messaging のプロトコルに従ってやり取りし、UDS のサーバへ 1 リクエストを転送し、1 応答を返して終了する。
    - リクエストと応答の上限、タイムアウト、固定のエラー、stdout の純度、stdout に書かないログ。
    - Chrome と Brave の manifest の install/uninstall。`allowed_origins` を固定の拡張 ID にする。
- **フェーズ 3: 拡張の Native Messaging への切り替え**
    - manifest に `nativeMessaging` を加え、`host_permissions` とオプションページを削除する。
    - トークン/ポートの設定と保存を削除する。右クリックメニューとポップアップの両方の送信を、固定のホスト名への送信に変える。
    - 応答の厳格な検査、エラーごとの表示、`requestId` の表示を保つ。
- **文書とテスト**
    - `security.md` §8・§8.1・§8.2、README、`project_overview.md`、`package_reference.md`、CLAUDE.md、Makefile、既存のドキュメントガードを更新する。
    - ユニットテスト、統合テスト、Chrome/Brave の手動確認。

### 2.3. スコープ外 (Out of Scope)

- **フル移行**: Native Messaging のホストに記事の生成・Slack への投稿を持たせ、サーバの手動起動をなくすこと。秘密情報の読み込み元（設定ファイルか Keychain か）とログの出力先の設計も、本タスクでは扱わない。
- **サーバの自動起動**: launchd などによるログイン時の起動。起動は手動のままとする。
- **ジョブの結果のポーリング、進捗の通知、拡張での成功・失敗の表示**: 結果は Slack だけで知らせる（0020 の決定を保つ）。
- **クライアントが付けるリクエスト ID による重複排除、再送しても二重にならないようにすること**: 送信は 1 回だけとし、リクエストがサーバに届いた可能性がある場合（応答が届かない、応答が想定外）は「結果不明」（F-004）として Slack を確認する。二重投稿の検出は別タスクとする。
- **入力拒否の Slack 通知の削減**: 枠（同時に処理するリクエストの数を数える単位。F-002）の確保後の入力拒否とジョブ失敗の通知は、現行どおり残す。通知の方針の変更は別タスクとする。
- **TCP と共有トークンのフォールバック、両方の経路の併存**: 移行は一括とし、旧経路は残さない。
- **別ユーザー分離、launchd によるソケットの保護、拡張のエクスポートできない鍵による認証**: 同一ユーザーのフル権限プロセスへの防御は、本タスクの範囲外とする（§4.2）。
- **生成記事の内容、プロンプト、Slack の投稿形式の変更**。
- **Windows**: 対象外（既存の方針と同じ）。macOS を主対象とし、Linux では Go のビルドとテストが通ることを求める。ブラウザの手動確認は macOS の Chrome と Brave で行う。
- **Chrome と Brave 以外のブラウザ**（Beta・Canary・Chromium・Edge など）。manifest の配置先を任意に指定する手段は設計で検討してよいが、手動確認の対象にはしない。
- **表示する文言の多言語化**。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: サーバの Unix ドメインソケット化

- サーバは、TCP の `127.0.0.1`・`::1` を待ち受けず、UDS だけを待ち受ける。TCP のポートを開かない。
- ソケットのパスは、`HOME` だけから導出する固定のパスとする（例: macOS は `$HOME/Library/Application Support/yt2column/run/server.sock`、他の Unix は `$HOME/.config/yt2column/run/server.sock`）。具体的なパスは設計で決める。
    - `XDG_CONFIG_HOME` などの他の環境変数は見ない。ブラウザが起動するホストは、利用者のシェルの環境変数を引き継がない。環境変数で変わるパスでは、シェルから起動したサーバとホストが別のパスを導出しうるためである。
    - キャッシュのディレクトリ（`internal/config/cachedir.go`）の導出の規則とは異なるが、上の理由から揃えない。
    - サーバとホストは同じ導出の規則を使い、パスをメッセージから受け取らない。
- ソケットを置くディレクトリは `0700`、ソケットは `0600` とする。既存のディレクトリの権限が `0700` でない場合、または所有者がサーバを実行しているユーザーでない場合は、権限を修復せずに起動を中止する（CLAUDE.md「Reject, don't normalize」）。ソケットの作成後にも権限を確かめる。
- 起動時にソケットのパスが存在する場合、次を守る。
    - `Lstat` でソケットであることを確かめる。通常ファイル・ディレクトリ・symlink・FIFO などは削除せず、起動を中止する。
    - サーバを実行しているユーザーが所有するソケットで、接続を受け付けていない（stale）場合だけ削除して bind する。接続できる場合は、既にサーバが起動しているものとして中止する。
    - 二重起動の競合を避けるため、同じディレクトリのロックを使って、stale かどうかの判定と bind を直列化する。
- ソケットのパスが OS の上限を超える場合、または `HOME` からパスを導出できない場合は、待ち受けを開始せず、原因の分かるエラーを値を含めずに出して終了する。
- 起動時に、待ち受けているソケットのパスをログに記録する。共有トークンを標準出力に表示しない。標準出力に書く値をなくす。
- 共有トークン、`YT2COLUMN_SERVER_PORT`、`internal/authtoken`、トークンのファイルのパス、トークンの生成・読み込み・表示を削除する。設定の読み込み（`internal/config`）からも、ポートとトークンのパスを削除する。
- 終了コードの契約（設定・構築の失敗は `2`、待ち受け・提供の失敗は `1`、シグナルによる停止は `0`）を保つ。設定のエラーに秘密の値を含めない。
- シグナルによる停止では、現行どおり新規の接続を止め、処理中のジョブと失敗通知の完了を待つ。正常終了時にソケットを削除する。異常終了で残ったソケットは、次の起動で stale として扱う。

**Acceptance Criteria**:
- **AC-01**: サーバを起動すると UDS だけを待ち受け、TCP の `127.0.0.1`・`::1` では接続できない。TCP のリスナーを作るコードが残っていない（ユニットテスト・静的な確認・手動確認）。
- **AC-02**: ソケットのディレクトリが `0700`、ソケットが `0600` で作られる。既存のディレクトリの権限が `0700` でない場合、または所有者がサーバを実行しているユーザーでない場合、サーバは権限を変更せずに起動を中止する（ユニットテスト）。
- **AC-03**: stale なソケットは削除して bind する。通常ファイル・symlink・FIFO は削除せずに起動を中止する。既に接続を受け付けるソケットがある場合は、二重起動として中止する（ユニットテスト）。
- **AC-04**: パスが長すぎる場合、および `HOME` からパスを導出できない場合、サーバは待ち受けを開始せず、値を含まないエラーで終了する。起動ログにソケットのパスが記録される（ユニットテスト）。
- **AC-05**: 共有トークン、`YT2COLUMN_SERVER_PORT`、トークンのファイルのパス、トークンの表示がコードと現在の文書から削除されている。サーバの標準出力にトークンが出ない。設定のエラーに秘密の値が現れない（静的な確認・ユニットテスト）。
- **AC-06**: シグナルで停止すると、処理中のジョブと失敗通知の完了を待ち、正常終了時にソケットを削除する。異常終了で残ったソケットは、次の起動で stale として削除される（ユニットテスト・手動確認）。

#### F-002: リクエストの受理と応答

- 1 回の送信は 1 つのリクエストとし、サーバは 1 つの応答を返す。リクエストの本文の形は、現行の API（0011 F-002）と同じく、`videoUrl` と `transcript` を必須、`title`・`channelName`・`description` を任意とする JSON のオブジェクト 1 つとする。
- 本文の検証（有効な UTF-8、対になっていないサロゲートの拒否、1 つのオブジェクト、末尾の余分な値の拒否、宣言したメンバの重複の拒否、`videoUrl` の検証、`transcript` の書式の検証、4 MiB の上限）を、現行どおり行う。宣言していないメンバは、現行どおり無視して受理する。
- `Host`・`Origin`・`Content-Type`・`Authorization`（共有トークン）の検査を削除する。これらに由来する拒否の理由（`forbidden_host`・`forbidden_origin`・`unsupported_media_type`・`unauthorized`）は、応答の理由の集合から削除する。
- パスやメソッドの不一致に由来する `not_found`・`method_not_allowed` は、拡張が個別の文言で表示する理由から削除する。サーバがこの 2 つを応答の理由に残すかどうかは、UDS 上のプロトコルの決定（`02_architecture.md`）に従う。
- どちらのプロトコルでも、リクエストの宛先（HTTP ならパスとメソッド）やフレームの不一致は `internal_error` として扱わず、Slack に通知せず、記事の生成を開始しない。拡張は、この不一致による応答を「想定外の応答」として表示する。
- 拡張が個別の文言で表示する拒否の理由は、`too_many_requests`・`body_too_large`・`invalid_body`・`invalid_video_url`・`invalid_transcript`・`internal_error` とする。
- 受理したリクエストには、`status` が `accepted` で、小文字の 16 進 16 文字の `requestId` を持つ応答を返す。拒否したリクエストには、`status` が `rejected` で、固定の `reason` と `requestId` を持つ応答を返す。`requestId` の生成に失敗した場合は、固定の `internal_error` を返し、`requestId` を空にする。拡張はこれを想定外の応答として扱う。応答に、API キー・Webhook URL・字幕・メタデータの値を含めない。
- 応答は、本文の検証とジョブの開始の後に返す。ジョブの完了は待たない。応答を返した後にブラウザやホストが終了しても、ジョブはサーバ側で続く。
- 同時に処理するリクエストは 2 つまでとする。上限に達しているときに届いたリクエストは、待ち行列に積まずに `too_many_requests` で拒否する。処理中のジョブは継続する。この上限は、Chrome と Brave の両方のホストからのリクエストを合算して数える。
- 上限を超える本文は、全体をメモリに読み込まずに拒否する。拒否したリクエストでは、記事の生成・Slack への投稿を開始しない。
- 枠を確保した後の入力拒否（`body_too_large`・`invalid_body`・`invalid_video_url`・`invalid_transcript`・`internal_error`）と、ジョブの失敗（LLM・投稿）は、現行どおり Slack に通知する。通知に、秘密の値・字幕・メタデータの値を含めない。通知の方針は本タスクで変更しない。
- ログは `redact.Writer` を通し、API キー・Webhook URL・字幕・メタデータの値を含めない。リクエスト ID・動画 ID・拒否の理由・失敗の種類という固定の値だけを記録する。

**Acceptance Criteria**:
- **AC-07**: 受理する形のリクエストを送ると、`accepted` と `requestId` の応答が返り、記事の生成と Slack への投稿が始まる。応答はジョブの完了を待たない（ユニットテスト。遅い writer を使い、応答が先に返ることを確かめる）。
- **AC-08**: `videoUrl`・`transcript` の欠落・型の不一致・空、字幕書式の不一致、無効な UTF-8、対になっていないサロゲート、末尾の余分な値、宣言したメンバの重複を、それぞれ現行の理由（`invalid_body`・`invalid_video_url`・`invalid_transcript`）で拒否し、記事の生成を開始しない（ユニットテスト）。
- **AC-09**: 4 MiB を超える本文を、全体をメモリに読み込まずに `body_too_large` で拒否し、記事の生成を開始しない（ユニットテスト）。
- **AC-10**: 2 つのジョブが処理中のときに 3 つ目のリクエストを送ると、`too_many_requests` で拒否される。処理中の 2 つは継続して完了する（ユニットテスト）。
- **AC-11**: 応答とログに、API キー・Webhook URL・字幕・メタデータの値が現れない（ユニットテスト。識別できる値を入れ、応答とログに現れないことを確かめる）。
- **AC-12**: `forbidden_host`・`forbidden_origin`・`unsupported_media_type`・`unauthorized` が、サーバの応答の理由と拡張の表示の理由から削除されている。`not_found`・`method_not_allowed` が拡張の表示の理由から削除されている。リクエストの宛先（HTTP ならパスとメソッド）やフレームの不一致は `internal_error` にならず、Slack に通知されず、記事の生成を開始せず、拡張では想定外の応答として表示される（静的な確認・ユニットテスト）。
- **AC-13**: 枠を確保した後の入力拒否とジョブの失敗で、現行どおり Slack に通知される。通知に秘密の値・字幕・メタデータの値が含まれない（ユニットテスト）。
- **AC-14**: 応答を受け取った後にホスト（およびブラウザ）を閉じても、ジョブがサーバ側で完了し、Slack への投稿が行われる（統合テスト。fake の遅い writer と publisher を使い、応答後に接続を閉じてから writer を解放する。手動確認でも確かめる）。

#### F-003: Native Messaging ホスト

- ホストは、ブラウザが起動する別の実行ファイルとする。Unix でビルドでき、外部の Go モジュールを追加しない。
- ホストは stdin/stdout 上で Native Messaging のプロトコルに従ってやり取りする。1 つのメッセージを受け取り、サーバへ 1 つのリクエストを転送し、1 つの応答を返し、ジョブの完了を待たずに終了する。
- ホストは記事の JSON を解釈しない。受け取ったメッセージ（本文のオブジェクトそのもの。外側の形で包まない）のバイト列を、変更せずにサーバへ渡し、サーバの応答を、設計で定めた固定の形で返す。ソケットのパスは固定の導出を使い、メッセージから受け取らない。シェルを経由しない。
- 本文の大きさの正否を判定する基準は、サーバの 4 MiB の上限（F-002）だけとする。
    - 拡張が測った大きさと、ホストが受け取るバイト数は一致しない。拡張は JS のオブジェクトを渡し、JSON への直列化は Chrome が行う。Chrome は一部の文字（`<`、U+2028/2029 など。正確な規則は設計で確かめる）をエスケープするためである。
    - ホストにもリクエストの上限を設ける。値は、サーバの上限より大きく、Chrome がホストへ送れる 1 メッセージの上限以下とし、具体値は設計で決める。この上限は、過大な入力から守るためだけに使う。
    - ホストはリクエストの長さを、サーバに接続する前に検査する。長さを読んだ時点でホストの上限を超えるリクエストは、`message_too_large` として拒否し、全体をメモリに読み込まない。
    - ホストの上限以下でサーバの上限を超えるリクエストは、サーバが `body_too_large` で拒否する。
- サーバの応答の上限を 64 KiB とする。サーバの応答は `status`・`reason`・`requestId` だけを持つ小さな JSON であり、ホストが固定の形で包んでも、Chrome がホストから受け取る 1 メッセージの上限（1 MiB）に届かない。サーバの応答が上限を超える場合、ホストは途中まで転送せずに `protocol_error` を返す。
- サーバに接続できない場合、接続したが応答が期限までに返らない場合、応答が読めない場合、リクエストが上限を超える場合を、固定のエラー（`server_unavailable`・`server_timeout`・`protocol_error`・`message_too_large`）として拡張へ返す。接続できなかった場合と、リクエストを送った後に応答が来なかった場合を区別する。自動で再送しない。
- 標準出力には Native Messaging のフレームだけを書く。ログは標準エラー出力に書き、字幕・メタデータ・秘密の値を含めない。ホストは `.envrc` や API キー・Webhook URL を読まない。ソケットのパスの導出に必要な `HOME` だけを読む。
- ホストはサーバを起動しない。サーバが動いていない場合は `server_unavailable` を返す。
- Chrome と Brave の Native Messaging の manifest を install/uninstall する明示的なコマンドを設ける。manifest は、`type` を `stdio`、`path` をホストのバイナリの絶対パスとし、`allowed_origins` には固定の拡張 ID のオリジンだけを入れる。`allowed_origins` は拡張の manifest の `key` から導出した ID と一致する。
- install は、選択したブラウザの manifest を置くだけで、サーバの設定を変更せず、サーバを起動せず、ビルド時に自動で実行されない。uninstall は、自分が作った manifest だけを削除する。バイナリを移動した場合は、install をやり直す必要があることを文書に記す。

**Acceptance Criteria**:
- **AC-15**: ホストに 1 つの Native Messaging のメッセージを渡すと、サーバへ 1 つのリクエストが転送され、応答が 1 つのメッセージとして返り、ホストが終了する。ジョブの完了は待たない（ユニットテスト・統合テスト）。
- **AC-16**: ホストの上限を超えるリクエストは、サーバに接続せず、全体をメモリに読み込まずに `message_too_large` になる。ホストの上限以下でサーバの上限（4 MiB）を超えるリクエストは、サーバの `body_too_large` の応答として拡張に返る。64 KiB を超えるサーバの応答は、途中まで転送されずに `protocol_error` になる（ユニットテスト）。
- **AC-17**: 標準出力にはフレーム以外のバイトが現れない。ログは標準エラー出力にだけ出て、字幕・メタデータ・秘密の値を含まない（ユニットテスト。識別できる値を入れ、標準出力と標準エラー出力を確かめる）。
- **AC-18**: ソケットのパスは `HOME` からの固定の導出で決まり、メッセージの値や `XDG_CONFIG_HOME` などの他の環境変数では変わらない。シェルを起動しない。`.envrc`・API キー・Webhook URL を読まない（静的な確認・ユニットテスト）。
- **AC-19**: サーバが動いていない場合、応答が期限までに返らない場合、応答の途中で接続が切れた場合に、それぞれ `server_unavailable`・`server_timeout`・`protocol_error` の固定のエラーが返り、自動で再送されない（ユニットテスト）。
- **AC-20**: install すると、選択したブラウザの manifest が `stdio`・絶対パス・固定の拡張 ID の `allowed_origins` で作られる。uninstall すると、その manifest だけが削除される。install/uninstall はビルド時に自動で実行されない（ユニットテスト・手動確認）。
- **AC-21**: ホストは Unix でビルドでき、外部の Go モジュールを追加しない（静的な確認・`make build`）。

#### F-004: 拡張の Native Messaging への切り替え

- 拡張の manifest の権限を、`activeTab`・`contextMenus`・`scripting`・`storage`・`nativeMessaging` とする。`host_permissions` とオプションページ（`options_ui`）を削除する。`storage` は、結果ウィンドウへ結果を渡す `chrome.storage.session` のために残す。`minimum_chrome_version` は、設計で必要が示されない限り上げない。
- 共有トークンとポートの設定画面・保存・読み込みを削除する。`chrome.storage.local` にトークン/ポートを保存しない。トークンを本文・ログ・表示・結果ウィンドウへ渡す値に含めない。
- 右クリックメニューとポップアップの両方の送信を、固定のホスト名（ホストの manifest の `name`）への Native Messaging の送信に変える。ホストの 1 回の起動につき、1 つのメッセージを送り、1 つの応答を受け取る。ジョブの完了まで Native Messaging の接続を開いたままにしない。自動で再送しない。
- 送る本文の形と、本文の大きさの上限（4 MiB）を保つ。拡張の 4 MiB の検査は、拡張が測った大きさに対する送信前の検査として残す。Chrome の直列化で 4 MiB を超えた本文は、サーバが `body_too_large` で拒否し、拡張は拒否として表示する。既存の収集（選択範囲・URL・タイトル）と、拒否の理由・順序を変えない。任意のメタデータ（`title`・`channelName`・`description`）の扱いを変えない。
- 受付応答では、受け付けたこと、`requestId`、結果が Slack に届くことを表示する。ジョブの成功・失敗は拡張では表示しない（0020 の決定を保つ）。
- 次のエラーを、互いに区別できる固定の文言と手順で表示する。表示は、リクエストがサーバに届いていないと確定する場合（未送信）、サーバが拒否した場合、届いた可能性がある場合（結果不明）に分ける。
    - 未送信: ホストを起動できない（ホストがインストールされていない）。ホストが起動した後に応答を返さず終了した場合は、結果不明とする。この 2 つを区別する方法は設計で決める。
    - 未送信: サーバが起動していない（`server_unavailable`）。
    - 未送信: リクエストがホストの上限を超える（`message_too_large`。ホストがサーバに接続する前に拒否する）。
    - サーバが拒否した（拡張が個別の文言で表示する理由ごとに、固定の文言を表示する）。
    - 結果不明: リクエストを送ったが応答が来ない（`server_timeout`）。
    - 結果不明: 「想定外の応答」。次の場合を含む。
        - ホストの応答の形が合わない。
        - 応答の版が合わない（ホストの応答に版を持たせるかは設計で決める）。
        - ホストが `protocol_error` を返した（応答が読めない、応答が上限を超える、応答の途中で接続が切れた）。
        - ホストが応答を返さずに終了した。
- 結果不明の表示では、ジョブが走っている可能性があることと、再送する前に Slack を確認する手順を示す。未送信の表示では、Slack の確認を求めない。
- ホストの応答を信頼できない入力として扱う。応答のメンバは固定の集合とし、未知・重複・型の不一致を拒否する。サーバの応答の本文は、現行の厳格な検査（`status`・`reason`・`requestId` の組、`requestId` の形）を通ったものだけを表示に使う。応答の本文の文字列をそのまま表示せず、HTML として解釈しない。検査に合わない応答は「想定外の応答」とする。
- 拡張は、固定のホスト名以外に接続しない。API キーと Webhook URL を持たず、入力も保存も表示もしない。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

| 境界 | 受理する形 | 上限 | 拒否時の扱い | 主な AC |
|---|---|---|---|---|
| ブラウザからホストへの Native Messaging のメッセージ | 本文の JSON のオブジェクト 1 つそのもの（外側の形で包まない）。Chrome が直列化したバイト列である。`videoUrl`・`transcript` は必須、`title`・`channelName`・`description` は任意とし、宣言していないメンバは無視する | ホストの上限（サーバの 4 MiB より大きく、Chrome の上限以下。設計で決める） | 長さを読んだ時点で、サーバに接続せずに `message_too_large` として拒否する。内容と 4 MiB の検証はサーバが行う | AC-16・AC-08 |
| ホストからサーバへのリクエスト | 上と同じ本文のバイト列。UDS 上で 1 リクエスト | 4 MiB（Chrome が直列化した後のバイト数で数える） | サーバが `body_too_large`・`invalid_body`・`invalid_video_url`・`invalid_transcript` で拒否する。部分的な受理をしない | AC-08・AC-09 |
| サーバからホストへの応答 | `accepted` または `rejected` の固定の形。`requestId` は小文字の 16 進 16 文字 | 64 KiB | ホストは上限を超える応答を `protocol_error` とする。部分的な転送をしない | AC-16 |
| ホストから拡張への応答 | ホストが返す固定の形（サーバの応答本文と、ホストの固定のエラー）。未知・重複するメンバを許さない | サーバの応答の上限（64 KiB）に、ホストが付ける固定の形の分を足した大きさ。Chrome の上限（1 MiB）より十分小さい | 拡張が「想定外の応答」として扱い、本文の文字列を表示しない | AC-27 |
| ソケットのパスと権限 | `HOME` から導出した固定のパス。`XDG_CONFIG_HOME` などの他の環境変数を見ない。ディレクトリ `0700`、ソケット `0600`、所有者はサーバを実行しているユーザー | パスの長さは OS の上限 | 権限・所有者・種別が合わない場合は起動を中止する。パスをメッセージから受け取らない | AC-02・AC-03・AC-18 |
| install/uninstall の入力（ブラウザの選択、manifest の置き場所） | 既知のブラウザ名（manifest の置き場所を明示する手段を設計で設ける場合は、そのディレクトリ）。値を補正しない | 形で決まる | 不明なブラウザ名・不正なパスは拒否し、manifest を書かない | AC-20 |
| 拡張が収集する値（選択範囲・URL・タイトル・メタデータ） | 0007・0020・0025 の境界をそのまま使う | 本文の 4 MiB の上限に含まれる | 既存の拒否の理由と順序を変えない | AC-30 |

- Native Messaging のメッセージは、ブラウザとホストの間の JSON である。ホストは記事の内容を解釈せず、長さと上限だけを検査してサーバへ渡す。内容の厳格な検査はサーバが行う。
- ホストの応答は、本物のサーバが返すとは限らない。サーバが停止している間に同一ユーザーの別のプロセスがソケットのパスを奪うことがある（§4.2 の残余リスク）。拡張は応答を信頼できない入力として扱い、受理する形に合わない応答を「想定外の応答」とする。
- 標準の JSON の解析が黙って修復・破棄・無視すれば受理できてしまう入力（重複したメンバ、無効な UTF-8 の置き換え、対になっていないサロゲートのエスケープなど）は、サーバの本文の検査と拡張の応答の検査で受理しない。応答のオブジェクトは拡張可能と宣言しない。
- ホストの標準出力は通信路であり、ログ・進捗・デバッグの出力を混ぜない。標準エラー出力にも、字幕・メタデータ・秘密の値を書かない。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

- ホストは、サーバの受付応答を受け取った時点で終了する。記事の生成（LLM の呼び出し）を待たない。
- 本文の読み込みと検証は、記事の生成より前に行う。過大な入力と不正な入力を、LLM と Slack の前に落とす。
- UDS と Native Messaging のフレーミングは、ローカルの小さな処理である。性能のための仕組みは設けない（CLAUDE.md「Performance」）。

### 4.2. セキュリティ (Security)

- **脅威モデル:** 同一ユーザーのフル権限プロセス（AI Agent を含む）は信頼する。他ユーザー・ウェブページ・サンドボックス化された Agent は信頼しない。排除の根拠は相手ごとに異なり、混同しない。
    - 他ユーザー: UDS のディレクトリ `0700` とソケット `0600`。
    - ウェブページ: UDS という通信手段そのもの。ブラウザは、ページから UDS へ接続する手段を持たない。拡張以外からホストを起動させない点は、ホストの `allowed_origins` で守る。
    - サンドボックス化された Agent: サンドボックスのポリシー。ファイルのモードは同じ uid のプロセスを区別しないので、UDS の権限では排除できない。ポリシーが Unix ソケットへの接続を許可していれば、Agent はサーバに到達できる。UDS 化によって、この点が後退することはない。
- **共有トークンの削除:** 共有トークンは拡張の認証ではなく、トークンのファイルを読める相手だけが示せる秘密の値（capability）で、ファイルを読めない相手を排除するものだった。同一ユーザーのフル権限プロセスはトークンも `.envrc` も読めるので、トークンを残しても防げない。そのため削除する。
- **サーバ:** TCP を待ち受けない。UDS だけを待ち受け、ディレクトリ `0700`、ソケット `0600`、所有者の検査を行う。既存の権限を修復しない。本文の検証を通過するまで、記事の生成・Slack への投稿を始めない。
- **ホスト:** 記事の JSON を解釈せず、固定のパスのソケットへ転送する。メッセージからソケットのパスを受け取らない。シェルを起動しない。`.envrc`・API キー・Webhook URL を読まない。標準出力はフレームだけ、ログは標準エラー出力だけとする。リクエスト（サーバの 4 MiB より大きい値）とサーバの応答（64 KiB）に、それぞれ上限を設ける。
- **拡張:** manifest の権限は `activeTab`・`contextMenus`・`scripting`・`storage`・`nativeMessaging` とする。`host_permissions` を持たない。固定のホスト名以外に接続しない。API キーと Webhook URL を持たない。ホストの応答を信頼できない入力として検査し、本文の文字列を表示しない。自動で再送しない。
- **拡張 ID:** Native Messaging の manifest の `allowed_origins` は、拡張の manifest の `key` から導出した固定の ID だけとする。拡張 ID は公開の `key` から決まるので、同じ `key` を使う拡張を読み込む相手は同じ ID を名乗れる。これは同一ユーザーのフル権限プロセスの信頼の範囲に含める。
- **秘密と字幕の出力:** API キー・Webhook URL・字幕・メタデータの値を、応答・ログ・エラーメッセージ・失敗の Slack 通知・結果ウィンドウへ渡す値に含めない。サーバのログは `redact.Writer` を通す。
- **残余リスク（受け入れる）:**
    - 同一ユーザーは、サーバが稼働中でもソケットのパスを `unlink` して自分のソケットを同じパスに bind でき、以後の字幕を受け取れる。
    - 同一ユーザーは、ホストのバイナリや manifest を置き換えられる。ホストはブラウザから起動されるため、置き換えたコードが同一ユーザーの権限で動く。
    - 上の 2 つは新たな後退ではない。同一ユーザーは現行でも、パッケージ化していない拡張のファイル（`extension/dist/`）やサーバのバイナリを書き換えて、同じ程度に静かに字幕を受け取れる。どちらも、同一ユーザーを信頼する前提に収まる既存のリスクと同じ種類である。
    - 同一ユーザーのフル権限プロセスは、`.envrc`・API キー・Webhook URL・トークン（削除前）を読み、サーバを経由せずに LLM API や Slack を直接使える。サーバの入口だけを拡張に限定しても、これらの資産は守れない。
    - サーバが停止している間に、同一ユーザーがソケットのパスを先に bind して、字幕を受け取れる。これは現行の TCP の残余リスク（`security.md` §8.2）と同じ種類である。
- **範囲外の防御:** 別ユーザー分離、サンドボックス、launchd などによるソケットの保護、拡張のエクスポートできない鍵によるリクエストの署名、リクエストごとの利用者の承認は、本タスクでは行わない。必要になった場合は別タスクとする。

**検証:** §4.2 の各項目は、サーバの AC-01・AC-02・AC-05・AC-08・AC-09・AC-11・AC-13、ホストの AC-16・AC-17・AC-18・AC-20、拡張の AC-22・AC-23・AC-27・AC-29、文書の AC-31 で確かめる。

### 4.3. 信頼性・可用性 (Reliability/Availability)

- 1 つのリクエストの失敗（入力の拒否、LLM の失敗、Slack の失敗、ホストの失敗）で、サーバは停止しない。次のリクエストを処理し続ける。
- ホストは、サーバに接続できない場合・応答が期限までに返らない場合に、固定のエラーを返して終了する。応答のないサーバを待ち続けない。
- 応答を受け取った後にブラウザやホストが終了しても、ジョブはサーバ側で完了する。
- サーバの異常終了で残ったソケットは、次の起動で stale として扱う。正常終了時はソケットを削除する。
- 二重起動は、既存のサーバを壊さずに中止する。新しいサーバが既存のソケットを削除して置き換えることはない。
- 応答が届かない場合、または応答が想定外の場合、拡張は自動で再送しない。リクエストがサーバに届いた可能性がある場合は、「結果不明」として Slack を確認する手順を示す。

### 4.4. 互換性 (Compatibility)

- 利用時: macOS 上の Chrome と Brave の、本タスクの作業時点の安定版で動作すること（0007 4.4 と同じ）。ブラウザの手動確認は macOS で行う。
- サーバとホストは Unix でビルドできること。Windows は対象外（既存の方針と同じ）。Linux では Go のビルドとテストが通ることを求める。ブラウザの手動確認は macOS に限る。
- 旧拡張と新サーバ、新拡張と旧サーバの互換性はない。サーバ・ホスト・拡張を同時に更新する。TCP と共有トークンのフォールバックを設けない。
- 拡張の `minimum_chrome_version` は、設計で必要が示されない限り上げない。上げる場合は理由を `02_architecture.md` に書く。
- Go の外部モジュールを追加しない。ホストは標準ライブラリだけで実装する。

### 4.5. 保守性 (Maintainability)

- ソケットのパスの導出は 1 か所に置き、サーバとホストで共有する。パスを二重に書かない。
- ホストは中継役に徹し、記事の JSON とサーバの応答の意味を解釈しない。プロトコルの契約は `02_architecture.md` に固定する。
- サーバの既存の本文の検証・ジョブ・同時実行数・失敗通知のコードを再利用する。UDS 化のために記事の生成ロジックを複製しない。
- 拡張の応答の検査と、拒否の理由ごとの表示の対応を型で表し、理由を追加したときに表示の追加が漏れると型検査が失敗するようにする（CLAUDE.md「Declare, don't infer」、0020 の `rejectionMessage` と同じ）。
- サーバ・ホスト・拡張のテストは、ブラウザなしでユニットテストできるようにする。ホストの stdin/stdout と UDS は fake や一時ディレクトリに置き換えられるようにする。
- 既存のドキュメントガードを更新し、コードと文書のずれを `make test` で検出する。

## 6. 用語集 (Glossary)

- **UDS**: Unix ドメインソケット。ファイルシステム上のパスを介したプロセス間通信。本タスクでは、サーバの唯一の待ち受け手段。
- **Native Messaging**: Chrome/Brave の拡張が、ブラウザの外の実行ファイルと stdin/stdout で通信する仕組み。メッセージは 4 バイトの native endian の長さの後に JSON が続く。
- **Native Messaging ホスト**: ブラウザが起動する実行ファイル。本タスクでは、拡張から受け取ったメッセージを UDS のサーバへ転送する中継役。単に「ホスト」とも呼ぶ。
- **manifest（ホスト）**: ブラウザにホストを登録する JSON。`name`・`description`・`path`・`type`・`allowed_origins` を持つ。
- **`allowed_origins`**: ホストに接続できる拡張のオリジンの一覧。本タスクでは固定の拡張 ID のオリジンだけを持つ。
- **受付応答（ack）**: サーバがリクエストを受理し、ジョブを開始したことを示す応答。`status` が `accepted` で、`requestId` を持つ。ジョブの完了を意味しない。
- **`requestId`**: サーバが生成する、小文字の 16 進 16 文字のリクエスト ID。応答・ログ・Slack の通知の照合に使う。
- **stale socket**: プロセスの異常終了などで残った、接続を受け付けないソケット。サーバは、サーバを実行しているユーザーが所有するソケットで接続できない場合だけ削除して bind する。
- **残余リスク**: 本タスクの防御では排除しないと決めたリスク。同一ユーザーによるソケットの `unlink`/再 bind、ホストのバイナリ/manifest の置き換え、`.envrc`・API キー・Webhook URL の読み取りを含む。
- **同一ユーザーのフル権限プロセス**: サーバや拡張と同じ OS ユーザーとして動き、ファイルの読み書きとプロセスの起動ができるプロセス。AI Agent を含む。本タスクでは信頼する。
- **サンドボックス化された Agent**: 同一ユーザーとして動いていても、サンドボックスのポリシーによってサンドボックスの外のファイルやソケットに到達できない Agent。排除しているのはサンドボックスのポリシーであり、UDS の権限ではない。ポリシーが Unix ソケットへの接続を許可していれば、サーバに到達できる。
- **0007**: ブラウザ拡張の骨格のタスク（`docs/tasks/0007_browser_extension_skeleton/`）。
- **0011**: localhost サーバと HTTP API のタスク（`docs/tasks/0011_localhost_server/`）。「0011 F-NNN」「0011 AC-NN」はその項番を指す。
- **0020**: ブラウザ拡張からサーバへの送信のタスク（`docs/tasks/0020_extension_send/`）。
- **0021**: 共有トークンの表示のタスク（`docs/tasks/0021_shared_token_display/`）。
- **0025**: 拡張の動画メタデータのタスク（`docs/tasks/0025_extension_video_metadata/`）。
- 用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
