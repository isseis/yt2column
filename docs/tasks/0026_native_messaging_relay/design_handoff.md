# 設計への申し送り：Native Messaging ホストを中継役にした Unix ドメインソケット経由の送信

本書は、[01_requirements.md](01_requirements.md) の起草（とレビュー）で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: ソケットの権限の位置づけ

-   **事項:** ディレクトリ `0700` とソケット `0600` のどちらを主な防御とするかを決め、作成と検査の順序を決める。
-   **理由:** `net.Listen("unix", ...)` は umask に従ってソケットを作るので、作成の後に `chmod` で `0600` にするまでの間に隙間ができる。この間も接続を防いでいるのは、ディレクトリの `0700` である。要件（F-001）は、ソケットの作成後にも権限を確かめることを求めている。
-   **候補の方針:** ディレクトリの検査（`Lstat`、symlink でないこと、所有者、`0700`）を主な防御とし、ソケットの `0600` は念のための防御と位置づける。ソケットの権限を作成後の `chmod` だけに頼らない。
-   **関連:** F-001、AC-02、§4.2

## H-02: stale の判定と bind を直列化するロック

-   **事項:** stale かどうかの判定と bind を直列化するロックの手段と、ロックのファイルの置き場所を決める。ロックの目的を設計に明記する。
-   **理由:** 2 つのサーバが同時にソケットを stale と判定すると、`unlink` と bind が入れ違い、片方が相手の新しいソケットを消す。要件（F-001）はロックを必須としている。`syscall.Flock` によるロックは標準ライブラリだけで書ける。
-   **候補の方針:** ソケットと同じ `0700` のディレクトリにロックのファイルを置き、`syscall.Flock` で排他ロックを取ってから、stale の判定・`unlink`・bind を行う。目的は、この入れ違いを防ぐことだと明記する。
-   **関連:** F-001、AC-03、§4.3

## H-03: シャットダウン中に次のサーバを起動できる期間

-   **事項:** シャットダウン中（リスナーを閉じた後、処理中のジョブの完了を待っている間）に次のサーバが起動できることを受け入れるかどうかを決める。
-   **理由:** Go の `UnixListener.Close` は、作ったパスを無条件に `unlink` する。正常終了の扱いとしてはこれで構わない。ただし、パスが消えた後は次のサーバが bind できるので、2 つのサーバが同時にジョブを処理しうる。その間は、同時に処理するリクエストの上限（2）がサーバの全体では効かない。
-   **候補の方針:** 受け入れるかどうかと、その理由を `02_architecture.md` に 1 行で書く。受け入れない場合は、ジョブの完了を待つ間もロック（H-02）を保持するなどの手段を検討する。
-   **関連:** F-001、F-002、AC-06、AC-10

## H-04: ソケットのパスの長さと、空白を含むパス

-   **事項:** macOS の `sun_path` の上限に対するパスの長さの扱いと、空白を含むパスの文書での示し方を決める。
-   **理由:** `/Users/<name>/Library/Application Support/yt2column/run/server.sock` は、ユーザー名を除いて約 61 バイトである。macOS の `sun_path` は 104 バイトなので、ユーザー名が約 40 文字を超えると AC-04 のエラーになる。また、パスは `Application Support` の空白を含む。
-   **候補の方針:** パスの長さの上限を超える場合は、要件どおり起動を中止する（AC-04）。README の `curl --unix-socket` の例では、パスを引用符で囲む。
-   **関連:** F-001、F-005、AC-04、AC-32

## H-05: 接続のエラーと固定のエラーの対応

-   **事項:** ホストが UDS に接続するときの OS のエラーを、固定のエラー（`server_unavailable` など）にどう対応させるかを決める。
-   **理由:** `ENOENT`（ソケットがない）と `ECONNREFUSED`（stale なソケット）は、どちらもリクエストがサーバに届いていないと確定するので、「未送信」の `server_unavailable` に当てはまる。TCP より判定がはっきりするのは UDS の利点である。`EACCES`（別のユーザーで起動したサーバ、`HOME` の違いなど）を同じ扱いにするか、別の文言にするかは決まっていない。
-   **候補の方針:** `ENOENT` と `ECONNREFUSED` は `server_unavailable` とする。`EACCES` は、`server_unavailable` に含めるか別の固定のエラーにするかを決める。別にする場合は、要件の固定のエラーの集合（F-003・F-004）を変えることになるので、要件の変更として扱う。
-   **関連:** F-003、F-004、AC-19、AC-26

## H-06: UDS 上のプロトコル

-   **事項:** UDS 上のプロトコルを、HTTP/1.1 の再利用と 4 バイト長 + JSON のフレームから選ぶ（要件 §1 の決定事項）。
-   **理由:** `http.Server` は `UnixListener` の上でそのまま動き、`MaxBytesReader`・タイムアウト・既存のハンドラのテストを再利用できる。README の `curl --unix-socket` による手動確認（F-005）も、HTTP なら使える。`Host`・`Origin` の検査は UDS では意味がない。ソケットに接続できる相手なら誰でも偽れる値だからである。
-   **候補の方針:** HTTP/1.1 を再利用する。`Host`・`Origin` の検査は削除し、ホストに `Origin` を付けて送らせる形で残すことはしない。`not_found`・`method_not_allowed` をサーバの応答の理由に残すかどうかも、ここで決める（F-002・AC-12）。
-   **関連:** F-002、F-003、F-005、AC-12

## H-07: 実機での確認（spike）

-   **事項:** 設計の前提を、承認の前に実機で確かめる。
    -   Native Messaging のホストが Chrome と Brave から起動され、`HOME` を受け取り、空白を含むパスの UDS に接続できること。
    -   ホストが登録されていない場合と、ホストが応答を返さずに終了した場合で、`chrome.runtime.lastError` がどう違うか（要件 F-004 は、前者を未送信、後者を結果不明とする）。
    -   Chrome が拡張のメッセージを直列化するときにエスケープする文字の規則（H-08）。
-   **理由:** どれも、設計の前提である。0020 H-02 では、ブラウザの `fetch` が接続の拒否と送信途中の切断を区別できなかった。`lastError` についても同じ種類の問題がありうる。区別できない場合は、F-004 の未送信と結果不明の分け方を見直すことになる。
-   **候補の方針:** 小さなホストと拡張で確かめ、観測の結果を `02_architecture.md` に記録する。README には、ホストのバイナリを TCC で保護されたフォルダ（`~/Documents`・`~/Desktop` など）の外に置くよう書く。
-   **関連:** F-001、F-003、F-004、AC-19、AC-26

## H-08: ホストのリクエストの上限と、Chrome の直列化

-   **事項:** ホストのリクエストの上限の具体値を決める。Chrome がエスケープする文字の規則を確かめる。
-   **理由:** 要件（F-003）は、本文の大きさの正否を判定する基準をサーバの 4 MiB の上限だけとし、ホストの上限は、サーバの上限より大きく、Chrome がホストへ送れる 1 メッセージの上限以下の値とした。拡張は JS のオブジェクトを渡し、JSON への直列化は Chrome が行うので、拡張が測った大きさとホストが受け取るバイト数は一致しない。
-   **候補の方針:** Chrome がエスケープする文字（`<`、U+2028/2029 など）を H-07 で確かめ、最悪の増え方からホストの上限を決める。ホストは長さをサーバに伝え、サーバが全体をメモリに読み込まずに `body_too_large` で拒否できるようにする。
-   **関連:** F-003、F-004、AC-16、AC-30

## H-09: ホストの応答の形と版

-   **事項:** ホストが拡張へ返す応答の固定の形を決める。応答に版を持たせるかどうかを決める。
-   **理由:** 要件（F-004）は、応答の版が合わない場合を想定外の応答とするが、版を持たせるかどうかは設計に委ねている。ホストのバイナリは拡張とは別にインストールするので、拡張を更新した後に古いホストが残ることがある。
-   **候補の方針:** 応答は、サーバの応答の本文と、ホストの固定のエラーを区別できる形にする。版を持たせる場合は、古いホストを検出して想定外の応答として表示できるようにする。
-   **関連:** F-003、F-004、AC-26、AC-27

## H-10: Linux のソケットの置き場所

-   **事項:** Linux でのソケットのパスを決める。
-   **理由:** 要件（F-001）の例の `$HOME/.config/yt2column/run/` は、実行時のソケットの置き場所としては不自然で、`~/.local/state` の下などの方が自然である。`HOME` だけからパスを導出する方針（`XDG_*` や `TMPDIR` を見ない）は、ホストがシェルの環境変数を引き継がないことへの対策として変えない。`TMPDIR` を使う案もあるが、標準ライブラリでは `confstr` を呼べないので採らない。Linux はビルドとテストだけの対象なので、優先度は低い。
-   **候補の方針:** `HOME` から導出できる範囲で、実行時の状態に向いた場所（`$HOME/.local/state/yt2column/run/` など）を選ぶ。
-   **関連:** F-001、AC-18、§4.4
