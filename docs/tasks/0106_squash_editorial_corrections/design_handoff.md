# 設計への申し送り（0106）

要件定義の際に出た、設計で決める事項。`02_architecture.md` が各項目の扱いを記録する。

-   **H-01: 訂正の行を取り出して確かめる場所。** 次の処理を、`mergepr` のツールに置くか（`prepare` が行を書いたファイルを作る、`merge` が本文を確かめるなど）、`mergepr.md` のエージェントの手順に置くかを決める。
    -   訂正の行の取り出しと、重複の除去と順序（AC-01〜AC-04）。
    -   受け付けない文字の確かめ（AC-10・AC-12）。
    -   マージに渡す本文の確かめ（AC-09）。

    あわせて、[ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md) との関係、プロトコル番号を上げるかどうか（`CLAUDE.md`「Protocol numbers」）を決める。ツールに置くときは番兵のエラーの名前を決める。エージェントの手順に置くときは、止まったことを手順の報告で示す形を決める。

    `log.txt` は今、`%h %s%n%n%b` の形で書かれる（`internal/mergepr/mergepr.go:250`）。この形からは、コミットの境目と、各行がコミットメッセージの何行目かを機械的に読めない（AC-10 の報告）。件名の行は `%h ` の後ろに出るので、1 列目から始まらない（3 章の「訂正の行」は件名の行も含む）。また、`git log` は `encoding` ヘッダーや `i18n.logOutputEncoding` で再エンコードするので、コミットオブジェクトのバイト列（3 章の「訂正の行」）をどう読むかも決める。
-   **H-02: squash の本文の中の置き方。** 訂正の行の段落と落とした記録の行を、本文のどこに置くかを決める（AC-06 の「トレーラーの段落より前」の中で、リードと箇条書きの後ろなど）。段落の前に見出しや導入の文を付けるかも決める。落とした記録の行の文面（英語）も決める（AC-14）。
-   **H-03: 承認の質問での保ち方と落とし方。** 次のことを、`mergepr.md` の step 3 と `runpr.md` のマージの質問のどこにどう書くかを決める。
    -   人が本文の修正を頼んだときに、訂正の行を保つこと（AC-08）。
    -   決まった場合に限って行を落とすこと（AC-13〜AC-15）。`/runpr` のマージの質問は 1 つの単一選択の問いである（[ADR-0047](../../dev/adr/0047-runpr-merge-question.md)）。そこで、落とす行と場合を、人がどう示すかを決める。
    -   AC-10・AC-11 の報告の後に、人がどちらの直し方を選ぶかを聞く方法。
-   **H-04: 規則の文書の分担。** 2.2 の F-005 の候補のうち、どれを変え、どこで squash の本文に触れるかを決める（AC-17・AC-18）。
-   **H-05: 文書のテストとコードのテスト。** 変更で古くなる文書のテスト（`cmd/mergepr/docs_test.go` など）を洗い出す。H-01 でツールを変えるなら、F-001〜F-004 をコードのテストで確かめる方法も決める。文書のテストは、値・構造・実行できる例だけを確かめる（[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。
-   **H-06: 止まる理由の案内。** AC-09 と AC-10 で止まったときの報告と直し方を、`docs/dev/guides/mergepr_guide.md` に止まる理由として載せるかを決める。
-   **H-07: GitHub の振る舞いの確かめ。** 実装の前に、次の 2 つを確かめて、設計書に記録する。
    -   `gh pr merge --body-file` で渡した本文が、バイト列を変えずに squash コミットのメッセージになるか。対象は、行末の空白と日本語の文字である。変わるなら、AC-01 を満たす方法を決める。
    -   既定のブランチに入った squash コミットの本文の `#N` と、issue を閉じるキーワード（`fixes #N` など）を、GitHub がどう扱うか。訂正の行に入りうるので、扱いによっては受け付けない文字に足すかを、要件に戻して決める。
