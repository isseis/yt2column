## 1. 概要 (Overview)

**目的:** 本書は、タスクの `docs/tasks/NNNN_<name>/_checks/` に置くスクリプトとそのテストの設計水準と規模を、本体の変更の規模・実行回数・想定運用環境に見合ったものにする要件を定義する。対象は、その基準を定める規約と、基準を当てはめるコマンドの定義のチェックリストである。

**背景:**

-   **比例原則は、今は `diff` の確かめだけが対象である。**
    -   規約の「Proportion」は、`diff` の確かめを、確かめる差分に見合った作りにせよと定める（`docs/dev/conventions/requirements_process.md:838`）。
    -   過大さを指摘する観点も、`diff` の確かめだけを見る。計画のチェックリスト（`.claude/commands/mkplan.md:164`）、フェーズのまとまりのレビュー（`.claude/commands/runplan.md:226`）、弱いモデルの作業のレビュー（`.claude/commands/_lib/high-review.md:647-654`）がそれに当たる。
    -   この決定は [ADR-0016](../../dev/adr/0016-document-test-policy.md) の「決定」にある（タスク 0080、#789）。
-   **`_checks/` には、`diff` の確かめのほかのスクリプトも置かれている。** 例は、移行ゲートと、実装を始める前の前提の確認である。
    -   `_checks/` は名前が `_` で始まるので、`go list ./...` の対象にならない（`requirements_process.md:839`）。そのため `make test` も CI も実行しない。マージの後は保守しない（`requirements_process.md:837`）。
    -   それでも、これらのスクリプトには比例原則が及ばない。設計とレビューのチェックリストにも、常設の開発ツールと一時スクリプトを区別する指針がない。
-   **タスク 0121（#1087、PR #1130）では、一時スクリプトが本体の変更より大きくなった。**
    -   本体の変更は、コマンドの定義 3 ファイル、`.claude/commands/_lib/review-records.sh` の 2 行、`cmd/yt2column/review_records_test.go` の 94 行にとどまる。
    -   一方、`_checks/` の 3 ファイルは計 1,293 行である。内訳は、`check_open_branches.sh` が 421 行、`escape_untrusted.go` が 126 行、`test_check_open_branches.sh` が 746 行である。どれも、実装を始める前とマージの直前の 2 回だけ実行する。
    -   数字は、PR #1130 の head（コミット `a13904d3c825`）で `git diff --stat origin/main...` と `wc -l` を実行して得た。
    -   設計書は、この移行ゲートに常設の開発ツール並みの環境への耐性を求めた。例は、shallow clone の扱い、相対パスの `origin` の解決、`GIT_GRAFT_FILE` などの環境変数の固定、制御文字の網羅的なエスケープである（`docs/tasks/0121_retire_legacy_review_records/02_architecture.md` §3.1、§5.2）。
    -   計画は、7 つのシナリオを網羅するテストスクリプトのコミットを決めた（`docs/tasks/0121_retire_legacy_review_records/03_implementation_plan.md:66`）。
-   **issue #1132 は、原因を 3 つ挙げる。**
    1.  比例原則の対象が `diff` の確かめに限られている。
    2.  一時スクリプトと常設のツールの設計とレビューの基準が分かれていない。
    3.  上流の過剰な仕様が、下流で雪だるま式に膨らむ。設計書に常設のツール並みの防御を書くと、計画・実装・各レビューが承認済みの設計書を忠実に満たそうとして、テストと壊し確認をさらに広げる。

対応 issue: [#1132](https://github.com/isseis/yt2column/issues/1132)（関連: [#1087](https://github.com/isseis/yt2column/issues/1087)（タスク 0121）、[#1130](https://github.com/isseis/yt2column/pull/1130)、[#789](https://github.com/isseis/yt2column/issues/789)（タスク 0080）、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）

**本書の記述範囲:** 本書は、次のことを定める。

-   一時スクリプトの定義と、比例原則の適用範囲。
-   一時スクリプトの設計水準：必須の核、核を超える防御の条件、想定運用環境の既定。
-   一時スクリプトのテストをコミットするかの基準と、その規模。
-   過剰な設計と過剰なテストを指摘する観点を置くチェックリスト。
-   適用の範囲（既存のタスクの扱い）。

次のことは `02_architecture.md` で決める（`design_handoff.md`）。

-   規約とコマンドの定義のどの節に、どの言い回しで書くか。
-   `diff` の確かめの既存の規則・観点と、新しい規則との関係。
-   文書を読む既存の guard への影響と、その扱い。

**issue #1132 で決めたこと:**

-   **比例原則の適用範囲を、`diff` の確かめから `_checks/` の一時スクリプト全般に広げる。** 設計とテストを、本体の変更の規模・実行回数・想定運用環境に見合ったものにする。移行ゲートや前提の確認も、`diff` の確かめと同じく、マージの後に実行も保守もしないためである。
-   **1〜2 回だけ手で実行する一時スクリプトには、常設の開発ツール並みの環境への耐性や、敵対的な入力への防御を、原則として求めない。** 必須の核は 4 つに絞る。
    -   目的のものを検出すること。
    -   正常なときに検出しないこと。
    -   異常なときにフェイルクローズすること。
    -   呼び出し元を汚さないこと。
-   **核を超える防御を入れるのは、実運用上の具体的な必要性があるときだけとする。** 0121 のように、使われない環境への耐性が設計・テスト・レビューを膨らませたためである。
-   **一時スクリプトのテストをコミットするかの基準を定める。コミットする場合も、核となる代表ケースにとどめ、常設のツール並みのエッジケースの網羅テストを書かない。** 0121 では、テスト（746 行）が本体のスクリプト（421 行）より大きくなったためである。
-   **`mkarch.md`（SRE レーン）、`mkplan.md`（SDET レーン）、`runplan.md`、`_lib/high-review.md` のチェックリストに、一時スクリプトとそのテストが用途と実行回数に比べて過剰でないかを確かめる観点を加える。** 上流で過剰な仕様を止め、下流の各段でも見つけるためである（原因 3）。
-   **タスク 0121（PR #1130）は、承認済みの設計と計画のとおりに通し、教訓を今後のタスクに取り込む。**

**要件定義の際に決めたこと（2026-11-24）:**

-   **進め方は、通常の進め方（`full`）とする。** 変更は、規約の `requirements_process.md` と、コマンドの定義の `mkreq.md`・`mkarch.md`・`mkplan.md`・`runplan.md`・`_lib/high-review.md` に及ぶ。既存の ADR（ADR-0016）の決定も変え、決めることも本節のとおり複数あった。そのため、通常の進め方を勧め、人がそれを選んだ（`.claude/commands/_lib/simple-process.md`「Recommending a process」）。
    -   除外の判断：除外に当たらない。`docs/dev/security.md` の規則とその前提を変えない（同書は開発用のスクリプトについての規則を持たない）。開発ツールの信頼の境界（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)。レビューのスレッドと Bot への依頼の扱い）を変えない。外部への依存を足すことも、変えることもしない（`docs/dev/conventions/requirements_process.md`「Simple Process」の「Excluded changes」）。
    -   ADR：なし。本タスクの中で閉じる、進め方の選択である。
-   **一時スクリプトは、置き場所で定める。用途（`diff` の確かめ、移行ゲート、前提の確認など）によらず、タスクの `_checks/` に置くスクリプトをすべて対象にする（F-001）。** `_checks/` という置き場所が、`make test` も CI も実行せず、マージの後に保守しないことを意味しているので、判定がぶれないためである。
    -   採らなかった案：計画が「一時スクリプト」と宣言したものだけを対象にする案。宣言を書き忘れると、今と同じ状態に戻る。
    -   ADR：[ADR-0056](../../dev/adr/0056-checks-script-proportion.md) を作る（本書の PR で行う）。
-   **想定運用環境の既定を、スクリプトを実行する人の、このリポジトリのふだんの作業ツリーとする。それ以外の環境への耐性は、その環境で実際に実行することを設計か計画が書いたときだけ求める（F-002）。** 既定がないと、「具体的な必要性」があるかの判断が人と文書によって分かれ、レビューで何が過剰かを決めにくいためである。0121 が耐性を求めた shallow clone などは、移行ゲートを実行する作業ツリーでは起きない状況だった。
    -   採らなかった案：環境の既定を置かず、核を超える防御には実運用上の具体的な必要性だけを求める案。上の理由で、判断が分かれる。
    -   ADR：[ADR-0056](../../dev/adr/0056-checks-script-proportion.md) の決定に含める。
-   **一時スクリプトのテストは、既定ではコミットしない。壊し確認（各チェックが少なくとも 1 つの壊し方で失敗すること）は 1 回行い、その結果を計画に記録する。テストをコミットするのは、計画が具体的な理由を書いたときだけとし、その場合も核の代表ケースに限る（F-003）。** 一時スクリプトは 1〜2 回しか実行しないので、壊し確認の結果が残れば足りる。コミットしたテストは、レビューで読む量を増やすためである。
    -   採らなかった案：理由がなくてもコミットしてよく、代表ケースに限るだけにする案。コミットが既定になり、規模を抑える歯止めが弱い。
    -   採らなかった案：テストを一切コミットしない案。スクリプトをマージの前に作り直して再実行するときなど、テストを残す具体的な理由がある場合に対応できない。
    -   ADR：[ADR-0056](../../dev/adr/0056-checks-script-proportion.md) の決定に含める。
-   **過剰な設計と過剰なテストを指摘する観点を、issue が挙げる 4 か所に加え、`mkreq.md` の要件定義のチェックリストにも置く（F-004）。** 原因 3（上流の過剰な仕様が下流で膨らむ）を、最も上流で止められるためである。
    -   採らなかった案：issue が挙げる 4 か所（`mkarch.md`・`mkplan.md`・`runplan.md`・`_lib/high-review.md`）に限る案。要件の段階で入った過剰な仕様を、設計のレビューまで見つけられない。
    -   タスク 0080 では、受け入れ基準の並べ挙げを指摘する項目を `mkreq.md` に足す案を、人が選ばなかった（[0080 要件定義書](../0080_diff_check_proportion/01_requirements.md)「要件定義の際に決めたこと（2026-11-10）」）。本書の項目は、一時スクリプトの過剰な設計を見るもので、その項目とは別である。
    -   ADR：[ADR-0056](../../dev/adr/0056-checks-script-proportion.md) の決定に含める。
-   **新しい基準は、この変更が `main` に入った後に書く文書と、その `_checks/` だけに当てはめる。それより前に承認された文書と、その `_checks/` は変えない（F-005）。** issue が 0121 を承認済みの設計と計画のとおりに通すと決めているのと同じく、承認済みの文書に後から基準を当てはめると、計画と実装が食い違うためである。0080 の観点にも同じ適用の範囲がある（`.claude/commands/runplan.md:226`）。
    -   採らなかった案：承認済みでも、まだ実装していない PR の `_checks/` には新しい基準を当てはめる案。承認済みの計画と実装が食い違う。
    -   ADR：[ADR-0056](../../dev/adr/0056-checks-script-proportion.md) の決定に含める。
-   **`_checks/` の比例原則を、主題を独立させた新しい ADR（ADR-0056）に置く。ADR-0016 の `diff` の確かめの比例原則の項目はそこへ移し、ADR-0016 からは ADR-0056 へリンクする。** 移行ゲートや前提の確認は文書のテストではないので、ADR-0016 の主題（文書のテストの方針）からはみ出すためである。1 つの主題は 1 つの有効な ADR に置く（`docs/dev/conventions/adr.md`「Location and naming」の「Subject」）。
    -   採らなかった案：ADR-0016 を更新して、比例原則の範囲を広げる案。上の理由で、主題がずれる。
    -   ADR：[ADR-0056](../../dev/adr/0056-checks-script-proportion.md) を作り、[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `_checks/` の一時スクリプトとそのテストの規模を、本体の変更の規模・実行回数・想定運用環境に見合ったものにする。
-   設計・計画・実装の各段で、一時スクリプトに常設の開発ツール並みの要求が積み上がることを止める。

### 2.2. スコープ (In Scope)

-   規約 `docs/dev/conventions/requirements_process.md` に、一時スクリプトの定義、比例原則の適用範囲、設計水準、テストの基準、適用の範囲を書くこと。
-   コマンドの定義 `.claude/commands/mkreq.md`・`mkarch.md`・`mkplan.md`・`runplan.md`・`_lib/high-review.md` のチェックリスト（`mkarch.md` と `mkplan.md` はレビュアーの役割の記述を含む）に、過剰な設計と過剰なテストを指摘する観点を加えること。

### 2.3. スコープ外 (Out of Scope)

-   **タスク 0121（PR #1130）とその `_checks/`、および既存のタスクの `_checks/` を変えること。** issue #1132 が、PR #1130 を承認済みの設計と計画のとおりに通すと決めている（F-005）。
-   **`diff` の確かめに固有の規則を変えること。** 記録した差分の読み取り、固定のコマンド、差分の記録の形、記録の確かめ直し、前後の関係を述べる受け入れ基準の書き方、スクリプトの既定の言語（シェル）が当たる（`requirements_process.md` §1、§4）。issue が求めていない。
-   **常設のツールの基準を変えること。** 開発ツール（`docs/dev/conventions/dev_tools.md`）、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテストが当たる。issue は、これらと一時スクリプトを区別することを求めており、これらの基準を緩めることは求めていない。
-   **`_checks/` のリテラルの言語の例外（`CLAUDE.md`「Go Idioms」）を変えること。** issue が求めていない。
-   **行数などの数の上限を設けること。** issue が求めていない。釣り合いは、本書の基準に照らして人とレビュアーが判断する。
-   **一時スクリプトの出力を GitHub に投稿するときの規則と、ネットワークの操作の承認を緩めること。** メンションの検査（`.claude/commands/_context.md` の「Rejected mentions」）と、`CLAUDE.md`「Tool Execution Safety」が当たる。これらは一時スクリプトの設計水準ではなく、エージェントの操作の規則である（AC-06）。

## 3. 機能要件 (Functional Requirements)

本書の要件は、規約とコマンドの定義の文に関するものである。受け入れ基準の「規約」は `docs/dev/conventions/requirements_process.md` を指す。

### 3.1. 機能一覧

#### F-001: 一時スクリプトの定義と比例原則の適用範囲

規約に、一時スクリプトを置き場所で定義し、比例原則を一時スクリプト全般に当てはめることを書く。

**Acceptance Criteria**:

-   **AC-01**: 規約が、タスクの `_checks/` に置くスクリプトを、用途（`diff` の確かめ、移行ゲート、前提の確認を例に挙げる）によらず一時スクリプトとして定義している。そのうえで、常設のツール（開発ツール、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテスト）と区別している。
-   **AC-02**: 規約が、一時スクリプトとそのテストの設計と規模を、本体の変更の規模・実行回数・想定運用環境に見合ったものにすると定めている。この原則は、`diff` の確かめに限らず、AC-01 の一時スクリプトのすべてに当てはまる。

#### F-002: 一時スクリプトの設計水準

規約に、一時スクリプトが必ず満たす核、核を超える防御を入れる条件、想定運用環境の既定を書く。

**Acceptance Criteria**:

-   **AC-03**: 規約が、一時スクリプトが必ず満たす核として、次の 4 つを挙げている。
    -   目的のものを検出すること。
    -   正常なときに検出しないこと。
    -   異常なときにフェイルクローズすること（判定できないときは、通ったと報告しない）。
    -   呼び出し元（作業ツリー、リポジトリ、環境）を汚さないこと。
-   **AC-04**: 規約が、核を超える防御（想定運用環境の外への耐性、敵対的な入力への防御、網羅的なエスケープなど）について、次のことを定めている。
    -   その防御は、設計書か計画が実運用上の具体的な必要性（どの実行で、どの状況が起きるか）を書いたときだけ入れる。
    -   必要性が書かれていない防御は求めない。
-   **AC-05**: 規約が、想定運用環境の既定を「スクリプトを実行する人の、このリポジトリのふだんの作業ツリー」と定めている。そのうえで、それ以外の環境への耐性は、その環境で実際に実行することを設計書か計画が書いたときだけ求めると定めている。
-   **AC-06**: 規約が、一時スクリプトの設計水準の基準は、エージェントの操作の規則を緩めないと述べている。そのような規則は、出力を GitHub に投稿するときのメンションの検査と、ネットワークの操作の承認（`CLAUDE.md`「Tool Execution Safety」）である。

#### F-003: 一時スクリプトのテストの基準

規約に、一時スクリプトのテストをコミットするかの基準と、コミットする場合の規模を書く。

**Acceptance Criteria**:

-   **AC-07**: 規約が、一時スクリプトのテストについて、次の 3 つを定めている。
    -   テストは、既定ではリポジトリにコミットしない。
    -   壊し確認（各チェックが少なくとも 1 つの壊し方で失敗すること）は 1 回行い、その結果を計画に記録する。
    -   テストをコミットするのは、計画がその具体的な理由を書いたときだけとする。
-   **AC-08**: 規約が、テストをコミットする場合も、核（AC-03）の代表ケースに限ると定めている。あわせて、常設のツール並みのエッジケースの網羅テストを書かないと定めている。

#### F-004: レビューのチェックリスト

過剰な設計と過剰なテストを指摘する観点を、要件・設計・計画・実装の各段のチェックリストに置く。

**Acceptance Criteria**:

-   **AC-09**: 次の 5 つのチェックリストのそれぞれが、`_checks/` の一時スクリプトとそのテストが規約の基準（F-002、F-003）に比べて過剰でないかを確かめる項目を持つ。
    -   `.claude/commands/mkreq.md` の「Requirements checklist」。
    -   `.claude/commands/mkarch.md` の「Technical correctness checklist」。
    -   `.claude/commands/mkplan.md` の「Technical correctness checklist」。
    -   `.claude/commands/runplan.md` の「Phase-group review checklist」。
    -   `.claude/commands/_lib/high-review.md` の「Weak-model failure checklist」。
-   **AC-10**: `.claude/commands/mkarch.md` のレビュアー B（senior SRE）の役割の記述が、次の 2 つを述べている。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   N/A。実行するコードを変えず、規約とコマンドの定義の文だけを変えるためである。

### 4.2. セキュリティ (Security)

-   N/A。条件付きのガイド（`docs/dev/security.md`）を当てはめる条件に当たらない。本書は、外部コマンド（`yt-dlp`）の起動、API キー、キャッシュのディレクトリ、LLM API への送信、信頼できないテキストのプロンプトや記事への埋め込みに触れない。
-   開発の進め方としては、一時スクリプトの出力を GitHub に投稿するときの規則と、ネットワークの操作の承認を緩めない（AC-06、2.3 節）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   一時スクリプトの核として、異常なときのフェイルクローズを残す（AC-03）。判定できない状態を、通ったと報告しないためである。

### 4.4. 互換性 (Compatibility)

-   既存のタスクの文書と `_checks/` は変えない（F-005）。
-   `diff` の確かめに固有の規則は変えない（2.3 節）。

### 4.5. 保守性 (Maintainability)

-   基準の正本は規約に 1 か所だけ置き、各コマンドのチェックリストは規約を参照する。どう参照するかは `02_architecture.md` で決める（`design_handoff.md`）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   規約とコマンドの定義は英語で書き、タスク文書と ADR は日本語で書く（`CLAUDE.md`「Document language」）。
-   文書のテストは、値・構造・実行できる例だけを確かめ、文の意味は PR のレビューで読む（`CLAUDE.md`「Testing Strategy」、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。本書の受け入れ基準の多くは文の内容を定めるので、計画は、その確かめ方にこの規則を当てはめる。

## 6. 用語集 (Glossary)

用語は `docs/translation_glossary.md` と統一する。

-   **一時スクリプト**: タスクの `docs/tasks/NNNN_<name>/_checks/` に置くスクリプト。用途（`diff` の確かめ、移行ゲート、前提の確認など）を問わない。`make test` も CI も実行せず、マージの後は保守しない（F-001）。
-   **常設のツール**: マージの後も実行し、保守するツールとスクリプト。開発ツール（`docs/dev/conventions/dev_tools.md`）、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテストを指す。
-   **核**: 一時スクリプトが必ず満たす 4 つの性質（AC-03）。
-   **想定運用環境**: 一時スクリプトを実行する環境。既定は、スクリプトを実行する人の、このリポジトリのふだんの作業ツリー（AC-05）。
-   **壊し確認**: 確かめの対象を壊して、確かめが失敗することを確かめる手順（`CLAUDE.md`「Testing Strategy」の「Every test must be able to fail for its stated reason」）。
-   **移行ゲート**: 移行の前提が成り立つかを、実装の開始やマージの前に確かめる一時スクリプト（例：タスク 0121 の `check_open_branches.sh`）。
