## 1. 概要 (Overview)

**目的:** 本書は、タスクの `docs/tasks/NNNN_<name>/_checks/` に置くスクリプトとそのテストの設計水準と規模を、本体の変更の規模・実行回数・想定運用環境に見合ったものにする要件を定義する。対象は、その基準を定める規約と、基準を当てはめるコマンドの定義である。

**背景:**

-   **比例原則は、今は `diff` の確かめだけが対象である。**
    -   規約の「Proportion」は、`diff` の確かめを、確かめる差分に見合った作りにせよと定める（`docs/dev/conventions/requirements_process.md:838`）。
    -   計画の規則（前のタスクの `_checks/` を写させない、壊し方を並べ挙げない）も、`diff` の確かめのある計画だけに当てはまる（`.claude/commands/mkplan.md:125-130`）。
    -   過大さを指摘する観点も、`diff` の確かめだけを見る。計画のチェックリスト（`.claude/commands/mkplan.md:164`）、フェーズのまとまりのレビュー（`.claude/commands/runplan.md:226`）、弱いモデルの作業のレビュー（`.claude/commands/_lib/high-review.md:647-654`）がそれに当たる。
    -   これらの決定は [ADR-0016](../../dev/adr/0016-document-test-policy.md) の「決定」にあった（タスク 0080、#789）。
-   **`_checks/` には、`diff` の確かめのほかのスクリプトも置かれている。** 例は、移行ゲートと、実装を始める前の前提の確認である。
    -   `_checks/` は名前が `_` で始まるので、`go list ./...` の対象にならない（`requirements_process.md:839`）。そのため `make test` も CI も実行しない。
    -   `diff` の確かめについては、規約がマージの後に保守しないと定めている（`requirements_process.md:837`）。ほかの用途のスクリプトには、この定めも比例原則も及ばない。設計とレビューのチェックリストにも、常設のツールと一時スクリプトを区別する指針がない。
-   **タスク 0121（#1087、PR #1130）では、一時スクリプトが本体の変更より大きくなった。** 数字は、PR #1130 の head（コミット `a13904d3c825`）で `git diff --numstat origin/main...` と `wc -l` を実行して得た。
    -   本体の変更は、次のとおりである。
        -   コマンドの定義 3 ファイル：追加 8 行、削除 14 行。
        -   `.claude/commands/_lib/review-records.sh`：2 行の書き換え。
        -   `cmd/yt2column/review_records_test.go`：追加 89 行、削除 5 行。
    -   一方、`_checks/` の 3 ファイルは計 1,293 行である。内訳は、移行ゲートの `check_open_branches.sh` が 421 行、その補助の `escape_untrusted.go` が 126 行、移行ゲートのテストの `test_check_open_branches.sh` が 746 行である。
    -   移行ゲートは、実装を始める前とマージの直前の 2 回だけ、実際の `origin` に対して実行するものだった（`docs/tasks/0121_retire_legacy_review_records/03_implementation_plan.md:23`、`:205`）。テストは、壊し確認とレビューの修正の後の再検証に使うために、コミットされた（同 `:66`）。
    -   設計書は、この移行ゲートに常設の開発ツール並みの環境への耐性と防御を求めた。例は、shallow clone の扱い、相対パスの `origin` の解決、`GIT_GRAFT_FILE` などの環境変数の固定、信頼しない文字列の網羅的なエスケープである（`docs/tasks/0121_retire_legacy_review_records/02_architecture.md` §3.1、§5.2）。
-   **issue #1132 は、原因を 3 つ挙げる。**
    1.  比例原則の対象が `diff` の確かめに限られている。
    2.  一時スクリプトと常設のツールの設計とレビューの基準が分かれていない。
    3.  上流の過剰な仕様が、下流で雪だるま式に膨らむ。設計書に常設のツール並みの防御を書くと、計画・実装・各レビュー（コードのレビュー、CLI レビュー、上位モデルのレビュー）が承認済みの設計書を忠実に満たそうとして、テストと壊し確認をさらに広げる。

対応 issue: [#1132](https://github.com/isseis/yt2column/issues/1132)（関連: [#1087](https://github.com/isseis/yt2column/issues/1087)（タスク 0121）、[#1130](https://github.com/isseis/yt2column/pull/1130)、[#789](https://github.com/isseis/yt2column/issues/789)（タスク 0080）、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）

**本書の記述範囲:** 本書は、次のことを定める。

-   一時スクリプトの定義と、比例原則の適用範囲。
-   一時スクリプトの設計水準：必須の核、核を超える防御の条件、想定運用環境の既定、信頼しない入力と投稿する出力の扱い。
-   一時スクリプトのテストをコミットするかの基準と、その規模。
-   計画が一時スクリプトについて書くことの規則。
-   過剰な設計と過剰なテストを指摘する観点を置く場所。
-   適用の範囲（既存のタスクと、基準の変更の前後にまたがるタスクの扱い）。

次のことは `02_architecture.md` で決める（`design_handoff.md`）。

-   規約とコマンドの定義のどの節に、どの言い回しで書き、正本をどう参照させるか。
-   `diff` の確かめの既存の規則・観点と、新しい規則との関係。
-   壊し確認の記録の形と、一時スクリプトを対象とする受け入れ基準の確かめ方。
-   文書を読む既存の guard への影響と、その扱い。
-   そのほか `design_handoff.md` の各項目（`CLAUDE.md` との整合、共有のチェックリストへの波及、ADR-0056 のリンクの向け直しなど）。

**issue #1132 で決めたこと:**

-   **比例原則の適用範囲を、`diff` の確かめから `_checks/` の一時スクリプト全般に広げる。** 設計とテストを、本体の変更の規模・実行回数・想定運用環境に見合ったものにする。移行ゲートや前提の確認も、`diff` の確かめと同じく、マージの後に実行も保守もしないためである。
-   **1〜2 回だけ手で実行する一時スクリプトには、常設の開発ツール並みの環境への耐性や、敵対的な入力への防御を、原則として求めない。** 必須の核（一時スクリプトが必ず満たす性質）は 4 つに絞る。
    -   目的のものを検出すること。
    -   正常なときに検出しないこと。
    -   異常なときにフェイルクローズすること。
    -   呼び出し元を汚さないこと。
-   **核を超える防御を入れるのは、実運用上の具体的な必要性があるときだけとする。** 0121 のように、使われない環境への耐性が設計・テスト・レビューを膨らませたためである。
-   **一時スクリプトのテストをコミットするかの基準を定める。コミットする場合も、核となる代表ケースにとどめ、常設のツール並みのエッジケースの網羅テストを書かない。** 0121 では、テスト（746 行）が移行ゲートの本体（421 行）より大きくなったためである。
-   **`mkarch.md`（SRE レーン）、`mkplan.md`（SDET レーン）、`runplan.md`、`_lib/high-review.md` のチェックリストに、一時スクリプトとそのテストが用途と実行回数に比べて過剰でないかを確かめる観点を加える。** 上流で過剰な仕様を止め、下流の各段でも見つけるためである（原因 3）。
-   **タスク 0121（PR #1130）は、承認済みの設計と計画のとおりに通し、教訓を今後のタスクに取り込む。**

**要件定義の際に決めたこと（2026-11-24）:**

ADR の判断は、進め方の選択を除き、どれも [ADR-0056](../../dev/adr/0056-checks-script-proportion.md) を作ってその決定に含める（本書の PR で行う）。各項目では、採らなかった案だけを挙げる。

-   **進め方は、通常の進め方（`full`）とする。** 変更は、規約の `requirements_process.md` と、コマンドの定義の `mkreq.md`・`mkarch.md`・`mkplan.md`・`runplan.md`・`_lib/high-review.md`・`_lib/local-cli-review.md` に及ぶ。既存の ADR（ADR-0016）の決定も変え、決めることも本節のとおり複数あった。そのため、通常の進め方を勧め、人がそれを選んだ（`.claude/commands/_lib/simple-process.md`「Recommending a process」）。
    -   除外の判断：除外に当たらない。`docs/dev/security.md` の規則とその前提を変えない（同書は開発用のスクリプトについての規則を持たない）。外部への依存を足すことも、変えることもしない。開発ツールの信頼の境界（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)。レビューのスレッドと Bot への依頼の扱い）も変えない。一時スクリプトの出力を GitHub に投稿するときは、メンションの検査などの既存の規則がそのまま効くと定めるためである（下の「信頼しない入力と投稿する出力」の項目、AC-07）。指摘を振り分ける規則の変更（AC-14）も、一時スクリプトへの指摘をどう分類するかを変えるだけで、レビューのスレッドの文を信頼するかどうかは変えない。
    -   ADR：なし。本タスクの中で閉じる、進め方の選択である。
-   **一時スクリプトは、置き場所で定める。用途（`diff` の確かめ、移行ゲート、前提の確認など）によらず、タスクの `_checks/` に置くスクリプトと、その補助のファイル（データのファイル、テストの入力など）をすべて対象にする（F-001）。** `_checks/` という置き場所が、`make test` も CI も実行しないことを意味しているので、判定がぶれないためである。
    -   採らなかった案：計画が「一時スクリプト」と宣言したものだけを対象にする案。宣言を書き忘れると、今と同じ状態に戻る。
-   **想定運用環境の既定を、スクリプトを実行する人またはエージェントの、手元の機械にあるこのリポジトリの作業ツリー（main のチェックアウトか linked worktree）とする。** クラウドのセッションは既定に入れない。ほかの環境への耐性は、その環境で実際に実行することを設計書か計画が書いたときだけ求める（F-002）。既定がないと、「具体的な必要性」があるかの判断が人と文書によって分かれ、レビューで何が過剰かを決めにくいためである。このリポジトリは linked worktree で作業し、`/runplan` のようにエージェントがスクリプトを実行するので、それらは既定に含める。
    -   採らなかった案：環境の既定を置かず、核を超える防御には実運用上の具体的な必要性だけを求める案。上の理由で、判断が分かれる。
    -   採らなかった案：クラウドのセッションの作業ツリーも既定に含める案。実行しない環境への耐性まで既定で求めることになる。
-   **信頼しない入力と投稿する出力：他者が書いた入力（ブランチの名前、コミットメッセージなど）で判定を誤らないこと、特に読めない入力でフェイルクローズすることを、核のフェイルクローズの性質に含める。** 出力を GitHub に投稿するときの守りは、エージェントの操作の既存の規則に任せ、出力をコミットするときは PR のレビューで読む。スクリプトの側で網羅的なエスケープをするのは、具体的な脅威を設計書か計画が書いたときだけとする（F-002）。一時スクリプトの判定の誤りは、核のフェイルクローズで止められる。投稿する文の守りは、メンションの検査（`.claude/commands/_context.md` の「Rejected mentions」）とネットワークの操作の承認（`CLAUDE.md`「Tool Execution Safety」）がすでに担っている。0121 の網羅的なエスケープは、それらに重ねた守りだった。
    -   採らなかった案：他者が書いた入力を読むか、出力を投稿・コミットするスクリプトでは、核を超える防御（エスケープなど）を常に必要とする案。0121 と同じ規模の防御が、移行ゲートのたびに既定で入る。
-   **一時スクリプトのテストは、既定ではコミットしない。** 壊し確認（各チェックが少なくとも 1 つの壊し方で失敗すること）は行い、その結果を計画に記録する。テストをコミットするのは、計画が具体的な理由を書いたときだけとし、その場合も核の代表ケースに限る。「レビューの修正の後に再実行するため」だけでは理由にならない。修正の後は、壊し確認をやり直して記録し直す（F-003）。一時スクリプトは 1〜2 回しか実行しないので、壊し確認の結果が残れば足りる。コミットしたテストは、レビューで読む量を増やす。どのスクリプトもレビューで直されるので、再実行を理由に認めると、0121 と同じくテストのコミットが既定になるためである。
    -   採らなかった案：理由がなくてもコミットしてよく、代表ケースに限るだけにする案。コミットが既定になり、規模を抑える歯止めが弱い。
    -   採らなかった案：テストを一切コミットしない案。テストを残す具体的な理由がある場合に対応できない。
    -   採らなかった案：理由の中身を定めず、計画とレビューの判断に任せる案。上の理由で、0121 の理由がそのまま通る。
-   **計画の 2 つの規則（前のタスクの `_checks/` を手本として写させない、壊し方は「チェックごとに少なくとも 1 つ」とだけ書いて並べ挙げない）を、`diff` の確かめから一時スクリプト全般に広げる（F-004）。** 前のタスクの大きなスクリプトの構造が受け継がれ、計画に並べた壊し方がそのまま作業になるのは、用途によらないためである。0121 の計画も、設計書が並べた 7 つのシナリオをテストで網羅するとした。
    -   採らなかった案：2 つの規則を `diff` の確かめだけに残す案。移行ゲートなどで、0121 と同じことが起きうる。
-   **過剰な設計と過剰なテストを指摘する観点を、issue が挙げる 4 か所に加え、`mkreq.md` の要件定義のチェックリストと、`runplan.md` のテストのレビューのチェックリストにも置く。CLI レビューとクロスチェックの部分レビューの指摘を振り分ける規則でも、一時スクリプトに核を超える防御を求める指摘は、基準に照らして実害がないと扱う（F-005）。** 原因 3 は、要件の段階から、コードのレビュー・CLI レビュー・上位モデルのレビューまでの各段で過剰な要求が積み上がることだった。そのため、最も上流と、テストを読むレビューと、外部の指摘を受け入れる振り分けでも止めるためである。
    -   採らなかった案：issue が挙げる 4 か所（`mkarch.md`・`mkplan.md`・`runplan.md` のフェーズのまとまりのレビュー・`_lib/high-review.md`）に限る案。要件の段階で入った過剰な仕様と、CLI レビューなどから来る過剰な要求を止められない。
    -   タスク 0080 では、受け入れ基準の並べ挙げを指摘する項目を `mkreq.md` に足す案を、人が選ばなかった（[0080 要件定義書](../0080_diff_check_proportion/01_requirements.md)「要件定義の際に決めたこと（2026-11-10）」）。本書の項目は、一時スクリプトの過剰な設計を見るもので、その項目とは別である。
-   **新しい基準は、文書ごとに当てはめる。** この変更が `main` に入った後に承認される文書には当てはめ、それより前に承認された文書と、その文書に従って作る `_checks/` は変えない。前に承認された文書が求めることは、後の文書のレビューで過剰と指摘しない（F-006）。境目を「書いた時」ではなく「承認された時」にするのは、変更の前に書き始めて後に承認される文書を、どちらかに必ず入れるためである。issue が 0121 を承認済みの設計と計画のとおりに通すと決めているのと同じく、承認済みの文書に後から基準を当てはめると、文書の間や計画と実装が食い違う。0080 の観点にも同じ適用の範囲がある（`.claude/commands/runplan.md:226`）。
    -   採らなかった案：承認済みでも、まだ実装していない PR の `_checks/` には新しい基準を当てはめる案。承認済みの計画と実装が食い違う。
    -   採らなかった案：最初の文書がこの変更より前に承認されたタスクは、後の文書も含めて新しい基準を当てはめない案。長いタスクで、古い基準が残り続ける。
-   **`diff` の確かめ以外の一時スクリプトの既定の言語は、定めない。** issue が求めていない。0121 の補助の Go のファイルでは、言語の違いよりも網羅的なエスケープが規模を膨らませた。シェルを既定とする規則は、`diff` の確かめにだけ残す（2.3 節）。
    -   採らなかった案：一時スクリプト全般の既定をシェルにする案。
-   **`_checks/` の比例原則を、主題を独立させた新しい ADR（ADR-0056）に置く。ADR-0016 の `diff` の確かめの比例原則の項目、計画の規則、過大さを指摘する観点はそこへ移し、ADR-0016 からは ADR-0056 へリンクする。** 移行ゲートや前提の確認は文書のテストではないので、ADR-0016 の主題（文書のテストの方針）からはみ出すためである。1 つの主題は 1 つの有効な ADR に置く（`docs/dev/conventions/adr.md`「Location and naming」の「Subject」）。
    -   採らなかった案：ADR-0016 を更新して、比例原則の範囲を広げる案。上の理由で、主題がずれる。
    -   ADR：[ADR-0056](../../dev/adr/0056-checks-script-proportion.md) を作り、[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `_checks/` の一時スクリプトとそのテストの規模を、本体の変更の規模・実行回数・想定運用環境に見合ったものにする。
-   要件・設計・計画・実装・レビューの各段で、一時スクリプトに常設のツール並みの要求が積み上がることを止める。

### 2.2. スコープ (In Scope)

-   規約 `docs/dev/conventions/requirements_process.md` に、一時スクリプトの定義、比例原則の適用範囲、設計水準、テストの基準、計画の規則、適用の範囲を書くこと。
-   コマンドの定義のうち、次のものを変えること。
    -   `.claude/commands/mkplan.md`：計画が一時スクリプトについて書くことの規則（F-004）と、チェックリスト・レビュアーの役割（F-005）。
    -   `.claude/commands/mkreq.md`・`mkarch.md`・`runplan.md`・`_lib/high-review.md`：チェックリスト（`mkarch.md` はレビュアーの役割の記述を含む。F-005）。
    -   `.claude/commands/_lib/local-cli-review.md`：指摘を振り分ける規則（F-005）。
    -   壊し確認の結果を計画に記録する手順を、計画を書くコマンドと実装するコマンドに置くこと（F-003）。どこにどう置くかは `02_architecture.md` で決める（`design_handoff.md` の H-07）。

### 2.3. スコープ外 (Out of Scope)

-   **タスク 0121（PR #1130）とその `_checks/`、および既存のタスクの `_checks/` を変えること。** issue #1132 が、PR #1130 を承認済みの設計と計画のとおりに通すと決めている（F-006）。
-   **`diff` の確かめに固有の規則を変えること。** 記録した差分の読み取り、固定のコマンド、差分の記録の形、記録の確かめ直し、前後の関係を述べる受け入れ基準の書き方、スクリプトの既定の言語（シェル）が当たる（`requirements_process.md` §1、§4）。issue が求めていない。ただし、比例原則と計画の 2 つの規則は、`diff` の確かめを含む一時スクリプト全般の規則に置き換わる（F-001、F-004）。
-   **`diff` の確かめ以外の一時スクリプトの既定の言語を定めること。** 「要件定義の際に決めたこと」のとおりである。
-   **常設のツールの基準を変えること。** 開発ツール（`docs/dev/conventions/dev_tools.md`）、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテストが当たる。issue は、これらと一時スクリプトを区別することを求めており、これらの基準を緩めることは求めていない。
-   **`_checks/` のリテラルの言語の例外（`CLAUDE.md`「Go Idioms」）を変えること。** issue が求めていない。
-   **行数などの数の上限を設けること。** issue が求めていない。釣り合いは、本書の基準に照らして人とレビュアーが判断する。
-   **エージェントの操作の規則を緩めること。** 一時スクリプトの出力を GitHub に投稿するときのメンションの検査と、ネットワークの操作の承認が当たる（AC-07）。

## 3. 機能要件 (Functional Requirements)

本書の要件は、規約とコマンドの定義の文に関するものである。受け入れ基準の「規約」は `docs/dev/conventions/requirements_process.md` を指す。基準の正本は規約に 1 か所だけ置く。

### 3.1. 機能一覧

#### F-001: 一時スクリプトの定義と比例原則の適用範囲

規約に、一時スクリプトを置き場所で定義し、比例原則を一時スクリプト全般に当てはめることを書く。

**Acceptance Criteria**:

-   **AC-01**: 規約が、タスクの `_checks/` に置くスクリプトとその補助のファイルを、用途（`diff` の確かめ、移行ゲート、前提の確認を例に挙げる）によらず一時スクリプトとして定義している。そのうえで、常設のツール（開発ツール、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテスト）と区別している。
-   **AC-02**: 規約が、一時スクリプトとそのテストの設計と規模を、本体の変更の規模・実行回数・想定運用環境に見合ったものにすると定めている。この原則は、`diff` の確かめに限らず、AC-01 の一時スクリプトのすべてに当てはまる。

#### F-002: 一時スクリプトの設計水準

規約に、一時スクリプトが必ず満たす核、核を超える防御を入れる条件、想定運用環境の既定、信頼しない入力と投稿する出力の扱いを書く。

**Acceptance Criteria**:

-   **AC-03**: 規約が、一時スクリプトが必ず満たす核として、次の 4 つを挙げている。
    -   目的のものを検出すること。
    -   正常なときに検出しないこと。
    -   異常なときにフェイルクローズすること。判定できないとき（読めない入力を含む）は、通ったと報告しない。
    -   呼び出し元（作業ツリー、リポジトリ、環境）を汚さないこと。
-   **AC-04**: 規約が、他者が書いた入力（ブランチの名前、コミットメッセージなど）を読む一時スクリプトについて、AC-03 のフェイルクローズの性質が次のことを含むと定めている。この性質は 5 つ目の核ではない。
    -   読めない入力や、受け入れる形に合わない入力では、通ったと報告しない。
    -   細工された入力への防御（網羅的なエスケープなど）は核に含まず、AC-05 の核を超える防御として扱う。
-   **AC-05**: 規約が、核を超える防御（想定運用環境の外への耐性、敵対的な入力への防御、網羅的なエスケープなど）について、次のことを定めている。
    -   その防御は、設計書か計画が実運用上の具体的な必要性を書いたときだけ入れる。必要性とは、どの実行で、どの状況や脅威が起きるかである。
    -   必要性が書かれていない防御は求めない。
-   **AC-06**: 規約が、想定運用環境の既定を「スクリプトを実行する人またはエージェントの、手元の機械にあるこのリポジトリの作業ツリー（main のチェックアウトか linked worktree）」と定めている。クラウドのセッションは既定に入れない。そのうえで、ほかの環境への耐性は、その環境で実際に実行することを設計書か計画が書いたときだけ求めると定めている。
-   **AC-07**: 規約が、次の 2 つを述べている。
    -   一時スクリプトの出力を GitHub に投稿するときは、エージェントの操作の既存の規則（メンションの検査、ネットワークの操作の承認（`CLAUDE.md`「Tool Execution Safety」））で守る。出力をコミットするときは、PR のレビューで読む。
    -   一時スクリプトの設計水準の基準は、それらの規則を緩めない。

#### F-003: 一時スクリプトのテストの基準

規約に、一時スクリプトのテストをコミットするかの基準と、コミットする場合の規模を書く。一時スクリプトのテストとは、一時スクリプトを実行してその判定を確かめるスクリプトである。

**Acceptance Criteria**:

-   **AC-08**: 規約が、一時スクリプトのテストについて、次の 3 つを定めている。
    -   テストは、既定ではリポジトリにコミットしない。
    -   壊し確認（各チェックが少なくとも 1 つの壊し方で失敗すること）を行い、その結果を計画に記録する。スクリプトをレビューの後に直したときは、壊し確認をやり直して記録し直す。
    -   テストをコミットするのは、計画がその具体的な理由を書いたときだけとする。「レビューの修正の後に再実行するため」だけでは理由にならない。理由が足りるかは、計画を書く者とレビュアーが判断する。
    -   テストの入力（フィクスチャなど）は、テストと同じく、コミットするかを決める。
-   **AC-09**: 規約が、テストをコミットする場合も、核（AC-03）の代表ケースに限ると定めている。あわせて、常設のツール並みのエッジケースの網羅テストを書かないと定めている。

#### F-004: 計画の規則

計画が一時スクリプトについて書くことの規則を、一時スクリプト全般に当てはめる。

**Acceptance Criteria**:

-   **AC-10**: `.claude/commands/mkplan.md` の、計画が `_checks/` について書くことの規則が、`diff` の確かめに限らず一時スクリプトのすべてに当てはまる。規則は、次の 2 つである。
    -   計画は、前のタスクの `_checks/` を手本として写させない。
    -   壊し方は「各チェックが少なくとも 1 つの壊し方で失敗すること」とだけ書き、並べ挙げない。

#### F-005: レビューの観点

過剰な設計と過剰なテストを指摘する観点を、要件・設計・計画・実装の各段のレビューと、外部の指摘を振り分ける規則に置く。

**Acceptance Criteria**:

-   **AC-11**: 次の 6 つのチェックリストのそれぞれが、項目を 1 つ持つ。その項目は、`_checks/` の一時スクリプトとそのテストが規約の基準（F-002、F-003）に比べて過剰でないかを確かめる。
    -   `.claude/commands/mkreq.md` の「Requirements checklist」。
    -   `.claude/commands/mkarch.md` の「Technical correctness checklist」。
    -   `.claude/commands/mkplan.md` の「Technical correctness checklist」。
    -   `.claude/commands/runplan.md` の「Phase-group review checklist」。
    -   `.claude/commands/runplan.md` の「Test-review checklist」。
    -   `.claude/commands/_lib/high-review.md` の「Weak-model failure checklist」。
-   **AC-12**: `.claude/commands/mkarch.md` のレビュアー B（senior SRE）の役割の記述が、次の 2 つを述べている。
    -   一時スクリプトについては、運用の観点（障害のモード、環境の違い、敵対的な入力など）を、規約の核と想定運用環境の範囲で当てはめる。
    -   その範囲を超える防御を求めることを、過剰な設計として扱う。
-   **AC-13**: `.claude/commands/mkplan.md` のパネルモードのレビュアー B（SDET）の役割の記述が、AC-11 の `mkplan.md` の項目をレビュアー B の担当として挙げている。
-   **AC-14**: `.claude/commands/_lib/local-cli-review.md` の「Triage rules」が、次のことを定めている。CLI レビューかクロスチェックの部分レビューの指摘が、一時スクリプトに核を超える防御を求め、設計書と計画にその具体的な必要性が書かれていないときは、規約の基準に照らして、実害がない指摘（`no-harm`）として扱う。

#### F-006: 適用の範囲

新しい基準を、この変更が `main` に入った後に承認される文書に、文書ごとに当てはめる。

**Acceptance Criteria**:

-   **AC-15**: AC-10 の計画の規則、AC-11 の項目、AC-12 のレビュアーの役割の記述、AC-14 の規則が、次のことを述べている。
    -   この変更が `main` に入る前に承認された文書と、その文書に従って作る `_checks/` には当てはめない。
    -   前に承認された文書が求めることは、過剰と指摘しない。
-   **AC-16**: 本タスクの実装の PR について、`docs/tasks/` の下の差分は、本タスクのディレクトリ（`docs/tasks/0124_checks_proportion/`）の中に限られる。比べるのは、マージの基点と PR の head である。

### 4.1. 性能 (Performance)

-   N/A。実行するコードを変えず、規約とコマンドの定義の文だけを変えるためである。

### 4.2. セキュリティ (Security)

-   N/A。条件付きのガイド（`docs/dev/security.md`）を当てはめる条件に当たらない。本書は、外部コマンド（`yt-dlp`）の起動、API キー、キャッシュのディレクトリ、LLM API への送信、信頼できないテキストのプロンプトや記事への埋め込みに触れない。

-   開発の進め方としては、一時スクリプトの判定が他者の書いた入力で誤らないことを核に含める（AC-04）。出力を投稿するときの既存の規則は緩めない（AC-07）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   一時スクリプトの核として、異常なときのフェイルクローズを残す（AC-03）。判定できない状態を、通ったと報告しないためである。

### 4.4. 互換性 (Compatibility)

-   既存のタスクの文書と `_checks/` は変えない（F-006）。
-   `diff` の確かめに固有の規則は変えない（2.3 節）。

### 4.5. 保守性 (Maintainability)

-   基準の正本は規約に 1 か所だけ置く。各コマンドの記述が正本とどう結びつくか（参照するか、写しを置くか）は `02_architecture.md` で決める（`design_handoff.md` の H-02）。

## 6. 用語集 (Glossary)

用語は `docs/translation_glossary.md` と統一する。

-   **一時スクリプト**: タスクの `docs/tasks/NNNN_<name>/_checks/` に置くスクリプトと、その補助のファイル（データのファイル、テストの入力など。テストの入力は、テストと同じくコミットするかを決める）。用途（`diff` の確かめ、移行ゲート、前提の確認など）を問わない。`make test` も CI も実行しない（F-001）。
-   **一時スクリプトのテスト**: 一時スクリプトを実行して、その判定を確かめるスクリプト（F-003）。
-   **常設のツール**: マージの後も実行し、保守するツールとスクリプト。開発ツール（`docs/dev/conventions/dev_tools.md`）、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテストを指す。
-   **核**: 一時スクリプトが必ず満たす 4 つの性質（AC-03）。他者が書いた入力についてのフェイルクローズ（AC-04）は、そのうちの 1 つに含まれる。
-   **想定運用環境**: 一時スクリプトを実行する環境。既定は、スクリプトを実行する人またはエージェントの、手元の機械にあるこのリポジトリの作業ツリー（AC-06）。
-   **壊し確認**: 確かめの対象を壊して、確かめが失敗することを確かめる手順（`CLAUDE.md`「Testing Strategy」の「Every test must be able to fail for its stated reason」）。
-   **移行ゲート**: 移行の前提が成り立つかを、実装の開始やマージの前に確かめる一時スクリプト（例：タスク 0121 の `check_open_branches.sh`）。
