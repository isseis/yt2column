# 設計への申し送り（タスク 0124）

`/mkreq` の作成時に出た、設計で決める事項である。`02_architecture.md` は、各項目について採る方針か、当てはまらない理由を記録する。

## H-01: 規約の中の置き場所と、`diff` の確かめの「Proportion」との関係

**内容:** 一時スクリプトの定義・比例原則・設計水準・テストの基準（F-001〜F-003）を、`requirements_process.md` のどこに置くかを決める。§4 の「`diff` verification」の下には「Proportion」の項目（`requirements_process.md:838`）がある。新しい基準と、その項目をどう関係づけるかも決める。候補は 2 つある。

-   §4 に `_checks/` の一時スクリプト全般の小節を設け、「Proportion」をそこへの参照にする。
-   「Proportion」を残し、新しい小節から参照する。

**理由:** 基準の正本を 1 か所に置かないと、2 つの記述が食い違う（4.5 節）。

**関係する ID:** F-001、F-002、F-003、AC-01〜AC-09。

## H-02: チェックリストの既存の `diff` の確かめの項目との統合と、正本との結びつけ方

**内容:** 過大な `diff` の確かめを指摘する既存の項目がある（`mkplan.md:164`、`runplan.md:226`、`_lib/high-review.md:647-654`）。新しい項目（AC-12）を、これらに統合して一時スクリプト全般に広げるか、別の項目として足すかを決める。統合する場合は、既存の項目の適用の範囲の文（「この項目が `main` に入る前に承認された計画には当てはめない」）が、0080 で足した部分と本タスクで足す部分の両方に正しく効くようにする（AC-16）。

チェックリストは、レビューの subagent の prompt に原文のまま写される。subagent に渡すファイルに `requirements_process.md` を含まないレビューもある（`runplan.md` の step 7、`_lib/high-review.md`）。そのため、各項目が正本を参照するのか、基準の要点を項目の中に写すのかも決める（4.5 節）。

**理由:** 似た項目が 2 つ並ぶと、レビュアーが片方だけを見る。統合すると、既存の部分の適用の範囲が変わりうる。参照先を読めないレビュアーは、参照だけの項目を当てはめられない。

**関係する ID:** F-005、F-006、AC-12、AC-16。

## H-03: 文書を読む既存の guard への影響

**内容:** 変更するコマンドの定義と規約を読む既存の Go の guard（`cmd/yt2column`・`cmd/fixprguard`・`internal/chief` などの文書のテスト）があるかを調べる。見出しや表の構造を変えて落ちるものがあれば、その扱いを決める。

**理由:** 文書だけの変更でも `doc-guard` の CI ジョブが guard を実行するため、見出しの変更で guard が落ちうる。

**関係する ID:** F-001〜F-005。

## H-04: `CLAUDE.md` と `dev_tools.md` との整合

**内容:** `CLAUDE.md`「Testing Strategy」は、`_checks/` を `diff` の確かめの置き場所として述べている。`docs/dev/conventions/dev_tools.md` は、開発ツールを `cmd/` と `internal/` の組と定める。一時スクリプトの定義（AC-01）と食い違う記述や、追記の要る記述がないかを確かめる。要るなら、変える場所を決める。`CLAUDE.md` の規則の写しを変えるときは、正本を先に変える。

**理由:** 一時スクリプトと常設のツールの区別が、文書の間で食い違わないようにするためである。

**関係する ID:** F-001、AC-01。

## H-05: `/weakreview` など、チェックリストを共有するコマンドへの波及

**内容:** `_lib/high-review.md` のチェックリストは `/weakreview` も使う。AC-12 の項目が、`/weakreview` の実行（承認済みの計画がない範囲を見る場合を含む）でも意味をなすかを確かめる。適用の範囲の文（AC-16）が、計画のない範囲でどう読まれるかも決める。同じく、`_lib/local-cli-review.md` の「Triage rules」（AC-15）は複数のコマンドが使うので、計画のない standalone の変更（`/runpr` step 1）での読まれ方を決める。

**理由:** 共有のチェックリストと規則に足した項目は、呼び出すすべてのコマンドに効くためである。

**関係する ID:** F-005、F-006、AC-12、AC-15、AC-16。

## H-06: 一時スクリプトを対象とする受け入れ基準の確かめ方

**内容:** テストを既定でコミットしないとき（AC-08）、一時スクリプトの振る舞いを述べる受け入れ基準（例：0121 の AC-02）を、どの確かめのラベル（`test`・`static`・`diff`・`manual`）で、どんな記録で確かめるかを決める。今の規約（`requirements_process.md` §4）と `mkplan.md` step 6（`mkplan.md:103`）は、各 AC に「実行される確かめ」を名指しさせている。

**理由:** コミットしたテストがないと、計画が AC の確かめとして名指すものがなくなるためである。

**関係する ID:** F-003、AC-08。

## H-07: 壊し確認の記録の形と、それを書く手順

**内容:** 壊し確認の結果を計画に記録する（AC-08）ための、次のことを決める。

-   記録の形と、計画の中の置き場所。
-   記録を書くコマンドと手順。計画を書く `mkplan.md` step 6 と、実装する `runplan.md` の手順のどちらに置くか。
-   承認済みの計画に記録を書き足すことが、編集上の訂正か、決定の変更か（`requirements_process.md`「Editing an approved document」）。0080 の差分の記録と同じ扱いでよいかも確かめる。
-   `diff` の確かめのスクリプトの規則（`requirements_process.md:839`）は、壊し確認を求めるが、その結果の記録は求めていない。この規則との関係。
-   `CLAUDE.md`「Testing Strategy」の「Every test must be able to fail for its stated reason」は、壊し確認をしたことをコミットメッセージに書くよう求めている。計画への記録との関係（どちらにも書くのか、計画への記録で代えるのか）。

**理由:** 記録を書く者と形が決まっていないと、AC-08 の記録が残らないか、計画ごとにばらつくためである。

**関係する ID:** F-003、AC-08。

## H-08: ADR-0056 の決定のリンクを、規約の節へ向け直す

**内容:** ADR-0056 の「決定」の多くの項目は、規約にまだ本文がないため、本タスクの要件定義書の F の番号へリンクしている（`docs/dev/conventions/adr.md`「Writing an ADR」は、仕様の置き場所として文書と節の見出しを示すよう求めている）。規約に本文を書いた PR で、各項目のリンクを規約の節の見出しへ向け直す。

**理由:** ADR の決定は、仕様の正本を指すべきであり、タスク文書は決めた時点の記録だからである。

**関係する ID:** F-001〜F-006。
