# 設計への申し送り（0105）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: マージを見た PR の記録を、セッションの間どう保つか

**懸念:** 今の観測の記録は、前のラウンドの分だけが残る（`internal/chief/records.go:1123-1146` の `pruneRounds`）。マージを見た後の記録は、自動送信のために次のラウンドへ引き継がれる。ただし引き継ぐのは、マージを最初に見てから 10 分（`carryWindow`、`internal/chief/autosend.go:22`）までである。今の記録のままでは、`main` にいる worktree のタスクを特定できるのも、マージから 10 分ほどに限られる。要件は「同じセッションの間」特定することである（01_requirements.md の要件定義の際に決めたこと、AC-01・AC-05）。

**なぜ重要か:** 自動送信の引き継ぎの期間を延ばすと、自動送信が古いマージにも働き、ADR-0046 の「見たマージだけを対象にする」の意図とずれうる。

**候補:**
-   自動送信の引き継ぎとは別に、worktree ごとに、マージを見た PR とそのタスクをセッションの間だけ持つ記録を足す。セッションが変われば読まない。
-   引き継ぎの記録に、自動送信の期間を過ぎたことを示す印を足し、`main` の特定にだけ使い続ける。

**関連:** F-001、AC-01・AC-05

## H-02: 人が選ぶ送信の直前の確かめ

**懸念:** 人が選ぶ送信は行から送るコマンドを決める（`internal/chief/request.go` の `offeredMkreq` などは行の状態と次のコマンドを見る）。`main` にいる worktree では、送る直前に行を作り直したときに、記録が消えるか食い違って、タスクが変わりうる。また、`main` が `origin/main` より先のコミットを持つときや、未コミットの変更があるときに送るかも、機能ブランチの行と合わせて決める必要がある。

**なぜ重要か:** 人が見た行のタスクと、送るコマンドのタスクが食い違うと、人の選んでいないタスクへ送ることになる。

**候補:**
-   送る直前に行を作り直し、タスクと次のコマンドが人に示したものと同じときだけ送る（今の送信の確かめを、そのまま当てる）。
-   `main` の行では、git の状態の条件（変更なし、`origin/main` と同じ）を送信の条件に足す。

**関連:** AC-03

## H-03: 要確認の理由の文言と、行の並べ方の印

**懸念:** AC-04・AC-05・AC-07 の理由の文言（英語の道具の出力）を決める。また AC-05 の行に、使っていないか残った worktree の印（`Row.Idle`。今は detached HEAD だけによる要確認の行に付く、`internal/chief/state.go:464`）を付ける条件を決める。AC-04・AC-07 の行に付けるかも決める必要がある。

**なぜ重要か:** 印を付けると表の最後に並ぶので、人が見るべき食い違いや読み取りの失敗を、後回しにさせうる。

**候補:**
-   AC-05 の行だけに印を付け、AC-04・AC-07 の行はふつうの順に並べる（画面や fetch を読めずに要確認になった行と同じ）。

**関連:** AC-04・AC-05・AC-07

## H-04: 出力の形とプロトコル番号

**懸念:** `snapshot`・`tick` の出力の項目は変えないが、`main` の行の値の組み合わせが変わる。`/chief` の定義（`.claude/commands/chief.md`）が値の組み合わせに依っているか、プロトコル番号（CLAUDE.md「Protocol numbers」）を上げる必要があるかを確かめる必要がある。

**なぜ重要か:** 定義が「タスクが空なら `/mkreq` を尋ねる」などの組み合わせに依っていれば、上げずに変えると、古い定義が新しい値を読み違える。

**候補:**
-   `chief.md` の読み方を確かめ、依っていなければ番号を上げない。

**関連:** 4.4
