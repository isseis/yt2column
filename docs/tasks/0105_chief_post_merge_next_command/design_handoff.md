# 設計への申し送り（0105）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: マージを見た PR の記録を、セッションの間どう保つか

**懸念:** 今の観測の記録は、前のラウンドの分だけが残る（`internal/chief/records.go:1123-1146` の `pruneRounds`）。マージを見た後の記録は、自動送信のために次のラウンドへ引き継がれる。ただし引き継ぐのは、マージを最初に見てから 10 分（`carryWindow`、`internal/chief/autosend.go:22`）までである。今の記録のままでは、`main` にいる worktree のタスクを特定できるのも、マージから 10 分ほどに限られる。要件は「chief のセッションの間」特定することである（01_requirements.md の要件定義の際に決めたこと、AC-01・AC-07）。

**なぜ重要か:**

-   自動送信の引き継ぎの期間を延ばすと、自動送信が古いマージにも働き、ADR-0046 の「見たマージだけを対象にする」の意図とずれうる。
-   新しい種類の記録を足すなら、消す規則が要る。`pruneRounds` が消さない記録は、セッションが変わるたびに溜まる。
-   ADR-0046 の「決定」は記録の種類と使い道を並べているので、新しい種類の記録を足すときは、その「決定」も同じ PR で更新する。

**候補:**

-   自動送信の引き継ぎとは別に、worktree ごとに、マージを見た PR とそのタスクを持つ、セッションに属する記録を足す。セッションが変われば読まず、`pruneRounds` と同じく古いセッションの分を消す。
-   引き継ぎの記録に、自動送信の期間を過ぎたことを示す印を足し、`main` の特定にだけ使い続ける。

**関連:** F-001、AC-01・AC-07

## H-02: 人が選ぶ送信の直前の確かめ

**懸念:** 人が選ぶ送信は、行から送るコマンドを決める（`internal/chief/request.go:414-425` の `offeredMkreq` などは、行の状態と次のコマンドを見る）。AC-05 は、送る直前に行のタスクか次のコマンドが変わっていれば拒むことを求める。そのため、送る直前に何を作り直して比べるかを決める必要がある。また、`main` が `origin/main` より先のコミットを持つときや、未コミットの変更があるときに送るかも、機能ブランチの行と合わせて決める。

**なぜ重要か:** 人が見た行のタスクと、送るコマンドのタスクが食い違うと、人の選んでいないタスクへ送ることになる。

**候補:**

-   送る直前に行を作り直し、タスクと次のコマンドが人に示したものと同じときだけ送る（今の送信の確かめを、そのまま当てる）。
-   `main` の行では、git の状態の条件（変更なし、`origin/main` と同じ）を送信の条件に足す。

**関連:** AC-04・AC-05

## H-03: 要確認の理由の文言と、行の並べ方の印

**懸念:** AC-06・AC-07・AC-09 の理由の文言（英語の道具の出力）を決める。AC-07 の行には、使っていないか残った worktree の印（`Row.Idle`。今は detached HEAD だけによる要確認の行に付く、`internal/chief/state.go:464`）を付ける。AC-06・AC-09 の行に付けるかは決まっていない。

**なぜ重要か:** 印を付けると表の最後に並ぶので、人が見るべき食い違いや読み取りの失敗を、後回しにさせうる。

**候補:**

-   AC-06・AC-09 の行には印を付けず、ふつうの順に並べる（画面や fetch を読めずに要確認になった行と同じ）。

**関連:** AC-06・AC-07・AC-09

## H-04: 出力の形とプロトコル番号

**懸念:** `snapshot`・`tick` の出力の項目は変えないが、`main` の行の値の組み合わせが変わる。`/chief` の定義（`.claude/commands/chief.md`）が値の組み合わせに依っているか、プロトコル番号（CLAUDE.md「Protocol numbers」）を上げる必要があるかを確かめる必要がある。

**なぜ重要か:** 定義が「タスクが空なら `/mkreq` を尋ねる」などの組み合わせに依っていれば、上げずに変えると、古い定義が新しい値を読み違える。

**候補:**

-   `chief.md` の読み方を確かめ、依っていなければ番号を上げない。

**関連:** 4.4

## H-05: 記録から特定したタスクの文書のディレクトリの見つけ方

**懸念:** ブランチからタスクを読むとき、`Read` は、`origin/main` のタスクのディレクトリの名前が、ブランチの名前の slug と合うことも確かめる（`internal/chief/task.go:804-818`）。`main` にはブランチの slug がないので、F-001 の「機能ブランチにいるときと同じ規則」をそのまま当てられない。

**なぜ重要か:** 確かめを外すと、同じ番号のディレクトリの取り違えを見逃しうる。

**候補:**

-   ディレクトリの名前から読む `ReadDir` と同じ規則（番号のディレクトリが 1 つだけあること）を当てる。
-   記録の `Branch`（PR を見たときのブランチ）の slug と照らし合わせる。

**関連:** F-001

## H-06: 記録の読み取りの細部

**懸念:** 要件の確認のレビューで、次の細部が設計に残った。

-   4.2 の形の求め（タスクの形、不正な UTF-8、対のないサロゲート、項目の繰り返しの拒否）を、今の自動送信の読み取りにも当てるか。今の読み取りは知らない項目を拒むが、その誤りは `errRecord` で包んでいない（`internal/chief/records.go:159-175`）。
-   マージを見たことを持つ項目（`MergedSince`・`OpenAt`）の形の確かめ。H-05 で記録の `Branch` を使うなら、4.2 の使う項目に足す。
-   記録の鍵は、今は `row.Workspace` である（`internal/chief/tick.go:56`）。同じパスに worktree を作り直したときに、古い記録を使わないか。
-   `main` にいて fetch に失敗した行に、AC-07 の並べ方の印を付けるか（今の detached の行は、fetch に失敗すると付けない。`internal/chief/state.go:464`）。
-   記録が示すタスクのディレクトリが `origin/main` にないときの行（要確認にするか、今のタスクのディレクトリがないときの扱いにするか）。

**なぜ重要か:** どれも、分からないときに次のコマンドを推し量らない（4.3）ことにかかわる。

**関連:** AC-07・AC-09、4.2
