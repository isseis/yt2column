## 1. 概要 (Overview)

**目的:** 本書は、タスク `0060_adr_records` で ADR にしなかった残りの候補 20 件を ADR にすることと、0060 の時点で実装中だったタスク 0058・0059 の決定を ADR に反映することの要件を定義する。

**背景:**

タスク 0060（issue [#602](https://github.com/isseis/yt2column/issues/602)）は、主要な設計の決定を `docs/dev/adr/` の ADR として記録する仕組みを作った。あわせて、issue #602 のコメント（2026-11-04）の調査で ADR の候補とした 35 件のうち、「優先」とした 15 件を ADR にした（`docs/tasks/0060_adr_records/01_requirements.md` F-006）。残りの 20 件と、後で足す経緯は、同書 F-007 のとおり issue [#666](https://github.com/isseis/yt2column/issues/666) に記録された。

今の状態は次のとおりである。

-   有効な ADR は ADR-0001〜ADR-0017 の 17 本である（`docs/dev/adr/README.md`）。ADR-0001〜ADR-0016 は 0060 で、ADR-0017 は 0063 で作られた。
-   0058 と 0059 は完了している。どちらも実装計画の最後の PR（0058 は #686、0059 は #661）がマージされ、未完了の項目はない（`docs/tasks/0058_same_video_article/03_implementation_plan.md`、`docs/tasks/0059_remove_legacy_articles_api/03_implementation_plan.md`）。
-   0060 は、B2・B8・B11 の ADR を書いた時点の `main` の状態で書き、0058・0059 の決定を経緯に入れなかった（`docs/tasks/0060_adr_records/01_requirements.md` の「要件定義の際に決めたこと」）。今の ADR-0006（B2）・ADR-0010（B8）・ADR-0011（B11）の「経緯」には、0058・0059 の項目がない（`docs/dev/adr/0006-threat-model.md:40`、`docs/dev/adr/0010-extension-stores-nothing.md:39`、`docs/dev/adr/0011-webhook-publishing.md:47` 以降）。
-   候補の一部は、既存の ADR の「決定」と重なる。たとえば、`internal/strictjson` の共有（A2 の一部）は ADR-0001 の「決定」にあり（`docs/dev/adr/0001-llm-adapter-stdlib.md:28`）、Claude の出力の上限の既定 40,000（A11 の一部）は ADR-0004 の「決定」にある（`docs/dev/adr/0004-production-profile.md:22`）。投稿を自動で再送しないこと（B9 の一部）と、Webhook URL を `secret.Secret` で持つこと（C1 の一部）は ADR-0011 の「決定」にある（`docs/dev/adr/0011-webhook-publishing.md:18`・`:20`）。

ADR の書き方は、規約 `docs/dev/conventions/adr.md` に従う。規約は、1 本の ADR が 1 つの主題を持ち、1 つの主題は有効な ADR のうち 1 本だけに属し、重なる主題は統合せずに互いにリンクすると定めている（同書「Location and naming」の Subject）。

対応 issue: [#666](https://github.com/isseis/yt2column/issues/666)（関連: [#602](https://github.com/isseis/yt2column/issues/602)（タスク `0060_adr_records`）、[#593](https://github.com/isseis/yt2column/issues/593)（タスク `0058_same_video_article`））

**本書の記述範囲:** 本書は、どの主題を ADR にするか、ADR に何が書かれているか、0058・0059 の決定をどの ADR にどう反映するかを定める。候補ごとに新しい ADR を作るか同じ主題の既存の ADR を更新するかの振り分け、ADR の本数と番号、主題ごとの仕様の正本の文書の対応、確かめる方法、PR の分け方は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る（本書は、その項目を H-01 などの番号で示す）。

**issue #666 で決めたこと:**

-   **残りの候補は、F-001 の表の 20 件である:** 調査の番号・主題・出典のタスクは、issue #602 のコメントのとおりである。
-   **B6 の ADR は、0058 と 0059 の完了の後に、両タスクの決定を含めて書く:** 0060 の要件定義の時点で、両タスクが実装中だったためである。
-   **0058 の完了の後に B2（脅威 T-10 の再評価）と B8（方針を保ったこと）の経緯へ、0059 の完了の後に B11（失敗の通知の削除）の経緯へ、項目を足す:** 0060 が、これらの ADR を書いた時点の `main` の状態で書いたためである。
-   **ADR の書き方は、0060 の PR-1 のマージの後の `docs/dev/conventions/adr.md` に従う。**

**要件定義の際に決めたこと（2026-11-06）:**

-   **20 件をすべて ADR にする:** 調査で「迷う」とした B12・C3・C4・D8 も含める。issue は 20 件を残りの候補として挙げており、どれも複数の箇所を縛るためである。C3 には仕様の正本 `docs/dev/cache_consistency.md` があり、D8 の規則は CLAUDE.md にある。しかし、ADR が正本へリンクして理由と経緯を持つ形は、ADR-0016 が CLAUDE.md の規則について採った前例があるので、ADR にする妨げにならない。ADR の判断：本タスクの作業範囲の決定で、タスクの中で閉じるので、ADR は作らない。
-   **B12 は、定数の値だが主要な決定として扱う（方針の例外）:** CLAUDE.md「Design decisions (ADR)」と `docs/dev/conventions/adr.md`「What counts as a major decision」は、定数の値を主要でない決定の例に挙げている。しかし `minimum_chrome_version` は、manifest と両方の README を縛り、変えると複数の箇所が変わる。同じ基準の「覆すと複数の箇所が変わる」に当たるので、例外として主要とする。ADR の判断：本タスクの作業範囲の決定で、タスクの中で閉じるので、ADR は作らない（規約の基準の文は変えない）。
-   **0058・0059 の決定は、有効な ADR のすべてと照らして反映する:** issue が挙げた B2・B8・B11 の 3 本に限らない。0058 は、ポップアップに選択の状態を加え、照会付きの生成の開始でビューアが既存の記事を表示するようにした（`docs/tasks/0058_same_video_article/01_requirements.md` §1）。そのため、起動の経路（ADR-0008）やビューアの開き方（ADR-0009）の主題にも触れうる。0059 は旧 API を削除したので、サーバの構成（ADR-0005）にも関係しうる。3 本だけにすると、ほかの ADR の「決定」が `main` と食い違ったまま残るおそれがあるためである。ADR の判断：本タスクの作業範囲の決定で、タスクの中で閉じるので、ADR は作らない。
-   **後のタスクが、決定の節で既存の方針を明示して保ったことも、経緯の項目にする:** 規約の経緯は、決定を下したときと変えたときの記録である（`docs/dev/conventions/adr.md`「History entries」）。0058 は、拡張に記事の履歴を保存しないことを、「`0050` の `chrome.storage` を使わない方針を保つ」と決定の節に明示した（`docs/tasks/0058_same_video_article/01_requirements.md` の「issue #593 で決めたこと」）。新しい機能にも同じ方針を当てはめると決めたことは、決定を下したことに当たるとみなす。issue が B8 の経緯にこの項目を求めており、後の読み手が、方針が新しい機能でも保たれたかを ADR から知れるためである。この解釈は本タスクの中で使い、規約は変えない（2.3）。ADR の判断：本タスクの作業範囲の決定で、タスクの中で閉じるので、ADR は作らない。
-   **採らなかった案は、出典のタスクのすべての文書から拾う:** 0060 は、調査が対象とした文書（`01_requirements.md`・`02_architecture.md` など）に限った（`docs/tasks/0060_adr_records/01_requirements.md` AC-27）。本タスクでは、出典のタスクの `docs/tasks/<task>/` にあるすべての文書（実装計画の「計画の際に決めたこと」「実装の際に決めたこと」、`design_handoff.md`、調査の記録を含む）に広げる。実装の段階で採らなかった案や、調査の記録にだけある案が落ちないようにするためである。文書に書かれた案だけを拾い、本タスクで新しい案や理由を作らないことは、0060 と同じである。ADR の判断：本タスクの作業範囲の決定で、タスクの中で閉じるので、ADR は作らない。

**上の決定と現行の規則・前例から導いたこと（PR のレビューで確認を求める）:**

以下は、レビュアーと個別には確認していない。上の決定と、規約・CLAUDE.md の規則・0060 の前例から導いたもので、PR のレビューで異論があれば改める。

-   **候補の主題が既存の ADR と同じなら既存の ADR を更新し、違うなら新しい ADR を作る:** 規約の「1 つの主題は有効な ADR のうち 1 本だけに属する」と「重なる主題は互いにリンクする」（`docs/dev/conventions/adr.md`「Location and naming」の Subject）に従う。どの候補をどちらにするかは設計で決める（H-01）。
-   **新しい ADR の主題に移った決定は、既存の ADR の「決定」から除く:** 同じ規約の「1 つの主題は有効な ADR のうち 1 本だけに属する」から導く。本タスクより前からある ADR 同士の重なりは、本タスクでは扱わない（2.3）。
-   **CLAUDE.md の規則を主題とする候補（D5・D8 など）は、規則の文を ADR に移さない:** CLAUDE.md「Design decisions (ADR)」の「The rules and cross-cutting principles of this file are not ADRs」に従い、規則は CLAUDE.md に残す。ADR は ADR-0016 と同じく、規則を正本としてリンクし、理由・採らなかった案・経緯を持つ。
-   **経緯には、調査が挙げたタスクに限らず、主題の決定を下したか変えたタスクをすべて入れる:** 規約の「One entry per event」（`docs/dev/conventions/adr.md`「History entries」）に従う。調査は誤りを含みうる（issue #602 のコメントの補足は、サブエージェントの報告の誤りを訂正している）。そのため、調査が挙げたタスクが実際には主題の決定を下していなかった場合は、経緯に入れず、その理由を設計書に書く。
-   **正本の文書とコードの食い違いは、0060 と同じく扱う:** ADR にはコードの振る舞いを書き、食い違いを issue にしてリンクする（`docs/tasks/0060_adr_records/01_requirements.md` AC-26。承認済みの前例）。issue の作成はネットワークの操作なので、作る前に利用者の承認を得る（CLAUDE.md「Tool Execution Safety」）。
-   **既存のタスク文書は変えない:** 0060 の「タスク文書にも書き、ADR へリンクする」の決定のとおり、タスク文書は変わらない記録として残す。
-   **`project_overview.md` の「決定済みの方針」から新しい ADR へリンクする:** CLAUDE.md「Design decisions (ADR)」の「`docs/dev/project_overview.md` keeps the summary of the current policies and links to the ADRs」と、0060 の AC-31 の前例に従う。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   調査で ADR の候補とした 35 件のすべてを、有効な ADR で読めるようにする。
-   0058・0059 の後も、有効な ADR の「決定」が今の `main` と食い違わないようにする。

### 2.2. スコープ (In Scope)

-   F-001 の表の 20 件の主題を含む ADR（新しい ADR、または同じ主題の既存の ADR の更新）。
-   新しい ADR を作ったことに伴う、既存の ADR の「決定」からの除去とリンク。
-   0058・0059 の決定の、有効な ADR への反映（「経緯」の項目と「決定」の更新）。
-   索引 `docs/dev/adr/README.md` の行の追加と更新。
-   `docs/dev/project_overview.md` の「決定済みの方針」から、新しい ADR へのリンク（F-003）。
-   正本の文書とコードの食い違いを見つけたときの GitHub の issue（AC-03）。

### 2.3. スコープ外 (Out of Scope)

-   **決定そのものの変更:** 本タスクは、既存の決定を記録するだけで、変えない。
-   **仕様の正本の文書の書き換え:** `security.md`・`cache_consistency.md`・`production_profile.md`・CLAUDE.md の規則などの、仕様の記述は変えない。ADR からそれらへリンクする。
-   **既存のタスク文書の書き換え:** 本タスク自身のディレクトリを除き、`docs/tasks/` の下の文書は変えない（AC-12）。
-   **ADR の規約と手順の変更:** `docs/dev/conventions/adr.md`・CLAUDE.md「Design decisions (ADR)」・`.claude/commands/` は変えない。本タスクは、0060 の規約に従って ADR を書くだけである。
-   **本タスクより前からある ADR 同士の重なりの解消:** たとえば ADR-0006 と ADR-0011 は、どちらも Webhook URL を `secret.Secret` で持つことを述べている。本タスクは、新しい ADR を作ったことで生じる重なりだけを扱う（AC-02）。C1 の主題を新しい ADR にしたことで両方の該当の部分が C1 に属するようになる場合は、AC-02 に当たる。
-   **35 件の候補の外の主題の ADR:** 0060 より後のタスク（0061〜0064）の決定のうち、20 件の主題に属さないものは扱わない。それらは CLAUDE.md の「主要な決定を下すか変える PR は、同じ PR で ADR を作るか更新する」規則の下で下された。20 件の主題に属する決定は、AC-05 により経緯に入る。
-   **ADR の文の意味を確かめるテスト:** CLAUDE.md「Document tests check values, structure, and executable examples, never prose」に従う。
-   **信頼しない入力:** 本タスクは文書だけを変え、信頼しない入力を受け取らない。

以下の基準で「PR の基点」は、その ADR を書くか変える本タスクの PR の、取り込んだ `main` とのマージの基点（merge-base）である。

**Acceptance Criteria**:
- **AC-01**: 上の 20 件の主題が、それぞれ、ちょうど 1 本の有効な ADR に含まれている。その ADR は、本タスクで新しく作った ADR か、同じ主題を持つ既存の ADR である。
- **AC-02**: 本タスクで新しく作った ADR の主題に属する決定を、ほかの有効な ADR の「決定」の節が、自分の決定として述べていない。新しい ADR の主題へ移った部分は、既存の ADR の「決定」から除かれ、その位置から新しい ADR へリンクしている。新しい ADR の名前を挙げてリンクする文は、自分の決定として述べることに当たらない。
- **AC-03**: 20 件の主題を含む各 ADR の「決定」の節は、PR の基点のコードの振る舞いと食い違わない。仕様の正本の文書とコードが食い違っているのを見つけたときは、ADR の「決定」にはコードの振る舞いを書き、その食い違いと、食い違いを記録した GitHub の issue へのリンクを書く。
- **AC-04**: 20 件の主題を含む各 ADR で、本タスクが書き足した「採らなかった案」とその理由は、その ADR の経緯に入るタスクの `docs/tasks/<task>/` の下の文書か、`docs/dev/project_overview.md` に書かれたものだけである。それらにない案や理由を書き足していない。
- **AC-05**: 20 件の主題を含む各 ADR の「経緯」は、PR の基点までに、その主題の決定を下したか変えたタスク（後のタスクが決定の節で方針を明示して保った場合を含む）を、それぞれ 1 項目以上として持つ。F-001 の表の「出典のタスク」のうち経緯に入れなかったものは、入れなかった理由が本タスクの設計書に挙がっている。
- **AC-06**: B6 を含む ADR の「決定」は、今の状態として、拡張とホストとサーバがジョブの API だけを使うこと（ホストのメッセージの `v` は `1` だけを受け付けること）を述べ、旧 API を述べていない。旧 API との併存、`v` の有無による旧形式と新形式の判別、0059 によるそれらの削除は、「経緯」に書かれている。
- **AC-07**: 20 件の主題を含む ADR のうち、主題の仕様の正本の文書があるものは、「決定」の節でその文書へリンクし、その文書の表・列挙・規則の一覧を書き写していない（AC-03 の食い違いの記述は除く）。主題ごとの正本の文書は、本タスクの設計書が挙げる（H-05）。CLAUDE.md の規則の文は、本タスクの PR で変わっていない。

#### F-002: 0058・0059 の決定の反映

0058・0059 の決定を、その主題を持つ有効な ADR に反映する。

**Acceptance Criteria**:
- **AC-08**: ADR-0006（脅威モデル）の「経緯」が、0058 で脅威 T-10（照会付きの生成の開始による、記事の有無の照会）を、排除する脅威ではなく信頼の境界の内側で受け入れるリスクとして再評価したことを、0058 の文書へのリンクとともに 1 項目として持つ。

## 6. 用語集 (Glossary)

-   **ADR（Architecture Decision Record）:** 主要な決定を主題ごとに記録する、生きた文書（`docs/dev/conventions/adr.md`）。
-   **主題:** 1 本の ADR が扱う決定のまとまり。1 つの主題は、有効な ADR のうち 1 本だけに属する。
-   **候補:** issue #602 のコメント（2026-11-04）の調査で、ADR の単位としてまとめた 35 件の決定。本書の F-001 の 20 件は、そのうち 0060 で ADR にしなかったものである。
-   **調査の番号:** 調査で候補に付けた番号（A1〜D8）。
-   **出典のタスク:** 調査が、候補の決定を下したか変えたとして挙げたタスク。
-   **仕様の正本の文書:** ある主題の今の仕様を定める文書（`security.md`・`cache_consistency.md`・CLAUDE.md の規則など）。ADR はそれを要約してリンクする。
-   **PR の基点:** F-001 で定義する。ADR を書くか変える本タスクの PR の、取り込んだ `main` とのマージの基点。
-   **有効:** ADR の状態。承認された決定であることを表す（`docs/dev/conventions/adr.md`「Status」）。
