## 1. 概要 (Overview)

**目的:** 本書は、タスク `0060_adr_records` で ADR にしなかった残りの候補 20 件を ADR にすることと、0060 の時点で実装中だったタスク 0058・0059 の決定を ADR に反映することの要件を定義する。

**背景:**

タスク 0060（issue [#602](https://github.com/isseis/yt2column/issues/602)）は、主要な設計の決定を `docs/dev/adr/` の ADR として記録する仕組みを作った。あわせて、issue #602 のコメント（2026-11-04）の調査で ADR の候補とした 35 件のうち、「優先」とした 15 件を ADR にした（`docs/tasks/0060_adr_records/01_requirements.md` F-006）。残りの 20 件と、後で足す経緯は、同書 F-007 のとおり issue [#666](https://github.com/isseis/yt2column/issues/666) に記録された。

今の状態は次のとおりである。

-   有効な ADR は ADR-0001〜ADR-0017 の 17 本である（`docs/dev/adr/README.md`）。ADR-0001〜ADR-0016 は 0060 で、ADR-0017 は 0063 で作られた。
-   0058 と 0059 は完了している。どちらも実装計画の最後の PR（0058 は #686、0059 は #661）がマージされ、未完了の項目はない（`docs/tasks/0058_same_video_article/03_implementation_plan.md`、`docs/tasks/0059_remove_legacy_articles_api/03_implementation_plan.md`）。
-   0060 は、B2・B8・B11 の ADR を書いた時点の `main` の状態で書き、0058・0059 の決定を経緯に入れなかった（`docs/tasks/0060_adr_records/01_requirements.md` の「要件定義の際に決めたこと」）。今の ADR-0006（B2）・ADR-0010（B8）・ADR-0011（B11）の「経緯」には、0058・0059 の項目がない（`docs/dev/adr/0006-threat-model.md:40`、`docs/dev/adr/0010-extension-stores-nothing.md:39`、`docs/dev/adr/0011-webhook-publishing.md:47` 以降）。
-   候補の一部は、既存の ADR の「決定」と重なる。たとえば、`internal/strictjson` の共有（A2 の一部）は ADR-0001 の「決定」にあり（`docs/dev/adr/0001-llm-adapter-stdlib.md:28`）、Claude の出力の上限の既定 40,000（A11 の一部）は ADR-0004 の「決定」にある（`docs/dev/adr/0004-production-profile.md:22`）。Webhook URL を `secret.Secret` で持つこと（C1 の一部）と、投稿を自動で再送しないこと（B9 の一部）は ADR-0011 の「決定」にある（`docs/dev/adr/0011-webhook-publishing.md:18`・`:20`）。

ADR の書き方は、規約 `docs/dev/conventions/adr.md` に従う。規約は、1 本の ADR が 1 つの主題を持ち、1 つの主題は有効な ADR のうち 1 本だけに属し、重なる主題は統合せずに互いにリンクすると定めている（同書「Location and naming」の Subject）。

対応 issue: [#666](https://github.com/isseis/yt2column/issues/666)（関連: [#602](https://github.com/isseis/yt2column/issues/602)（タスク `0060_adr_records`）、[#593](https://github.com/isseis/yt2column/issues/593)（タスク `0058_same_video_article`））

**本書の記述範囲:** 本書は、どの主題を ADR にするか、ADR に何が書かれているか、0058・0059 の決定をどの ADR にどう反映するかを定める。候補ごとに新しい ADR を作るか同じ主題の既存の ADR を更新するかの振り分け、ADR の本数と番号、確かめる方法、PR の分け方は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る（本書は、その項目を H-01 などの番号で示す）。

**issue #666 で決めたこと:**

-   **残りの候補は、F-001 の表の 20 件である:** 調査の番号・主題・出典のタスクは、issue #602 のコメントのとおりである。
-   **B6 の ADR は、0058 と 0059 の完了の後に、両タスクの決定を含めて書く:** 0060 の要件定義の時点で、両タスクが実装中だったためである。
-   **0058 の完了の後に B2（脅威 T-10 の再評価）と B8（方針を保ったこと）の経緯へ、0059 の完了の後に B11（失敗の通知の削除）の経緯へ、項目を足す:** 0060 が、これらの ADR を書いた時点の `main` の状態で書いたためである。
-   **ADR の書き方は、0060 の PR-1 のマージの後の `docs/dev/conventions/adr.md` に従う。**

**要件定義の際に決めたこと（2026-11-06）:**

-   **20 件をすべて ADR にする:** 調査で「迷う」とした B12・C3・C4・D8 も含める。B12（`minimum_chrome_version`）は定数の値ではあるが、manifest と両方の README を縛り、変えると複数の箇所が変わるので、CLAUDE.md「Design decisions (ADR)」の主要な決定の基準に当たる。C3 には仕様の正本 `docs/dev/cache_consistency.md` があり、D8 の規則は CLAUDE.md にある。しかし、ADR が正本へリンクして理由と経緯を持つ形は、ADR-0016 が CLAUDE.md の規則について採った前例があるので、ADR にする妨げにならない。issue は 20 件を残りの候補として挙げており、どれも複数の箇所を縛るためである。ADR の判断：本タスクの作業範囲の決定で、タスクの中で閉じるので、ADR は作らない。
-   **0058・0059 の決定は、有効な ADR のすべてと照らして反映する:** issue が挙げた B2・B8・B11 の 3 本に限らない。0058 は、ポップアップに選択の状態を加え、照会付きの送信でビューアが既存の記事を表示するようにした（`docs/tasks/0058_same_video_article/01_requirements.md` §1）。そのため、起動の経路（ADR-0008）やビューアの開き方（ADR-0009）の主題にも触れうる。0059 は旧 API を削除したので、サーバの構成（ADR-0005）にも関係しうる。3 本だけにすると、ほかの ADR の「決定」が `main` と食い違ったまま残るおそれがあるためである。ADR の判断：本タスクの作業範囲の決定で、タスクの中で閉じるので、ADR は作らない。

**上の決定と現行の規則から導いたこと（PR のレビューで確認を求める）:**

以下は、レビュアーと個別には確認していない。上の決定と、規約・CLAUDE.md の規則から導いたもので、PR のレビューで異論があれば改める。

-   **候補の主題が既存の ADR と同じなら既存の ADR を更新し、違うなら新しい ADR を作る:** 規約の「1 つの主題は有効な ADR のうち 1 本だけに属する」と「重なる主題は互いにリンクする」に従う。どの候補をどちらにするかは設計で決める（H-01）。
-   **同じ決定を 2 本の有効な ADR の「決定」に書かない:** 新しい ADR を作ったことで、既存の ADR の「決定」の一部がその新しい主題に属するようになったときは、既存の ADR からその部分を除き、新しい ADR へリンクする。正本を 2 つにしないという 0060 の決定（`docs/tasks/0060_adr_records/01_requirements.md` の「要件定義の際に決めたこと」）を ADR 同士にも当てはめたものである。
-   **CLAUDE.md の規則を主題とする候補（D5・D8 など）は、規則の文を ADR に移さない:** CLAUDE.md の「The rules and cross-cutting principles of this file are not ADRs」に従い、規則は CLAUDE.md に残す。ADR は ADR-0016 と同じく、規則を正本としてリンクし、理由・採らなかった案・経緯を持つ。
-   **採らなかった案の出典は、0060 と同じ範囲に限る:** 0060 の AC-27 と同じく、調査が対象とした文書に書かれた案だけを書き、それ以外の案を書き足さない。ADR が記録するのは過去に下した決定の理由であり、本タスクで新しい理由を作らないためである。
-   **既存のタスク文書は変えない:** 0060 の「タスク文書にも書き、ADR へリンクする」の決定のとおり、タスク文書は変わらない記録として残す。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   調査で ADR の候補とした 35 件のすべてを、有効な ADR で読めるようにする。
-   0058・0059 の後も、有効な ADR の「決定」が今の `main` と食い違わないようにする。

### 2.2. スコープ (In Scope)

-   F-001 の表の 20 件の主題を含む ADR（新しい ADR、または同じ主題の既存の ADR の更新）。
-   新しい ADR を作ったことに伴う、既存の ADR の「決定」の重なりの解消とリンク。
-   0058・0059 の決定の、有効な ADR への反映（「経緯」の項目と「決定」の更新）。
-   索引 `docs/dev/adr/README.md` の行の追加と更新。
-   `docs/dev/project_overview.md` の「決定済みの方針」から、新しい ADR へのリンク（F-003）。

### 2.3. スコープ外 (Out of Scope)

-   **決定そのものの変更:** 本タスクは、既存の決定を記録するだけで、変えない。
-   **仕様の正本の文書の書き換え:** `security.md`・`cache_consistency.md`・`production_profile.md`・CLAUDE.md の規則などの、仕様の記述は変えない。ADR からそれらへリンクする。
-   **既存のタスク文書の書き換え:** 本タスク自身のディレクトリを除き、`docs/tasks/` の下の文書は変えない（AC-12）。
-   **ADR の規約と手順の変更:** `docs/dev/conventions/adr.md`・CLAUDE.md「Design decisions (ADR)」・`.claude/commands/` は変えない。本タスクは、0060 の規約に従って ADR を書くだけである。
-   **調査の 35 件に入らない決定の ADR:** 0060 より後のタスク（0061〜0064）の決定は、CLAUDE.md の「主要な決定を下すか変える PR は、同じ PR で ADR を作るか更新する」規則の下で下されたので、本タスクでは扱わない。0060 より前のタスクで、調査の 35 件に入らなかった決定も扱わない。
-   **ADR の文の意味を確かめるテスト:** CLAUDE.md「Document tests check values, structure, and executable examples, never prose」に従う。索引と ADR の構造は、既存の `TestADRRecords` が確かめる。

## 6. 用語集 (Glossary)

-   **ADR（Architecture Decision Record）:** 主要な決定を主題ごとに記録する、生きた文書（`docs/dev/conventions/adr.md`）。
