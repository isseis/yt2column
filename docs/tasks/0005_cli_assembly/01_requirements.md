## 1. 概要 (Overview)

**目的:** 本書は、`cmd/yt2column` で各段階をつなぎ、動画 URL から記事を生成してローカルのファイルに出力できる最小構成の CLI に関する要件を定義する。対象は、環境変数からの設定の読み込み（`internal/config`）、記事をファイルに書き出す `FilePublisher`、設定に応じた LLM プロバイダの選択、CLI 引数、キャッシュの後始末、および testdata から記事のファイル出力までを通しで実行する統合テストである。

**背景:**
yt2column は `URL → TranscriptSource → Transcript → ArticleWriter → Article → Publisher` というパイプラインで動作する（[project_overview.md](../../dev/project_overview.md)）。パイプラインの骨格（#2、タスク `0001_pipeline_skeleton`）、字幕取得の `YtDlpSource`（#3、タスク `0002_ytdlp_transcript_source`）、DeepSeek アダプタ（#4、タスク `0003_deepseek_llm_client`）、`ArticleWriter`（#5、タスク `0004_article_writer`）は実装済みである。しかし、これらを組み立てて実行する CLI はまだなく、`cmd/yt2column/main.go` は空の `main` だけである。

各段階のコンストラクタは、意図的に環境変数を読まない。キャッシュディレクトリ・`yt-dlp` のパス・強制再取得の指定（#3）、API キーとモデル名（#4）、プロンプトテンプレートの上書きファイルのパス（#5）は、いずれも構築時に受け取る。本タスクは、これらを環境変数と CLI 引数から集めて検証し、各段階に渡す。

キャッシュについては、#3 が削除（`RemoveCache`）と掃除（`PruneCache`）の操作を提供し、それをいつ呼ぶかを本タスクに委ねている（#3 の要件定義書 2.3）。掃除は、同じキャッシュディレクトリに対して実行中の別の `Fetch` が書き込み中のエントリを、dangling なエントリ（§6）として削除しうる（[cache_consistency.md](../../dev/cache_consistency.md) P1）。そこで本タスクは、同じキャッシュディレクトリに対する CLI の同時実行を排他する。

**本書の記述範囲:** 本書は、観測できる振る舞い（何を受け取り、何を出力し、何をどの終了コードやエラーで拒否するか）を定める。その振る舞いを実現する手段（型や関数の名前、番兵エラーの名前、排他の仕組み、タイムアウトの値、出力ファイルの正確な書式など）は設計（`02_architecture.md`）で決める。レビューで挙がった事項のうち、設計で決めるものは [design_handoff.md](design_handoff.md) に、実装計画とテストの組み立てで扱うものは [implementation_handoff.md](implementation_handoff.md) に記録する。

対応 issue: #6

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   動画 URL を引数に CLI を実行すると、字幕を取得し、記事を生成して、指定したローカルのファイルに出力できる。
-   設定を環境変数から読み込み、起動時に検証する。不正な値は補正せず、変数名を示して拒否する。秘密情報の値は、どの出力にも現れない。
-   投稿に成功した動画のキャッシュを既定で削除し、中断などで残った dangling なエントリを各実行で掃除する。
-   同じキャッシュディレクトリに対する CLI の同時実行を排他し、掃除が実行中の別プロセスのエントリを削除しないようにする。
-   YouTube にアクセスせず、testdata の字幕から実 LLM API を経て記事のファイル出力までを、CLI と同じ組み立てで通しで確認できる。

### 2.2. スコープ (In Scope)

-   `internal/config`: 環境変数の読み込みと検証。秘密情報（API キー・Webhook URL）は `secret.Secret` 型で保持する。
-   `FilePublisher`（`internal/publisher` 内）: 記事をローカルのファイルに書き出す `Publisher` の実装。
-   設定に応じた `LLMClient` の選択（小さなファクトリ関数）。
-   `cmd/yt2column`: CLI 引数の解析、各段階の構築、パイプラインの実行、キャッシュの後始末、終了コード。
-   同じキャッシュディレクトリに対する同時実行の排他。
-   fake を使うユニットテストと、testdata から実 DeepSeek API を経てファイル出力までを行う統合テスト。
-   README・[project_overview.md](../../dev/project_overview.md)・[package_reference.md](../../dev/developer_guide/package_reference.md)・[security.md](../../dev/security.md) の更新（F-010）。

### 2.3. スコープ外 (Out of Scope)

-   `SlackWebhookPublisher` と、CLI から Slack を投稿先に選ぶこと（#7）。本タスクの投稿先はファイルだけである。`SLACK_WEBHOOK_URL` の読み込みと検証は本タスクで行う（F-001）が、それを使う投稿先は #7 で追加する。
-   testdata から Slack への投稿までを通しで行う統合テスト。本タスクの統合テスト（F-009）はファイル出力までとし、Slack への投稿までを含む統合テストは #7 の要件に含める。
-   `--dry-run`。本タスクの投稿先はローカルのファイルだけであり、外部への投稿を止めるという `--dry-run` の目的は、Slack を投稿先に加えて初めて意味を持つ。設けるかどうかと、設ける場合に LLM API の呼び出しも止めるかどうかは #7 で決める。
-   Gemini・Claude などの他のプロバイダ（#15・#9）。本タスクのプロバイダは `deepseek` だけであり、選択の仕組みは追加しやすい形にとどめる（4.5）。
-   thinking モードの切り替え（#11）、LLM 呼び出しのリトライ（#48）。
-   プロンプトの文面（#8）。
-   プロンプトテンプレートの上書きファイルのパスを環境変数から受け取ること。上書きは CLI 引数でだけ指定する（F-005）。
-   字幕と記事の言語の切り替え（#64）。
-   タイムアウトの値を設定で変えること。`yt-dlp` と LLM の呼び出しのタイムアウトは固定値とし、値は `02_architecture.md` で決める。
-   ブラウザ拡張と localhost サーバ（#43）。
-   Windows での動作（4.4）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 環境変数からの設定の読み込み

`internal/config` は、次の環境変数を読み込んで検証し、設定の値を返す。環境変数の値は補正しない（前後の空白を取り除く、大文字と小文字を区別しない、などをしない）。

| 変数 | 未設定のとき | 受理する値 |
|---|---|---|
| `YT2COLUMN_LLM_PROVIDER` | `deepseek` | `deepseek` に完全一致する値だけ |
| `YT2COLUMN_MODEL` | エラー | 空でない値 |
| `DEEPSEEK_API_KEY` | プロバイダが `deepseek` ならエラー | 空でない値 |
| `SLACK_WEBHOOK_URL` | 受理する（値なし） | `https://hooks.slack.com/` で始まり、その後に 1 文字以上続き、空白文字（§6）を含まない値 |
| `YT2COLUMN_CACHE_DIR` | 利用者のキャッシュディレクトリ（Go の `os.UserCacheDir` と同じ規則で決まるディレクトリ）の下の `yt2column` | 絶対パス |
| `YT2COLUMN_YTDLP_PATH` | `PATH` 上の `yt-dlp` | 空でない値 |

-   「未設定」は、変数が環境に存在しないことを指す。変数が存在して値が空の場合は「未設定」として扱わず、いずれの変数でもエラーにする。既定値のある変数を空にして既定値を選ぶことはできない。
-   `YT2COLUMN_CACHE_DIR` の既定値も、`internal/config` が引数で受け取った環境をもとに決める。プロセスの環境変数を直接読む `os.UserCacheDir` は、そのまま呼ばない。利用者のキャッシュディレクトリを決められない場合（`HOME` が未設定、`XDG_CACHE_HOME` が相対パスなど）は、既定値を補わずに `YT2COLUMN_CACHE_DIR` の「未設定または空」としてエラーにする。
-   `YT2COLUMN_MODEL` の値の中身（前後の空白など）は、ここでは空かどうかだけを確かめ、それ以上の検証はプロバイダのアダプタ（`deepseek.New`）に任せる。
-   `DEEPSEEK_API_KEY` と `SLACK_WEBHOOK_URL` の値は `secret.Secret` 型で保持する。設定の値をどの形式で出力しても（`fmt`・`log/slog`・JSON）、秘密情報の値は現れない。
-   `SLACK_WEBHOOK_URL` は、本タスクでは使う投稿先がない（2.3）。それでも、設定されていれば起動時に検証し、形式の違う値は拒否する。使うときになって初めて誤りが分かることを避けるためである。
-   プロバイダの値は、文字列のままではなく、取りうる値を列挙した型で保持する（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。
-   検証で拒否するとき、エラーは拒否した変数の名前を示し、値（またはその一部）は含めない。これは秘密情報でない変数にも適用する。秘密情報を取り違えて別の変数に設定した場合にも、その値を出力しないためである。
-   複数の変数が不正な場合は、最初の 1 つで止めずに、不正な変数をすべて報告する。
-   「未設定または空」と「値が不正」は、`errors.Is` で判別できる別々の番兵エラーで報告する。
-   `internal/config` は環境変数を読む手段を引数として受け取れるようにし、テストがプロセスの環境変数を変更せずに任意の環境を与えられるようにする。

**Acceptance Criteria**:
- **AC-01**: すべての変数を有効な値に設定した環境から読み込むと、エラーにならず、各変数の値を反映した設定を返す。`DEEPSEEK_API_KEY` と `SLACK_WEBHOOK_URL` の値は `secret.Secret` として保持され、`Reveal` で元の値が得られる。
- **AC-02**: `YT2COLUMN_LLM_PROVIDER`・`YT2COLUMN_CACHE_DIR`・`YT2COLUMN_YTDLP_PATH`・`SLACK_WEBHOOK_URL` が未設定の環境から読み込むと、それぞれ表の「未設定のとき」の値（`SLACK_WEBHOOK_URL` は値なし）になり、エラーにならない。
- **AC-03**: `YT2COLUMN_MODEL` が未設定、または `YT2COLUMN_LLM_PROVIDER` が未設定か `deepseek` で `DEEPSEEK_API_KEY` が未設定の場合、読み込みは「未設定または空」の番兵エラーになり、エラーのメッセージは該当する変数の名前を含む。
- **AC-04**: 表のいずれかの変数が、存在して値が空の場合、読み込みは「未設定または空」の番兵エラーになり、エラーのメッセージはその変数の名前を含む。
- **AC-05**: 次の値は、それぞれ「値が不正」の番兵エラーになり、エラーのメッセージは該当する変数の名前を含む。
    -   `YT2COLUMN_LLM_PROVIDER`: `DeepSeek`、` deepseek`、`deepseek `、`gemini`、`claude`
    -   `SLACK_WEBHOOK_URL`: `http://hooks.slack.com/services/x`、`https://hooks.slack.com.example/services/x`、`https://HOOKS.SLACK.COM/services/x`、`https://hooks.slack.com/`（接頭辞だけ）、` https://hooks.slack.com/services/x`、`https://hooks.slack.com/services/x` の末尾に改行（U+000A）を付けた値
    -   `YT2COLUMN_CACHE_DIR`: `cache`、`./cache`、`~/cache`（相対パス）
- **AC-06**: AC-03〜AC-05 のすべての拒否について、エラーのメッセージ（`Error()` の値）は、拒否した変数の値も、他の変数の値も含まない。この確認は、各変数に互いに異なる特徴的な文字列を含む値を設定して行う。
- **AC-07**: 2 つ以上の変数が不正な環境から読み込むと、エラーは不正な変数の名前をすべて含み、「未設定または空」と「値が不正」が混在する場合は両方の番兵に対して `errors.Is` が真になる。
- **AC-08**: 読み込んだ設定の値を `fmt` の `%v`・`%+v`・`%#v`、`log/slog`、`encoding/json` で出力しても、`DEEPSEEK_API_KEY` と `SLACK_WEBHOOK_URL` の値は現れない。

#### F-002: 環境変数を読む場所の限定

秘密情報を環境変数から読むのは `internal/config` だけとする（[security.md](../../dev/security.md) §2）。

-   テスト以外の Go のコードで、プロセスの環境変数を読む標準ライブラリの関数（環境変数を直接返すものに限らず、内部で環境変数を読むものを含む）を参照するのは、次の場所だけとする。
    -   `internal/config`
    -   `cmd/yt2column`（プロセスの環境を `internal/config` に渡すためだけに参照する）
    -   `internal/transcript` の、`yt-dlp` に引き継ぐ環境変数を allowlist で選ぶ処理（既存。秘密情報の変数を引き継がない。[security.md](../../dev/security.md) §1）
-   秘密情報の変数名（`DEEPSEEK_API_KEY`・`SLACK_WEBHOOK_URL`）の文字列は、テスト以外の Go のコードでは `internal/config` にだけ現れる。

**Acceptance Criteria**:
- **AC-09**: リポジトリのテスト以外の Go のファイルを走査するテストがあり、上記の場所以外でプロセスの環境変数を読む標準ライブラリの関数のいずれかを参照するか、`internal/config` 以外に秘密情報の変数名の文字列があると失敗する。

#### F-003: プロバイダの選択

設定のプロバイダの値に応じて `LLMClient` を構築する。

-   プロバイダが `deepseek` のとき、`deepseek.New` に、設定の API キーとモデル名、および固定のタイムアウト（2.3）を渡して構築する。
-   プロバイダの型の値のうち、構築の仕方を定めていない値（ゼロ値や範囲外の値）は、構築をエラーにする。既定のプロバイダに読み替えない。
-   `deepseek.New` が返したエラー（モデル名の前後に空白がある場合など）は、包む場合も `%w` で元のエラーをたどれるようにし、`errors.Is` で判別できる形で報告する。`deepseek.New` の番兵エラーは現在エクスポートされていないため、判別の手段（番兵のエクスポートなど）は `02_architecture.md` で決める（5 章）。

**Acceptance Criteria**:
- **AC-10**: プロバイダが `deepseek` の設定から構築した `LLMClient` は、DeepSeek アダプタである（テストでは、構築したクライアントがテスト用の送信先へ設定のモデル名と API キーで要求を送ることで確認する）。
- **AC-11**: プロバイダの型のゼロ値、および列挙した値の範囲外の値を与えると、構築はエラーになり、`LLMClient` を返さない。
- **AC-12**: モデル名の前後に空白がある設定から構築すると、構築はエラーになり、`LLMClient` を返さない。エラーは、`deepseek.New` が前後の空白を理由に拒否したことを `errors.Is` で判別できる（判別に使う番兵は設計で決める）。

#### F-004: FilePublisher

`FilePublisher` は、`Publisher` interface を実装し、記事を 1 つのローカルのファイルに書き出す。

-   出力先のパスは構築時に受け取る。空のパスは構築をエラーにする。
-   書き出す内容は Markdown とし、次をこの順に含む。正確な書式は `02_architecture.md` で固定する。
    -   `Article.Title` を内容とするレベル 1 の見出し
    -   生成に使ったモデル（`Article.Model`）とモデルの版の識別子（`Article.ModelVersion`。空の場合は空であることを示す）。どのモデルで生成したかを追えるようにするためである（[project_overview.md](../../dev/project_overview.md)「前提・制約」）。
    -   `Article.Body`（加工しない）。ファイルは `Article.Body` で終わり、その後に何も書かない。`ArticleWriter` は元動画へのリンク（出典）を `Article.Body` の末尾に置く（#5）ため、出典がファイルの末尾に来る（[project_overview.md](../../dev/project_overview.md)「記事の末尾には必ず元動画へのリンク」）。
-   出力先のパスに既に何かが存在する場合（通常のファイル、ディレクトリ、シンボリックリンク（リンク先が存在しない場合を含む）など）は、上書きせずにエラーにする。存在の確認とファイルの作成は、確認から作成までの間に別のものが作られても、それを上書きしない方法で行う（手段は設計で決める）。
-   出力先のディレクトリが存在しない場合は作成せず、エラーにする。
-   書き出しに失敗した場合（書き込みエラー、`ctx` のキャンセルなど）、出力先のパスには何も残さない（途中まで書いたファイルを残さない）。
-   次の `Article` は書き出さずにエラーにする（[CLAUDE.md](../../../CLAUDE.md)「Empty is an error」）。
    -   `Title` が空、または空白文字だけである。
    -   `Title` が改行（`\n`・`\r`）を含む（見出しの 1 行に収まらないため）。
    -   `Body` が空、または空白文字だけである。
    -   `Model` が空、または空白文字だけである（どのモデルで生成したかを追えないため）。
    -   `SourceURL` が空である。
    -   `ModelVersion` は空でも書き出す（プロバイダが版の識別子を返さない場合があるため）。
-   作成するファイルのパーミッションは `02_architecture.md` で固定する。
-   `ctx` が既にキャンセルされている場合は、ファイルを作成せずに `ctx` のエラーを返す。

**Acceptance Criteria**:
- **AC-13**: 存在しないパスを出力先とし、有効な `Article` を書き出すと、エラーにならず、そのパスに通常のファイルが作られる。ファイルの内容は、`Title` の見出し、`Model` と `ModelVersion`、加工していない `Body` をこの順に含み、ファイルは `Body` で終わる（したがって `Body` の末尾の出典がファイルの末尾に来る）。`ModelVersion` が空の `Article` も書き出せる。
- **AC-14**: 出力先のパスに、通常のファイル、ディレクトリ、存在するファイルへのシンボリックリンク、存在しないパスへのシンボリックリンクがある場合、書き出しはエラーになる。既存のファイルの内容とリンク先は変更されず、存在しないパスへのリンクの先にファイルは作られない。
- **AC-15**: 出力先のディレクトリが存在しない場合と、書き込めない場合、書き出しはエラーになり、出力先のパスには何も作られない。
- **AC-16**: `Title` が空・空白文字だけ・`\n` を含む・`\r` を含む `Article`、`Body` が空・空白文字だけの `Article`、`Model` が空・空白文字だけの `Article`、および `SourceURL` が空の `Article` は、書き出しがエラーになり、出力先のパスには何も作られない。
- **AC-17**: キャンセル済みの `ctx` で書き出すと、`errors.Is(err, context.Canceled)` が真になるエラーになり、出力先のパスには何も作られない。
- **AC-18**: 空のパスで構築するとエラーになる。
- **AC-46**: 出力先のファイルを作成して一部を書き込んだ後に書き込みが失敗する（ディスクの容量不足や I/O エラーなど）と、書き出しはエラーになり、出力先のパスには何も残らない。

#### F-005: CLI 引数と終了コード

CLI の呼び出し形式は `yt2column [フラグ] <動画 URL>` とする。

| フラグ | 意味 |
|---|---|
| `--out <パス>` | 記事を書き出すファイルのパス（F-004）。本タスクでは必須 |
| `--refresh` | キャッシュを無視して `yt-dlp` を実行し、キャッシュを置き換える（`YtDlpSource` の強制再取得） |
| `--keep-cache` | 投稿の成功後も、その動画のキャッシュを削除しない（F-006） |
| `--system-prompt <パス>` | system プロンプトのテンプレートの上書きファイル（`ArticleWriter` の構築時に渡す） |
| `--user-prompt <パス>` | user プロンプトのテンプレートの上書きファイル（同上） |
| `-h`・`--help` | 使い方を表示して終了する |

-   位置引数（動画 URL）はちょうど 1 つとする。フラグは動画 URL より前に置く。
-   `--out` を必須にするのは、本タスクの投稿先がファイルだけだからである。Slack を投稿先に加えるときに、`--out` を省いた場合の扱いを #7 で決める。
-   終了コードは次のとおりとする。
    -   `0`: 投稿（ファイルへの書き出し）に成功した。キャッシュの掃除や削除の失敗による警告（F-006）があっても `0` とする。`-h`・`--help` も `0` とする。
    -   `1`: 実行中の失敗（字幕の取得・記事の生成・投稿の失敗、同時実行の検出（F-007）、中断）。
    -   `2`: 使い方の誤りまたは設定の誤り（引数の誤り、動画 URL の形式の誤り、環境変数の誤り、各段階の構築の失敗（テンプレートの上書きファイルの誤りを含む））。
-   終了コード `2` になる誤りは、同時実行の排他の取得、キャッシュの掃除、`yt-dlp` の起動、LLM API の呼び出しのいずれよりも前に検出する。動画 URL の形式も、この時点で `YtDlpSource` が受理するのと同じ規則（`transcript` パッケージの動画 URL の検証。現在は非公開の `validateVideoURL`）で検証する。規則を CLI 側で複製せずに共有する手段は `02_architecture.md` で決める。
-   エラーと警告は標準エラー出力に書く。標準出力には、`-h`・`--help` の使い方のほかは何も書かない。

##### 実行経路の一覧

CLI の出力と副作用に関する保証（本節の終了コードと標準出力、F-006 のキャッシュの扱い、F-008 の出力に含めない値とエスケープ）は、次のすべての実行経路で成り立つ。各 AC が「実行経路の一覧」と書く場合は、この表を指す。

| 経路 | 終了コード |
|---|---|
| 成功 | `0` |
| `-h`・`--help` | `0` |
| 引数の誤り（AC-20 の引数・フラグ・動画 URL の誤り） | `2` |
| 環境変数の誤り（F-001 の拒否のいずれか） | `2` |
| `LLMClient` の構築の失敗（例: `YT2COLUMN_MODEL` の前後に空白がある。F-001 は受理し、`deepseek.New` が拒否する（F-003）） | `2` |
| テンプレートの構築の失敗（存在しない `--system-prompt`・`--user-prompt` のパス、`ArticleWriter` の構築で拒否されるテンプレート） | `2` |
| 字幕の取得の失敗 | `1` |
| 記事の生成の失敗 | `1` |
| 投稿の失敗 | `1` |
| 掃除または削除の失敗による警告（投稿は成功） | `0` |
| キャッシュディレクトリの作成または排他の取得の失敗（同時実行以外の理由。F-007） | `1` |
| 同時実行の検出（F-007） | `1` |
| 実行中の SIGINT（F-006） | `1` |
| 実行中の SIGTERM（F-006） | `1` |

**Acceptance Criteria**:
- **AC-19**: 有効な環境と `--out <存在しないパス> <有効な動画 URL>` で実行し、各段階が成功すると、終了コードは `0` で、`--out` のパスに記事が書き出される。
- **AC-20**: 次の呼び出しは、終了コード `2` になり、標準エラー出力に誤りの内容を書く。いずれの場合も、排他のためのファイル（F-007）を作らず、キャッシュディレクトリを変更せず、`yt-dlp` を起動せず、LLM API を呼ばない。
    -   動画 URL がない、動画 URL が 2 つある、動画 URL の後にフラグがある
    -   未定義のフラグ
    -   `--out` がない
    -   動画 URL の形式が不正（例: `https://example.com/watch?v=dQw4w9WgXcQ`、`https://www.youtube.com/watch?v=short`、`--` の後に置いた `-rf`）。`--` を付けない `-rf` は未定義のフラグとして拒否されるため、URL の形式の検証を確かめる入力にはならない。
    -   環境変数の誤り（F-001 の拒否のいずれか）。このとき、標準エラー出力には変数の名前が現れ、値は現れない。
    -   `YT2COLUMN_MODEL` の前後に空白がある（F-001 は受理し、`LLMClient` の構築で拒否される）
    -   存在しない `--system-prompt` または `--user-prompt` のパス、`ArticleWriter` の構築で拒否されるテンプレート
- **AC-21**: `-h` または `--help` で実行すると、終了コード `0` で、標準出力に使い方を書く。使い方は F-005 の表のすべてのフラグを含む。環境変数が未設定でも同じである。
- **AC-22**: `--system-prompt`・`--user-prompt` に与えたファイルの内容から組み立てたプロンプトが、`LLMClient` に渡る（fake の `LLMClient` が受け取ったプロンプトで確認する）。
- **AC-23**: 字幕の取得・記事の生成・投稿のいずれかが失敗すると、終了コードは `1` で、標準エラー出力のメッセージは失敗した段階（`pipeline.StageError` の段階名）を含む。
- **AC-44**: 実行経路の一覧のすべての経路で実行し、経路ごとに次をすべて確認する。
    -   (a) 終了コードが一覧の値である。
    -   (b) 標準出力は、`-h`・`--help` の経路を除いて空である。
    -   (c) 秘密情報の値もその末尾 8 文字も現れない（AC-38）。
    -   (d) 信頼できない文字列の制御文字がそのままの形で現れない（AC-39。成功の経路では `Model`・`ModelVersion`、失敗の経路では `yt-dlp` の標準エラー出力と LLM のエラーのメッセージ）。
    -   (e) 終了コード `2` の経路では、排他のためのファイル（F-007）を作らず、キャッシュディレクトリを変更せず、`yt-dlp` を起動せず、LLM API を呼ばない（AC-20 と同じ基準）。
    -   (f) 終了コード `1` の経路（失敗・同時実行の検出・SIGINT・SIGTERM）では、`--out` のパスには何も作られず、その動画のキャッシュは削除されない。

#### F-006: 実行の流れとキャッシュの後始末

使い方と設定の検証（F-005）を通った後、CLI は次の順に処理する。

1.  キャッシュディレクトリが存在しなければ、パーミッション `0o700` で作成する（既存のディレクトリのパーミッションは変更しない）。そのうえで、同じキャッシュディレクトリに対する排他を取得する（F-007）。
2.  キャッシュの掃除（`PruneCache`）を呼ぶ。掃除の失敗は標準エラー出力への警告にとどめ、処理を続ける。掃除は残った不要なエントリを削除するだけで、有効なキャッシュには触れないため、失敗しても後続の処理の正しさに影響しない（[cache_consistency.md](../../dev/cache_consistency.md) §5.2）。
3.  パイプラインを実行する（字幕の取得 → 記事の生成 → 投稿）。`--refresh` を指定した場合は、`YtDlpSource` を強制再取得の指定で構築する。
4.  投稿に成功し、`--keep-cache` を指定していない場合は、その動画のキャッシュを削除する（`RemoveCache`）。削除の失敗は標準エラー出力への警告にとどめ、終了コードは `0` とする。投稿は既に完了しており、残ったキャッシュは次の同じ動画の実行で再利用されるだけだからである。
5.  投稿に成功した場合、標準エラー出力に、出力先のパス、`Article.Model`、`Article.ModelVersion` を書く（F-008）。

-   掃除を実行の開始時に呼ぶのは、前の実行が中断で残したエントリを、今回の実行の成否によらず回収するためである。
-   いずれかの段階が失敗した場合は、キャッシュを削除しない。記事の生成や投稿の失敗後の再実行で、`yt-dlp` を再び起動せずに済むようにするためである（[project_overview.md](../../dev/project_overview.md)「前提・制約」）。
-   投稿の完了前に SIGINT または SIGTERM を受けた場合は、実行中の段階に渡した `context` をキャンセルし、キャッシュを削除せずに終了コード `1` で終了する。`yt-dlp` の実行中に受けた場合は、CLI の終了後に `yt-dlp` のプロセスを残さない。投稿の完了後（手順 4・5）に受けた場合は、キャッシュの削除は、行わなくても途中で中断してもよい。いずれの場合も、投稿は完了しているため終了コードは `0` とする（F-005）。

**Acceptance Criteria**:
- **AC-24**: 字幕のキャッシュが揃った動画を、`--keep-cache` を付けずに実行して成功すると、終了コード `0` で、その動画のキャッシュのエントリはキャッシュディレクトリに残らない。キャッシュディレクトリの他の動画の有効なキャッシュは残る。
- **AC-25**: 同じ条件で `--keep-cache` を付けて実行して成功すると、その動画のキャッシュは残る。続けて、起動されたことを記録する偽の `yt-dlp`（以下、トリップワイヤ）を `YT2COLUMN_YTDLP_PATH` に指定して同じ動画で再実行すると、成功し、トリップワイヤは起動されない。
- **AC-26**: 字幕の取得には成功し、記事の生成または投稿が失敗した実行では、終了コード `1` で、その動画のキャッシュは残る。続けてトリップワイヤを指定して同じ動画で再実行すると、トリップワイヤは起動されない。
- **AC-27**: 実行の開始時に、別の動画の dangling なエントリ（例: ポインタのない `<動画 ID>.b` のスロット）をキャッシュディレクトリに置いておくと、実行後にそのエントリは削除されている。後続の段階が失敗する実行でも同じである。
- **AC-28**: 掃除が失敗する条件で実行すると、標準エラー出力に警告を書き、パイプラインは実行され、成功すれば終了コードは `0` である。
- **AC-29**: 投稿に成功した後にキャッシュの削除が失敗する条件で実行すると、標準エラー出力に警告を書き、終了コードは `0` で、`--out` のファイルは残る。
- **AC-30**: 字幕のキャッシュが揃った動画を、`--refresh` を付けて実行すると、`yt-dlp`（テストではキャッシュに置いた内容と異なる字幕を出力する偽の `yt-dlp`）が起動され、記事の生成には新しく取得した字幕が使われる。
- **AC-31**: 字幕の取得、記事の生成、投稿のそれぞれの実行中にプロセスの中断（テストでは `context` のキャンセル）が起きると、終了コード `1` で、その動画のキャッシュは削除されず、`--out` のパスには何も作られない。この確認は各段階での中断の扱いを対象とし、実際のシグナルの受信（AC-45）の確認には代えない。
- **AC-45**: 実行中の CLI のプロセスに、`yt-dlp`（テストでは字幕の取得の途中で止まる偽の `yt-dlp`）の実行中に実際の SIGINT を送ると、終了コード `1` で終了し、AC-44 の (f) を満たし、CLI の終了後に `yt-dlp` のプロセスが残っていない。SIGTERM でも同じである。
- **AC-32**: 実装計画書に、日本語字幕のある実際の動画 1 本に対する CLI の手動実行を完了条件として含める。手動実行では、その動画の URL で CLI を実行し、記事が `--out` のファイルに書き出されることを確かめる。使用した動画 URL と結果を実装計画書に記録する。
- **AC-33**: 実装計画書に、キャッシュが揃った実際の動画 1 本に対する `--refresh` 付きの CLI の手動実行を完了条件として含める。手動実行では、`yt-dlp` が再実行されることを、`yt-dlp` の出力やキャッシュのスロットの切り替わりで確かめる。使用した動画 URL と結果を実装計画書に記録する。

#### F-007: 同時実行の排他

同じキャッシュディレクトリに対して CLI を同時に実行すると、一方の掃除が他方の書き込み中のエントリを削除しうる（[cache_consistency.md](../../dev/cache_consistency.md) P1）。cron などで実行が重なる場合に備え、利用者への注意にとどめず、CLI が排他する。

-   排他は、キャッシュディレクトリごとに取得する。異なるキャッシュディレクトリを使う実行は互いを妨げない。
-   排他を取得できない場合（同じキャッシュディレクトリを使う別の実行が進行中の場合）は、待たずに、終了コード `1` で終了する。エラーは同時実行を検出したことを示し、`errors.Is` で判別できる番兵エラーで報告する。このとき、キャッシュの掃除、`yt-dlp` の起動、LLM API の呼び出し、`--out` のファイルの作成のいずれも行わない。
-   キャッシュディレクトリの作成、または排他の取得が、同時実行以外の理由（親ディレクトリを作成できない、権限がない、I/O エラーなど）で失敗した場合も、終了コード `1` で終了し、キャッシュの掃除、`yt-dlp` の起動、LLM API の呼び出し、`--out` のファイルの作成のいずれも行わない。このエラーは同時実行の番兵エラーとは区別し、`errors.Is` で同時実行と判別されない。利用者が「別の実行が進行中」と誤解しないようにするためである。
-   排他は、プロセスが異常終了した場合（SIGKILL を含む）にも、利用者の手作業なしに解放される。残った排他のために後の実行がいつまでも失敗することはない。
-   排他のためにキャッシュディレクトリにファイルを置く場合、そのファイルは掃除と削除の対象にならず、掃除と削除もそのファイルを誤って扱わない（[security.md](../../dev/security.md) §5 の命名規則と一致しない名前にする）。

**Acceptance Criteria**:
- **AC-34**: 1 つ目の実行が排他を保持している間（テストでは、字幕の取得の途中で止まる偽の `yt-dlp` で実行を保持する）に、同じキャッシュディレクトリで 2 つ目の実行を始めると、2 つ目は待たずに終了コード `1` で終了し、同時実行の番兵エラーを報告する。2 つ目の実行は、キャッシュディレクトリを変更せず、`yt-dlp` を起動せず、LLM API を呼ばず、`--out` のファイルを作らない。
- **AC-35**: 1 つ目の実行が排他を保持している間でも、別のキャッシュディレクトリを使う実行は成功する。
- **AC-36**: 排他を保持したプロセスを SIGKILL で終了させた後、同じキャッシュディレクトリで実行すると、排他を取得でき、成功する。
- **AC-37**: 排他のためのファイルがキャッシュディレクトリにある状態で掃除を行っても、そのファイルは削除されず、掃除はエラーを報告しない。
- **AC-47**: 次の条件で実行すると、終了コード `1` で終了し、エラーは同時実行の番兵エラーに対して `errors.Is` が偽である。いずれの場合も、`yt-dlp` を起動せず、LLM API を呼ばず、`--out` のファイルを作らない。
    -   `YT2COLUMN_CACHE_DIR` の親ディレクトリが通常のファイルであり、キャッシュディレクトリを作成できない。
    -   キャッシュディレクトリは存在するが、書き込みの権限がなく、排他のためのファイルを作成できない（排他の仕組みがファイルを必要とする場合）。

#### F-008: 出力に含めない値と、信頼できない値の表示

-   API キーと Webhook URL の値（またはその一部）は、標準出力・標準エラー出力・`--out` のファイルのいずれにも書かない。F-005 の実行経路の一覧のすべての経路で同じである。
-   成功時に表示する `Article.Model` と `Article.ModelVersion` は、LLM プロバイダが返した信頼できない値である。端末の表示を変える制御文字などがそのまま出力されないよう、エスケープして表示する（手段は設計で決める）。エラーのメッセージに含まれうる、外部から得た文字列（`yt-dlp` の標準エラー出力、LLM API のエラーのメッセージなど）も同様とする。

**Acceptance Criteria**:
- **AC-38**: `DEEPSEEK_API_KEY` と `SLACK_WEBHOOK_URL` に特徴的な値を設定し、F-005 の実行経路の一覧の各経路で実行すると、標準出力・標準エラー出力・`--out` のファイルのいずれにも、どちらの値も、その末尾 8 文字も現れない。記事の生成の失敗の経路には、fake の `LLMClient` が返すエラーのメッセージに API キーを含む場合を含める。
- **AC-39**: 信頼できない文字列にエスケープシーケンス（`\x1b[2J` など）と改行を含めて実行すると、標準エラー出力にはそれらの制御文字がそのままの形では現れない。次の各経路で確認する。
    -   成功: fake の `ArticleWriter` が、`Model` と `ModelVersion` にこれらを含む `Article` を返す。実物の `ArticleWriter` は制御文字を含む `Model`・`ModelVersion` を拒否する（#5）ため、この確認には fake を使う。
    -   字幕の取得の失敗: 偽の `yt-dlp` が、標準エラー出力にこれらを書いて失敗する。改行は、偽の行（たとえば成功やエラーを装う行）を始めるものとする。
    -   記事の生成の失敗: fake の `LLMClient` が、メッセージにこれらを含むエラーを返す。

#### F-009: testdata からファイル出力までの統合テスト

YouTube にアクセスせず、testdata の字幕から、実際の DeepSeek API で記事を生成し、ファイルに書き出すまでを、CLI と同じ組み立てで通しで実行する統合テストを設ける。

-   テストは `//go:build integration` のビルドタグを持ち、`make test` と CI では実行しない。専用の make のターゲット（名前は設計で決める）だけが、オプトインの環境変数（名前は設計で決める。[design_handoff.md](design_handoff.md) H-01）を値 `1` でエクスポートして実行する。オプトインの変数の値がちょうど `1` のときだけ実行し、それ以外（未設定、空、`0`、`true` など）の場合はスキップする。これは、実 API を呼ぶ統合テストの既存の取り決め（[security.md](../../dev/security.md) §2）に従い、`go test -tags integration ./...` や IDE からの実行で料金が発生しないようにするためである。
-   API キーは、テスト専用の環境変数 `YT2COLUMN_TEST_DEEPSEEK_API_KEY` からだけ読む。本番の `DEEPSEEK_API_KEY` は読まない。テストは、この値を CLI の組み立てに与える環境の `DEEPSEEK_API_KEY` として渡し、プロセスの環境変数は変更しない。オプトインの変数があってテスト用の API キーがない場合は、スキップせずに失敗する。
-   モデル名は `YT2COLUMN_MODEL` から読み、make のターゲットは、それが未定義のときだけ `deepseek-flash` を既定値とする（既存の `make test-integration-deepseek` と同じ）。
-   字幕は `testdata/2tcCWM-sRBw.ja.json3` と `testdata/2tcCWM-sRBw.info.json` を使う。テストは、一時ディレクトリをキャッシュディレクトリとし、この 2 ファイルを `YtDlpSource` が有効なキャッシュとして読む配置で置く。字幕の取得はキャッシュから行われ、`yt-dlp` は起動されない。
-   `YT2COLUMN_YTDLP_PATH` にはトリップワイヤを指定し、`yt-dlp` が起動されないことを確認する。
-   CLI の引数の解析から投稿までを、CLI と同じ組み立て（`cmd/yt2column` が使うもの）で実行する。テストが各段階を個別に組み立てたパイプラインでは代えない。
-   統合テストの 1 回の実行で発生する LLM API の呼び出しは 1 回である（確認の方法は [implementation_handoff.md](implementation_handoff.md) I-04）。
-   テストの出力（ログ・失敗メッセージ・スキップの理由）に、API キーもその一部も書かない。`GODEBUG` が `http2debug=1` または `http2debug=2` を含む場合は、API を呼ぶ前に失敗する（既存の DeepSeek の統合テストと同じ。[security.md](../../dev/security.md) §2）。Go の HTTP/2 の Transport が `Authorization` ヘッダーの API キーを標準エラー出力に記録するためである。

**Acceptance Criteria**:
- **AC-40**: 統合テストは、環境に応じて次のように振る舞う。
    -   オプトインの変数が未設定、または値が `1` 以外（空、`0`、`true`、` 1` など）の環境では、スキップし、DeepSeek API を呼ばない。
    -   オプトインの変数の値が `1` で、`YT2COLUMN_TEST_DEEPSEEK_API_KEY` がない環境では、API を呼ばずに失敗する。本番の `DEEPSEEK_API_KEY` だけが設定されている環境でも、それを使わない。
    -   オプトインの変数の値が `1` で、`GODEBUG` が `http2debug=1` または `http2debug=2` を含む環境では（他の設定と並んでいる場合を含む）、API を呼ばずに失敗する。失敗のメッセージに API キーもその一部も書かない。
- **AC-41**: make のターゲットで実行すると、次をすべて確認して成功する。
    -   CLI の組み立ての終了コードが `0` である。
    -   トリップワイヤが起動されていない。
    -   `--out` のファイルが作られ、空でないタイトルの見出しと本文、出典リンク `https://www.youtube.com/watch?v=2tcCWM-sRBw`、空でないモデル名を含む。
    -   `--keep-cache` を付けていないので、`2tcCWM-sRBw` のキャッシュのエントリがキャッシュディレクトリに残っていない。
    -   AC-38 と同じ基準で、テスト用の API キーの値もその末尾 8 文字も、標準出力・標準エラー出力・`--out` のファイル、およびテストの出力（ログ・失敗メッセージ・スキップの理由）のいずれにも現れない。
- **AC-42**: 統合テストは `make lint`（`go vet -tags integration`）でコンパイルされ、`make test` では実行されない。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   CLI 自身の処理（設定の読み込み、排他、掃除、ファイルの書き出し）は、`yt-dlp` と LLM API の呼び出しに比べて無視できる時間で終わればよい。性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。

### 4.2. セキュリティ (Security)
-   秘密情報は `internal/config` だけが環境変数から読み、`secret.Secret` で保持する（F-001・F-002）。値はどの出力にも書かない（F-008）。
-   `yt-dlp` に引き継ぐ環境変数は既存の allowlist のままとし、本タスクで秘密情報を引き継ぐ経路を作らない。
-   キャッシュディレクトリは `0o700` で作成する（[security.md](../../dev/security.md) §5）。
-   信頼できない文字列を端末に表示するときはエスケープする（F-008）。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   `yt-dlp` と LLM API の呼び出しには固定のタイムアウトを設定する（値は `02_architecture.md` で決める）。
-   失敗時に不完全な記事のファイルを残さない（F-004）。
-   排他は異常終了でも残らない（F-007）。

### 4.4. 互換性 (Compatibility)
-   macOS と Linux で動作すること。Windows は対象外とする（排他の仕組みが OS に依存しうるため）。

### 4.5. 保守性 (Maintainability)
-   プロバイダを追加するときは、プロバイダの列挙値、`internal/config` の検証、ファクトリ関数の分岐、アダプタのパッケージを追加すれば済み、`ArticleWriter`・パイプライン・CLI の引数の処理を変更せずに済むこと。
-   CLI の処理（引数の解析から終了コードの決定まで）は、`main` から分離した関数とし、環境・標準出力・標準エラー出力・各段階の外部との境界（`yt-dlp` のパス、LLM の送信先など）をテストから差し替えられること。F-005〜F-008 のユニットテストは、実 `yt-dlp`・実 LLM API を使わずに行う。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。
-   標準ライブラリだけで実装する（CLI 引数は `flag`）。外部のモジュールを追加しない。
-   既存の段階（`YtDlpSource`・`deepseek`・`ArticleWriter`・`pipeline`）の振る舞いは変更しない。本タスクで必要になった変更があれば、`02_architecture.md` で理由とともに示す。
-   [cache_consistency.md](../../dev/cache_consistency.md) の前提（P1 単一ライター）を、F-007 の排他で満たす。キャッシュのコードを変更する場合は、同書の §7 のチェックリストを確認する。
-   統合テストで使う testdata の字幕は、CC BY 3.0 で公開された動画の字幕であり（[testdata/README.md](../../../testdata/README.md)）、生成した記事はテストの一時ディレクトリに書き、リポジトリにコミットしない。

## 6. 用語集 (Glossary)

-   **dangling なエントリ**: キャッシュディレクトリに残った、有効な世代として参照されていないエントリ（中断した書き込みのスロットなど）。[cache_consistency.md](../../dev/cache_consistency.md) を参照。
-   **掃除**: `YtDlpSource.PruneCache`。キャッシュディレクトリ内のすべての動画の dangling なエントリを削除する。
-   **キャッシュの削除**: `YtDlpSource.RemoveCache`。1 つの動画のキャッシュのエントリを、有効なものも含めてすべて削除する。
-   **トリップワイヤ**: テストで `yt-dlp` の代わりに指定する実行ファイル。起動されたことを記録し、起動されてはならないことを確認するために使う。
-   **空白文字**: Unicode の空白文字（Go の `unicode.IsSpace` が真になる文字）。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
