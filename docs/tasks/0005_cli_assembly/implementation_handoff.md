## I-01: 環境変数を読む標準ライブラリの関数の走査範囲

-   **事項:** AC-09 の走査は、プロセスの環境変数を読む標準ライブラリの関数をすべて対象にする必要がある。`os.Getenv`・`os.LookupEnv`・`os.Environ` だけでなく、`os.ExpandEnv`（内部で `os.Getenv` を呼ぶ）、`syscall.Getenv`・`syscall.Environ` なども含む。
-   **理由:** 対象を一部の関数に限ると、たとえば利用者が与えたパスを `os.ExpandEnv` で展開するコードは、`$DEEPSEEK_API_KEY` を含むパスから秘密情報を `internal/config` の外で読める。このコードは変数名の文字列を直接書かないため、秘密情報の変数名の文字列の検査も通り抜ける。
-   **方法の候補:** テストの中で対象の関数を列挙し、なぜその関数が対象か（内部で環境変数を読むこと）をコメントで示す。あるいは、`depguard` や `forbidigo` などの lint の規則で、許可した場所以外での参照を禁止する。どちらの場合も、対象の関数を 1 つ外すと失敗することを、実装を壊して確かめる。
-   **関連:** F-002・AC-09

## I-02: 実際のシグナルを CLI のプロセスに送るテストの組み立て

-   **事項:** AC-45 と、AC-44 の SIGINT・SIGTERM の経路は、`context` のキャンセルではなく、実行中の CLI のプロセスに実際のシグナルを送って確認する。そのためには、テストが CLI を別のプロセスとして起動し、偽の `yt-dlp` が字幕の取得の途中で止まっていることを確かめてからシグナルを送り、CLI の終了後に偽の `yt-dlp` のプロセスが残っていないことを確かめる必要がある。
-   **理由:** AC-31 の `context` のキャンセルは、シグナルの受信から `context` のキャンセルまでのつなぎ（シグナルの購読の登録漏れ、SIGTERM の扱い漏れなど）と、子プロセスの後始末を通らない。同じプロセス内のテストだけでは、これらが壊れても気づけない。
-   **方法の候補:** テストのバイナリ自身を、環境変数で CLI の処理を実行するモードに切り替えて子プロセスとして起動する（または `go build` した CLI を起動する）。偽の `yt-dlp` は、起動したことと自身の PID をファイルに書いてから待ち続けるスクリプトとし、テストはそのファイルが現れるのを待ってからシグナルを送る。終了後、記録した PID のプロセスが存在しないことを確認する。固定の待ち時間には頼らず、待ちには上限を設ける。シグナルの購読を外すと失敗することを、実装を壊して確かめる。
-   **関連:** F-005・F-006・AC-44・AC-45

## I-03: 書き込みの途中での失敗を起こす手段

-   **事項:** AC-46 は、出力先のファイルを作成して一部を書き込んだ後の書き込みの失敗で、出力先のパスに何も残らないことを確認する。ディスクの容量不足や I/O エラーをテストで実際に起こすのは難しいため、書き込みの途中で失敗させる手段が要る。
-   **理由:** 作成前の失敗（AC-15）やキャンセル（AC-17）だけを確認すると、作成後の失敗で途中まで書いたファイルを消し忘れる実装でも、テストが通る。
-   **方法の候補:** `FilePublisher` の内部に、書き込み先を差し替えられるテスト用の継ぎ目（一定のバイト数を書いた後にエラーを返す書き込み先など）を設ける。あるいは、Linux では `/dev/full` を使う方法もあるが、出力先のパスに既に何かがあると拒否する F-004 の振る舞いと両立しないため、継ぎ目のほうが適する。後始末の処理を外すと失敗することを、実装を壊して確かめる。
-   **関連:** F-004・AC-46

## I-04: 統合テストの LLM API の呼び出しを 1 回に限ることの確認

-   **事項:** F-009 の統合テストでは、LLM API の呼び出しが 1 回でなければならない。テストが CLI の組み立てを 2 回以上実行したり、組み立てにリトライが入ったりすると、AC-40〜AC-42 を満たしたまま、DeepSeek API の料金が複数回分発生しうる。
-   **理由:** 統合テストは実際の API を呼び、料金が発生する。呼び出しの回数は AC-40〜AC-42 の確認項目に含まれないため、回数が増えても失敗しない。
-   **方法の候補:** テストは CLI の組み立てを 1 回だけ実行する。LLM 呼び出しのリトライはスコープ外（#48）であり、組み立てにリトライはない。実装計画は、これをどう確かめるかを定める。たとえば、レビューで確認する、または CLI の差し替えられる LLM の送信先（4.5）を通して要求を数える（実際の DeepSeek API へ中継し、要求の数が 1 であることを確認する）。
-   **関連:** F-009・AC-40・AC-41・AC-42
