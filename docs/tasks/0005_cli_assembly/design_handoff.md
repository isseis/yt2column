## H-01: 統合テストのオプトインの変数と、実行条件の判定の共有

-   **事項:** F-009 の統合テストの実行条件（オプトインの変数の値がちょうど `1`、テスト用の API キーがある、`GODEBUG` が `http2debug=1`・`http2debug=2` を含まない）は、既存の DeepSeek の統合テスト（`internal/llm/deepseek` の `integrationSettingsFrom`）とほぼ同じである。ただし、テスト用の API キーがない場合の扱いが異なる。既存の判定は、オプトインの値が `1` でキーがない場合にスキップするが、AC-40 はこの場合に失敗することを求める。したがって、既存の判定をそのまま共有すると AC-40 を満たせない。設計では次の 3 点を決める。
    -   オプトインの変数を、既存の `YT2COLUMN_DEEPSEEK_INTEGRATION` と共有するか、本タスクの統合テスト専用の変数を設けるか。
    -   実行条件の判定を共有するか、本タスクの統合テストで書き直すか。既存の判定は `internal/llm/deepseek` のテスト用のファイルにある非公開の関数であり、`cmd/yt2column` のテストからは使えない。
    -   共有する場合、キーがない場合の扱い（スキップか失敗か）を呼び出し側が指定する形にするか、既存の DeepSeek の統合テストの扱いも失敗に揃えるか。揃える場合は、既存のテストの振る舞いの変更として理由を示す。
-   **理由:** 判定を 2 か所で別々に書くと、一方だけが変わったとき（たとえば `GODEBUG` の検出の対象を広げたとき）に、もう一方の統合テストが料金の発生する呼び出しや API キーの出力を防げなくなる。変数を共有すると、`make test-integration-deepseek` を意図して設定したオプトインで、より多くの呼び出しを行う本タスクの統合テストも走る。
-   **手段の候補:** オプトインの変数は、実行する make のターゲットと 1 対 1 に対応させるため、本タスク専用のものを設ける。実行条件の判定は、`test` または `integration` のビルドタグでだけビルドされる共有のテスト用パッケージ（例: `internal/testutil/integration`）に移し、変数名とキーがない場合の扱いを引数で受け取る形にして、既存の DeepSeek の統合テストと本タスクの統合テストの両方から使う。キーがない場合の扱いを型（列挙値）で受け取り、文字列の内容から推し量らない（CLAUDE.md「Declare, don't infer」）。
-   **関連:** F-009・AC-40

## H-02: CLI が SIGKILL で終了した後に残る `yt-dlp` と排他

-   **事項:** `internal/transcript` は `yt-dlp` を `exec.CommandContext` で起動するだけで、親プロセスの終了に子プロセスを連動させる仕組みを持たない。CLI が `yt-dlp` の実行中に SIGKILL で終了すると、`yt-dlp` は動き続けうる。排他の解放を CLI の終了だけに結び付けると、次の実行が排他を取得して掃除と字幕の取得を始め、残った `yt-dlp` と同時にキャッシュへ書き込む。[cache_consistency.md](../../dev/cache_consistency.md) P1（単一ライター）が破れ、F-007 が防ごうとした競合が再び起きる。
-   **理由:** 2 つのプロセスが同じファイルに書き込むと、2 回分の取得のバイトが混ざったファイルが、JSON として正しいまま残りうる（同じ `.part` ファイルの続きからの書き込み、同じ名前のファイルへの直接の書き込みなど）。これは厳格な解析では見分けられず（[cache_consistency.md](../../dev/cache_consistency.md) §6「構文として正しいまま中身が変わる破損」と同じ種類）、利用者が気づかないまま壊れたデータから記事を作りうる。検出ではなく、同時の書き込みそのものを防ぐ必要がある。
-   **要件での決定:** 排他を、CLI が起動した `yt-dlp` にも保持させる。`yt-dlp` が終了するまで排他は解放されず、次の実行は同時実行の検出として終了する（F-007、AC-36・AC-49）。
-   **手段の候補:** 排他を `flock` で取る場合、ロックは開いたファイル記述（open file description）に結び付き、それを参照するすべての記述子が閉じるまで解放されない（macOS・Linux とも）。`yt-dlp` を起動するときに排他のファイルの記述子を引き継がせれば（Go では `exec.Cmd.ExtraFiles`）、CLI が SIGKILL されても、`yt-dlp` が終了するまで排他が続く。設計では次を決める、または確かめる。
    -   `internal/transcript` に、`yt-dlp` に引き継ぐファイルを受け取る構築時のオプションを足すこと。既存の段階の変更になるので、`02_architecture.md` に理由を示す（要件書 §5）。`internal/transcript` が排他の意味を知る必要はなく、「子プロセスに引き継ぐファイル」として受け取れば足りる。
    -   `fcntl` のレコードロック（POSIX ロック）は、プロセスに結び付き、引き継いだ記述子では保持されない。`flock` を使うこと。
    -   `yt-dlp` が起動する子プロセス（`deno`・`ffmpeg` など）が記述子を引き継ぐかどうか。Python の `subprocess` は既定で `close_fds=True` なので引き継がないと考えられるが、確かめる。引き継いだ場合も、排他が長く保持されるだけで、安全側に倒れる。
    -   残った `yt-dlp` がネットワークで止まったまま終了しない場合、利用者が止めるまで後の実行は失敗し続ける。同時実行のエラーのメッセージで対処の方法を示す（F-007）。
-   **却下した候補:** `yt-dlp` を独自のプロセスグループで起動し、CLI の終了時にグループごと終了させる方法は、SIGKILL では CLI が後始末を実行できないため防げない。Linux の `Pdeathsig` は macOS にない（4.4 互換性）。防がずに残るリスクとして受け入れ、壊れたキャッシュを検出する方法は、上記の理由で JSON として正しいまま混ざったデータを検出できない。
-   **関連:** F-007・AC-36・AC-49、F-006（`yt-dlp` のプロセスを残さないこと。これは SIGINT・SIGTERM の場合の要件であり、SIGKILL は含まない）

## H-03: `--out` の事前確認の手段と、`FilePublisher` の確認との関係

-   **事項:** F-006 は、手順 1（キャッシュディレクトリの作成と排他の取得）より前に、`--out` のパスに既に何かが存在しないかを best effort で確認し、存在すれば副作用なく終了コード `1` で終了することを求める（AC-50）。設計では、確認の手段（例: `os.Lstat` を使い、シンボリックリンクをたどらずに存在を見る）、確認の途中でエラーになった場合の扱い、確認と `FilePublisher`（F-004）の原子的な確認との関係を決める。
-   **理由:** 事前確認と `FilePublisher` の確認は別の時点で走るため、間に作られたパスは事前確認をすり抜ける。上書き防止の保証は `FilePublisher` の原子的な確認（`O_CREATE|O_EXCL` 相当）に残し、事前確認は費用のかかる処理（`yt-dlp` の起動と LLM API の呼び出し）を避けるためだけに置く。事前確認を排他の取得後に行うと、キャッシュディレクトリを変更しないという早期終了の目的を満たせない。
-   **手段の候補:** 事前確認は存在の確認だけを行い、ファイルを開かない・作成しない（利用者の指定により、作成できることの保証までは要らない）。確認の途中でエラーになった場合は、存在すると決めつけず、早期の拒否を行わない。`FilePublisher` の確認と重複するコードを共有できるかは設計で検討する。
-   **関連:** F-004・F-006・AC-50
