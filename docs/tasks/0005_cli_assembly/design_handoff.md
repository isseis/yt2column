# 設計への申し送り：CLI の組み立て

## 本書の位置づけ

[01_requirements.md](01_requirements.md) の作成とレビューの過程で挙がった事項のうち、要件（観測できる振る舞い）ではなく、設計の段階で決める事項をまとめる。

-   本書は承認対象の文書ではない。設計の作成時に参照し、項目を追加してよい。
-   テストの組み立て方など、実装計画で扱う事項は [implementation_handoff.md](implementation_handoff.md) に申し送る。

## H-01: 統合テストのオプトインの変数と、実行条件の判定の共有

-   **事項:** F-009 の統合テストの実行条件（オプトインの変数の値がちょうど `1`、テスト用の API キーがある、`GODEBUG` が `http2debug=1`・`http2debug=2` を含まない）は、既存の DeepSeek の統合テスト（`internal/llm/deepseek` の `integrationSettingsFrom`）とほぼ同じである。ただし、テスト用の API キーがない場合の扱いが異なる。既存の判定は、オプトインの値が `1` でキーがない場合にスキップするが、AC-40 はこの場合に失敗することを求める。したがって、既存の判定をそのまま共有すると AC-40 を満たせない。設計では次の 3 点を決める。
    -   オプトインの変数を、既存の `YT2COLUMN_DEEPSEEK_INTEGRATION` と共有するか、本タスクの統合テスト専用の変数を設けるか。
    -   実行条件の判定を共有するか、本タスクの統合テストで書き直すか。既存の判定は `internal/llm/deepseek` のテスト用のファイルにある非公開の関数であり、`cmd/yt2column` のテストからは使えない。
    -   共有する場合、キーがない場合の扱い（スキップか失敗か）を呼び出し側が指定する形にするか、既存の DeepSeek の統合テストの扱いも失敗に揃えるか。揃える場合は、既存のテストの振る舞いの変更として理由を示す。
-   **理由:** 判定を 2 か所で別々に書くと、一方だけが変わったとき（たとえば `GODEBUG` の検出の対象を広げたとき）に、もう一方の統合テストが料金の発生する呼び出しや API キーの出力を防げなくなる。変数を共有すると、`make test-integration-deepseek` を意図して設定したオプトインで、より多くの呼び出しを行う本タスクの統合テストも走る。
-   **手段の候補:** オプトインの変数は、実行する make のターゲットと 1 対 1 に対応させるため、本タスク専用のものを設ける。実行条件の判定は、`test` または `integration` のビルドタグでだけビルドされる共有のテスト用パッケージ（例: `internal/testutil/integration`）に移し、変数名とキーがない場合の扱いを引数で受け取る形にして、既存の DeepSeek の統合テストと本タスクの統合テストの両方から使う。キーがない場合の扱いを型（列挙値）で受け取り、文字列の内容から推し量らない（CLAUDE.md「Declare, don't infer」）。
-   **関連:** F-009・AC-40

## H-02: CLI が SIGKILL で終了した後に残る `yt-dlp` と排他

-   **事項:** `internal/transcript` は `yt-dlp` を `exec.CommandContext` で起動するだけで、親プロセスの終了に子プロセスを連動させる仕組み（プロセスグループ、Linux の `Pdeathsig` など）を持たない。CLI が `yt-dlp` の実行中に SIGKILL で終了すると、`yt-dlp` は動き続けうる。一方、F-007 は異常終了後に排他が解放されることを求め（AC-36）、次の実行はすぐに排他を取得して掃除と字幕の取得を始める。このとき、残った `yt-dlp` が同じ動画のスロットに書き込み続けると、[cache_consistency.md](../../dev/cache_consistency.md) P1（単一ライター）が破れ、F-007 が防ごうとした競合が再び起きうる。設計では、この状況を防ぐか、残るリスクとして受け入れるかを決める。
-   **理由:** 排他の解放を、排他を取得したプロセス（CLI）の終了だけに結び付けると、そのプロセスが起動した子プロセスの書き込みは排他の外に出る。受け入れる場合の根拠として、残った `yt-dlp` が書くのはその動画の固定の名前のファイルだけであること、壊れた json3・info.json は読み込み時の厳格な検査で拒否され記事にならないことが挙げられる。ただし、`yt-dlp` のタイムアウトは CLI の `context` によるもので、CLI が SIGKILL されると効かない。残った `yt-dlp` が動き続ける時間に上限はない。ただし、掃除が残った `yt-dlp` の書き込み中のスロットを削除する場合の結果は [cache_consistency.md](../../dev/cache_consistency.md) §6 の保証の外にある。
-   **手段の候補:**
    -   排他を子プロセスにも保持させる（排他のファイルの記述子を `yt-dlp` に引き継ぎ、すべての保持者が終了するまで解放されないようにする）。この場合、次の実行が排他を取得できるのは残った `yt-dlp` の終了後になる。AC-36 は SIGKILL の直後に取得できることを求めているので、要件の文言の見直しが必要になる。
    -   `yt-dlp` を独自のプロセスグループで起動し、CLI の終了時にグループごと終了させる。ただし、SIGKILL では CLI 自身が後始末を実行できないため、これだけでは防げない。Linux の `Pdeathsig` は macOS にない（4.4 互換性）。
    -   防がずに、残るリスクとして受け入れ、その根拠を `02_architecture.md` と [cache_consistency.md](../../dev/cache_consistency.md) §6 に記す。
-   **関連:** F-007・AC-36、F-006（`yt-dlp` のプロセスを残さないこと。これは SIGINT・SIGTERM の場合の要件であり、SIGKILL は含まない）
