## 1. 概要 (Overview)

**目的:** 本書は、chief（`/chief` のコマンドの定義（以下、定義）と、Go の開発用の道具 `chief`）の今の仕様を 1 か所にまとめる開発者向けの文書 `chief_architecture.md` の要件を定義する。あわせて、chief のプロトコル番号を上げる基準を定める。

**背景:**

chief の文書は、今は次のように分かれている。

-   **使う人向けのガイド:** `docs/dev/guides/chief_guide.md`。サブコマンドの表と終了コードの表（`docs/dev/guides/chief_guide.md:165-189`）、状態のディレクトリの表（同 `:232-250`）を持つ。細部は 0088 と 0092 の設計書へ案内している（同 `:167`）。
-   **決定:** [ADR-0046](../../dev/adr/0046-chief-of-staff.md)。構成と拒む呼び出しの一覧は 0088 と 0092 の設計書の節を指している（`docs/dev/adr/0046-chief-of-staff.md:160`・`:175`）。
-   **パッケージの一覧:** `docs/dev/conventions/package_reference.md` の `cmd/chief`・`internal/chief`・`internal/chief/paneinput` の行（`docs/dev/conventions/package_reference.md:116`・`:122`・`:123`）。設計は 0088・0092・0093 の設計書を指している。
-   **各タスクの設計書:** chief を変えたタスクの `02_architecture.md` は 10 本あり（0088・0092・0093・0095・0097・0102・0103・0105・0110・0113）、計 5,909 行である（issue は約 7,200 行と見積もっている）。取り下げたタスク 0096 の設計書は、`main` の振る舞いに入っていないので数えない。

今の chief がどう動くかをまとめた開発者向けの文書はない。そのため、次の 3 つの不便がある。

-   **今の仕様のまとめがない。** `internal/chief` を変える開発者は、設計書を時系列で読み、後のタスクで上書きされた部分を自分で差し引く必要がある。CLAUDE.md の「Design decisions (ADR)」は、`docs/dev/security.md` や `docs/dev/production_profile.md` のような「今の仕様を持つ文書」を ADR とは別に置くとしているが、chief にはそれがない。
-   **全体の構成図がない。** `/chief` の定義（`.claude/commands/chief.md`）、道具 `chief`、Herdr・git・gh、状態のディレクトリ、作業する側のエージェントの pane の関係と、信頼の境界を一度に見られる図がない。
-   **プロトコル番号を上げる基準がない。** chief のプロトコル番号は `internal/chief/records.go:29` の `const Protocol = 6` で、`/chief` の定義が `--protocol` で渡す（`.claude/commands/chief.md:58-62`）。番号の決め方とマージの時点の確かめは CLAUDE.md の「Protocol numbers」と [0099 要件定義書](../0099_protocol_number_rule/01_requirements.md) にあるが、どの変更で上げるかは 0099 の範囲の外である（`docs/tasks/0099_protocol_number_rule/01_requirements.md:98`）。各タスクの判断は、次のように分かれてきた。
    -   出力の JSON を変えたので上げた（`docs/tasks/0093_chief_status_sheet/02_architecture.md:38`、`docs/tasks/0095_chief_transcript_report/02_architecture.md:504`）。
    -   フラグ `--item` を足したので上げた。ただし、値の組み合わせが変わるだけなら上げる必要はないとした（`docs/tasks/0105_chief_post_merge_next_command/02_architecture.md:406`）。
    -   サブコマンド `reset` を足し、出力の項目にも `reset` の欄を足した（`docs/tasks/0097_chief_reset_offer/02_architecture.md:49`）が、上げなかった。利用者は 1 人で、道具と定義は同じ `main` から入れるためである（`docs/tasks/0097_chief_reset_offer/01_requirements.md:63`）。古い道具は新しい呼び出しを使い方の誤りとして拒み、何も送らないとも述べている（同 `:185`）。
    -   コマンドラインの引数も出力の JSON の形も変わらないので、上げなかった（`docs/tasks/0113_plan_step_reading/01_requirements.md:90-91`）。

    ほかの道具には、それぞれの基準がある。`fixprguard` は、引数・出力・範囲の規則を変えたら上げ、3 つの条件がすべて成り立つときは上げなくてよいとする（`docs/dev/guides/fixprguard_guide.md:587-594`）。`mergepr` は、引数・出力・終了コードの契約を変えたら上げる（`docs/dev/guides/mergepr_guide.md:413`）。

**道具が書き出すもの（今の振る舞い）:**

-   **ログのファイルはない。** 状態のディレクトリに書くのは、記録、ロック、作成の排他のディレクトリである（`docs/dev/guides/chief_guide.md:234-243`）。
-   **状態のディレクトリの外:** `create` は worktree と workspace を作り、`remove` はそれらを消す。pane への入力や `/model` の送信も、外に残る変化である（`docs/dev/guides/chief_guide.md` の 5 章と 8 章、[ADR-0046](../../dev/adr/0046-chief-of-staff.md) の「workspace の作成と削除」）。
-   **標準出力:** 結果の JSON を 1 つ書く（`docs/dev/guides/chief_guide.md:167`）。ただし、使い方の誤り（終了コード `2`）のときは JSON を書かず、標準エラーに理由を書くだけである（`cmd/chief/main.go:164-167`・`:182-185`）。
-   **標準エラー:** 書くのは、使い方の誤りと、結果を書き出せなかったときだけである（`cmd/chief/main.go:166`・`:184`・`:352`・`:356`）。
-   **状態のディレクトリ:** ロック、通知・ラウンド・観測・自動送信の記録、workspace ごとの送信の記録・控え・停止・見送り・作ったことの記録・履歴の記録を書く（`docs/dev/guides/chief_guide.md:234-244`）。

これらについて、どこに何が書かれ、いつ消えるかの説明は、ガイドの表と設計書に分かれている。

対応 issue: [#1055](https://github.com/isseis/yt2column/issues/1055)（関連: [ADR-0046](../../dev/adr/0046-chief-of-staff.md)、[ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md)、タスク [0099](../0099_protocol_number_rule/01_requirements.md)）

**要件定義の際に決めたこと（2026-11-20）:**

-   進め方は通常の進め方にする。対象外の判断は「対象外ではない」で、上書きはない。
    -   ADR: なし（進め方の選択はこのタスクの中で閉じるため）。
    -   **対象外ではない理由:** 文書と文書のガードテストだけを変える。(1) `docs/dev/security.md` の規則と前提を変えない。(2) 開発用ツールの信頼の境界を変えない（道具の振る舞いを変えず、`/chief` の定義には終了コード `2` の案内の一文を足すだけである）。(3) 外部の依存を足さない。
    -   **通常の進め方にする理由:** (1) 10 本の設計書を集める大きな文書になり、章立てと持ち分けを設計の段階で詰める必要がある。(2) 番号を上げる基準は新しい方針で、ADR-0046 の決定を足す。(3) ADR-0046、chief_guide、package_reference と、ガードテストに手が入る。
-   番号を上げる基準の対象は chief だけにする（F-003）。
    -   理由: issue の範囲が chief である。`fixprguard` と `mergepr` には、それぞれの基準がすでにある。4 つの道具の基準をそろえることは別の issue で扱う。
    -   ADR: ADR-0046 を更新する。CLAUDE.md の「Protocol numbers」と ADR-0014 は変えない。
-   基準は「約束を変えたら上げ、3 つの条件がすべて成り立つときだけ上げなくてよい」とする（F-003）。
    -   **約束:** 道具と `/chief` の定義の間の約束とは、サブコマンド、フラグ、出力の JSON の形、定義が読む出力の項目の意味、定義が分岐に使う出力の値、終了コードの意味である。
    -   **3 つの条件:** (1) 古い道具が、新しい定義の呼び出しを使い方の誤り（終了コード `2`）として拒む。(2) 新しい道具が、古い定義の呼び出しを受け付け、同じ形の出力を返す。(3) 古い定義がする呼び出しについて、出力の形、定義が読む項目の意味、定義が分岐に使う値、終了コードの意味が変わらない。
    -   **約束を変えない変更:** 道具の判定を変える PR は、副作用の条件（pane へ送る、自動で送る、workspace と worktree を作る、消す条件）を変えるときだけ上げる。それ以外の判定（状況の表の分類、文書の読み方など）だけを変える PR は、上げない（下の「基準の細部」の判定の項）。
    -   理由: 古い定義と新しい道具の組み合わせが黙って誤ることだけを防ぎ、害のない追加では番号を上げないためである。上げるたびに道具の入れ直しが要り、並行するタスクとの番号の衝突も増える。`fixprguard` の基準の形にそろえる。背景に挙げた判断のうち、0093・0095・0105 は上げる側に、0113 は上げない側にあたる。0097 は出力の項目を足したので、この基準では上げる側にあたる。
    -   採らなかった案: 「約束を変えたら例外なく上げる」（`mergepr` の形）は、害のない追加でも上がる。「黙って誤りうるときだけ上げる」は、そのつどの判断に頼り、今の状態が続く。
    -   ADR: ADR-0046 を更新する。
-   基準の細部を次のように定める（F-003）。レビューで条件の読み方があいまいだと指摘され、人に確かめた。
    -   **条件 (3) の範囲:** 条件 (3) は、古い定義がする呼び出しの出力だけを見る。新しいサブコマンドの出力の形は、条件 (3) を妨げない。定義が分岐に使う項目に新しい値を足すことは、約束の変更にあたる。
        -   理由: 文字どおりに「出力の形が変わらない」と読むと、新しいサブコマンドを足すたびに上げることになり、条件 (1) を置いた意味がなくなる。分岐に使う項目の新しい値は、古い定義が知らない値として誤って扱いうる。
    -   **項目の意味:** 定義が読む出力の項目の意味を変える PR は、上げる。分岐に使う項目も、人に示すだけの項目も含む。
        -   理由: issue が「フィールドの意味」を上げる理由の例に挙げている。人に示すだけの項目でも、古い定義は誤った説明を人に示しうる。判断も単純になる。
    -   **記録の形式:** 状態のディレクトリの記録の形式は、約束に含めない。文書は、その理由を述べる。
        -   理由: 記録は道具だけが読み書きし、`/chief` の定義は読まない。古い版に戻すときの扱いは chief_guide にある（`docs/dev/guides/chief_guide.md:40`）。
    -   **上げない追加に古い道具が当たったとき:** 文書は、人が見ることと戻し方を述べ、`/chief` の定義にも案内を足す（下の「終了コード `2` の案内」）。古い道具は新しいフラグやサブコマンドを、`--protocol` の照合より前に使い方の誤りとして拒む（`cmd/chief/main.go:164-167`）。`/chief` の定義は、終了コード `2` を定義の誤りとして止まって報告する（`.claude/commands/chief.md:85`）。そのため、人は入れ直せば直ることを、その報告からは読めない。
        -   理由: `fixprguard` も、同じ 3 つの条件に、見分け方と入れ直しを文書に書くことを添えている（`docs/dev/guides/fixprguard_guide.md:592`）。
    -   **判定の変更:** 約束を変えずに道具の判定を変える PR は、副作用の条件を変えるときだけ上げる。副作用の条件とは、pane へ入力を送る、自動で送る、workspace と worktree を作る、消す条件である。状況の表の分類や文書の読み方など、それ以外の判定だけを変える PR は上げない。条件 (3) の「定義が読む項目の意味」は、項目が何を表すかの定めのことで、判定の変更で値が出る場面が変わることは含めない。
        -   理由: Fable の部分レビューの指摘を受けて、人に確かめた。`fixprguard` は判定の規則を変えたら上げる（`docs/dev/guides/fixprguard_guide.md:587`、[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）。入れ直しを忘れると、古い道具が古い規則で黙って判定し続けるためである。chief でこの危険が害になるのは、送る・作る・消すといった取り消せない副作用の条件である。表の分類などは人が見て判断するので、古い判定が残っても誤った副作用は起きない。境目を副作用かどうかで決めれば、判断も分かれにくい。
    -   **終了コード `2` の案内:** `/chief` の定義（`.claude/commands/chief.md`）の終了コード `2` の行に、道具が定義より古いこともあり、そのときは `main` から入れ直すよう利用者に促す、という案内を足す。開発者向けの文書にも、人が見ることと戻し方を書く（上の「上げない追加に古い道具が当たったとき」）。
        -   理由: Fable の部分レビューの指摘を受けて、人に確かめた。人は `/chief` の報告を見るので、報告から入れ直しを読めるようにする。案内を足しても、道具と定義の約束は変わらない。
    -   ADR: ADR-0046 を更新する（条件 (3) の範囲、項目の意味、記録の形式、判定の変更）。終了コード `2` の案内は、文書と定義の中身なので ADR にしない。
-   サブコマンドの表と終了コードの表は、chief_guide から chief_architecture.md へ移す（F-004）。chief_guide には使い方とリンクを残す。プロトコル番号の値の表は、入れ直しの手順で使うので chief_guide に残す。
    -   理由: 表は道具の契約で、issue の「細部はこの文書が持つ」に合う。
    -   ADR: なし（文書の置き場所の選択で、このタスクの中で閉じるため）。
-   文書は、chief の契約と構成をこの文書だけで分かるように持つ（F-001・F-002）。持つのは、サブコマンド、フラグ、出力の JSON の項目とその意味、終了コード、状態のディレクトリ・ロック・記録、信頼の境界と入力の型、画面と transcript の読み取りの扱い（範囲は CLAUDE.md へリンクする）である。設計の理由と判定の手順の細部は、設計書と ADR の節へリンクする。
    -   理由: 後のタスクが上書きした部分の差し引きを、読む人に残さないためである。設計書の内容をすべて集めると量が大きく、保守できない。
    -   ADR: ADR-0046 を更新する（下の保守の項にまとめる）。
-   道具が書き出すもの（標準出力、標準エラー、状態のディレクトリの記録）を、出力ごとに文書が持つ（F-002）。持つのは、書く中身、書き出す先、残る期間と消えるとき、信頼できない文字列を含むかである。ログのファイルがないことも書く。状態のディレクトリの外に作るか変えるもの（worktree、workspace、pane への入力）は、それを述べる節へ案内する。
    -   理由: レビュアーの提案による。今は、どこに何が書かれ、いつ消えるかがガイドの表と設計書に分かれていて、障害の調べや記録の片付けのたびに探す必要がある。
    -   ADR: ADR-0046 を更新する（保守の項の、文書が持つ話題に含める）。
-   ガードテストは、今のテストを移すだけにする（F-005）。`TestGuideValuesMatchTool` が今 chief_guide と照らしている値のうち、サブコマンド、終了コード、状態のディレクトリを、chief_architecture.md と照らすように移す。プロトコル番号の値は chief_guide のまま照らす。新しいテストは足さない。
    -   理由: 出力の JSON の項目やフラグを照らすテストは、出力が変わるたびに直す手間がかかり、防ぐ誤りに見合わない（CLAUDE.md の「Document tests」の最後の規則）。
    -   ADR: なし（[ADR-0016](../../dev/adr/0016-document-test-policy.md) を当てはめるだけのため）。
-   chief_architecture.md が述べる事柄（F-002 の話題）を変える PR は、同じ PR で chief_architecture.md を直す（F-006）。この決まりを ADR-0046 の決定と文書の冒頭に書く。決まりは、文書を作る実装の PR がマージされた時から効く。
    -   決まりの範囲: 道具と定義の約束に限らず、画面と transcript の読み取り、記録、書き出すものを変える PR も含む。
    -   理由: 同じ PR で直さなければ、文書はまた古くなり、設計書を読み直すことになる。
    -   ADR: ADR-0046 を更新する。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `internal/chief` と `/chief` の定義を変える開発者が、今の仕様を `chief_architecture.md` から読めるようにする。設計書を時系列で読み、上書きを差し引く必要をなくす。
-   chief のプロトコル番号を上げるかどうかを、決まった基準で判断できるようにする。
-   chief が何をどこへ書き出し、いつ消えるかを、1 か所で分かるようにする。

### 2.2. スコープ (In Scope)

-   `docs/dev/chief_architecture.md` を作る。
-   chief のプロトコル番号を上げる基準、上げる手順、入れ直す順を、その文書に書く。
-   ADR-0046、chief_guide、package_reference から文書へリンクする。重複する表を移す。
-   `cmd/chief/docs_test.go` のガードテストの照合先を移す。
-   ADR-0046 を更新する（本 PR で行う）。

#### F-002: 文書が持つ話題

-   **AC-06**: **定義と道具の契約。** 次を、実装の時点の道具と一致させて持つ。

    -   `--protocol` の照合と、合わないときの振る舞い

-   **AC-07**: **状態のディレクトリ、ロック、記録。** 次を持つ。

-   **AC-09**: **画面と transcript の読み取り。** 次を持つ。

#### F-003: プロトコル番号を上げる基準

文書のプロトコル番号の節に、chief の番号を上げる基準、上げる手順、入れ直す順を書く。

**Acceptance Criteria**:

-   **AC-11**: 節は、約束（サブコマンド、フラグ、出力の JSON の形、定義が読む出力の項目の意味、定義が分岐に使う出力の値、終了コードの意味）を変える PR は番号を上げる、と述べる。定義が分岐に使う項目に新しい値を足すことも約束の変更にあたる、と述べる。
-   **AC-12**: 節は、上げなくてよいのは次の 3 つがすべて成り立つときだけである、と述べる。
    1.  古い道具が、新しい定義の呼び出しを使い方の誤り（終了コード `2`）として拒む。
    2.  新しい道具が、古い定義の呼び出しを受け付け、同じ形の出力を返す。
    3.  古い定義がする呼び出しについて、出力の形、定義が読む項目の意味、定義が分岐に使う値、終了コードの意味が変わらない（新しいサブコマンドの出力の形は、この条件を妨げない）。

    あわせて、約束を変えずに道具の判定を変える PR は、副作用の条件（pane へ送る、自動で送る、workspace と worktree を作る、消す条件）を変えるときだけ上げ、それ以外の判定だけを変えるときは上げない、と述べる。
-   **AC-12a**: 節は、状態のディレクトリの記録の形式は約束に含めないことと、その理由（記録は道具だけが読み書きし、`/chief` の定義は読まない）を述べる。古い版に戻すときの記録の扱いは、それを持つ文書へリンクする。
-   **AC-13**: 節は、基準の当てはめ方を、上げる場合と上げない場合の例で示す。例は少なくとも次の 5 つを含む。
    -   出力の JSON の項目を足す（上げる）
    -   新しいサブコマンドを足し、古い道具がその呼び出しを使い方の誤りとして拒む（上げない）
    -   自動で送る条件を変える（上げる）
    -   状況の表の分類だけを変える（上げない）
    -   定義が人に示すだけの出力の項目の意味を変える（上げる）
-   **AC-14**: 節は、番号を上げる PR が変える場所（道具の `Protocol` の定数、`/chief` の定義の `--protocol`、chief_guide の値の表）を述べる。入れ直す順は、それを持つ chief_guide の 2 章へリンクする。番号の値の決め方とマージの時点の確かめは、CLAUDE.md の「Protocol numbers」と `mergepr_guide.md` へリンクし、繰り返さない。
-   **AC-14a**: 節は、番号を上げない追加に古い道具が当たったときに人が見ることを述べる。古い道具は新しい呼び出しを使い方の誤りとして拒み、`/chief` はそれを定義の誤りとして止まって報告する。あわせて、その報告から、道具が古い場合を見分ける手がかりを述べ、戻し方は chief_guide の入れ直しの手順へリンクする。
-   **AC-14b**: `/chief` の定義の終了コード `2` の行は、道具が定義より古いこともあり、そのときは `main` から入れ直すよう利用者に促す、と述べる。定義の差分は、この案内と F-004 の案内の文の直しに限られる。
-   **AC-15**: ADR-0046 の決定は、AC-11・AC-12 と食い違わない基準の要約を持ち、約束と条件の一覧の置き場所へリンクする。一覧そのものは ADR に写さない（[adr.md](../../dev/conventions/adr.md) の「What 決定 holds」）。

## 6. 用語集 (Glossary)

用語は `docs/translation_glossary.md` と統一する。本書で使う語は次のとおりである。

-   **今の仕様の文書:** ある主題の今の仕様を持つ文書。ADR は決定の要約と理由と経緯を持ち、仕様はこの文書へリンクする（CLAUDE.md の「Design decisions (ADR)」）。
-   **約束（道具と定義の間の）:** サブコマンド、フラグ、出力の JSON の形、定義が読む出力の項目の意味、定義が分岐に使う出力の値、終了コードの意味。状態のディレクトリの記録の形式は含めない。プロトコル番号はこの約束の版を表す。
-   **プロトコル番号:** 道具とそれを呼ぶ文書が `--protocol` で照合する番号（CLAUDE.md の「Protocol numbers」）。
-   **状態のディレクトリ:** chief が記録とロックを置く、リポジトリの外のディレクトリ（`docs/dev/guides/chief_guide.md` の 7 章）。
