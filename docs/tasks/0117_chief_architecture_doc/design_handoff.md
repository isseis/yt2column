# 設計への申し送り（0117）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: 章立てと、chief_guide との線引き

**懸念:** issue #1055 は 7 章の構成を想定し、要件の段階で見直すとした。要件は話題（F-002）だけを定め、章立ては決めていない。chief_guide には、使う人向けの手順と仕様の表が混ざっている。仕様の表は、サブコマンドと終了コード（`docs/dev/guides/chief_guide.md:165-189`）と、状態のディレクトリの記録（同 `:232-250`）である。手順は、送信の停止の解き方、片付け、すべてを消すとき（同 `:246-250`）などである。どこまでを chief_architecture.md へ移し、どこを使い方として残すかで、AC-17 の差分が決まる。

**なぜ重要か:** 線引きがあいまいだと、同じ記録の説明が 2 か所に残り、片方だけが古くなる（F-004）。

**候補:**

-   記録の種類・中身・書くとき・消えるとき（仕様）は chief_architecture.md へ移す。人が行う手順（停止を解く、記録を消す）は chief_guide に残し、仕様へリンクする。
-   issue の 7 章に、「道具が書き出すもの」（AC-08）の節を足す。

**関連:** F-002・F-004、AC-07・AC-08・AC-17・AC-18

## H-02: 出力の JSON の項目の書き方

**懸念:** AC-06 は、出力の JSON の項目とその意味を文書に持つことを求める。出力の型は `internal/chief/output.go` にあり、サブコマンドごとに形が違う。すべての項目を表にすると大きくなり、出力を変える PR のたびに直す量が増える。

**なぜ重要か:** 粒度が細かすぎると保守されず、粗すぎると `/chief` の定義が分岐に使う値が文書から読めない。プロトコル番号の基準（F-003）は、「定義が分岐に使う値」を約束に含めるので、その値は文書から分かる必要がある。

**候補:**

-   共通の項目（`protocol`・`outcome`・`reason` など）と、`/chief` の定義が読む項目と値だけを、サブコマンドごとに表にする。そのほかの項目は、型の doc コメントへ案内する。
-   定義が分岐に使う値には、表で印を付ける。

**関連:** F-002・F-003、AC-06・AC-11

## H-03: CLAUDE.md の Quick Links とほかの索引への登録

**懸念:** CLAUDE.md の「Quick Links」は、`docs/dev/` の直下の文書（`security.md`・`production_profile.md`・`cache_consistency.md`）を挙げている。issue は ADR-0046・chief_guide・package_reference からのリンクだけを求めている。CLAUDE.md の chief の例外の記述や、`docs/dev/project_overview.md` からリンクするかは決めていない。

**なぜ重要か:** 索引にない文書は、開発者に見つけられない。一方、CLAUDE.md は agent の指示であり、足す行は毎回のセッションで読まれる。

**候補:**

-   CLAUDE.md の「Quick Links」に 1 行を足す。足すなら、要件の範囲を広げることになるので人に確かめる。
-   足さず、ADR-0046 と chief_guide からのリンクに任せる。

**関連:** F-004

## H-04: ガードテストの移し方

**懸念:** `TestGuideValuesMatchTool`（`cmd/chief/docs_test.go:503`）は、1 つのテストで、chief_guide のサブコマンドの表・終了コードの表・プロトコル番号・状態のディレクトリを照らしている。AC-20 と AC-21 は、このうち 3 つの照合先を chief_architecture.md に移し、プロトコル番号だけを chief_guide に残すことを求める。テストを 2 つに分けるか、文書のパスを引数にした 1 つの照合にするかは、設計で決める。

**なぜ重要か:** 照合先を移したテストが、移した表を本当に読んでいることを確かめる必要がある。CLAUDE.md の「Every test must be able to fail for its stated reason」に従い、表を壊して失敗することを確かめる。

**候補:**

-   値ごとに照合先の文書を持つ形に書き直す。
-   `TestGuideValuesMatchTool` を、プロトコル番号だけを照らすテストと、chief_architecture.md の 3 つの値を照らすテストに分ける。

**関連:** F-005、AC-20・AC-21

## H-05: 並行するタスクの変更との順序

**懸念:** タスク 0115（マージコンフリクトの解消）は要件が承認済みで、設計がまだである（`docs/tasks/0115_chief_conflict_resolution/01_requirements.md`）。0115 は、出力の形とプロトコル番号を変えうる（`docs/tasks/0115_chief_conflict_resolution/design_handoff.md` の H-10）。0117 の実装の前後どちらで 0115 がマージされるかで、文書が書く振る舞いが変わる。

**なぜ重要か:** 0117 が先にマージされ、0115 がこの文書を直さないと、文書はすぐに古くなる。F-006 の決まりは、0117 がマージされた後の PR にだけ効く。

**候補:**

-   0117 の実装は、実装の時点の `origin/main` の振る舞いを書く。0115 が後にマージされる場合に備えて、0115 の設計にこの文書を直す項目があるかを、0117 の実装の PR で確かめる。
-   0115 が先にマージされたら、0117 の実装の PR で `main` を取り込み、文書に反映する。

**関連:** F-001・F-006、AC-03
