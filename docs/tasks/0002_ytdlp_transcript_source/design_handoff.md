# 設計への申し送り：yt-dlp による字幕取得

## 本書の位置づけ

[01_requirements.md](01_requirements.md) の作成とレビュー（PR #33）の過程で挙がった事項のうち、要件（観測できる振る舞い）ではなく、設計・実装の段階で決める、または注意すべき事項をまとめる。

-   要件書は「何を受理し、何をどの番兵で拒否し、キャッシュがどう変わるか」だけを定める。本書の項目は、その振る舞いを実現する手段の候補と、レビューで判明した落とし穴である。
-   `02_architecture.md` は、本書の各項目について、採用した手段または扱わない理由を記録する（要件書 §5）。本書の手段は候補であり、設計で別の手段を選んでもよい。ただし、対応する AC を満たすこと。
-   本書は承認対象の文書ではない。設計の作成時に参照し、項目を追加してよい。

## H-01: 子プロセスの環境変数を nil にしない

-   `exec.Cmd.Env` が nil の場合、子プロセスは親の環境をすべて引き継ぐ。allowlist の変数を nil のスライスに `append` して組み立てると、allowlist の変数が 1 つも設定されていない環境では `Env` が nil のままになり、`DEEPSEEK_API_KEY` などが子プロセスへ漏れる。
-   候補: 空の（非 nil の）スライスから組み立てる（例: `make([]string, 0, n)`）。
-   AC-44 の「allowlist の変数が 1 つもない環境」のケースがこれを検出する。

## H-02: `yt-dlp` のオプション列と出力先の渡し方

-   要件レビュー時点のオプション列の案: `--ignore-config --no-plugin-dirs --skip-download --write-subs --write-auto-subs --sub-langs ja --sub-format json3 --write-info-json`、出力先の指定、`--`、正規化 URL。最終的な列は事前調査の結果とあわせて設計で固定する。
-   `yt-dlp` は `-o` の値を出力テンプレートとして展開する。キャッシュディレクトリのパスを `-o` に連結すると、パス中の `%(title)s`・`%%`・`%20` などが書式として解釈され、動画のタイトルなど外部由来の値で展開されたパスに書き込まれたり、起動に失敗したりする。
-   候補: 出力先のディレクトリは `-P`（`--paths`）の値として渡し、`-o` は `%(id)s` に基づく固定の文字列にする。`-o` には呼び出し元が与えたパスを含めない。`-P` の値がテンプレートとして展開されないことは、設計時に実 `yt-dlp` で確認し、`02_architecture.md` に記録する。
-   別案として、パス中の `%` を `%%` にエスケープする方法がある。エスケープ漏れが起きやすいため、`-P` を第一候補とする。

## H-03: タイムアウト後の待機を有界にする

-   `exec.CommandContext` がタイムアウト・キャンセル時に終了させるのは直接の子プロセスだけである。`yt-dlp`（またはテストで差し替えた実行ファイル）が起動した子孫プロセスが標準エラー出力のパイプを引き継いで開いたままにすると、捕捉の読み取りが EOF に達せず、`Wait` がいつまでも戻らない。
-   候補: `exec.Cmd.WaitDelay` に正の有限の値を設定する。値は設計で固定する（AC-08 の「設計で固定した猶予」）。
-   PR #33 のレビューでは、`sh -c 'sleep 3 & wait'` を 300 ms のタイムアウトで起動すると `WaitDelay` なしでは `Run` が約 3 秒戻らず、設定すると約 0.8 秒で戻ったと報告された。設計時に再確認すること。

## H-04: 標準エラー出力の捕捉

-   保持するのは先頭 4 KiB までだが、読み取り自体は止めずに最後まで読み捨てる（ドレインする）。読み取りを 4 KiB で止める（例: `io.LimitReader`）と、パイプが詰まった子プロセスが書き込みでブロックし、タイムアウトで殺されるまで終了しない。その結果、本来 `ErrYtDlpExec` として報告すべき失敗が `context.DeadlineExceeded` になる（AC-56）。
-   候補: 4 KiB を超える書き込みも全量を消費済みとして受け付け、超過分を捨てる上限付きの `io.Writer` を `Cmd.Stderr` に設定する。

## H-05: `encoding/json` が黙って補正する入力

要件書 3.2 の「標準ライブラリのデコーダが黙って置換・切り捨て・無視しうる入力も拒否する」を具体化する。レビューで判明したものは次のとおり。検出の手段は設計で決める。

-   **不正な UTF-8:** `encoding/json` は不正なバイト列を U+FFFD に置換して成功する。候補: デコードの前に生のバイト列を `utf8.Valid` で検証する（AC-52・AC-53）。
-   **対になっていないサロゲートのエスケープ:** `"\ud800"` や `"\udc00"` は ASCII のバイト列なので `utf8.Valid` を通過し、`encoding/json` はエラーを返さずに U+FFFD に置換する。`json.Decoder.Token` も同様に置換するため、デコード結果からは検出できない。候補: 生のバイト列の JSON 文字列を走査し、`\uD800`〜`\uDBFF` の直後に `\uDC00`〜`\uDFFF` が続くこと、単独の下位サロゲートがないことを検証する（AC-52・AC-53）。
-   **後続データ:** `json.Decoder.Decode` は最初の値だけを読んで成功し、後続のバイト列を読み残す。`{"events":[]} {}` が `ErrNoSubtitles` になりうる。候補: `json.Unmarshal` を使う（後続データをエラーにする）、または `Decode` の後に `dec.More()` / 次の `Token` が `io.EOF` であることを確認する（AC-12・AC-15）。
-   **配列中の `null`:** 構造体のスライスにデコードすると、`null` 要素はゼロ値の構造体になり、エラーにならない。候補: 要素を `json.RawMessage` で受けて種別を確認する、またはポインタ型の要素にして nil を検出する。入れ子の `segs` にも同じ検査を適用する（AC-55・AC-57）。
-   **型の不一致:** `utf8` が `null` の場合、`string` フィールドへのデコードはエラーにならず空文字列のままになる。存在する `utf8` が文字列であることを区別して検証する（AC-57）。
-   **数値の範囲:** `tStartMs` の負数・非整数・`int64` の範囲外（`9223372036854775808` 以上）を拒否する。`int64` へのデコードは範囲外や小数をエラーにするが、欠落（ゼロ値）と `0` を区別できないため、欠落の検出には別の手段（ポインタ型など）が要る（AC-45・AC-54）。

## H-06: 重複判定に使う数値フィールドの検証

-   重複判定の規則は事前調査の結果から設計で固定する（要件書 F-003）。規則が `tStartMs` 以外の数値フィールド（`dDurationMs` など）を読む場合、そのフィールドにも `tStartMs` と同じ検証（0 以上の整数で `int64` で表現できること）を適用し、欠落時の扱いを規則とあわせて `02_architecture.md` で固定する。
-   満たさない入力は `ErrParseSubtitles` とし、部分的な結果を返さない。

## H-07: キャッシュの更新手順

要件（F-005）は「成功したときだけキャッシュを変更する」「前回の残存ファイルを誤認しない」「一時ファイルを残さない」「他の動画のファイルに触れない」である。レビューで合意した実現手段の候補は次のとおり。

-   **ステージング領域:** `yt-dlp` にはキャッシュファイルへ直接書かせず、実行ごとに新しく作る空の一時ディレクトリへ出力させる。前回の実行の残存ファイルを誤認しない（AC-30）ことも、これで満たせる。
-   **配置:** ステージング領域はキャッシュディレクトリ内など、キャッシュと同じファイルシステム上に作り、置き換えを `os.Rename` で行えるようにする。名前は動画 ID から組み立てるキャッシュファイル名と衝突しないものにする（例: `os.MkdirTemp(cacheDir, ".staging-*")`）。
-   **置き換え:** ステージング領域の出力から `Transcript` を組み立てられた後に限り、ステージング領域のファイルで当該動画のキャッシュファイルを置き換え、今回の出力に含まれない当該動画の古いキャッシュファイル（前回だけ存在した手動字幕など）を取り除く（AC-34）。
-   **失敗時:** 実行失敗・タイムアウト・キャンセル・パース失敗・字幕なし・info.json なし（AC-60）のいずれでも、既存のキャッシュに触れない（AC-58）。
-   **後始末:** 成功・失敗を問わず、`Fetch` の終了時にステージング領域を削除する（例: `defer os.RemoveAll`）（AC-59）。
-   **途中で中断した場合:** 2 つのファイルの置き換えは不可分ではない。置き換えの途中でプロセスが終了すると、新旧のファイルが混在するか、片方だけが残りうる。片方だけの場合は AC-29 によりキャッシュミスとして再取得される。新旧が混在した場合の扱い（許容するか、置き換えの順序で防ぐか）は設計で決める。
-   **パスの信用:** キャッシュの読み込みは動画 ID から組み立てたファイル名だけを開き、ディレクトリ内の他の名前（ステージング領域を含む）を信用しない（AC-20）。

## H-08: `yt-dlp` が作るファイルのパーミッション

-   `yt-dlp` が書き出すファイルのパーミッションは umask に依存し、`0o644` などになりうる。ステージング領域から移したファイルをそのままキャッシュにすると AC-19（ファイルは `0o600`）を満たさない。
-   候補: ステージング領域のディレクトリを `0o700` で作り（`os.MkdirTemp` は `0o700` で作る）、置き換えの前に各ファイルを `0o600` に変更する。

## H-09: サイズ・件数の上限値

-   json3 のファイルサイズ、json3 のイベント数、info.json のファイルサイズの上限値を `02_architecture.md` で固定する（AC-48・AC-49・AC-50）。
-   事前調査で得た実データ（長時間の動画を含む）の大きさを基に、十分な余裕を持たせて決める。上限の判定はファイルの読み込み時点で行う（[security.md](../../dev/security.md) §3）。

## H-10: テストの構成

AC を検証するテストの組み立て方について、レビューで挙がった案を記す。

-   **AC-06（`%` を含むキャッシュディレクトリ）:** 外部コマンドの実行を差し替え、渡された引数の配列を検査する。キャッシュディレクトリのパスが出力先の引数（例: `-P` の値）にだけそのまま現れ、出力テンプレートの引数（`-o` の値）が固定の文字列と一致することを確認する。
-   **AC-08（子孫プロセスが残る場合）:** 標準エラー出力を引き継ぐ子孫プロセスを起動し、その子孫がタイムアウト後も標準エラー出力を開いたまま実行を続けるスクリプトを `yt-dlp` の実行パスに指定する。`Fetch` がタイムアウト + 猶予 + 余裕分の時間内に戻ることを確認する。
-   **AC-56（大量の標準エラー出力）:** 4 KiB を大きく超える標準エラー出力を書いてから非ゼロ終了するスクリプトを使い、`ErrYtDlpExec` が返ることを確認する。タイムアウトは、子プロセスが自分で終了するのに十分な長さにする。
-   **AC-58・AC-59（失敗時にキャッシュを残す）:** 外部コマンドの実行を差し替え、失敗の種類ごとにステージング領域へ書く内容と終了コードを変える。キャンセルは、差し替えた実行の途中で `ctx` をキャンセルして起こす。各ケースの後に、既存のキャッシュファイル・他の動画のファイル・無関係なファイルのバイト列が変わっていないこと、ステージング領域が残っていないことを確認する。
-   CLAUDE.md のテスト方針に従い、各テストは対象の仕組みを実際に壊して失敗することを確認してからコミットする。

## H-11: 既存のキャッシュのパーミッション（扱わない）

-   PR #33 のレビューで、既存のキャッシュディレクトリやファイルが `0o755` / `0o644` などの緩いパーミッションである場合に、検査して厳しくするか拒否すべきだという指摘があった。
-   扱わないと決めた。キャッシュの中身は公開動画の字幕とメタ情報であり、利用者が自分で用意したディレクトリ（多くは `0o755` の `~/.cache` 配下）のパーミッションを変更・拒否しても機密性は向上せず、利用者の設定を上書きするだけだからである。要件書 §2.3 のスコープ外に記載した。
-   `0o700` / `0o600` は、本プログラムが新たに作るディレクトリとファイルにだけ適用する（AC-19）。

## H-12: 境界の網羅チェックリスト

要件レビューで使っていたチェックリストを、設計の検討用に移したものである。`02_architecture.md` で各境界（URL・json3・info.json・`yt-dlp` の実行）の検証手段を決めるときに、次の各観点を確認する。見落とし防止のためのもので、網羅を保証するものではない。

-   **バイト列:** デコードの前に有効な UTF-8 か。JSON 文字列中のサロゲートのエスケープが対になっているか（H-05）。
-   **トップレベル:** 期待する JSON 種別か。`null` や別の種別を受理しないか。ちょうど 1 つの値で、後続データを受理しないか（H-05）。
-   **配列:** 各要素が期待する種別か。`null` 要素や非オブジェクト要素を受理しないか。入れ子の配列にも再帰的に適用しているか（H-05）。
-   **数値:** 符号・整数性・対象の Go 型で表現できる範囲を検証しているか。ロジックが読むすべての数値フィールドに適用しているか（H-05・H-06）。
-   **必須項目と任意項目:** 欠落と空（ゼロ値）を区別できているか。
-   **同一性:** 要求と一致すべき識別子（info.json の `id`）を検証しているか。
-   **サイズ・件数の上限:** 有限の上限があり、超過時は対応する番兵で拒否するか（H-09）。
-   **部分結果:** 拒否時に部分的な結果を返さず、キャッシュも変更しないか（H-07）。
-   **外部プロセス:** 出力の捕捉は上限を設けつつドレインしているか（H-04）。タイムアウト後の待機は子孫プロセスがあっても有界か（H-03）。呼び出し元の値が書式として解釈される引数に入っていないか（H-02）。
