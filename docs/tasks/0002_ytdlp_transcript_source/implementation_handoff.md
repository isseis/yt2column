# 実装への申し送り：yt-dlp による字幕取得

## 本書の位置づけ

[01_requirements.md](01_requirements.md) と [design_handoff.md](design_handoff.md) の検討過程で挙がった事項のうち、設計の要求ではなく、実装段階で具体的な手段として扱うべき事項をまとめる。

-   要件書は「何を受理し、何をどの番兵で拒否し、キャッシュがどう変わるか」だけを定める。設計への申し送りは [design_handoff.md](design_handoff.md) に置く。本書は、その設計要求を満たす実装手段と、実装時に踏みやすい落とし穴を記録する。
-   `02_architecture.md` と実装計画書は、本書の各項目について採用した手段または扱わない理由を記録する。本書の手段は候補であり、別の手段を選んでもよい。ただし、対応する AC を満たすこと。
-   本書は承認対象の文書ではない。実装時に参照し、項目を追加してよい。

## I-01: 後続データの拒否（`json.Decoder.More` を使わない）

-   **懸念:** 要件は、トップレベルの JSON 値の後に空白以外のデータが続く入力を受理せず、対応する番兵（json3 は `ErrParseSubtitles`、info.json は `ErrParseInfo`）で拒否すると定めている（AC-12・AC-15）。`json.Decoder.Decode` は最初の値だけを読んで成功し、後続のバイト列を読み残す。そのため `{"events":[]} {}` のような入力が後続データを見落として受理されうる。
-   **なぜ重要か:** 後続データを見落とすと、要件で拒否すべき入力が受理され、AC-12・AC-15 の番兵対応が満たされない。静かな見落としは以降の実装にもコピーされる。
-   **候補:**
    -   生のバイト列を一度メモリに読み、`json.Unmarshal` でデコードする。`json.Unmarshal` は値の後に空白以外のデータが続く入力をエラーにする。
    -   ストリームを保つ場合は、`Decode` の後に、値の後に空白以外のデータが残っていないこと（実際に EOF に到達すること）を確認する。`json.Decoder.More` は「現在の配列・オブジェクトに次の要素があるか」を返すものであり、トップレベル値の後続データや EOF の判定には使えない。`More` を EOF の確認として使わないこと。
-   **関連 AC:** AC-12（json3）、AC-15（info.json）。[design_handoff.md](design_handoff.md) H-05 の「後続データ」も参照。

## I-02: 重複判定の時間計算のオーバーフロー（該当しない）

-   **懸念:** 重複判定で `tStartMs` と `dDurationMs` からイベントの終端（`tStartMs + dDurationMs`）を求める場合、両者が個別に 0 以上かつ `int64` の範囲内でも、和が `int64` を超えてオーバーフローしうる（例: `tStartMs` = `math.MaxInt64`、`dDurationMs` = 1）。オーバーフローすると、無関係なイベントが重なって見えたり、本来重なるものが重ならなかったりして、重複判定が誤る（AC-32・AC-46）。
-   **候補:** 終端を求める前に和が表現可能かを確認し、超える入力を `ErrParseSubtitles` とする。または、オーバーフローしない比較（`dDurationMs` を引く形など）で重なりを判定する。境界の組み合わせをテストで覆う。
-   **関連 AC:** AC-32・AC-46。[design_handoff.md](design_handoff.md) H-06 も参照。
-   **状況（2026-09-30）:** 該当しない。要件 F-003 の改訂でローリング重複の除去を取りやめ、`dDurationMs` を読まないため、終端の計算そのものが無い（`02_architecture.md` §3.7）。除去規則を将来追加する場合は、この懸念をあわせて扱う。

## I-03: 消費するメンバーの重複の検出

-   **懸念:** `02_architecture.md` §3.4 は、消費するメンバーが同じオブジェクトの中で重複する入力（json3 のトップレベルの `events`、`events` の各要素の `tStartMs`・`segs`、`segs` の各要素の `utf8`、info.json のトップレベルの `id`・`title`・`channel`・`description`）を、形式ごとの番兵（`ErrParseSubtitles`・`ErrParseInfo`）で拒否すると定めている。`encoding/json` は重複したメンバーについて後の値を黙って採るため、構造体や `map` へのデコード結果からは重複を検出できない。
-   **なぜ重要か:** 検出しないと、`{"id":"wrong","id":"<動画 ID>"}` が info.json の `id` の照合（AC-47）を通り、`events`・`segs` の重複は本文を黙って入れ替える。要件 3.2 の「標準ライブラリのデコーダが黙って置換・無視しうる入力を拒否する」に反する。
-   **候補:** `json.Decoder.Token` で消費する各オブジェクトのレベルを走査し、メンバー名の集合で重複を検出する（キー名の比較はエスケープを解いた後の文字列で行う）。消費しないメンバーの値は読み飛ばし、その重複は拒否しない（AC-64・AC-67）。同じ値の重複と異なる値の重複の両方をテストで覆う。
-   **関連:** F-003・F-004、AC-12・AC-15・AC-47・AC-64・AC-67。[design_handoff.md](design_handoff.md) H-05・H-12 も参照。

## I-04: ポインタの読み取りの上限

-   **懸念:** `02_architecture.md` §3.5 は、ポインタ（`<id>.current`）の内容が `a` または `b` の 1 バイトちょうどのときだけ有効なスロットとし、それ以外をキャッシュミス（dangling の判定では「内容がそれ以外」）とする。破損した、または手で置かれた巨大な通常ファイルのポインタを `os.ReadFile` などで全体として読むと、`Fetch`・`RemoveCache`・`PruneCache` が上限なくメモリを確保しうる。他のキャッシュの入力には 8 MiB の上限（§3.7）があるが、ポインタには無い。
-   **なぜ重要か:** 判定に必要なのは高々 2 バイトであり、それ以上を読むのは無駄なうえ、他の入力の上限を迂回する。脅威モデル上、キャッシュディレクトリは `0o700` で同じローカル利用者だけが書けるため（[security.md](../../dev/security.md)）、影響は自分の環境の破損や誤操作に限られるが、読み取りを有界にする費用は小さい。
-   **候補:** 種別を辿らずに（lstat で）確認した大きさが 1 でなければ読まずに「内容がそれ以外」とする。または、高々 2 バイトだけを読み、1 バイトちょうどで `a`・`b` のどちらかであるかを判定する。大きなポインタでキャッシュミスになり、dangling として削除されることをテストで覆う。
-   **関連:** F-005、AC-29・AC-69・AC-70。
