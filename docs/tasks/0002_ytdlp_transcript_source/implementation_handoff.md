## 本書の位置づけ

[01_requirements.md](01_requirements.md) と [design_handoff.md](design_handoff.md) の検討過程で挙がった事項のうち、設計の要求ではなく、実装段階で具体的な手段として扱うべき事項をまとめる。

-   要件書は「何を受理し、何をどの番兵で拒否し、キャッシュがどう変わるか」だけを定める。設計への申し送りは [design_handoff.md](design_handoff.md) に置く。本書は、その設計要求を満たす実装手段と、実装時に踏みやすい落とし穴を記録する。

-   本書は承認対象の文書ではない。実装時に参照し、項目を追加してよい。

## I-01: 後続データの拒否（`json.Decoder.More` を使わない）

-   **懸念:** 要件は、トップレベルの JSON 値の後に空白以外のデータが続く入力を受理せず、対応する番兵（json3 は `ErrParseSubtitles`、info.json は `ErrParseInfo`）で拒否すると定めている（AC-12・AC-15）。`json.Decoder.Decode` は最初の値だけを読んで成功し、後続のバイト列を読み残す。そのため `{"events":[]} {}` のような入力が後続データを見落として受理されうる。
-   **なぜ重要か:** 後続データを見落とすと、要件で拒否すべき入力が受理され、AC-12・AC-15 の番兵対応が満たされない。静かな見落としは以降の実装にもコピーされる。
-   **候補:**
    -   生のバイト列を一度メモリに読み、`json.Unmarshal` でデコードする。`json.Unmarshal` は値の後に空白以外のデータが続く入力をエラーにする。
    -   ストリームを保つ場合は、`Decode` の後に、値の後に空白以外のデータが残っていないこと（実際に EOF に到達すること）を確認する。`json.Decoder.More` は「現在の配列・オブジェクトに次の要素があるか」を返すものであり、トップレベル値の後続データや EOF の判定には使えない。`More` を EOF の確認として使わないこと。
-   **関連 AC:** AC-12（json3）、AC-15（info.json）。[design_handoff.md](design_handoff.md) H-05 の「後続データ」も参照。
