# 設計への申し送り（0115）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: PR の状態を読む呼び出しの形

**懸念:** AC-01 は、`mergeable`・PR の head・base ブランチを読むことを求める。今のラウンドは、workspace ごとに `gh pr list --head <branch> --state open --json headRefName,number,title,url` を呼ぶ（`internal/chief/workspace.go:143`）。`mergeable` をこの `--json` に足すか、PR ごとに `gh pr view` を足すかで、呼び出しの回数と応答の時間が変わる。GitHub は `mergeable` を求められたときに計算するので、一覧の呼び出しでは `UNKNOWN` が続きやすいかどうかも確かめる必要がある。

**なぜ重要か:** 4.1 は、呼び出しの回数を、開いている PR の数に比例する以上に増やさないことを求める。`UNKNOWN` が続くと、コンフリクトに気づくのが遅れる。

**候補:**

-   `gh pr list` の `--json` に `mergeable` を足す。`strictjson.Object.Collect` は列挙しないメンバーを無視する（`internal/strictjson/strictjson.go:89-104`）。そのため、足すのは読み取りの側の列挙だけである。
-   実物で、一覧の呼び出しが返す `mergeable` と `gh pr view` が返すものの違いを確かめる。

**関連:** F-001、AC-01・AC-04

## H-02: 早く気づく仕組みが要るか

**懸念:** issue #1019 は、chief が `main` へのマージを見た直後に、ほかの開いている PR を確かめ直すと早く気づける、と挙げた。今の `chief wait` は Herdr の変化でだけ終わる（`internal/chief/wait.go:66-82`）。そのため、コンフリクトに気づくのは、最長で制限時間（10 分）の後のラウンドになる。

**なぜ重要か:** 要件は、この仕組みをスコープ外にした（2.3）。ただし、マージの自動送信のラウンドで `mergeable` がまだ `UNKNOWN` なら、さらに 1 ラウンド遅れる。

**候補:**

-   今のラウンドの間隔のままにし、遅れを「結果」に書く。
-   マージを見たラウンドの後に、ほかの PR を短い間隔で読み直す。この候補は要件の変更になるので、採るなら人に確かめる。

**関連:** F-001、2.3

## H-03: 送った記録の形と、「送り終えた」の判定

**懸念:** AC-08 は、PR とその head のコミットの組ごとに 1 回だけ送ることを求める。AC-14 は、送り終えた記録があり、エージェントがすべて入力を待っていることを「解消できず」の条件にする。今の `autosend-<PR>.json` は PR ごとの 1 件で（`internal/chief/records.go:1291-1325`）、送信の記録 `send-*` は保持の期間が `observeWindow + carryWindow` に限られる（`internal/chief/records.go:941`）。人が選んだ送信の記録（AC-19）も同じ記録に入れるかを決める必要がある。

**なぜ重要か:** 送信の記録が保持の期間を過ぎて消えると、「送り終えた」を判定できなくなり、「解消できず」の表示が消えうる。記録の種類を足すときは、ADR-0046 の「記録」の決定も同じ PR で更新する。

**候補:**

-   PR と head の組を名前に持つ、作るだけで上書きしない記録を足し、送り終えた結果もそこから引けるようにする。
-   消す規則（PR が閉じたかマージされた後、または一定の日数の後）を決める。

**関連:** F-002・F-003・F-004、AC-08・AC-14・AC-19

## H-04: 衝突の種類の判定を誰が行うか

**懸念:** AC-22・AC-23 は、解消してよい衝突と止める衝突を分ける。判定の一部（パスが `.md` か、内容の衝突か、Go のファイルの衝突がプロトコル番号の宣言の行だけか）は決定的に判定できる。一方、「両側の変更を保てるか」はエージェントの判断である。

**なぜ重要か:** 決定的に判定できる部分をエージェントに任せると、手順の読み違いで範囲の外の衝突を解消しうる（ADR-0014 の「決定的な検査は Go に置く」）。逆に道具を足すと、開発の道具が 1 つ増える。

**候補:**

-   `git ls-files -u` の段（stage）と `git diff --name-only --diff-filter=U` などで判定する Go の道具（既存の道具のサブコマンド、または新しい道具）を置き、エージェントはその結果に従う。
-   コマンドの定義に、エージェントが実行する決まったコマンドと、その出力の読み方を書く。

**関連:** F-005、AC-22・AC-23

## H-05: merge コミットと、PR レビューの再依頼の判定、ローカルのレビューの記録

**懸念:** `/mergemain` はローカルの CLI レビューを走らせない（AC-30）。`/runpr` は、最後の PR レビューの後の変更を見て、PR レビューの再依頼を決める（`.claude/commands/_lib/pr-review-escalation.md`）。また、ローカルのレビューの記録が後のコミットをすべて見たかを確かめる（`.claude/commands/_lib/review-records.sh`）。merge コミットは、`main` の変更全体を差分に含む。そのため、これらの判定が、`main` の変更を PR の変更として数えるかどうかを確かめる必要がある。

**なぜ重要か:** `main` の変更を PR の変更と数えると、毎回、マージの質問で再依頼を尋ねるか、再依頼の条件（信頼の境界、セキュリティ）に誤って当たる。数えないと、解消の差分が誰にも見られずに通りうる。

**候補:**

-   今の判定を `/mergemain` の merge コミットで試し、結果を記録する。判定を変える必要があれば、それは要件の範囲（`/runpr` を変えない）を越えるので、人に確かめる。

**関連:** F-005、AC-30、要件定義の際に決めたこと（解消のコミットのレビュー）

## H-06: 作業の前の状態への戻し方

**懸念:** AC-28 は、止まるときに、HEAD を始める前の PR の head に戻し、作業ツリーを変更のない状態にし、merge の途中の状態を残さないことを求める。merge コミットを作る前（`git merge --abort`）と、作った後（検査の失敗、push の失敗）では、戻し方が違う。

**なぜ重要か:** 作った後の戻しは、手元の履歴を捨てる操作になる。手順を誤ると、ほかの作業を失いうる。AC-21 は作業ツリーに変更がないことを前提にしているが、検査が作ったファイルを消すかどうかも決める必要がある。

**候補:**

-   始める前の head のコミットを控え、merge コミットを作った後の戻しは、そのコミットへ戻す操作に限る。戻した後に、HEAD と作業ツリーの状態を確かめて報告する。

**関連:** F-005、AC-21・AC-27・AC-28

## H-07: 送る前の報告の控え

**懸念:** AC-12 は、送る前に、Claude Code の pane の最後の報告がその PR の報告として読めれば控えを作ることを求める。今の控えは、人の `chief detail` で、`detail-` の記録がすでにあり、pane のソースでないときに作られる（`internal/chief/detail.go:520-563`）。自動送信の前に作るときの条件と、`resetAfterRunpr` が控えから読む pane とその順番（`internal/chief/reset.go:162-243`）との関係を決める必要がある。

**なぜ重要か:** 控えの pane とその順番は、`/runpr` の後のリセットの確かめに使われる。`/mergemain` を送った後に、PR を作った pane の人の最後の入力は `/mergemain` になる。そのため、`/runpr` の後のリセットの確かめは通らなくなる。

**候補:**

-   既存の `keptReport` の読み取りを使い、自動送信の前に控えを作る経路を足す。リセットの確かめへの影響を設計に書く。
-   AC-12 の引き継ぎ（新しい head が控えのある head を第 1 の親とする merge コミットのとき）を、控えを読むときに親をたどって判定するか、引き継ぐ記録を作るかを決める。親をたどるには、手元の git でそのコミットを読める必要がある。

**関連:** F-002、AC-12

## H-08: 送った後に pane が動いたことの確かめ

**懸念:** AC-14 は、送り終えた後に Claude Code の pane が動いたことを確かめるまで、「解消できず」としないことを求める。送り終えた直後は、Herdr がまだ pane を動いていると報告していないことがある。動いていた間がラウンドとラウンドの間に収まると、chief は動いているところを見ない。

**なぜ重要か:** 動いたことを見落とすと、解消できなかった行がいつまでも「送った」のままになる。逆に、動く前に判定すると、まだ走っていない `/mergemain` を「解消できず」と示す。

**候補:**

-   Herdr の `state_change_seq` が、送り終えたときの値から進んだことで確かめる（`internal/chief/wait.go:66-82` が待ち受けで比べている値）。
-   Claude Code の transcript に、送った後の応答が終わったことで確かめる。

**関連:** F-003、AC-14

## H-09: コマンドの定義の比べ方と、タスクのコマンドの読み取り

**懸念:** AC-05 の (8) は、PR のブランチの `.claude/commands/mergemain.md` と `origin/main` のものを比べることを求める。比べる対象を、作業ツリーのファイルにするか、HEAD のコミットにするかを決める必要がある（AC-05 の (3) で作業ツリーに変更がないことは確かめる）。また、AC-05 の (6) は、`/mergemain` をタスクのコマンドとして数え、タスクのコマンドがないセッションの扱いを決めている。今の読み取り（`internal/chief/screen_transcript.go:309` の `readRunningCommand`）は 5 つのコマンドだけを知り、タスクのコマンドがないセッションを「決まらない」と返す。

**なぜ重要か:** 読み取りの変更は、表の実行中のコマンドの表示（`＋指示`）と、Claude Code の pane のリセットの確かめ（人の最後の入力が PR を作ったコマンドであること）にも及ぶ。`/mergemain` を走らせた pane は、PR を作ったコマンドの後に `/mergemain` を走らせたことになる。そのため、`/runpr` の後のリセットは見送られる（H-07）。

**候補:**

-   `git show origin/main:.claude/commands/mergemain.md` と `git show HEAD:.claude/commands/mergemain.md` のバイト列を比べる。
-   実行中のコマンドの種類に `/mergemain` を足し、リセットの確かめが PR を作ったコマンドだけを見ることは変えない。

**関連:** F-002、AC-05

## H-10: 表の語と状態の詳細、道具の出力とプロトコル番号

**懸念:** コンフリクトの行と「解消できず」の行の状態の文字列、状態の詳細、番（人か AI か）を決める必要がある。表の語は、CLAUDE.md の「Go Idioms」の状況の表の例外（`internal/chief/table.go`）の範囲に入る日本語の文字列である。道具の出力の形が変われば、`chief.md` が渡す `--protocol` と道具のプロトコル番号の扱いも決める必要がある（CLAUDE.md の「Protocol numbers」）。

**なぜ重要か:** 表の語を `table.go` の外に置くと、例外の範囲を越える。出力の形を変えてプロトコル番号を上げないと、古い `chief.md` と新しい道具が食い違う。

**候補:**

-   状態の文字列を `table.go` の固定の語に足し、`chief_guide.md` の表と凡例も合わせる。出力の形が変わるなら、番号を `main` の値 + 1 にする。

**関連:** F-001・F-003・F-007、AC-02・AC-14・AC-35

## H-11: merge コミットのメッセージと、コマンドの定義の置き場所

**懸念:** `/mergemain` の merge コミットのメッセージの形と、エディタを開かずに作る方法を決める必要がある。コマンドの定義は英語で書き（CLAUDE.md の「Document language」(b)）、その承認の段落（AC-31）をほかのコマンドの形に合わせる必要もある。

**なぜ重要か:** `/mergepr` は、PR のコミットのメッセージの行（編集上の訂正の行など）を読んで squash の本文を作る（`internal/mergepr/corrections.go`）。merge コミットのメッセージが、その読み取りに影響しないことを確かめる必要がある。

**候補:**

-   git の既定の merge のメッセージ（`Merge remote-tracking branch 'origin/main' into <branch>`）を使う。

**関連:** F-005、AC-21・AC-31
