## 1. 概要 (Overview)

**目的:** 本書は、複数の Herdr の workspace で並行して進むタスクを見渡し、人の判断を待つものを選択式で示し、人の判断が要らない操作を自動で行うコーディネーター（以下 chief）の要件を定義する。

**背景:**

このリポジトリでは、タスクごとに git の worktree を作り、それを Herdr の workspace で開いて、シェル、OpenCode、Claude Code の pane で作業している。タスクは、`/mkreq` → `/mkarch` → `/mkplan` → `/runplan`（プランの PR の数だけ）の順に、それぞれが PR を作り、人がレビューしてから `/runpr` を実行し、`/runpr` がマージの確認を人に尋ねてマージする（[CLAUDE.md](../../../CLAUDE.md)「Claude Commands」）。

workspace が増えると、次のことが起きる。

-   どの workspace が人を待っているか（エージェントの質問、レビュー待ちの PR、マージの確認）が見えない。
-   人の判断が要らない操作にも人の手がかかる。`/runpr` はマージの後に次のコマンド（NEXT）を示すが、走らせるかは人が選ぶ（[runpr.md](../../../.claude/commands/runpr.md) の「4. Confirm, record, and merge」、783〜786 行）。次のコマンドを決まったモデルで走らせるには、人がその pane で `/clear` と `/model` を打ってからコマンドを打つ。
-   送り先のエージェントとモデルを人が毎回選ぶので、取り違えが起きる。`/runplan` のモデルは実装計画書の PR マーカーの `**実装モデル要件**` で決まる（[_context.md](../../../.claude/commands/_context.md) の「PR marker conventions」、[ADR-0042](../../dev/adr/0042-implementation-model-tiers.md)）。

2026-11-11 に、chief の試作（コマンドの定義とシェルスクリプト。リポジトリには入れていない）を 6 つの workspace で動かした。分かったことは親 issue [#836](https://github.com/isseis/yt2column/issues/836) の「試作で分かったこと」にあり、本書の要件はそれを踏まえる。

対応 issue: [#837](https://github.com/isseis/yt2column/issues/837)・[#838](https://github.com/isseis/yt2column/issues/838)（親: [#836](https://github.com/isseis/yt2column/issues/836)、関連: [#839](https://github.com/isseis/yt2column/issues/839)・[#840](https://github.com/isseis/yt2column/issues/840)・[#760](https://github.com/isseis/yt2column/issues/760)・[#790](https://github.com/isseis/yt2column/issues/790)）

**本書の記述範囲:** 本書は、chief が何を示し、何を誰に送り、何を送らないかという観測できる振る舞いを定める。chief の作り（コマンドの定義だけか、Go の道具を足すか）、Herdr の出力の読み方、質問の見分け方、モデルの切り替えの確かめ方、待ち受けの仕組み、記録の置き場所、表と選択肢の文言、テストの手段は、設計（`02_architecture.md`）で決める。要件の段階で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #836・#837・#838 で決めたこと:**

-   **#837 と #838 を 1 つのタスクにする。** 状況の表と自動の進行は、同じ状況の読み取りと同じ送信の経路を使うためである。worktree と workspace の作成と削除（#839）と、`/runpr` の Opus への切り替え（#840）は、別のタスクにする。ADR: なし（タスクの分け方はこのタスクの中で閉じるため）。
-   **コマンドごとのエージェントとモデル:** `/mkreq`・`/mkarch`・`/mkplan` は Claude Code・Opus、`/runplan` は実装計画書の PR マーカーの `**実装モデル要件**` が指すもの、`/runpr` は OpenCode・DeepSeek V4.1 Flash で走らせる。`/runpr` を Flash にするのは、通常は `/runpr` に Opus までは要らないと人が判断したためである。ADR: [ADR-0046](../../dev/adr/0046-chief-of-staff.md) を作り、[ADR-0042](../../dev/adr/0042-implementation-model-tiers.md) を更新する（下の「要件定義の際に決めたこと」の Flash の 2 項目）。
-   **実装の後の Opus のレビューは、`/runplan` が PR を開く前に行う仕組み（ADR-0042）を前提にする。** chief はそのためのコマンドを送らない。ADR: ADR-0046 に含める。
-   **`/runpr` は人がレビューした後に送る。** PR を開いたことだけを理由に、chief が `/runpr` を送ることはしない。人がレビューしてから `/runpr` を実行するという今の流れ（[task-pr-handoff.md](../../../.claude/commands/_lib/task-pr-handoff.md) の冒頭）を保つためである。ADR: ADR-0046 に含める。
-   **実装計画書の PR のレビューは、不要と判断できれば省いてよい。chief は「レビュー省略可」と示すだけで、`/runpr` を送るかは人が選ぶ。** 人の判断を変えずに、読む PR を選ぶ手がかりを与えるためである。ADR: なし（示すだけで、承認の規則を変えないため）。
-   **試作のコードは参考にとどめる。** 試作で分かったことは #836 に残し、実装は作り直す。ADR: なし。

**要件定義の際に決めたこと（2026-11-11）:**

-   **進め方は通常の進め方にする。** chief はほかのエージェントのセッションに入力を送る。開発用ツールの信頼の境界に当たるので、簡易な進め方の対象外である（[requirements_process.md](../../dev/conventions/requirements_process.md)「Simple Process」の「Excluded changes」）。新しい仕組みで、コマンドの定義、ルーティング、`/runpr`・`/mkplan` との接点という複数の場所に及ぶことも理由である。ADR: なし（進め方の選択はこのタスクの中で閉じるため）。
-   **`/runpr` を OpenCode・DeepSeek V4.1 Flash で走らせることを、決定として記録する。** ADR-0042 は、DeepSeek V4.1 Flash を開発のモデルの候補にする案を、外部のサービスを加えることになる点と、確かめていない点が多い点を理由に採らず、[#790](https://github.com/isseis/yt2column/issues/790) の PoC に回した（ADR-0042 の「採らなかった案」）。0081 の要件定義書（[01_requirements.md](../0081_implementation_model_choice/01_requirements.md) 57 行）は、コードを DeepSeek のサービスへ送ることになる点と、手順を守れるかを確かめていない点を書いた。2026-11-11 の時点で、`/runpr` と `/runplan` はすでに OpenCode の Flash で動いており、記録を運用に合わせる。コードとレビューのスレッドが DeepSeek のサービスへ送られることは 4.2 に書く。ADR: ADR-0046 に記録し、ADR-0042 の「採らなかった案」と「経緯」を更新する。
-   **実装モデル要件が `sonnet`（旧い値の `standard`）の `/runplan` も、OpenCode・DeepSeek V4.1 Flash で走らせる。** `opus` は Claude Code・Opus、`sonnet+opus-review` は Claude Code・Sonnet のままにする。ADR-0042 は `sonnet` を「Sonnet で実装し、追加のレビューはしない」と決めており、その決定を変える。`sonnet` の PR は Opus のレビューを受けないので、Flash の実装の誤りは、`/runplan` の中のレビュー、ローカルの CLI レビュー、Codex の PR レビューで見つける。手順を守れるかは #790 で確かめていない。ADR: ADR-0042 の決定を更新し、ADR-0046 から参照する。
-   **`sonnet+opus-review` の `/runplan` は、いまは Claude Code・Sonnet で走らせる。後で DeepSeek V4.1 Flash に差し替えて比べられるように、準備だけしておく（F-006）。** Flash で実装して Opus のレビューを受けた成果物と、Sonnet で実装して Opus のレビューを受けた成果物の品質を比べ、どちらにするかは別の issue で決める。そのため、実装モデル要件の値ごとの送り先とモデルを 1 か所だけ直せば差し替えられるようにする（AC-39）。差し替えた後は、OpenCode のセッションが Opus のレビューを走らせられずに PR を開かずに止まるので、PR を開く段だけを Claude Code・Sonnet の `/runplan` に渡す（AC-40）。比べるときに要る「どの PR をどのエージェントとモデルで実装したか」は、ADR-0042 の実装の記録（commit メッセージ）と F-011 の報告で分かる。ADR: ADR-0046。
-   **止まっているエージェントの質問には、人が chief の選択肢で選んだ答えだけを中継する（F-005）。** chief 自身は答えを選ばない。送る直前に、質問と選択肢が人に示したときと同じであることを確かめ、変わっていれば送らない。人の判断であることを保ったまま、pane を移る手間をなくすためである。ADR: ADR-0046。
-   **権限の確認（コマンドを実行してよいか）は中継しない（F-005）。** 中身を示すだけで、答えは人がその pane で直接入れる。chief 越しに答えると、実行されるコマンドを見ないまま許可しやすくなるためである。ADR: ADR-0046。
-   **自由に書く答えと、複数を選ぶ問いは中継しない。中継するのは、1 つを選ぶ問いの選択肢だけにする（F-005）。** 自由な文を送れると、chief が送る入力が人の書いた任意の文まで広がるためである。複数を選ぶ問いは、選んだ組を確かめる手間に対して、中継の利点が小さいためである。ADR: ADR-0046。
-   **`/runpr` のマージの確認の「NEXT をこのセッションで実行する」答えは中継しない（F-005）。** この答えを選ぶと、次のコマンドが `/runpr` のセッション（Flash）で走り、コマンドごとのモデルの決まりを chief 自身が破ることになるためである。人がその pane で直接選ぶことはできる。ADR: ADR-0046。この決定は、「実装の際に決めたこと（2026-11-12）」で、扱う答えがなくなったので外した。
-   **マージの後の自動送信を止める例外は、実装計画書の PR マーカーに欄を足して宣言し、`/mkplan` が書く。欄の意味は「この PR を作る `/runplan` を、自動で送ってよいか」とする（F-008）。** chief の手元のファイルに人が書く案は採らない。途中で対話のセッションを挟むこと（例: 0084 の PR-1 の後）は計画を作るときに決まる事柄で、計画書に置けば別の場所へ書き写さずに済むためである（[CLAUDE.md](../../../CLAUDE.md)「Key Design Patterns」の「Declare, don't infer」）。欄を「この PR のマージの後」ではなく「この PR を作る `/runplan`」に付けるのは、実装計画書そのものの PR にはマーカーがなく、「計画書のマージの後、PR-1 の前で止める」を表せないためである。ADR: ADR-0046。
-   **自動送信の欄がない計画書は、自動送信してよいものとして扱う（F-008）。** 欄がないのは、この決定より前に書かれた計画書の正しい形だからである（ADR-0042 の旧い値の扱いと同じ考え方）。進行中の 0084 の PR-2 を止める必要があれば、その計画書を直す PR で欄を足す。ADR: ADR-0046。
-   **自動送信は、マージした PR 1 件につき 1 回までとし、chief を起動し直しても 2 回送らない。chief は同時に 1 つだけ動かす（F-007、F-010）。** 送ったコマンドが失敗して条件がまた満たされても、同じコマンドを 2 回走らせないためである。ADR: ADR-0046。
-   **画面の文字列から人を待っていることを見分けるのは、CLAUDE.md の「Declare, don't infer」の例外とする。自動送信の引き金（マージを終えたこと）は、画面ではなく GitHub の PR の状態と git の状態で確かめる（F-002、F-007、5 章）。** OpenCode の質問の画面は変えられず、型で表せない外部の値だからである。引き金を画面に頼らないのは、人に尋ねずに入力を送る判断を、信頼できない文字列に委ねないためである。ADR: ADR-0046。CLAUDE.md の例外の一覧に足す（5 章）。
-   **人の判断を待つものは、種類の順に並べ、同じ種類の中では待っている時間の長い順に並べる（F-003）。** 種類の順は、エージェントを止めている質問、マージの確認、レビュー待ちの PR、そのほかの提案である。エージェントが止まっている間はそのタスクが進まないためである。issue の優先度ラベルを先に見る案は採らない。ADR: なし（並べ方はこのタスクの中で閉じるため）。
-   **自動の進行は、chief のセッションが待ち受けている間だけ行う（F-010）。** セッションと別に常駐するプロセスは置かない。止まっている間に溜まったものは、次に状況の表を出したときに拾う。止まっている間にマージされた PR の次のコマンドは、自動では送らず、提案として示す（AC-41・AC-59）。その間に人が手で次のコマンドを走らせたか、chief を入れる前の古いマージかを、chief が確かめられないためである。常駐のプロセスは、chief のセッションの外から、人が見ていないときにほかのセッションへ入力を送ることになり、信頼の境界が広がるためである。ADR: ADR-0046。
-   **人の判断を待つものが新しく増えたときに通知する。種類は問わない（F-010）。** レビュー待ちの PR もマージの確認も、気づかなければタスクが止まるためである。ADR: なし。
-   **chief の読み取り専用のネットワークの操作（PR・CI・レビューの状態の取得、`git fetch`）は、chief を起動したことで承認したものとする（F-010）。** 待ち受けの中で、人がいないときにも走らせる必要があるためである。書き込みの操作（push、マージ、コメント、issue の操作）は含めない。CLAUDE.md の「Tool Execution Safety」に書く。ADR: ADR-0046。
-   **実装計画書の PR を「レビュー省略可」と示す基準は、設計で決める（F-004）。** 要件では、基準を満たすときに示すことと、示しても人が決めることだけを定める。ADR: なし。
-   **chief は `/weakreview` を送らない（F-006）。** Opus のレビューは `/runplan` が PR を開く前に行う（ADR-0042）ので、chief が送る場面がないためである。ADR: ADR-0046。
-   **chief は、人が issue を示したときに、タスクのない空いた workspace へ `/mkreq` を送る（F-006）。** issue を選ぶのは常に人である。workspace を作る仕組み（#839）ができるまで、`/mkreq` を走らせる workspace は人が用意する。ADR: ADR-0046。
-   **pane のリセットは、PR を作ったコマンドが走った pane と、`/runpr` を走らせた pane に限る（F-009）。** 人が対話の作業に使っている pane を、確認なしで空にしないためである。ADR: なし（どの pane を空にするかは F-009 の中で閉じるため）。
-   **chief の作り（コマンドの定義だけか、Go の道具を足すか）は設計で決める（design_handoff.md の H-01）。** #836 は要件定義で決めるとしたが、判定と副作用をどこに置くかは機構の選択であり、[ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md) の方針との関係も設計で比べるためである。ADR: 設計で判断する。

**実装の際に決めたこと（2026-11-12）:**

-   **AC-30 と AC-46 を外す。** タスク 0089（#866）で、`/runpr` のマージの質問から「NEXT をこのセッションで実行する」答えがなくなり、`/runpr` は NEXT を示すだけになった（[ADR-0047](../../dev/adr/0047-runpr-merge-question.md)）。この 2 つの AC が扱う答えがなくなったので、外して番号を空ける。答えを中継しないという決定（「要件定義の際に決めたこと」）も、扱う答えがなくなった。理由: 対象のない AC を実装と確かめの対象に残さないため。ADR: [ADR-0046](../../dev/adr/0046-chief-of-staff.md) の決定はすでにこの変更を持つ。その後の段落の、この 2 つの AC を外すと書いたずれの文を消す。
-   **1 つの画面に複数の問い（タブ）がある質問は、中継しない。示すのは画面に出ている問いで、ほかの問いがあることと、人がその pane で直接答えることを示す（AC-25〜AC-27）。** 画面の採取（PR-1）で、Claude Code も OpenCode も、タブの画面には今のタブの問いだけを描き、次の問いは前の問いに答えるまで出さないことが分かった。キーを送らずにすべての問いを読むことはできない。問いを読むためにタブを移るキーを送ると、chief が人の選んでいない入力を送ることになる。理由: 示せない問いへの答えを、人に選ばせないため。ADR: なし（中継しない質問の種類を足すだけで、ADR-0046 の決定の範囲に収まるため）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   すべてのタスクの workspace の状況を 1 つの表で見られるようにする。
-   人の判断を待つものを優先度の順に選択式で示し、人が選ぶだけで次の操作に進めるようにする。
-   マージの後の次のコマンドを、人の手を介さずに、決まったエージェントとモデルで送る。
-   chief がほかのエージェントへ送る入力を決まった範囲に限り、chief が人の代わりに判断しないようにする。

### 2.2. スコープ (In Scope)

-   状況の表（F-001）
-   人の判断を待つものの見分け（F-002）
-   選択式の提示と優先度（F-003）
-   PR の詳細と「レビュー省略可」の提示（F-004）
-   エージェントの質問の中継（F-005）
-   送り先とモデルの決定、送信（F-006）
-   マージの後の自動送信（F-007）
-   実装計画書の PR マーカーの自動送信の欄（F-008）
-   役目を終えた pane の文脈のリセット（F-009）
-   待ち受けと通知（F-010）
-   送信の結果の報告（F-011）
-   ADR-0042 の更新、CLAUDE.md の「Declare, don't infer」の例外と「Tool Execution Safety」への追記、`_context.md` の実装モデル要件の値とモデルの対応の更新（5 章）

### 2.3. スコープ外 (Out of Scope)

-   タスク用の worktree と workspace の作成と削除。#839 で扱う。
-   `/runpr` を Flash で動かし、難度の高い修正を求められたら Opus でやり直すこと。#840 で扱う。
-   chief のセッションと別に常駐するプロセス。要件定義の際に決めたことのとおり置かない。
-   レビュー待ちの PR への `/runpr` の自動送信。人がレビューした後に人が選ぶ。
-   chief が自分で質問への答えを選ぶこと。権限の確認、自由に書く答え、複数を選ぶ問いの中継。
-   `/weakreview` の送信。
-   OpenCode のモデルの切り替え。OpenCode はコマンドでモデルを切り替えられないので、chief はモデルが合わないことを示し、人がその pane で切り替える（AC-35）。
-   issue の作成と、issue を閉じること。issue を閉じるのは `/runpr` が最後のプランの PR の後に行う（`runpr.md` の「5. Switch branch, then show NEXT」）。
-   進行中の計画書（0081・0083・0084・0085）に自動送信の欄を書き足すこと。必要になったときに、その計画書を直す PR で行う。
-   DeepSeek V4.1 Flash が手順を守れるかの確かめ。#790 で扱う。

## 3. 機能要件 (Functional Requirements)

本書でいう **chief の workspace** は、chief のセッションが動いている workspace である。**タスクの workspace** は、それ以外の Herdr の workspace のうち、このリポジトリの worktree を開いているものである。**エージェント**は、タスクの workspace の pane で動く Claude Code か OpenCode である。**入力を受け付ける状態**は、エージェントが実行中でも質問で止まってもいない状態である。

### 3.1. 機能一覧

#### F-001: 状況の表

人が求めたとき（1 回の呼び出しで）と、待ち受けの中で状況が変わったときに、タスクの workspace の状況を 1 つの表で示す。

workspace の状態は、次の表の上から順に、最初に当たるものとする。1 つの workspace に複数のエージェントがあるときも、この順で 1 つに決まる。

| 状態 | 条件 |
|---|---|
| 要確認 | タスクの状態（文書の承認、プランの PR のマージ）、エージェントの状態、PR の状態のどれかを読めない。または下のどれにも当たらない |
| 質問で停止 | どれかのエージェントが質問で止まっている（F-002。マージの確認を含む） |
| 実行中 | どれかのエージェントが実行中である |
| レビュー待ち | worktree のブランチに開いている PR がある |
| 次を提案 | 開いている PR がなく、次のコマンドが決まる（タスクのない workspace で `/mkreq` を待つ場合を含む） |
| タスク完了 | 計画のすべての PR がマージされている |

**Acceptance Criteria**:
-   **AC-01**: 表は、タスクの workspace ごとに 1 行を持ち、chief の workspace の行を持たない。
-   **AC-02**: 各行は、workspace の名前、タスクの番号（タスクがないときは「タスクなし」）、状態、次にやることを持つ。状態は上の表のどれか 1 つである。「実行中」の行は、走っているコマンドとモデルが分かるときはそれを示す。「質問で停止」の行は、マージの確認かどうかを示す。
-   **AC-03**: 「要確認」「質問で停止」「レビュー待ち」「次を提案」の行は、「実行中」「タスク完了」の行より上に並ぶ。その中の順は F-003 の並べ方に従い、「要確認」は「次を提案」の後に並ぶ。
-   **AC-04**: 表は、PR の詳細（F-004）を集め終わるのを待たずに示す。
-   **AC-05**: 表の下に、「質問で停止」の行ごとに、質問の要点と pane が示される。
-   **AC-06**: 「要確認」の行は、読めなかったもの（項目の名前）か、当たらなかった状態を示す。推し量って別の状態として扱わない。
-   **AC-07**: chief が Herdr の中で起動されていないときは、表を示さず、何も送らず、Herdr の中で起動するよう示す。
-   **AC-08**: chief がすでに別のセッションで動いているときは、表を示さず、何も送らず、動いている chief があることを示す。

#### F-002: 人の判断を待つものの見分け

次のものを、人の判断を待つものとして見分ける。

-   エージェントを止めている質問（決める点、権限の確認を含む）
-   `/runpr` のマージの確認
-   レビュー待ちの PR
-   そのほかの提案（「次を提案」の行のコマンド。マージの後の自動送信の条件を満たさなかったものを含む）

**Acceptance Criteria**:
-   **AC-09**: Claude Code のエージェントが質問で止まっているとき、その workspace は「質問で停止」になる。
-   **AC-10**: OpenCode のエージェントが質問を示して入力を待っているとき、Herdr がそのエージェントを `blocked` と報告していなくても、その workspace は「質問で停止」になる。
-   **AC-11**: `/runpr` がマージの確認で止まっている workspace は、PR が開いていても「質問で停止」になり、その workspace へ `/runpr` を送る選択肢は示されない。
-   **AC-12**: 質問で止まっているかを画面から確かめられないエージェント（画面が想定した形に合わない）がある workspace は「要確認」になり、その workspace には何も送らない。

#### F-003: 選択式の提示と優先度

人の判断を待つものと提案を、選択式で 1 回尋ねる。人は選ぶだけで、次の操作（PR の詳細を見る、質問に答える、コマンドを送る、何もしない）に進める。

**Acceptance Criteria**:
-   **AC-13**: 選択肢は、エージェントを止めている質問（マージの確認を除く）、マージの確認、レビュー待ちの PR、そのほかの提案の順に並ぶ。同じ種類の中では、待っている時間の長いものが先に並ぶ。選択肢には常に「何もしない」が含まれる。
-   **AC-14**: 1 回の問いで示せる数を超えるときは、先頭から示せるだけ示し、示さなかったものを問いの中で workspace の名前で挙げる。人はその名前を答えに書いて選べる。
-   **AC-15**: 人が選ぶまで、chief はどのエージェントにも入力を送らない（F-007 の自動送信を除く）。
-   **AC-16**: 表の下に、chief がこのセッションで人に尋ね、まだ答えのない問い（たとえば、OpenCode のモデルを切り替えた後に送り直すか）を、1 行ずつ示す。

#### F-004: PR の詳細と「レビュー省略可」の提示

人がレビュー待ちの PR を選んだとき、`/runpr` を送るかを決める材料を示し、送るかを尋ねる。

**Acceptance Criteria**:
-   **AC-17**: PR の詳細は、タスク、PR の番号・タイトル・URL、規模（変えたファイルの数、足した行と消した行の数、コミットの数）、CI の各ジョブの結果、PR レビューの書き手と状態、PR を作ったコマンドの報告の要約を持つ。報告の要約は、PR の変える内容、レビューの結果と直さなかった指摘、編集上の訂正、レビュアーに見てほしい点を含む。
-   **AC-18**: CI のジョブのうち実行されなかったもの（`skipping`）は、通ったもの（`pass`）と区別して示される。実行されなかったジョブがあるとき、「CI は通った」とだけ示さない。
-   **AC-19**: PR を作ったコマンドの報告が pane に残っていないとき（スクロールで消えた、`/clear` で消した）は、PR の説明から要約を示す。このとき、要約が報告と PR の説明のどちらから作ったものかが分かるようにする。
-   **AC-20**: PR レビューの本文は示さない（書き手と状態だけを示す）。
-   **AC-21**: 詳細のうち取得に失敗した項目（GitHub に届かない、`gh` が失敗した）は「取得できなかった」と示し、ほかの項目は示す。
-   **AC-22**: PR の詳細を示した後に、「`/runpr` を送る」「送らない」「ほかの PR を見る」を尋ねる。「`/runpr` を送る」には送り先のエージェントとモデルが示される。
-   **AC-23**: 実装計画書の PR が設計で決める基準を満たすとき、その PR の選択肢と詳細に「レビュー省略可」が示される。示しても、`/runpr` を送るかは人が選ぶ。
-   **AC-24**: 人が「`/runpr` を送る」を選んだとき、chief は送信の終わりを待たずに次の問いか報告に進み、送信の結果は F-011 で示す。

#### F-005: エージェントの質問の中継

エージェントを止めている質問を人に示し、人が chief の選択肢で選んだ答えだけをその pane へ送る。

**Acceptance Criteria**:
-   **AC-25**: 質問を示すときは、workspace の名前、pane、質問の文、すべての選択肢の文を、画面のとおりに示す（制御文字は見える形に置き換える）。1 つの画面に複数の問い（タブ）があるときは、画面に出ている問いを示し、ほかの問いがあることを示す。
-   **AC-26**: 中継の選択肢を示すのは、1 つを選ぶ問いだと確かめられた質問だけである。権限の確認、自由に書く答えを求める問い、複数を選ぶ問い、1 つの画面に複数の問い（タブ）がある質問、読み取る量の上限（4.2）で切った質問、どれに当たるか確かめられない質問は、中身を示すだけで、中継の選択肢を示さず、人がその pane で直接答えることを示す。
-   **AC-27**: 1 つの画面に複数の問い（タブ）があるときは、どの問いへの答えも送らない。
-   **AC-28**: 人が chief の選択肢で答えを選んだとき、chief は、送る直前に、その pane の質問と選択肢が人に示したときと同じであることを確かめ、同じときだけ、その選択肢を選ぶ入力を送る。違うとき（質問が変わった、答えられた、エージェントが動き出した）は何も送らず、そのことを示す。
-   **AC-29**: chief は、人が選んでいない答えを送らない。選択肢の文を、入力の文字列として送らない。

#### F-006: 送り先とモデルの決定、送信

コマンドごとに送り先のエージェントとモデルを決め、決まった手順でだけ送る。

chief がタスクの workspace へ送る入力は、次のものだけである。

| 入力 | 送る場面 |
|---|---|
| `/clear`・`/model <モデル>`（Claude Code） | コマンドを送る前、pane のリセット（F-009） |
| `/new`（OpenCode） | コマンドを送る前、pane のリセット（F-009） |
| `/mkreq <issue>` | 人が issue を示し、送り先を選んだとき |
| `/mkarch <タスク>`・`/mkplan <タスク>`・`/runplan <タスク>` | 人が選んだとき、またはマージの後の自動送信（F-007） |
| `/runpr <PR>` | 人が PR の詳細を見て選んだとき（F-004） |
| 1 つを選ぶ問いの選択肢を選ぶ入力 | 人が選んだ答えの中継（F-005） |

コマンドごとの送り先とモデルは次のとおりである。

| コマンド | エージェントとモデル |
|---|---|
| `/mkreq`・`/mkarch`・`/mkplan` | Claude Code・Opus |
| `/runplan`（実装モデル要件が `opus`） | Claude Code・Opus |
| `/runplan`（実装モデル要件が `sonnet+opus-review`） | Claude Code・Sonnet |
| `/runplan`（実装モデル要件が `sonnet`） | OpenCode・DeepSeek V4.1 Flash |
| `/runpr` | OpenCode・DeepSeek V4.1 Flash |

**Acceptance Criteria**:
-   **AC-31**: chief は、上の表にない入力（`git` のコマンド、`gh pr merge`、自由な文、`/weakreview` を含む）をタスクの workspace へ送らない。chief の workspace の pane には何も送らない。
-   **AC-32**: chief は、`/runplan` の実装モデル要件として、次に作るプランの PR の `**実装モデル要件**`（PR マーカーがない計画書では、計画書の「PR 構成」の節の値）を読む。読み方は `_context.md` の「PR marker conventions」の読み替えに従い、旧い値（`frontier-required` など）も新しい値（`opus` など）も受け付ける。
-   **AC-33**: 実装モデル要件の値が読み替えの表にないとき、または値がないときは、chief は `/runplan` を送らず、値が読めないこと（またはないこと）を示す。推し量って別の値として扱わない。
-   **AC-34**: Claude Code へ送るときは、`/clear` と `/model` を送り、モデルが切り替わったことを確かめてから、コマンドを送る。切り替わったことを確かめられないとき、または別のモデルになったときは、コマンドを送らず、そのことを示す。
-   **AC-35**: OpenCode へ送るときは、その pane のモデルが送るモデルと同じことを確かめてから、`/new` とコマンドを送る。`DeepSeek V4.1` と `DeepSeek V4.1 Flash` は別のモデルとして扱う。pane のモデルが送るモデルと違うときは、何も送らず、人にその pane でモデルを切り替えるよう示し、切り替えた後に送り直す選択肢を示す。
-   **AC-36**: 送り先の pane が入力を受け付ける状態でないとき、エージェントが動いていない pane のとき、または入力欄に送っていない文字が残っているときは、何も送らず、そのことを（残っている文字とともに）示す。
-   **AC-37**: 入力を送った後に失敗したとき（送れたかが分からないときを含む）は、送り直さず、その pane の状態と画面を示して、その workspace への送信を止める。止めたことは chief を起動し直しても残り、人が chief の選択肢で送信の停止を解くまで、その workspace へ自分から送らない。
-   **AC-38**: `/mkreq` は、タスクのない workspace のうち、エージェントが入力を受け付ける状態のものへだけ送る。issue の番号は人が示したものだけを使う。
-   **AC-39**: 実装モデル要件の値ごとの送り先とモデル（上の表の `/runplan` の 3 行）は、1 か所の設定を直すだけで変えられる。たとえば `sonnet+opus-review` を OpenCode・DeepSeek V4.1 Flash に変えても、ほかの振る舞い（F-001〜F-005、F-007〜F-011）は変わらない。
-   **AC-40**: 実装モデル要件が `sonnet+opus-review` か `opus` の `/runplan` を OpenCode に送り、その `/runplan` が PR を開かずに止まったとき（ブランチに `origin/main` より先のコミットがあり、PR がなく、エージェントが入力を受け付ける状態で、ブランチの計画書でその PR の対象ステップがすべて済んでいるとき）は、同じ workspace の Claude Code へ、Sonnet で同じ `/runplan` を送ることを提案として示す（F-003）。人が選べば送る。

#### F-007: マージの後の自動送信

`/runpr` がマージを終えたとき、次のコマンドを人に尋ねずに送る。人がマージの確認に答えたことを、次のコマンドの承認とみなす。

**Acceptance Criteria**:
-   **AC-41**: 次のすべてを満たすとき、chief は次のコマンド（要件定義書のマージの後は `/mkarch`、設計書のマージの後は `/mkplan`、実装計画書かプランの PR のマージの後は次の `/runplan`）を、人に尋ねずに F-006 のエージェントとモデルで送る。
    -   その workspace のタスクの PR が、GitHub で `MERGED` の状態である。
    -   直前に取得した `origin/main` に対して、worktree に未コミットの変更がなく、`origin/main` より先のコミットがない。
    -   worktree の HEAD が `origin/main` を指しており、かつ、そのタスクの機能ブランチの命名に合うブランチにあるか、ブランチのない状態である。ブランチのない状態を許すのは、次のコマンドが `/runplan` で、`/runpr` の報告が pane に残っていて、報告の NEXT が chief の決めた次のコマンドとコマンドもタスクも同じときだけである（`/runpr` は次のブランチがまだないときにブランチのない状態にするため）。マージした PR のブランチが チェックアウトされたままのとき（`/runpr` が次のブランチを用意する前に止まったとき）は満たさない。
    -   その workspace に、実行中のエージェントも、質問で止まっているエージェントもない。
    -   次のコマンドが `/runplan` のとき、その `/runplan` が作る PR の PR マーカーが自動送信を止めていない（F-008）。
    -   そのマージした PR について、まだ自動送信していない（AC-44）。
    -   chief が、このセッションの待ち受けの中で、その PR が開いている状態から `MERGED` になったことを見ている。chief が動いていなかった間にマージされた PR と、chief を起動する前にマージされた PR は満たさない。
-   **AC-42**: `/runpr` の報告が pane に残っていて、報告の NEXT が chief の決めた次のコマンドと、コマンドかタスクのどちらかで違うとき（報告が次のコマンドはないと示すときを含む）は、送らずに、違いとともに提案として示す。報告の文字列は照合にだけ使い、そのまま送らない。
-   **AC-43**: 簡易な進め方のタスクで 3 文書の PR がマージされた後の次のコマンドは `/runplan` である。
-   **AC-44**: マージした PR 1 件につき、自動送信は 1 回までである。chief を起動し直しても、同じマージした PR について 2 回送らない。送ったかどうかの記録を読めないときは、送らない。
-   **AC-45**: マージした PR があって、AC-41 のどれかを満たさないときは、chief は自動では送らず、満たさなかった条件とともに、次のコマンドを提案として示す（F-003）。
-   **AC-47**: `/mkreq` と `/runpr` は、自動では送らない。計画のすべての PR がマージされたタスクは「タスク完了」と示し、何も送らない。

#### F-008: 実装計画書の PR マーカーの自動送信の欄

実装計画書の PR マーカーに、その PR を作る `/runplan` を自動で送ってよいかを宣言する欄を足す。

**Acceptance Criteria**:
-   **AC-48**: `/mkplan`（`/mkplan2` と、簡易な進め方の `/mkreq` を含む）が書く PR マーカーは、自動送信の欄を 1 つ持つ。値は「自動で送ってよい」か「自動で送らない」かを表す 2 つの値のどちらかである。欄の名前と値の綴りは設計で決める。
-   **AC-49**: chief は、マージの後の `origin/main` の計画書から欄を読む。欄の値が「自動で送らない」のときは、その PR を作る `/runplan` を自動では送らず、提案として示す（AC-45 と同じ）。
-   **AC-50**: 欄がない PR マーカー（この決定の前に書かれた計画書）は、「自動で送ってよい」として扱う。
-   **AC-51**: 欄が 2 つ以上あるとき、または値が 2 つの値のどちらでもないときは、自動では送らず、欄が読めないことを示す。推し量ってどちらかの値として扱わない。

#### F-009: 役目を終えた pane の文脈のリセット

役目を終えた pane の文脈を空にし、次のコマンドが前のコマンドの文脈を持ち込まないようにする。

**Acceptance Criteria**:
-   **AC-52**: chief が `/runpr` を送った後、PR を作ったコマンド（`/mkreq`・`/mkarch`・`/mkplan`・`/runplan`）が走った pane を、Claude Code なら `/clear`、OpenCode なら `/new` で空にする。その pane が `/runpr` を送った pane と同じとき、またはその pane が PR を作ったコマンドの後に再び実行中になったとき（人が別の作業を始めたとき）は空にしない。ほかの pane は空にしない。
-   **AC-53**: 自動送信（F-007）で次のコマンドを送った後、`/runpr` を走らせた pane が次のコマンドの送り先と別の pane なら、その pane も空にする。
-   **AC-54**: 入力を受け付ける状態でない pane（OpenCode がマージの確認を示して待っている pane を含む）と、入力欄に送っていない文字が残っている pane は空にせず、そのことを（残っている文字とともに）示す。
-   **AC-55**: PR を作ったコマンドの報告の要約は、その pane を空にした後も F-004 で示せる（AC-19 の PR の説明を含む）。

#### F-010: 待ち受けと通知

chief のセッションが待ち受けている間、エージェントの状態の変化を待ち、変化したら状況を読み直して次を判断する。

**Acceptance Criteria**:
-   **AC-56**: 待ち受けの間、実行中のエージェントが実行を終えて止まると、chief は状況を読み直し、自動送信（F-007）の条件を満たすものを送り、人の判断を待つものを示す。
-   **AC-57**: 待ち受けは、エージェントが質問で止まっている間も、そのエージェントが動き出して止まるまで続く。質問で止まったことだけで待ち受けを終えない。
-   **AC-58**: 人の判断を待つものが新しく増えたとき、chief は通知を送る。種類（質問、マージの確認、レビュー待ちの PR、提案）は問わない。同じ workspace の同じ質問（文と選択肢が同じ）、同じ PR、同じ提案については、そのセッションで 2 回以上通知しない。通知が届かないときも、表には示す。
-   **AC-59**: chief のセッションが動いていない間は、自動送信も通知も行わない。次に状況の表を出したとき、その間に増えた人の判断を待つものが示される。その間にマージされた PR の次のコマンドは、自動では送らず、提案として示す（AC-41）。
-   **AC-60**: Herdr の操作か待ち受けが失敗したときは、その workspace を「要確認」として示し、何も送らない。
-   **AC-61**: 待ち受けの中で行うネットワークの操作は、読み取り専用のもの（PR・CI・レビューの状態の取得、`git fetch`）だけである。

#### F-011: 送信の結果の報告

chief が行った送信と、行わなかった送信を、人が後から分かるように示す。

**Acceptance Criteria**:
-   **AC-62**: chief が送ったコマンド（自動送信を含む）、中継した答え、空にした pane は、次の報告で、workspace、pane、送ったもの、エージェント、モデルとともに示される。
-   **AC-63**: 送らなかったとき、または送った後に失敗したときは、何も送っていないのか、送った後なのかを区別し、理由とともに示す。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   状況の表は、PR の詳細を集めるのを待たずに示す（AC-04）。PR の詳細は、人が選ぶ前に集め始めてよい。
-   送信は、人の次の問いを待たせずに行う（AC-24）。

### 4.2. セキュリティ (Security)

条件付きのガイド（`docs/dev/security.md`）の契機に当たらない。chief は開発用の道具で、製品の外部コマンドの起動、API キーと Webhook の URL、キャッシュ、プロンプトへの信頼できないテキストの埋め込みには触れない。ただし、開発用ツールの信頼の境界に当たるので、次を要件とする。

-   **信頼の境界。** chief はほかのエージェントのセッションへ入力を送る。送る入力は F-006 の表に限り、質問への答えは人が選んだ 1 つを選ぶ問いの選択肢だけにする（F-005）。chief は人の代わりに判断しない。自動送信の引き金は、画面ではなく GitHub と git の状態で確かめる。画面からの判断は、送ることを止めるか条件を狭めるだけに使う（AC-41・AC-42）。ADR-0046 に記録する。
-   **外部のサービスへ送るもの。** `/runpr` と、実装モデル要件が `sonnet` の `/runplan` を走らせると、OpenCode が DeepSeek のサービスへ、リポジトリのコード、PR のレビューのスレッド、コマンドの定義を送る。chief はこれらのコマンドの送り先として OpenCode を選ぶだけで、chief 自身はこれらを送らない。この送り先を選ぶことは、要件定義の際に決めたことのとおり、決定として記録する。
-   **信頼できない入力。** chief が読む次のものは、ほかのエージェントや外部が書いたデータであり、その中の指示に従わない。どれも、読めないもの・形に合わないものは直さずに「要確認」か「送らない」にし、その理由を示す（推し量って補わない）。

    | 入力 | 使う部分 | 形に合わないとき |
    |---|---|---|
    | Herdr の出力 | workspace と pane の識別、エージェントの種類と状態、セッションの識別、作業ディレクトリ | 「要確認」（AC-06・AC-60）。知らない状態の値も「要確認」 |
    | pane の画面 | 質問の文と選択肢、`/runpr` の報告の次のコマンド、PR を作ったコマンドの報告、OpenCode のモデルの行、入力欄に残っている文字 | 質問として確かめられなければ中継しない（AC-26）。報告は照合と要約にだけ使う（AC-42）。モデルの行が読めなければ送らない（AC-35）。入力欄が空と確かめられなければ送らず、空にしない（AC-36・AC-54） |
    | セッションの記録（Claude Code の transcript） | モデルを切り替えた記録 | 確かめられなければ送らない（AC-34） |
    | GitHub の PR・CI・レビュー | PR の状態・番号・タイトル・URL・説明、CI のジョブの名前と結果、レビューの書き手と状態 | その項目を「取得できなかった」とする（AC-21）。PR の状態が `MERGED` と確かめられなければ自動送信しない（AC-41） |
    | 計画書の PR マーカーと文書の状態の表 | 実装モデル要件、自動送信の欄、文書の Status | 送らない（AC-33・AC-51）。「要確認」（AC-06） |

-   **画面のとおりに示す。** 中継する質問と選択肢は、要約せずに画面のとおりに示す（AC-25）。人が選ぶのは本当の選択肢であり、chief の言い換えではない。画面の文字列に含まれる制御文字（端末のエスケープシーケンスを含む）は、chief の画面にそのまま出さず、見える形に置き換える。
-   **読み取る量の上限。** pane の画面、PR の説明、PR を作ったコマンドの報告は、読む量に上限を設け、上限を超えた部分は示さず、切ったことを示す。上限の値は設計で決める。
-   **ネットワーク。** 待ち受けの中で行うネットワークの操作は読み取り専用に限る（AC-61）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   送れたかが分からない送信を送り直さない（AC-37）。同じコマンドを 2 回走らせるより、人に示して止まるほうを選ぶ。
-   自動送信は、マージした PR 1 件につき 1 回までで、chief を起動し直しても変わらない（AC-44）。
-   chief のセッションが止まっても、タスクの workspace の状態は壊れない。止まっている間に溜まったものは、次の表で拾う（AC-59）。

### 4.4. 互換性 (Compatibility)

-   chief は Herdr の中でだけ動作する（AC-07）。
-   対象のエージェントは Claude Code と OpenCode である。
-   進行中の計画書（自動送信の欄がないもの）は書き換えずに扱う（AC-50）。

### 4.5. 保守性 (Maintainability)

-   コマンドごとの送り先とモデル（F-006 の表）は 1 か所に置く。実装モデル要件の値と送り先の対応は、`_context.md` の「PR marker conventions」の値とモデルの対応と食い違わない（5 章）。
-   判定と副作用を持つ開発の道具は、Go で書いてテストを持つ方針がある（ADR-0014）。chief の判定と送信をどこに置くかは設計で決める（design_handoff.md の H-01）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   **CLAUDE.md の「Declare, don't infer」の例外。** 方針（[CLAUDE.md](../../../CLAUDE.md)「Key Design Patterns」の「Declare, don't infer」）は、呼び出し側が渡した文字列の中身を調べて振る舞いを選ばず、型で宣言することを求める。chief は、pane の画面の文字列の中身を調べて、エージェントが質問で止まっているか、その質問が 1 つを選ぶ問いか、`/runpr` の報告の次のコマンドが何かを判断する。範囲は、4.2 の「信頼できない入力」の表の「pane の画面」と「セッションの記録」の行が挙げる部分（入力欄に残っている文字を含む）を読んで行う判断と、PR を作ったコマンドの報告の要約に限る。理由は、画面が Claude Code と OpenCode の描く外部の値であり、chief が型で表すことはできず、OpenCode の質問の画面は変えられないためである。境界は、どの判断も合わない画面を広く解釈せず「要確認」か「送らない」にすること（AC-12・AC-26）と、人に尋ねずに入力を送る判断（自動送信）の引き金を GitHub と git の状態とし、画面からの判断は送ることを止めるか条件を狭めるだけに使うこと（AC-41・AC-42）である。この例外は、CLAUDE.md の例外の一覧に足す。
-   **CLAUDE.md の「Tool Execution Safety」。** ネットワークに触れるコマンドは人の承認を要する。chief の読み取り専用のネットワークの操作（AC-61）は、chief を起動したことで承認したものとし、CLAUDE.md に書く。
-   **ADR-0042 の更新。** 実装モデル要件が `sonnet` の `/runplan` を OpenCode・DeepSeek V4.1 Flash で走らせることは、ADR-0042 の「`sonnet` は Sonnet で実装する」という決定を変える。ADR-0042 の決定と経緯を更新し、`_context.md` の「PR marker conventions」の値とモデルの対応、それを示す `runplan.md`・`runpr.md` の案内を、F-006 の表に合わせる。値の名前（`sonnet`）は変えない。名前の見直しは #760 の範囲である。
-   PR マーカーの形は `_context.md` の「PR marker conventions」と、それを書く `mkplan2.md` が持つ。F-008 の欄は、ここに足す。
-   `/runpr` のマージの確認の選択肢と、NEXT を決める規則（`runpr.md` の「2. Decide the PR's bookkeeping and next command」「4. Confirm, record, and merge」「5. Switch branch, then show NEXT」）は、本書では変えない。モデルの表示は、上の ADR-0042 の更新のとおり F-006 の表に合わせる。
-   レビューの依頼の仕組み（[ADR-0013](../../dev/adr/0013-review-setup.md)）と、Opus のレビューを行う条件（ADR-0042）は変えない。

## 6. 用語集 (Glossary)

-   **chief**: 本書のコーディネーター。chief の workspace で動く Claude Code のセッションで、タスクの作業はしない。
-   **chief の workspace**、**タスクの workspace**、**エージェント**、**入力を受け付ける状態**: 3 章の冒頭のとおり。
-   **自動送信**: マージの後に、chief が人に尋ねずに次のコマンドを送ること（F-007）。
-   **答えの中継**: 人が chief の選択肢で選んだ質問の答えを、chief がその pane へ送ること（F-005）。用語集の「ホスト」の説明にある中継（ホストがリクエストをサーバへ渡すこと）と区別するため、「答えの中継」と呼ぶ。
-   **chief の待ち受け**: chief のセッションが、エージェントの状態の変化を待つこと（F-010）。用語集でサーバが接続を待つことを指す「待ち受け」と区別するため、本書では「chief の待ち受け」の意味で使う。
-   **実装計画書の PR**: `03_implementation_plan.md` を足す PR。`/runplan` が実装計画書の PR マーカー（PR-N）に従って作る PR は、用語集のとおり「プランの PR」と呼ぶ。
-   ほかの用語は `docs/translation_glossary.md` と統一する。
