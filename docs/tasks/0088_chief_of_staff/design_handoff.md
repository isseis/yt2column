# 設計への申し送り（0088）

要件定義の段階で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: chief の判定と副作用をどこに置くか

**懸念:** 状態の区分（F-001・F-002）、自動送信の条件（F-007）、送信の手順と送る前の確かめ（F-006・F-009）は、判定と副作用を持つ。試作はこれをコマンドの定義とシェルスクリプトに置き、エージェントが手順を読んで実行した。

**なぜ重要か:** [ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md) は、判定と副作用を持つ開発の道具を Go で書いてテストを持つ方針を決めている。エージェントが手順を読み違えると、送ってはいけない入力が送られうる（4.2 の信頼の境界）。

**候補:** 判定と送信を `cmd/<名前>` と `internal/<名前>` の Go の道具に置き、コマンドの定義（`.claude/commands/` の下）は道具の呼び出しと人への問いだけを持つ。道具の引数・出力・終了コードを、コマンドの定義と文書のガードが読む契約にする（ADR-0014）。

**関連:** F-001・F-002・F-006・F-007・F-009、AC-27・AC-30〜AC-33・AC-35

## H-02: エージェントが人を待っていることの見分け方

**懸念:** Herdr は Claude Code の質問を `blocked` と報告するが、OpenCode は質問を文章で示して `done` か `idle` になる（試作で観測）。`/runpr` のマージの確認も、OpenCode では `done` で示される。

**なぜ重要か:** 状態だけで判断すると、マージの確認を見落とす（AC-08・AC-09）。画面の文字列から推し量ると、CLAUDE.md の「Declare, don't infer」とぶつかり、画面は信頼できない文字列である（4.2）。

**候補:** エージェントの側が、待っていることを決まった形で示す（例：コマンドの定義が最後に決まった形の行を出す、Herdr の状態を明示して変える手段を使う）。画面を読むしかない場合は、読む範囲と形を決め、合わないものは「要確認」にする（AC-06）。

**関連:** F-002、AC-07〜AC-10

## H-03: モデルが切り替わったことの確かめ方

**懸念:** Claude Code の `/model` の確認は、`herdr agent read` が返す画面に残らない。試作は、セッションの記録（transcript）の `Set model to` の行で確かめた。記録は少し遅れて書かれる。OpenCode はコマンドでモデルを切り替えられず、画面のモデルの行を読んで比べた。

**なぜ重要か:** モデルを確かめずに送ると、違うモデルでコマンドが走る（AC-30・AC-31）。

**候補:** transcript の場所と行の形を、`/clear` の前後のセッションの違いとあわせて確かめる。遅れは決まった回数と間隔で確かめ直す。OpenCode のモデル名は語ごとに比べる。

**関連:** F-006、AC-30・AC-31

## H-04: 待ち受けの仕組み

**懸念:** `herdr agent wait` は、`blocked` のエージェントではすぐに戻る（試作で観測）。chief のセッションの中で、複数のエージェントを同時に待つ必要がある。

**なぜ重要か:** 質問で止まったエージェントの待ち受けがすぐ終わると、その後の変化を拾えない（AC-50）。

**候補:** 質問から抜けるのを待ってから、止まるのを待つ二段の待ち方にする。待ち受けはバックグラウンドで行い、人への問いを妨げない。

**関連:** F-010、AC-49〜AC-52

## H-05: 中継の確かめと送り方

**懸念:** 人が選んだ答えを送る直前に、質問と選択肢が人に示したときと同じであることを確かめる（AC-22）。選択肢を選ぶ入力（矢印のキー、番号、Enter など）の送り方は、Claude Code と OpenCode で違いうる。1 つの画面に複数の問い（タブ）がある。

**なぜ重要か:** 質問が変わった後に送ると、人が選んでいない答えになる（AC-23）。

**候補:** 示したときの質問と選択肢の文字列を控え、送る直前に読み直して一致を比べる。選択肢を選ぶ入力は、選択肢の番号から決め、選択肢の文字列を入力として送らない（4.2）。権限の確認と自由に書く答えの見分け方も決める（AC-24・AC-25）。

**関連:** F-005、AC-21〜AC-26

## H-06: 自動送信の欄の名前と値

**懸念:** PR マーカーに足す欄の名前と 2 つの値の綴りを決める（AC-41）。`mkplan2.md` の step 4 で値を決める原則（どういう計画なら「自動で送らない」にするか）も要る。

**なぜ重要か:** 値の綴りが決まらないと、chief が読めない値として扱い、自動送信が止まる（AC-44）。

**候補:** 欄は `**マージ後の自動実行**`、値は `する`・`しない`。「しない」にするのは、PR のマージの後に `/runplan` の外の作業（対話のセッション、手での確かめ）を挟む計画のときとする。`_context.md` の「PR marker conventions」、`mkplan2.md`、`mkplan.md`、`_lib/simple-process.md` を変える。

**関連:** F-008、AC-41〜AC-44

## H-07: 「レビュー省略可」の基準

**懸念:** 実装計画書の PR を「レビュー省略可」と示す基準を、設計で決める（AC-19）。

**なぜ重要か:** 要件定義書や設計書を `draft` に戻す計画の PR（2026-11-11 の 0083・0084）は、決定の変更を含み、人が読むべきである。

**候補:** PR の差分が `03_implementation_plan.md` だけで、要件定義書・設計書・ADR を変えていないとき。

**関連:** F-004、AC-19

## H-08: PR の詳細とまとめの控え

**懸念:** PR を作ったコマンドのまとめは pane の画面にあり、F-009 で pane を空にすると消える。試作は、人が選ぶ前に詳細を集めて一時的なファイルに控えた。

**なぜ重要か:** 控えがないと、空にした後にまとめを示せない（AC-48）。控えは信頼できない文字列を含む（4.2）。

**候補:** `/runpr` を送る前に、その PR の詳細を集めて控える。控えの置き場所はリポジトリの外（セッションの一時的なディレクトリ）にし、リポジトリに入れない。

**関連:** F-004・F-009、AC-14〜AC-16・AC-48

## H-09: 待っている時間の測り方

**懸念:** 同じ種類の中で、待っている時間の長い順に並べる（AC-11）。いつから待っているかを知る手段が要る。

**なぜ重要か:** 測れないと、並べ方が決まらない。

**候補:** Herdr のエージェントの状態の変化の順番（`state_change_seq` など）や、chief が最初に見つけた時刻を使う。chief のセッションが止まっていた間に増えたものは、次に見つけた時刻で並べる。

**関連:** F-003、AC-11

## H-10: 通知の重複の防ぎ方

**懸念:** 同じ人の判断を待つものを 2 回以上通知しない（AC-51）。待ち受けのたびに状況を読み直すので、同じものを何度も見つける。

**なぜ重要か:** 同じ通知が続くと、通知に注意が払われなくなる。

**候補:** 通知したものを、workspace・種類・PR か質問の識別でセッションの中に控える。

**関連:** F-010、AC-51

## H-11: Herdr への依存

**懸念:** chief は Herdr の CLI（`herdr agent get`・`read`・`prompt`・`wait`）の出力の形に依る。Herdr はリポジトリの外の道具で、出力の形が変わりうる。

**なぜ重要か:** 形が変わったときに、黙って誤った状態を示すおそれがある（AC-06）。

**候補:** 読む値を決め、読めないときは「要確認」にする。Herdr の外では動かない（4.4）。外部の道具への依存として ADR-0046 に記録する。

**関連:** F-001・F-002、AC-06
