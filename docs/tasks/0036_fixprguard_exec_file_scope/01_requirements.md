## 1. 概要 (Overview)

**目的:** 本書は、ガードツール `fixprguard` の範囲の規則を改めるための要件を定義する（[#425](https://github.com/isseis/yt2column/issues/425)）。改めた規則では、下の階層に置かれた指示ファイルと Go のビルドの入力が範囲外になる。あわせて、規則 2・3 が範囲に入れるファイルを、決まった種類だけに限る。用語の意味は 6 章で定める。

**背景:**

`fixprguard inspect` は、`/fixpr` の修正のフェーズが変えたファイルを、処理したスレッドの `path` から決まる範囲と照らす。範囲外の変更があれば、終了コード `3` で利用者の確認に回す（`docs/dev/developer_guide/fixprguard_guide.md:156`）。範囲の規則は、タスク 0030（[#395](https://github.com/isseis/yt2column/issues/395)）で決まった（0030 `02_architecture.md` 3.6）。次の 3 つのどれかに当たる変更が範囲に入る（`internal/fixprguard/scope.go:16-28`）。

1.  `path` そのもの。
2.  `path` と同じディレクトリのファイル（サブディレクトリの中は含まない）。
3.  `path` が `docs/tasks/NNNN_<name>/` の中にあれば、そのディレクトリの下のすべてのファイル。

ただし、実行関連ファイルは、`path` そのものでなければ範囲外とする。名指しされた想定外の著者のスレッドでは、`path` そのものでも範囲外とする（0030 `02_architecture.md` 3.6 の規則 4。`internal/fixprguard/scope.go:170-172`）。

実行関連ファイルの定義は、名前の拒否リストである（`internal/fixprguard/scope.go:39-54`）。規則 2・3 は、このリストに当たらないファイルをすべて通す（`internal/fixprguard/scope.go:181-189`）。ところが、リストは次の点で不十分である。

-   `CLAUDE.md`・`AGENTS.md` と、名前が `.` で始まるファイルは、リポジトリの最上位にあるときだけ当たる（`internal/fixprguard/scope.go:48`・`:119`）。
-   `.claude/` は、最上位のディレクトリだけが当たる（`internal/fixprguard/scope.go:45`・`:114-118`）。
-   Go のビルドの入力（`.syso`・`.s`・`.c` など）は、リストにない。

そのため、指示ファイルや Go のビルドの入力が下の階層にあると、範囲内と判定される。issue #425 は、`inScope` と `isExecutionRelated` を直接呼んで、次の判定を確かめた（一部を抜粋した）。

| 変更したパス | スレッドの `path` | 名指し | 今の判定 |
|---|---|---|---|
| `internal/writer/CLAUDE.md` | `internal/writer/writer.go` | なし | 範囲内 |
| `CLAUDE.local.md` | `README.md` | なし | 範囲内 |
| `docs/tasks/0030_x/.claude/commands/evil.md` | `docs/tasks/0030_x/01_requirements.md` | なし | 範囲内 |
| `docs/tasks/0030_x/CLAUDE.md` | `docs/tasks/0030_x/01_requirements.md` | あり | 範囲内 |
| `internal/writer/foo.syso` | `internal/writer/writer.go` | なし | 範囲内 |

issue #425 によれば、影響は次のとおりである。

-   Claude Code はサブディレクトリの `CLAUDE.md` を読むので、そこに書かれた指示は commit・push されて残る。
-   `.syso` はパッケージのビルドに無条件でリンクされる。`make test` は `-race` を付けて実行するので外部リンクになり（`Makefile:84`）、ELF のコンストラクタがテストバイナリの起動時に実行されうる。名指しのスレッドで `.go` のファイルを範囲外にする規則（`internal/fixprguard/scope.go:182-184`）を、`.syso` で迂回できる。
-   下の階層の `.gitignore` は、以後の変更を git から隠せる（0030 `02_architecture.md` 5.3「無視されるファイル」）。

対応 issue: [#425](https://github.com/isseis/yt2column/issues/425)（関連: [#395](https://github.com/isseis/yt2column/issues/395)、タスク `0030_fixpr_untrusted_threads`。[#424](https://github.com/isseis/yt2column/issues/424)、タスク `0034_fixprguard_ignored_files`）

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。どの変更が範囲に入り、どの変更が範囲外になるか、利用者に何が示されるか、ガイドに何が書かれるかである。次のことは設計（`02_architecture.md`）で決める。

-   判定の順序と、定義を持つデータの形
-   ガイドへの定義の載せ方と、文書のガードがそれを確かめる手段
-   テストの手段

要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #425 で決めたこと:**

-   **完了条件:** issue の表（AC-12 に全行を載せる）の変更したパスが、すべて範囲外になる。例外は、変更したパスがスレッドの `path` そのもので、かつそのスレッドが信頼する著者のスレッドである場合だけである（AC-13）。`make test`・`make lint`・`doc-guard` が通る。
    -   理由: 表の各行は、規則 4 が範囲外にしようとしたファイルの種類に当たる。
    -   表の 10 行のうち、`.md` でない 5 行（`.syso`・`.s`・`.c`・`.gitattributes`・`.gitignore`）は、許可リスト（F-002）だけでも範囲外になる。拒否リストを広げたこと（F-001）は、規則 1 の位置の入力（AC-13）と、規則 2・3 の位置の `.md` の入力（AC-01）で確かめる。
-   **指示ファイルと git の設定を、どの階層でも実行関連ファイルとする:** `claude.md`・`agents.md`・`claude.local.md`・`.claude/`（ディレクトリの名前として）・`.gitattributes`・`.gitignore` が対象である。
    -   理由: Claude Code はサブディレクトリの指示ファイルを読む。下の階層の `.gitignore` は、以後の変更を隠せる。
-   **定義を変えたら、一覧・ガイド・ガードを合わせる:** `ExecutionFilePatterns`（`internal/fixprguard/scope.go:60-75`）、`fixprguard_guide.md` 6 章の表、`cmd/fixprguard/docs_test.go` のガードを更新する。
    -   理由: ガイドは定義と同じ一覧を載せると約束している（`docs/dev/developer_guide/fixprguard_guide.md:219`）。
-   **表の各行をテストに入れる:** 壊して失敗を確かめる（`CLAUDE.md`「Testing Strategy」）。

**要件定義の際に決めたこと（2026-10-22）:**

-   **拒否リストを広げ、規則 2・3 には許可リストも加える:** issue は「拒否リストを拡張子の許可リストに反転する案を検討する」とした。本書は、拒否リストを広げたうえで（F-001）、規則 2・3 が範囲に入れるファイルを許可リストに限る（F-002）。
    -   理由: 拒否リストは、原理的に網羅できない（issue #425）。許可リストに当たらないファイルは、利用者の確認に回る。
    -   受け入れる負担: 0030 は、範囲を `path` だけに絞る案を退けた。同じディレクトリのテストを直すたびに確認が入り、`/runpr` の繰り返しのたびに利用者を待たせるためである（0030 `01_requirements.md:55`）。本書でも、Go のテストは許可リストの (c)（AC-06）で今までどおり確認なしに通る。一方、`.ts` のテスト（`extension/src/` の `*.test.ts`）など、Go でない隣のファイルの修正では、毎回確認が入る。この負担は、レビュアーが受け入れた（2026-10-22）。
    -   拒否リストを残す理由: 規則 1（`path` そのもの）と名指しのスレッドの扱いは、拒否リストで決まる。許可リストは `.md` を通すので、`CLAUDE.md` のような `.md` の指示ファイルは拒否リストで止める必要もある。
-   **許可リストは issue の例だけにする:** 規則 2・3 が範囲に入れるのは、`.md`・`.txt` のファイル、`testdata` のディレクトリの下のファイル、既存の `.go` の規則（`internal/fixprguard/scope.go:182-184`）に当たる `.go` のファイルだけである。`.tmpl`・`.ts`・`.json`・`.sh`・`.py` などは、規則 2・3 では範囲に入らない。
    -   理由: 範囲を最小にし、ほかの種類は利用者の確認に回す。プロンプトテンプレート（`.tmpl`）を確認なしで通す案は採らない。
-   **Go のビルドの入力は、`.go` の規則ではなく実行関連ファイルとする:** issue の「やること」は、`.syso` などを「`.go` と同じ規則」にするとした。本書は、これらを実行関連ファイルとして扱う。範囲に入るのは、信頼する著者のスレッドの `path` そのものであるときだけである。
    -   理由: `.go` の規則では、`foo.syso`（スレッドの `path` は `writer.go`、名指しなし）が範囲内のまま残り、issue の完了条件と食い違う。
    -   このリポジトリには、この種類のファイルは 1 つもない（2026-10-22 に `git ls-files` で確かめた）。そのため、正当な修正で確認が増えることはない。
-   **Go のビルドの入力の拡張子は、Go が扱うもの全部にする:** issue が挙げた 7 種類（`.syso`・`.s`・`.c`・`.h`・`.cc`・`.m`・`.S`）に、Go がパッケージのビルドで扱うほかの拡張子を加える（AC-03）。
    -   理由: issue の 7 種類だけでは、`.cpp`・`.hpp` などで同じ迂回ができる。拡張子の一覧は `go help filetype` と、`go/build` の `Package` の `FFiles`（Fortran）を根拠とする。
-   **自動レビュアーが既定で読む指示ファイルの名前も加える:** issue が挙げた 3 つの名前に、`agent.md`・`gemini.md`・`agents.override.md` を加える（AC-01）。
    -   理由: 信頼する自動レビュアーは `coderabbitai` と `chatgpt-codex-connector` である（`.claude/commands/_context.md:185`）。CodeRabbit は、既定で `AGENT.md`・`GEMINI.md` なども指示として読み、Codex は `AGENTS.override.md` も読む。以上の挙動は、要件定義の際のレビューで挙がった知識によるもので、ベンダーの文書では確かめていない。これらは `.md` なので、加えなければ許可リストを通る。すると、次のレビューのスレッド（信頼する著者のスレッド）を操作されうる。
-   **`.` で始まる要素を、どの階層でも実行関連ファイルとする:** issue が挙げた `.claude/`・`.gitattributes`・`.gitignore` に限らない。パスのどの要素（ファイルの名前またはディレクトリの名前）でも、`.` で始まれば実行関連ファイルとする。
    -   理由: ツールは、下の階層の `.` で始まるファイルも読む。たとえば direnv は、下のディレクトリの `.envrc` を読む。`.npmrc` も下の階層に置ける。最上位で `.` で始まるファイルを実行関連ファイルとする今の規則（`internal/fixprguard/scope.go:119`）を、どの階層にも広げる。
-   **`inspect` の出力の形は変えない:** 範囲外になった理由（拒否リストか、許可リストに当たらないか）は出力しない。`outOfScope` の要素は今の項目のままである（`docs/dev/developer_guide/fixprguard_guide.md:156`）。
    -   理由: 利用者は、一覧を見て続けるかを判断できる。出力の契約を変えずに済む。
-   **`protocol` の番号を上げる:** 本タスクの前のツールは、新しい文書から呼ばれると終了コード `2` で止まる（AC-16）。
    -   理由: 前のツールは範囲を広く判定する。番号が同じなら、入れ直していない利用者は、古い規則で判定されていることに気づけない（`docs/dev/developer_guide/fixprguard_guide.md:46`）。入れ直しの手順はガイド 3 章にある（`docs/dev/developer_guide/fixprguard_guide.md:52`）。
-   **タスク 0034 の対象は 0034 で決める:** 本書の定義の変更は、範囲の規則に影響する。0034（PR #429、`draft`）が、git が無視するファイルのうちどれを対象にするか（本書の定義に従うか、部分集合を使うか）は、0034 の要件で決める。
    -   理由: 0034 の要件定義書は、対象を「実行関連ファイルの定義全体」とし、定義そのものは変えないとしている。AC-02 の規則に従えば、無視される `extension/node_modules/` の下の `.bin/` や `.DS_Store` も 0034 の対象になる。対象の数と止まり方への影響は、0034 の要件で扱うのが適切である。
-   **指示として読まれる文書は、実行関連ファイルにしない:** 手順書や自動レビュアーが読んで従うよう指示されている文書は、実行関連ファイルとせず、残余のリスクとして記録する（4.2）。
    -   理由: これらの文書は、正当な修正でもよく変わる。変更は PR の diff として人が確かめる。

以下の決定は、要件定義書を作成する際に、安全側の既定として選んだ。PR のレビューで確かめてほしい。

-   **許可リストの照合は、大文字と小文字を区別する:** `README.MD`・`TestData/` は許可リストに当たらない（AC-09）。
    -   理由: 許可リストは範囲を広げる側の規則なので、狭いほうが安全である。リポジトリの既存のファイルは、`.md`・`.txt`・`testdata` をすべて小文字で使う（2026-10-22 に `git ls-files` で確かめた）。拒否リストは今までどおり ASCII の大文字小文字を同一視して照合する（`internal/fixprguard/scope.go:37-38`）。
-   **`.` で始まるディレクトリの中は、すべて実行関連ファイルとする:** `.` で始まる要素の規則は、ディレクトリの名前にも当たる（AC-02）。
    -   理由: `.claude/`・`.github/` のように、`.` で始まるディレクトリはツールの設定を置く場所として使われる。issue が挙げた `.claude/` もこれに含まれる。
-   **0030 の設計書と要件定義書に、規則が変わったことの注記を加える:** 対象は 0030 `02_architecture.md` 3.6 と 0030 `01_requirements.md` F-004 で、本タスクで規則が変わったことと、本書への参照を加える（AC-18）。
    -   理由: ガイドは、設計の背景として 0030 の設計書を挙げる（`docs/dev/developer_guide/fixprguard_guide.md:5`）。古い規則のまま残すと、読み手が今の規則を誤解する。
    -   注記は決定を変えないので、0030 の文書の状態は `approved` のままとする（要件定義のプロセスのガイド「Editing an approved document」の Editorial correction）。
-   **ガイドの説明と残余のリスク、用語集を改める:** ガイドの実行関連ファイルの説明に、指示ファイルを加える（AC-17）。4.2 の残余のリスクをガイド 7.2 に書く（AC-20）。新しい用語を用語集に加える（AC-21）。
    -   理由: 定義が指示ファイルを含むようになるので、「build checks と CI が読むファイル」という今の説明（`docs/dev/developer_guide/fixprguard_guide.md:219`）は定義と合わなくなる。残余のリスクがガイドになければ、利用者がツールの守りを誤解する。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   どの階層に置かれた指示ファイル・`.` で始まる要素を含むパス・Go のビルドの入力も、規則 2・3 では範囲に入らないようにする。
-   名指しされた想定外の著者のスレッドで、`.go` のファイルを範囲外にする規則を、Go のビルドの入力で迂回できないようにする。
-   規則 2・3 が範囲に入れるファイルを決まった種類に限り、拒否リストに載っていない新しい種類のファイルが、確認なしに commit されないようにする。

### 2.2. スコープ (In Scope)

-   実行関連ファイルの定義を広げる（F-001）。
-   規則 2・3 に許可リストを加える（F-002）。
-   issue の表の各行を範囲外にする（F-003）。
-   `inspect` の出力の形と終了コードの意味を保ち、`protocol` の番号を上げる（F-004）。
-   ガイド（日英）・文書のガード・0030 の文書・用語集を新しい規則に合わせる（F-005）。

### 2.3. スコープ外 (Out of Scope)

-   **git が無視するファイルの検出:** 無視されるファイルへの書き込みは、変更の集合に入らない。これはタスク 0034（[#424](https://github.com/isseis/yt2column/issues/424)）が扱う。0034 の対象と本書の定義の関係も、0034 で決める（1 章の決定）。
-   **指示として読まれる文書の保護:** 手順書や自動レビュアーが読むよう指示されている文書は、実行関連ファイルにしない（1 章の決定）。残余のリスクとして 4.2 に記録する。
-   **規則 1（`path` そのもの）の変更:** 実行関連ファイルでないファイルは、今までどおり、`path` そのものなら範囲に入る。種類は問わない。
-   **範囲の規則以外の、ガードツールの振る舞い:** 著者の判定、基準値、`finish`・`push` の確認は変えない。
-   **AC-01 に挙げない名前の指示ファイル:** 信頼する自動レビュアーと Claude Code が読む名前のほかは、対象にしない。名前が `.` で始まるもの（`.cursorrules` など）と、`.` で始まるディレクトリの中のもの（`.github/copilot-instructions.md` など）は、AC-02 に含まれる。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

以下で「判定」とは、変更したパス・変更の種類・スレッドの `path`・名指しの有無から、その変更が範囲に入るかを決めることをいう。判定の結果は、`fixprguard inspect` の `outOfScope` に現れる（範囲外ならその要素になる）。各 AC の例は、断りがなければ、変更が通常のファイルの追加または変更である場合を示す。範囲の規則は、追加・変更・削除のどれにも同じく働く。

#### F-001: 実行関連ファイルの定義を広げる

実行関連ファイルの定義に、どの階層でも当たる 3 種類を加える。指示ファイルの名前、`.` で始まる要素、Go のビルドの入力の拡張子である。拒否リストの照合は、今までどおり ASCII の大文字小文字を同一視して行う。実行関連ファイルであることは、次の 2 つの判定で観測できる。

-   規則 1 の位置（変更したパスがスレッドの `path` そのもの）では、信頼する著者のスレッドなら範囲内、名指しのスレッドなら範囲外になる。実行関連ファイルでないファイルは、名指しのスレッドでも範囲内になる（AC-10）。
-   規則 2・3 の位置では、許可リストに当たっていても範囲外になる。

**Acceptance Criteria**:
- **AC-01**: 名前が `claude.md`・`agents.md`・`claude.local.md`・`agent.md`・`gemini.md`・`agents.override.md` のどれか（ASCII の大文字小文字を同一視する）のファイルは、どの階層にあっても実行関連ファイルとして扱われる。
    -   規則 2・3 の位置の例（名指しなし。どれも範囲外）:
        -   スレッドの `path` が `internal/writer/README.md` のときの `internal/writer/CLAUDE.md`・`internal/writer/AGENTS.md`・`internal/writer/Gemini.md`
        -   `README.md` のときの `CLAUDE.local.md`
        -   `docs/tasks/0030_x/01_requirements.md` のときの `docs/tasks/0030_x/sub/agents.override.md`
    -   規則 1 の位置の例: 変更したパスとスレッドの `path` がどちらも `internal/writer/CLAUDE.md` のとき、信頼する著者のスレッドなら範囲内、名指しのスレッドなら範囲外になる。
- **AC-02**: パスの要素（ディレクトリの名前とファイルの名前）のどれかが `.` で始まるファイルは、どの階層にあっても実行関連ファイルとして扱われる。`.claude/`・`.gitattributes`・`.gitignore` はこれに含まれる。
    -   規則 2・3 の位置の例（名指しなし。どれも範囲外）: スレッドの `path` が `docs/tasks/0030_x/01_requirements.md` のときの `docs/tasks/0030_x/.claude/commands/evil.md` と `docs/tasks/0030_x/.notes.md`。

- **AC-03**: 名前が次の拡張子のどれかで終わるファイルは、どの階層にあっても実行関連ファイルとして扱われる。拡張子は ASCII の大文字小文字を同一視して照合するので、`.S`・`.F` も当たる。

- **AC-04**: 今の定義（`internal/fixprguard/scope.go:39-54`）に当たるファイルは、引き続き実行関連ファイルとして扱われる。例: `Makefile`・`internal/x/go.mod`・`build/rules.mk`・`.github/workflows/ci.yml`・`extension/scripts/has-extension-changes.sh`・`extension/package.json`。どれも、変更したパスとスレッドの `path` が同じとき、信頼する著者のスレッドなら範囲内、名指しのスレッドなら範囲外になる。

    -   **`testdata` の下のファイル:** テストは `testdata` の下のファイルを読む。実行関連ファイルを除き、種類を問わず規則 2・3 で範囲に入る。テストがそれを実行しない限り、実行されるコードにはならない。

## 6. 用語集 (Glossary)

用語は `docs/translation_glossary.md` と統一する。本書は、範囲外の変更・信頼する著者のスレッド・想定外の著者のスレッド・名指し・ガードツールを、用語集の定義どおりに使う。「名指しのスレッド」は、名指しされた想定外の著者のスレッドの略である。次の用語は本書で使う意味を定める（AC-21）。

-   **実行関連ファイル（コマンドの実行に関わるファイル）:** 範囲の規則が、`path` そのものでなければ範囲外とするファイル。次の 3 つである。(1) build checks と CI が設定として読む、またはコンパイル・実行するファイル。(2) 指示ファイル。(3) `.` で始まる要素を含むパス。定義は F-001 と `internal/fixprguard/scope.go` にある。
-   **拒否リスト:** 実行関連ファイルの定義を、名前・拡張子・パスの要素の一覧として見たときの呼び方。
-   **許可リスト:** 規則 2・3 で範囲に入りうるファイルの種類（AC-06）。
-   **指示ファイル:** Claude Code や自動レビュアーが、置かれたディレクトリへの指示として自動で読むファイル（AC-01 の名前のもの）。
-   **Go のビルドの入力:** Go がパッケージのビルドで、`.go` のファイルのほかに扱うファイル（AC-03 の拡張子）。
