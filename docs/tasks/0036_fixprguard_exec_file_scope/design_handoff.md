# 設計への申し送り：fixprguard の範囲の規則で、下の階層の指示ファイルとビルドの入力を範囲外にする

要件定義の際に挙がった設計の事項である。`02_architecture.md` は、各項目にどう対応したか、または対応しない理由を記録する。

-   **H-01: `protocol` の番号.** 範囲の規則が変わっても、引数と出力の形は変わらない（AC-14）。ガイド 9 章の規則（`docs/dev/developer_guide/fixprguard_guide.md:287-292`）では、`Protocol` を上げる必要はない。ただし、古いツールを入れたままの利用者は、新しい文書から呼んでも古い規則で判定され、それに気づかない（ガイド 3 章）。番号を上げて古いツールを止めるか、上げずにガイドの案内に任せるかを決める。
-   **H-02: 判定の順序.** 今の順序は、実行関連、`path` との一致、ASCII でない文字、`.go`、同じディレクトリ・タスクのディレクトリである（`internal/fixprguard/scope.go:169-190`）。許可リストをどこに入れるかを決める。`.go` のファイルには許可リストの (b)（`testdata`）を適用しない（AC-06）。
-   **H-03: 定義を持つデータの形と、ガイドへの載せ方.** `ExecutionFilePatterns` が出力する形（`internal/fixprguard/scope.go:56-75`）では、`.claude/` は最上位のディレクトリを表す。どの階層でも当たる `.` で始まる要素、指示ファイルの名前、拡張子を、ガイドの表にどう表すかを決める。最上位だけの規則（`/.*`・`/claude.md`・`/agents.md`）と、`.claude/`・`.github/` のディレクトリの規則は、新しい規則に含まれる。これらを表に残すか、まとめるかも決める。許可リストの項目を一覧に出す関数と、文書のガード（`cmd/fixprguard/docs_test.go:42-58`）がそれを確かめる手段も決める（AC-18）。
-   **H-04: タスク 0034 との調整.** 0034 の要件定義書（PR #429）は、コマンドの実行に関わるファイルの定義を、無視されるファイルの基準値の対象を決めるのに使う。AC-02 の規則では、無視される `extension/node_modules/` の下の `.bin/`・`.package-lock.json` なども対象になり、基準値に含めるファイルの数が増えうる。どちらのタスクが先に実装されるかに応じて、0034 が定義をそのまま使うか、別の部分集合を使うかを決める。
-   **H-05: テストの作り方.** AC-12 の各行と、AC-01〜AC-10 の例を、`inScope` の表のテストに入れる。各行について、対応する規則を外すと失敗することを確かめる（`CLAUDE.md`「Testing Strategy」）。拒否リストと許可リストのどちらでも範囲外になる入力では、どちらの規則を確かめているかが分からない。たとえば `internal/writer/foo.syso`（スレッドの `path` は `writer.go`）は、拒否リストを外しても、許可リストに当たらないので範囲外のままである。拒否リストを確かめるには、許可リストだけなら範囲に入る入力（`internal/writer/CLAUDE.md` は `.md`）か、規則 1 の入力（AC-13）を使う。片方の規則だけが働く入力を選ぶ（`CLAUDE.md`「A layered path needs inputs only one layer can handle」）。
-   **H-06: 大文字と小文字の扱いの組み合わせ.** 拒否リストは ASCII の大文字小文字を同一視し、許可リストは区別する（AC-09）。たとえば `internal/x/Claude.MD` は拒否リストに当たり、許可リストには当たらない。この組み合わせで、範囲に入るファイルが広がらないことを確かめる。
