## 1. 概要 (Overview)

**目的:** 本書は、記事を作る Go のパイプラインを WASM（WebAssembly）にビルドし、ブラウザ拡張のページで動かす PoC（概念実証）の要件を定める。測るのは、拡張だけの構成の設計（[#772](https://github.com/isseis/yt2column/issues/772)）で使う値である。成果は 2 つある。1 つは、`main` に入れる小さな変更で、パイプラインのコアを WASM でビルドできるようにする。もう 1 つは、測った値と 3 つの問いへの答えを `docs/research/` の下に記録する。PoC のコードそのものは `main` にマージしない。

**背景:**

[#769](https://github.com/isseis/yt2column/issues/769) は、拡張だけで記事を作る構成への移行を方針としている。この構成では、localhost サーバと Native Messaging のホストを廃止し、利用者が自分の Anthropic API キーを拡張に設定する。記事を作る処理は Go のコアを WASM にビルドして拡張から使い、CLI と共有する案である。#772 でこの構成を決めるには、次の 3 つの問いに実測で答える必要がある（#771）。

1. Go の WASM 版のパイプラインは、拡張のページで現実的に動くか。WASM のサイズ、読み込みの時間、`net/http` が `fetch` に変換されて Claude API を呼べるかを確かめる。
2. 記事の生成をビューアのタブで実行できるか。数分かかる記事の生成が、背面のタブのまま（定義は §3.1 F-004 と §6）完走するか、メモリセーバーなどによるタブの破棄を受けないかを確かめる。
3. ストリーミングは要るか。ストリーミングなしで、本番の `max_tokens` 40,000 の応答を受け取りきれるかを確かめる。

今の構成では、ビューアは記事の生成の開始と同時に背面のタブで開き、一度も前面にならないまま開いていることがある（[ADR-0009](../../dev/adr/0009-viewer-opening.md)）。記事の生成はサーバが行い、状態の正しい値もサーバが持つ。ビューアは状態を問い合わせるだけである（[ADR-0010](../../dev/adr/0010-extension-stores-nothing.md)）。Claude アダプタは、出力の上限の既定を 40,000 トークンとし（`internal/llm/claude/request.go:31`）、ストリーミングを使わない（[ADR-0025](../../dev/adr/0025-claude-output-limit.md)）。CLI とサーバは、LLM の呼び出しごとに 15 分の期限を設ける（`internal/llm/provider/provider.go:24` の `LLMTimeout`）。

今のコアは WASM でビルドできない。`GOOS=js GOARCH=wasm go build` を 2026-11-10 に試した結果は、次のとおりである。

-   `internal/transcript` は、`internal/transcript/exec.go:99` の `syscall.SysProcAttr{Setpgid: true}` で失敗する（yt-dlp を起動する経路の一部）。
-   `internal/writer` は、`internal/transcript` を import するので失敗する。さらに、`internal/writer/template.go:38` の `syscall.O_NONBLOCK`・`syscall.O_NOCTTY` でも失敗する（上書き用のテンプレートのファイルを開くフラグ）。issue #771 は「`internal/writer` はそのままビルドできることを確認済み」としているが、この 2 つ目の原因は issue の確認から漏れていた。
-   `internal/pricing` は `internal/writer` に依存するので、同じ理由で失敗する。
-   `internal/llm/claude` は、そのままビルドできる。
-   `internal/llm/provider` は、`internal/config` を経て `internal/privatefile` に依存し、`js` ではビルドできない。本書は、このパッケージを WASM でビルドできるようにすることを求めない。
-   `internal/transcript` から yt-dlp の経路のファイル（`exec.go`・`ytdlp.go`・`cache.go`・`info.go`・`json3.go`）を外し、`template.go` のフラグを `os.O_RDONLY` だけにすると、`internal/transcript`・`internal/writer`・`internal/pricing`・`internal/llm/claude` はどれも WASM でビルドできた（`go build -overlay` による試行）。

対応 issue: [#771](https://github.com/isseis/yt2column/issues/771)（親: [#769](https://github.com/isseis/yt2column/issues/769)、後続: [#772](https://github.com/isseis/yt2column/issues/772)・[#773](https://github.com/isseis/yt2column/issues/773)）

**本書の記述範囲:** 本書は、`main` に入れる変更の観測できる振る舞い（何が WASM でビルドでき、CLI とサーバの何が変わらないか）を定める。PoC で行う操作、測る値、調査記録に残す内容も定める。次のものは、設計（`02_architecture.md`）で決める。

-   パッケージの分け方（パッケージを分割するか、ビルドタグで切り替えるか）。
-   WASM の入口の関数と、測定の呼び出しの関数の形。
-   拡張のページから API を呼ぶ方法（CORS・権限・ヘッダ）。
-   WASM の読み込みと測定の手段。
-   API キーを貼り付ける画面の形。

要件定義の過程で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #771 で決めたこと:**

-   **`main` に入れるのは分割だけにする。** PoC のコードは使い捨てにし、`main` にマージしない。`internal/transcript` の分割は本番でも要るので、別の小さな PR として `main` に入れる。ADR: 分割で変わるパッケージの構成は設計（H-01）で決まるので、ADR を作るかの判断は `02_architecture.md` が記録する。パッケージを分けて構成要素の置き場所が変わるなら、[ADR-0019](../../dev/adr/0019-pipeline-component-interfaces.md) を更新するかも、`02_architecture.md` で判断する。
-   **結果はリポジトリに残す。** 調査記録を `docs/research/` の下に置き、#772 の ADR の根拠として引用する。ADR: なし（構成の決定は #772 が ADR に記録する）。
-   **WASM の入口を 1 つ作る。** 拡張のページから呼ぶ入口が、コピーした字幕・動画メタデータ・API キーを受け取り、記事を返す。ビューアが WASM を読み込み、3 つの工程（生成、字数の調整、検証・推敲）を実行する。ADR: なし（PoC の中に閉じる）。
-   **API キーはメモリにだけ持つ。** 開発用に、API キーをその場で貼り付ける。メモリにだけ持ち、保存しない。ADR: なし（PoC の中に閉じる。本番の API キーの保存は #772 が決める）。
-   **測るもの:** WASM のサイズ、読み込みの時間、工程ごとの所要時間。背面のタブで完走するかを、`chrome://discards` による破棄の試行も含めて確かめる。タブを閉じたときに中止されるかも確かめる。ADR: なし。
-   **API の費用:** 仕組みの確認と繰り返しの試行には `claude-haiku-5-5` を使い、Haiku が `effort` を受け付けるかも確かめる。本番の構成（`claude-opus-5-5+high`）を使うのは、成功の基準の確認だけにする。本番の構成での実行は、3 本の動画で 1 回ずつ（約 1.1 USD）を基本とし、全体で約 4 USD を上限の目安とする。実 API の呼び出しは、その都度承認を得る。ADR: なし。
-   **成功の基準:** 本番の構成で、3 本の動画のすべてについて、背面のタブのまま記事が完成し、CLI の出力と同じ構造の記事が出る。ADR: なし。
-   **含めないもの:** API キーの保存と設定の UI、ストリーミングの実装、Offscreen Document の実装、TS 版との比較の実装、Web Store への対応、アクセシビリティと多言語への対応は含めない。ストリーミングは、問い 3 の答えが「要る」なら #772 の設計の範囲に入れる。Offscreen Document は、問い 2 が失敗したとき（失敗の定義は AC-17）だけ試す。ADR: なし。

**要件定義の際に決めたこと（2026-11-11）:**

-   **進め方は通常の進め方（`full`）とする。** 変更は 3 つの部品（`internal/transcript`・`internal/writer`・拡張）にまたがる。新しい仕組み（WASM の入口、ビューアでの読み込み）を作り、決めることも多いためである。簡易な進め方から除外する変更に当たるかの判断は「当たる」とした。`main` に入れるのは分割と調査記録だけで、セキュリティの規則を変えない。しかし PoC は、拡張のページに API キーを持たせ、拡張から外部のサービス（Anthropic API）を直接呼ぶ。これは [security.md](../../dev/security.md) §2・§8 の前提（API キーは CLI の環境変数かサーバの設定ファイルだけにある）に触れるので、疑わしいときは除外する規則に従い、除外の対象と判断した。人は通常の進め方を選び、この判断を覆していない。ADR: なし（このタスクの進め方の決定で、タスクの外に及ばない）。
-   **`internal/writer` の修正も、`main` に入れる分割の PR に含める（F-001）。** issue は `internal/transcript` の分割だけを挙げている。しかし、背景のとおり `internal/writer/template.go:38` も WASM でビルドできない。本番の WASM 化でも必ず要る変更で、規模も小さいためである。ADR: なし。WASM でビルドできることを規則として守り続けるかは #772 が決める（次の決定）。
-   **WASM でビルドできることを守る検査は加えない（§2.3）。** `make test`・`make lint`・CI に、`GOOS=js GOARCH=wasm` のビルドの検査を加えない。加えると「コアは WASM でビルドできる」が後のタスクを縛る規則になる。Go の WASM にするか TS に一本化するかは #772 でまだ決まっていないので、その判断を先取りしないためである。ADR: なし。検査を加えるなら #772・#773 が ADR とともに決める。
-   **PoC のコードは origin のブランチに残す（F-005）。** PoC のブランチを origin に push してマージせずに残し、調査記録にブランチ名とコミットの SHA を書く。測定を再現できるようにし、かつ `main` に PoC のコードを入れないためである。ADR: なし。
-   **PoC のコードは、調査記録の PR で見る（§5）。** PoC のブランチだけの PR は開かない。調査記録を `main` に入れる PR のレビューで、調査記録と、そこに書いた PoC のブランチの SHA のコードを見る。マージしないコードのために、マージで終わる流れ（`/runplan`・`/runpr`）を使わず、Codex の PR レビューの割り当ても使わないためである。ADR: なし。
-   **問い 2 が失敗したら、このタスクの中で Offscreen Document を試す（F-004）。** #772 の判断には、代わりの案の値も要るためである。ADR: なし。
-   **問い 2 の失敗は、ブラウザが自動で行った破棄で記事の生成が失われることと、背面のまま完走しないことだけとする（AC-17）。** 自動で行った破棄とは、メモリセーバーやメモリの不足による破棄である。`chrome://discards` などの操作で人が強制した破棄は、タブがメモリの状態を失うので、記事の生成はほぼ必ず失われる。これを失敗に数えると、問い 2 は常に失敗となり、何も区別できない。強制した破棄は、その結果を観測として記録するだけにする。ADR: なし。
-   **測るブラウザは Chrome と Brave の両方とし、本番の構成での実行は Chrome だけにする（F-003・F-004）。** 対象のブラウザは Chrome と Brave である（[ADR-0026](../../dev/adr/0026-extension-platform.md)）。タブの破棄の振る舞いはブラウザごとに違いうるので、Haiku での試行は両方で行う。本番の構成での 3 本は、費用を抑えるため Chrome だけで行う。ADR: なし。
-   **問い 3 は、Haiku で上限の近くまで出力させる長い応答を足して確かめる（AC-19）。** 0018 の評価では、10 件の出力が最大でも 13,688 トークンだった（[production_profile.md](../../dev/production_profile.md)「品質の目標と結果」）。本番の 3 本だけでは、40,000 トークンの近くの長さを確かめられない見込みであるためである。ADR: なし。
-   **長い応答は、入口とは別の、測定のためだけの呼び出しで送る（F-002）。** `internal/writer` のテンプレートには、40,000 トークンの近くまで出力させるものがない。issue の「入口を 1 つ」は、記事を作る入口のことである。そこで PoC に、同じ Claude アダプタで長い出力を求める呼び出しを 1 つ足す。PoC のブランチの中だけに置き、`main` には入れない。ADR: なし。
-   **本番の構成で試す動画は、0008 の評価の 5 本から、字幕の最も長い動画 1 を含む 3 本とし、CLI は実行せずに記事の構造で形式を判定する（AC-20）。** 評価の 5 本は [0008 評価記録](../0008_column_prompt/02_evaluation.md) §3.2 にある。最も長いのは動画 1（`roNZ-rLxhUE`、32:29）で、応答が長くなりやすく、問い 2・3 の条件として厳しい。形式は、記事の構造を CLI の出力の構造と見比べて判定する。同じ 3 本を CLI でも実行すると約 1.1 USD 増え、得られるのは同じコード（`internal/writer`）の出力の比較だけであるためである。ADR: なし。
-   **PoC に貼り付ける API キーは、テスト用の API キーとする（§4.2）。** テスト用の API キーとそのワークスペース ID は、`YT2COLUMN_TEST_ANTHROPIC_API_KEY`・`YT2COLUMN_TEST_ANTHROPIC_WORKSPACE_ID` に割り当てているものである。そのワークスペースには利用の上限がある（[security.md](../../dev/security.md) §2）。キーが漏れたときや暴走したときの被害をその上限で抑えるために、テスト用の API キーを使う。ADR: なし（例外は PoC の中に限り、`main` の規則を変えない）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   #772 が構成を決めるのに要る 3 つの問いに、実測の値で答える。
-   パイプラインのコア（コピーした字幕の解析、記事の生成、Claude のアダプタ、料金の概算）を、CLI とサーバの振る舞いを変えずに WASM でビルドできるようにする。
-   測定の結果と条件を、#772 の ADR が根拠として引用できる形でリポジトリに残す。

### 2.2. スコープ (In Scope)

-   `main` に入れる変更（F-001）。`internal/transcript` を、コピーした字幕の経路（`CopiedSource`）と yt-dlp の経路に分け、`internal/writer` の上書き用のテンプレートのファイルを開く処理を分けて、コアを WASM でビルドできるようにする。
-   PoC のブランチだけに置く変更（F-002・F-003）。WASM の入口と測定のための呼び出しを作り、ビューアから読み込んで実行できるようにする。
-   測定（F-004）。測定は、Chrome と Brave での Haiku の試行と、Chrome での本番の構成の 3 本からなる。問い 2 が失敗した場合に限り、Offscreen Document での測定も行う。
-   調査記録（F-005）。`docs/research/` の下に置き、`main` に入れる。

### 2.3. スコープ外 (Out of Scope)

-   API キーの保存と設定の UI。issue #771 で決めたとおりである。
-   ストリーミングの実装。issue #771 で決めたとおりで、問い 3 の答えが「要る」なら #772 の設計の範囲に入れる。
-   問い 2 が成功した場合の Offscreen Document の実装。issue #771 で決めたとおりで、失敗した場合の試行はスコープに含める（AC-21）。
-   TS 版との比較の実装、Web Store への対応。issue #771 で決めたとおりである。
-   PoC の画面のアクセシビリティと多言語への対応。issue #771 で決めたとおりである。PoC の画面は `main` にマージせず利用者に届かないので、[CLAUDE.md](../../../CLAUDE.md)「Accessibility」の例外（機能を確かめるためだけの最小限の UI）の手続き（issue の作成と、PR の説明への記載）の対象にもならない。
-   `internal/llm/provider` を WASM でビルドできるようにすること。PoC はアダプタを直接作る（AC-07）。
-   WASM でビルドできることを守る検査（`make` の目標や CI）。要件定義の際に決めたとおり、#772・#773 が決める。
-   同じ 3 本を CLI でも本番の構成で生成して比べること。要件定義の際に決めたとおりである。
-   本番の構成での Brave の測定。要件定義の際に決めたとおりで、調査記録に「確かめていない事項」として書く（AC-27）。
-   localhost サーバ・Native Messaging のホスト・今の拡張の記事の生成の経路の変更。`main` の拡張・サーバ・ホストは変えない。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: パイプラインのコアを WASM でビルドできるようにする（`main` に入れる）

`internal/transcript` を、コピーした字幕の経路と yt-dlp の経路に分ける。`internal/writer` は、上書き用のテンプレートのファイルを開く処理を分ける。これにより、コピーした字幕を解析する部分・記事の生成・Claude のアダプタ・料金の概算を、`GOOS=js GOARCH=wasm` でビルドできるようにする。CLI とサーバの振る舞いは変えない。この変更は PoC と別の PR として `main` に入れる。

**Acceptance Criteria**:

-   **AC-01**: 次のパッケージが、`GOOS=js GOARCH=wasm go build` でエラーなくビルドできる。
    -   `CopiedSource` と、それが返す `Transcript` の型を持つパッケージ。
    -   `internal/writer`。
    -   `internal/llm/claude`。
    -   `internal/pricing`。
-   **AC-02**: `GOOS=js GOARCH=wasm` でビルドした AC-01 のパッケージの依存に、外部のプロセスを起動するこのリポジトリのパッケージ（yt-dlp の経路）が含まれない。
-   **AC-03**: `GOOS`・`GOARCH` を指定しない通常のビルドで、`make test`・`make lint`・`make deadcode` が通る。
-   **AC-04**: 既存のテストのコード（`_test.go` のファイルと、`test_helpers*.go`・`testutil/` の下のテストの補助）の差分は、次のものに限られる。
    -   ファイルの移動。
    -   パッケージ名の行と import の行。
    -   移動に伴う、パッケージの名前で修飾した識別子の書き換え。
    -   ビルドの制約の行。

    テストの関数の削除と、アサーションの変更はない。
-   **AC-05**: テストではない製品のコードの差分は、次のものに限られる。
    -   ファイルの移動。
    -   パッケージ名の行と import の行。
    -   移動に伴う、パッケージの名前で修飾した識別子の書き換え。
    -   ビルドの制約の行。
    -   上書き用のテンプレートのファイルを開く処理の、`js` のビルドとそれ以外のビルドへの分割。`js` 以外のビルドで開くときのフラグ（`internal/writer/template.go:38`）は変わらない。
    -   `js` のビルドで上書き用のテンプレートを指定されたときの扱い（H-02）。
    -   [package_reference.md](../../dev/conventions/package_reference.md) の表の、パッケージの分け方に合わせた行の変更。
-   **AC-06**: `.golangci.yml` の `depguard` の `deps` の規則に、モジュールを加えない（標準ライブラリの外のモジュールを増やさない）。

#### F-002: WASM の入口と測定のための呼び出し（PoC のブランチだけ）

拡張のページから呼べる WASM の入口を 1 つ作る。入口は、次の値を受け取る。

-   コピーした字幕の文字列。
-   動画の URL・タイトル・チャンネル名・概要欄。
-   API キーとワークスペース ID。
-   3 つの工程のそれぞれのモデルと effort。

入口は、CLI と同じコード（`internal/writer`）で 3 つの工程を実行し、記事を返す。ほかに、問い 3 のための測定の呼び出しを 1 つ置く（AC-10）。どちらも PoC のブランチにだけ置き、`main` にマージしない。

**Acceptance Criteria**:

-   **AC-07**: 入口は、生成、字数の調整、検証・推敲の 3 つの工程を、CLI と同じ順で、次の条件を CLI と同じにして実行する。
    -   プロンプトは、埋め込みの既定のテンプレートを使う。
    -   `max_tokens` は、Claude アダプタの既定（`internal/llm/claude/request.go:31`）を使う。
    -   呼び出しごとの期限は、CLI と同じ 15 分（`internal/llm/provider/provider.go:24`）とする。
    -   字数の調整は、CLI と同じ条件で、生成した本文が長すぎるときだけ実行する。

    入口は、CLI が出力する記事と同じ文字列の形（`internal/writer` が組み立てる Markdown）を返す。
-   **AC-08**: 入口は、受け取った値を、今のサーバの記事の生成の開始と同じ形で受け付け、同じ番兵で拒否する。サーバの検査は `internal/server/request.go:63` の `validateBody` にあり、字幕の形の拒否は `transcript.ErrCopiedTranscriptFormat`（`internal/transcript/errors.go:18`）である。モデル・effort・API キー・ワークスペース ID は、Claude アダプタとその型（`internal/llm/claude`・`internal/llm/claudeparam`）が受け付ける形に限って受け付ける。拒否したときは、LLM を呼ばない。
-   **AC-09**: どの工程の失敗でも、入口は失敗を返し、記事を返さない。失敗には、コピーした字幕の拒否、API の失敗、出力の打ち切り、空の応答、検証・推敲の応答の拒否を含む。失敗は、`internal/transcript`・`internal/writer`・`internal/llm` の番兵で分かる種類として、呼び出し元の JavaScript に返す。途中の工程までの記事を、成功として返さない。
-   **AC-10**: 測定の呼び出しは、Claude アダプタを入口と同じ条件（`max_tokens`・期限）で作り、Claude API に長い出力を求めるプロンプトを 1 回送る。出力のトークン数・終了の理由・所要時間を返す。出力が上限で打ち切られたときも、アダプタが返す使用量（[ADR-0021](../../dev/adr/0021-llm-client-contract.md)）からトークン数を返す。API の失敗や期限切れのように値を得られない失敗では、得られない値を「不明」として返し、失敗の種類とそこまでの所要時間を返す。
-   **AC-11**: 入口は、工程ごとに次の値を呼び出し元に返す。
    -   開始から終了までの所要時間。
    -   モデル名。
    -   入力と出力のトークン数。
    -   料金の概算（`internal/pricing` が出すもの）。

    失敗した工程も、分かる範囲で同じ値を返す。

#### F-003: ビューアでの実行（PoC のブランチだけ）

ビューアが WASM を読み込み、利用者が貼り付けた API キーで、入口と測定の呼び出し（F-002）を実行する。

**Acceptance Criteria**:

-   **AC-12**: ビューアは、WASM を読み込み、API キーとワークスペース ID の入力欄を表示する。記事の生成と測定の呼び出しは、利用者がボタンを押したときだけ始まる。
-   **AC-13**: 次の場合、ビューアは API を呼ばず、その理由を表示する。
    -   WASM の読み込みに失敗した。
    -   API キーかワークスペース ID の欄が空である。
    -   記事の生成か測定の呼び出しが実行中である（実行中は、どちらも新しく始めない）。
-   **AC-14**: API キーとワークスペース ID は、ビューアのタブのメモリにだけ持つ。次のどれにも書かない。
    -   `chrome.storage`（`local`・`session`・`sync`）。
    -   `localStorage`・`sessionStorage`・IndexedDB・Cookie。
    -   ページの URL。
    -   コンソールと開発者向けのログ。
    -   エラーの表示。

    タブを閉じると、どこにも残らない。
-   **AC-15**: 成功したときは記事を、失敗したときは失敗の種類を表示する。工程ごとの値（AC-11）と、WASM の読み込みの時間も表示する。記事は、今のビューアと同じく untrusted のテキストとして描画する（[security.md](../../dev/security.md) §8.1「記事を untrusted テキストとして描画する」）。
-   **AC-16**: ビューアのタブで実行する形では、記事の生成はそのタブの中だけで行う。タブを閉じた後に、Service Worker など別の場所で続けない。Offscreen Document で実行する形（AC-21）は、この AC の対象外である。

#### F-004: 測定

PoC で次の値を測る。実 API を呼ぶ測定は、その都度、人の承認を得てから行う。本書で**背面のまま**とは、記事の生成を始めた後に、同じウィンドウの別のタブを前面にし、完了までビューアのタブを前面に戻さないことをいう。

**Acceptance Criteria**:

-   **AC-17**: 問い 2 について、Chrome と Brave で、`claude-haiku-5-5` を使い次の試行を行う。
    -   ビューアのタブを背面のまま、3 つの工程が完走するか。
    -   長い応答の測定（AC-19）を背面のまま行い、完走するか。数分かかる記事の生成に近い長さを、背面で確かめるためである。
    -   メモリセーバーを有効にした状態で、背面のまま完走するか。メモリセーバーの設定と、背面にしていた時間と、ブラウザがタブを破棄したかを記録する。
    -   記事の生成の途中で、タブの破棄の操作（Chrome は `chrome://discards`、Brave はそれに当たる画面）で人が破棄を強制したとき、記事の生成がどうなるか。

    問い 2 の失敗とは、背面のまま完走しないことと、ブラウザが自動で（メモリセーバーやメモリの不足で）タブを破棄して記事の生成が失われることである。本番の構成の回（AC-20）で、背面での中断や破棄によって記事が完成しなかった場合も、問い 2 の失敗に数える。背面での実行と関係のない原因（API の 5xx・529 の応答、CLI でも起こるモデルの出力の拒否）で完走しなかった試行は、問い 2 の失敗に数えない。原因とともに記録し、人の承認を得て手でやり直してよい。人が強制した破棄の結果は、観測として記録するだけで、失敗に数えない。
-   **AC-18**: 問い 1 について、次の値と振る舞いを Chrome と Brave で測る。
    -   WASM のファイルのサイズ。圧縮しないものと gzip で圧縮したもの。
    -   ビューアを開いてから入口を呼べるようになるまでの読み込みの時間。3 回以上測り、各回の値を記録する。
    -   `claude-haiku-5-5` で、3 つの工程が WASM から Claude API を呼んで完了するか。
    -   Haiku が `effort` を受け付けるか。受け付けない場合は、その応答（状態コードとエラーの種類）も記録する。
    -   拡張のページから API を呼ぶのに要ったもの（権限・ヘッダ。H-03）。
    -   `fetch` に変換された `net/http` で、次の守りがネイティブのビルドと同じように働くか（H-04）。
        -   リダイレクトに従わないこと（[security.md](../../dev/security.md) §3）。
        -   応答の本文の大きさの上限。
        -   期限切れとキャンセルで、リクエストが中止されること。
-   **AC-19**: 問い 3 について、次の 2 つを測る。
    -   本番の構成の 3 本（AC-20）の各工程の、出力のトークン数と所要時間。
    -   測定の呼び出し（AC-10）で、`claude-haiku-5-5` に、ストリーミングなしで 36,000 トークン以上（`max_tokens` 40,000 の 9 割以上）を出力させる応答 1 回。出力が 36,000 トークンに届かない場合は、プロンプトを変え、人の承認を得たうえで送り直してよい。応答を受け取りきれたか、出力のトークン数、所要時間、終了の理由を記録する。

    Haiku は Opus より速く出力するので、この応答の所要時間は、Opus で 40,000 トークンを出力するときの所要時間より短い見込みである。本番の 3 本で観測した Opus の出力の速さから 40,000 トークンの所要時間を見積もり、測定の呼び出しの所要時間と並べて記録する。
-   **AC-20**: 成功の基準を、本番の構成（3 つの工程とも `claude-opus-5-5`、effort `high`）で、Chrome で確かめる。動画は、0008 評価記録 §3.2 の 5 本から、動画 1（`roNZ-rLxhUE`）を含む 3 本とし、各 1 回生成する。入力の字幕は、本番の経路と同じく、文字起こしパネルからコピーしたものである。各回について、次の 3 点を記録する。
    -   ビューアのタブを背面のまま、記事が完成したか。
    -   記事が CLI の出力と同じ構造を持つか。構造とは、1 行目のレベル 1 の見出しのタイトル、本文、出典の段落（`出典: ` と動画の URL）である（`internal/writer/output.go:23`・`internal/writer/output.go:29`・`internal/writer/output.go:239`）。
    -   料金の概算。

    3 本のすべてで 1 点目と 2 点目を満たせば、成功の基準を満たす。

    問いと関係のない原因（API の 5xx・529 の応答、CLI でも起こるモデルの出力の拒否）で失敗した回は、原因とともに記録し、人の承認を得て同じ動画で手でやり直してよい。成功の基準は、各動画の最後の回で判定する。問い 2・3 に関わる原因（背面での中断・破棄・`fetch` の失敗）による失敗は、成功の基準を満たさない結果として記録する。
-   **AC-21**: 問い 2 が失敗した場合（AC-17 の最後の段落）に限り、失敗したブラウザで、同じ試行（AC-17・AC-22）を、記事の生成を Offscreen Document で実行する形で行う。
-   **AC-22**: 記事の生成の途中でビューアのタブを閉じたときの中止を、Chrome と Brave で観測する。ブラウザの側でリクエストの接続が中止されたかと、テスト用のワークスペースの使用量に、中止したリクエストの分が計上されたかを記録する。
-   **AC-23**: 費用は、テスト用のワークスペースのコンソールの使用量で数える。全体で約 4 USD の目安を超えそうになったら、超える前に測定を止め、人に続けるかを尋ねる。

#### F-005: 調査記録

測定の結果を、`docs/research/` の下の日本語の文書に残し、`main` に入れる。PoC のブランチは origin に残す。

**Acceptance Criteria**:

-   **AC-24**: 調査記録は、3 つの問いのそれぞれに答えを書き、その根拠として AC-17〜AC-22 の測定の値を挙げる。
    -   問い 1 は 2 つに分ける。仕組みとして動くか（3 つの工程が WASM から Claude API を呼んで完了するか）は「はい」か「いいえ」で答える。現実的かどうかは、サイズと読み込みの時間の値だけを挙げ、判断は #772 に委ねる（§4.1）。
    -   問い 2 は、問い 2 の失敗（AC-17 の最後の段落）が 1 つもなければ「はい」、あれば「いいえ」と答え、失敗した試行を挙げる。
    -   問い 3 は、測った条件の範囲で答える。長い応答（AC-19）と本番の 3 本のすべてを、ストリーミングなしで受け取りきれたなら「測った範囲では要らない」と答える。応答の受け取りそのもの（`fetch` の失敗や期限切れ）で受け取れなかったものがあれば「要る」と答える。API の 5xx・529 の応答やモデルの出力の拒否のように、受け取りと関係のない失敗は判定に含めない（AC-20 のやり直しの対象である）。Opus で 40,000 トークンを出力する長さの応答は確かめていないので、AC-19 の見積もりの所要時間とともに、その結論を答えと分けて書く。長い応答が 36,000 トークンに届かなかった場合は「決められない」と答え、届いた最大の出力のトークン数を書く。
-   **AC-25**: 調査記録は、測定の条件を書く。条件は次のとおりである。
    -   ブラウザの名前と版、OS と版、測った日。
    -   Go の版。
    -   使ったモデルと effort、`max_tokens`、呼び出しごとの期限。
    -   メモリセーバーの設定と、背面にしていた時間。
    -   PoC のブランチの名前とコミットの SHA。
    -   動画の ID。
    -   実行ごとの料金の概算と、コンソールの使用量による合計（AC-23）。
    -   やり直した回とその原因（AC-20）。
-   **AC-26**: PoC のブランチは origin に push され、`main` にマージされない。AC-25 のコミットは、そのブランチから辿れる。
-   **AC-27**: 調査記録は、確かめていない事項を挙げる。少なくとも次のものを含む。
    -   本番の構成での Brave の測定。
    -   一度も前面にならなかった背面のタブ（[ADR-0009](../../dev/adr/0009-viewer-opening.md) の開き方）での記事の生成。PoC で試した場合は、確かめた事項に移す。
    -   Opus で 40,000 トークンを出力する長さの、ストリーミングなしの応答（AC-19）。
    -   問い 2 が成功した場合の Offscreen Document。
    -   メモリセーバーの試行でブラウザがタブを一度も破棄しなかった場合の、ブラウザが自動で行う破棄を受けたときの振る舞い。
-   **AC-28**: 調査記録には、API キー、ワークスペース ID、記事の本文、字幕の本文を書かない。測定の途中で取ったログ（`chrome://net-export` の記録、HAR、DevTools の画面の写しなど）は、リポジトリにコミットせず、使い終えたら消す。調査記録に引用する場合は、API キーとワークスペース ID を含まない部分だけを引用する。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   WASM のサイズと読み込みの時間には、合否の閾値を設けない。値を測って記録し（AC-18）、現実的かどうかは #772 が判断する。

### 4.2. セキュリティ (Security)

[security.md](../../dev/security.md) を当てはめる。本タスクは、API キーを扱い、LLM API へデータを送り、字幕と動画メタデータ（untrusted のテキスト）をプロンプトに入れるので、条件つきのガイドの対象である。

-   **`main` に入れる変更（F-001）は、セキュリティの規則を変えない。** 上書き用のテンプレートのファイルを開くときのフラグを、`js` 以外のビルドで変えない（AC-05）。yt-dlp の起動の守り（[security.md](../../dev/security.md) §1）も変えない。
-   **PoC の API キーは、テスト用の API キーとする。** テスト用の API キーとそのワークスペース ID（[security.md](../../dev/security.md) §2。利用の上限のあるワークスペースのもの）を使い、本番の `ANTHROPIC_API_KEY` は使わない。人がビューアに貼り付け、メモリにだけ持ち、どこにも書かない（AC-14・AC-28）。
-   **untrusted の入力は、今のサーバと同じ形で受け付け、同じ番兵で拒否する（AC-08）。**
-   **記事は untrusted のテキストとして描画する（AC-15）。** PoC でも、今のビューアと同じ描画（[ADR-0017](../../dev/adr/0017-viewer-markdown-rendering.md)）を使う。
-   **LLM に送るデータは今と同じにする。** 工程ごとに送るものは [security.md](../../dev/security.md) §4 のとおりで、API キーをプロンプトに入れない。
-   **方針の例外（PoC の中だけ）:** PoC は、`main` の次の方針と異なる。どれも PoC のブランチと PoC の測定の中に限り、`main` にはマージしない。測定のために、拡張のページから API を直接呼ぶ必要があるためである。
    -   [security.md](../../dev/security.md) §2：API キーは CLI では環境変数から、サーバでは設定ファイルからだけ読む。PoC は、ビューアに貼り付けた値を使う。
    -   [security.md](../../dev/security.md) §2：テスト用の API キーを使うのは、オプトインのある 3 つの統合テストだけである。PoC の測定でも、人がビューアに貼り付けて使う。
    -   [security.md](../../dev/security.md) §3：リダイレクトに従わないことと、応答の大きさに上限を設けること。`fetch` に変換された `net/http` でこれらが働くとは限らない。PoC はアダプタの守りを変えずに使い、働くかどうかを観測して記録する（AC-18）。働かないことが分かっても、PoC の中では受け入れる。送り先はテスト用の API キーで呼ぶ `api.anthropic.com` だけである。
    -   [security.md](../../dev/security.md) §8.1：拡張のページの既定の Content Security Policy を緩めない。PoC は、WASM を動かすのに要る `'wasm-unsafe-eval'` を加えうる。
    -   [ADR-0010](../../dev/adr/0010-extension-stores-nothing.md)：拡張は権限を加えず、状態の正しい値をサーバに置く。PoC は、Anthropic API を呼ぶのに要る権限やヘッダを加えうる（その手段は設計で決める）。記事の生成の状態はビューアのタブが持つ。
    -   [ADR-0026](../../dev/adr/0026-extension-platform.md)：成果物は自前のコードだけにし、Go の手順は拡張のディレクトリを含まず Node.js を呼ばない。PoC の成果物には、Go のツールチェーンの `wasm_exec.js` とビルドした WASM が入り、そのビルドは Go と拡張の両方にまたがる。
    -   [ADR-0009](../../dev/adr/0009-viewer-opening.md)：ビューアは記事の生成の開始と同時に背面のタブで開く。PoC では、人がビューアを開き、ボタンで記事の生成を始める。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   入口は、失敗を成功として返さない（AC-09）。空の応答と打ち切りは失敗である（[CLAUDE.md](../../../CLAUDE.md)「Empty is an error」）。
-   PoC は、自動で API に送り直さない。結果が分からないときに費用を重ねないためで、[ADR-0028](../../dev/adr/0028-no-automatic-resend.md) と同じ考えである。手でのやり直しは、AC-19・AC-20 の範囲で、人の承認を得て行う。

### 4.4. 互換性 (Compatibility)

-   CLI とサーバの振る舞いを変えない（AC-03〜AC-05）。
-   PoC は、Chrome と Brave で動かす（[ADR-0026](../../dev/adr/0026-extension-platform.md)）。版は測定の条件として記録する（AC-25）。

### 4.5. 保守性 (Maintainability)

-   F-001 は、新しいモジュールを加えない（AC-06）。
-   F-001 は、構成要素ごとのパッケージが interface と入出力の型を持ち、`internal/pipeline` が interface だけに依存する、という [ADR-0019](../../dev/adr/0019-pipeline-component-interfaces.md) の決定を保つ。分けた後にどのパッケージが何を持つかは、設計で決める（H-01）。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。
-   実 API の呼び出しは、その都度、人の承認を得る（[CLAUDE.md](../../../CLAUDE.md)「Tool Execution Safety」と issue #771）。
-   本番の構成での実行は 3 本で 1 回ずつを基本とし、全体の費用は約 4 USD を目安とする（AC-23）。
-   PoC のコードは `main` にマージしない。`main` に入れるのは F-001 の変更と F-005 の調査記録だけである。
-   **受け入れの確かめ方の例外:** [requirements_process.md](../../dev/conventions/requirements_process.md) §4 は、各 AC をテスト・静的な検査・`diff` の検証・手での読みのどれかで確かめるとする。F-001 の AC（AC-01〜AC-06）は、これに従う。PoC の AC（AC-07〜AC-23）は、PoC のコードが `main` に入らず、多くが測定であるため、テストで確かめない。調査記録の PR のレビューで、調査記録に書いた値と観測、および調査記録に書いた SHA の PoC のコードを読んで確かめる。F-005 の AC（AC-24〜AC-28）は、同じレビューでの読みで確かめる。

## 6. 用語集 (Glossary)

用語は [docs/translation_glossary.md](../../translation_glossary.md) と統一する。

-   **PoC:** 概念実証（proof of concept）。本書では、`main` にマージしない、測定のための実装を指す。
-   **WASM:** WebAssembly。本書では、Go のコードを `GOOS=js GOARCH=wasm` でビルドしたものを指す。
-   **入口:** 拡張のページの JavaScript から呼ぶ、記事を作る WASM の側の関数（F-002）。
-   **測定の呼び出し:** 問い 3 のために長い出力を求める、WASM の側の関数（AC-10）。
-   **記事の生成:** 3 つの工程を通して記事を作る一連の処理。工程の 1 つの「生成」とは区別する。
-   **3 つの工程:** 生成、字数の調整、検証・推敲（[ADR-0002](../../dev/adr/0002-post-generation-steps.md)）。
-   **背面のまま:** 記事の生成を始めた後に、同じウィンドウの別のタブを前面にし、完了までビューアのタブを前面に戻さないこと（F-004）。
-   **PoC のブランチ:** PoC のコードを置き、`main` にマージしないブランチ（F-005）。
-   **本番の構成:** 3 つの工程とも `claude-opus-5-5`、effort `high` の構成（[production_profile.md](../../dev/production_profile.md)）。
-   **調査記録:** `docs/research/` の下に置く、測定の結果の文書（F-005）。
-   **テスト用の API キー:** 本番とは別に用意し、利用の上限のあるワークスペースに割り当てた Anthropic API のキー（[security.md](../../dev/security.md) §2）。
