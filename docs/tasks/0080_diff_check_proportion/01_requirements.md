## 1. 概要 (Overview)

**目的:** 本書は、変更の前後の関係を述べる受け入れ基準（AC）の確かめ方（`diff` の確かめ）を、確かめる変更の大きさに見合ったものにする要件を定義する。対象は、その確かめ方を定める規約・コマンドの定義・言語の例外である。

**背景:**

-   前後の関係を述べる AC は、`diff` の確かめで確かめる。`diff` の確かめは、タスクの `docs/tasks/NNNN_<name>/_checks/` に置いたスクリプトで、マージの基点と PR の head を比べるものである（`docs/dev/conventions/requirements_process.md:790`、`.claude/commands/mkplan.md:101`、[ADR-0016](../../dev/adr/0016-document-test-policy.md)「決定」）。規約は、スクリプトの作りを、確かめる差分の大きさに見合ったものにせよとは定めていない。言語も定めていない。
-   スクリプトの大きさは、確かめる変更に比べて大きくなった。タスク 0044・0053・0056・0066 のスクリプトは、63〜126 行のシェルスクリプトだった。タスク 0067 から後は、どれも `data.json` を伴う Go のプログラムである。行数は 0067 が 733、0068 が 851、0070 が 805、0071 が 901、0073 が 1,550、0074 が 713 である（`docs/tasks/*/_checks/` の `git ls-files` の合計行数。`data.json` を含む）。
-   タスク 0078（#776）では、ADR-0024 の差分が 1 行の書き換えと 1 行の追加だけだった。それでも、確認のプログラムは 547 行になり、壊し方の確認は 13 通りになった。#787 で約 50 行のシェルスクリプトに替えたが、確かめる性質は変わらなかった（issue #789）。
-   スクリプトは、マージの後に保守しない（`docs/dev/conventions/requirements_process.md:790`）。そのため、主な費用は、PR のレビューで読む量と、書くための作業である。
-   issue #789 は、原因を 4 つ挙げる。
    1.  規約に、釣り合いの基準がない。
    2.  計画が、前のタスクの版を手本として写させる。0078 の計画は「タスク 0071 の `_checks/main.go` を写して使う」と書いた（`docs/tasks/0078_adr0024_server_env_result/03_implementation_plan.md:39`）。
    3.  AC と計画が細かすぎる。0078 の AC-02 は、守る部分を「題名、各節、項目の数と順序……」と並べ挙げた（`docs/tasks/0078_adr0024_server_env_result/01_requirements.md:72`）。計画は壊し方を十数通り並べた。
    4.  日本語の文字列を避ける手間がかかる。`_checks/` は guard-test literal exception（`CLAUDE.md`「Go Idioms」）の対象ではない。そのため、見出しなどの日本語の文字列を置く `data.json` と、それを読む仕組みが足された（`docs/tasks/0078_adr0024_server_env_result/03_implementation_plan.md:55`）。

対応 issue: [#789](https://github.com/isseis/yt2column/issues/789)（関連: [#776](https://github.com/isseis/yt2column/issues/776)（タスク 0078）、[#787](https://github.com/isseis/yt2column/pull/787)（0078 のスクリプトの差し替え）、[ADR-0016](../../dev/adr/0016-document-test-policy.md)、[ADR-0035](../../dev/adr/0035-language-policy.md)）

**本書の記述範囲:** 本書は、次のことを定める。
-   `diff` の確かめの作りの基準と、スクリプトの既定の言語。
-   スクリプトの代わりに、`git diff` の出力を計画に記録してレビューで読む形を認める範囲。
-   前後の関係を述べる AC の書き方。
-   計画が `_checks/` について書くことの規則。
-   過大なスクリプトを指摘する、レビューの観点を置く場所。
-   `_checks/` の日本語の文字列の扱い。
-   ADR の更新と、適用の範囲。

次のことは `02_architecture.md` で決める（`design_handoff.md`）。
-   各文書のどの節に、どの言い回しで書くか。
-   文書を読む既存の guard への影響と、その扱い。
-   PR の分け方。

**issue #789 で決めたこと:**

-   **`diff` の確かめは、確かめる差分の大きさに見合った作りにする。** スクリプトはマージの後に保守しないので、費用はレビューで読む量と書く作業である。その費用を、確かめる変更に見合ったものにするためである。
-   **前のタスクの `_checks/` を手本にして、構造を写させない。** 前のタスクの大きなプログラムの構造が、そのまま受け継がれるためである（背景の原因 2）。
-   **壊し方は、計画で並べ挙げない。** 計画が並べた壊し方が、そのまま作業になるためである（背景の原因 3）。
-   **AC は、守る部分を並べ挙げない。** 並べた部分の一つ一つを解析するコードが生まれるためである（背景の原因 3）。
-   **確かめるものに比べて過大なスクリプトを、レビューで指摘する。**
-   **開発の進め方の方針の変更なので、major な決定として ADR を作るか更新する。**

**要件定義の際に決めたこと（2026-11-10）:**

-   **進め方は、通常の進め方（`full`）とする。** 変更が及ぶのは、規約の `requirements_process.md`、コマンドの定義の `mkplan.md`・`runplan.md`・`weakreview.md`、`CLAUDE.md` である。これらに加えて、既存の ADR（ADR-0016）の決定を変える。決めることも、本節のとおり複数あった。新しい仕組みは作らず、文言を変えるだけだが、ADR の決定を変え、複数の場所に及ぶので、通常の進め方を勧め、人がそれを選んだ（`.claude/commands/_lib/simple-process.md`「Recommending a process」）。
    -   除外の判断：除外に当たらない。`docs/dev/security.md` の規則とその前提を変えない。開発の道具（`fixprguard`・`codexreview`・`mergepr`）の信頼の境界を変えず、レビューのスレッドや Bot への依頼の扱いにも触れない。外部への依存も足さず、変えない（`docs/dev/conventions/requirements_process.md`「Simple Process」の「Excluded changes」）。
    -   ADR：なし。本タスクの中で閉じる、進め方の選択である。
-   **小さな文書の変更では、`git diff` の出力を計画に記録してレビューで読むことも、`diff` の確かめとして認める（F-002）。** 出力は、PR のブランチで実際に実行したもので、マージの基点と PR の head の 2 つのコミットの ID を添える。「小さい」かどうかは、計画を書く者が判断する。レビュアーは、その判断に異論を述べられる。行数などの数の閾値は設けない。0078 のように差分が 2 行の変更では、差分そのものを読むほうが、それを確かめるスクリプトを読むより少なく済むためである。閾値を設けないのは、[ADR-0040](../../dev/adr/0040-simple-task-documents.md) が簡易な進め方の判定に機械的な基準を設けなかったのと同じく、変更の性質を人が読んで判断するほうが合うためである。
    -   採らなかった案：行数の閾値を設けて、その範囲だけで認める案。閾値の値を根拠をもって決められず、差分の行数は読む手間の大きさと必ずしも一致しない。
    -   採らなかった案：記録した差分の読み取りを認めず、スクリプトだけを `diff` の確かめとする案。差分が数行の変更でもスクリプトが要り、issue の原因 1 が残る。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。
-   **`diff` の確かめのスクリプトの既定の言語は、シェル（`git diff`、`cmp`、`sed` など）とする。ほかの言語は、シェルで足りない理由を計画に書いたときに使ってよい（F-001）。** 0044〜0066 のシェルスクリプトと、#787 の差し替えは、60〜130 行ほどで同じ性質を確かめられた。一方で、0048 のファイルの分割のように、構造を比べる確かめにはシェルで足りないものもある。
    -   採らなかった案：シェルだけに限る案。構造を比べる確かめが書けなくなる。
    -   採らなかった案：既定を決めず、見合った作りにせよとだけ書く案。基準がないまま、前のタスクの版を写す流れが残る。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。
-   **guard-test literal exception（`CLAUDE.md`「Go Idioms」）を、`_checks/` のスクリプトに広げる（F-005）。** 日本語の文書の文字列（見出し・表のセル・行の始めの項目の名前・太字の印）と一致しなければならないリテラルを、スクリプトの言語にかかわらず、`_checks/` のスクリプトに置いてよいことにする。コメントと識別子は英語のままとする。リテラルが日本語の文書の文字列と一致しなければならないという理由は、既存の例外と同じである。例外を広げれば、`data.json` とそれを読む仕組みが要らなくなり、変更も最も小さい。
    -   採らなかった案：見出しを構造（見出しの深さや位置）で見つけることを既定にし、例外を広げない案。構造で見つけるためのコードが増え、スクリプトがかえって大きくなりうる。
    -   採らなかった案：構造で見つけることを既定にし、足りないときだけ例外を使う案。規則が 2 段になり、どちらを使うかの判断が要る。
    -   ADR：[ADR-0035](../../dev/adr/0035-language-policy.md) を更新する（経緯に足す。本書の PR で行う）。ADR-0035 の「決定」は、日本語のリテラルの例外の一覧を `CLAUDE.md`「Go Idioms」に委ねているので、「決定」の文は変えない。例外を足したことは、0061 の前例に倣って経緯に記録する。
-   **前後の関係を述べる AC は、「X の差分は Y と Z に限られる」の形で書く。守る部分を並べ挙げない（F-003）。** これは規則とし、勧めにとどめない。勧めにとどめると、並べ挙げる書き方が残り、背景の原因 3 が残るためである。
    -   採らなかった案：勧めにとどめる案。上の理由による。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。`diff` の確かめの作りの方針の一部だからである。
-   **`mkplan.md` に、次の 2 つの規則を足す（F-004）。前のタスクの `_checks/` を手本として写させないこと。壊し方は「チェックごとに少なくとも 1 つ」とだけ書き、並べ挙げないこと。** 片方だけでは、背景の原因 2 と 3 の片方が残るためである。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。
-   **確かめるものに比べて過大なスクリプトを指摘する観点を、`mkplan.md` の計画のレビュー、`runplan.md` のフェーズのまとまりのレビュー、`weakreview.md` のレビューの 3 か所に置く（F-006）。** issue は `runplan.md` と `weakreview.md` を挙げた。しかし、スクリプトの大きさは計画を書くときに決まるので、実装の前に見つけられるよう、計画のレビューにも置く。
    -   採らなかった案：`runplan.md` と `weakreview.md` だけに置く案。計画の段階で過大さを見逃し、実装の後に初めて見つかる。
    -   採らなかった案：上の 3 か所に加え、AC の並べ挙げを指摘する項目を `mkreq.md` のチェックリストに足す案。人がこの案を選ばなかった。AC の書き方の規則は、F-003 で規約に置く。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。
-   **新しい規則は、本タスクの実装がマージされた後に書く計画から当てはめる。既存の `_checks/` と、承認済みで実装中の計画は変えない（F-007）。** `_checks/` のスクリプトは、マージの後に保守しない（`docs/dev/conventions/requirements_process.md:790`）。0078 のスクリプトは、すでに #787 で替えた。
    -   採らなかった案：承認済みで、`_checks/` のステップがまだ実装されていない計画も改める案。承認済みの計画を決定の変更で `draft` に戻すことになり、実装中のタスクを止める。
    -   ADR：なし。本タスクの中で閉じる、適用の範囲の決定である。

**上の決定と issue から導いたこと（PR のレビューで異論があれば改める）:**

-   **記録した差分の読み取りは、`diff` の確かめの一つの形とし、ラベルは `diff` のままにする（AC-03）。** issue は「`diff` の確かめとして認める」と書いている。また、`manual` は文の内容だけを述べる AC の確かめ方なので（`docs/dev/conventions/requirements_process.md:789`）、前後の関係を述べる AC には使わない。ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) の更新に含める。
-   **`CLAUDE.md`「Testing Strategy」の「Every test must be able to fail for its stated reason.」は、スクリプトに当てはめ、記録した差分の読み取りには当てはめない（AC-02）。** 記録した差分の読み取りには、壊して失敗を確かめる対象のコードがないためである。スクリプトでは、チェックごとに少なくとも 1 つの壊し方で失敗を確かめる（AC-05）。ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) の更新に含める。
-   **`CLAUDE.md`「Testing Strategy」が `diff` の確かめを「`_checks/` のスクリプト」とだけ述べる箇所も、記録した差分の読み取りの形と合うようにそろえる（AC-09）。** そろえないと、規約と `CLAUDE.md` が食い違うためである。ADR：なし。F-002 の決定を書き写すことである。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `diff` の確かめを書く作業と、PR のレビューでそれを読む量を、確かめる変更の大きさに見合ったものにする。
-   前のタスクの大きな確認のプログラムが、手本として受け継がれないようにする。

### 2.2. スコープ (In Scope)

-   `docs/dev/conventions/requirements_process.md` の §1（AC の書き方）と §4（`diff` の確かめ）、および §3・§5 のうち `diff` の確かめに触れる箇所（F-001〜F-003）。
-   `.claude/commands/mkplan.md` の step 6（確かめの種類と計画の規則）と step 8（計画のレビューのチェックリスト）（F-001・F-002・F-004・F-006）。
-   `.claude/commands/runplan.md` の step 7（フェーズのまとまりのレビューのチェックリスト）（F-006）。
-   `.claude/commands/weakreview.md` のチェックリスト（F-006）。
-   `CLAUDE.md` の「Go Idioms」（guard-test literal exception）と「Testing Strategy」（`diff` の確かめに触れる箇所）（F-002・F-005）。
-   ADR-0016 と ADR-0035 の更新（F-008。本書の PR で行う）。実装が入った後の、ADR-0016 の食い違いの記述の削除（AC-12）。

### 2.3. スコープ外 (Out of Scope)

-   既存のタスクの `_checks/` とタスク文書の書き換え。マージの後に保守しないためである（1 章）。
-   承認済みで実装中の計画の書き換え（1 章）。
-   AC の並べ挙げを指摘する、`mkreq.md` のチェックリストの項目。人がこの案を選ばなかった（1 章）。
-   `diff` の確かめ以外の確かめの種類（`test`・`static`・`manual`）の規則の変更。issue は `diff` の確かめだけを扱う。
-   `diff` の確かめを、`make test` や CI で実行するようにすること。ADR-0016 の決定のとおり、PR ごとに 1 回だけ手で実行する。
-   開発の道具（`fixprguard`・`codexreview`・`mergepr`・`coveragecompare`）の変更。

## 3. 機能要件 (Functional Requirements)

本章で「規約」は `docs/dev/conventions/requirements_process.md` を、「記録した差分の読み取り」は F-002 の形の `diff` の確かめを指す。各 AC の「述べる」は、規約・コマンドの定義・`CLAUDE.md` が、エージェントが従う規則としてその内容を書いていることをいう。

### 3.1. 機能一覧

#### F-001: 作りの基準と既定の言語

`diff` の確かめの作りを、確かめる差分の大きさに見合ったものにする。

**Acceptance Criteria**:
- **AC-01**: 規約の §4 と `mkplan.md` は、次のことを述べる。`diff` の確かめの作りは、確かめる差分の大きさに見合ったものにする。スクリプトの既定の言語はシェル（`git diff`、`cmp` など）とする。ほかの言語は、シェルで足りない理由を計画に書いたときに使ってよい。

#### F-002: 記録した差分の読み取り

小さな文書の変更では、スクリプトの代わりに、差分を記録してレビューで読むことを認める。

**Acceptance Criteria**:
- **AC-02**: 規約の §4 と `mkplan.md` は、次のことを述べる。差分が小さい文書の変更では、PR のブランチで実際に実行した `git diff` の出力を、マージの基点と PR の head のコミットの ID とともに計画の確かめの行に記録し、PR のレビューで読むことを、`diff` の確かめとして認める。「小さい」かどうかは計画を書く者が判断し、レビュアーはその判断に異論を述べられる。数の閾値は設けない。記録した差分の読み取りには、壊して失敗を確かめる手順は要らない。
- **AC-03**: 規約の §3・§4・§5 と `mkplan.md` の確かめの種類の定義（step 6 と step 8 のチェックリスト）は、記録した差分の読み取りを `diff` のラベルの確かめとして扱う。`diff` のラベルの確かめを「`_checks/` のスクリプト」だけと述べる箇所が残らない。

#### F-003: 前後の関係を述べる AC の書き方

**Acceptance Criteria**:
- **AC-04**: 規約の §1 は、前後の関係を述べる AC を「X の差分は Y と Z に限られる」の形で書き、守る部分を並べ挙げないことを、規則として述べる。`/mkreq` は、AC を書くときにこの規則に従う（`.claude/commands/mkreq.md` の step 6 が規約の §1 に従うと定める）。

#### F-004: 計画が `_checks/` について書くことの規則

**Acceptance Criteria**:
- **AC-05**: `mkplan.md` は、次の 2 つを規則として述べる。計画は、前のタスクの `_checks/` を手本として写すよう書かない。計画は、スクリプトの壊し方を「チェックごとに少なくとも 1 つ」とだけ書き、壊し方を並べ挙げない。

#### F-005: `_checks/` の日本語の文字列

**Acceptance Criteria**:
- **AC-06**: `CLAUDE.md`「Go Idioms」の guard-test literal exception は、範囲に `docs/tasks/*/_checks/` のスクリプトを、スクリプトの言語にかかわらず含む。この範囲で認めるリテラルは、既存の例外と同じ種類（日本語の文書の見出し・表のセル・行の始めの項目の名前・太字の印と一致しなければならないもの）である。コメントと識別子は英語のままとする。

#### F-006: 過大なスクリプトを指摘するレビューの観点

**Acceptance Criteria**:
- **AC-07**: `mkplan.md` の step 8 のチェックリスト、`runplan.md` の step 7 のフェーズのまとまりのレビューのチェックリスト、`weakreview.md` のチェックリストは、それぞれ、`diff` の確かめ（計画に書いたものか、実装したスクリプト）が確かめるものに比べて過大であることを指摘の対象とする項目を持つ。
- **AC-08**: `_lib/simple-process.md` の「Reviewing the three documents」が `mkplan.md` の step 8 のチェックリストをそのまま使う形は、今のまま保たれ、簡易な進め方の計画のレビューにも AC-07 の項目が及ぶ。

## 6. 用語集 (Glossary)

-   **`diff` の確かめ**：前後の関係を述べる AC の確かめ方。マージの基点と PR の head を比べ、PR ごとに 1 回だけ実行する（規約の §4）。本タスクで、`_checks/` のスクリプトと、記録した差分の読み取りの 2 つの形にする。
-   **記録した差分の読み取り**：F-002 で認める `diff` の確かめの形。`git diff` の出力をコミットの ID とともに計画に記録し、PR のレビューで読む。
-   **前後の関係を述べる AC**：何かが保たれる、変わらない、同じ順序で残る、といった変更の前と後の関係を述べる AC（規約の §4）。
-   **壊し方**：スクリプトが、確かめる性質を破った入力で失敗することを確かめるための変更（`CLAUDE.md`「Testing Strategy」の「Every test must be able to fail for its stated reason.」）。
-   用語は `docs/translation_glossary.md` と統一する。
