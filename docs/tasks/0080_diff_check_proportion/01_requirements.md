## 1. 概要 (Overview)

**目的:** 本書は、変更の前後の関係を述べる受け入れ基準（AC）の確かめ方（`diff` の確かめ）を、確かめる変更の大きさに見合ったものにする要件を定義する。対象は、その確かめ方を定める規約・コマンドの定義・言語の例外である。

**背景:**

-   前後の関係を述べる AC は、`diff` の確かめで確かめる。`diff` の確かめは、タスクの `docs/tasks/NNNN_<name>/_checks/` に置いたスクリプトで、マージの基点と PR の head を比べるものである（`docs/dev/conventions/requirements_process.md:790`、`.claude/commands/mkplan.md:101`、[ADR-0016](../../dev/adr/0016-document-test-policy.md)「決定」）。規約は、スクリプトの作りを、確かめる差分の大きさに見合ったものにせよとは定めていない。言語も定めていない。
-   スクリプトの大きさは、確かめる変更に比べて大きくなりやすい。次の行数は、各タスクの `_checks/` の下で `git ls-files` が挙げるファイルの合計行数で、`data.json` を含む。
    -   シェルスクリプトは、0044 が 63 行、0053 と 0056 が 76 行、0057 が 266 行、0066 が 126 行だった。
    -   0066 より前にも、大きな Go や TypeScript のプログラムがあった。0048 は 2,206 行、0052 は 1,398 行、0059 は 1,000 行、0062 は 1,633 行、0065 は 1,283 行である。
    -   0067 から後は、どれも `data.json` を伴う Go のプログラムである。0067 は 733 行、0068 は 851 行、0069 は 629 行、0070 は 805 行、0071 は 901 行、0073 は 1,550 行、0074 は 713 行、0075 は 377 行である。
-   タスク 0078（#776）では、ADR-0024 の差分が 1 行の書き換えと 1 行の追加だけだった。それでも、確かめの Go のプログラムは 547 行になり、壊し方は 13 通りになった。#787 は、これを 45 行のシェルスクリプト（`docs/tasks/0078_adr0024_server_env_result/_checks/check.sh`）に替えた。このスクリプトは、節を見出しの構造で見つけ、`data.json` を使わずに、同じ性質を確かめる（issue #789、同じスクリプトのコミット `b47a8d46` のメッセージ）。
-   スクリプトは、マージの後に保守しない（`docs/dev/conventions/requirements_process.md:790`）。そのため、主な費用は、PR のレビューで読む量と、書くための作業である。
-   issue #789 は、原因を 4 つ挙げる。
    1.  規約に、釣り合いの基準がない。
    2.  計画が、前のタスクの版を手本として写させる。0078 の計画は「タスク 0071 の `_checks/main.go` を写して使う」と書いた（PR #780 でマージした版（コミット `9a30d0d3`）の `docs/tasks/0078_adr0024_server_env_result/03_implementation_plan.md:39`。#787 で書き換えた）。
    3.  AC と計画が細かすぎる。0078 の AC-02 は、守る部分を「題名、各節、項目の数と順序……」と並べ挙げた（`docs/tasks/0078_adr0024_server_env_result/01_requirements.md:72`）。計画は、壊し方を十数通り並べた。
    4.  日本語の文字列を避けるための手間がかかる。`_checks/` は、guard-test literal exception（`CLAUDE.md`「Go Idioms」）の対象ではない。そのため、日本語の文字列を置く `data.json` と、それを読む仕組みが足された（PR #780 でマージした版（コミット `9a30d0d3`）の `docs/tasks/0078_adr0024_server_env_result/03_implementation_plan.md:55`。#787 で書き換えた）。`data.json` に置かれた文字列は、見出しだけではない。0067 は語と文の断片（`docs/tasks/0067_stage_terminology/_checks/data.json`）を、0070 は置き換えの前後の文（`docs/tasks/0070_adr_writing_criteria/_checks/data.json`）を、0074 は文をそのまま（`docs/tasks/0074_adr_editorial_correction/_checks/data.json`）置いている。
        -   例外の外で、日本語の文字列を直接置いたシェルスクリプトもある（`docs/tasks/0066_server_config_file/_checks/retired_docs_removed.sh:65`）。

対応 issue: [#789](https://github.com/isseis/yt2column/issues/789)（関連: [#776](https://github.com/isseis/yt2column/issues/776)（タスク 0078）、[#787](https://github.com/isseis/yt2column/pull/787)（0078 のスクリプトの差し替え）、[ADR-0016](../../dev/adr/0016-document-test-policy.md)、[ADR-0035](../../dev/adr/0035-language-policy.md)）

**本書の記述範囲:** 本書は、次のことを定める。
-   `diff` の確かめの作りの基準と、スクリプトの既定の言語。
-   スクリプトの代わりに、`git diff` の出力を記録してレビューで読む形を認める範囲と、その扱い。
-   前後の関係を述べる AC の書き方。
-   計画が `_checks/` について書くことの規則。
-   過大な `diff` の確かめを指摘する、レビューの観点を置く場所。

-   各文書のどの節に、どの言い回しで書くか。
-   文書を読む既存の guard への影響と、その扱い。
-   PR の分け方。

**issue #789 で決めたこと:**

-   **`diff` の確かめは、確かめる差分の大きさに見合った作りにする。** スクリプトはマージの後に保守しないので、費用はレビューで読む量と書く作業である。その費用を、確かめる変更に見合ったものにするためである。
-   **前のタスクの `_checks/` を手本にして、構造を写させない。** 前のタスクの大きなプログラムの構造が、そのまま受け継がれるためである（背景の原因 2）。
-   **壊し方は、計画で並べ挙げない。** 計画が並べた壊し方が、そのまま作業になるためである（背景の原因 3）。
-   **AC は、守る部分を並べ挙げない。** 並べた部分の一つ一つを解析するコードが生まれるためである（背景の原因 3）。
-   **確かめるものに比べて過大なスクリプトを、レビューで指摘する。**
-   **開発の進め方の方針の変更なので、major な決定として ADR を作るか更新する。**

**要件定義の際に決めたこと（2026-11-10）:**

-   **進め方は、通常の進め方（`full`）とする。** 変更は、規約の `requirements_process.md`、コマンドの定義の `mkplan.md`・`runplan.md`・`weakreview.md`、`CLAUDE.md` に及ぶ。さらに、既存の ADR（ADR-0016）の決定を変える。決めることも、本節のとおり複数あった。新しい仕組みは作らず、文言を変えるだけである。それでも、ADR の決定を変え、複数の場所に及ぶので、通常の進め方を勧め、人がそれを選んだ（`.claude/commands/_lib/simple-process.md`「Recommending a process」）。
    -   除外の判断：除外に当たらない。`docs/dev/security.md` の規則とその前提を変えない。開発の道具（`fixprguard`・`codexreview`・`mergepr`）の信頼の境界を変えず、レビューのスレッドや Bot への依頼の扱いにも触れない。外部への依存を足すことも、変えることもしない（`docs/dev/conventions/requirements_process.md`「Simple Process」の「Excluded changes」）。
    -   ADR：なし。本タスクの中で閉じる、進め方の選択である。
-   **小さな文書の変更では、`git diff` の出力を記録してレビューで読むことも、`diff` の確かめとして認める（F-002）。** 出力は、PR のブランチで実際に実行したものとし、マージの基点と PR の head の 2 つのコミットの ID を添える。「小さい」かどうかは、計画を書く者が判断する。レビュアーは、その判断に異論を述べられる。行数などの数の閾値は設けない。0078 のように差分が 2 行の変更では、差分そのものを読むほうが、それを確かめるスクリプトを読むより少なく済むためである。閾値を設けないのは、[ADR-0040](../../dev/adr/0040-simple-task-documents.md) が簡易な進め方の判定に機械的な基準を設けなかったのと同じく、変更の性質を人が読んで判断するほうが合うためである。
    -   採らなかった案：行数の閾値を設けて、その範囲だけで認める案。閾値の値を根拠をもって決められない。差分の行数も、読む手間の大きさと必ずしも一致しない。
    -   採らなかった案：記録した差分の読み取りを認めず、スクリプトだけを `diff` の確かめとする案。差分が数行の変更でもスクリプトが要り、背景の原因 1 が残る。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。
-   **記録した差分の読み取りでは、次の 4 つを守る（AC-03）。** 人がこれらを要件に入れることを選んだ。
    -   出力は、計画の確かめの行に `/runplan` が記録する。計画を書く時点では、差分がまだないためである。
    -   記録の後で、比べたパスの内容が変わったときは、記録し直す。古い記録は、PR の今の差分を表さないためである。
    -   比べるパスは、AC が名指すパスに限ってよい。計画そのものを比べる範囲から外せる。計画に記録すると、計画が変わり、記録した差分に計画の変更が入り続けるためである。変わるファイルを限る AC では、差分全体の変わったファイルの一覧も記録する（AC-03）。
    -   レビュアーが「小さい」という判断に異論を述べたときは、マージの前に `_checks/` のスクリプトに替える。
    -   ADR：なし。F-002 の決定を実行する手順である。
-   **`diff` の確かめのスクリプトの既定の言語は、シェル（`git diff`、`cmp`、`sed` など）とする。ほかの言語は、シェルで足りない理由を計画に書いたときに使ってよい（F-001）。** #787 の 45 行のシェルスクリプトは、547 行の Go のプログラムと同じ性質を確かめた。0044・0053・0056・0066 のシェルスクリプトも、63〜126 行だった（背景）。一方で、0048 のファイルの分割のように、文書の構造を比べる確かめもある（`docs/tasks/0048_doc_language_policy/_checks/split/main.go`）。
    -   採らなかった案：シェルだけに限る案。構造を比べる確かめが書きにくくなる。
    -   採らなかった案：既定を決めず、見合った作りにせよとだけ書く案。基準がないまま、前のタスクの版を写す流れが残る。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。
-   **`_checks/` のスクリプトでは、日本語の文書の文字列と一致しなければならないリテラルを、種類を限らず、スクリプトの言語にかかわらず置いてよいことにする。CLAUDE.md「Go Idioms」の guard-test literal exception を、この形で `_checks/` に広げる（F-005）。** コメントと識別子は英語のままとする。リテラルが日本語の文書の文字列と一致しなければならないという理由は、既存の例外と同じである。既存の例外は、リテラルの種類を見出し・表のセル・行の始めの項目の名前・太字の印に限っている。しかし、`data.json` には語・文の断片・文が置かれてきた（背景の原因 4）。種類を限ると `data.json` が残るので、`_checks/` では種類を限らない。
    -   採らなかった案：既存の例外と同じ 4 種類に限る案。上の理由で、`data.json` が残る。
    -   採らなかった案：見出しを構造（見出しの深さや位置）で見つけることを既定にし、例外を広げない案。#787 のスクリプトは、節を構造で見つけて `data.json` をなくした。しかし、構造で見つけられるのは節の位置だけで、語や文そのものを確かめる場合（0067・0070・0074）には足りない。
    -   採らなかった案：構造で見つけることを既定にし、足りないときだけ例外を使う案。規則が 2 段になり、どちらを使うかの判断が要る。
    -   ADR：[ADR-0035](../../dev/adr/0035-language-policy.md) を更新する（本書の PR で行う）。ADR-0035 の「決定」は、日本語のリテラルの例外の一覧を `CLAUDE.md`「Go Idioms」に委ねている。そのため、「決定」の規則の文は変えず、経緯に項目を足す。実装までの食い違いの記述は、「決定」に足す（AC-12）。この判断は、人が確かめた。
-   **英語だけを求めるコマンドの定義の規則は、`CLAUDE.md`「Go Idioms」の例外に当たるリテラルを、指摘の対象にしない（AC-07）。** 対象は、`mkplan.md`・`runplan.md`・`weakreview.md` の規則である。0078 の計画は、これらの規則に従い、日本語の文字列を `data.json` に逃がした（背景の原因 4）。人がこれを要件に入れることを選んだ。
    -   ADR：[ADR-0035](../../dev/adr/0035-language-policy.md) の更新に含める。
-   **前後の関係を述べる AC は、「X の差分は Y と Z に限られる」の形で書き、守る部分を並べ挙げない。ただし、移動と分割の AC だけは、「A の内容が B に変わらずにある」の形で書いてよい（F-003）。** これは規則とし、勧めにとどめない。勧めにとどめると、並べ挙げる書き方が残り、背景の原因 3 が残るためである。移動と分割は、「差分が限られる」の形では言い表せない。移動と分割の形を認めたのは人である。
    -   採らなかった案：勧めにとどめる案。上の理由による。
    -   採らなかった案：移動と分割の例外を設けず、規則をその場の書き換えだけに当てはめる案。移動と分割の AC の書き方が定まらないまま残る。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。`diff` の確かめの作りの方針の一部だからである。
-   **`mkplan.md` に、次の 2 つの規則を足す（F-004）。** 片方だけでは、背景の原因 2 と 3 の片方が残るためである。
    -   前のタスクの `_checks/` を手本として写させない。
    -   壊し方は「チェックごとに少なくとも 1 つ」とだけ書き、並べ挙げない。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。

    -   `mkplan.md` の計画のレビュー。
    -   `runplan.md` のフェーズのまとまりのレビュー。
    -   `weakreview.md` のレビュー。
    -   採らなかった案：`runplan.md` と `weakreview.md` だけに置く案。計画の段階で過大さを見逃し、実装の後に初めて見つかる。
    -   採らなかった案：上の 3 か所に加え、AC の並べ挙げを指摘する項目を `mkreq.md` のチェックリストに足す案。人がこの案を選ばなかった。AC の書き方の規則は、F-003 で規約に置く。
    -   ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) を更新する（本書の PR で行う）。
-   **新しい規則は、本タスクの実装がマージされた後に書く計画から当てはめる。既存の `_checks/` と、承認済みで実装中の計画は変えない（F-007）。** `_checks/` のスクリプトは、マージの後に保守しない（`docs/dev/conventions/requirements_process.md:790`）。0078 のスクリプトは、すでに #787 で替えた。
    -   採らなかった案：承認済みで、`_checks/` のステップがまだ実装されていない計画も改める案。承認済みの計画を、決定の変更で `draft` に戻すことになり、実装中のタスクを止める。

    -   ADR：なし。規約に従う手順である。

**上の決定と issue から導いたこと（PR のレビューで異論があれば改める）:**

-   **記録した差分の読み取りは、`diff` の確かめの一つの形とし、ラベルは `diff` のままにする（AC-04）。** issue は「`diff` の確かめとして認める」と書いている。また、`manual` は、文の内容だけを述べる AC の確かめ方である（`docs/dev/conventions/requirements_process.md:789`）。そのため、前後の関係を述べる AC には使わない。ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) の更新に含める。
-   **`CLAUDE.md`「Testing Strategy」の「Every test must be able to fail for its stated reason.」は、スクリプトに当てはめる。記録した差分の読み取りには当てはめない（AC-02）。** 記録した差分の読み取りには、壊して失敗を確かめる対象のコードがないためである。スクリプトでは、チェックごとに少なくとも 1 つの壊し方で失敗を確かめる（AC-06）。ADR：[ADR-0016](../../dev/adr/0016-document-test-policy.md) の更新に含める。
-   **規約・コマンドの定義・`CLAUDE.md` のうち、`diff` の確かめを「`_checks/` のスクリプト」とだけ述べる箇所と、前後の関係の例を、守る部分を並べ挙げる形で書いた箇所も、新しい規則と合うようにそろえる（AC-04・AC-05）。** そろえないと、規約とコマンドの定義が食い違うためである。ADR：なし。上の決定を書き写すことである。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `diff` の確かめを書く作業と、PR のレビューでそれを読む量を、確かめる変更の大きさに見合ったものにする。
-   前のタスクの大きなスクリプトが、手本として受け継がれないようにする。

### 2.2. スコープ (In Scope)

-   `docs/dev/conventions/requirements_process.md` の「1. Requirements Document」（AC の書き方）と「4. Acceptance Tests」（`diff` の確かめ）、および「3. Implementation Plan」と「5. Pre-Commit Checklist」のうち `diff` の確かめに触れる箇所（F-001〜F-003）。
-   `.claude/commands/mkplan.md` の確かめの種類と計画の規則、英語だけを求める規則、計画のレビューのチェックリスト（F-001〜F-006）。
-   `.claude/commands/runplan.md` の `diff` の確かめに触れる箇所（PR を作る前の確かめ、フェーズのまとまりのレビューのチェックリスト、すべてのフェーズが終わったときの確かめ）と、英語だけを求める規則（F-002・F-005・F-006）。
-   `.claude/commands/weakreview.md` のチェックリストと、英語だけを求める規則（F-005・F-006）。
-   `CLAUDE.md` の「Go Idioms」（guard-test literal exception）と「Testing Strategy」（`diff` の確かめに触れる箇所）（F-002・F-003・F-005）。
-   `.claude/commands/mkreq.md`。`design_handoff.md` の H-01 で、ここに書くと決めたときに限る（F-003）。

## 3. 機能要件 (Functional Requirements)

本章の用語は、次のとおりとする。
-   「規約」は、`docs/dev/conventions/requirements_process.md` を指す。
-   「記録した差分の読み取り」は、F-002 の形の `diff` の確かめを指す。
-   各 AC の「述べる」は、規約・コマンドの定義・`CLAUDE.md` が、エージェントが従う規則としてその内容を書いていることをいう。規則を書いた箇所への明示の参照も、「述べる」に含める。どこに書き、どこから参照するかは、設計で決める（`design_handoff.md` の H-03）。

### 3.1. 機能一覧

#### F-001: 作りの基準と既定の言語

`diff` の確かめの作りを、確かめる差分の大きさに見合ったものにする。

**Acceptance Criteria**:
- **AC-01**: 規約の「4. Acceptance Tests」と `mkplan.md` は、次のことを述べる。
    -   `diff` の確かめの作りは、確かめる差分の大きさに見合ったものにする。
    -   スクリプトの既定の言語はシェル（`git diff`、`cmp` など）とする。
    -   ほかの言語は、シェルで足りない理由を計画に書いたときに使ってよい。

#### F-002: 記録した差分の読み取り

小さな文書の変更では、スクリプトの代わりに、差分を記録してレビューで読むことを認める。

**Acceptance Criteria**:
- **AC-02**: 規約の「4. Acceptance Tests」と `mkplan.md` は、次のことを述べる。
    -   差分が小さい文書の変更では、記録した差分の読み取りを `diff` の確かめとして認める。PR のブランチで実際に実行した `git diff` の出力を、マージの基点と PR の head のコミットの ID とともに、計画の確かめの行に記録し、PR のレビューで読む。
    -   計画は、記録した差分の読み取りを使うことと、比べるパスを書く。
    -   「小さい」かどうかは、計画を書く者が判断し、レビュアーはその判断に異論を述べられる。数の閾値は設けない。
    -   記録した差分の読み取りには、壊して失敗を確かめる手順は要らない。
- **AC-03**: 規約の「4. Acceptance Tests」と `runplan.md` は、記録した差分の読み取りについて、次のことを述べる。
    -   `/runplan` が、PR のブランチで `git diff` を実行し、その出力と 2 つのコミットの ID を計画の確かめの行に記録する。
    -   記録の後で、比べたパスの内容が変わったとき（`/fixpr` の修正、`main` の取り込み、レビューの後の修正）は、PR を作る前とマージの前に記録し直す。
    -   記録する PR の head は、比べたコミットである。記録をコミットすると head は進むが、比べたパスの内容が最終の head と同じである限り、記録は有効である。
    -   比べるパスは、AC が名指すパスに限ってよく、計画そのものを比べる範囲から外せる。ただし、変わるファイルを限る AC では、差分全体の変わったファイルの一覧（`git diff --name-only`）も記録する。対象外のファイルの変更を見落とさないためである。
    -   レビュアーが「小さい」という判断に異論を述べたときは、マージの前に、その AC の確かめを `_checks/` のスクリプトに替える。
- **AC-04**: 規約の「3. Implementation Plan」「4. Acceptance Tests」「5. Pre-Commit Checklist」、`mkplan.md` の確かめの種類の定義と計画のレビューのチェックリスト、`runplan.md` の `diff` の確かめに触れる箇所（PR を作る前の確かめ、フェーズのまとまりのレビューのチェックリスト、すべてのフェーズが終わったときの確かめ）、`CLAUDE.md`「Testing Strategy」は、記録した差分の読み取りを `diff` のラベルの確かめとして扱う。これらの箇所に、`diff` のラベルの確かめを「`_checks/` のスクリプト」だけとして述べる文が残らない。

#### F-003: 前後の関係を述べる AC の書き方

**Acceptance Criteria**:
- **AC-05**: 規約の「1. Requirements Document」は、次のことを規則として述べる。
    -   前後の関係を述べる AC は、「X の差分は Y と Z に限られる」の形で書き、守る部分を並べ挙げない。
    -   移動と分割の AC だけは、「A の内容が B に変わらずにある」の形で書いてよい。

  `/mkreq` は、AC を書くときにこの規則に従う（`.claude/commands/mkreq.md` の step 6 が、規約の §1 に従うと定める）。規約の「4. Acceptance Tests」、`mkplan.md`、`CLAUDE.md`「Testing Strategy」が挙げる前後の関係の例（今は「既存の見出しの言い回しと順序が保たれる」の形）は、この規則の形に書き換える。

#### F-004: 計画が `_checks/` について書くことの規則

**Acceptance Criteria**:

#### F-005: `_checks/` の日本語の文字列

## 6. 用語集 (Glossary)

-   **`diff` の確かめ**：前後の関係を述べる AC の確かめ方。マージの基点と PR の head を比べ、PR ごとに 1 回だけ行う（規約の「4. Acceptance Tests」）。本タスクで、スクリプトと、記録した差分の読み取りの 2 つの形にする。
-   **スクリプト**：`diff` の確かめのために、タスクの `_checks/` に置くプログラム。言語を問わない。
-   **記録した差分の読み取り**：F-002 で認める `diff` の確かめの形。`git diff` の出力をコミットの ID とともに計画に記録し、PR のレビューで読む。
-   **前後の関係を述べる AC**：何かが保たれる、変わらない、同じ順序で残る、といった変更の前と後の関係を述べる AC（規約の「4. Acceptance Tests」）。
-   **チェック**：スクリプトが確かめる性質の一つ一つ。チェックが成り立たないとき、スクリプトはそのチェックを名指して失敗する。
-   **壊し方**：スクリプトのチェックが、その性質を破った入力で失敗することを確かめるための変更（`CLAUDE.md`「Testing Strategy」の「Every test must be able to fail for its stated reason.」）。
-   用語は `docs/translation_glossary.md` と統一する。
