# 設計への申し送り（0108）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: 判定の規則の中での置き場所

**懸念:** `runpr.md` step 3 の「State of the latest request」は、規則 1〜6 を順に当て、最初に当たったものが決める。今は、結果のない完了は規則 1（Indeterminate）に当たる。受領コメントを待つ（AC-02）・人に尋ねる（AC-01）・止める（AC-12）の 3 つを、規則 1 の中に分けるか、新しい規則として足すかが決まっていない。

**なぜ重要か:** 受領コメントは `codex` の種類のコメントなので、規則の順序を誤ると、規則 3（Ended (unexpected post)）に当たって、尋ねずに止まりうる。逆に、規則 3 を緩めすぎると、ほかの想定外の投稿まで見逃しうる。待つ間の扱い（AC-02）を規則 4（Ended (timed out)）・規則 6（Waiting）とどう合わせるか、「On arriving at this step」の判定（Completed・Ended・Not started・Waiting・Indeterminate）と「Never post while ... Waiting or Indeterminate」とどう合わせるかも、同じ所で決まる。

**候補:**
-   `state` に結果のない完了を表す値（たとえば `completed-null <sha>`）を足し、規則 1 の前に、受領コメントの条件で「尋ねる」「待つ」「止める」を決める規則を置く。
-   規則 1 の中で、結果のない完了だけを例外として扱う。

**関連:** F-001・F-004、AC-01〜AC-03・AC-12

## H-02: 受領コメントの絞り込みの形

**懸念:** 受領コメントの形の判定（AC-05）を、今の一覧の `--jq` の絞り込みの中で行い、判定の結果だけを出す（AC-06）。`kind` を足すか、`codex` の種類に真偽値と短い SHA のメンバーを足すかが決まっていない。

**なぜ重要か:** 出力に本文の文字列が混ざると、AC-06 とガードテスト（AC-17）に反する。短い SHA を出すのは、`^[0-9a-f]{7,40}$` に合ったときだけにする必要がある。

**候補:**
-   `{kind: "receipt", url, created_at, ok: <bool>, short_sha: <形に合えば SHA、合わなければ null>}` を出す。
-   `codex` の種類のまま、`receipt` と `ok` と `short_sha` のメンバーを足す。

**関連:** F-002、AC-04〜AC-07・AC-17

## H-03: 人への問いと、詳細の示し方

**懸念:** AC-08 の問いを、step 3 の中でどう出すかが決まっていない。step 4 には、要約と詳細ファイルの決まり（`runpr.md` step 4 の「Summary and detail file」）があるが、step 3 の `AskUserQuestion`（ほかの Bot のメンションの問い、想定外のスレッドの問い）は URL を示すだけである。

**なぜ重要か:** 問いに示す値が決まっていないと、本文から読んだ文字列を示してしまうおそれがある（AC-08 は決まった文で示すと定める）。

**候補:**
-   step 3 のほかの問いと同じく、会話に値を示し、1 問の単一選択で尋ねる。
-   step 4 と同じ形の要約と詳細ファイルを使う。

**関連:** F-003、AC-08〜AC-11

## H-04: 人が認めた完了の持ち方と、LAST_REVIEWED・step 4 への渡し方

**懸念:** 人が認めた完了（AC-09）を、実行の中でどう持ち、LAST_REVIEWED の計算（AC-14）、step 4 の要約と詳細ファイル（AC-16）、最後の報告にどう渡すかが決まっていない。要約コメントの `commit_sha` か `updated_at` が変わったら無効にする（AC-11）ことも、持ち方で決まる。

**なぜ重要か:** LAST_REVIEWED は「その実行で見た完了の印と、今の要約コメントの完了の印」から決める（`.claude/commands/runpr.md:563-575`）。今の要約コメントは結果のない完了のままなので、人が認めた完了を「その実行で見た」側に入れないと、LAST_REVIEWED が「なし」になる。

**候補:**
-   「その実行で見た完了の印」に、人が認めた完了の `commit_sha` を加える、と LAST_REVIEWED の定義に書き足す。

**関連:** F-005、AC-14〜AC-16

## H-05: ガードテストの偽のデータ

**懸念:** `TestRunprDocContract` の `listings_print_no_body` は、`runprListingFixtures`（`cmd/yt2column/fixpr_docs_test.go:301`）の偽のコメントで絞り込みを実行する。受領コメントの受け入れる形と合わない形（AC-18）を、同じ偽のデータに足すか、別の subtest にするかが決まっていない。

**なぜ重要か:** 本文の印（`bodyMarker`）を、結果の行の後ろの文と 6 行目から後に置かないと、本文が出ないことを確かめられない（AC-17）。形の判定は、受け入れる形に合うものと合わないものの両方がないと、判定が常に真や常に偽でも通ってしまう。

**候補:**
-   `runprListingFixtures` に受領コメントを足し、形の判定は別の subtest で、入力ごとの期待する `ok` と `short_sha` を表にして確かめる。

**関連:** F-006、AC-17・AC-18
