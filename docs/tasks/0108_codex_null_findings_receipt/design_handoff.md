# 設計への申し送り（0108）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: 判定の規則の中での置き場所

**懸念:** `runpr.md` step 3 の「State of the latest request」は、規則 1〜6 を順に当て、最初に当たったものが決める。今は、結果のない完了は規則 1（Indeterminate）に当たる。受領コメントを待つ（AC-02）・利用者に尋ねる（AC-01）・止める（AC-14）の 3 つを、規則 1 の中に分けるか、新しい規則として足すかが決まっていない。

**なぜ重要か:** 受領コメントは `codex` の種類のコメントなので、規則の順序を誤ると、規則 3（Ended (unexpected post)）に当たって、尋ねずに止まりうる。逆に、規則 3 を緩めすぎると、ほかの想定外の投稿まで見逃しうる。待つ間の扱い（AC-02）を規則 4（Ended (timed out)）・規則 6（Waiting）とどう合わせるか、「On arriving at this step」の判定（Completed・Ended・Not started・Waiting・Indeterminate）と「Never post while ... Waiting or Indeterminate」とどう合わせるかも、同じ所で決まる。

**候補:**
-   `state` に結果のない完了を表す値（たとえば `completed-null <sha>`）を足し、規則 1 の前に、受領コメントの条件で「尋ねる」「待つ」「止める」を決める規則を置く。
-   規則 1 の中で、結果のない完了だけを例外として扱う。

形に合う受領コメントを規則 3 から除くこと（AC-03）と、断りのコメントの例外で除かないこと（F-001 の条件 3）も、同じ所で書き表す。承認の後は Completed と同じに扱い、承認を要約コメントと受領コメントの組に結び付ける（AC-13）ので、承認の持ち方（H-04）とも合わせる。

**関連:** F-001・F-004、AC-01〜AC-04・AC-13・AC-14

## H-02: 受領コメントの絞り込みの形

**懸念:** 受領コメントの形の判定（AC-06）を、今の一覧の `--jq` の絞り込みの中で行い、判定の結果だけを出す（AC-07）。`kind` を足すか、`codex` の種類に真偽値と短い SHA のメンバーを足すかが決まっていない。

**なぜ重要か:** 出力に本文の文字列が混ざると、AC-07 とガードテスト（AC-19）に反する。短い SHA を出すのは、`^[0-9a-f]{7,40}$` に合ったときだけにする必要がある。

**候補:**
-   `{kind: "receipt", url, created_at, ok: <bool>, short_sha: <形に合えば SHA、合わなければ null>}` を出す。
-   `codex` の種類のまま、`receipt` と `ok` と `short_sha` のメンバーを足す。

**関連:** F-002、AC-05〜AC-09・AC-19

## H-03: 利用者への問いと、詳細の示し方

**懸念:** AC-10 の問いを、step 3 の中でどう出すかが決まっていない。step 4 には、要約と詳細ファイルの決まり（`runpr.md` step 4 の「Summary and detail file」）があるが、step 3 の `AskUserQuestion`（ほかの Bot のメンションの問い、想定外のスレッドの問い）は URL を示すだけである。

**なぜ重要か:** 問いに示す値が決まっていないと、本文から読んだ文字列を示してしまうおそれがある（AC-10 は決まった文で示すと定める）。

**候補:**
-   step 3 のほかの問いと同じく、会話に値を示し、1 問の単一選択で尋ねる。
-   step 4 と同じ形の要約と詳細ファイルを使う。

**関連:** F-003、AC-10〜AC-13

## H-04: 利用者が認めた完了の持ち方と、LAST_REVIEWED・step 4 への渡し方

**懸念:** 利用者が認めた完了（AC-11）を、実行の中でどう持ち、LAST_REVIEWED の計算（AC-16）、step 4 の要約と詳細ファイル（AC-18）、最後の報告にどう渡すかが決まっていない。要約コメントの `commit_sha` か `updated_at` が変わったら無効にする（AC-13）ことも、持ち方で決まる。

**なぜ重要か:** LAST_REVIEWED は「その実行で見た完了の印と、今の要約コメントの完了の印」から決める（`.claude/commands/runpr.md:563-575`）。今の要約コメントは結果のない完了のままなので、利用者が認めた完了を「その実行で見た」側に入れないと、LAST_REVIEWED が「なし」になる。

**候補:**
-   「その実行で見た完了の印」に、利用者が認めた完了の `commit_sha` を加える、と LAST_REVIEWED の定義に書き足す。


**関連:** F-005、AC-16〜AC-18

## H-05: ガードテストの偽のデータ

**懸念:** `TestRunprDocContract` の `listings_print_no_body` は、`runprListingFixtures`（`cmd/yt2column/fixpr_docs_test.go:301`）の偽のコメントで絞り込みを実行する。受領コメントの受け入れる形と合わない形（AC-20）を、同じ偽のデータに足すか、別の subtest にするかが決まっていない。

**なぜ重要か:** 本文の印（`bodyMarker`）を、結果の行の後ろの文と 6 行目から後に置かないと、本文が出ないことを確かめられない（AC-19）。形の判定は、受け入れる形に合うものと合わないものの両方がないと、判定が常に真や常に偽でも通ってしまう。

**候補:**
-   `runprListingFixtures` に受領コメントを足し、形の判定は別の subtest で、入力ごとの期待する `ok` と `short_sha` を表にして確かめる。

**関連:** F-006、AC-19・AC-20

## H-06: 結果の行の前方一致の文字列と、シェルの引用

**懸念:** 受け入れる前方（`Codex Review: Didn't find any major issues.`）は ASCII のアポストロフィ（U+0027。本書の作成のときに API の JSON の本文で確かめた）を含む。`--jq` の絞り込みはシェルの単一引用符で囲むので、そのままでは書けない。

**なぜ重要か:** 引用を誤ると絞り込みが壊れる。符号位置を誤ると、すべての受領コメントが形に合わないと判定され、毎回止まる（止まる側に倒れるが、本タスクの目的を果たさない）。

**候補:**
-   jq の文字列の中で `\u0027` と書く。
-   絞り込みを単一引用符で囲まない形にする（ガードテストが読む形との兼ね合いを含む）。

**関連:** F-002、AC-06・AC-20
