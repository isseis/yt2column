## 1. 概要 (Overview)

**目的:** 本書は、Codex の要約コメントが `completed` なのに `has_any_findings` が `null` のとき、`/runpr` が受領コメントを使って人に確かめ、人が認めたときに次の段階へ進むようにする要件を定義する。

**背景:**

-   `/runpr` の step 3 は、Codex の要約コメントの 2 行目（状態の行）だけを `--jq` で読む。`completed` で `has_any_findings` が JSON の真偽値のときだけ完了の印とし、`completed` で真偽値でないものは `indeterminate` とする（`.claude/commands/runpr.md:416-457`）。要約コメントの状態が `indeterminate` なら、規則 1 で判定できない状態として止まる（`.claude/commands/runpr.md:537-539`、`:599-617`）。真偽値を求めるのは、タスク 0031 の観測で、完了したレビューでは必ず真偽値、途中では `null` だったためである（[0031 設計書](../0031_codex_pr_review/02_architecture.md) 1.2・3.2）。
-   PR #998 の `/runpr` は、この規則で止まった。2026-11-18T13:51:47Z の手動の依頼に対し、Codex は要約コメントを `completed` に更新したが、`has_any_findings` は `null` だった。レビューの結果は、Codex が投稿した受領コメント（1 行目が `<!-- codex-review-receipt:v1 -->`）のほうにあった（issue #1005）。
-   受領コメントは、今は `codex` の種類のコメントとして数えるだけで、本文は読まない（`.claude/commands/runpr.md:430-436`）。step 3 の一覧の絞り込みは、要約コメントの最初の 2 行のほかは本文をセッションに出さない（`.claude/commands/runpr.md:413-414`）。ガードテスト `TestRunprDocContract` の `listings_print_no_body` は、絞り込みを偽の本文で実行して、本文が出ないことを確かめる（`cmd/yt2column/fixpr_docs_test.go:187-189`）。
-   PR #998 の受領コメントは、2026-11-18 と 2026-11-19 の 2 件を確かめた。どちらも、1 行目が `<!-- codex-review-receipt:v1 -->`、2 行目と 4 行目が空、3 行目が結果の行、5 行目が ``**Reviewed commit:** `<短い SHA>` `` だった。結果の行は、1 件目が `Codex Review: Didn't find any major issues. :+1:`、2 件目（`has_any_findings` が `false` だったレビュー）が `Codex Review: Didn't find any major issues. Already looking forward to the next diff.` で、`Didn't find any major issues.` の後ろの文が違った。短い SHA は、どちらも 10 桁だった。
-   `codex-review-state:v1` の行にも受領コメントにも、OpenAI の公式の文書はない（issue #1005）。

対応 issue: [#1005](https://github.com/isseis/yt2column/issues/1005)（関連: PR [#998](https://github.com/isseis/yt2column/pull/998)（止まった PR）、PR [#984](https://github.com/isseis/yt2column/pull/984)（受領コメントのない `null`）、タスク 0031（今の判定の規則の元）、openai/codex#57326、openai/codex#57619）

本書は、`/runpr` が人に尋ねる条件、受領コメントの受け入れる形と読む範囲、人の答えの扱い、エスカレーションとの関係、ガードテストの対象、ADR を決める。規則を `runpr.md` の判定の規則のどこに置くか、`--jq` の絞り込みの書き方、ガードテストの偽のデータの作り方は、`02_architecture.md` が決める（`design_handoff.md`）。

### issue #1005 で決めたこと

-   **要約コメントが `completed` で `has_any_findings` が `null` でも、受領コメントがレビューの結果を示していれば、`/runpr` は止まらずに `AskUserQuestion` で人に尋ね、人が「指摘なしとして進む」を選んだときだけ、そのコミットの完了の印として扱う（F-001・F-003）。** 規則どおりに止まった #998 でも、レビューの結果は受領コメントにあったためである。
    -   ADR：[ADR-0013](../../dev/adr/0013-review-setup.md) を更新する。
-   **受領コメントがない場合（#984 の形）は、今までどおり判定できない状態として止める（F-004）。** 結果を示すものがなく、レビューが行われたかが分からないためである。止まるまでの時間は、要件定義の際に決めた（受領コメントを待つ項）。
    -   ADR：ADR-0013。
-   **尋ねる条件は、要約コメントが 1 件で依頼の後に更新されていること、依頼の後に完了を待つ PR レビュアーが投稿した受領コメントがあること、受領コメントの短い SHA が要約コメントの `commit_sha` の先頭と一致し、そのコミットが依頼したコミットであること、とする（F-001）。** 受領コメントが、その依頼に答えたレビューの、そのコミットの結果だと確かめるためである。
    -   ADR：ADR-0013。
-   **問いには、受領コメントの URL、結果の行、レビューしたコミットを示す。人が「指摘なしとして進む」以外を選んだときは、今までどおり止める（F-003）。** 結果の行がどう示されるかは、要件定義の際に決めた（本文を読む範囲の項）。
    -   ADR：ADR-0013。
-   **Codex の状態の行の、ほかの形の変化への対応（`status: failed` など）は範囲外とする。** issue #1005 が範囲外とした。
    -   ADR：なし。本タスクでは決めない。

### 要件定義の際に決めたこと（2026-11-19）

-   **進め方は通常の進め方（`full`）とする。この変更は、除外される変更に当たる。** 除外の判断：Bot（Codex）が書いた受領コメントの本文を読んで、レビュー済みの判定に使う。これは、Bot のテキストの扱い方に触れる、開発の道具の信頼境界の変更である（`docs/dev/conventions/requirements_process.md`「Simple Process」の「Excluded changes」、[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）。PR レビューを追加で頼むかを決めるレビューの関門（LAST_REVIEWED の定義）も変える（[ADR-0013](../../dev/adr/0013-review-setup.md)）。規模の面でも、決めることが多く、ADR-0013 の決定を変える。人の答え：通常の進め方。
    -   ADR：なし。本タスクの中で閉じる、進め方の選択である。
-   **受領コメントの本文は、`--jq` の絞り込みの中で形を判定し、セッションには判定の結果だけを出す。出すのは、形に合うかどうかの真偽値、小文字の 16 進の 7〜40 桁と確かめた短い SHA、URL、時刻だけで、本文の文字列は出さない（F-002）。人は URL から GitHub で本文を確かめる。** 要約コメントの最初の 2 行のほかは本文をセッションに出さないという今の原則を保つためである。本文の 3 行をそのまま出す案は、本文の一部がエージェントに渡り、ADR-0015 の更新とガードの例外が要るので採らない。人の答え：判定の結果だけを出す。
    -   ADR：[ADR-0013](../../dev/adr/0013-review-setup.md) を更新する。本文をセッションに出さないので、ADR-0015 は変えない。
-   **受け入れる結果の行は、指摘なしの形だけとする。3 行目が `Codex Review: Didn't find any major issues.` で始まる行を受け入れ、後ろの文は問わず、読まない。ほかの形は止める（F-002）。** 決まった形以外は止めるのが今の方針である。後ろの文は観測した 2 件で違ったので、ちょうどの一致にすると、Codex が後ろの文を変えるたびに止まる。指摘ありの形を受け入れてスレッドの処理に回す案は採らない。指摘ありなら、`has_any_findings` が `null` の理由がさらに分からないためである。人の答え：指摘なしの形だけ、前方一致。
    -   ADR：ADR-0013（指摘なしの形だけを受け入れること）。前方一致の文字列は値の形の細部なので、ADR には書かない。
-   **受領コメントの短い SHA は、小文字の 16 進の 7〜40 桁で、要約コメントの `commit_sha` の先頭と一致するものだけを受け入れる（F-002）。** git の短い SHA の桁数はリポジトリの大きさで変わりうるので、観測した 10 桁ちょうどに限ると、桁数が変わったときに止まるためである。人の答え：7〜40 桁。
    -   ADR：なし。値の形の細部である。
-   **依頼の後に投稿された受領コメントが 2 件以上あるときは、判定できない状態として止める（F-004）。** 要約コメントが 2 件以上あるときに、どれを使うかを選ばずに止める今の規則 1 と同じ考え方である。人の答え：止める。
    -   ADR：ADR-0013。
-   **要約コメントが `completed` で `has_any_findings` が `null` で、受領コメントがまだないときは、依頼から約 15 分の期限まで待つ。期限までに受領コメントが来れば人に尋ね、来なければ判定できない状態として止める（F-001・F-004）。** 受領コメントが要約コメントの更新より遅れて投稿されると、すぐ止める規則では、その間のポーリングで止まるためである。#998 の要約コメントの更新の時刻は、後のレビューで上書きされて確かめられない。費用として、#984 の形は、すぐ止まる代わりに約 15 分待ってから止まる。待つ間に依頼はしないので、割り当ては使わない。人の答え：期限まで待つ。
    -   ADR：ADR-0013。
-   **人が認めた完了は、その実行の中で完了の印として扱い、LAST_REVIEWED を決める完了の印に含める（F-005）。** 受領コメントが、レビューしたコミットを示しているためである。含めないと LAST_REVIEWED が「なし」になり、マージの質問が PR レビューの依頼を勧めて、割り当てを余分に使う。人の答え：数える。
    -   ADR：ADR-0013。
-   **人が認めたことは、その実行の報告と、step 4 のマージの質問の要約と詳細ファイルに示すだけにし、永続的な記録は足さない。再実行では、もう一度人に尋ねる（F-005）。** 要約コメントと受領コメントは GitHub に残り、マージは人がマージの質問に答えて決めるためである。squash コミットに残す案は `mergepr.md` の変更が要り、PR にコメントを残す案は GitHub への書き込みが増えるので採らない。人の答え：報告とマージの質問だけ。
    -   ADR：ADR-0013。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   Codex が要約コメントに結果を書かずに完了し、受領コメントに指摘なしの結果を書いたとき、`/runpr` が止まらず、人の確認を経て次の段階へ進めるようにする。
-   受領コメントの本文をセッションに出さないまま、受け入れる形を決まった形に限る。

### 2.2. スコープ (In Scope)

-   `.claude/commands/runpr.md` の step 3 の、レビューの状態の判定と停止の報告（F-001〜F-004）。
-   `.claude/commands/runpr.md` の、人が認めた完了の LAST_REVIEWED への算入、step 4 のマージの質問の要約と詳細ファイル、最後の報告（F-005）。
-   ガードテスト `TestRunprDocContract`（`cmd/yt2column/fixpr_docs_test.go`）の、受領コメントの絞り込みへの拡張（F-006）。
-   ADR-0013 の更新（F-007）。

### 2.3. スコープ外 (Out of Scope)

-   Codex の状態の行の、ほかの形の変化への対応（`status: failed` など）（issue #1005）。
-   指摘ありの形の受領コメントの受け入れ（要件定義の際に決めたこと）。
-   人が認めたことの永続的な記録（squash コミット、PR へのコメント）と、実行をまたいでの引き継ぎ（要件定義の際に決めたこと）。
-   受領コメントのない `null` の完了（#984 の形）を進めること。今までどおり止める。
-   `_lib/task-pr-handoff.md` Part B step 5（PR を開いた直後の開始の印の確かめ）。要約コメントの更新の時刻だけを見て、状態の行の形を確かめないので、影響を受けない。
-   `mergepr`・`fixprguard`・`codexreview`・`pr-review-escalation.md`・`review-records.sh` の変更。LAST_REVIEWED は `runpr.md` が決めて渡す値で、その渡し方は変えない。
-   リアクション（👍）を読むこと。今も読まない（`.claude/commands/runpr.md:497-498`）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

本章の用語は 6 章で定義する。「依頼」は `runpr.md` step 3 の最新の依頼（latest request）、「依頼したコミット」は同じく requested commit である。

#### F-001: 結果のない完了で人に尋ねる条件

最新の依頼について、次のすべてが成り立つとき、`/runpr` は判定できない状態として止まる代わりに、人に尋ねる（F-003）。

1.  要約コメントがちょうど 1 件で、依頼の後に更新されている。
2.  その要約コメントの状態の行が、結果のない完了である。
3.  依頼の後に作られた `codex` の種類のコメント（今の `runpr.md` の断りのコメントの例外で除くものを除く）が、ちょうど 1 件の受領コメントだけである。
4.  その受領コメントが、受け入れる形（F-002）に合う。
5.  受領コメントの短い SHA が、要約コメントの `commit_sha` の先頭と一致する。
6.  要約コメントの `commit_sha` が、依頼したコミットである。

**Acceptance Criteria**:
- **AC-01**: `runpr.md` の step 3 は、上の 1〜6 がすべて成り立つとき、判定できない状態として止まらず、F-003 の問いを出す、と述べる。
- **AC-02**: `runpr.md` の step 3 は、1 と 2 が成り立ち、受領コメントがまだなく（`codex` の種類のコメントが依頼の後に 1 件もなく）、依頼から約 15 分たっていないときは、止まらず、依頼もせずにポーリングを続ける、と述べる。この待ちは、今の待ちと同じく依頼の時刻から数える期限を延ばさない。
- **AC-03**: `runpr.md` の step 3 は、結果のない完了でない要約コメント（`completed` で `has_any_findings` が真偽値、`running`、ほかの判定できない形）と、要約コメントが 2 件以上ある場合の判定を変えない。`completed` で `has_any_findings` が真偽値なら、受領コメントの有無によらず今までどおり完了の印である。

#### F-002: 受領コメントの受け入れる形と読む範囲

受領コメントは GitHub の応答から読む、信頼できない入力である。`/runpr` は、要約コメントと同じ一覧の読み取りの中で、受領コメントの形を `--jq` の絞り込みで判定し、判定の結果だけをセッションに出す。

**Acceptance Criteria**:
- **AC-04**: 受領コメントとみなすのは、著者が `Bot` の種類で名前が `<awaited-reviewer>[bot]` で、本文の 1 行目がちょうど `<!-- codex-review-receipt:v1 -->` のコメントだけである。`runpr.md` の step 3 はこの定義を述べる。
- **AC-05**: 受け入れる形は、本文を改行（LF）で分けた行が次のとおりのものだけである。`runpr.md` の step 3 はこの形を述べ、ほかの形の受領コメントは受け入れる形に合わないとする、と述べる。
    -   1 行目がちょうど `<!-- codex-review-receipt:v1 -->`。
    -   2 行目と 4 行目が空。
    -   3 行目が `Codex Review: Didn't find any major issues.` で始まる。後ろの文は問わない。
    -   5 行目が、ちょうど `` **Reviewed commit:** ` `` と、小文字の 16 進の 7〜40 桁と、`` ` `` を並べたもの。

    6 行目から後は読まず、形を問わない（拡張を許すメンバーとする）。行の終わりに CR がある行、5 行に満たない本文、大文字の 16 進、桁数が範囲の外の SHA は、補わずに受け入れる形に合わないとする。
- **AC-06**: 受領コメントについてセッションに出るのは、URL・`created_at`・受け入れる形に合うかの真偽値・形に合ったときの短い SHA だけである。結果の行の後ろの文を含め、本文の文字列は出さない。形に合わないときは、短い SHA も出さない。`runpr.md` の step 3 の絞り込みと、それを述べる文がこれを満たす。
- **AC-07**: 受領コメントの読み取りで使うのは、コメントの `user.type`・`user.login`・`body`（絞り込みの中で 1〜5 行目だけ）・`html_url`・`created_at` だけである。ほかのメンバーは使わない。

#### F-003: 人への問いと答え

**Acceptance Criteria**:
- **AC-08**: F-001 の条件がそろうと、`/runpr` は `AskUserQuestion` で 1 問だけ尋ねる。問いと詳細の説明には、受領コメントの URL、要約コメントの URL、要約コメントの `commit_sha`（40 桁）と受領コメントの短い SHA、そのコミットが依頼したコミットであること、受領コメントの結果の行が指摘なしの形（AC-05）に合ったことを示す。結果の行は、本文から読んだ文字列ではなく、決まった文（指摘なしの形に合った、ということ）で示す。選択肢は「指摘なしとして進む」と「止める」である。
- **AC-09**: 人が「指摘なしとして進む」を選ぶと、`/runpr` はその要約コメントの `commit_sha` の完了の印があるものとして、最新の依頼を Completed と同じに扱い、step 3 の続き（スレッドの処理、エスカレーション、CI）へ進む。
- **AC-10**: 人がそれ以外を答えたとき（「止める」と自由記述を含む）は、`/runpr` は今の判定できない状態と同じく止まり、同じ報告をする。報告には受領コメントの URL を加える。
- **AC-11**: 人が認めたのは、問いを出したときの要約コメント（その `commit_sha` と `updated_at`）についてだけである。その後のポーリングで要約コメントの `commit_sha` か `updated_at` が変わったときは、新しい状態として step 3 の規則で判定し直す。

#### F-004: 受領コメントで確かめられないときは止める

**Acceptance Criteria**:
- **AC-12**: 要約コメントが 1 件で、依頼の後に更新され、結果のない完了で、次のどれかに当たるときは、`/runpr` は判定できない状態として止まる。止まるときの報告は今の判定できない状態の報告に、依頼の後の `codex` の種類のコメント（受領コメントを含む）の URL と、それぞれが受領コメントか、受け入れる形に合ったかを加えたものである。本文は出さない。
    -   依頼から約 15 分たっても、依頼の後の `codex` の種類のコメントが 1 件もない（#984 の形）。
    -   依頼の後の受領コメントが 2 件以上ある。
    -   依頼の後に、受領コメントでない `codex` の種類のコメントがある（今の断りのコメントの例外で除くものを除く）。
    -   受領コメントが受け入れる形に合わない。
    -   受領コメントの短い SHA が `commit_sha` の先頭と一致しない。
    -   `commit_sha` が依頼したコミットでない。
- **AC-13**: AC-12 で止まったとき、`/runpr` は依頼を投稿しない。再実行も依頼を投稿しない。今の判定できない状態と同じである（`.claude/commands/runpr.md:616-618`）。

#### F-005: 人が認めた完了の扱い

**Acceptance Criteria**:
- **AC-14**: `runpr.md` の LAST_REVIEWED の定義は、人が認めた完了（AC-09）を、その実行で見た完了の印に含める、と述べる。
- **AC-15**: 人が認めた完了は、その実行の中だけで持つ。`runpr.md` は、再実行が同じ要約コメントと受領コメントを見たときは、もう一度 F-003 の問いを出す、と述べる。
- **AC-16**: 人が認めた完了があった実行では、step 4 のマージの質問の要約と詳細ファイル、および最後の報告が、Codex の完了を受領コメントで人が認めたことを、そのコミットと受領コメントの URL とともに示す。コミット・PR へのコメント・PR の説明には記録しない。

#### F-006: ガードテスト

**Acceptance Criteria**:

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   受領コメントを待つ間（AC-02）は、今の約 30 秒ごとのポーリングを続ける。受領コメントの読み取りは、今の一覧の読み取りと同じ API の呼び出しの中で行い、呼び出しの回数を増やさない。
-   #984 の形は、すぐに止まる代わりに、依頼から約 15 分たってから止まる（要件定義の際に決めたこと）。

### 4.2. セキュリティ (Security)

-   受領コメントは、GitHub の応答から読む信頼できない入力である。著者が `Bot` の種類で名前が `<awaited-reviewer>[bot]` のコメントだけを受領コメントとし（AC-04）、決まった形に合うものだけを受け入れ、補わない（AC-05）。
-   本文の文字列はセッションに出さない（AC-06）。セッションはファイルを編集できるエージェントなので、Bot の本文に書かれた指示がエージェントに届かないようにするためである。この点で、要約コメントの最初の 2 行のほかは本文を出さないという今の原則（`.claude/commands/runpr.md:413-414`）と、[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md) の考え方を保つ。
-   受領コメントだけでは完了としない。人が URL から GitHub で本文を確かめ、「指摘なしとして進む」を選んだときだけ進む（AC-08・AC-09）。`/runpr` が自動で進むことはない。
-   受け入れる危険：完了を待つ PR レビュアーの名前の `Bot` が書いた受領コメントの形を、人の確認を経て信じる。Codex 自身が実際にはレビューしていないのに指摘なしの受領コメントを投稿した場合は、人の確認でも見分けられない。これは、`completed` と真偽値がそろっても中身のあるレビューを保証しない、今の危険（[0031 設計書](../0031_codex_pr_review/02_architecture.md) 5 章）と同じ種類である。
-   本変更はレビューの関門（LAST_REVIEWED の定義）を変えるので、実装の PR は Escalation の基準で PR レビューの追加の依頼の対象になる（[ADR-0013](../../dev/adr/0013-review-setup.md)）。
-   `docs/dev/security.md` の規則と前提は変えない。条件付きのガイドの適用条件（外部コマンド `yt-dlp`、API キー、キャッシュ、LLM API への送信、信頼できないテキストのプロンプトや記事への埋め込み）にはどれも当たらない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   形の合わないもの、そろわないものは、補わずに今までどおり止める（AC-12）。Codex が受領コメントの形を変えたときも、止まる側に倒れる。
-   止まったときの回避の手段（GitHub で Codex のレビューを確かめて `/mergepr` で直接マージする、手で依頼を投稿して再実行する）は、今のまま使える（`.claude/commands/runpr.md:619-629`）。

### 4.4. 互換性 (Compatibility)

-   `completed` で `has_any_findings` が真偽値の要約コメントでの振る舞いは変わらない（AC-03）。受領コメントがあっても、今までどおり完了の印で判定する。
-   人が認めたことは実行の中だけで持つので、古い実行の記録や、ほかのコマンドとの間の新しい約束はできない（AC-15）。

### 4.5. 保守性 (Maintainability)

-   受領コメントの受け入れる形（1 行目の印、結果の行の前方、5 行目の形）は、`runpr.md` の step 3 の絞り込みとそれを述べる文、ガードテストの偽のデータの 3 か所にある。Codex が形を変えたときは、3 つとも変える。
-   `codex-review-state:v1` の行と受領コメントには公式の文書がない。観測に基づく規則であり、形が変われば止まる（ADR-0013 の「結果」）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   CLAUDE.md の「Reject, don't normalize」に従い、受領コメントの形を補わずに拒む。
-   CLAUDE.md の「Document tests check values, structure, and executable examples, never prose」に従う。ガードテストは、本文を出してはならない `--jq` の絞り込み（信頼の境界で実行するコマンドの例外）を実行して確かめる。`runpr.md` の文の中身は、PR のレビューで読んで確かめる。
-   CLAUDE.md の「Keep internals unobservable」の考え方に従い、人が認めた完了の記録を、ほかのコマンドが読む値にしない。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。
-   **要約コメント:** 完了を待つ PR レビュアー（Codex）の要約コメント。著者が `Bot` の種類で名前が `<awaited-reviewer>[bot]`、1 行目がちょうど `<!-- codex-pull-request-review-summary -->` のコメント（`.claude/commands/runpr.md:446-448`）。
-   **状態の行:** 要約コメントの 2 行目。`<!-- codex-review-state:v1 <JSON> -->` の形をとる。
-   **完了の印:** 状態の行の `status` が `completed` で `has_any_findings` が JSON の真偽値のもの（`.claude/commands/runpr.md:451-453`）。
-   **結果のない完了:** 状態の行が、`runpr.md` の step 3 の状態の行の形（`code_review` がオブジェクトで、`status` が文字列、`commit_sha` が小文字の 16 進の 40 桁）に合い、`status` が `completed` で、`has_any_findings` が JSON の `null` のもの。`has_any_findings` が欠けているものや、ほかの型のものは含まない。
-   **受領コメント:** 完了を待つ PR レビュアーが投稿した、本文の 1 行目がちょうど `<!-- codex-review-receipt:v1 -->` のコメント（AC-04）。
-   **人が認めた完了:** 結果のない完了の要約コメントについて、受領コメントで人が「指摘なしとして進む」を選んだもの（AC-09）。その実行の中だけで完了の印として扱う。
