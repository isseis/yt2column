## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

`.claude/commands/runpr.md` の step 3〜5 を設計書 3.1〜3.4 のとおりに書き換え、Codex の要約コメントが結果のない完了のときに、受領コメントで利用者に確かめて進めるようにする。あわせて、ガードテスト `TestRunprDocContract` の `listings_print_no_body` を設計書 3.5 のとおりに広げ、ADR-0013 の「決定」から食い違いの記述を消す（設計書 3.6）。

### 1.2. 実装の原則

-   **絞り込みとガードテストを先に固める。** 設計書 8 章の優先順位 1 のとおり、一覧の絞り込みが本文を出さないことを、ガードテストを広げて確かめてから、規則の文を書く。偽のデータと期待する値を先に足し、今の絞り込みでテストが落ちることを確かめてから、絞り込みを書き換える。
-   **規則の文の前提を、文を書く前に確かめる。** 一覧を読めなかったときの扱い（設計書 1.2 の決定 10）は、`gh` の `--paginate` の振る舞いを前提にする。その前提を `gh` で確かめてから（ステップ 1-3）、規則の文を書く（ステップ 1-4 から後）。
-   **`runpr.md` の文は英語で書く**（`CLAUDE.md`「Document language」の原則 (b)）。利用者に示す問いの文、選択肢、要約の行の決まった文は、今の `runpr.md` の問いと要約の行と同じく日本語で書く。
-   **テストのコメント・識別子・文字列のリテラルは英語で書く**（`CLAUDE.md`「Go Idioms」）。偽の受領コメントの本文は英語の観測の形（要件書 1 章の背景）である。U+2019 は、文字そのものではなく Go の Unicode のエスケープ（バックスラッシュ、`u`、`2019` を並べたもの）で書き、U+0027 の場合と見分けやすくする。
-   **止まる側に倒す。** 設計書 1.1 のとおり、崩れたものは補わずに Indeterminate にするか判定をやり直す。
-   **今の振る舞いは、結果のない完了と受領コメントに関わる所のほかは変えない**（AC-04、設計書 1.1）。

## 4. テスト戦略 (Test Strategy)

-   **ユニットテスト:** 製品の Go のコードを足さないので、新しいユニットテストはない（設計書 7.1）。
-   **ガードテスト:** `TestRunprDocContract` の `listings_print_no_body` を広げ、一覧の絞り込みを jq で偽のコメントに実行する（ステップ 1-1）。確かめるのは、出力の鍵、`state`・`form_ok`・`short_sha` の値、`bodyMarker` が出ないことである。これは `CLAUDE.md`「Document tests check values, structure, and executable examples, never prose」の例外（信頼の境界で実行するコマンドの `--jq` の絞り込み）に当たる。新しいテストの関数は作らない（設計書 1.2 の決定 8）。
-   **境界値:** 短い SHA の桁数（6・7・40・41）、本文の行数（1・4・ちょうど 5・6 以上）、3 行目の後ろの文（なし・あり・途中の CR）、行の終わりの CR を、偽のデータで押さえる（ステップ 1-1）。
-   **壊して確かめる:** ステップ 1-2 で、設計書 7.2・7.3 の壊し方と、ステップ 1-2 に挙げた壊し方を 1 つずつ試し、テストが落ちることをコミットのメッセージに記録する（`CLAUDE.md`「Every test must be able to fail for its stated reason」）。
-   **gojq:** ガードテストは jq で実行するので、`gh` の gojq での振る舞いはステップ 1-3 で一度だけ確かめて記録する。継続して確かめる仕組みは足さない（設計書 5.3 の残るリスク）。
-   **文の中身:** `runpr.md` の規則・問い・報告の文は、PR のレビューで読んで確かめる（`manual`、設計書 7.2）。
-   **後方互換:** 今の偽の要約コメントの項目は、期待する状態を変えずに通ることで、AC-04 の今の振る舞いを確かめる（設計書 3.7）。
