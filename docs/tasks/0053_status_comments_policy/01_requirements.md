## 1. 概要 (Overview)

**目的:** 本書は、タスク文書（`01_requirements.md`・`02_architecture.md`・`03_implementation_plan.md`）の状態表の `Comments` に何を書くか、編集上の訂正と状態の遷移をどこに記録するかを定める要件を定義する（[#596](https://github.com/isseis/yt2column/issues/596)）。

**背景:**

タスク文書の状態表の `Comments` が肥大化している。issue #596 の調べでは、150 文書のうち 77 文書で 500 バイトを、19 文書で 2,000 バイトを超え、最大は約 8.9KB（`docs/tasks/0030_fixpr_untrusted_threads/02_architecture.md`）である。どれも表の 1 つのセルに一段落で書かれているため、読みにくい。たとえば `docs/tasks/0049_codex_local_review/03_implementation_plan.md:11` の `Comments` には、PR-1〜PR-5 の実装で入れた編集上の訂正の詳細が続けて書かれている。

主な原因は、`docs/dev/conventions/requirements_process.md`「Editing an approved document」の規則である（同書 16〜38 行）。承認後の編集上の訂正は `Comments` に記録し、そこに決定の変更でないことを明記する（同書 28〜32 行）。`/runplan`・`/fixpr`・`/mkarch` はこの規則に従って `Comments` に書き込む（`.claude/commands/runplan.md:63`、`.claude/commands/fixpr.md:456-461`、`.claude/commands/mkarch.md:72`）。そのため PR のたびに訂正の詳細が追記され、レビューが終わった後も残り続ける。

この規則の目的は、LLM が自分の編集を編集上の訂正と判断したときに、レビュアーが反論できるようにすることである（同書 36〜38 行）。この目的は、その PR のレビュアーが一度読めば果たせる。何をどう直したかは GitHub の PR に残る（squash の後の main のコミットメッセージは短い本文だけになる。`.claude/commands/mergepr.md:82`）ので、文書に恒久的に残す必要はない。

一方、状態の遷移（承認・`draft` への戻しなどの 4 種類。3 章で定義）の記録も `Comments` に積み重なる。決定の変更で `draft` に戻すときは、過去の承認を `Comments` に履歴として残す（同書 21〜24 行）。`/runplan` のセッション中の承認は、決定・日付・承認したことを `Comments` に書く（同書 24〜27 行、`.claude/commands/runplan.md:64`）。`/mkplan2` は PR 境界を加えた日を `Comments` に書く（`.claude/commands/mkplan2.md:107`）。そのため、`Comments` には今の状態の理由と過去の経緯が混ざり、レビュアーが今読むべきことが埋もれる。

対応 issue: [#596](https://github.com/isseis/yt2column/issues/596)

**本書の記述範囲:** 本書は、規則とコマンドの定義に従って文書と PR に何を書くか（`Comments` の内容、変更履歴の内容と作る時期、PR 本文に書く編集上の訂正、既存の文書の扱い）を定める。コマンドの定義のどの手順をどう書き換えるか、PR 番号を書き足す時期と手順、`/fixpr` が PR 本文を書き換える手段、変更履歴の 1 行の正確な書式、確かめる方法は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #596 で決めたこと:**

-   **編集上の訂正の詳細は PR 本文に書く:** 何を何に直したか、決定の変更でないことは、その PR のレビュアーが読む PR 本文（とコミットメッセージ）に書き、文書には書かない。レビュアーが一度読めば反論の機会は確保でき、何を直したかは PR に残るためである。
-   **決定の変更の中身は本文に反映する:** 後から読む人全員が必要とするためである。
-   **状態の遷移は 1 件 1 行で残す:** 承認、決定の変更、`withdrawn` とその理由は、後から読む人全員が必要とするので、日付・種類・PR 番号（または理由へのリンク）を 1 件 1 行で残す。置き場所は「要件定義の際に決めたこと」で変更履歴とした。
-   **`withdrawn` の日付と理由は文書に残す:** 現行どおり、日付と理由、または理由を記録した文書へのリンクを残す。
-   **既存のタスク文書の `Comments` は、本タスクでは改訂しない:** 新しい規則は、これ以降の編集から適用する。

**要件定義の際に決めたこと（2026-11-01）:**

-   **`Comments` は今の状態の理由だけにする:** `Comments` には、今の状態についてレビュアーが今知るべき理由だけを書き、状態が変わるたびに書き換える（追記しない）。`approved` と作ったばかりの `draft` では `-`、決定の変更で `draft` に戻した文書ではその旨と変更の要旨、`withdrawn` の文書では日付と理由（または理由を記録した文書へのリンク）を書く。issue の表は状態の遷移を `Comments` に 1 件 1 行で残すとし、受け入れの目安も「決定の変更を加える PR で `Comments` に追加されるのが 1 行の記録だけ」としていた。しかしそれでは遷移のたびに `Comments` が伸び、今の状態の理由が過去の行に埋もれる。そこで、この受け入れの目安は「`Comments` には今の状態の理由だけがあり、変更履歴に 1 行が加わる」に置き換える（F-002・F-003）。
-   **状態の遷移は文書末尾の変更履歴に書く:** 状態の遷移の履歴は、文書の末尾に変更履歴のセクションを設けて、そこに 1 件 1 行で、古い順に追記する。後から読む人全員のための記録を、表のセルではなく、行を増やしても読みやすい場所に置くためである。各行には、issue の形（日付・種類・PR 番号）に加えて、遷移の種類に応じた情報（承認者、変更の要旨、`withdrawn` の理由）を書く。何が誰の承認で変わったかを、行だけで読めるようにするためである。
-   **変更履歴に書くのは状態の遷移だけ:** 承認、決定の変更による `draft` への戻し、`/runplan` のセッション中の再承認、`withdrawn` を書く。編集上の訂正は書かない。訂正の記録は PR 本文で足り（issue #596 で決めたこと）、変更履歴に入れると、`Comments` と同じ肥大化が変更履歴でも起きるためである。
-   **承認も毎回変更履歴に書く:** `/runpr` での承認は、初回も、決定の変更で `draft` に戻した後も、変更履歴に 1 行ずつ書く。`draft` に戻すと `Review date` と `Reviewer` が `-` になるので、承認の記録が変更履歴になければ過去の承認が消えるためである。
-   **変更履歴のセクションは最初の 1 行を書くときに作る:** 文書を作るときには入れない。多くの場合、初回の承認を記録する `/runpr` が作る。テンプレートのない `02_architecture.md` と `03_implementation_plan.md` でも同じ扱いにでき、要件定義書のテンプレートを変えずに済むためである。
-   **`/fixpr` が入れた編集上の訂正は、PR 本文に追記する:** スレッドへの返信やコミットメッセージだけに任せず、PR 本文に書く。issue #596 の受け入れの目安（訂正の説明が PR 本文にある）を、PR を作った後の訂正でも満たすためである。
-   **変更履歴の行は、どれもその行を加えた PR の番号を持つ:** main に入った変更履歴の行には、どれもその行を加えた PR の番号がある。`/runplan` のセッション中の決定の変更のように、PR を作る前に行を書く場合がある（`.claude/commands/runplan.md:64`。PR はチェックポイントで作る）。`/mkplan2`（`.claude/commands/mkplan2.md:107`）と `/mkarch`（`.claude/commands/mkarch.md:72`）も同じである。手作業で取り下げた変更を、`/runpr` が単独の変更の PR にする場合も同じである。番号を書き足す時期（PR を作った直後か、`/runpr` のマージ前の記録か）は設計で決める。どの経路でも同じ結果を求め、時期の選び方は設計に任せるためである。
-   **`/runplan` のセッション中の決定の変更の理由は、変えた文書の本文に書く:** 変えた文書の本文に「実装の際に決めたこと（YYYY-MM-DD）」の節を設け、決定と理由を書く。変更履歴の行には要旨だけを書く。`/mkreq` などが決定を「…で決めたこと」の節に理由とともに記録する形にそろえ、変更履歴を 1 件 1 行に保つためである。
-   **`Comments` に複数の事項を書くときは `<br>` で区切る:** 表を崩さずに、1 件ずつ改行して表示するためである。
-   **既存の文書は、新しい規則で最初の状態の遷移を書くときに移す:** 旧規則（本タスクより前の規則）の `Comments` の文（`-` 以外）は、内容を変えずに変更履歴の先頭へ移し、そのうえで `Comments` を今の状態の理由に置き換える。移した文は、旧規則の `Comments` であると示す印を付けた先頭の 1 項目とし、1 件 1 行の規則の例外とする（PR 番号も求めない）。編集上の訂正だけの PR では移さない。この扱いは、issue #596 の「既存の `Comments` は改訂しない」を文の内容を変えないことと読み、置き場所だけを新しい規則にそろえるものである。また、編集上の訂正だけの PR で `Comments` を変えない、という受け入れの目安も守れる。本タスクの PR そのものでは、既存の文書を変えない。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

以下は、レビュアーと個別には確認していない。上の決定と現行の規則から導いたもので、PR のレビューで異論があれば改める。

-   **連鎖して `draft` に戻る文書:** `/fixpr` は、申し送りの項目を変えると、本文を変えていない後の文書も `draft` に戻す（`.claude/commands/fixpr.md:226-235`）。そうした文書の `Comments` と変更履歴の行には、その文書自身の変更の要旨の代わりに、どの文書のどの決定の変更に伴って戻したかを書く（AC-14）。
-   **PR 本文に書けなかった訂正:** `/fixpr` が編集上の訂正を PR 本文に追記できなかった場合（メンションの確認に通らない、`fixprguard edit-pr` が止まる。`.claude/commands/fixpr.md:705-723`）は、最終報告にその訂正と理由を挙げる（AC-05）。レビュアーが読む場所に訂正の記録がないまま終わらせないためである。
-   **PR 本文の書き換えで訂正の説明を消さない:** `/fixpr` の Phase 6 が PR 本文を書き直すとき（`.claude/commands/fixpr.md:693-701`）も、既にある編集上の訂正の説明を残す（AC-04）。
-   **承認者の表し方:** `/runplan` のセッション中の再承認の行の承認者は、`/runpr` の承認と同じ形（GitHub のユーザー名）で書く（AC-15）。
-   **本タスクのマージの時点で進行中の文書:** 本タスクのマージの後に行う記録（承認を含む）は、新しい規則に従う。それより前に書かれた `Comments` は、旧規則の文として F-004 の扱いを受ける。
-   **決定の履歴の付録との関係:** `/mkarch` は設計書の過去の決定を「決定の履歴」の付録に置く（`.claude/commands/mkarch.md:74`）。変更履歴は状態の遷移の記録であり、決定の中身や理由を書く付録とは別のセクションとする。変更履歴は文書の最後に置く。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `Comments` を、今の状態についてレビュアーが今知るべき理由だけにする。
-   編集上の訂正の詳細を、その PR のレビュアーが読む PR 本文に置き、文書には残さない。
-   状態の遷移の履歴を、文書末尾の変更履歴に 1 件 1 行で残す。
-   規則（`requirements_process.md`）と、それに従って書き込むコマンドの定義を矛盾させない。

### 2.2. スコープ (In Scope)

-   `docs/dev/conventions/requirements_process.md` の「Editing an approved document」、状態表の `Comments` の説明、`withdrawn` の記録の規則。
-   上の規則に従って文書や PR 本文に書き込むコマンドの定義（本書でいう「対象のコマンドの定義」）：`.claude/commands/runplan.md`、`.claude/commands/fixpr.md`、`.claude/commands/mkarch.md`、`.claude/commands/mkplan2.md`、`.claude/commands/runpr.md`、`.claude/commands/_lib/task-pr-handoff.md`、`.claude/commands/_lib/settle-decisions.md`（`/runplan` が決定の記録先として `Comments` を渡している。`.claude/commands/runplan.md:64`）。
-   次の 2 つは規則を参照するだけで、`Comments` の書き方を定めていないので変えない：`.claude/commands/mkplan.md:82`（規則への参照）、`.claude/commands/_context.md:48`（状態の値の一覧）。
-   `docs/tasks/0000_template/requirements.md` の確認。状態表の `Comments` は `-` で、新しい規則と合っている（同ファイル 11 行）。変更履歴は最初の 1 行を書くときに作るので、テンプレートには加えない。

### 2.3. スコープ外 (Out of Scope)

-   **既存のタスク文書の書き換え:** 本タスクの PR では、既存のタスク文書の `Comments` を移さず、変更履歴も加えない。新しい規則は、本タスクの後の編集から適用する（issue #596）。
-   **コマンドを実行した結果を確かめること:** 新しい規則に従った PR（編集上の訂正だけの PR、決定の変更の PR）が実際にどうなるかは、本タスクの後の PR で分かる。本タスクでは、規則とコマンドの定義の記述を確かめる。
-   **`Created`・`Review date`・`Reviewer` の意味の変更:** 現行どおりとする。

## 3. 機能要件 (Functional Requirements)

本書でいう「規則」は `docs/dev/conventions/requirements_process.md`、「対象のコマンドの定義」は 2.2 に挙げた `.claude/commands/` 以下の 7 ファイルを指す。「状態の遷移」は次の 4 種類を指す。

-   **承認:** `/runpr` で文書を `approved` にすること。初回の承認と、決定の変更で `draft` に戻した後の承認の両方を含む。
-   **`draft` への戻し:** 決定の変更で、承認済みの文書を `draft` に戻すこと。
-   **セッション中の再承認:** `/runplan` のセッション中に、レビュアーが決定の変更を承認し、文書の内容が変わっても `approved` のままであること。
-   **`withdrawn`:** タスクを取り下げ、文書を `withdrawn` にすること。

### 3.1. 機能一覧

#### F-001: 編集上の訂正を PR 本文に記録する

承認済みの文書に編集上の訂正を加えるとき、状態と `Comments` と変更履歴は変えず、訂正の説明をその PR の本文に書く。

**Acceptance Criteria**:
- **AC-01**: 規則の「Editing an approved document」が、編集上の訂正について次を定めている。状態を保つ。`Comments` と変更履歴は変えない。何を何に直したかと、決定の変更でないことを、その PR の本文とコミットメッセージに書く。訂正の説明は、レビューのスレッドや PR 本文の文を引用せず、自分の言葉で書く。
- **AC-02**: PR を作るコマンドの定義（`task-pr-handoff.md` Part B、`runpr.md` の単独の変更の PR）が、PR に編集上の訂正が含まれるとき、その説明（何を何に直したか、決定の変更でないこと）を PR 本文に書くことを定めている。
- **AC-03**: PR を作った後に編集上の訂正を加えるコマンドの定義（`fixpr.md`、PR が既にある場合の `runplan.md`）が、その訂正の説明を PR 本文に追記することを定めている。`fixpr.md` では、PR 本文が大きく古くなっていない場合でも追記する。
- **AC-04**: `fixpr.md` が、Phase 6 で PR 本文を書き直すときも、既にある編集上の訂正の説明を残すことを定めている。
- **AC-05**: `fixpr.md` が、編集上の訂正を PR 本文に追記できなかったとき（メンションの確認に通らない、PR 本文の書き換えが止まった）、最終報告にその訂正と追記できなかった理由を挙げることを定めている。
- **AC-06**: 対象のコマンドの定義のどれも、編集上の訂正を `Comments` または変更履歴に記録させていない。

#### F-002: Comments に今の状態の理由だけを書く

`Comments` には、今の状態についてレビュアーが今知るべき理由だけを書き、状態が変わるたびに書き換える。

**Acceptance Criteria**:
- **AC-07**: 規則の状態表の `Comments` の説明と本文が、`Comments` の内容を次のとおり定めている。`approved` と作ったばかりの `draft` では `-`。決定の変更で `draft` に戻した文書では、その旨と変更の要旨。`withdrawn` の文書では、日付と理由、または理由を記録した文書へのリンク。
- **AC-08**: 規則が、状態が変わるたびに `Comments` を書き換え、前の内容を残さない（過去の経緯は変更履歴に置く）ことを定めている。
- **AC-09**: 規則が、`Comments` に複数の事項を書くときは `<br>` で区切ることを定めている。

#### F-003: 状態の遷移を変更履歴に記録する

状態の遷移は、文書末尾の変更履歴のセクションに 1 件 1 行で追記する。

**Acceptance Criteria**:
- **AC-10**: 規則が、文書の最後のセクションとして変更履歴（見出しは `変更履歴`）を定め、そこに状態の遷移だけを、1 件 1 行で古い順に追記することを定めている。各行には、日付、遷移の種類、PR 番号を書く。承認とセッション中の再承認の行には承認者を、`draft` への戻しとセッション中の再承認の行には変更の要旨を、`withdrawn` の行には理由または理由を記録した文書へのリンクを書く。例外は F-004 の移した項目だけである。
- **AC-11**: 規則が、変更履歴のセクションを文書の作成時には設けず、最初の 1 行を書くときに文書の最後に作ることを定めている。
- **AC-12**: 規則が、main に入った変更履歴の行（F-004 の移した項目を除く）は、どれもその行を加えた PR の番号を持つことを定めている。PR を作る前に書いた行も含む。対象のコマンドの定義のうち、PR を作る前に変更履歴の行を書くもの（`runplan.md`・`mkplan2.md`・`mkarch.md`）と、手作業の変更から PR を作る `runpr.md` が、この要件を満たす手順を持つ。
- **AC-13**: `runpr.md` の承認の記録が、状態を `approved`、`Review date` を当日、`Reviewer` を承認者にするほか、`Comments` を `-` にし、変更履歴に承認の行（日付、承認者、PR 番号）を追記することを定めている。初回の承認と、`draft` に戻した後の承認の両方に当てはまる。
- **AC-14**: 決定の変更で文書を `draft` に戻すコマンドの定義（`fixpr.md`、`mkarch.md`、`mkplan2.md`）と規則が、次を定めている。決定の中身を本文に反映する。`Comments` をその旨と変更の要旨にする。変更履歴に `draft` への戻しの行（日付、変更の要旨、PR 番号）を追記する。承認者は、後の承認の行（AC-13）に記録される。本文を変えずに、前の文書の決定の変更に伴って `draft` に戻す文書では、変更の要旨の代わりに、どの文書の決定の変更に伴って戻したかを書く。
- **AC-15**: `runplan.md` と規則が、`/runplan` のセッション中の決定の変更について次を定めている。決定の中身を本文に反映する。決定と理由を、変えた文書の本文の「実装の際に決めたこと（YYYY-MM-DD）」の節に書く（`settle-decisions.md` に渡す記録先もこの節とする）。状態は `approved` のままにし、`Comments` は `-` にする。変更履歴にセッション中の再承認の行（日付、変更の要旨、承認者、PR 番号）を追記する。承認者は AC-13 と同じ形（GitHub のユーザー名）で書く。PR 本文に決定の変更を挙げる。
- **AC-16**: 規則が、タスクを取り下げるとき、各文書の `Comments` に日付と理由（または理由を記録した文書へのリンク）を書き、変更履歴に `withdrawn` の行を追記することを定めている。

#### F-004: 既存の文書を移す

旧規則で書かれた文書は、新しい規則で最初の状態の遷移を書くときに、旧 `Comments` を変更履歴へ移す。

**Acceptance Criteria**:
- **AC-17**: 規則が、旧規則で書かれた文書を「変更履歴のセクションがなく、`Comments` が `-` でない文書」と定めている。
- **AC-18**: 規則が次を定めている。旧規則で書かれた文書に、新しい規則で最初の状態の遷移を書くときは、旧 `Comments` の文を、内容を変えずに、旧規則の `Comments` であると示す印を付けた 1 項目として変更履歴の先頭に移す。そのうえで、`Comments` を今の状態の理由（AC-07）に置き換え、遷移の行を追記する。編集上の訂正だけを加えるときは移さず、`Comments` を変えない。
- **AC-19**: 本タスクの PR は、`docs/tasks/` 以下の既存のタスク文書（`docs/tasks/0053_status_comments_policy/` 以外）を変えない。

#### F-005: 規則とコマンドの定義を矛盾させない

**Acceptance Criteria**:
- **AC-20**: 規則と対象のコマンドの定義のあいだで、`Comments`、変更履歴、PR 本文に何を書くかの記述が矛盾しない。対象のコマンドの定義は、`Comments` と変更履歴の内容を、規則の該当する節を参照して述べ、規則と異なる書き方を定めない。

## 6. 用語集 (Glossary)

-   **編集上の訂正（editorial correction）:** 承認済みの文書が言っている内容は変えず、古くなった名前、相互参照、表のセル、行番号などを直す編集（規則「Editing an approved document」）。
-   **決定の変更（decision change）:** 何を作るか、なぜ作るかについて、文書の言っている内容が変わる編集（同上）。
-   **状態の遷移:** 承認、`draft` への戻し、セッション中の再承認、`withdrawn` の 4 種類（3 章）。
-   **変更履歴:** 文書の最後に置く、状態の遷移を 1 件 1 行で記録するセクション（F-003）。設計書の「決定の履歴」の付録とは別のもの。
-   **旧規則で書かれた文書:** 変更履歴のセクションがなく、`Comments` が `-` でない文書（AC-17）。
-   `docs/translation_glossary.md` は README の翻訳のための用語集で、上の用語は README に現れないため載っていない。本書では上の定義で統一する。
