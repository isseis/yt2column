## 1. 概要 (Overview)

**目的:** 本書は、タスク文書（`01_requirements.md`・`02_architecture.md`・`03_implementation_plan.md`）の状態表の `Comments` に何を書くか、編集上の訂正と状態の遷移をどこに記録するかを定める要件を定義する（[#596](https://github.com/isseis/yt2column/issues/596)）。

**背景:**

タスク文書の状態表の `Comments` が肥大化している。issue #596 の調べでは、150 文書のうち 77 文書で 500 バイトを、19 文書で 2,000 バイトを超え、最大は約 8.9KB（`docs/tasks/0030_fixpr_untrusted_threads/02_architecture.md`）である。どれも表の 1 つのセルに一段落で書かれているため、読みにくい。たとえば `docs/tasks/0049_codex_local_review/03_implementation_plan.md` の `Comments` には、PR-1 と PR-2 の実装で入れた編集上の訂正の詳細が続けて書かれている。

主な原因は、`docs/dev/conventions/requirements_process.md`「Editing an approved document」の規則である（同書 16〜38 行）。承認後の編集上の訂正は `Comments` に記録し、そこに決定の変更でないことを明記する（同書 28〜32 行）。`/runplan`・`/fixpr`・`/mkarch` はこの規則に従って `Comments` に書き込む（`.claude/commands/runplan.md:63`、`.claude/commands/fixpr.md:456-461`、`.claude/commands/mkarch.md:72`）。そのため PR のたびに訂正の詳細が追記され、レビューが終わった後も残り続ける。

この規則の目的は、LLM が自分の編集を編集上の訂正と判断したときに、レビューアーが反論できるようにすることである（同書 36〜38 行）。この目的は、その PR のレビューアーが一度読めば果たせる。何をどう直したかは PR とコミットに残るので、文書に恒久的に残す必要はない。

一方、状態の遷移の記録も `Comments` に積み重なる。決定の変更で `draft` に戻すときは、過去の承認を `Comments` に履歴として残す（同書 21〜24 行）。`/runplan` のセッション中の承認は、決定・日付・承認したことを `Comments` に書く（同書 24〜27 行、`.claude/commands/runplan.md:64`）。`/mkplan2` は PR 境界を加えた日を `Comments` に書く（`.claude/commands/mkplan2.md:107`）。そのため、`Comments` には今の状態の理由と過去の経緯が混ざり、レビューアーが今読むべきことが埋もれる。

対応 issue: [#596](https://github.com/isseis/yt2column/issues/596)

**本書の記述範囲:** 本書は、規則とコマンドの定義が文書と PR に何を書かせるか（`Comments` の内容、変更履歴の内容と作る時期、PR 本文に書く編集上の訂正、既存の文書の扱い）を定める。コマンドの定義のどの手順をどう書き換えるか、PR 番号を後から書き足す手順、`/fixpr` が PR 本文を書き換える手段、変更履歴の 1 行の正確な書式、確かめの方法は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #596 で決めたこと:**

-   **編集上の訂正の詳細は PR 本文に書く:** 何を何に直したか、決定の変更でないことは、その PR のレビューアーが読む PR 本文（とコミットメッセージ）に書き、文書には書かない。レビューアーが一度読めば反論の機会は果たせ、何を直したかは PR とコミットに残るためである。
-   **決定の変更の中身は本文に反映する:** 後から読む人全員が必要とするためである。
-   **状態の遷移は 1 件 1 行で残す:** 承認、決定の変更による再承認、`withdrawn` とその理由は、後から読む人全員が必要とするので、日付・種類・PR 番号（または理由へのリンク）を 1 件 1 行で残す。置き場所は「要件定義の際に決めたこと」で変更履歴とした。
-   **`withdrawn` の日付と理由は文書に残す:** 現行どおり、日付と理由、または理由を記録した文書へのリンクを残す。
-   **既存のタスク文書の `Comments` は、本タスクでは改訂しない:** 新しい規則は、これ以降の編集から適用する。

**要件定義の際に決めたこと（2026-11-01）:**

-   **`Comments` は今の状態の理由だけにする:** `Comments` には、今の状態についてレビューアーが今知るべき理由だけを書き、状態が変わるたびに書き換える（追記しない）。`approved` と作ったばかりの `draft` では `-`、決定の変更で `draft` に戻した文書ではその旨と変更の要旨、`withdrawn` の文書では日付と理由（または理由を記録した文書へのリンク）を書く。issue の表は状態の遷移を `Comments` に 1 件 1 行で残すとしていたが、それでは遷移のたびに `Comments` が伸び、今の状態の理由が過去の行に埋もれるためである。
-   **状態の遷移は文書末尾の変更履歴に書く:** 状態の遷移の履歴は、文書の末尾に変更履歴のセクションを設けて、そこに 1 件 1 行で追記する。後から読む人全員のための記録を、表のセルではなく、行を増やしても読みやすい場所に置くためである。
-   **変更履歴に書くのは状態の遷移だけ:** 承認、決定の変更による `draft` への戻し、`/runplan` のセッション中の再承認、`withdrawn` を書く。編集上の訂正は書かない。訂正の記録は PR 本文で足り（issue #596 で決めたこと）、変更履歴に入れると `Comments` と同じ肥大化が変更履歴で起きるためである。
-   **承認も毎回変更履歴に書く:** 初回の承認も再承認も、変更履歴に 1 行ずつ書く。`draft` に戻すと `Review date` と `Reviewer` が `-` になるので、承認の記録が変更履歴になければ過去の承認が消えるためである。
-   **変更履歴のセクションは最初の 1 行を書くときに作る:** 文書を作るときには入れない。多くの場合、初回の承認を記録する `/runpr` が作る。テンプレートのない `02_architecture.md` と `03_implementation_plan.md` でも同じ扱いにでき、要件定義書のテンプレートを変えずに済むためである。
-   **`/fixpr` が入れた編集上の訂正は、PR 本文に追記する:** スレッドへの返信やコミットメッセージだけに任せず、PR 本文に書く。issue #596 の受け入れの目安（訂正の説明が PR 本文にある）を、PR を作った後の訂正でも満たすためである。
-   **PR を作る前に書いた変更履歴の行には、PR を作った直後に PR 番号を書き足す:** `/runplan` のセッション中の決定の変更は、PR を作る前に記録される（`.claude/commands/runplan.md:64`。PR はチェックポイントで作る）。その行にも PR 番号を残すため、PR を作った直後に書き足す。同じ事情は、PR を作る前に状態を変える `/mkplan2`（`.claude/commands/mkplan2.md:107`）と、承認済みの文書を改訂する `/mkarch`（`.claude/commands/mkarch.md:72`）にもあるので、同じ扱いにする。
-   **`Comments` に複数の事項を書くときは `<br>` で区切る:** 表を崩さずに、1 件ずつ改行して表示するためである。
-   **既存の文書は、新しい規則で初めて書き換えるときに移す:** 旧規則の `Comments` の文（`-` 以外）は、内容を変えずに変更履歴の先頭へ移し、そのうえで `Comments` を今の状態の理由に置き換える。issue #596 の「既存の `Comments` は改訂しない」を、文の内容を変えないことと読み、置き場所は新しい規則に揃える。本タスクの PR そのものでは、既存の文書を変えない。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `Comments` を、今の状態についてレビューアーが今知るべき理由だけにする。
-   編集上の訂正の詳細を、その PR のレビューアーが読む PR 本文に置き、文書には残さない。
-   状態の遷移の履歴を、文書末尾の変更履歴に 1 件 1 行で残す。
-   規則（`requirements_process.md`）と、それに従って書き込むコマンドの定義を矛盾させない。

### 2.2. スコープ (In Scope)

-   `docs/dev/conventions/requirements_process.md` の「Editing an approved document」、状態表の `Comments` の説明、`withdrawn` の記録の規則。
-   上の規則に従って文書や PR 本文に書き込むコマンドの定義：`.claude/commands/runplan.md`、`.claude/commands/fixpr.md`、`.claude/commands/mkarch.md`、`.claude/commands/mkplan2.md`、`.claude/commands/runpr.md`、`.claude/commands/_lib/task-pr-handoff.md`。設計で、ほかにも書き込む箇所が見つかれば含める。
-   `docs/tasks/0000_template/requirements.md` の確認。状態表の `Comments` は `-` で、新しい規則と合っている（同ファイル 11 行）。変更履歴は最初の 1 行を書くときに作るので（1 章「要件定義の際に決めたこと」）、テンプレートには加えない。

### 2.3. スコープ外 (Out of Scope)

-   **既存のタスク文書の書き換え:** 本タスクの PR では、既存のタスク文書の `Comments` を移さず、変更履歴も加えない。新しい規則は、本タスクの後の編集から適用する（issue #596）。
-   **コマンドの実行の結果の確かめ:** 新しい規則に従った PR（編集上の訂正だけの PR、決定の変更の PR）が実際にどうなるかは、本タスクの後の PR で現れる。本タスクでは、規則とコマンドの定義の記述を確かめる。
-   **`Created`・`Review date`・`Reviewer` の意味の変更:** 現行どおりとする。

## 3. 機能要件 (Functional Requirements)

本書でいう「規則」は `docs/dev/conventions/requirements_process.md`、「コマンドの定義」は 2.2 に挙げた `.claude/commands/` 以下のファイルを指す。「状態の遷移」は、承認、決定の変更による `draft` への戻し、`/runplan` のセッション中の再承認、`withdrawn` の 4 種類を指す。

### 3.1. 機能一覧

#### F-001: 編集上の訂正を PR 本文に記録する

承認済みの文書に編集上の訂正を加えるとき、状態と `Comments` と変更履歴は変えず、訂正の説明をその PR の本文に書く。

**Acceptance Criteria**:
- **AC-01**: 規則の「Editing an approved document」が、編集上の訂正について次を定めている。状態を保つ。`Comments` と変更履歴は変えない。何を何に直したかと、決定の変更でないことを、その PR の本文とコミットメッセージに書く。
- **AC-02**: PR を作るコマンドの定義（`task-pr-handoff.md` Part B、`runpr.md` の単独の変更の PR）が、PR に編集上の訂正が含まれるとき、その説明（何を何に直したか、決定の変更でないこと）を PR 本文に書くことを定めている。
- **AC-03**: PR を作った後に編集上の訂正を加えるコマンドの定義（`fixpr.md`、PR が既にある場合の `runplan.md`）が、その訂正の説明を PR 本文に追記することを定めている。`fixpr.md` では、PR 本文が大きく古くなっていない場合でも追記する。
- **AC-04**: どのコマンドの定義も、編集上の訂正を `Comments` または変更履歴に記録させていない。

#### F-002: Comments に今の状態の理由だけを書く

`Comments` には、今の状態についてレビューアーが今知るべき理由だけを書き、状態が変わるたびに書き換える。

**Acceptance Criteria**:
- **AC-05**: 規則の状態表の `Comments` の説明と本文が、`Comments` の内容を次のとおり定めている。`approved` と作ったばかりの `draft` では `-`。決定の変更で `draft` に戻した文書では、その旨と変更の要旨。`withdrawn` の文書では、日付と理由、または理由を記録した文書へのリンク。
- **AC-06**: 規則が、状態が変わるたびに `Comments` を書き換え、前の内容を残さない（過去の経緯は変更履歴に置く）ことを定めている。
- **AC-07**: 規則が、`Comments` に複数の事項を書くときは `<br>` で区切ることを定めている。

#### F-003: 状態の遷移を変更履歴に記録する

状態の遷移は、文書末尾の変更履歴のセクションに 1 件 1 行で追記する。

**Acceptance Criteria**:
- **AC-08**: 規則が、文書末尾の変更履歴のセクション（見出しは `変更履歴`）を定め、そこに状態の遷移だけを、1 件 1 行で古い順に追記することを定めている。各行には、日付、遷移の種類、PR 番号を書く。承認と再承認の行には承認者を、決定の変更の行には変更の要旨を、`withdrawn` の行には理由または理由を記録した文書へのリンクを書く。
- **AC-09**: 規則が、変更履歴のセクションを文書の作成時には設けず、最初の 1 行を書くときに文書末尾に作ることを定めている。
- **AC-10**: `runpr.md` の承認の記録が、状態を `approved`、`Review date` を当日、`Reviewer` を承認者にするほか、`Comments` を `-` にし、変更履歴に承認の行（日付、承認者、PR 番号）を追記することを定めている。初回の承認と、決定の変更の後の再承認の両方に当てはまる。
- **AC-11**: 決定の変更で文書を `draft` に戻すコマンドの定義（`fixpr.md`、`mkarch.md`、`mkplan2.md`）と規則が、次を定めている。決定の中身を本文に反映する。`Comments` をその旨と変更の要旨にする。変更履歴に `draft` への戻しの行（日付、変更の要旨、PR 番号）を追記する。承認者は、後の承認の行（AC-10）に記録される。
- **AC-12**: `runplan.md` と規則が、`/runplan` のセッション中の決定の変更について次を定めている。決定の中身を本文に反映する。状態は `approved` のままにし、`Comments` は `-` にする。変更履歴に再承認の行（日付、変更の要旨、承認者、PR 番号）を追記する。
- **AC-13**: 規則とコマンドの定義が、PR を作る前に書いた変更履歴の行（`/runplan`・`/mkplan2`・`/mkarch` の場合）には、PR を作った直後に PR 番号を書き足すことを定めている。
- **AC-14**: 規則が、タスクを取り下げるとき、各文書の `Comments` に日付と理由（または理由を記録した文書へのリンク）を書き、変更履歴に `withdrawn` の行を追記することを定めている。

#### F-004: 既存の文書を移す

旧規則で書かれた文書は、新しい規則で初めて書き換えるときに、旧 `Comments` を変更履歴へ移す。

**Acceptance Criteria**:
- **AC-15**: 規則が次を定めている。`Comments` が `-` でない文書を、新しい規則に従って初めて書き換えるときは、旧 `Comments` の文を内容を変えずに変更履歴の先頭へ移す。そのうえで、`Comments` を今の状態の理由（AC-05）に置き換える。
- **AC-16**: 本タスクの PR は、`docs/tasks/` 以下の既存のタスク文書（`docs/tasks/0053_status_comments_policy/` 以外）を変えない。

#### F-005: 規則とコマンドの定義を矛盾させない

**Acceptance Criteria**:
- **AC-17**: 規則と、2.2 に挙げたコマンドの定義のあいだで、`Comments`、変更履歴、PR 本文に何を書くかの記述が矛盾しない。コマンドの定義は、規則と異なる書き方を独自に定めない。

## 6. 用語集 (Glossary)

-   **編集上の訂正（editorial correction）:** 承認済みの文書が言っている内容は変えず、古くなった名前、相互参照、表のセル、行番号などを直す編集（規則「Editing an approved document」）。
-   **決定の変更（decision change）:** 何を作るか、なぜ作るかについて、文書の言っている内容が変わる編集（同上）。
-   **状態の遷移:** 承認、決定の変更による `draft` への戻し、`/runplan` のセッション中の再承認、`withdrawn` の 4 種類（3 章）。
-   **変更履歴:** 文書末尾に置く、状態の遷移を 1 件 1 行で記録するセクション（F-003）。
-   用語は `docs/translation_glossary.md` と統一する。
