# 設計への申し送り：OpenAI API のアダプタ

本書は [01_requirements.md](01_requirements.md) の要件を満たすために設計で確認する事項を記す。実装の手段を本書で確定しない。`02_architecture.md` は各 H-NN をどう扱うか、または該当しない理由を記録する。

## H-01: Responses の出力と終了状態

SDK の `output_text` は便宜的なプロパティであり、HTTP の応答では `output` の各要素を読む必要がある。最初の要素が文面とは限らない。推論、拒否、未知の種類、複数のテキストの並び、終了状態の優先順位を要件の境界に対応させる。新しいモデルが途中経過のメッセージを返す場合、その扱いが「生成テキスト」の契約に合うかを実応答と公式仕様で確認し、要件の変更が必要なら先にレビュアーへ戻す。

## H-02: 使用量の変換と不明の理由

`input_tokens` は合計なので、キャッシュから読んだ分と書き込んだ分を引く。和の桁あふれと差の桁あふれを避け、整合しない内訳を「不明」にする理由を共有の `Usage` でどう表すか設計する。使用量の検証は本文の受理と分けるが、本文全体の UTF-8 や JSON の形の検査は先に行う。`cache_write_tokens` のない旧モデルの応答を0で補わず、要件どおり不明として扱う。

## H-03: 公表単価と実際の要求の一致

Astra と Sol は、通常・Fast・Flex などの処理方式と、キャッシュの保持期間で単価が異なる。既存の `pricing` は呼び出しの処理方式を持たないので、通常の単価と対応する要求にする方法を確認する。要求の既定をアカウントの設定に任せて別の処理方式になる場合や、応答が別の処理方式を報告する場合に、誤った料金を既知としないようにする。

候補モデルは入力が272,000トークンを超えると入力・キャッシュの単価が2倍、出力が1.5倍になる。入力の区分の合計を閾値と比較する既存の料金方式で表せるかを確認する。30分と12時間のキャッシュの書き込みの内訳を消費する必要がある場合は、要件の使用量の境界と整合させる。

## H-04: 出力上限を決める実測

要件 AC-10 の測定は、要件の承認後、設計段階で別途許可を得て行う。アダプタの実装前に測るための最小の要求と、既存の素材・プロンプト・中間生成物を使う手順を用意する。承認前に製品コードを書かない。呼び出しごとのトークン数と実時間を記録し、打ち切られた出力を真の最大出力と扱わない。数値を決めたら根拠、更新する定数、測り直す条件を設計とガイドに記す。

## H-05: 設定と秘密の経路

OpenAI の設定値を既存の工程ごとの選択に加え、サーバの許可するキー、雛形、設定名を列挙する文書と静的な確認をそろえる。CLI とサーバの `redact.SecretStrings` の呼び出しにも OpenAI のキーを渡す。外部コマンドの環境の許可リストは変更しない。必要なら OpenAI の effort の型をアダプタの外に置く既存の方針を適用する。

## H-06: 実 API の確認とサンプル

成功と打ち切りの実応答は、明示的な実行の指定とテスト専用の API キーで取得する。本番の `OPENAI_API_KEY` にフォールバックしない。実行の前に、HTTP/2 のデバッグで認証が漏れる設定を検出する。テスト用の設定を読む場所、オプトイン、取得手順、加工の内容を、既存の統合テストと実データの方針に合わせて設計する。
