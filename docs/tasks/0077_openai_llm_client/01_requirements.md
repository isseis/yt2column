## 1. 概要 (Overview)

対応 issue: [#568](https://github.com/isseis/yt2column/issues/568)

親 issue は [#567](https://github.com/isseis/yt2column/issues/567)、前提は完了済みの [#566](https://github.com/isseis/yt2column/issues/566)（[0051 要件定義書](../0051_llm_effort/01_requirements.md)）である。組み合わせの評価と本番の構成の見直しは、後続の [#569](https://github.com/isseis/yt2column/issues/569) が扱う。

**目的:** 生成（字数の調整を含む）と検証・推敲で、OpenAI のモデルを選べるようにする。本番の構成の既定は変えない。

**背景:** 現在の選択肢は Claude と DeepSeek で、工程ごとに `<プロバイダ>/<モデル ID>[+<effort>]` を指定する（`internal/config/config.go:546`、[ADR-0003](../../dev/adr/0003-llm-config-contract.md)）。本番の構成は Claude の `claude-opus-5-5`、effort `high` である（[production_profile.md](../../dev/production_profile.md)）。#567 は、別系統のモデルを組み合わせることで記事の品質を上げられるかを調べる。その前段として、OpenAI を既存の `LLMClient` の契約に載せる。

**本書の記述範囲:** API の選択、設定、応答を受理する条件、失敗の通知、使用量と料金、データの保持、出力上限の決め方を定める。パッケージ内部の型、HTTP・JSON の組み立て方、検証の手段、検証項目の配置、実測による上限の数値は `02_architecture.md` で決める。設計上の注意は [design_handoff.md](design_handoff.md) に記す。

### issue #568 で決めたこと

- **OpenAI を両方の工程で選べるようにする。** 生成と字数の調整は同じ選択を使い、検証・推敲は独立に指定できるようにする。後続の評価で組み合わせを比べるためである。既定の変更と評価は対象外とする。
- **専用のアダプタを標準ライブラリで書く。** `internal/llm/openai` を追加し、SDK は使わず、`net/http`・`encoding/json` と `internal/llm/llmhttp` を使う。DeepSeek 固有の要求・応答の処理とは共通化しない。提供元ごとの詳細を閉じ込め、共有の送信経路を使う既存方針に従う（[ADR-0001](../../dev/adr/0001-llm-adapter-stdlib.md)）。
- **認証には `OPENAI_API_KEY` を使う。** ChatGPT の契約とは別に OpenAI API の課金が必要である。CLI の環境変数とサーバの設定ファイルに同じキー名を加える。読む場所を分ける既存方針を保ち、受理するキーの追加を [ADR-0018](../../dev/adr/0018-server-config-file.md) に記録する。設定の契約を変えるため、同 ADR の更新が必要である。
- **評価候補の単価と実応答のサンプルを加える。** 使用量から料金を見積もれ、実際の応答の形を確認できるようにする。README の日英版、プロジェクト概要、セキュリティの文書も対応させる。

### 要件定義の際に決めたこと（2026-11-10）

レビュアーは次の5点をそれぞれ選択肢 A として確定した。

1. **Responses API を使う。** issue の第一候補であり、既存 API との互換性を維持する必要がない新規アダプタだからである。1 回の要求を非ストリーミングで送り、ツールと会話の継続は対象外とする。外部 API の契約を決めるため、[ADR-0041](../../dev/adr/0041-openai-api.md) を新設する。
2. **effort は全7値を受理し、既定は `medium` とする。** API 全体の `none`・`minimal`・`low`・`medium`・`high`・`xhigh`・`max` を完全一致で受理する。モデルの一覧を制限することなく、省略時の振る舞いを固定するためである。モデルが対応しない組み合わせは API のエラーとして示す。設定の契約を変えるため、[ADR-0003](../../dev/adr/0003-llm-config-contract.md) を更新する。
3. **`store: false` を固定する。** 会話を継続せず、保存した応答を取得する必要がないためである。保存を有効にする設定は設けない。監視ログとプロンプトキャッシュの保持は別にあることを文書に記す。データの扱いを定めるため、ADR-0041 に記録する。
4. **料金表に `gpt-6-astra` と `gpt-6.1-sol` を追加する。** 品質重視の候補と料金を抑えた候補を後続の評価に残すためである。指定できるモデルをこの2つに限るものではない。候補モデルの選定は本タスク内に閉じるため、新しい ADR は不要である。料金の算出は [ADR-0022](../../dev/adr/0022-cost-estimate.md) の既存方針を使う。
5. **既定の出力上限は設計段階で実測して決める。** 両モデルを既定の `medium` で使い、3工程を、[claude_output_limit.md](../../dev/guides/claude_output_limit.md) と同じ方法で測る。出力の長さと所要時間の両方に根拠を持たせるためである。課金される実測は別途許可を得る。条件を両立できなければ方針を再相談する。後続の設計と運用を拘束するため、ADR-0041 に記録する。

### 仕様の根拠

2026-11-10 に OpenAI の公式文書を確認した。

- [Responses API リファレンス](https://developers.openai.com/api/reference/resources/responses/methods/create): 応答の `status`・`incomplete_details`・`model`・`output`・`usage`、および `max_output_tokens` を参照する。モデルの版を示す `system_fingerprint` に相当するメンバーは文書化されていない。
- [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning): effort の対応範囲はモデルごとに異なる。出力上限には推論も含まれ、文面が出る前に上限に達することがある。
- [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)・[GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol): 候補のモデルの対応 effort、出力上限、長い入力に対する料金を参照する。
- [Pricing](https://developers.openai.com/api/docs/pricing)・[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching): 通常の入力、キャッシュの読み取り、キャッシュの書き込み、出力で単価が異なる。処理方式とキャッシュの保持期間によっても料金が変わる。
- [Data controls](https://developers.openai.com/api/docs/guides/your-data): 応答の保存を止めても、監視ログやキャッシュの保持は別に適用される。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

- CLI と localhost サーバのどちらでも、工程ごとに OpenAI を選んで記事を生成できるようにする。
- 不完全な応答を記事として返さず、使用量と料金を既存の出力に載せる。
- 送り先とデータの保持、課金の前提、設定の方法を利用者が確認できるようにする。

### 2.2. スコープ (In Scope)

- OpenAI アダプタ、設定とプロバイダの選択、API キーの伏せ字、候補モデルの単価。
- 成功・打ち切りの実応答のサンプルと、その取得・加工の記録。
- `README.md`・`README.en.md`、`docs/dev/project_overview.md`、`docs/dev/security.md` と、追加した構成を説明するパッケージの参照表。
- 出力上限の実測による根拠と、測り直し方の文書化。

### 2.3. スコープ外 (Out of Scope)

- モデルの組み合わせの品質評価、プロンプトの調整、本番の構成の変更。#569 で扱う。
- ストリーミング、ツールの実行、会話の継続、バッチ処理、画像・音声の入出力。記事を1回のテキスト生成で処理する範囲に限る。
- モデルごとの対応表による設定時の拒否、利用可能なモデルの API 照会。モデル ID を不透明な文字列として扱う既存方針を保つ。
- 出力上限の環境変数の追加や、上限を LLM の選択値に含める文法の追加。#566 の範囲外でもあり、既存の `MaxOutputTokens` の契約を使う。
- Gemini、Codex のレビュー処理、ブラウザ拡張の UI の変更。本機能には不要である。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: OpenAI の選択と認証

既存の選択と継承の規則（[0051 要件定義書](../0051_llm_effort/01_requirements.md)、[0066 要件定義書](../0066_server_config_file/01_requirements.md)）に `openai` を加える。

**Acceptance Criteria**:

- **AC-01**: `YT2COLUMN_LLM` と `YT2COLUMN_REVIEW_LLM` のプロバイダに、小文字の `openai` を完全一致で指定できる。モデル ID は空でなければ、料金表にないものも選択でき、最初の `/` より後ろ、`+` より前の文字列を変換せずに送る。`/` を含むモデル ID も要求本文の値として扱い、URL を変えない。
- **AC-02**: OpenAI の effort の部分は `none`・`minimal`・`low`・`medium`・`high`・`xhigh`・`max` だけを受理し、省略時は `medium` を明示して送る。空、大文字の違い、前後の空白、未知の値、2つ以上の `+` は `config.ErrInvalid` とし、設定名と固定の拒否理由を示す。不正な effort を補正せず、モデル ID の一部ともみなさず、通信しない。
- **AC-03**: 検証・推敲の選択が未設定なら、生成のプロバイダ・モデル・effort を継承する。検証・推敲に OpenAI を明示して effort だけ省略した場合は、その工程に `medium` を使う。Claude・DeepSeek を明示した場合の既定は変えない。字数の調整には生成の選択を使う。OpenAI と Claude または DeepSeek をどちらの向きでも組み合わせられる。
- **AC-04**: CLI は `OPENAI_API_KEY` を環境変数から読み、サーバは同名のキーを設定ファイルからだけ読む。OpenAI が必要な工程で選ばれた場合、未設定と空の値は `config.ErrMissing` とし、`OPENAI_API_KEY` と固定の理由を示す。CLI の設定エラーとサーバの起動時の設定エラーは終了コード `2` となり、API を呼ばない。
- **AC-05**: OpenAI を選んでいなければ、その API キーの未設定・空・不正な値で拒否しない。再開では、実行する工程と、その選択を継承するために必要な設定だけを読む。サーバは環境の `OPENAI_API_KEY` を読まず、設定ファイルの欠けを環境の値で補わない。
- **AC-06**: サーバの設定ファイルで `OPENAI_API_KEY` を既存の6キーに加えて受理し、`config init` のコメントだけの雛形にも記す。64 KiB の上限、UTF-8、行の書式、重複、所有者とモード `0600` の検査を保つ。書式違反は `config.ErrConfigFileFormat` でファイル全体を拒否する。ほかのキーは拡張可能とせず、未知のキーを拒否する。

#### F-002: 生成要求と出力上限

**Acceptance Criteria**:

- **AC-07**: `LLMClient.Generate` に与えたシステムプロンプトとユーザープロンプトを、それぞれの役割を保って Responses API に送る。送り先は `https://api.openai.com/v1/responses` に固定し、認証に API キーを使う。プロンプトの内容を解釈して送り先・役割・要求の設定を変えない。ツールや過去の応答に依存せず、1回の呼び出しで非ストリーミングの応答を受け取る。
- **AC-08**: 空のプロンプト、不正な UTF-8 のプロンプト、負の `MaxOutputTokens` は `llm.ErrInvalidRequest` とし、送信しない。クライアントの構築時には、空・不正な UTF-8・前後に空白のあるモデル ID、空または印字可能な ASCII（`0x21`〜`0x7E`）以外を含む API キー、不正な effort、正でないタイムアウトを、補正せずに拒否する。拒否理由に API キーとプロンプトを含めない。
- **AC-09**: 正の `MaxOutputTokens` はその値を出力上限として送り、0 の場合だけ OpenAI アダプタの既定値を使う。既定値は生成・字数の調整・検証・推敲で共有する。上限は推論と文面の合計に適用する。
- **AC-10**: 既定値は設計段階で、Astra と Sol の `medium` による3工程の実測を根拠に決める。40分前後を含む既存の評価用動画を使い、(a) 観測した最大出力の2倍以上、(b) 最も遅い観測速度でもその値の出力に要する時間が `LLMTimeout`（15分）の半分以下、(c) 両モデルが受理する範囲、の3条件を満たす。上限・測定対象・出力トークン数・実時間・打ち切りの有無・確認日を記録する。両立する値がなければ、数値を確定せずレビュアーに再相談する。実測の実行には別途許可を得る。

#### F-003: 応答の受理と終了の判定

HTTP 200 の本文は信頼できない入力として、次の境界で扱う。本文全体の上限は 8 MiB とし、配列の要素数と文字列の長さもこの上限内に限る。受理する JSON は、有効な UTF-8、対になったサロゲートのエスケープ、後続データのない1つのオブジェクトである。標準ライブラリが補正・破棄する入力を受理しない。

| 境界 | 消費するメンバーと受理する形 | 拡張可能な部分 |
|---|---|---|
| 応答の最上位 | `model`: 空でない文字列、`status`: 文字列、`output`: オブジェクトの配列。`incomplete_details` は `incomplete` の場合にオブジェクトで、`reason` が文字列。それ以外では欠けまたは `null`。`error` は欠け・`null`・オブジェクト。`usage` は F-004 | これら以外のメンバー。`error` の内部は表示せず無視する |
| `output` の要素 | `type`: 文字列。`reasoning` と `message` を受理する。`message` は `role: assistant`、`status`: 文字列、`content`: オブジェクトの配列。`phase` は欠け・`null`・`commentary`・`final_answer` だけを受理する | `reasoning` では `type` 以外のメンバー。`message` では列挙したメンバー以外 |
| `message.content` の要素 | `type`: 文字列。`output_text` は `text`: 文字列、`refusal` は `refusal`: 文字列 | 列挙したメンバー以外。注釈やトークン確率は使わない |
| `incomplete_details` | `reason`: 文字列 | `reason` 以外のメンバー |

消費するメンバーは、エスケープを解いた名前の完全一致で照合する。欠け・重複・型違いは拒否する。表で明示した欠けと `null` だけを例外とする。拡張可能としたメンバーは、重複・型違いも含めて無視できるが、本文全体の JSON の条件は免除しない。`type` の未知の値は、未知のメンバーとは異なり拒否する。使用量だけの不正は F-004 に従う。

**Acceptance Criteria**:

- **AC-11**: 本文の大きさ、JSON の条件、上表の形のどれかに違反した場合は `openai.ErrInvalidResponse` とし、応答のゼロ値を返す。不正な配列要素、未知の出力の種類、未知の文面の種類も同様とし、途中までのテキストを返さない。
- **AC-12**: `status: completed`、`error` が欠けまたは `null`、すべてのメッセージが `completed`、拒否がない場合に限り成功できる。最終回答を表す `phase: final_answer` のメッセージと、`phase` が欠けまたは `null` のメッセージから、`output_text.text` を出現順に区切りを足さずにつなぎ、生成テキストとする。途中経過を表す `phase: commentary` と推論の要素はテキストに含めない。応答の `model` をモデル名として返す。モデルの版は空文字列とし、要求したモデル ID や応答 ID から版を推測しない。
- **AC-13**: `status: incomplete` かつ `reason: max_output_tokens` は `llm.ErrTruncated` とする。テキストがない場合も打ち切りと判定する。メッセージは送った出力上限と effort を示し、文面がない場合は effort を下げるよう案内する。
- **AC-14**: `incomplete` のその他の理由、`failed`・`cancelled`・`in_progress`・`queued`・未知の終了状態、完了していないメッセージ、`refusal`、`error` オブジェクトは `llm.ErrUnexpectedFinishReason` とする。拒否の自由文を記事にもエラーにも含めない。正常に完了した形でも、生成テキストがない、空、空白だけなら `llm.ErrEmptyResponse` とする。形の検査を先に行い、その後は打ち切り、想定外の終了、空の応答の順に判定する。
- **AC-15**: 打ち切り・想定外の終了・空の応答では、拒否した応答のモデル名と使用量を返し、テキストとモデルの版は空にする。その他のエラーでは応答のゼロ値を返す。失敗した応答を記事として保存・表示・投稿しない。既存の契約（`internal/llm/llm.go:71`、[ADR-0021](../../dev/adr/0021-llm-client-contract.md)）を保つ。

#### F-004: 使用量と料金

`usage` も信頼できない入力である。消費するメンバーは `input_tokens`・`input_tokens_details`・`output_tokens` とし、入力の内訳では `cached_tokens`・`cache_write_tokens` を消費する。これらは必須で、数値は符号・小数部・指数部のない、`int64` の範囲の負でない整数とする。`-0`・`null` も拒否する。これら以外のメンバーは拡張可能とし、重複・型違いも含めて無視する。`total_tokens` と出力の推論内訳は料金の区分に足さない。本文全体の JSON の検査と上限は F-003 に従う。

**Acceptance Criteria**:

- **AC-16**: 有効な使用量では、キャッシュから読んだ入力を `cached_tokens`、キャッシュに書き込んだ入力を `cache_write_tokens`、通常の入力を `input_tokens` からその2つを引いた値、出力を `output_tokens` として返す。出力には推論分を含め、推論の内訳を重ねて加えない。
- **AC-17**: `usage` の欠け・重複・型違い、消費する内訳の欠け・重複・型違い・範囲外、またはキャッシュの読み取りと書き込みの合計が入力の合計を超える場合、その呼び出しの使用量全体を理由つきの「不明」とする。不明を0と扱わず、値を補正せず、有効な区分だけを部分的に使わない。理由は固定の規則とメンバー名だけで示す。使用量の不正だけでは生成を失敗させない（[0019 要件定義書](../0019_token_usage/01_requirements.md) F-002）。
- **AC-18**: 既存の工程ごとの使用量の行、記事のメタデータ、中間生成物、失敗時の使用量の出力に OpenAI のモデル名と4区分を載せる。再開しても、再利用した工程の記録を変えない。
- **AC-19**: 料金表の `gpt-6-astra` と `gpt-6.1-sol` に、公式の単価と確認日・出典を加える。通常の入力・キャッシュの読み取り・キャッシュの書き込み・出力の4区分、および長い入力の料金を、実際に使う処理方式とキャッシュの保持期間に合う単価で算出する。対応する単価を確定できない実行は料金を不明とする。料金表にない応答モデル名の料金も不明とし、モデル名の部分一致から推測しない。料金の不明で記事の生成や公開を止めない。

#### F-005: 通信の失敗と秘密の保護

**Acceptance Criteria**:

- **AC-20**: すべての要求で `store: false` を送る。API キーは認証のためにだけ送信し、プロンプトに含めない。リダイレクトに従わず、自動再送しない。1回の呼び出しは送信から本文の読み取りまで15分で制限され、呼び出し元の短い期限とキャンセルにも従う。
- **AC-21**: HTTP 200 以外は `openai.ErrHTTPStatus` と状態コードを返し、本文の自由文を読んで表示しない。401 では API キー、403 では権限、400・404 ではモデル・effort・上限・入力の設定、429 では利用上限・課金設定・時間を置いての再実行、5xx では提供元の障害について、固定の案内を示す。タイムアウトとキャンセルはそれぞれ `context.DeadlineExceeded`・`context.Canceled` と照合でき、その他の通信の失敗は `openai.ErrTransport` とする。
- **AC-22**: アプリケーションが出す CLI・サーバのエラーとログ、記事、メタデータ、一覧、実応答のサンプルに `OPENAI_API_KEY` とその断片を出さない。CLI とサーバの既存の伏せ字の対象にも加える。秘密の保持は `secret.Secret` の契約を使い、拒否の理由は秘密やプロンプト、応答の自由文を含めない。Go の HTTP/2 のデバッグ出力は既存の例外とし、本番の CLI・サーバでは拒否せず、通信前の警告を保つ（`security.md` §2）。利用者が明示したデバッグで認証のヘッダーが出る残余リスクは変えない。実 API の統合テストでは同設定を拒否して送信しない。

#### F-006: 実応答のサンプルと利用案内

**Acceptance Criteria**:

- **AC-23**: `testdata/` に Responses API の成功と出力上限による打ち切りの実応答を追加する。`testdata/README.md` に取得日、モデルと effort、要求の条件、出典、秘密や取得者を特定する情報を取り除いた加工内容、再取得の手順を記す。動画素材を使う場合は再配布可能なものだけを使う。実 API の呼び出しは別途許可を得て行う。
- **AC-24**: README の日英版とプロジェクト概要に、CLI の環境変数とサーバの設定ファイルそれぞれの OpenAI の指定例、effort の一覧と既定、非対応の組み合わせの失敗、API キー、API 課金の必要性を示す。出力上限の測定根拠と測り直し方も文書からたどれるようにする。本番の既定値は Claude のままにする。
- **AC-25**: `security.md` に OpenAI の送信先と送るデータ、`store: false` の適用範囲を記す。学習への利用は既定で行われないこと、監視ログは通常最大30日保持されうること、プロンプトキャッシュも別に保持されうることを、公式の出典と確認日とともに説明する。`store: false` をゼロデータ保持と説明しない。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

40分前後の動画を分割せず一括で処理する既存の想定を保つ（[project_overview.md](../../dev/project_overview.md)「前提・制約」）。出力上限の根拠は AC-10 に従う。すべての入力や effort について15分以内の成功を保証するものではなく、期限を超えれば AC-21 の失敗とする。

### 4.2. セキュリティ (Security)

[security.md](../../dev/security.md) の攻撃ベクトルを適用する。

- **外部コマンド・ローカルのキャッシュ（§1・§5）:** 本タスクはこれらの処理を変えない。API キーの追加後も、外部コマンドへ引き継ぐ環境変数の許可リストを広げない。
- **秘密（§2）:** AC-04〜06・AC-08・AC-22 に従う。本番の API キーをテストで使わない。実 API の確認を行う場合もテスト専用のキーと明示的な実行の指定を要し、HTTP/2 のデバッグログがキーを出す設定では送信しない。
- **ネットワーク（§3・§4）:** AC-07・AC-20・AC-21・AC-25 に従う。モデル ID を送り先の URL に埋め込まず、API キーの送信先を設定で変更できないようにする。
- **信頼できないテキスト（§6）:** AC-11〜17 に従う。推論と拒否の自由文を公開せず、生成テキストをコマンドやコードとして実行しない。出典のリンクは既存どおり検証済みの動画 ID から付ける。
- **実データ（§7）:** AC-23 に従う。秘密と取得者を特定する情報をコミットしない。
- **サーバと拡張（§8）:** 設定ファイルの安全性とサーバの伏せ字を維持する。ジョブ API と拡張の権限は変えない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

既存の HTTP 送信経路を使い、失敗時の部分的なテキストや再送による重複課金を生まない。上限に達した場合も料金は発生しうる。使用量や料金の欠けだけでは記事の生成を止めない。

### 4.4. 互換性 (Compatibility)

macOS と Linux の既存の実行経路を保つ。Claude・DeepSeek の設定と既定値、再開の規則、記事とジョブ API の書式は維持する。サーバの設定ファイルにはキーを1つ追加し、従来の有効なファイルを引き続き受理する。UI を追加しないため、UI のアクセシビリティ要件は N/A である。

### 4.5. 保守性 (Maintainability)

提供元に依存する要求・応答とエラーは OpenAI のアダプタに閉じ込める。共有の `LLMClient` の型に OpenAI 専用のフィールドを加えない。既存の HTTP 送信と厳格な JSON の部品を使い、設定とアダプタの effort の受理範囲を一致させる。具体的な構成は設計で定める。

## 5. 制約条件 (Constraints)

- [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」と `CLAUDE.md` に従う。従来の選択肢に OpenAI を加えるが、本番の構成は変えない。JSON の補正の禁止、秘密、API キーを読む場所についての例外は作らない。
- 文書は要件、設計、実装計画の順に承認を受ける。この PR では要件書と設計への申し送り、ADR だけを作り、アダプタは実装しない。
- ユニットテストは実 API を呼ばない。実測と実応答の取得をこの要件書の承認だけで実行せず、その都度実行の許可を得る。
- 要件を定めた時点では上限の数値、応答の実測値、候補モデルの品質とアカウントの利用権限は未確認である。設計で測定条件と結果を記録し、後続の #569 に品質の判断を渡す。

## 6. 用語集 (Glossary)

- **effort:** モデルが推論にかける程度。受理する値と既定はプロバイダごとに定める。
- **生成・字数の調整・検証・推敲:** 記事を書く3工程。検証と推敲で1つの工程である。
- **応答の保存:** Responses API の応答を後で取得するための保持。`store` が制御する。監視ログやプロンプトキャッシュとは区別する。
- **使用量:** 1回の LLM 呼び出しが報告したトークン数。通常の入力、キャッシュから読んだ入力、キャッシュに書き込んだ入力、推論を含む出力の4区分で扱う。
- **打ち切り:** 出力上限に達して生成が完了しなかった状態。文面が出る前に発生する場合も含む。
- その他の用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
