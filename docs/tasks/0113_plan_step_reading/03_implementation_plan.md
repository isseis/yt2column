## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

chief の計画書の読み取り（`internal/chief/task.go` の `ParsePlan`）が、ステップを形 A・形 B・形 C から読むようにする。読めないときと 0 件のときは、要確認の理由を分けて示す（設計書 3 章）。`CLAUDE.md` の例外の文言に 1 語を足す。

### 1.2. 実装の原則

-   **形 A の読み方と、PR の進み具合と完了の判定は変えない**（AC-11・AC-13）。
-   **テストの計画書は `internal/chief/testdata/plans/` のサンプルに置き、Go のリテラルに持たない**（要件書 4.5 節）。
-   **Go のコメント、識別子、文字列リテラルは英語で書く。** 日本語のリテラルは、計画書のテキストと一致させる `ステップ` などに限る（AC-15）。
-   **protocol 番号は変えない**（AC-14）。

### 1.3. 計画の際に決めたこと（2026-11-19）

-   **フェーズは 1 つ、PR は 1 本とする。** 人に聞くべき未決の判断はなかった。読み取りと理由の文は、互いのテストがないと確かめられず、分けても小さな PR が 2 つになるだけである。
    -   ADR: なし。本タスクの中で閉じる。
-   **本計画書のステップは、形 A（`- [ ] **ステップ N-M**`）で書く。** 本タスクの実装がマージされるまで、入れてある chief は形 A しか読まない。形 B で書くと、3 文書の PR のマージの後、本タスク自身の `/runplan` が決まらない。
    -   ADR: なし。本タスクの中で閉じる。

### 1.4. 既存コード調査結果

コミット `b93d1111`（`origin/main`）で確かめた。

-   ステップの読み取りは `ParsePlan`（`task.go:532-602`）の中にある。`stepBox`（`:522`）に合う行を `plan.steps` に入れ、重複は `ParsePlan` の誤りにする（`:550-555`）。

## 2. 実装のステップ (Implementation Steps)

### フェーズ 1: ステップの読み取りと理由の文（設計書 3 章、AC-01〜AC-16）

- [ ] **ステップ 1-1**: ステップの読み取り
    - 変えるファイル: `internal/chief/task.go`・`internal/chief/task_test.go`・`internal/chief/testdata/plans/`（新しいサンプル）・`internal/chief/testdata/README.md`
    - 設計書 3.2 節のとおり、`ParsePlan` が 2 章を判定し、形 B・形 C のステップと、その範囲のステップのチェックボックスを読むようにする。ステップの行に似た行、別の形のチェックボックス、チェックボックスのないステップ、ステップ ID の重複を、`Plan` のステップの読み取りの誤りとする（AC-01〜AC-04・AC-07・AC-09・AC-10）
    - 設計書 3.3 節のとおり、`StepsLeft` を `(bool, error)` にし、0 件では `errNoSteps` を返す。`StepsDone` は、ステップの読み取りの誤りを最初に返す。ステップの問題で `ParsePlan` が誤りを返さないようにする（AC-11）
    - サンプルを足す。足すのは、形 B、形 C、2 章の外の記録の行、読めない 4 つの条件、0 件、すべてマージ済みで読めないものである。`b93d1111` の 0110・0111・0102 の計画書の写しも足す（設計書 7 章）。写しと作ったサンプルの出どころを `testdata/README.md` に書く
    - `task_test.go` に、サンプルごとの `StepsLeft`・`StepsDone`・`Done`・`NextPR` の表のテストを足す。今の形 A のサンプルの結果が変わらないことも同じ表で確かめる（AC-13）。誤りは `errors.Is` で見分ける
    - テストが想定した理由で失敗できることを確かめる。読み取りの部分を 1 つずつ外して失敗することを見て、コミットメッセージに書く（設計書 7 章）。外す部分は、形 B、形 C、2 章の判定、似た行の判定、別の形のチェックボックスの判定、チェックボックスのないステップの判定、重複の判定、`errNoSteps` の分岐である
    - 完了の条件: `go test -tags test ./internal/chief` が通る。上の壊し方でテストが失敗したことを、コミットメッセージが述べる
- [ ] **ステップ 1-2**: 判定の理由
    - 変えるファイル: `internal/chief/state.go`・`internal/chief/snapshot_test.go`（引き継ぎのテストが別のファイルなら、そのファイルも）
    - 設計書 3.4 節のとおり、`nextFromPlan` が `StepsLeft` の 3 つの結果で理由を選ぶようにする（AC-03・AC-06・AC-07・AC-12）
    - 状態の表のテストに、次の行を足す（AC-01・AC-02・AC-06・AC-07・AC-11・AC-12）。0110 と 0111 の写しで `/runplan` を提案すること。形 C で `/runplan` を提案すること。読めない計画書と 0 件の計画書で要確認になり、理由が互いに違い、`no step left` の理由とも違うこと。すべてマージ済みで読めない計画書が完了になること
    - 引き継ぎのテストに、ブランチの計画書が形 B で対象ステップが済んでいるときに提案すること、読めないときに提案せず要確認の理由を示すことを足す（AC-05・AC-08）
    - テストが想定した理由で失敗できることを、`nextFromPlan` の分岐を 1 つずつ外して確かめ、コミットメッセージに書く
    - 完了の条件: `go test -tags test ./internal/chief` が通る
- [ ] **ステップ 1-3**: `main` の計画書のなめ

    - 結果と、通したコミットを 7 章の「`main` の計画書のなめの記録」に書く。PR が残っている計画書（作業中のタスク）に誤りが出たら、止めて人に知らせる

## 5. リスク管理 (Risk Management)

| リスク | 対策 |
|---|---|
| 2 章の中の、ステップでない行が、似た行として拒まれ、作業中のタスクの計画書が要確認になる | ステップ 1-3 で `main` のすべての計画書を通し、PR が残る計画書に誤りが出たら止めて人に知らせる |
