## 1. 概要 (Overview)

**目的:** 本書は、chief が実装計画書のステップを、いま `main` の計画書が使っている 3 つの形で読み、PR が残っている承認済みの計画書で次のコマンド（`/runplan <タスク>`）を決められるようにする要件を定める。

**背景:**

-   chief は、計画書のステップを、`- [ ] **ステップ N-M**` の形のチェックボックスの行だけから読む（`internal/chief/task.go:522` の `stepBox`、`:550-555`）。
-   承認済みの計画書に作っていない PR が残っていても、まだのステップがなければ、chief は次のコマンドを決めない。理由として `the plan has a PR left to create but no step left to do` を返す（`internal/chief/state.go:353-359`）。
    -   ステップのチェックボックスが 1 つも読めない計画書も、「残りなし」と読む（`task.go:682-691` の `StepsLeft`）。
    -   その行は「要確認」（`needs_check`）になり、この文を `unreadable` に出す（`state.go:455-461`）。
    -   この規則は、タスク 0088 の設計で決めたものである（`docs/tasks/0088_chief_of_staff/02_architecture.md:65`・`:441`）。`/runpr` の NEXT の定義（`.claude/commands/runpr.md:377-387`）に合わせるためである。
-   同じステップの読み取りを、OpenCode から Claude Code への引き継ぎの提案の判定も使う（`task.go:707-734` の `StepsDone`、`internal/chief/snapshot.go:315-338`）。
    -   PR マーカーの対象ステップにチェックボックスが見つからないと、`the steps of the next PR on the branch` を読めないものとして要確認にする（`snapshot.go:331-334`）。
-   `main` の計画書は、ステップを 3 つの形で書いている（2026-11-19、`b93d1111` の 110 件で数えた）。
    -   **形 A**: `- [ ] **ステップ 1-1**: …` のチェックボックスの行。56 件が使う。chief が読めるのはこの形だけである。
    -   **形 B**: `#### ステップ 1-1: …` の見出しと、その下のラベルのないチェックボックス。約 50 件が使う。タスク 0107・0110・0111 も、この形である。
    -   **形 C**: `**ステップ 1-1: …**` の 1 行の太字の段落と、その下のチェックボックス。タスク 0100 が使う。
-   規約は、ステップをチェックボックスで書くことだけを求め、形 A を求めていない（`docs/dev/conventions/requirements_process.md:739`、`.claude/commands/mkplan.md:97`）。chief の読み方が、規約より狭い。
-   その結果、PR #1016（タスク 0110）と PR #1020（タスク 0111）のマージの後、chief は `/runplan` を決めず、自動送信もしなかった。行は要確認になり、人がペインで `/runplan` を手で送るまでタスクが止まった（issue #1021）。
-   形 C と同じ見た目の太字の行（`**ステップ 1-1（実物の確かめ、…）。**` など）は、受け入れ基準の検証の章（5・7・9 章）でも、検証の記録の見出しとして使われている（0027・0081・0102 など）。
    -   2 章（実装のステップ）の外にある形 B・形 C の行は、どの計画書でもステップではない。
    -   2 章の中にも、ステップではない太字の行が 1 件ある（0051 の `**ステップ 4-1・4-2 の完了の条件:**`）。

以上の行番号と件数は、コミット `b93d1111`（`origin/main`）で確かめた。

対応 issue: [#1021](https://github.com/isseis/yt2column/issues/1021)（関連: タスク 0088・0110・0111）

**本書の記述範囲:** 本書は、chief がどの行をステップとして読み、ステップの状態をどう判断し、読めないときに何を示すかを定める。読み取りの組み立て（関数、正規表現、エラーの持ち方）は `02_architecture.md` で、確かめ方は `03_implementation_plan.md` で定める。

**issue #1021 で決めたこと:**

-   **計画書の読み取りの誤りでも、ステップが 0 件の計画書でも、誤ったコマンドは送らない。** 今の振る舞い（要確認にするだけ）を保つ。issue の「補足」が、これを前提にしている。
    -   ADR: なし。0088 の設計の規則（読めない文書からコマンドを推し量らない）をそのまま保つ。

**要件定義の際に決めたこと（2026-11-19）:**

-   **進め方は簡易な進め方（`simple`）とする。この変更は、除外される変更に当たらない。**
    -   理由: 変えるのは chief の計画書の読み取りの 1 か所と、`CLAUDE.md` の例外の文言の 1 か所である。新しい仕組みは作らない。既存の ADR の決定も変えない（ADR-0046 には、ステップの読み方の記載がない）。未決の判断も少ない。
    -   除外の判断: `docs/dev/security.md` の規則と前提、開発の道具の信頼境界（`fixprguard`・`codexreview`・`mergepr`、[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）、外部依存のどれも変えない。chief が読むのは `origin/main` とブランチの計画書で、レビューのスレッドや Bot への依頼の扱いは変えない（`docs/dev/conventions/requirements_process.md`「Simple Process」の「Excluded changes」）。
    -   ADR: なし。本タスクの中で閉じる、進め方の選択である。
-   **chief の側で直し、形 A・形 B・形 C の 3 つを読む。計画書と `/mkplan` は変えない（F-001・F-004）。**
    -   形 B・形 C のステップは、その下のチェックボックスがすべて `[x]` か `[-]` なら済み、1 つでも `[ ]` なら残りとする。
    -   理由: 規約は形 A を求めていない。計画書の側（0110・0111 を直し、`/mkplan` に形 A を指示させる）で直しても、形 B・形 C で書いた約 50 件の計画書は救えない。
    -   採らなかった案: 計画書の側だけで直す案。両方で直す案（`/mkplan` に形を指示させる部分は、chief が 3 つの形を読めば要らない）。
    -   ADR: なし。chief の計画書の読み取りの中で閉じる。
-   **形 B・形 C は、計画書の 2 章（見出しが `## 2.` で始まる章）の中だけで読む。形 A は、今のまま文書全体で読む（F-001）。**
    -   理由: `main` の計画書の形 B・形 C のステップは、どれも 2 章にある。2 章の外で同じ見た目をとる太字の行は、検証の記録である。文書全体で読むと、0102 のような計画書が同じステップ ID を 2 度持つことになり、ステップの状態を読めなくなる。
    -   採らなかった案: 文書全体で読む案。
    -   ADR: なし。本タスクの中で閉じる。
-   **ステップの下にチェックボックスがないとき、ステップの状態は読めないものとする。済みとは読まない（F-002）。**
    -   理由: 推し量らずに拒むためである（`CLAUDE.md`「Reject, don't normalize」）。
    -   採らなかった案: 済みとして読む案。
    -   ADR: なし。本タスクの中で閉じる。
-   **2 章の中で、ステップの行に似ているが、受け入れる形にない行は、ステップの状態を読めないものにする。形 B・形 C のステップの範囲にある、別の形のチェックボックスの行も同じとする（F-002）。**
    -   ステップの行に似た行の例は、0051 の `**ステップ 4-1・4-2 の完了の条件:**` である。別の形のチェックボックスの例は、`* [ ]`・`1. [x]`・`- [X]` である。
    -   理由: 黙って無視すると、未着手のステップを見落とし、「残りなし」や「対象ステップが済んだ」と誤って読みうる。
    -   採らなかった案: その行を無視する案。
    -   ADR: なし。本タスクの中で閉じる。
-   **ステップの読み取りの問題は、ステップを使う判定（次のコマンドを決める判定と、引き継ぎの提案の判定）だけに出す。すべての PR がマージ済みの計画書は、ステップの形にかかわらず完了と読む（F-002 の AC-11）。**
    -   形 A のステップ ID の重複も、同じ扱いにする。今は、計画書全体を読めないものにしている（`task.go:551-553`）。
    -   理由: 上の 2 つの決定を人が選んだとき、その選択肢は「すべての PR がマージ済みの計画書は完了と読める」ことを含んでいた。読み取りの問題がタスクの完了の判定まで止めると、終わったタスクの workspace が要確認のまま残る。PR マーカーの対象ステップの読み取りの誤りは、すでにこの扱いである（`task.go:497-499` の `stepsErr`）。
    -   ADR: なし。本タスクの中で閉じる。
-   **PR が残っているのに、どの形のステップも 1 つも読めない計画書には、「残りなし」とは別の理由を示す（F-003）。**
    -   理由: 今の文（`no step left to do`）は、すべてのステップが済んだように読める。issue #1021 で、人が原因に気づくのを遅らせた。
    -   採らなかった案: 今の文のままにする案。
    -   ADR: なし。本タスクの中で閉じる。
-   **形 C の行の頭のリテラルを、`CLAUDE.md` の「Go Idioms」にある `internal/chief/task.go` の例外に、種類として足す（F-004 の AC-15）。**
    -   理由: 今の例外は、見出しのテキストとその固定部分、欄のラベル、値の行の頭、チェックボックスのテキストを挙げる（`CLAUDE.md:919-933`）。形 A はチェックボックスのテキスト、形 B は見出しのテキストの固定部分に当たる。形 C の太字の行の頭は、どれにもはっきりとは当たらない。
    -   採らなかった案: 「値の行の頭」に当たると読み、`CLAUDE.md` を変えない案。
    -   ADR: なし。例外の範囲の文言で、本タスクの中で閉じる。
-   **chief の protocol 番号は上げない（F-004 の AC-14）。**
    -   理由: コマンドラインの引数も、出力の JSON の形も変わらない。変わるのは計画書の読み方と、理由の文だけである。古い道具が残っていても、今と同じく要確認にするだけで、誤ったコマンドは送らない。番号は、道具と文書の約束が変わったときに上げる（`CLAUDE.md`「Protocol numbers」、ADR-0014）。
    -   採らなかった案: 番号を `main` の値 + 1 に上げ、入れ直しを強いる案。
    -   ADR: なし。ADR-0014 の規則の当てはめで、決定は変わらない。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   形 B・形 C でステップを書いた、PR が残っている承認済みの計画書について、chief がマージの後の次のコマンド（`/runplan <タスク>`）を決め、条件が合えば自動送信できるようにする。
-   ステップを読めないとき、chief が要確認にし、理由を正しく示すようにする。

### 2.2. スコープ (In Scope)

-   chief の計画書のステップの読み取り（F-001）と、読めないときの扱い（F-002・F-003）。
-   ステップの読み取りを使う 2 つの判定、すなわち次のコマンドの判定と、引き継ぎの提案の判定（F-001・F-002）。
-   `CLAUDE.md`「Go Idioms」の、`internal/chief/task.go` の例外の種類の追記（F-004）。

### 2.3. スコープ外 (Out of Scope)

-   計画書の書き直し（0110・0111 などのステップを形 A に直すこと）と、`/mkplan`・`/mkplan2`・規約にステップの形を指示させること。理由は 1 章の「要件定義の際に決めたこと」にある。
-   `/runpr`・`/runplan` の、ステップの読み方。どちらもエージェントが計画書を読むもので、chief の読み取りを使わない。
-   次のコマンドの規則そのもの（まだのステップがあるときだけ `/runplan` とする規則、0088 の設計 3.1.4）の変更。読み方だけを広げる。
-   タスク 0088 の設計書の書き換え。0088 は完了したタスクで、本タスクの文書が今の読み方を定める。
-   形 A の読み方の変更。ステップ ID の重複の扱い（AC-11）を除く。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

本書の「2 章」は、計画書のフェンスで囲んだコードブロックの外で、`## 2.` と空白で始まる見出しの行から、次のレベル 1 かレベル 2 の見出しの行の前までを指す。「ステップの行」は、次の 3 つの形の行を指す。どれもフェンスで囲んだコードブロックの外の行だけを読む。`N-M` は、1 桁以上の数字、`-`、1 桁以上の数字である。

-   **形 A**: 文書のどこでも、行頭が `- ` と空白とタブの並び、`[<印>]`、空白とタブの並び、`**ステップ N-M**` の行。`<印>` は空白、`x`、`-` のどれかである。今の chief が読む形で、変えない（`task.go:522`）。
-   **形 B**: 2 章の中の見出しの行（行頭の 1〜6 個の `#` と、空白かタブ）で、見出しのテキストが `ステップ N-M` で始まり、その直後が `:`、`：`、行末のどれかであるもの。
-   **形 C**: 2 章の中の行で、`**ステップ N-M` で始まり、その直後が `:` か `：` で、行が `**` で終わり、行全体が 1 つの太字であるもの。

形 B・形 C のステップの「範囲」は、その行の次の行から、次の見出しの行、次のステップの行、2 章の終わりのどれかの前までとする。範囲の中の「ステップのチェックボックス」は、行頭の空白とタブの並び（なくてもよい）の後に `- `、空白とタブの並び、`[ ]`・`[x]`・`[-]` のどれかが続く行である。

#### F-001: 3 つの形のステップを読む

chief は、承認済みの計画書のステップを、形 A・形 B・形 C から読む。ステップを使う 2 つの判定（次のコマンドの判定と、引き継ぎの提案の判定）は、どの形のステップも同じ規則で扱う。

**Acceptance Criteria**:
- **AC-01**: 承認済みの計画書が形 B でステップを書き、作っていない PR と、`[ ]` のチェックボックスを持つステップを持つとき、chief はその workspace の次のコマンドを `/runplan <タスク>` と決める。送り先は、今と同じく PR の実装モデル要件で決まる。例: `b93d1111` の `docs/tasks/0110_chief_work_item_terms/03_implementation_plan.md` と `docs/tasks/0111_doc_style_rules/03_implementation_plan.md`。
- **AC-02**: AC-01 は、形 C でステップを書いた計画書でも成り立つ。
- **AC-03**: 形 B・形 C のステップは、範囲の中のステップのチェックボックスがすべて `[x]` か `[-]` のとき済みとし、1 つでも `[ ]` があるとき残りとする。すべてのステップが済んだ計画書で、作っていない PR が残るとき、chief は今の形 A の計画書と同じく次のコマンドを決めない。行を要確認にし、ステップが残っていないことを理由に示す。
- **AC-04**: 2 章の外にある、形 B・形 C と同じ見た目の行（受け入れ基準の検証の章の `**ステップ 1-1（…）。**` など）は、ステップとして読まない。そのような行を持ち、2 章のステップが読める計画書は、その行がないときと同じ判定になる。例: `b93d1111` の `docs/tasks/0102_chief_text_table/03_implementation_plan.md`。
- **AC-05**: 引き継ぎの提案の判定は、ブランチの計画書の、次の PR の対象ステップ（PR マーカーの `**対象ステップ**`、マーカーのない計画書ではすべてのステップ）が済んだかを、形 B・形 C のステップでも AC-03 の規則で判断する。

#### F-002: ステップを読めないときは要確認にする

次のどれかに当たる計画書は、ステップの状態を読めないものとする。

-   形 B・形 C のステップで、範囲の中にステップのチェックボックスが 1 つもないものがある。
-   2 章の中に、ステップの行に似ているが受け入れる形にない行がある。そのような行は、次の 2 つである。見出しの行で、見出しのテキストが `ステップ` で始まり、その後に空白があってもなくても数字が続くもの。行頭が `**ステップ` で、その後に空白があってもなくても数字が続くもの。
-   形 B・形 C のステップの範囲の中に、別の形のチェックボックスの行がある。そのような行は、行頭の空白とタブの並び（なくてもよい）の後に、リストの印（`-`・`*`・`+`、または数字と `.` か `)`）、空白かタブ、`[` と 1 文字と `]` が続き、ステップのチェックボックスではないものである。例: `* [ ]`・`1. [x]`・`- [X]`。
-   同じステップ ID が、形を問わず 2 度ある。

**Acceptance Criteria**:
- **AC-06**: ステップの状態を読めない承認済みの計画書で、作っていない PR が残るとき、chief は次のコマンドを決めない。行を要確認にし、自動送信も提案もしない。
- **AC-07**: AC-06 の理由は、上の 4 つのうちどれに当たったかを示す。ステップのチェックボックスがないときと、ステップ ID が重複するときは、そのステップ ID を示す。ステップの行に似た行と、別の形のチェックボックスの行のときは、その行を示す。
- **AC-08**: 引き継ぎの提案の判定で、ブランチの計画書のステップの状態を読めないとき、chief は引き継ぎを提案しない。今と同じく、ブランチの計画書の次の PR のステップを読めないことを、要確認の理由に示す。
- **AC-09**: AC-06 の判定は、範囲の中の別の形のチェックボックスが `[ ]` でも `[x]` でも同じに行う。読めない計画書を、ステップが残っているとも、残っていないとも読まない。
- **AC-10**: 2 章の外の行は、F-002 のどの条件の対象にもしない。ただし、形 A の行のステップ ID の重複は、文書のどこにあっても対象にする。
- **AC-11**: すべての PR の作成とマージのチェックボックスが済んだ承認済みの計画書は、ステップの状態を読めるかどうかにかかわらず、chief がタスクを完了（`task_done`）と読む。形 A のステップ ID の重複も、これに含む。

#### F-003: ステップが 1 つもない計画書には別の理由を示す

**Acceptance Criteria**:
- **AC-12**: 承認済みの計画書に作っていない PR が残り、形 A・形 B・形 C のどのステップも 1 つもないとき、chief は次のコマンドを決めず、行を要確認にする。理由は、ステップを 1 つも読めなかったことを示す。AC-03 の「ステップが残っていない」理由とは違う文にする。

#### F-004: 変えないもの

**Acceptance Criteria**:
- **AC-13**: 形 A でだけステップを書き、ステップ ID の重複のない計画書について、chief の判定（次のコマンド、完了、引き継ぎの提案）は変わらない。
- **AC-14**: chief の `--protocol` の番号（`internal/chief/records.go:29` の `Protocol`）と、`chief` の各サブコマンドの引数と、出力の JSON の項目は変わらない。ただし、要確認の理由の文（`unreadable` と `reasons` に出る文）は、F-002・F-003 のとおりに変わる。
- **AC-15**: `CLAUDE.md` の「Go Idioms」の `internal/chief/task.go` の例外が、リテラルの種類として、ステップの太字の行の頭を挙げる。
- **AC-16**: 実装の PR の差分は、次のものに限る。たとえば `docs/tasks/` のほかのタスクの計画書と、`.claude/commands/` は変わらない。
    -   `internal/chief` の Go のファイルと、`internal/chief/testdata/plans/` のサンプルの追加と変更
    -   `internal/chief/testdata/README.md` の、足したサンプルの出どころの記述
    -   `CLAUDE.md` の AC-15 の箇所
    -   本タスクのディレクトリ（`docs/tasks/0113_plan_step_reading/`）

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   N/A。計画書 1 つを読む処理の中で、行を一度なめるだけの変更である。

### 4.2. セキュリティ (Security)
-   N/A。`docs/dev/security.md` の条件（外部コマンドの起動、API キー、キャッシュのディレクトリ、ネットワークへの送信、信頼できない文字列の埋め込み）のどれにも当たらない。chief が読むのは、`origin/main` と workspace のブランチにある本リポジトリの計画書である。chief が送るコマンドの種類と、送る条件の規則は変えない。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   読めない計画書から、コマンドを推し量らない（F-002・F-003）。読み方を広げても、読めないものは要確認にとどめ、送らない。

### 4.4. 互換性 (Compatibility)
-   chief の protocol 番号を変えない（AC-14）。実装の PR のマージの後は、道具を変えたほかのマージと同じく `make install-chief` で入れ直す（`CLAUDE.md`「Commands」）。入れ直す前の古い道具は、形 B・形 C の計画書を今と同じく要確認にする。

### 4.5. 保守性 (Maintainability)
-   テストが読む計画書は、`internal/chief/testdata/plans/` のサンプルファイルに置き、Go のリテラルに持たない（`CLAUDE.md`「Go Idioms」の `task.go` の例外）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   Go のコメント、識別子、文字列リテラルは英語で書く。計画書のテキストと一致させる日本語のリテラルは、`CLAUDE.md`「Go Idioms」の `task.go` の例外の範囲に限る（AC-15）。
-   読み取りは「Reject, don't normalize」に従い、受け入れる形から外れた行を黙って読み替えない（F-002）。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。
-   **ステップの行:** 3 章の冒頭で定める、形 A・形 B・形 C の行。
-   **ステップの範囲:** 形 B・形 C のステップの行から、次の見出し、次のステップの行、2 章の終わりのどれかまでの行（3 章の冒頭）。
-   **ステップのチェックボックス:** 3 章の冒頭で定める、`- [ ]`・`- [x]`・`- [-]` の行。
-   **要確認（`needs_check`）:** chief の状態の表の行の状態の 1 つ。何かを読めなかった workspace で、何も送らない（`docs/dev/guides/chief_guide.md` の 3.1）。
-   **引き継ぎの提案:** OpenCode に送った `/runplan` が PR を開かずに止まったとき、同じ `/runplan` を Claude Code に送ることを示す chief の提案（0088 の要件 AC-40）。
