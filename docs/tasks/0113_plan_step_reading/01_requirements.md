## 1. 概要 (Overview)

**目的:** 本書は、`main` の計画書が今使っている 3 つの書き方のステップを、chief が読めるようにする要件を定める。これにより、作っていない PR が残っている承認済みの計画書で、chief が次のコマンド（`/runplan <タスク>`）を決められるようになる。

**背景:**

-   chief は、計画書のステップを、`- [ ] **ステップ N-M**` の形のチェックボックスの行だけから読む（`internal/chief/task.go:522` の `stepBox`、`:550-555`）。
-   承認済みの計画書に作っていない PR が残っていても、まだのステップがなければ、chief は次のコマンドを決めない。理由として `the plan has a PR left to create but no step left to do` を返す（`internal/chief/state.go:353-359`）。
    -   ステップのチェックボックスが 1 つも読めない計画書も、「残りなし」と読む（`task.go:682-691` の `StepsLeft`）。
    -   chief の状態の表で、その workspace の行は「要確認」（`needs_check`）になり、`unreadable` にこの文が出る（`state.go:455-461`）。
    -   「まだのステップがなければ次のコマンドを決めない」という規則は、`/runpr` の NEXT の定義（`.claude/commands/runpr.md:377-387`）に合わせて、タスク 0088 の設計で決めたものである（`docs/tasks/0088_chief_of_staff/02_architecture.md:65`・`:441`）。
-   OpenCode から Claude Code への引き継ぎの提案の判定も、同じステップの読み取りを使う（`task.go:707-734` の `StepsDone`、`internal/chief/snapshot.go:315-338`）。
    -   PR マーカーの対象ステップにチェックボックスが見つからないと、`the steps of the next PR on the branch` を読めないものとして要確認にする（`snapshot.go:331-334`）。
-   `main` の計画書は、ステップを主に 3 つの書き方で書いている。本書では、それぞれを「書き方 A」「書き方 B」「書き方 C」と呼ぶ（本タスクの用語で、用語集のコピーした字幕の「形 A」「形 B」とは別のものである）。件数は、2026-11-19 に `b93d1111` の 105 件の計画書で数えた。
    -   **書き方 A**: `- [ ] **ステップ 1-1**: …` のチェックボックスの行。56 件が使う。chief が読めるのはこの書き方だけである。
    -   **書き方 B**: `#### ステップ 1-1: …` の見出しと、その下のラベルのないチェックボックス。48 件が使う。タスク 0107・0110・0111 も、この形である。
    -   **書き方 C**: `**ステップ 1-1: …**` の 1 行の太字の段落と、その下のチェックボックス。タスク 0100 が使う。
    -   このほか、書き方 A に似た行を書き方 A の行に混ぜて使う計画書が 7 件ある（0022・0069・0070・0071・0074・0075・0083）。似た行は 2 種類で、ステップ ID の後に括弧が続く行（`- [x] **ステップ 1-1（内容のコミット 1）**:`）と、ID が数字でない行（`- [x] **ステップ M-1**:`）である。どちらも 2 章の中にある。chief は今、この行を読まず、読めないものとも扱わない。0069 では、8 つのステップのうち 1 つしか読まれない。
-   規約は、ステップをチェックボックスで書くことだけを求め、書き方 A を求めていない（`docs/dev/conventions/requirements_process.md:739`、`.claude/commands/mkplan.md:97`）。chief の読み方が、規約より狭い。
-   その結果、PR #1016（タスク 0110）と PR #1020（タスク 0111）のマージの後、chief は `/runplan` を決めず、自動送信もしなかった。行は要確認になり、人がペインで `/runplan` を手で送るまでタスクが止まった（issue #1021）。
-   書き方 C と同じ見た目の太字の行（`**ステップ 1-1（実物の確かめ、…）。**` など）は、受け入れ基準の検証の章（5・7・9 章）でも、検証の記録の見出しとして使われている（0027・0081・0102 など）。
    -   2 章（実装のステップ）の外にある書き方 B・書き方 C の行は、どの計画書でもステップではない。
    -   2 章の中にも、受け入れる形にない、ステップに似た行がある。0051 の `**ステップ 4-1・4-2 の完了の条件:**`、0028 の `#### ステップ 4-10a:`、0057 の `#### ステップ 1-1・1-2:` である。

以上の行番号と件数は、コミット `b93d1111`（`origin/main`）で確かめた。

対応 issue: [#1021](https://github.com/isseis/yt2column/issues/1021)（関連: タスク 0088・0110・0111）

**本書の記述範囲:** 本書は、chief がどの行をステップとして読み、ステップの状態をどう判断し、読めないときに何を示すかを定める。読み取りの組み立て（関数、正規表現、エラーの持ち方）は `02_architecture.md` で、確かめ方は `03_implementation_plan.md` で定める。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   書き方 B・書き方 C でステップを書いた、PR が残っている承認済みの計画書について、chief がマージの後の次のコマンド（`/runplan <タスク>`）を決め、条件が合えば自動送信できるようにする。
-   ステップを読めないとき、chief が要確認にし、理由を正しく示すようにする。

### 2.2. スコープ (In Scope)

-   chief の計画書のステップの読み取り（F-001）と、読めないときの扱い（F-002・F-003）。
-   ステップの読み取りを使う 2 つの判定、すなわち次のコマンドの判定と、引き継ぎの提案の判定（F-001・F-002）。
-   `CLAUDE.md`「Go Idioms」の、`internal/chief/task.go` の例外の種類の追記（F-004）。

### 2.3. スコープ外 (Out of Scope)

-   計画書の書き直し（0110・0111 などのステップを書き方 A に直すこと）と、`/mkplan`・`/mkplan2`・規約にステップの書き方を指示させること。理由は 1 章の「要件定義の際に決めたこと」にある。
-   `/runpr`・`/runplan` の、ステップの読み方。どちらもエージェントが計画書を読むもので、chief の読み取りを使わない。
-   次のコマンドの規則そのもの（まだのステップがあるときだけ `/runplan` とする規則、0088 の設計 3.1.4）の変更。読み方だけを広げる。
-   タスク 0088 の設計書の書き換え。0088 は完了したタスクで、本タスクの文書が今の読み方を定める。
-   書き方 A の読み方の変更。ステップ ID の重複の扱い（AC-11）を除く。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

本書の「2 章」は、計画書のフェンスで囲んだコードブロックの外で、`## 2.` と空白で始まる見出しの行から、次のレベル 1 かレベル 2 の見出しの行の前までを指す。

「ステップの行」は、次の 3 つの書き方の行を指す。どれもフェンスで囲んだコードブロックの外の行だけを読む。`N-M` は、1 桁以上の数字、`-`、1 桁以上の数字である。

-   **書き方 A**: 文書のどこでも、行頭が `-`、1 つ以上の空白かタブ、`[<印>]`、1 つ以上の空白かタブ、`**ステップ N-M**` の行。`<印>` は空白、`x`、`-` のどれかである。今の chief が読む形で、変えない（`task.go:522`）。
-   **書き方 B**: 2 章の中の見出しの行（行頭の 1 つ以上の `#` と、空白かタブ。chief が今、見出しと見なす行と同じ、`task.go:277` の `anyHeading`）で、見出しのテキストが `ステップ N-M` で始まり、その直後が `:`、`：`、行末のどれかであるもの。
-   **書き方 C**: 2 章の中の行で、`**ステップ N-M` で始まり、その直後が `:` か `：` で、行が `**` で終わり（その後に空白もない）、行頭の `**` と行末の `**` のほかに `**` を含まないもの。

書き方 B・書き方 C のステップの「範囲」は、その行の次の行から、次のどれかの前までとする。次のステップの行。2 章の終わり。書き方 B では、そのステップの見出しと同じか、それより上のレベル（`#` の数が同じか少ない）の見出しの行。書き方 C では、どのレベルの見出しの行も。書き方 B のステップの下の小見出しは、範囲を終えない。範囲の中の「ステップのチェックボックス」は、行頭の空白とタブの並び（なくてもよい）の後に `-`、1 つ以上の空白かタブ、`[ ]`・`[x]`・`[-]` のどれかが続く行である。

#### F-001: 3 つの書き方のステップを読む

chief は、承認済みの計画書のステップを、書き方 A・書き方 B・書き方 C から読む。ステップを使う 2 つの判定（次のコマンドの判定と、引き継ぎの提案の判定）は、どの形のステップも同じ規則で扱う。

**Acceptance Criteria**:
- **AC-01**: 承認済みの計画書が書き方 B でステップを書き、作っていない PR と、`[ ]` のチェックボックスを持つステップを持つとき、chief はその workspace の次のコマンドを `/runplan <タスク>` と決める。送り先は、今と同じく PR の実装モデル要件で決まる。例: `b93d1111` の `docs/tasks/0110_chief_work_item_terms/03_implementation_plan.md` と `docs/tasks/0111_doc_style_rules/03_implementation_plan.md`。
- **AC-02**: AC-01 は、書き方 C でステップを書いた計画書でも成り立つ。
- **AC-03**: 書き方 B・書き方 C のステップは、範囲の中のステップのチェックボックスがすべて `[x]` か `[-]` のとき済みとし、1 つでも `[ ]` があるとき残りとする。すべてのステップが済んでいて、作っていない PR が残る計画書では、chief は今の書き方 A の計画書と同じく次のコマンドを決めない。行を要確認にし、その理由として、ステップが残っていないことを示す。書き方 B のステップの下の小見出しの下にあるチェックボックスも、そのステップのチェックボックスとして数える。
- **AC-04**: 2 章の外にある、書き方 B・書き方 C と同じ見た目の行（受け入れ基準の検証の章の `**ステップ 1-1（…）。**` など）は、ステップとして読まない。そのような行を持ち、2 章のステップが読める計画書は、その行がないときと同じ判定になる。例: `b93d1111` の `docs/tasks/0102_chief_text_table/03_implementation_plan.md` と、7 章に書き方 C そのままの行（`**ステップ 3-1: …**`）を持ち、その ID が 2 章の書き方 A のステップと同じ `docs/tasks/0098_fable_partial_review/03_implementation_plan.md`。
- **AC-05**: 引き継ぎの提案の判定は、ブランチの計画書の、次の PR の対象ステップ（PR マーカーの `**対象ステップ**`、マーカーのない計画書ではすべてのステップ）が済んだかを、書き方 B・書き方 C のステップでも AC-03 の規則で判断する。

#### F-002: ステップを読めないときは要確認にする

次のどれかに当たる計画書は、ステップの状態を読めないものとする。

-   書き方 B・書き方 C のステップで、範囲の中にステップのチェックボックスが 1 つもないものがある。
-   2 章の中に、ステップの行に似ているが受け入れる形にない行がある。そのような行は、次の 3 つである。書き方 A・書き方 B・書き方 C の行は、似た行ではない。
    -   見出しの行で、見出しのテキストが `ステップ` で始まり、その後に空白があってもなくても数字が続くもの。
    -   行頭が `**ステップ` で、その後に空白があってもなくても数字が続くもの。
    -   行頭の空白とタブの並び（なくてもよい）の後に、リストの印（`-`・`*`・`+`、または数字と `.` か `)`）、1 つ以上の空白かタブ、`[` と 1 文字と `]`、1 つ以上の空白かタブが続き、その後が `**ステップ` と、空白があってもなくても ASCII の数字か英字であるもの（例: `- [x] **ステップ 1-1（内容のコミット 1）**:`、`- [x] **ステップ M-1**:`）。
-   書き方 B・書き方 C のステップの範囲の中に、別の形のチェックボックスの行がある。そのような行は、行頭の空白とタブの並び（なくてもよい）の後に、リストの印（`-`・`*`・`+`、または数字と `.` か `)`）、1 つ以上の空白かタブ、`[` と 1 文字と `]` が続き、ステップのチェックボックスではないものである。例: `* [ ]`・`1. [x]`・`- [X]`。
-   同じステップ ID が、書き方を問わず 2 度ある。

**Acceptance Criteria**:
- **AC-06**: ステップの状態を読めない承認済みの計画書で、作っていない PR が残るとき、chief は次のコマンドを決めない。行を要確認にし、自動送信も提案もしない。書き方 A に似たチェックボックスの行を 2 章に持つ計画書も、これに含む。例: `b93d1111` の `docs/tasks/0069_readme_display_language/03_implementation_plan.md`（書き方 A の行が 1 つ、似た行が 7 つ）の、PR の進み具合のチェックボックスを `[ ]` に戻したもの。0069 そのものは PR がすべてマージ済みなので、AC-11 のとおり完了と読む。
- **AC-07**: AC-06 の理由は、上の 4 つのうちどれに当たったかを示す。ステップのチェックボックスがないときと、ステップ ID が重複するときは、そのステップ ID を示す。ステップの行に似た行と、別の形のチェックボックスの行のときは、その行を示す。
- **AC-08**: 引き継ぎの提案の判定で、ブランチの計画書のステップの状態を読めないとき、chief は引き継ぎを提案しない。今と同じく、ブランチの計画書の次の PR のステップを読めないことを、要確認の理由に示す。
- **AC-09**: AC-06 の判定は、範囲の中の別の形のチェックボックスが `[ ]` でも `[x]` でも同じに行う。読めない計画書を、ステップが残っているとも、残っていないとも読まない。
- **AC-10**: 2 章の外の行は、F-002 のどの条件にも当てはめない。ただし、書き方 A の行のステップ ID の重複は、文書のどこにあっても対象にする。
- **AC-11**: すべての PR の作成とマージのチェックボックスが済んだ承認済みの計画書は、ステップの状態を読めるかどうかにかかわらず、chief がタスクを完了（`task_done`）と読む。書き方 A のステップ ID の重複も、これに含む。

#### F-003: ステップが 1 つもない計画書には別の理由を示す

**Acceptance Criteria**:
- **AC-12**: 承認済みの計画書に作っていない PR が残り、書き方 A・書き方 B・書き方 C のどのステップも 1 つもないとき、chief は次のコマンドを決めず、行を要確認にする。理由は、ステップを 1 つも読めなかったことを示す。AC-03 の「ステップが残っていない」理由とは違う文にする。ステップが 0 件で、F-002 の条件にも当たる計画書には、AC-07 の理由を示す。

#### F-004: 変えないもの

**Acceptance Criteria**:
- **AC-13**: 書き方 A でだけステップを書き、ステップ ID の重複も、2 章の中の F-002 の似た行もない計画書について、chief の判定（次のコマンド、完了、引き継ぎの提案）は変わらない。
- **AC-14**: chief の `--protocol` の番号（`internal/chief/records.go:29` の `Protocol`）と、`chief` の各サブコマンドの引数と、出力の JSON の項目は変わらない。ただし、要確認の理由の文（`unreadable` と `reasons` に出る文）は、F-002・F-003 のとおりに変わる。
- **AC-15**: `CLAUDE.md` の「Go Idioms」の `internal/chief/task.go` の例外が、リテラルの種類として、ステップの太字の行の頭を挙げる。また、そのリテラルを読む目的として、計画書のステップとその進み具合を挙げる。
- **AC-16**: 実装の PR の差分は、次のものに限る。たとえば `docs/tasks/` のほかのタスクの計画書と、`.claude/commands/` は変わらない。
    -   `internal/chief` の Go のファイルと、`internal/chief/testdata/plans/` のサンプルの追加と変更
    -   `internal/chief/testdata/README.md` の、足したサンプルの出どころの記述
    -   `CLAUDE.md` の AC-15 の箇所
    -   本タスクのディレクトリ（`docs/tasks/0113_plan_step_reading/`）

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   N/A。計画書 1 つを読む処理の中で、行を一度走査するだけの変更である。

### 4.2. セキュリティ (Security)
-   N/A。`docs/dev/security.md` の条件（外部コマンドの起動、API キー、キャッシュのディレクトリ、ネットワークへの送信、信頼できない文字列の埋め込み）のどれにも当たらない。chief が読むのは、`origin/main` と workspace のブランチにある本リポジトリの計画書である。chief が送るコマンドの種類と、送る条件の規則は変えない。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   読めない計画書から、コマンドを推し量らない（F-002・F-003）。読み方を広げても、読めないものは要確認にとどめ、送らない。

### 4.4. 互換性 (Compatibility)
-   chief の protocol 番号を変えない（AC-14）。実装の PR のマージの後は、道具を変えたほかのマージと同じく `make install-chief` で入れ直す（`CLAUDE.md`「Commands」）。入れ直す前の古い道具は、書き方 B・書き方 C の計画書を今と同じく要確認にする。

### 4.5. 保守性 (Maintainability)
-   テストが読む計画書は、`internal/chief/testdata/plans/` のサンプルファイルに置き、Go のリテラルに持たない（`CLAUDE.md`「Go Idioms」の `task.go` の例外）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   Go のコメント、識別子、文字列リテラルは英語で書く。計画書のテキストと一致させる日本語のリテラルは、`CLAUDE.md`「Go Idioms」の `task.go` の例外の範囲に限る（AC-15）。
-   読み取りは「Reject, don't normalize」に従い、受け入れる形から外れた行を黙って読み替えない（F-002）。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。
-   **ステップの行:** 3 章の冒頭で定める、書き方 A・書き方 B・書き方 C の行。
-   **ステップの範囲:** 書き方 B・書き方 C のステップの行から、次の見出し、次のステップの行、2 章の終わりのどれかまでの行（3 章の冒頭）。
-   **ステップのチェックボックス:** 3 章の冒頭で定める、`- [ ]`・`- [x]`・`- [-]` の行。
-   **要確認（`needs_check`）:** chief の状態の表の行の状態の 1 つ。何かを読めなかった workspace で、何も送らない（`docs/dev/guides/chief_guide.md` の 3.1）。
-   **引き継ぎの提案:** OpenCode に送った `/runplan` が PR を開かずに止まったとき、同じ `/runplan` を Claude Code に送ることを示す chief の提案（0088 の要件 AC-40）。
