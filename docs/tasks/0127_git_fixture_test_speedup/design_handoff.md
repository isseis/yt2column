# 設計への申し送り：review_records・high_review_decision・mergemain のテストの高速化

本書は、[01_requirements.md](01_requirements.md) の起草で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 時間の内訳を測ってから手段を選ぶ

-   **事項:** 3 つのファイルのテストについて、時間がどこにかかるか（フィクスチャの作成、枝の組み立て、スクリプトや `mergemain` の実行、Go の処理、`-race` の負担、並列の取り合い）を測り、その内訳から短縮の手段を選ぶ。
-   **理由:** 要件書 §1 の計測では、git の設定のシナリオ 1 件の時間のうち、スクリプトの実行（約 0.93 秒 × 2 回）が、フィクスチャの作成と枝の組み立て（計 約 0.68 秒）より大きい。issue が挙げるテンプレートのリポジトリの複製だけでは、目標（半分以下、AC-01・AC-02）に届かないおそれがある。`CLAUDE.md`「Performance」は、手段を選ぶ前に測ることを求める。
-   **候補の方針:** 設定の前の実行は同じ枝なら同じ出力になるので、16 のシナリオ（スコープ 2 × 設定 8）の間で、設定の前の実行の結果を共有する。同じ初期状態を共有できるケースは、テンプレートの複製から始める。`high_review_decision_test.go` と `mergemain_test.go` についても、内訳を測ってから同じ考え方を当てはめる。
-   **関連:** F-001、AC-01、AC-02

## H-02: 目標に届かないときの扱い

-   **事項:** 内訳を測った結果、bash 3 での全件の実行を残したまま半分以下にするのが難しいと分かった場合の扱いを決める。
-   **理由:** 要件書は、bash 3 での全件の二重の実行を残すこと（AC-05）と、末端のサブテストの名前の集まりを変えないこと（AC-04）を決めた。この 2 つは手段を狭める。届かない見込みを設計の段階で見つければ、実装の前に要件を見直せる。
-   **候補の方針:** 届かない見込みなら、`02_architecture.md` を書く前に、見込みの数値を添えて要件の決定の変更をレビューに諮る（`docs/dev/conventions/requirements_process.md`、「Editing an approved document」）。
-   **関連:** F-001、F-002、AC-01、AC-02、AC-04、AC-05

## H-03: テンプレートの複製が作り直しと同じ状態になること

-   **事項:** 共通の初期状態をテンプレートとして作って複製する場合、複製した状態が、ケースごとに作り直した状態と同じになることを保つ手段を決める。
-   **理由:** 複製には次の落とし穴がある。
    -   `.git/config` などに、テンプレートの絶対パスが残る。`newTakeIn` の clone は `remote.origin.url` に origin の絶対パスを持つので、複製のあとでも複製した origin を指すようにしないと、ケースがテンプレートの origin に push する。
    -   index は stat の情報を持つので、複製でファイルの時刻が変わると、git がファイルを変わったものとして読み直すことがある。
    -   フィクスチャの `HOME`・`TMPDIR`（`cmd/yt2column/test_helpers_gitfixture.go:30-46`）は、ケースごとに別でなければならない。グローバルの git の設定のシナリオは `HOME` の `.gitconfig` に書くので、共有すると、ほかのケースが設定を読む。
    -   テンプレートを並列のケースが同時に作らないように、作るのは 1 回にする。作れなかったときは、それに依るケースを失敗させる（AC-08）。
-   **候補の方針:** 複製した状態と作り直した状態を比べるテスト（refs・オブジェクト・設定・index の比較）を置き、`CLAUDE.md`「Performance」の「An optimization that adds a correctness obligation」の義務として固定する。
-   **関連:** F-002、F-003、AC-07、AC-08、AC-10

## H-04: 実行の結果を共有するときの前提の確認

-   **事項:** 設定の前の実行など、実行の結果をケースの間で共有する場合、今は各ケースが行う前提の確認（設定の前の出力が期待の先頭で始まること、設定が plain git の出力を変えること）を、共有のあとも各ケースが行うようにする。
-   **理由:** 共有すると、前提の確認が 1 か所だけになり、あるケースの枝が前提を満たさなくなっても見逃すおそれがある。AC-07 は、前提が崩れたときに各ケースが今と同じく失敗することを求める。
-   **候補の方針:** 共有するのは同じ枝の同じ実行の結果だけにし、ケースごとの plain git の比較は各ケースに残す。共有する結果が期待の先頭で始まることは、共有の側で確かめ、失敗したときはそれに依るすべてのケースを失敗させる。
-   **関連:** F-002、AC-07、AC-08

## H-05: 計測と名前の集まりの比較の手段

-   **事項:** AC-01〜AC-04 の計測と比較を行う手段（手順を書くだけにするか、`_checks/` の一時スクリプトにするか）を決める。
-   **理由:** 計測は前と後で 3 回ずつ、計 6 回流し（1 回あたり数分）、名前の集まりの比較は `go test -json` の出力を読む。手で行うと記録の誤りが入りやすい。一方、一時スクリプトの作りは、変更の規模と実行の回数に見合うものにする（`docs/dev/conventions/requirements_process.md`、「Temporary scripts (`_checks/`)」）。
-   **候補の方針:** 前のコミットと後のコミットを worktree で取り出して流し、時間と名前の集まりを出す小さなスクリプトを `_checks/` に置く。機械の情報の記録も、同じスクリプトで出す。
-   **関連:** F-001、F-002、AC-01、AC-02、AC-03、AC-04
