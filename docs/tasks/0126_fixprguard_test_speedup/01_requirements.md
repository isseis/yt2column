## 1. 概要 (Overview)

**目的:** 本書は、`internal/fixprguard` と `cmd/fixprguard` のテストを並列に実行できるようにし、テストの git フィクスチャの費用を下げて、2 つのパッケージのテストの実行時間を短くするための要件を定義する（[#1167](https://github.com/isseis/yt2column/issues/1167)）。

**背景:**

issue #1167 の計測（`go test -tags test -race -count=1 ./...`）では、`internal/fixprguard` が全パッケージの中で最も遅く（壁時計で 493.0 秒）、`cmd/fixprguard` も 88.0 秒かかる。`make test` は `go test -race ./...` を 1 回実行する（`Makefile:93-95`）。`go test` は既定でパッケージを並列に走らせるので、全体の時間は最も遅いパッケージの時間で決まる。この 2 つのパッケージがテスト全体のボトルネックになっている。

遅い原因は 2 つある。

-   **並列に実行できない:** テストのリポジトリを作る `newTestRepo` は、`t.Setenv("HOME", ...)`・`t.Setenv("XDG_CONFIG_HOME", ...)` と `t.Chdir` を呼ぶ（`internal/fixprguard/test_helpers_git.go:127-155`、`cmd/fixprguard/test_helpers.go:52-77`）。Go では、`t.Setenv` か `t.Chdir` を呼ぶテストは `t.Parallel()` にできない。そのため、2 つのパッケージのテストは 1 つずつ順に実行される。
-   **テストごとに多くの git を起動する:** `newTestRepo` は 1 回の呼び出しで、`git init` を 2 回、`git config` を 7 回、`git remote add`・`git add`・`git commit`・`git push` を 1 回ずつ実行する（`internal/fixprguard/test_helpers_git.go:127-169,237-241`）。`cmd/fixprguard` の `newTestRepo` も同じ形で、`git config` は 6 回である（`cmd/fixprguard/test_helpers.go:52-94`）。

`t.Chdir` をやめられないのは、製品コードがプロセスの作業ディレクトリを前提にしているからである。fixprguard は、作業ディレクトリが作業ツリーの最上位であることを前提に動き、`.git` を作業ディレクトリからの相対パスで読む（`internal/fixprguard/gitstate.go:182-204`、`internal/fixprguard/worktree.go:48-49`、[fixprguard_guide.md](../../dev/guides/fixprguard_guide.md) の「作業ディレクトリ」の行）。一方、環境変数は製品コードの問題ではない。`internal/fixprguard` はプロセスの環境変数を読まず、子のコマンドの環境は呼び出し元が runner に渡す（`cmdrunner.Options.Env`。CLI は `cmd/fixprguard/main.go:172-190` で、引き継いだ環境変数から `GIT_*` を除いて渡す）。テストの `HOME` がプロセスの環境変数に左右されるのは、テストの補助が、runner と準備の git に渡す環境を `os.Environ()` から作っているからである（`internal/fixprguard/test_helpers_git.go:182,196,261-262`）。

対応 issue: [#1167](https://github.com/isseis/yt2column/issues/1167)

**本書の記述範囲:** 本書は、観測できる結果を定める。どのテストが並列に動くか、製品の外から見た振る舞いを変えないこと、フィクスチャが作るリポジトリの状態、実行時間の目標、検証範囲を保ったことの確かめ方である。作業ツリーのディレクトリを受け渡す API の形、テストの補助が子のコマンドに渡す環境の作り方、フィクスチャを速くする手段（ひな形のコピーか、設定ファイルへの直接の書き込みか）、直列のまま残すテストの一覧、計測の手順の細部は、設計（`02_architecture.md`）で決める。要件の段階で挙がった設計の事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #1167 で決めたこと:**

-   **並列化の方針:** fixprguard の作業ツリーの操作と環境変数の参照を、作業ディレクトリと環境変数の注入で完結させる。`newTestRepo` から `t.Chdir` と `t.Setenv` への依存をなくし、`t.Parallel()` を使えるようにする（F-001、F-002）。
-   **フィクスチャの軽量化:** テストのリポジトリ 1 つあたりの git の起動の回数を減らす。手段の候補は、初期状態のリポジトリ（`work` と `remote.git`）をひな形として 1 回だけ作って各テストでコピーすることと、`git config` の連続した呼び出しを `.git/config` への直接の書き込みに置き換えることである（F-003）。
-   **完了の条件:** 2 つのパッケージの主要なテストが `t.Parallel()` で安全に並列に動き、`-race` で通ること。テストの検証範囲を保ったまま、2 つのパッケージの実行時間が大幅に短くなること。`make test` と `make lint` が通ること（F-001、F-004、F-005）。

**要件定義の際に決めたこと（2026-11-26）:**

-   **プロセス:** フルプロセスで進める。fixprguard の製品コードを変えるので、簡易プロセスの除外（[requirements_process.md](../../dev/conventions/requirements_process.md) の「Excluded changes」の、開発ツールの信頼の境界の変更。[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）に当たると判断した。外から見た振る舞いは変えないが、境界を守るツールのコードに手を入れることには変わりないためである。人はフルプロセスを選んだ。ADR: なし（タスクのプロセスの選択で、ほかのタスクを縛らない）。
-   **製品の変更の扱い:** 製品の変更を範囲に含める。テストだけを変える案（製品は変えず、フィクスチャを軽くするだけで並列化しない）は採らなかった。並列にできなければ短縮の幅が小さく、issue の完了の条件に届かないためである。製品のコードを、作業ツリーのディレクトリを呼び出し元から受け取る形に変える（F-002）。子のコマンドの環境は、製品がすでに呼び出し元から受け取っているので、テストの補助を変えるだけで済む（F-001 の AC-05）。ADR: なし（fixprguard の内部の構造の変更で、外から見た契約は変えず、ほかの構成要素やタスクを縛らない）。
-   **CLI の契約とプロトコル番号:** どちらも変えない。CLI は今までどおりプロセスの作業ディレクトリを作業ツリーとし、引き継いだ環境変数から子のコマンドの環境を作る。サブコマンド・引数・出力・終了コードは変えない（F-002）。[dev_tools.md](../../dev/conventions/dev_tools.md) は、開発ツールの引数・出力・終了コードを契約として保つよう求めている。契約を変えないので、プロトコル番号（`CLAUDE.md`「Protocol numbers」）も上げない。ADR: なし（既存の規則をそのまま当てはめる）。
-   **短縮の目標:** 同じ機械での前後の比で 50% 以下にする。変更の前と後で、同じ機械と同じコマンドで 2 つのパッケージを計り、それぞれ前の時間の 50% 以下になることを目標にする（F-004）。絶対の秒数を目標にすると、機械の性能で結果が変わるためである。数値の目標を置かない案は、「大幅に」を確かめられないので採らなかった。ADR: なし（このタスクの完了の条件で、ほかのタスクを縛らない）。
-   **直列のまま残してよいテスト:** プロセス全体の状態そのものを確かめるテストに限り、`t.Parallel()` にしなくてよい。例は、引き継いだ `GIT_DIR` が子のコマンドに届かないことや、`PATH` からコマンドを探すこと、本物のプロセスの作業ディレクトリでの振る舞いを確かめるテストである（F-001）。これらは確かめる対象がプロセスの状態なので、注入の形に書き直すと、確かめたいことを確かめられなくなるためである。例外を認めない案は、この理由で採らなかった。直列のまま残すテストの一覧とそれぞれの理由は、設計で決めて設計書に記録する。ADR: なし（このタスクのテストの扱いで、ほかのタスクを縛らない）。
-   **検証範囲の保ち方:** 次の 2 つで確かめる（F-005）。
    -   1 つは、テストだけを変えた範囲を `make coverage-compare` で比べて `PASS` になることである。テストを削除したときだけ比較を求める今の規則（[ADR-0037](../../dev/adr/0037-test-deletion-coverage.md)）では、テストを書き直して確かめる範囲が狭まっても見つけられないためである。
    -   もう 1 つは、2 つのパッケージのテストとサブテストの名前が、前から後へ欠けずに残ることである。カバレッジだけでは、同じ行を通る別のテストに置き換わったことが分からない。テストの名前だけでは、テストの中身が減ったことが分からない。そのため 2 つを組み合わせる。
    -   PR のレビューで差分を読むだけにする案は、機械的に確かめられないので採らなかった。
    -   ADR: なし（このタスクの確かめ方で、ADR-0037 の決定は変えない）。
-   **カバレッジの比較の範囲:** テストだけを変えた範囲に当てる（同日、自己レビューの後に決め直した）。最初は PR 全体を比べるつもりだったが、`make coverage-compare` は削除以外の変更を含む比較を止める（`internal/coveragecompare/classify.go:49-57`、ADR-0037 の 2026-11-02 の履歴）。製品の関数を書き換える F-002 の変更を含む範囲では `PASS` にならない。そこで、実装の PR の中で製品の変更をテストの書き直しより前のコミットに置き、製品を最後に変えたコミットを `BASE` にして比べる（AC-14）。製品の変更そのものは、既存のテストが通ることと、AC-08 の CLI の入口のテストと、PR のレビューで確かめる。テストの名前の比較と PR のレビューだけにする案は、カバレッジの比較を失うので採らなかった。パッケージ全体のカバレッジだけを比べる案は、関数ごとの低下を見落とすので採らなかった。ADR: なし（このタスクの確かめ方である）。
-   **順に動くサブテストの扱い:** 親のテストが並列なら、サブテストは直列でよい。1 つのフィクスチャを順に使うサブテストは、直列のまま残してよい（AC-03 の 2 つ目）。1 つのリポジトリを段階を追って変える表のように、順序そのものが確かめる内容の一部であるテストがあるためである。この場合も、親のテストは並列にする。一方、直列の親の下で `t.Setenv` を呼ぶサブテスト（`cmd/fixprguard/main_test.go:254`）は、プロセスの状態を確かめるテストの下のサブテストとして扱う（AC-03 の 1 つ目）。例外を認めずにサブテストごとにフィクスチャを作り直す案は、確かめる内容が変わり、フィクスチャの費用も増えるので採らなかった。ADR: なし（このタスクのテストの扱いである）。
-   **計測の判定と、期待値の確かめ（同日、ローカルのレビューの後に決めた）:** 計測は、2 つのパッケージをそれぞれ単独の `go test` で、前と後で 3 回ずつ行い、中央値どうしを比べる（AC-12）。単独で計るのは、ほかのパッケージの影響を受けずに比べるためである。issue の数値は `./...` 全体の実行で取ったものなので、単独の計測とは一致しない。`./...` 全体で計る案は、ほかのパッケージの負荷で結果が揺れるので採らなかった。中央値を使うのは、1 回の揺れで判定が変わらないようにするためである。また、カバレッジとテストの名前では、名前を残したまま期待値を削ったり弱めたりしたことと、製品を変えるコミットの中で書き換えたテストの経路が減ったことを見つけられない。そこで、期待値を変えたテストを理由とともに記録し、製品を変えるコミットでのテストの差分を呼び出しの引数と準備に限り、PR のレビューで読んで確かめる（AC-16）。既知の限界として記すだけにする案は、確かめる手段がなくなるので採らなかった。ADR: なし（このタスクの確かめ方である）。
-   **目標に届かなかったときの扱い:** 止めて人に尋ねる。AC-12 の目標に届かなかったときは、PR を開く前に止め、計測の結果と原因の見立てを人に示す。目標を見直すか、対策を足すかは人が決める（AC-13）。届かないまま PR を開く案は、完了の条件を黙って緩めることになるので採らなかった。ADR: なし（このタスクの進め方である）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   `internal/fixprguard` と `cmd/fixprguard` のテストを並列に実行できるようにし、`-race` で安全に通るようにする。
-   2 つのパッケージのテストの実行時間を、それぞれ変更の前の 50% 以下にする。
-   fixprguard の外から見た振る舞い（CLI の契約と、信頼の境界の確かめ）を変えない。
-   テストが確かめる範囲を狭めない。

### 2.2. スコープ (In Scope)

-   `internal/fixprguard` の製品コードを、作業ツリーのディレクトリを呼び出し元から受け取る形に変えること（F-002）。
-   `cmd/fixprguard` の製品コードを、上の形に合わせて変えること。CLI としての振る舞いは変えない（F-002）。
-   2 つのパッケージのテストとテストの補助（`test_helpers*.go`）を、`t.Chdir` と `t.Setenv` を使わずに `t.Parallel()` で動く形に書き直すこと。テストの補助が子のコマンドに渡す環境も、プロセスの環境変数を変えずにテストごとの `HOME` を持つ形にする（F-001）。
-   テストのリポジトリを作るフィクスチャの git の起動の回数を減らすこと（F-003）。
-   変更の前後の実行時間の計測と記録（F-004）、検証範囲を保ったことの確かめ（F-005）。

### 2.3. スコープ外 (Out of Scope)

-   **ほかのパッケージのテストの高速化:** `internal/mergepr`・`internal/chief` などの遅いテストは扱わない。issue #1167 が対象にしているのは fixprguard の 2 つのパッケージだけである。
-   **`make test`・CI の設定の変更:** `-race` を外すこと、パッケージを分割すること、テストの対象を絞ることはしない。テストの実行のしかたを変えずに、テストそのものを速くするのが issue の方針だからである。
-   **fixprguard の CLI の契約とプロトコル番号の変更:** §1 の「要件定義の際に決めたこと」のとおり変えない。
-   **[fixprguard_guide.md](../../dev/guides/fixprguard_guide.md) の変更:** CLI の振る舞いが変わらないので、利用者向けの説明も変わらない（AC-09）。
-   **`internal/cmdrunner` の振る舞いの変更:** `cmdrunner.Options` は作業ディレクトリ（`Dir`）と環境（`Env`）をすでに受け取れる（`internal/cmdrunner/runner.go:35-62`）。このタスクはそれを使う側を変えるだけで、`cmdrunner` の振る舞いは変えない。
-   **後のタスクへの規則:** このタスクの後に足すテストに `t.Parallel()` を義務づける規則や linter は置かない。AC-01 は、このタスクを終えた時点のテストに対して確かめる。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: テストの並列実行

2 つのパッケージのテストを、直列のまま残してよいテスト（AC-03）を除いて、並列に実行する。

**Acceptance Criteria**:
- **AC-01**: `internal/fixprguard` と `cmd/fixprguard` の `_test.go` にあるすべてのテスト関数（`func TestXxx(t *testing.T)`）とすべてのサブテスト（`t.Run` に渡す関数）は、AC-03 の一覧にあるものを除き、`t.Parallel()` を呼ぶ。
- **AC-02**: `go test -tags test -race -count=3 ./internal/fixprguard ./cmd/fixprguard` が、データ競合の報告も失敗もなく通る。
- **AC-03**: `t.Parallel()` を呼ばないテストとサブテストは、次のどちらかに当たるものだけである。設計書は、それらを（パッケージ, テストの名前）の組で 1 つずつ、理由とともに一覧に記録している。一覧にないテストは、すべて `t.Parallel()` を呼ぶ。
    - プロセス全体の状態（引き継いだ環境変数、`PATH` からのコマンドの探索、本物のプロセスの作業ディレクトリ）そのものを確かめるテストと、その下のサブテスト。
    - 並列の親の下で 1 つのフィクスチャを順に使うサブテスト。
- **AC-04**: AC-03 の一覧にないテストとテストの補助は、`t.Chdir`・`t.Setenv`・`os.Chdir`・`os.Setenv`・`os.Unsetenv` を呼ばない。AC-07 の確かめのために、パッケージのテストを始める前に一度だけプロセスの作業ディレクトリを変えることは、設計書がその場所と理由を記録している場合に限って認める。
- **AC-05**: テストの補助は、プロセスの環境変数を変えずに、テストごとの `HOME` と `XDG_CONFIG_HOME` を、製品の runner と準備の git の両方に渡す。開発者の大域の git の設定（署名・フック・除外のファイル）は、テストの結果に届かない。

#### F-002: 作業ツリーのディレクトリの受け渡し

`internal/fixprguard` の、作業ツリーを読み書きする操作と git を起動する操作は、作業ツリーのディレクトリを呼び出し元から受け取る。CLI は、その値をプロセスの作業ディレクトリから作り、外から見た振る舞いを変えない。

**Acceptance Criteria**:
- **AC-06**: `internal/fixprguard` の操作に作業ツリーのディレクトリを渡すと、プロセスの作業ディレクトリが別の場所（別のリポジトリ、または `.git` のないディレクトリ）であっても、渡したディレクトリの作業ツリーに対して動く。読むファイル、書くファイル、起動する git の対象は、渡した作業ツリーのものである。
- **AC-07**: テストの中で動く fixprguard の操作とその子の git が、渡したディレクトリを使わずにプロセスの作業ディレクトリに頼っても、パッケージを含むリポジトリ（このリポジトリ自身）とその `origin` には届かない。作業ディレクトリへの依存を製品にわざと 1 か所入れ直すとテストが失敗することを一度確かめ、その結果を PR の説明に記録する。文書のガードテスト（`cmd/fixprguard/docs_test.go`）と `testdata/` を読むテストが、このリポジトリのファイルを読むことは、この AC の対象外である。
- **AC-08**: `fixprguard` の CLI は、変更の前と同じく、プロセスの作業ディレクトリを作業ツリーとし、プロセスから引き継いだ環境変数から `GIT_*` を除いた環境で子のコマンドを起動する。次のことを、CLI の入口（`run`）を本物のプロセスの作業ディレクトリで動かすテストが確かめる。それらのテストの期待値（終了コード・出力・番兵）の、マージベースに対する差分は空である。
    - [fixprguard_guide.md](../../dev/guides/fixprguard_guide.md) の「作業ディレクトリ」の行の条件のすべて。最上位でないときの `begin` の終了コード `2` と `inspect`・`finish`・`push` の `git-state-changed`（`config`）、`.git` がないときに `check`・`push-review` が git を起動せずに終了コード `2` で止まること、`.git` の形が誤っているときの `git-state-changed`（`config`）、detached HEAD での `begin` の終了コード `2` である。
    - 作業ツリーの最上位から動かしたときに、サブコマンドが今と同じ結果を返すこと。
    - 継承した `GIT_DIR` が子のコマンドに届かないこと。
- **AC-09**: マージベースに対する `docs/dev/guides/fixprguard_guide.md` の差分は空である。`internal/fixprguard` の `const Protocol = <整数>` の行の差分も空である。

#### F-003: フィクスチャの軽量化

テストのリポジトリを作るフィクスチャが起動する git の回数を減らす。作られるリポジトリの状態は変えない。

**Acceptance Criteria**:
- **AC-10**: `internal/fixprguard` と `cmd/fixprguard` のそれぞれで、テストが 1 つのリポジトリを受け取るまでに起動する git のプロセスの数が、変更の前より少ない。ひな形を 1 回だけ作る手段を採るときは、ひな形を作る回数をこの数に含めず、別に数える。前後の数は PR の説明に記録されている。
- **AC-11**: それぞれのパッケージで、変更の前のフィクスチャが作るリポジトリ（作業ツリー、bare リポジトリ、`HOME`）と、変更の後のフィクスチャが作るものとの差分は、テストごとに変わる値に限られる。テストごとに変わる値とは、一時ディレクトリの絶対パスとそれを含む設定の値（`remote.origin.url`・`core.excludesFile` など）、コミットの時刻とそれで決まるオブジェクトの ID、インデックスが持つファイルの stat の情報である。あるテストがリポジトリを変えても、ほかのテストのリポジトリは変わらない。

#### F-004: 実行時間の短縮

**Acceptance Criteria**:
- **AC-12**: 同じ機械で、変更の前（このタスクの最初の実装 PR のマージベース）と後（タスクを終える PR の先頭）のそれぞれについて、`go test -tags test -race -count=1 ./internal/fixprguard` と `go test -tags test -race -count=1 ./cmd/fixprguard` を 1 つずつ別に、前と後でそれぞれ 3 回実行する。`go test` が報告するパッケージの時間の 3 回の中央値は、2 つのパッケージのそれぞれで、前の中央値の 50% 以下である。
- **AC-13**: AC-12 の計測は、機械（OS と CPU のコア数、`GOMAXPROCS`）、Go の版、前後のコミット、パッケージごとの時間とともに、PR の説明に記録されている。3 回を超えて計測を繰り返したときは、目標に届かなかった回も含めてすべての回を記録し、判定に使った 3 回を示す。計測と判定は、タスクを終える PR で行う。目標に届かないときは、PR を開く前に止め、結果を人に示して判断を求める。

#### F-005: 検証範囲の維持

**Acceptance Criteria**:
- **AC-14**: テストを書き直す実装の PR では、製品のコードを変えるコミットが、テストだけを変えるコミットより前にある。製品のコードとは、`internal/fixprguard` と `cmd/fixprguard` の Go のファイルのうち、`make coverage-compare` が製品のコードと分類するもの（`internal/coveragecompare/product.go`）である。製品を変えるコミットは、コンパイルを通すためにテストとテストの補助を一緒に変えてよい。その PR で製品のコードを最後に変えたコミット（その PR が製品を変えないときはマージベース）を `BASE` にした `make coverage-compare BASE=<そのコミット>` が、最後の行に `coverage-compare: PASS` を出して終わる。`FAIL` か `STOP` で終わったときは、原因を直して比べ直すか、止めて人に尋ねる。すべての回の出力が、最後の行まで PR の説明に記録されている。
- **AC-15**: 実装の PR ごとに、マージベースで `internal/fixprguard` と `cmd/fixprguard` のテストが報告する（パッケージ, テストの名前）の組（`go test -json` の `Package` と `Test` の値。サブテストを含む）は、PR の先頭でもすべて報告される。ただし、`CLAUDE.md`「Testing Strategy」の削除の規則に従って削除したテストを除く。PR の先頭で新しく現れた組は、その理由とともに PR の説明に記録されている。
- **AC-16**: 実装の PR ごとに、期待値（比べる値・番兵・終了コード・出力）を変えたテストは、変えた理由とともに PR の説明に記録されている。製品を変えるコミット（AC-14）でのテストとテストの補助の差分は、製品の呼び出しの引数と、テストの準備の変更に限られる。どちらも、PR のレビューで差分を読んで確かめる。
- **AC-17**: 実装の PR ごとに、`make test` と `make lint` が通る。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   F-004 のとおり、2 つのパッケージのテストの時間を、それぞれ変更の前の 50% 以下にする。製品の実行時間は目標にしない。CLI の実行時間は git と gh の呼び出しで決まり、このタスクの変更で意味のある差は生じないためである（`CLAUDE.md`「Performance」）。

### 4.2. セキュリティ (Security)
-   [security.md](../../dev/security.md) の条件付きの指針は当てはまらない（N/A）。このタスクは `yt-dlp` を起動せず、API キーもキャッシュのディレクトリも扱わず、LLM の API にも送らず、信頼できないテキストをプロンプトや記事に埋め込まないためである。
-   新しく受け取る信頼できない入力はない（N/A）。fixprguard が読む外部の入力（`gh` と `git` の出力、レビューのスレッド）の扱いは変えないためである。
-   fixprguard は、レビューのスレッドを信頼しないための境界を守るツールである（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）。このタスクは、その境界の確かめ（作成者の判定、範囲の規則、git の状態の確かめ、`GIT_*` を除いた子のコマンドの環境）の振る舞いを変えない（AC-08）。
-   今は `t.Chdir` があるので、テストの中の fixprguard がこのリポジトリ自身を対象にすることはない。作業ディレクトリに頼らない形に変えたとき、渡したディレクトリを使わない箇所が残っていると、テストが開発者のこのリポジトリを読み書きし、その `origin` に push するおそれがある。AC-07 はこれを防ぐ。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   並列のテストは、互いのリポジトリ・`HOME`・一時ファイルを共有しない（AC-11）。1 つのテストの失敗や変更が、ほかのテストの結果に影響しない。
-   並列のテストの中で動く fixprguard の操作が、プロセスの作業ディレクトリ（パッケージのディレクトリ）にある本物のリポジトリを読んだり書いたりしない（AC-06、AC-07）。文書のガードテストと `testdata/` の読み込みは対象外である。

### 4.4. 互換性 (Compatibility)
-   macOS（大文字と小文字を区別しないボリュームを含む）と Linux の CI の両方で通る。今のフィクスチャが固定している無視の規則と名前の比較（`internal/fixprguard/test_helpers_git.go:157-169`）は保つ（AC-11）。

### 4.5. 保守性 (Maintainability)
-   このタスクの後でテストを書く人が、新しいテストを `t.Parallel()` で書けるようにする。テストの補助は、`t.Chdir`・`t.Setenv` を使わずにリポジトリと `HOME` を用意できる（AC-04、AC-05）。それを義務づける規則は置かない（2.3）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   開発ツールの引数・出力・終了コードは契約として保つ（[dev_tools.md](../../dev/conventions/dev_tools.md)）。
-   エージェントは fixprguard をインストールもビルドもしない（`CLAUDE.md`「Tool Execution Safety」）。テストと lint のためのパッケージのコンパイルは、ビルドに当たらない。
-   テストを削除するときは、削除だけのコミットでカバレッジを比べる（`CLAUDE.md`「Testing Strategy」、[ADR-0037](../../dev/adr/0037-test-deletion-coverage.md)）。

## 6. 用語集 (Glossary)

-   **作業ツリー:** git のリポジトリのファイルを置く最上位のディレクトリ。fixprguard が確かめて commit と push をする対象である。
-   **作業ディレクトリ:** プロセスのカレントディレクトリ。今の CLI は、作業ディレクトリが作業ツリーの最上位であることを前提にしている。
-   **フィクスチャ:** テストのために用意する、作業ツリーとローカルの bare リポジトリ（`origin`）の組。今は `newTestRepo` が作る。
-   **直列のまま残すテスト:** `t.Parallel()` を呼ばないテスト。AC-03 の条件に当たるものだけである。
-   (用語は `docs/translation_glossary.md` と統一する)
