# 設計への申し送り：0126 fixprguard のテストの並列化と git フィクスチャの軽量化

要件定義（[01_requirements.md](01_requirements.md)）の段階で挙がった、設計（`02_architecture.md`）で決める事項である。設計書は、各項目について採った方法か、当てはまらない理由を記録する。

## H-01: 作業ツリーのディレクトリを受け渡す API の形

**懸念:** 今の `internal/fixprguard` は、作業ディレクトリを作業ツリーの最上位とみなし、`.git`・無視されたファイル・見張る最上位のディレクトリを相対パスで読む（`internal/fixprguard/gitstate.go:182-204`、`internal/fixprguard/ignored.go:410-433`、`internal/fixprguard/worktree.go:48-49`）。git の子プロセスも、`cmdrunner.Options.Dir` を空にして作業ディレクトリで動かしている。
**重要な理由:** 渡したディレクトリを使わない箇所が 1 つでも残ると、並列のテストはパッケージのディレクトリ（このリポジトリ自身）を読む。結果が誤るか、このリポジトリを書き換え、その `origin` に push するおそれがある（AC-06、AC-07）。
**候補:** `Worktree` などの入口に作業ツリーのディレクトリを持たせ、ファイルの操作はすべてそこからの絶対パスで行い、git の runner には `Dir` を渡す。漏れがないことを確かめる方法も合わせて決める。例は、`TestMain` でプロセスの作業ディレクトリを `.git` のないディレクトリに一度だけ変えて、全テストを走らせることである。AC-04 は、設計書が場所と理由を記録すればこれを認める。そのディレクトリは、どの git リポジトリの下にも置かない。git が親のリポジトリを見つけてしまうためである。確かめ方として、作業ディレクトリへの依存をわざと入れ直してテストが失敗することを一度だけ確かめる手順も決める（AC-07）。作業ディレクトリを変えると、パッケージのディレクトリからの相対パスで読むテスト（`cmd/fixprguard/docs_test.go` の `repoRoot = "../.."`、`internal/fixprguard/review_state_test.go` の `testdata/`）が読めなくなるので、その扱いも決める。

あわせて、Go の `os/exec` は `Cmd.Env` が nil のときだけ子の `PWD` を `Cmd.Dir` に合わせる。fixprguard の runner は `Env` を必ず渡すので、`Dir` を設定しても、子は親の古い `PWD`（テストではこのリポジトリの中のパッケージのディレクトリ）を引き継ぐ。git やその子が `PWD` を読む場合の扱いを決める。
**関連:** F-002、AC-06、AC-07

## H-02: 最上位の確かめと相対パスの意味を保つ方法

**懸念:** 今の CLI は、作業ディレクトリが最上位でないと止まる（[fixprguard_guide.md](../../dev/guides/fixprguard_guide.md) の「作業ディレクトリ」の行）。この確かめは、git を起動せずに、作業ディレクトリにある `.git`（ディレクトリか、リンクされた作業ツリーを指すファイル）をファイルだけで調べて行っている（`internal/fixprguard/gitstate.go:182-204`）。ディレクトリを外から渡す形にすると、CLI が渡す値（`"."` か `os.Getwd()` の結果か）によって、調べ方の意味が変わりうる。たとえば、`.git` のファイルが相対パスで指す先の解き方である。記録のファイル（`internal/fixprguard/gitstate.go:614` など）の置き場所も同じである。
**重要な理由:** 調べ方が変わると、最上位でない場所で動いてしまったり、今は通る場所で止まったりする（AC-08）。fixprguard は信頼の境界を守るツールなので、確かめが緩むことは許されない。
**候補:** CLI が渡す値と、内部での調べ方を設計で決める。最上位でない場合、`.git` がない場合、リンクされた作業ツリーの場合の振る舞いを、既存のテストで保つ。
**関連:** F-002、AC-08

## H-03: テストの補助が子のコマンドに渡す環境と `HOME` の分離

**懸念:** 製品の `internal/fixprguard` はプロセスの環境変数を読まず、子のコマンドの環境は runner の `cmdrunner.Options.Env` で決まる。これはテストの補助だけの変更である。テストの補助は、runner と準備の git の環境を `os.Environ()` から作り（`internal/fixprguard/test_helpers_git.go:182,196,261-262`、`cmd/fixprguard/test_helpers.go`）、`t.Setenv("HOME")` と `t.Setenv("XDG_CONFIG_HOME")` で利用者の git の設定（署名・フック）を遮っている（`internal/fixprguard/test_helpers_git.go:136-137`）。`cmd/fixprguard` の CLI のテストは、`run` に渡す `env` の runner と `lookupEnv` も同じように作る必要がある。`cmdrunner.GitEnv` は `GIT_*` を除くので、`GIT_CONFIG_GLOBAL` で遮ることはできない（`internal/cmdrunner/git.go:32-45`）。
**重要な理由:** 子のコマンドに渡す環境から `HOME` が漏れると、開発者の大域の設定がテストに届き、機械によって結果が変わる（AC-05、AC-11）。
**候補:** テストの補助が、`cmdrunner.GitEnv` の結果の `HOME`・`XDG_CONFIG_HOME` をテストごとのディレクトリに差し替えた環境を作り、製品の runner・テストの準備の git・fake の外のコマンド（`make`・`gh`）のすべてに渡す。CLI の側は今の `osEnv`（`cmd/fixprguard/main.go:172-190`）を保つ。
**関連:** F-001、AC-05

## H-04: フィクスチャを速くする手段

**懸念:** issue は、ひな形のリポジトリを 1 回だけ作ってコピーする方法と、`git config` を `.git/config` への直接の書き込みに置き換える方法を挙げている。コピーでは、bare リポジトリの場所を指す `remote.origin.url` と、`core.excludesFile` の絶対パスを、コピー先に合わせて直す必要がある。直接の書き込みでは、git が書くときと同じ形の設定ファイルになることを保つ必要がある。作業ツリーをコピーすると、インデックスが持つファイルの stat の情報（mtime・inode）がコピー先と合わなくなり、git の変更の検出（racy git の扱いを含む）の振る舞いが変わりうる。
**重要な理由:** 状態が今と違うフィクスチャでは、既存のテストが確かめる前提が崩れる（AC-11）。コピーのひな形をテストの間で共有すると、1 つのテストの変更がほかのテストに漏れるおそれもある。
**候補:** 2 つの方法を計測して比べ、片方か両方を選ぶ。ひな形は `sync.Once` などで 1 回だけ作り、テストはコピーだけを変える。コピーした状態が今のフィクスチャと同じであることを確かめるテストを置く。AC-10 の git のプロセスの数の数え方も決める。`cmdrunner.GitEnv` は `GIT_*` を除くので、`GIT_TRACE` は子の git に届かない（`internal/cmdrunner/git.go:36-45`）。`PATH` に置く数える wrapper か、テストの補助が記録する呼び出しで数える。フィクスチャの変更は、テストだけの最適化として、振る舞いの変更とは別のコミットにする（`CLAUDE.md`「Performance」）。
**関連:** F-003、AC-10、AC-11

## H-05: 直列のまま残すテストの一覧

**懸念:** プロセスの状態そのものを確かめるテストがある。継承した `GIT_DIR` が除かれること（`internal/fixprguard/gitstate_test.go:457`、`cmd/fixprguard/main_test.go:276-277,298-299`）、`PATH` の上の偽のコマンド、作業ディレクトリが `.git` のないディレクトリのときの振る舞い（`cmd/fixprguard/main_test.go:180,381,971,1129,1549`、`internal/fixprguard/ignored_test.go:379,470,652,662,697,729,824,863,877,929,1386`、`internal/fixprguard/review_test.go:239,257,430`、`internal/fixprguard/gitstate_test.go:249`）である。gh の対象を決める環境変数を `t.Setenv` で変えるサブテスト（`cmd/fixprguard/main_test.go:254`）もある。後者の多くは、H-01 の後はディレクトリを渡す形で書けるかもしれない。
**重要な理由:** 例外を広く取ると並列化の効果が下がる。狭く取りすぎると、プロセスの状態を確かめるテストが確かめる対象を失う（AC-01、AC-03）。
**候補:** 1 つずつ、確かめる対象がプロセスの状態そのものかを判断し、一覧と理由を、（パッケージ, テストの名前）の組で設計書に書く。順に動くサブテスト（AC-03 の 2 つ目）も同じ一覧に入れる。CLI の `run` の入口のテストのうち、作業ディレクトリでの振る舞いを確かめるものは、CLI がプロセスの作業ディレクトリを読む 1 か所を確かめるのに必要な数だけ残す。
**関連:** F-001、AC-03

## H-06: 並列のテストで共有される状態

**懸念:** テストの補助には、呼び出しを記録する `gitRouter.Calls` や、`Before` のフックなど、変更できる状態がある（`internal/fixprguard/test_helpers_git.go:34-79`）。パッケージ変数で持つ設定や、テストの表の中で共有される値があると、並列にしたときにデータ競合になる。
**重要な理由:** 競合は `-race` で見つかることもあるが、実行の順序によっては見つからない（AC-02）。
**候補:** パッケージ変数とテストの間で共有される値を洗い出し、テストごとに作る形にする。AC-02 の `-count=3` に加えて、`-cpu` の値を変えた実行も検討する。
**関連:** F-001、AC-02

## H-07: 計測とテストの名前の比べ方、コミットの順序

**懸念:** AC-12 の時間は、機械の負荷で揺れる。AC-15 のテストの名前の組は、`go test -json` の出力から取り出す手順を決める必要がある。AC-14 は、テストを書き直す PR の中で、製品を変えるコミットをテストだけを変えるコミットより前に置くことを求めるので、その順序を実装計画書の PR の区切りに反映する必要がある。また、`make coverage-compare` には、`cmdrunner` の `signalGroup` で時間に依存して `FAIL` になる既知の揺れがある。
**重要な理由:** 手順が決まっていないと、前後の比べ方が実装の PR ごとに違ってしまう（AC-12、AC-15）。
**候補:** 計測と名前の取り出しの手順を、実装計画書に固定のコマンドとして書く。coverage-compare の揺れには、きれいな作業ツリーで比べ直し、すべての回を記録する手順を書く。一時的なスクリプトにする場合は、[requirements_process.md](../../dev/conventions/requirements_process.md) の「Temporary scripts (`_checks/`)」に従い、変更の大きさに見合った範囲にとどめる。
**関連:** F-004、F-005、AC-12、AC-13、AC-14、AC-15
