## 1. 概要 (Overview)

**目的:** 本書は、chief（[0088 要件定義書](../0088_chief_of_staff/01_requirements.md)）の状況の表に加える 3 つの表示の要件を定義する。1 つ目は行ごとの急ぎの度合いの印、2 つ目はタスクの段階と、次に動くのが人か AI か、3 つ目は「質問で停止」の行の「次」の列に書く中身である。人が表を一目見て、何から手を付ければよいかを分かるようにする。

**背景:**

chief の状況の表は、workspace ごとに状態を示す。chief の今の振る舞いは次のとおりである。

-   道具 `chief` は、行ごとに 6 つの状態（要確認、質問で停止、実行中、レビュー待ち、次を提案、タスク完了）のどれか 1 つを返す（`internal/chief/state.go:382-440`、0088 要件定義書の F-001）。どの行に人がすぐ答えるべきかは、状態の名前を読まないと分からない。
-   送信の停止は状態ではない。どの状態の行にも付く印 `stopped` である（`internal/chief/snapshot.go:179-188`）。`/runpr` のマージの確認は、「質問で停止」の一種として `merge_question` で示す（0088 要件定義書の AC-02・AC-11）。
-   行は、使っていないか残った worktree の行を最後に置く。それ以外の行は、質問で停止 → レビュー待ち → 次を提案 → 要確認 → 実行中 → タスク完了 の順に並ぶ（`internal/chief/state.go:58`、`internal/chief/snapshot.go:335-354`、0088 要件定義書の AC-03）。送信が止まった行は、使っていない worktree の行には当たらない（`internal/chief/snapshot.go:185-188`）。
-   道具は、次のコマンドを `origin/main` の要件定義書・設計書・計画書から決める（`internal/chief/state.go:269-342`）。ただし、タスクがどの文書の段階にあるかは出力に含まない（`internal/chief/output.go:27-40`）。
-   「実行中」の行に示すコマンドとモデルは、chief の送信の記録からだけ決める（`internal/chief/snapshot.go:199-214`）。Claude Code の transcript からは、人が最後に入力したコマンドを読むことができる（`internal/chief/screen_transcript.go:160-170`）。ただし、それを使うのは pane のリセットの候補を狭めるときだけである（[ADR-0046](../../dev/adr/0046-chief-of-staff.md) の決定）。
-   `/chief` の定義は、「質問で停止」の行の「次」の列に `merge_question` だけを書くと定めている（`.claude/commands/chief.md:130-131`）。質問の要点と pane は表の下に書く（`.claude/commands/chief.md:140`、0088 要件定義書の AC-05）。0088 の PR-7 の実地の確かめでは、セッションが `merge_question: false` を言葉にして、「/runpr のマージ確認ではありません」と書いた（issue #890）。
-   `/chief` の定義は、状態や次のコマンドを道具が決め、セッションは決めないと定めている（`.claude/commands/chief.md:8-14`、ADR-0046 の決定）。

対応 issue: [#890](https://github.com/isseis/yt2column/issues/890)（親: [#836](https://github.com/isseis/yt2column/issues/836)、関連: タスク 0088、タスク [0092](../0092_chief_task_workspace/01_requirements.md)（[#839](https://github.com/isseis/yt2column/issues/839)））

**本書の記述範囲:** 本書は、表の各行に何を示し、行をどう並べるかという観測できる振る舞いを定める。次の事項は設計（`02_architecture.md`）で決める。

-   道具の出力の形（項目の名前、値の綴り）と、`--protocol` の番号の扱い
-   送信の記録と transcript の両方から実行中のコマンドが読めるときの扱い
-   端末で表の列をそろえる方法
-   テストの手段

要件の段階で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #890 で決めたこと:**

-   **表の各行に、急ぎの度合いを「すぐ」「あとで」「待つ」の 3 つに分けた印を付ける（F-001）。** 人が表を一目見て、どの行から手を付ければよいか分かるようにするためである。Herdr が workspace の名前の左に出す状態の色に近い役割を持たせる。ADR: [ADR-0046](../../dev/adr/0046-chief-of-staff.md) を更新する（下の「要件定義の際に決めたこと」の、道具が決める項にまとめる）。
-   **「すぐ」は、AI が人の答えを待って止まり、答えないと進まない行（質問で停止、マージの確認待ち、送信の停止）とする。「あとで」は、少し時間のかかる人の対応が要る行（レビュー待ち、次を提案）とする。「待つ」は、AI が作業中か終わっていて、人はとりあえず待てばよい行（実行中、タスク完了）とする（F-001）。** 答えないと進まないものを、時間をかけて読むものより先に示すためである。ADR: なし（印の対応は表示の細部で、下の道具が決める項の範囲に収まるため）。
-   **各行に、タスクの段階（文書 × 進み具合）と、次に動くのが人か AI か（番）を示す。番は段階から決める（F-002・F-003）。** タスクがどこまで進み、誰を待っているかを、状態の名前から推し量らずに分かるようにするためである。ADR: ADR-0046 を更新する。
-   **文書は `origin/main` の文書から決める。動いているコマンドは、chief の送信の記録か transcript からだけ決め、画面からは決めない（F-003）。** 0088 の画面の読み取りの範囲を広げないためである。ADR: ADR-0046 を更新する（transcript を表示にも使うため）。
-   **「質問で停止」の行の「次」の列には、質問の要点と pane を書く（F-005）。** `merge_question: false` をそのまま言葉にした文は、人にとって意味がないためである。ADR: なし（`/chief` の表示の細部のため）。

**要件定義の際に決めたこと（2026-11-16）:**

-   **進め方は通常の進め方にする。対象外の判断は「対象外ではない」で、上書きはない。** 対象外ではない理由は 3 つある。送る入力の範囲も、開発用ツールの信頼の境界も変えないこと。`docs/dev/security.md` の規則と前提を変えないこと。外部の依存を足さないこと（[requirements_process.md](../../dev/conventions/requirements_process.md) の「Simple Process」の「Excluded changes」）。それでも通常の進め方にするのは、次のためである。変更が道具の出力、`/chief` の定義、chief 利用ガイドの 3 か所に及ぶ。決める点が多い。段階を求める仕組みは新しく、0092 の削除の提案とも重なる。ADR: なし（進め方の選択はこのタスクの中で閉じるため）。
-   **「要確認」の行は「あとで」に置く（AC-04）。** 多くは、chief 以外のエージェントが長い出力を書いている途中など、chief が画面を読めないだけのためである（issue #890 の勧め）。本当に止まっている場合を見落とさないよう「すぐ」に置く案は採らない。読めないだけの行でも人をすぐに呼ぶことになるためである。ADR: なし（印の対応の細部のため）。
-   **印は、色の付いた絵文字（🔴・🟡・🟢）に「すぐ」「あとで」「待つ」の文字を添えた形にする（AC-01）。** Herdr の状態の色に近く、一目で分かるためである。文字を添えるのは、色だけで状態を伝えないためである。形の違う記号（●・▲・○）の案は採らない。色がなく、Herdr の状態の色と結び付きにくいためである。絵文字の幅で表の列がずれうることは、設計で扱う（design_handoff.md の H-03）。ADR: なし（表示の細部のため）。
-   **急ぎの度合い、番、段階は、どれも道具 `chief` が決めて出力に含める。`/chief` のセッションは、道具の値をそのまま示し、自分では決めない（F-006）。** ADR-0046 の「道具が決め、セッションは決めない」に合い、Go のテストで確かめられるためである。印は今の状態から定義の中で付け、段階だけを道具で決める案は採らない。判定の一部がセッションに残るためである。ADR: ADR-0046 を更新する。
-   **表の行は、急ぎの度合いの順（すぐ → あとで → 待つ）に並べる。同じ度合いの中は今の順に並べ、使っていないか残った worktree の行は今と同じく最後に並べる（F-004）。** 今の並びはほぼこの順なので、変わるのは、送信が止まった行と、0092 の削除の提案がある「タスク完了」の行の位置だけである。印だけを足して並びを変えない案は採らない。「すぐ」の行が「あとで」の行より下に来うるためである。ADR: なし（並べ方の細部のため）。
-   **印と番と段階は、3.1 の対応表のとおりにする（F-001〜F-003）。** 主な取り決めは次のとおりである。
    -   送信が止まった行は、状態によらず「すぐ」・人とする。
    -   使っていないか残った worktree の行は「待つ」・なしとする。人が対応しなくても困らない行だからである。
    -   0092 の削除の提案がある「タスク完了」の行は「あとで」・人とする。
    -   実行中のコマンドが記録から決まらないときは、推し量らずに進み具合を「実行中」とする。
    -   番は独立した列として示す。issue のとおりにするためである。番を印に含め、列を足さない案は採らない。
    -   ADR: ADR-0046 を更新する。
-   **簡易な進め方の 3 文書の PR の文書も「要件定義書」と示す（AC-07）。** 3 文書の PR がマージされる前は、`origin/main` に進め方の記録がなく、道具は簡易な進め方かどうかを `origin/main` から読めないためである。ADR: なし（段階の表示の細部のため）。
-   **「質問で停止」の行の質問の要点と pane は、「次」の列にだけ書き、表の下の同じ一覧は外す。これは 0088 要件定義書の AC-05 を置き換える（F-005）。** 同じものを 2 回書かないためである。質問の全文と選択肢は、人がその質問を選んだときに、今までどおり示す（0088 要件定義書の AC-25）。表の下にも残す案は採らない。ADR: なし（表示の細部のため）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   人が状況の表を一目見て、すぐ答えるべき行と、あとで対応する行と、待てばよい行を見分けられるようにする。
-   タスクがどの文書の段階にあり、次に動くのが人か AI かを、状態の名前から推し量らずに分かるようにする。
-   判定を道具に置いたままにし、chief のセッションが自分で判断しないという決まり（ADR-0046）を保つ。

### 2.2. スコープ (In Scope)

-   急ぎの度合いの印（F-001）
-   番（F-002）
-   タスクの段階（F-003）
-   表の並べ方（F-004）
-   「質問で停止」の行の「次」の列（F-005）
-   道具が決めて出力に含め、`/chief` の定義がそれを示すこと（F-006）
-   ADR-0046 の更新、`/chief` の定義（`.claude/commands/chief.md`）の更新、chief 利用ガイド（`docs/dev/guides/chief_guide.md`）の更新（5 章）

### 2.3. スコープ外 (Out of Scope)

-   Herdr の状態の色そのものを chief から変えること（issue #890 の範囲の外）。
-   macOS の通知の出し方。今は `PushNotification` の端末への通知が、Herdr のベルと状態の色として届く（issue #890 の範囲の外）。
-   人の判断を待つものの一覧（選択肢）の並べ方。0088 要件定義書の AC-13 のまま変えない。issue は表の並べ方だけを決めることとして挙げているためである。
-   画面から動いているコマンドを読むこと（issue #890 で決めたこと）。
-   「実行中」の行の「次」の列に示すコマンドとモデル（0088 要件定義書の AC-02）の決め方を変えること。今までどおり送信の記録から決める。issue は段階の表示だけを求めているためである。
-   0092 の削除の提案そのもの。本書は、0092 が実装された後に、その行に付ける印と番だけを定める。

## 3. 機能要件 (Functional Requirements)

本書の用語は 0088 要件定義書の 3 章（タスクの workspace、エージェント、入力を受け付ける状態）に従う。加えて、本書では次の用語を使う。

-   **状態**: 0088 要件定義書の F-001 の 6 つの状態（要確認、質問で停止、実行中、レビュー待ち、次を提案、タスク完了）。
-   **送信が止まった行**: 0088 で、送れたかが分からない送信のために、人が解除するまで送信を止めた workspace の行（`stopped`）。
-   **使っていない worktree の行**: 0088 要件定義書の AC-03 で、表のほかのすべての行の後に並べる行。
-   **削除の提案**: 0092 要件定義書の F-005・F-006 の、chief が作った workspace のうちタスクが完了したものに示す提案。
-   **実行中のコマンド**: 実行中のエージェントが走らせているコマンド。AC-11 の記録から決まるものだけをいう。

### 3.1. 機能一覧

#### 対応表

道具は、行ごとに次の表を上から順に当てはめ、最初に当たる行の印と番を決める。

| 行の条件 | 急ぎの度合い | 番 |
|---|---|---|
| 送信が止まった行 | 🔴 すぐ | 人 |
| 質問で停止（マージの確認を含む） | 🔴 すぐ | 人 |
| 使っていない worktree の行 | 🟢 待つ | なし |
| レビュー待ち、次を提案、要確認 | 🟡 あとで | 人 |
| タスク完了で、削除の提案があるもの | 🟡 あとで | 人 |
| 実行中 | 🟢 待つ | AI |
| タスク完了（削除の提案がないもの） | 🟢 待つ | なし |

#### F-001: 急ぎの度合いの印

**Acceptance Criteria**:
-   **AC-01**: 状況の表の各行は、急ぎの度合いの印をちょうど 1 つ持つ。印は「🔴 すぐ」「🟡 あとで」「🟢 待つ」のどれかで、絵文字と文字の両方を示す。
-   **AC-02**: 各行の急ぎの度合いは、対応表を上から順に当てはめて最初に当たる行のものである。対応表のどれにも当たらない行はない。
-   **AC-03**: 送信が止まった行は、状態が何であっても「🔴 すぐ」である。
-   **AC-04**: 「要確認」の行は、使っていない worktree の行を除き、「🟡 あとで」である。読めなかった理由から、別の度合いを推し量らない。
-   **AC-05**: 0092 の削除の提案がある「タスク完了」の行は「🟡 あとで」である。削除の提案がまだ実装されていないうちは、「タスク完了」の行はすべて「🟢 待つ」である。

#### F-002: 番

**Acceptance Criteria**:
-   **AC-06**: 状況の表の各行は、番を「人」「AI」「なし」のどれか 1 つで示す。値は、AC-02 で当たった対応表の行のものである。

#### F-003: タスクの段階

各行は、段階を「文書」と「進み具合」の組で示す。

**Acceptance Criteria**:
-   **AC-07**: 文書は、chief が次のコマンドを決めるときと同じ `origin/main` の文書から、次のように決める。
    -   タスクがあり、`origin/main` に要件定義書がない: 「要件定義書」（簡易な進め方の 3 文書の PR も同じ）
    -   要件定義書があり、設計書がない: 「設計書」
    -   設計書があり、計画書がない: 「計画書」
    -   計画書があり、タスクが完了していない: 「PR-N」。N は、計画書の PR マーカーのうち、PR がまだマージされていない最初のものの番号である。PR マーカーのない計画書は、PR が 1 つなので「PR-1」とする
    -   タスクが完了している: 「なし」
    -   タスクがなく、次のコマンドが `/mkreq` か、実行中のコマンドが `/mkreq`: 「要件定義書」
    -   タスクがなく、上に当たらない: 「-」
-   **AC-08**: 文書を決めるのに要る `origin/main` の文書か計画書の欄を読めないときは、文書を「要確認」と示す。読めなかったものから、ほかの文書を推し量らない。行の状態は、0088 要件定義書の F-001 で決まったまま変えない。
-   **AC-09**: 進み具合は、行の状態と実行中のコマンドから、次のように決める。
    -   次を提案: 「作成待ち」
    -   実行中で、実行中のコマンドが `/mkreq`・`/mkarch`・`/mkplan`・`/runplan`: 「作成中」
    -   実行中で、実行中のコマンドが `/runpr`: 「`/runpr` 実行中」
    -   実行中で、実行中のコマンドが決まらない: 「実行中」
    -   質問で停止で、マージの確認でない: 「質問で停止」
    -   質問で停止で、マージの確認: 「マージの確認待ち」
    -   レビュー待ち: 「レビュー待ち」
    -   タスク完了: 「タスク完了」
    -   要確認: 「要確認」
-   **AC-10**: マージの後の自動送信（0088 要件定義書の F-007）でコマンドを送った周の行は、送ったコマンドを実行中のコマンドとして、AC-09 の進み具合を示す。
-   **AC-11**: 実行中のコマンドは、実行中のエージェントの pane について、次の 2 つの記録からだけ決める。画面からは決めない。
    -   chief の送信の記録のうち、その pane へ最後に送ったコマンド
    -   その pane が Claude Code のとき、その transcript で、人が最後に入力した行。0088 で読む形（`internal/chief/screen_transcript.go:160-170`）のコマンドで、名前が `mkreq`・`mkarch`・`mkplan`・`runplan`・`runpr` のどれかのものに限る

    どちらからも決まらないとき、または 2 つの記録から 1 つに決まらないときは、実行中のコマンドは「決まらない」とする。示すのはコマンドの名前だけで、引数や transcript の文字列はそのまま示さない。
-   **AC-12**: 実行中のエージェントが 2 つ以上あり、それぞれの実行中のコマンドが 1 つに決まらないときは、実行中のコマンドは「決まらない」とする。

#### F-004: 表の並べ方

**Acceptance Criteria**:
-   **AC-13**: 状況の表の行は、急ぎの度合いが「すぐ」の行、「あとで」の行、「待つ」の行の順に並ぶ。ただし、使っていない worktree の行は、今までどおりほかのすべての行の後に並ぶ。
-   **AC-14**: 同じ急ぎの度合いの行の中の順は、0088 要件定義書の AC-03 の順である。このため、今の並びとの違いは、送信が止まった行と、削除の提案がある「タスク完了」の行が、それぞれ AC-13 の度合いの位置へ移ることだけである。
-   **AC-15**: 人の判断を待つものの一覧（選択肢）の並べ方は変わらない（0088 要件定義書の AC-13）。

#### F-005: 「質問で停止」の行の「次」の列

**Acceptance Criteria**:
-   **AC-16**: 「質問で停止」の行の「次」の列には、その行で止まっている質問ごとに、質問の要点と pane を書く。マージの確認かどうかは、進み具合（AC-09）で示し、「次」の列には書かない。マージの確認でないことを、それだけで文にしない。
-   **AC-17**: 表の下の示し方の差分は、「質問で停止」の行ごとの質問の要点と pane の一覧がなくなることだけである。まだ答えのない問い（0088 要件定義書の AC-16）と、道具の `problems` は、今までどおり表の下に示す。

#### F-006: 道具が決め、`/chief` が示す

**Acceptance Criteria**:
-   **AC-18**: 道具 `chief` の `snapshot` と `tick` の出力は、行ごとに、急ぎの度合い、番、文書、進み具合を持つ。行は AC-13・AC-14 の順に並んでいる。
-   **AC-19**: `/chief` の定義は、状況の表の各行に、道具が返した急ぎの度合い（AC-01 の形）、番、段階（文書と進み具合）を、道具の順のまま示すと定める。セッションが状態などから自分でこれらを決めることや、行を並べ替えることを定めない。
-   **AC-20**: 引数のない `/chief`（待ち受け）でも、`once` でも、表は AC-18・AC-19 のとおりに示される。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   段階を求めるために、新しいネットワークの操作を足さない。文書は、次のコマンドを決めるために今も読んでいる `origin/main` から読む（`internal/chief/state.go:269-342`）。

### 4.2. セキュリティ (Security)

-   N/A。条件付きのガイド（`docs/dev/security.md`）の適用条件（外部コマンド `yt-dlp` の呼び出し、API キー、キャッシュのディレクトリ、LLM API へのネットワークの送信、信頼できない文字列のプロンプトや記事への埋め込み）のどれにも当たらない。
-   chief が送る入力の範囲と、送る判断の条件は変えない。急ぎの度合い、番、段階は表示にだけ使い、何を送るかを左右しない。
-   **transcript の境界（AC-11）:** transcript は Claude Code が書く外部の値である。受け付ける形は、0088 で読む形（人の入力であると Claude Code が宣言した行の、採取した形のコマンド）だけである（`internal/chief/screen_transcript.go:160-170`）。この形に合わない行や読めない行は、今の読み取りと同じく、transcript 全体を読めないものとする。そのときと、名前が AC-11 の 5 つのどれでもないときは、実行中のコマンドは「決まらない」とし、推し量らない。示すのは、決まった 5 つのコマンドの名前だけである。transcript の文字列は表に出さない。新しい拒否の理由は足さない。読めない transcript は、段階の表示だけを「実行中」にし、行の状態を変えない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   文書、計画書、記録のどれかを読めないときは、推し量らずに、AC-08 の「要確認」か AC-11 の「決まらない」にする。

### 4.4. 互換性 (Compatibility)

-   `/chief` の定義と道具は、`--protocol` の番号で版を照合する（`.claude/commands/chief.md:52-56`）。出力を変えるときの番号の扱いは、設計で決める（design_handoff.md の H-01）。

### 4.5. 保守性 (Maintainability)

-   急ぎの度合いと番の対応は、道具の中の 1 か所に置く。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   ADR-0046 の決定（chief の判定は道具が行い、セッションは決めない。画面の文字列は「Declare, don't infer」の例外の範囲だけで読む）に従う。このタスクで、ADR-0046 に次の決定を足す。行ごとの急ぎの度合い、番、段階を道具が決める。実行中のコマンドを、送信の記録と transcript からも表示のために決める。
-   transcript の読み取りは、CLAUDE.md の「Declare, don't infer」の chief の画面の読み取りの例外の範囲（人の最後のコマンド）に収まる。その範囲は広げない。
-   次の文書を更新する。`.claude/commands/chief.md`（表の示し方と表の下の一覧）、`docs/dev/guides/chief_guide.md`（表の見方）、ADR-0046。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。
-   **急ぎの度合い**: 行ごとに、人がどれだけ早く対応すべきかを「すぐ」「あとで」「待つ」に分けたもの（F-001）。
-   **番**: 次に動くのが人か AI か。動く者がいないときは「なし」（F-002）。
-   **段階**: タスクの文書と進み具合の組（F-003）。
