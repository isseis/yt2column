## 1. 概要 (Overview)

**目的:** 本書は、chief（[0088 要件定義書](../0088_chief_of_staff/01_requirements.md)）の状況の表に加える表示の要件を定義する。加えるのは次の 4 つである。(1) 行ごとの急ぎの度合いの印、(2) タスクの進行の位置（issue #890 の「段階」）、(3) 次に動くのが人か AI か、(4) 「質問で停止」の行の「次」の列に書く中身。人が表を一目見て、何から手を付ければよいかが分かるようにする。

**背景:**

chief の状況の表は、workspace ごとに状態を示す。chief の今の振る舞いは次のとおりである。

-   道具 `chief` は、行ごとに 6 つの状態（要確認、質問で停止、実行中、レビュー待ち、次を提案、タスク完了）のどれか 1 つを返す（`internal/chief/state.go:382-440`、0088 要件定義書の F-001）。どの行に人がすぐ答えるべきかは、状態の名前を読まないと分からない。
-   送信の停止は状態ではない。どの状態の行にも付く印 `stopped` である（`internal/chief/snapshot.go:179-188`）。`/runpr` のマージの確認は、「質問で停止」の一種として `merge_question` で示す（0088 要件定義書の AC-02・AC-11）。
-   行の並びは次のとおりである（`internal/chief/state.go:58`、`internal/chief/snapshot.go:335-354`、0088 要件定義書の AC-03）。
    -   使っていないか残った worktree の行を最後に置く。
    -   それ以外の行は、質問で停止 → レビュー待ち → 次を提案 → 要確認 → 実行中 → タスク完了 の順に並ぶ。
    -   送信が止まった行は、使っていないか残った worktree の行には当たらない（`internal/chief/snapshot.go:185-188`）。
-   道具は、タスクの文書を `origin/main` から読み（`internal/chief/snapshot.go:259-267`）、次のコマンドを決める（`internal/chief/state.go:269-342`）。ただし、タスクがどの文書の段にあるかは、出力に含まない（`internal/chief/output.go:27-40`）。
-   「実行中」の行に示すコマンドとモデルは、chief の送信の記録からだけ決める（`internal/chief/snapshot.go:199-214`）。
-   Claude Code は、pane に打たれた入力を、chief が打ったものも人が打ったものも、セッションの記録（Claude Code の transcript）に人の入力として残す。chief は、そのうち人の最後の入力を読める（`internal/chief/screen_transcript.go:141-144`・`:160-170`）。ただし、それを使うのは pane のリセットの候補を狭めるときだけである（[ADR-0046](../../dev/adr/0046-chief-of-staff.md) の決定）。
-   `/chief` の定義は、「質問で停止」の行の「次」の列に `merge_question` だけを書くと定めている（`.claude/commands/chief.md:130-131`）。質問の要点と pane は、表の下に書く（`.claude/commands/chief.md:140`、0088 要件定義書の AC-05）。0088 の PR-7 の実地の確かめでは、セッションが `merge_question: false` を文に直して、「/runpr のマージ確認ではありません」と表に書いた（issue #890）。
-   `/chief` の定義は、状態や次のコマンドを道具が決め、セッションは決めないと定めている（`.claude/commands/chief.md:8-14`、ADR-0046 の決定）。

対応 issue: [#890](https://github.com/isseis/yt2column/issues/890)（親: [#836](https://github.com/isseis/yt2column/issues/836)、関連: タスク 0088、タスク [0092](../0092_chief_task_workspace/01_requirements.md)（[#839](https://github.com/isseis/yt2column/issues/839)））

**本書の記述範囲:** 本書は、表の各行に何を示し、行をどう並べるかという観測できる振る舞いを定める。次の事項は設計（`02_architecture.md`）で決める。

-   道具の出力の形（項目の名前、値の綴り）と、`--protocol` の番号の扱い
-   端末で表の列をそろえる方法
-   対応表を置く場所
-   テストの手段

要件の段階で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #890 で決めたこと:**

-   **表の各行に、急ぎの度合いを「すぐ」「あとで」「待つ」の 3 つに分けた印を付ける（F-001）。** 人が表を一目見て、どの行から手を付ければよいかを分かるようにするためである。Herdr が workspace の名前の左に出す状態の色に近い役割を持たせる。ADR: [ADR-0046](../../dev/adr/0046-chief-of-staff.md) を更新する（下の「要件定義の際に決めたこと」の、道具が決める項にまとめる）。
-   **3 つの度合いには、次の行を当てる（F-001）。** 答えないと進まないものを、時間をかけて読むものより先に示すためである。ADR: なし（印の対応は表示の細部で、下の「要件定義の際に決めたこと」の、道具が決める項の範囲に収まるため）。
    -   「すぐ」: AI が人の答えを待って止まり、答えないと進まない行（質問で停止、マージの確認待ち、送信の停止）
    -   「あとで」: 少し時間のかかる人の対応が要る行（レビュー待ち、次を提案）
    -   「待つ」: AI が作業中か作業を終えていて、人はとりあえず待てばよい行（実行中、タスク完了）
-   **各行に、タスクの進行の位置（文書 × 進み具合）と、次に動くのが人か AI か（番）を示す（F-002・F-003）。** タスクがどこまで進み、誰を待っているかを、状態の名前から推し量らずに分かるようにするためである。issue は番を進行の位置から決めるとしたが、要件定義で、番は対応表の行から決めることにした（下の「要件定義の際に決めたこと」）。ADR: ADR-0046 を更新する。
-   **文書は `origin/main` の文書から決める。動いているコマンドは、chief の送信の記録かセッションの記録からだけ決め、画面からは決めない（F-003）。** 0088 の画面の読み取りの範囲を広げないためである。ADR: ADR-0046 を更新する（セッションの記録を表示にも使うため）。
-   **「質問で停止」の行の「次」の列には、質問の要点と pane を書く（F-005）。** `merge_question: false` をそのまま文に直したものは、人にとって意味がないためである。ADR: なし（`/chief` の表示の細部のため）。

**要件定義の際に決めたこと（2026-11-16）:**

-   **進め方は通常の進め方にする。対象外の判断は「対象外ではない」で、上書きはない。** ADR: なし（進め方の選択はこのタスクの中で閉じるため）。
    -   対象外ではない理由は 3 つある。(1) 送る入力の範囲も、開発用ツールの信頼の境界も変えない。(2) `docs/dev/security.md` の規則と前提を変えない。(3) 外部の依存を足さない（[requirements_process.md](../../dev/conventions/requirements_process.md) の「Simple Process」の「Excluded changes」）。
    -   それでも通常の進め方にする理由は 3 つある。(1) 変更が道具の出力、`/chief` の定義、chief 利用ガイドの 3 か所に及ぶ。(2) 決める点が多い。(3) 進行の位置を求める仕組みが新しく、0092 の削除の提案とも重なる。
-   **「要確認」の行は「あとで」に置く（AC-04）。** 多くは、chief 以外のエージェントが長い出力を書いている途中など、chief が画面を読めないだけのためである（issue #890 の勧め）。本当に止まっている場合を見落とさないよう「すぐ」に置く案は採らない。読めないだけの行でも、人をすぐに呼ぶことになるためである。ADR: なし（印の対応の細部のため）。
-   **印は、色の付いた絵文字（🔴・🟡・🟢）に「すぐ」「あとで」「待つ」の文字を添えた形にする（AC-01）。** Herdr の状態の色に近く、一目で分かるためである。文字を添えるのは、色だけで状態を伝えないためである。形の違う記号（●・▲・○）の案は採らない。色がなく、Herdr の状態の色と結び付きにくいためである。絵文字の幅で表の列がずれうることは、設計で扱う（design_handoff.md の H-03）。ADR: なし（表示の細部のため）。
-   **急ぎの度合い、番、進行の位置は、どれも道具 `chief` が決めて出力に含める。`/chief` のセッションは、道具の値をそのまま示し、自分では決めない（F-006）。** ADR-0046 の「道具が決め、セッションは決めない」に合い、Go のテストで確かめられるためである。印は今の状態から定義の中で付け、進行の位置だけを道具で決める案は採らない。判定の一部がセッションに残るためである。ADR: ADR-0046 を更新する。
-   **表の行は、急ぎの度合いの順（すぐ → あとで → 待つ）に並べる。同じ度合いの中は今の順に並べ、使っていないか残った worktree の行は今と同じく最後に並べる（F-004）。** ADR: なし（並べ方の細部のため）。
    -   今の並びはほぼこの順なので、変わるのは、送信が止まった行と、0092 の削除の提案がある「タスク完了」の行の位置だけである。これは 0088 要件定義書の AC-03 の並べ方を変える。
    -   印だけを足して並びを変えない案は採らない。「すぐ」の行が「あとで」の行より下に来うるためである。
-   **印と番は、3.1 の対応表のとおりにする。番も、進行の位置からではなく、対応表の行から決める（F-001・F-002）。** issue は番を進行の位置から決めるとしたが、人と対応表を確かめて、次のように決めた。ADR: ADR-0046 を更新する。
    -   送信が止まった行は、状態によらず「すぐ」・人とする。進み具合が「作成中」でも、送信の停止を解くのは人だからである。
    -   使っていないか残った worktree の行は「待つ」・なしとする。`/mkreq` を提案していても、人が対応しなくても困らない行だからである。
    -   0092 の削除の提案がある「タスク完了」の行は「あとで」・人とする。この行は、使っていないか残った worktree の行より先に当てはめる。完了したタスクの worktree は `origin/main` で detached になり、0088 の規則では使っていないか残った worktree の行に当たりうるためである。
    -   「要確認」の行は人とする。読めないだけのことが多くても、確かめるのは人だからである。
    -   番は独立した列として示す。issue のとおりにするためである。番を印に含め、列を足さない案は採らない。
-   **実行中のコマンドは、pane の種類で決める。Claude Code の pane はセッションの記録の人の最後の入力だけから、OpenCode の pane は chief の送信の記録だけから決める（AC-11）。** ADR: ADR-0046 を更新する。
    -   理由: chief が Claude Code の pane に打った入力も、セッションの記録に人の入力として残る。このため、2 つの記録のどちらを優先するかを決めずに済む。OpenCode にはセッションの記録がないので、送信の記録を使う。
    -   受け入れること: 人が質問に自由な文で答えた後や、セッションの記録を読めない周は、コマンドが決まらず「実行中」と示す。
    -   採らない案: 両方の記録の時刻を比べて新しい方を使う案。規則と確かめることが増えるためである。送信の記録だけを使う案。人が自分で打ったコマンドを示せないためである。
-   **「実行中」の行の「次」の列に示すコマンドも、進行の位置と同じ規則（AC-11）で決める。これは 0088 要件定義書の AC-02 の「走っているコマンド」の決め方を変える（AC-14）。** 同じ行の中で、進行の位置と「次」の列が別のコマンドを示さないようにするためである。「次」の列を送信の記録のままにする案は採らない。ADR: なし（表示の細部で、上の項の ADR-0046 の更新に収まるため）。
-   **issue #890 の「段階」は、本書と表示では「進行の位置」と呼ぶ。** 用語集（`docs/translation_glossary.md`）で、「段階」はパイプラインの「ステージ」の旧称であり、使わない語だからである。ADR: なし（用語の選択のため）。
-   **簡易な進め方の 3 文書の PR の文書も「要件定義書」と示す（AC-07）。** 3 文書の PR がマージされる前は、`origin/main` に進め方の記録がなく、道具は簡易な進め方かどうかを `origin/main` から読めないためである。ADR: なし（表示の細部のため）。
-   **「質問で停止」の行の質問の要点と pane は、「次」の列にだけ書き、表の下の同じ一覧は外す。これは 0088 要件定義書の AC-05 を置き換える（F-005）。** 同じものを 2 回書かないためである。質問の全文と選択肢は、人がその質問を選んだときに、今までどおり示す（0088 要件定義書の AC-25）。表の下にも残す案は採らない。ADR: なし（表示の細部のため）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   人が状況の表を一目見て、すぐ答えるべき行と、あとで対応する行と、待てばよい行を見分けられるようにする。
-   タスクがどの文書の段にあり、次に動くのが人か AI かを、状態の名前から推し量らずに分かるようにする。
-   判定を道具に置いたままにし、chief のセッションが自分で判断しないという決まり（ADR-0046）を保つ。

### 2.2. スコープ (In Scope)

-   急ぎの度合いの印（F-001）
-   番（F-002）
-   タスクの進行の位置と、「実行中」の行の「次」の列のコマンド（F-003）
-   表の並べ方（F-004）
-   「質問で停止」の行の「次」の列（F-005）
-   道具が決めて出力に含め、`/chief` の定義がそれを示すこと（F-006）
-   ADR-0046 の更新、`/chief` の定義（`.claude/commands/chief.md`）の更新、chief 利用ガイド（`docs/dev/guides/chief_guide.md`）の更新（5 章）

### 2.3. スコープ外 (Out of Scope)

-   Herdr の状態の色そのものを chief から変えること（issue #890 の範囲の外）。
-   macOS の通知の出し方。今は `PushNotification` の端末への通知が、Herdr のベルと状態の色として届く（issue #890 の範囲の外）。
-   人の判断を待つものの一覧（選択肢）の並べ方。0088 要件定義書の AC-13 のまま変えない。issue は、表の並べ方だけを決めることとして挙げているためである。
-   画面から動いているコマンドを読むこと（issue #890 で決めたこと）。
-   0092 の削除の提案そのもの。本書は、削除の提案がある行に付ける印、番、進行の位置だけを定める。

## 3. 機能要件 (Functional Requirements)

本書の用語は、0088 要件定義書の 3 章（タスクの workspace、エージェント、入力を受け付ける状態）に従う。加えて、本書では次の用語を使う。

-   **状態**: 0088 要件定義書の F-001 の 6 つの状態（要確認、質問で停止、実行中、レビュー待ち、次を提案、タスク完了）。
-   **送信が止まった行**: 0088 で、送れたかが分からない送信のために、人が解除するまで送信を止めた workspace の行（`stopped`）。
-   **使っていないか残った worktree の行**: 0088 要件定義書の AC-03 で、表のほかのすべての行の後に並べる行。ただし、削除の提案がある行は含めない（AC-05）。
-   **削除の提案**: 0092 要件定義書の F-005・F-006 の、chief が作った workspace のうちタスクが完了したものに示す提案。
-   **進行の位置**: タスクの文書と進み具合の組（F-003）。issue #890 の「段階」にあたる。
-   **実行中のコマンド**: 実行中のエージェントが走らせているコマンドのうち、AC-11・AC-12 の規則で決まるもの。

### 3.1. 機能一覧

#### 対応表

道具は、行ごとに次の表を上から順に当てはめ、最初に当たる行の印と番を決める。

| 行の条件 | 急ぎの度合い | 番 |
|---|---|---|
| 送信が止まった行 | 🔴 すぐ | 人 |
| 質問で停止（マージの確認を含む） | 🔴 すぐ | 人 |
| タスク完了で、削除の提案があるもの | 🟡 あとで | 人 |
| 使っていないか残った worktree の行 | 🟢 待つ | なし |
| レビュー待ち、次を提案、要確認 | 🟡 あとで | 人 |
| 実行中 | 🟢 待つ | AI |
| タスク完了（削除の提案がないもの） | 🟢 待つ | なし |

#### F-001: 急ぎの度合いの印

**Acceptance Criteria**:
-   **AC-01**: 状況の表の各行は、急ぎの度合いの印をちょうど 1 つ持つ。印は「🔴 すぐ」「🟡 あとで」「🟢 待つ」のどれかで、絵文字と文字の両方を示す。
-   **AC-02**: 各行の急ぎの度合いは、対応表を上から順に当てはめて最初に当たる行のものである。対応表のどれにも当たらない行はない。
-   **AC-03**: 送信が止まった行は、状態が何であっても「🔴 すぐ」である。
-   **AC-04**: 「要確認」の行は、使っていないか残った worktree の行を除き、「🟡 あとで」である。読めなかった理由から、別の度合いを推し量らない。
-   **AC-05**: 削除の提案がある「タスク完了」の行は、0088 要件定義書の AC-03 の、使っていないか残った worktree の行の条件にも当たるときでも、「🟡 あとで」である。削除の提案がまだ実装されていないうちは、この行は現れない。この AC は、このタスクと 0092 のうち、後に実装する方で確かめる（design_handoff.md の H-05）。

#### F-002: 番

**Acceptance Criteria**:
-   **AC-06**: 状況の表の各行は、番を「人」「AI」「なし」のどれか 1 つで示す。値は、AC-02 で当たった対応表の行のものである。

#### F-003: タスクの進行の位置

各行は、進行の位置を「文書」と「進み具合」の組で示す。

**Acceptance Criteria**:
-   **AC-07**: 文書は、chief が次のコマンドを決めるときと同じ、fetch した後の `origin/main` の文書から決める。次の規則を上から順に当てはめ、最初に当たるものとする。
    1.  `git fetch origin main` に失敗したか、要件定義書・設計書・計画書、その状態の表、進め方の記録、計画書の PR マーカーのどれかを読めない: 「要確認」
    2.  削除の提案がある行: 「なし」
    3.  タスクがなく、次のコマンドが `/mkreq` であるか、実行中のコマンドが `/mkreq` である: 「要件定義書」
    4.  タスクがない: 「-」
    5.  `origin/main` に要件定義書がない: 「要件定義書」（簡易な進め方の 3 文書の PR も同じ）
    6.  計画書が `approved` で、計画のすべての PR がマージされている: 「なし」
    7.  計画書が `approved`: 「PR-N」。N は、計画書の PR マーカーのうち、PR がまだマージされていない最初のものの番号である。PR マーカーのない計画書は、PR が 1 つなので「PR-1」とする。PR を作ったがまだマージしていないとき、N はその PR の番号であり、次の `/runplan` が作る PR の番号より小さい。作った PR のレビューとマージを待っていることを示すためである
    8.  設計書が `approved` で、計画書がない: 「計画書」
    9.  要件定義書が `approved` で、進め方が通常（記録がないものを含む）で、設計書がない: 「設計書」
    10. 上のどれにも当たらない（`approved` でない文書が `origin/main` にある、進め方の記録が読めない、簡易な進め方なのに設計書か計画書がない、など）: 「要確認」
-   **AC-08**: 文書が「要確認」でも、行の状態は、0088 要件定義書の F-001 で決まったまま変えない。読めなかったものから、ほかの文書を推し量らない。
-   **AC-09**: 進み具合は、行の状態と実行中のコマンドから、次のように決める。
    -   次を提案: 「作成待ち」
    -   実行中で、実行中のコマンドが `/mkreq`・`/mkarch`・`/mkplan`・`/runplan`: 「作成中」
    -   実行中で、実行中のコマンドが `/runpr`: 「`/runpr` 実行中」
    -   実行中で、実行中のコマンドが決まらない: 「実行中」
    -   質問で停止で、質問がすべてマージの確認: 「マージの確認待ち」
    -   質問で停止で、マージの確認でない質問が 1 つ以上ある: 「質問で停止」
    -   レビュー待ち: 「レビュー待ち」
    -   タスク完了: 「タスク完了」
    -   要確認: 「要確認」
-   **AC-10**: マージの後の自動送信（0088 要件定義書の F-007）でコマンドを送った周の行は、送ったコマンドを実行中のコマンドとして、AC-09 の進み具合と AC-14 の「次」の列を示す。
-   **AC-11**: 実行中のコマンドは、実行中のエージェントの pane ごとに、次のように決める。画面からは決めない。
    -   Claude Code の pane: セッションの記録で人が最後に入力した行が、0088 で読む形のコマンドで、名前が `mkreq`・`mkarch`・`mkplan`・`runplan`・`runpr` のどれかであるとき、そのコマンド。次のときは、決まらない。最後の入力が自由な文であるとき、ほかの名前のコマンドであるとき、人の入力がないとき、セッションの記録を読めないとき。
    -   OpenCode の pane: chief の送信の記録のうち、その pane へ最後に送ったコマンド。記録がないときは、決まらない。
-   **AC-12**: 実行中のエージェントが 2 つ以上あるときは、次の 2 つをどちらも満たすときだけ、そのコマンドを実行中のコマンドとする。それ以外は、決まらない。
    -   そのすべての pane で、実行中のコマンドが決まる。
    -   それらが同じ 1 つのコマンドである。
-   **AC-13**: 表に示すのは、実行中のコマンドの名前と、その引数（タスクの番号か PR の番号）だけである。引数は、0088 で受け付ける形の番号のときだけ示す。セッションの記録の文字列は、そのまま示さない。
-   **AC-14**: 「実行中」の行の「次」の列には、実行中のコマンドを示す。
    -   モデルは、実行中のエージェントが 1 つで、その pane への chief の送信の記録のコマンドが実行中のコマンドと同じとき、その記録のモデルを示す。それ以外は、モデルを示さない。
    -   実行中のコマンドが決まらないときは、コマンドもモデルも示さない。

#### F-004: 表の並べ方

**Acceptance Criteria**:
-   **AC-15**: 状況の表の行は、急ぎの度合いが「すぐ」の行、「あとで」の行、「待つ」の行の順に並ぶ。ただし、使っていないか残った worktree の行は、今までどおりほかのすべての行の後に並ぶ。削除の提案がある行は、この行に当たらない（AC-05）。
-   **AC-16**: 同じ急ぎの度合いの行の中の順は、0088 要件定義書の AC-03 の順である。このため、今の並びとの違いは、送信が止まった行と、削除の提案がある「タスク完了」の行が、それぞれ AC-15 の度合いの位置へ移ることだけである。
-   **AC-17**: 人の判断を待つものの一覧（選択肢）の並べ方は変わらない（0088 要件定義書の AC-13）。

#### F-005: 「質問で停止」の行の「次」の列

**Acceptance Criteria**:
-   **AC-18**: 「質問で停止」の行の「次」の列には、その行で止まっている質問ごとに、質問の要点と pane を書く。マージの確認である質問には、そのことを添える。マージの確認でないことだけを文にして書くことはしない。
-   **AC-19**: 表の下の示し方の差分は、「質問で停止」の行ごとの質問の要点と pane の一覧がなくなることだけである。まだ答えのない問い（0088 要件定義書の AC-16）と、道具の `problems` は、今までどおり表の下に示す。

#### F-006: 道具が決め、`/chief` が示す

**Acceptance Criteria**:
-   **AC-20**: 道具 `chief` の `snapshot` と `tick` の出力は、行ごとに、急ぎの度合い、番、文書、進み具合を持つ。行は AC-15・AC-16 の順に並んでいる。
-   **AC-21**: `/chief` の定義は、状況の表の各行に、道具が返した急ぎの度合い（AC-01 の形）、番、進行の位置（文書と進み具合）を、道具の順のまま示すと定める。セッションが状態などから自分でこれらを決めることや、行を並べ替えることは定めない。
-   **AC-22**: 引数のない `/chief`（待ち受け）でも、`once` でも、表は AC-20・AC-21 のとおりに示される。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   進行の位置を求めるために、新しいネットワークの操作を足さない。文書は、次のコマンドを決めるために今も読んでいる `origin/main` から読む（`internal/chief/snapshot.go:259-267`）。
-   chief は、周ごとに、実行中の Claude Code の pane のセッションの記録を読む。これは、今の読み取りの上限（64 MiB、`internal/chief/transcript.go:30`）の中で、ローカルのファイルを読むだけである。そのため、CLAUDE.md の「Performance」の基準で、仕組みを足して減らすほどの費用ではないとみなす。

### 4.2. セキュリティ (Security)

-   N/A。条件付きのガイド（`docs/dev/security.md`）の適用条件のどれにも当たらない。適用条件は、外部コマンド `yt-dlp` の呼び出し、API キー、キャッシュのディレクトリ、LLM API へのネットワークの送信、信頼できない文字列のプロンプトや記事への埋め込みである。
-   chief が送る入力の範囲と、送る判断の条件は変えない。急ぎの度合い、番、進行の位置は表示にだけ使い、何を送るかを左右しない。
-   **セッションの記録の境界（AC-11）:** セッションの記録は、Claude Code が書く外部の値である（0088 要件定義書の 4.2 の「信頼できない入力」の表の「セッションの記録」の行）。このタスクでは、その行の「使う部分」に、人が最後に入力したコマンドを足し、表示のためにも使う。
    -   受け付ける形: 0088 で読む形だけである。行が人の入力であるかは、Claude Code が宣言する値で見分ける。コマンドは、採取した形のもので、2 つの名前が同じものに限る（`internal/chief/screen_transcript.go:141-144`・`:160-170`）。
    -   形に合わないとき: 次のいずれかの行が 1 行でもあれば、記録全体を読めないものとする。(1) 1 つの JSON の値でない行、(2) 読むメンバーが重なる行、(3) 採取していない種類の行。その行を直したり、飛ばしたりしない。これは今と同じである。読めない記録は、新しい拒否の理由やエラーにせず、AC-11 の「決まらない」にする。行の状態は変えない。
    -   上限: 今の読み取りの上限（64 MiB）をそのまま使い、超えた記録は読めないものとする（`internal/chief/transcript.go:84-96`）。
    -   示すもの: AC-13 のとおり、決まった 5 つのコマンドの名前と、受け付ける形の番号の引数だけである。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   文書、計画書、記録のどれかを読めないときは、推し量らずに、AC-07 の「要確認」か AC-11 の「決まらない」にする。
-   実行中の Claude Code は、セッションの記録に書き足している途中でありうる。書きかけの最後の行のために記録を読めなかった周では、進み具合が「実行中」になる。そのため、周によって「作成中」と「実行中」が入れ替わりうる。受け付ける形を広げずにこれを減らす方法は、設計で扱う（design_handoff.md の H-06）。

### 4.4. 互換性 (Compatibility)

-   `/chief` の定義と道具は、`--protocol` の番号で版を照合する（`.claude/commands/chief.md:52-56`）。出力を変えるときの番号の扱いは、設計で決める（design_handoff.md の H-01）。

### 4.5. 保守性 (Maintainability)

-   N/A。対応表を置く場所は、設計で決める（design_handoff.md の H-01）。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。「段階」は、用語集でパイプラインの「ステージ」の旧称なので、使わない。
-   **急ぎの度合い**: 行ごとに、人がどれだけ早く対応すべきかを「すぐ」「あとで」「待つ」に分けたもの（F-001）。

-   **進行の位置**: タスクの文書と進み具合の組（F-003）。
-   **セッションの記録**: Claude Code の transcript。0088 要件定義書と同じ語である。
