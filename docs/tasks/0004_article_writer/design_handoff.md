# 設計への申し送り：ArticleWriter とプロンプトテンプレート

## 本書の位置づけ

[01_requirements.md](01_requirements.md) の作成過程で挙がった事項のうち、要件（観測できる振る舞い）ではなく、設計・実装の段階で決める、または注意すべき事項をまとめる。

-   要件書は「何を受け取り、LLM に何を送り、何を返し、何をどの番兵で拒否するか」だけを定める。本書の項目は、その振る舞いを実現する手段の候補と、既知の落とし穴である。
-   `02_architecture.md` は、本書の各項目について、採用した手段または扱わない理由を記録する。本書の手段は候補であり、設計で別の手段を選んでもよい。ただし、対応する AC を満たすこと。
-   本書は承認対象の文書ではない。設計の作成時に参照し、項目を追加してよい。

## H-01: `prompts/` の埋め込みとパッケージ配置

-   `//go:embed` は、ディレクティブを書いた Go ファイルのディレクトリとその下にあるファイルしか参照できない（`..` を使えない）。`internal/writer` から、リポジトリ直下の `prompts/` を直接埋め込むことはできない。
-   候補: `prompts/` に小さな Go パッケージ（例: `prompts.go`）を置き、埋め込んだ内容を `embed.FS` または文字列として公開する。`internal/writer` はそれを import する。`depguard` や `deadcode` の設定に影響しないか確認する。
-   既定のテンプレートの検証（AC-06）は、このパッケージが公開する実物の内容に対して行う。テスト用の複製で行わない。

## H-02: 参照できない値の構築時の検出

-   `text/template` の `Parse` は、存在しないフィールドの参照（例: `{{.APIKey}}`）をエラーにしない。構造体を渡した `Execute` の時点で初めてエラーになる。
-   試しに `Execute` するだけでは不十分である。`{{if .Description}}{{.APIKey}}{{end}}` のように、試行に使った値では通らない分岐の中の参照を検出できない。
-   候補: 解析木（`text/template/parse`）を走査し、すべてのフィールドの参照（`FieldNode`、`with`・`range` の中で `.` が変わる場合を含む）が、参照できる値の名前に限られることを確認する。`range`・`with` で `.` が別の値になる場合の扱い（拒否するか、許すか）も決める。
-   代替案: テンプレートの機能を制限し、`{{.Name}}` の形の参照だけを許す（`if`・`range` などの制御構造を拒否する）。仮のテンプレートと #8 の本番用テンプレートに制御構造が要るかで判断する。
-   `{{template "x"}}` で未定義のテンプレートを呼ぶ形、`{{define}}` で別のテンプレートを定義する形の扱いも決める。

## H-03: テンプレートに渡す値の形と名前

-   参照できる値の名前（例: `.Title`・`.ChannelName`・`.Description`・`.Transcript`）は、上書きファイルを書く利用者に見える仕様である。設計で確定し、`prompts/` の README などに記す。
-   `transcript.Transcript` をそのまま渡すと、`VideoID`・`VideoURL`・`Segments`（`StartMs` を含む）も参照できてしまい、F-001 の「4 つの値」と食い違う。テンプレート専用の構造体を用意する。
-   `text/template` は値をエスケープしない（`html/template` と異なる）。字幕がプロンプトにそのまま入ることは要件どおりである（AC-10・AC-12）。`html/template` を使うと HTML エスケープで字幕が変わるので使わない。

## H-04: 閉じていないコードフェンスの判定

-   CommonMark のフェンスは、行頭から 3 個以下の空白のインデントの後に、同じ文字（```` ` ```` または `~`）が 3 個以上続く行で始まる。閉じるフェンスは、開いたフェンスと同じ文字で、開いたフェンス以上の個数でなければならない。```` ` ```` のフェンスの info string は ```` ` ```` を含められない。
-   判定を簡略にすると、受理すべき出力を拒否する、または閉じていないフェンスを見逃す。見逃すと出典ブロックがコードブロックの中に入る。どこまで CommonMark に忠実に判定するかを決め、境界の例（4 個の空白でインデントしたフェンス、```` ```` ```` で開いて ```` ``` ```` で閉じる形など）をテストに加える。
-   コードフェンス以外に出典ブロックを隠しうる構造（閉じていない HTML コメント `<!--`、インデントによるコードブロック、リストの継続など）を検討し、扱う場合は要件に AC を追加する。扱わない場合は理由を記録する。出典ブロックの前に空行を置くこと（H-05）で、インデントのコードブロックやリストの継続は避けられる見込みである。

## H-05: 出典ブロックの書式と、本文との区切り

-   書式の候補: `出典: <https://www.youtube.com/watch?v=<VideoID>>`（自動リンク）、または `出典: https://www.youtube.com/watch?v=<VideoID>`。Slack の `markdown` ブロック（#7）でリンクとして表示されるかは #7 で確認する。区切りとして水平線（`---`）を置くかも決める。`---` の直前の行が空行でないと Setext 見出しの下線と解釈されるので、置く場合は前に空行を置く。
-   区切り方: LLM が生成した本文は加工しない（AC-17）。そのうえで、本文が改行で終わらない場合も、改行が続いて終わる場合も、出典ブロックの直前に空行が 1 つ以上あるようにする（AC-19）。本文の末尾の改行を除去して付け直す方法は、AC-17 の「本文を加工しない」と両立するか（除去は本文の末尾の加工に当たるか）を確認したうえで選ぶ。
-   URL は検証済みの動画 ID から組み立てるので、Markdown のエスケープは不要である。

## H-06: 動画 ID と正規化 URL の検証の共有

-   `internal/transcript` の `videoIDPattern` と、正規化 URL の組み立て（`validateVideoURL`）は unexported である。`ArticleWriter` が同じ規則を書き直すと、2 か所の規則がずれうる（CLAUDE.md の DRY）。
-   候補: `internal/transcript` に、動画 ID の検証と正規化 URL の組み立てを行う exported な関数を追加し、`internal/writer` から使う。
-   より強い案として、動画 ID を検証済みの型にする（CLAUDE.md の「Enforce invariants with the type」）方法があるが、`Transcript` の型の変更は本タスクのスコープ外とした（要件書 2.3）。必要なら別 issue とする。

## H-07: typed nil の判定の共有

-   `internal/pipeline` の `isTypedNil` は unexported である。`ArticleWriter` の構築でも同じ判定が要る（AC-02）。
-   候補: 共有する小さな関数を置く、または `ArticleWriter` の側で同等の判定を持つ。DRY と、パッケージの依存の向きを踏まえて決める。

## H-08: 上書きファイルの読み込みとサイズの上限

-   上限値を決める。仮のテンプレートと、#8 で想定する本番用テンプレートの大きさに十分な余裕を持たせる。
-   上限の判定は、`os.ReadFile` で全体を読んでから長さを見るのではなく、上限＋1 バイトまで読んで超過を検出する。巨大なファイルや、終わらない特殊ファイル（`/dev/zero` など）を誤って指定しても、メモリを使い切らないようにするためである。
-   ディレクトリを指定した場合、`os.Open` は成功し、読み取りでエラーになる。AC-05 のとおり `ErrInvalidTemplate` にする。
-   エラーメッセージにパスを含めてよいか（利用者自身が与えたパスであり、秘密情報ではない）を確認する。

## H-09: エラーのラップとメッセージ

-   `LLMClient` のエラーは `%w` でラップし、`errors.Is` で元の番兵と `context` のエラーを判別できるようにする（AC-14）。
-   上書きファイルの読み込みの失敗は、`ErrInvalidTemplate` と元の `*fs.PathError` の両方を `errors.Is` で判別できるようにする（AC-05 の `fs.ErrNotExist`）。
-   `ErrMalformedOutput` のエラーには、拒否した理由だけを含め、生成テキストの内容（タイトルを含む）を含めない（AC-26）。

## H-10: 展開結果が空白文字だけかの判定

-   「空白文字」の定義を、`llm.GenerateRequest.Validate`・DeepSeek アダプタの空の応答の判定・`internal/transcript` の空白だけのセグメントの判定とそろえる（`strings.TrimSpace` が除く文字など）。本書の「空白文字」はすべて同じ定義とする。
-   `llm.GenerateRequest.Validate` は空文字列だけを拒否し、空白文字だけのプロンプトは拒否しない。AC-13 は `ArticleWriter` の側で判定する。
