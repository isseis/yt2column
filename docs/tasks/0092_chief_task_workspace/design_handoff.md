# 設計への申し送り（0092）

要件定義の段階で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: 作ったことの記録の置き場所と形

**懸念:** 削除の提案（F-005）は、chief が作った workspace と、そのときの issue 番号を記録から読む。0088 の記録は、リポジトリの外の状態のディレクトリに、同名のものがあれば作らない形で置く（[ADR-0046](../../dev/adr/0046-chief-of-staff.md)）。

**なぜ重要か:** 記録が worktree と正しく結び付かないと、別の workspace を削除の候補にしうる（4.2 の残る危険）。消し終えた後に記録が残ると、同じパスで作り直した workspace を、前の issue の候補として読みうる（AC-26）。

**候補:** 0088 の workspace ごとのディレクトリ（worktree の正規のパスの SHA-256）に置く。記録には、worktree の正規のパス、workspace の識別、issue 番号、作った日時を持たせる。消し終えたら、記録を「消した」と閉じる。作成の途中で失敗したとき（AC-09）に記録を作るかも決める。

**関連:** F-002・F-005・F-006、AC-18・AC-19・AC-26

## H-02: worktree と workspace の作り方

**懸念:** Herdr 0.9.1 には `herdr worktree create`（`--branch`・`--base`・`--path`・`--label`・`--trust-repository` などの引数を持つ）がある。この呼び出しで、ブランチを作らずに detached の worktree を作れるかは確かめていない。`git worktree add --detach` と `herdr workspace create` を組み合わせる方法もある。

**なぜ重要か:** ブランチを作ると、要件定義の際に決めたこと（detached にする）に反する（AC-04）。作り方によって、途中で失敗したときに残るもの（AC-09）が変わる。

**候補:** 両方の方法を実際に試し、AC-04・AC-05 を満たし、途中の失敗を段ごとに示せるほうを選ぶ。pane の配置（シェル・OpenCode・Claude Code）と、作った pane の識別の読み方も決める。

**関連:** F-002、AC-04〜AC-09

## H-03: エージェントの起動と、入力を受け付ける状態の確かめ

**懸念:** 新しいディレクトリで Claude Code を起動すると、フォルダを信頼するかの確認が出ることがある。これは質問の画面で、0088 の見分けでは「質問で停止」になる。OpenCode にも、初回の画面がありうる。

**なぜ重要か:** 確認が出たまま `/mkreq` を送ると、送れない（AC-36）か、確認に答える入力として届きうる。chief は権限の確認を中継しない（0088 の F-005）。

**候補:** 信頼の確認を出さない起動の方法（`herdr worktree create` の `--trust-repository` など）が、何を信頼させるかを確かめてから使うかを決める。入力を受け付ける状態を待つ時間の上限（AC-12）と、その間の確かめの間隔を決める。確認の画面が出たときは送らず、人が答えるよう示す。

**関連:** F-002・F-003、AC-11〜AC-13

## H-04: issue からタスクを見つけ、完了を読む方法

**懸念:** 要件定義書の `対応 issue` の行は、2 つ以上の issue を挙げることがある（例: 0088 は `#837`・`#838`）。`/mkreq` の重複の探し方（`対応 issue: \[#N\]`）は、行の最初の issue しか見ない。

**なぜ重要か:** 見つけ方が `/mkreq` と食い違うと、同じ issue のタスクを見落とすか、2 つあることを見落とす（AC-18・AC-19）。

**候補:** `対応 issue` の行に挙がるすべての issue 番号を、リンクの形で読む規則を決め、`/mkreq` の探し方との関係を記録する。完了の判定は、0088 の「タスク完了」の判定（`internal/chief/state.go` の `decideNext`）と同じものを使う。

**関連:** F-005、AC-18・AC-19

## H-05: 作る呼び出しを、セッションへの拒否に足すか

**懸念:** `.claude/settings.json` は、入力を送る呼び出しと、閉じるか消す呼び出しを拒むが、`herdr worktree create`・`herdr workspace create`・pane を作る呼び出しは拒まない。

**なぜ重要か:** 作成を道具だけが行うと決めた（要件定義の際に決めたこと）。それでも、セッションがこれらを直接呼べば、道具を通さずに workspace を作れる。作るだけでは作業を失わないが、`herdr agent start` を拒んでいるので、作った pane でエージェントは動かない。

**候補:** 作る呼び出しを拒否に足す案と、足さずに残る危険とする案を、人が手で作るときの手間（人が Claude Code に頼むと拒まれる）とあわせて比べる。

**関連:** 4.2 の信頼の境界と残る危険

## H-06: 消す順序と、消すときの git と Herdr の振る舞い

**懸念:** `git worktree remove` は、変更か追跡していないファイルがあると拒む。git が無視するファイルの扱いや、`herdr worktree remove` が workspace を閉じるかは確かめていない。

**なぜ重要か:** 確かめ（AC-23）と消す操作の間に状態が変わると、確かめていないものを消しうる。消す順序で、途中の失敗のときに残るもの（AC-25）が変わる。

**候補:** `--force` を使わずに消し、確かめの後に変わったものがあれば git に拒ませる。workspace を閉じる段と worktree を消す段の順序を決め、それぞれの失敗のときに示すものを決める。

**関連:** F-006、AC-23〜AC-25

## H-07: issue を読む操作と、issue か PR かの見分け

**懸念:** `gh issue view` が PR の番号に何を返すかは確かめていない。issue か PR かを表す値（REST の `pull_request` のメンバーなど）をどう得るかで、呼ぶ操作が変わる。

**なぜ重要か:** CLAUDE.md の「Tool Execution Safety」に書く操作の名前と形が、これで決まる（5 章）。PR の番号で workspace を作らないため（AC-02）。

**候補:** `gh issue view <N> --json` と `gh api repos/{owner}/{repo}/issues/<N>` を比べ、受け付ける形（4.2）を厳格に確かめられるほうを選ぶ。

**関連:** F-001、AC-01〜AC-03、4.2

## H-08: `/chief` の流れと道具の契約

**懸念:** `/mkreq` を始める先の選択（F-004）、削除の提案と確かめの問い（F-005・F-006）が、`/chief` の問いと道具のサブコマンドに加わる。

**なぜ重要か:** 0088 は、`/chief` の定義と道具を `--protocol` の番号で照合する（chief 利用ガイドの「2. インストール」）。サブコマンドや出力を変えるときは番号を上げ、入れ直しの手順が要る。

**候補:** 作成と削除のサブコマンドを足し、出力の拒否の理由の値を決める。番号を上げるかと、文書のガードテストが読む契約を決める。

**関連:** F-004〜F-006
