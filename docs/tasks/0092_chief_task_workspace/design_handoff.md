# 設計への申し送り（0092）

要件定義の段階で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: 作ったことの記録の置き場所と形

**懸念:** 削除の提案（F-006）は、chief が作った workspace と、そのときの issue 番号を記録から読む。0088 の記録は、リポジトリの外の状態のディレクトリに、同名のものがあれば作らない形で置く（[ADR-0046](../../dev/adr/0046-chief-of-staff.md)）。

**なぜ重要か:** 記録が worktree と正しく結び付かないと、別の workspace を削除の候補にしうる（4.2 の残る危険）。消し終えた後や、作成か削除が途中で失敗した後（AC-12・AC-32）、人が端末で片付けた後に記録が残ると、同じパスで作り直した workspace を、前の issue の候補として読みうる（AC-14・AC-33）。

**候補:** 0088 の workspace ごとのディレクトリ（worktree の正規のパスの SHA-256）に置く。記録には、worktree の正規のパス、workspace の識別、issue 番号、作った日時を持たせる。消し終えたら、記録を「消した」と閉じる。作成の途中で失敗したとき（AC-12）に記録を作るかと、AC-14 で前の記録を終わったものとする方法（同じ名前の記録を上書きしないという 0088 の決まりとの関係）も決める。

**関連:** F-003・F-006・F-007、AC-14・AC-23・AC-24・AC-33

## H-02: worktree と workspace の作り方

**懸念:** Herdr 0.9.1 には `herdr worktree create`（`--branch`・`--base`・`--path`・`--label`・`--trust-repository` などの引数を持つ）がある。この呼び出しで、ブランチを作らずに detached の worktree を作れるかは確かめていない。`git worktree add --detach` と `herdr workspace create` を組み合わせる方法もある。

**なぜ重要か:** ブランチを作ると、要件定義の際に決めたこと（detached にする）に反する（AC-08）。作り方によって、途中で失敗したときに残るもの（AC-12）が変わる。

**候補:** 両方の方法を実際に試し、AC-08・AC-09 を満たし、途中の失敗を段ごとに示せるほうを選ぶ。pane の配置（シェル・OpenCode・Claude Code）と、作った pane の識別の読み方も決める。`~/.herdr/worktrees/yt2column/` がないときに作るか、`~/.herdr` がシンボリックリンクのときにパスをどう比べるか（AC-11）も決める。

**関連:** F-003、AC-08〜AC-12

## H-03: エージェントの起動と、入力を受け付ける状態の確かめ

**懸念:** 新しいディレクトリで Claude Code を起動すると、フォルダを信頼するかの確認が出ることがある。これは質問の画面で、0088 の見分けでは「質問で停止」になる。今は、同じリポジトリの worktree では確認が出ていないように見える（`~/.claude.json` に、本体のチェックアウトの信頼だけが記録され、worktree の記録はない）が、Claude Code の仕様として確かめてはいない。OpenCode にも、初回の画面がありうる。

**なぜ重要か:** 確認が出るなら、毎回 `/mkreq` を送れず（AC-16・AC-17）、2.1 の目的を果たせない。chief は人の代わりに許可や信頼を与える引数を付けない（AC-10）。

**候補:** 作った worktree で実際に Claude Code と OpenCode を起動して、確認が出るかを確かめる。`herdr worktree create` の `--trust-repository` が何を信頼させるか（Herdr 自身の設定か、エージェントの信頼か）を確かめ、AC-10 に当たるなら使わない。入力を受け付ける状態を待つ時間の上限（AC-16）と、その間の確かめの間隔を決める。

**関連:** F-003・F-004、AC-10・AC-15〜AC-17

## H-04: issue からタスクを見つけ、完了を読む方法

**懸念:** 要件定義書の `対応 issue` の行は、2 つ以上の issue を挙げることがあり（例: 0088 は `#837`・`#838`）、`（` の中に親 issue と関連 issue も挙げる。数えるのは最初の `（` より前のリンクだけと、要件で決めた（AC-23）。`/mkreq` の重複の探し方（`対応 issue: \[#N\]`）は、行の最初の issue しか見ない。

**なぜ重要か:** 見つけ方が `/mkreq` と食い違うと、同じ issue のタスクを見落とすか、2 つあることを見落とす（AC-23・AC-24）。

**候補:** 最初の `（` より前に挙がる issue のリンクを読む形（リンクの綴り、区切りの `・`、リンクでない番号の扱い）を決め、`/mkreq` の探し方との関係を記録する。完了の判定は、0088 の「タスク完了」の判定（`internal/chief/state.go` の `decideNext`）と同じものを使う。

**関連:** F-005・F-006、AC-20・AC-23・AC-24

## H-05: セッションへの拒否と、削除のサブコマンドの許可

**懸念:** `.claude/settings.json` は、入力を送る呼び出しと、閉じるか消す `herdr` の呼び出しを拒むが、`herdr worktree create`・`herdr workspace create`・pane を作る呼び出しも、`git worktree add`・`git worktree remove` も拒まない。また、`chief` の呼び出しを確認なしに許す（`.claude/settings.json:6`）ので、削除のサブコマンドも確認なしに呼べる。

**なぜ重要か:** 作成を道具だけが行うと決めた（要件定義の際に決めたこと）。それでも、セッションがこれらを直接呼べば、道具を通さずに workspace を作れる。作るだけでは作業を失わないが、`herdr agent start` を拒んでいるので、作った pane でエージェントは動かない。

道具は人の確認（AC-27）が行われたかを確かめられない（4.2）。

**候補:** 作る呼び出しと `git worktree` の呼び出しを拒否に足す案と、足さずに残る危険とする案を、人が手で作るときの手間（人が Claude Code に頼むと拒まれる）とあわせて比べる。削除のサブコマンドを `Bash(chief *)` の許可から外して、呼ぶたびに Claude Code の許可の確認を出させる案も比べる。

**関連:** 4.2 の信頼の境界と残る危険

## H-06: 消す順序と、消すときの git と Herdr の振る舞い

**懸念:** `git worktree remove` は、変更か追跡していないファイルがあると拒む。git が無視するファイルの扱いや、`herdr worktree remove` が workspace を閉じるかは確かめていない。

**なぜ重要か:** 確かめ（AC-28）と消す操作の間に状態が変わると、確かめていないものを消しうる。消す順序で、途中の失敗のときに残るもの（AC-32）が変わる。workspace を閉じると、エージェントでない pane のプロセスも終わる（4.2 の残る危険）。

**候補:** `--force` を使わずに消し、確かめの後に変わったものがあれば git に拒ませる。workspace を閉じる段と worktree を消す段の順序を決め、それぞれの失敗のときに示すものを決める。chief が作った 3 つのほかに pane があるときや、シェルの pane で前面のプロセスが動いているときに消さないかを、Herdr の出力で読めるかとあわせて比べる。

**関連:** F-007、AC-27〜AC-32

## H-07: issue を読む操作と、issue か PR かの見分け

**懸念:** `gh issue view` が PR の番号に何を返すかは確かめていない。issue か PR かを表す値（REST の `pull_request` のメンバーなど）をどう得るかで、呼ぶ操作が変わる。

**なぜ重要か:** CLAUDE.md の「Tool Execution Safety」に書く操作の名前と形が、これで決まる（5 章）。PR の番号で workspace を作らないため（AC-05）。受け付ける形（4.2）は、応答のそのままの形について決めた。`--jq` で形を変えると、jq が重なったメンバーを黙ってまとめるので、重なりを拒めなくなる。

**候補:** `gh issue view <N> --json` と `gh api repos/{owner}/{repo}/issues/<N>` を比べ、受け付ける形（4.2）を厳格に確かめられるほうを選ぶ。

**関連:** F-002、AC-05〜AC-07、4.2

## H-08: `/chief` の流れと道具の契約

**懸念:** 新しいタスクを始める入口と始める先の選択（F-001）、完了した行の示し方（F-005）、削除の提案と人の確認の問い（F-006・F-007）が、`/chief` の問いと道具のサブコマンドと出力に加わる。

**なぜ重要か:** 0088 は、`/chief` の定義と道具を `--protocol` の番号で照合する（chief 利用ガイドの「2. インストール」）。サブコマンドや出力を変えるときは番号を上げ、入れ直しの手順が要る。

**候補:** 作成と削除のサブコマンドを足し、出力の拒否の理由の値を決める。番号を上げるかと、文書のガードテストが読む契約を決める。

**関連:** F-001・F-005〜F-007

## H-09: 削除の提案がある行の急ぎの度合い・番・進行の位置（0093 から）

**懸念:** [0093 要件定義書](../0093_chief_status_sheet/01_requirements.md) は、状況の表の各行に急ぎの度合い・番・進行の位置を示し、削除の提案がある「タスク完了」の行を次のように扱うと定める。0093 は、0092 の削除の提案がまだ `main` になければ、削除の提案の行の扱いを持たずに実装し、あれば 0093 の中で扱う（[0093 設計書](../0093_chief_status_sheet/02_architecture.md)「設計の際に決めたこと（2026-11-16）」と 3.12）。この項目は、0093 が先に入ったときに 0092 が足すものである。
-   急ぎの度合いは「🟡 あとで」、番は「人」とする。対応表で、使っていないか残った worktree の行より先に当てはめる（0093 の AC-05、3.1 の対応表）。
-   使っていないか残った worktree の行（`Row.Idle`）に当てない。表の最後に並べず、「あとで」の位置に並べる（0093 の AC-15）。
-   進行の位置の文書は「なし」とする（0093 の AC-07 の規則 2）。

**なぜ重要か:** 0092 の行は HEAD が detached なので、0088 の規則（`internal/chief/state.go:434`）では `Row.Idle` になる。0092 がこれを扱わないと、削除の提案の行が表の最後に「🟢 待つ」として並ぶ。

**候補:** 0093 が先に入っていれば、削除の提案の有無を行の値として宣言し、0093 が置いた急ぎの度合いの対応表の関数と文書の規則の関数に、それぞれ要件どおりの位置で 1 行を足す。0092 が先に入るなら、この項目は当てはまらない。0093 の計画書が、自分の PR の前に削除の提案が `main` にあるかを確かめ、0093 の中で足す。2 つの PR が並行して開いていたときに備え、0092 の計画書も、削除の提案を実装する PR のマージの直前に、0093 の対応表が `main` にあるかを確かめ直す手順を持つ。`Row.Idle` は、削除の提案がある行には付けない。0093 の AC-05・AC-07 の規則 2・AC-15 の確かめ（削除の提案がある行が「あとで」・人・文書「なし」で、「あとで」の位置に並ぶこと）を、0092 の計画書に入れる。

**関連:** 0093 の F-001・F-003・F-004、AC-05・AC-07・AC-15。0092 の F-005・F-006

## H-10: `--protocol` の番号を上げる値（0093 から）

**懸念:** 0092 の PR-7 と 0093 の出力の形を変える PR は、どちらも `Protocol`（`internal/chief/records.go:28`）を `1` から `2` に上げる設計である（0092 設計書 3.1、[0093 設計書](../0093_chief_status_sheet/02_architecture.md) 3.8）。2 つのタスクは並行して進み、どちらが先に `main` に入るかは決まっていない。0093 の計画書は、`Protocol` を実装するときの `origin/main` の値に 1 を足した値にし、後からマージする PR がマージの直前に確かめ直すと決めた（[0093 計画書](../0093_chief_status_sheet/03_implementation_plan.md) の「計画の際に決めたこと」）。3 つの道具に共通するこの規則は、タスク 0099（[#933](https://github.com/isseis/yt2column/issues/933)）が CLAUDE.md と ADR-0014 に置く。

**なぜ重要か:** 後から入る方が `2` のままにすると、出力の形が違う 2 つの版が同じ番号になり、`/chief` の定義と道具の照合（chief 利用ガイドの「2. インストール」）が版の違いを見分けられない。古い定義と新しい道具を組み合わせても `protocol_mismatch` で止まらず、定義が知らない形の出力を読み違える。

**候補:** 0092 の PR-7 も、`Protocol` を実装するときの `origin/main` の値に 1 を足した値にする（0093 が先に入っていれば `3`）。`/chief` の定義と chief 利用ガイドの番号は、今のガードテスト（`cmd/chief/docs_test.go` の `TestDocumentedProtocolMatches`・`TestGuideValuesMatchTool`）が定数と比べるので、定数に合わせて直す。0092 の計画書の「`Protocol` 2」「`--protocol 2`」の記述は、この値に読み替える。2 つの PR が並行して開いているときは、後にマージする方が、マージの直前に `origin/main` の値を確かめ直し、同じ値なら 1 つ上げる。

**関連:** 0092 の決定 3（PR-7）、0093 の H-01
