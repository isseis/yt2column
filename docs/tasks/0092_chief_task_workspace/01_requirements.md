## 1. 概要 (Overview)

**目的:** 本書は、chief（[0088 要件定義書](../0088_chief_of_staff/01_requirements.md)）に加える 2 つの機能の要件を定義する。1 つは、人が示した issue から、タスク用の git の worktree と Herdr の workspace を作り、エージェントを起動して `/mkreq` を送ること。もう 1 つは、タスクが終わった workspace を、人の確認を得て消すことである。

**背景:**

今は、タスクを始めるたびに、人が手で worktree を作り、そのディレクトリを開いた workspace を作って、シェル・OpenCode・Claude Code の pane を開いている（0088 要件定義書の 1 章の背景、[chief 利用ガイド](../../dev/guides/chief_guide.md) の「1. 前提条件」の「workspace の作り」）。chief の今の振る舞いは次のとおりである。

-   chief は、タスクのない workspace のうち、エージェントが入力を受け付ける状態のものへ、人が示した issue の `/mkreq` を送る（0088 要件定義書の AC-38、`internal/chief/request.go:344-353`）。そうした workspace は、0088 の表で「次を提案」の行になり、そこから選ぶ。workspace は人が用意する（0088 要件定義書の「要件定義の際に決めたこと（2026-11-11）」の `/mkreq` の項）。
-   chief はタスクを worktree のブランチから読む。HEAD が detached の worktree は、ブランチからタスクの有無が分からないので「要確認」にする（`internal/chief/state.go:259-262`）。この行は、表のほかのすべての行の後に並ぶ（0088 要件定義書の AC-03）。
-   `/runpr` は、タスクの最後のプランの PR をマージした後、HEAD を `origin/main` で detached にし（`.claude/commands/runpr.md:1254-1256`）、要件定義書の `対応 issue` を閉じる（`.claude/commands/runpr.md:1257-1282`）。そのため、完了したタスクの worktree からは、ブランチでタスクを読めない。
-   リポジトリの `.claude/settings.json` は、Claude Code のセッションに `herdr agent start`・`herdr workspace close`・`herdr worktree remove` などの呼び出しを禁じ（`.claude/settings.json:8-32`）、`chief` の呼び出しを確認なしに許す（`.claude/settings.json:6`）。道具 `chief` は子のプロセスとして `herdr` を呼ぶので、この拒否の影響を受けない（chief 利用ガイドの「6. `.claude/settings.json` の拒否」）。
-   chief の記録は、送るコマンドとタスクを決めるためには使わない（[ADR-0046](../../dev/adr/0046-chief-of-staff.md) の決定）。

対応 issue: [#839](https://github.com/isseis/yt2column/issues/839)（親: [#836](https://github.com/isseis/yt2column/issues/836)、関連: [#837](https://github.com/isseis/yt2column/issues/837)・[#838](https://github.com/isseis/yt2column/issues/838)（タスク 0088））

**本書の記述範囲:** 本書は、chief が何を作り、何を送り、何を消し、何を消さないかという観測できる振る舞いを定める。次の事項は設計（`02_architecture.md`）で決める。

-   道具のサブコマンドと引数と出力の形
-   Herdr と git の呼び出し方（`herdr worktree create` を使うかなど）
-   pane の配置
-   エージェントが起動したことの確かめ方と待つ時間
-   作ったことの記録の置き場所と形
-   問いと表示の文言、拒否の理由の値の綴り
-   テストの手段

要件の段階で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #839 で決めたこと:**

-   **タスク用の worktree を git で作り、Herdr の workspace をその worktree のディレクトリで開く。シェルのほかに 2 つの pane を開いて、OpenCode と Claude Code を起動する。** 今は人が手で行っている形を、そのまま自動にするためである。ADR: [ADR-0046](../../dev/adr/0046-chief-of-staff.md) を更新する。
-   **人は chief で issue 番号を答えるだけでよい。worktree のパスと workspace の名前は chief が決める。chief は worktree と workspace を作り、エージェントを起動し、Claude Code の pane に `/mkreq <issue>` を送る。** 人が名前を考えたり、`git worktree` や Herdr を手で操作したりしなくて済むようにするためである（0088 の PR-7 の実地の確かめの後に、人が求めた。2026-11-16）。ADR: ADR-0046 を更新する。
-   **タスクのすべての PR がマージされたら、chief は人の確認を得て、workspace を閉じ、worktree を消す。消す前に、未コミットの変更と push していないコミットがないことを確かめる。** 作業を失わずに、終わった workspace を片付けるためである。ADR: ADR-0046 を更新する。
-   **タスクのブランチとタスクのディレクトリの名前は、今までどおり `/mkreq` が issue から決める。** 名前を二重に決めないためである。ADR: なし（今の `/mkreq` の規則を変えないため）。

**要件定義の際に決めたこと（2026-11-16）:**

-   **進め方は通常の進め方にする。対象外の判断は「対象外」で、上書きはない。** chief が、リポジトリの外にディレクトリを作って消し、ほかのエージェントを起動するようになる。これは開発用ツールの信頼の境界を変えるので、簡易な進め方の対象外である（[requirements_process.md](../../dev/conventions/requirements_process.md) の「Simple Process」の「Excluded changes」）。ADR-0046 の決定を変え、道具、コマンドの定義、CLAUDE.md、利用ガイドに及ぶことも理由である。ADR: なし（進め方の選択はこのタスクの中で閉じるため）。
-   **worktree のパスと workspace の名前は、issue 番号から機械的に決める。パスは `~/.herdr/worktrees/yt2column/issue-<N>`、workspace の名前は `issue-<N>` とする（`<N>` は issue 番号）（F-003）。** こうすれば、chief は issue の題名などの中身で振る舞いを選ばずに済み、CLAUDE.md の「Declare, don't infer」に合う。`issue-<N>` の部分に、chief が送れない文字（`_` など。chief 利用ガイドの「8. 既知の制限」の「worktree のパスの文字」）は入らない。人に確かめる問いも増えない。`/mkreq` の後は、表の行にタスクの番号が出るので区別できる。issue の内容から名前を付けて人が確かめる案は採らない。ADR: ADR-0046 を更新する。
-   **作る worktree の HEAD は、`origin/main` から detached にする（F-003）。** `/mkreq` は `origin/main` からタスクのブランチを作る（[task-pr-handoff.md](../../../.claude/commands/_lib/task-pr-handoff.md) の Part A の step 4）。一時的なブランチを作ると、`/mkreq` がタスクのブランチへ移った後に残ってしまう。作った直後の worktree は、`/mkreq` がブランチを作るまで「要確認」になる（`internal/chief/state.go:259-262`）。ただし chief は作った直後に `/mkreq` を送る（F-004）ので、妨げにならない。一時的なブランチ `issue-<N>` を作る案は採らない。ADR: ADR-0046 を更新する。
-   **chief が削除を提案するのは、chief が作った workspace のうち、作ったときの issue のタスクが完了したものだけにする（F-006）。** 人が手で作った workspace は対象にしない。完了したタスクの worktree は `origin/main` で detached になり、ブランチからタスクを読めない。そこで chief は、作ったときに記録した issue 番号を使い、その issue を `対応 issue` とするタスクを `origin/main` で探して、完了したかを確かめる。
    -   これは、記録を、削除の候補を名指すためにも使う点で、ADR-0046 の記録の決定を広げる。名指された workspace は、git、Herdr、`origin/main` の文書で確かめ直す。記録を送るコマンドとタスクの決定に使わないことは変えない。
    -   chief が作った workspace のうちタスクのないもの（`/mkreq` が止まったものなど）を対象に含める案は採らない。タスクがなければ、`origin/main` で完了を確かめる相手がなく、`/mkreq` が途中で止まったのか、これから使うのかを chief が見分けられないためである。
    -   ADR: ADR-0046 を更新する。
-   **完了した、chief が作った workspace の行は、状態を「タスク完了」、次にやることを「削除を提案」と示す。削除の提案は新しい種類として、人の判断を待つものの一覧の「そのほかの提案」の後に並べる（AC-20・AC-22）。** 0088 の規則のままでは、この行は HEAD が detached なので「要確認」になり、削除を提案していることと食い違うためである。これは、0088 要件定義書の F-001 の状態の決め方と、F-002・F-003 の人の判断を待つものの種類と並べ方に足す。行を「要確認」のままにして提案だけを足す案は採らない。ADR: なし（表示と並べ方の細部で、ADR-0046 の決定を変えないため）。
-   **新しいタスクを始める入口として、人の判断を待つものの一覧の最後に「新しいタスクを始める」を常に置く。人が選ぶと、chief は issue 番号を尋ね、次に始める先（新しい workspace か、既存の workspace か）を尋ねる（F-001）。** 0088 では、`/mkreq` はタスクのない workspace の「次を提案」の行からしか選べず、workspace がなければ始められないためである。issue 番号の入力だけで始める案は採らない。ADR: なし（`/chief` の問いの細部で、ADR-0046 の決定を変えないため）。
-   **worktree・workspace の作成と削除、エージェントの起動は、道具 `chief` だけが行う。セッションへの `.claude/settings.json` の拒否は緩めない（F-003・F-007、4.2）。** chief のセッションが道具に渡すのは、人が答えた issue 番号と、人が選んだ workspace だけである。パスと名前は道具が決める。0088 と同じく、セッションが信頼できない文字列に従っても、決まった範囲の外の操作をしないようにするためである（[ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md)、ADR-0046）。拒否を緩めてセッションに herdr を直接呼ばせる案は採らない。ADR: ADR-0046 を更新する。
-   **chief は、エージェントを、人の代わりに許可や信頼を与える引数を付けずに起動する。フォルダの信頼を問う画面などが出たときは、`/mkreq` を送らず、人がその pane で答えるよう示す（AC-10・AC-16・AC-17）。** 確認を飛ばす起動の仕方は、chief が人の代わりにリポジトリの hooks や設定を信頼することになるためである。今は、同じリポジトリの worktree では Claude Code がフォルダの信頼の確認を出していないように見えるが、確かめてはいない。確認が出るかと、`herdr worktree create` の `--trust-repository` が何をするかは、設計で確かめる（design_handoff.md の H-03）。確認を飛ばして起動する案は採らない。ADR: ADR-0046 を更新する。
-   **作る前に、GitHub から issue を読んで確かめる。存在しない issue、閉じた issue、GitHub のラベル `draft` が付いた issue（下書きの issue）、PR の番号は拒む。題名は作った結果に示す（F-002）。chief を起動したことで承認する読み取り専用のネットワークの操作に、issue を読む操作を加える（4.2、5 章）。** 存在しない番号、閉じた issue、下書きの issue、PR の番号で workspace を作らないためである。このような workspace にはタスクができないので、削除の提案の対象にもならず（F-006）、残り続ける。下書きの issue は、まだタスクを始めてはならない issue で、`/mkreq` も下書きの issue では止まる（issue #934）。そのため、chief が下書きの issue で作った workspace には、`/mkreq` を送ってもタスクができない。下書きの issue を拒むことは 2026-11-17 に足した（決定の変更）。打ち間違えた番号がほかの開いた issue に当たる場合は、この確かめでは防げない。結果に示す題名で人が気づき、`/mkreq` が最初に尋ねる問いで止められる。chief では確かめず、`/mkreq` の確かめに任せる案は採らない。ADR: ADR-0046 を更新する。
-   **消す前の確かめは、次のように厳しくする（F-007）。追跡していないファイルを含めて変更がないこと。HEAD が、fetch した後の `origin/main` から届くこと。workspace のどのエージェントも実行中でなく、質問でも止まっていないこと。** issue が挙げる 2 つの条件に加え、エージェントの作業を途中で失わないためである。push していないコミットを HEAD についてだけ確かめるのは、chief がブランチを消さず（AC-31）、ほかのブランチのコミットは worktree を消しても失われないためである。完了したタスクの worktree は `origin/main` で detached になっているはずなので、普通の場合はこの形でも妨げにならない。確かめを、未コミットの変更がないことと、HEAD が origin のどれかのブランチから届くことだけにし、エージェントの状態は問わない案は採らない。ADR: ADR-0046 を更新する。
-   **issue を閉じること（issue #839 の「やること」の 4）は、このタスクの範囲外とする。** `/runpr` が、タスクの最後のプランの PR の後に、すでに `対応 issue` を閉じている（`.claude/commands/runpr.md:1257-1282`）ためである。ADR: なし（chief の振る舞いを変えないため）。
-   **作成の途中で失敗したときは、止まって、作ったものと失敗した段を示す。作ったものは消さず、`/mkreq` も送らない（AC-12）。** 消す操作を減らし、片付けは人が確かめてから行うためである。作ったものを消してから止まる案は採らない。ADR: ADR-0046 に含める（決定の作成の項目に書く）。
-   **`issue-<N>` のパスか worktree か workspace がすでにあるときは、何も作らずに拒む（AC-11）。その issue のタスクがすでにあるかは、chief は確かめず、`/mkreq` の step 1 に任せる。** 存在しない issue で作った workspace は残り続ける（上の issue の確かめの項）が、すでにタスクのある issue で作った workspace は、そのタスクが完了したときに、記録した issue のタスクとして削除の提案の対象になり（AC-23）、残り続けないためである。すでにあるものへ `/mkreq` を送る案は採らない。ADR: ADR-0046 に含める（決定の作成の項目に書く）。
-   **タスクのない既存の workspace へ `/mkreq` を送る今の流れ（0088 要件定義書の AC-38）は残し、始める先の選択肢に新しい workspace を作ることを加える（F-001）。既存の workspace を選んだときは、issue を確かめない（AC-04）。** 人が手で作った workspace でも、今までどおり始められるようにするためである。既存の workspace では、確かめないまま `/mkreq` が止まっても、新しく残るものがない。新しく作ることだけにする案は採らない。ADR: なし（0088 の振る舞いを変えないため）。
-   **作った後に `/mkreq` を送れなかったときは、送れなかったことと理由を示し、人がその pane で `/mkreq <N>` を打つ。chief は、その workspace に `/mkreq` を改めて提案しない（AC-17）。** 作った直後の worktree は detached なので、chief はブランチからタスクのない workspace だと分からない。記録からタスクの有無を決めると、ADR-0046 の記録の決定をさらに広げることになるためである。chief が作ったばかりの worktree をタスクのない workspace とみなして `/mkreq` を提案する案は採らない。ADR: ADR-0046 に含める（結果に書く。記録の決定は変えない）。

**実装の際に決めたこと（2026-11-18）:**

-   **AC-28 で、AC-23 の条件がもう満たされないときは、それだけを通らなかったものとして示し、ほかの確かめは行わない（実装計画書の決定 21、人が承認した）。** ほかの確かめは、AC-23 の条件を満たす workspace（削除の候補）を前提にするためである。何も消さないことは変わらない。PR-6 のレビューが、AC-28 の「通らなかったものを示す」とこの振る舞いが食い違うと指摘した。ADR: なし。
-   **AC-02 で、始める先を尋ねる前に issue を GitHub から読み、題名を示す。拒む issue なら、そこで止める。既存の workspace を選ぶ場合も、この確かめを通す（AC-04。実装計画書の決定 22、人が承認した）。** PR-7 の実地の確かめで、人が、番号を打ち間違えても作る前に気づけるよう、始める先を選ぶ前に issue の題名を見たいと求めた。作る前の確かめ（AC-05）は、作る直前にもう一度行う。既存の workspace へ送る経路でも、閉じた issue や下書きの issue で `/mkreq` を始めないので、AC-05 の拒否は害にならない。GitHub を読めないときは、この経路も止まる。ADR: なし（ADR-0046 の「issue 番号を答えると道具が GitHub から issue を読み、拒む」決定の中で閉じるため）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   人が issue 番号を答えるだけで、タスクの workspace が用意され、`/mkreq` が始まるようにする。
-   終わったタスクの workspace を、作業を失わずに、人の確認だけで片付けられるようにする。
-   作ることと消すことを道具の決まった操作に限り、chief の信頼の境界を必要以上に広げない。

### 2.2. スコープ (In Scope)

-   新しいタスクを始める入口と、始める先の選択（F-001）
-   作る前の issue の確かめ（F-002）
-   worktree と workspace の作成と、エージェントの起動（F-003）
-   作った workspace への `/mkreq` の送信（F-004）
-   完了した、作った workspace の行の示し方（F-005）
-   削除の提案（F-006）
-   消す前の確かめと削除（F-007）
-   ADR-0046 の更新、`/chief` の定義（`.claude/commands/chief.md`）の更新、CLAUDE.md の「Tool Execution Safety」・「Go Idioms」・コマンドの一覧の更新、chief 利用ガイドの更新（5 章）

### 2.3. スコープ外 (Out of Scope)

-   issue を閉じること。`/runpr` が最後のプランの PR の後に行う（要件定義の際に決めたこと）。
-   人が手で作った workspace の削除と、chief が作った workspace のうちタスクのないもの（`/mkreq` が止まったものなど）の削除。人が端末で行う。chief がタスクのない workspace の完了を確かめられないためである（要件定義の際に決めたこと）。
-   作った後に `/mkreq` を送れなかった workspace に、chief が `/mkreq` を改めて提案すること（要件定義の際に決めたこと）。
-   タスクのブランチ（ローカルと `origin`）の削除。マージの後のブランチの片付けは `/mergepr` が行う。
-   issue の内容から workspace の名前を付けること、作った後に名前を変えること（要件定義の際に決めたこと）。
-   `.claude/settings.json` の拒否を緩めること（要件定義の際に決めたこと）。
-   pane の配置を人が選べるようにすること。issue が求めていないためである。
-   OpenCode のモデルの切り替え。0088 と同じく、モデルが合わないときは人がその pane で切り替える（0088 要件定義書の AC-35）。
-   作成と削除を、人が選ばずに自動で行うこと。issue が、削除の前に人の確認を求めているためである。

## 3. 機能要件 (Functional Requirements)

本書の用語は 0088 要件定義書の 3 章に従う（chief の workspace、タスクの workspace、エージェント、入力を受け付ける状態）。加えて、本書では次の用語を使う。

-   **作った workspace**: chief が F-003 で作った workspace と、その worktree の組。chief は、作ったことを記録に残す。
-   **タスクの完了**: 0088 要件定義書の F-001 の「タスク完了」と同じく、計画のすべての PR がマージされていること。
-   **人の確認**: 人が chief の問いに答えて、操作をしてよいと示すこと。chief が機械的に調べることは「確かめ」と呼び、区別する。

### 3.1. 機能一覧

#### F-001: 新しいタスクを始める入口と、始める先の選択

人がいつでも新しいタスクを始められるようにし、始める先を選べるようにする。

**Acceptance Criteria**:
-   **AC-01**: chief は、人の判断を待つものの一覧の最後（0088 要件定義書の AC-13 の「そのほかの提案」と、本書の削除の提案の後）に、「新しいタスクを始める」を常に示す。`once` の問いで示せる数を超えたときは、0088 要件定義書の AC-14 のとおり、問いの中で名前を挙げ、人はその名前を答えに書いて選べる。
-   **AC-02**: 人が「新しいタスクを始める」を選び issue 番号を答えると、chief は AC-06 の形を確かめ、AC-05 と同じく issue を GitHub から読む。AC-05 で拒む issue なら、拒んだ理由を示して何もしない。通れば、issue の番号と題名を示してから、始める先を尋ねる（実装の際に決めたこと（2026-11-18））。始める先は、新しい workspace を作ること（F-002〜F-004）と、0088 要件定義書の AC-38 を満たす既存の各 workspace と、「何もしない」である。既存の候補がないときは、新しく作ることと「何もしない」だけを示す。
-   **AC-03**: 0088 の「次を提案」の行から、タスクのない workspace へ `/mkreq` を選ぶ流れは、今までどおり残る。
-   **AC-04**: 既存の workspace を選んだときの振る舞いは、0088 要件定義書の AC-38 のとおりである。issue は AC-02 で確かめてあり、選んだ後に確かめ直さない（実装の際に決めたこと（2026-11-18））。

#### F-002: 作る前の issue の確かめ

人が新しい workspace を作ることを選んだとき、chief は何かを作る前に issue を確かめる。

**Acceptance Criteria**:
-   **AC-05**: chief は、新しい workspace を作る前に、このリポジトリの issue を GitHub から読み、番号・状態・題名・ラベルと、PR かどうかを確かめる。issue が存在しないとき、閉じているとき、ラベル `draft` が付いているとき、番号が PR を指すとき、読めないとき、または応答が 4.2 の受け付ける形に合わないときは、何も作らずに拒み、拒んだ理由（4.2 の拒否の種類）を示す。
-   **AC-06**: chief は、issue 番号として、`0` で始まらない 1 個以上 9 個以下の ASCII の数字だけを受け付ける。これは、0088 で `/mkreq` の issue 番号に使う規則（`internal/chief/paneinput/paneinput.go:59-80`）と同じである。それ以外（`#839`、空白を含むもの、符号のあるもの、全角の数字を含むもの、10 桁以上のものなど）は、何も作らずに拒み、受け付ける形を示す。
-   **AC-07**: 作った結果には、issue の番号と題名が示される。題名は示すためだけに使い、パス、名前、送る入力を左右しない。

#### F-003: worktree と workspace の作成と、エージェントの起動

F-002 の確かめを通った issue について、worktree と workspace を作り、エージェントを起動する。

**Acceptance Criteria**:
-   **AC-08**: chief は `origin/main` を fetch する。その後、`~/.herdr/worktrees/yt2column/issue-<N>` に worktree を作り、その HEAD を、fetch した後の `origin/main` のコミットで detached にする。ブランチは作らない。
-   **AC-09**: chief は、その worktree のディレクトリを開いた `issue-<N>` という名前の Herdr の workspace を、chief が動いている Herdr のセッションに作る。workspace は、シェルの pane、OpenCode が動く pane、Claude Code が動く pane の 3 つを持つ。Claude Code の pane も OpenCode の pane も、ちょうど 1 つである。
-   **AC-10**: 新しい pane で chief が起動するのは、Claude Code と OpenCode だけである。どちらも、権限の確認を飛ばす引数や、フォルダを信頼させる引数など、人の代わりに許可や信頼を与える引数を付けずに起動する。作った workspace のエージェントへ送る入力は、0088 要件定義書の F-006 の表のものだけである（F-004）。
-   **AC-11**: 次のときは、何も作らずに拒み、理由を示す。
    -   `~/.herdr/worktrees/yt2column/issue-<N>` にファイルかディレクトリがすでにあるとき。そのパスの worktree が git に登録されているとき。そのパスを開いた workspace が Herdr にあるとき。この場合は、すでにあるものを示す。
    -   作る worktree のパスが、chief が送れない文字（chief 利用ガイドの「8. 既知の制限」の「worktree のパスの文字」）を含むとき（たとえば、ホームディレクトリのパスに `_` があるとき）。
    -   `origin/main` の fetch が失敗したとき。
-   **AC-12**: 作る途中のどこかの段が失敗したときは、そこで止まる。作ったもの（worktree のパス、workspace、pane、起動したエージェント）と、失敗した段とその理由を示す。作ったものは消さず、`/mkreq` を送らない。
-   **AC-13**: 作成は、人が選んだときにだけ行う。chief の待ち受けの中で自動では作らない。作成の間に、ほかの workspace と chief の workspace には何も送らず、何も変えない。
-   **AC-14**: chief は、worktree を作った時点で、作ったことの記録（worktree のパス、workspace、issue 番号）を残す。AC-12 で途中で止まったときも、記録は残す。同じパスについて、前に作ったことの記録が残っていても、AC-11 の拒む条件に当たらなければ、chief は前の記録を無効なものとして扱い、新しい記録で置き換えて作る。前の記録の issue 番号は、新しい workspace の削除の提案に使わない。

#### F-004: 作った workspace への `/mkreq` の送信

F-003 を終えた workspace へ、`/mkreq` を送る。

**Acceptance Criteria**:
-   **AC-15**: chief は、作った workspace の Claude Code の pane へ、F-002 で確かめた番号の `/mkreq <N>` を送る。送り先のエージェントとモデル、送る前の確かめ（`/clear`・`/model` とモデルの切り替えの確かめ、入力欄が空であること）は、0088 要件定義書の F-006（AC-34・AC-36）に従う。作った直後の worktree は、HEAD が detached なので 0088 の規則では「要確認」の行になるが、この送信は作成に続けて行うもので、行の状態によっては止めない。
-   **AC-16**: chief は、起動した Claude Code が入力を受け付ける状態になるのを、設計で決める時間まで待つ。その時間のうちに入力を受け付ける状態にならないとき、または Claude Code が質問の画面（フォルダの信頼を問う画面を含む）で止まっているときは、送らない。
-   **AC-17**: AC-15 か AC-16 の確かめが通らずに `/mkreq` を送らなかったときは、送らなかったことと理由を示す。質問の画面で止まっていたときは、人がその pane で答えるよう示す。質問の画面で止まっていたかどうかにかかわらず、人がその pane で `/mkreq <N>` を打つよう示す。chief はその workspace を残し、後の周でもその workspace に `/mkreq` を提案しない。
-   **AC-18**: `/mkreq` を送った後に送れたかが分からなくなったときは、0088 要件定義書の AC-37 のとおり、送り直さず、その workspace への送信を止める。
-   **AC-19**: 作った workspace は、chief の表に、ほかのタスクの workspace と同じ規則（0088 要件定義書の F-001）で示される。例外は F-005 の行だけである。`/mkreq` がタスクのブランチを作った後は、そのタスクの行として示される。

#### F-005: 完了した、作った workspace の行

作ったときの issue のタスクが完了した workspace を、表で「タスク完了」と示す。

**Acceptance Criteria**:
-   **AC-20**: 次のすべてを満たす、作った workspace の行は、0088 要件定義書の F-001 の規則では「要確認」になる場合でも、状態を「タスク完了」、タスクの番号を記録した issue のタスクの番号、次にやることを「削除を提案」と示す。
    -   AC-23 の条件を満たす。
    -   HEAD が detached である。
    -   どのエージェントも、実行中でも質問で止まってもいない。
-   **AC-21**: 作った workspace でも、AC-20 に当たらないものは、0088 要件定義書の F-001 のとおりに示す。

#### F-006: 削除の提案

タスクが完了した、作った workspace の削除を、人の判断を待つものとして示す。

**Acceptance Criteria**:
-   **AC-22**: chief は、削除の提案を、人の判断を待つものの新しい種類として示す。種類の順は、0088 要件定義書の AC-13 の 4 つの種類の後で、F-001 の「新しいタスクを始める」の前である。同じ種類の中では、0088 要件定義書の AC-13 のとおり、待っている時間の長いものが先に並ぶ。
-   **AC-23**: chief は、次のすべてを満たす workspace だけについて、削除を提案する。
    -   chief が作った workspace であると、chief の記録から読める。
    -   その workspace が、記録と同じ worktree のパスを開いたまま、Herdr にある。
    -   chief が最後に fetch した後の `origin/main` に、記録した issue 番号を `対応 issue` として挙げるタスクがちょうど 1 つあり、そのタスクが完了している。`対応 issue` として数えるのは、要件定義書の `対応 issue:` の行のうち、最初の `（` より前に挙がる issue のリンクだけである。`（` の中の親 issue と関連 issue は数えない。そのため、ある issue が、タスク X の `対応 issue` であり、タスク Y の関連 issue でもあるときは、タスク X だけが当たる（X と Y は説明のための仮の名前）。
-   **AC-24**: chief が作っていない workspace（chief の workspace と、人が手で作った workspace を含む）は、削除を提案しない。作った workspace でも、次のときは削除を提案しない。記録を読めないとき。記録した issue のタスクが `origin/main` にないとき、または 2 つ以上あるとき。そのタスクが完了していないとき。
-   **AC-25**: 提案は、次のものを示す。workspace の名前、worktree のパス、issue の番号、タスクの番号、workspace の pane の数、その時点の AC-28 の確かめの結果（通ったか、どれが通らなかったか）。
-   **AC-26**: chief は、人が選ばずに削除しない。マージの後の自動送信（0088 要件定義書の F-007）と chief の待ち受けは、削除を提案するだけで、削除しない。

#### F-007: 消す前の確かめと削除

人が削除の提案を選んだとき、人の確認を得て、確かめてから消す。

**Acceptance Criteria**:
-   **AC-27**: 人が削除の提案を選ぶと、chief は、消す workspace の名前、worktree のパス、workspace のすべての pane が閉じられることを示して、消すかを尋ねる。人が消すと答えたときだけ、AC-28 に進む。
-   **AC-28**: 消す直前に、chief は `origin/main` を fetch してから、次のすべてを確かめ直す。どれかが通らないか、読めないときは、何も消さず、通らなかったものを示す。ただし、AC-23 の条件がもう満たされないときは、それだけを示し、ほかは確かめない（実装の際に決めたこと（2026-11-18））。
    -   AC-23 の条件がまだ満たされている。
    -   worktree に、追跡しているファイルの変更（ステージしたものを含む）も、追跡していないファイルもない。git が無視するファイルは数えない。
    -   worktree の HEAD のコミットが、`origin/main` から届く。
    -   workspace のどのエージェントも、実行中でも、質問で止まってもいない（0088 要件定義書の F-001・F-002 の見分けによる）。どのエージェントの状態も読める。
-   **AC-29**: `origin/main` の fetch が失敗したときは、何も消さない。
-   **AC-30**: AC-28 を通ったとき、chief は workspace（そのすべての pane とエージェントを含む）を閉じ、worktree を消す。
-   **AC-31**: chief はほかのものを消さない。タスクのブランチ、ほかの worktree、worktree のディレクトリの外のファイル（chief 自身の記録を除く）は残る。
-   **AC-32**: 消す途中で失敗したときは、そこで止まり、残ったもの（workspace、worktree のディレクトリ、git の worktree の登録）と、失敗した段とその理由を示す。自分から消し直さない。残ったものは人が片付ける。
-   **AC-33**: 消し終えた workspace は、chief の表から消え、二度と削除を提案されない。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   作成と削除は、人が選んだときに 1 回ずつ行う操作で、かかる時間はエージェントの起動と Herdr の操作で決まる。エージェントの起動を待つ時間の上限は、設計で決める（AC-16）。
-   削除の提案（AC-23・AC-25）は、chief の待ち受けの周ごとに、作った workspace の数だけ git と `origin/main` の文書を読む。0088 の周が、タスクの workspace ごとにすでに同じ種類の読み取りをしているので、新しい時間の要件は置かない。

### 4.2. セキュリティ (Security)

条件付きのガイド（`docs/dev/security.md`）は N/A。chief は開発用の道具で、その契機（`yt-dlp` の起動、API キー、キャッシュのディレクトリ、LLM の API への送信、プロンプトや記事への信頼できないテキストの埋め込み）のどれにも触れないためである。issue を読む操作は GitHub への読み取りで、LLM の API への送信ではない。ただし、開発用ツールの信頼の境界に当たるので、次を要件とする。

-   **信頼の境界。**
    -   chief は、0088 で決めた入力の送信に加えて、次のことを行う。リポジトリの外に worktree のディレクトリを作って消す。Herdr の workspace を作って閉じる。エージェントを起動する。
    -   これらは道具 `chief` が行う。パスと名前は、AC-06 の形の issue 番号だけから決まり、セッションが渡す文字列や issue の題名からは決まらない。
    -   エージェントは、人の代わりに許可や信頼を与える引数を付けずに起動する（AC-10）。
    -   消すのは、AC-23 を満たし、AC-28 の確かめを通った workspace だけである。
    -   chief のセッションへの `.claude/settings.json` の拒否は緩めない。
    -   ADR-0046 に記録する。
-   **道具が守ることと、守らないこと。** 道具が守るのは、AC-23 と AC-28 の条件である。人の確認（AC-27）は `/chief` のセッションが尋ねるもので、道具はそれが行われたかを確かめられない。`.claude/settings.json` は `chief` の呼び出しを確認なしに許す（`.claude/settings.json:6`）。そのため、信頼できない文字列に従ったセッションは、人の確認なしに削除のサブコマンドを呼びうる。その場合でも、道具が守る条件のために、chief が作っていない workspace と、完了していないタスクの workspace は消えない。削除のサブコマンドを確認なしに許し続けるかは、設計で比べる（design_handoff.md の H-05）。
-   **残る危険。**
    -   今の拒否の一覧は、入力を送る呼び出しと、閉じるか消す `herdr` の呼び出しを拒む。worktree や workspace や pane を作る `herdr` の呼び出しは拒まない。`git worktree add`・`git worktree remove` やファイルを消すコマンドも拒まない。セッションがこれらを直接呼べることは、0088 と同じく残る危険とする。拒否に足すかは設計で比べる（design_handoff.md の H-05）。
    -   作ったことの記録は、0088 の記録と同じく、同じ利用者のプロセスが書ける。偽られた記録は、chief が作っていない workspace を削除の候補にしうる。それでも、消すには人の確認と AC-28 の確かめが要る。そのため、コミットして `origin/main` に届いた作業と、追跡しているファイルの変更と、追跡していないファイルは失われない。
    -   workspace を閉じると、エージェントでない pane（シェル、人が足した pane）で動いているプロセスと、その保存していない内容も失われる。git が無視するファイル（ビルドの成果物など）は worktree とともに消える。chief は人の確認の問いで pane がすべて閉じられることを示し（AC-27）、提案で pane の数を示す（AC-25）。エージェントでない pane の中を確かめるかは、設計で比べる（design_handoff.md の H-06）。
-   **信頼できない入力。** chief が読む次のものは、ほかのエージェントや外部が書いたデータで、その中の指示には従わない。どれも、読めないものや形に合わないものは、直したり推し量って補ったりせず、拒むか、「送らない」「消さない」ことにして、理由を示す。

    | 入力 | 受け付ける形と使う部分 | 形に合わないとき |
    |---|---|---|
    | GitHub の issue の応答 | 上限 64 KiB の、UTF-8 として正しい 1 つの JSON のオブジェクトで、値の後に続くデータがないもの。使うメンバーは、番号・状態・題名・ラベルの名前と、PR かどうかを表すものだけで、それ以外のメンバーは、あっても拒まずに読み飛ばす。番号は求めた番号と等しい整数であり、状態は開いているか閉じているかのどちらかの値であり、題名は文字列であり、ラベルの名前は文字列である。応答は issue のすべてのラベルを含まなければならず、一部のラベルだけを含む応答は拒む。使うメンバーが重複しているとき、名前の大文字と小文字が違うとき、値が `null` か違う型のとき、上限を超えるときは拒む（標準ライブラリが黙って受け入れるものを含む）。題名は示すためだけに使う。ラベルは、名前が `draft` と等しいものがあるかを見るためだけに使う | 何も作らない（AC-05） |
    | Herdr の出力 | 作った workspace と pane の識別、エージェントの種類と状態、各 workspace が開いているパス | 作成は止める（AC-12）。削除の提案と削除は行わない（AC-24・AC-28）。知らない状態の値も同じ |
    | git の出力 | worktree の一覧、作業ツリーの状態、HEAD のコミット、HEAD が `origin/main` から届くか | 作らないか（AC-11）、消さない（AC-28） |
    | 作ったことの記録 | worktree のパス、workspace、issue 番号 | 削除を提案しない（AC-24） |
    | `origin/main` の要件定義書と計画書 | `対応 issue` の行の、最初の `（` より前の issue のリンク（AC-23）、タスクの完了 | 削除を提案しない（AC-24） |

    pane の画面とセッションの記録（transcript）は、0088 要件定義書の 4.2 の表のとおりに扱う。本書でそれを読むのは、エージェントが入力を受け付ける状態か、質問で止まっているかの見分け（AC-16・AC-28）である。

    **拒否の種類。** 作成の拒否は、次の種類に分けて示す。issue 番号の形が違う、issue が存在しない、issue が閉じている、issue にラベル `draft` が付いている、番号が PR を指す、issue を読めないか形が違う、作る先がすでにある、作る先のパスに送れない文字がある、fetch に失敗した。削除の拒否は、AC-28 のどの確かめが通らなかったか、または fetch に失敗したかで分けて示す。各種類の綴り（道具の出力の値）は設計で決める。

-   **示す文字列。** issue の題名とエラーの理由は、制御文字（端末のエスケープシーケンスを含む）を chief の画面にそのまま出さず、見える形に置き換えて示す。0088 要件定義書の 4.2 の「画面のとおりに示す」と同じ扱いである。題名を示す長さの上限は設計で決め、上限で切ったときは切ったことを示す。
-   **ネットワーク。** chief が新しく行うネットワークの操作は、issue を読むこと（読み取り）と、作る前と消す前の `origin/main` の fetch（0088 ですでに承認された読み取り）だけである。GitHub への書き込み（issue の操作、push、コメント、マージ）はしない。issue を読む操作は、chief を起動したことで承認したものとし、CLAUDE.md の「Tool Execution Safety」に足す（5 章）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   作成も削除も、途中で失敗したら止まり、自分からやり直さない（AC-12・AC-32）。消すか作り直すかは人が決める。
-   同じ issue で 2 回作ろうとしても、2 つ目は拒まれる（AC-11）。
-   `/mkreq` の送信は、0088 の送信と同じく、送れたかが分からないときは送り直さない（AC-18）。

### 4.4. 互換性 (Compatibility)

-   chief 利用ガイドの「1. 前提条件」の Herdr、Claude Code、OpenCode、gh の版で確かめる。
-   人が手で作った今の workspace は、今までどおり chief の表に示され、既存の workspace への `/mkreq` も今までどおり送れる（AC-03・AC-04）。削除の提案の対象にはならない（AC-24）。

### 4.5. 保守性 (Maintainability)

-   worktree のパスと workspace の名前の規則は、1 か所に置く。
-   作成と削除の判定と操作は、テストのある Go の道具に置く方針がある（ADR-0014、ADR-0046）。どこに置くかの詳細は設計で決める。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   **ADR-0046 の更新。** 本書の決定は ADR-0046 の決定を変える。次のことを ADR-0046 に書き、本書と同じ PR で更新する。
    -   作成と削除を道具だけが行い、セッションの拒否を緩めないこと
    -   エージェントを、人の代わりに許可や信頼を与える引数なしで起動すること
    -   記録を、削除の候補を名指すことにも使うこと
    -   issue を読む操作を承認に加えること
-   **CLAUDE.md の「Tool Execution Safety」。** ネットワークに触れるコマンドは人の承認を要する。今は、`/chief` を起動したことで、chief の道具が行う読み取り専用のネットワークの操作（`git fetch origin main`・`git ls-remote`・`gh pr list`・`gh pr view`・`gh pr checks`）を承認している。これに issue を読む操作を足す。書き込みの操作は承認しないままにする。
-   **CLAUDE.md の「Go Idioms」の日本語の文字列の例外。** 方針（CLAUDE.md の「Go Idioms」）は、Go の文字列を英語にすることを求める。chief の task reader の例外（`internal/chief/task.go`）は、今は実装計画書の見出しと欄の名前だけを対象にする。F-006 は `origin/main` の要件定義書の `対応 issue` の行を読むので、その欄の名前の文字列をこの例外に足す。理由は、要件定義書が日本語の文書で、文字列がその文と等しくなければならないためである（task reader の例外と同じ理由）。どのファイルで読むかは設計で決め、決めたファイルを例外の範囲に書く。
-   **CLAUDE.md の「Declare, don't infer」。** パスと名前は issue 番号から決め、issue の題名などの文字列の中身で振る舞いを選ばない。`対応 issue` の行を読むことは、文書の決まった欄を読むことで、0088 で計画書の欄を読むのと同じく、この方針の例外にしない。
-   **0088 の決定を保つ。** 次のことは変えない。chief がタスクの workspace へ送る入力の範囲（0088 要件定義書の F-006 の表）、送り先とモデル、送れたかが分からない送信の扱い、記録を送るコマンドとタスクの決定に使わないこと。0088 要件定義書の F-001 の状態の決め方と、AC-13 の種類と並べ方には、本書の F-005・F-006・AC-01 が例外と種類を足す。
-   **`/chief` の定義、CLAUDE.md のコマンドの一覧、chief 利用ガイドの更新。** `.claude/commands/chief.md` に、新しいタスクを始める問いと、削除の提案と人の確認の問いを足す。CLAUDE.md の「Claude Commands」の `/chief` の項と、chief 利用ガイドの「1. 前提条件」の workspace の作り、「3. 使い方」、「4. サブコマンドと終了コード」、「5. 保証すること・しないこと」、「6. `.claude/settings.json` の拒否」、「8. 既知の制限」を、本書の振る舞いに合わせる。道具とコマンドの定義を照合するための番号（`--protocol`）を上げるかは、設計で決める（design_handoff.md の H-08）。

## 6. 用語集 (Glossary)

用語は [docs/translation_glossary.md](../../translation_glossary.md) と 0088 要件定義書の 6 章に従う。本書で加える用語は次のとおりである。

-   **作った workspace**: chief が F-003 で作った workspace と、その worktree の組（3 章）。
-   **タスクの完了**: 計画のすべての PR がマージされていること（3 章、0088 要件定義書の F-001 の「タスク完了」）。
-   **人の確認**: 人が chief の問いに答えて、操作をしてよいと示すこと。chief が機械的に調べる「確かめ」と区別する（3 章）。
-   **`issue-<N>`**: issue 番号 `<N>` から決まる、作った worktree のディレクトリの名前と workspace の名前（F-003）。
