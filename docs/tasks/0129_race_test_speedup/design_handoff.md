# 設計への申し送り（0129）

`01_requirements.md` を書く際に挙がった、設計（`02_architecture.md`）で決める事項である。`02_architecture.md` は、各項目について採った方法か、当てはまらない理由を記す。

## H-01: `-race` 付きのビルドの入力の大きさとその置き場所

**懸念:** `TestParseCopiedLargeInputs` の 7 つの入力は、今は共通の定数 `copiedLargeInputLimit`（`internal/transcript/copied_format_test.go:1043`）から作る。`-race` 付きのビルドだけ小さくするには、大きさをビルドごとに分ける必要がある。

**なぜ重要か:** 大きさの選び方によっては、AC-03（2 乗の確保を見分けられること）を満たせない。入力が小さいほど、入力の長さによらない固定の確保が 1 バイトあたりの確保量に占める割合が大きくなり、`-race` 付きのビルドの上限（1 バイトあたり 8,192 バイト、`copied_format_race_test.go`）を見直す必要が出うる。各入力の `wantSegments` は大きさから計算しているので、大きさに合わせて変わる。

**候補:** AC-03 の壊し方（7 つの入力のそれぞれで確保量が入力の長さの 2 乗に比例する壊し方。例えば、行ごとに残りの入力を写す）を先に決め、変更の前の 4 MiB の `-race` 付きの実行で失敗することを確かめる。壊し方は、4 MiB の `-race` 付きの実行が `go test` のタイムアウトの前に確保量の検査に届くもの（写さずに確保するなど）を選ぶ。大きさを、今の `copiedParseAllocPerByte` と同じく `copied_format_race_test.go` と `copied_format_norace_test.go` の定数に置く。大きさは、`-race` 付きのビルドで測った確保量と、2 乗の確保を起こすように壊した解析で確かめて決める。

**関連:** F-001、AC-01、AC-02、AC-03

## H-02: 並列にするサブテストの選び方

**懸念:** `TestMakeDeadcodeVerdict` のケースは `PATH` を替えたスタブや記録用の `mktemp` を使い（`cmd/yt2column/deadcode_test.go:205-224`）、`TestMakeDeadcodeScope` は子のプロセスで `make` と `go list` を走らせる。`t.Setenv` や `t.Chdir` を使うテストは `t.Parallel()` と併用できない。

**なぜ重要か:** 状態を共有するサブテストを並列にすると、結果が不安定になる（4.3）。

**候補:** 各サブテストが、環境を `exec.Cmd.Env` で子にだけ渡しているか、プロセスの環境と作業ディレクトリを変えていないかを読んで確かめ、共有するものだけを直列に残す。並列の実行で子のプロセスが同時に多く走ることによる負荷も考える。

**関連:** F-002、AC-04、AC-05

## H-03: 時間の測り方

**懸念:** issue #1166 の表はファイルごとの時間で、測り方が書かれていない。並列にしたテストの時間は、`go test -json` の各テストの `Elapsed` では一時停止の時間を含むので、テストごとでは比べにくい。1 回の計測は、機械の負荷でばらつく。

**なぜ重要か:** 測り方が決まっていないと、AC-13 と AC-14 を確かめられない。

**候補:** `go test -tags test -race -count=1 -json ./...` の出力から、テストごとの `Elapsed` と、パッケージごとの `pass` の行の `Elapsed` を取る。前と後をそれぞれ 3 回以上測る（比べ方は AC-14 が決める）。パッケージの時間がほかのパッケージの割り当てで揺れる場合は、対象のパッケージだけを `go test -tags test -race -count=1 ./internal/<パッケージ>` で測ることも考える。`deadcode` コマンドがある機械で測り、測った機械（OS、CPU の数）を記録する。

**関連:** F-005、AC-13、AC-14

## H-04: カバレッジの比べ方

**懸念:** AC-11 は、本番のコードの関数ごとの文のカバレッジが下がらないことを求める。

**なぜ重要か:** テストを小さくしたり並列にしたりして、確かめていた経路を通らなくなることを見逃さないためである。

**候補:** `make coverage-compare BASE=<変更の前のコミット>` で比べる。このツールはテストを削除するコミットのために作られたが、どの 2 つのコミットでも比べられる。`internal/cmdrunner` の `signalGroup` のように、時間の具合で揺れる関数が `FAIL` になることがあるので、揺れた場合はきれいな作業ツリーで実行し直し、すべての実行を記録する。

**関連:** F-004、AC-11

## H-05: 大きな出力のテストの大きさと実行の回数

**懸念:** `TestRunAcceptsLargeOutput` は、BASE と HEAD の両方の時点で大きな出力を出す（`internal/coveragecompare/run_test.go:848-867`）。

**なぜ重要か:** AC-12 は 1 MiB を超える行を読めることだけを求める。合計の大きさと、大きな出力を出す時点の数が、時間を決める。

**候補:** 大きな出力を 1 MiB を超える行の数行にし、大きな出力を出すのを BASE か HEAD の片方の時点だけにする。テストの doc コメントの「over 20 MiB」を、新しい大きさに合わせて直す。

**関連:** F-004、AC-12

## H-06: 線形の時間のテストの入力の大きさ

**懸念:** `TestNeutralizedDisplayMarkdownLinearTime` は、2,000 単位と 8,000 単位の入力の時間の比を見る（`internal/publisher/display_render_test.go:259-262`）。単位の数を減らすと、1 回の時間が短くなり、測定の誤差の割合が大きくなる。

**なぜ重要か:** 小さくしすぎると、線形の処理が 8 倍を超えて誤って失敗するか、2 乗の処理が 8 倍未満で見逃される（AC-07）。

**候補:** 単位の数を何通りか試し、線形の今の処理と、2 乗に壊した処理の両方で比を測って、見分けられる最小の数より余裕のある数を選ぶ。小さくする利点がなければ今のまま残す。

**関連:** F-003、AC-07

## H-07: 境界のテストの、テストの側の軽量化

**懸念:** 境界のテストは本番の上限の大きさの入力を作る（`internal/ytdlpsource/json3_test.go:244-285`、`internal/strictjson/strictjson_test.go:559`）。入力の作り方（`strings.Builder` での組み立て、`padToSize`、`eventsDocument`、`segsDocument`）にかかる時間と、解析にかかる時間の内訳は測られていない。

**なぜ重要か:** 本番のコードを変えずに短くできるのは、並列化と入力の作り方の側だけである（「要件定義の際に決めたこと（2026-11-26）」の「本番のコードを変えない」）。

**候補:** 内訳を測り、入力の作り方に時間がかかっていれば、作った入力をサブテストの間で使い回すなどで短くする。解析が時間の大半であれば、並列化だけにする。

**関連:** F-002、F-004、AC-04、AC-10

## H-08: 並列の実行でのメモリと子のプロセスの数

**懸念:** `go test ./...` はパッケージを並行に実行する。境界のテストを並列にすると、`-race` 付きのビルドで大きな入力（8 MiB の字幕、`internal/ytdlpsource/json3.go:14`。131,073 件の要素）の解析が同時に走り、`TestMakeDeadcodeScope` と `TestMakeDeadcodeVerdict` を並列にすると、`make`・`go list`・`deadcode` の子のプロセスが同時に多く走る。

**なぜ重要か:** メモリの使用量の山と CPU の負荷が上がり、CI のランナーでメモリが足りなくなるか、`TestNeutralizedDisplayMarkdownLinearTime` のような時間を測るテストが不安定になりうる（AC-09）。

**候補:** 並列にした後の `-race` 付きの実行で、メモリの使用量の山を手元と CI で見る。子のプロセスの数が多すぎれば、並列にするサブテストを絞る。

**関連:** F-002、F-003、AC-04、AC-09
