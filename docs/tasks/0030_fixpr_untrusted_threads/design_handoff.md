# 設計への申し送り：fixpr でレビュースレッドの本文を信頼できないデータとして扱う

本書は、[01_requirements.md](01_requirements.md) の起草（とレビュー）で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 書き込み権限の判定の手段

-   **事項:** コメントの著者がリポジトリへの書き込み権限（write・maintain・admin）を持つかを判定する手段を決める。
-   **理由:** GraphQL のコメントの `authorAssociation`（`OWNER`・`MEMBER`・`COLLABORATOR` など）は、権限の強さと一致しない。`COLLABORATOR` は読み取りや triage の権限だけのこともある。`MEMBER` は組織への所属を表すだけで、そのリポジトリへの書き込み権限を意味しない。REST の権限の照会は、`permission` に maintain を write、triage を read と丸めて返し、丸める前の値は `role_name` に入る。カスタムのロールの扱いもここで決める（要件書 AC-02）。照会はネットワークの操作であり、Authorization に挙げる必要がある（AC-36）。
-   **候補の方針:** REST の collaborator の権限の照会（`GET /repos/{owner}/{repo}/collaborators/{username}/permission`）を、著者ごとに 1 回行う。照会の失敗と、`404` などの予期しない応答は、AC-06 の「権限を照会できない」とする。
-   **関連:** F-001、AC-01、AC-02、AC-06、AC-36

## H-02: 自動レビュアーの名前の書き方と照合

-   **事項:** `_context.md` に書く自動レビュアーの名前の形と、コメントの著者との照合の方法を決める。
-   **理由:** 同じ CodeRabbit のアカウントでも、API によって名前の形が違う。GraphQL の `author.login` は `coderabbitai`、REST の `user.login` は `coderabbitai[bot]` である（`runpr.md:169` は REST の形で照合している）。種類と名前の両方で照合する（AC-03）ので、どちらの API の種類の表し方（`__typename`、`type`）を使うかも決める。
-   **候補の方針:** `_context.md` に、どちらの API の形かを明記した名前を 1 つ置く。照合する側で、使う API の形に合わせる。
-   **関連:** F-001、AC-03、AC-35

## H-03: 全コメントの取得と、本文を取得する範囲

-   **事項:** 次の 3 点を決める。11 件以上のコメントを持つスレッドで、残りのコメントを取得する方法。本文を受け取らずに著者を判定する構成（AC-08）。想定外の著者のスレッドの本文を取得しない構成（AC-09）。
-   **理由:** 現在の取得は `comments(first:10)` で、ページングしない（`fixpr.md:164`）。取得のフェーズのエージェントは、本文を連結して返す（`fixpr.md:176-180`）。このままでは、想定外の著者のスレッドの本文が `/fixpr` を実行するセッションに渡る。また、本文を読んだエージェントが判定すると、本文で判定を変えられる。信頼する著者のスレッドで、トリアージに渡す本文を 10 件に限るか（要件書 4.4）も、ここで決めてよい。
-   **候補の方針:** 1 つのスレッドから取得するコメントの数の上限（AC-05）の値も決める。まず著者・種類・コメントの数と ID・更新時刻だけを取得し、エージェントを使わずに判定する。そのうえで、信頼する著者のスレッドと、名指しされたスレッドだけについて本文を取得する。判定と本文の取得を別の呼び出しに分けると、その間に想定外の著者がコメントを追加できる。そのため、本文を取得したら、コメントの ID・著者・更新時刻が判定のときと同じであることを確かめ直す（AC-09）。H-06 の確認と同じ手段を使える。
-   **関連:** F-001、F-002、AC-05、AC-08、AC-09

## H-04: 区切りの形と、本文が区切りを含む場合

-   **事項:** プロンプトで、スレッドの本文と返信の文面を囲む区切りの形を決める。本文に同じ文字列が含まれる場合の扱いも決める（AC-18）。
-   **理由:** 固定の区切り（たとえば `<thread-body>`）は、本文に同じ文字列を書けば閉じられる。現在は、本文を JSON の文字列として埋め込んでいる。そのため、JSON の引用符のエスケープも、区切りの一部になりうる。
-   **候補の方針:** 実行ごとに予測できない値（乱数の nonce）を区切りに含め、その値が本文に含まれないことを確かめる（含まれていれば値を選び直す）。nonce だけでは衝突の確率を下げるにとどまり、AC-18 の保証にならないためである。あるいは、本文を JSON の文字列としてエスケープしたまま渡し、JSON の文字列の外が指示である、とプロンプトで定める。
-   **関連:** F-003、AC-16、AC-18

## H-05: 変更範囲を判定する対象と時点

-   **事項:** F-004 の範囲の判定を、どの時点で、どの変更の集合に対して行うかを決める。誰が利用者に確かめるかも決める。commit される変更が、判定した変更の集合と一致することを保つ手段も決める（AC-21a）。
-   **理由:** Phase 4 は、`make fmt` の後に `git add -A` で commit する（`fixpr.md:344-349`）。判定は build checks の前に行う（AC-21）。build checks は修正したコード（Makefile やテスト）を実行するからである。未追跡のファイルも、`git add -A` で commit に入る。Phase 4 のエージェント（haiku）は、利用者に聞くのに向かない。判定の後、とくに AC-23 で利用者の回答を待つ間にも、作業ツリーは変わりうる。このまま `git add -A` で commit すると、範囲と照らしていない変更が commit に入る。
-   **候補の方針:** 修正のフェーズの後、Phase 4 の前に、`/fixpr` を実行するセッション自身が判定する。`git status --porcelain`（名前の変更の前後のパスを含む）で変更の集合を取り、範囲と照らす。確認が要るときは、そのセッションで利用者に聞く。AC-23 の変更の種類・行の数・バイナリの判定は、`git status --porcelain` だけでは得られない。そのため、`git diff --numstat -M HEAD`（バイナリは `-` で示される）を使い、未追跡のファイルは `git add -N` の後に同じ集計に含める、などの方法を決める。AC-21a には、次のどちらかを採る。(1) 判定の時点で、変更したファイルのパスと内容のハッシュのスナップショットを取り、build checks の前と commit の直前に取り直して比べる。違えば止める。`make fmt` の整形の後は、整形したファイルだけを例外として扱う方法も決める。(2) `git add -A` をやめ、判定したパスだけを明示して stage し、stage した内容が判定のときと同じことを確かめる。判定した集合にない変更が作業ツリーに残っていれば止める。
-   **関連:** F-004、AC-21、AC-21a、AC-22〜AC-25

## H-10: コマンドの実行に関わるファイルの一覧

-   **事項:** F-004 で、スレッドの `path` そのものでなければ範囲外とする「コマンドの実行に関わるファイル」の一覧を確定する。
-   **理由:** 要件書は例（`.claude/`・`.github/` の下、`Makefile`、lint・pre-commit の設定、`go.mod`・`go.sum`）を挙げるだけである。build checks・CI・Claude のコマンドが読むファイルは、ほかにもありうる（`extension/package.json`・`extension/package-lock.json`、`.golangci.yml`、`.pre-commit-config.yaml`、`CLAUDE.md` など）。
-   **候補の方針:** 一覧を `fixpr.md` に 1 か所で定め、リポジトリの最上位の設定ファイルと、build checks が読むファイルを調べて決める。
-   **関連:** F-004

## H-06: 確かめた後のコメントの変化の検出

-   **事項:** 名指しされたスレッドのコメントが、利用者に確かめた時点より後で変わったこと（AC-13）を検出する手段を決める。
-   **理由:** 利用者が確かめた後に、想定外の著者がコメントを追加・編集・削除すると、利用者が見ていない本文が処理される。
-   **候補の方針:** `/runpr` が質問を示す時点で、コメントの ID と更新時刻（`updatedAt`・`lastEditedAt`）の集合を記録する。`/fixpr` は、本文を取得する時点で同じ集合であることを確かめる。
-   **関連:** F-002、AC-12、AC-13、AC-28

## H-07: 返信の文面をシェルに渡す手段

-   **事項:** 返信の文面と、PR の説明を確かめるフェーズが書く PR のタイトルと本文を、シェルのコマンドとして解釈させずに GitHub に送る手段を決める（AC-19）。
-   **理由:** 現在の手段は、引用符付きの heredoc である（`fixpr.md:398-403`・`fixpr.md:442-444`）。PR のタイトルは、二重引用符の中に直接書かれる（`fixpr.md:442`）。文面に終端の文字列だけの行があると、heredoc はそこで閉じ、後の行はシェルのコマンドとして実行される。
-   **候補の方針:** 文面を Write の道具でファイルに書き、`gh api ... -F body=@<file>` で送る。PR のタイトルも同じく、コマンドの文字列に埋め込まず、ファイルから渡す（`gh api ... -F title=@<file>` など）。ファイルの書き出しにシェルを使わない。あるいは、文面に含まれない終端の文字列（乱数の nonce）を実行ごとに選ぶ。
-   **関連:** F-003、AC-19

## H-08: 修正のフェーズの異常の検出

-   **事項:** 修正のフェーズの前と後での HEAD、リモートのブランチ、`.git` の下の違いを検出する手段を決める（AC-26）。
-   **理由:** 修正のフェーズのエージェントは、Bash で `git commit`・`git push` を実行できる。`.git/hooks/` を書けば、Phase 4 の commit で実行させることもできる。どれも、commit される変更の集合（AC-21）には現れない。
-   **候補の方針:** 修正のフェーズの前後で、`git rev-parse HEAD`、`git ls-remote` で取ったリモートのブランチの値、hooks のディレクトリと config のスナップショットを比べる。スナップショットには、内容だけでなく、パス・ファイルの種類・モード（実行ビット）・シンボリックリンクの先も含める。既存の hook の実行ビットだけを変えても、Phase 4 の commit で実行されるようになるためである。worktree では `.git` はファイルであり、hooks と共有の config は共有の git のディレクトリ（`git rev-parse --git-common-dir`）にある。`core.hooksPath` が設定されていれば、その先も対象にする。AC-26 は前と後の違いを求めるので、この前後の比較で AC-26 を満たす。修正のフェーズの間に変えて元に戻したものは検出しないが、これは要件書 4.2 の残余のリスクとして受け入れている。その間に行える操作は、修正のフェーズのエージェントが Bash で直接行える操作を超えないためである。
-   **関連:** F-004、AC-26

## H-09: fork の PR の判定と、`/runpr` が本文を取得しない構成

-   **事項:** 次の 2 点を決める。PR の head がこのリポジトリのブランチかを判定する手段（AC-27）。`/runpr` が、想定外の著者のスレッドの本文をセッションに読み込まない構成（AC-32）。
-   **理由:** `/runpr` のスレッドの取得（`runpr.md:185-211`）は、未解決のすべてのスレッドの `body` を取得する。`/runpr` に必要なのは、スレッドの ID・著者・状態だけである。
-   **候補の方針:** fork の判定には、`gh pr view` の `isCrossRepository`、または `headRepository` と base のリポジトリの比較を使う。`/runpr` の取得では `body` を取得せず、本文が要るときは信頼する著者のスレッドだけを個別に取得する。
-   **関連:** F-005、F-006、AC-27、AC-32
