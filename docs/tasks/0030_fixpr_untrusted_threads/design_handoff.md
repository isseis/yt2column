# 設計への申し送り：fixpr でレビュースレッドの本文を信頼できないデータとして扱う

本書は、[01_requirements.md](01_requirements.md) の起草（とレビュー）で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 書き込み権限の判定の手段

-   **事項:** コメントの著者がリポジトリへの書き込み権限（write・maintain・admin）を持つかを判定する手段を決める。
-   **理由:** GraphQL のコメントの `authorAssociation`（`OWNER`・`MEMBER`・`COLLABORATOR` など）は、権限の強さと一致しない。`COLLABORATOR` は読み取りや triage の権限だけのこともあり、`MEMBER` は組織の所属を表すだけで、そのリポジトリへの書き込み権限を意味しない。照会はネットワークの操作であり、Authorization に挙げる必要がある（AC-27）。
-   **候補の方針:** REST の collaborator の権限の照会（`GET /repos/{owner}/{repo}/collaborators/{username}/permission`）を、著者ごとに 1 回行う。照会の失敗と、`404` などの予期しない応答は、AC-04 の「権限を照会できない」とする。
-   **関連:** F-001、AC-01、AC-04、AC-27

## H-02: 自動レビュアーの名前の書き方と照合

-   **事項:** `_context.md` に書く自動レビュアーの名前の形と、コメントの著者との照合の方法を決める。
-   **理由:** 同じ CodeRabbit のアカウントでも、GraphQL の `author.login` は `coderabbitai`、REST の `user.login` は `coderabbitai[bot]` と、API によって形が違う（`runpr.md:169` は REST の形で照合している）。名前だけで照合すると、同じ login を持つ `User` と取り違えるおそれもある。
-   **候補の方針:** 著者の種類（`__typename` が `Bot`）と login の組で照合する。`_context.md` には、どちらの API の形かを明記した名前を 1 つ置く。
-   **関連:** F-001、AC-01、AC-25

## H-03: 全コメントの取得と、取得の段階で本文を扱う範囲

-   **事項:** 11 件以上のコメントを持つスレッドで、残りのコメントを取得する方法を決める。また、想定外の著者のスレッドの本文が、取得の段階の結果に入らない構成を決める（AC-06）。
-   **理由:** 現在の取得は `comments(first:10)` で、ページングしない（`fixpr.md:164`）。取得の段階のエージェントが本文を連結して返すと、想定外の著者のスレッドの本文が `/fixpr` を実行するセッションに渡る。トリアージに渡す本文を 10 件に限るかどうか（`fixpr.md:176-180`）は、著者の判定とは別に決められる。
-   **候補の方針:** まず著者とコメントの数だけを取得して判定し、信頼する著者のスレッドだけ本文を取得する。あるいは、取得の段階のエージェントが判定まで行い、想定外の著者のスレッドについては本文を除いた結果を返す。
-   **関連:** F-001、F-002、AC-03、AC-06

## H-04: 区切りの形と、本文が区切りを含む場合

-   **事項:** プロンプトでスレッドの本文を囲む区切りの形と、本文に同じ文字列が含まれる場合の扱いを決める（AC-14）。
-   **理由:** 固定の区切り（たとえば `<thread-body>`）は、本文に同じ文字列を書けば閉じられる。現在は本文を JSON の文字列として埋め込んでいるので、JSON の引用符のエスケープも区切りの一部になりうる。
-   **候補の方針:** 実行ごとに予測できない値（乱数の nonce）を区切りに含める。あるいは、本文を JSON の文字列のまま渡し、JSON の文字列の外は指示である、とプロンプトで定める。
-   **関連:** F-003、AC-12、AC-14

## H-05: 変更範囲を判定する対象と時点

-   **事項:** F-004 の範囲の判定を、どの時点のどの変更の集合に対して行うかを決める。
-   **理由:** Phase 4 は `make fmt` の後に `git add -A` で commit する（`fixpr.md:344-349`）。`make fmt` は変更した Go のファイルを整形するので、修正の段階が終わった直後の変更と、commit される変更が一致しないことがある。未追跡のファイルも `git add -A` で commit に入る（AC-20）。確認を Phase 4 の中で行うと、Phase 4 のエージェント（haiku）が人に聞くことになる。
-   **候補の方針:** 修正の段階の後、Phase 4 の前に、`/fixpr` を実行するセッション自身が `git status --porcelain` で変更の集合（未追跡を含む）を取り、範囲と照らす。確認が要るときは、そのセッションで人に聞く。
-   **関連:** F-004、AC-16〜AC-20

## H-06: 想定外の著者のスレッドを名指しで処理するときの本文の再取得

-   **事項:** 人が確かめた後に名指しで処理するとき（AC-09）、本文をいつ取得するかを決める。
-   **理由:** 人が確かめた後に、想定外の著者がコメントを追加・編集すると、人が見ていない本文が処理される。
-   **候補の方針:** 名指しのときは、人に示した内容と同じコメントの集合（コメントの ID と更新時刻）であることを確かめてから処理する。または、名指しの時点で取得した本文を人に示し、確かめてもらう。
-   **関連:** F-002、AC-09、AC-22
