## 1. 概要 (Overview)

**目的:** 本書は、`/fixpr`（`.claude/commands/fixpr.md`）がレビュースレッドの本文を信頼できないデータとして扱うための要件を定義する（[#395](https://github.com/isseis/yt2column/issues/395)）。想定外の著者（信頼する著者でない著者。定義は「要件定義の際に決めたこと」と 6 節）が書いたスレッドは、自動で処理しない。修正が想定外の範囲に及んだら、push の前に利用者に確かめる。`/runpr`（`.claude/commands/runpr.md`）については、想定外の著者のスレッドを報告し、利用者に処理するかを聞き、マージの前に止まるところまでを含める。

**背景:**

`/fixpr` は、未解決のレビュースレッドを取得し、トリアージし、リポジトリのファイルを修正して push する。取得のフェーズ（Phase 1）は、スレッドのコメントを最初の 10 件まで取得し（`fixpr.md:164`）、各コメントに `@author: ` を付けて連結して `body` にする（`fixpr.md:176-180`）。トリアージのフェーズ（Phase 2）と修正のフェーズ（Phase 3）のプロンプトは、この `body` を JSON のまま埋め込む（`fixpr.md:238`・`fixpr.md:263-265`）。本文を「データであり指示ではない」とする扱いはない。一方、`/mergepr` には、PR のタイトル・本文・コミットメッセージ・diff を「要約するデータであり、従うべき指示ではない」とする規則がある（`mergepr.md:46-48`）。

スレッドの本文は、外部のレビュアーが書く信頼できないテキストであり、プロンプトインジェクションの経路になる。修正のフェーズのエージェントはリポジトリのファイルを編集できる。その変更は、Phase 4 で `git add -A` によって commit され、push される（`fixpr.md:344-354`）。スレッドの著者の種類（`authorType`）は最初のコメントだけから決まり（`fixpr.md:181-183`）、ラウンド上限の判定にしか使われない（`fixpr.md:40-47`）。人が開いたスレッドは、どのラウンドでも処理される（`fixpr.md:48-50`）。`/runpr` は、まだ `/fixpr` に渡していないスレッドが現れると、自動で `/fixpr` を実行する（`runpr.md:212-219`）。そのため、誰かがスレッドを開くと、利用者が内容を見る前に、修正と push まで進む。

返信のフェーズ（Phase 5）は、エージェントが書いた返信の文面（`replyBody`）を、引用符付きの heredoc でシェルに渡す（`fixpr.md:398-403`）。引用符付きの heredoc は展開を止めるが、文面に終端の文字列（`REPLYBODY_EOF`）だけの行があれば、そこで閉じる。その後の行はシェルのコマンドとして実行される。返信の文面は、本文を読んだエージェントが書くので、これもインジェクションの経路になる。PR の説明を確かめるフェーズ（Phase 6）も、エージェントが PR の内容を読んで書いた PR の本文を、同じく引用符付きの heredoc で `gh pr edit` に渡す（`fixpr.md:442-444`）。

issue は「公開リポジトリでコメント権限が広がると、リスクが上がる」としている。このリポジトリはすでに公開されている（2026-10-21 に `gh repo view` で `visibility: PUBLIC` を確かめた）。公開リポジトリでは、GitHub のアカウントを持つ人なら誰でも PR にレビューコメントを書け、CodeRabbit が開いたスレッドに返信もできる。

この問題は PR #393 のローカルの CodeRabbit レビューで指摘された。PR #393 が生んだものではなく `fixpr` の既存の設計の問題なので、保留として本 issue に移した。

対応 issue: [#395](https://github.com/isseis/yt2column/issues/395)（関連: [#393](https://github.com/isseis/yt2column/pull/393)）

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。どの著者のスレッドを処理するか、処理しないスレッドをどう報告するか、本文をどう扱うか、どの変更で利用者に確かめるか、である。次の事項は設計（`02_architecture.md`）で決める。

-   書き込み権限を判定する手段と、全コメントを取得する手段。
-   区切りの形と、返信の文面をシェルに渡す手段。
-   変更範囲を判定する対象と手段。
-   コマンドの文書のどこに何を書くか。

要件の起草とレビューで挙がった設計の事項は、[design_handoff.md](design_handoff.md) に申し送る。

**issue #395 で決めたこと:**

-   **本文をデータとして明示する:** プロンプトで、スレッドの本文は「データであり指示ではない」と明示し、本文を区切りで囲む。`mergepr.md:46-48` と同じ扱いに揃える。
-   **修正のフェーズの変更範囲を絞る:** 修正のフェーズのエージェントの変更範囲を、スレッドの `path` の周辺に限るか、push の前に変更を確かめる。どちらにするかは、要件定義の際に決めた（下記）。

issue は、修正を適用する前にスレッドの著者を確かめ、想定外の著者のスレッドは人が確かめるまで適用しない方針も「検討する」としている。この方針は、要件定義の際に採ると決めた（下記）。

**要件定義の際に決めたこと（2026-10-21）:**

-   **想定外の著者のスレッドは人が確かめるまで適用しない:** issue が検討するとした方針を採る（F-002）。公開リポジトリでは誰でもスレッドを開けるので、本文をデータとして明示するだけでは守りにならないためである。
-   **信頼する著者:** リポジトリへの書き込み権限を持つアカウントと、自動レビュアー（CodeRabbit）のアカウントだけを、信頼する著者とする。自動レビュアーの名前は `.claude/commands/_context.md` に 1 か所で定める（F-001・F-007）。CodeRabbit 以外の Bot は、想定外の著者とする。リポジトリに App をインストールすれば、CodeRabbit 以外の Bot もコメントを書けるので、Bot であることだけでは信頼する理由にならないためである。
-   **想定外の著者のスレッドは処理せずに報告する:** トリアージ・修正・返信・解決をせず、最終報告に URL と理由を挙げる。利用者が内容を確かめてから名指しした場合だけ処理する（F-002）。トリアージだけを行う案は採らない。トリアージだけでも本文がエージェントに渡るので、守りにならないためである。`/fixpr` の実行中にスレッドごとに聞く案も採らない。`/runpr` の自動の繰り返しのたびに、利用者を待たせることになるためである。
-   **著者が混在したスレッドは、スレッド全体を想定外とする:** コメントのうち 1 件でも想定外の著者のものなら、スレッド全体を想定外の著者のスレッドとして扱う（F-001）。想定外の著者のコメントだけを除く案は採らない。会話の文脈が欠けて、指摘を誤って理解するおそれがあるためである。
-   **全コメントの著者を確かめる:** スレッドのコメントが 11 件以上あっても、すべてのコメントを取得して著者を確かめる。著者を確かめられないコメントがあれば、スレッドを想定外の著者のスレッドとする（F-001）。著者がない場合や、権限を照会できない場合などである。
-   **範囲外の変更は、build checks の前に利用者に確かめる:** 修正のフェーズが範囲の外のファイルを変えたら、build checks・commit・push の前に、範囲外のファイルの一覧を示して利用者に確かめる（F-004）。build checks の前にするのは、build checks が修正したコード（Makefile やテスト）を実行するためである。範囲外なら止める案は採らない。コードの修正では別のパッケージを変えることもあり、正当な修正まで止まるためである。範囲を制限しない案も採らない。CodeRabbit が PR の内容を引用した本文など、信頼する著者のスレッドを経てもインジェクションは届きうるので、著者の確認とは別の守りを残す。
-   **範囲は、スレッドの `path` と同じディレクトリまでとする:** 範囲は、Phase 3 に渡したスレッドの `path` のファイル、それと同じディレクトリのファイル、その `path` があるタスクのディレクトリのファイルである。ただし、コマンドの実行に関わるファイル（`.claude/`・`.github/` の下のファイルや `Makefile` など）は、スレッドの `path` そのものでなければ範囲外とする（F-004）。スレッドの `path` だけに限る案は採らない。同じパッケージのテストのファイル（`_test.go`）を直すたびに確認が入り、`/runpr` の繰り返しのたびに利用者を待たせるためである。実行に関わるファイルを除くのは、リポジトリの最上位のファイルへの指摘で、最上位にある `Makefile` などまで範囲に入らないようにするためである。
-   **利用者が続けないと答えたら、変更を残して止める:** 変更は作業ツリーに残し、利用者が調べられるようにする。`/runpr` はマージの前に止まる。作業ツリーに変更があれば、`/fixpr` は始めない（F-004・F-006）。範囲外の変更だけ、またはすべての変更を捨てる案は採らない。何が書き換えられたかを、利用者が確かめられなくなるためである。
-   **返信のフェーズも対象にする:** 返信の文面が本文を途中で終えず、シェルのコマンドとして実行されないことを要件にする（F-003）。返信の文面は本文を読んだエージェントが書くので、取得とトリアージを守っても、ここが経路として残るためである。PR の説明を確かめるフェーズが書く PR の本文も、同じ理由で同じ扱いにする。
-   **確かめた後に変わったスレッドは処理しない:** 利用者が確かめた後にコメントが追加・編集・削除されたスレッドは、名指しされても処理しない（AC-13）。利用者が見ていない本文が処理されるのを防ぐためである。
-   **`/fixpr` を直接実行するときの「確かめた時点」は、直前の報告の時点とする:** 利用者は、`/fixpr` を直接実行するときも、想定外の著者のスレッドを名指しできる。確かめた時点は、そのスレッドを挙げた直前の `/fixpr` の報告（AC-11）の時点とする。そのような報告がなければ、名指しを受け付けない（AC-12・AC-13）。`/runpr` を経ない実行でも、確かめた後の変化を検出できるようにするためである。
-   **作業ツリーに変更があれば始めない:** `/fixpr` は、始める前に作業ツリーを確かめ、commit していない変更があれば始めない（AC-20）。前の実行で残した変更や利用者の編集が、修正のフェーズの変更と混ざって範囲の判定と commit に入るのを防ぐためである。
-   **修正のフェーズの異常では止める:** 修正のフェーズの間に、HEAD、リモートのブランチ、`.git` の hooks・config が変わったら、利用者に確かめずに止める（AC-26）。修正のフェーズは自分で commit・push できるので、commit される変更の集合を確かめるだけでは、範囲の確認を迂回できるためである。
-   **`/runpr` は想定外の著者の本文を読まない:** `/runpr` は、自分が取得するスレッドのうち、想定外の著者のスレッドの本文を自分のセッションに読み込まない（AC-32）。`/runpr` を実行するセッションもエージェントであり、本文の指示に従うおそれがあるためである。
-   **CodeRabbit を経て持ち込まれる指示は、残余のリスクとして記録する:** 想定外の著者は、PR の会話コメントで CodeRabbit に依頼できる。その結果、CodeRabbit が書いたスレッド（信頼する著者のスレッド）に指示が入りうる。これは、本文をデータとして明示すること（F-003）と変更範囲の確認（F-004）で抑え、要件では検出しない（4.2）。会話コメントの著者まで確かめて止める案は採らない。CodeRabbit が何をもとにスレッドを書いたかは、会話コメントの著者だけからは決まらないためである。
-   **fork の PR では止める:** PR の head がこのリポジトリのブランチでなければ、`/fixpr` と `/runpr` は何もせずに止まり、報告する（F-005）。head を外部の人が管理すると、チェックアウトした `CLAUDE.md` や `.claude/commands/` そのものが攻撃者のものになり、本書のどの守りも働かないためである。
-   **`/runpr` は、`runpr.md` の step 3 でその場で聞く:** 止まる理由が想定外の著者のスレッドだけのとき、`/runpr` は URL を示して、どれを処理するか（なしを含む）を 1 回聞く。選ばれたスレッドを名指しして `/fixpr` を実行し、続ける（F-006）。止めてから利用者が手で `/fixpr` を実行する案は採らない。手順が増え、名指しの経路がコマンドの外に出るためである。マージの質問（`runpr.md` の step 4）に含める案も採らない。step 4 はマージの直前の 1 回の確認であり、処理すると head が変わるので、どのみち step 3 に戻ることになるためである。
-   **対象は `/fixpr` の該当フェーズと `/runpr`:** `/fixpr` では、スレッドの本文、本文から作った文面、PR のテキストを受け取るすべてのフェーズを対象にする。`/runpr` は、F-006 の範囲を対象にする。issue の本文を読む `/mkreq` など、ほかのコマンドはスコープ外とする（2.3）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   想定外の著者のスレッドの本文を、利用者が確かめる前に、どのエージェントにも、`/fixpr`・`/runpr` を実行するセッションにも渡さない。リポジトリの変更と push の材料にしない。
-   信頼する著者のスレッドの本文も、データとしてプロンプトに渡す。本文から作った返信の文面を、シェルのコマンドとして実行させない。
-   修正が範囲の外に及んだら、build checks・commit・push の前に利用者が気づけるようにする。
-   信頼する著者のスレッドの処理（トリアージ、修正、ラウンド上限、返信と解決）は、今までどおりに保つ。

### 2.2. スコープ (In Scope)

-   スレッドのすべてのコメントの著者の確認と、信頼する著者の判定（F-001）。
-   想定外の著者のスレッドを処理せずに報告することと、利用者が確かめた後の処理（F-002）。
-   エージェントのプロンプトで、スレッドの本文・返信の文面・PR のテキストをデータとして扱うこと。返信の文面をシェルに安全に渡すこと（F-003）。
-   修正のフェーズの変更範囲の確認と、作業ツリーの状態の確認（F-004）。
-   fork の PR での停止（F-005）。
-   `/runpr` での報告、処理するかの質問、停止、取得した本文の扱い（F-006）。
-   文書: `.claude/commands/fixpr.md`・`.claude/commands/runpr.md`・`.claude/commands/_context.md`・`docs/translation_glossary.md`（F-007）。

### 2.3. スコープ外 (Out of Scope)

-   `/fixpr`・`/runpr` 以外のコマンドが読む外部のテキスト。たとえば、`/mkreq` が読む issue の本文や、`_lib/coderabbit-local-review.md` が読むローカルの CodeRabbit の出力である。公開リポジトリでは誰でも issue を書けるので、`/mkreq` にも同じ問題がある。ただし、本 issue の対象ではないので、別の issue で扱う。`/mergepr` は、すでに PR のテキストをデータとして扱っている（`mergepr.md:46-48`）。
-   GitHub の設定（リポジトリの非公開化、操作の制限（interaction limits）、ブランチの保護）。リポジトリの外の設定であり、コマンドでは変えない。
-   信頼する著者が意図して書いた指摘の妥当性の判断。これは今までどおりトリアージ（`_lib/triage-pattern.md`）で行う。
-   修正のフェーズのエージェントが本文の指示に従わないことの保証。本文をデータとして明示しても、LLM が指示に従わないことは保証できない。そのため、著者の確認（F-001・F-002）と変更範囲の確認（F-004）を、別の守りとして重ねる。F-004 で検出できない操作は、4.2 に残余のリスクとして挙げる。
-   `docs/dev/security.md` の変更。同書は製品を対象にした文書であり、本タスクは開発用のコマンドを変えるものだからである（4.2）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 信頼する著者の判定

`/fixpr` は、未解決のスレッドごとに、すべてのコメントの著者を確かめる。そのうえで、スレッドを「信頼する著者のスレッド」と「想定外の著者のスレッド」に分ける。

**Acceptance Criteria**:
- **AC-01**: 信頼する著者は次の 2 つだけである。リポジトリへの書き込み権限（write・maintain・admin のいずれか）を持つ、Bot でないアカウントと、`_context.md` に名前を定めた自動レビュアーのアカウント（AC-35）である。
- **AC-02**: 権限が write・maintain・admin のいずれでもないアカウントは、信頼する著者ではない。read・triage の権限だけのアカウント、collaborator でないアカウント、書き込み権限を確かめられないカスタムのロール、未知の権限の値が、これに当たる。
- **AC-03**: 自動レビュアーとの一致は、アカウントの種類が Bot であることと、名前が一致することの両方で判定する。名前が同じでも Bot でないアカウントは、自動レビュアーではない（書き込み権限を持たなければ、信頼する著者ではない）。名前が違う Bot は、書き込み権限を持っていても信頼する著者ではない。
- **AC-04**: スレッドのすべてのコメントの著者が信頼する著者のとき、そのスレッドは信頼する著者のスレッドである。1 件でも信頼する著者でないコメントがあれば、そのスレッドは想定外の著者のスレッドである。最初のコメントの著者が信頼する著者であっても同じである。
- **AC-05**: スレッドのコメントが 11 件以上あるときも、すべてのコメントの著者で AC-04 を判定する。最初の 10 件だけで判定しない。1 つのスレッドから取得するコメントの数には上限を設け、上限を超えるスレッドは、すべてのコメントを取得できなかったものとする（AC-06）。
- **AC-06**: 著者を確かめられないコメントがあれば、そのスレッドは想定外の著者のスレッドである。次の場合がこれに当たる。著者がない（削除されたアカウント）。名前が空。権限を照会できない（照会の失敗や、API の利用の上限を含む）。すべてのコメントを取得できない（AC-05 の上限を超える場合を含む）。
- **AC-07**: 判定は、`/fixpr` を実行するたびに、その時点のコメントと権限で行う。前のラウンドの判定は使わない。前のラウンドで信頼する著者のスレッドだったものに想定外の著者が返信すれば、そのラウンドからは想定外の著者のスレッドである。
- **AC-08**: 判定は、コメントの著者と権限の情報だけから行う。コメントの本文を受け取ったエージェントは、判定に関わらない。本文が何を書いていても、判定は変わらない。

#### F-002: 想定外の著者のスレッドを処理せずに報告する

`/fixpr` は、想定外の著者のスレッドを処理せず、報告だけをする。利用者が内容を確かめて名指しした場合だけ処理する。

**Acceptance Criteria**:
- **AC-09**: 想定外の著者のスレッドは、トリアージも修正もされない。その本文は、どのエージェントのプロンプトにも、`/fixpr` を実行するセッションにも入らない。取得のフェーズも例外ではない。
- **AC-10**: 想定外の著者のスレッドには、返信せず、解決もしない。GitHub の上では未解決のまま残る。
- **AC-11**: `/fixpr` の最終報告は、想定外の著者のスレッドを、ほかの「スキップしたスレッド」と区別した一覧で挙げる。各スレッドには、URL と、想定外とした理由を付ける。当てはまる理由が複数あれば、すべてを付ける。理由は次の 5 つである。(a) 書き込み権限がない（アカウントの名前を付ける）。(b) 自動レビュアーでない Bot である（アカウントの名前を付ける）。(c) 著者がない、または名前が空である。(d) 権限を照会できなかった。(e) すべてのコメントを取得できなかった。報告には、スレッドの本文を含めない。利用者は、URL から GitHub の上で内容を確かめる。
- **AC-12**: 呼び出し元が想定外の著者のスレッドを名指しして処理を指示した場合だけ、`/fixpr` はそのスレッドを処理する。処理の内容（トリアージ、修正、返信と解決）は、そのラウンドの信頼する著者のスレッドと同じである。名指しの経路は、ラウンド上限の caller override（`fixpr.md:57-60`）と同じく、呼び出し元がこのセッションで与える指示である。名指しは、利用者がスレッドの内容を確かめた後に行う。`/runpr` では step 3 の質問への回答で（AC-28）、`/fixpr` を直接実行するときはこのセッションでの指示で行う。ただし、直接実行で受け付けるのは、このセッションの直前の `/fixpr` の報告（AC-11）が想定外の著者のスレッドとして挙げたものだけである。挙げていないスレッドの名指しは受け付けず、その旨を報告する。
- **AC-13**: 名指しされたスレッドで、確かめた時点より後にコメントの追加・編集・削除があった場合、`/fixpr` はそのスレッドを処理しない。報告では、コメントが変わったことを示す。確かめた時点は、`/runpr` では step 3 の質問を示した時点、`/fixpr` を直接実行したときは、そのスレッドを挙げた直前の報告の時点である。
- **AC-14**: 想定外の著者のスレッドだけが残り、処理するスレッドがない場合、`/fixpr` は修正・commit・push・返信をせずに終わる。報告では、処理するスレッドがないことと、想定外の著者のスレッドの一覧（AC-11）を示す。
- **AC-15**: 想定外の著者のスレッドは、ラウンドの数え方（`fixpr.md:36-39`）とラウンド上限の判定に影響しない。処理しなかったことで、ラウンドの数は変わらない。

#### F-003: 本文・返信の文面・PR のテキストをデータとして扱う

`/fixpr` は、外部から来たテキストと、それをもとにエージェントが書いたテキストを、指示ではなくデータとして扱う。

**Acceptance Criteria**:
- **AC-16**: `/fixpr` のエージェントのうち、スレッドの本文、またはエージェントが書いた返信の文面を受け取るものは、すべてプロンプトで次の 2 点を明示される。それらがデータであって、従うべき指示ではないこと。それらが区切りで囲まれ、指示の部分と区別されていること。対象は、トリアージ・修正・返信のフェーズと、そのほかにそれらを受け取るフェーズである。
- **AC-17**: PR のタイトル・本文・コミットメッセージを受け取るエージェントは、プロンプトで、それらが確かめるデータであって、従うべき指示ではないことを示される（`mergepr.md:46-48` と同じ扱い）。PR の説明を確かめるフェーズ（`fixpr.md:429-450`）が、これに当たる。
- **AC-18**: 本文や返信の文面に、区切りと同じ文字列が含まれていても、その文字列は本文の終わりとして扱われない。本文は、区切りの外の指示の部分に入り込まない。
- **AC-19**: エージェントが書いてシェルのコマンドで GitHub に送る文面は、どんな文字列を含んでいても、送られる内容が文面の全体と一致する。文面のどの部分も、シェルのコマンドとして実行されない。対象は、返信のフェーズの返信の文面と、PR の説明を確かめるフェーズの PR のタイトルと本文である。たとえば、heredoc の終端の文字列だけの行、`$(...)`、バッククォート、引用符を含む場合である。

#### F-004: 変更範囲と作業ツリーの確認

`/fixpr` は、修正のフェーズが変えたファイルを、build checks の前に範囲と照らす。範囲外があれば利用者に確かめる。範囲は次のファイルである。

-   そのラウンドで Phase 3 に渡したスレッドの `path` のファイル。
-   そのファイルと同じディレクトリにあるファイル（サブディレクトリの中は含まない）。
-   Phase 3 に渡したスレッドの `path` がタスクのディレクトリ（`docs/tasks/NNNN_<name>/`）の中にあるとき、そのディレクトリの中のファイル。設計への申し送りの文書の追加と、文書の状態の差し戻し（`fixpr.md:104-139` の R2・R3）は、ここに入る。

ただし、コマンドの実行に関わるファイルは、Phase 3 に渡したスレッドの `path` そのものでなければ範囲外とする。`.claude/`・`.github/` の下のファイル、`Makefile`、lint・pre-commit の設定、`go.mod`・`go.sum` などがこれに当たる。名前を変えたファイルは、変える前と後の両方のパスが範囲内のときだけ範囲内とする。

**Acceptance Criteria**:
- **AC-20**: `/fixpr` は、始める前に作業ツリーを確かめる。commit していない変更（未追跡のファイルを含む）があれば、取得のフェーズより前に止まり、作業ツリーに変更があることを報告する。
- **AC-21**: 範囲の判定は、修正のフェーズの後、build checks の前に、commit される変更の全体に対して行う。追加・削除・名前の変更と、修正のフェーズが作った未追跡のファイルを含む。判定の後の `make fmt` が整形したファイルは、判定し直さない。`make fmt` は、変更した Go のファイルだけを整形するからである（`CLAUDE.md`「Code Quality」）。
- **AC-22**: 変更したファイルがすべて範囲内なら、`/fixpr` は利用者に確かめずに、今までどおり build checks・commit・push に進む。
- **AC-23**: 範囲外のファイルが 1 つでもあれば、`/fixpr` は build checks の前に止まる。範囲外のファイルの一覧を示して、続けるかを利用者に確かめる。一覧には、ファイルごとに変更の種類と変更した行の数を示す。バイナリのファイルは、行の数の代わりにバイナリであることを示す。
- **AC-24**: 利用者が続けると答えたら、`/fixpr` は build checks・commit・push・返信と解決を、今までどおり行う。
- **AC-25**: 利用者が続けないと答えたら、`/fixpr` は build checks・commit・push・返信・解決のいずれも行わない。変更は作業ツリーに残す。最終報告では、範囲外の変更のために止めたことと、範囲外のファイルの一覧を示す。
- **AC-26**: 修正のフェーズの間に、次のいずれかが起きた場合、`/fixpr` は利用者に確かめずに止まる。build checks・commit・push・返信・解決は行わない。(a) ブランチの HEAD が変わった（新しい commit、ブランチの切り替え、reset）。(b) リモートのブランチが変わった。(c) git の hooks（hooks のディレクトリの中のファイル）か、git の設定ファイル（リポジトリの config と、worktree の config）が変わった。worktree では、共有の git のディレクトリの中のものも含む。index・`FETCH_HEAD`・reflog など、git の通常の操作で変わるファイルの変化は、異常として扱わない。最終報告では、起きたことを示す。`/fixpr` の手順では、修正のフェーズはこれらを行わないので、起きたこと自体を異常として扱う。

#### F-005: fork の PR での停止

**Acceptance Criteria**:
- **AC-27**: PR の head がこのリポジトリのブランチでない場合（fork のブランチなど）、`/fixpr` と `/runpr` はスレッドの取得・修正・commit・push・返信・マージのいずれも行わずに止まる。報告では、head がこのリポジトリのブランチでないことを示す。

#### F-006: `/runpr` での報告・質問・停止

`/runpr` は、想定外の著者のスレッドを区別して扱う。利用者に処理するかを聞き、残っている間はマージしない。

**Acceptance Criteria**:
- **AC-28**: step 3 で、マージを妨げるスレッドが想定外の著者のスレッドだけになったとき、`/runpr` は 1 回だけ質問する。質問では各スレッドの URL と想定外とした理由（AC-11）を示し、どれを処理するか（なしを含む）を聞く。選ばれたスレッドは、名指しして `/fixpr` を実行し（AC-12）、step 3 を続ける。ほかの止まる理由（`runpr.md:220-226`）もある場合は、質問せずに止まり、すべての理由を報告する。
- **AC-29**: 処理するスレッドが選ばれなかった場合、`/runpr` はマージせずに止まる。報告では、想定外の著者のスレッドの URL と理由を示す。あわせて、GitHub の上でスレッドを解決すれば、`/runpr` を再び実行してマージに進めることを示す。
- **AC-30**: 想定外の著者のスレッドが未解決で残っている間、`/runpr` はマージしない。
- **AC-31**: `/fixpr` が範囲外の変更のために止まった場合（AC-25）や、修正のフェーズの異常で止まった場合（AC-26）、`/runpr` はマージせずに止まり、`/fixpr` の報告を示す。作業ツリーに commit していない変更がある場合も、マージの手順（step 4）に進まない。
- **AC-32**: `/runpr` は、自分で取得するスレッド（`runpr.md:185-211`）のうち、想定外の著者のスレッドの本文を、自分のセッションに読み込まない。信頼する著者のスレッドの本文は、従うべき指示ではなくデータであると、`runpr.md` に明記する。
- **AC-33**: `/runpr` が `/fixpr` を自動で再実行する条件（`runpr.md:212-217`）は変えない。新しく現れた想定外の著者のスレッドでも `/fixpr` を実行し、`/fixpr` はそのスレッドを処理せずに報告する（F-002）。

#### F-007: 文書

コマンドの文書と用語集を、F-001〜F-006 に合わせる。

**Acceptance Criteria**:
- **AC-34**: `fixpr.md` の Convergence policy の「People are always answered」（`fixpr.md:48-50`）が、信頼する著者が開いたスレッドに限った記述になる。想定外の著者のスレッドの扱い（F-002）は、同じ文書の中で参照できる。
- **AC-35**: `_context.md` に、自動レビュアーのアカウントの名前を 1 か所で定める。`/fixpr` と `/runpr` は、その名前を参照する。
- **AC-36**: F-001 のために新たに必要になったネットワークの操作（著者の権限の照会など）は、`/fixpr` を実行するコマンドの Authorization に挙げる。`fixpr.md` には Authorization の節がないので、新たに設ける。`runpr.md` は既存の Authorization（`runpr.md:32-43`）に加える。
- **AC-37**: 本書の用語（フェーズ・信頼する著者・想定外の著者のスレッド・範囲外の変更）を、`docs/translation_glossary.md` に加える。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   N/A。著者の確認のための API の呼び出しの数は、1 回の実行あたり、スレッドとコメントの数に比例する程度である。LLM のエージェントの呼び出し（数十秒から数分）に比べて小さい。

### 4.2. セキュリティ (Security)

-   条件付きのセキュリティガイド（`docs/dev/security.md`）のトリガーに該当する。本タスクは、信頼できないテキストを LLM のプロンプトに埋め込み、ネットワークで GitHub に送る。同書は製品を対象にした文書だが、§6 の原則「生成結果を他のコマンドやコードとして実行しない」（`security.md:70`）を本タスクにも当てはめる（AC-19）。同書そのものは変えない（2.3）。
-   守りは 3 つの層からなる。
    -   層 (1): 想定外の著者のスレッドを処理しない（F-001・F-002・F-005）。
    -   層 (2): 本文と返信の文面をデータとして扱う（F-003）。
    -   層 (3): 範囲外の変更と修正のフェーズの異常を、build checks の前に検出する（F-004）。

    層 (2) は LLM の振る舞いに依存するので、保証にならない（2.3）。層 (1) は層 (2) に依存しない。著者と権限の情報だけで判定するからである（AC-08）。層 (3) が検出するのは、commit される変更と、HEAD・リモートのブランチ・git の hooks と設定ファイルの変化である（AC-21・AC-26）。それ以外の変化は検出しない。
-   著者を確かめられない場合は、想定外の著者として扱い、安全側に倒す（AC-06）。
-   信頼できない入力として受け取るのは、GitHub の API が返すコメントの著者（種類と名前）・権限・コメントの数と ID・更新時刻、およびスレッドの本文である。著者と権限は、AC-01〜AC-03 の受理する値の集合に入るものだけを信頼する著者とし、それ以外の値（未知の値、空の値、欠けた値）は補正せずに想定外とする（AC-02・AC-06）。コメントの数の上限は AC-05 で定める。本文は解析せず、データとして渡すだけなので、受理する形は定めない（F-003）。
-   **残余のリスク:** 次の 3 つは、本タスクの要件では検出しない。いずれも、層 (2) と、Claude Code の権限の確認（利用者の設定による）に依存する。
    -   修正のフェーズのエージェントが、git が無視するファイル（`.envrc` など）を変えること、またはネットワークに接続すること。
    -   想定外の著者が PR の会話コメントで CodeRabbit に依頼し、信頼する著者のスレッドに指示を持ち込むこと（1. 要件定義の際に決めたこと）。
    -   信頼する著者のスレッドの本文が、PR の内容を引用して指示を持ち込むこと。

    これらのうち、範囲外のファイルの変更として現れるものは、層 (3) が検出する。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   著者の権限の照会が失敗しても、`/fixpr` の実行そのものは失敗させない。照会できなかったスレッドは想定外の著者のスレッドとし（AC-06）、ほかのスレッドの処理を続ける。
-   想定外の著者のスレッドは、利用者が処理を選ぶか、GitHub の上で解決するまで、マージを妨げる（AC-30）。スレッドが多数あれば、利用者は 1 つずつ解決する必要がある。これは受け入れる。
-   想定外の著者のスレッドも、スレッドの取得の上限（100 件。`fixpr.md:184-196`）に数える。上限に達したときの報告は今までどおりである。

### 4.4. 互換性 (Compatibility)

-   信頼する著者のスレッドの処理は、今までと変わらない。トリアージの分類、修正、ラウンド上限、caller override、返信と解決、最終報告の既存の項目が対象である。11 件以上のコメントを持つ信頼する著者のスレッドで、トリアージに渡すコメントの数も変えない。この扱いは設計で見直してよい（design_handoff.md H-03）。
-   変わる点は次の 5 つである。範囲外の変更があるときの確認（F-004）。作業ツリーに変更があるときの停止（AC-20）。fork の PR での停止（F-005）。本文をデータとして明示する記述（F-003）。返信の文面の渡し方（AC-19）。
-   修正のフェーズは、別のディレクトリのファイルの規則を直すことがある（`fixpr.md:277-282` の「Generalize before patching」）。そのラウンドでは、範囲外の変更の確認（AC-23）が起きる。この確認の回数が増えることは、受け入れる。
-   ラウンドの数え方（Phase 4 の commit の件名、`fixpr.md:36-39`）は変えない。

### 4.5. 保守性 (Maintainability)

-   自動レビュアーの名前は、1 か所で定める（AC-35）。CodeRabbit を別の自動レビュアーに替えるとき、変える場所を 1 つにするためである。
-   `/fixpr` の規則は、今までどおり Shared rules（`fixpr.md:73-139`）のように 1 か所で定め、各フェーズの本文で言い換えない。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。本タスクは製品のコードを変えないので、方針の例外はない。
-   コマンドの定義（`.claude/commands/` の下）は英語で書く（`CLAUDE.md`「Language」）。
-   GitHub の上の返信と報告は日本語で書く（`CLAUDE.md`「Language」）。
-   `CLAUDE.md`「Tool Execution Safety」に従い、コマンドの Authorization に挙げていないネットワークの操作は行わない（AC-36）。

## 6. 用語集 (Glossary)

-   **フェーズ:** `/fixpr` を構成する処理の単位（Phase 1〜6）。取得・トリアージ・修正・build と push・返信と解決・PR の説明の確認、の各フェーズがある。パイプラインの「段階」（`docs/translation_glossary.md`）とは区別する。
-   **信頼する著者:** リポジトリへの書き込み権限を持つアカウントと、`_context.md` に名前を定めた自動レビュアーのアカウント（AC-01）。
-   **想定外の著者のスレッド:** コメントの 1 件以上が信頼する著者のものでないスレッド、または著者を確かめられないコメントを含むスレッド（AC-04〜AC-06）。
-   **信頼する著者のスレッド:** すべてのコメントの著者が信頼する著者であるスレッド（AC-04）。
-   **範囲外の変更:** 修正のフェーズが変えたファイルのうち、F-004 の範囲に入らないもの。
-   **build checks:** Phase 4 が commit の前に実行する検査（`make fmt && make test && make lint`、`fixpr.md:26`）。
-   **利用者:** `/fixpr`・`/runpr` を実行し、質問に答える人。
-   **caller override:** 呼び出し元が、このセッションでの指示によって、`/fixpr` に特定のスレッドの処理を求めること（`fixpr.md:57-60`）。本タスクでは、想定外の著者のスレッドの処理にも使う（AC-12）。
-   用語は `docs/translation_glossary.md` と統一する（AC-37）。
