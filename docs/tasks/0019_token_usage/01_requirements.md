## 1. 概要 (Overview)

**目的:** 本書は、LLM の API が応答で報告するトークン数（入力・キャッシュに当たった入力・出力）を、CLI がパイプラインの段階（生成・字数の調整・検証・推敲）ごとに記録し、標準エラーと中間生成物の来歴に出力するための要件を定義する。

**背景:**
現在の CLI は、LLM の応答が報告するトークン数を読み捨てている（`llm.GenerateResponse` はテキスト・モデル名・ModelVersion だけを持ち、DeepSeek と Claude のアダプタは応答の `usage` を読まない）。そのため、記事 1 本にかかった料金を後から見積もれない（[#247](https://github.com/isseis/yt2column/issues/247)）。

-   **評価で構成のコストを比べるため（直接の動機）。** タスク `0018_article_quality`（[#248](https://github.com/isseis/yt2column/issues/248)）は、構成（生成・字数の調整・検証・推敲のテンプレートとモデル）を、品質と推定コストの両方で比べる（0018 の F-007）。推定コストは、API が報告するトークン数と公開の単価から求める。
-   **文字数からは推定できない。** `claude-opus-5-5` の effort high の thinking や、DeepSeek の推論の出力トークンは、記事の文字数に現れない。文字数から推定すると、これらの構成のコストを大きく少なく見積もる。
-   **後から取り直せない。** 0018 は、固定した生成の出力の集合（基準の集合）を 1 度作り、タスク `0017_intermediate_artifacts` の `--after` で後の段階だけを当て直して比べる。再開で呼ばなかった段階のコストには、基準の集合を作った実行のトークン数を使う。その実行のときに記録していないと、後から取り直す方法がない。そのため、本タスクは 0018 の基準の集合を作る前に終える。
-   **失敗した実行にも料金がかかる。** 生成の応答の打ち切り（`llm.ErrTruncated`）などで記事を公開しなかった実行でも、それまでに呼んだ LLM の料金はかかる。0010 の評価では、`roNZ-rLxhUE` で生成の打ち切りが複数回起きている（[0010 の 02_evaluation.md](../0010_post_generation_review/02_evaluation.md) §3.5・§3.6）。現在の CLI は、失敗した実行ではエラーを報告して終わり、それまでの呼び出しの情報を残さない。

対応 issue: #247。先行: #213（0017、中間生成物の保存と再開）。後続: #248（0018）、[#99](https://github.com/isseis/yt2column/issues/99)（料金の概算の算出と、利用者への提示）。関連: #171（Claude の `max_tokens` と effort high。出力トークン数が記録できれば、この前提の確認にも使える）。

要件レビューの過程で挙がった、設計で決める事項は [design_handoff.md](design_handoff.md) に申し送る。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   LLM の呼び出し 1 回ごとに、API の応答が報告するトークン数を、プロバイダに依存しない形で取得する（F-001）。
-   応答の `usage` を信頼できない入力として検証し、規則に合わない `usage` の値を受理せず、トークン数を「不明」とする。`usage` の不在・不正で、記事の生成を失敗させない（F-002）。
-   段階ごとのトークン数を、記事の生成の結果として呼び出し元に渡す（F-003）。
-   成功した実行の標準エラーの要約に、段階ごとのトークン数を出す。`--after` で再利用した段階は、その中間生成物を作った実行の値を、再利用した値であることが分かる形で出す（F-004）。
-   記事を公開せずに失敗した実行でも、失敗までに応答を受け取った呼び出しのトークン数を標準エラーに出す（F-005）。
-   0017 の中間生成物の来歴に、その段階の呼び出しのトークン数を含める（F-006）。

### 2.2. スコープ (In Scope)

-   `internal/llm` のプロバイダに依存しないトークン数の型と、`GenerateResponse` での受け渡し（F-001）。
-   DeepSeek と Claude のアダプタでの `usage` の読み取りと検証（F-001・F-002）。
-   `ArticleWriter` の結果（成功と失敗）での段階ごとのトークン数の受け渡し（F-003・F-005）。
-   CLI の標準エラーの要約（成功と失敗）（F-004・F-005）。
-   0017 の中間生成物の形式の変更（来歴へのトークン数の追加、形式の版、`id`）（F-006）。
-   ユニットテスト（F-007）。
-   文書（README・`project_overview.md`・`security.md`・`package_reference.md`）の更新（F-008）。

### 2.3. スコープ外 (Out of Scope)

-   料金の計算（単価の保持、単価の出典と確認日、通貨、DeepSeek のピーク時間帯の料金など）。本タスクでは CLI に単価を持たせない。CLI が料金の概算を算出して利用者に示すことは、将来の予定として #99 で扱う。0018 の推定コストは、本タスクの出力から評価の側（0018 の `02_evaluation.md`）で求める。
-   トークン数の合計の計算と出力。段階ごとの値だけを出す（区分ごとに単価が異なり、トークン数の合計は料金の計算に使えないため）。
-   `--out` の記事の出力と Webhook の投稿に、トークン数を書くこと。トークン数そのものは記事の読者に不要である。料金の概算を `--out`・Webhook の投稿・CLI の要約で利用者に示すことは、#99 で扱う。本タスクは、#99 がその概算を算出できるように、段階ごとのトークン数を `ArticleWriter` の結果として呼び出し元に渡す（F-003・§4.5）。
-   localhost サーバ（タスク `0011_localhost_server`）のログや応答に、トークン数を出すこと。サーバは本タスクで変わる `writer` の結果を受け取るが、その振る舞いは変えない（AC-28）。
-   トークン数による実行の制限（予算の上限など）。
-   推論・thinking の出力トークン数の内訳（DeepSeek の `completion_tokens_details.reasoning_tokens`、Claude の `output_tokens_details.thinking_tokens`）の記録。料金は出力トークン数の全体にかかり、内訳は推定コストに要らない。
-   Claude のキャッシュの書き込みの TTL ごとの内訳（`usage.cache_creation`）の記録。本プロジェクトはプロンプトキャッシュを指定しておらず、TTL ごとの単価の差は推定コストに影響しない（キャッシュの書き込みの合計だけを記録する。F-001）。
-   機械可読な出力のための新しいフラグ（`--usage-log <path>` など）。標準エラーの要約を固定の書式にすることで足りるとした（F-004 の「決定」）。
-   API がトークン数を報告しない失敗（HTTP のエラー応答、タイムアウト、接続の失敗）でのトークン数の推定。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 呼び出しごとのトークン数の取得

`LLMClient.Generate` は、生成のテキストとモデル名に加えて、その呼び出しで API の応答が報告したトークン数を返す。トークン数は、料金の単価が異なる次の 4 つの区分に分ける。

| 区分 | 意味 | DeepSeek（Chat Completions） | Claude（Messages API） |
|---|---|---|---|
| 入力 | キャッシュから読まず、キャッシュに書き込みもしなかった入力 | `usage.prompt_cache_miss_tokens` | `usage.input_tokens` |
| キャッシュから読んだ入力 | キャッシュに当たった入力 | `usage.prompt_cache_hit_tokens` | `usage.cache_read_input_tokens` |
| キャッシュに書き込んだ入力 | キャッシュの作成に使った入力 | 区分がない。常に 0 とする | `usage.cache_creation_input_tokens` |
| 出力 | 推論・thinking の出力を含む出力 | `usage.completion_tokens` | `usage.output_tokens` |

表の対応は、2026-10-15 に次の公式の記述で確かめた。

-   **DeepSeek:** API リファレンス（`create-chat-completion`）は、`prompt_tokens` を「`prompt_cache_hit_tokens + prompt_cache_miss_tokens` に等しい」とし、`prompt_cache_hit_tokens`・`prompt_cache_miss_tokens`・`completion_tokens` を必須の要素とする。推論の出力トークン数（`reasoning_tokens`）は `completion_tokens_details`（「completion で使ったトークンの内訳」）の中にあり、`completion_tokens` の内訳として報告される。料金表は、入力をキャッシュに当たった分と当たらなかった分で別の単価とし、「入力と出力のトークンの合計に基づいて請求する」とする。キャッシュの書き込みの区分はない。`completion_tokens` が推論の出力を含むと明記した文はないので、2026-10-15 に実際の応答（`deepseek-flash`、推論が有効な既定の設定、アダプタと同じ形のリクエスト）で確かめた。`completion_tokens` は 59、`completion_tokens_details.reasoning_tokens` は 38 で、残りの 21 は本文（52 文字）に見合う。`total_tokens`（109）は `prompt_tokens`（50）と `completion_tokens` の和だった。したがって、`completion_tokens` は推論の出力を含む。リポジトリに記録済みの実際の応答（`testdata/deepseek_chat_completion_stop.json`・`deepseek_chat_completion_length.json`）も同じ形で、打ち切りの応答（`finish_reason` が `length`）も `usage` を持つ（後者は `completion_tokens` と `reasoning_tokens` がともに 16 で、推論の途中で打ち切られている）。
-   **Claude:** プロンプトキャッシュの文書は、`input_tokens` を「キャッシュから読まず、キャッシュの作成にも使わなかった入力のトークン数」とし、入力の合計を `cache_read_input_tokens + cache_creation_input_tokens + input_tokens` とする。公式の Go SDK（`anthropic-sdk-go` の `Usage`）は、4 つの要素をすべて必須とし、`output_tokens_details` について「`output_tokens` は請求に使う、内訳を含む正式な合計である」とする。thinking の出力は `output_tokens` に含まれる。公式の Python SDK（`anthropic-sdk-python` の `Usage`）は、`input_tokens`・`output_tokens` を `int`、`cache_creation_input_tokens`・`cache_read_input_tokens` を `Optional[int]` とする。後の 2 つは、要素としては必須だが、値が `null` になり得る。リポジトリに記録済みの実際の応答（`testdata/claude_messages_end_turn.json`・`claude_messages_max_tokens.json`、2026-10 の記録）では、2 つとも `0` であり、打ち切りの応答（`stop_reason` が `max_tokens`）も `usage` を持つ。

プロバイダ固有の要素名と、区分への対応は、アダプタ（`internal/llm/<provider>`）の中に閉じる。`internal/llm` には、プロバイダに依存しない 4 つの区分だけを置く（0009・0010 と同じく、[CLAUDE.md](../../../CLAUDE.md)「Provider details stay in their adapter package」）。DeepSeek の「キャッシュに書き込んだ入力」を 0 とするのは、DeepSeek がその区分を持たず、料金も取らないことをアダプタで宣言した対応であり、応答の値を補ったものではない。

Claude の `cache_read_input_tokens`・`cache_creation_input_tokens` が `null` の場合は、その区分を 0 として記録する。これは、文書化された値（`null`）に対する、アダプタで宣言した解釈であり、壊れた入力の修復ではない。0 としてよい理由は、本プロジェクトが Claude へのリクエストでプロンプトキャッシュを指定しておらず（`cache_control` を送らない）、キャッシュの読み書きが起きないためである。`null` を不明（F-002）として扱うと、文書どおりの応答で、トークン数が分かるはずの呼び出しの記録が欠ける。将来プロンプトキャッシュを指定する場合は、`null` が「0」と「報告なし」のどちらを意味するかを確かめ直し、本書を変更する（§5）。要素がない場合と、`null` 以外の不正な値は、F-002 のとおりトークン数を不明とする。

**Acceptance Criteria**:
- **AC-01**: DeepSeek のアダプタは、受理した応答について、`usage.prompt_cache_miss_tokens` を入力、`usage.prompt_cache_hit_tokens` をキャッシュから読んだ入力、`usage.completion_tokens` を出力として返し、キャッシュに書き込んだ入力を 0 として返す。4 つの区分がそれぞれ異なる値の応答で、各区分が対応する要素の値になることを確かめる。
- **AC-02**: Claude のアダプタは、受理した応答について、`usage.input_tokens` を入力、`usage.cache_read_input_tokens` をキャッシュから読んだ入力、`usage.cache_creation_input_tokens` をキャッシュに書き込んだ入力、`usage.output_tokens` を出力として返す。4 つの区分がそれぞれ異なる値の応答で、各区分が対応する要素の値になることを確かめる。
- **AC-02a**: Claude の応答の `usage.cache_read_input_tokens` または `usage.cache_creation_input_tokens` が `null` の場合、アダプタは応答を受理し、その区分を 0 として返す。2 つの要素のそれぞれについて、その要素だけが `null` の応答で確かめる。`input_tokens`・`output_tokens` の `null` は、AC-05 のとおり拒否する。
- **AC-03**: `internal/llm` のトークン数の型と `GenerateResponse` は、プロバイダ固有の要素名（`prompt_cache_hit_tokens`・`cache_read_input_tokens` など）を含まない（静的な確認）。

#### F-002: 応答の `usage` の検証

応答の `usage` は、ネットワークから受け取る信頼できない入力である。既存の応答の検証（0003 の DeepSeek、0009 の Claude）と同じく `internal/strictjson` の規則で検証し、規則に合わない値を受理しない（[requirements_process.md](../../dev/developer_guide/requirements_process.md)「Untrusted input boundaries」）。ただし、`usage` の検証の失敗は、応答の拒否にしない。その呼び出しのトークン数を「不明」とし、応答のほかの部分は本タスクの前と同じに扱う。

**決定（issue #247 の検討事項 1）:** `usage` がない応答、または `usage` の消費する要素がない・形が不正な応答でも、記事の生成は続ける。その呼び出しのトークン数は「不明」として記録し、出力する。理由は次のとおり。

-   料金の把握は、評価（0018）では重要だが、ツールを使い始めてからは副次的な情報である。トークン数は記事の正しさに関わらない。
-   `usage` の不在・不正を応答の拒否にすると、プロバイダが `usage` の形を変えただけで、記事が 1 本も生成できなくなる。副次的な情報のために、本来の機能を失う危険は冒さない。

「不明」は、壊れた値の修復ではない。不正な `usage` から値を推測したり、0 で補ったり、正しい要素だけを部分的に使ったりはしない（[CLAUDE.md](../../../CLAUDE.md)「Reject, don't normalize」）。`usage` の値は受理せずに捨て、「不明」という、0 とも区別できる状態を宣言して記録する。不明になったことは、標準エラーの要約で、その段階の行に理由とともに示す（F-004・F-005）。

評価（0018）への影響: 不明が混ざると、その記事の推定コストを求められない。0018 は、基準の集合を作る実行の標準エラーで不明の行がないことを確かめ、不明があればその場で気付ける（不明の行は固定の語で示す。AC-15）。現在の両プロバイダの応答は `usage` を持つので（F-001）、不明はプロバイダの仕様変更か異常な応答のときにだけ起きる。評価のために不明を失敗にする厳格な指定（フラグなど）は設けない（YAGNI）。

**Acceptance Criteria**:
- **AC-04**: 応答に `usage` がない、または `usage` がオブジェクトでない（`null` を含む）場合、アダプタは、応答のほかの部分が正しければ本タスクの前と同じ結果（テキスト・モデル名・ModelVersion）を返し、エラーを返さない。その呼び出しのトークン数は「不明」であり、0 と区別できる。
- **AC-05**: `usage` の中の、F-001 の表でそのアダプタが消費する要素のどれかがない場合、または値が負でない整数でない（負数、小数、`int64` で表せない数（例: `9223372036854775808`）、文字列、真偽値、`null`、配列、オブジェクト）場合、AC-04 と同じく、トークン数を「不明」とし、応答を拒否しない。ほかの消費する要素が正しくても、その値を部分的に使わない（4 つの区分のすべてが不明になる）。ただし、Claude の `cache_read_input_tokens`・`cache_creation_input_tokens` の `null` は、不正ではなく 0 として受理する（AC-02a）。要素ごと・不正な形ごとに、その入力だけで不明になることを確かめる。
- **AC-06**: `usage` の中で、消費する要素が重複している場合、AC-05 と同じく、トークン数を「不明」とする。後に現れた値も先に現れた値も使わない。
- **AC-07**: `usage` の中の、消費しない要素（DeepSeek の `prompt_tokens`・`total_tokens`・`prompt_tokens_details`・`completion_tokens_details`、Claude の `cache_creation`・`output_tokens_details`・`server_tool_use`・`service_tier`・`inference_geo` など、および未知の要素）は、値の種類にかかわらず無視する（拡張可能として宣言する。既存のアダプタの応答の最上位と同じ規則）。それらがあっても、トークン数は不明にならない。
- **AC-08**: トークン数が不明になった理由は、壊れた規則と要素の名前だけで示し、応答のテキストと `usage` の値を含めない。
- **AC-09**: `usage` の検証の結果は、応答のほかの検証の結果を変えない。応答の本文が規則に合わない場合（`ErrInvalidResponse`）、打ち切り（`llm.ErrTruncated`）、想定外の終了理由（`llm.ErrUnexpectedFinishReason`）、空の応答（`llm.ErrEmptyResponse`）は、`usage` が正しいか不明かにかかわらず、本タスクの前と同じエラーになる。`usage` だけが規則に合わない正常な応答は、本タスクの前と同じく受理される。

#### F-003: 段階ごとのトークン数の受け渡し

`ArticleWriter` は、記事の生成の結果として、LLM を呼んだ段階ごとにトークン数を呼び出し元に渡す。1 本の記事の LLM の呼び出しは、生成 1 回・字数の調整 0〜1 回・検証・推敲 0〜1 回である（0010 の §4.1）。

**Acceptance Criteria**:
- **AC-10**: 生成・字数の調整・検証・推敲がすべて走った実行で、`ArticleWriter` の結果は、3 つの段階それぞれのトークン数を持ち、各値はその段階の `LLMClient` が返したトークン数と一致する。段階ごとに異なる値を返す fake の `LLMClient` で、段階の取り違えがないことを確かめる。
- **AC-11**: 字数の調整が LLM を呼ばなかった実行、検証・推敲が走らなかった実行（`--no-review` を含む）では、その段階のトークン数は「呼ばなかった」ことが分かる形で表される。各段階は「呼ばなかった」「呼んでトークン数が分かった（0 を含む）」「呼んだがトークン数が不明」の 3 つを区別できる。
- **AC-11a**: ある段階の `LLMClient` がトークン数を「不明」として返した成功した実行で、`ArticleWriter` は記事を返し、その段階のトークン数は不明として渡される。ほかの段階のトークン数は影響を受けない。

#### F-004: 成功した実行の要約への出力

成功した実行は、標準エラーの要約に、段階ごとのトークン数を 1 段階 1 行で出す。各行は、段階の名前・モデル名・4 つの区分のトークン数と、その値がこの実行の呼び出しのものか、`--after` で再利用した中間生成物のものかを示す。

**決定（issue #247 の検討事項 2）:** 機械可読な出力のための新しいフラグは設けない。代わりに、トークン数の行の書式を固定し、README に書く。0018 は、実行の標準エラーをファイルに残し、この行から値を読む。理由は次のとおり。

-   失敗した実行のトークン数は中間生成物に残らない（F-005）。中間生成物の来歴だけでは、0018 の失敗した実行の記録（0018 の AC-20）を満たせない。標準エラーなら、成功と失敗の両方を同じ書式で読める。
-   新しいフラグは、出力先の検査（キャッシュディレクトリの中の拒否など）と、新しい書き込みの失敗の扱いを要する。0018 の記録の量（構成ごとに 10 件 × 3 段階）では、固定の書式の行で足りる。

**決定（issue #247 の検討事項 5）:** 呼ばなかった段階（字数の調整が走らなかった、検証・推敲を無効にした）の行は出さない。0 の行は出さない。0010 の AC-22（`--out` の出力に、呼ばなかった段階のモデルの行を書かない）と同じ規則である。

**Acceptance Criteria**:
- **AC-12**: 生成・字数の調整・検証・推敲がすべて走って成功した実行の標準エラーに、3 つの段階それぞれについて 1 行、段階の名前・モデル名・入力・キャッシュから読んだ入力・キャッシュに書き込んだ入力・出力のトークン数が、F-003 で渡された値のとおりに出る。
- **AC-13**: 字数の調整が LLM を呼ばなかった、または検証・推敲が走らなかった成功した実行では、その段階のトークン数の行を出さない。
- **AC-14**: `--after` で再開した成功した実行では、再開が読み込んだ中間生成物の段階（`--after generation` では生成、`--after shorten` では生成と字数の調整、`--after review` では 3 つの段階のうち保存されたもの）の行に、その中間生成物の来歴のトークン数とモデル名を出し、その行が再利用した値であることを示す。再開で呼んだ段階の行は、この実行の呼び出しの値を出し、再利用の印を付けない。
- **AC-15**: トークン数の行の書式（段階の名前・区分の並び・再利用の印・不明の印）は、README に書かれている（静的な確認）。書式は、段階の名前・再利用の印・不明の印を、行の固定の位置の固定の語で示し、モデル名などの値の内容から判定させない。
- **AC-15a**: トークン数が不明の段階（AC-11a）がある成功した実行では、その段階の行は、不明の印と、不明になった理由（AC-08）を示し、数値を出さない。0 を出さない。実行は記事を公開し、終了コードは 0 である。

#### F-005: 失敗した実行のトークン数の出力

記事を公開せずに失敗した実行（LLM の応答の拒否、字数の上限、中間生成物の保存の失敗、公開の失敗などで終了コードが 0 でない実行）も、失敗までに受け取った呼び出しのトークン数を、標準エラーに F-004 と同じ書式で出す。対象は次のとおり。

-   失敗の前に完了した段階の呼び出し（例: 検証・推敲が失敗したときの生成と字数の調整）。
-   失敗した呼び出しのうち、応答の本文を受け取ったもの（打ち切り・想定外の終了理由・空の応答）。その `usage` が F-002 の規則を満たせばその値を、満たさなければ不明を出す。
-   `--after` で再利用した段階（F-004 と同じく、再利用の印を付ける）。

失敗した呼び出しのうち、トークン数を得られなかったもの（HTTP のエラー応答、タイムアウト、接続の失敗、応答の本文の形の検証の失敗（`ErrInvalidResponse`））は、その段階について、トークン数が不明であることを示す行を出す。課金されたかどうかを CLI は判断しない。

**Acceptance Criteria**:
- **AC-16**: 検証・推敲の呼び出しが失敗した実行（fake の検証・推敲の `LLMClient` がエラーを返す）の標準エラーに、生成と字数の調整のトークン数の行が、F-004 と同じ書式で出る。実行は記事を公開せず、終了コードは 0 でない。
- **AC-17**: 生成の呼び出しが打ち切り（`llm.ErrTruncated`）で失敗し、その応答の `usage` が規則を満たす場合、標準エラーに、生成のトークン数の行が、その応答の値で出る。`usage` が規則を満たさない場合は、不明の行が出る（AC-15a と同じ表し方）。想定外の終了理由（`llm.ErrUnexpectedFinishReason`）・空の応答（`llm.ErrEmptyResponse`）でも同じである。アダプタは、これらのエラーとともにトークン数を呼び出し元に渡す（DeepSeek と Claude の両方で、記録した形の応答で確かめる）。
- **AC-18**: トークン数を得られなかった失敗（fake の `LLMClient` が `context.DeadlineExceeded` を返す、`ErrInvalidResponse` を返すなど）では、その段階の行は、AC-15a と同じ不明の印で示し、数値を出さない。0 を出さない。
- **AC-19**: すべての呼び出しが成功した後に、字数の上限（0010 の F-001 の 4）・中間生成物の保存・公開のいずれかで失敗した実行でも、呼んだ段階すべてのトークン数の行が出る。
- **AC-20**: LLM を 1 つも呼ぶ前に終わった実行（使い方の誤り、設定の誤り、字幕の取得の失敗、`--after` の入力の拒否）では、トークン数の行を出さない。ただし、`--after` の入力を受理した後に失敗した実行は、AC-14 と同じく再利用した段階の行を出す。

#### F-006: 中間生成物の来歴へのトークン数

0017 の中間生成物は、その段階の呼び出しのトークン数（4 つの区分）を来歴に記録する。トークン数が不明の呼び出しの中間生成物は、不明であることを記録する（0 と区別できる形。表し方は設計で決める）。`--after` で再開した実行は、読み込んだ中間生成物のトークン数を F-004・F-005 の要約に使う。0018 は、再開で呼ばなかった段階のコストを、この値から求める。

**決定（issue #247 の検討事項 3）:**

-   中間生成物の形式の版（`version`）を上げる。古い版（本タスクより前の CLI が保存したもの）の中間生成物は、再開の入力として受理せず、0017 の中間生成物の拒否と同じ番兵エラーで拒否する。0017 の §4.4 は、別のバージョンの CLI との互換を対象外としている。トークン数のない中間生成物を受理すると、再開した実行の要約で、その段階のトークン数を出せない（0018 の記録が欠ける）。
-   トークン数を中間生成物の `id`（内容から計算する識別子）の計算に含める。トークン数も来歴の一部であり、モデル名と同じく、どの呼び出しから来たものかを示す。含めないと、トークン数だけが異なる 2 つの中間生成物が同じ `id` になり、`id` で中間生成物を区別できなくなる。

**Acceptance Criteria**:
- **AC-21**: `--artifacts` を付けた実行で保存した生成・字数の調整・検証・推敲の中間生成物は、それぞれ、その段階の呼び出しのトークン数（4 つの区分）を来歴に持ち、その値は F-003 で渡された値と一致する。トークン数が不明の段階の中間生成物は、不明であることを記録し、保存と再開の妨げにならない。`--after` でそれを再利用した実行の要約は、その段階の行に、再利用の印と不明の印を出す。
- **AC-22**: 中間生成物のトークン数の要素が、ない、重複している、または設計で定める不明の表し方でも負でない整数でもない（負数、小数、`int64` で表せない数、文字列など）場合、その中間生成物は 0017 の中間生成物の破損の番兵エラー（`artifact.ErrMalformed`）で拒否され、LLM を呼ばず、記事を公開しない。要素ごと・不正な形ごとに、その入力だけで拒否することを確かめる。
- **AC-23**: 本タスクより前の形式の版の中間生成物は、再開の入力として、0017 の中間生成物の破損の番兵エラー（`artifact.ErrMalformed`）で拒否される。
- **AC-24**: トークン数だけが異なる 2 つの中間生成物は、異なる `id` を持つ。中間生成物のトークン数だけを書き換えたファイルは、記録した `id` と内容が一致しないものとして、同じ番兵エラー（`artifact.ErrMalformed`）で拒否される。

#### F-007: テスト可能性

**Acceptance Criteria**:
- **AC-25**: アダプタのトークン数の取得と検証（F-001・F-002・AC-17）のユニットテストは、実際の API を呼ばず、`net/http/httptest` と、記録した形の応答で確かめる。
- **AC-26**: `ArticleWriter` と CLI のトークン数の受け渡しと出力（F-003〜F-006）のユニットテストは、実際の API・`yt-dlp`・Webhook を呼ばず、段階ごとに異なるトークン数を返す fake の `LLMClient`、fake の `TranscriptSource` と `Publisher`、`t.TempDir` を使う。
- **AC-27**: 既存のテストのうち、トークン数に関わらない振る舞い（記事の本文、モデル名の行、検証・推敲の一覧、中間生成物の再開の規則）を検証するものは、fake の `LLMClient` の変更（トークン数を返すこと）を除き、本タスクの後もそのまま通る。
- **AC-28**: localhost サーバ（`internal/server`）の既存のテストは、本タスクの後もそのまま通る（サーバの振る舞いは変えない）。

#### F-008: 文書

**Acceptance Criteria**:
- **AC-29**: README に、成功・失敗した実行の標準エラーのトークン数の行の書式と、各区分の意味、再利用の印、不明の表し方が書かれている。`project_overview.md` の CLI の出力の説明と、`security.md` の LLM の応答の検証の節に、`usage` の受理する形と拒否の規則が加えられている。`package_reference.md` に、`internal/llm` のトークン数の型が加えられている（静的な確認）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

本タスクが新たに扱う境界は、LLM の応答の `usage` と、中間生成物のトークン数の要素である。応答の本文（テキスト・終了理由・モデル名）と、中間生成物のほかの要素の境界は、既存のタスク（0003・0009・0017）のままとする。

| 境界 | 消費する要素 | 受理する形 | 上限 | 拒否時の扱い | 主な AC |
|---|---|---|---|---|---|
| DeepSeek の応答の `usage` | `prompt_cache_hit_tokens`・`prompt_cache_miss_tokens`・`completion_tokens` | オブジェクト。消費する要素はそれぞれ 1 回だけ現れ、負でない整数で `int64` で表せる。消費しない要素は拡張可能として無視する | `int64` の範囲（応答全体の上限は既存のとおり） | `usage` の値を受理せず、トークン数を「不明」とする。応答は拒否しない（部分的な値も使わない） | AC-04〜AC-09 |
| Claude の応答の `usage` | `input_tokens`・`cache_read_input_tokens`・`cache_creation_input_tokens`・`output_tokens` | 同上。ただし `cache_read_input_tokens`・`cache_creation_input_tokens` は `null` も受理し、0 として記録する | 同上 | 同上 | AC-02a・AC-04〜AC-09 |
| 中間生成物のトークン数 | 4 つの区分、または不明であること | 宣言した要素だけを持ち、それぞれ 1 回だけ現れ、負でない整数で `int64` で表せる。または、設計で定める不明の表し方（0017 の中間生成物は、宣言していない要素を拒否する） | `int64` の範囲（ファイル全体の上限は 0017 のとおり） | `artifact.ErrMalformed`（0017 の中間生成物の破損）。LLM を呼ばず、公開しない | AC-22〜AC-24 |

-   標準ライブラリが黙って修復・破棄・無視すれば受理できてしまう入力（`int64` を超える数の丸め、小数の切り捨て、重複した要素の後勝ち）は、受理しない。応答の `usage` では、その呼び出しのトークン数を不明とし、中間生成物では、その中間生成物を拒否する。応答の `usage` を中間生成物より緩く扱うのは、前者がプロバイダの仕様変更で変わり得る外部の形であり、後者は本プロジェクトが書いた形だからである。不正な形の検出方法は `02_architecture.md` で決める。
-   トークン数の値によって実行する処理を選ばない。トークン数は記録して出力するだけで、生成・字数の調整・検証・推敲の振る舞いを変えない（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   トークン数の読み取りと出力は、LLM の呼び出しに比べて無視できる時間で終わればよい。性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   LLM の呼び出しの回数・リクエストの内容（プロンプト、`max_tokens` など）は変えない。トークン数の取得のために、追加の API 呼び出し（トークン数を数える API など）を行わない。

### 4.2. セキュリティ (Security)

-   トークン数の行とエラーメッセージに、API キー・Webhook URL・共有トークン・応答のテキスト・素材を含めない（[security.md](../../dev/security.md) §2・§6）。トークン数とモデル名だけを出す。モデル名は、既存の応答のモデル名の検証（0004 の AC-25・AC-29・AC-31）を通った値だけを出す。
-   トークン数が不明になった理由は、壊れた規則と要素の名前だけを示す（AC-08）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   `usage` の不在・不正で、記事の生成を失敗させない（F-002）。プロバイダが `usage` の形を変えても、記事は生成・公開でき、その呼び出しのトークン数は不明として示される。
-   失敗した実行でも、失敗までに受け取った呼び出しのトークン数を失わない（F-005）。

### 4.4. 互換性 (Compatibility)

-   CLI のフラグ・終了コード・`--out` の出力・Webhook の投稿は変えない。標準エラーには、トークン数の行が加わる（F-004・F-005）。既存の要約の行（公開先とモデル名、字数の調整が走ったこと、検証・推敲の項目数）は変えない。
-   中間生成物の形式の版を上げる。本タスクより前の CLI が保存した中間生成物は、再開の入力として拒否する（AC-23）。0017 の §4.4 のとおり、別のバージョンの CLI との互換は対象外とする。
-   `writer.Article` などの exported の型の形を変える場合は、`internal/pipeline` の guard（`TestCommonTypesFieldSets`）を同じ変更で更新する（[design_handoff.md](design_handoff.md) H-03）。

### 4.5. 保守性 (Maintainability)

-   プロバイダ固有の要素名と区分への対応は、アダプタの中だけに置く（F-001・AC-03）。プロバイダを追加するときは、そのアダプタが 4 つの区分への対応を宣言する。
-   `usage` の検証は、既存の応答の検証（`internal/strictjson`）を再利用し、複製しない（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   中間生成物のトークン数の保存と読み込みは、0017 の形式の定義（保存と読み込みが同じ定義を読む）に加え、別の定義を作らない。
-   要約の行の書式は 1 か所で定義し、成功と失敗の両方が同じ定義を使う（F-004・F-005）。
-   段階ごとのトークン数は、モデル名とともに `ArticleWriter` の結果から取り出せるようにする。#99 は、この値とモデル名から料金の概算を算出し、`Publisher`（Webhook・`--out`）と CLI の要約に渡す。本タスクは、その算出と提示のための経路（単価の参照、`Publisher` への受け渡し）を作らない（YAGNI）が、トークン数を CLI の要約の中だけに閉じた形にしない。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」と [CLAUDE.md](../../../CLAUDE.md) に従う。外部ライブラリを追加しない。
-   本タスクは、0017 の中間生成物の形式（来歴）を変える。0017 の要件定義書は `approved` であり、本書の F-006 を 0017 の F-001（来歴）への追加として扱う。0017 の再開の規則（F-003・F-004）は変えない。
-   本タスクは、0003（DeepSeek）と 0009（Claude）のアダプタに、`usage` の読み取りと検証を加える。`usage` の検証の結果は、応答の受理・拒否を変えない（AC-09）。応答のテキスト・終了理由・モデル名の検証は変えない。
-   パイプラインの各段階の振る舞い（プロンプト、モデル、呼び出しの回数、出力の検証）を変えない。本タスクは、各呼び出しのトークン数を記録して出力するだけである。
-   ユニットテストは、実際の `yt-dlp` も LLM の API も Webhook も呼ばない（[CLAUDE.md](../../../CLAUDE.md)「Testing Strategy」）。F-001 の DeepSeek の確認のための実際の API の呼び出しは、人の承認を得て、要件定義の段階で 1 回だけ行った。
-   Claude へのリクエストでプロンプトキャッシュを指定しないこと（`cache_control` を送らないこと）を、F-001 の `null` の解釈の前提とする。プロンプトキャッシュを指定する変更は、本書の変更を伴う。
-   0018 は本タスクの完了後に基準の集合を作る（§1）。

## 6. 用語集 (Glossary)

-   **トークン数:** LLM の API の応答が `usage` で報告する、その呼び出しで処理したトークンの数。本書では、入力・キャッシュから読んだ入力・キャッシュに書き込んだ入力・出力の 4 つの区分に分ける（F-001）。
-   **キャッシュから読んだ入力:** プロバイダのプロンプトのキャッシュに当たった入力のトークン数。DeepSeek の `prompt_cache_hit_tokens`、Claude の `cache_read_input_tokens`。
-   **キャッシュに書き込んだ入力:** プロバイダのプロンプトのキャッシュの作成に使った入力のトークン数。Claude の `cache_creation_input_tokens`。DeepSeek にはこの区分がない。
-   **出力:** 生成のテキストと、推論・thinking の出力を含む出力のトークン数。
-   **再利用した値:** `--after` で再開した実行が、読み込んだ中間生成物の来歴から出すトークン数。その中間生成物を作った実行の呼び出しの値である（F-004・F-006）。
-   **推定コスト:** トークン数と公開の単価から求めた LLM の料金の推定値。本タスクでは求めない（0018 の F-007）。
-   **段階・中間生成物・来歴・再開:** 0017 の用語と同じ。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
