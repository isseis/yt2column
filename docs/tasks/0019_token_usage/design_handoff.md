# 設計への申し送り：LLM のトークン数の段階ごとの記録と出力

本書は、[01_requirements.md](01_requirements.md) のレビューで挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 区分の対応を実際の応答で確かめる

-   **事項:** F-001 の表の対応のうち、公式の文書が明記していない点を、記録した実際の応答で確かめる。
    -   DeepSeek の `completion_tokens` が、推論の出力（`completion_tokens_details.reasoning_tokens`）を含むこと。`completion_tokens` が `reasoning_tokens` 以上であり、本文のトークン数を足した値と整合すること。
    -   Claude の `cache_read_input_tokens`・`cache_creation_input_tokens` が、キャッシュを指定しない本プロジェクトのリクエストでも、`null` ではなく整数（0）で返ること。`null` が返る場合は、F-002 の決定（拒否する）では記事が生成できなくなるので、要件定義書を変更する。
-   **理由:** DeepSeek の文書は、推論のトークン数を `completion_tokens` の内訳として示すが、含むと明記していない。Claude の Go SDK は 4 つの要素を必須とするが、`null` の可否を示していない（要件定義書 F-001・F-002）。
-   **候補の方針:** 人の承認を得て、両プロバイダに 1 回ずつ（DeepSeek は推論を有効にした既定の設定、Claude は effort を指定した既定の設定で）リクエストを送り、応答の `usage` を記録する。記録した応答は、アダプタのテストの入力の形の根拠にする。記事の本文を含む応答を `testdata/` に置く場合は、[security.md](../../dev/security.md) §7 の規則に従う。
-   **関連:** F-001、F-002、AC-01・AC-02・AC-05

## H-02: 失敗した呼び出しのトークン数の受け渡し

-   **事項:** 打ち切り・想定外の終了理由・空の応答で失敗した呼び出しのトークン数を、エラーとともに呼び出し元に渡す方法を決める。次を含む。
    -   `LLMClient.Generate` がエラーを返すときに、トークン数をどう運ぶか（エラーの型に持たせて `errors.AsType` で取り出す、エラーのときも `GenerateResponse` のトークン数だけを返す、など）。`LLMClient` の契約（「エラーのときはゼロ値を返す」に当たる既存の規則）との関係。
    -   `ArticleWriter.Write` が失敗したときに、それまでの段階のトークン数と、失敗した呼び出しのトークン数（または不明であること）を CLI に渡す方法。0017 の「返る `Article` はゼロ値」の規則との関係。
    -   中間生成物の保存の失敗・字数の上限・公開の失敗（すべての呼び出しが成功した後の失敗）で、CLI がトークン数を出す経路。
-   **理由:** 現在のアダプタは、拒否のときに `GenerateResponse` のゼロ値を返し、`ArticleWriter` は失敗のときにゼロ値の `Article` を返す。失敗した実行のトークン数（要件定義書 F-005）を出すには、この契約を変える必要がある。
-   **関連:** F-005、AC-16〜AC-20

## H-03: `Article` と結果の型の形

-   **事項:** 段階ごとのトークン数を、`writer.Article` などの結果の型にどう持たせるかを決める。次を含む。
    -   `StepModel` にトークン数を加えて、生成・字数の調整・検証・推敲のすべてで同じ型を使うか。現在、生成のモデルは `Article.Model`・`ModelVersion`、字数の調整は `Article.Shorten`、検証・推敲は `Article.Review.Model` にあり、形がそろっていない。
    -   「呼ばなかった」と「0 のトークン数で呼んだ」を区別する表し方（要件定義書 AC-11）。
    -   「この実行の呼び出し」と「再利用した中間生成物の値」を区別する表し方（AC-14）。値の由来を、値の内容から推測せず、型で宣言する（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。
    -   exported のフィールドの集合を変えるなら、`internal/pipeline` の guard（`TestCommonTypesFieldSets`）を同じ変更で更新する。`GenerateResponse` の変更が及ぶ各テストの fake の `LLMClient` の範囲。
-   **理由:** issue #247 の検討事項 4。要件定義書は、観測できる振る舞い（区別できること）だけを定める。
-   **関連:** F-003、F-004、F-006、AC-10・AC-11・AC-14、§4.4

## H-04: 要約の行の書式

-   **事項:** トークン数の行の具体的な書式を決める。次を含む。
    -   段階の名前（`generation`・`shorten`・`review` など、0017 の `--after` の値とそろえるか）、区分の名前と並び、再利用の印、不明の表し方。
    -   既存の要約の行（公開先とモデル名、字数の調整が走ったこと、検証・推敲の項目数）との順序。失敗した実行では、エラーメッセージの前に出すか後に出すか。
    -   0018 がファイルに残した標準エラーから行を取り出しやすいこと（固定の接頭辞、1 段階 1 行、値の区切り）。モデル名に空白や区切りの文字が含まれても、行の解釈が曖昧にならないこと（モデル名は応答のモデル名の検証を通った値）。
-   **理由:** 要件定義書は、行に含める値と、固定の位置の固定の語で判定できること（AC-15）だけを定める。
-   **関連:** F-004、F-005、AC-12〜AC-15・AC-18

## H-05: 中間生成物の形式の変更

-   **事項:** 0017 の中間生成物に、トークン数を加える形を決める。次を含む。
    -   要素の名前と構造（4 つの区分を 1 つのオブジェクトにまとめるか、最上位に並べるか）。0017 の `CollectOnly` の規則（宣言していない要素を拒否する）をトークン数の要素にも適用する。
    -   形式の版（`artifactVersion`）を 2 に上げることと、版 1 の拒否のエラーメッセージ（古い CLI の中間生成物であることが分かる文言）。
    -   `id` の計算（`recordID`）にトークン数を加える位置。
    -   `--after review` の再開で、生成と字数の調整の中間生成物を照合のために読み込む既存の経路から、それらのトークン数を要約に渡す方法（AC-14）。
-   **理由:** 要件定義書 F-006 の決定を実装する形は、0017 の形式の定義の中で決める。
-   **関連:** F-006、AC-14・AC-21〜AC-24

## H-06: 数値の検証の方法

-   **事項:** `usage` と中間生成物のトークン数の値を、負でない `int64` として検証する方法を決める。`internal/strictjson` の `Value.AsInt64` が、小数（`1.0`・`1.5`）・指数表記（`1e3`）・`int64` を超える数・負のゼロ（`-0`）をどう扱うかを確かめ、要件定義書の「負でない整数で `int64` で表せる」を満たすようにする。負数の拒否は、`AsInt64` の後に呼び出し側で行うか、`strictjson` に負でない整数を読む関数を加えるか（DeepSeek・Claude・中間生成物の 3 か所で共有する）。
-   **理由:** [requirements_process.md](../../dev/developer_guide/requirements_process.md) の型ごとの確認表（Numbers）。数の表記の受理の範囲は、要件定義書では「負でない整数」とだけ定め、具体的な構文の扱いを設計で決める。
-   **関連:** F-002、F-006、AC-05・AC-22
