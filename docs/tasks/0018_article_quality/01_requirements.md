## 1. 概要 (Overview)

**目的:** 本書は、生成した記事がタスク `0008_column_prompt` の合格条件（0008 の F-006・AC-17）を満たすように、記事を作る構成（生成・字数の調整・検証・推敲のテンプレートとモデル）を改善するための要件と、その評価の要件を定義する。

**背景:**
0008 では、記事を 1 回の LLM 呼び出しで生成するテンプレートを v5 まで調整したが、合格条件を満たせず、評価を保留した（[0008 の 02_evaluation.md](../0008_column_prompt/02_evaluation.md)、以下「0008 評価記録」）。続くタスク `0010_post_generation_review` では、生成の後に字数の調整と検証・推敲の 2 つの段階を加え、v5 のテンプレートと組み合わせて評価した（[0010 の 02_evaluation.md](../0010_post_generation_review/02_evaluation.md)、以下「0010 評価記録」）。結果は次のとおりで、どの構成も 1 回目の 5 本で合格条件を満たしていない。

| 構成（生成は v5・deepseek-flash） | 合格 | 記録 |
|---|---|---|
| 段階なし | 0/5 | 0008 評価記録 §5.6 |
| 検証・推敲が deepseek-flash | 0/5 | 0010 評価記録 §3.1 |
| 検証・推敲が claude-sonnet-5-5（medium） | 2/5 | 0010 評価記録 §3.5 |
| 同上、検証・推敲のテンプレートを強めた版 | 2/5 | 0010 評価記録 §3.6 |
| 検証・推敲が claude-opus-5-5（high）、強めたテンプレート | 3/5 | 0010 評価記録 §3.7 |

最も合格の多い構成（0010 評価記録 §3.7）でも、次の不合格が残った。

-   **評した人と評された人の取り違え（`18tbwwPM91A`）:** 松井がイチローを評した天才の定義を、イチローが松井を評した理由として書く。0008 の v1 以降、生成のモデルとテンプレートを変えても繰り返し現れ、検証・推敲は直せなかった。§3.7 では、検証・推敲がこれを直そうとして、新しい話者のずれを入れた。
-   **最も重要な論点の欠落（`roNZ-rLxhUE`）:** 最も重要な論点が記事から欠け、観点「重要度の順」が 1 になる。この動画は字数の調整が走るので、生成で落ちたのか、字数の調整が落としたのかを区別できなかった。
-   **意味の取れない文（`roNZ-rLxhUE`）:** 字幕の崩れを写した文（「ロボットが自衛隊のようなものを目指す」）が、0008 の v5 以降どの構成でも残り、観点「読みやすさ」が 1 になる。
-   **長さの不足（`18tbwwPM91A`）:** 本文が下限の 2,500 字を下回った（生成のばらつき）。

生成のモデルを変えた評価もある。0008 評価記録 §5.9 では、生成を claude-opus-5-5（effort medium）にし、字数の調整と検証・推敲なしで生成して、5 本のうち 1 本が合格した（LLM の判定で、人の確認はまだ）。誤認識の写しと、字数・節の数・タイトルの字数の不合格はなくなった。一方、話者の言葉を広げる一般化（「最も〜」）と確かめられない話者の割り当てによる観点「根拠」の不合格が 4 本に残り、`roNZ-rLxhUE` では最も重要な論点が 5 節中 4 番目の節に回った（観点「重要度の順」が 1）。生成のモデルを上位にするだけでは、話者と論点の選び方の原因は直らない。生成と検証・推敲の両方を claude-opus-5-5 にした構成は、まだ評価していない。

残った原因のうち話者に関わるものは、映像も音声もなく、句読点も話者の区別もない字幕だけから話者を特定する課題である。0008 評価記録 §5.5 は、これをモデルの能力より課題そのものの難しさによると判断した。人が字幕だけを読んでも、話者を確実に特定できるとは限らない。また、0008 の合格条件は 10 件すべての合格を求める。記事 1 本が合格する確率を p とし、10 件が互いに独立とすると、10 件すべてが合格する確率は p の 10 乗で、p が 0.8 なら約 11%、0.9 でも約 35% である。最も合格の多い構成（3/5）の記事 1 本あたりの合格の割合は 0.6 で、その場合の確率は 1% に満たない。そのため本タスクでは、構成の改善と並行して、この物差しに緩和の余地があるかを判断する材料も集める（F-009）。

0010 の評価には、記録の側にも限界があった。各実行は生成からやり直すので、構成の差が段階の差なのか生成のばらつきなのかを切り分けられず、字数の調整の前後の文面も残らなかった（0010 評価記録 §4.2）。この限界は、タスク `0017_intermediate_artifacts`（中間生成物の保存と再開。`--artifacts`・`--after`）で解消した。本タスクは 0017 の仕組みを使い、段階ごとに原因を特定してから改善する。

本書の承認の後、記事を作る主な経路はブラウザ拡張になった（タスク `0015`・`0020`・`0024`〜`0028`）。利用者が YouTube の文字起こしパネルから字幕を選んでコピーし、拡張が動画ページの DOM から動画タイトル・チャンネル名・概要欄を読み取って、localhost のサーバに送る（以下「本番の経路」）。一方、本タスクの評価は、中間生成物・テンプレートの上書き・`--review-log`・料金の概算を備えた CLI で行う（以下「評価の経路」）。2 つの経路では、生成に渡る素材が次の点で異なりうる。

-   **字幕:** 評価の経路は `yt-dlp` の json3（日本語。手動の字幕があればそれ、なければ自動の字幕）をイベント単位のセグメントにする。本番の経路は、パネルに表示された字幕を利用者が選んだ範囲で、パネルの 1 行を 1 セグメントにする（`CopiedSource`）。どちらの経路でも、生成のプロンプトにはセグメントの本文を改行で連結したものが入り、時刻は入らない。そのため、セグメントの区切りと本文の違いが、そのままプロンプトの違いになる。
-   **概要欄:** 評価の経路は info.json の全文を使う。本番の経路は、概要欄が折りたたまれていれば DOM にある冒頭だけを送り、読み取れなければ省略する（0025 の F-001）。話者の名前を確かめる素材は概要欄であることが多く（0008 の F-002）、概要欄の違いは話者に関わる原因の出方を変えうる。

本タスクは評価の経路で評価を続け、2 つの経路の素材の違いを確かめて記録する（F-010）。違いがある場合に、推薦の前に本番の経路の素材で確かめるかどうかは人が判断する。

**本書の記述範囲と、後続の文書:**
本タスクの成果物は、0008 と同じく、コードではなくテンプレートの文面と評価の記録である。テンプレートの上書き（`--system-prompt` などのフラグ）、検証・推敲のプロバイダとモデルの設定、中間生成物の保存と再開、トークン数の記録、料金の概算は、実装済みである（0017、0019、0022）。本タスクに新しく設計する構造はない。そのため、`02_architecture.md`・`03_implementation_plan.md` は作らず、本書の承認後、評価の手順と記録を `02_evaluation.md` に残す（F-005）。

本番のコード（`ArticleWriter`・CLI・設定・アダプタ）は本タスクでは変えない（§2.3）。ただし、構成の変更では直らない原因について、本番のコードの変更が必要かどうかは本タスクで確かめる。そのために、段階の間に処理を挟む、段階を置き換えるなどの使い捨ての試作のコードを書いて評価する（F-008）。試作で効果が確かめられた変更は、本番のコードとして別のタスクで実装する。

対応 issue: #248。先行: #213（0017）、#247（0019、トークン数の記録）。どちらも完了している。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   0008 の合格条件を満たす見込みのある構成を見つけ、0008 の最終の版の評価（0008 の AC-17）を再開できるようにする。
-   不合格の原因を、どの段階（生成・字数の調整・検証・推敲）が入れたか、どの段階が直さなかったかまで特定する。
-   1 つの変更が狙った原因に効いたかを、変更していない段階のばらつきを除いて確かめる。
-   構成ごとの推定コスト・呼び出し回数・所要時間を記録し、品質と並べて比べられるようにする。合格の見込みと費用のどちらを取るかを、人が判断できる材料を残す。
-   残った原因のそれぞれについて、構成の変更で直るのか、本番のコードの変更が必要なのかを、試作の結果を根拠に判断できるようにする。
-   0008 の合格条件（10 件すべての合格、字幕から確かめられない話者の割り当てを不合格とすること）に緩和の余地があるかを判断する材料を集め、緩和の案を人に示す。

### 2.2. スコープ (In Scope)

-   評価の基準となる、固定した生成の出力の集合（基準の集合）の作成（F-001）。
-   不合格の原因の段階ごとの特定（F-002）。
-   構成の変更とその評価。対象は、生成のテンプレート、生成のモデル、字数の調整のテンプレート、検証・推敲のテンプレート、検証・推敲のモデルと effort（F-003）。
-   検証・推敲のばらつきの測定（F-004）。
-   評価の手順と記録（`02_evaluation.md`）（F-005）。
-   合格の見込みの判断と、0008 への引き継ぎ（F-006）。
-   構成ごとの推定コストの算出と、品質との比較（F-007）。
-   本番のコードの変更が必要かどうかを確かめる、使い捨ての試作のコードとその評価（F-008）。生成の前に発言を整理する段階を挟む試作（試作 A）を含む。
-   0008 の合格条件の見直しの材料と、緩和の案（F-009）。
-   採用した字数の調整・検証・推敲のテンプレートの `prompts/` への反映（F-006）。
-   評価の経路と本番の経路の素材の違いの確認と記録（F-010）。

### 2.3. スコープ外 (Out of Scope)

-   0008 の最終の版の評価（0008 の AC-17）と、生成のテンプレートの `prompts/system.tmpl`・`prompts/user.tmpl` への反映（0008 の F-007）。0008 で行う。本タスクは、再開してよい構成を推薦するところまでを扱う（F-006）。
-   0008 の評価の観点・段階の基準・合格条件・対象の動画の変更そのもの。本タスクは、人が物差しを変えるまでは 0008 の F-006 の物差しをそのまま使う。合格条件については、見直しの材料と緩和の案を作る（F-009）。物差しを変えるかどうかは人が判断し、変える場合は 0008 の要件定義書の手順で行う。
-   本番のコード（`ArticleWriter`・CLI・設定・アダプタなど、`cmd/`・`internal/` の下のコード）の変更。たとえば、検証・推敲の既定のプロバイダとモデルの変更、段階の追加（生成の前に字幕を整える段階、記事の主な論点を確かめる段階など）、段階の繰り返し。必要かどうかは試作で確かめ（F-008）、必要と分かったものは別の issue にする。
-   LLM の API が報告するトークン数を、CLI が段階ごとに記録して出力する仕組みと、料金の概算の算出（F-007 の前提）。先行タスク 0019（#247）と 0022 で実装済みであり、本タスクはそれを使う（§5）。
-   評価の経路を本番の経路の素材に揃えるための本番のコードの変更（たとえば、CLI がコピーした字幕とメタデータを入力として受け取る手段、サーバが中間生成物を保存する手段）。F-010 で必要と分かった場合は、別の issue にする。
-   話者の区別が難しい動画を検出して、生成を上位のモデルに回すこと（#146）。
-   検証・推敲の無変更の項目の扱い（#186、タスク `0013_identical_review_revisions`）。
-   0017 の中間生成物の形式と、保存・再開の振る舞い。本タスクは 0017 が定めたとおりに使う。
-   評価の手順のうち、0017 の AC-34 が 0010 評価記録 §2 に加える、中間生成物を固定して段階だけを比べる方法そのもの。本タスクはそれを参照する。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 基準の集合

評価は、固定した生成の出力の集合（以下「基準の集合」）を中心に行う。基準の集合は、0008 の評価の 5 本の動画それぞれについて、同じ構成で 2 回ずつ生成した 10 件の生成の出力からなる。2 回ずつとするのは、0008 の合格条件（AC-17）が 2 回ずつの生成を求めることと、1 回だけでは生成のばらつきによる不合格と構成による不合格を区別できないためである。

-   基準の集合は、0017 の `--artifacts` で保存した中間生成物（生成の出力と、走った場合は字数の調整の出力）とする。
-   基準の集合を作る構成は、0010 評価記録 §3.7 の構成（生成が v5・deepseek-flash、検証・推敲が claude-opus-5-5・effort high、強めたテンプレート）を初期値とする。
-   基準の集合は、評価の途中で作り直さない。生成のテンプレートまたは生成のモデルを変える場合（F-003）は、新しい基準の集合を作り、どの基準の集合での結果かを記録で区別する。
-   中間生成物は、評価のために再開するたびに、別の評価の結果で上書きされないように扱う（具体的な方法は 0010 評価記録 §2 の手順による）。

**Acceptance Criteria**:
- **AC-01**: `02_evaluation.md` に、基準の集合ごとに、作った構成（生成のテンプレートの版、生成のモデル名と ModelVersion、字数の調整と検証・推敲のテンプレートとモデル）、生成の日時、10 件の生成の出力それぞれの中間生成物の識別子（0017 が記録する識別子）が記録されている。
- **AC-02**: `02_evaluation.md` の、基準の集合を使った評価の記録はどれも、使った基準の集合と、再開した段階（0017 の `--after` の値）を示している。同じ生成の出力に当てた評価どうしは、記録した中間生成物の識別子が一致している。

#### F-002: 不合格の原因の段階ごとの特定

0008 の F-006 の観点で不合格になった記事と、品質の観点が 1 の記事について、その原因になった記述を、どの段階が入れたか、どの段階が直さなかったかまで特定する。中間生成物の生成の出力・字数の調整の出力・適用後の記事を順に見比べて判断する。

-   **入れた段階:** その記述が最初に現れた段階（生成、字数の調整、検証・推敲）。主な論点の欠落の場合は、論点が最初に失われた段階。
-   **直さなかった段階:** その記述が現れた後の段階のうち、直さなかった段階。検証・推敲の一覧の項目がその文に触れながら、原因の部分を直さなかった場合は、それも記録する（0010 評価記録 §3.5・§3.6 で見られた形）。

**Acceptance Criteria**:
- **AC-03**: `02_evaluation.md` に、基準の集合を作った実行の記事（10 件）の、必須の観点の不合格と品質の観点の 1 のすべてについて、原因の記述（記事からの短い引用）、入れた段階、直さなかった段階が記録されている。
- **AC-04**: 字数の調整が走った記事のすべてについて、`02_evaluation.md` に、0008 評価記録 §3.2 の主な論点のそれぞれが、生成の出力と字数の調整の出力に含まれるかどうかが記録されている。
- **AC-05**: `02_evaluation.md` に、原因を種類（0010 の F-003 の 5 つの種類、主な論点の欠落、長さ、形式の規則）ごとに、入れた段階の別に数えた表がある。

#### F-003: 構成の変更と評価

構成の変更は、F-002 で特定した原因のどれを狙うかを先に決めてから行い、1 回に 1 つの要素だけを変える。変えられる要素は次のとおりとする。

| 要素 | 変え方 | 評価に使う入力 |
|---|---|---|
| 検証・推敲のテンプレート | `--review-system-prompt`・`--review-user-prompt` で上書きする | 基準の集合。字数の調整が走った生成の出力は `--after shorten`、走らなかった生成の出力は `--after generation` で再開する（`--after generation` は本文が上限を超えると字数の調整をやり直し、そのばらつきが比較に混ざるため） |
| 検証・推敲のモデル・effort | `YT2COLUMN_REVIEW_PROVIDER`・`YT2COLUMN_REVIEW_MODEL`・`YT2COLUMN_CLAUDE_EFFORT` | 基準の集合（同上） |
| 字数の調整のテンプレート | `--shorten-system-prompt`・`--shorten-user-prompt` で上書きする | 基準の集合のうち、字数の調整が走る生成の出力（`--after generation`） |
| 生成のテンプレート | `--system-prompt`・`--user-prompt` で上書きする。版の番号は 0008 の続き（v6 以降）とする | 新しい基準の集合（F-001） |
| 生成のモデル・effort | `YT2COLUMN_LLM_PROVIDER`・`YT2COLUMN_MODEL`・`YT2COLUMN_CLAUDE_EFFORT` | 新しい基準の集合（F-001） |

-   後の段階（字数の調整・検証・推敲）を変える評価は、基準の集合の同じ生成の出力に当て、変更の前の構成と比べる。生成を変えると、後の段階の差が生成のばらつきと混ざるからである。
-   生成を変える評価は、基準の集合を作り直すので、1 回目の 5 本だけでは判断しない（2 回ずつの 10 件で比べる）。
-   テンプレートの上書きファイルは本タスクのディレクトリに置き、版ごとに前の版からの差分と、狙った原因を記録する。
-   変更が狙った原因を直したか、ほかの記事を壊したか（新しいずれ、直す必要のない変更、構成の変更）の両方を記録する（0010 の F-008 の「直したこと」「壊したこと」と同じ面）。

**Acceptance Criteria**:
- **AC-06**: `02_evaluation.md` に、評価した構成の変更ごとに、変えた要素（1 つ）、変更の内容（テンプレートは前の版からの差分）、狙った原因（F-002 の記録への参照）、評価に使った基準の集合と再開した段階が記録されている。

#### F-007: 推定コスト

構成を比べるときは、品質（F-003 の判定）に加えて、記事 1 本を作るのにかかる LLM の料金の推定値（以下「推定コスト」）を並べて見る。

-   **単価:** `internal/pricing` の単価の表（0022）を使う。表は提供元の公開している料金表から作られ、エントリごとに出典と確認した日がコメントで記録されている（[pricing_update.md](../../dev/developer_guide/pricing_update.md)）。評価には、評価に使った CLI をビルドしたコミットの表を使い、そのコミットを記録する。評価で使うモデルが表にない場合は、評価の前に、その手順で表に加える。料金の時間帯によって単価が変わるプロバイダ（DeepSeek）では、構成の比較に通常の時間帯の単価（表の off-peak の単価。料金が 2 倍になる peak の時間帯でない単価）を使う。比較の結果が、実行した時刻に左右されないようにするためである。評価の実行は peak の時間帯を避ける（§5）ので、CLI が出す単価の区分は off-peak になる。区分が peak になった実行は、実行条件の未達として記録する（F-005）。
-   **記事 1 本の推定コスト:** 生成・字数の調整・検証・推敲のうち、記事を作るのに走ったすべての段階の推定コストの合計とする。再開した評価で呼ばなかった段階は、その中間生成物を作った実行（基準の集合の作成）で記録したトークン数を使い、合計に含める。こうすると、後の段階だけを変えた評価どうしでも、構成全体のコストを比べられる。CLI は、再開で呼ばなかった段階の分を中間生成物の来歴から読み、記事全体の合計（`cost-total: article` の行）に含めて出すので、それを記事 1 本の推定コストとする。
-   **失敗した実行:** 生成の応答の打ち切り（0010 評価記録 §3.5・§3.6）などで記事が得られなかった実行も料金がかかるので、失敗した実行の呼び出しのトークン数と推定コストを、構成ごとに別に記録する。

**Acceptance Criteria**:

#### F-008: 試作による、本番のコードの変更の要否の確認

構成の変更（F-003）では直らない原因について、本番のコードの変更で直るかどうかを、使い捨ての試作のコードで確かめる。試作では、段階の間に処理を挟む（例: 生成の前に字幕を整える、字数の調整の後に主な論点が残っているかを確かめる）、段階を置き換える、段階を繰り返す、などを行う。試作は、本番のコードを変えずに、本番のコードを変えた場合の効果を見積もるためのものであり、その結果は採用ではなく、本番のコードの変更が必要かどうかの判断の根拠である。

試作のコードは、本番のコードと次のように分ける。

-   **置き場所:** 本タスクのディレクトリの下に置く。本番のコード（`cmd/`・`internal/`・`prompts/`）には置かず、本番のコードから参照されない。
-   **ビルドと検査:** `make build`・`make test`・`make lint` の対象にならず、それらの結果を変えない。CI の結果も変えない。
-   **品質の水準:** 本番のコードの規則（ユニットテスト、AC との対応付け、レビューの観点）は求めない。既存の `internal/` のパッケージは、変えずに使ってよい。試作のために `internal/` のパッケージを変える必要がある場合、それは本番のコードの変更であり、別の issue にする。
-   **入力と出力:** 字幕のキャッシュと基準の集合の中間生成物は、読むだけで書き換えない。試作の出力は、リポジトリの外に書き出す。試作の出力を、本番の段階が作ったものとして 0017 の中間生成物の形で書き出さない（来歴が実際と食い違うため）。
-   **入力の受理と拒否:** 字幕のキャッシュと基準の集合の中間生成物は、信頼できない入力として扱う。試作はこの 2 つを、既存の読み込み（字幕のキャッシュは `internal/transcript` の `TranscriptSource`、中間生成物は `internal/artifact` の `Store.Load`）を変えずに使って読み、自前で構文を解析しない。受理する形、消費するメンバー、未知のメンバーと重複したメンバーの扱い、標準ライブラリが黙って修復・破棄・無視する入力の扱い、サイズと件数の上限、拒否時の番兵は、それぞれの境界を定めた要件のとおりとする。
    -   **字幕のキャッシュ（json3・info.json）:** 0002 の要件定義書 §3.2 のとおり。消費しないメンバーは無視して受理し、実 `yt-dlp` の出力にある未知のフィールドは拒否理由にしない。拒否は `transcript.ErrParseSubtitles`・`transcript.ErrParseInfo`・`transcript.ErrNoSubtitles` である。読むときは YouTube にアクセスしない設定（0008 評価記録 §2.3）とし、キャッシュがない場合に `yt-dlp` で取り直さない。

##### 試作 A: 発言の整理

最初の試作として、生成の前に字幕から「発言の整理表」を作る段階を挟み、生成が字幕と一緒に整理表を受け取る構成を評価する。生成のモデルが、字幕を読み取ることと記事を書くことを 1 回の呼び出しで同時に行っている点を、2 つの段階に分ける。

-   **狙う原因:** 評した人と評された人の取り違え（`18tbwwPM91A`）、確かめられない話者の割り当て（0008 評価記録 §5.9 の動画 2）、最も重要な論点の欠落と観点「重要度の順」の 1（`roNZ-rLxhUE`）。誤認識の写しと意味の取れない文は狙わない。
-   **字幕を書き直さない理由:** 話者・句読点・誤認識を直した字幕で元の字幕を置き換える方法はとらない。採点は元の字幕を根拠に行うので、書き直しで入った誤りが観点「根拠」の不合格に直結し、しかも生成からは誤りと見分けられない。また、出力が字幕とほぼ同じ長さになり、長い動画（`roNZ-rLxhUE`、32 分）で出力トークンが多くなる。
-   **整理の段階の入力:** 生成と同じ素材（動画タイトル・チャンネル名・概要欄・字幕）。ただし字幕には、試作のコードが各セグメントの開始時刻（`Segment.StartMs`）から作った時刻を付ける。生成のプロンプトの字幕は、セグメントの本文を改行で連結したもので、時刻を含まない（`internal/writer` の `newTemplateData`）。整理表が字幕の時刻で区間と論点を指すには、整理の段階の字幕に時刻が要る。生成には、本番と同じ時刻のない字幕と、整理表を渡す。
-   **整理表の内容:** 次の 4 つからなる。
    -   **話者:** 名前または役割（「聞き手」など）と、名前を確かめた素材の箇所。名前は 0008 の F-002 の規則（素材で確かめられる場合だけ使う）に従う。
    -   **発言の区間:** 字幕の時刻の範囲ごとに、話者（上の話者のいずれか、または「不明」）、判断の根拠（質問と答えの関係、呼びかけ、名乗りなど、字幕のどの時刻から判断したか）、確信度（「確か」「不明」の 2 値）。
    -   **人を評した発言:** 評した人、評された人、字幕の時刻、それぞれの判断の根拠、確信度。0008 の F-002 の「評した人と評された人の両方を字幕から確かめられる場合」を満たすときだけ「確か」とする。
    -   **主な論点:** 重要度の順の一覧と、それぞれの字幕の時刻の範囲、1 番目を最も重要とした理由。
-   **整理表に書かないもの:** 字幕の要約・言い換えは書かない。区間と論点は字幕の時刻で指し、見出しは短くとどめる。生成が整理表の言い換えを事実として写すと、字幕にない記述が記事に入るからである。
-   **整理の段階のモデル:** claude-opus-5-5、effort medium を初期値とする。effort high は、生成で起きた `max_tokens` の打ち切り（#171）が起きないことを確かめてから試す。
-   **生成:** deepseek-flash と、v5 のテンプレートに整理表の使い方の指示を加えた試作用のテンプレートを使う。試作用のテンプレートは試作のディレクトリに置き、v5 からの差分を記録する（0008 の版の番号は付けない）。加える指示は次のとおりとする。発言を話者に割り当てるのは、整理表で「確か」とした区間だけとする。「不明」の区間の発言は話者を断定しない。人を評した発言は、整理表で「確か」としたものだけを書く。節の順は、整理表の主な論点の順を原則とする。記事に書く事実の出典は字幕などの素材とし、整理表を出典にしない。
-   **字数の調整と検証・推敲:** 基準の集合を作った構成（F-001）と同じとし、整理表は渡さない。試作 A の効果を、生成の前に挟んだ段階だけの差として見るためである。
-   **整理表の扱い:** 整理表は字幕の内容を含むので、試作の出力としてリポジトリの外に書き出す。

試作 A の評価は、F-008 の評価の方法に次を加えて行う。

-   **生成の回数:** 生成より前に処理を挟む試作なので、5 本の動画で 2 回ずつ生成した 10 件を作る。整理表は生成のたびに作り直す（本番のコードにした場合と同じ）。同じ動画の 2 つの整理表の食い違いを、整理の段階のばらつきとして記録する。
-   **整理表の正しさ:** 記事を判定する前に、整理表そのものを字幕と照らす。最も害が大きいのは、「確か」とした割り当ての誤りである。生成がそれを正しいものとして書くからである。人を評した発言と、F-002 で記録した話者の原因の箇所は、人が照らす。ほかの区間は LLM が照らし、人は誤りの候補だけを確かめる。
-   **記事に残った話者の不合格の切り分け:** 話者の割り当てまたは人を評した発言による観点「根拠」の不合格のそれぞれを、「整理表が誤った」「整理表は正しいが、生成が従わなかった」「整理表が扱わなかった区間」のどれかに分ける。
-   **本番のコードの変更の要否の判断（AC-24）:** 狙った原因が 10 件のどれにも残らず、整理表の誤りによる新しい観点「根拠」の不合格がない場合に、本番のコードに整理の段階を加える根拠とする。整理表に「確か」の誤りがあった場合は、その箇所が、人でも字幕だけからは特定が難しい箇所か（F-009）を併せて記録する。

**Acceptance Criteria**（AC-22〜AC-26 に加えて）:
- **AC-27**: `02_evaluation.md` に、試作 A の整理表の内容の定義、整理の段階のモデルと effort とテンプレート、生成に使った試作用のテンプレートの v5 からの差分が記録されている。
- **AC-28**: `02_evaluation.md` に、試作 A の 10 件の整理表それぞれについて、「確か」とした話者の割り当てと人を評した発言のうち誤っていたもの、整理表の主な論点の 1 番目が 0008 評価記録 §3.2 の最も重要な論点と一致するか、F-002 で記録した話者の原因の箇所を整理表がどう扱ったか（「確か」で正しい、「確か」で誤り、「不明」）、同じ動画の 2 つの整理表の食い違いが記録されている。
- **AC-29**: `02_evaluation.md` に、試作 A の記事に残った、話者の割り当てまたは人を評した発言による観点「根拠」の不合格のそれぞれについて、記事からの短い引用と、「整理表が誤った」「整理表は正しいが、生成が従わなかった」「整理表が扱わなかった区間」のどれに当たるかが記録されている。

#### F-009: 合格条件の見直しの材料

0008 の合格条件は、5 本の動画で 2 回ずつ生成した 10 件すべてが合格することを求め、字幕から確かめられない話者の割り当てを観点「根拠」の不合格とする。しかし、字幕には映像も音声も話者の区別もなく、人が字幕だけを読んでも話者を確実に特定できるとは限らない。また、記事 1 本に 1〜2 か所のずれが確率的に残る状況で 10 件すべての合格を求めると、記事 1 本の品質がかなり高くても合格しにくい（§1）。本タスクでは、この物差しに緩和の余地があるとみて、緩和するかどうかを人が判断するための材料と案を作る。物差しを変えるかどうかは人が判断し、変える場合は 0008 の要件定義書の手順で変える（§2.3）。

-   **字幕だけからの話者の特定の難しさ:** F-002 で記録した原因のうち、話者の割り当てと人を評した発言に関わるもののそれぞれについて、人が字幕だけ（映像と音声なし）を読んで話者を特定できるか（「できる」「迷う」「できない」）と、その根拠を記録する。そのうえで、人が動画（映像と音声）で話者を確かめ、字幕だけからの人の判断と、採点の判定（LLM と人）が、動画で確かめた話者と一致したかを記録する。字幕だけからは人も特定できない箇所で記事が取れる正しい振る舞いは、書かないことだけである。そうした箇所が主な論点に関わると、観点「要点の網羅」との両立が難しくなる。逆に、採点の判定が動画と食い違う箇所は、物差しの側の誤りである。
-   **合格の確率の見積もり:** 評価した構成ごとに、記事 1 本あたりの合格の割合と、10 件が互いに独立だとした場合に 10 件すべてが合格する確率を記録する。5〜10 件からの見積もりで幅が大きいことも併せて記録する。
-   **緩和の案:** 上の材料に基づいて、緩和の案（緩和しないという判断を含む）を示す。案の例として、字幕だけからは人も話者を特定できない箇所の扱いを変える（動画で確かめた話者と一致すれば合格とする、必須の観点から品質の観点に移す、など）、10 件すべての合格を別の条件に変える、がある。案ごとに、評価した構成を案の物差しで判定し直した合格の件数と、案を採ると合格になる記事の誤りが読者に何を誤って伝えるかを示す。評した人と評された人の取り違えは、断定を避けた書き方でも意味が逆になる（0008 の F-002）ので、緩和の対象にするかは、この点を示して人が判断する。
-   **物差しの版:** 人が案を採って 0008 の物差しを変えた場合、それ以降の判定は変えた後の物差しで行い、判定ごとにどの版の物差しによるかを記録する。それ以前の評価は、生成をやり直さずに、記録した記事を変えた後の物差しで判定し直して併記する。

**Acceptance Criteria**:
- **AC-30**: `02_evaluation.md` に、F-002 で記録した原因のうち話者の割り当てと人を評した発言に関わるもののすべてについて、字幕だけから人が話者を特定できるか（「できる」「迷う」「できない」）とその根拠、動画で確かめた話者、字幕だけからの人の判断と採点の判定が動画で確かめた話者と一致したかが記録されている。
- **AC-31**: `02_evaluation.md` に、評価した構成ごとに、記事 1 本あたりの合格の割合と、10 件すべてが合格する確率の見積もりが記録されている（AC-19 の比較の表に加えてよい）。
- **AC-32**: `02_evaluation.md` の結論に、緩和の案（緩和しないという判断を含む）と根拠、案ごとに判定し直した合格の件数、案を採ると合格になる記事の誤りの内容、人の判断が記録されている。人が案を採った場合は、0008 の要件定義書の変更（コミットまたは PR）への参照が記録されている。

#### F-010: 評価の経路と本番の経路の素材の違い

本タスクの評価は評価の経路（CLI と `yt-dlp`）で行うが、利用者が読む記事は本番の経路（ブラウザ拡張とサーバ）で作られる（§1）。評価の経路での合格の見込みが本番の経路の記事にも当てはまるかを判断するため、0008 の 5 本の動画のそれぞれについて、2 つの経路で生成に渡る素材を比べ、違いを記録する。

-   **本番の経路の素材:** 人が、本番の経路と同じ操作で用意する。動画ページの文字起こしパネルを開き、字幕の全体を選んでコピーした文字列（§5 の前提）と、概要欄を「…もっと見る」で開いた状態の動画タイトル・チャンネル名・概要欄である。あわせて、概要欄を開かない状態で拡張が送る概要欄（冒頭）も用意する。コピーした字幕のパネルの言語の設定も記録する。
-   **比べるもの:** 生成のプロンプトに入る 4 つの値。字幕は、セグメントの本文を改行で連結したもの（`internal/writer` がプロンプトに入れる形）、ほかは動画タイトル・チャンネル名・概要欄である。値が一致しない場合は、違いの種類（セグメントの区切りだけの違い、本文の文字の違い、本番の経路だけにある行・ない行、概要欄の欠けた範囲など）と、その量（違う行の数、文字数）を記録する。
-   **比べ方:** 比べるスクリプトは、F-008 の試作のコードと同じ規則（置き場所、ビルドと検査、品質の水準、入力と出力、入力の受理と拒否、秘密情報）に従う。評価の経路の素材は字幕のキャッシュを `internal/transcript` の `TranscriptSource`（`YtDlpSource`）で、本番の経路の素材は `internal/transcript` の `NewCopiedSource` で読み、自前で構文を解析しない。`NewCopiedSource` が拒否した字幕（拒否の番兵は `transcript.ErrCopiedTranscriptFormat`）は補正せず、拒否として記録する。
-   **概要欄の折りたたみの影響:** F-002 で記録した原因と、評価した記事で話者の名前を確かめた素材の箇所が概要欄にある場合、その箇所が、概要欄を開かない状態で拡張が送る冒頭に含まれるかを記録する。含まれない場合、本番の経路で概要欄を開かずに送ると、その名前を素材で確かめられない。
-   **違いがあった場合の扱い:** 違いが生成のプロンプトに入る（4 つの値のどれかが一致しない）場合、推薦（F-006 の (a)）の前に、本番の経路の素材で推薦する構成を確かめるかどうかと、その方法を人が判断する。確かめる方法が本番のコードの変更を要する場合は、別の issue にする（§2.3）。

**Acceptance Criteria**:
- **AC-34**: `02_evaluation.md` に、5 本の動画のそれぞれについて、本番の経路の素材を用意した日とパネルの言語の設定、生成のプロンプトに入る 4 つの値（字幕、動画タイトル、チャンネル名、概要欄）のそれぞれが評価の経路の素材と一致したか、一致しない場合の違いの種類と量、比べたスクリプトの場所とコミット、読み込みが拒否した場合はその番兵が記録されている。記録とリポジトリに置いたファイルに、字幕と概要欄の全文が含まれない。
- **AC-35**: `02_evaluation.md` に、話者の名前を確かめた素材の箇所が概要欄にある記事のそれぞれについて、その箇所が概要欄を開かない状態の冒頭に含まれるかが記録されている。違いが生成のプロンプトに入る動画がある場合は、本番の経路の素材で確かめるかどうかの人の判断と、確かめた場合はその結果または作った issue の番号が記録されている。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   推薦する構成の所要時間・呼び出し回数（AC-09）と推定コスト（AC-18・AC-19）を記録する。本番の CLI の構成では、0010 の要件定義書 §4.1 と同じく、1 本の記事の LLM の呼び出しは、生成 1 回・字数の調整 0〜1 回・検証・推敲 1 回が上限である。試作（F-008）はこの上限に縛られないが、その呼び出しの回数とトークン数を記録し、本番のコードにした場合の費用を推定コストで示す。

### 4.2. セキュリティ (Security)

-   生成した記事の全文、中間生成物、字幕は、リポジトリにコミットしない（0008 の要件定義書 §4.2）。中間生成物は記事の本文と字幕の引用を含むので、`--artifacts` のディレクトリはリポジトリの外に置く。評価の記録には、判定の理由に必要な短い引用だけを書く。
-   F-010 で人が用意する本番の経路の素材（コピーした字幕と概要欄）は、字幕と概要欄の全文を含むので、リポジトリの外に置く（AC-34）。
-   評価のための記事は `--out` でリポジトリの外のファイルに書き出し、Webhook には投稿しない。
-   テンプレートに秘密情報を書かない（[prompts/README.md](../../../prompts/README.md)）。
-   試作のコードは、API キーを環境変数から読み、コードと出力に書かない。試作の出力はリポジトリの外に書き出す（F-008・AC-26）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   LLM の出力は、生成でも検証・推敲でも実行ごとに変わる。生成のばらつきは基準の集合を 2 回ずつの生成にすること（F-001）で、検証・推敲のばらつきは同じ入力に 2 回当てること（F-004）で扱う。

### 4.4. 互換性 (Compatibility)

-   `prompts/` のテンプレートを変える場合（AC-15）は、テンプレートの検証規則（[prompts/README.md](../../../prompts/README.md)）を満たし、既存のテストが通る。

### 4.5. 保守性 (Maintainability)

-   テンプレートを変える場合は、どの指示がどの原因（F-002）に対応するかを、変更の理由として記録する（AC-06）。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。
-   中間生成物を使う評価は、タスク `0017_intermediate_artifacts` の実装（`--artifacts`・`--after`）と、0010 評価記録 §2 への手順の追加（0017 の AC-34）が終わってから始める。どちらも完了している（0010 評価記録 §2.6）。
-   推定コスト（F-007）には、LLM の API が報告するトークン数を、CLI が段階ごとに記録して出力する仕組みが必要である。この仕組みは先行タスク 0019（#247）で実装され、トークン数は標準エラーの要約と中間生成物の来歴に記録される。料金の概算は 0022 で実装され、CLI が段階ごとと記事全体の推定コストを出す。基準の集合を作る実行のトークン数は後から取り直せないので、基準の集合は、評価に使う CLI がトークン数を記録することを確かめてから作る。
-   **評価の素材の前提:** 本番の経路では、利用者が文字起こしパネルの字幕を選ぶ。本タスクの評価は、パネルの字幕の全体を選んでコピーしたもの（評価の経路では `yt-dlp` で取得した字幕の全体）を素材とする。利用者が字幕の一部だけを選んで送った場合の記事は、観点「要点の網羅」が前提とする素材と異なるので、本タスクの評価の対象にしない。
-   評価の対象の動画、主な論点、観点、段階の基準、合格条件は、0008 の要件定義書と 0008 評価記録 §3.2・§4 のものを使う。
-   評価で LLM の API を呼ぶ実行は、実行のたびに人の承認を得る（CLAUDE.md「Tool Execution Safety」）。DeepSeek の料金が 2 倍になる時間帯（日本時間の平日 10〜13 時と 15〜19 時）を避ける（0008 評価記録 §2.3）。
-   字幕の取得と、YouTube にアクセスしない設定での実行は、0008 評価記録 §2.2・§2.3 に従う。再開を使う評価では、0017 の AC-17 のとおり、すべての実行に `--keep-cache` を付ける。
-   `deepseek-flash` は提供元が指すモデルを切り替えるエイリアスである。基準の集合の間で比べるときは、ModelVersion の違いに注意する（0008 の要件定義書 §5）。
-   字幕には話者の区別がない（0008 の要件定義書 §5）。評した人と評された人の取り違えは、テンプレートやモデルの変更で直らない可能性があり、人でも字幕だけからは話者を特定できない可能性がある。直らない場合は F-006 の (b) として記録し、F-009 の材料にする。

## 6. 用語集 (Glossary)

-   **構成:** 記事を作る設定の組。生成のテンプレートとモデル、字数の調整のテンプレート、検証・推敲のテンプレートとモデル・effort からなる（F-003）。
-   **基準の集合:** 評価のために固定した、5 本の動画で 2 回ずつ生成した 10 件の生成の出力（と、走った場合は字数の調整の出力）の中間生成物（F-001）。
-   **中間生成物・再開:** タスク 0017 の用語と同じ。
-   **推定コスト:** 記事 1 本を作るのに走った段階の、API が報告するトークン数と公開の単価から求めた LLM の料金の推定値（F-007）。
-   **本番のコード:** `cmd/`・`internal/`・`prompts/` の下にあり、`make build`・`make test`・`make lint` の対象になるコード（§2.3）。
-   **試作のコード:** 本番のコードの変更が必要かどうかを確かめるために書く、使い捨てのコード。本タスクのディレクトリの下に置き、本番のコードの規則を求めない（F-008）。
-   **発言の整理表:** 試作 A で、生成の前に字幕から作る表。話者、発言の区間ごとの話者と確信度、人を評した発言、主な論点の順からなる（F-008）。
-   **物差しの版:** 判定に使った 0008 の評価の観点と合格条件の版。F-009 で人が物差しを変えると版が変わる。
-   **本番の経路:** 利用者が文字起こしパネルからコピーした字幕と、ブラウザ拡張が DOM から読み取ったメタデータを、localhost のサーバが受け取って記事を作る経路（§1、F-010）。
-   **評価の経路:** CLI が `yt-dlp` で取得した字幕と info.json から記事を作る経路。中間生成物・テンプレートの上書き・料金の概算を使えるので、本タスクの評価はこの経路で行う（§1、F-010）。
-   **入れた段階・直さなかった段階:** 不合格の原因の記述が最初に現れた段階と、その後に直さなかった段階（F-002）。
