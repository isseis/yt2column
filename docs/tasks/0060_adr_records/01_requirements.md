## 1. 概要 (Overview)

**目的:** 本書は、主要な設計の決定を ADR（Architecture Decision Record）として `docs/dev` の下に記録するための要件を定義する。ADR の置き場所と書式、どの決定を主要とするかの基準、タスク文書・プロジェクト概要・仕様の正本の文書・CLAUDE.md との分担、コマンドの手順への組み込み、既存の決定のうち本タスクで ADR にする範囲を定める。

**背景:**

今は、設計の決定とその理由（採らなかった案を含む）が、各タスクの文書に分かれて残っている。要件定義書には「…で決めたこと」の節があり、設計書には「設計の際に決めたこと」の節と、付録の「決定の履歴」がある。この付録は `/mkarch` の指示で書かれる（`.claude/commands/mkarch.md:74`）。たとえば `docs/tasks/0012_doc_sync_guards/02_architecture.md` と `docs/tasks/0014_doc_guard_ci/02_architecture.md` は、§11「決定の履歴」に採らなかった案を書いている。今の方針の要約は `docs/dev/project_overview.md` の「決定済みの方針」（同書 7〜16 行）にあり、規則は CLAUDE.md にある。

この形では、ある決定の理由を知るには、関係するタスクの文書をすべて探して読む必要がある。後のタスクで決定が変わった場合も、今どの決定が効いているかが一か所では分からない。issue #602 のコメント（2026-11-04）に記録した調査では、タスク 0001〜0059 から ADR の候補を 35 件にまとめた。そのうち 10 件を超える候補では、決定が 3〜5 のタスクにまたがって変わっていた。たとえば LLM の設定の契約は、0009 → 0041 → 0042 → 0045 → 0051 と変わった。

対応 issue: [#602](https://github.com/isseis/yt2column/issues/602)

関連: タスク 0050 の設計書の付録 B「決定の履歴」（`docs/tasks/0050_viewer_tab/02_architecture.md:1975-2005`）は、その内容を本 issue で ADR に移すと書いている（同書 1977 行）。

**本書の記述範囲:** 本書は、ADR とその索引・規約に何が書かれているか、CLAUDE.md・`requirements_process.md`・コマンドの定義に何が書かれているか、本タスクでどの決定を ADR にするかを定める。ADR の雛形の構成、見出しの正確な文言、番号の振り方の細部、規約の文書のファイル名、コマンドの定義のどの手順をどう書き換えるか、確かめる方法、PR の分け方は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #602 で決めたこと:**

-   **ADR は `docs/dev` の下に置く:** 置き場所と書式は本タスクで決める。
-   **ADR は日本語で書く:** 人が決め、承認する文書なので、CLAUDE.md「Document language」の原則 (a) に当たる。
-   **主要な決定は ADR として記録することを CLAUDE.md に書く:** どの決定を主要とするかの基準と、タスク文書との分担もあわせて書く。
-   **コマンドの定義と `requirements_process.md` に手順が要るかを検討する:** 検討の結果は「要件定義の際に決めたこと」に記録した。
-   **既存の決定を ADR にする:** 候補として、0027 の起動経路、0026 の Native Messaging の構成、0050 のビューアの開き方とポップアップを閉じない決定が挙がっている。
-   **0050 の付録 B の内容を ADR にする:** issue は付録 B から ADR へ「移す」としていた。移し方は「要件定義の際に決めたこと」で改めた。

**要件定義の際に決めたこと（2026-11-04）:**

-   **ADR は主題ごとに 1 本の生きた文書にする:** 本文には今効いている決定と、採らなかった案を書く。決定が変わったら本文を今の決定に書き換え、末尾の「経緯」に 1 項目足す。一般的な ADR の形（Nygard 式）、つまり承認後は書き換えず、新しい ADR で置き換える形は採らない。その形では、LLM の設定の契約のような連鎖が 5 本の ADR になり、今の決定を知るのに鎖をたどる必要がある。変わらない記録の役割は、すでにタスク文書が担っている。1 つの主題を 2 本以上の有効な ADR に分けることはしない。主題そのものが終わって別の主題に代わるときだけ、元の ADR を廃止し、代わりの主題の ADR へリンクする。
-   **置き場所は `docs/dev/adr/`、名前は `NNNN-<kebab>.md`:** 番号はタスクの番号とは別の連番とする。すべての ADR とその状態を挙げる索引を、同じディレクトリの `README.md` に日本語で置く。今どの決定が効いているかを一か所で示すためである。
-   **ADR の書式の規約は `docs/dev/conventions/` に英語で書く:** エージェントが ADR を書くときに従う規約なので、CLAUDE.md「Document language」の原則 (b) に当たる。ADR 本体と索引は、人が決め、承認する文書なので日本語とする（原則 (a)）。
-   **ADR の状態は「有効」と「廃止」の 2 つだけにし、承認は PR で行う:** ADR は、その決定を下した PR に入るので、その PR のレビューとマージが ADR の承認を兼ねる。タスク文書の状態表（`draft` → `approved`）と `/runpr` での承認の記録は ADR に持ち込まない。持ち込むと、`/runpr` の承認の記録を ADR に広げる必要があり、変更が大きくなるためである。
-   **「有効」は、承認された決定であることを意味する:** 実装を終えたかどうかは問わない。要件定義で下した決定は、その要件定義書の PR のマージで「有効」になる。決定を下したタスクを取り下げたときは、取り下げの PR で ADR を前の決定に戻し、経緯に 1 項目足す。そのタスクで新しく作った ADR なら「廃止」にする。実装の完了を記録する 3 つ目の状態は、完了を記録する手順が別に要るので設けない。
-   **「主要な決定」の基準は、影響がそのタスクの外に及ぶこととする:** 後のタスクや複数の部品を縛る決定、または覆すと複数の箇所が変わる決定を主要とする。例は、構成と部品の境界、プロトコル、外部の依存やサービス、セキュリティの前提、製品の範囲、開発のプロセスとツールの方針である。既存の ADR の決定を変える決定は、常に主要とする。1 つのタスクの中で閉じる決定（テストの名前、文言、1 つの関数の形、定数の値、実装の順序など）は、従来どおりタスク文書だけに残す。
-   **主要かどうかはエージェントが判断し、人に示す:** 決定を人に尋ねるとき、エージェントは、その決定で ADR を作るか更新するか（どの ADR か）の判断を添える。人は決定と一緒にその判断も直せる。判断のためだけの問いを毎回足さないためである。
-   **主要な決定を下すか変える PR は、同じ PR で ADR を作るか更新する:** この規則を CLAUDE.md に置き、すべての PR に効かせる。決定を人に確かめる手順（`settle-decisions.md`）を通らない決定も対象にするためである。たとえば、エージェントが設計書の中で下した決定、`/fixpr` で PR のレビューの後に改めた決定、タスクに属さない単独の PR で決めたプロセスの方針がある。
-   **コマンドへの組み込みは、決定を人に確かめる共通の手順に段を足す形にする:** `/mkreq`・`/mkarch`・`/mkplan`・`/runplan` は、未決の決定を人に確かめる手順を `.claude/commands/_lib/settle-decisions.md` で共有している（同書 7〜13 行）。そこに、決定を尋ねる前に索引を読んで関係する ADR を探すことと、主要な決定なら同じ PR で ADR を作るか更新することを足し、4 つのコマンドに効かせる。各コマンドに同じ手順を書き写さないためである。
-   **仕様の正本は既存の文書に残し、ADR は理由と経緯を持つ:** 今の仕様は、すでに `docs/dev/security.md`（脅威モデル。同書 §8）、`docs/dev/production_profile.md`（本番の構成）、CLAUDE.md や `.claude/commands/_context.md`（開発のプロセス）などに書かれている。ADR の「決定」の節は、正本の文書がある主題では、決定を要約して正本へリンクする。理由・採らなかった案・経緯が ADR の役割である。正本を 2 つにしないためである。
-   **`project_overview.md` の「決定済みの方針」は要約を残し、ADR へリンクする:** 理由と採らなかった案は ADR に置く。`project_overview.md` は、CLAUDE.md の Quick Links で「設計する前に読む」文書とされており、その役割を保つためである。
-   **タスク文書にも書き、ADR へリンクする:** 主要な決定も、従来どおりタスク文書の「…で決めたこと」の節に理由とともに書き、そこから ADR へリンクする。タスク文書は、そのタスクで何をなぜ決めたかの、後から変わらない記録として残す。
-   **設計書の付録「決定の履歴」の役割を狭める:** `/mkarch` の付録の指示（`.claude/commands/mkarch.md:74`）を改め、主要な決定のタスクをまたぐ経緯は ADR に置き、付録にはそのタスクの中で閉じる決定の経緯だけを置く。両者に同じ経緯を書かないためである。
-   **`requirements_process.md` の記録の置き場所の説明に ADR を足す:** 同書は、タスク文書の記録をどこに置くかを 5 つの置き場所で説明している（同書 96〜108 行）。ADR もその 1 つとして挙げ、エージェントが置き場所を選ぶときに ADR を見落とさないようにする。
-   **CLAUDE.md の Quick Links に、ADR の索引と規約を足す:** 設計の前に今の決定と理由を探す入口を、エージェントが毎回読む CLAUDE.md に置くためである。
-   **本タスクで ADR にするのは、調査で「優先」とした 15 件にする:** 置き換えの連鎖があるもの、または採らなかった案が今の文書（CLAUDE.md・`security.md` など）に残っていないものである（F-006 の表）。調査の番号 B6（§6 で定義。記事のジョブの API。0044 → 0058 → 0059）は、0058 と 0059 がまだ実装中なので、本タスクでは書かない。残りの候補は別の issue に回す（F-007）。
-   **B2・B8・B11 は今効いている状態で書き、0058・0059 の分は後で足す:** B2（0058 で脅威 T-10 を再評価）、B8（0058 が方針を保つ）、B11（0059 で失敗の通知を削除）の出典には、実装中の 0058・0059 が入っている。これらの ADR は、本タスクで ADR を書く時点のコードと文書の状態で書き、0058・0059 の決定は経緯に入れない。0058・0059 の完了の後に足すことを、F-007 の issue に書く。B6 と同じく後に回すと、本タスクで作る ADR から脅威モデルなどの重要なものが欠けるためである。
-   **0050 の付録 B は変えずに残し、ADR に内容を写す:** issue は付録 B から ADR へ「移す」としていた。しかし、承認済みの文書から本文を取り除くことは、`requirements_process.md`「Editing an approved document」の編集上の訂正（古くなった名前・参照・表のセルの修正）に当たるとは言いにくく、タスク文書を変わらない記録とするという決定とも合わない。そこで 0050 の文書は変えず、ADR に付録 B の内容を写して、ADR から付録 B へリンクする。付録 B の 1977 行の「ADR に移す」という予告は、文の内容が少し古くなるが、そのまま残す。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

以下は、レビュアーと個別には確認していない。上の決定と現行の規則から導いたもので、PR のレビューで異論があれば改める。

-   **CLAUDE.md の横断の原則は ADR にしない:** 「Declare, don't infer」などの原則とその例外は、CLAUDE.md が規則として管理している。ADR にすると管理が二重になる。
-   **0050 以外の既存のタスク文書も変えない:** ADR から既存のタスク文書へリンクするだけで、既存のタスク文書から ADR へのリンクは足さない。タスク文書を変わらない記録とするという決定に従う。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   主要な決定ごとに、今効いている決定、その理由、採らなかった案、変わってきた経緯を、1 つの文書で読めるようにする。
-   今どの決定が効いているかを、一か所（索引）で分かるようにする。
-   これからの PR で、主要な決定を下したときに ADR が作られ、更新されるようにする。

### 2.2. スコープ (In Scope)

-   `docs/dev/adr/` の ADR と索引（`README.md`）。
-   `docs/dev/conventions/` の、ADR の書式の規約（英語）。
-   CLAUDE.md：ADR の規則、主要な決定の基準、ほかの文書との分担、Quick Links への追加。
-   `docs/dev/conventions/requirements_process.md`：記録の置き場所の説明（同書 96〜108 行）への ADR の追加。
-   `.claude/commands/_lib/settle-decisions.md`：索引を読む段と、ADR を作るか更新する段の追加。
-   `.claude/commands/mkarch.md:74`：設計書の付録「決定の履歴」の役割の調整。
-   ADR を作るか更新するコマンドが、その変更を自分の PR に含めるために必要な、コマンドの定義の変更（どこを変えるかは設計で決める。H-01）。
-   `docs/dev/project_overview.md` の「決定済みの方針」から ADR へのリンク。
-   F-006 の 15 件の主題を含む ADR。
-   残りの候補を記録する GitHub の issue。

### 2.3. スコープ外 (Out of Scope)

-   **決定そのものの変更:** 本タスクは、既存の決定を記録するだけで、変えない。
-   **既存のタスク文書の書き換え:** 0050 の付録 B を含め、変えない（「要件定義の際に決めたこと」）。
-   **F-006 に入らない候補の ADR:** 調査の 35 件のうち残りの 20 件（B6 を含む）は、F-007 の issue で扱う。B2・B8・B11 の経緯への 0058・0059 の追加も、同じ issue で扱う。
-   **仕様の正本の文書の書き換え:** `security.md`・`production_profile.md`・CLAUDE.md の規則などの、仕様の記述は変えない。ADR からそれらへリンクする。
-   **ADR の英訳:** 翻訳の対象は README の 1 組だけである（CLAUDE.md「Translation Guidelines」）。
-   **ADR の文の意味を確かめるテスト:** CLAUDE.md「Document tests check values, structure, and executable examples, never prose」に従う。値と構造の確認を足すかどうかは設計で決める（H-02）。
-   **ADR 用の外部ツール（adr-tools など）の導入:** 依存を最小にする方針（CLAUDE.md「Dependencies」）と YAGNI に従う。
-   **`/runpr` の承認の記録の ADR への拡張:** ADR は状態表を持たない（「要件定義の際に決めたこと」）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: ADR の置き場所、名前、索引

ADR を決まった場所に決まった名前で置き、今効いているかどうかを索引で一覧できるようにする。

**Acceptance Criteria**:
- **AC-01**: ADR は `docs/dev/adr/` の直下に、`NNNN-<kebab>.md` の名前で置かれている。`NNNN` は 4 桁の数字で、`0001` から始まる、タスクの番号とは別の連番である。`<kebab>` は、主題を表す英小文字・数字・`-` の名前である。
- **AC-02**: 同じ番号を持つ ADR は 2 つ以上ない。廃止した ADR の番号は、別の ADR に使わない。
- **AC-03**: `docs/dev/adr/README.md`（索引）が、`docs/dev/adr/` にあるすべての ADR を、番号・題名・状態とともに挙げている。索引に挙がっている ADR は、すべてファイルとして存在する。索引に挙がった状態は、その ADR の状態と一致する。
- **AC-04**: ADR と索引の本文は日本語で書かれている（コード・パス・識別子を除く）。

#### F-002: ADR の書式

ADR を読めば、今の決定、その理由、採らなかった案、変わってきた経緯が分かるようにする。

**Acceptance Criteria**:
- **AC-05**: 各 ADR は、状態・背景・決定・採らなかった案・結果・経緯の 6 つの節を持つ。
- **AC-06**: 状態は「有効」か「廃止」のどちらかである。「有効」は、承認された決定であることを表し、実装を終えたかどうかを表さない。
- **AC-07**: 「決定」の節は、今効いている決定だけを述べる。過去の決定は「経緯」に書く。その主題の仕様の正本の文書があるときは、決定を要約し、正本へリンクする。
- **AC-08**: 「採らなかった案」の節は、案ごとに、採らなかった理由を書く。出典の文書に理由がない案は、理由が記録されていないことを明記する。
- **AC-09**: 「経緯」の節は、決定を下したとき、または変えたときの 1 回につき 1 項目を、古い順に並べる。各項目は、日付、その時点の決定または変更の要旨、決定を記録した文書へのリンクを持つ。
- **AC-10**: 廃止した ADR は、削除せずに残す。状態を「廃止」とし、廃止の日付と理由、代わりの主題の ADR があればそのリンクを書き、「経緯」に 1 項目を足す。同じ主題の決定が変わるときは、廃止して新しい ADR を作るのではなく、AC-07・AC-09 のとおり同じ ADR を更新する。
- **AC-11**: ADR が今のコードの振る舞いや文書の仕様について述べるときは、その仕様の正本の文書か、それを記録したタスク文書へのリンクを示す。行番号は求めない（生きた文書なので、行番号はすぐ古くなる）。

#### F-003: ADR の規約

エージェントが ADR を作り、更新し、廃止するときに従う規約を、1 つの文書にまとめる。

**Acceptance Criteria**:
- **AC-12**: `docs/dev/conventions/` に、ADR の規約が英語で書かれた文書がある。
- **AC-13**: 規約は次のことを定めている。
  - 置き場所と名前と番号（F-001）、節と状態とその意味（F-002）、索引の内容。
  - 主要な決定の基準（AC-15 と同じ基準）。
  - 決定が変わったときの更新の仕方：本文を今の決定に書き換え、「経緯」に 1 項目を足す。
  - 廃止の仕方（AC-10）。
  - 決定を下したタスクを取り下げたときの扱い：取り下げの PR で、ADR を前の決定に戻して経緯に 1 項目足すか、そのタスクで新しく作った ADR なら廃止する。
  - 承認は、ADR を含む PR のレビューとマージで行うこと。
  - ADR を作るか更新する PR は、その決定を下すか変える PR であること。
  - 仕様の正本の文書との分担（AC-07）。

#### F-004: CLAUDE.md と記録の置き場所の規則

主要な決定を ADR として記録すること、その基準、ほかの文書との分担を、エージェントが毎回読む CLAUDE.md に書く。

**Acceptance Criteria**:
- **AC-14**: CLAUDE.md が、主要な決定を下すか変える PR は、同じ PR で ADR を作るか更新する、と述べている。この規則は、コマンドを通らない PR を含むすべての PR に効く。CLAUDE.md は ADR の規約（F-003）を参照している。

## 6. 用語集 (Glossary)

-   **ADR（Architecture Decision Record）:** 主要な決定を主題ごとに記録する文書。本タスクでは、今効いている決定を本文に書き、決定の変化を「経緯」に重ねる、生きた文書とする。
-   **主題:** 1 本の ADR が扱う決定のまとまり。1 本の ADR は 1 つ以上の主題を持ち、1 つの主題は有効な ADR のうち 1 本だけに属する。廃止した ADR の主題は数えない。
-   **主要な決定:** 影響がそのタスクの外に及ぶ決定（AC-15）。
-   **索引:** `docs/dev/adr/README.md`。すべての ADR を、番号・題名・状態とともに挙げる。
-   **有効・廃止:** ADR の状態。「有効」は承認された決定であること、「廃止」はその決定がもう効いていないことを表す。タスク文書の状態の `withdrawn`（取り下げ）とは別のものである。
-   **経緯:** ADR の節。決定を下したとき、または変えたときの記録を古い順に並べる。
-   **仕様の正本の文書:** ある主題の今の仕様を定める文書（`security.md`・`production_profile.md`・CLAUDE.md の規則など）。ADR はそれを要約してリンクする。
-   **調査の番号:** issue #602 のコメント（2026-11-04）で、ADR の候補に付けた番号（A1〜D8）。
