## 1. 概要 (Overview)

**目的:** 本書は、主要な設計の決定を ADR（Architecture Decision Record）として `docs/dev` の下に記録するための要件を定義する。ADR の置き場所と書式、どの決定を主要とするかの基準、タスク文書・プロジェクト概要・CLAUDE.md との分担、コマンドの手順への組み込み、既存の決定のうち本タスクで ADR にする範囲を定める。

**背景:**

今は、設計の決定とその理由（採らなかった案を含む）が、各タスクの文書に分かれて残っている。要件定義書には「…で決めたこと」の節があり、設計書には「設計の際に決めたこと」の節と、付録の「決定の履歴」がある。付録は `/mkarch` の指示による（`.claude/commands/mkarch.md:74`）。たとえば `docs/tasks/0012_doc_sync_guards/02_architecture.md` と `docs/tasks/0014_doc_guard_ci/02_architecture.md` は、§11「決定の履歴」に採らなかった案を書いている。今の方針の要約は `docs/dev/project_overview.md` の「決定済みの方針」（同書 7〜16 行）にあり、規則は CLAUDE.md にある。

この形では、ある決定の理由を知るには、関係するタスクの文書をすべて探して読む必要がある。後のタスクで決定が変わった場合も、今どの決定が効いているかが一か所では分からない。issue #602 のコメント（2026-11-04）に記録した調査では、タスク 0001〜0059 から ADR の候補を 35 件にまとめた。そのうち 10 件を超える候補で、1 つの決定が 3〜5 のタスクにまたがって変わっていた。たとえば LLM の設定の契約は、0009 → 0041 → 0042 → 0045 → 0051 と変わった。

対応 issue: [#602](https://github.com/isseis/yt2column/issues/602)

関連: タスク 0050 の設計書の付録 B「決定の履歴」（`docs/tasks/0050_viewer_tab/02_architecture.md:1975-2005`）は、その内容を本 issue で ADR に移すと書いている（同書 1977 行）。

**本書の記述範囲:** 本書は、ADR とその索引・規約に何が書かれているか、CLAUDE.md・`requirements_process.md`・コマンドの定義に何が書かれているか、本タスクでどの決定を ADR にするかを定める。ADR の雛形の形、見出しの正確な文言、番号の振り方の細部、規約の文書のファイル名、コマンドの定義のどの手順をどう書き換えるか、確かめる方法、PR の分け方は、設計（`02_architecture.md`）で決める。要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #602 で決めたこと:**

-   **ADR は `docs/dev` の下に置く:** 置き場所と書式は本タスクで決める。
-   **ADR は日本語で書く:** 人が決め、承認する文書なので、CLAUDE.md「Document language」の原則 (a) に当たる。
-   **主要な決定は ADR として記録することを CLAUDE.md に書く:** どの決定を主要とするかの基準と、タスク文書との分担もあわせて書く。
-   **コマンドの定義と `requirements_process.md` に手順が要るかを検討する:** 検討の結果は「要件定義の際に決めたこと」に記録した。
-   **既存の決定を ADR にする:** 候補として、0027 の起動経路、0026 の Native Messaging の構成、0050 のビューアの開き方とポップアップを閉じない決定が挙がっている。
-   **0050 の付録 B の内容は ADR に移す:** 0050 の中の記録は、本 issue を待たずに付録 B に書いた（PR #600 の範囲）。本 issue で ADR を作るときに、そこから移す。

**要件定義の際に決めたこと（2026-11-04）:**

-   **ADR は主題ごとに 1 本の生きた文書にする:** 本文には今効いている決定と、採らなかった案を書く。決定が変わったら本文を今の決定に書き換え、末尾の「経緯」に 1 行足す。承認後は書き換えず、新しい ADR で置き換える一般的な形（Nygard 式）は採らない。その形では、LLM の設定の契約のような連鎖が 5 本の ADR になり、今の決定を知るのに鎖をたどる必要がある。変わらない記録の役は、すでにタスク文書が担っている。
-   **置き場所は `docs/dev/adr/`、名前は `NNNN-<kebab>.md`:** 番号はタスクの番号とは別の連番とする。ADR が効いているかどうかの一覧（索引）を、同じディレクトリの `README.md` に日本語で置く。今どの決定が効いているかを一か所で示すためである。
-   **ADR の書式の規約は `docs/dev/conventions/` に英語で書く:** エージェントが ADR を書くときに従う規約なので、CLAUDE.md「Document language」の原則 (b) に当たる。ADR 本体と索引は、人が決め、承認する文書なので日本語とする（原則 (a)）。
-   **ADR の状態は「有効」と「廃止」の 2 つだけにし、承認は PR で行う:** ADR は、その決定を下したタスク文書と同じ PR に入るので、その PR のレビューとマージが ADR の承認を兼ねる。タスク文書の状態表（`draft` → `approved`）と `/runpr` での承認の記録は ADR に持ち込まない。持ち込むと、`/runpr` の承認の記録を ADR に広げる必要があり、変更が大きくなるためである。
-   **「主要な決定」の基準は、影響がそのタスクの外に及ぶこととする:** 後のタスクや複数の部品を縛る決定、または覆すと複数の箇所が変わる決定を主要とする。例は、構成と部品の境界、プロトコル、外部の依存やサービス、セキュリティの前提、製品の範囲、開発のプロセスとツールの方針である。既存の ADR の決定を変える決定は、常に主要とする。1 つのタスクの中で閉じる決定は、従来どおりタスク文書だけに残す。
-   **`project_overview.md` の「決定済みの方針」は要約を残し、ADR へリンクする:** 理由と採らなかった案は ADR に置く。概要は、CLAUDE.md の Quick Links で「設計する前に読む」文書とされており、その役割を保つためである。
-   **コマンドへの組み込みは、決定を人に確かめる共通の手順に 1 段足す形にする:** `/mkreq`・`/mkarch`・`/mkplan`・`/runplan` は、未決の決定を人に確かめる手順を `.claude/commands/_lib/settle-decisions.md` で共有している（同書 7〜13 行）。そこに「主要な決定の基準に当たるなら、同じ PR で ADR を作るか更新する」を足し、4 つのコマンドに効かせる。各コマンドに同じ手順を書き写さないためである。
-   **本タスクで ADR にするのは、調査で「優先」とした 15 件にする:** 置き換えの連鎖があるもの、または採らなかった案が今の文書（CLAUDE.md・`security.md` など）に残っていないものである（F-006 の表）。調査の「B6」（記事のジョブの API。0044 → 0058 → 0059）は、0058 と 0059 がまだ実装中なので、本タスクでは書かない。残りの候補は別の issue に回す（F-007）。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

以下は、レビュアーと個別には確認していない。上の決定と現行の規則から導いたもので、PR のレビューで異論があれば改める。

-   **ADR を作る PR:** 主要な決定を下したタスク文書の PR に、ADR の作成か更新を含める。要件定義で下した決定なら `/mkreq` の PR、設計で下した決定なら `/mkarch` の PR、実装中のセッションで下した決定の変更なら `/runplan` の PR である。その PR のレビューで決定が改められたときは、同じ PR の中で ADR も改める。
-   **タスク文書と ADR の両方に書く:** 主要な決定は、従来どおりタスク文書の「…で決めたこと」の節にも理由とともに書き、そこから ADR へリンクする。タスク文書は、そのタスクで何をなぜ決めたかの、後から変わらない記録として残す。
-   **設計書の付録「決定の履歴」の役割を狭める:** `/mkarch` の付録の指示（`.claude/commands/mkarch.md:74`）は、主要な決定の、タスクをまたぐ経緯を ADR に置くよう改める。付録には、そのタスクの中で閉じる決定の経緯だけを残す。両者に同じ経緯を書かないためである。
-   **既存のタスク文書は変えない:** 0050 の付録 B を除き、既存のタスク文書は書き換えず、ADR からリンクする。タスク文書は変わらない記録という役割を持つためである。0050 の付録 B は、issue の決定に従って ADR へ移し、付録には ADR へのリンクを残す。決定の内容は変えないので、0050 の設計書にとっては編集上の訂正に当たる（`docs/dev/conventions/requirements_process.md`「Editing an approved document」）。
-   **CLAUDE.md の横断の原則は ADR にしない:** 「Declare, don't infer」などの原則とその例外は、CLAUDE.md が規則として管理している。ADR にすると管理が二重になる。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   主要な決定ごとに、今効いている決定、その理由、採らなかった案、変わってきた経緯を、1 つの文書で読めるようにする。
-   今どの決定が効いているかを、一か所（索引）で分かるようにする。
-   これからのタスクで、主要な決定を下したときに ADR が作られ、更新されるようにする。

### 2.2. スコープ (In Scope)

-   `docs/dev/adr/` の ADR と索引（`README.md`）。
-   `docs/dev/conventions/` の、ADR の書式の規約（英語）。
-   CLAUDE.md：ADR の規則、主要な決定の基準、タスク文書との分担、Quick Links への追加。
-   `docs/dev/conventions/requirements_process.md`：記録の置き場所の説明（同書 96〜108 行の「Five places hold a record」）への ADR の追加。
-   `.claude/commands/_lib/settle-decisions.md`：ADR を作るか更新する段の追加。
-   `.claude/commands/mkarch.md:74`：設計書の付録「決定の履歴」の役割の調整。
-   上の手順で ADR を作るコマンドが、ADR の変更を自分の PR に含めるのに要る、コマンドの定義の変更（どこを変えるかは設計で決める。H-01）。
-   `docs/dev/project_overview.md` の「決定済みの方針」から ADR へのリンク。
-   F-006 の 15 件の ADR。
-   `docs/tasks/0050_viewer_tab/02_architecture.md` の付録 B の、ADR への移動。
-   残りの候補を記録する GitHub の issue。

### 2.3. スコープ外 (Out of Scope)

-   **決定そのものの変更:** 本タスクは、既存の決定を記録するだけで、変えない。ADR を書く途中で、今の文書とコードの食い違いが見つかった場合は、ADR に今の状態を書いたうえで、食い違いを別の issue にする。
-   **0050 の付録 B 以外の、既存のタスク文書の書き換え:** タスク文書は、変わらない記録として残す。
-   **F-006 に入らない候補の ADR:** 調査の 35 件のうち残りの 20 件（B6 を含む）は、F-007 の issue で扱う。
-   **ADR の英訳:** 翻訳の対象は README の 1 組だけである（CLAUDE.md「Translation Guidelines」）。
-   **ADR の文の意味を確かめるテスト:** CLAUDE.md「Document tests check values, structure, and executable examples, never prose」に従う。値と構造の確認を足すかどうかは設計で決める（H-02）。
-   **ADR 用の外部ツール（adr-tools など）の導入:** 依存を最小にする方針（CLAUDE.md「Dependencies」）と YAGNI に従う。
-   **`/runpr` の承認の記録の ADR への拡張:** 「要件定義の際に決めたこと」のとおり、ADR は状態表を持たない。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: ADR の置き場所、名前、索引

ADR を決まった場所に決まった名前で置き、今効いているかどうかを索引で一覧できるようにする。

**Acceptance Criteria**:
- **AC-01**: ADR は `docs/dev/adr/` の直下に、`NNNN-<kebab>.md` の名前で置かれている。`NNNN` は 4 桁の数字で、`0001` から始まる、タスクの番号とは別の連番である。`<kebab>` は、主題を表す英小文字・数字・`-` の名前である。
- **AC-02**: 同じ番号を持つ ADR は 2 つ以上ない。廃止した ADR の番号は、別の ADR に使わない。
- **AC-03**: `docs/dev/adr/README.md`（索引）が、`docs/dev/adr/` にあるすべての ADR を、番号・題名・状態とともに挙げている。索引に挙がっている ADR は、すべてファイルとして存在する。索引に挙がった状態は、その ADR の状態と一致する。
- **AC-04**: ADR と索引は日本語で書かれている。

#### F-002: ADR の書式

ADR を読めば、今の決定、その理由、採らなかった案、変わってきた経緯が分かるようにする。

**Acceptance Criteria**:
- **AC-05**: 各 ADR は、状態・背景・決定・採らなかった案・結果・経緯の 6 つの節を持つ。
- **AC-06**: 状態は「有効」か「廃止」のどちらかである。
- **AC-07**: 「決定」の節は、今効いている決定だけを述べる。過去の決定は「経緯」に書く。
- **AC-08**: 「採らなかった案」の節は、案ごとに、採らなかった理由を書く。出典の文書に理由がない案は、理由が記録されていないことを明記する。
- **AC-09**: 「経緯」の節は、決定を下したとき、または変えたときの 1 回につき 1 項目を、古い順に並べる。各項目は、日付、その時点の決定または変更の要旨、決定を記録したタスク文書へのリンクを持つ。
- **AC-10**: 廃止した ADR は、削除せずに残す。状態を「廃止」とし、廃止の日付と理由、置き換えた ADR があればそのリンクを書き、「経緯」に 1 項目を足す。
- **AC-11**: ADR が今のコードや文書の振る舞いについて述べるときは、`file:line` か、それを記録したタスク文書を示す。

#### F-003: ADR の規約

エージェントが ADR を作り、更新し、廃止するときに従う規約を、1 つの文書にまとめる。

**Acceptance Criteria**:
- **AC-12**: `docs/dev/conventions/` に、ADR の規約が英語で書かれた文書がある。
- **AC-13**: 規約は次のことを定めている。置き場所と名前と番号（F-001）、節と状態（F-002）、索引の内容、主要な決定の基準（F-004 の AC-15 と同じ基準）、決定が変わったときの更新の仕方（本文を今の決定に書き換え、「経緯」に 1 項目を足す）、廃止の仕方（AC-10）、承認は ADR を含む PR のレビューとマージで行うこと、ADR を作るか更新する PR は、その決定を下したタスク文書の PR であること。

#### F-004: CLAUDE.md と記録の置き場所の規則

主要な決定を ADR として記録すること、その基準、ほかの文書との分担を、エージェントが毎回読む場所に書く。

**Acceptance Criteria**:
- **AC-14**: CLAUDE.md が、主要な決定を ADR として記録することを述べ、ADR の規約（F-003）を参照している。
- **AC-15**: CLAUDE.md が、主要な決定の基準を述べている。基準は、影響がそのタスクの外に及ぶこと（後のタスクや複数の部品を縛る、または覆すと複数の箇所が変わる）であり、既存の ADR の決定を変える決定は常に主要とする。
- **AC-16**: CLAUDE.md が、分担を述べている。タスク文書は、そのタスクで下した決定を理由とともに書き、主要な決定については ADR へリンクする。ADR は、今効いている決定とタスクをまたぐ経緯を持つ。`project_overview.md` は今の方針の要約を持ち、ADR へリンクする。CLAUDE.md の規則と横断の原則は、ADR にしない。
- **AC-17**: CLAUDE.md の Quick Links が、ADR の索引と ADR の規約を挙げている。
- **AC-18**: `docs/dev/conventions/requirements_process.md` の記録の置き場所の説明（今は「Five places hold a record」で始まる段落）が、ADR を記録の置き場所の 1 つとして挙げ、何をそこに置くかを述べている。
- **AC-19**: `.claude/commands/mkarch.md` の、設計書の付録「決定の履歴」の指示が、主要な決定のタスクをまたぐ経緯は ADR に置き、付録にはそのタスクの中で閉じる決定の経緯だけを置く、と述べている。

#### F-005: コマンドの手順

これからのタスクで、主要な決定を下したときに、同じ PR で ADR が作られ、更新されるようにする。

**Acceptance Criteria**:
- **AC-20**: `.claude/commands/_lib/settle-decisions.md` の手順が、決定を記録した後に、その決定が主要な決定の基準に当たるかを判断し、当たるなら ADR を作るか更新する段を持つ。更新には、既存の ADR の決定を変えることと、廃止することを含む。
- **AC-21**: この段は、ADR の規約（F-003）を参照し、規約の内容を書き写さない。
- **AC-22**: `/mkreq`・`/mkarch`・`/mkplan`・`/runplan` のどれかが上の段で ADR を作るか更新したとき、その変更は、そのコマンドが開く PR に含まれる。
- **AC-23**: `/mkreq`・`/mkarch`・`/mkplan`・`/runplan` の定義は、上の段と同じ手順を書き写していない。

## 6. 用語集 (Glossary)

-   **ADR（Architecture Decision Record）:** 主要な決定を 1 つの主題ごとに記録する文書。本タスクでは、今効いている決定を本文に書き、決定の変化を「経緯」に重ねる、生きた文書とする。
