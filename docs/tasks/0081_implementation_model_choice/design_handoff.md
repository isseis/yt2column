# 設計への引き継ぎ事項（0081_implementation_model_choice）

要件定義の際に挙がった、設計（`02_architecture.md`）で決める事項である。`02_architecture.md` は、項目ごとに、とった方法か、当てはまらない理由を記録する。

## H-01: 一般的な正しさのレビューを、サブエージェントでどう行うか

AC-23 は、`/code-review` に相当する範囲の一般的な正しさのレビューを求める。`/code-review` は組み込みのスキルで、リポジトリの外にある。Opus で走らせるサブエージェント（Agent ツールの `model` に Opus を指定する）から Skill ツールでこのスキルを呼べるかは、確かめていない。呼べないとき、または呼べても範囲や出力の形を固定できないときは、`/code-review` に相当するレビューの観点を、`_lib/review-subagent-pattern.md` の CRITERIA としてリポジトリの中に書く。候補は、まず呼べるかを小さく確かめ、その結果で選ぶ方法である。選んだ方法で、AC-23 の「相当する範囲」が何を指すかも決める。関連: F-006、AC-23。

## H-02: 二つのレビューの定義を、`/weakreview` と `/runplan` でどう共有するか

F-005 と F-006 は同じ二つのレビュー、統合、直し、確認の規則を使う。`/runplan` が `/weakreview` を呼ぶのか、両方が `_lib/` に置く共通の手順を呼ぶのかを決める（`CLAUDE.md`、「DRY」）。`/weakreview` の手順の step 1〜3（タスクの特定、文書の読み込み、決定的な事前の確かめ）のうち、`/runplan` の中から使うときに省けるもの、重なるもの（`runplan.md` step 6.5 の事前の確かめ）も決める。関連: F-005、F-006、AC-17、AC-19、AC-23〜AC-26。

## H-03: 二つのレビューの指摘の統合とトリアージ

AC-19 と AC-25 は、二つのレビューの指摘から重複を除き、一つにまとめてトリアージすることを求める。重複をどう判定するか（同じ場所で同じ問題を指すか）、重大度が食い違うときにどちらをとるか、`_lib/triage-pattern.md` の尺度を使うかを決める。統合を Opus のサブエージェントに任せるか、セッションが行うかも決める。関連: AC-19、AC-25。

## H-04: `/runplan` の中で Opus のレビューを置く位置

AC-17 は、PR を開く前（Part B より前）に、PR のすべての commit に対してレビューすることを求める。`runplan.md` step 5a（PR マーカーのある計画書）と step 8（単一フェーズの計画書の PR）のどこに置くかを決める。あわせて、次も決める。

-   グリーンゲートの確認と、`作成ポイント` の最初のチェックボックスの commit との前後関係。
-   このレビューの直しの commit を、ローカルの CLI レビューでもう一度見るか。step 7.7 は、phase group ごとにローカルの CLI レビューを行う。この直しは step 7.7 の後に入るので、Codex の PR レビュー（AC-22）以外に異なる系統のレビューを受けない。
-   直しの後にグリーンゲートを再び実行すること。

関連: F-005、AC-17、AC-19、AC-22。

## H-05: セッションのモデルの判定

AC-15、AC-17、AC-20 は、`/runplan` のセッションが Opus で動いているかで振る舞いを分ける。セッションが自分のモデルを何から知るか（Claude Code がセッションに与えるモデル名など）と、分からないときの扱いを決める。分からないときは、レビューを省かない側（Opus のレビューを行う）に倒すのが安全側である。関連: AC-15、AC-17、AC-20。

## H-06: Opus で走らせられないことの検知

AC-18 と AC-24 は、レビューを Opus で走らせられないときに止まることを求める。Agent ツールの `model` に Opus を指定した呼び出しが、どんな形で失敗するか、また指定が黙って無視される場合があるかを確かめ、何をもって「Opus で走らせられない」とするかを決める。関連: AC-18、AC-24。

## H-07: 単一フェーズの計画書の値を書く場所と、`/mkplan2` の扱い

AC-06 は、単一フェーズの計画書の値を書く場所を一つに決めることを求める。PR マーカーがないので、計画書のどこに、どの形で書くか（PR マーカーと同じ `**実装モデル要件**`・`**判定理由**` の行を、どの節に置くか）を決める。`/runplan` と `/runpr` がその場所を読む方法、`mkplan2.md` が単一フェーズの計画書で止まる今の扱い（`mkplan2.md` step 2）を変えるかも決める。関連: F-002、AC-06〜AC-08。

## H-08: 読み替えの表と、読めない値の判定

AC-09〜AC-12 は、旧い値の読み替え、読めない値、欄がないときを区別することを求める。値の欄のどの部分を値として読むか（既存の計画書には、値の後に括弧書きの注を付けたものがある。例: `docs/tasks/` の中の `frontier-required（…）`）を決める。表を読むのはエージェントなので、表の形と、値の読み方を一つの場所に書く。関連: F-003、AC-09〜AC-12。
