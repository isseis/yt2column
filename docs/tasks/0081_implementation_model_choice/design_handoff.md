# 設計への引き継ぎ事項（0081_implementation_model_choice）

要件定義の際に挙がった、設計（`02_architecture.md`）で決める事項である。`02_architecture.md` は、項目ごとに、とった方法か、当てはまらない理由を記録する。

## H-01: 正しさのレビューを、サブエージェントでどう行うか

AC-28 は、正しさの不具合（バグ、要件・設計・計画とのずれ）を範囲とする正しさのレビューを求める。`/code-review` は組み込みのスキルで、リポジトリの外にある。Opus で走らせるサブエージェント（Agent ツールの `model` に Opus を指定する）から、Skill ツールでこのスキルを呼べるかは確かめていない。呼べても、範囲（cleanup を含まないこと）と出力の形を固定できるかは分からない。

候補: まず、サブエージェントから `/code-review` を呼べるかと、範囲と出力の形を指定できるかを、小さく確かめる。固定できないときは、正しさのレビューの観点を、`_lib/review-subagent-pattern.md` に渡す CRITERIA としてリポジトリの中に書く。リポジトリの中に書けば、リポジトリの外のスキルの変化に左右されない。

関連: F-006、AC-28。

## H-02: 二つのレビューの定義を、`/weakreview` と `/runplan` でどう共有するか

F-005 と F-006 は、同じ二つのレビュー、統合、直し、確認、退けない規則を使う。

候補: Opus のレビューの手順を `_lib/` の共通の手順（たとえば `_lib/opus-review.md`）に置き、`/weakreview` と `/runplan` の両方がそれを呼ぶ。`/runplan` が `/weakreview` を呼ぶ形は、`/weakreview` の引数の解釈、範囲の確かめ（AC-33）、作業ツリーの確かめが `/runplan` の手順と重なる。

あわせて決めること:
-   `weakreview.md` の今の step 1〜3（タスクの特定、文書の読み込み、決定的な事前の確かめ）のうち、共通の手順に移すもの。
-   `runplan.md` step 6.5 の事前の確かめと重なるもの。

関連: F-005、F-006、AC-21〜AC-23、AC-28〜AC-31。

## H-03: 二つのレビューの指摘の統合とトリアージ

AC-22 と AC-30 は、二つのレビューの指摘から重複を除いて一つにまとめ、トリアージすることを求める。

候補: `_lib/review-subagent-pattern.md` の panel mode の「Synthesize before fixing」を使う（重複を除き、重大度が食い違えば高い方をとり、境目の問題を組み立て直す）。二つのレビューを panel の二人のレビュアーとし、それぞれの担当と担当外を決める。統合は、panel mode と同じく呼ぶ側（セッション）が行う。

あわせて決めること: トリアージに `_lib/triage-pattern.md` の尺度を使うか。

関連: AC-22、AC-30。

## H-04: `/runplan` の中で Opus のレビューを置く位置

AC-19 は、PR を開く前（Part B より前）に、PR のすべての commit に対してレビューすることを求める。

候補: `runplan.md` の step 5a（PR マーカーのある計画書）と step 8（単一フェーズの計画書の PR）で、グリーンゲートの確認の後、`作成ポイント` の最初のチェックボックスの commit より前に置く。直しの後は、グリーンゲートを再び実行する。

あわせて決めること:
-   このレビューの直しの commit を、ローカルの CLI レビューでもう一度見るか。step 7.7 は、phase group ごとにローカルの CLI レビューを行う。この直しは step 7.7 の後に入るので、そのままでは、Codex の PR レビューのほかに異なる系統のレビューを受けない。
-   AC-25 や AC-22 の上限で止まった後、または Part B のブランチのレビューで止まった後に再び実行したとき、Opus のレビューから続けるか、済んだレビューをやり直さないための手がかり（ブランチの状態か、commit の記録か）。利用者が `/weakreview` を手で実行した後の扱いも含む。

関連: F-005、AC-19、AC-22、AC-25、AC-26。

## H-05: 実装したモデルの記録の形と、セッションのモデルの知り方

AC-18 は、phase group を実装したモデルを、その phase group の commit に記録することを求める。AC-15 は、実装を始める前に、このセッションのモデルを示すことを求める。

候補: Claude Code がセッションに与えるモデル名（モデル ID）を、セッションが自分のモデルとして読む。それを、phase group の commit メッセージの、決まった形の 1 行に書く（ローカルの CLI レビューの記録の行と同じ考え方。`_lib/local-cli-review.md`、「Reading the record lines」）。読むときは、決まった形の行だけを読み、ほかの形は記録がないものとして扱う。

あわせて決めること:
-   1 つの phase group を複数の commit で作るときに、どの commit に記録するか。記録が phase group をどう識別するか（記録のない phase group を見つけられるように）。merge-base から HEAD までの commit のうち、phase group に属さない commit（グリーンゲートのチェックボックスの commit、README の同期の commit、Opus のレビューの直しの commit など）をどう除くか。
-   セッションの途中でモデルが変わったときの扱い。
-   モデルが分からないときは、記録を書かず、記録がないものとして扱う（AC-19 で、レビューを行う側に倒れる）。

関連: AC-15、AC-18〜AC-20。

## H-06: Opus で走らせられないことの検知

AC-25 と AC-29 は、レビューを Opus で走らせられないときに止まることを求める。

候補: Agent ツールの `model` に Opus を指定した呼び出しが失敗する形と、指定が黙って無視される場合があるかを確かめる。サブエージェントに自分のモデル名を報告させ、それが Opus でなければ走らせられなかったものとして扱う。

関連: AC-25、AC-29。

## H-07: 単一フェーズの計画書の値を書く場所と、`/mkplan2` の扱い

AC-06 は、単一フェーズの計画書の値を書く場所を一つに決めることを求める。

候補: PR マーカーと同じ `**実装モデル要件**`・`**判定理由**` の 2 行を、`runplan.md` step 8 が単一 PR の記録を足す §6（チェックリストの節）の前に、決まった見出しの下に置く。`/runplan` と `/runpr` は、その見出しの下を読む。

あわせて決めること: `mkplan2.md` は、単一フェーズの計画書で止まる（`mkplan2.md` step 2）。この扱いを変えるか。値を書くのは `mkplan.md` と、簡易な進め方の手順（AC-08）である。

関連: F-002、AC-06〜AC-08。

## H-08: 読み替えの表と、値の読み方

AC-09〜AC-12 は、新しい値、旧い値、読めない値、欄がないときを区別することを求める。

候補: 値の欄のうち、`**実装モデル要件**: ` の後から行の終わりまでを、前後の空白を除いて読む。それが 6 つの値のどれかと完全に一致すれば、その値とする。それ以外は読めない値とする。既存の計画書には、値の後に括弧書きの注を付けたものがある（`docs/tasks/0017_intermediate_artifacts/03_implementation_plan.md` の `frontier-required（…）`）。0017 は完了しているので、読めない値になっても `/runplan` には影響しない。表と読み方は、`_context.md` の 1 か所に書く。

関連: F-003、AC-09〜AC-12。

## H-09: PR の説明に書く Opus のレビューの結果

AC-27 は、Opus のレビューの結果を PR の説明に示すことを求める。PR の説明は日本語で、GitHub に投稿するテキストである。

候補: `_lib/task-pr-handoff.md` Part B step 3 の本文の項目に加える。指摘はサブエージェントの文をそのまま写さず、場所と自分の言葉の要旨で書く（ローカルの CLI レビューの Codex の指摘の扱いと同じ。`_lib/task-pr-handoff.md` Part B step 3）。Part B の mention check が、この本文も対象にすること。

関連: AC-27。
