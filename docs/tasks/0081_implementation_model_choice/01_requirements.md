## 1. 概要 (Overview)

**目的:** 本書は、計画書に書く実装モデル要件を、`/runplan` を Opus と Sonnet のどちらで実行するかと、Opus のレビュー（6 節で定義）を足すかどうかに直結する値にするための要件を定義する。あわせて、`/weakreview` を、一つのコマンドで Opus のレビューを行う形に改める。

対応 issue: [#760](https://github.com/isseis/yt2column/issues/760)
関連 issue: [#790](https://github.com/isseis/yt2column/issues/790)（OpenCode と DeepSeek-V4.1-Flash で開発できるかを PoC で確かめる。本タスクの範囲外とした）

本書が決めるのは、値とその意味、値を書く場所と読む場所、Opus のレビューを行う条件と時点、指摘を直す主体、`/weakreview` の振る舞い、旧い値の扱いである。どのコマンドのどの手順に何を書くか、二つのレビューの指示をどこに置くか、指摘をどう統合するか、実装したモデルをどう記録するかは、`02_architecture.md` に委ねる（[design_handoff.md](design_handoff.md)）。

**背景:**

`/mkplan2` は、PR マーカーの `**実装モデル要件**` に `frontier-required`・`frontier-recommended`・`standard` のどれかを書く（`.claude/commands/mkplan2.md:41-44`、`:66`、`:84`）。`/mkplan` は step 8.5 でこれを実行する。この値には、次の問題がある。

-   値がモデル名ではない。`runplan.md` は「frontier モデルで実行する」「frontier モデルが望ましい」「安いモデルで実行し、`weakreview.md` で確かめる」としか書かない（`.claude/commands/runplan.md:15-20`）。`runpr.md` は値をそのまま見せるだけである（`.claude/commands/runpr.md:713-722`、`:1018-1019`）。Opus と Sonnet のどちらに当たるかは、どこにも書かれていない。
-   中間の `frontier-recommended` は「frontier モデルが望ましい」としか言わない。Sonnet で進めてよいのか、よいならどんな条件なのかが決まらない。この値の行は、既存の計画書に 89 行ある（`b47a8d46` の `docs/tasks/*/03_implementation_plan.md` で、`**実装モデル要件**: frontier-recommended` の行を数えた）。
-   `**判定理由**` は、どの契機に当たったかを書く形である（`mkplan2.md:85`）。Sonnet に任せると何が起きやすいかは、書かれない。
-   `standard` の PR を実装した後に `weakreview.md` で確かめる手順を、呼び出すコマンドはない。`.claude/commands/` の中で `weakreview` を名指すのは、案内の文（`runplan.md:19`、`mkplan2.md:41`）だけである。また、`weakreview.md` は `code-review` と `simplify` が別に走ることを前提にし（`.claude/commands/weakreview.md:14-29`）、`--fix` がなければ報告だけで終わる（同 128-132 行目）。
-   `/runplan` の中のサブエージェントのレビューは、呼ぶ側が MODEL を指定しない限り、セッションのモデルを引き継ぐ（`.claude/commands/_lib/review-subagent-pattern.md:30-35`、`:89-99`）。`/runplan` は MODEL を指定しない。そのため Sonnet のセッションでは、Opus のレビューを誰も行わない。
-   PR マーカーのない単一フェーズの計画書には、値がない。`runpr.md` は「値なし」と表示する（`runpr.md:713-722`）。

**費用の目安（要件定義の際に手元で集計した値）:** Claude Code がこのリポジトリの worktree ごとに残すセッションの記録（`~/.claude/projects/` の下）から、`/runplan` で始まったセッション 123 件を選んだ。メインのスレッドとサブエージェントのトークン数（入力、キャッシュ書き込み、キャッシュ読み、出力）を、Opus 5.5 の単価（入力 $4、キャッシュ書き込み $5、キャッシュ読み $0.20、出力 $20。100 万トークンあたり。`internal/pricing/rates.go:104-109`）で換算した。

-   1 セッションの中央値は約 $13（四分位は $7.5〜$19.2）で、費用の大半はキャッシュ読みだった。1 つの PR が複数のセッションにまたがるときは、PR あたりの費用はこれより大きい。
-   レビューのサブエージェントは、1 回で中央値約 $0.5、上位四分位で約 $1.2 だった。多くは phase group ごとのレビューである。Opus のレビュー（二つのレビューと確認のレビュー）は約 $1.5〜4 と見込むが、PR のすべての commit を範囲とし、確認のレビューを繰り返すこともあるので、これより大きくなりうる。
-   Sonnet 5.5 の単価は、どの区分も Opus 5.5 の半分である（`rates.go:110-115`）。Sonnet で同じ量のトークンを使うとすれば、Sonnet で実装して Opus のレビューを足しても、中央値の PR で約 3 割安くなる。
-   ただし、Sonnet が手戻りなどで Opus より多くのトークンを使えば、その分だけ安くなくなる。Opus での実装の費用を C、Opus のレビューの費用を R とすると、Sonnet のトークンが Opus の 2×(1−R/C) 倍を超えれば安くならない。C を $13 とすると、R が $1.5 なら約 1.8 倍、R が $4 なら約 1.4 倍である。この倍率は測っていない。記録は利用者の手元にあり、リポジトリからは同じ集計をやり直せない。

**issue #760 で決めたこと:**

-   **実装モデル要件を、とるべき行動で表す 3 つの値にする。** Opus で実装する値、Sonnet で実装して Opus のレビューを足す値、Sonnet で実装する値の 3 つである。理由: 値から、セッションのモデルと、追加のレビューの要否が直接分かるようにするため。
-   **当てはめる契機は、今の区分の契機を引き継ぐ。** Opus で実装する値は今の `frontier-required` の契機、Sonnet で実装して Opus のレビューを足す値は `frontier-recommended` の契機、Sonnet で実装する値は `standard` に対応する。理由: 契機は今の設計でも判断の材料になっているので、値の意味だけを変えれば足りるため。issue は、Opus で実装する値を「実装中のやり方の選択が成果を決め、後からのレビューでは補えない」もの、Sonnet で実装して Opus のレビューを足す値を「誤りは入りやすいが、レビューで見つけて直せる」ものとした。そのうえで、「競合するやり方があるステップ」を後者に置いた。本書もこれに従う。
-   **`**判定理由**` の書き方を変える。** Opus で実装する値と、Sonnet で実装して Opus のレビューを足す値には「Sonnet に任せると何が起きやすいか」を書く。Sonnet で実装する値には「当たる契機がない」ことを書く。理由: モデルを選ぶ人が、Sonnet にしたときの危険を読めるようにするため。
-   **Sonnet で実装する値では、追加のレビューをしない。** 理由: `/runplan` の中のレビュー、ローカルの CLI レビュー、Codex の PR レビューで足りるとしたため。
-   **`/weakreview` が、二つのレビューを Opus で一度に行う。** 一つは正しさのレビュー（`/code-review` 相当）、もう一つは弱いモデルの失敗のレビュー（今の `/weakreview` 相当。能力の低いモデルが `runplan.md` の字面だけを満たして判断を落とす失敗を探す）である。二つの指摘を統合し、重複を除いて、トリアージする。実行するセッションのモデルに関係なく、レビューは Opus で走る。理由: 今は二つを別々に手で実行する必要があり、手間が大きいため。また、セッションのモデルを引き継ぐと、Sonnet のセッションでは Opus のレビューにならないため。
-   **完了した計画書は書き換えない。** 理由: 完了した計画書の値を読むコマンドはなく、承認済みの記録を書き換える費用に見合わないため。

**要件定義の際に決めたこと（2026-11-10）:**

-   **進め方: 通常の進め方にする。** 変更は、コマンドの定義（`mkplan2.md`・`mkplan.md`・`runplan.md`・`runpr.md`・`weakreview.md`）、それらが使う共通の定義（`_context.md`・`_lib/simple-process.md`・`_lib/review-subagent-pattern.md`・`_lib/task-pr-handoff.md`、新しく作りうる共通の手順）、`CLAUDE.md` に及ぶ。未決の判断も多い。さらに、Opus のサブエージェントを二つ走らせて指摘を統合するという、新しい仕組みを作る。そのため、簡易な進め方は推奨しなかった。除外の判断: 除外に当たらない。`docs/dev/security.md` の規則と前提、開発用ツールの信頼境界（`fixprguard`・`codexreview`・`mergepr`、レビューのスレッドの扱い）、外部の依存は、どれも変えないからである（`docs/dev/conventions/requirements_process.md`、「Simple Process」の「Excluded changes」）。利用者は通常の進め方を選んだ。ADR: なし（進め方の選択はタスクの中で閉じる）。
-   **3 段階を残す。** 段階の数を減らす案と比べたうえで、3 段階を採る。大きくて誤りの入りやすい PR（今の `frontier-recommended`）は、Sonnet にしたときの節約の額が最も大きい層である。誤りがレビューで見つけて直せる種類なら、Sonnet で実装して Opus のレビューを足す形が効く（上の「費用の目安」）。この比較は、Sonnet が使うトークンが、上の「費用の目安」の分かれ目（約 1.4〜1.8 倍）を超えない、という測っていない前提に立つ。ADR: [ADR-0042](../../dev/adr/0042-implementation-model-tiers.md) を作る（下の ADR の項）。
    -   採らない案 1: `opus` と `sonnet` の 2 段階（今の `frontier-recommended` を `opus` に寄せる）。仕組みは最も単純だが、最も節約できる層で、その節約を手放す。
    -   採らない案 2: `opus` と `sonnet+opus-review` の 2 段階（Sonnet で実装するときは必ず Opus がレビューする）。小さな PR では、レビューの費用が実装の費用と同じくらいになる。
-   **値の名前は `opus`・`sonnet+opus-review`・`sonnet` にする。** モデルのファミリー名だけを使い、版を含めない。理由: モデルの版が上がっても、値と計画書を書き換えずに済むため。ADR: ADR-0042。
-   **DeepSeek-V4.1-Flash を実装モデルの候補にすることは、本タスクの範囲外にする。** OpenCode と DeepSeek-V4.1-Flash で開発できるかは、PoC から始める別の issue（#790）で扱う。理由: 開発の道具に外部のサービスを加えることになり、除外される変更に当たる。コードを DeepSeek のサービスへ送ることと、DeepSeek のモデルがこのリポジトリのコマンドの手順を守れるかも、確かめていない。ADR: なし（本タスクは何も決めない）。
-   **進行中の計画書の旧い値は書き換えず、`_context.md` に読み替えを置く。** PR がまだ作られていない PR マーカーを持つ承認済みの計画書は、0073（PR-4〜6）・0076（PR-1、PR-2）・0077（PR-1〜5）の 3 つである（0029 は `withdrawn`）。読み替えは、`frontier-required` を `opus`、`frontier-recommended` を `sonnet+opus-review`、`standard` を `sonnet` とする。理由: 承認済みの文書の本文に触れずに済み、読み替えが 1 か所に集まるため。この読み替えで、承認済みの計画書の値の意味が変わることは承知している。0077 の PR-3 と PR-5（`frontier-recommended`）は、「Opus が望ましい」から「Sonnet で実装し、Opus のレビューを足す」に変わる。値の行だけを書き換える案は、この意味の変化があるので、編集上の訂正と呼べるかに議論の余地がある。決定の変更として `draft` に戻す案は、3 つの計画書の再承認を要する。ADR: ADR-0042。
-   **Opus のレビューは、`/runplan` が PR を開く前に自分で行う。** 理由: Codex の PR レビューは、PR を開いたときに 1 回だけ自動で行われる。それより後の変更はローカルの CLI レビューで見て、PR レビューを追加で頼むのは、ローカルの CLI レビューで代われない種類の変更か、利用者が求めるときだけである（[ADR-0013](../../dev/adr/0013-review-setup.md)）。PR を開く前に直せば、直した後のコードを、最初の PR レビューが見る。人が `/weakreview` を手で実行する手順も増えない。採らない案: PR を作った後、`/runpr` の前に人が `/weakreview` を実行する案（issue の例）と、`/runpr` が最初に実行する案。どちらも、直したものが最初の PR レビューに届かない。ADR: ADR-0042。
-   **Opus のレビューを行う条件は、PR を開く時点の値と、その PR の phase group を実装したモデルで決める。** 値が `sonnet+opus-review` か `opus` のとき（読み替えた値と、読めない値を含む）、PR のいずれかの phase group（`/runplan` が一度に実装するフェーズのまとまり。6 節で定義）が Opus 以外で実装されている場合と、実装したモデルの記録がない場合に、レビューを行う。PR のすべての phase group が Opus で実装されたと記録されているときだけ省く。そのため、各 phase group を実装したモデルを、その phase group の commit に記録する。理由: 1 つの PR は複数の `/runplan` のセッションにまたがりうる（Part A は、前の phase group を持つブランチを引き継ぐ。`runplan.md:28-33`）。PR を開く時点のセッションのモデルだけで決めると、Sonnet が書いた commit がレビューなしで PR に入りうる。記録がないときにレビューを行うのは、迷うときに安全側に倒すためである。採らない案: PR を開く時点のセッションのモデルで決める案と、いつも省かずに行う案（Opus で実装したものに同じ費用を二重に払う）。ADR: ADR-0042。
-   **`opus` の PR でも、Opus 以外で実装された phase group があれば、Opus のレビューを行う。** 理由: 案内に従わずに Sonnet で実装されると、最もリスクの高い区分が、Opus の実装も Opus のレビューも受けなくなるため。採らない案: 案内だけにし、そのリスクを受け入れる案。ADR: ADR-0042。
-   **セッションのモデルと値が合わなくても、`/runplan` は止めない。** 始めるときに、値と勧めるモデルと、Opus のレビューを行う見込みを示す。理由: 値は案内であり、止めると人が別のセッションを開き直す手間がかかる。合わないときの不足は、上の条件の Opus のレビューで補う。採らない案: `opus` の PR を Opus 以外のセッションで実行したら止める案。ADR: ADR-0042。
-   **読めない値でも `/runplan` は止めず、Opus のレビューを行うものとして扱う。** 新しい 3 つの値と旧い 3 つの値のどれでもない値は、推し量って別の値として扱わない。読めないことを示し、レビューを行う側に倒す。理由: 値は案内であり、読めない値で止めると、計画書を直す PR が要る。読めないまま進むときの危険は、レビューを行うことで抑える。採らない案: 実装を始める前に止める案。ADR: ADR-0042。
-   **値の欄がない計画書では、Opus のレビューを行わない。** 理由: 本タスクの前に書かれた単一フェーズの計画書と、欄のない PR マーカーは、値がないのが正しい形である。今と同じ振る舞いを保つ。本タスクの後に書かれた計画書で欄が抜けていることは、計画書のレビューで見つける。ADR: ADR-0042。
-   **統合した指摘は、セッションが直し、確認のレビューを Opus で走らせる。** `/runplan` のセッションが Critical と Major の指摘をすべて直す。直した後の確認のレビューも Opus で走らせる。`_lib/review-subagent-pattern.md` は確認のレビューを安いモデルで走らせてよいとしているが（`review-subagent-pattern.md:100-110`）、Opus のレビューでは Opus に固定する。理由: 指摘は場所が決まっているので、Sonnet でも直せる。直し方を誤っても、Opus の確認で見つかる。採らない案: 直す作業も Opus のサブエージェントに任せる案（費用が増える）と、報告だけにする案（PR が直す前の状態で開かれる）。ADR: ADR-0042。
-   **セッションは、Opus のレビューの Critical と Major の指摘を自分の判断で退けない。** 指摘が誤っていると考えるときは、PR を開く前に人に尋ね、人の答えに従う。理由: Sonnet のセッションが Opus の指摘を退けられると、Opus のレビューを足す意味が失われるため。採らない案: 理由を添えて退け、PR の説明に示す案。ADR: ADR-0042。
-   **Opus のレビューの指摘を直すのに、要件・設計・計画の決定の変更が要るときは、`runplan.md` step 5 の今の規則に従う。** 編集上の訂正はその場で直し、決定の変更は人と決める（`runplan.md:62-65`）。理由: 実装の中で見つかる決定の変更と同じ扱いにし、別の規則を作らないため。ADR: なし（今の規則を当てるだけである）。
-   **Opus のレビューを Opus で走らせられないときは、PR を開かずに止まり、何も push しない。** Opus が使えるようになってから `/runplan` を再び実行すると、Opus のレビューから続ける。理由: レビューが Opus で走ったと思い込んだまま PR を開かないため。採らない案: PR を開き、Opus のレビューを行っていないことを PR の説明に記録する案。ADR: ADR-0042。
-   **手で実行する `/weakreview` は、既定で直し、`--no-fix` を付けたときだけ報告だけにする。`--fix` は、何もしない引数として受け入れる。** 今の、`--fix` を付けたときだけ直す規則を逆にする。理由は記録されていない（利用者がこの形を選んだ）。`--fix` を受け入れるのは、旧い呼び方でも、直すという意図どおりに動くためである。ADR: ADR-0042。
-   **手で実行する `/weakreview` が直すのは、今 checkout しているブランチの範囲だけである。作業ツリーが clean でなければ止まる。直しは commit するが、push しない。PR が既に開いているときは、直しが最初の PR レビューに届かないことを報告に添える。** 理由: ほかのブランチや、利用者の作業中の変更を書き換えないため。push と、その後のレビューの扱いは、利用者か `/runpr` に委ねるため。採らない案: 直しを push まで行う案。ADR: ADR-0042。
-   **正しさのレビューの範囲は、正しさの不具合（バグ、要件・設計・計画とのずれ）に限る。cleanup（再利用・単純化・効率。`/simplify` の範囲）は、Opus のレビューの範囲に入れない。** 理由: issue が「一般的な正しさのレビュー」を求めているため。cleanup の指摘は、直すか否かの判断を Sonnet に課すことになり、統合と確認の費用も増やす。ADR: ADR-0042。
-   **単一フェーズの計画書にも、実装モデル要件の値を持たせる。** `/mkplan` が、PR マーカーのある計画書と同じ規則で値と判定理由を決めて書く。`/runplan` と `/runpr` は、PR マーカーの値と同じように読む。理由: 単一フェーズの計画書でも、モデルを選び、Opus のレビューの要否を決める必要があるため。採らない案: 今のまま値を持たせない案。ADR: ADR-0042。
-   **PR の説明に、Opus のレビューを行ったかと、その結果を示す。** 理由: Codex と人のレビュアーが、PR の commit が Opus のレビューを受けたかを PR から読めるようにするため。ADR: なし（PR の説明の中身で、タスクの中で閉じる）。
-   **ADR: [ADR-0042](../../dev/adr/0042-implementation-model-tiers.md) を作る。** 実装モデル要件の値とその意味、Opus のレビューを行う条件と時点、旧い値の読み替えは、後のすべての計画書と、複数のコマンドを縛る。これは `CLAUDE.md`、「Design decisions (ADR)」の基準で主要な決定であり、開発プロセスの方針に当たる。[ADR-0013](../../dev/adr/0013-review-setup.md) の決定（Codex の PR レビューを作成時の 1 回だけにする）は変えないので、ADR-0013 は更新しない。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   実装モデル要件の値を見れば、`/runplan` を Opus と Sonnet のどちらで実行するかと、Opus のレビューが足されるかが分かるようにする。
-   Sonnet で実装した phase group を含む `sonnet+opus-review`・`opus` の PR では、人が別のコマンドを実行しなくても、PR を開く前に Opus のレビューが行われるようにする。
-   `/weakreview` 一つで、正しさのレビューと弱いモデルの失敗のレビューを、Opus で行えるようにする。

### 2.2. スコープ (In Scope)

-   実装モデル要件の 3 つの値、その意味、当てはめる契機、判定理由の書き方（F-001）。
-   単一フェーズの計画書の値（F-002）。
-   旧い値の読み替え、読めない値、欄がないときの扱い（F-003）。
-   `/runplan` と `/runpr` での値の案内（F-004）。
-   phase group を実装したモデルの記録と、`/runplan` が PR を開く前に行う Opus のレビュー（F-005）。
-   `/weakreview` の改良（F-006）。
-   関連する記述（`_context.md`、`CLAUDE.md`、案内の文）の更新（F-007）。
-   ADR-0042 の作成と、ADR の索引の更新。

### 2.3. スコープ外 (Out of Scope)

-   **DeepSeek-V4.1-Flash など、Claude 以外のモデルでの実装。** 理由は 1 節「要件定義の際に決めたこと」のとおりで、#790 で扱う。
-   **完了した計画書と、進行中の計画書（0073・0076・0077）の書き換え。** 旧い値は読み替えで扱う（F-003）。
-   **`/runplan` の中のレビュー（step 7・7.5）と、ローカルの CLI レビューのモデルの変更。** issue が求めていない。これらは今のまま、セッションのモデルを引き継ぐ。
-   **Codex の PR レビューの方針（ADR-0013）の変更。**
-   **cleanup（`/simplify` の範囲）のレビュー。** 1 節「要件定義の際に決めたこと」のとおり、Opus のレビューの範囲に入れない。
-   **Sonnet と Opus の実際の費用の測定と、それを記録する仕組み。** 1 節「費用の目安」の前提（Sonnet が使うトークンの倍率）は、本タスクでは確かめない。
-   **`/code-review` と `/simplify` そのものの変更。** 組み込みのスキルであり、リポジトリの外にある。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 実装モデル要件の値と意味

`/mkplan2`（`/mkplan` の step 8.5 と、簡易な進め方の `/mkreq` から使われるものを含む）が PR マーカーに書く `**実装モデル要件**` を、次の 3 つの値のどれか一つにする。

| 値 | 意味 | 当てはめる契機 |
|---|---|---|
| `opus` | Opus で実装する。 | 今の `frontier-required` の契機（前例のない設計判断、`mkplan.md` step 8 の panel mode の契機） |
| `sonnet+opus-review` | Sonnet で実装し、PR を開く前に Opus のレビュー（F-005）を行う。 | 今の `frontier-recommended` の契機（競合するやり方があるステップ、Conditional checks に二つ以上当たるステップ、復旧処理・並行処理・状態機械などの複雑なステップ） |
| `sonnet` | Sonnet で実装し、追加のレビューはしない。 | それ以外 |

**Acceptance Criteria**:
- **AC-01**: `mkplan2.md` の PR マーカーの書式と説明が、`**実装モデル要件**` の値として `opus`・`sonnet+opus-review`・`sonnet` の 3 つだけを挙げる。`frontier-required`・`frontier-recommended`・`standard` を、書く値として挙げない。
- **AC-02**: `mkplan2.md` が、上の表のとおり、各値の意味と当てはめる契機を述べる。PR は、その PR のステップが求める値のうち最も高いものをとる（`opus` が最も高く、`sonnet` が最も低い）と述べる。
- **AC-03**: `mkplan2.md` が、`**判定理由**` の書き方として、`opus` と `sonnet+opus-review` のときは当たった契機とあわせて「Sonnet に任せると何が起きやすいか」を、`sonnet` のときは当たる契機がないことを書くと述べる。
- **AC-04**: `mkplan2.md` の `### 3.2 PR 構成` の表の例と、step 9 の PR 境界のレビューの観点とチェックリストが、新しい値で書かれている。
- **AC-05**: `mkplan2.md` が、値の意味と判定理由の書き方を一か所でだけ定める。旧い値の意味や、旧い判定理由の書き方が残っていない。

#### F-002: 単一フェーズの計画書の値

PR マーカーのない単一フェーズの計画書にも、実装モデル要件の値と判定理由を持たせる。

**Acceptance Criteria**:
- **AC-06**: `mkplan.md` が、`### フェーズ` が一つの計画書にも、F-001 と同じ値・契機・判定理由の書き方で、実装モデル要件と判定理由を書くと述べる。書く場所は、計画書の中で一つに決まっている。
- **AC-07**: `runplan.md` と `runpr.md` が、単一フェーズの計画書では AC-06 の場所から値を読み、その値に対して、PR マーカーの値と同じ案内（F-004）と、同じ Opus のレビューの条件（F-005）を当てると述べる。
- **AC-08**: 簡易な進め方で単一フェーズの計画書を書く手順（`.claude/commands/_lib/simple-process.md`、「Writing the three documents」）が、AC-06 の値と判定理由を書くことを含む。

#### F-003: 旧い値の読み替え、読めない値、欄がないとき

本タスクの前に書かれた計画書の旧い値を、書き換えずに読み替える。

**Acceptance Criteria**:
- **AC-09**: `_context.md` の PR marker conventions が、読み替えを一つの表で持つ: `frontier-required` は `opus`、`frontier-recommended` は `sonnet+opus-review`、`standard` は `sonnet` として扱う。読み替えを持つ場所は、この表だけである。
- **AC-10**: `/runplan` と `/runpr` は、旧い値を読み替えの表で新しい値として扱う。旧い値を示すときは、旧い値と読み替えた値の両方を示す。
- **AC-11**: 値の欄に、新しい 3 つの値と旧い 3 つの値のどれでもない文字列があるとき（読めない値）、`/runplan` は止まらない。読めない値を別の値として扱わず、その文字列と、読めない値であることを示し、Opus のレビューの条件（F-005）では `sonnet+opus-review` と同じに扱う。`/runpr` は、その文字列をそのまま示し、読めない値であることを添える。
- **AC-12**: 値の欄がない計画書では、`/runplan` と `/runpr` は値がないものとして扱う。案内は値がないことを示し、`/runplan` は Opus のレビューを行わない。
- **AC-13**: 0073・0076・0077 の計画書は、本タスクの PR で変更されない。

#### F-004: 値の案内

**Acceptance Criteria**:
- **AC-14**: `runplan.md` の冒頭の案内が、3 つの値それぞれについて、セッションを始めるモデル（`opus` は Opus、`sonnet+opus-review` と `sonnet` は Sonnet）と、Opus のレビューが足される条件（F-005）を述べる。
- **AC-15**: `/runplan` は、実装を始める前に、対象の PR（単一フェーズの計画書では計画書）の値（旧い値なら読み替えた値も）、勧めるモデル、このセッションのモデル、Opus のレビューを行う見込みを示す。値が読めないときと値の欄がないときは、勧めるモデルはないと示し、読めない値ならその文字列も示す。`/runplan` は、セッションのモデルと値が合わなくても止まらない。
- **AC-16**: `runplan.md` の冒頭の案内が、「この案内はどのステップも変えない」という今の記述（`runplan.md:19-20`）を持たない。値が Opus のレビューの条件に関わることを述べる。
- **AC-17**: `/runpr` が step 4 の質問と step 5 の `/clear` の案内で次の PR の実装モデル要件を示すとき、値に加えて、新しいセッションを始めるモデル（Opus か Sonnet）を示す。値がないときは、その旨と分かる範囲の理由を示す。読めない値のときは、その文字列と、読めない値であることを示す。

#### F-005: 実装したモデルの記録と、PR を開く前の Opus のレビュー

**Acceptance Criteria**:
- **AC-18**: `/runplan` は、phase group を実装するたびに、その phase group の commit に、実装したセッションのモデルを記録する。
- **AC-19**: PR を開く前（`_lib/task-pr-handoff.md` の Part B より前）に、`/runplan` は次の条件のすべてが成り立つとき、Opus のレビューを行う。PR マーカーのある計画書でも、単一フェーズの計画書でも同じである。
    1. PR の値が `sonnet+opus-review` か `opus` である（読み替えた値と、読めない値を含む）。
    2. PR のどれかの phase group について、AC-18 の記録が Opus 以外のモデルを示すか、記録がない。
- **AC-20**: AC-19 の条件が成り立たないとき、`/runplan` は Opus のレビューを行わない。値が `sonnet` のとき、値の欄がないとき（AC-12）、PR のすべての phase group が Opus で実装されたと記録されているときがこれに当たる。
- **AC-21**: Opus のレビューは、F-006 の二つのレビューを、その PR のすべての commit（`origin/main` との merge-base から HEAD まで）に対して行う。二つのレビューと確認のレビューは、セッションのモデルに関係なく Opus で走る。
- **AC-22**: 二つのレビューの指摘は、重複を除いて一つにまとめ、トリアージする。`/runplan` のセッションは Critical と Major の指摘をすべて直して commit し、直したことの確認のレビューを Opus で走らせる。確認のレビューの繰り返しの上限と、上限に達したときに止まって報告することは、`_lib/review-subagent-pattern.md` の規則に従う。上限に達して止まるときは、AC-25 と同じく PR を開かず、何も push しない。
- **AC-23**: セッションが Critical か Major の指摘を誤りと考えるときは、自分の判断で退けず、PR を開く前に人に尋ねる。人がその指摘を退けたときだけ、直さずに進む。
- **AC-24**: 指摘を直すのに要件・設計・計画の決定の変更が要るときは、`runplan.md` step 5 の規則（編集上の訂正と決定の変更の区別）に従う。
- **AC-25**: Opus で走らせられないときは、セッションのモデルで代わりに走らせない。PR を開かずに止まり、何も push せず、その旨と、Opus が使えるようになってから `/runplan` を再び実行することを報告する。再び実行した `/runplan` は、Opus のレビューから続ける。
- **AC-26**: Opus のレビューの直しの commit は、PR を開く前にブランチに入っている。
- **AC-27**: PR の説明は、この PR で Opus のレビューを行ったか、行わなかったかを示す。行わなかったときは、AC-19 の条件のどれが成り立たなかったかを示す。行ったときは、指摘の件数を重大度ごとに示す。直さずに進んだ Critical と Major の指摘（人が退けたものと、AC-24 で人が決定の変更を認めなかったもの）があれば、その場所と要旨を示す。

#### F-006: `/weakreview` の改良

**Acceptance Criteria**:
- **AC-28**: `/weakreview` は、二つのレビューを行う。一つは正しさのレビューで、範囲は正しさの不具合（バグ、要件・設計・計画とのずれ）であり、cleanup（再利用・単純化・効率）を含まない。もう一つは弱いモデルの失敗のレビューで、今の「Weak-model failure checklist」による。
- **AC-29**: 二つのレビューと確認のレビューは、`/weakreview` を実行するセッションのモデルに関係なく Opus で走る。Opus で走らせられないときは、セッションのモデルで代わりに走らせず、止まってその旨を報告する。
- **AC-30**: `/weakreview` は、二つのレビューの指摘を重複を除いて一つにまとめ、重大度ごとに報告する。
- **AC-31**: 引数に `--no-fix` がないとき、`/weakreview` は Critical と Major の指摘を直して commit し、直したことの確認のレビューを Opus で走らせる（AC-22・AC-23 と同じ規則）。push はしない。直すのに要件・設計・計画の決定の変更が要る指摘は直さず、その指摘を報告して、人に委ねる。`--no-fix` があるときは、何も直さずに報告だけをする。
- **AC-32**: `--fix` は受け入れ、何もしない引数として扱う（直すのは既定である）。`--no-fix` と `--fix` が両方とも渡されたときと、受け付けないほかの引数が渡されたときは、推し量らずに止まり、受け付ける引数を示す。
- **AC-33**: 直すとき、`/weakreview` は、対象の範囲が今 checkout しているブランチの commit でなければ止まる。作業ツリーが clean でなければ止まる。どちらも、何も変えずに理由を報告する。
- **AC-34**: 直すとき、対象のブランチに PR が既に開いていれば、直しが最初の PR レビューに届かないことを報告に添える。
- **AC-35**: `weakreview.md` の Purpose が、`code-review` と `simplify` が別に走ることを前提にしない形に書き換えられている。
- **AC-36**: 範囲の指定（commit の範囲、PR 番号、省略時の `origin/main...HEAD`）は、今と同じに受け付ける。

#### F-007: 関連する記述

**Acceptance Criteria**:
- **AC-37**: `_context.md` の PR marker conventions が、新しい 3 つの値と、それを書くコマンドと読むコマンドを述べる。`mkplan.md` が値を書く場面として、単一フェーズの計画書（F-002）を含む。
- **AC-38**: `CLAUDE.md` のコマンドの一覧の `/weakreview` の行が、F-006 の振る舞い（Opus の二つのレビュー、既定で直す）と、受け付ける引数（`--no-fix` を含む）に合っている。`weakreview.md` の frontmatter の `argument-hint` も、受け付ける引数に合っている。
- **AC-39**: `.claude/commands/` の中に、実装モデル要件の値として旧い 3 つの値を書く指示が残っていない。旧い値が現れるのは、`_context.md` の読み替えの表（AC-09）と、旧い値を読むときの扱いを述べる箇所だけである。「安いモデルで実装し、`weakreview.md` で確かめる」という今の案内の文（`mkplan2.md:41`、`runplan.md:18-19`）も残っていない。
- **AC-40**: ADR-0042 が、本書の決定（3 つの値とその意味、Opus のレビューを行う条件と時点、直す主体と退けないこと、Opus で走らせられないときに止まること、読めない値の扱い、単一フェーズの計画書の値、旧い値の読み替え、`/weakreview` の既定と範囲）を `## 決定` に持ち、ADR の索引に行がある。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   **費用:** Opus のレビューを行う PR では、二つのレビューと確認のレビューの分だけ費用が増える。1 節「費用の目安」の集計では、約 $1.5〜4 である。この費用は、Sonnet で実装して節約する額より小さいことを前提にしている。この前提は確かめていない（2.3 節）。
-   **時間:** Opus のレビューを行う PR では、PR を開くまでの時間がレビューの分だけ延びる。時間の上限は設けない。

### 4.2. セキュリティ (Security)

-   N/A。条件付きのガイド（`docs/dev/security.md`）の契機に当たらない。変えるのは開発用のコマンドの手順で、外部コマンドの起動、API キーと Webhook の URL、キャッシュ、プロンプトへの信頼できないテキストの埋め込みには触れない。レビューのサブエージェントが Anthropic の API にコードを送ることは今と同じで、送り先のサービスも変わらない。開発用ツールの信頼境界（ADR-0015）も変えない。phase group を実装したモデルの記録（AC-18）は、セッションが自分について書くもので、レビューを省くかの判断に使う、品質を保つための仕組みであり、セキュリティの境界ではない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   Opus のレビューを Opus で実行できないときは、より弱いモデルで代えずに止まる（AC-25、AC-29）。理由: レビューが Opus で走ったと思い込んだまま PR を開くと、Opus のレビューを足す意味が失われるため。
-   実装したモデルの記録がない phase group と、読めない値は、Opus のレビューを行う側に倒す（AC-11、AC-19）。

### 4.4. 互換性 (Compatibility)

-   本タスクの前に書かれた計画書は、書き換えずに読み替えの表で読める（F-003）。
-   本タスクの前に作られた phase group の commit には、実装したモデルの記録がない。そうした commit を含む PR は、値が `sonnet+opus-review` か `opus` なら Opus のレビューを受ける（AC-19）。
-   `/weakreview --fix` は、引き続き受け付ける（AC-32）。

### 4.5. 保守性 (Maintainability)

-   値にはモデルのファミリー名だけを使い、版を含めない。Opus や Sonnet の版が上がっても、値と計画書は書き換えない。
-   二つのレビューの指示は、`/weakreview` と `/runplan` で一つの定義を共有する（`CLAUDE.md`、「DRY」）。共有の仕方は `02_architecture.md` で決める（`design_handoff.md`）。
-   読み替えの表は、PR がまだ作られていない PR マーカーに旧い値を持つ計画書がなくなれば、消してよい。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   Codex の PR レビューの頼み方は変えない（ADR-0013）。
-   コマンドの定義は英語で書く（`CLAUDE.md`、「Document language」の原則 (b)）。PR の説明は日本語で書く（`CLAUDE.md`、「Language」）。

## 6. 用語集 (Glossary)

-   **実装モデル要件:** 計画書の PR マーカー（単一フェーズの計画書では、F-002 が決める場所）にある `**実装モデル要件**` の値。`/runplan` を実行するモデルと、Opus のレビューの条件に関わる。
-   **正しさのレビュー:** 正しさの不具合（バグ、要件・設計・計画とのずれ）を探すレビュー。cleanup を含まない。
-   **弱いモデルの失敗のレビュー:** `weakreview.md` の「Weak-model failure checklist」によるレビュー。能力の低いモデルが手順の字面だけを満たして判断を落とす失敗を探す。
-   **phase group:** `/runplan` が一度に実装する、計画書のフェーズのまとまり（`runplan.md` step 4 の「implementation group」）。
-   **確認のレビュー:** 指摘を直した後に、その直しが正しく、新しい問題を生んでいないかを確かめるレビュー。
-   **Opus のレビュー:** 正しさのレビューと弱いモデルの失敗のレビューを Opus で行い、指摘を統合して直し、確認のレビューを Opus で行う一連の手順。`/weakreview` と、F-005 の条件の `/runplan` が行う。
-   **旧い値:** 本タスクの前の実装モデル要件の値、`frontier-required`・`frontier-recommended`・`standard`。
-   **読めない値:** 値の欄にある、新しい 3 つの値と旧い 3 つの値のどれでもない文字列。
-   **読み替えの表:** 旧い値を新しい値として扱うための、`_context.md` の表（AC-09）。
-   **通常の進め方・簡易な進め方:** `docs/translation_glossary.md` のとおり。
-   ほかの用語は `docs/translation_glossary.md` と統一する。
