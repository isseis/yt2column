## 1. 概要 (Overview)

**目的:** 本書は、次の 2 つの要件を定義する。

1. タスクの PR を開くコマンドが、PR を開く前に、Fable のサブエージェントに範囲を絞ったレビュー（Fable の部分レビュー。6 節で定義）を行わせる。
2. 修正の後に Codex の PR レビューを `/runpr` が自動で頼む条件を絞る。

対応 issue: [#924](https://github.com/isseis/yt2column/issues/924)

本書が決めるのは、次の点である。

-   Fable の部分レビューを行うコマンドと時機
-   範囲の基準と選び方
-   Fable に渡すもの
-   指摘のトリアージと却下の規則
-   Fable が走らないときの扱い
-   記録
-   Codex の PR 再レビューを自動で頼む条件
-   `/runpr` のマージの質問で示すもの

次の点は `02_architecture.md` に委ねる（[design_handoff.md](design_handoff.md)）。

-   共通の手順をどのファイルに置き、ほかの手順とどう分担するか
-   並列に走らせた結果をどう待ち合わせるか
-   範囲の基準の具体的な文言
-   記録の行の形
-   Opus のレビューとの順序

**背景:**

今の手順で、PR を開く前に行うレビューは次のとおりである。

-   **タスク文書の PR**（`/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2`）: 書いた後に、サブエージェントのセルフレビュー（`.claude/commands/_lib/review-subagent-pattern.md`）と `japrose` を行う（たとえば `.claude/commands/mkreq.md:164-202`）。その後、共有の手順 `.claude/commands/_lib/task-pr-handoff.md` の Part B step 1 で、ブランチ全体にローカルの CLI レビューを行ってから、PR を開く（`task-pr-handoff.md:180-203`）。簡易な進め方の 3 文書の PR も、`/mkreq` が同じ Part B で開く（`mkreq.md:204`）。
-   **実装の PR**（`/runplan`）: phase group ごとに、サブエージェントのレビュー（step 7・7.5）とローカルの CLI レビュー（step 7.7）を行う（`.claude/commands/runplan.md:187-252`）。PR を開く前には、「Before the PR」の B1〜B5 で、必要なときにブランチ全体のローカルの CLI レビューと Opus のレビューを行う（`runplan.md:261-335`）。
-   **Codex の PR レビュー**: PR を開いたときに 1 回だけ自動で行われる。その後の変更はローカルの CLI レビューで見る（[ADR-0013](../../dev/adr/0013-review-setup.md)）。PR レビューを追加で頼むのは、`.claude/commands/_lib/pr-review-escalation.md` の判断か、利用者が求めたときだけである。判断の基準は 5 つある（`pr-review-escalation.md:34-56`）: 振る舞いや契約の変更、モジュールの境界をまたぐ変更、要件や設計の決定に触れる変更、セキュリティと耐久性に触れる変更、新しい仕組み。判断が `request` なら、`/runpr` が PR ごとに 1 回まで自動で頼む（`.claude/commands/runpr.md:665-678`）。判断が `ask` なら、マージの質問の「先に PR レビューを依頼」を推奨にする（`runpr.md:1029-1036`）。

これまで 7 件の PR では、PR を作成した後に、Fable のサブエージェントのレビューを手作業で頼んできた（issue #924 の表）。

-   7 件中 6 件で、マージの前に直すべき Major 級の問題が見つかり、その指摘は採用された。#855・#885・#914 では、Codex の最初の PR レビューが指摘 0 件を返した。同じ内容から、Fable は Major を見つけた。#914 の指摘には、API キーの漏れが含まれていた。
-   成果が大きかったのは、範囲を絞って役目を狭めた回（役目は、信頼の境界、先行文書との照合、技術的な主張の実験による確認）と、文書の PR である。効果が薄かったのは #865 だった。#865 は、承認済みの設計を写した実装で、すでに Opus のレビューを受けていた。
-   弱点は、受け取る側のトリアージだった。#865 と #914 で、正しい指摘を誤って却下した。#914 では、前回のローカルの CLI レビューの指摘を、Opus で動くセッションがトリアージで誤って却下していた。Fable の指摘は、その却下された指摘と同じものだった（出典は issue #924。却下されたのはローカルの CLI レビューの指摘で、Opus のレビュー（`_lib/opus-review.md`）の指摘ではない）。
-   #865・#880・#887 では、Codex の既出の指摘を Fable がもう一度出した。
-   PR を作った後に Fable の指摘を直すと、その修正は Codex の PR レビューに見られない。
-   PR を作成した後に手作業で頼んだ Fable のレビューの指摘を直し、そのうえで Codex の PR 再レビューを頼んだところ、7 件中 6 件で新しい指摘は 0 件だった。例外は #887 で、送信の信頼の境界のロジックを書き換えた PR である。#887 の 2 件のうち 1 件は、Fable の指摘の修正の穴だった。

**issue #924 で決めたこと:**

-   **Fable の部分レビューを、PR を開く前に行う。** 時機は、セルフレビューの修正が済んだ後で、ローカルの CLI レビューと並列に走らせる。`/runplan` では PR ごとに 1 回とし、phase group ごとには走らせない。理由: PR を開いた後に直すと、その修正は Codex の PR レビューに見られないため。phase group ごとに走らせると、費用が phase group の数だけ増えるため。 ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md)。
-   **範囲は決まった基準に当たる箇所に限る。** 基準は、信頼の境界（秘密、送信、削除、pane の操作、不可逆な副作用）、先行文書（承認済みの要件書・設計書・ADR）との照合、外部の振る舞いについての技術的な主張、人に問わずに決めたこと、の 4 つである。外した箇所とその理由は PR の説明に残す。当たる箇所がないときは、issue では走らせず `not run` とその理由を記録するとしたが、要件定義の際に変えた（下の「要件定義の際に決めたこと」の、範囲から外した箇所の項）。理由: 範囲を絞って役目を狭めた回の成果が大きかったため。 ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md)。
-   **プロンプトでは狭い役目を与え、却下した指摘と決着済みの論点を渡す。** 再提起は、具体的な筋書きがあるときに限る。理由: Codex の既出の指摘との重複を避けるため。 ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md)。
-   **Fable の指摘とローカルの CLI レビューの指摘を 1 回のトリアージにまとめ、重複を除いてから直す。直した後は、ローカルの CLI レビューの指摘の修正と同じ経路で確かめる。** 理由: 同じ問題を 2 回直さず、修正を確かめずに push しないため（#855 では、修正をローカルの CLI レビューにかけずに push した）。 ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md)。
-   **却下するときは、コードの確認か実験で根拠を確かめ、その結果を記録する。** 理由: 誤った却下が #865 と #914 で起きたため。 ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md)。
-   **Fable が使えないときは、止めずに `not run` とその理由を記録して進める。** 理由: Fable は追加のレビューであり、使えないことで PR を止める必要はないため。 ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md)。
-   **Fable の部分レビューを実施したか（`run`／`not run`）を、ローカルの CLI レビューの記録の行にならって、コミットメッセージに残す。** 理由: 1 つの PR が複数のセッションにまたがっても、後のセッションが記録を読めるようにするため。 ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md)。
-   **修正の後は、ローカルの CLI レビューで確かめることを基本とする。Codex の PR 再レビューは、`_lib/pr-review-escalation.md` の条件に当たる場合に限り、条件を今の実績に照らして見直す。マージの質問の「先に PR レビューを依頼」の示し方も見直す。** 理由: Codex の割り当てを節約するため。 ADR: [ADR-0013](../../dev/adr/0013-review-setup.md)。
-   **Codex の最初の PR レビュー（PR の作成時の 1 回）は残す。`/fixpr` の手順には Fable を組み込まない。** 理由: issue の範囲の外とした。 ADR: [ADR-0013](../../dev/adr/0013-review-setup.md)（Codex の最初の PR レビューを残すこと）。

**要件定義の際に決めたこと（2026-11-17）:**

-   **進め方: 通常の進め方にする。** 変更は多くのコマンドの定義（`mkreq.md`・`mkarch.md`・`mkplan.md`・`mkplan2.md`・`runplan.md`・`runpr.md`）と共通の手順（`_lib/task-pr-handoff.md`・`_lib/local-cli-review.md`・`_lib/pr-review-escalation.md`、新しく作る共通の手順）、`CLAUDE.md`、ADR に及ぶ。Fable のサブエージェントを並列に走らせる新しい仕組みを作り、[ADR-0013](../../dev/adr/0013-review-setup.md) の決定（PR レビューを追加で頼む条件）を変える。そのため、簡易な進め方は推奨しなかった。除外の判断: 簡易な進め方の除外には当たらないと判断した。`docs/dev/security.md` の規則と前提、`fixprguard`・`codexreview`・`mergepr`、レビューのスレッドの本文の扱い、外部の依存は、どれも変えない。Fable は Claude Code の Agent ツールで選べるモデルの 1 つで（`model` の値 `fable`）、新しい外部のサービスではない。ただし、本タスクは開発用のツールの信頼の境界（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）の近くに触れる。新しいサブエージェントの出力の文をコミットや PR の説明に入れない扱いを加え（AC-29）、PR レビューを自動で追加で頼む関門を絞る（F-007）。また、Codex CLI の指摘の本文を Fable のプロンプトに渡すと、信頼しないテキストの扱い（`.claude/commands/_lib/local-cli-review.md:206-212`、`:264-269`）に触れるので、渡すのはセッション自身の要約だけとする（F-003）。利用者は通常の進め方を選んだ。境界に当たるかに迷いが残るが、通常の進め方を選んだので、この判断で進め方は変わらない。ADR: なし（進め方の選択はタスクの中で閉じる）。
-   **Codex の PR 再レビューを `/runpr` が自動で頼むのは、信頼の境界・セキュリティ・耐久性に触れる変更だけにする。** 信頼の境界には、開発用のツールのもの（秘密、送信、削除、pane の操作、不可逆な副作用）を含める。今の基準のうち、ほかの 4 つ（振る舞いや契約の変更、モジュールの境界をまたぐ変更、要件や設計の決定に触れる変更、新しい仕組み）に当たる変更の扱いは、Codex の PR レビューの後の変更をローカルの CLI レビューが見たかで分ける。すべて見ていれば `skip`、見ていない範囲があれば `ask` とする。理由: PR を作成した後に手作業で頼んだ Fable のレビューの指摘を直した後の再レビューは、7 件中 6 件で新しい指摘が 0 件で、例外の #887 は信頼の境界のロジックの書き換えだったため。ただし、この実績は Fable の指摘の修正についてのものである。本タスクの後は Fable の修正は PR を開く前に入り、この条件が扱うのは、主に `/fixpr` による Codex の指摘の修正など、PR を開いた後の変更である。実績と違う種類の変更に当てはめること、#887 のように修正が新しい穴を開けうることは、受け入れる危険とする。ADR: [ADR-0013](../../dev/adr/0013-review-setup.md) を更新する。
    -   採らない案: 基準は今のまま、マージの質問の示し方だけを見直す案。基準 1・3・5 は Fable の修正の多くに当たるので、割り当ての節約にならない。
    -   採らない案: 変えない案。同じ理由で採らない。
-   **却下の根拠を確かめて記録する規則は、Fable の指摘とローカルの CLI レビューの指摘をまとめた 1 回のトリアージの全体に当てはめる。** 理由: #914 の誤った却下は、ローカルの CLI レビューの指摘の却下と同じものだったため。Opus のレビューの指摘は、もともとセッションが自分の判断で退けず、人に尋ねる（[ADR-0042](../../dev/adr/0042-implementation-model-tiers.md)）ので、この規則の対象にしない。ADR: [ADR-0050](../../dev/adr/0050-fable-partial-review.md) を作る。
    -   採らない案: Fable の指摘だけに当てはめる案。同じトリアージの中で却下の基準が 2 つになり、#914 の型の誤りを防げない。
    -   採らない案: `/fixpr` の PR のスレッドとセルフレビューの指摘にも広げる案。issue の範囲（`/fixpr` を変えない）を超える。
-   **Fable で走ったかは、サブエージェントが報告するモデル ID で確かめる。Fable でなければ `not run` とし、別のモデルで代えない。** 理由: 代えると、Fable で走ったつもりの記録が残るため。Opus のレビューが Opus で走ったかを確かめる今の方法（`.claude/commands/_lib/opus-review.md:391-410`）とも揃う。ADR: ADR-0050。
    -   採らない案: Opus で代える案。Opus のレビューと役目が重なり、記録の意味も曖昧になる。
    -   採らない案: 確かめない案。Agent ツールの `model` の指定が効いたことが分からない。
-   **対象のコマンドに `/mkplan2` も含める。** `/mkplan2` の PR は、PR の境界・実装モデル要件・自動送信の値を人に問わずに決める。これは範囲の基準「人に問わずに決めたこと」に当たりうる。また、タスク文書の PR を開く共有の手順（`task-pr-handoff.md` Part B）に置けば、コマンドごとの例外が要らない。issue の挙げた 4 つのコマンドを超えるので、ここに記録する。ADR: ADR-0050。
-   **OpenCode で動く `/runplan` では、Fable のレビューを `not run`（エージェントが Fable を呼べない）と記録して進める。** 実装モデル要件が `sonnet` の PR の `/runplan` は、OpenCode で動く（`.claude/commands/_context.md:161`）。OpenCode からは、Claude Code の Agent ツールで選ぶ Fable のサブエージェントを呼べない。理由: issue の「使えないときは止めずに `not run`」に揃え、chief の送り先（[ADR-0046](../../dev/adr/0046-chief-of-staff.md)）を変えずに済むため。ADR: ADR-0050。
    -   採らない案: PR を開く前に Claude Code に引き継ぎ、Fable を走らせる案。`runplan-takeover` の行（`_context.md:162`）の役目を広げることになり、chief の動きが変わる。
-   **書き手が範囲から外した箇所とその理由も Fable に渡す。外した判断が基準に当たると Fable が見たときは、指摘として返せるようにする。** 外した箇所の中身を全部は読ませない。どの基準にも当たる箇所がないと書き手が判断したときも、Fable に外した箇所の一覧と理由だけを渡して確かめさせる（2026-11-17 のセルフレビューの後に確かめた）。理由: 書き手のセッションが自分の盲点を範囲から外すのを防ぎつつ、範囲を絞った効果を保つため。当たる箇所がないときに Fable を呼ばないと、すべてを外した判断を誰も確かめない。ADR: ADR-0050。
    -   採らない案: 外した箇所を PR の説明に残すだけにする案（issue の案）。人が PR の説明を読むまで盲点に気づけない。
    -   採らない案: 範囲を別のサブエージェントに選ばせる案。サブエージェントが 1 つ増え、そのサブエージェントの選び方を確かめる者がいない。
-   **`/runpr` のマージの質問の「先に PR レビューを依頼」の示し方（どの位置に示し、どのとき推奨にするか）は変えない。そのうえで、Codex が見ていない変更をローカルの CLI レビューが見たかと、その PR の Fable の部分レビューの記録を、要約に 1 行で示す。** Fable の部分レビューは PR を開く前に 1 回走るだけなので、PR を開いた後の変更は見ていない。要約はそれと分かる形で示す。理由: 人が PR レビューを追加で頼むかを決める材料を、詳細ファイルを開かずに読めるようにするため。ADR: ADR-0050。[ADR-0047](../../dev/adr/0047-runpr-merge-question.md) の決定（要約は 1 項目 1 行、選択肢と推奨の規則）は変わらないので、ADR-0047 は更新しない（要件定義の質問では ADR-0047 の更新と示したが、決定が変わらないので ADR-0050 に記録する）。
    -   採らない案: Escalation の判断が `ask` のときだけ選択肢を示す案。人がレビューを頼む手段が減る。
    -   採らない案: 変えない案。範囲を絞ったことで、人が判断する材料が要る。
-   **`/runplan` では、「先行文書との照合」の基準を、実装が先行文書の決めていない点・先行文書を解釈した点・先行文書と違えた点に限る。** 当たる点がなく、ほかの基準にも当たらなければ `not run` とする。理由: 実装の PR には必ず先行文書があるので、字面どおりに当てはめると、実装の全体が毎回範囲に入るため。承認済みの設計を写した実装（#865）では効果が薄かった。ADR: ADR-0050。
    -   採らない案: Opus のレビューが走る PR では Fable を走らせない案。信頼の境界と技術的な主張は、Opus のレビューのチェックリスト（`_lib/opus-review.md` の「Correctness checklist」と「Weak-model failure checklist」）の役目と違う。
    -   採らない案: 字面どおりに当てはめる案。上の理由で採らない。
-   **簡易な進め方の 3 文書の PR では、3 文書をまとめて 1 回だけ走らせる。** 「先行文書との照合」には、3 文書どうしの食い違いと、既存の ADR との照合を含める。理由: 3 文書は 1 本の PR で 1 回のローカルの CLI レビューを受けるので、それに揃えるため。文書ごとに走らせると、費用が 3 倍になる。ADR: ADR-0050。
-   **Fable の部分レビューの効果を後から測れるように、指摘ごとの記録と 1 回ごとの費用を、PR の説明に決まった形で残す。** 指摘ごとに残すのは、場所・範囲に入れた基準・ファイルの種類・重大度・ローカルの CLI レビューが同じ問題を挙げたか・扱いである（AC-43、AC-44）。直した指摘も残す。記録を使って効果を測り、範囲の基準や指示を改良する仕組み（PR を開いた後の指摘の分類と集計）は、[#936](https://github.com/isseis/yt2column/issues/936) で扱う（2.3 節）。理由: 範囲の基準やレビューさせるファイルの種類を後から見直すには、どの基準のどの種類のファイルで、ほかが見つけなかった指摘が出たかが要るため。記録の形は本タスクで決めるので、後から項目を足すと、記録を読む手順を 2 回変えることになる。PR の説明に置くのは、`/mergepr` が squash でマージしてブランチを消すので、ブランチのコミットメッセージの行は後から集めにくいためである。比べる相手はローカルの CLI レビューとする。同じ commit を並列に見るので、その場で重なりを判定できる。Codex の最初の PR レビューは、Fable の指摘を直した後のコードしか見ないので、比べる相手にならない。ADR: ADR-0050。
    -   採らない案: 却下・`deferred`・`unclear` の指摘だけを残す（AC-29 のまま）案。当たった指摘が分からず、効果を測れない。
    -   採らない案: 記録をブランチのコミットメッセージにだけ残す案。上の理由で、マージの後に集めにくい。
    -   採らない案: マージの質問で、人に指摘の当否を尋ねる案。人の手間が増える。PR を開いた後の指摘による分類（#936）で代える。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   タスクのコマンドが PR を開く前に、Fable の部分レビューを、範囲を絞って行う。指摘の修正が Codex の最初の PR レビューに見られるようにする。
-   指摘の誤った却下を減らす。
-   Codex の PR 再レビューを、ローカルのレビューで代われない変更に限って自動で頼み、割り当てを節約する。
-   Fable の部分レビューの効果を後から測れる記録を残す。

### 2.2. スコープ (In Scope)

-   Fable の部分レビューの共通の手順を `.claude/commands/_lib/` に追加する。
-   `mkreq.md`・`mkarch.md`・`mkplan.md`・`mkplan2.md`・`runplan.md`・`_lib/task-pr-handoff.md`・`_lib/local-cli-review.md`・`_lib/simple-process.md` を、Fable の部分レビューを行う形に変える（変える必要のあるものに限る）。
-   `_lib/pr-review-escalation.md` と `runpr.md` の、Codex の PR 再レビューを自動で頼む条件と、マージの質問の要約を変える。
-   ADR-0050 を作り、ADR-0013 を更新する。
-   `CLAUDE.md` のコマンドの説明を、変わった手順に合わせる。`docs/dev/guides/` の下のガイドのうちレビューの手順を述べるものがあれば、それも合わせる（どのガイドが当たるかは設計で洗い出す。design_handoff.md H-09）。
-   `_lib/local-cli-review.md` のトリアージの規則（AC-21、AC-22）は、その呼び出し元のすべて（`fixpr.md` Phase 4.5 を含む）に効く。`fixpr.md` そのものは、変える必要がなければ編集しない。

### 2.3. スコープ外 (Out of Scope)

-   **Codex の最初の PR レビュー（PR の作成時の 1 回）の廃止。** 理由: issue で範囲の外とした。
-   **`/fixpr` の手順への Fable の組み込み。** 理由: issue で範囲の外とした。`/fixpr` が PR のスレッドを却下するときの規則も変えない（1 節「要件定義の際に決めたこと」）。
-   **`/runpr` が単独の変更のために PR を作るとき（`runpr.md` step 1）の Fable の部分レビュー。** 理由: issue の挙げたコマンドはタスクのコマンドで、単独の変更はタスクの PR ではない。
-   **`/runpr` の「通常の進め方へ戻す」（3 文書の PR を要件定義書だけの PR に作り直す。`runpr.md` step 4）での Fable の部分レビュー。** 理由: 戻した PR は、3 文書の PR として Fable の部分レビューを受けた内容から文書を減らすだけで、新しい内容を書かないため。
-   **`/weakreview` への Fable の組み込み。** 理由: issue の範囲にない。
-   **OpenCode から Fable を呼べるようにすること。** 理由: 1 節「要件定義の際に決めたこと」のとおり、`not run` と記録する。
-   **Opus のレビュー（`_lib/opus-review.md`）の範囲・条件・記録の変更。** 理由: issue の範囲にない。Fable の部分レビューとの順序と重なりの避け方は設計で決める（design_handoff.md H-03）。ただし、Fable の指摘の修正の commit は、Opus のレビューの範囲に入れる（AC-06）。
-   **Fable の部分レビューの効果の分類と集計。** PR を開いた後に出た指摘を Fable の範囲と突き合わせる分類、却下した指摘が後に挙がった場合の記録、記録を集計するスクリプトを含む。理由: 記録が溜まってから作れば足りるため。[#936](https://github.com/isseis/yt2column/issues/936) で扱う。本タスクは、その材料となる記録（AC-43、AC-44）だけを残す。
-   **chief（`internal/chief`）の変更。** 理由: chief は、コミットメッセージの記録の行を読まない（`internal/chief` の Go のファイルに、ローカルの CLI レビューと Opus のレビューの記録の行を読むコードはない）。記録の行の形を決めるときに、改めて確かめる（design_handoff.md H-04）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: Fable の部分レビューを行うコマンドと時機

タスクの PR を開くコマンドは、PR を開く前に Fable の部分レビューを行う。対象は、タスク文書の PR を開くコマンド（`/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2`）と、実装の PR を開く `/runplan` である。

**Acceptance Criteria**:
- **AC-01**: `/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2` は、PR を作る前に、Fable の部分レビューを 1 回行うか、`not run` とその理由を記録する。Fable の部分レビューを行うのは、セルフレビュー（`/mkreq` の簡易な進め方では「Reviewing the three documents」）と `japrose` の修正をコミットした後である。
- **AC-02**: タスク文書の PR では、Fable の部分レビューとブランチ全体のローカルの CLI レビュー（`task-pr-handoff.md` Part B step 1）を並列に走らせる。両方の結果がそろってから、トリアージ（F-004）に進む。
- **AC-03**: 簡易な進め方の 3 文書の PR では、Fable の部分レビューを、3 文書をまとめて 1 回だけ行う。
- **AC-04**: `/runplan` は、1 つの PR につき、PR を開く前に Fable の部分レビューを 1 回行うか、`not run` とその理由を記録する。phase group ごとには行わない。範囲は、その PR のすべての commit（`origin/main` との merge-base から HEAD まで）から選ぶ。AC-07 で記録が足りないときに限り、記録の後の commit を対象にもう 1 回行う。
- **AC-05**: `/runplan` では、Fable の部分レビューを、PR を開く前の最後の phase group のローカルの CLI レビュー（step 7.7）と並列に走らせる。両方の結果がそろってから、トリアージ（F-004）に進む。
- **AC-06**: `/runplan` が PR のチェックポイントに来たときに、その PR の有効な記録（AC-07）がなければ、Fable の部分レビューを単独で行う（単独の経路）。単独の経路では、次のとおりにする。
  -   範囲は、有効な記録がないときは PR のすべての commit から、記録の後に足りない commit があるときはその commit から選ぶ。
  -   Fable の指摘のトリアージは F-004 に従う。Fable の指摘を直したときは、その直しの commit をローカルの CLI レビューにかける（直しの前の HEAD を BASE とする）。そのレビューが見られなかったとき（試行の結果が `none`）は、直しの範囲を `Local CLI review: not run` の行で記録する。
  -   単独の経路とその直しは、Opus のレビューを行うかの判断（`runplan.md`「Before the PR」の B2）より前に済ませる。直しの commit が Opus のレビューの範囲に入るようにするためである。B1（ブランチのレビュー）との順序は設計で決める（design_handoff.md H-03）。
- **AC-07**: Fable の部分レビューの記録（AC-28 の `run` か `not run`）は、Fable が見た範囲の後の commit が、すべて次のどれかであるときに限り、その PR の有効な記録とする。
  -   除外できる commit（`_lib/opus-review.md` の「Excludable commit」）
  -   同じ実行のトリアージとその確かめ（AC-06、AC-20〜AC-22）で作った直しの commit
  -   同じ PR のチェックポイントの実行が、step 5a から PR を作るまで（`task-pr-handoff.md` Part B step 2 を含む）に作った commit。具体的には次のとおりである。
      -   green gate を通すための直し
      -   終わりの確かめの直し
      -   「Before the PR」の B1〜B4 の commit（ブランチのレビューの直し、Opus のレビューの直し、diff 記録の再確認の commit）
      -   Part B step 2 の直し

  Fable が見た範囲は、最初の実行では、Fable を呼んだときの merge-base から HEAD までである。単独の経路で足りない commit だけを見た実行では、前の有効な記録の Fable が見た範囲の終わりから、Fable を呼んだときの HEAD までである。`not run` の記録では、Fable を呼ぶはずだった時点の範囲を同じ規則で決める。

  そうでない commit（後の phase group の実装や、ほかのセッションの commit）があるときは、その commit について AC-06 の単独の経路で行う。これらの commit をどう見分けるかは、設計で決める（design_handoff.md H-05）。
- **AC-08**: その PR の有効な記録（AC-07）がブランチにない間は、`/runplan` は PR を開かない。Opus のレビューの直しなど、AC-07 が挙げる commit は、記録を無効にしないので、Fable の部分レビューをもう一度は行わせない。
- **AC-09**: タスク文書のコマンドが、Fable の部分レビューの記録を残す前に止まったとき（並列のローカルの CLI レビューが `stop` になったときなど）、Fable の結果は使わず、何も記録しない。やり直した実行は、Fable の部分レビューをもう一度行う。有効な記録（AC-07 と同じ規則）がブランチにあれば、もう一度は行わない。
- **AC-10**: Fable のサブエージェントは、作業ツリー・index・HEAD・ref を変えない。push、GitHub への書き込み、ほかの pane への入力もしない。実験（技術的な主張の確かめ）は、作業ツリーの外（スクラッチパッドなど）でだけ行う。ファイルを読むコマンドと、作業ツリーの外での実験のコマンドは実行してよい。この制約は、並列に走るローカルの CLI レビュー（特に `codexreview`。作業ツリーが変わると `state_changed` で止まる。`_lib/local-cli-review.md:121-124`、`:145`）を止めないためである。

#### F-002: 範囲の基準と選び方

Fable の部分レビューの範囲は、決まった基準に当たる箇所に限る。範囲はセッションが選び、外した箇所とその理由を残す。

**Acceptance Criteria**:
- **AC-11**: 範囲の基準は次の 4 つで、範囲に入れるのは、どれかに当たる箇所だけである。
  1. 信頼の境界: 秘密、送信（マシンの外へのデータの送信、GitHub への投稿、ほかのエージェントの pane への入力）、削除、pane の操作、不可逆な副作用
  2. 先行文書との照合: 承認済みの要件書・設計書・ADR との照合
  3. 外部の振る舞いについての技術的な主張
  4. 人に問わずに決めたこと
- **AC-12**: `/runplan` では、基準 2 に当たるのは、実装が先行文書の決めていない点・先行文書を解釈した点・先行文書と違えた点だけである。先行文書の決めたとおりに写した箇所は、基準 2 には当たらない。
- **AC-13**: 3 文書の PR では、基準 2 に、3 文書どうしの食い違いと、既存の ADR との照合を含める。
- **AC-14**: セッションは、範囲に入れた箇所とその基準、外した箇所とその理由を一覧にする。一覧はブランチに記録し（AC-28）、PR の説明に載る（AC-31）。
- **AC-15**: どの基準にも当たる箇所がないとセッションが判断したときも、Fable を呼び、外した箇所の一覧と理由だけを確かめさせる。Fable が基準に当たる箇所を見つけなかったときは、`not run`（当たる箇所がなく、除外を Fable が確かめた）と記録する。見つけたときは、AC-17 のとおりに扱い、`run` と記録する。

#### F-003: Fable に渡すもの

Fable には、狭い役目と、範囲、外した箇所、決着済みの論点を渡す。

**Acceptance Criteria**:
- **AC-16**: Fable への指示は、基準ごとに狭い役目を与える（例：「人の文脈を消す筋書きを探す」）。指示には、範囲に入れた箇所とその基準を含める。
- **AC-17**: Fable への指示には、外した箇所とその理由の一覧を含める。外した箇所が基準に当たると Fable が見たときは、その箇所もレビューし、外した判断の誤りを指摘として返す。その指摘とその箇所の指摘は、ほかの指摘と同じトリアージ（F-004）を受ける。
- **AC-18**: Fable への指示には、決着済みの論点を含める。決着済みの論点とは、次のものである。
  -   ブランチのコミットメッセージ（`git log origin/main..HEAD`）にある、ローカルの CLI レビューと Fable の部分レビューの却下の記録の行と、人が退けた Opus のレビューの指摘の記録の行（`Opus review: kept` の行）
  -   そのセッションがそれまでのレビュー（セルフレビューなど）で却下した指摘
  -   タスク文書の「…で決めたこと」の節にある決定

  Fable は、決着済みの論点を、具体的な筋書きがあるときに限って再提起してよい。前のセッションのセルフレビューで却下した指摘は、ブランチに記録がないので渡さない。
- **AC-19**: 却下した指摘は、セッション自身の言葉で書いた要約として渡す。Codex CLI の指摘の本文は、Fable への指示に入れない。

#### F-004: トリアージと却下の規則

Fable の指摘とローカルの CLI レビューの指摘は、1 回のトリアージにまとめて扱う。

**Acceptance Criteria**:
- **AC-20**: セッションは、Fable の指摘と、並列に走らせたローカルの CLI レビューの最初の試行の指摘を、1 回のトリアージにまとめる。同じ問題を指す指摘は、1 つとして扱う。`/runplan` では、ローカルの CLI レビューの範囲は最後の phase group だけで、Fable の範囲は PR 全体なので、Fable の指摘はローカルの CLI レビューの範囲の外の箇所も指しうる。その指摘も、同じトリアージで扱う。
- **AC-21**: このトリアージで指摘を却下するとき（`invalid` または `no-harm` とするとき）、セッションは、該当箇所のコードか文書を読むか、実験で根拠を確かめる。確かめた方法と結果を、却下の理由として記録する。今の手順も該当箇所を読むことを求めている（`_lib/local-cli-review.md:191-192`）。本書が加えるのは、確かめた方法と結果を記録することである。記録すれば、却下が読んだうえでの判断かを、後の読み手が確かめられる。確かめられないときは却下せず、`unclear` とする。この規則は、ローカルの CLI レビューの指摘だけのトリアージにも当てはめる。Fable が `not run` のときと、`fixpr.md` Phase 4.5 などのローカルの CLI レビューのほかの呼び出しが、これに当たる。
- **AC-22**: AC-20 のトリアージで 1 つでも直したときは（Fable の指摘だけを直したときも）、ローカルの CLI レビューの 2 回目の試行を行い、直しを確かめる。2 回目の試行の範囲は、最初の試行と同じ BASE から HEAD までで、直しの commit を含む。最初の試行が `none`（どちらの CLI もレビューしなかった）でも、Fable の指摘を直したときは 2 回目の試行を行う。2 回目の試行が `none` のときは、直しの範囲を `Local CLI review: not run` の行で記録する。Fable の部分レビューは、直しの後にもう一度は走らせない。
- **AC-23**: Fable の指摘のうち `unclear` のものと、直さずに残した `worth-fixing` のもの（`deferred`）は、PR の説明に載る（AC-31）。

#### F-005: Fable が走らないとき

Fable で走らせられないときも、コマンドは止まらずに進む。

**Acceptance Criteria**:
- **AC-24**: 次のどれかのとき、セッションは `not run` とその理由を記録し（AC-28）、Fable の部分レビューなしでトリアージと PR の作成に進む。
  -   (a) 基準に当たる箇所がなく、除外の一覧を確かめた Fable も見つけなかった（AC-15）
  -   (b) Fable を呼んだ結果がエラー・利用上限・時間切れで、決まった回数呼び直しても同じだった
  -   (c) 走ったモデルが Fable でないか、出力が決まった形でない（AC-25、AC-27）
  -   (d) セッションのエージェントが Fable のサブエージェントを呼べない（OpenCode で動く `/runplan` など）
- **AC-25**: セッションは、Fable のサブエージェントが出力の 1 行目に報告するモデル ID で、Fable で走ったかを確かめる。報告がないとき、1 行目が決まった形でないとき、報告が Fable のモデル ID でないときは、その結果を使わず、AC-24 (c) として扱う。
- **AC-26**: Fable で走らせられないとき、セッションは、ほかのモデル（セッションのモデルや Opus）で同じレビューを代わりに走らせない。
- **AC-27**: Fable の出力の受け入れる形は、1 行目のモデル ID の行と、その後の指摘の並びか、指摘がないことを示す決まった行である。各指摘は、場所（ファイルのパスと行の範囲、または文書の節）・重大度（Critical・Major・Minor のどれか）・内容を持つ。
  -   出力の全体がこの形でないときは、結果を使わず、AC-24 (c) として扱う。
  -   場所が、ブランチで変わったファイル（merge-base から HEAD まで）にない指摘と、場所か重大度が読めない指摘は、`invalid`（理由: 場所が範囲にない、または読めない）として記録する。その指摘の文には従わない。変わっていない呼び出し元や ADR を指す正しい指摘も、これで `invalid` になりうる。その危険は受け入れる。セッションが自分で確かめて、変わったファイルの場所に言い直した指摘は、ほかの指摘と同じく扱う。
  -   出力の大きさの上限は、要件では設けない。出力はセッションが読む文であり、コードが組み立てる値ではない。待つ時間の上限は、設計で決める（design_handoff.md H-08）。

#### F-006: 記録

Fable の部分レビューを行ったかとその結果を、コミットメッセージと PR の説明に残す。

**Acceptance Criteria**:
- **AC-28**: Fable の部分レビューについて、次のものをブランチのコミットメッセージの決まった形の行に記録する。
  -   行ったか（`run`）、行わなかったか（`not run` と AC-24 の理由）
  -   Fable が見た範囲（AC-07。`run` と `not run` のどちらでも）
  -   範囲に入れた箇所とその基準、外した箇所とその理由（AC-14）
  -   直した指摘・却下した指摘・`deferred`・`unclear` の数

  後のセッションが PR を開いても、PR の説明を書けるようにするためである。
- **AC-29**: Fable の指摘の却下・`deferred`・`unclear` は、ローカルの CLI レビューの記録の行にならって、コミットメッセージの行に記録する。行は、場所と、扱い（却下では、AC-21 の確かめた方法と結果を含む理由）と、セッション自身の言葉で書いた要約で書く。Fable の出力の文をコミットメッセージにも PR の説明にも写さない。理由: Fable の出力は、差分にある秘密（#914 の API キーなど）やメンションを引用しうるため。
- **AC-30**: AC-28・AC-29・AC-43 の行を含むコミットメッセージは、コミットの前にメンションの確認を通す。確認に通らないときの扱いは、`_lib/local-cli-review.md` step 7 の「Mention check」と同じである。要約を除いてもう一度確かめ、それでも通らなければ、コミットせずに止まる。
- **AC-31**: PR の説明（日本語）には、ブランチの記録（AC-28、AC-29）から、次のことを載せる。
  -   Fable の部分レビューの記録ごとに、実施（`run`／`not run` とその理由）と Fable が見た範囲（AC-07）
  -   範囲に入れた箇所とその基準、外した箇所とその理由
  -   直した指摘の数、却下した指摘（理由とともに）、`deferred` の指摘、`unclear` の指摘
- **AC-32**: AC-28・AC-29・AC-43 の行は、既存の記録の行を読む手順の読み方を変えない。既存の手順とは、`_lib/local-cli-review.md`「Reading the record lines」、`_lib/opus-review.md`「Record lines」と `_lib/opus-review-decision.sh`、`internal/chief` である。AC-28・AC-29・AC-43 の行は、これらの手順が読む既存の行の形と一致しない。また、記録の行だけを持つ空のコミットは、Opus のレビューの判断で、除外できるコミットとして扱われる（`_lib/opus-review.md:102-106`）。新しい行を読むのは、`task-pr-handoff.md` Part B step 3（AC-31）、`runplan.md`（AC-07）、`runpr.md`（AC-39）である。
- **AC-33**: AC-28 の行がないブランチの PR では、`/runpr` のマージの質問の要約は、Fable の部分レビューの記録がないことを示す（AC-39）。
- **AC-43**: Fable の指摘のすべて（直した指摘を含む）について、次の項目を記録する。値は、セッションが決まった値の中から選ぶ。Fable の出力の文は入れない（AC-29）。
  -   場所（ファイルと行、または文書の節）
  -   範囲に入れた基準（AC-11 の 4 つの基準のどれか、または外した判断の誤り（AC-15））
  -   ファイルの種類（たとえば、コマンドの定義、タスク文書、ADR、Go のコード、ブラウザー拡張機能のコード。値の一覧は設計で決める）
  -   重大度（Critical／Major／Minor）
  -   ローカルの CLI レビューが同じ問題を挙げたか（あり／なし／比べられない）。「あり」は、AC-20 のトリアージで重複として 1 つにしたときである。指摘の場所を、そのトリアージのローカルの CLI レビューの範囲が含まないとき（`/runplan` で、前の phase group の箇所を指すときなど）は、「比べられない」とする。前の phase group のローカルの CLI レビューが同じ問題を挙げて直していても、その記録は残らず、「なし」と区別できないためである。
  -   扱い（直した／却下／`deferred`／`unclear`／`invalid`）

  AC-27 で `invalid` とした指摘のうち、場所か重大度が読めないものは、読めない項目を「読めない」と記録し、値を作らない。場所が読めないときは、範囲に入れた基準とファイルの種類も「読めない」とする。

  あわせて、Fable の部分レビューの 1 回ごとに、かかった時間と、取れるときは出力トークン数を記録する。理由: 範囲の基準とファイルの種類ごとに、ほかが見つけなかった指摘の数と費用を後から比べるため（#936）。
- **AC-44**: PR の説明には、AC-31 のものに加えて、AC-43 の記録を、決まった形で載せる。形は、マージ済みの PR の説明から、スクリプトが Fable の部分レビューの記録ごと・指摘ごとに項目を読み取れるものとする。理由: `/mergepr` は squash でマージしてブランチを消すので、マージの後はブランチのコミットメッセージより PR の説明の方が読みやすいため。

#### F-007: Codex の PR 再レビューを自動で頼む条件

`/runpr` が Codex の PR 再レビューを自動で頼むのは、信頼の境界・セキュリティ・耐久性に触れる変更だけにする。

**Acceptance Criteria**:
- **AC-34**: `_lib/pr-review-escalation.md` の判断は、Codex の最後の PR レビューの後の変更（LAST_REVIEWED..HEAD）が信頼の境界・セキュリティ・耐久性に触れるときに `request` を返す。信頼の境界には、開発用のツールのもの（AC-11 の基準 1 に挙げたもの）を含める。
- **AC-35**: 変更が AC-34 に当たらず、今の基準のほかの 4 つ（振る舞いや契約の変更、モジュールの境界をまたぐ変更、要件や設計の決定に触れる変更、新しい仕組み）のどれかに当たるときは、次のとおり返す。
  -   LAST_REVIEWED..HEAD の判断の対象の commit のすべてを、ローカルの CLI レビューが見たとブランチの記録から分かるとき: `skip`
  -   そうでないとき: `ask`

  判断の対象の commit は、LAST_REVIEWED..HEAD のうち `origin/main` から届かない commit である（`main` から取り込んだ commit は、それぞれの PR でレビューされている）。「見たと分かる」とは、試行の結果が `coderabbit` か `codex` だったローカルの CLI レビューの範囲に、その commit が入ると記録から分かることである。次の commit は、見たと分からない。
  -   `Local CLI review: not run` の行と、ブランチ全体を表す `CodeRabbit local review: not run` の行（`_lib/local-cli-review.md`「Reading the record lines」）が示す範囲の commit
  -   どのレビューの記録にも入らない commit（人が直接 push した commit、ほかのセッションの commit など）
  -   merge commit
  -   未レビューの範囲を報告にだけ残し、ブランチに記録しない手順（`fixpr.md` Phase 4.5 の Final report など）の範囲の commit。ただし、設計でその範囲をブランチに記録するようにしたときは除く
- **AC-36**: AC-34 にも AC-35 にも当たらない変更では、今と同じく `skip` を返す。
- **AC-37**: `_lib/pr-review-escalation.md` の diff は、次のものに限られる。
  -   「Criteria」の節の、`request`・`skip`・`ask` を返す条件の部分
  -   AC-35 の判断に要る入力

  「Procedure」の step 1 の判断（LAST_REVIEWED が HEAD の祖先でないときの `ask` と、同じときの `skip`）、返す JSON の形、サブエージェントへの「迷うときは `ask`」の指示は変わらない。
- **AC-38**: `runpr.md` の Escalation の扱い（`request` は PR ごとに 1 回まで自動で頼むこと、`ask` はマージの質問に持ち越すこと）は変わらない。

#### F-008: マージの質問の要約

`/runpr` のマージの質問の要約に、Codex が見ていない変更をローカルの CLI レビューが見たかと、その PR の Fable の部分レビューの記録を示す。

**Acceptance Criteria**:
- **AC-39**: Codex が見ていない変更があるとき（LAST_REVIEWED が head の祖先で head と異なるか、LAST_REVIEWED がないとき）、マージの質問の要約は、次の 2 つを 1 行で示す。
  -   その変更のすべてをローカルの CLI レビューが見たか（AC-35 と同じ判断）
  -   その PR の Fable の部分レビューの記録（`run`／`not run` と短い理由の符号／記録なし）。PR を開く前の記録であることが分かる形で示す。
- **AC-40**: `runpr.md` のマージの質問の diff は、次のものに限られる。
  -   要約の行の追加と、その行の値の読み方
  -   要約の行の数の上限の記述

  選択肢の表（label、description、示す条件、推奨）、問いの文、詳細ファイルの扱いは変わらない。

#### F-009: 文書の更新

変わった手順を、エージェントが読む説明と ADR に反映する。

**Acceptance Criteria**:
- **AC-41**: `CLAUDE.md` の「Claude Commands」の、タスクの PR の流れとレビューの説明は、Fable の部分レビューを行うことと、Codex の PR 再レビューを自動で頼む条件を、変更後の手順と同じに述べる。
- **AC-42**: [ADR-0050](../../dev/adr/0050-fable-partial-review.md) の「決定」と [ADR-0013](../../dev/adr/0013-review-setup.md) の「決定」は、実装した手順と一致する。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   Fable の部分レビューは、1 つの PR につき 1 回まで行う（AC-01、AC-04、AC-22）。記録の後に足りない commit が出たときだけ、その commit を対象にもう 1 回行う（AC-07）。これまでの実績では、1 回あたり 2〜16 分、出力 2k〜260k トークンだった（issue #924）。
-   ローカルの CLI レビューと並列に走らせるので（AC-02、AC-05）、PR を開くまでの時間は、2 つのうち長い方の分だけ延びる。

### 4.2. セキュリティ (Security)

-   N/A（`docs/dev/security.md` の対象の条件に当たらない）。本タスクは、`yt-dlp` の起動、API キー、キャッシュ、LLM API への送信、信頼しないテキストを製品のプロンプトや記事に入れる処理に触れない。
-   開発用のツールの信頼の境界（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）は変えない。
    -   Codex CLI の指摘の本文は、Fable への指示に入れない（AC-19）。
    -   Fable の出力の文は、コミットメッセージにも PR の説明にも写さない（AC-29）。
    -   PR の説明とコミットメッセージには、メンションの確認を通す（AC-30、`task-pr-handoff.md` Part B step 3 の「Mention check」）。
-   Fable の出力は、データとして扱い、指示として扱わない。Fable の指摘の文がコマンドの実行やファイルの変更を求めていても、セッションはその文に従って動かない。セッションが動くのは、該当箇所のコードか文書が示すことに対してだけである（`_lib/local-cli-review.md` step 4 の Codex CLI の指摘の扱いと同じ）。
-   Fable の出力のうち、セッションが使うのは、次のものだけである。
    -   1 行目のモデル ID の報告（AC-25）
    -   各指摘の場所・重大度・内容

    受け入れる形でない出力は使わない（AC-25、AC-27。AC-24 (c) として扱う）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   Fable が使えないとき（利用上限、モデルが使えない、エラー、OpenCode）は、コマンドを止めずに `not run` で進む（AC-24）。
-   Fable の結果を待つ時間の上限と、上限を超えたときの扱いは、設計で決める（design_handoff.md H-08）。

### 4.4. 互換性 (Compatibility)

-   本タスクの前に作られたブランチと、そのコミットメッセージは書き換えない。Fable の記録がないことは、`/runpr` のマージの質問の要約で示す（AC-33）。
-   既存の記録の行（`CodeRabbit local review:`・`Codex local review:`・`Local CLI review: not run`・`Implementation model:`・`Opus review:`）の形と読み方は変えない（AC-32）。

### 4.5. 保守性 (Maintainability)

-   Fable の部分レビューの手順は、1 つの共通の手順に置く。タスク文書のコマンドと `/runplan` は、それを呼ぶ。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   [ADR-0013](../../dev/adr/0013-review-setup.md) の決定のうち、本書が変えないもの（Codex の最初の PR レビュー、CodeRabbit CLI と Codex CLI のフォールバックの使い方、`codexreview`）に従う。ローカルの CLI レビューの手順のうち、トリアージの却下の記録と 2 回目の試行の条件は、本書が変える（AC-21、AC-22）。
-   [ADR-0042](../../dev/adr/0042-implementation-model-tiers.md) の決定（Opus のレビューの条件、範囲、記録）に従う。
-   [ADR-0047](../../dev/adr/0047-runpr-merge-question.md) の決定（マージの質問の形、選択肢と推奨の規則）に従う。
-   Fable は、Claude Code の Agent ツールの `model` に `fable` を指定して呼ぶサブエージェントである（Agent ツールの `model` の値の一覧にある）。OpenCode からは呼べない（OpenCode は Claude Code の Agent ツールを持たない）。

## 6. 用語集 (Glossary)

-   **Fable の部分レビュー**: PR を開く前に、Fable のサブエージェントに、F-002 の基準に当たる箇所だけを、基準ごとの狭い役目でレビューさせること。Fable は、Claude のモデルのファミリーの 1 つである。
-   **ローカルの CLI レビュー**: CodeRabbit CLI、またはそれが失敗したときの Codex CLI で行うレビュー（`_lib/local-cli-review.md`）。
-   **Codex の PR レビュー**: GitHub の PR に対する Codex のレビュー。PR の作成時に 1 回自動で行われ、それより後は `/runpr` か利用者が頼んだときだけ行われる（ADR-0013）。
-   **Codex の PR 再レビュー**: PR の作成時の後に追加で頼む Codex の PR レビュー。ADR-0013 の「PR レビューを追加で頼む」と同じものを指す。
-   **Opus のレビュー**: `/runplan` が PR を開く前に行う、正しさのレビューと弱いモデルの失敗のレビュー（`_lib/opus-review.md`、ADR-0042）。
-   **決着済みの論点**: AC-18 で定義する。
-   **phase group**: `/runplan` が一度に実装するフェーズのまとまり（ADR-0042）。
-   用語は `docs/translation_glossary.md` と統一する。
