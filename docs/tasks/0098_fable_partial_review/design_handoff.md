# 設計への引き継ぎ事項（0098_fable_partial_review）

要件定義の際に挙がった、設計（`02_architecture.md`）で決める事項である。`02_architecture.md` は、項目ごとに、とった方法か、当てはまらない理由を記録する。

## H-01: 共通の手順の置き場所と、ほかの手順との分担

**懸念:** Fable の部分レビューは、`_lib/task-pr-handoff.md` Part B step 1 と `runplan.md` step 7.7 の 2 か所から、ローカルの CLI レビューと並列に呼ばれる（AC-02、AC-05）。どちらも同じ手順を使う。

**なぜ重要か:** 置き場所を誤ると、範囲の選び方・記録・トリアージの規則が 2 か所に分かれる。

**候補:**
-   新しい共通の手順（たとえば `_lib/fable-review.md`）に、範囲の選び方・指示・モデルの確かめ・記録を置く。
-   まとめたトリアージ（AC-20〜AC-22）は `_lib/local-cli-review.md` の step 4〜6 に入れる。
-   `task-pr-handoff.md` Part B には、Fable を呼ぶかを決める入力を足す（`runplan.md` は LOCAL_REVIEW を `done` で渡すので、別の入力が要る）。

並列に走らせたときの待ち合わせ方も決める。たとえば、Agent ツールのバックグラウンドの実行と、CLI の実行の終わりをどう待つか。

**関連:** F-001、F-004、AC-01〜AC-06、AC-20〜AC-22。

## H-02: 範囲の基準の具体的な文言と、範囲の一覧の形

**懸念:** AC-11〜AC-15 の基準を、セッションが同じように当てはめられる文言にする必要がある。

**なぜ重要か:** 文言が曖昧だと、書き手のセッションが自分の盲点を外しうる。外した箇所を Fable に渡す形（AC-15、AC-17）が決まっていないと、Fable が外した判断を確かめられない。

**候補:** 基準ごとに、当たる例と当たらない例を置く。範囲の一覧は、箇所（ファイルと行、または文書の節）・基準・理由の表にする。

**関連:** F-002、F-003、AC-11〜AC-19。

## H-03: `/runplan` での Opus のレビューとの順序と、範囲の重なり

**懸念:** `/runplan` は、PR を開く前に Opus のレビュー（`runplan.md`「Before the PR」の B2〜B5）を行う。Fable の部分レビューは、最後の phase group の step 7.7 と並列に走る（AC-05）。

**なぜ重要か:** Fable の修正の commit が Opus のレビューの範囲に入るか、Opus の修正の commit が Fable に見られるかが、順序で決まる。Opus のレビューの直しは、ローカルの CLI レビューにかけ直さない（ADR-0042）。

**候補:** Fable の部分レビューとその修正を step 7.7 の中で済ませ、Opus のレビューの範囲に入れる（単独の経路では B2 より前に済ませる。AC-06）。指示では、Opus のレビューのチェックリスト（正しさ、弱いモデルの失敗）の役目を Fable に重ねて与えない。

単独の経路（AC-06）を B1 の前に置くか、B1 と並列に置くかも決める。

**関連:** F-001、F-002、AC-04〜AC-06、AC-12。

## H-04: 記録の行の形と、記録を読む側への影響

**懸念:** AC-28・AC-29・AC-43 の行の形を決める必要がある。範囲に入れた箇所と外した箇所の一覧（AC-28）は長くなりうるので、コミットメッセージに収める形も決める。

**なぜ重要か:** 次の手順が、既存の記録の行を読む。
-   `_lib/local-cli-review.md`「Reading the record lines」
-   `_lib/opus-review.md`「Record lines」と `_lib/opus-review-decision.sh`
-   `task-pr-handoff.md` Part B step 3

新しい行がこれらの読み方を変えてはならない（AC-32）。

**候補:**
-   `Fable review: run <START12>..<END12>`・`Fable review: not run (<reason>)`・`Fable review: <path>:<start>-<end> <handling>: <summary>` のように、既存の行と前置きの違う行にする。
-   `_lib/opus-review-decision.sh` の除外できるコミットの判断で、記録の行だけの空のコミットが除外されることを確かめる。
-   `internal/chief` がコミットメッセージを読まないことを、改めて確かめる。

**関連:** F-006、AC-28〜AC-33、AC-43。

## H-05: 複数のセッションにまたがる PR と、最後の phase group の見分け方

**懸念:** `/runplan` は phase group ごとに走りうる。step 7.7 の時点では、その phase group が PR を開く前の最後のものかを知る必要がある（AC-05）。最後と見たのに commit が足された場合は、AC-07 の規則で記録が足りなくなる。

**なぜ重要か:** 最後の phase group を OpenCode で実装し、PR のチェックポイントを Claude Code が引き継ぐ場合（`_context.md` の `runplan-takeover` の行）がある。この場合、step 7.7 と並列に走らせる時機がない。

**候補:**
-   step 4 で次の未完了の項目が PR のチェックポイントかを見て、最後の phase group を見分ける。
-   有効な記録（AC-07）がないまま 5a に来たときは、AC-06 の単独の経路で走らせる。
-   AC-07 が記録を無効にしないとする commit（同じ実行の直し、step 5a から Part B step 2 までの commit）を、記録の行や commit の範囲でどう見分けるかを決める。

**関連:** F-001、AC-04〜AC-08、AC-24 (d)。

## H-06: Fable で走ったことの確かめ方

**懸念:** AC-25 は、サブエージェントが報告するモデル ID で確かめることを求める。AC-27 は、出力の受け入れる形を求める。

**なぜ重要か:** 確かめ方が Opus のレビューと違う形になると、規則が 2 つになる。

**候補:**
-   Opus のレビュー（`_lib/opus-review.md`「Running on Opus」）にならい、出力の 1 行目を `Model: claude-fable-<...>` の形として、`grep -Eqx` で確かめる。
-   Fable の ID の判定の規則（前置き `claude-fable-`）を 1 か所に置く。
-   呼び出しが失敗したときに呼び直す回数を決める（AC-24 (b)）。
-   `fork` のサブエージェントは `model` の指定を無視する（`_lib/opus-review.md`「Running on Opus」）。Fable を呼ぶときも `fork` を使わない。
-   AC-10 の制限（作業ツリーを変えない）を、指示だけで守らせるか、サブエージェントの種類（読み取りの道具だけを持つもの）でも守らせるかを決める。

**関連:** F-001、F-005、AC-10、AC-24〜AC-27。

## H-07: Escalation の判断の入力と、ローカルの CLI レビューが見たかの判定

**懸念:** AC-35 は、LAST_REVIEWED..HEAD の判断の対象の commit を、ローカルの CLI レビューが見たとブランチの記録から分かるかで、`skip` と `ask` を分ける。今の記録は、見なかった範囲（`not run` の行）と指摘しか残さず、見た範囲を残さない。`fixpr.md` Phase 4.5 は、見なかった範囲を Final report にだけ残すことがある。

**なぜ重要か:** 判定を Escalation のサブエージェントの解釈に任せると、見ていない範囲を見落としうる。

**候補:**
-   ローカルの CLI レビューが見た範囲を、ブランチに記録する行を足す（`fixpr.md` Phase 4.5 の範囲も含める）。
-   `runpr.md` が、見た範囲の記録と LAST_REVIEWED..HEAD の判断の対象の commit を決まったコマンドで突き合わせ、FINDINGS とともにサブエージェントに渡す。
-   サブエージェントは、信頼の境界・セキュリティ・耐久性に当たるか（AC-34）と、ほかの基準に当たるかだけを判断する。

見た範囲の記録を足さないと、AC-35 はいつも `ask` になり、`skip` の経路が働かない。あわせて、最初の試行が `none` で 2 回目の試行がレビューしたとき、BASE..HEAD1 を未レビューの範囲として記録しないよう、`_lib/local-cli-review.md` の Terms を合わせる（AC-22）。

**関連:** F-004、F-007、F-008、AC-22、AC-34〜AC-39。

## H-08: Fable の結果を待つ時間の上限と費用の目安

**懸念:** これまでの実績では、1 回あたり 2〜16 分、出力 2k〜260k トークンだった（issue #924）。

**なぜ重要か:** 待つ時間に上限がないと、Fable が返らないときに PR を開けない。

**候補:** 上限を決め、超えたら AC-24 (b) と同じく `not run`（理由: 時間切れ）として進む。上限の値は実績から決める。

**関連:** F-005、4.1 節、4.3 節。

## H-09: 変わる文書を読む既存のテスト

**懸念:** 次のテストが、`runpr.md`・`task-pr-handoff.md`・`fixpr.md` の文面とコマンドを読む。
-   `TestRunprDocContract`
-   `TestHandoffListingPrintsNoBody`
-   `TestFixprPhase6CountFilter`
-   `cmd/fixprguard` と `cmd/codexreview` の文書の確かめ

**なぜ重要か:** 本タスクで文書を変えると、これらのテストが失敗しうる。

**候補:** 変える節を読むテストを設計の時点で洗い出す。値と構造の確かめだけを直し、文の意味を確かめるテストは足さない（`CLAUDE.md` の「Testing Strategy」、ADR-0016）。

**関連:** F-006〜F-009。

## H-10: 効果を測るための記録の形と、費用の取り方

**懸念:** AC-43 の項目の値の一覧（とくにファイルの種類）と、AC-44 の PR の説明の決まった形を決める必要がある。後の集計（#936）は、マージ済みの PR の説明からこの形を読む。

**なぜ重要か:** 値の一覧が曖昧だと、セッションごとに同じものを違う値で記録し、基準やファイルの種類ごとに比べられない。PR の説明の形が人の読む部分と混ざると、スクリプトが読めないか、人が読みにくくなる。

**候補:**
-   ファイルの種類は、パスの前置き（`.claude/commands/`・`docs/tasks/`・`docs/dev/adr/`・`internal/`・`cmd/`・`extension/` など）から決める表にする。指摘の場所から機械的に決まるので、セッションの判断に頼らない。
-   PR の説明では、人の読む節の後に、決まった見出しの下に 1 指摘 1 行の表を置く（`<details>` で畳むことも検討する）。
-   かかった時間は、Agent ツールの呼び出しの前後の時刻から取る。出力トークン数は、Agent ツールの結果が報告するときだけ取り、取れないときは「不明」と記録する。
-   ローカルの CLI レビューと重なったかは、AC-20 のトリアージで重複として除いたかをそのまま使う。

**関連:** F-006、AC-20、AC-43、AC-44、#936。
