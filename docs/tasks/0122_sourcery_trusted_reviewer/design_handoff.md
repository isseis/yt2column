# 設計への申し送り（0122）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: `_context.md` での複数 PR レビュアーと依頼文面の表の表現・文書ガード更新

**懸念:** 現在 `.claude/commands/_context.md:299-300` は、単一の `Awaited PR reviewer`（`coderabbitai`）と単一の `PR review request`（`@coderabbitai review`）を 1 行ずつ持っている。`cmd/yt2column/fixpr_docs_test.go:63,1066-1096,1155-1228` と `cmd/yt2column/review_mention_docs_test.go:88-137` は、期待一覧（`wantReviewers`）、壊した写しの表（`TestContextReviewerRowsMalformed`）、およびこれら 2 行の形と出現回数（ちょうど 1 回）を厳密に検査している。F-002・F-004（AC-06・AC-09・AC-15）では `coderabbitai` と `sourcery-ai` の 2 つ（さらに Sourcery AI は投稿用 `@sourcery-ai review` と手動認識用 `@sourceryai review`）を 1 か所で定義する必要がある。

**なぜ重要か:** `_context.md` の行名や区切り形式、および `TestMentionsOnlyInAllowedRows`・`TestContextAndCommandsAgree`・`TestContextReviewerRowsMalformed` が許可する行の形を揃えないと、ガードテストとコマンド文書の参照が食い違う。

**候補:**

-   `Awaited PR reviewer`・`PR review request` を複数レビュアー向けの表または対応行（例: レビュアーごとの行、またはペア表記）に改め、コマンド文書はそこからプレースホルダーを組み立てる。
-   `cmd/yt2column/fixpr_docs_test.go` の `wantReviewers` を `coderabbitai` と `sourcery-ai` の 2 つに更新し、`TestContextReviewerRowsMalformed`・`TestMentionsOnlyInAllowedRows`・`TestPostingCommandsInventory` を複数レビュアーと依頼文面に対応させる。

**関連:** F-002、F-003、F-004、AC-06・AC-09・AC-12・AC-15・AC-23

## H-02: `fixprguard review-state` の複数レビュアー・自動の PR レビュー対応の契約設計

**懸念:** 現在の `internal/fixprguard/review_state.go:44-50,655-679` は、GraphQL クエリに `checkName: "CodeRabbit"` を直書きし、分類表（`Finished`・`Review rate limited`・`Review skipped: automatic reviews are disabled`）も CodeRabbit 固定である。また、依頼コメントが 0 件なら CheckRun を読まずに `RequestNone` を返している（`review_state.go:417-421`）。さらに `CLAUDE.md:490-502` の `Declare, don't infer` の例外は、CheckRun について `status`・`conclusion`・`title` の 3 つだけを対象としている。F-004（AC-16〜AC-20）では、Sourcery AI の `Sourcery review` CheckRun（自動実行を含む、待機対象は `head` コミットのみ）、未開始（`QUEUED` で `startedAt == null`）時の 15 分起点と step 4 再読込での再待機抑止、手動依頼コメント認識（`@sourcery-ai review`・`@sourceryai review`）に対応する必要がある。

**なぜ重要か:** Sourcery AI では依頼コメントがなくても自動の PR レビューの CheckRun が走り得るため、現在の「依頼がなければ `none` を即返す」経路のままでは進行中の自動の PR レビューを待てず、自動完了を `markers` に含められない。また、自動実行と手動依頼が近接して走った場合の競合判定（`indeterminate`）、自動スキップ（止めない）対手動スキップ（止める）の区別、および `name` を検査する場合の `CLAUDE.md:490-502` の例外更新を明確にする必要がある。

**候補:**

-   `review-state` にレビュアー種別を宣言する引数（または複数 `--request` とプロファイル切替。`CLAUDE.md` の「Declare, don't infer」に従い文字列内容から推測しない）を設け、CodeRabbit と Sourcery AI をそれぞれ呼び出すか、1 回の呼び出しで両者の状態を返すかを設計で選ぶ。
-   自動の PR レビューの状態（進行中・成功・スキップ・失敗・未認識）と手動依頼の状態を出力 JSON の型で明確に分け、時間切れになった `head`・CheckRun で step 4 の再読込が待機ループに戻らない仕組みを設計する。
-   F-001 の観測記録（`observations.md`）で確定した `output.title`・`conclusion`・`checkName` のみを分類表に組み込み、`name` をコードで照合する場合は `CLAUDE.md:490-502` の例外範囲を更新する（AC-29）。

**関連:** F-001、F-004、F-005、AC-05・AC-16〜AC-20・AC-29

## H-03: `fixprguard` の `Protocol` 番号の引き上げと PR 分割

**懸念:** 現在 `internal/fixprguard/types.go:21` の `Protocol` は `8` である。F-002（`_context.md` の一覧追加）は既存バイナリでそのまま動く。F-003（`RejectedMentions` の追加）は受け付ける入力を狭めるだけの変更で `fixprguard_guide.md:670` の例外に当たりうる。一方、F-004 で `review-state` の引数や出力 JSON の契約が変わる場合、`fixprguard_guide.md:663` と `CLAUDE.md`「Protocol numbers」に従い `Protocol` を `main` の値 + 1 へ引き上げる必要がある。

**なぜ重要か:** `Protocol` を上げると、マージ前後の `make install-fixprguard` の再インストールと他ブランチへの `main` 取り込みが必要になる。また、`Protocol` を上げる PR と上げない PR（F-002・F-003 の先行導入など）をどう分けるかで、並行作業への影響が変わる。

**候補:**

-   F-002・F-003（自動レビュアーの一覧と拒否するメンション・ガイド除外）と、F-004（`review-state` 拡張と `Protocol` の `main` の値 + 1 引き上げ）を別の実装 PR に分けるか、一括にするかを実装計画と合わせて設計する。
-   `Protocol` を上げる PR では、`CLAUDE.md`「Protocol numbers」に従い、コマンド文書・ガイド・テストのすべてを同一 PR で更新する。

**関連:** F-002、F-003、F-004、4.4

## H-04: `/runpr` step 3 のメンション除外フィルタと依頼コメント分類の一般化

**懸念:** `.claude/commands/runpr.md:441-489` の 3 つの `--jq` フィルタには、次の 2 点の制約がある。
1. `cr_observed` は `coderabbitai[bot]` の 2 種の定型ヘッダーを除外しているが、Sourcery AI のレビューガイドコメントの 1 行目 `<!-- Generated by sourcery-ai[bot]: start review_guide -->` は **`sourcery-ai` と `sourcery-ai[bot]` の部分文字列そのものを含む**。`TestContextAndCommandsAgree`（`cmd/yt2column/fixpr_docs_test.go:1144`）は `strings.Contains(doc, name)` でコマンド文書内の直書きを禁じるため（AC-08）、このヘッダー文字列を `runpr.md` にリテラルで直書きできない。
2. `runpr.md:453-455` は単一の `<review-request>` と一致するコメントだけを `{kind: "request"}` として `mention` から除外している。F-004 では `@coderabbitai review`・`@sourcery-ai review`・`@sourceryai review` の 3 種類をすべて `request` として分類する必要がある。

**なぜ重要か:** `TestRunprDocContract` が `runpr.md` step 3 の `--jq` フィルタを実際に `jq` で実行し、`TestContextAndCommandsAgree` が直書き禁止を検証するため、プレースホルダー展開とフィルタ構造の両方を壊さずに設計する必要がある。

**候補:**

-   `_context.md` から展開するプレースホルダー（例: `<!-- Generated by <sourcery-reviewer>[bot]: start review_guide -->`、または観測済みヘッダー一覧自体を `_context.md` のプレースホルダーで定義する形）を使い、`runpr.md` 内に `sourcery-ai` が現れないようにする。
-   `{kind: "request"}` の判定を単一文字列比較から `<review-requests>`（JSON 配列）の包含判定へ広げる。
-   `TestRunprDocContract` に、`sourcery-ai[bot]` のレビューガイドコメント（除外）、非定型コメント（`by_bot: true` で確認対象）、同じ名前の `User`（停止対象）、利用者の `@sourcery-ai review`・`@sourceryai review`（`request` 分類）、他アカウントの `@sourcery-ai`・`@sourceryai`（停止対象）のテストケースを加える。

**関連:** F-001、F-003、F-004、AC-08・AC-13・AC-15

## H-05: マージの質問の要約行・依頼先選択質問と `chief` の整合

**懸念:** `.claude/commands/runpr.md:1087-1166` はマージの質問の要約行を最大 15 行と定め、kind 15 に単一レビュアーの `手動 PR レビュー:` 行を置いている。F-004（AC-23・AC-24）では、(a) CodeRabbit と Sourcery AI の 2 社分のレビュー状態を要約に収める必要があり、(b) 「先に PR レビューを依頼」選択後に依頼先を選ぶ 3 択の単一選択の問いが加わる。

**なぜ重要か:** `internal/chief` は `/runpr` のマージの質問画面と報告行を読み取るため（[ADR-0046](../../dev/adr/0046-chief-of-staff.md)）、要約行の形式変更や新しい単一選択の問いが `chief` の画面判定（マージ確認かどうか、単一選択の中継可否）にどう影響するかを確認し、必要ならサンプルとテストを更新する必要がある（AC-28）。

**候補:**

-   要約行は 1 行に 2 社を簡潔に並べるか、レビュアーごとに 1 行（最大行数の更新を伴う）とするかを、画面幅と読みやすさから設計で選ぶ。
-   依頼先選択の質問は通常の単一選択の問い（マージの質問ではない）として `chief` が中継できる形にし、`internal/chief` の画面読み取り規則との整合を確認する。

**関連:** F-004、F-005、AC-23・AC-24・AC-28

## H-06: `/runpr` の CI 待機と `Sourcery review` CheckRun の分離

**懸念:** 現在の `.claude/commands/runpr.md:710-713` は `gh pr checks <number> --watch --fail-fast` で `head` コミットのすべての CheckRun を監視している。`Sourcery review` も `head` 上の CheckRun であるため、自動の PR レビューが `FAILURE` や `TIMED_OUT` で終わると `gh pr checks` が非 0 で終了し、AC-19（「自動の PR レビューが失敗しても止めない」）に反して `/runpr` が停止する。また、`/fixpr` の push 後に自動の PR レビューが進行中だと 15 分上限なしで待ち続ける。

**なぜ重要か:** CI 待機でリポジトリの CI チェック（`Test`・`Code Quality & Lint`・`Documentation guard`・`Secret scan`・`Browser extension`・`Check changed files` 等）の失敗を確実に止めつつ、外部レビュー Bot の CheckRun（`Sourcery review`・`CodeRabbit`）による誤停止を防ぐ仕組みが不可欠である。

**候補:**

-   `gh pr checks --required` を使う（リポジトリの ruleset / branch protection で必須チェックが設定されているかを設計時に確認する）、または GitHub Actions のチェックのみを対象に待機する（`gh pr checks --json` / `fixprguard` のサブコマンドで `github-actions` の CheckRun に絞って監視する）かを設計で選ぶ。
-   `/fixpr` が新しいコミットを push した後も step 3 のループの先頭で進行中の自動の PR レビューを待機（15 分上限）し、完了後に開かれたスレッドを処理してから CI 待機へ進む順序を明確にする。

**関連:** F-004、AC-16・AC-19
