# 設計への申し送り（0122）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: `_context.md` での複数 PR レビュアーと依頼文面の表の表現

**懸念:** 現在 `.claude/commands/_context.md:299-300` は、単一の `Awaited PR reviewer`（`coderabbitai`）と単一の `PR review request`（`@coderabbitai review`）を 1 行ずつ持っている。`cmd/yt2column/fixpr_docs_test.go:1066-1096` と `cmd/yt2column/review_mention_docs_test.go:88-137` は、この 2 行の形と出現回数（ちょうど 1 回）を厳密に検査している。F-004（AC-15）では CodeRabbit と Sourcery AI の 2 つ（さらに Sourcery AI は投稿用 `@sourcery-ai review` と手動認識用 `@sourceryai review`）を 1 か所で定義する必要がある。

**なぜ重要か:** `_context.md` の行名や区切り形式、および `TestMentionsOnlyInAllowedRows`・`TestContextAndCommandsAgree`・`TestContextReviewerRowsMalformed` が許可する行の形を揃えないと、ガードテストとコマンド文書の参照が食い違う。

**候補:**

-   `Awaited PR reviewer`・`PR review request` を複数レビュアー向けの表または対応行（例: レビュアーごとの行、またはペア表記）に改め、コマンド文書はそこからプレースホルダーを組み立てる。
-   `TestMentionsOnlyInAllowedRows` が許可する行と `TestPostingCommandsInventory` が例外扱いする投稿コマンド（step 4 の依頼コメント投稿）を、複数レビュアーの依頼文面に対応させる。

**関連:** F-003、F-004、AC-12・AC-15・AC-23

## H-02: `fixprguard review-state` の複数レビュアー・自動レビュー対応の契約設計

**懸念:** 現在の `internal/fixprguard/review_state.go:44-50,655-679` は、GraphQL クエリに `checkName: "CodeRabbit"` を直書きし、分類表（`Finished`・`Review rate limited`・`Review skipped: automatic reviews are disabled`）も CodeRabbit 固定である。また、依頼コメントが 0 件なら CheckRun を読まずに `RequestNone` を返している（`review_state.go:417-421`）。F-004（AC-16〜AC-20）では、Sourcery AI の `Sourcery review` CheckRun（自動実行を含む）と、手動依頼コメントの認識（`@sourcery-ai review`・`@sourceryai review`）の両方に対応する必要がある。

**なぜ重要か:** Sourcery AI では依頼コメントがなくても自動レビューの CheckRun が走り得るため、現在の「依頼がなければ `none` を即返す」経路をそのまま使うと進行中の自動レビューを待てず、自動完了を `markers` に含められない。また、自動レビューと手動依頼が近接して走った場合の競合判定（`indeterminate`）と、自動スキップ（止めない）対手動スキップ（止める）の区別を明確にする必要がある。

**候補:**

-   `review-state` にレビュアー種別を宣言する引数（または複数 `--request` とプロファイル切替。`CLAUDE.md` の「Declare, don't infer」に従い文字列内容から推測しない）を設け、CodeRabbit と Sourcery AI をそれぞれ呼び出すか、1 回の呼び出しで両者の状態を返すかを設計で選ぶ。
-   自動レビューの状態（進行中・成功・スキップ・失敗）と手動依頼の状態を出力 JSON の型で明確に分け、`/runpr` が分岐を誤らないようにする。
-   F-001 の観測記録（`observations.md`）で確定した `output.title`・`conclusion`・`checkName` のみを分類表に組み込む。

**関連:** F-001、F-004、AC-05・AC-16〜AC-20

## H-03: `fixprguard` の `Protocol` 番号の引き上げと PR 分割

**懸念:** 現在 `internal/fixprguard/types.go:21` の `Protocol` は `8` である。F-002（`_context.md` の一覧追加）は既存バイナリでそのまま動く。F-003（`RejectedMentions` の追加）は受け付ける入力を狭めるだけの変更で `fixprguard_guide.md:670` の例外に当たりうる。一方、F-004 で `review-state` の引数や出力 JSON の契約が変わる場合、`fixprguard_guide.md:663` と `CLAUDE.md`「Protocol numbers」に従い `Protocol` を `main` の値 + 1 へ引き上げる必要がある。

**なぜ重要か:** `Protocol` を上げると、マージ前後の `make install-fixprguard` の再インストールと他ブランチへの `main` 取り込みが必要になる。また、`Protocol` を上げる PR と上げない PR（F-002・F-003 の先行導入など）をどう分けるかで、並行作業への影響が変わる。

**候補:**

-   F-002・F-003（信頼一覧と拒否メンション・ガイド除外）と、F-004（`review-state` 拡張と `Protocol` の `main` の値 + 1 引き上げ）を別の実装 PR に分けるか、一括にするかを実装計画と合わせて設計する。
-   `Protocol` を上げる PR では、`CLAUDE.md`「Protocol numbers」に従い、コマンド文書・ガイド・テストのすべてを同一 PR で更新する。

**関連:** F-002、F-003、F-004、4.4

## H-04: `/runpr` step 3 のメンション除外フィルタへの Sourcery AI 組み込み

**懸念:** `.claude/commands/runpr.md:441-489` の 3 つの `--jq` フィルタは、`cr_observed` で `coderabbitai[bot]` の 2 種の定型ヘッダーを除外している。F-003（AC-13）では、ここに `sourcery-ai[bot]` の `<!-- Generated by sourcery-ai[bot]: start review_guide -->`（および F-001 で他に観測された定型ヘッダーがあればそれ）を加える必要がある。

**なぜ重要か:** `cmd/yt2column/fixpr_docs_test.go` の `TestRunprDocContract` が `runpr.md` step 3 の `--jq` フィルタを実際に `jq` で実行してテストしているため、フィルタのプレースホルダー展開・`sourcery-ai[bot]` の識別（直書き禁止の `TestContextAndCommandsAgree` との両立）・テストケース追加を合わせて設計する必要がある。

**候補:**

-   `_context.md` から展開するプレースホルダーを使って `bot_observed` 関数を一般化し、`coderabbitai[bot]` と `sourcery-ai[bot]` それぞれの観測済み 1 行目ヘッダーだけを除外する。
-   `TestRunprDocContract` に、`sourcery-ai[bot]` のレビューガイドコメント（除外）、非定型コメント（`by_bot: true` で確認対象）、同じ名前の `User`（停止対象）、他アカウントの `@sourcery-ai`・`@sourceryai`（停止対象）のテストケースを加える。

**関連:** F-001、F-003、AC-08・AC-13

## H-05: マージの質問の要約行・依頼先選択質問と `chief` の整合

**懸念:** `.claude/commands/runpr.md:1087-1166` はマージの質問の要約行を最大 15 行と定め、kind 15 に単一レビュアーの `手動 PR レビュー:` 行を置いている。F-004（AC-23・AC-24）では、(a) CodeRabbit と Sourcery AI の 2 社分のレビュー状態を要約に収める必要があり、(b) 「先に PR レビューを依頼」選択後に依頼先を選ぶ単一選択の問いが加わる。

**なぜ重要か:** `internal/chief` は `/runpr` のマージの質問画面と報告行を読み取るため（[ADR-0046](../../dev/adr/0046-chief-of-staff.md)）、要約行の形式変更や新しい単一選択の問いが `chief` の画面判定（マージ確認かどうか、単一選択の中継可否）にどう影響するかを確認し、必要ならサンプルとテストを更新する必要がある（AC-28）。

**候補:**

-   要約行は 1 行に 2 社を簡潔に並べるか、レビュアーごとに 1 行（最大行数の更新を伴う）とするかを、画面幅と読みやすさから設計で選ぶ。
-   依頼先選択の質問は通常の単一選択の問い（マージの質問ではない）として `chief` が中継できる形にし、`internal/chief` の画面読み取り規則との整合を確認する。

**関連:** F-004、F-005、AC-23・AC-24・AC-28
