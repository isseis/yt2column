# 設計への申し送り：開発文書を変更の規模に合わせて簡易にとどめる分岐

要件定義書（[01_requirements.md](01_requirements.md)）を書く際に挙がった、設計で決めることを記録する。`02_architecture.md` は、各項目をどう扱ったかを記す。

## H-01: 進め方の記録の形と読み方

AC-03 は、後のコマンドが文の意味を解釈せずに進め方を読み取れる形で記録することを求める。記録を置く場所（Document Status の表の行、概要の決まった行など）、取りうる値、値が欠けているときと壊れているときの区別（記録を持たない文書を通常の進め方として扱う AC-21 と、壊れた記録で止まる AC-22）を設計で決める。`CLAUDE.md` の「Declare, don't infer」と、`/runpr` の承認が Document Status の表の行を読む仕組み（`docs/dev/conventions/requirements_process.md`「Cell text」）との関係も考える。コマンドは、記録を作業中のブランチではなく `origin/main` の版から読むか（`/mkarch` の step 1.5 の後に読む版）も決める。

## H-02: 3 文書のファイルの構成

簡易な進め方でも 3 つのファイルに分けるか、1 つにまとめるかを設計で決める。`/runpr` の承認と次のコマンドの選び方（`.claude/commands/runpr.md:349`・`:378-380`）、計画書の PR の定義（`.claude/commands/_context.md`「Plan PR」）、`/runplan`、タスクの識別の規則（`docs/dev/conventions/task_identification.md`）は、3 つのファイル名を読む。3 つに分ければこれらを変えずに使える見込みがある。

## H-03: `/mkreq` の定義の分け方

簡易な進め方では、`/mkreq` が、今の `/mkarch`・`/mkplan` の決定の確かめ方、文書の書き方、レビューのチェックリスト、PR の境界の設計を使う（AC-04・AC-08）。これらを `/mkreq` に書き写すと、同じ手順が 2 か所になる（要件定義書 4.5）。`/mkarch`・`/mkplan` の手順を `_lib/` に移して共有するか、`/mkreq` から `/mkarch`・`/mkplan` の該当する step を参照するかなど、定義の分け方を設計で決める。

## H-04: 3 文書のレビューの単位

AC-06 は、3 文書のセルフレビューを 1 人のレビュアーで行ってよいとする。3 文書をまとめて 1 回レビューするか、文書ごとに 1 回ずつレビューするか、各文書のチェックリスト（`/mkreq` の step 7、`/mkarch` の step 8、`/mkplan` の step 8）をどう渡すかを設計で決める。

## H-05: 通常の進め方へ戻す手順を誰が行うか

AC-17・AC-18 の戻し方を、どのコマンドがどの契機で行うかを設計で決める。候補は、`/runpr` のマージの質問の選択肢と、人がコマンドに指示することである。レビューのスレッドの本文の求めでは戻さない（AC-17、[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）ので、`/fixpr` がスレッドを受けて戻すことはしない。`/runpr` の次のコマンドの選び方（`.claude/commands/runpr.md:378-380`）が、戻した後の PR で `/mkarch` を勧めること（AC-19）も確かめる。PR の題名と説明（`.claude/commands/_context.md`「Task-document PR title」）を戻した後にどう直すかも決める。

## H-06: 3 文書の PR の題名と説明

`.claude/commands/_lib/task-pr-handoff.md` の Part A・Part B は、1 つの文書を作るコマンドを前提に書かれている。3 文書の PR のブランチ名、PR の題名（`docs(<task-id>): ...`）、コミットの件名（今は文書ごとに `docs(NNNN): draft requirements for ...` などの形）を設計で決める。

## H-07: 既存の文書のテスト

コマンドの定義と規約を読む既存の Go のテスト（`TestRunprDocContract` など。`CLAUDE.md`「Development Notes」）が、変更した定義で失敗しないかを確かめる。簡易な進め方について値と構造を確かめるテストを足すかは、`CLAUDE.md` の「Document tests check values, structure, and executable examples, never prose.」と [ADR-0016](../../dev/adr/0016-document-test-policy.md) に照らして決める。

## H-08: 推奨の拠り所

AC-01 は、推奨する進め方とその理由を示すことを求める。機械的な上限は設けない（AC-15）ので、エージェントが何を考えて推奨するか（変更の広がり、決定の数、既存の ADR との関係など）を、定性的な観点としてコマンドの定義に書くかどうかを設計で決める。

## H-09: 決定を確かめる手順との関係

AC-01 は、決定を確かめる手順の中で毎回尋ねることを求める。`.claude/commands/_lib/settle-decisions.md` の step 4（開いた決定がなければ 1 行で述べて続ける）と、どう両立させるかを設計で決める。簡易な進め方で 3 文書分の決定を 1 回の実行で確かめる（AC-04）ときに、質問を何回に分けるかも決める。

## H-10: 途中で止まった実行の続け方

AC-12 は、3 文書の PR を開く前に止まった `/mkreq` の実行を続けられることを求める。今の `/mkreq` は、issue を名指しする要件定義書がどこかのブランチにあると止まる（`.claude/commands/mkreq.md` の step 1）。走らせ直すコマンド（`/mkreq` が続きから進めるか、別の入口を設けるか）と、続ける前に確かめる状態（ブランチ、コミット済みの文書、ADR の変更）を設計で決める。

## H-11: 戻したときに設計と計画の決定を残す場所

AC-18 は、通常の進め方へ戻したときに、確かめ済みの設計と計画の決定を、後で `/mkarch`・`/mkplan` が読める場所に残すことを求める。`design_handoff.md`・`implementation_handoff.md` に移すか、ほかの場所に置くかを設計で決める。

## H-12: `/runplan`・`/fixpr` が除外に当たる決定に気づく手がかり

AC-16 は、3 文書のマージの後に除外に当たる決定が要ると分かったときに、`/runplan` が止まることを求める。今の `/runplan` が決定の変更を見つけて人に尋ねる手順（セッション中の再承認）の中に、除外の判定をどう組み込むかを設計で決める。`/fixpr` が 3 文書の PR と実装の PR で同じ判定をする手順（AC-16 の 2 項目めと 3 項目め）も決める。

## H-13: 3 文書の PR での申し送りの扱い

AC-10 は、3 文書の PR で後の文書へ送る懸念を同じ PR の中で扱い、マージの時点で扱いの記されていない申し送りの項目を残さないことを求める。`/fixpr` の R2・R3（`.claude/commands/fixpr.md`）を、3 文書の PR でどう変えるか（申し送りのファイルを経ずに後の文書を直すか、ファイルに書いてから同じ回で扱いを記すか）、扱いを誰がどこに記すか、「扱いの記されていない項目が残らない」ことを誰がいつ確かめるかを設計で決める。
