## 1. 概要 (Overview)

**目的:** 本書は、タスクの開発文書（`01_requirements.md`・`02_architecture.md`・`03_implementation_plan.md`）を変更の規模に合わせて簡易な内容にとどめ、1 本の PR で作る進め方を、`/mkreq`・`/mkarch`・`/mkplan` の正式な分岐として定めるための要件を定義する。

**背景:**

-   今の流れでは、3 文書を 1 本ずつ別の PR で作り、前の文書が `approved` になるまで次の文書を書き始めない（`docs/dev/conventions/requirements_process.md:11-13`、「Review Flow」の `:85`）。`/mkarch` は要件定義書が `approved` でなければ止まり（`.claude/commands/mkarch.md:28`）、`/mkplan` は要件定義書と設計書の両方が `approved` でなければ止まる（`.claude/commands/mkplan.md:31`）。PR ごとに、Codex の PR レビュー、CI、`/runpr` の往復がかかる。
-   タスク 0069 と 0071 では、文書の内容を簡易にとどめて、文書を作る負荷を減らした。3 文書の行数は、0069 が計 718 行、0071 が計 563 行である。0060〜0068 では、設計書か計画書の 1 本だけで 450〜1,259 行あった（issue #743）。ただし、`mk*` のコマンドの定義には、文書の分量を変更の規模に合わせる指示がない。今の簡易化は、その場の判断に頼っている。
-   設計書のレビューは、2 人のレビュアーの panel で行う（`.claude/commands/mkarch.md:78`）。設計書には、概念モデル・システム構成・処理の流れ・脅威モデルの Mermaid 図を求めている（`.claude/commands/mkarch.md:69`、`docs/dev/conventions/requirements_process.md:671-691`）。
-   軽量プロセス（`docs/dev/conventions/requirements_process.md`「Lightweight Process」）は、定義した後、一度も使われていない。0069 と 0071 も、要件定義書に「軽量プロセスを取らない理由」を書いて、通常のプロセスを選んだ（`docs/tasks/0071_security_source_link/01_requirements.md` §1）。軽量プロセスの削除は #744 で扱う。
-   `/runpr` は、PR が足すか変えるタスク文書のうち `draft` のものを、マージの質問への答えで、すべて `approved` にする（`.claude/commands/runpr.md:349`）。マージの後に勧めるコマンドは、承認した文書のうち最も後のものから選び、`03_implementation_plan.md` なら `/runplan` である（`.claude/commands/runpr.md:378-380`）。

**軽量プロセスを取らない理由:** この変更は `.claude/commands/` と `docs/dev/conventions/` の文の意味を変え、ADR を足す。これは「常に通常プロセスになる変更」の「A change of wording that changes a meaning」に当たる（`docs/dev/conventions/requirements_process.md`「Changes that always take the normal process」）。

対応 issue: [#743](https://github.com/isseis/yt2column/issues/743)（関連: [#744](https://github.com/isseis/yt2column/issues/744)、タスク 0069（[#719](https://github.com/isseis/yt2column/issues/719)）、タスク 0071（[#725](https://github.com/isseis/yt2column/issues/725)）、タスク 0061（[#619](https://github.com/isseis/yt2column/issues/619)）、[ADR-0040](../../dev/adr/0040-simple-task-documents.md)）

**本書の記述範囲:** 本書は、簡易な進め方を選ぶ手順、簡易な進め方の文書と PR、簡易な進め方を選べない変更、通常の進め方へ戻す手順を定める。選んだ進め方の記録の形、コマンドがそれを読む方法、ファイルの構成、コマンドの定義の分け方は、`02_architecture.md` で決める（`design_handoff.md`）。

**issue #743 で決めたこと:**

-   **`/mkreq` が、決定を人に確かめる手順（`.claude/commands/_lib/settle-decisions.md`）の中で、簡易な文書で足りるかを提案し、人の承認を得る。** 結果は要件定義書に記録する。
-   **`/mkarch` と `/mkplan` は、その記録を読んで分岐する。**
-   **簡易な文書でも、受け入れ基準、受け入れ基準ごとの確かめ方とその対応、ADR が要るかの判断、`docs/dev/security.md` が当てはまるかの判断は省かない。当てはまらない節（N/A と書く）と、レビューの panel（1 人のレビュアーにする）は省いてよい。**
-   **分岐は人の判断で決め、機械的な判定（行数やファイル数の上限、判定のスクリプト）は設けない。** 軽量プロセスでは、判定のスクリプトとそのテストが維持のコストの大半を占めたためである。
-   **分岐の方針を ADR に記録する。** 開発プロセスの方針なので、重要な決定に当たる。
-   **軽量プロセスの削除は扱わない（#744）。**

**要件定義の際に決めたこと（2026-11-09）:**

-   **簡易な進め方では、3 文書を 1 本の PR で作り、実装は別の PR で行う。** 人は 3 文書を 1 回のレビューとマージの質問で承認する（F-002）。PR ごとの Codex の PR レビュー・CI・`/runpr` の往復が、文書を書く負荷より大きい可能性がある（issue #743）。実装の前に人が承認する関門は残す。採らなかった案：3 文書を別々の PR のまま内容だけを簡易にする案は、PR の往復の待ちが減らない。文書と実装を 1 本の PR にする案は、計画の承認の前に実装を書くことになり、文書を差し戻すと実装も無駄になる。ADR：[ADR-0040](../../dev/adr/0040-simple-task-documents.md) を作る。
-   **簡易な進め方では、`/mkreq` が 3 文書を書く。** `/mkreq` は、要件・設計・計画の決定を 1 回の実行でまとめて人に確かめ、3 文書を書いて 1 本の PR を開く（F-002）。簡易な進め方のタスクで `/mkarch`・`/mkplan` を走らせると、文書を作らずに止まる（AC-10）。人が走らせるコマンドを 1 つにするためである。採らなかった案：人が同じブランチで `/mkreq`・`/mkarch`・`/mkplan` を続けて走らせ、`/mkplan` が PR を開く案は、人の操作が 3 回のまま残る。ADR：ADR-0040 に含める。
-   **セキュリティの前提か信頼の境界を変える変更と、外部への依存を足す変更は、簡易な進め方を選べない（F-003）。** 判定は読んで行い、スクリプトは作らない。誤ると影響の大きい変更を、設計の panel のレビューと文書ごとの承認に残すためである。セキュリティにかかわる文書の記述をコードに合わせるだけの変更（タスク 0071 のような変更）は、前提を変えないので除外しない。採らなかった案：除外を設けず、どの変更も人の判断だけで選べるようにする案は、誤ると影響の大きい変更が簡易な設計で通りうる。ADR：ADR-0040 に含める。
-   **issue の例のほかに、設計書の Mermaid 図を必須にしないことも、省いてよいものとする。** 日本語の推敲（`japrose`）は省かない（AC-06・AC-07）。図を書く負荷は大きく、小さな変更では文で足りることが多い。一方、文が読みにくいと承認の判断を誤らせる。採らなかった案：`japrose` の推敲も省く案は、上の理由で採らない。ADR：ADR-0040 に含める。
-   **`/mkreq` は、要件定義書を書くタスクでは毎回、簡易な進め方と通常の進め方のどちらにするかを、推奨を添えて尋ねる（AC-01）。** 機械的な判定を設けないので、判断を人に残すためである。費用は質問 1 つである。採らなかった案：エージェントが簡易で足りると判断したときだけ提案する案は、提案しなかった変更について人が選ぶ機会がない。ADR：ADR-0040 に含める。
-   **3 文書の PR をマージする前なら、レビュアーの判断で通常の進め方へ戻せる。マージの後は戻さない（F-004）。** レビューで簡易では足りないと分かったときに、要件定義書のレビューを無駄にしないためである。採らなかった案：戻さずにタスクを取り下げて作り直す案は、レビューの済んだ要件定義書を捨てることになる。ADR：ADR-0040 に含める。
-   **簡易な進め方は、この変更がマージされた後に `/mkreq` で要件定義書を書くタスクだけに当てはまる（AC-17）。** 進行中のタスクは、要件定義書がすでに別の PR で承認されており、残りの文書だけを簡易にすると、1 本の PR にまとめる利点がないためである。ADR：なし。移行の範囲の決定で、本タスクの中で閉じる。
-   **簡易な進め方でも、実装の PR の数は限らない。** 計画書が今と同じように PR の境界を決める（AC-08）。機械的な上限を設けない方針（issue #743）に合わせるためである。ADR：ADR-0040 に含める。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   小さな変更のタスクで、3 文書を作る負荷と、文書の PR の往復の待ちを減らす。
-   文書の分量を変更の規模に合わせる判断を、その場の判断ではなく、コマンドの定義にある手順で行い、選んだ結果を要件定義書に残す。
-   簡易な進め方でも、受け入れ基準とその確かめ方、ADR の判断、セキュリティの判断を省かず、実装の前に人が承認する関門を残す。

### 2.2. スコープ (In Scope)

-   `/mkreq` の、進め方を尋ねて記録する手順と、簡易な進め方で 3 文書を書いて 1 本の PR を開く手順（F-001・F-002）。
-   `/mkarch`・`/mkplan` の、簡易な進め方のタスクで止まる分岐（AC-10）。
-   簡易な進め方を選べない変更（F-003）。
-   通常の進め方へ戻す手順（F-004）。
-   `docs/dev/conventions/requirements_process.md` と `CLAUDE.md` の、簡易な進め方の記述（F-005）。
-   ADR-0040 の作成と ADR の索引の行（本書の PR で行う）。

### 2.3. スコープ外 (Out of Scope)

-   軽量プロセスの削除。#744 で扱う。本タスクの後も、軽量プロセスが残る間は、`/mkreq` の軽量プロセスの判定（`.claude/commands/mkreq.md` の step 1）が先に行われる。
-   通常の進め方で書き始めたタスクを、後から簡易な進め方に切り替えること。issue が求めているのは `/mkreq` での選択だからである。
-   進行中のタスク（この変更がマージされる前に要件定義書を書いたタスク）への適用。1 章の決定による。
-   行数・ファイル数の上限や判定のスクリプトなど、機械的な判定。issue #743 の決定による。
-   `/mkplan2` の変更。簡易な進め方の計画書は `/mkreq` が PR の境界とともに書くので、`/mkplan2` の対象にならない。
-   `/runpr`・`/fixpr`・`/runplan` の、文書の承認・スレッドの解決・実装の手順の変更。ただし、通常の進め方へ戻す手順（F-004）がこれらのコマンドに及ぶ範囲は、設計で決める。
-   Codex の PR レビュー、ローカルの CLI レビュー、CI の変更。
-   簡易な進め方の文書の内容を確かめる新しい文書のテスト。文の意味は PR のレビューで読んで確かめる、というのが文書のテストの方針だからである（`CLAUDE.md`「Testing Strategy」の「Document tests check values, structure, and executable examples, never prose.」、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。値と構造を確かめるテストを足すかは設計で決める。
-   既存のタスク文書の書き換え。タスク文書は、そのタスクの時点の記録だからである。

## 3. 機能要件 (Functional Requirements)

本章では、今の 3 文書を 1 本ずつ PR にする進め方を「通常の進め方」、3 文書を簡易な内容で 1 本の PR で作る進め方を「簡易な進め方」と呼ぶ（6 章）。

### 3.1. 機能一覧

#### F-001: 進め方の選択と記録

`/mkreq` は、要件定義書を書くタスクで、簡易な進め方と通常の進め方のどちらにするかを人に尋ね、結果を要件定義書に記録する。

**Acceptance Criteria**:
- **AC-01**: `/mkreq` は、要件定義書を書くとき（`[task]` を与えた場合も含む）、決定を人に確かめる手順の中で、簡易な進め方と通常の進め方のどちらにするかを尋ねる。尋ねる前に、推奨する進め方とその理由を示す。軽量プロセスの仕様のコメントを投稿して止まる実行では尋ねない。
- **AC-02**: `/mkreq` は、変更が簡易な進め方を選べない変更（F-003）に当たると判断したときは、簡易な進め方を選択肢に出さず、当たる項目とその理由を示して通常の進め方で進む。当たるか迷うときは、当たるとして扱う。
- **AC-03**: 要件定義書は、選んだ進め方と、その理由を記録する。F-003 で通常の進め方になったときは、当たる項目を理由として記録する。記録は、後のコマンド（`/mkarch`・`/mkplan`・F-004 の手順）が、文の意味を解釈せずに進め方を読み取れる形で置く。

#### F-002: 簡易な進め方の文書と PR

簡易な進め方では、`/mkreq` が 3 文書を書いて 1 本の PR を開く。

**Acceptance Criteria**:
- **AC-04**: 簡易な進め方では、`/mkreq` は、文書を書く前に、要件定義書・設計書・計画書のそれぞれで今の `/mkreq`・`/mkarch`・`/mkplan` が人に確かめる範囲の決定を、同じ実行の中で人に確かめる。その後、同じタスクのディレクトリに `01_requirements.md`・`02_architecture.md`・`03_implementation_plan.md` を、どれも `draft` で書き、1 本の PR を開いて止まる。
- **AC-05**: 簡易な進め方の文書は、次のものを省かない。
    -   要件定義書の、文書の中で一意な ID を持つ受け入れ基準。
    -   計画書の、受け入れ基準ごとの確かめ方とその対応（`docs/dev/conventions/requirements_process.md`「AC traceability」）。
    -   各文書の、決定ごとの ADR の判断と、重要な決定の ADR の作成か更新。
    -   各文書の、`docs/dev/security.md` が当てはまるかの判断。当てはまらないときは、セキュリティの節に N/A とその理由を書く。
- **AC-06**: 簡易な進め方の文書は、次のものを省いてよい。
    -   当てはまらない節の本文。節の見出しを残し、N/A とその理由を 1 行で書く。
    -   設計書の Mermaid 図。必要と判断したときは書く。
    -   設計書のレビューの panel。3 文書のレビューは 1 人のレビュアーで行う。
- **AC-07**: 簡易な進め方でも、`/mkreq` は、3 文書と ADR の変更に日本語の推敲（`japrose`）を行い、ローカルの CLI レビューを行ってから PR を開く。
- **AC-08**: 簡易な進め方の計画書は、通常の進め方の `/mkplan` と同じように PR の境界を持つ。実装の PR の数に上限はない。
- **AC-09**: 3 文書の PR を `/runpr` で扱うと、1 回のマージの質問への答えで 3 文書がすべて `approved` になり、マージの後に `/runplan` を勧める。
- **AC-10**: 簡易な進め方を記録したタスクで `/mkarch` または `/mkplan` を走らせると、文書を作らず、ブランチも作らずに止まり、このタスクは簡易な進め方で、文書は `/mkreq` が作ることを報告する。
- **AC-11**: `docs/dev/conventions/requirements_process.md` の「LLM Constraints」は、簡易な進め方の例外を述べる。簡易な進め方のタスクでは、設計書と計画書を要件定義書の承認の前に同じ PR で作ってよい。例外はそこまでで、3 文書がすべて `approved` になるまで実装を書き始めない。

#### F-003: 簡易な進め方を選べない変更

**Acceptance Criteria**:
- **AC-12**: 次のどれかに当たる変更は、簡易な進め方を選べない。
    -   セキュリティの前提を変える変更。脅威モデル、信頼する主体とその範囲、秘密の扱いを変える変更である（`docs/dev/security.md`）。
    -   信頼の境界を変える変更。`fixprguard`・`codexreview`・`mergepr`、秘密、`yt-dlp` の呼び出し、キャッシュの扱いを変える変更である。
    -   外部への依存を足す変更。Go のモジュール、拡張の npm パッケージ、外部のサービスを足す変更である。
- **AC-13**: F-003 の判定は、エージェントと人が変更の内容を読んで行う。行数・ファイル数の上限と、判定のスクリプトはない。セキュリティにかかわる文書の記述を、前提を変えずにコードの振る舞いに合わせる変更は、F-003 に当たらない。

#### F-004: 通常の進め方へ戻す

**Acceptance Criteria**:
- **AC-14**: 3 文書の PR をマージする前に、レビュアーが簡易な進め方では足りないと判断したときは、通常の進め方へ戻せる。戻した後の PR は、`02_architecture.md` と `03_implementation_plan.md` を含まず、要件定義書の記録は通常の進め方とその理由になる。設計と計画の決定のためだけに作るか変えた ADR の変更も、PR から外れる。
- **AC-15**: 戻した後の PR を `/runpr` でマージすると、要件定義書が `approved` になり、マージの後に `/mkarch` を勧める。以後は通常の進め方で進む。
- **AC-16**: 3 文書の PR をマージした後は、進め方を戻さない。マージの後に決定を変えるときは、通常の進め方と同じく「Editing an approved document」（`docs/dev/conventions/requirements_process.md`）に従う。

#### F-005: 適用の範囲と文書

**Acceptance Criteria**:
- **AC-17**: 進め方の記録を持たない要件定義書のタスク（この変更の前に要件定義書を書いたタスク）では、`/mkarch`・`/mkplan` は通常の進め方として振る舞う。
- **AC-18**: `docs/dev/conventions/requirements_process.md` は、簡易な進め方の流れ（「Review Flow」に並ぶ形）、省かないものと省いてよいもの、選べない変更、通常の進め方へ戻す手順を述べる。`CLAUDE.md` の「Requirements and Acceptance Criteria」と、`/mkreq`・`/mkarch`・`/mkplan` の説明（「Claude Commands」）は、簡易な進め方に触れる。
- **AC-19**: 変更後に `make test` と `make lint` が通る。コマンドの定義と規約を読む既存の文書のテストを含む。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   N/A。製品の実行時の処理は変わらない。

### 4.2. セキュリティ (Security)
-   N/A。本タスクはエージェントの開発の手順だけを変え、外部コマンドの呼び出し、秘密、キャッシュ、ネットワークへの送信、信頼できないテキストの埋め込みのどれにも触れない（`.claude/commands/_context.md` の「Conditional-guide trigger」）。
-   セキュリティにかかわる変更を誤って簡易な設計で通さないように、F-003 で、セキュリティの前提と信頼の境界を変える変更を簡易な進め方から外す。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   N/A。

### 4.4. 互換性 (Compatibility)
-   進行中のタスクは、今の通常の進め方のまま進む（AC-17）。CLI・サーバ・拡張の振る舞いは変わらない。

### 4.5. 保守性 (Maintainability)
-   簡易な進め方は、機械的な判定のスクリプトとそのテストを持たない（AC-13）。軽量プロセスで維持のコストの大半を占めた部分を作らないためである（issue #743）。
-   簡易な進め方の手順は、通常の進め方の手順（決定の確かめ方、レビューのチェックリスト、PR の引き渡し）を使い回し、同じ手順を 2 か所に書かない（`CLAUDE.md` の「DRY」）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   方針の例外：`docs/dev/conventions/requirements_process.md:11-12`（「LLM Constraints」）は、前の文書が `approved` になるまで次の文書を書き始めないと定める。簡易な進め方は、要件定義書の承認の前に設計書と計画書を書く例外である（AC-11）。理由は、文書の PR の往復の待ちを減らすためで、例外は簡易な進め方を記録したタスクに限る。実装の前の承認は残す。
-   方針の例外：`.claude/commands/mkarch.md:78` は、設計書のレビューを panel で行うと定める。簡易な進め方は 1 人のレビュアーで行う例外である（AC-06）。理由は issue #743 の決定による。
-   新しいタスクの決定は、ADR の規約（`docs/dev/conventions/adr.md`）に従って ADR-0040 に記録する。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。
-   **通常の進め方**: 要件定義書・設計書・計画書を 1 本ずつ別の PR で作り、前の文書が `approved` になってから次の文書を書く、今の進め方。
-   **簡易な進め方**: 3 文書を、変更の規模に合わせた簡易な内容で、`/mkreq` が 1 本の PR で作る進め方。人は 3 文書を 1 回のマージの質問で承認する。
-   **3 文書の PR**: 簡易な進め方で `/mkreq` が開く、3 文書を含む 1 本の PR。
-   **軽量プロセス**（lightweight process）: タスク文書を作らず、issue の仕様のコメントで 1 本の PR にする進め方（`docs/dev/conventions/requirements_process.md`「Lightweight Process」）。簡易な進め方とは別のもので、#744 で削除する。
