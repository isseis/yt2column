## 1. 概要 (Overview)

**目的:** 本書は、タスクの開発文書（要件定義書 `01_requirements.md`、アーキテクチャ設計書 `02_architecture.md`、実装計画書 `03_implementation_plan.md`。以下、要件定義書・設計書・計画書、まとめて 3 文書）を、変更の規模に合わせて簡易な内容にとどめ、1 本の PR で作る進め方の要件を定義する。この進め方を、`/mkreq`・`/mkarch`・`/mkplan` の正式な分岐として定める。

**背景:**

-   今の流れでは、3 文書を 1 本ずつ別の PR で作る。次の文書は、前の文書が `approved` になるまで書き始めない（`docs/dev/conventions/requirements_process.md:11-13`、同書「Review Flow」の `:85`）。`/mkarch` は、要件定義書が `approved` でなければ止まる（`.claude/commands/mkarch.md:28`）。`/mkplan` は、要件定義書と設計書の両方が `approved` でなければ止まる（`.claude/commands/mkplan.md:31`）。PR ごとに、Codex の PR レビュー、CI、`/runpr` の往復がかかる。
-   タスク 0069 と 0071 では、文書の内容を簡易にとどめて、文書を作る負荷を減らした。issue #743 によると、3 文書の行数は 0069 が計 718 行、0071 が計 563 行である。0060〜0068 の多くでは、設計書か計画書の 1 本だけで 450 行を超えた（issue #743）。ただし、`mk*` のコマンドの定義には、文書の分量を変更の規模に合わせる指示がない。今の簡易化は、その場の判断に頼っている。
-   設計書のレビュー（エージェントによるセルフレビュー）は、2 人のレビュアーの panel で行う（`.claude/commands/mkarch.md:78`）。計画書のセルフレビューは、1 人のレビュアーが既定で、リスクの高い計画だけを panel で行う（`.claude/commands/mkplan.md:104`）。設計書には、概念モデル・システム構成・処理の流れ・脅威モデルの Mermaid 図を求めている（`.claude/commands/mkarch.md:69`、`docs/dev/conventions/requirements_process.md:671-691`）。
-   `/fixpr` は、要件定義書へのレビューで挙がった設計の懸念を `design_handoff.md` に、要件定義書か設計書へのレビューで挙がった実装の懸念を `implementation_handoff.md` に送る（`.claude/commands/fixpr.md` の R2）。これらの項目は、後の文書を書く `/mkarch`・`/mkplan` が扱う。
-   軽量プロセス（`docs/dev/conventions/requirements_process.md`「Lightweight Process」）は、定義した後、一度も使われていない（issue #743）。0069 と 0071 も、要件定義書に「軽量プロセスを取らない理由」を書いて、軽量プロセスを選ばなかった（`docs/tasks/0071_security_source_link/01_requirements.md` §1）。軽量プロセスの削除は #744 で扱う。
-   `/runpr` は、マージの質問への答えで、PR が足すか変えるタスク文書のうち `draft` のものを、すべて `approved` にする（`.claude/commands/runpr.md:349`）。マージの後に勧めるコマンドは、承認した文書のうち最も後のものから選ぶ。計画書なら `/runplan` である（`.claude/commands/runpr.md:378-380`）。

**軽量プロセスを取らない理由:** この変更は、`.claude/commands/` と `docs/dev/conventions/` の文の意味を変え、ADR を足す。これは、軽量プロセスの「Changes that always take the normal process」のうち「A change of wording that changes a meaning」に当たる（`docs/dev/conventions/requirements_process.md`）。

対応 issue: [#743](https://github.com/isseis/yt2column/issues/743)（関連: [#744](https://github.com/isseis/yt2column/issues/744)、タスク 0069（[#719](https://github.com/isseis/yt2column/issues/719)）、タスク 0071（[#725](https://github.com/isseis/yt2column/issues/725)）、タスク 0061（[#619](https://github.com/isseis/yt2column/issues/619)）、[ADR-0040](../../dev/adr/0040-simple-task-documents.md)）

**本書の記述範囲:** 本書は、次のことを定める。
-   進め方を選ぶ手順。
-   簡易な進め方の文書と PR。
-   簡易な進め方を選べない変更。
-   通常の進め方へ戻す手順。

次のことは `02_architecture.md` で決める（`design_handoff.md`）。
-   選んだ進め方の記録の形と、コマンドがそれを読む方法。
-   3 文書のファイルの構成。
-   コマンドの定義の分け方。

**issue #743 で決めたこと:**

-   **`/mkreq` は、決定を人に確かめる手順（`.claude/commands/_lib/settle-decisions.md`）の中で、簡易な文書で足りるかを提案し、人の承認を得る。** 結果は要件定義書に記録する。
-   **`/mkarch` と `/mkplan` は、その記録を読んで分岐する。**
-   **簡易な文書でも、次のものは省かない。** 受け入れ基準、受け入れ基準ごとの確かめ方とその対応、ADR が要るかの判断、`docs/dev/security.md` が当てはまるかの判断である。
-   **当てはまらない節（N/A と書く）と、レビューの panel（1 人のレビュアーにする）は省いてよい。**
-   **分岐は人の判断で決め、機械的な判定（行数やファイル数の上限、判定のスクリプト）は設けない。** 軽量プロセスでは、判定のスクリプトとそのテストが維持のコストの大半を占めたためである。
-   **分岐の方針を ADR に記録する。** 開発プロセスの方針なので、重要な決定に当たる。
-   **簡易な進め方を選べない変更の例として、セキュリティの前提・信頼の境界・外部への依存を変える変更を挙げる。** 設けるかどうかは、下の 2026-11-09 の決定で決めた。
-   **軽量プロセスの削除は扱わない（#744）。**

**要件定義の際に決めたこと（2026-11-09）:**

-   **簡易な進め方では、3 文書を 1 本の PR で作り、実装は別の PR で行う（F-002）。** 人は、3 文書を 1 回のレビューとマージの質問で承認する。issue #743 によると、PR ごとの Codex の PR レビュー・CI・`/runpr` の往復は、文書を書く負荷より大きい可能性がある。一方で、実装の前に人が承認する関門は残す。
    -   採らなかった案：3 文書を別々の PR のまま、内容だけを簡易にする案。PR の往復の待ちが減らない。
    -   採らなかった案：文書と実装を 1 本の PR にする案。計画の承認の前に実装を書くことになり、文書を差し戻すと実装も無駄になる。
    -   ADR：[ADR-0040](../../dev/adr/0040-simple-task-documents.md) を作る。
-   **簡易な進め方では、`/mkreq` が 3 文書を書く。** `/mkreq` は、要件・設計・計画の決定を 1 回の実行でまとめて人に確かめ、3 文書を書いて、1 本の PR を開く（F-002）。簡易な進め方のタスクで `/mkarch`・`/mkplan` を走らせると、文書を作らずに止まる（AC-11）。人が走らせるコマンドを 1 つにするためである。
    -   採らなかった案：人が同じブランチで `/mkreq`・`/mkarch`・`/mkplan` を続けて走らせ、`/mkplan` が PR を開く案。人の操作が 3 回のまま残る。
    -   ADR：ADR-0040 に含める。
-   **セキュリティの規則か前提を変える変更、開発の道具の信頼の境界を変える変更、外部への依存を足すか変える変更は、簡易な進め方を選べない（F-003）。** 変更の内容を読んで判定し、スクリプトは作らない。誤ると影響の大きい変更を、設計書の panel のレビューと、文書ごとの承認に残すためである。セキュリティにかかわる文書の記述を、規則を変えずにコードに合わせるだけの変更（タスク 0071 のような変更）は、除外しない。issue #743 は外部への依存を「変える」変更を挙げているので、足す変更も、版を上げるか差し替える変更も除外に含める。
    -   採らなかった案：除外を設けず、どの変更も人の判断だけで選べるようにする案。誤ると影響の大きい変更が、簡易な設計で通りうる。
    -   ADR：ADR-0040 に含める。
-   **除外に当たるか迷うときは、エージェントは当たると判定する。人は、エージェントの判定を覆して、簡易な進め方を選べる（AC-02）。** 安全な側に倒した判定を示しつつ、選ぶ判断は人に残すためである（issue #743 の「分岐は人の判断で決め」）。
    -   採らなかった案：除外と判定したら人も覆せないようにする案。判定は読んで行うので誤りうるが、それを人が正す手段がなくなる。
    -   ADR：ADR-0040 に含める。
-   **3 文書をマージした後に、除外に当たる決定が実装で要ると分かったときは、`/runplan`（実装の PR のレビュー中なら `/fixpr`）は止まり、その変更を通常の進め方の別のタスクにするよう報告する（AC-16）。** マージの後は進め方を戻さないので、除外に当たる変更が、簡易な設計とセッション中の再承認だけで通ることを防ぐためである。
    -   採らなかった案：今のセッション中の再承認で扱い、そのリスクを受け入れる案。除外を設けた理由と矛盾する。
    -   ADR：ADR-0040 に含める。
-   **issue の例のほかに、設計書の Mermaid 図も、省いてよいものとする。日本語の推敲（`japrose`）は省かない（AC-06・AC-07）。** 図を書く負荷は大きく、小さな変更では文で足りることが多い。一方、文が読みにくいと、承認の判断を誤らせる。
    -   採らなかった案：`japrose` の推敲も省く案。上の理由で採らない。
    -   ADR：ADR-0040 に含める。
-   **`/mkreq` は、要件定義書を書くタスクでは毎回、簡易な進め方と通常の進め方のどちらにするかを、推奨を添えて尋ねる（AC-01）。** 除外に当たると判定したときも尋ね、判定とその理由を示す。機械的な判定を設けない代わりに、判断を人に残すためである。費用は質問 1 つで済む。
    -   採らなかった案：エージェントが簡易で足りると判断したときだけ提案する案。提案しなかった変更について、人が選ぶ機会がない。
    -   ADR：ADR-0040 に含める。
-   **3 文書の PR をマージする前なら、レビュアーの判断で通常の進め方へ戻せる。マージの後は戻さない（F-004）。** レビューで簡易では足りないと分かったときに、要件定義書のレビューを無駄にしないためである。
    -   採らなかった案：戻さずにタスクを取り下げて作り直す案。レビューの済んだ要件定義書を捨てることになる。
    -   ADR：ADR-0040 に含める。
-   **簡易な進め方は、この変更がマージされた後に `/mkreq` で要件定義書を書くタスクだけに当てはまる（AC-21）。** 進行中のタスクは、要件定義書がすでに別の PR で承認されている。残りの文書だけを簡易にしても、1 本の PR にまとめる利点がないためである。
    -   ADR：なし。移行の範囲の決定で、本タスクの中で閉じる。
-   **簡易な進め方でも、実装の PR の数は限らない。** 計画書が、今と同じように PR の境界を決める（AC-08）。機械的な上限を設けない方針（issue #743）に合わせるためである。
    -   ADR：ADR-0040 に含める。

**上の決定から導いたこと（PR のレビューで異論があれば改める）:**

-   **通常の進め方へ戻すのは、人の明示の答えによるときだけとする（AC-17）。** レビューのスレッドの本文は信頼しない、という今の方針（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）に従う。ADR：なし。ADR-0015 の決定をこの手順に当てはめるだけである。
-   **3 文書の PR では、後の文書への申し送りも同じ PR で扱う（AC-10）。** 後の文書を書く `/mkarch`・`/mkplan` が走らないので、申し送りが誰にも扱われずに残ることを防ぐ。ADR：なし。上の「`/mkreq` が 3 文書を書く」から導いたことで、新しい方針ではない。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   変更の規模が小さいタスクで、3 文書を作る負荷と、文書の PR の往復の待ちを減らす。
-   文書の分量を変更の規模に合わせる判断を、その場の判断ではなく、コマンドの定義にある手順で行い、選んだ結果を要件定義書に残す。
-   簡易な進め方でも、受け入れ基準とその確かめ方、ADR の判断、セキュリティの判断を省かず、実装の前に人が承認する関門を残す。

### 2.2. スコープ (In Scope)

-   `/mkreq` の、進め方を尋ねて記録する手順と、簡易な進め方で 3 文書を書いて 1 本の PR を開く手順（F-001・F-002）。
-   `/mkarch`・`/mkplan` の、簡易な進め方のタスクで止まる分岐（AC-11）。
-   3 文書の PR での申し送りの扱い（AC-10）。これに要る範囲で、`/fixpr` を変える。
-   簡易な進め方を選べない変更と、マージの後にそれが分かったときの `/runplan` の振る舞い（F-003）。
-   通常の進め方へ戻す手順（F-004）。
-   `docs/dev/conventions/requirements_process.md`・`CLAUDE.md`・`docs/translation_glossary.md` の、簡易な進め方の記述（F-005）。
-   ADR-0040 の作成と、ADR の索引の行（本書の PR で行う）。

### 2.3. スコープ外 (Out of Scope)

-   軽量プロセスの削除。#744 で扱う。本タスクの後も、軽量プロセスが残る間は、`/mkreq` の軽量プロセスの判定（`.claude/commands/mkreq.md` の step 1）が先に行われる。
-   通常の進め方で書き始めたタスクを、後から簡易な進め方に切り替えること。issue が求めているのは、`/mkreq` での選択だからである。
-   進行中のタスク（この変更がマージされる前に要件定義書を書いたタスク）への適用。1 章の決定による。
-   行数・ファイル数の上限や判定のスクリプトなど、機械的な判定。issue #743 の決定による。
-   `/mkplan2` の変更。簡易な進め方の計画書は、`/mkreq` が PR の境界とともに書くので、`/mkplan2` の対象にならない。
-   `/runpr`・`/fixpr`・`/runplan` の、文書の承認・スレッドの解決・実装の手順の変更。ただし、AC-10・AC-16・F-004 が求める範囲は除く。その範囲がどのコマンドに及ぶかは、設計で決める。
-   Codex の PR レビュー、ローカルの CLI レビュー、CI の変更。
-   簡易な進め方の文書の内容を確かめる新しい文書のテスト。文の意味は PR のレビューで読んで確かめる、というのが文書のテストの方針だからである（`CLAUDE.md`「Testing Strategy」の「Document tests check values, structure, and executable examples, never prose.」、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。値と構造を確かめるテストを足すかは、設計で決める。
-   既存のタスク文書の書き換え。タスク文書は、そのタスクの時点の記録だからである。

## 3. 機能要件 (Functional Requirements)

本章では、3 文書を 1 本ずつ PR にする今の進め方を「通常の進め方」と呼ぶ。3 文書を簡易な内容で 1 本の PR で作る進め方を「簡易な進め方」と呼ぶ（6 章）。「3 文書」は要件定義書・設計書・計画書の内容を指し、ファイルを 3 つに分けるかどうかは設計で決める（`design_handoff.md` の H-02）。

### 3.1. 機能一覧

#### F-001: 進め方の選択と記録

`/mkreq` は、要件定義書を書くタスクで、簡易な進め方と通常の進め方のどちらにするかを人に尋ね、結果を要件定義書に記録する。

**Acceptance Criteria**:
- **AC-01**: `/mkreq` は、要件定義書を書くとき（`[task]` を与えた場合も含む）は毎回、決定を人に確かめる手順の中で、簡易な進め方と通常の進め方のどちらにするかを尋ねる。尋ねる前に、推奨する進め方とその理由、変更が除外（F-003）に当たるかの判定とその理由を示す。軽量プロセスの仕様のコメントを投稿して止まる実行では尋ねない。
- **AC-02**: エージェントは、除外に当たるか迷うときは、当たると判定する。当たると判定したときは、通常の進め方を推奨する。人は、その判定を覆して簡易な進め方を選べる。そのときは、覆したことを記録する（AC-03）。
- **AC-03**: 要件定義書は、選んだ進め方とその理由を記録する。除外の判定とその理由、人が判定を覆したときはそのことも記録する。記録は、後のコマンド（`/mkarch`・`/mkplan`・`/runplan`・F-004 の手順）が、文の意味を解釈せずに進め方を読み取れる形で置く。

#### F-002: 簡易な進め方の文書と PR

簡易な進め方では、`/mkreq` が 3 文書を書いて 1 本の PR を開く。

**Acceptance Criteria**:
- **AC-04**: 簡易な進め方では、`/mkreq` は、文書を書く前に、同じ実行の中で決定を人に確かめる。範囲は、要件定義書・設計書・計画書のそれぞれについて、今の `/mkreq`・`/mkarch`・`/mkplan` が人に確かめる範囲である。その後、同じタスクのディレクトリに 3 文書を、どれも `draft` で書き、1 本の PR を開いて止まる。
- **AC-05**: 簡易な進め方の文書は、次のものを省かない。
    -   要件定義書の、文書の中で一意な ID を持つ受け入れ基準。
    -   計画書の、受け入れ基準ごとの確かめ方とその対応（`docs/dev/conventions/requirements_process.md`「AC traceability」）。
    -   3 文書の、決定ごとの ADR の判断と、重要な決定の ADR の作成か更新。
    -   3 文書の、`docs/dev/security.md` が当てはまるかの判断。当てはまらないときは、セキュリティの節に N/A とその理由を書く。
- **AC-06**: 簡易な進め方の文書は、次のものを省いてよい。
    -   当てはまらない節の本文。節の見出しを残し、N/A とその理由を 1 行で書く。
    -   設計書の Mermaid 図。必要と判断したときは書く。
    -   セルフレビューの panel。3 文書のセルフレビューは、1 人のレビュアーで行ってよい。エージェントがリスクが高いと判断したときは、panel で行う。
- **AC-07**: 簡易な進め方でも、`/mkreq` は、PR を開く前に、3 文書と ADR の変更に日本語の推敲（`japrose`）を行い、ローカルの CLI レビューを行う。
- **AC-08**: 簡易な進め方の計画書は、通常の進め方の `/mkplan` と同じように、PR の境界を持つ。実装の PR の数に上限はない。
- **AC-09**: 3 文書の PR を `/runpr` で扱うと、1 回のマージの質問への答えで、3 文書がすべて `approved` になる。マージの後は `/runplan` を勧める。
- **AC-10**: 3 文書の PR で、ある文書へのレビューから、同じ PR の後の文書が扱うべき懸念（今の `/fixpr` が `design_handoff.md`・`implementation_handoff.md` に送る懸念）が挙がったときは、その懸念を同じ PR の中で後の文書が扱う。3 文書の PR がマージされる時点で、申し送りのファイルに、扱いが記されていない項目は残らない。
- **AC-11**: 簡易な進め方を記録した要件定義書が `origin/main` にあるタスクで `/mkarch` または `/mkplan` を走らせると、文書を作らずに止まる。報告は、このタスクが簡易な進め方であり、文書は `/mkreq` が作ることを述べる。設計書か計画書がすでにあるときも、報告はこのことを述べる。設計書か計画書が欠けているときは、この報告ではなく、AC-22 の食い違いとして報告する。
- **AC-12**: 簡易な進め方の `/mkreq` が、3 文書の PR を開く前に止まったとき（途中の失敗、人の中断）は、人がコマンドを走らせ直して、残りの文書を書き、PR を開くところまで進められる。止まったときの報告は、走らせ直すコマンドを示す。
- **AC-13**: `docs/dev/conventions/requirements_process.md` の「LLM Constraints」は、簡易な進め方の例外を述べる。簡易な進め方のタスクでは、設計書と計画書を、要件定義書の承認の前に、同じ PR で作ってよい。例外はそこまでで、3 文書がすべて `approved` になるまで、実装を書き始めない。

#### F-003: 簡易な進め方を選べない変更

**Acceptance Criteria**:
- **AC-14**: 次のどれかに当たる変更は、除外に当たる。
    -   `docs/dev/security.md` の規則か、その前提（脅威モデル。[ADR-0006](../../dev/adr/0006-threat-model.md)）を変える変更。
    -   開発の道具の信頼の境界を変える変更（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）。`fixprguard`・`codexreview`・`mergepr` を変える変更のほか、これらを変えなくても、レビューのスレッドの本文や Bot への依頼の扱いなど、境界に影響する変更を含む。判定は、名前の挙がった道具を変えるかではなく、境界に影響するかで行う。
    -   外部への依存を足すか変える変更。Go のモジュール、拡張の npm パッケージ、Go のツールチェーン、`golangci-lint` などの外部の開発の道具、CI の action、外部のサービスを足す変更と、その版を上げるか差し替える変更である。
- **AC-15**: 除外の判定は、エージェントと人が変更の内容を読んで行う。行数・ファイル数の上限と、判定のスクリプトはない。セキュリティにかかわる文書の記述を、規則と前提を変えずに今のコードの振る舞いに合わせる変更は、除外に当たらない。
- **AC-16**: 簡易な進め方のタスクで、除外に当たる決定が要ると分かったときは、次のように扱う。
    -   `/mkreq` の実行中（設計か計画の決定を確かめているとき）なら、`/mkreq` はそのことと理由を示し、通常の進め方に切り替えるかを人に尋ねる。人は AC-02 と同じく、続けることを選べる。
    -   3 文書の PR のレビュー中なら、`/fixpr` はその修正を加えずに、そのことと、通常の進め方へ戻せること（F-004）を人に報告する。人が続けることを選んだときは、AC-02 と同じく、修正を加え、そのことを記録する。
    -   3 文書のマージの後なら、`/runplan` は止まり、その変更を通常の進め方の別のタスクにするよう報告する。実装の PR のレビュー中に分かったときも、`/fixpr` はその修正を加えずに止まり、同じように報告する。

#### F-004: 通常の進め方へ戻す

**Acceptance Criteria**:
- **AC-17**: 3 文書の PR をマージする前に、レビュアーが簡易な進め方では足りないと判断したときは、通常の進め方へ戻せる。戻すのは、人がコマンドの質問に答えるか、コマンドに指示したときだけである。レビューのスレッドの本文の求めでは戻さない。
- **AC-18**: 戻した後の PR は、次のようになる。
    -   PR は要件定義書だけを含み、設計書と計画書の内容を含まない。
    -   要件定義書の記録は、通常の進め方とその理由になる。
    -   設計と計画の決定のためだけに作るか変えた ADR の変更は、PR から外れる。
    -   要件の決定と、設計か計画の決定の両方で変えた ADR は、要件の決定の分だけを残す。
    -   同じ実行で人に確かめ済みの設計と計画の決定は、失われず、後で `/mkarch`・`/mkplan` が読める場所に残る。
- **AC-19**: 戻した後の PR を `/runpr` でマージすると、要件定義書が `approved` になり、マージの後は `/mkarch` を勧める。以後は通常の進め方で進む。
- **AC-20**: 3 文書の PR をマージした後は、進め方を戻さない。マージの後に決定を変えるときは、通常の進め方と同じく、`docs/dev/conventions/requirements_process.md` の「Editing an approved document」に従う（除外に当たる決定は AC-16 による）。

#### F-005: 適用の範囲と文書

**Acceptance Criteria**:
- **AC-21**: 進め方の記録を持たない要件定義書のタスク（この変更の前に要件定義書を書いたタスク）では、`/mkarch`・`/mkplan`・`/runplan` は通常の進め方として振る舞う。
- **AC-22**: 進め方の記録が、定めた値（簡易な進め方・通常の進め方）のどちらでもないとき、または文書の状態と食い違うとき（例：簡易な進め方なのに、マージした後に設計書か計画書がない）は、コマンドは止まって報告する。どちらかの進め方と推測して進めない（`CLAUDE.md`「Reject, don't normalize」）。
- **AC-23**: `docs/dev/conventions/requirements_process.md` は、次のことを述べる。
    -   簡易な進め方の流れ（「Review Flow」の通常の流れと並べて示す形）。
    -   省かないものと省いてよいもの。
    -   除外に当たる変更。#744 で軽量プロセスの節が消えた後も、除外の一覧はこの記述に残る。
    -   通常の進め方へ戻す手順。

    `CLAUDE.md` の「Requirements and Acceptance Criteria」と、「Claude Commands」の `/mkreq`・`/mkarch`・`/mkplan` の説明は、簡易な進め方に触れる。`docs/translation_glossary.md` は、「簡易な進め方」と「通常の進め方」を定める。
- **AC-24**: 変更後に、`make test` と `make lint` が通る。コマンドの定義と規約を読む既存の文書のテストを含む。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   N/A。製品の実行時の処理は変わらない。

### 4.2. セキュリティ (Security)
-   N/A。本タスクは、エージェントの開発の手順だけを変える。外部コマンドの呼び出し、秘密、キャッシュ、ネットワークへの送信、信頼できないテキストの埋め込みのどれにも触れない（`.claude/commands/_context.md` の「Conditional-guide trigger」）。
-   セキュリティにかかわる変更を誤って簡易な設計で通さないように、F-003 で、セキュリティの規則と前提、信頼の境界、外部への依存を変える変更を、簡易な進め方から外す。
-   通常の進め方へ戻すことは、人の答えか指示でだけ行い、レビューのスレッドの本文では行わない（AC-17）。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   簡易な進め方の `/mkreq` が途中で止まっても、走らせ直して続けられる（AC-12）。
-   進め方の記録が壊れているときは、推測せずに止まる（AC-22）。

### 4.4. 互換性 (Compatibility)
-   進行中のタスクは、今の通常の進め方のまま進む（AC-21）。CLI・サーバ・拡張の振る舞いは変わらない。

### 4.5. 保守性 (Maintainability)
-   簡易な進め方は、機械的な判定のスクリプトとそのテストを持たない（AC-15）。軽量プロセスで維持のコストの大半を占めた部分を作らないためである（issue #743）。
-   簡易な進め方の手順は、通常の進め方の手順（決定の確かめ方、レビューのチェックリスト、PR の引き渡し）を使い回し、同じ手順を 2 か所に書かない（`CLAUDE.md` の「DRY」）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   新しいタスクの決定は、ADR の規約（`docs/dev/conventions/adr.md`）に従って ADR-0040 に記録する。

簡易な進め方は、次の方針の例外である。どの例外も、簡易な進め方を記録したタスクに限る。

| 方針 | 場所 | 例外の内容 | 理由 |
|---|---|---|---|
| 前の文書が `approved` になるまで次の文書を書き始めない | `docs/dev/conventions/requirements_process.md:11-13`（「LLM Constraints」）、`CLAUDE.md`「Requirements and Acceptance Criteria」の「the next one is not started until a human reviewer sets the previous one to `approved`」 | 設計書と計画書を、要件定義書の承認の前に同じ PR で書く。実装の前の承認は残す（AC-13） | 文書の PR の往復の待ちを減らす（1 章の決定） |
| 3 文書を 1 本ずつ PR にする | `docs/dev/conventions/requirements_process.md:85`（「Review Flow」） | 3 文書を 1 本の PR にする（AC-04） | 同上 |
| 設計書のセルフレビューは panel で行う | `.claude/commands/mkarch.md:78` | 1 人のレビュアーで行ってよい（AC-06） | issue #743 の決定 |
| 設計書に Mermaid 図を書く | `.claude/commands/mkarch.md:69`、`docs/dev/conventions/requirements_process.md:671-691` | 図を必須にしない（AC-06） | 1 章の決定 |
| 設計書と計画書の必須の節 | `docs/dev/conventions/requirements_process.md:666-776` | 当てはまらない節は、見出しを残して N/A とその理由だけを書く（AC-06） | issue #743 の決定 |

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。設計書・計画書は、用語集のアーキテクチャ設計書・実装計画書を本書で短く呼ぶ名である。
-   **通常の進め方**: 要件定義書・設計書・計画書を 1 本ずつ別の PR で作り、前の文書が `approved` になってから次の文書を書く、今の進め方。用語集には AC-23 で足す。
-   **簡易な進め方**: 3 文書を、変更の規模に合わせた簡易な内容で、`/mkreq` が 1 本の PR で作る進め方。人は、3 文書を 1 回のマージの質問で承認する。用語集には AC-23 で足す。
-   **3 文書の PR**: 簡易な進め方で `/mkreq` が開く、3 文書を含む 1 本の PR。
-   **除外**: 簡易な進め方を選べない変更（F-003）。
-   **panel**: 役割を分けた 2 人以上のレビュアーによるセルフレビュー（`.claude/commands/_lib/review-subagent-pattern.md` の「Panel mode」）。コマンドの定義の名をそのまま使う。
-   **軽量プロセス**（lightweight process）: タスク文書を作らず、issue の仕様のコメントをもとに 1 本の PR にする進め方（`docs/dev/conventions/requirements_process.md`「Lightweight Process」）。簡易な進め方とは別のもので、#744 で削除する。
