# 設計への申し送り：タスク番号と ADR 番号が並行して重複しないようにする

## 本書の位置づけ

[01_requirements.md](01_requirements.md) の作成の過程で挙がった事項のうち、要件（観測できる振る舞い）ではなく、設計で決める事項、または設計で注意すべき事項をまとめる。`02_architecture.md` は、各項目について、採った手段か、扱わない理由を記録する。本書の手段は候補であり、対応する AC を満たす限り、設計で別の手段を選んでよい。

## H-01: 番号の記録を置く ref の名前空間

**懸念:** 案 A をとる場合、番号の記録を置く ref の名前空間を決める必要がある。候補は tag（例：`refs/tags/task-number/NNNN`、`refs/tags/adr-number/NNNN`）とブランチである。

**重要な理由:**

-   保護された ref の ruleset が、その名前空間での作成を拒むことがある。cloud のセッションの権限でも作れるかも確かめる（F-005）。
-   ブランチにすると、`chief` がブランチ名からタスクを読む規則（`internal/chief/task.go:739` の `featureBranch`）と、`/mkreq` が使用中の番号を見る `git branch -a` に、記録用のブランチが混ざる。
-   tag にすると、`git fetch --tags` や、tag を辿る既定の fetch で、記録用の tag が各クローンに増える。
-   番号の記録を消されると、その番号が再び使われうる。`CLAUDE.md` で道具以外の書き換えに承認を要ることにした（AC-21）が、ruleset で記録の作成と削除を道具の経路に限れるかも調べる。

**候補:** tag の名前空間を番号の空間ごとに分ける。ruleset の設定を、設計の段階で読み取って確かめる。

**関連:** F-001、F-002、F-005、AC-04、AC-15

## H-02: 方式の比較（A・B・D）と番号の空間ごとの選択

**懸念:** issue は案 A（番号だけの ref の予約）を第一の候補とし、A〜D を比べて ADR に残すことを求めている。要件定義では、タスク番号について案 B（タスク番号を issue 番号にする）も設計で比べることにした（要件定義書の「要件定義の際に決めたこと（2026-11-17）」）。

**重要な理由:**

-   案 B は、1 つの issue から 2 つのタスクを作れなくなる。issue 番号は今 900 台であり、4 桁の範囲（AC-04）を超えるまでの余裕も見積もる必要がある。番号は作った順の連番でなくなる。
-   案 B では、同じ issue に 2 つの `/mkreq` を走らせると同じ番号になり、ブランチ名はスラッグで違うので、どちらも成功する（AC-01 に反する）。中断したタスクの番号は二度と決まらないので、その issue からはタスクを作れなくなる（AC-03 との兼ね合い）。
-   案 B は ADR 番号には使えないので、案 B をタスク番号に採ると、タスク番号と ADR 番号で仕組みを共有できない（要件定義書 4.5）。
-   案 D は、2 つのセッションが同時に確かめ直すと重複が残る（issue の表）。

**候補:** A・B・D を、AC-01〜AC-15 を満たせるか、cloud のセッションで動くか（F-005）、共有できるかで比べる。採らなかった案と理由を ADR-0051 の「採らなかった案」に書く（AC-25）。

**関連:** F-001、F-002、AC-25

## H-03: 道具の言語と置き場所（ADR-0014 との関係）

**懸念:** issue は `_lib/` の配下のスクリプトを想定している。一方、[ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md) は、判定と副作用を持つ開発の道具を Go で書いてテストを持つと決めている。かつて bash を選んだ [ADR-0012](../../dev/adr/0012-lightweight-check-in-bash.md) は廃止されている。

**重要な理由:** 番号の判定（使用中の番号の集め方、どの失敗で次の番号を試すか）は、テストで壊して確かめたい判定である（4.5「GitHub の API を呼ばないテスト」）。

**候補:** Go の道具（`cmd/<名前>` と `internal/<名前>`）にし（その場合、ADR-0014 の「決定」にある道具の一覧とインストールの規則も更新する）、GitHub と git の呼び出しを fake に差し替えてテストする。bash にするなら、ADR-0014 の例外として理由を ADR-0051 に記録する。道具のインストールの扱い（`main` から入れる）も決める。

**関連:** F-001、F-002、AC-05、AC-07

## H-04: 「番号がすでに使われている」失敗の見分け方

**懸念:** GitHub の ref 作成の API（`POST /repos/{owner}/{repo}/git/refs`）は、同じ名前の ref があると 422 を返す。ただし、422 はほかの検証の誤りでも返る。

**重要な理由:** 4.2 の規則で、「その番号がすでに使われている」と確かめた失敗だけが、次の番号を試す理由になる。応答の `message` の自由文で見分けると、`CLAUDE.md` の「Declare, don't infer」に反し、文言が変わったときに誤って次の番号へ進むか、止まる。

**注意:** `git push` で記録の tag を作る場合、同じ名前の tag を同じオブジェクトに向けて 2 つのクローンから push すると、2 回目は `[up to date]` で終了コード 0 になり、拒否されない（Fable の部分レビューの手元の実験で確かめた）。この場合、終了コードでは成功を判定できない。記録が呼び出しごとに一意なオブジェクトを指すようにするか、porcelain の出力で新しく作られたこと（`*`）を読む必要がある。REST の ref 作成は、同じ SHA でも 422 を返すと考えられるが、設計で確かめる。

**候補:** 422 を受けたら、その名前の ref があるかを別の読み取りで確かめ、あれば次の番号へ進み、なければ止める。`git push` で tag を作る方式なら、終了コードと出力の扱いを同じ観点で決める。

**関連:** AC-06、AC-07、4.2

## H-05: 使用中の番号の集め方と、記録の前からある番号

**懸念:** 試す最初の番号の決め方である。既存のタスク（0001〜0100）と ADR（0001〜0051）、この仕組みより前に作られたブランチや PR にある番号には、記録の ref がない。

**重要な理由:** 記録の ref だけを見ると、記録のない使用中の番号を決めてしまう（AC-02・AC-11）。

**候補:** 「記録の ref の最大」「`origin/main` の最大」「`origin` のブランチとオープン PR にある番号の最大」の最大の次から試す。または、既存の番号の記録を一度だけまとめて作る。ADR 番号では、`origin` のブランチとオープン PR のヘッドにある `docs/dev/adr/` の番号も使用中とする（AC-11。#927 の例）ので、その読み方も決める。

**関連:** AC-02、AC-10、AC-11

## H-06: 記録の ref に何を持たせるか

**懸念:** 番号の記録を残すことにした（AC-03）。ref が何を指し、どんな情報を持つかを決める。

**重要な理由:** 欠番になった番号がどのタスクや PR のために決まったのかを、後で辿れると調べやすい。ただし、ref の内容は推測の材料にせず、番号の判定には ref の名前だけを使う（「Declare, don't infer」）。

**候補:** 決めたときの `origin/main` の commit を指す軽量の tag にする。ただし H-04 の注意のとおり、2 つのセッションが同じ commit を指す同じ名前の tag を push すると両方が成功しうるので、`git push` を使うなら呼び出しごとに一意な内容の注釈付きの tag にする。または、issue 番号やブランチ名を注釈に持つ注釈付きの tag にする。

**関連:** AC-03

## H-07: cloud のセッションでの実行の前提

**懸念:** cloud のセッション（claude.ai/code）で、`gh` が使えるか、認証されているか、tag やブランチを `origin` に push できるかは確かめていない。番号を決める道具を `codexreview` のように利用者が `main` から入れる形にすると、cloud のセッションには入っていない。cloud のセッションは自分のセッションのブランチ（`claude/<名前>` の形で、feature branch の形でない）にしか push できない可能性もある（確かめていない）。

**重要な理由:** 番号を決められなければ止める（AC-06）ので、cloud で書き込めないと、cloud では `/mkreq` と ADR の作成が常に止まる。

**候補:** 設計の段階で、cloud のセッションの権限と、道具を cloud でどう入れるか（入れられないときは AC-06 のどの理由で止まるか）、feature branch の形のブランチを作れるかを調べる。AC-22 の手動の確かめの手順（どのリポジトリ・どの名前空間で試し、試した記録をどう片付けるか）も決める。試しに作った番号の記録は残る点に注意する。

**関連:** F-005、AC-22

## H-08: 移行の順序

**懸念:** 道具と新しい `mkreq.md` が `main` に入った後も、古い `mkreq.md` を持つクローンのセッションは、「使用中の最大値 + 1」で番号を計算し続ける。作業中の PR のブランチも、`main` を取り込むまで古い `adr.md` を持ち、ADR の番号を手で選び続ける（ADR-0039 により、ブランチが `main` を取り込むのは主に衝突を解くときである）。これらの番号は番号の記録に残らない。

**重要な理由:** 古い手順で決めた番号と、道具が決めた番号が重なりうる（AC-01・AC-02）。

**候補:** 道具が、記録のない使用中の番号も見る（H-05）ことで、道具の側の重なりを防ぐ。古い手順の側が道具の決めた番号を取る重なりは、マージの前の確かめ（F-007、H-10）で見つける。そのうえで、PR の順序と、マージの後に各クローンが `main` を取り込むまでの扱いを実装計画で決める。

**関連:** AC-01、AC-02、AC-11

## H-09: 時間と件数の上限の値

**懸念:** 要件は、ネットワークの呼び出しの時間、試行の回数、一覧の件数と大きさに上限を設けることと、番号が不自然に跳んだと見なす幅（AC-09）があることだけを定め、値を決めていない（要件定義書 4.1〜4.3、AC-07）。

**重要な理由:** 値によって、番号の空間が大きくなったときに一覧が上限で切れて止まるか、遅い回線で止まるかが変わる。

**候補:** 今の番号の数（タスク約 100、ADR 約 50）と、ブランチと PR の数から見積もって値を決め、上限で切れたことを見つける手段（ページの続きの有無など）も決める。

**関連:** AC-07、4.1、4.2、4.3

## H-10: マージの前の確かめの場所と、移行の間の扱い

**懸念:** F-007 は、PR が加える番号に記録があることと、最新の `origin/main` で使われていないことを、マージの前に確かめることを求める。確かめる場所（CI のジョブか、`/runpr` と `/mergepr` か）と、比べる `origin/main` の新しさを決める必要がある。

**重要な理由:** CI は PR のブランチの時点の `main` と比べるので、後から `main` に入った同じ番号を見ない。`/runpr` だけで確かめると、`/runpr` を通らない手のマージで漏れる。番号の記録の仕組みより前に作られた作業中の PR（#927、#938 など）は記録を持たないので、そのままでは AC-27 で止まる。

**候補:** マージの直前に最新の `origin/main` と記録の一覧を読む確かめを `/mergepr` に置き、CI のジョブでも同じ確かめを PR の時点で行う。仕組みより前の PR は、記録を後から作るか、決めた日より前に作られた PR を対象から外すかを決める。

**関連:** F-007、AC-27、AC-28、AC-29、H-08
