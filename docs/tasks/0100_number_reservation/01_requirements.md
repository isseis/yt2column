## 1. 概要 (Overview)

**目的:** 本書は、並行して作られるタスクと ADR が同じ番号を取らないようにするための要件を定義する（[#917](https://github.com/isseis/yt2column/issues/917)）。対象は、`/mkreq` が決めるタスク番号と、どの PR でも作られうる ADR の番号である。

**背景:**

今のタスク番号は、`/mkreq` の step 2 が「使用中の最大値 + 1」として計算する（`.claude/commands/mkreq.md:68-75`）。使用中の番号として見るのは、`origin/main` の `docs/tasks/`、ローカルと `origin` のブランチ、オープン PR のヘッドブランチである。番号を計算してから step 3 でブランチを `origin` に作るまでの間には、排他がない。2 つのセッションが同じ時点の状態から計算すると、同じ番号になる。ブランチ名には `<slug>` が入るので（`.claude/commands/_context.md` の「Feature branch name」）、`0093-foo-01` と `0093-bar-01` は名前がぶつからず、どちらのブランチの作成も成功する。オープン PR による確認は、PR を作る段階まで効かない。

ADR の番号は、「`main` と、その PR のブランチにある最大の番号の次」と決めている（`docs/dev/conventions/adr.md` の「Location and naming」の Number）。ほかの PR のブランチにある番号は見ない。実際に、ADR-0050 を別の PR（#927）が使っていたため、#934 では空いている番号を手で確かめる必要があった。番号の衝突は、`main` を取り込むときの付け替えで直している（`docs/dev/conventions/adr.md` の「Taking in `main`」）。また、`main` で番号が重複したり抜けたりすると `TestADRRecords` が失敗する（`cmd/yt2column/adr_test.go:336-353`）。

Claude Code は、ローカルの worktree だけでなく cloud のセッション（claude.ai/code）でも使う。cloud のセッションは別のクローンで動くので、ローカルのロックでは重複を防げない（issue #917 の追記）。

対応 issue: [#917](https://github.com/isseis/yt2column/issues/917)（関連: #927・#934。ADR 番号の重複の実例）

**本書の記述範囲:** 本書が定めるのは、観測できる振る舞いである。具体的には、番号が重複しないこと、番号を決められないときに何が起きて利用者に何が示されるか、ADR 番号の欠番の扱い、承認の扱い、文書に何を書くかを定める。番号を一意にする仕組みは、設計（`02_architecture.md`）で比べて決める。比べる対象は、issue の案 A（番号だけの ref の予約）と案 B（タスク番号を issue 番号にする）、案 D（再確認）である。ref の名前空間、道具の言語と置き場所、テストの手段も設計で決める。設計に申し送る事項は [design_handoff.md](design_handoff.md) にある。「番号の空間」「番号を決める道具」「番号の記録」「欠番」の意味は §6 で定義する。

**issue #917 で決めたこと:**

-   **重複を防ぐ範囲:** 並行して実行した `/mkreq` が、同じタスク番号を取らないようにする。ADR 番号にも同じことを求める（issue の追記）。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **別のクローン・別の環境の間でも重複しない:** cloud のセッションでも Claude Code を使うので、別のクローンや別の環境の間でも番号が重複しないことを要件とする。案 C（git の共通ディレクトリでのローカルのロック）は、この要件を満たさないので採らない（issue の追記）。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **番号の判定はエージェントではなく道具が行う:** 番号を一意にする判定は道具で行い、エージェントには決まった番号だけを返す（issue の「方針（案）」）。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **番号の種類ごとに分ける:** タスク番号と ADR 番号は、別々の番号の空間に持つ（issue の追記）。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **ADR 番号を決める手順を ADR の規約に書く:** ADR 番号はどのコマンドの PR でも作られうるので、番号を決める手順を ADR の規約（`docs/dev/conventions/adr.md` の「Location and naming」）に書く（issue の追記）。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **決定を ADR に残す:** 方式の比較（A〜D）を含めて ADR に記録する（issue の「範囲」）。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) を作る。
-   **既存の番号は振り直さない**（issue の「範囲」）。ADR の判断: なし（今の番号を変えないという、このタスクの範囲の決定であり、ほかのタスクを縛らない）。

**要件定義の際に決めたこと（2026-11-17）:**

-   **プロセス:** full process をとる。番号を一意にする新しい仕組みを作り、その影響は `/mkreq`、ADR の規約、`_lib/settle-decisions.md`、`CLAUDE.md`、`TestADRRecords` に及ぶ。決めることも多く、方式の比較を設計に残すためである。ADR の判断: なし（このタスクの進め方であり、タスクの中で閉じる）。
-   **除外の判断:** 除外される変更（`docs/dev/conventions/requirements_process.md` の「Simple Process」の Excluded changes）には当たらない。GitHub は今も `gh` と `git push` で使っている外部サービスであり、新しい外部サービスや依存を加えない。`docs/dev/security.md` の規則と前提を変えず、レビューのスレッドの扱い（[ADR-0015](../../dev/adr/0015-untrusted-review-threads.md)）にも触れない。`CLAUDE.md` の「Tool Execution Safety」に常設の承認を 1 つ加えるが、承認するのは決まった形の呼び出しだけである。レビューのスレッドや Bot への依頼の扱いは変わらない。除外の変更に当たると判断しても当たらないと判断しても、full process をとる。ADR の判断: なし（このタスクの進め方の判断であり、タスクの中で閉じる）。
-   **番号を決められなければ止める:** 番号を一意に決められないとき（権限がない、ネットワークの失敗、cloud のセッションから書き込めないなど）は、番号を決めずに止めて理由を示す。従来の計算に戻して続けることはしない（F-001、F-002）。目的は重複を防ぐことであり、代わりの計算で続けると重複の余地が戻るためである。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) を作る。
-   **ADR 番号の欠番を許す:** ADR 番号に欠番があってもよいことにし、重複だけを禁じる（F-003）。番号を決めた順とマージの順が違うとき、`main` には先にマージされた番号だけが載り、間の番号が一時的に欠ける。取り下げた PR の番号は欠けたまま残る。欠番を禁じたままでは、このどちらでも `TestADRRecords` がすべての PR で失敗するためである。今の規約の「欠番なし」（`docs/dev/conventions/adr.md` の Number）を変える。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **一度決めた番号は使い回さない:** 番号を決めた記録は、タスクや PR が終わった後も、中断した後も残す。同じ番号が二度と使われないようにするためである。中断したタスクの番号は欠番になる（F-001、F-002）。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **番号を決める道具の呼び出しを常設の承認にする:** 番号を決める道具の呼び出しは、`CLAUDE.md` の「Tool Execution Safety」が定める形で行う限り、利用者に確かめずに実行してよいことにする（F-004）。ADR 番号はどのコマンドの PR でも、手で作る PR でも決めるので、コマンドごとの承認では足りないためである。`codexreview` と同じ扱いである。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **番号の形は設計で比べる:** タスク番号を作った順の連番にするかは、要件では決めない。案 B（タスク番号を issue 番号にする）も設計で比べる。要件で決めるのは、タスク番号が 4 桁の数字であること（ディレクトリ名とブランチ名の形を変えない）までである（F-001）。ADR 番号は issue に結びつかないので、案 B の対象にならない。ADR の判断: 設計で決める方式を [ADR-0051](../../dev/adr/0051-number-reservation.md) に書く（AC-23）。
-   **cloud のセッションからの確かめを受け入れ基準に含める:** cloud のセッションから番号を決められるかを、手動で 1 回確かめる（F-005）。決められない場合は、止まって理由が示されることを確かめ、制約として記録する。cloud でも使うことが、この要件の前提だからである。ADR の判断: なし（このタスクの確かめ方であり、タスクの中で閉じる。結果が制約になるときは ADR-0051 の「結果」に書く）。
-   **付け替えの番号も道具で決める:** `main` を取り込むときの ADR 番号の付け替え（`docs/dev/conventions/adr.md` の「Taking in `main`」の手順 2）と、`main` で `TestADRRecords` が失敗したときの直しでも、新しい番号は道具で決める（F-002）。手で選ぶと、ほかの PR が決めてまだマージしていない番号と重なり、防ごうとしている重複が戻るためである。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。
-   **使用中とみなす PR は、このリポジトリの中にヘッドがあるものに限る:** fork からの PR のブランチ名は、使用中の番号として数えない（F-001）。fork の PR のブランチ名はリポジトリの外の人が付けられ、数えると、番号を押し上げて 4 桁の範囲を使い切らせることができるためである。ADR の判断: [ADR-0051](../../dev/adr/0051-number-reservation.md) に含める。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   並行して実行した `/mkreq` が、同じタスク番号を取らないようにする。別のクローンや cloud のセッションの間でも同じである。
-   並行して作られる ADR が、同じ ADR 番号を取らないようにする。ADR を作るのがどのコマンドの PR でも、手で作る PR でも同じである。
-   番号を一意に決められないときは、推測した番号で進めずに止まり、理由を示す。

### 2.2. スコープ (In Scope)

-   `/mkreq` のタスク番号の決め方の変更と、番号を一意に決める道具の追加（F-001）。
-   ADR 番号の決め方の変更。ADR の規約に、番号を決める手順と、付け替えの番号の決め方を書く（F-002）。
-   ADR 番号の欠番の許容。規約と `TestADRRecords` の変更（F-003）。
-   番号を決める道具の呼び出しの承認の扱い（`CLAUDE.md` の「Tool Execution Safety」と、`/mkreq` の Authorization）（F-004）。
-   cloud のセッションからの手動の確かめ（F-005）。
-   決定を記録する ADR の新設（方式の比較を含む）と、関係するガイドとコマンド文書の更新（F-006）。

### 2.3. スコープ外 (Out of Scope)

-   既存のタスク番号と ADR 番号の振り直し（issue の「範囲」）。
-   `fixprguard` などの道具の `--protocol` の番号。issue #917 は、タスク番号と ADR 番号だけを対象にしているためである。
-   `main` を取り込むときの ADR の付け替えの規則のうち、番号の決め方（AC-12）以外の部分（`docs/dev/conventions/adr.md` の「Taking in `main`」の手順 1・3 と、手順 2 の文書の直し方）。この仕組みより前に作られた ADR や、仕組みを通さずに番号を付けた ADR の衝突に備えて残す。
-   ブランチ名の連番 `-<NN>`（`_lib/task-pr-handoff.md` の Part A step 4）と、issue に結びつける PR の数の上限への対処（同 Choosing the issue to link）。どちらも同じタスクの中の番号であり、ほかのタスクとは衝突しないためである。
-   番号を決めない `/mkreq` の経路：`[task]` で既存のタスクのディレクトリを指定する経路（`.claude/commands/mkreq.md:65-67`）と、止まった simple process の実行を続ける経路（`_lib/simple-process.md` の「Resuming a stopped run」）。どちらも番号はすでに決まっているためである。
-   コマンドを使わずに手でタスクのディレクトリを作ること。タスクのディレクトリは `/mkreq` が作るので（`CLAUDE.md` の「Requirements and Acceptance Criteria」）、手で作る経路は対象にしない。
-   番号の記録を誰かが消すことへの備え。記録を消す権限はリポジトリへの書き込みの権限と同じで、その権限を持つのは利用者だけだからである。記録を ruleset で守れるかは設計で調べる（[design_handoff.md](design_handoff.md) H-01）。
-   古い `mkreq.md` を持つクローンで動くセッションへの対処。移行の順序は実装計画で決める（[design_handoff.md](design_handoff.md) H-08）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: タスク番号を一意に決める

`/mkreq` は、新しいタスクの番号を、ほかのセッションが決めた番号と重ならないように決める。

**Acceptance Criteria**:

-   **AC-01**: 2 つの `/mkreq` が同じ時点の状態から番号を決めても、2 つは異なる番号を得る。2 つが別のクローンにあっても同じである。
-   **AC-02**: 決まった番号は、次のどの番号とも違う：`origin/main` の `docs/tasks/` にある番号、ローカルと `origin` のブランチにある番号、ヘッドがこのリポジトリの中にあるオープン PR のヘッドブランチにある番号。fork からの PR のヘッドブランチは数えない。
-   **AC-03**: 一度 `/mkreq` が決めた番号は、そのタスクが中断しても（ブランチやディレクトリが消されても）、後の `/mkreq` では決まらない。
-   **AC-04**: 番号は 4 桁の数字である。タスクのディレクトリ名 `NNNN_<name>` とブランチ名 `<user>/NNNN-<slug>-<NN>` の形は変わらない。`chief` がブランチ名からタスクを読む規則（`internal/chief/task.go:739`）は、変えなくても、この形のブランチ名をそのまま読める。
-   **AC-05**: 番号は道具が決め、`/mkreq` は道具が返した番号だけを使う。`mkreq.md` の step 2 には、エージェントが自分で番号を計算する手順が残らない。
-   **AC-06**: 番号を決められないとき、`/mkreq` は止まり、ブランチもタスクのディレクトリも作らない。利用者には、番号を決められなかったことと、その理由の種類と、次にすること（または、それが書かれたガイドの節。AC-24）を示す。理由の種類は、少なくとも次を区別する：「権限がない」「ネットワークまたは GitHub の失敗」「試す回数の上限に達した」「4 桁の番号が残っていない」「GitHub やリポジトリから受け入れない形のデータを受け取った」。決まっていない番号を推測して示さない。
-   **AC-07**: 番号を決めるための試行を繰り返すときは、回数に上限がある。上限に達したら AC-06 のとおり止まる。
-   **AC-08**: 次に試す番号が 9999 を超えるときは、番号を決めずに AC-06 の「4 桁の番号が残っていない」で止まる。5 桁の番号は決まらない。

#### F-002: ADR 番号を一意に決める

新しい ADR の番号と、付け替えた後の ADR の番号を、ほかの PR が決めた番号と重ならないように決める。

**Acceptance Criteria**:

-   **AC-09**: 2 つの PR が同じ時点の状態から新しい ADR の番号を決めても、2 つは異なる番号を得る。片方の番号が、もう片方の PR のブランチにしかない場合も同じである（#927 と #934 の例）。
-   **AC-10**: 決まった番号は、次のどの番号とも違う：`origin/main` の `docs/dev/adr/` にある番号、`origin` のブランチの `docs/dev/adr/` にある番号、ヘッドがこのリポジトリの中にあるオープン PR のヘッドの `docs/dev/adr/` にある番号、一度決まった番号（その PR が中断した場合を含む）。
-   **AC-11**: `docs/dev/conventions/adr.md` の「Location and naming」の Number に、新しい ADR の番号は道具で決めることと、その呼び出しの形が書かれている。これはコマンドが作る PR にも、手で作る PR にも当てはまる。`_lib/settle-decisions.md` の ADR を作る手順は、この規約に従って番号を決める。
-   **AC-12**: `docs/dev/conventions/adr.md` の「Taking in `main`」の手順 2（番号の付け替え）と「When `TestADRRecords` fails on `main`」の直しでは、付け替えた後の番号を AC-11 と同じ形の呼び出しで決める。
-   **AC-13**: 番号を決められないときは、推測した番号で ADR のファイルを作らず、付け替えもせずに止まり、理由の種類を AC-06 と同じく示す。番号が 9999 を超えるときも AC-08 と同じく止まる。
-   **AC-14**: タスク番号と ADR 番号は互いに影響しない。ある番号を ADR 番号として決めても、同じ番号がタスク番号の空間で空いていれば、タスク番号として決まりうる。逆も同じである。

#### F-003: ADR 番号の欠番を許す

ADR 番号の欠番を誤りとして扱わない。重複は今までどおり誤りとして扱う。

**Acceptance Criteria**:

-   **AC-15**: ADR 番号に欠番があっても、`TestADRRecords` は欠番を理由に失敗しない。
-   **AC-16**: 2 つの ADR のファイルが同じ番号を持つと、`TestADRRecords` は今までどおり失敗する。
-   **AC-17**: `docs/dev/conventions/adr.md` の変更は、次の差分に限られる。
    -   「Location and naming」の Number から「`0001` から欠番なしで続く」という規則を除き、番号の決め方を AC-11 の内容に置き換える。番号を使い回さないこと（廃止した ADR の番号も含む）は残す。
    -   「Taking in `main`」の手順 2 の「次に空いている番号」を、AC-12 の決め方に置き換える。
    -   「When `TestADRRecords` fails on `main`」から、番号の欠落（missing number）を失敗の原因として挙げる記述を除き、直しの番号の決め方を AC-12 の決め方にする。重複の記述は残す。
    -   ADR の索引の説明の「番号の順」に並べる規則は変えない。

#### F-004: 番号を決める道具の呼び出しの承認

番号を決める道具の呼び出しを、決まった形で行う限り、利用者に確かめずに実行してよいことにする。

**Acceptance Criteria**:

-   **AC-18**: `CLAUDE.md` の「Tool Execution Safety」に、番号を決める道具を決まった形で呼ぶ限り、利用者に確かめずに実行してよいことが書かれている。道具がネットワークに書き込む方式なら、何を書き込むかも書かれている。
-   **AC-19**: `mkreq.md` の Authorization と、ADR 番号を決める手順（AC-11・AC-12）の呼び出しの形は、AC-18 の形と一致する。それ以外の形での呼び出しや、道具を介さない同じ操作は、常設の承認に含まれない。

#### F-005: cloud のセッションからの確かめ

cloud のセッションから番号を決められるかを確かめる。

**Acceptance Criteria**:

-   **AC-20**: cloud のセッション（claude.ai/code）で、番号を決める道具を 1 回実行し、その結果を記録する（手動）。決められた場合は、決まった番号が AC-02・AC-10 の条件を満たすことを確かめる。決められなかった場合は、AC-06 のとおり止まって理由の種類が示されることを確かめ、cloud では番号を決められないことを制約として ADR-0051 の「結果」とガイドに記録する。

#### F-006: 文書

決定を ADR に記録し、道具の使い方を利用者が読む文書に書く。

**Acceptance Criteria**:

-   **AC-21**: 索引 `docs/dev/adr/README.md` に ADR-0051 の行がある。
-   **AC-22**: ADR-0051 の「決定」にある食い違いの記述（規約と `TestADRRecords` が、まだ欠番を誤りとし、番号を決める道具がまだないこと）は、その食い違いを直す PR で除かれる。
-   **AC-23**: ADR-0051 の「決定」は、本書の決定と設計で選んだ方式に一致する。「採らなかった案」には、設計で採らなかった方式（issue の A〜D のうち採らなかったもの）と、その理由がある。
-   **AC-24**: 番号を決める道具の使い方（呼び出しの形、止まったときの理由の種類と次にすること、cloud のセッションでの制約）が、利用者が読む文書に書かれている。置き場所は設計で決める。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   番号を決める処理は、番号を決める `/mkreq` の 1 回の実行で 1 度だけ行う。番号を決めない経路（2.3）では行わない。所要時間の上限は設計で決める（[design_handoff.md](design_handoff.md) H-09）。

### 4.2. セキュリティ (Security)

-   N/A（`docs/dev/security.md` の適用条件には当たらない。`yt-dlp` を起動せず、API キーを扱わず、キャッシュを読み書きせず、LLM API に送らず、信頼できない文字列をプロンプトや記事に入れない）。
-   ただし、開発ツールの扱いとして次を守る。
    -   番号を決める道具は、GitHub の認証の情報（`gh` のトークンなど）を出力に出さない。
    -   道具が番号を決めるために読む外部のデータは、どの方式でも、受け入れない形のものを読み飛ばさずに拒否する（`CLAUDE.md` の「Reject, don't normalize」）。拒否したときは、AC-06 の「GitHub やリポジトリから受け入れない形のデータを受け取った」で止まる。対象と受け入れる形は次のとおりである。
        -   ブランチ名と PR のヘッドブランチ名：今の feature branch の形（`.claude/commands/_context.md` の「Feature branch name」）のものだけから番号を読む。この形でない名前は、タスクのブランチではないので番号を読まない。拒否はしない。
        -   ディレクトリの一覧：`docs/tasks/` の下の `NNNN_<name>` と、`docs/dev/adr/` の下の `NNNN-<kebab>.md` から番号を読む。
        -   方式が番号の記録を持つ場合、その記録の一覧：記録の名前空間の下には 4 桁の数字だけの名前を受け入れ、それ以外の名前があれば拒否する。
    -   一覧を読むときは、件数と大きさに上限を設ける。一覧が上限で切れたこと、またはページに分かれて残りを読めなかったことを見つけたら、読めた分だけで番号を決めずに、AC-06 の「GitHub やリポジトリから受け入れない形のデータを受け取った」で止まる。上限の値は設計で決める（[design_handoff.md](design_handoff.md) H-09）。
    -   番号を決める試行が失敗したときは、「その番号がすでに使われている」と確かめられた失敗だけを、次の番号を試す理由にする。それ以外の失敗は、すべて止める理由にする（AC-06）。確かめ方は設計で決める（[design_handoff.md](design_handoff.md) H-04）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   ネットワークへの呼び出しには時間の上限を設ける。値は設計で決める（[design_handoff.md](design_handoff.md) H-09）。
-   番号を決めた後に `/mkreq` が止まった場合、その番号は欠番として残る（AC-03）。この欠番は誤りではない。

### 4.4. 互換性 (Compatibility)

-   タスクのディレクトリ名とブランチ名の形を変えない（AC-04）。`chief` がブランチ名からタスクを読む規則（`internal/chief/task.go:739`）は、そのまま働く。
-   すでにある番号（タスク 0001〜0100、ADR 0001〜0051）と、この仕組みより前に作られたブランチや PR にある番号は、使用中として扱う（AC-02・AC-10）。振り直しはしない。

### 4.5. 保守性 (Maintainability)

-   番号の判定は道具の中にあり、コマンドの文書には呼び出しの形だけを書く。タスク番号と ADR 番号で道具や仕組みをどこまで共有するかは、選ぶ方式によるので、設計で決める（[design_handoff.md](design_handoff.md) H-02）。
-   道具の判定は、GitHub の API を呼ばないテストで確かめられる。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   別のクローンや cloud のセッションの間でも番号の一意性が効くことが要るので、一意性はサーバ側（GitHub）で保証する。ローカルのロックやファイルは使わない（issue #917 の追記）。
-   判定と副作用を持つ開発の道具は、Go で書いてテストを持つという方針がある（[ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md)）。issue は `_lib/` のスクリプトを想定している。どちらにするかは設計で決め、ADR-0014 の例外にするときは、その理由を ADR に記録する（[design_handoff.md](design_handoff.md) H-03）。

## 6. 用語集 (Glossary)

-   用語は `docs/translation_glossary.md` と統一する。
-   **番号の空間:** 番号の種類（タスク番号、ADR 番号）ごとに独立した、番号の集まり。ある空間で番号を決めても、ほかの空間には影響しない。
-   **番号を決める道具:** 番号の空間について、一意な番号を 1 つ決めて返す道具。名前、言語、置き場所、呼び出しの形は設計で決める。
-   **番号の記録:** 一度決めた番号を、使い回さないために残す記録。方式によって、何に残すかが変わる。
-   **欠番:** 一度決まったのに、そのタスクや ADR が `main` にない番号。中断したタスクや取り下げた PR の番号のように、ずっと欠けたままのものと、マージの順が番号の順と違うために一時的に欠けているものがある。
