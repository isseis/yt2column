## 1. 概要 (Overview)

**目的:** 本書は、次の 2 つの要件を定義する。1 つ目は、本番の構成・品質の目標・製品の制約・構成の比較を、プロジェクトに共通の文書（以下「共通の文書」。`docs/dev/production_profile.md`）にまとめること。2 つ目は、プロジェクトの文書での主経路（定義は §6）の書き方を、ブラウザ拡張の経路を主とするように改めること（[#488](https://github.com/isseis/yt2column/issues/488)）。

**背景:**

タスク 0008（コラム生成プロンプト）の最終の版の評価で、次のことが決まった（[0008 評価記録](../0008_column_prompt/02_evaluation.md) §6）。

-   **本番の構成:** 生成、字数の調整、検証・推敲の 3 つの段階を、すべて claude-opus-5-5（effort `high`）で行う。生成のテンプレートは v5 で、`prompts/` の既定のテンプレートになっている（0008 評価記録 §6.1・§6.5）。
-   **品質の目標:** 記事が必須の観点をすべて満たし、品質の観点に 1（不十分）がないこと。目標は、既定にするための関門ではなく、記事が目指す水準である（[0008 要件定義書](../0008_column_prompt/01_requirements.md) F-006）。最終の版では、10 件中 8 件（文言どおりの判定では 7 件）が目標を満たした（0008 評価記録 §6.2）。
-   **製品の制約:** 目標に届かなかった点と、この構成で起こりうる誤りや欠けの 8 項目である（0008 評価記録 §6.3）。

これらはタスクに固有の情報ではなく、プロジェクトに共通の情報である。ところが今は、タスクの評価記録の中にしかない。0008 評価記録 §6.5 は、タスクを終えた後に `docs/` の下の共通の文書へまとめる予定だと記録している。

最終の版の評価の記事は、CLI が yt-dlp で取得した字幕（キャッシュ）から生成した（0008 評価記録 §6.1・§6.2、0018 評価記録 §4.7.2）。ブラウザ拡張から送るコピーした字幕は、yt-dlp で取得した字幕とは素材が異なる。たとえば、区間が結合される、概要欄を開かずに送ると概要欄が途中で切れる、といった違いがある（0018 評価記録 §4.9.1）。

あわせて、文書での主経路の位置づけを直す。現在の文書は、次のように CLI を主な使い方として書いている。

-   README の冒頭は、本ツールを「YouTube 動画の URL を受け取る CLI」と説明し、字幕は yt-dlp で取得すると書いている（`README.md:3-15`）。パイプラインの図は `URL →` から始まる（`README.md:9`）。Requirements（`README.md:19-27`）と Usage（`README.md:29`）も CLI を前提にしている。
-   `docs/dev/project_overview.md` の冒頭は、本ツールを CLI ツールと説明している（`docs/dev/project_overview.md:3`）。決定済みの方針のうち、「実行形式」は CLI を先に書いている（同 `:10`）。「字幕取得」は yt-dlp を主として、コピーした字幕のパーサを例外として書いている（同 `:11`）。パイプラインの図は `URL →` から始まる（同 `:21`）。
-   `CLAUDE.md` の「Architecture Overview」の冒頭の一文は、本ツールを「A Go CLI」と書き（`CLAUDE.md:134`）、その下の図は `URL →` から始まる（`CLAUDE.md:137`）。
-   `docs/dev/security.md` の冒頭は、「yt2column はローカルで実行する CLI であり、利用者本人が入力（動画 URL）を与える」と書いている（`docs/dev/security.md:5`）。

実際の主経路は次のとおりである。ブラウザ拡張が、YouTube の文字起こしパネルからコピーした字幕を集める。Native Messaging のホストがそれを localhost サーバへ中継し、サーバが記事を生成して Webhook へ投稿する（[#43](https://github.com/isseis/yt2column/issues/43)。README「Localhost server」`README.md:448`、「Browser extension」`README.md:818`）。CLI は、LLM の呼び出しや投稿の処理を開発・検証するための補助の経路である。

対応 issue: [#488](https://github.com/isseis/yt2column/issues/488)（前提: [#490](https://github.com/isseis/yt2column/issues/490)・[#171](https://github.com/isseis/yt2column/issues/171)、関連: [#43](https://github.com/isseis/yt2column/issues/43)・[#146](https://github.com/isseis/yt2column/issues/146)）

**本書の記述範囲:** 本書が定めるのは、共通の文書の置き場所と載せる内容、および各文書（README・`project_overview.md`・`CLAUDE.md`・`security.md`・`prompts/README.md`・0008 評価記録）で何を書き直し、何を変えないかである。設計（`02_architecture.md`）に残すのは、共通の文書の節の構成と順序、README に加える Quick start の節の見出しの文言と手順の粒度、図の具体的な形、文書の値を検査するテストの形である。要件定義で挙がった設計上の論点は [design_handoff.md](design_handoff.md) に申し送る。

本タスクは、文書と、文書を読むテストだけを変える。コードの振る舞い、設定の既定値、テンプレートは変えない（2.3）。既定値の変更は #490（プロバイダとモデル）と #171（effort）で行い、本タスクの文書はその変更を前提に書く。

**issue #488 で決めたこと:**

-   **共通の文書に載せる内容:** 4 つの内容を載せる。システム構成（パイプライン、各段階の役割・プロバイダ・モデル・effort、本番の構成を表す環境変数）。品質の目標と判定の物差し（0008 F-006 への参照）。製品の制約の 8 項目（頻度が 10 件を母数とする値であることを含む）。構成の比較の要点と、構成を決めた理由。issue がこれらを、タスクではなくプロジェクトに共通の情報としたためである。
-   **主経路:** README（英語）と `project_overview.md` の冒頭の説明・使い方・要件の書き方を、ブラウザ拡張の経路を主、CLI を開発用の補助として書き直す。README の推奨構成を本番の構成に合わせる。実際の使い方と文書の書き方を一致させるためである。
-   **参照の張り替え:** `prompts/README.md`・0008 評価記録 §6 などから共通の文書を参照し、`CLAUDE.md` の Quick Links にも加える。
-   **既定のプロバイダは本 issue では変えない:** 既定を変えるかは本 issue のスコープ外とし、必要なら別の issue にする。その別の issue が #490 である（後述の「要件定義の際に決めたこと」）。
-   **言語:** `CLAUDE.md` の文書の言語の規則に従う（`docs/` は日本語、README は英語）。
-   **README を読むテストを壊さない:** README の値を読むテストがある（拡張の `serverReasons.test.ts`・`metadataDocs.test.ts`、`TestReadmeHostExitCodes` など。`CLAUDE.md`「Development Notes」）。README の構成を変えるときは、それらを壊さない。

**要件定義の際に決めたこと（2026-10-25）:**

-   **既定は #490・#171 で本番の構成にし、文書はそれを前提に書く:** 現在のコード上の既定のプロバイダは DeepSeek である（`README.md:718`、`docs/dev/project_overview.md:109`、`internal/config/config.go` の `parseProvider`）。レビュアーの判断で、既定を Claude Opus 5.5（`claude-opus-5-5`）にする変更を別の issue [#490](https://github.com/isseis/yt2column/issues/490) とし、本 issue をブロックする issue とした。本タスクの文書（共通の文書・README・`project_overview.md`）は、#490 で既定が本番の構成になったことを前提に書く（AC-02・AC-04・AC-14・AC-19）。本番の構成を既定にすれば、利用者は環境変数を指定しなくても本番の構成で記事を作れる。文書が「本番の構成は環境変数で指定する必要がある」と書けば、それは誤りになる。effort の既定は、レビュアーの判断で #171 が扱う。#171 は、effort の既定値 `high` をプログラムに持たせ、`YT2COLUMN_CLAUDE_EFFORT` で上書きできるようにする。あわせて `max_tokens` の上限を緩和する。#171 も本 issue をブロックする。`YT2COLUMN_MODEL` に既定を持たせるかなど、残りの既定の変数と値は #490 で決める。本タスクの文書は、#490 と #171 の決定に合わせて書く。
-   **共通の文書は新しい 1 つの文書にする:** `docs/dev/production_profile.md`（題は「本番の構成と品質」）を新しく作り、4 つの内容をまとめる（F-001）。4 つの内容は「本番の構成と、その構成で得られた結果」として一続きだからである。`project_overview.md` に節として加える案は採らなかった。決定済みの方針の文書に評価の数値が混ざるからである。2 つの文書に分ける案も採らなかった。
-   **共通の文書の更新の規則を明記する:** 本番の構成・品質の目標・製品の制約を変えるタスクは、共通の文書も更新する。このことを共通の文書の冒頭に書く（AC-06）。`project_overview.md` の冒頭の規則（`docs/dev/project_overview.md:5`）と同じ形である。タスクの評価記録はその時点の記録として残る。共通の文書が最新の値を持ち続けるには、更新する者を決めておく必要がある。
-   **未解決の関連 issue の一覧は共通の文書に載せない:** 共通の文書には、#171（claude の effort の既定と `max_tokens` の上限）・#146（話者の区別が難しい動画）を挙げる「未解決の関連 issue」の節や一覧を設けない。README の推奨構成の小節にも、#171 の注意を書かない（AC-07）。共通の文書は、評価で確かめた構成と結果を載せる文書であり、未解決の課題は issue で追うためである。ただし、製品の制約の項目の本文が出典の評価記録で issue に触れている場合（0008 評価記録 §6.3 の 4 が #146 に触れる）は、その言及を項目の本文の一部として写す。

-   **パイプラインの図は 3 つとも直す:** README・`project_overview.md`・`CLAUDE.md` のパイプラインの図を、主経路の入力（コピーした字幕）と補助の経路の入力（URL と yt-dlp）の両方を示す形にする（AC-08・AC-18・AC-24）。冒頭の文を主経路に直しても、すぐ下の図が `URL →` から始まると、読者が最初に見る図が補助の経路を示すことになるためである。
-   **`CLAUDE.md` は Quick Links、Architecture Overview の冒頭の一文、図を直す:** Quick Links に共通の文書を加える。「Architecture Overview」の冒頭の一文と図を主経路に合わせる（F-005）。文書全体の主経路を改めるという issue の目的に沿い、変更も小さいからである。
-   **`security.md` の冒頭の位置づけの文を直す:** `docs/dev/security.md:5` の、CLI を主とし入力を動画 URL とする文を、主経路に合わせて直す（F-005）。脅威の分析の中身（§1 以降）は変えない。CLAUDE.md の Quick Links から読まれる文書であり、主経路では利用者が与える入力がコピーした字幕だからである。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   本番の構成・品質の目標・製品の制約・構成の比較を、タスクの評価記録を読まずに、1 つの共通の文書で把握できるようにする。
-   README・`project_overview.md`・`CLAUDE.md`・`security.md` を読んだ人が、ブラウザ拡張の経路が主な使い方であり、CLI は開発・検証用の補助であると読み取れるようにする。
-   README を読んだ利用者が、本番の構成を表す環境変数の値を README だけで知れるようにする。
-   コードの振る舞いを変えない。すべてのテストが、変更の後も通る（既存の文書のテストを調整した場合は、調整した後のテストを含む）。

-   共通の文書 `docs/dev/production_profile.md` の新規作成（F-001）。

-   本タスクで文書に書く値と構造に対応するテストの追加と、既存の文書のテストの調整（`*_test.go`・`extension/test/*.test.ts`）。`CLAUDE.md`「Testing Strategy」が、文書の値や構造を変えたら、それに合うテストも必要だと定めているためである（「A change to a documented value or structure still needs the matching test」）。テストの形は設計で決める（design_handoff.md H-01）。

-   README の既存の節の並べ替えと、既存の見出しの変更（1 の「要件定義の際に決めたこと」）。
-   0008 評価記録 §6 の中身の移動・削除と、0018 評価記録の変更。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 本番の構成と品質の共通の文書

`docs/dev/production_profile.md` を日本語で新しく作り、本番の構成・品質の目標・製品の制約・構成の比較をまとめる。数値と判断は、0008 評価記録 §6 と、そこから参照する 0018 評価記録から取り、出典の節を示す。

**Acceptance Criteria**:
- **AC-01**: `docs/dev/production_profile.md` が存在し、次の 2 つが書かれている。パイプラインの段階を、コピーした字幕の取得 → 生成 → 字数の調整 → 検証・推敲 → 投稿の順に挙げ、各段階の役割を述べた一覧。LLM を呼ぶ 3 つの段階（生成、字数の調整、検証・推敲）のそれぞれについて、本番の構成のテンプレート・プロバイダ・モデル・effort。
- **AC-02**: 本番の構成を表す環境変数として、`YT2COLUMN_LLM_PROVIDER=claude`・`YT2COLUMN_MODEL=claude-opus-5-5`・`YT2COLUMN_CLAUDE_EFFORT=high` が書かれている。あわせて、次の 3 つが書かれている。`YT2COLUMN_REVIEW_PROVIDER`・`YT2COLUMN_REVIEW_MODEL` を指定しなければ、検証・推敲のプロバイダとモデルは生成と同じになること。effort は 3 つの段階で共通であること。本番の構成がコード上の既定であること（#490・#171）。既定で決まる変数と、利用者が指定しなければならない変数（`ANTHROPIC_API_KEY` など）の区別は、#490 と #171 の決定に合わせる。
- **AC-03**: 品質の目標（記事が必須の観点をすべて満たし、品質の観点に 1（不十分）がないこと）が書かれている。目標が既定にするための関門ではなく、記事が目指す水準であることも書かれている。判定の物差しとして、0008 要件定義書 F-006 にリンクしている。最終の版の結果（解釈による判定で 10 件中 8 件、文言どおりの判定で 10 件中 7 件）が、0008 評価記録 §6.2 への参照とともに書かれている。
