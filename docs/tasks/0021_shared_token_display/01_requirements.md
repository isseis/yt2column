## 1. 概要 (Overview)

**目的:** 本書は、localhost サーバ（タスク `0011_localhost_server`、`cmd/yt2column-server`）が、起動のたびに共有トークンを表示する振る舞いの要件を定義する。初回に生成したときだけでなく、保存済みのトークンを読み込んだときにも表示する。

**背景:**
`0011` の要件書 F-001 は、共有トークンを「生成したときだけ標準出力に表示する」とし、AC-02 も、再起動時に新しいトークンを表示しないことを定めている。共有トークンは再起動をまたいで同じ値を使うため、2 回目以降の起動では値が表示されない。

利用者が値を再び必要とするとき（ブラウザのプロファイルを作り直したとき、拡張を入れ直したとき、別のブラウザで使うとき）の経路として、`0011` の要件書 F-010 が README に記すことを求めるのは、「トークンのファイルを削除して作り直す手順」だけである。この手順は新しい値を生成するので、それまで使っていた値が無効になり、貼り付け直しが必要になる。現在の README は、OS ごとに異なるファイルのパスを `cat` で読む手順も記しているが、利用者はその節を探し、パスを確かめる必要がある。

`0011` の設計への申し送り H-02 は「2 回目以降の起動では表示しない。利用者が値を再び必要とするときは、ファイルを読む手順を README に記す」としている。しかし F-010 の README の記載事項にその手順は無く、`0011` の設計書（`02_architecture.md`）§3.12 の README の項目にだけ現れている。要件と設計のあいだで、値をもう一度確認する経路の記述が食い違っている。

利用者からの要望（[#266](https://github.com/isseis/yt2column/issues/266)）により、起動のたびにトークンを表示し、貼り付ける値をいつでも確認できるようにする。

`0011` の要件書・設計書・`design_handoff.md` は、当時の振る舞いの記録として残し、変更しない（`0020_extension_send` の F-008 と同じ方針）。現在の振る舞いを記す生きている文書（README・`security.md`）を本タスクで更新する。

対応 issue: #266（親: #104、#43）

**本書の記述範囲:** 本書は、観測できる振る舞い（いつ、どこに、何を表示するか）を定める。実現の手段（表示を行う場所、表示の判断の仕方、案内の文言、テストの手段など）は設計（`02_architecture.md`）で決める。要件のレビューで挙がった、設計で決める事項は [design_handoff.md](design_handoff.md) に申し送る。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   サーバの起動のたびに、共有トークンを表示する。生成した場合も、保存済みを読み込んだ場合も表示する。
-   利用者が、破壊的な手順（ファイルの削除と再生成）を取らずに、いつでも貼り付ける値を確認できるようにする。
-   トークンの露出を、標準出力への表示とトークンのファイルに限り、ログ・応答・エラーメッセージ・失敗の Slack への投稿には出さない（`0011` の要件 4.2 を維持する）。
-   トークンの生成・保存・検査と、リクエストの認証の振る舞いを変えない。

### 2.2. スコープ (In Scope)

-   起動時の共有トークンの表示（F-001）。
-   文書: README（起動のたびの表示と、貼り付ける値の確認）、`security.md` §8.2（表示のタイミングと露出の扱い）（F-002）。

### 2.3. スコープ外 (Out of Scope)

-   トークンのファイルの場所・形式・権限・生成方法・読み込み時の検査（`0011` のまま。F-001 は表示の条件だけを変える）。
-   トークンの自動のローテーション、複数のトークンの併用、利用者による値の指定。
-   リクエストの認証（`Authorization: Bearer`、定数時間の比較）と API の変更（`0011` のまま）。
-   拡張側の変更（#110・#111・#170）。表示された値を利用者が貼り付ける手順は変えない。
-   `--show-token` のような、起動とは別の表示の手段。起動のたびに必ず表示するので、別の手段を設けない（1. 概要）。
-   `0011` の要件書・設計書・`design_handoff.md` の改訂。当時の記録として残す（1. 概要。F-002）。
-   起動の自動化（launchd など）。起動は手動のままとする（`0011` F-001）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 起動時の共有トークンの表示

-   サーバは、起動のたびに共有トークンを標準出力に表示する。
    -   トークンのファイルがない場合は、`0011` の F-001 のとおり生成して保存し、生成した値を表示する。
    -   トークンのファイルがある場合は、`0011` の F-001 のとおり読み込んで検査し、読み込んだ値を表示する。新しい値は生成しない。
-   表示は、待ち受けを開始する前に行う。生成した後に待ち受けが失敗しても、表示が失われない側にする（`0011` の設計書 §3.1 の手順 2 の順序を維持する）。
-   表示は、共有トークンの値だけを含む 1 行とする。前後の説明やラベルを同じ行に含めず、利用者が値をそのままコピーできる形にする。拡張への貼り付けの案内は、標準エラー出力に書く（案内を、生成した起動と読み込んだ起動で変えるか、常に同じ文言にするかは設計で決める）。案内は、値が再び表示されないとするなど、起動のたびに表示する振る舞いと食い違う内容を含めない。
-   表示先は標準出力とし、ログ・案内・エラーは標準エラー出力に書く。共有トークンがログの経路（`0011` の設計書 §3.10 の `redact.Writer` を通す経路）に流れないようにする。
-   共有トークンは、上記の表示とトークンのファイルを除き、応答・ログ・エラーメッセージ・失敗の Slack への投稿に現れない（`0011` の AC-02・AC-21・AC-24 を維持する）。
-   トークンのファイルが不正（通常ファイルでない、権限が所有者以外に開いている、所有者が自分でない、大きさと内容が規定の形式に合わない、末尾に改行がある）な場合は、`0011` の F-001・AC-03 のとおり、待ち受けを開始せずに終了し、トークンの値を表示しない。ファイルを修復も再生成もしない（CLAUDE.md「Reject, don't normalize」）。
-   待ち受けを開始する前に設定を読み込む順序（`0011` の設計書 §3.1 の手順 1、2）を維持する。必要な設定が欠けている場合は、トークンの読み込みと表示の前に終了し、値を表示しない（`0011` の AC-03 を維持する）。

**Acceptance Criteria**:
- **AC-01**: トークンのファイルがない状態で起動すると、生成したトークンが標準出力に 1 行で表示され、所有者だけが読み書きできる権限のファイルに保存される。同じ値で API の認証が通る。
- **AC-02**: トークンのファイルがある状態で起動すると、保存済みのトークンが標準出力に 1 行で表示される。新しい値は生成されず、ファイルの内容は変更されない。標準エラー出力の案内に、値が再び表示されないとする記述が現れない。
- **AC-03**: サーバを再起動しても、同じ共有トークンが表示され、同じ値で API の認証が通る。
- **AC-04**: トークンのファイルが不正な場合、サーバは待ち受けを開始せずに終了し、その出力にトークンの値が現れない。トークンのファイルを修復も再生成もしない。
- **AC-05**: 必要な設定が欠けている場合、サーバはトークンを表示せずに終了し、その出力に欠けている設定の値・API キー・Webhook URL・共有トークンが現れない。
- **AC-06**: 共有トークンが、標準出力への表示とトークンのファイルを除き、ログ・エラーメッセージ・応答・失敗の Slack への投稿に現れない（識別できる値を使い、各出力に現れないことを確かめる）。
- **AC-07**: 表示される値だけ（説明やラベルを含まない 1 行）を取り出して `Authorization: Bearer` に使うと、API の認証が通る。

#### F-002: 文書

-   README: サーバの起動のたびに共有トークンが標準出力に表示されること、表示された値を拡張のオプションページに貼り付けること、値を再び確認したいときは起動し直せば表示されることを記す。`0011` の設計書 §3.12 が示した「値を再び表示する手順（ファイルを読む）」を、起動時の表示を主とした記述に改める。ファイルを読む手順は、表示に失敗したときの経路（4.3）として補足に残す。標準出力をファイルにリダイレクトする例を示す場合は、トークンがそのファイルに残ることに注意を記す（`0011` の起動例は標準エラー出力だけをファイルに残す形なので、それを維持する）。
-   `security.md` §8.2: 「表示と作り直し」の記述を、生成した起動だけでなく起動のたびに表示する形に改める。表示の露出（標準出力、端末のスクロールバック、標準出力をリダイレクトしたファイル、呼び出し元による出力の捕捉）と、ログへの非露出、標準出力と標準エラー出力の分離を記す。
-   `0011` の要件書・設計書・`design_handoff.md` は、当時の振る舞いの記録として残し、変更しない（1. 概要。`0020` の F-008 と同じ方針）。

**Acceptance Criteria**:
- **AC-08**: README に、F-002 の上記の内容（起動のたびの表示、貼り付け、再確認、ファイルを読む補足の手順、リダイレクトの注意）が記載されている（静的な確認）。
- **AC-09**: `security.md` §8.2 に、F-002 の上記の内容（起動のたびの表示、露出の経路、ログへの非露出、標準出力と標準エラー出力の分離）が記載されている（静的な確認）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

本タスクは新しい入力の境界を設けない。トークンのファイルは `0011` の境界をそのまま使う。

| 境界 | 受理する形 | 上限 | 拒否時の扱い | 主な AC |
|---|---|---|---|---|
| 共有トークンのファイル | 通常ファイル。権限が `0077` のビットを持たない。所有者が実行中の利用者。ちょうど 64 バイトで EOF。内容が `^[0-9a-f]{64}$` に一致する | 64 バイト | 起動の中止（`ErrInvalidTokenFile` を wrap した `*FileError`）。値を表示しない | AC-04 |

-   読み込んだトークンは、表示する前に `0011` の検査（通常ファイル・権限・所有者・大きさ・内容）をすべて通る。検査を通らない値は表示しない。
-   表示は値をそのまま書き出すだけで、解釈も変換もしない（CLAUDE.md「Reject, don't normalize」）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   起動時にトークンの 1 行を書き出すだけであり、性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。

### 4.2. セキュリティ (Security)

-   `security.md` §8 に従う。`0011` の 4.2 の方針（loopback への bind は認証ではない、`Host`・`Origin`・共有トークンの検査、秘密情報の扱い）を維持する。
-   **露出を標準出力とファイルに限る:** 表示先を標準出力に限り、ログは標準エラー出力に分ける（`0011` の設計書 §3.10）。共有トークンを、ログの経路に流さない。
-   **起動のたびの表示による露出（受け入れる）:** 起動のたびに表示すると、共有トークンが次の場所に残りうる。利用者 1 人の macOS で起動は手動であることを前提に、この露出は受け入れる。
    -   端末のスクロールバック（過去の出力の履歴）。
    -   標準出力をファイルへリダイレクトした場合のそのファイル（利用者が明示的に行った場合）。
    -   サーバを起動した呼び出し元（`nohup`・`tee`・端末の出力の保存など）による出力の捕捉。
-   **ログへの非露出:** ログへは標準エラー出力に書く経路だけを使い、その経路は `redact.Writer` を通す（`0011` の設計書 §3.10）。利用者が標準エラー出力だけをファイルに残す起動例（`0011` の README の `2>>server.log`）では、トークンはそのファイルに残らない。
-   **トークンを他の出力に載せない:** 応答・エラーメッセージ・失敗の Slack への投稿に、共有トークンを載せない（`0011` の AC-02・AC-21・AC-24・AC-27 を維持する）。利用者が標準出力に表示された値を拡張のオプションページに貼り付けて保存する経路（F-001、`0011`）は、この禁止に含まない。
-   **残余のリスク（変わらない）:** 同じ OS 利用者として動くプロセスはトークンのファイルを読める（`0011` の設計書 §5.4・`0011` の要件 4.2）。この信頼の範囲は `.envrc` に置く秘密情報と同じである。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   表示に失敗しても、サーバを停止させない。トークンの値はファイルに残るので、利用者はファイルから読める。
-   表示は、待ち受けを開始する前に行う。待ち受けが失敗した起動でも、利用者はトークンを確認できる（`0011` の設計書 §3.1 の順序を維持する）。

### 4.4. 互換性 (Compatibility)

-   利用時: macOS 上の Chrome と Brave の、作業時点の安定版からのリクエストを受理する（`0011` 4.4 を維持する）。
-   サーバは Go のシングルバイナリとしてビルドでき、外部ライブラリを追加しない（`0011` 4.4 を維持する）。標準出力と標準エラー出力の使い分けは、CLI の慣例の範囲に留める。

### 4.5. 保守性 (Maintainability)

-   サーバ固有の変更は、表示を行う条件（生成した起動だけでなく、常に表示する）に限る。トークンの形式・生成・検査・比較と、リクエストの処理を変えない（2.3）。
-   表示の判断に、`LoadOrCreate` の `created` の戻り値を引き続き使うか、使わずに常に表示するかは設計で決める（[design_handoff.md](design_handoff.md) H-01）。
-   観測できる振る舞い（いつ、どこに、何を表示するか）をユニットテストで確かめられるようにする。標準出力と標準エラー出力を、テストで差し替えられるようにする。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」に従う。外部ライブラリは追加しない。
-   `0011` の実装（`internal/authtoken`・`cmd/yt2column-server`）と、生きている文書（README・`security.md`）を変更する。
-   変更するのは `0011` の F-001・AC-02 が定めた「生成したときだけ表示する」という条件だけとする。`0011` の他の AC（入力の検証、`Host`・`Origin`・共有トークンの検査、応答、失敗の投稿、設定の読み込み）を維持する。
-   `0011` の要件書・設計書・`design_handoff.md` は、当時の記録として残し、変更しない。
-   ユニットテストは、実際のブラウザを起動せず、LLM の API も Slack の Webhook も呼ばない。表示の検査は、標準出力と標準エラー出力を差し替えて行う（`0011` の制約を維持する）。
-   [project_overview.md](../../dev/project_overview.md) と CLAUDE.md のサーバの起動の記述を変える必要がある場合は、同じ変更で更新する。

## 6. 用語集 (Glossary)

-   **サーバ:** `0011` で作った、loopback で待ち受ける localhost サーバ（`cmd/yt2column-server`）。
-   **共有トークン:** サーバが初回の起動時に生成してファイルに保存し、拡張が `Authorization: Bearer` で送る、256 ビットの乱数を小文字の 16 進 64 文字で表した値（`0011` の設計書 §3.3）。サーバの再起動をまたいで同じ値を使う。
-   **`0011`:** localhost サーバ本体と拡張との HTTP API のタスク（`docs/tasks/0011_localhost_server/`）。「`0011` F-NNN」はその要件書の項番、「`0011` §N」はその設計書の節を指す。
-   **生成した起動 / 読み込んだ起動:** トークンのファイルが無く、共有トークンを生成した起動と、トークンのファイルがあり、保存済みの値を読み込んだ起動。
-   **標準出力 / 標準エラー出力:** サーバが使う 2 つの出力。標準出力には共有トークンの 1 行だけを書き、ログ・案内・エラーは標準エラー出力に書く（`0011` の設計書 §3.1）。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
