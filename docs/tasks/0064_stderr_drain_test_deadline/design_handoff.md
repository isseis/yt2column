# 設計への申し送り（タスク 0064）

要件定義（`01_requirements.md`）の段階で挙がった、設計で決める論点。`02_architecture.md` は、各項目について、採った方法または当てはまらない理由を記録する。

## H-01: 期限の定数と、その根拠の書き方

期限（30 秒。AC-01）を、テストの中の定数のままにするか、同じファイルの `helperStartBound`（`internal/transcript/exec_test.go:427-429`）と共通にするか、別の名前の定数にするかを決める。あわせて、期限が「詰まったときにテストを終わらせる上限で、正常な実行の時間を測るものではない」ことを、どこに書くか（コメント、定数の名前）を決める（要件書 4.5）。`helperStartBound` の意味は「ヘルパーが PID を記録するのを待つ上限」なので、共通にするなら意味が合うかを確かめる。

## H-02: 原因の計測の方法

AC-06 の 3 つの条件を、どう作り、どう計測するかを決める。

-   「新しいファイル」と「一度実行した同じファイル」を確実に作り分ける方法（ファイルのパス、内容、`t.TempDir()` を使うかどうか）。
-   計測するのが、子プロセスの起動から終了までの時間か、Go のテストとしての所要時間か。macOS の検査の待ちは、`exec` の呼び出しから子プロセスが動き出すまでに入ると見られるので、それを含む区間を測る。
-   各条件の回数。issue のコメントの観察（遅いときと速いときで 10 倍以上違う）を区別できる回数にする。
-   条件 (c) の負荷のかけ方（`make test` を並行して実行するときの始める時刻、繰り返し）と、その負荷を記録する方法（例: 1 分の負荷の平均、`XprotectService` の CPU 使用率）。

## H-03: 記録を置く文書

## H-04: AC-05 の壊し方

`osExecutor` が標準エラー出力を読み出さない形を、どう作るかを決める。例えば、`cmd.Stderr` に読み出さない `io.Writer` をつなぐ、パイプだけを作って読まない、など。どの形でも、子プロセスがパイプのバッファ（macOS では 64 KiB 程度）を超えて書いたときに詰まるか、SIGPIPE で終わる必要がある。期限の 30 秒と `execWaitDelay`（5 秒）の後にテストが失敗するので、確認に 35 秒ほどかかることを見込む。
