# 設計への申し送り：Claude と OpenAI の組み合わせの評価

本書は [01_requirements.md](01_requirements.md) の要件を満たすために設計で確認する事項を記す。実装の手段を本書で確定しない。`02_architecture.md` は各 H-NN をどう扱うか、または該当しない理由を記録する。

## H-01: 評価記録の文書の名前と構成

0018 は評価記録を `02_evaluation.md` に置いたが、本タスクは full のプロセスで `02_architecture.md` と `03_implementation_plan.md` を持つ。評価記録の文書の名前、置く時期（計画の承認後の実装の PR か）、節の構成を決める。AC-01〜AC-23 の記録の項目を、どの節に置くかを対応させる。関連: §3 の冒頭、F-001〜F-006。

## H-02: 構成 A の再開の工程

構成 A は基準の構成の生成物から検証・推敲だけを再実行する（issue #569）。`--after` の値は `generation`・`shorten`・`review` である（`cmd/yt2column/run.go:159`）。字数の調整が走った記事と走らなかった記事で、検証・推敲だけを再実行する正しい再開の工程が異なりうる。B3 の生成物に字数の調整の中間生成物がどう残っているかを確かめ、字数の調整を再実行しない（生成と字数の調整を基準と共有する）方法を決める。B3 の roNZ-rLxhUE-1 は字数の調整に一度失敗してやり直している（0018 評価記録 §4.7.2）。どの実行の生成物を基準とするかも決める。関連: F-001・F-002、AC-03。

## H-03: 基準の生成物を変えないこと

基準の構成の生成物は読み取り専用で、評価は写しに対して行う（0018 評価記録 §3.3 の方法）。評価の前後で内容が変わっていないことを確かめる方法（ハッシュの一覧の比較など）を決める。関連: AC-04。

## H-04: CLI の実行の条件

0018 の実行は旧い環境変数（`YT2COLUMN_MODEL`・`YT2COLUMN_REVIEW_PROVIDER` など）を使った（0018 評価記録 §3.3）。今の設定（`YT2COLUMN_LLM`・`YT2COLUMN_REVIEW_LLM`）で同じ条件を表す。`yt-dlp` で字幕を取り直さないための設定（0018 では `YT2COLUMN_YTDLP_PATH=/usr/bin/false` と `--keep-cache`）、並列に実行する場合のキャッシュの写し、出力先（リポジトリの外）、CLI のビルドとコミットの記録を決める。関連: F-001・F-002・F-004、AC-02・AC-06・AC-16。

## H-05: 所要時間と推定コストの集計

所要時間の測り方（0018 は `time` と標準エラーの `at=`）、基準の構成の所要時間の平均の値（0018 評価記録の B3 の記録から取る）、集計のスクリプトを置く場所（リポジトリの外か、タスクのディレクトリか）を決める。再開で呼ばなかった工程の値の足し方を 0018 と合わせる。関連: F-004・F-006、AC-14〜AC-18。

## H-06: 採点の手順と記録の置き場所

1 回目の採点のプロンプト（0018 は動画ごとにサブエージェントを使い、プロンプトと全文の採点はリポジトリの外に置いた。0018 評価記録 §3.8）、人の確認の進め方、観点「根拠」の合格を全構成で確かめる手順を決める。採点の LLM が記事・字幕の中の指示に従わないよう、プロンプトでの扱いを決める。関連: F-003、AC-09〜AC-13。

## H-07: 一括の承認で示す内容と費用の監視

承認のときに示す構成・回数・推定費用の見積もりの根拠（0077 の実測のトークン数と料金表）、実行の途中で累計の推定コストを追い、上限の 30 USD を超える前に止める方法を決める。2 段目の B は 1 段目の結果で構成が決まるので、1 段目の承認に含めるか、上限の中で事前に含めておくかを決める。関連: F-005、AC-19・AC-20。

## H-08: 本番の構成を変える場合の既定の表し方

今のコード上の既定は 1 つのプロバイダとモデル（`internal/config/config.go:73-80`）で、検証・推敲は未設定なら生成の選択を継承する（[ADR-0003](../../dev/adr/0003-llm-config-contract.md)）。選んだ構成が A・B のように工程ごとにプロバイダの異なる構成の場合、検証・推敲の既定を生成から継承しない形で表す必要があり、継承の規則と既定の関係を設計する。そのとき、利用者が生成だけを指定した場合に検証・推敲が何を使うかを決める。継承の規則を変える必要があれば、要件 §4.4 のとおり、変える前に人に確認する。必要な API キーの検査（AC-25）、サーバの設定ファイルの雛形、README の推奨構成と設定の説明、ガードテストへの影響を洗い出す。この場合は ADR-0003 の更新が必要かも判断する。関連: F-007、AC-24〜AC-28。
