# 設計への申し送り：Claude と OpenAI の組み合わせの評価

本書は [01_requirements.md](01_requirements.md) の要件を満たすために設計で確認する事項を記す。実装の手段を本書で確定しない。`02_architecture.md` は各 H-NN をどう扱うか、または該当しない理由を記録する。

## H-01: 評価記録の文書の名前と構成

0018 は評価記録を `02_evaluation.md` に置いたが、本タスクは full のプロセスで `02_architecture.md` と `03_implementation_plan.md` を持つ。評価記録の文書の名前、置く時期（計画の承認後の実装の PR か）、節の構成を決める。AC-01〜AC-23 の記録の項目を、どの節に置くかを対応させる。関連: §3 の冒頭、F-001〜F-006。

## H-02: 構成 A の再開の工程

構成 A は基準の構成の保存した出力から検証・推敲だけを再実行する（issue #569）。`--after` の値は `generation`・`shorten`・`review` である（`cmd/yt2column/run.go:159`）。B3 は 2 段で作られ、生成だけの出力が `~/yt2column-eval/0018/base/B3/`、字数の調整と検証・推敲の出力が `~/yt2column-eval/0018/work/B3/` にある（0018 評価記録 §4.7.2）。0018 の C03・C05 は `work/B3/` から再開した（0018 評価記録 §4.7.3・§4.7.5）。字数の調整が走った記事と走らなかった記事で、検証・推敲だけを再実行する正しい再開の工程が異なりうる。字数の調整を再実行しない（生成と字数の調整を基準と共有する）方法を決める。B3 の roNZ-rLxhUE-1 は字数の調整に一度失敗してやり直しており、やり直しの出力だけが `work/B3/roNZ-rLxhUE-1/` にある。関連: F-001・F-002、AC-03。

## H-03: 基準の保存した出力を変えないこと

基準の構成の保存した出力（`base/B3/` と `work/B3/`）は変えず、評価はその写しに対して行う（0018 評価記録 §3.3 の方法）。評価の前後で差分が空であることを確かめる方法（ハッシュの一覧の比較など）と、拒否された入力を元に戻すためのバックアップの取り方を決める。関連: AC-04・AC-05。

## H-04: CLI の実行の条件

0018 の実行は旧い環境変数（`YT2COLUMN_MODEL`・`YT2COLUMN_REVIEW_PROVIDER` など）を使った（0018 評価記録 §3.3）。今の設定（`YT2COLUMN_LLM`・`YT2COLUMN_REVIEW_LLM`）で同じ条件を表す。次を決める。

- `yt-dlp` で字幕を取り直さないための設定（0018 では `YT2COLUMN_YTDLP_PATH=/usr/bin/false` と `--keep-cache`）。
- 並列に実行する場合のキャッシュの写しと、出力先（リポジトリの外）。
- CLI のビルドとコミットの記録。
- 実行の順序と並列の度合い。OpenAI のプロンプトのキャッシュは 30 分で、同じ動画の 2 回目が 1 回目のキャッシュを読みうる。所要時間の基準の値は 10 件を並列に起動して測った値である（0018 評価記録 §4.8）。

関連: F-001・F-002・F-004、AC-02・AC-06・AC-16。

## H-05: 所要時間と推定コストの集計

所要時間の測り方（0018 は `time` と標準エラーの `at=`）と、集計のスクリプトを置く場所（リポジトリの外か、タスクのディレクトリか）を決める。再開で呼ばなかった工程の値の足し方を 0018 と合わせる。`claude-opus-5-5` の単価が基準の構成のときと同じかの確かめ方（AC-15）も決める。関連: F-004・F-006、AC-14〜AC-18。

## H-06: 採点の手順と記録の置き場所

次を決める。

- 1 回目の採点のプロンプト。0018 は動画ごとにサブエージェントを使い、プロンプトと全文の採点をリポジトリの外に置いた（0018 評価記録 §4.2.2）。

## H-07: 一括の承認で示す内容と費用の監視

承認は 1 段目と 2 段目を一度に受ける（要件定義の際に決めたこと 8）。次を決める。

- 示す構成・回数・推定費用と、見積もりの根拠（0077 の実測のトークン数と料金表）。
- 2 段目の B の見積もり。両方のモデルで作る場合も含める。
- 実行の途中で累計の推定コストを追い、上限の 30 USD を超える前に止める方法。
- 構成 A が再利用した工程の推定コストを、累計から除く方法。

関連: F-005、AC-19・AC-20。

## H-08: 本番の構成を変える場合の既定の表し方

今のコード上の既定は 1 つのプロバイダとモデルである（`internal/config/config.go:73-80`）。検証・推敲は、未設定なら生成の選択を継承する（[ADR-0003](../../dev/adr/0003-llm-config-contract.md)）。選んだ構成が A・B のように工程ごとにプロバイダの異なる構成の場合は、検証・推敲の既定を生成から継承しない形で表す必要がある。

次を設計する。

- 継承の規則と既定の関係。利用者が生成だけを指定した場合に、検証・推敲が何を使うかを決める。継承の規則を変える必要があれば、要件 §4.4 のとおり、変える前に人に確認する。人が採らない場合は、要件 F-006 の手順 3 で次の候補に移る。
- 影響の洗い出し。必要な API キーの検査（AC-25）、サーバの設定ファイルの雛形、README の推奨構成と設定の説明、`project_overview.md` の既定と例外の記述、ガードテストを対象にする。

関連: F-007、AC-24〜AC-30。
