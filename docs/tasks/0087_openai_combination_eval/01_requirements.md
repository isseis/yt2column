## 1. 概要 (Overview)

対応 issue: [#569](https://github.com/isseis/yt2column/issues/569)

親 issue は [#567](https://github.com/isseis/yt2column/issues/567)、前提は完了済みの [#568](https://github.com/isseis/yt2column/issues/568)（[0077 要件定義書](../0077_openai_llm_client/01_requirements.md)）である。

**目的:** 本書は、生成（字数の調整を含む）と検証・推敲に Claude と OpenAI を組み合わせた構成の記事の品質・料金・所要時間を、今の本番の構成と同じ物差しで評価し、本番の構成を変えるかどうかを決めるための要件を定義する。

**背景:** 本番の構成は、3 つの工程とも `claude` の `claude-opus-5-5`、effort `high` である（[production_profile.md](../../dev/production_profile.md)「本番の構成」、[ADR-0004](../../dev/adr/0004-production-profile.md)）。この構成（0018 の B3）は、品質の目標を物差し 2 の解釈による判定で 10 件中 8 件、文言どおりの判定で 10 件中 7 件の記事で満たした（[0008 評価記録](../0008_column_prompt/02_evaluation.md) §6.2）。0077 で、生成と検証・推敲の工程ごとに OpenAI を選べるようになった（0077 要件定義書 F-001）。料金表には、品質を重視した候補の `gpt-6-astra` と、料金を抑えた候補の `gpt-6.1-sol` がある（`internal/pricing/rates.go:131-148`）。別系統のモデルを組み合わせると記事の品質が上がるか、または同じ品質で費用が下がるかは、まだ確かめていない。

**本書の記述範囲:** 評価する構成、素材、物差しと採点の手順、記録する項目、実行の承認、本番の構成を変える条件、変える場合に合わせて直すものを定める。評価の手順の細部（作業ディレクトリの配置、実行のコマンド、集計の方法）、評価記録の文書の名前と構成、本番の構成を変える場合のコードと文書の変更の設計は、`02_architecture.md` と `03_implementation_plan.md` で決める。設計上の注意は [design_handoff.md](design_handoff.md) に記す。

### issue #569 で決めたこと

- **構成は、生成（字数の調整を含む）と検証・推敲の、それぞれのプロバイダの組み合わせで分ける。** 基準（Claude + Claude）、A（Claude + OpenAI）、B（OpenAI + Claude）、C（OpenAI + OpenAI）である。生成の違いと検証・推敲の違いを分けて比べるためである。
- **物差しは 0008 と 0018 の評価に合わせる。** 同じ 5 本の動画で 2 回ずつ生成した 10 件を、0008 要件定義書 F-006 の観点で判定する。製品の制約 1〜3 が直るかも見る。今の本番の構成の結果と比べられるようにするためである。
- **品質のほかに、料金と所要時間も記録する。** 本番の構成を変えるかの判断に要るためである。
- **構成 A は、基準の構成の生成物から検証・推敲だけを再実行して作る（`--after` による再開）。** 生成を共有すれば、検証・推敲の違いだけを比べられるためである。
- **本番の構成を変える場合は、`docs/dev/production_profile.md`、README の推奨構成、コード上の既定と、それらを読むガードテストを合わせて変える。** [ADR-0004](../../dev/adr/0004-production-profile.md) の「本番の構成を変えるタスクは共通の文書と README の推奨構成を合わせて更新する」に従うためである。
- **OpenAI 以外のプロバイダ（Gemini など）は対象外とする。**

### 要件定義の際に決めたこと（2026-11-11）

1. **プロセスは full とする。** 評価の結果によっては、ADR-0004 の決定（本番の構成）を変える。また、本番で記事の素材を送る外部サービスに OpenAI が加わりうる。これは簡易プロセスの除外の条件「外部サービスの追加・置き換え」（[requirements_process.md](../../dev/conventions/requirements_process.md)「Simple Process」の「Excluded changes」）に当たると判断した。決めることも多いため、レビュアーは full を選んだ。除外の判断の上書きはない。
2. **OpenAI のモデルは `gpt-6-astra` と `gpt-6.1-sol` の両方とし、effort はどちらも `medium` とする。** 品質と料金の両面から候補を比べるためである。`medium` は OpenAI アダプタの既定の effort であり、既定の出力上限 6,080 トークンの根拠になった実測の条件でもある（[0077 設計書](../0077_openai_llm_client/02_architecture.md) §1.4）。`high` 以上は推論が増え、既定の出力上限で打ち切られる恐れがあるが、その量は測っていない。モデルの選定はこのタスクの中で閉じるので、ADR は作らない。
3. **基準の構成の記事は、0018 の B3 の 10 件を作り直さずに使う。** B3 の生成物（リポジトリの外の `~/yt2column-eval/0018/base/B3/`）と、人が確認した判定（[0008 評価記録](../0008_column_prompt/02_evaluation.md) §6.2）がそのまま使えるためである。B3 のテンプレートは今の `prompts/` と同じであり、生成のテンプレート v5 は今の既定のテンプレートになっている。違いは、Claude アダプタの出力上限の既定が 16,000 から 40,000 に上がったこと（[production_profile.md](../../dev/production_profile.md)「評価の条件」）と、B3 の実行（2026-10-23）以降のコードの変更である。比べるときはこの違いを条件として記録する（F-001）。ADR は作らない。
4. **プロンプトは今のテンプレートのまま比べる。** OpenAI 向けのテンプレートの調整は対象外とする。モデルの違いとプロンプトの違いを切り分けるためである。有望な構成が出て、調整の余地があると判断した場合は、別の issue にする。ADR は作らない。
5. **評価する構成は段階的に絞る。** 1 段目で C と A を両方のモデルで作る（4 構成）。2 段目で、B を C の合格件数が多いほうのモデルで作る。C の合格件数が同じなら、両方のモデルで作る。B の生成の良し悪しを最もよく表すのは、同じ生成を使う C の結果だからである。ADR は作らない。
6. **本番の構成を変える条件は、品質の向上、または同等の品質で費用が下がることとする。** 条件は §3 の F-006 に定める。記事 10 件では 1 件の差はばらつきの範囲にあるため、品質の向上は 2 件以上の差とする。条件そのものはこのタスクの中で閉じるので、ADR は作らない。本番の構成を変える場合は、そのタスクの PR で ADR-0004 を更新する（F-007）。
7. **採点は、0018 と同じく Claude Code のセッションの `claude-opus-5-5` が 1 回目の採点を行い、人が確認する。観点「根拠」の合格は、すべての構成で人が確かめる。** 0018 では、採点の LLM と同じ系統のモデルが作った記事に限って、人が「根拠」の合格を確かめた（[0018 要件定義書](../0018_article_quality/01_requirements.md) AC-12）。本タスクは系統の違う構成を比べるので、採点の偏りが合否に効かないよう、すべての構成で同じ確認をする。ADR は作らない。
8. **実 API を呼ぶ評価の実行は、総額の上限つきで一括して承認を受ける。** 実装計画が承認された後、実行する構成と回数を示し、推定費用の総額 30 USD を上限として人の承認を受ける。1 段目と 2 段目の 6 構成をすべて作っても、0077 の実測（[0077 設計書](../0077_openai_llm_client/02_architecture.md) §1.4）と料金表から見積もった額は約 17 USD であり、やり直しを含めても上限に収まる見込みである。ADR は作らない。
9. **実行の失敗は記録し、同じ構成でやり直す。やり直しは記事 1 件あたり 2 回までとする。** 0018 と同じ扱い（0018 要件定義書 AC-20）である。失敗の回数と費用は構成ごとに記録し、本番の構成を変えるかの判断の材料として人に示す。F-006 の条件には加えない。ADR は作らない。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

- Claude と OpenAI を組み合わせた構成の記事の品質・料金・所要時間を、今の本番の構成と同じ物差しで比べる。
- 評価の前に決めた条件に従って、本番の構成を変えるかを決め、変える場合は本番の構成を表すコードと文書をそろえて変える。

### 2.2. スコープ (In Scope)

- 構成 A・C（`gpt-6-astra` と `gpt-6.1-sol`）と構成 B（F-002 で選んだモデル）の記事の生成と採点。
- 基準の構成（0018 の B3）の記事と判定の再利用。
- 構成ごとの品質・料金・所要時間・失敗の記録と、構成を並べた比較。
- 本番の構成を変えるかの判断。
- 本番の構成を変える場合の、コード上の既定、`docs/dev/production_profile.md`、`README.md`・`README.en.md` の推奨構成、ADR-0004、それらを読むガードテストの更新。

### 2.3. スコープ外 (Out of Scope)

- OpenAI 向けのテンプレートの調整。要件定義の際に決めたこと 4 のとおり、別の issue で扱う。
- `gpt-6-astra`・`gpt-6.1-sol` 以外の OpenAI のモデルと、`medium` 以外の effort の評価。要件定義の際に決めたこと 2 のとおりである。
- 基準の構成の記事の作り直し。要件定義の際に決めたこと 3 のとおりである。
- 物差しの変更。0008 要件定義書 F-006 の現在の物差し（物差し 2）で判定する。issue #569 が 0008・0018 の物差しに合わせると決めているためである。
- OpenAI の出力上限の既定（6,080）の変更。`medium` の実測の範囲で評価するためである。評価の途中で打ち切りが起きた場合は、F-004 の失敗として記録する。
- 本番の構成を変えない場合の `docs/dev/production_profile.md` の更新。issue #569 は、変える場合に限って共通の文書を影響範囲に挙げている。評価の結果は本タスクの評価記録に残る。
- ブラウザ拡張の経路（コピーした字幕）での評価。基準の構成の記事が CLI の経路（`yt-dlp` の字幕のキャッシュ）で作られており、同じ素材で比べるためである。経路による素材の違いは 0018 の F-010 で記録済みである（[0018 評価記録](../0018_article_quality/02_evaluation.md) §4.9）。
- Gemini など、OpenAI 以外のプロバイダ。issue #569 の対象外である。

## 3. 機能要件 (Functional Requirements)

本章の「評価記録」は、本タスクのディレクトリに置く、評価の結果を記録する文書を指す。文書の名前と構成は設計で決める。

### 3.1. 機能一覧

#### F-001: 基準の構成と評価の素材

基準の構成は 0018 の B3 である。素材は、B3 と同じ 5 本の動画（`roNZ-rLxhUE`・`18tbwwPM91A`・`zW1RBacSqjk`・`leE02uqgaKg`・`EqnGQDU71-Y`）の、0018 で取得した `yt-dlp` の字幕のキャッシュである（[0018 評価記録](../0018_article_quality/02_evaluation.md) §3.3・§4.9）。各動画で 2 回ずつ記事を作り、構成ごとに 10 件とする。

基準の構成の生成物は読み取り専用のまま残し、評価はその写しに対して行う。生成物は既存の中間生成物の読み込み（`internal/artifact` の `Store.Load`）で読み、拒否された生成物は使わない。

**Acceptance Criteria**:

- **AC-01**: 評価記録に、基準の構成について、0018 の B3 であること、判定の出典（[0008 評価記録](../0008_column_prompt/02_evaluation.md) §6.2）、10 件の生成物の識別子、生成の日付が記録されている。基準の構成と本タスクの実行の条件の違い（Claude アダプタの出力上限の既定、CLI のコミット）が記録されている。
- **AC-02**: 評価記録に、評価に使った字幕のキャッシュの場所（リポジトリの外の場所の説明）と取得日、5 本の動画の ID が記録されている。本タスクの実行が `yt-dlp` で字幕を取り直していないことが記録されている。
- **AC-03**: 構成 A の 10 件の記事のそれぞれについて、評価記録に記録した生成の中間生成物の識別子が、基準の構成の同じ記事の識別子と一致している。
- **AC-04**: 評価の後、基準の構成の生成物（`~/yt2column-eval/0018/base/B3/` の内容）が、評価の前と変わっていない。評価記録に、そのことを確かめた方法と結果が記録されている。
- **AC-05**: 中間生成物の読み込みが拒否した入力は評価に使われていない。拒否があった場合、評価記録に、その入力と拒否の番兵が、記事を得られなかった実行として記録されている。

#### F-002: 評価する構成と実行の順序

構成と各工程の設定を次に示す。テンプレートは、どの構成も今の既定（生成は `prompts/system.tmpl`・`prompts/user.tmpl`、字数の調整と検証・推敲は既定のテンプレート）とする。

| 構成 | 段 | 生成・字数の調整 | 検証・推敲 | 作り方 |
|---|---|---|---|---|
| 基準 | - | `claude/claude-opus-5-5+high` | `claude/claude-opus-5-5+high` | 0018 の B3 を使う（F-001） |
| A-astra | 1 | 基準と同じ（再利用） | `openai/gpt-6-astra+medium` | 基準の生成物から検証・推敲だけを再実行する |
| A-sol | 1 | 基準と同じ（再利用） | `openai/gpt-6.1-sol+medium` | 同上 |
| C-astra | 1 | `openai/gpt-6-astra+medium` | `openai/gpt-6-astra+medium` | 全工程を実行する |
| C-sol | 1 | `openai/gpt-6.1-sol+medium` | `openai/gpt-6.1-sol+medium` | 同上 |
| B-<モデル> | 2 | C で選んだモデル、`+medium` | `claude/claude-opus-5-5+high` | 全工程を実行する |

2 段目の B は、1 段目の C-astra と C-sol のうち、合格件数（物差し 2、解釈による判定）が多いほうのモデルで作る。同数なら両方のモデルで作る。

**Acceptance Criteria**:

- **AC-06**: 評価記録に、評価した構成ごとに、各工程のプロバイダ・モデル・effort、テンプレート（既定であること）、CLI のコミット、生成の日時、10 件の記事のそれぞれの中間生成物の識別子が記録されている。再開した構成は、再開した工程（`--after` の値）が記録されている。
- **AC-07**: 評価記録に、1 段目の 4 構成（A-astra・A-sol・C-astra・C-sol）の 10 件の記事のすべての判定（F-003）が記録されている。
- **AC-08**: 評価記録に、2 段目で B を作ったモデルと、その選択の根拠（C-astra と C-sol の合格件数）が記録されている。B の記事は、C の判定が人の確認を終えた後に生成されている。選んだモデルの B の 10 件の判定が記録されている。

#### F-003: 採点

判定は、0008 要件定義書 F-006 の現在の物差し（0018 の緩和の案 I-1・S-1・A-1・L-1 を含む物差し 2。[0018 評価記録](../0018_article_quality/02_evaluation.md) §5.5）で行う。必須の観点（形式の選択・形式の規則・根拠・長さ・表記）の合否と、品質の観点（要点の網羅・重要度の順・構成・読みやすさ・タイトル・リード文・冗長さ）の 3 段階を、解釈による判定と文言どおりの判定の両方で記録する（[0008 要件定義書](../0008_column_prompt/01_requirements.md) F-006、0018 評価記録 §3.8）。

長さ・節の数・タイトルの字数は既存のスクリプト（`docs/tasks/0008_column_prompt/check_article.py`）で判定し、それ以外は Claude Code のセッションの `claude-opus-5-5` が 1 回目の採点をする。人は、必須の観点の不合格、品質の観点の 1 と 2、観点「根拠」の合格のすべてを、どの構成でも確認する。

**Acceptance Criteria**:

- **AC-09**: 評価記録に、評価した構成ごとに、10 件の記事のそれぞれについて、必須の観点ごとの合否、品質の観点ごとの段階、品質の目標を満たしたかどうかが、解釈による判定と文言どおりの判定の両方で記録されている。構成ごとの合格件数（10 件中）が記録されている。
- **AC-10**: 評価記録に、判定ごとの判定者（スクリプト・LLM・人）と、1 回目の採点に使った LLM のモデル名が記録されている。人が LLM の判定を変えた場合は、変えた判定と理由が記録されている。
- **AC-11**: 評価記録に、すべての構成の記事について、人が観点「根拠」の合格の判定を確認したことが記録されている。
- **AC-12**: 評価記録に、評価した構成ごとに、必須の観点の不合格と品質の観点の 1 のそれぞれについて、記事からの短い引用と、その誤りを入れた工程と、直さなかった工程が記録されている。
- **AC-13**: 評価記録に、評価した構成ごとに、本番の構成の製品の制約 1〜3（[production_profile.md](../../dev/production_profile.md)「製品の制約」の意味の変わる言い換え、節の中身と見出しのずれ、発言の主体を広げたまとめ）のそれぞれについて、基準の構成で該当した記事（0008 評価記録 §6.3 の leE02uqgaKg-2・18tbwwPM91A-2・EqnGQDU71-Y-2）と同じ動画・同じ回の記事に、同じ種類の誤りがあるかどうかが記録されている。そのほかの記事に同じ種類の誤りがあった場合は、その記事も記録されている。

#### F-004: 料金・所要時間・失敗

推定コストは、CLI が出す工程ごとの `cost:` の行と記事の `cost-total: article` の行の値を使う（単価は `internal/pricing` の表）。再開で呼ばなかった工程は、その工程を実行した実行の値（`reused`）を含める。

**Acceptance Criteria**:

- **AC-14**: 評価記録に、評価した構成ごとに、10 件の記事のそれぞれについて、工程ごとのトークン数（入力・キャッシュから読んだ入力・キャッシュに書いた入力・出力）と推定コスト、記事 1 本の推定コストが記録されている。再開で呼ばなかった工程は、どの実行の値を使ったかが示されている。推定コストが不明の工程がある場合は、その理由と、記事 1 本の推定コストを比べられないことが記録されている。
- **AC-15**: 評価記録に、推定コストに使った単価の表のコミットと、評価に使ったモデルのそれぞれの単価（通常の入力・キャッシュの読み取り・キャッシュの書き込み・出力、USD）が記録されている。
- **AC-16**: 評価記録に、評価した構成ごとに、10 件の記事のそれぞれの所要時間（記事を作った工程の時間の和。再開で呼ばなかった工程は、その工程を実行した実行の時間を足す）が記録されている。並列に実行した場合は、そのことが記録されている。
- **AC-17**: 実行が失敗した場合（打ち切り、字数の調整の失敗、想定外の終了、空の応答、通信の失敗など）、評価記録に、構成ごとに、失敗した実行の記事・工程・エラーの種類（番兵）・その呼び出しのトークン数と推定コストが記録されている。失敗した記事は同じ構成で 2 回までやり直されている。2 回やり直しても記事を得られなかった場合は、その記事を記事を得られなかったものとして記録し、合格件数に数えず、その構成の比較の表にそのことが示されている。
- **AC-18**: 評価記録に、評価した構成を並べた比較の表がある。表には、構成ごとに、合格件数（解釈・文言）、品質の観点の判定の分布、記事 1 本の推定コストの平均と最大、所要時間の平均と最大、失敗した実行の回数とその推定コストの合計がある。

#### F-005: 実行の承認

実 API を呼ぶ評価の実行は、実装計画の承認の後、人の一括の承認を受けてから始める。承認は、実行する構成と回数と推定費用を示し、総額の上限を 30 USD として受ける。

**Acceptance Criteria**:

- **AC-19**: 評価記録に、承認を受けた日、承認のときに示した構成・回数・推定費用、上限（30 USD）が記録されている。承認の前に実 API を呼んだ実行はない。
- **AC-20**: 評価記録に、評価のすべての実行（失敗した実行を含む）の推定コストの合計が記録され、上限以下である。合計が上限を超える見込みになった場合は、超える実行を始める前に止め、人の承認を改めて受けたことが記録されている。

#### F-006: 本番の構成を変えるかの判断

本番の構成を変える条件を次に定める。合格件数は物差し 2 の解釈による判定の値、基準の値は基準の構成の値（合格件数 8 件、記事 1 本の推定コストの平均 0.361554 USD。[production_profile.md](../../dev/production_profile.md)「構成の比較と、構成を決めた理由」）とする。所要時間の基準の値は、0018 評価記録に記録された B3 の所要時間の平均とする。

1. 候補になる構成は、次の (i) か (ii) を満たし、かつ (iii) を満たす構成である。
   - (i) **品質の向上:** 合格件数が、基準の構成より 2 件以上多い。
   - (ii) **同等の品質で費用が下がる:** 合格件数が基準の構成以上で、基準の構成で必須の観点をすべて満たした記事と同じ動画・同じ回の記事に、必須の観点の不合格がなく、記事 1 本の推定コストの平均が基準の構成より低い。
   - (iii) **許容する料金と所要時間:** 記事 1 本の推定コストの平均が基準の構成の 3 倍以下で、所要時間の平均が基準の構成の 2 倍以下である。
2. 候補が 1 つ以上あれば、本番の構成を、合格件数の最も多い候補に変える。合格件数が同じ候補が複数あれば、記事 1 本の推定コストの平均が最も低い候補に変える。
3. 候補がなければ、本番の構成を変えない。
4. 失敗した実行の回数と費用（F-004）は、条件に加えない。判断のときに人に示す材料とする。

**Acceptance Criteria**:

- **AC-21**: 評価記録の結論に、評価した構成ごとに、(i)・(ii)・(iii) のそれぞれを満たしたかどうかとその値、候補になったかどうかが記録されている。
- **AC-22**: 評価記録の結論に、上の手順で選んだ構成（候補がない場合は「変えない」）と、その判断を人が承認したことが記録されている。人が承認するときに、失敗した実行の回数と費用が示されている。
- **AC-23**: 評価記録の結論に、評価した構成ごとに、製品の制約 1〜3 が直ったかどうか（AC-13 の記録の要約）が記録されている。

#### F-007: 本番の構成の変更

F-006 で本番の構成を変えると決めた場合に限り、本番の構成を表すものを、選んだ構成にそろえて変える。変えない場合、本機能は行わない。

**Acceptance Criteria**:

- **AC-24**: 変える場合、CLI と localhost サーバで、LLM の設定（`YT2COLUMN_LLM`・`YT2COLUMN_REVIEW_LLM`）を何も指定しない実行が、選んだ構成の各工程のプロバイダ・モデル・effort で記事を作る。
- **AC-25**: 変える場合、選んだ構成が使うプロバイダの API キーのうち設定されていないものがあると、CLI とサーバは、既存の設定の誤りの扱い（`config.ErrMissing`、終了コード `2`、API を呼ばない）で拒否し、足りないキーの名前を示す。選んだ構成が使わないプロバイダの API キーの有無では拒否しない。
- **AC-26**: 変える場合、`docs/dev/production_profile.md` の「本番の構成」「品質の目標と結果」「製品の制約」「構成の比較と、構成を決めた理由」の値と、`README.md`・`README.en.md` の推奨構成の値が、選んだ構成と評価記録の値に一致している。利用者が指定しなければならない設定の記述が、選んだ構成が使うプロバイダの API キーに一致している。
- **AC-27**: 変える場合、[ADR-0004](../../dev/adr/0004-production-profile.md) の決定が選んだ構成に更新され、今の構成は採らなかった案として、その理由（評価記録への参照）とともに記録されている。経緯に本タスクの行が加わっている。
- **AC-28**: 変える場合、`make test`・`make lint` が成功する。本番の構成の値を文書と照合するガードテストは、新しい値で成功する。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

- 新しい性能の要件はない。所要時間は F-004 で記録し、F-006 の (iii) で判断する。

### 4.2. セキュリティ (Security)

本タスクは、字幕と動画のメタ情報（信頼できない入力）を埋め込んだプロンプトを LLM API に送り、API キーを使うため、[security.md](../../dev/security.md) の対象である。新しい外部コマンド、新しい入力の形式、新しい送り先は加えない。OpenAI への送信とデータの保持は 0077 の決定（`store: false` の固定など。[ADR-0041](../../dev/adr/0041-openai-api.md)）に従う。

- 評価記録とリポジトリに、API キー、記事の全文、字幕の全文、中間生成物を含めない。評価記録に載せる記事と字幕の文は、判定の根拠に要る短い引用に限る（0018 要件定義書 §4.2 と同じ）。
- 記事・中間生成物・ログの出力先は、リポジトリの外に置く。Webhook には投稿しない。
- 採点の LLM に渡す記事と字幕は信頼できない入力であり、その中の指示に従わない（security.md §6）。
- 本番の構成を変えて OpenAI を使う構成にした場合、記事の素材の既定の送り先に OpenAI が加わる。送り先とデータの保持の説明は 0077 で README と security.md に加えた記述に従う。それらの記述が選んだ構成の既定と食い違う場合は、F-007 で合わせて直す。

### 4.3. 信頼性・可用性 (Reliability/Availability)

- 実行の失敗は F-004 の AC-17 のとおり記録し、やり直す。失敗を記事として採点しない。
- 自動の再送は加えない（[ADR-0028](../../dev/adr/0028-no-automatic-resend.md)）。やり直しは人の手順として行う。

### 4.4. 互換性 (Compatibility)

- 評価は既存の CLI と設定の契約（`YT2COLUMN_LLM`・`YT2COLUMN_REVIEW_LLM`、`--after`。[ADR-0003](../../dev/adr/0003-llm-config-contract.md)・[ADR-0023](../../dev/adr/0023-artifact-resume.md)）だけで行い、それらを変えない。
- 本番の構成を変える場合も、設定の文法（`<プロバイダ>/<モデル ID>+<effort>`）は変えない。
- 今は、検証・推敲の選択が未設定なら生成の選択を継承する（[ADR-0003](../../dev/adr/0003-llm-config-contract.md)）。選んだ構成が A・B のように工程ごとにプロバイダの異なる構成で、その既定を表すのに継承の規則を変える必要がある場合は、規則を変える前に人に確認する。この変更は ADR-0003 の決定の変更になるためである（[design_handoff.md](design_handoff.md) H-08）。

### 4.5. 保守性 (Maintainability)

- 評価のためにリポジトリに置くスクリプトは、タスクのディレクトリの中に置き、`make test`・`make lint` の対象とその結果を変えない。

## 5. 制約条件 (Constraints)

- `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
- 実 API の呼び出しは F-005 の承認の範囲に限る（`CLAUDE.md`「Tool Execution Safety」）。
- 評価の時点のモデルの振る舞いは、提供元の変更で変わりうる。基準の構成の記事は 2026-10-23 の生成であり、本タスクの記事とは生成の時期が違う。比べるときは、生成の日付を併せて示す（AC-01・AC-06）。
- 記事 10 件の合格件数には、生成のばらつきによる幅がある。F-006 の条件は、この幅を踏まえて決めた（要件定義の際に決めたこと 6）。
