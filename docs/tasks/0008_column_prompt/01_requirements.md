## 1. 概要 (Overview)

**目的:** 本書は、記事の生成に使う本番用のプロンプトテンプレート（`prompts/system.tmpl`・`prompts/user.tmpl`）の文面と、それを決めるための評価に関する要件を定義する。

**背景:**
`ArticleWriter`（#5、タスク `0004_article_writer`）は、埋め込みの既定のテンプレートからプロンプトを組み立てる。現在の既定のテンプレートは、出力の形（先頭行がタイトルの見出し、生の HTML を使わない、出典を書かない）だけを指示する仮のものであり、文体・長さ・見出しの構成は決まっていない（[prompts/README.md](../../../prompts/README.md)）。CLI（#6、タスク `0005_cli_assembly`）は `--system-prompt`・`--user-prompt` で上書きファイルを受け取り、字幕を動画 ID ごとにキャッシュするので、字幕を取り直さずにプロンプトだけを変えて記事を生成し直せる。

書き起こしから記事を作るのに向く動画には、インタビュー・対談・レビュー・講演や解説などの種類があり、種類によって適した記事の形式（インタビュー記事・対談記事・レビュー記事・解説コラム）が異なる。本タスクでは、4 つの記事の形式を定め、1 回の生成の中で LLM が動画の素材から形式を選んで記事を書くよう、テンプレートで指示する。形式の選択のために LLM の呼び出しを分けることや、利用者が形式を指定することは、本タスクでは行わない（2.3）。

本タスクは、実際の出力を複数の動画で比較・評価しながら、本番用の文面を決める。

**本書の記述範囲と、後続の文書:**
本タスクの成果物は、コードではなく、テンプレートの文面と評価の記録である。テンプレートの差し替えと上書きの仕組みは実装済みであり、新しく設計する構造がない。そのため、通常のタスクと異なり、`02_architecture.md`・`03_implementation_plan.md` は作らない。代わりに、本書の承認後、評価の記録を `02_evaluation.md` に残す（F-006）。

本書は、記事の形式とその選び方、記事が満たすべき性質（文体・長さ・構成・出力の形）、評価の観点と合格条件、評価に使う動画の選び方を定める。テンプレートの具体的な文面は、評価を通じて決める。

対応 issue: #8

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   動画を見ていない読者が、記事だけで動画の主な内容と論点を把握できる、雑誌の記事風の文章を生成できる。
-   動画の種類に適した記事の形式を、1 回の生成の中で LLM に選ばせる。
-   記事の形式ごとに文体・構成を定め、全形式に共通する長さ・出力の形とあわせて、テンプレートで LLM に指示する。
-   字幕・概要欄に根拠のない内容（発言の話者の取り違えを含む）を、事実として記事に書かせない。
-   素材（動画タイトル・概要欄・字幕）の言語によらず、記事を日本語で書かせる。
-   動画の書き起こしをなぞるのではなく、読み物として編集させる。本筋に関係のないエピソードは省き、動画に現れる順序より読みやすさを優先して並べ替え、重要なことを先に書く。
-   複数の動画で出力を評価し、評価の記録を残す。記録から、どの版の文面で、どのモデルで、どの動画を、どう評価したかを追える。

### 2.2. スコープ (In Scope)

-   既定のテンプレート `prompts/system.tmpl`・`prompts/user.tmpl` の文面
-   記事の形式の定義と、形式の選び方の規則（本書）
-   評価の観点・合格条件・対象の動画の選定（本書）
-   評価の記録（`02_evaluation.md`）
-   文面の確定に伴う文書の更新（`prompts/README.md` の「現在の文面は仮のもの」という記述、[project_overview.md](../../dev/project_overview.md)「未確定事項」のプロンプトの詳細の項目）

### 2.3. スコープ外 (Out of Scope)

-   `ArticleWriter`・CLI・テンプレートの検証規則のコードの変更。テンプレートで参照できる値（`.Title`・`.ChannelName`・`.Description`・`.Transcript`）と使える構文は、現行の [prompts/README.md](../../../prompts/README.md) のままとする。評価の途中で、現行の仕組みでは要件を満たせないと分かった場合は、本タスクでは対応せず、別の issue にする。
-   形式の選択のための LLM の呼び出し（形式を選ぶ呼び出しと、記事を書く呼び出しに分けること）。同じモデルが選ぶので、1 回の生成の中で選ばせる場合より選択の精度が上がる見込みがなく、呼び出しの回数と、選んだ形式をコードで検証する仕組みが増える。
-   利用者による形式の指定（CLI のフラグ、ブラウザ拡張の UI など）。評価で、LLM の選ぶ形式が安定しない、または期待とずれることが分かった場合は、別の issue にする。
-   F-001 の 4 つ以外の記事の形式。
-   プロバイダごとのプロンプトの微調整（[project_overview.md](../../dev/project_overview.md)「未確定事項」）。評価は DeepSeek だけで行う。
-   DeepSeek の thinking モードの切り替えと、`temperature` などの生成パラメータの設定。評価は現行の設定（API の既定）で行う。
-   長い動画のチャンク分割（#13）。対象の動画は 40 分前後までとする。
-   見出しごとの、動画の該当時刻へのリンク（#10）。
-   日本語の字幕がない動画で、原語の字幕を取得すること。現行の CLI は日本語の字幕（`ja`）だけを取得する。日本語の字幕があればそれを使い、なければ原語の字幕を取得して LLM が日本語に訳しながら記事を書く、という方針とし、字幕の取得の変更は #136 で扱う（YouTube が機械翻訳した日本語の自動字幕を「日本語の字幕」として扱うかどうかも、#136 で決める）。本タスクのテンプレートは、素材が日本語以外でも日本語で記事を書くよう指示する（F-002）が、原語の字幕での評価は、#136 で行う。
-   ブラウザ拡張から受け取る字幕（#43）での評価。拡張から受け取る値も同じテンプレートの値として埋め込まれるが、本タスクの評価は CLI（yt-dlp）で取得した字幕で行う。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 記事の形式と、その選び方

記事の形式は次の 4 つとする。LLM は、動画タイトル・チャンネル名・概要欄・字幕から動画の種類を判断し、1 つの形式を選んで記事を書く。

| 形式 | 向く動画 |
|---|---|
| インタビュー記事 | 聞き手が質問し、1 人の話し手が答える動画 |
| 対談記事 | 2 人以上の話者が、対等に意見を交わす動画（対談・鼎談・座談会など） |
| レビュー記事 | 製品・作品・サービスなどを紹介し、評価する動画 |
| 解説コラム | 講演・解説・独白など、上の 3 つに当てはまらない動画 |

-   1 本の記事では 1 つの形式だけを使い、形式を混ぜない。
-   字幕には話者の区別がない。発言を話者に割り当てる形式（インタビュー記事・対談記事）は、字幕から聞き手と話し手、または話者どうしの発言の区別を読み取れる場合にだけ選ぶ。読み取れない場合は、解説コラムを選ぶ。
-   どの形式にも当てはまるか迷う場合も、解説コラムを選ぶ。
-   選んだ形式の名前を、記事の中に書かない。形式は、記事の構成と文体から分かるようにする（F-003）。

**Acceptance Criteria**:
- **AC-01**: 評価に使うすべての動画（F-006）で、記事の形式が、評価の前に動画ごとに記録した期待する形式（1 つ、または許容する複数）のいずれかである。
- **AC-02**: 評価に使うすべての動画の記事で、1 つの形式の構成と文体（F-003）だけが使われている。

#### F-002: 全形式に共通する文体・内容・編集の方針

-   話し言葉のくだけた表現・言いよどみ・繰り返しは、書き言葉に整える。発言を引用する場合や、発言を記事の段落にする場合は、意味を変えない範囲で整えてよい。
-   記事に事実として書く内容は、字幕・概要欄・動画タイトル・チャンネル名に根拠があるものに限る。書き手の解釈や評価を書く場合は、解釈であると読み取れる書き方にする。
-   発言を特定の話者のものとして書くのは、その発言がその話者のものであると字幕から読み取れる場合に限る。読み取れない発言は、話者を断定しない書き方にする。
-   人を評した発言（ある話者が別の人や自分自身を評した言葉）は、評した人と評された人の両方を字幕から確かめられる場合にだけ書く。確かめられない場合は、話者を断定しない書き方にしても書かない。評した人と評された人を取り違えると、断定を避けた書き方でも意味が逆になるからである。
-   話者の名前は、動画タイトル・チャンネル名・概要欄・字幕（話者の名乗りなど）のいずれかで確かめられる場合にだけ使う。確かめられない場合は、「聞き手」「ゲスト」など役割で呼ぶ。
-   字幕の誤認識と思われる語は、文脈から明らかな場合に限り正しい語に読み替えてよい。固有名詞など、正しい語が文脈から明らかでない場合は、その語を断定的に使わない。
-   絵文字・顔文字、誇張した宣伝調の表現（「必見」「衝撃」など）は使わない。
-   記事は、素材の言語によらず日本語で書く。日本語以外の素材（動画タイトル・概要欄・字幕）は、日本語に訳して使う。発言の引用も日本語に訳す。
-   人名・製品名・組織名などの固有名詞は、定着した日本語の表記があればそれを使い、なければ原語の表記のまま書く。
-   人名と難読地名には、記事で最初に出てくる箇所で 1 回だけ、`堀田良幸（ほりた・よしゆき）` のように括弧で読み仮名を併記する。人名の読みは、動画タイトル・チャンネル名・概要欄・字幕で確かめられる場合にだけ付け、推測で付けない（「堀田」が「ほりた」であるように、読みは推測と違うことがある）。地名の読みは、一般的な知識で付けてよい。
-   素材が演出のために使う表記（「町」を片仮名で「マチ」と書くなど）は、一般的な表記に直す。固有名詞と、発言の引用の中の表記は直さない。

編集の方針は次のとおりとする。

-   記事は書き起こしの要約ではなく、読み物として編集する。
-   話の本筋に関係のないエピソード・脱線・雑談は省いてよい。
-   話題を並べる順序は、動画に現れる順序を厳密に守らなくてよい。読みやすさと、重要なことを先に書くこと（F-003）を優先して並べ替える。
-   ただし、省略と並べ替えで発言の意味を変えない。話者が主張に付けた条件や留保は省かない。話の前後関係（意見が途中で変わった、前の話を受けて答えた、など）が意味に関わる場合は、その関係が分かるように書く。

**Acceptance Criteria**:
- **AC-03**: 評価に使うすべての動画の記事で、字幕・概要欄・動画タイトル・チャンネル名に根拠のない事実の記述がない。確認の方法は F-006 の観点「根拠」による。
- **AC-04**: 評価に使うすべての動画の記事で、発言の話者の割り当てと、話者の名前が、字幕・概要欄・動画タイトル・チャンネル名から確かめられる。確認の方法は F-006 の観点「根拠」による。
- **AC-25**: 評価に使うすべての動画の記事で、併記した人名の読みが動画タイトル・チャンネル名・概要欄・字幕で確かめられ、併記した地名の読みが正しい。確認の方法は F-006 の観点「根拠」による。
- **AC-05**: 評価に使うすべての動画の記事に、絵文字・顔文字がない。
- **AC-23**: 評価に使うすべての動画の記事に、誇張した宣伝調の表現（「必見」「衝撃」など）がない。
- **AC-22**: 評価に使うすべての動画の記事が、日本語で書かれている（固有名詞の原語の表記を除く）。動画タイトル・概要欄が日本語以外の動画でも同じである。
- **AC-20**: 評価に使うすべての動画の記事で、省略と並べ替えによって発言の意味が変わっていない（話者が付けた条件・留保が落ちていない、意味に関わる前後関係が取り違えられていない）。確認の方法は F-006 の観点「根拠」による。

#### F-003: 形式ごとの文体と構成

全形式に共通する構成は次のとおりとする。

-   1 行目はタイトルの見出しとする（F-005）。タイトルは記事の主題を表す 40 字以内の文とし、動画タイトルをそのまま写さない。
-   タイトルの次に、見出しを付けないリード文（1〜2 段落）を置く。リード文は、動画が何について、誰が語っているかと、動画の主な結論・論点を示す。
-   リード文の後に、`## ` で始まるレベル 2 の見出しで区切った節を 3〜5 個置く。レベル 3 以下の見出しは使わない。
-   記事は新聞記事のように、重要なことから先に書く。読者が途中で読むのをやめても、そこまでで動画の大枠が分かるようにする。リード文で動画の大枠を示し、節は重要度の高い順に並べ、個々の細かいエピソードは後に回す。節の中でも、要点を先に、具体例や補足を後に書く。
-   ただし、話の前後関係は重要度の順より優先する。ある節が別の節の説明（歴史の流れ、前提となる知識、問題とその解決など）を前提とする場合は、前提となる節を先に置く。前後関係のために最も重要な論点の節を後に置く場合も、最も重要な論点の中身はリード文で示す。
-   地の文（リード文・見出し・書き手の説明の文。発言の引用と、発言の段落は含まない）は「だ・である」調とし、書き手は動画の外にいる第三者とする。地の文に、話者の一人称（「私は」「僕は」のほか、「私たち」「我々」などの一人称複数を含む）を使わない。話者が使った「私たち」などを地の文に写さず、主語を省くか、「人」などの一般的な主語にする。
-   箇条書きは、手順や列挙など、文章より箇条書きのほうが読みやすい箇所に限って使う。記事の大半を箇条書きにしない。

形式ごとの文体と構成は次のとおりとする。

-   **インタビュー記事**: 各節は、聞き手の質問と話し手の答えの一問一答で構成する。聞き手の質問は `――` で始まる段落とし、質問の要旨を短く書く。話し手の答えは、話し手の一人称の話し言葉を整えた段落とし、「です・ます」調でもよい。答えの段落には話者の名前を付けない。節の見出しは、その節で語られる話題を表す。
-   **対談記事**: 各節は、話者の発言の段落で構成する。発言の段落は `**話者の名前**：` で始め、話者の一人称の話し言葉を整えた文とする。話者の名前は F-002 の規則に従う。節の見出しは、その節の論点を表す。
-   **レビュー記事**: リード文で、評価の対象と、話者の総合的な評価を示す。節は、対象の概要、話者が評価する点、話者が気になるとする点を含む。評価は話者のものとして紹介し、書き手の評価として書かない。
-   **解説コラム**: 話者の主張を「〜と語る」「〜と指摘する」のように話者のものとして紹介し、論点を整理する。話者のものとして紹介するのは、主張・評価・意見とする。名前の分からない話者（ナレーションなど）が説明する一般的な知識は、文ごとに「動画は〜と説明する」のように紹介せず、地の文で書いてよい。その場合も、内容は F-002 の根拠の規則に従う。

**Acceptance Criteria**:
- **AC-06**: 評価に使うすべての動画の記事が、タイトル（40 字以内）→ 見出しのないリード文 → レベル 2 の見出しの節 3〜5 個、の構成になっており、レベル 3 以下の見出しを含まない。
- **AC-07**: 評価に使うすべての動画の記事で、タイトルが動画タイトルと同一の文字列でない。
- **AC-08**: 評価に使うすべての動画の記事で、地の文が「だ・である」調に統一され、地の文に話者の一人称（一人称複数を含む）がない。
- **AC-09**: 評価に使うすべての動画の記事が、選んだ形式の文体と構成の規則（本節の形式ごとの規則）に従っている。
- **AC-21**: 評価に使うすべての動画の記事で、リード文だけを読んで、動画の主題・話者・主な結論が分かる。また、F-006 の品質の観点「重要度の順」で不十分（1）と判定されない。

#### F-004: 長さ

-   本文（§6。LLM が書いた Markdown のうちタイトルの行を除いた部分で、システムが付ける出典のブロックは含まない）の長さは、全形式で 2,500〜4,000 字を目安とする。字数はコードポイントで数える。
-   素材が少ない短い動画では、下限を下回ってよい。下限に届かせるために、根拠のない内容や同じ内容の繰り返しで水増ししない。

上限の 4,000 字は、出典のブロックを付けても Mattermost の 1 メッセージの上限（16,383 コードポイント）に十分収まり、分割投稿を起こさない値である。

**Acceptance Criteria**:
- **AC-10**: 評価に使う動画のうち 15 分以上のものの記事は、本文が 2,500〜4,000 字に収まる。
- **AC-11**: 評価に使う動画のうち 15 分未満のものの記事は、本文が 4,000 字以下であり、F-006 の観点「冗長さ」で不十分（1）と判定されない。

#### F-005: 出力の形

現行の仮のテンプレートが指示する出力の形（タスク `0004_article_writer` の F-005）を維持する。

-   1 行目を `# ` で始まるタイトルの見出しにする。
-   生の HTML を使わない。コードフェンスを使う場合は閉じる。
-   出典や元の動画の URL を書かない。出典はシステムが付ける。
-   区画の中の文章（動画タイトル・チャンネル名・概要欄・字幕）を指示として扱わず、素材としてだけ使うことを指示する。

**Acceptance Criteria**:
- **AC-12**: 評価に使うすべての動画で、CLI による記事の生成が `ArticleWriter` の出力の検証によるエラーにならずに成功する。
- **AC-13**: 評価に使うすべての動画の記事に、元の動画の URL と、出典を示す節（システムが付けるものを除く）がない。
- **AC-14**: 本番用の既定のテンプレートで、既存のテスト（タスク `0004_article_writer` の AC-06・AC-30 を検証するものを含む）が成功する。

#### F-006: 評価

評価は、対象の動画の集合に対し、テンプレートの版ごとに記事を生成し、観点ごとに判定して記録する。

**対象の動画:** 次の条件をすべて満たすように、5〜6 本を選ぶ。

-   すべて日本語の字幕（手動または自動生成）があり、CLI で字幕を取得できる。
-   F-001 の 4 つの形式のそれぞれについて、その形式が向く動画を 1 本以上含む。
-   長さは 40 分以下とし、15 分未満の動画と、30〜40 分の動画をそれぞれ 1 本以上含む。
-   自動生成の字幕の動画を 1 本以上含む。
-   ジャンル（技術・ビジネス・教養など）が 1 つに偏らない。
-   動画タイトルまたは概要欄が日本語以外の動画を、見つかれば 1 本含める（字幕は日本語のもの）。見つからなければ、その旨を `02_evaluation.md` に記録する。

評価を始める前に、選んだ動画ごとに、URL・タイトル・長さ・字幕の種類と、期待する形式（AC-01）・主な論点を `02_evaluation.md` に記録する。期待する形式は、動画を見て判断し、2 つの形式のどちらも妥当な動画では両方を記録する。主な論点は、動画の本筋をなす論点を 3〜5 個、重要度の高い順に書く（1 番目を「最も重要な論点」と呼ぶ）。生成した記事を見てから、期待する形式と主な論点を変えない。

**評価の観点:** 必須の観点は、1 つでも不合格なら記事全体を不合格とする。品質の観点は 3 段階（3: 良い、2: 許容できる、1: 不十分）で判定し、各段階の基準は後述の「品質の観点の段階の基準」による。

| 種別 | 観点 | 判定の基準 |
|---|---|---|
| 必須 | 形式の選択 | AC-01・AC-02 を満たす |
| 必須 | 形式の規則 | AC-06・AC-07・AC-08・AC-09・AC-12・AC-13 を満たし、AC-21 のリード文の条件を満たす |
| 必須 | 根拠 | 記事の事実の記述が、字幕・概要欄・動画タイトル・チャンネル名で裏付けられ、発言の話者の割り当てと話者の名前が確かめられ、省略と並べ替えで発言の意味が変わっていない。併記した読み仮名が確かめられる（AC-03・AC-04・AC-20・AC-25） |
| 必須 | 長さ | AC-10・AC-11 を満たす |
| 必須 | 表記 | AC-05・AC-22・AC-23 を満たす |
| 品質 | 要点の網羅 | 動画の主な論点が記事に含まれ、本筋に関係のないエピソードに字数を割いていない |
| 品質 | 重要度の順 | 記事の前半ほど重要なことが書かれ、どこで読むのをやめても、そこまでで動画の大枠が分かる |
| 品質 | 構成 | 節の分け方と順序が読み物として自然で、見出しが節の内容を表している |
| 品質 | 読みやすさ | 話し言葉が書き言葉に整えられ、読み物として通して読める |
| 品質 | タイトル・リード文 | タイトルとリード文から、記事の主題と要点が分かる |
| 品質 | 冗長さ | 同じ内容の繰り返しや水増しがない |

**品質の観点の段階の基準:** 各観点は、次の表で 1 の条件に当てはまれば 1、当てはまらず 3 の条件をすべて満たせば 3、それ以外は 2 とする。箇所の数は、記事の中で該当する文または段落を数える。

| 観点 | 3: 良い | 1: 不十分 |
|---|---|---|
| 要点の網羅 | 記録した主な論点をすべて含み、本筋に関係のないエピソードは各 1 段落以内 | 記録した主な論点のうち 2 つ以上が欠ける、または本筋に関係のないエピソードが 1 つの節の大半を占める |
| 重要度の順 | 最も重要な論点がリード文に現れ、節が、話の前後関係を崩さない範囲で、記録した主な論点の重要度の順に並ぶ（細かいエピソードは、その論点の節の後半に置かれる） | 最も重要な論点が、リード文にも最初の節にも現れない、または最も重要な論点を扱う節が記事の後半の節（節が 3 個なら 3 番目、4 個なら 3・4 番目、5 個なら 4・5 番目）である（話の前後関係のために後に置いた場合を除く） |
| 構成 | 各節が 1 つの話題を扱い、見出しがその話題を表し、同じ話題が複数の節に分かれておらず、前提となる説明より前に置かれた節がない | 見出しと内容がずれる節、同じ話題が複数の節に分かれている箇所、または前提となる説明より前に置かれた節が、合わせて 2 つ以上ある |
| 読みやすさ | 地の文に、話し言葉の言いよどみ・崩れの残りと、意味の取れない文がなく、素材で読みを確かめられる人名と難読地名に読み仮名が併記され、素材が演出のために使う表記が一般的な表記に直されている | 話し言葉の言いよどみ・崩れの残りが 3 箇所以上ある、または意味の取れない文が 1 つ以上ある |
| タイトル・リード文 | タイトルが記事全体の主題を表し、リード文が最も重要な論点の中身（結論や主張そのもの）を示し、400 字以内で、本文で述べる細部（製品名の整理、数値の詳細、個々の理由の説明など）を含まない | タイトルが記事の一部の話題だけを表す、または記事の主題とずれる |
| 冗長さ | 同じ内容を繰り返す箇所がない（リード文と節の間の重なりは除く） | 同じ内容を繰り返す箇所が 2 つ以上ある、または素材にない一般論で字数を埋めた段落がある |

段階の基準の数え方と、観点の振り分けは次のとおりとする。

-   **冗長さ:** 節と節の間で、新しい情報を加えずに前の節と同じ内容を繰り返す箇所と、リード文を繰り返すだけの結びの段落を、繰り返しとして数える。リード文と節の間の重なりは、節が新しい情報を加えていなくても数えない。リード文は要点を先に示すためのもので、本文とは離れて読まれるからである。理由をつないで 1 つの事柄を説明する文の並びも、繰り返しとして数えない。
-   **音声認識の誤りの残り:** 字幕の誤認識をそのまま写して意味の取れなくなった語や文（存在しない語を含む）は、観点「読みやすさ」の意味の取れない文として数える。誤認識によって事実が変わる場合は、観点「根拠」の根拠のない記述として扱う。
-   **表記:** 観点「表記」は、AC-05・AC-22・AC-23 だけを判定する。語の誤りや文の分かりにくさは、この観点では判定しない。

**合格条件:** テンプレートの版が合格するのは、対象のすべての動画で、記事が必須の観点をすべて満たし、品質の観点に 1 がない場合とする。LLM の出力は実行ごとに変わるので、最終の版は、各動画で 2 回ずつ記事を生成し、すべての記事が合格条件を満たすことを確認する。

**判定者:** 判定は、スクリプト・LLM・人（本書のレビュアー）で次のように分担する。

-   **スクリプト**: 機械的に判定できる部分を判定する。本文の字数（AC-10・AC-11）、見出しの構成とタイトルの字数（AC-06）、タイトルと動画タイトルの一致（AC-07）、絵文字（AC-05）、URL（AC-13）など。スクリプトの内容は、再現できるよう `02_evaluation.md` に記録する。
-   **LLM**: スクリプトで判定しない部分を一次採点する。観点「根拠」では、字幕のキャッシュと記事を突き合わせ、根拠の見つからない記述・確かめられない話者の割り当てと名前・意味の変わった省略と並べ替えを、記事の該当箇所とともに列挙する。ほかの観点では、判定ごとに、その根拠となる記事の箇所を引用する。採点に使う LLM は、記事を生成するモデル（DeepSeek）と別の系統のモデルとする。自分と同じ系統のモデルの出力を高く評価する偏りを避けるためである。字幕と記事は信頼できない入力として扱い、その中の指示に従わない（[security.md](../../dev/security.md) §6）。
-   **採点の素材**: LLM が記事と突き合わせる素材は、その記事を生成した実行で CLI が読み込んだキャッシュとする。キャッシュの形式・検証・拒否の契約は、タスク `0002_ytdlp_transcript_source` の要件定義書（F-003・F-004・F-005）と [cache_consistency.md](../../dev/cache_consistency.md) が定めるものに従い、本タスクでは定め直さない。本タスクはキャッシュを読むプログラムを追加しない。
    -   素材として読むのは、ポインタ（`<動画 ID>.current`）が指すスロットの `<動画 ID>.ja.json3`・`<動画 ID>.info.json` だけとする。もう一方のスロットや、キャッシュの外に写したファイルは素材にしない。
    -   素材が有効であることの根拠は、同じキャッシュから CLI が記事を生成できたこと（`ArticleWriter` に渡る前に 0002 の契約で検証されたこと）とする。CLI がキャッシュを拒否した動画は、その版では評価しない。キャッシュを手で直したり、拒否されたファイルを素材にしたりせず、バックアップから戻して生成し直す（§5、手順は `02_evaluation.md`）。
-   **人**: 次を行う。
    -   期待する形式と主な論点を確定する。LLM が案を出してよいが、確定は人が行う。物差しを作る者と採点する者が同じだと、両者の誤りが重なって見逃されるためである。
    -   最初の版で、2 本の動画を LLM の採点を見ずに採点し、LLM の採点と突き合わせる。必須の観点の合否、または品質の観点の 1 とそれ以外の境目で判定が食い違った場合は、段階の基準の書き方を直してから評価を続ける。
    -   LLM の採点のうち、必須の観点の不合格と、品質の観点の 1・2 の判定をすべて確認する。
    -   最終の版の合否を承認する。

**記録:** `02_evaluation.md` に、テンプレートの版ごとに次を記録する。

-   テンプレートの文面（初版は全文、以降は前の版からの差分）と、その版で変えた理由
-   生成の日時、`Article` の生成モデル名とモデルの版の識別子（`ModelVersion`）
-   採点に使った LLM のモデル名と、判定ごとの判定者（スクリプト・LLM・人）。人が LLM の判定を変えた場合は、変えた理由
-   動画ごとの、記事の形式と、観点ごとの判定。不合格や 2 以下の判定には理由を書く（記事からの短い引用を含めてよい）
-   次の版で変える点

**Acceptance Criteria**:
- **AC-15**: `02_evaluation.md` に、評価を始める前に選んだ対象の動画と、それぞれの期待する形式・主な論点が記録され、その集合が本節の条件をすべて満たす。
- **AC-16**: `02_evaluation.md` に、評価したテンプレートの版ごとに、本節の「記録」の項目がすべてある。
- **AC-24**: `02_evaluation.md` に、最初の版での、人による 2 本の動画の採点と LLM の採点の突き合わせの結果と、それによって段階の基準を直したかどうか（直した場合はその内容）が記録されている。
- **AC-17**: 最終の版について、対象のすべての動画で 2 回ずつ生成した記事が合格条件を満たし、その判定が `02_evaluation.md` に記録されている。

#### F-007: 既定のテンプレートへの反映

合格した最終の版を、既定のテンプレートとして `prompts/` に反映する。

**Acceptance Criteria**:
- **AC-18**: `prompts/system.tmpl`・`prompts/user.tmpl` の内容が、`02_evaluation.md` に記録した最終の版と一致する。
- **AC-19**: `prompts/README.md` から「現在の文面は仮のもの」という記述が除かれ、[project_overview.md](../../dev/project_overview.md)「未確定事項」からコラム生成プロンプトの詳細の項目が除かれている。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   40 分前後の動画で、記事の生成が 1 回の LLM 呼び出しで完了すること（出力が打ち切られないこと。AC-12 で確認する）。

### 4.2. セキュリティ (Security)

-   テンプレートに秘密情報を書かない（[prompts/README.md](../../../prompts/README.md)「秘密情報を書かない」）。
-   生成した記事の全文と字幕は、リポジトリにコミットしない。記事は字幕から作られ、動画の内容を大きく再現するため、`testdata/` の方針（[security.md](../../dev/security.md) §7）と同じく、再配布の許可が確認できないものを残さない。評価の記録には、判定の理由に必要な短い引用だけを書く。
-   評価のための記事の生成は、`--out` でリポジトリの外のファイルに書き出して行い、Webhook には投稿しない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   LLM の出力は実行ごとに変わる。最終の版は複数回の生成で確認する（F-006）。

### 4.4. 互換性 (Compatibility)

-   既定のテンプレートは、現行のテンプレートの検証規則（[prompts/README.md](../../../prompts/README.md)）を満たす（AC-14）。

### 4.5. 保守性 (Maintainability)

-   テンプレートの文面は、後から形式や文体を調整する人が、どの指示がどの要件に対応するかを読み取れるよう、全形式に共通する指示と、形式ごとの指示を分けて書く。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   LLM の API の呼び出し（記事の生成）は、CLAUDE.md「Tool Execution Safety」に従い、実行のたびに人の承認を得る。
-   DeepSeek の料金が 2 倍になる時間帯（日本時間の平日 10–13 時と 15–19 時）を避けて生成することが望ましい。
-   評価中は字幕を取り直さないよう、`--keep-cache` を付けて生成する。
-   家庭用回線から yt-dlp で字幕を取得すると、YouTube のアクセス制限を受けやすい。字幕の取得は家庭用回線から行わず、携帯電話のテザリングなどで 1 回に 1 本ずつ行う。評価中は、YouTube にアクセスしない設定（`YT2COLUMN_YTDLP_PATH` に必ず失敗するコマンドを指定するなど）で CLI を実行する。手順は `02_evaluation.md` に記す。
-   評価に使うモデルは、現行の設定（`YT2COLUMN_MODEL`）のモデルとする。`deepseek-flash` は提供元が指すモデルを切り替えるエイリアスなので、版の間の比較では `ModelVersion` の違いに注意する。
-   字幕には話者の区別がない（json3 の字幕にも、ブラウザ拡張でコピーする書き起こしにも、話者の情報は含まれない）。発言の話者の割り当ては、字幕の文脈からしか判断できない（F-001・F-002）。
-   句読点もない字幕の対談では、発言の切れ目と話者の区別が字幕から読み取れないことがある。評価では、生成モデルを上位のもの（deepseek-v4-pro）に変えても、同じ箇所の話者を同じように取り違えた（`02_evaluation.md` §5.5）。本タスクのテンプレートは、確かめられない発言を書かないことで誤りを避けるが、話者を区別できたかどうかを記事の外に知らせる仕組みはない。話者の区別が難しい動画を検出し、より能力の高いモデルに生成を回すことは、後日の拡張として別の issue で扱う。

## 6. 用語集 (Glossary)

-   **記事の形式**: F-001 の 4 つ（インタビュー記事・対談記事・レビュー記事・解説コラム）のいずれか。
-   **期待する形式**: 評価の前に、対象の動画ごとに記録する、その動画に適した記事の形式（F-006）。
-   **主な論点**: 評価の前に、対象の動画ごとに重要度の高い順に記録する、動画の本筋をなす論点（F-006）。1 番目を「最も重要な論点」と呼ぶ。
-   **テンプレートの版**: 評価の単位とする、system 用と user 用のテンプレートの文面の組。`02_evaluation.md` で連番を付けて区別する。
-   **本文**: 記事の Markdown のうち、1 行目のタイトルの見出しを除いた部分。出典のブロックは含まない。
-   **本筋**: 動画の主題と主な結論・論点に関わる話。これに関わらないエピソード・脱線・雑談は省いてよい（F-002）。
-   **地の文**: 記事のうち、発言の引用と、発言の段落（インタビュー記事の答え・対談記事の発言）を除いた部分（F-003）。
-   **必須の観点・品質の観点**: F-006 の評価の観点の種別。
-   用語は `docs/translation_glossary.md` と統一する。
