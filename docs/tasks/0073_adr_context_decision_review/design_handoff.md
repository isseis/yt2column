# 設計への申し送り：既存の ADR-0001〜0030 の背景と決定を、ADR の規約の基準で見直す

要件定義書（[01_requirements.md](01_requirements.md)）を書く際に挙がった、設計で決めることを記録する。`02_architecture.md` は、各項目をどう扱ったかを記す。

## H-01: ADR を PR へまとめる方法

AC-14 は、1 つの PR が見直す ADR を 8 本以下とする。どの ADR を同じ PR にまとめるか（番号の順、主題の系列、互いに参照し合う ADR を同じ PR にするかなど）と、PR の順序を、設計で決める。たとえば ADR-0001 は ADR-0019 と ADR-0020 を参照し、ADR-0009 は ADR-0008・ADR-0010・ADR-0011 を参照する。参照し合う ADR を別の PR に分けると、後の PR の見直しが前の PR の書き直しを読む前提になる。PR の境界そのものは `03_implementation_plan.md` で決める。

## H-02: 変えないものの確かめ方

AC-06（正本の文書とずれの issue へのリンクが残る）、AC-08（「状態」を変えず、「採らなかった案」「結果」「経緯」は移動と訂正を除いて変えない）、AC-10（変えるファイルの範囲）は、前後の関係を述べる。これらを、本タスクの `_checks/` の下の差分の確認で確かめるか、PR のレビューで読んで確かめるかを、設計で決める。差分の確認にするときは、移動（AC-02）と訂正（AC-09）を、確認がどう見分けるかも決める。タスク 0065 の `_checks/adrchecks` とタスク 0070 の `_checks/` が、使える前例である。

## H-03: 決定が変わらないことをレビュアーに示す方法

AC-05 は、書き直した「決定」が同じ決定を述べることを求め、PR のレビューで確かめる。「決定」の項目を書き直したり、まとめたり、細部を正本へ移したりすると、前後の対応がレビュアーから見えにくい。PR の説明やコミットの分け方で、前後の項目の対応（どの項目がどの項目になったか、除いた細部がどの正本の文書か出典のタスク文書にあるか）をどう示すかを設計で決める。

## H-04: 古くなった参照の見つけ方

AC-09 は、対象の ADR の全体で古くなった参照を直すことを求める。リンクの先のファイルの有無は `TestInstructionDocPaths` などが確かめるが、節の見出し・名前・パッケージ名が今の文書やコードと合っているかは、読んで確かめるしかない。見直しの手順で、何をどう確かめるかを設計で決める。

## H-05: 「背景」から除いた前の決定の「経緯」への置き方

AC-02 と AC-17 は、「背景」から除いた前の決定を、まだ「経緯」になければ、規約の「History entries」の日付の規則で「経緯」に置くことを求める。出典の文書から日付を決める手順（見出しの日付、承認の行、`Review date`、文書を加えたコミット）と、その確認を、見直しの手順のどこに置くかを設計で決める。
