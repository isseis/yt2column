## 1. 概要 (Overview)

**目的:** 本書は、ADR-0001〜0038 の「背景」と「決定」を、ADR の規約 `docs/dev/conventions/adr.md` の「Writing an ADR」の基準に合わせて見直すための要件を定義する。見直しは、決定を変えない編集上の訂正として行う（[#729](https://github.com/isseis/yt2column/issues/729)）。

**背景:**

ADR は、後の開発者が、変えようとしている主題の決定とその理由を知るために読む文書である（`docs/dev/conventions/adr.md:143-145`）。タスク 0070（[#728](https://github.com/isseis/yt2column/issues/728)）は、規約に「背景」と「決定」の基準を足した。「背景」には、決定が答える問題と、決定を縛る前提だけを書く（`docs/dev/conventions/adr.md:147-152`）。「決定」には、後の変更が守るべき規則を 1 項目ずつ、短い理由と正本の場所とともに書き、正本の一覧の写しや、腐りやすい実装の細部は書かない（`docs/dev/conventions/adr.md:154-166`）。

ADR-0001〜0030 は、この基準より前に書かれた。基準に合わない記述の例を挙げる。

-   ADR-0009 の「決定」は、`index + 1`・`openerTabId`・`BroadcastChannel`・`tabs.remove`・最大 5 秒の待ちといった実装の細部を含む（`docs/dev/adr/0009-viewer-opening.md:17`・`:23`）。
-   ADR-0001 と ADR-0009 などは、「決定」の各項目に正本の場所を添えず、末尾の段落に正本をまとめて挙げる（`docs/dev/adr/0001-llm-adapter-stdlib.md:29`、`docs/dev/adr/0009-viewer-opening.md:26`）。
-   ADR-0001 の「背景」は、アダプタが同じ振る舞いを求められる項目の一覧を持つ（`docs/dev/adr/0001-llm-adapter-stdlib.md:13-17`）。

ADR-0031〜0038 は、タスク 0065 の最後の PR（[#727](https://github.com/isseis/yt2column/pull/727)）で、そのときレビュアーと決めた基準に合わせて書き直された。タスク 0070 は、その基準を規約に入れた（`docs/tasks/0070_adr_writing_criteria/01_requirements.md`「issue #728 で決めたこと」）。ただし、出典に理由がない「決定」の項目には `理由は記録されていない` と書くという規則は、#727 ではなく、タスク 0070 の要件定義で足された（同「要件定義の際に決めたこと（2026-11-09）」）。ADR-0031〜0038 にも、規約の文面に合わない記述がある。

-   ADR-0031 は、ADR-0001 と同じく、「決定」の末尾の段落に正本をまとめて挙げる（`docs/dev/adr/0031-secret-closure.md:22`）。
-   ADR-0033 の「決定」の 3 つ目から 6 つ目の項目は、正本の文書か場所を添えないか、理由を添えない（`docs/dev/adr/0033-transcript-cache-slots.md:21-24`）。

ADR-0039 は、タスク 0070 が規約の基準に沿って書いた。

規約は、決定を下しも変えもしない PR にも、4 種類の編集上の訂正を認める（`docs/dev/conventions/adr.md:264-281`）。(1) 基準に合わせる書き直し、(2) ずれの記述の削除、(3) 古くなった参照の訂正、(4) 意味を変えない誤字の訂正である。訂正は、コミットメッセージと PR の説明に記録し、「経緯」には項目を足さない（`docs/dev/conventions/adr.md:298-306`）。PR を作った後は、ADR に新しい編集上の訂正を加えない（`docs/dev/conventions/adr.md:308-315`）。issue #729 が求めた「決定を変えずに書き方だけを直す PR の扱い」は、これらの規則で決まっている。

ADR の記述には、ほかの文書とコードが頼っているものがある。たとえば ADR-0031 の「決定」は、Webhook の送信の失敗を URL を含まないエラーに変える規則を ADR-0011 が定めるとする（`docs/dev/adr/0031-secret-closure.md:18`）。軽量プロセスの確かめ直しのスクリプトとそのテストは、ADR-0012 の「見直しの条件」の節を指す（`.claude/commands/_lib/lightweight-check.sh:30-33`、`cmd/yt2column/lightweight_docs_test.go:485-486`、`docs/dev/adr/0012-lightweight-check-in-bash.md:30`）。

**軽量プロセスを取らない理由:** 38 本の ADR と索引を変えるので、軽量プロセスの全体の上限（手で変えるファイル 10 個まで）を超える（`docs/dev/conventions/requirements_process.md`「Lightweight Process」の「Limits」）。

対応 issue: [#729](https://github.com/isseis/yt2column/issues/729)（前提: [#728](https://github.com/isseis/yt2column/issues/728)、タスク 0070。関連: タスク 0065 の [#666](https://github.com/isseis/yt2column/issues/666) と [#727](https://github.com/isseis/yt2column/pull/727)、[#732](https://github.com/isseis/yt2column/issues/732)、[#747](https://github.com/isseis/yt2column/issues/747)、[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md)（ADR の背景と決定の書き方と、決定を変えない編集上の訂正））

**本書の記述範囲:** 本書は、見直しの対象、見直した後の ADR が満たすこと、変えないもの、PR の大きさの上限、記録の仕方を定める。ADR を PR へどうまとめるか、変えないものをどう確かめるか、見直しの手順は、`02_architecture.md` と `03_implementation_plan.md` で決める（[design_handoff.md](design_handoff.md)）。

**上の決定から導いたこと（PR のレビューで確認を求める）:**

-   **見直しで見つけたずれは、ADR に書かずに issue にする:** 規約は、決定を変えない PR が ADR のずれを見つけたときは、ずれの記述を足さずに issue を立てるとする（`docs/dev/conventions/adr.md:329-336`）。本タスクの PR は決定を変えないので、これに従う（F-003）。
-   **今あるずれの記述は、意味を変えずに残す:** ADR-0006（`docs/dev/adr/0006-threat-model.md:29`、[#678](https://github.com/isseis/yt2column/issues/678)）と ADR-0028（`docs/dev/adr/0028-no-automatic-resend.md:24`、[#720](https://github.com/isseis/yt2column/issues/720)）の「決定」は、ずれの記述を持つ。issue #729 は、ずれの issue へのリンクを変えないと述べるので、見直しの PR は、ずれが直ったかどうかを確かめず、記述を残す。ずれを直す PR が消す（`docs/dev/conventions/adr.md`「Discrepancy statements」）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   後の開発者が、ADR-0001〜0038 のどれを読んでも、「背景」から決定が答える問題と前提を、「決定」から守るべき規則とその理由と正本の場所を、規約の「Writing an ADR」の基準どおりに読み取れるようにする。

### 2.2. スコープ (In Scope)

-   ADR-0001〜0038 の「背景」と「決定」を、規約の「Writing an ADR」の基準に合わせて書き直すこと（F-001・F-002）。
-   書き直しで「背景」と「決定」から除いた前の決定と退けた案を、「経緯」と「採らなかった案」へ移すこと（F-001）。
-   書き直した「決定」と合わなくなった題名と、その索引の行を書き直すこと（F-002）。
-   ADR-0001〜0038 の全体で見つけた古い参照と誤字を直すこと（F-003）。
-   ほかの文書とコードが頼る ADR の記述を残すこと（F-004）。
-   見直しで見つけたずれを issue にすること（F-003）。

### 2.3. スコープ外 (Out of Scope)

-   **ADR-0039 の見直し。** 1 章の「要件定義の際に決めたこと」のとおりである。
-   **ADR の決定の変更。** 本タスクの PR は、AC-20 の場合を除いて、どの ADR の決定も変えない。決定を変えずには基準に合わせられない記述が見つかったときは、書き直さずに残す（AC-14）。
-   **ずれの記述の追加と削除。** ずれの記述を足せるのは決定を下すか変える PR だけで、消すのはずれを直す PR である（`docs/dev/conventions/adr.md`「Discrepancy statements」）。
-   **ADR を参照するほかの文書とコードの変更。** タスク文書は、各タスクが決めたことの変わらない記録として残す（`docs/dev/conventions/adr.md:1-8`）。生きた文書とコードが頼る ADR の記述は、ADR の側で残す（F-004）ので、それらを直す必要は生じない。
-   **規約・`CLAUDE.md`・コマンドの定義（`.claude/commands/`）の変更。** 基準と編集上の訂正の規則は、タスク 0070 が規約に入れた。ADR の訂正の記録をコマンドの手順に広げることは [#732](https://github.com/isseis/yt2column/issues/732) で、squash コミットの本文に引き継ぐかは [#747](https://github.com/isseis/yt2column/issues/747) で扱う。
-   **基準に合っているかを確かめるテスト。** 基準は文の意味についての規則で、文書のテストは文の意味を確かめない（`CLAUDE.md`「Testing Strategy」、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。

## 3. 機能要件 (Functional Requirements)

本章の「規約」は `docs/dev/conventions/adr.md` を、「対象の ADR」は ADR-0001〜0038 を指す。「本タスクの PR」は、本タスクの実装の PR（`03_implementation_plan.md` の PR の境界で分ける PR）を指す。「受け持つ ADR」は、本タスクの PR のそれぞれが見直す対象の ADR で、`03_implementation_plan.md` が PR ごとに定める。AC-01〜AC-07 は、本タスクの PR がマージされた後の、その PR が受け持つ ADR が満たすことを定め、その PR のレビューで ADR を読んで確かめる。

### 3.1. 機能一覧

#### F-001: 「背景」の見直し

対象の ADR の「背景」を、規約の「What 背景 holds」（`docs/dev/conventions/adr.md:147-152`）に合わせる。

**Acceptance Criteria**:
- **AC-01**: 対象の ADR の「背景」は、決定が答えている問題と、決定を縛る前提だけを述べる。前の規則の中身、調査の数字、規則の由来は、決定の根拠そのもの（規約の例では、ビルドの時間の上限を決めた、測った遅さの数字。`docs/dev/conventions/adr.md:151-152`）である場合を除いて述べない。ただし、AC-14 と AC-16 で残した記述を除く。
- **AC-02**: 書き直しで「背景」と「決定」から除いた記述は、次のとおりに置かれている。
  -   前の決定は「経緯」にある。もともと「経緯」になかったものは、規約の「History entries」の形と日付の規則（`docs/dev/conventions/adr.md:184-227`）で置かれている。
  -   退けた案は「採らなかった案」にある。もともとそこになかったものは、規約の「Writing an ADR」の「採らなかった案」の形（`docs/dev/conventions/adr.md:131-133`）で置かれている。
  -   「背景」にあった、今効いている規則で「決定」になかったものは、「決定」にある。
  -   前の決定でも、退けた案でも、今効いている規則でもない記述は、ADR から消えている。

#### F-002: 「決定」と題名の見直し

対象の ADR の「決定」を、規約の「What 決定 holds」（`docs/dev/conventions/adr.md:154-166`）と「Links」（`docs/dev/conventions/adr.md:168-174`）に合わせ、合わなくなった題名を書き直す。

**Acceptance Criteria**:
- **AC-03**: 対象の ADR の「決定」は、後の変更が守るべき規則を 1 項目ずつ述べ、各項目は短い理由と、その規則の仕様の場所を、行番号なしで添える。場所は、正本の文書と節の見出し、パッケージかファイル、または、正本の文書がないときにその規則を記録したタスク文書と節の見出し（`docs/dev/conventions/adr.md:168-170`）である。出典に理由がない項目は `理由は記録されていない` と書き、理由を補わない。
- **AC-04**: 対象の ADR の「決定」は、正本の文書が持つ一覧（構文の一覧、例外の一覧など）の写しと、腐りやすい実装の細部（関数の呼び出しの順序、呼び出し箇所の列挙、手順の細部など）を持たない。ただし、AC-14 と AC-16 で残した記述を除く。
- **AC-05**: 対象の ADR の「決定」が述べる決定は、本タスクの前と同じである。見直しの前の「決定」にあった規則は、書き直した「決定」に残るか、AC-04 で除いた細部として正本の文書か出典のタスク文書にある。正本の文書にも出典のタスク文書にもない細部は、除かずに残す（AC-14）。
- **AC-06**: 本タスクの前に対象の ADR にあった、正本の文書へのリンクと、ずれの記述とそれがリンクする issue は、本タスクの後も同じ ADR にある。ずれの記述の意味は変わらない。ただし、古くなったリンクを AC-09 で直したものは、同じ正本の今の場所へのリンクがある。
- **AC-07**: 対象の ADR の題名は、書き直した「決定」にもう書かれていない細部を述べているときに限って、意味を変えずに書き直されている。題名を書き直した ADR は、索引 `docs/dev/adr/README.md` の行の題名が同じ PR で ADR の 1 行目とそろっている。それ以外の題名と索引の行は変わらない。

#### F-003: 変えないものと、見つけたものの扱い

**Acceptance Criteria**:
- **AC-08**: 本タスクの PR は、対象の ADR の「状態」の表を変えない。「採らなかった案」「結果」「経緯」は、AC-02 で置く記述と、AC-09 の訂正と、AC-20 の「経緯」の項目を除いて変えない。
- **AC-09**: 本タスクの PR は、受け持つ ADR の全体で見つけた、古くなったリンク・名前・見出しへの参照と、意味を変えない誤字を、規約の「Editorial corrections」の (3) と (4) として直す。直した結果は、その ADR の「決定」と合う（`docs/dev/conventions/adr.md:283-288`）。
- **AC-10**: 本タスクの PR は、受け持つ ADR と索引 `docs/dev/adr/README.md` と、本タスクのタスク文書（`docs/tasks/0073_adr_context_decision_review/` の下）だけを変える。受け持たない ADR、ADR-0039、規約、`CLAUDE.md`、`.claude/commands/` の下のファイル、ほかのタスクの文書、コードは変えない。
- **AC-11**: 本タスクの PR の後も、`make test` が通る。すべての ADR と索引は規約の構造の検査（`TestADRRecords`）に、ADR の中のリンクは文書のパスの検査（`TestInstructionDocPaths`）に通る。
- **AC-12**: 見直しで、対象の ADR の決定と、正本の文書と、コードのどれかが食い違っているのを見つけたときは、その ADR にずれの記述を足さない（`docs/dev/conventions/adr.md:329-336`）。そのずれを扱う issue がすでにあれば、PR の説明はその issue を挙げる。なければ、本タスクの作業者がその ADR を名指しする issue を立て、PR の説明はその issue を挙げる。
- **AC-13**: AC-12 の issue は、PR を作る前に立てる。PR を作った後のレビューでずれが見つかったときも、AC-12 と同じく issue を立てる。PR の説明は、そのとき見つかったずれを挙げなくてよい。
- **AC-14**: 決定を変えずには基準に合わせられない記述（たとえば、決定の意味を変えないと除けない記述、正本の文書にも出典のタスク文書にもない細部、「経緯」に置くための出典の文書がない前の決定）を見つけたときは、本タスクの PR は、その記述を書き直さずに残し、PR の説明にその記述と理由を挙げる。

#### F-004: ほかの文書とコードが頼る記述

**Acceptance Criteria**:
- **AC-15**: 本タスクの後も、対象の ADR の外の文書とコード（ほかの ADR、生きた文書、コード、コメント、テスト、スクリプト）が、ある対象の ADR に定めがあるとして参照する規則は、その ADR の「決定」にある。それらが見出しで参照する節は、同じ見出しで同じ ADR にある。タスク文書からの参照は、この条件に含めない（2.3）。
- **AC-16**: AC-15 を守ると基準に合わせられない記述（たとえば、ほかの ADR が頼る規則が腐りやすい実装の細部に当たるもの）は、書き直さずに残し、PR の説明に、その記述と、頼っている文書かコードを挙げる。

#### F-005: PR の分け方

**Acceptance Criteria**:
- **AC-17**: 本タスクの PR の 1 つが受け持つ ADR は 8 本以下である。後の PR が、前の PR の受け持った ADR を AC-19 で見直すときは、その ADR は後の PR の受け持ちにも数える。
- **AC-18**: 本タスクの PR を合わせると、ADR-0001〜0038 のすべてを受け持つ。見直して変える箇所がなかった ADR は、その ADR を受け持つ PR の説明が、変える箇所がなかったことを述べる。

#### F-006: 記録

**Acceptance Criteria**:
- **AC-19**: 本タスクの PR は、PR を作った後に、受け持つ ADR に新しい編集上の訂正を加えない（`docs/dev/conventions/adr.md:308-315`）。PR を作った後のレビューで足りない書き直しが見つかったときは、その ADR を本タスクの後の PR で受け持って見直すか、本タスクの最後の PR の後なら issue にする。その PR 自身が加え、まだ `main` にない記述を直すことは、この制限を受けない。
- **AC-20**: PR のレビュアーが、ある変更を編集上の訂正とする分類に異を唱えたときは、その変更を決定の変更として扱う（`docs/dev/conventions/adr.md:316-327`）。その ADR の「経緯」に項目を足し、決定とその ADR の判断を本タスクのタスク文書に記録する。どのタスク文書にどの手順で記録するかは、設計で決める（[design_handoff.md](design_handoff.md) H-07）。
- **AC-21**: 本タスクの PR が対象の ADR と索引に加える変更は、規約の「Editorial corrections」の「Recording」（`docs/dev/conventions/adr.md:298-306`）のとおり、その変更を行うコミットのメッセージに訂正の行として、PR の説明に訂正の段落として記録される。訂正の行は、ADR のリポジトリからのパス、何を何に変えたか（消した記述と移した記述を含む）、決定を変えないことを述べる。PR の説明は、それらの変更を編集上の訂正と明示する。AC-20 の変更は、この記録ではなく AC-20 の記録による。
- **AC-22**: 本タスクの PR は、対象の ADR の「経緯」に、編集上の訂正そのものの項目を足さない。AC-02 で「経緯」に置く前の決定の項目は、新しい出来事の項目ではなく、規約の「History entries」の「No entry for an editorial correction」（`docs/dev/conventions/adr.md:195-202`）のとおり日付の順の位置に置く。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)
-   N/A（文書だけの変更である）。

### 4.2. セキュリティ (Security)
-   N/A。外部コマンドの呼び出し、秘密、キャッシュ、ネットワークへの送信、信頼できない文字列の埋め込みのどれにも触れないので、`docs/dev/security.md` を適用する条件に当たらない（`.claude/commands/_context.md`「Conditional-guide trigger」）。脅威モデルの ADR-0006 と、秘密の扱いの ADR-0031 も、書き方だけを直し、決定と `docs/dev/security.md` を変えない（AC-05・AC-10）。

### 4.3. 信頼性・可用性 (Reliability/Availability)
-   N/A。

### 4.4. 互換性 (Compatibility)
-   ADR のファイル名と番号は変えない。ほかの文書から ADR へのリンクは、本タスクの後も同じ ADR を指す（AC-10）。ほかの文書とコードが頼る規則と見出しは残る（AC-15）。

### 4.5. 保守性 (Maintainability)
-   見直した「決定」は、腐りやすい実装の細部を持たない（AC-04）。後の PR が実装を変えても、決定が同じなら、ADR を変える必要が生じにくい。各項目が添える正本の場所（節の見出し、パッケージ、ファイル）は、それらが変わると古くなるので、規約の (3) の訂正で直す。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   ADR と索引は日本語で書く（`CLAUDE.md`「Document language」の原則 (a)）。
-   基準に合っているかと、決定が変わらないかは文の意味の問題なので、PR のレビューで読んで確かめる（`CLAUDE.md`「Testing Strategy」、[ADR-0016](../../dev/adr/0016-document-test-policy.md)）。AC-08・AC-10 のような前後の関係は、本タスクの `_checks/` の下の差分の確認で確かめられる（`docs/dev/conventions/requirements_process.md` §4）。
-   コマンドの記録の手順は、PR を作った後の ADR の訂正を運ばない（[#732](https://github.com/isseis/yt2column/issues/732)、[ADR-0039](../../dev/adr/0039-adr-writing-criteria.md) の「結果」）。AC-19 は、この制約から来る。
-   squash マージの後、訂正の記録は PR の説明にだけ残る（[#747](https://github.com/isseis/yt2column/issues/747)）。1 章の「要件定義の際に決めたこと」のとおり、これを受け入れる。

## 6. 用語集 (Glossary)

用語は `docs/translation_glossary.md` と統一する。

-   **正本の文書:** ある主題の今の仕様を持つ文書（`CLAUDE.md`「Design decisions (ADR)」の "a document that holds the current specification"）。
-   **ずれの記述:** ADR の「決定」にある、決定・正本の文書・コードの食い違いを述べ、それを扱う issue へリンクする記述（規約の「discrepancy statement」）。
-   **編集上の訂正:** 決定を変えずに ADR を直す変更（規約の「editorial correction」）。規約の 4 種類に限る。
-   **基準に合わせる書き直し:** 編集上の訂正の 1 つ目の種類。規約の「Writing an ADR」の基準に合わせる直しで、ADR かその出典の文書にすでにある内容を別の節へ移すことを含み、新しい事実を足さない。
-   **前の決定:** 今は効いていない、過去に下した決定（規約の "an earlier decision"）。「経緯」に置く。
-   **前の規則の中身:** 前の決定が定めていた規則の内容（規約の "the content of an earlier rule"）。決定の根拠そのものでない限り「背景」に書かない。
-   **退けた案:** 採らなかった形（規約の "a rejected form"）。「採らなかった案」に置く。
-   **腐りやすい実装の細部:** コードの変更で、決定が変わらなくても古くなる記述。関数の呼び出しの順序、呼び出し箇所の列挙、手順の細部などである。
-   **受け持つ ADR:** 本タスクの PR のそれぞれが見直す対象の ADR（3 章の冒頭）。
-   **見直す:** ADR を読み、基準に合わない記述を書き直すこと。書き直す箇所がないと判断することも含む。
