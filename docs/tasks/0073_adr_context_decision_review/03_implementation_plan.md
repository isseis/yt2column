## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

[01_requirements.md](01_requirements.md)（以下、要件書）と [02_architecture.md](02_architecture.md)（以下、設計書）に従い、ADR-0001〜0038 の「背景」と「決定」を、規約 `docs/dev/conventions/adr.md` の「Writing an ADR」の基準に合わせて、編集上の訂正として見直す。本書の用語（系列・追加の PR・最後の PR・PR の基点・名指し・頼る参照・見直しの記録・対応表・持ち越し・差分の確認・確かめのデータ）は、設計書の冒頭の定義と同じ意味で使う。既存のファイルの内容は、コミット `3709c2d6` で確かめた（以下、本書を確かめたコミット）。`file:line` は、このコミットでの行番号である。

### 1.2. 実装の原則

-   系列ごとに 1 つのフェーズと 1 本の PR にする（設計書 3.1）。各フェーズは、2.0 の共通の手順を、その系列の ADR に当てはめる。
-   差分の確認は、フェーズ 1 で足し、すべての PR で使う（設計書 8 章）。名指しの洗い出しとマージの前の鮮度の確認も、差分の確認のサブコマンドにする（1.3）。
-   ADR の見直しは、PR を作る前に、ADR 1 本につき 1 つのコミットにして、訂正の行を付ける（設計書 3.7.1）。
-   本書には、コマンドの文字列や表の行の中身を書かない。それらは、差分の確認のプログラムと見直しの記録が持つ。

## 2. 実装手順 (Implementation Steps)

### 2.0. 系列の見直しの共通の手順

各フェーズの「系列の見直し」のステップは、次の手順 1〜8 をその系列の ADR（持ち越しの ADR を含む）に当てはめる。ブランチは、前の PR のマージの後に `/runpr` が作る（設計書 3.1.1）。手順 9 と 10 は PR を作った後の手順で、ステップのチェックボックスではなく、2.1 と 7.2 の確認の項目で扱う。

1.  `mentions <系列>` を PR の基点で実行し、名指しとずれの記述を挙げる。名指しを読み、頼る参照を選ぶ（設計書 3.3）。前の系列の ADR が自分の ADR を名指ししていれば、それも読む（設計書 3.1.2）。
2.  ADR を 1 本ずつ、設計書 3.2〜3.5 と図 5 のとおり見直し、1 つのコミットにする。訂正の行を付ける（設計書 3.7.1）。題名を書き直したときは、索引の行を同じコミットでそろえ、索引の訂正の行も付ける。変える箇所がなかった ADR には、コミットを作らない。
3.  見つけたずれを、ユーザーの承認を得て issue にする（設計書 3.6）。承認が得られなければ、PR を作らずに止まる。
4.  見直しの記録 `review_<系列>.md` を書き、コミットする（設計書 3.7.2）。
5.  確かめのデータに、その系列の許す変更と持ち越しを書き足し、コミットする（設計書 3.9.3）。
6.  `check <系列>` と `make test` を実行する。違反は設計書 3.9.4 のとおり直す。ADR の直しは、その ADR のコミットに、確かめのデータの直しは手順 5 のコミットに畳み込む。畳み込み（履歴の書き換え）は PR を作る前だけ行う。
7.  `check` の出力と、比べた 2 つのコミット（マージベースと先頭）の ID を 7.2 に記録する。記録の後に、ADR か確かめのデータを変えるコミットや `main` を取り込むコミットを加えたとき（PR を作った後の `/fixpr` の回を含む）は、`check` を実行し直して記録を改める（設計書 3.9.4）。
8.  PR の説明に、設計書 3.7.3 のもの（訂正の段落、見直しの記録へのリンク、残した記述の要約、ずれの issue、変えなかった ADR、`check` の結果と許した変更の一覧）を書く。
9.  （PR を作った後）レビューで足りない書き直しが見つかれば 1.5 に書き足し、2.1 の戻し方でその ADR を取り下げるか、まだ変えていない ADR ならそのまま持ち越す（設計書 3.1.3）。分類に異論が出れば設計書 3.8 のとおり扱う。
10. （マージの前）2.1 のマージの前の確認を行う。

`/fixpr` が、ADR を対象にしたスレッドに答えるために本書の 1.5 や確かめのデータを変えると、`fixprguard` はその変更を範囲の外と判断し、ユーザーの承認を求める（終了コード 3）。これは想定どおりの動作で、ユーザーが認めてから進める。

### 2.1. PR を作った後の手順（各 PR 共通）

**ADR の取り下げ（設計書 3.8 の「前の記述に戻すとき」と 3.10 の手順 4）:** 次をまとめて 1 回の push で行う。

-   その ADR と、題名を書き直していれば索引の行を、マージベースの版に戻す 1 つのコミットを作る。
-   確かめのデータから、その ADR の許す変更（`link_changes`・`line_changes`・`retitled_adrs`）を消し、戻したコミットを `unrecorded_commits` に挙げる。
-   見直しの記録のその ADR の表に、取り下げたことと理由を書く。
-   本書の 1.5 にその ADR を書き足す。持ち越し先の系列の `carried_in` には、持ち越し先の PR が書き足す。
-   `check` と `make test` を実行し直し、7.2 の記録を改める。スレッドへの返信か PR へのコメントで、その ADR の訂正の行を取り下げたと述べる。

**マージの前の確認（設計書 3.10）:** `/runpr` が最初にマージの質問をしたら、レビュアーは自由記述で「マージしない。マージの前の確認を行う」と答える。`/runpr` はマージせずに止まる。その後、同じセッションで次を行う。

1.  ユーザーの承認を得て `origin/main` を取得し、`freshness <系列>` を実行する。
2.  `freshness` が 0 で終わり、表示された変わったファイルが見直しの記録の「根拠」の列の文書を含まず、名指しの違いもなければ、その結果を PR へのコメントに残してから、`/runpr` をやり直し、マージの質問に答える。
3.  受け持つ ADR か索引が変わっていれば（`freshness` が 1）、PR をマージせずに `main` を取り込み、変わった ADR を上の「ADR の取り下げ」のとおり取り下げる。「根拠」の文書か名指しが変わっていれば、影響する対応表の行を読み直し、見直しで除いた細部が根拠の文書にもうないときや、新しい頼る参照が頼っている規則を見直しで除いていたときは、同じく取り下げる。CI を待ってから、`/runpr` をやり直す。
4.  （PR-5 だけ）手順 3 の取り下げを済ませた後、1.5 に追加の PR への持ち越しがなければ、ステップ 6-1 と PR-6 のチェックボックスをすべて `[-]`（当てはまらない）にして、本書をコミットする。あわせて、7 章のすべての AC に検証の記録があることを確かめる（PR-6 があるときは、PR-6 のマージの前に確かめる）。`/runpr` をやり直すと、PR-5 を最後の PR として扱う。マージの質問で、次のコマンドの案内がなく、issue #729 を閉じる案内が出ることを確かめる。

PR へのコメントは、投稿の前に Codex を呼ぶ言及を含まないことを確かめる（`.claude/commands/_context.md`「PR review request」）。
