## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

[01_requirements.md](01_requirements.md)（以下、要件書）と [02_architecture.md](02_architecture.md)（以下、設計書）に従い、ADR-0001〜0038 の「背景」と「決定」を、規約 `docs/dev/conventions/adr.md` の「Writing an ADR」の基準に合わせて、編集上の訂正として見直す。本書の用語（系列・追加の PR・最後の PR・PR の基点・名指し・頼る参照・見直しの記録・対応表・持ち越し・差分の確認・確かめのデータ）は、設計書の冒頭の定義と同じ意味で使う。既存のファイルの内容は、コミット `3709c2d6` で確かめた（以下、本書を確かめたコミット）。`file:line` は、このコミットでの行番号である。

### 1.2. 実装の原則

-   系列ごとに 1 つのフェーズと 1 本の PR にする（設計書 3.1）。各フェーズは、2.0 の共通の手順を、その系列の ADR に当てはめる。
-   差分の確認は、フェーズ 1 で足し、すべての PR で使う（設計書 8 章）。名指しの洗い出しとマージの前の鮮度の確認も、差分の確認のサブコマンドにする（1.3）。
-   ADR の見直しは、PR を作る前の 1 本の ADR の変更を 1 つのコミットにし、訂正の行を付ける（設計書 3.7.1）。
-   本書には、コマンドの文字列や表の行の中身を書かない。それらは、差分の確認のプログラムと見直しの記録が持つ。

### 1.3. 計画の際に決めたこと（2026-11-09）

-   **名指しの洗い出しとマージの前の鮮度の確認は、差分の確認のサブコマンドにする:** 設計書が実装計画書に回した `git grep` の形（設計書 3.3）と、鮮度の確認の手順 2〜3（設計書 3.10）を、差分の確認のプログラムの `mentions` と `freshness` のサブコマンドとして実装する。本書はコマンドの形を書かず、そのサブコマンドを指す。
    -   **理由:** 38 本の ADR と 5 回以上の鮮度の確認で、同じ検索を手で打ち直すと、打ち間違いが見つからないまま残る。実行される物に置けば、フェーズ 1 で壊して確かめられる。
    -   **採らなかった案:** 本書に `git grep` の形を書き、本書を書くときに実行して出力を記録する案は、実装の各 PR が手で打ち直すことになるので採らない。
    -   ADR：なし。本タスクの道具の置き場所の決定で、本タスクの中で閉じる。

## 2. 実装手順 (Implementation Steps)

### 2.0. 系列の見直しの共通の手順

フェーズ 2〜6 の「系列の見直し」のステップは、次の手順をその系列の ADR に当てはめる。フェーズ 1 のステップ 1-3 も同じ手順を使う。

1.  前の PR のマージの後、PR の基点でブランチを作る（設計書 3.1.1）。
2.  `mentions <系列>` を PR の基点で実行し、名指しとずれの記述を挙げる。名指しを読み、頼る参照を選ぶ（設計書 3.3）。前の系列の ADR が自分の ADR を名指ししていれば、それも読む（設計書 3.1.2）。
3.  ADR を 1 本ずつ、設計書 3.2〜3.5 と図 5 のとおり見直し、1 つのコミットにする。訂正の行を付ける（設計書 3.7.1）。題名を書き直したときは、索引の行を同じコミットでそろえる。変える箇所がなかった ADR には、コミットを作らない。
4.  見つけたずれを、ユーザーの承認を得て issue にする（設計書 3.6）。承認が得られなければ、PR を作らずに止まる。
5.  見直しの記録 `review_<系列>.md` を書き、コミットする（設計書 3.7.2）。
6.  確かめのデータに、その系列の許す変更と持ち越しを書き足す（設計書 3.9.3）。
7.  `check <系列>` と `make test` を実行する。違反は設計書 3.9.4 のとおり直し、直しは該当する ADR のコミットに畳み込む。出力と 2 つのコミットの ID を 7.2 に記録する。
8.  PR の説明に、設計書 3.7.3 のものを書く。
9.  PR を作った後、レビューで足りない書き直しが見つかれば 1.5 に書き足し（設計書 3.1.3）、分類に異論が出れば設計書 3.8 のとおり扱う。
10. マージの前に `freshness <系列>` を実行し、設計書 3.10 のとおり扱う。
