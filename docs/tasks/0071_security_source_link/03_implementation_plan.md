## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

`docs/dev/security.md` §6 の出典リンクの項目を、どの記事の出力にも当てはまる規則の形に改める（F-001）。同じ PR で、ADR-0034 のずれの記述を消す（F-002）。PR は 0070 の実装の PR のマージの後に作り、その後にマージする（F-003）。前後の関係を述べる AC は、`_checks/` の 1 回限りの確認のプログラムで確かめる。

### 1.2. 実装の原則

-   **変える箇所は設計書 2.2 の表のとおりにする。** Go と拡張のコード、ADR の索引は変えない。
-   **項目の文面は実装で決める。** 本計画は、項目が述べる内容を設計書 3.1 の表と箇条に委ね、文面を書かない。
-   **新しい恒久的なテストは足さない**（設計書 1.2・7.1）。
-   **0070 の実装の PR のマージを確かめるまでは、何も書かない**（設計書 1.2・8 章）。

### 1.3. 計画の際に決めたこと（2026-11-09）

次の 2 点は、計画を書く前に利用者に尋ねて決めた。

-   **確認のプログラムは Go で書く。** タスク 0069 の `_checks/main.go` と `_checks/data.json` の形にならう。先頭に `//go:build test` を置き、`go build -tags test -o <scratchpad の中のパス> ./docs/tasks/0071_security_source_link/_checks/` でビルドして実行する。理由は次のとおりである。
    -   macOS の BSD 版と GNU 版のツールの違いに左右されない。
    -   `go run` と違い、ビルドした実行ファイルなら終了コードで違反（1）と読み取りの失敗（2）を区別できる。
    -   0069 のプログラムの、git でファイルを読む関数、変えたファイルを集める関数、祖先を確かめる関数を写して使える。

    日本語の文字列（§6 の見出し、項目の前後の箇条の書き出し、ADR-0034 の `## 決定` の見出しと項目の太字の 1 文目）は `data.json` に置く。`_checks/` には guard-test literal exception（`CLAUDE.md`「Go Idioms」）が及ばないからである。ADR の判断：ADR は作らない。本タスクの中で閉じる道具の選択である。
-   **確認のプログラムを壊して確かめるのは、確認の項目ごとに 1 件とする。** 確認の項目（AC-04〜AC-09 と、変えたファイルの範囲）をそれぞれ 1 件ずつ壊し、読み取りの失敗も 1 件確かめる。0069 は失敗の経路ごとに複数の壊し方を試したが、本タスクでは、各項目が狙った理由で失敗できることを示せれば足りる（`CLAUDE.md`「Testing Strategy」）。ADR の判断：ADR は作らない。本タスクの中で閉じる検証の範囲の決定である。

次の点は、設計書と既存の仕組みから導いた。PR のレビューで異論があれば改める。どれも本タスクの中で閉じるので、ADR は作らない。

-   **フェーズは 1 つにし、PR の作成ポイントは置かない。** 設計書 8 章は PR を 1 本と決めている。フェーズが 1 つの計画では、`/runplan` がフェーズの完了の後に PR を作る（`.claude/commands/runplan.md:231`）。
-   **0070 の実装の PR は、0070 の実装計画書の §6 にある単独の PR の記録で特定する。** 0070 の実装計画書はフェーズが 1 つで、PR の作成ポイントがない（`docs/tasks/0070_adr_writing_criteria/03_implementation_plan.md:37`）。そのため、設計書 6.2 の 1 が述べる「`adr.md` を変える PR の境目の `PR を作成した` の行」は、`/runplan` が同書の §6 に足す `- [x] PR を作成した: <URL>` の 1 行である（`.claude/commands/runplan.md:231` の AFTER_CREATE）。その行がない、または 2 行以上あるときは、設計書 6.2 の 1 のとおり止まる。
-   **AC-08 の比較の起点は、`PR を作成した` の行を足したコミットの親とする。** 設計書 7.2 の AC-08 の行は、PR を作った時点の先頭のコミットを使う。`/runplan` は PR を作った直後に、計画書だけを変える記録のコミットを足すので、その親が PR を作った時点の先頭である。確認のプログラムは、このコミットを省略できる引数（例：`-created <commit>`）で受け取る。引数がないときは AC-08 の項目を「実行しない」と表示し、合格とは表示しない。PR を作った後に `data.json` を変えないためである。
-   **0070 の実装の PR のマージのコミットの ID は、`data.json` に書く。** ステップ 1-1 で確かめた ID を、確認のプログラムを足すコミット（ステップ 1-4）で書く。タスク 0069 の `merge_commit` と同じ扱いである。
