## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

`docs/dev/security.md` §6 の出典リンクの項目を、どの記事の出力にも当てはまる規則の形に改める（F-001）。同じ PR で、ADR-0034 のずれの記述を消す（F-002）。PR は 0070 の実装の PR のマージの後に作り、その後にマージする（F-003）。前後の関係を述べる AC は、`_checks/` の 1 回限りの確認のプログラムで確かめる。

### 1.2. 実装の原則

-   **変える箇所は設計書 2.2 の表のとおりにする。** Go と拡張のコード、ADR の索引は変えない。
-   **項目の文面は実装で決める。** 本計画は、項目が述べる内容を設計書 3.1 の表と箇条に委ね、文面を書かない。
-   **新しい恒久的なテストは足さない**（設計書 1.2・7.1）。
-   **0070 の実装の PR のマージを確かめるまでは、何も書かない**（設計書 1.2・8 章）。

### 1.3. 計画の際に決めたこと（2026-11-09）

次の 2 点は、計画を書く前に利用者に尋ねて決めた。

-   **確認のプログラムは Go で書く。** タスク 0069 の `_checks/main.go` と `_checks/data.json` の形にならう。先頭に `//go:build test` を置き、`go build -tags test -o <scratchpad の中のパス> ./docs/tasks/0071_security_source_link/_checks/` でビルドして実行する。理由は次のとおりである。
    -   macOS の BSD 版と GNU 版のツールの違いに左右されない。
    -   `go run` と違い、ビルドした実行ファイルなら終了コードで違反（1）と読み取りの失敗（2）を区別できる。
    -   写して使える 0069 のプログラムの関数は、git の読み取り（`read`・`git`・`gitLines`・`changedFiles`・`isAncestor`）、目印による範囲の決定（`uniqueLine`・`paragraphRange`・`maskParagraph`・`maskLine`）、ADR の「決定」の項目の切り出し（`adrSectionItem`）、訂正の行の確認（`checkCorrections`・`isCorrectionLine`）、マージのコミットの確認（`checkMergeCommit`）である。節の切り出しには `internal/doctestutil` の `SectionOutsideBlocks`（`internal/doctestutil/markdown.go:44`）を使う。

    日本語の文字列（`security.md` §6 の見出し、項目の前後の箇条の書き出し、ADR-0034 の `## 決定` の見出しと項目の太字の 1 文目）は `data.json` に置く。`_checks/` には guard-test literal exception（`CLAUDE.md`「Go Idioms」）が及ばないからである。ADR の判断：ADR は作らない。本タスクの中で閉じる道具の選択である。
-   **`data.json` は、比べるコミットからではなく作業ツリーから読む。** 設計書 7.2 は「結果は引数のコミットだけで決まる」と述べるが、文書はすべて引数のコミットから読み、`data.json` だけを例外とする。ステップ 1-5 で壊し方ごとに作る一時的なコミットに `data.json` を含めないまま、確認のプログラムを走らせるためで、0069 と同じ扱いである（`docs/tasks/0069_readme_display_language/03_implementation_plan.md:39`）。設計書 7.2 の補足であり、設計の変更ではない。
-   **確認のプログラムを壊して確かめるのは、確認の項目ごとに 1 件とする。** 確認の項目（AC-04〜AC-09 と、変えたファイルの範囲）をそれぞれ 1 件ずつ壊し、読み取りの失敗も 1 件確かめる。0069 は失敗の経路ごとに複数の壊し方を試したが、本タスクでは、各項目が狙った理由で失敗できることを示せれば足りる（`CLAUDE.md`「Testing Strategy」）。ADR の判断：ADR は作らない。本タスクの中で閉じる検証の範囲の決定である。

次の点は、設計書と既存の仕組みから導いた。PR のレビューで異論があれば改める。どれも本タスクの中で閉じるので、ADR は作らない。

-   **フェーズは 1 つにし、PR の作成ポイントは置かない。** 設計書 8 章は PR を 1 本と決めている。フェーズが 1 つの計画では、`/runplan` がフェーズの完了の後に PR を作る（`.claude/commands/runplan.md:231`）。
-   **0070 の実装の PR は、0070 の実装計画書の §6 にある単独の PR の記録で特定する。** 0070 の実装計画書はフェーズが 1 つで、PR の作成ポイントがない（`docs/tasks/0070_adr_writing_criteria/03_implementation_plan.md:37`）。そのため、設計書 6.2 の 1 が述べる「`adr.md` を変える PR の境目の `PR を作成した` の行」は、`/runplan` が同書の §6 に足す単独の PR の記録の行である（`.claude/commands/runplan.md:231` の AFTER_CREATE）。数えるのは、行の全体が `- [x] PR を作成した: https://github.com/isseis/yt2column/pull/<番号>` の形の行だけで、本文の中でこの語句に触れる文は数えない。その行がない、または 2 行以上あるときは、設計書 6.2 の 1 のとおり止まる。
-   **AC-08 の比較の起点は、本計画の §6 に単独の PR の記録の行を足したコミットの親とし、マージの前に求めて記録する。** 設計書 6.1 の 7 は、PR を作った時点の先頭のコミット ID を PR を作るときに記録するとしている。しかし、`/runplan` は PR を作った直後に、本計画の §6 に記録の行を足すコミットを作る（`_lib/task-pr-handoff.md` Part B 手順 3 の後の手順 4）。このコミットの親が PR を作った時点の先頭なので、本計画ではこの親を後から求め、マージの前の実行のときに本計画 §7 に記録する。設計書 6.1 の 7 の記録の時期を変えるが、記録する値と目的は変わらない。求め方は、本計画のファイルの履歴のうち、`- [x] PR を作成した: https://` で始まる行を足したコミットがちょうど 1 つであることを確かめ、その最初の親を取る（例：`git log --format=%H -G '^- \[x\] PR を作成した: https://' -- <本計画のパス>`）。PR を作った後のブランチは、rebase も force push もしないことを前提とする。確認のプログラムは、このコミットを省略できる引数（例：`-created <commit>`）で受け取る。引数がないときは AC-08 の項目を「実行しない」と表示する。この表示は合格ではなく、本計画 §6 の最後の項目を満たさない。
-   **AC-08 の「差分が等しい」は、ADR のファイルごとに、消した行と足した行の内容が等しいことと定める。** 比べるのは、それぞれのマージベースからの差分の、ファイルごとの消した行と足した行の内容の並びで、前後の文脈の行と hunk の見出しは比べない。`main` を取り込んでマージベースが動き、ADR のほかの行が変わっても、PR 自身の変更が同じなら合格になる。
-   **0070 の実装の PR のマージのコミットの ID は、`data.json` に書く。** ステップ 1-1 で本計画 §6 に記録した ID を、確認のプログラムを足すコミット（ステップ 1-4）で `data.json` に写す。設計書 7.2 の AC-09 の行の「実装計画書に記録した ID」はこの値である。2 か所の値が等しいことは、ステップ 1-6 で確かめる。タスク 0069 の `merge_commit` と同じ扱いである。
