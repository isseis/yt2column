## 1. 実装の概要 (Implementation Overview)

### 1.1. 目的

用語集で stage の訳語を「ステージ」と定め、ステージ・構成要素・工程の使い分けを書く（F-001）。対象の文書の「段階」を、出現箇所が指すものに従って置き換える（F-002）。`CLAUDE.md` の英語の 3 か所を stage・component・step の使い分けに揃える（F-003）。変えないもの（F-004）は、一回の確認で確かめる。

### 1.2. 実装の原則

-   **割り当ては要件書の付録 A に従う。** 付録 A・付録 B にない出現箇所（実装時点の `main` で増えたもの）だけを、設計書 6.1 の判定で割り当てる。付録 A と 6.1 の判定が食い違ったら付録 A に従い、食い違いを PR の説明に挙げる（設計書 1.2）。
-   **文の組み立ては設計書 3.6 の規則で直す。** 意味は変えない。
-   **互いに読み合う変更は同じコミットにする。** 列名とテストの locator（フェーズ 2）、ADR の題名と索引（フェーズ 3）である（設計書 8 章）。
-   **恒久的なテストは足さない。** 範囲と「変えないもの」は一回の確認で確かめ、文の中身は PR のレビューで読む（設計書 1.1・7.3・7.4）。

### 1.3. 計画の際に決めたこと（2026-11-08）

人間のレビュアーが決めたもの:

-   **一回の確認は Go のプログラムにする。** 置き場所は `docs/tasks/0067_stage_terminology/_checks/main.go` とする。`go build -tags test -o <scratchpad の中のパス> ./docs/tasks/0067_stage_terminology/_checks/` でビルドし、できた実行ファイルを `[<base> <head>]` の引数で直接走らせる。`go run` は、プログラムの終了コードが 0 でないとき、その値によらず 1 で終わるので（2026-11-08 に go1.27.1 で、`os.Exit(2)` するプログラムを `go run` で走らせ、終了コードが 1 になることを確かめた）、終了コードの 1 と 2 を区別できないためである。設計書 7.3 が実装計画に委ねた選択である。理由: 判定の数が多いため（ファイルごとの回数、改行をまたぐ「段階」、改行を空白と同じに扱う照合、見出しから末尾までの比較）。終了コードを 0・1・2 に分けることも求められる。シェルでは、これらを `grep`・`awk` の組み合わせで書くことになり、誤りやすい。先例はタスク 0040・0048・0064 の `_checks` である。`-tags test` を付けるのは、`internal/doctestutil`（`//go:build test`）の表と節の読み取りを再利用するためで、先例はタスク 0048 の `_checks/split/main.go:8` である。ADR の判断: ADR は作らない。このタスクの一回の確認の書き方で、タスクの中で閉じる。以下、このプログラムを「一回の確認のプログラム」と呼ぶ。設計書 7.3 の「スクリプト」に当たる。
-   **AC-16 の「Go のコード」は、製品のコードとテストのコードと読み、このタスクのディレクトリの `_checks/` の下の Go のファイルを含めない。** 一回の確認を Go にすると、`_checks/main.go` が差分の `.go` のファイルに入り、AC-16 と、それを確かめる設計書 7.3 の「禁止のファイル」の行の両方に、字面のうえでは違反する形になる。設計書 7.3 は、言語を決める前にこの行を書いた。`_checks/` は `go list ./...` に入らず（`requirements_process.md` §4）、製品にもテストにも組み込まれない。また、AC-14 はこのタスクのディレクトリを変えてよいとしている。そこで、一回の確認のプログラムは、差分の `.go` のファイルから `docs/tasks/0067_stage_terminology/` の下のものを除き、残りが `cmd/yt2column/docs_test.go` だけであることを確かめる。要件書を `draft` に戻して AC-16 を直す案は、承認のやり直しの手間に見合わないので採らない（設計書 1.2 の AC-06 の読み方と同じ扱い）。この読み方は PR の説明にも挙げる（ステップ 6-5）。ADR の判断: ADR は作らない。このタスクの範囲の読み方で、タスクの中で閉じる。

計画で決めたもの（人間のレビュアーに諮らず、理由とともに記す）:

-   **PR は 1 本にし、フェーズは設計書 8 章の 6 項目に合わせる。** PR を 1 本にするのは、設計書 1.2 の決定である。フェーズごとにコミットを分けると、PR のレビューで差分を追いやすい。
-   **一回の確認のプログラムで確かめる AC の種類は `diff` とする。** AC-09・AC-13・AC-14・AC-16 は、基点と head を比べる。AC-01 の行の位置も、基点の行と比べる。AC-04・AC-06・AC-15 と AC-10 の列名は head だけを読む。これらの AC はどれも、この変更が何を置き換え、何を残したかを述べているため、恒久的なテストにすると、古い語がないことを確かめるテストになる（`CLAUDE.md` の「Document tests …」は、古い名前がないことを確かめるテストと、退いた仕様を文書が持ち続けることを確かめるテストを禁じている）。そのため、設計書 7.3 のとおり同じプログラムに置き、PR のブランチで一度だけ走らせる。
-   **一回の確認のプログラムが使う日本語の文字列は、プログラムの横のデータのファイルに置く。** 許可の一覧の文言（「観点と段階の基準」など、locator ではない文の断片）、探す語「段階」、旧称の記述、列名、見出し「## 経緯」、`CLAUDE.md` の 3 か所の「今の文言」と「変えた後」の文言など、日本語の文字列はすべてデータのファイルに置く。Go のソースの文字列は英語に保つ。guard-test literal exception（`CLAUDE.md` の「Go Idioms」）は `_test.go` の guard test と `internal/doctestutil` だけに及び、`_checks/` には及ばないためである。先例はタスク 0048 の `_checks/split/splits.json`・`destinations.txt` である。
-   **設計書 7.3 の表の「確かめること」の欄に、次の 3 つを加える。** どれも同じプログラムの中で、設計書 7.3 の確かめ方を補うものであり、設計書の決定は変えない。
    -   `CLAUDE.md` の 3 つの「変えた後」の文言が head にちょうど 1 回ずつあること（AC-11・AC-12・AC-13）。7.3 の照合（「変えた後」を「今の文言」に戻すと基点に一致する）だけでは、`CLAUDE.md` を変えなかったときにも成功してしまう。
    -   `production_profile.md` のパイプラインの節の表の 1 列目の名前が「処理」であること（AC-10）。AC-10 は文の中身（`manual`）と列名（値）が混ざった AC で、列名には `manual` 以外の確かめ方が要る（mkplan の規則）。本番の構成の表の列名「工程」（AC-08）は `checkProfileTable` が確かめる。
    -   用語集の「ステージ」の行が、基点の「段階」の行と表の中の同じ位置にあり、英語の列が `stage`、備考に「旧称: 段階」を含むこと（AC-01。設計書 3.1 の「項の位置は変えない」）。
