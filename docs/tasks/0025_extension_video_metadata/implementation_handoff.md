# 実装への申し送り：ブラウザ拡張による動画タイトル・チャンネル名・概要欄の取得と送信

本書は、レビューで挙がった懸念のうち、実装の段階で扱うものを集める。`03_implementation_plan.md` が、各項目について、採った方針または当てはまらない理由を記録する。`02_architecture.md` の記述を設計のレベルに保つため、レビューで実装の詳細に踏み込んだ指摘はここに置く。設計レベルの懸念は [design_handoff.md](design_handoff.md) に置く。

## I-01. 読み取りの結果（JSON）の大きさの上限をどこで適用するか

-   **懸念:** `MetadataReader` の結果（JSON の文字列）は `parsePageMetadata` で受信・解析されるが、本文の大きさの上限（要件書 F-002・AC-08、0020 §3.4）はその後の本文の生成時に適用される。`02_architecture.md` 3.6 は概要欄が数 MiB になりうるとするので、大きな JSON が受信・解析された後に拒否される経路が残る、という指摘である。レビューは、読み取りの結果に有限の上限を定義し、超過時は値を返さず `read-failure` として起動を続行することを求めた。
-   **なぜ重要か:** 読み取りの境界に独自の有限の上限を設けるか、本文の生成時の 1 つの検査に委ねるかを、実装の段階で決めておかないと、大きな値の扱いが実装ごとにばらつく。要件書 §2.3 は「値の大きさの独自の上限」をスコープ外とし、§3.2 は値の大きさを「本文の上限（0020 F-004 の 4 MiB）に含む」として、独立した大きさの上限を設けないことを既に決めている。この決定を実装が破らないようにする。
-   **方針の候補:** 読み取りの境界に独立した大きさの上限を設けない（要件書 §2.3・§3.2 の決定どおり）。値の大きさは 0020 の本文の大きさ（4 MiB）に含め、本文が上限を超える場合は既存の `body-too-large` の扱い（AC-08 の「送る内容が大きすぎる」）に委ねる。上限の判定はこの 1 か所だけに置く。`03_implementation_plan.md` は、読み取りの境界に上限を設けないこと、値の大きさが本文の上限に含まれること、その検証（大きな値でも起動が成功し、本文が上限を超える場合に既存の表示になること）を記録する。
-   **関連:** F-002、F-004、AC-08、要件書 §2.3・§3.2、`02_architecture.md` 3.6・5.2
