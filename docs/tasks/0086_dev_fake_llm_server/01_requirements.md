## 1. 概要 (Overview)

**目的:** 本書は、実際の LLM を呼ばずに拡張とサーバを手で確かめるための要件を定義する。決まった記事を返し、シナリオ（記事の種類・失敗）と遅れを選べる fake の LLM を、サーバに依存しない構成要素として作る。それを使う開発用のサーバのバイナリを、本番の `yt2column-server` とは別に作る。

**背景:**

拡張とサーバを手で確かめるとき（レイアウト、状態の遷移、エラーの表示など）、今は実際の LLM を呼んでいる。fake の `LLMClient` は単体テスト用のもの（`internal/llm/testutil/mocks.go:1`。ビルドタグ `test`）しかなく、サーバを動かして確かめるときには選べないためである。例えば `docs/tasks/0050_viewer_tab/03_implementation_plan.md` の 4.3.2 の統合の確認では、料金を抑えるために `claude-haiku-5-5` でサーバを起動し、「やり直す」の表示は、存在しないモデルで起動したサーバで生成を失敗させて出した。どちらも、LLM の出力の中身を必要としない確認だった。

このやり方には次の問題がある。

-   確認のたびに LLM の料金がかかり、API キーが要る。
-   出力が毎回変わるので、同じ画面を再現できない。長い記事や見出しの多い記事など、レイアウトの確認に向く記事を狙って出せない。
-   生成にかかる時間を選べない。進捗の表示を確かめるには遅れが要り、ほかの確認では速く終わってほしい。
-   失敗（空の応答、出力の打ち切り、API のエラー、タイムアウト）は、存在しないモデルを指定するような遠回りの方法でしか起こせない。

issue #687 の後に立った [#769](https://github.com/isseis/yt2column/issues/769) は、localhost サーバと Native Messaging のホストを撤去し、拡張だけで記事を作る構成に移る方針である（撤去は [#773](https://github.com/isseis/yt2column/issues/773)）。#769 は Go のコアを WASM にビルドして拡張から使う案を挙げているが、Go の WASM にするか TS に一本化するかは [#772](https://github.com/isseis/yt2column/issues/772) で決める。開発用のサーバはサーバの撤去とともに使えなくなる。一方で、手での確認は #773 までの間も続く。そこで本書は、fake の LLM そのものをサーバから独立させ、移行の後も開発用のビルドで使えるようにする（「要件定義の際に決めたこと」）。

対応 issue: [#687](https://github.com/isseis/yt2column/issues/687)（前提: [#770](https://github.com/isseis/yt2column/issues/770)（タスク `0083_remove_slack_webhook`）、関連: [#769](https://github.com/isseis/yt2column/issues/769)・[#771](https://github.com/isseis/yt2column/issues/771)・[#772](https://github.com/isseis/yt2column/issues/772)・[#773](https://github.com/isseis/yt2column/issues/773)）

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。開発用のサーバの起動と引数の拒否、fake が返す記事と失敗、本番のバイナリに fake が入らないこと、文書に書くことである。次のものは設計（`02_architecture.md`）で決める。構成要素のパッケージの名前と置き場所、バイナリ・引数・`make` のターゲットの名前、fake がジョブと工程を区別する手段、本番のバイナリから fake を締め出す検査の手段、記事の文面、テストの手段である。要件の段階で挙がった設計の事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #687 で決めたこと:**

-   **本番の `yt2column-server` には fake を組み込まない。** 設定を誤ったときに、fake の記事が Webhook に投稿されたり本番の利用者の前に出たりすることを、設定の検査ではなく構成で防ぐためである。
-   **開発用のサーバは、本番のサーバと同じ `internal/server` を使い、同じソケットのパスで待ち受ける。** Native Messaging のホストと拡張を変えずに、サーバだけを差し替えて確かめられるようにするためである。
-   **fake の LLM は決まった記事を返し、シナリオ（遅れ、失敗の種類、記事の種類）を選べる。**
-   **シナリオは、呼び出し側の文字列の中身から推測せず、列挙値として宣言する。** CLAUDE.md の「Declare, don't infer」に従う。
-   **fake の記事は、生成の後の 2 つの工程（字数の調整、検証・推敲）でも失敗しない。** 字数の調整にも検証・推敲にも、検証を通る応答を返す。
-   **範囲の外:** 記事の品質の評価（実際の LLM で行う）と、LLM の API の HTTP の振る舞いの再現（`httptest` を使う単体テストの役目）。

**要件定義の際に決めたこと（2026-11-11）:**

-   **プロセスは full とする。** この変更は簡易な進め方から除外する変更に当たると判断した。`docs/dev/security.md` の §8.2 に開発用のサーバの規則を加えるので、requirements_process.md の「Simple Process」の「Excluded changes」の 1 つ目（`security.md` の規則を変える）に当たるためである。除外の判断を別にしても、新しい構成要素とバイナリを作り、まだ決めていない事項が多く、新しい ADR も要るので、通常の進め方が向く。人はこの判断を覆していない。ADR: なし（このタスクの進め方の決定で、タスクの外に及ばない）。
-   **fake の LLM を、サーバに依存しない構成要素として作り、今は開発用のサーバに配線する（F-001・F-005）。** #769 がサーバの撤去を決めたので、issue の提案（開発用のサーバ）をこの形に改めた。撤去されるのはサーバへの配線だけになり、作業の大半を占める fake の構成要素は、移行の後の開発用のビルドでも使える。採らなかった案は 2 つある。#772 の設計を待って保留する案は、#773 までの間の手での確認に料金と再現性の問題を残す。issue のとおりサーバと一体で作り、#773 でまとめて撤去する案は、移行の後に使える構成要素を残さない。移行の後の配線は #772・#773 に任せる。ADR: [ADR-0044](../../dev/adr/0044-dev-fake-llm.md) を作る（本番のバイナリと開発用のビルドの境界を決め、#773 の後のタスクも縛る）。
-   **fake の構成要素は、`GOOS=js GOARCH=wasm` でビルドできることを要件とし、それを検査する（AC-03）。** これはタスク 0084 の決定の例外である。0084 は、WASM でビルドできることを守る検査を `make test`・`make lint`・CI に加えないと決めた（`docs/tasks/0084_wasm_pipeline_poc/01_requirements.md` の「要件定義の際に決めたこと（2026-11-11）」）。Go の WASM にするか TS に一本化するかを #772 がまだ決めておらず、その判断を先取りしないためである。本書は、fake の構成要素を移行の後の開発用のビルドで使えるようにすることを目的に、人の判断でこの例外を置く。検査がなければ、WASM でビルドできることは後の変更で黙って失われうる。例外の範囲は、fake の構成要素とそれが依存するパッケージ（`internal/llm` など）を `GOOS=js GOARCH=wasm` でビルドできることに限る。0084 が検査しないと決めたコア（`internal/transcript`・`internal/writer` など）の WASM でのビルドは検査しない。#772 が TS に一本化すると決めたときは、#772 がこの検査と ADR-0044 の該当の項を見直す。0084 の決定に従って検査しない案は採らなかった。ADR: ADR-0044 の決定に含める。
-   **fake の振る舞いは、生成のジョブごとに独立させる（AC-04）。** 本番のサーバは、生成のクライアントと検証・推敲のクライアントを起動のときに 1 つずつ作ってすべてのジョブで共有し（`cmd/yt2column-server/run.go:323-335`）、生成のジョブを同時に 2 つまで動かす（`internal/server/jobs_api.go:15`）。呼び出しの順序を数えるだけでは、同時に動くジョブや前のジョブの呼び出しが混ざり、選んだ工程で失敗させられない。手段は設計に任せ（[design_handoff.md](design_handoff.md) H-01）、本番のサーバと `LLMClient` の契約を変えずに実現する。同時に 1 ジョブだけで使う制限を受け入れる案は採らなかった。ADR: ADR-0044 の決定に含める。
-   **シナリオは、開発用のサーバのコマンドライン引数で、起動のときに選ぶ（F-002）。** シナリオを変えるときは起動し直す。本番の設定の読み込み（`YT2COLUMN_LLM` の構文と設定ファイルのキー）に fake を持ち込まず、[ADR-0018](../../dev/adr/0018-server-config-file.md)（サーバは設定ファイルだけから設定を読む）と [ADR-0024](../../dev/adr/0024-env-access-in-config.md)（環境変数を読むのは決めた入口だけ）に例外を作らないためである。設定ファイルのキーで渡す案と、環境変数で渡す案は採らなかった。ADR: ADR-0044 の決定に含める。
-   **失敗のシナリオでは、失敗の種類（空の応答、出力の打ち切り、API のエラー、タイムアウト）と、失敗させる工程（生成、字数の調整、検証・推敲）の両方を選べる（F-004）。** 工程ごとの失敗の表示も確かめられるようにするためである。失敗させる工程を常に生成とする案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **失敗の後に「やり直す」で成功する流れは、確かめる範囲の外とする（§2.3）。** シナリオは起動のときに決まるので、同じサーバでやり直しても同じ失敗になる。記事のキャッシュはメモリにあるので、起動し直すと失敗したジョブも消える。「最初のジョブだけ失敗する」指定を加える案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **開発用のサーバは、設定ファイルを読まず、API キーも要らない（F-002）。** 設定ファイルから読むものがない（LLM は fake で、Webhook への投稿は次の決定のとおり存在しない）。本番の設定ファイルを読む案は採らなかった。ADR: ADR-0044 の決定に含める。
-   **このタスクは、タスク 0083（Webhook への投稿の廃止、[#770](https://github.com/isseis/yt2column/issues/770)）の実装が `main` に入った後に着手する。開発用のサーバは Webhook への投稿に対応しない。** 0083 は投稿の API を消し、投稿のリクエストを `not_found` で拒否する（`docs/tasks/0083_remove_slack_webhook/01_requirements.md` の AC-02）。その後に実装すれば、投稿の経路そのものがなく、開発用のサーバに投稿の振る舞いを定める要件が要らない。先に実装して、投稿を Webhook が設定されていないときと同じく拒否する案は採らなかった。0083 の実装で要件が食い違うためである。ADR: ADR-0044 の決定に含める。
-   **開発用のバイナリは、`make build` とは別の `make` のターゲットで作る（F-005）。** 普段のビルドの成果物に開発用のバイナリが混ざらないようにするためである。`make build` に 4 つ目のバイナリとして入れる案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **fake の記事の種類は 3 つとする（F-003）。** 標準の記事（字数の調整が動かない長さ）、長い記事（字数の調整が動き、見出しが多い）、ビューアの Markdown の規則の要素を網羅した記事である。レイアウトの確認に要る記事を狙って出せるようにするためである。標準と長い記事の 2 つだけにする案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **遅れは、シナリオとは別のコマンドライン引数で、LLM の呼び出し 1 回ごとの秒数として指定する。受理するのは 0 から 600 までの 10 進の整数だけで、既定は 0 とする（F-002・F-004）。** 進捗の表示の確認では長くし、ほかの確認では 0 にできるようにするためである。形を 1 つに絞り、標準ライブラリの長さの解析が受理しうる `+5s`・`.5s`・単位のない値のような形を扱わずに済むようにする。10 分あれば進捗の表示の確認に足りる。遅れの長さを固定した「遅い」シナリオを 1 つ設ける案と、単位付きの長さを受理する案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **fake のモデルは料金の単価の表に入れず、料金が不明と表示されるようにする。fake の記事のタイトルは決まった印で始める（F-003）。** 本番の単価の表（`internal/pricing`）に fake を持ち込まないためである。表にないモデルの料金は今も不明になる（`internal/pricing/pricing.go:113-115`）。タイトルの印は、スクリーンショットなどで fake の記事を本物と取り違えないためである。単価 0 を表に入れて 0 USD と表示する案と、印を付けない案は採らなかった。ADR: 単価の表に fake を入れないことは ADR-0044 の決定に含める。タイトルの印は ADR にしない（タスクの中で閉じる決定である）。
-   **CLI（`cmd/yt2column`）は範囲の外とする（§2.3）。** CLI は記事の品質を実際の LLM で確かめる経路であり、issue が問題にしている手での確認は拡張とサーバのものだからである。ADR: なし（タスクの中で閉じる決定である）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   拡張とサーバの手での確認を、LLM の料金も API キーもなしに行えるようにする。
-   同じ記事、同じ遅れ、同じ失敗を、起動のときの指定で何度でも再現できるようにする。
-   本番のバイナリに fake を入れず、それを機械的に確かめる。
-   fake の LLM を、サーバの撤去（#773）の後も開発用のビルドで使える構成要素にする。

### 2.2. スコープ (In Scope)

-   サーバに依存しない fake の LLM の構成要素（F-001）。
-   fake の LLM を使う開発用のサーバのバイナリと、その起動の引数（F-002）。
-   fake が返す記事の 3 つの種類と、記事の印・モデル名・料金の扱い（F-003）。
-   失敗の種類と失敗させる工程の選択、遅れの指定（F-004）。
-   本番の 3 つのバイナリが fake に依存しないことの機械的な検査、fake の構成要素の WASM でのビルドの検査、開発用のバイナリを作る `make` のターゲット（F-005）。
-   文書：`docs/dev/security.md` §8.2、`docs/dev/guides/development.md`、`docs/dev/project_overview.md`、`docs/dev/conventions/package_reference.md`、`docs/dev/conventions/test_organization.md`、`CLAUDE.md`、ADR-0044 と ADR の索引（F-006）。

### 2.3. スコープ外 (Out of Scope)

-   CLI（`cmd/yt2column`）で fake を使えるようにすること（「要件定義の際に決めたこと」）。
-   移行の後の構成（拡張だけの構成）への fake の配線。#772・#773 で決める。
-   Webhook への投稿。このタスクは 0083 の実装の後に着手するので、そのときサーバに投稿の経路はない（「要件定義の際に決めたこと」）。
-   失敗の後に「やり直す」で成功する流れの確認（「要件定義の際に決めたこと」）。
-   起動した後にシナリオを切り替えること。シナリオを変えるときは起動し直す。
-   F-004 の 4 つ以外の失敗を起こすこと。例えば、記事の検査で拒否される失敗（`article_invalid`）や、記事が大きすぎる失敗（`article_too_large`）である（`internal/server/status.go:233-252`）。これらは LLM の失敗ではなく、issue が問題にしているのは LLM の失敗の再現だからである。
-   記事の品質の評価（issue #687）。
-   LLM の API の HTTP の振る舞いの再現（issue #687）。
-   本番のサーバ（`yt2column-server`）・ホスト・拡張の振る舞いの変更。
-   単体テスト用の fake（`internal/llm/testutil`）を置き換えること。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: サーバに依存しない fake の LLM の構成要素

`LLMClient` を満たし、起動のときに受け取ったシナリオに従って決まった応答を返す fake を、サーバに依存しない構成要素として作る。

**Acceptance Criteria**:
- **AC-01**: fake の構成要素は `internal/llm` の `LLMClient` を満たす。ネットワークにも外部コマンドにもファイルにも触れずに応答を返す。
- **AC-02**: fake の構成要素の推移的な依存に、サーバだけが使うパッケージ（`internal/server`・`internal/articlecache`・`internal/serversock`・`internal/privatefile`・`internal/nmhost`）と、`cmd/` の下のパッケージが 1 つも含まれない。
- **AC-03**: fake の構成要素は `GOOS=js GOARCH=wasm` でビルドでき、それを確かめる検査が `make test` か `make lint` で走る。検査の範囲は、fake の構成要素とその依存に限る（「要件定義の際に決めたこと」の 0084 の例外）。
- **AC-04**: 生成のジョブごとに、fake の振る舞い（どの工程にどの応答を返すか、どの工程で失敗するか）は、選んだシナリオだけで決まる。同時に動くほかのジョブにも、前に動いたジョブにも影響されない。生成のジョブを 2 つ同時に始めても、続けて何度始めても、どのジョブも同じ結果になる。同じ結果とは、fake が返すタイトルと本文が同じ記事、または同じ工程の同じ失敗である。チャンネル名と出典の URL は、本番と同じくジョブの入力から付く（§4.2）ので、比べる対象に含めない。fake は、プロンプトの文字列の中身によって振る舞いを変えない（CLAUDE.md「Declare, don't infer」）。

#### F-002: 開発用のサーバの起動

fake の LLM を使う開発用のサーバのバイナリを、本番の `yt2column-server` とは別に作る。開発用のサーバは、本番のサーバと同じ `internal/server` を使い、同じソケットのパスで待ち受ける。

**Acceptance Criteria**:
- **AC-05**: 開発用のサーバは、本番のサーバと同じく `HOME` から導出したソケットのパスで待ち受ける。ホストと拡張を変えずに、拡張から生成の開始と状態の取得ができる。
- **AC-06**: 開発用のサーバは、設定ファイル（`$HOME/.config/yt2column/config.env`）がない場合も、受理されない形（モードが `0600` でない、書式が正しくないなど）の場合も、同じように起動して同じように振る舞う。API キーも要らない。
- **AC-07**: プロセスの環境変数のうち、開発用のサーバの振る舞いと出力を変えるのは、ソケットのパスを導出する `HOME` だけである。`YT2COLUMN_LLM`・`ANTHROPIC_API_KEY`・`GODEBUG` などを設定しても、振る舞いも出力も変わらない。本番のサーバが `GODEBUG` を読むのは、HTTP/2 のデバッグログに秘密が出ることを警告するためで（[ADR-0018](../../dev/adr/0018-server-config-file.md)）、開発用のサーバは秘密を持たず HTTP のリクエストを送らないので、その警告が要らない。Go 自身が `GODEBUG` で自分の振る舞いを変えることは除く。
- **AC-08**: 起動の引数は次のとおりである。名前と値の綴りは設計で決め、`development.md` に書く。
  - **記事の種類**: 標準・長い・要素を網羅、の 3 つから 1 つ。省くと標準になる。
  - **失敗**: 失敗の種類（空の応答・出力の打ち切り・API のエラー・タイムアウト）と、失敗させる工程（生成、字数の調整、検証・推敲の 3 つ）の組。種類と工程はいつも組で指定し、両方を省くと失敗しない。
  - **遅れ**: 0 から 600 までの 10 進の整数で、単位は秒。省くと 0 になる。
  - **使い方の案内の要求**: 案内を標準エラー出力に出し、何も待ち受けずに終了コード `0` で終わる。

  引数を何も指定しない場合は、標準の記事を遅れなしで、失敗せずに返す。
- **AC-09**: 次の指定は受理しない。受理しないときは、何も待ち受けずに起動を中止し、標準エラー出力に、受理する値を示す使い方の案内を出して、終了コード `2` で終わる。値を近いものに直して起動することはしない（CLAUDE.md「Reject, don't normalize」）。
  - 知らない引数、知らない値、引数の後に残る余分な語、同じ引数の繰り返し、値の欠けた引数、失敗の種類と工程の片方だけの指定。
  - 遅れの値で、10 進の数字以外を含むもの（符号・小数点・単位・空白）、先頭が `0` の 2 桁以上の値（`05`）、空の値、600 を超える値。
  - 字数の調整の工程で失敗させる指定のうち、記事の種類が長い記事でないもの（字数の調整は本文が 4,000 字を超えるときだけ動く。`internal/writer/length.go:9`）。
- **AC-10**: 起動したとき、開発用のサーバは標準エラー出力に、fake の LLM で動いていることと、選んだ記事の種類・失敗・遅れを 1 行で示す。
- **AC-11**: 本番のサーバが起動のロックを持っているとき、開発用のサーバは、本番のサーバが 2 つ目のサーバの起動を中止するのと同じく中止する。開発用のサーバがロックを持っているときの本番のサーバも同じである。ソケットのディレクトリの検査、stale のソケットの判定、ロックの規則は本番のサーバと同じである（`docs/dev/security.md` §8.2「起動のロック」「stale の判定」）。

#### F-003: fake の記事

fake は、3 つの種類の記事を返す。

**Acceptance Criteria**:
- **AC-12**: 標準の記事では、完成した記事の本文が 4,000 字以下（`internal/writer/length.go:9-22` の数え方）で、字数の調整の工程は動かない。検証・推敲の工程を通って記事が完成する。
- **AC-13**: 長い記事では、生成の工程が返す本文が 4,000 字を超え、字数の調整の工程が動く。字数の調整と検証・推敲の工程を通って記事が完成する。完成した記事は、標準の記事より多くの見出しを持つ。
- **AC-14**: 要素を網羅した記事では、本文が 4,000 字以下で、字数の調整の工程は動かない。完成した記事の表示用の Markdown は、ビューアの記事の解析の規則（`docs/tasks/0063_viewer_markdown/01_requirements.md` §3.2「記法の規則」、[ADR-0017](../../dev/adr/0017-viewer-markdown-rendering.md)）のうち、記事の検査（`internal/writer`）を通る入力で現れうる規則のそれぞれに当てはまる箇所を、1 つ以上含む。各工程を通って記事が完成する。
- **AC-15**: どの種類の記事でも、完成した記事のタイトルは決まった印で始まる。印の文字列は設計で決め、`development.md` に書く。
- **AC-16**: fake の応答のモデル名は、`internal/pricing` の単価の表にない決まった値である。完成した記事について、状態の取得が返す記事の料金は不明（`cost.state` が `unknown`。`internal/server/status.go:54-62`）になり、ビューアは料金を不明として表示する。単価の表は変えない。

#### F-004: 失敗と遅れ

fake は、選んだ工程で選んだ種類の失敗を返し、指定した遅れの後に応答する。

**Acceptance Criteria**:
- **AC-17**: 失敗の種類ごとに、状態の取得が返す失敗の理由のコードは、空の応答で `llm_empty`、出力の打ち切りで `llm_truncated`、API のエラーで `llm_failed`、タイムアウトで `llm_timeout` になる（`internal/server/status.go:233-252`）。失敗の工程は、選んだ工程として示される（`internal/server/generation.go:146-158`）。
- **AC-18**: 失敗させる工程より前の工程は成功する。その工程で失敗したジョブは、完成した記事を返さない（CLAUDE.md「Empty is an error」）。
- **AC-19**: 遅れを指定すると、fake は LLM の呼び出しのたびに、応答（成功も失敗も）の前にその秒数だけ待つ。1 つのジョブの待ち時間の合計は、呼び出しの回数（標準の記事と要素を網羅した記事で 2 回、長い記事で 3 回。失敗した場合はその工程まで）と遅れの積である。
- **AC-20**: 待っている間に呼び出しの `context` が取り消されたとき（サーバが停止を始めた場合など）、fake は待ち終わるのを待たずに、`context` のエラーを返す。そのジョブの失敗の理由は、本番のサーバがそのエラーを分類するとおりになる（`internal/server/generation.go:163-180`）。

#### F-005: 本番のバイナリとの分離とビルド

**Acceptance Criteria**:
- **AC-21**: 本番の 3 つのバイナリ（`cmd/yt2column`・`cmd/yt2column-server`・`cmd/yt2column-nmhost`）の推移的な依存に、fake の構成要素も開発用のサーバのパッケージも含まれない。
- **AC-22**: 本番の 3 つのバイナリのいずれかが、直接にも間接にも fake の構成要素に依存するように変えると、`make test` か `make lint` が失敗する。
- **AC-23**: `make build` は今までどおり本番の 3 つのバイナリだけを作り、開発用のバイナリを作らない。開発用のバイナリは別の `make` のターゲットで作る。
- **AC-24**: 記事の種類と失敗の組み合わせのうち AC-08・AC-09 が受理するすべてについて、記事が完成するか、選んだ工程で選んだ失敗になるかを、実際の LLM を呼ばずに確かめるテストが `make test` で走る。

#### F-006: 文書

**Acceptance Criteria**:
- **AC-25**: `docs/dev/security.md` §8.2 に、開発用のサーバの規則がある。本番のバイナリに fake を入れないこと、開発用のサーバは設定ファイルも API キーも読まないこと、本番のサーバと同じソケットのパスと起動のロックを使うこと、開発用のバイナリを常用の環境に置かないこと、および本書 §4.2 の残余のリスクである。
- **AC-26**: `docs/dev/guides/development.md` に次のものがある。開発用のバイナリの作り方、起動のしかた（引数と受理する値、タイトルの印）、本番のサーバと同時には動かせないこと、拡張から確かめる手順、やり直しの成功は確かめられないこと。
- **AC-27**: 追加した構成要素・バイナリ・`make` のターゲットが、次の場所にある。`docs/dev/project_overview.md` の想定ディレクトリ構成、`docs/dev/conventions/package_reference.md` のパッケージの表、`CLAUDE.md` の「Build Commands」。
- **AC-28**: `docs/dev/conventions/test_organization.md` の「Pipeline fakes」に、fake の構成要素がこの規則（fake は `testutil/mocks.go` に置き、ビルドタグ `test` を付ける）の例外であることを、範囲と理由とともに書く。fake の構成要素は `testutil/` の下に置かない。
- **AC-29**: ADR-0044 と ADR の索引の行がある。ADR-0044 の決定は、本書の決定と一致する。本書の決定とは、本番のバイナリに fake を入れないこと、fake はサーバに依存せず WASM でビルドできる構成要素であること、振る舞いはジョブごとに選んだシナリオで決まること、開発用のサーバは設定ファイルを読まず投稿に対応しないこと、シナリオは起動のときの引数で選ぶこと、単価の表に fake を入れないことである。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   遅れを指定しない場合、fake の LLM の呼び出しは待たずに戻る。手での確認とテストで、生成の完了を待つ時間をなくすためである。

### 4.2. セキュリティ (Security)

`docs/dev/security.md` を適用する。このタスクは、条件付きのガイドの条件のうち、API キーと Webhook URL の扱い、ネットワークへの送信、公開する記事に埋め込むテキストに当たる。

-   **本番のバイナリに fake を入れない（AC-21・AC-22）。** 設定の誤りで、fake の記事が本番の利用者の前に出たり Webhook に投稿されたりすることを、構成で防ぐ。
-   **秘密を扱わない（AC-06・AC-07）。** 開発用のサーバは API キーも Webhook URL も読まず、LLM の API にも Webhook にも送らない。0083 の実装の後に着手するので、サーバに投稿の経路はない。秘密を出力に流す経路がない。
-   **受け取る入力の境界は本番のサーバと同じである。** 開発用のサーバは `internal/server` を使うので、拡張からのリクエストの検査（`security.md` §8.2「受け取る入力の境界」）は本番のサーバと同じである。コピーした字幕は本番と同じく検査する。fake はプロンプトを読まないので、字幕の中身は fake の応答を変えない。
-   **記事の外部由来の部分は本番と同じ扱いを受ける。** fake が返すタイトルと本文は決まった文面である。一方、記事のチャンネル名と出典の URL は、本番と同じく拡張が送った値から `internal/writer` が付ける（`internal/writer/output.go:216-227`）。これらには本番と同じ規則がかかる（`security.md` §6、§8.1、0083 のコピーでのメンションの無効化）。
-   **残余のリスク（許容する）。** 開発用のサーバは本番のサーバと同じソケットのパスで待ち受ける。利用者が本番のサーバの代わりに開発用のサーバを起動すると、拡張は fake の記事を表示する。タイトルの印（AC-15）、起動の行（AC-10）、料金の不明（AC-16）で気づけるようにし、`security.md` で開発用のバイナリを常用の環境に置かないことを求める。これは同一ユーザーの信頼の範囲（[ADR-0006](../../dev/adr/0006-threat-model.md)）に含める。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   開発用のサーバの停止（シグナル、処理中のジョブの扱い）は本番のサーバと同じである。遅れの間に停止を始めた場合は、AC-20 のとおり待ち終わるのを待たずに戻る。

### 4.4. 互換性 (Compatibility)

-   拡張・ホスト・本番のサーバの振る舞いと API、`LLMClient` の契約（[ADR-0021](../../dev/adr/0021-llm-client-contract.md)）は変えない。
-   本番のサーバと同じく、macOS と Linux で動く。

### 4.5. 保守性 (Maintainability)

-   fake の構成要素は、サーバの撤去（#773）の後も、移行の後の開発用のビルドで使える（AC-02・AC-03）。
-   記事の種類・失敗の種類・工程を足すときは、列挙値に値を足す。呼び出し側の文字列の中身から推測する分岐は作らない（AC-04）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   このタスクの実装は、タスク 0083 の実装が `main` に入った後に始める（「要件定義の際に決めたこと」）。
-   外部のライブラリを加えない（CLAUDE.md「Dependencies」）。
-   本番の設定の読み込み（`internal/config`、[ADR-0003](../../dev/adr/0003-llm-config-contract.md)・[ADR-0018](../../dev/adr/0018-server-config-file.md)）に fake のプロバイダを加えない。
-   [ADR-0024](../../dev/adr/0024-env-access-in-config.md) の、環境変数を読む場所を限る規則に従う。
-   方針の例外が 2 つある。タスク 0084 の「WASM でビルドできることを守る検査は加えない」と、`docs/dev/conventions/test_organization.md` の「Pipeline fakes」（fake はビルドタグ `test` の `testutil/mocks.go` に置く）である。前者の理由と範囲は「要件定義の際に決めたこと」にある。後者の例外の理由は、fake の構成要素を開発用のバイナリに組み込むので、ビルドタグ `test` のファイルには置けないことである。範囲は fake の構成要素に限る。単体テスト用の fake は今の規則のままにする。

## 6. 用語集 (Glossary)

-   **fake の LLM（fake の構成要素）**: `LLMClient` を満たし、実際の LLM を呼ばずに決まった応答を返す構成要素。単体テスト用の fake（`internal/llm/testutil`）とは別のもの。「構成要素」は `docs/translation_glossary.md` の「構成要素パッケージ」の用法に従う。
-   **開発用のサーバ**: fake の LLM を使い、`internal/server` で待ち受ける開発用のバイナリ。本番のサーバ（`yt2column-server`）とは別に作る。
-   **シナリオ**: 開発用のサーバの起動のときに選ぶ fake の振る舞いで、記事の種類と失敗の組である。遅れは別の引数で指定する。
-   **工程**: `ArticleWriter` の中の 3 つの処理、すなわち生成、字数の調整、検証・推敲（「検証・推敲」で 1 つの工程。`docs/translation_glossary.md`「構成要素パッケージ」）。
-   用語は `docs/translation_glossary.md` と統一する。
