## 1. 概要 (Overview)

**目的:** 本書は、実際の LLM を呼ばずに拡張とサーバを手で確かめられるようにするための要件を定義する。決まった記事を返し、シナリオ（記事の種類・遅れ・失敗）を選べる fake の LLM を、サーバに依存しない部品として作り、それを使う開発用のサーバのバイナリを本番の `yt2column-server` とは別に作る。

**背景:**

拡張とサーバの手での確認（レイアウト、状態の遷移、エラーの表示など）では、実際の LLM を呼んでいる。fake の `LLMClient` は単体テスト用のもの（`internal/llm/testutil/mocks.go:1`。ビルドタグ `test`）しかなく、サーバを動かして確かめるときには選べないためである。例えば `docs/tasks/0050_viewer_tab/03_implementation_plan.md` の 4.3.2 の統合の確認では、料金を抑えるために `claude-haiku-5-5` でサーバを起動し、「やり直す」の表示は存在しないモデルで起動したサーバで生成を失敗させて出した。どちらも、LLM の出力の中身を必要としない確認だった。

このやり方には次の問題がある。

-   確認のたびに LLM の料金がかかり、API キーが要る。
-   出力が毎回変わるので、同じ画面を再現できない。長い記事や見出しの多い記事など、レイアウトの確認に向く記事を狙って出せない。
-   生成にかかる時間を選べない。進捗の表示を確かめるには遅れが要り、ほかの確認では速く終わってほしい。
-   失敗（空の応答、出力の打ち切り、API のエラー、タイムアウト）を、存在しないモデルを指定するような遠回りの方法でしか起こせない。

issue #687 の後に立った [#769](https://github.com/isseis/yt2column/issues/769) は、localhost サーバと Native Messaging のホストを撤去し、拡張から Go の WASM 版のパイプラインで Claude API を直接呼ぶ構成に移る方針である（撤去は [#773](https://github.com/isseis/yt2column/issues/773)）。開発用のサーバはその撤去とともに使えなくなるが、手での確認は #773 までの間（[#770](https://github.com/isseis/yt2column/issues/770) など）も続く。本書は、fake の LLM そのものをサーバから独立させ、移行の後も開発用のビルドで使えるようにする（「要件定義の際に決めたこと」）。

対応 issue: [#687](https://github.com/isseis/yt2column/issues/687)（関連: [#769](https://github.com/isseis/yt2column/issues/769)・[#770](https://github.com/isseis/yt2column/issues/770)・[#772](https://github.com/isseis/yt2column/issues/772)・[#773](https://github.com/isseis/yt2column/issues/773)）

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。開発用のサーバの起動のしかたと拒否、fake が返す記事と失敗、本番のバイナリに fake が入らないこと、文書に書くことである。部品のパッケージの名前と置き場所、バイナリとコマンドライン引数と `make` のターゲットの名前、fake が工程を区別する手段、本番のバイナリから fake を締め出す検査の手段（`depguard` の規則、ビルドタグ、テストなど）、記事の文面、テストの手段は、設計（`02_architecture.md`）で決める。要件の段階で挙がった設計の事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #687 で決めたこと:**

-   **本番の `yt2column-server` には fake を組み込まない。** 設定を誤ったときに、fake の記事が Webhook に投稿されたり本番の利用者の前に出たりすることを、設定の検査ではなく構成で防ぐためである。
-   **開発用のサーバは、本番のサーバと同じ `internal/server` を使い、同じソケットのパスで待ち受ける。** ネイティブメッセージングのホストと拡張を変えずに、サーバだけを差し替えて確かめられるようにするためである。
-   **fake の LLM は決まった記事を返し、シナリオ（遅れ、失敗の種類、記事の種類）を選べる。**
-   **シナリオは、呼び出し側の文字列の中身から推測せず、列挙値として宣言する。** CLAUDE.md の「Declare, don't infer」に従う。
-   **fake の記事は、生成の後の 2 つの工程（字数の調整、検証・推敲）でも失敗しない。** 字数の調整にも検証・推敲にも、検証を通る応答を返す。
-   **範囲の外:** 記事の品質の評価（実際の LLM で行う）と、LLM の API の HTTP の振る舞いの再現（`httptest` を使う単体テストの役目）。

**要件定義の際に決めたこと（2026-11-11）:**

-   **プロセスは full とする。** 除外にあたる変更と判断した。`docs/dev/security.md` の §8.2 に開発用のサーバの規則を加えるので、requirements_process.md の「Simple Process」の「Excluded changes」の 1 つ目（`security.md` の規則を変える）にあたるためである。除外を除いても、新しい部品とバイナリという新しい仕組みを作ること、開いている決定が多いこと、新しい ADR が要ることから、full プロセスが向く。判断は覆していない。ADR: なし（タスクの中で閉じる決定である）。
-   **fake の LLM を、サーバに依存しない部品として作り、今は開発用のサーバに配線する（F-001・F-006）。** #769 がサーバの撤去を決めたことを受けて、issue の提案（開発用のサーバ）をこの形に改めた。撤去されるのはサーバへの配線だけになり、作業の大半を占める fake の部品は、移行の後の開発用のビルドでも使える。#772 の設計を待って保留する案と、issue のとおりにサーバと一体で作って #773 でまとめて撤去する案は採らなかった。前者は #773 までの間の手での確認の料金と再現性の問題を残し、後者は移行の後に使える部品を残さない。移行の後の配線は #772・#773 に任せる。ADR: [ADR-0044](../../dev/adr/0044-dev-fake-llm.md) を作る（本番のバイナリと開発用のビルドの境界を決め、#773 の後のタスクも縛る）。
-   **シナリオは、開発用のサーバのコマンドライン引数で、起動のときに 1 つ選ぶ（F-002）。** シナリオを変えるときは起動し直す。本番の設定の読み込み（`YT2COLUMN_LLM` の構文と設定ファイルのキー）に fake を持ち込まず、[ADR-0018](../../dev/adr/0018-server-config-file.md)（サーバは設定ファイルだけから設定を読む）と [ADR-0024](../../dev/adr/0024-env-access-in-config.md)（環境変数を読むのは決めた入口だけ）に例外を作らないためである。設定ファイルのキーと環境変数の案は採らなかった。ADR: ADR-0044 の決定に含める。
-   **失敗のシナリオでは、失敗の種類（空の応答、出力の打ち切り、API のエラー、タイムアウト）と、失敗させる工程（生成、字数の調整、検証・推敲）の両方を選べる（F-004）。** 工程ごとの失敗の表示も確かめられるようにするためである。失敗の工程を常に生成とする案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **開発用のサーバは Webhook への投稿に対応しない。設定ファイルを読まず、API キーを要らない（F-002・F-005）。** Webhook への投稿は #770 で廃止される予定なので、最初から対応しない。fake の記事が実際の Webhook に投稿されることも構成で起きなくなる。本番と同じ設定ファイルを読んで投稿もできるようにする案は採らなかった。ADR: ADR-0044 の決定に含める。
-   **開発用のバイナリは、`make build` とは別の `make` のターゲットで作る（F-006）。** 普段のビルドの成果物に開発用のバイナリが混ざらないようにするためである。`make build` に 4 つ目のバイナリとして入れる案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **fake の記事の種類は 3 つとする（F-003）。** 標準の記事（字数の調整が動かない長さ）、長い記事（字数の調整が動き、見出しが多い）、ビューアの Markdown の規則の要素を網羅した記事である。レイアウトの確認に要る記事を狙って出せるようにするためである。標準と長い記事の 2 つだけにする案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **遅れは、シナリオとは別のコマンドライン引数で、LLM の呼び出し 1 回ごとの長さとして指定する。既定は遅れなしとする（F-002・F-004）。** 進捗の表示の確認では長くし、ほかの確認では 0 にできるようにするためである。遅れの長さを固定した「遅い」シナリオを 1 つ設ける案は採らなかった。ADR: なし（タスクの中で閉じる決定である）。
-   **fake のモデルは料金の単価の表に入れず、料金は不明と表示させる。fake の記事のタイトルは決まった印で始める（F-003）。** 本番の単価の表（`internal/pricing`）に fake を持ち込まないためで、表にないモデルの料金は今も不明になる（[ADR-0022](../../dev/adr/0022-cost-estimate.md)）。タイトルの印は、スクリーンショットなどで fake の記事を本物と取り違えないためである。単価 0 を表に入れて 0 USD と表示する案と、印を付けない案は採らなかった。ADR: 単価の表に fake を入れないことは ADR-0044 の決定に含める。タイトルの印は ADR にしない（タスクの中で閉じる決定である）。
-   **CLI（`cmd/yt2column`）は範囲の外とする（§2.3）。** CLI は記事の品質を実際の LLM で確かめる経路であり、issue が困っている手での確認は拡張とサーバのものだからである。ADR: なし（タスクの中で閉じる決定である）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   拡張とサーバの手での確認を、LLM の料金も API キーもなしに行えるようにする。
-   同じ記事、同じ遅れ、同じ失敗を、起動のときの指定で何度でも再現できるようにする。
-   本番のバイナリには fake を入れず、それを機械的に確かめる。
-   fake の LLM を、サーバの撤去（#773）の後も開発用のビルドで使える部品にする。

### 2.2. スコープ (In Scope)

-   サーバに依存しない fake の LLM の部品（F-001・F-006）。
-   fake の LLM を使う開発用のサーバのバイナリと、その起動の引数（F-002・F-005）。
-   fake が返す記事の 3 つの種類と、記事の印・モデル名・料金の扱い（F-003）。
-   失敗の種類と失敗させる工程の選択、遅れの指定（F-004）。
-   本番の 3 つのバイナリが fake に依存しないことの機械的な検査と、開発用のバイナリを作る `make` のターゲット（F-006）。
-   文書：`docs/dev/security.md` §8.2、`docs/dev/guides/development.md`、`docs/dev/project_overview.md`、`docs/dev/conventions/package_reference.md`、`CLAUDE.md`、ADR-0044 と ADR の索引（F-007）。

### 2.3. スコープ外 (Out of Scope)

-   CLI（`cmd/yt2column`）で fake を使えるようにすること（「要件定義の際に決めたこと」）。
-   移行の後の構成（拡張の WASM 版のパイプライン）への fake の配線。#772・#773 で決める。
-   開発用のサーバからの Webhook への投稿（「要件定義の際に決めたこと」）。
-   記事の品質の評価（issue #687）。
-   LLM の API の HTTP の振る舞いの再現（issue #687）。
-   起動した後にシナリオを切り替えること。シナリオを変えるときは起動し直す。
-   本番のサーバ（`yt2column-server`）・ホスト・拡張の振る舞いの変更。
-   単体テスト用の fake（`internal/llm/testutil`）を置き換えること。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: サーバに依存しない fake の LLM の部品

`LLMClient` を満たし、起動のときに受け取ったシナリオに従って決まった応答を返す fake を、サーバに依存しない部品として作る。

**Acceptance Criteria**:
- **AC-01**: fake の部品は、`internal/llm` の `LLMClient` を満たし、ネットワークにも外部コマンドにもファイルにも触れずに応答を返す。
- **AC-02**: fake の部品は、サーバだけが使うパッケージ（`internal/server`・`internal/articlecache`・`internal/serversock`・`internal/privatefile`・`internal/nmhost`、および `cmd/` の下のパッケージ）に依存しない。`go list -deps` で、その部品の依存にこれらのパッケージがないことを確かめられる。
- **AC-03**: fake の部品は `GOOS=js GOARCH=wasm` でビルドできる。
- **AC-04**: fake の振る舞いは、受け取ったシナリオの値（列挙値）と、`LLMClient` の呼び出しの順序だけで決まる。プロンプトの文字列の中身によって振る舞いを変えない（CLAUDE.md「Declare, don't infer」）。同じシナリオで同じ順序で呼べば、同じ応答（本文・モデル名・使用量）を返す。

#### F-002: 開発用のサーバの起動

fake の LLM を使う開発用のサーバのバイナリを、本番の `yt2column-server` とは別に作る。開発用のサーバは、本番のサーバと同じ `internal/server` を使い、同じソケットのパスで待ち受ける。

**Acceptance Criteria**:
- **AC-05**: 開発用のサーバは、本番のサーバと同じ `HOME` から導出したソケットのパスで待ち受け、ホストと拡張を変えずに、拡張から生成の開始・状態の取得ができる。
- **AC-06**: 開発用のサーバは設定ファイル（`$HOME/.config/yt2column/config.env`）を読まない。設定ファイルがない場合も、ファイルが受理されない形（モードが `0600` でないなど）の場合も、起動の結果は変わらない。API キーを要らない。
- **AC-07**: 開発用のサーバがプロセスの環境から設定として読むのは、ソケットのパスを導出するための `HOME` だけである。環境に `YT2COLUMN_LLM`・`ANTHROPIC_API_KEY`・`SLACK_WEBHOOK_URL` などがあっても読まない。
- **AC-08**: シナリオ（記事の種類、失敗の種類と工程）と遅れは、コマンドライン引数で起動のときに指定する。シナリオを指定しない場合は、標準の記事を遅れなしで返す。
- **AC-09**: 受理しない引数（知らないシナリオの値、知らない引数、負の遅れ、遅れとして読めない値、同じ引数の繰り返し、組み合わせられない指定（AC-17））では、何も待ち受けずに起動を中止し、標準エラー出力に、受理する値を示す使い方の案内を出して、終了コード `2` で終わる。値を近いものに直して起動しない（CLAUDE.md「Reject, don't normalize」）。
- **AC-10**: 起動したとき、開発用のサーバは標準エラー出力に、fake の LLM で動いていることと、選んだシナリオと遅れを 1 行で示す。
- **AC-11**: 本番のサーバがすでに動いているとき（起動のロックを持っているとき）、開発用のサーバは本番のサーバと同じく起動を中止する。逆も同じである。ソケットのディレクトリの検査、stale のソケットの判定、ロックの規則は本番のサーバと同じである（`docs/dev/security.md` §8.2）。

#### F-003: fake の記事

fake は、3 つの種類の記事を返す。

**Acceptance Criteria**:
- **AC-12**: 標準の記事では、生成された記事の本文が 4,000 字以下（`internal/writer/length.go:9` の数え方）で、字数の調整の工程は動かない。検証・推敲の工程を通り、記事が完成する。
- **AC-13**: 長い記事では、生成の工程が返す本文が 4,000 字を超え、字数の調整の工程が動く。字数の調整と検証・推敲の工程を通り、記事が完成する。完成した記事は、標準の記事より多くの見出しを持つ。
- **AC-14**: 要素を網羅した記事では、完成した記事が、ビューアの記事の解析の規則（`docs/tasks/0063_viewer_markdown/01_requirements.md` §3.2、[ADR-0017](../../dev/adr/0017-viewer-markdown-rendering.md)）が定めるブロックとインラインの要素をそれぞれ 1 つ以上含む。各工程を通り、記事が完成する。
- **AC-15**: どの種類の記事でも、完成した記事のタイトルは決まった印で始まる。印の文字列は設計で決め、`development.md` に書く。
- **AC-16**: fake の応答のモデル名は、`internal/pricing` の単価の表にない決まった値である。完成した記事の料金は、工程ごとにも合計でも不明として示される。単価の表は変えない。

#### F-004: 失敗と遅れ

fake は、選んだ工程で選んだ種類の失敗を返し、指定した遅れの後に応答する。

**Acceptance Criteria**:
- **AC-17**: 失敗の種類（空の応答、出力の打ち切り、API のエラー、タイムアウト）と、失敗させる工程（生成、字数の調整、検証・推敲）を組み合わせて選べる。字数の調整の工程で失敗させる指定は、字数の調整が動く記事（長い記事）とだけ組み合わせられる。それ以外の記事との組み合わせは AC-09 で拒否する。
- **AC-18**: 失敗の種類ごとに、状態の取得が返す失敗の理由のコードは、空の応答で `llm_empty`、出力の打ち切りで `llm_truncated`、API のエラーで `llm_failed`、タイムアウトで `llm_timeout` になる（`internal/server/status.go:233-252`）。失敗の工程は、選んだ工程として示される（`internal/server/generation.go:150-156`）。
- **AC-19**: 失敗させる工程より前の工程は成功し、その工程で失敗した記事は完成した記事として返されない（CLAUDE.md「Empty is an error」）。
- **AC-20**: 遅れを指定すると、fake は LLM の呼び出しのたびに、応答（成功も失敗も）の前にその長さだけ待つ。待っている間にサーバが停止を始めた場合など、呼び出しの文脈が取り消されたときは、待ち終わるのを待たずに戻る。

#### F-005: Webhook への投稿に対応しない

**Acceptance Criteria**:
- **AC-21**: 開発用のサーバは Webhook へのリクエストを一切送らない。投稿の操作は、本番のサーバに Webhook の URL を設定していないときと同じく `webhook_not_configured` で拒否される（`internal/server/response.go:57`）。

#### F-006: 本番のバイナリとの分離とビルド

**Acceptance Criteria**:
- **AC-22**: 本番の 3 つのバイナリ（`cmd/yt2column`・`cmd/yt2column-server`・`cmd/yt2column-nmhost`）の依存に、fake の部品も開発用のサーバのパッケージも含まれない。
- **AC-23**: 本番の 3 つのバイナリのいずれかが fake の部品に依存するように変えると、`make test` か `make lint` が失敗する。
- **AC-24**: `make build` は今までどおり本番の 3 つのバイナリだけを作り、開発用のバイナリを作らない。開発用のバイナリは別の `make` のターゲットで作る。
- **AC-25**: fake の部品の決まった記事と応答は、生成の後の 2 つの工程の検証を通る。シナリオごとに、記事が完成するか、選んだ工程で選んだ失敗になるかを、実際の LLM を呼ばずに確かめるテストが `make test` で走る。

#### F-007: 文書

**Acceptance Criteria**:
- **AC-26**: `docs/dev/security.md` §8.2 に、開発用のサーバの規則がある。本番のバイナリに fake を入れないこと、開発用のサーバは設定ファイルも API キーも読まず Webhook へ送らないこと、本番のサーバと同じソケットのパスとロックを使うこと、開発用のバイナリを常用の環境に置かないこと、残余のリスク（§4.2）である。
- **AC-27**: `docs/dev/guides/development.md` に、開発用のバイナリの作り方、起動のしかた（シナリオ・遅れの引数と受理する値、タイトルの印）、本番のサーバと同時には動かせないこと、拡張から確かめる手順がある。
- **AC-28**: `docs/dev/project_overview.md` の想定ディレクトリ構成、`docs/dev/conventions/package_reference.md` のパッケージの表、`CLAUDE.md` の「Build Commands」に、追加した部品・バイナリ・`make` のターゲットがある。
- **AC-29**: ADR-0044 と ADR の索引の行がある。ADR-0044 の決定は、本書の決定（本番のバイナリに fake を入れない、fake はサーバに依存しない部品、開発用のサーバは設定ファイルを読まず投稿に対応しない、シナリオは起動のときの引数、単価の表に fake を入れない）と一致する。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   遅れを指定しない場合、fake の LLM の呼び出しは待たずに戻る。手での確認とテストで、生成の完了を待つ時間をなくすためである。

### 4.2. セキュリティ (Security)

`docs/dev/security.md` を適用する（条件付きのガイドの条件のうち、API キーと Webhook URL の扱い、ネットワークへの送信、公開する記事に埋め込むテキストに関わる）。

-   **本番のバイナリに fake を入れない（AC-22・AC-23）。** 設定の誤りで fake の記事が本番の利用者の前に出たり Webhook に投稿されたりすることを、構成で防ぐ。
-   **秘密を扱わない（AC-06・AC-07・AC-21）。** 開発用のサーバは API キーも Webhook URL も読まず、LLM の API にも Webhook にも送らない。秘密を出力に流す経路がない。
-   **受け取る入力の境界は本番のサーバと同じ。** 開発用のサーバは `internal/server` を使うので、拡張からのリクエストの検査（`security.md` §8.2「受け取る入力の境界」）は本番のサーバと同じである。コピーした字幕は本番と同じく検査し、fake はその中身を記事に使わない。
-   **fake の記事は、決まった文面である。** 字幕と動画メタデータを記事に埋め込まないので、プロンプトインジェクションの経路を新しく作らない。ただし、ビューアに渡す記事は本番と同じく untrusted なテキストとして扱われる（§8.1）。
-   **残余のリスク（許容する）。** 開発用のサーバは本番のサーバと同じソケットのパスで待ち受けるので、利用者が本番のサーバの代わりに開発用のサーバを起動すると、拡張は fake の記事を表示する。タイトルの印（AC-15）、起動の行（AC-10）、料金の不明（AC-16）で気づけるようにし、`security.md` で開発用のバイナリを常用の環境に置かないことを求める。同一ユーザーの信頼の範囲（[ADR-0006](../../dev/adr/0006-threat-model.md)）に含める。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   開発用のサーバの停止（シグナル、処理中のジョブの扱い）は本番のサーバと同じである。遅れの間に停止を始めた場合は、AC-20 のとおり待ち終わるのを待たずに戻る。

### 4.4. 互換性 (Compatibility)

-   拡張・ホスト・本番のサーバの振る舞いと API は変えない。
-   本番のサーバと同じく、macOS と Linux で動く。

### 4.5. 保守性 (Maintainability)

-   fake の部品は、サーバの撤去（#773）の後も、移行の後の開発用のビルドで使える（AC-02・AC-03）。
-   記事の種類・失敗の種類・工程を足すときは、列挙値に値を足す。呼び出し側の文字列の中身から推測する分岐を作らない（AC-04）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   外部のライブラリを加えない（CLAUDE.md「Dependencies」）。
-   本番の設定の読み込み（`internal/config`、[ADR-0003](../../dev/adr/0003-llm-config-contract.md)・[ADR-0018](../../dev/adr/0018-server-config-file.md)）に fake のプロバイダを加えない。
-   [ADR-0024](../../dev/adr/0024-env-access-in-config.md) の、環境変数を読む場所を限る規則に従う。

## 6. 用語集 (Glossary)

-   **fake の LLM**: `LLMClient` を満たし、実際の LLM を呼ばずに決まった応答を返す部品。単体テスト用の fake（`internal/llm/testutil`）とは別のもの。
-   **開発用のサーバ**: fake の LLM を使い、`internal/server` で待ち受ける開発用のバイナリ。本番のサーバ（`yt2column-server`）とは別に作る。
-   **シナリオ**: 開発用のサーバの起動のときに選ぶ、fake の振る舞い（記事の種類、失敗の種類と工程）。遅れは別の引数で指定する。
-   **工程**: 生成・字数の調整・検証・推敲の 3 つ（`docs/dev/project_overview.md`「パイプライン」）。
-   用語は `docs/translation_glossary.md` と統一する。
