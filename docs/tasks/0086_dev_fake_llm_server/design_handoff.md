# 設計への申し送り（0086）

要件定義の段階で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目について採った方法か、当てはまらない理由を記録する。

## H-01: fake がジョブと工程を区別する手段

**懸念:** 本番のサーバは、生成のクライアント（生成と字数の調整が共有する）と検証・推敲のクライアントを起動のときに 1 つずつ作り、すべてのジョブで共有する（`cmd/yt2column-server/run.go:323-335`）。生成のジョブは同時に 2 つまで動く（`internal/server/jobs_api.go:15`）。AC-04 は、ジョブごとに独立した振る舞いを求め、プロンプトの中身から工程を推測することを禁じる（CLAUDE.md「Declare, don't infer」）。本番のサーバと `LLMClient` の契約は変えない（§4.4）。

**理由:** 共有のクライアントで呼び出しの順序を数えると、同時に動くジョブや前のジョブの呼び出しが混ざり、選んだ工程で失敗させられない。

**候補:** 開発用のサーバが `internal/server` に渡す `ArticleWriter` を包みにし、`Write` のたびに新しい fake のクライアント（生成用と検証・推敲用）と `writer` を作る。1 つのジョブの中では、生成用のクライアントの 1 回目が生成、2 回目が字数の調整になり、順序が決まる。

**関係:** F-001、AC-04、AC-13、AC-17、AC-18

## H-02: 本番のバイナリから fake を締め出す検査の手段

**懸念:** AC-21・AC-22 と AC-02・AC-03 を何で確かめるか。`depguard` の規則、ビルドタグ、`go list -deps` を使うテストが候補である。fake は `GOOS=js GOARCH=wasm` でビルドできる必要があり（AC-03）、移行の後の開発用のビルドから使える必要がある。ビルドタグ `test` は単体テスト用の fake に使っているので、同じタグにはできない。AC-03 の検査の範囲は fake の構成要素とその依存に限る（0084 の例外の範囲）。fake が `internal/writer` や `internal/transcript` に依存すると、それらも検査の範囲に入り、0084 が検査しないと決めたコアに例外が広がる。依存させないか、広がることを設計で明記する。

**理由:** 検査の手段によって、移行の後に WASM の開発用のビルドから fake を使えるかが変わる。

**候補:** `depguard` で、本番の 3 つの `cmd/` から fake のパッケージへの import を禁じる。あるいは、3 つのバイナリの `go list -deps` に fake のパッケージがないことを確かめるテストを `make test` に置く。間接的な依存も捉えられるのは後者である。

**関係:** F-001、F-005、AC-02、AC-03、AC-21、AC-22

## H-03: 開発用のサーバの入口と本番のサーバの共有

**懸念:** 開発用のサーバは、ソケット・ロック・シグナル・ログの伏せ字など、`cmd/yt2column-server/run.go` の起動の手順の大半を本番と共有する。本番の `cmd/yt2column-server` は `package main` なので、別のバイナリから直接は使えない。共有する部分を `internal/` に移すか、開発用のサーバで書き直すかを決める。移す場合も、本番のバイナリの依存に fake が入らないこと（AC-21）を保つ。

**理由:** 書き直すと、起動の検査（ソケットのディレクトリ、ロック、stale の判定）が本番と食い違いうる（AC-11）。

**関係:** F-002、AC-05、AC-11、AC-21

## H-04: ADR-0024 の入口の一覧

**懸念:** [ADR-0024](../../dev/adr/0024-env-access-in-config.md) は、プロセスの環境を読める入口を決めてテストで固定している。開発用のサーバの `main` は新しい入口で `HOME` を読み、`GODEBUG` を読まない（AC-07）。検査の一覧に加えるか、`internal/config` のどの関数で `HOME` を読むかを決め、要れば ADR-0024 の経緯を更新する。

**関係:** F-002、AC-07

## H-05: 名前と引数の形

**懸念:** fake の構成要素のパッケージ名と置き場所（`testutil/` の下には置かない。AC-28）、開発用のバイナリと `cmd/` の名前、`make` のターゲットの名前と成果物の場所、引数の名前と値の綴り、タイトルの印の文字列、fake のモデル名を決める。標準ライブラリの `flag` を使う場合は、次の扱いが AC-08・AC-09 と食い違わないようにする。最初の位置引数で解析を止めて残りを黙って残すこと、`-h`・`-help` を特別に扱うこと、同じフラグを繰り返すと後の値が勝つことである。

**関係:** F-002、F-003、F-004、F-005、AC-08、AC-09、AC-15、AC-16、AC-23

## H-06: 決まった記事の文面と検証・推敲の応答

**懸念:** 3 つの記事の文面と、字数の調整・検証・推敲の工程が返す応答を、生成の後の工程の検証を通る形で作る（AC-24）。検証・推敲の応答は直す箇所の一覧であり（[ADR-0002](../../dev/adr/0002-post-generation-steps.md)）、空の一覧にするか、記事に当てはまる直しを含めるかを決める。文面は、実在の動画や人物の内容を含まない作文にする（`docs/dev/security.md` §7）。要素を網羅した記事が含む要素の一覧は、0063 の規則が変わると古くなるので、テストでの確かめ方を決める。

**関係:** F-003、AC-12、AC-13、AC-14、AC-24
