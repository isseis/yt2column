# 設計への申し送り：パイプラインの中間生成物の保存と再開

本書は、[01_requirements.md](01_requirements.md) のレビューで挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 保存の形式

-   **事項:** 中間生成物のファイルの形式を決める。次を含む。
    -   ファイルの名前と配置（動画 ID と段階の名前からどう決めるか）。
    -   表現の構文。記事（タイトルと本文）、検証・推敲の一覧（`Revision` の `Before`・`Action`・`After`・`Reason`・`Evidence`）、来歴（段階・モデル名・ModelVersion・テンプレートの識別子・入力の識別子）をどう表すか。
    -   入力の識別子と、テンプレートの識別子の作り方（ハッシュの種類と対象。末尾の改行や BOM の扱い）。
    -   応答全体と要素の数の上限の値。
-   **理由:** 保存と再開の両方が同じ定義を読み、形式が決まらなければ、実装もテストもできない（要件定義書 F-001・F-004・§4.5）。
-   **候補の方針:** JSON で表し、`internal/strictjson` を再利用する。`encoding/json` が黙って修復する入力（不正な UTF-8・対になっていないサロゲート）と、宣言していない要素・重複した要素・末尾の内容を拒否する。記事のタイトルと本文は保存した値も生成テキストの検証（0004 の F-005・§3.2）を通す。テンプレートの識別子は、既定の埋め込みか上書きファイルかと、その内容から作る。
-   **関連:** F-001、F-004、AC-01・AC-02・AC-20・AC-23

## H-02: 保存・読み込みの置き場所と `Article` の契約

-   **事項:** 保存と読み込みをどのパッケージが担うか、段階の出力をどう保持するかを決める。次を含む。
    -   `writer.ArticleWriter` の `Write` の中で保存するか、`internal/job`・`internal/pipeline` が段階の出力を受け取って保存するか。再開の入力（保存した生成の出力など）をどの型で `ArticleWriter` に渡すか。
    -   中間生成物を保持するために `writer.Article` の exported フィールドの集合を変えるなら、その形。`internal/pipeline` の guard（`TestCommonTypesFieldSets`）を同じ変更で更新する。
    -   再開のとき、どの段階を実行し、どの段階を読み込みで置き換えるかを、`writer.Options` でどう表すか。
-   **理由:** 現在 `Article` は最終の記事と段階ごとのモデル名しか持たず、字数の調整の前・後の文面を持たない。段階の出力を保存・再利用するには、契約の変更が要る（要件定義書 §4.5・AC-01・AC-12〜AC-14）。
-   **関連:** F-001、F-003、AC-01・AC-04・AC-12〜AC-14

## H-03: 保存の完了と公開の順序、中断への強さ

-   **事項:** 中間生成物の書き込みの方法を決める。次を含む。
    -   段階ごとに、その場で書くか、一時ファイルに書いて置き換えるか。
    -   公開（`--out`・`--slack`）との順序。保存の失敗を公開の前に検出するか。
    -   中断（電源断を含む）で残り得る状態と、それを次の再開が拒否できること。`docs/dev/cache_consistency.md` の規則をどこまで中間生成物に適用するか。
-   **理由:** 保存の失敗と、中断で壊れた中間生成物を、記事の失敗として扱い、次の再開が部分受理しないようにする必要がある（要件定義書 F-004・§4.3・AC-06・AC-20・AC-29）。
-   **関連:** F-001、F-004、§4.3、AC-04・AC-06・AC-20

## H-04: 再開のときの設定の読み込み

-   **事項:** 実行する段階に応じて、どの設定を必須にし、どれを検査しないかを決める。次を含む。
    -   `internal/config` が実行する段階を知る方法（`--after` の値をどう渡すか）。
    -   生成を実行しないときの `YT2COLUMN_MODEL`・生成のプロバイダの API キー・生成のテンプレートの扱い（必須にしない。設定されていても検査しない、またはエラーにする）。
    -   字数の調整は生成の `LLMClient` を使うので、`--after generation` では字数の調整が走るかどうか（本文の長さ）が実行時まで分からない。設定の読み込みの時点では、`--no-shorten` の有無だけで生成のモデルと API キーの要否を決める（要件定義書 AC-15）。
    -   検証・推敲を実行するときに必須になる設定。
-   **理由:** 要件定義書 F-003・AC-15 が、再開した段階より前の設定を必須にしないと定めている。既存の設定の規則（0009 の F-006、`project_overview.md` の設定の表）との整合を決める必要がある。
-   **関連:** F-003、AC-15

## H-05: 不正な入力の検出方法と上限の値

-   **事項:** 中間生成物の読み込みで、標準ライブラリが黙って修復・破棄・無視する入力をどう見つけて拒否するかを決める。次を含む。
    -   `internal/strictjson` を再利用する範囲と、足す必要のある検査（宣言した要素以外の拒否、重複した要素の拒否、末尾の内容の拒否、`null` と他の種類の拒否）。
    -   上限の値（応答全体の大きさ、記事の長さ、一覧の項目の数）と、超えた場合の番兵エラー。
    -   読み込むファイルの種別の検査（通常のファイルか、シンボリックリンクでないか）と、大きさの上限。
-   **理由:** 中間生成物は信頼できない入力であり、`requirements_process.md` の「Untrusted input boundaries」に従って、受理する形・上限・拒否の番兵を実装とテストで確かめる必要がある（要件定義書 §3.2・AC-20・AC-23）。
-   **関連:** F-004、§3.2、AC-20・AC-23

## H-06: フラグの組み合わせの規則

-   **事項:** `--artifacts`・`--after` と既存のフラグの組み合わせの扱いを決める。次を含む。
    -   `--no-shorten`・`--no-review` を再開と同時に指定したときの扱い（許すか、拒否するか。`--after review` は検証・推敲を実行しないので、`--no-review` と同じ結果になる）。
    -   上書きテンプレート（`--shorten-system-prompt` など）を、その段階を実行しない再開と同時に指定したときの扱い。
    -   `--after` の値の検証（受理する値、拒否した値をエラーのメッセージに出すか）。
    -   当初案の `--article`・`--review-only` を新たに設けないことの確認。
-   **理由:** 要件定義書 F-005 が、生成でしか使わない指定の拒否と、`--after review` と `--review-log` の組み合わせだけを定めている。残りの組み合わせの規則を設計で決める（`writer.New` の `validateStepOptions` の方針にそろえる）。
-   **関連:** F-005、AC-16・AC-24〜AC-28

## H-07: `--out` の出力の来歴

-   **事項:** `--out` の出力に、再利用した段階のモデル名と ModelVersion をどう書くかを決める。次を含む。
    -   既存のモデルの行（`--out` の先頭）の書式との整合。生成のモデル名を、保存した生成の出力の来歴から書くか、実行した段階だけを書くか。
    -   再利用した段階の ModelVersion が空のときの表示（既存の `orNone` と同じ扱いにするか）。
-   **理由:** 要件定義書 AC-27 が、再利用した段階の来歴を出力に含めると定めている。既存の `--out` の書式（0010 の F-005・AC-22）との整合を決める必要がある。
-   **関連:** F-005、AC-27

## H-08: 検証・推敲の一覧の保存と `--review-log` の関係

-   **事項:** 検証・推敲の一覧の中間生成物と、`--review-log` の Markdown の関係を決める。次を含む。
    -   一覧の中間生成物の形式（H-01）と、`--review-log` の出力（0010 の AC-20）が、同じ値から作られること。
    -   再開（`--after shorten`）で検証・推敲を実行したとき、`--review-log` を指定すれば新しい一覧を書き出せること。
-   **理由:** 要件定義書 AC-07 が、`--review-log` を再利用の入力にしないと定めている。一覧を二重に持たず、用途（再利用と表示）ごとに作る必要がある。
-   **関連:** F-001、AC-07・AC-16

## H-09: 評価の手順の更新

-   **事項:** この仕組みで評価を切り替えるときの、`0010_post_generation_review/02_evaluation.md` §2 の手順の更新を決める。次を含む。
    -   生成を 1 回だけ行って中間生成物を保存し、同じ生成の出力に別の字数の調整・検証・推敲を当てるコマンドの形。
    -   段階の呼び出し回数と料金の記録の方法（再開では呼ばない段階があること）。
    -   評価の最初の実行に `--keep-cache` を付けること（成功した実行の後にキャッシュが削除され、取り直した字幕が変わると再開が AC-21 で拒否されるため。要件定義書 AC-17）。
-   **理由:** 要件定義書 AC-34 が、手順の更新だけを本タスクに含めている。実際の評価の再実行と §3 の記録の更新は別に行う。
-   **関連:** F-008、AC-34

## H-10: 保存を既定で行うか

-   **事項:** 中間生成物の保存を既定で行うか、`--artifacts` で有効にするかを、レビューで確認する。要件定義書 F-002 は、記事の本文と素材に由来する値がディスクに残ることを理由に、既定では保存しないとした。保存先を `--artifacts` の外（既定の保存先）に持つ案や、保存を常に行う案を採る場合は、要件定義書の変更として扱う。
-   **関連:** F-002

## H-11: 古い中間生成物の扱い

-   **事項:** 同じ動画 ID で生成からやり直した実行で、後の段階（字数の調整・検証・推敲）が走らなかった場合に、前の実行の後の段階の中間生成物が残る（AC-03・AC-10）。これを次のどちらで扱うかを決める。
    -   ある段階を保存するときに、同じ動画 ID の後の段階の中間生成物を削除する。
    -   再開のときに、使う中間生成物から生成の出力まで入力の識別子を順にたどり、途中が食い違えば拒否する。
-   **理由:** `--after review` の適用後の記事が、古い字数の調整の出力（自身の古い生成の出力とは整合する）を指していると、直前の照合だけでは新しい生成の出力との食い違いを見つけられず、`--out` の来歴（AC-27）も実際とずれる（要件定義書 F-004・AC-21）。
-   **関連:** F-001、F-004、AC-03・AC-10・AC-21
