## 1. 概要 (Overview)

**目的:** 本書は、パイプラインの中間生成物（生成の出力、字数の調整の出力、検証・推敲の一覧と適用後の記事）を保存し、保存したどの段階からでも再開して、その後の段階だけを実行できるようにするための要件を定義する。

**背景:**
現在の CLI は、記事を生成して公開するだけで、途中の段階の生成物を残さない（`--review-log` は変更点を表示するだけで、再利用の入力にはならない）。そのため、次の 2 つの問題がある（[#213](https://github.com/isseis/yt2column/issues/213)）。

-   **評価で段階の効果を切り分けられない。** タスク `0010_post_generation_review` の評価（[02_evaluation.md](../0010_post_generation_review/02_evaluation.md) §3.6・§3.7）では、実行 A（検証・推敲が `claude-sonnet-5-5`）と実行 B（検証・推敲が `claude-opus-5-5`）を、どちらも生成からやり直して比べている。生成の文面が実行ごとに変わるため（DeepSeek の非決定性）、差が「検証・推敲のモデルの差」なのか「生成のばらつき」なのか切り分けられない。同書 §3.5 も「§3.1〜§3.3 と同じ記事を検証・推敲し直したのではなく、生成からやり直した」と断っている。
-   **どの段階が記述を落としたか確かめられない。** 同書 §3.7 の `roNZ-rLxhUE` では、最も重要な論点が記事から欠けていた。この実行では字数の調整が走ったが、CLI は字数の調整の前後の文面を保存しないので、生成で落ちたのか、字数の調整が落としたのかを区別できなかった（同書 §4.2）。生成済みの記事を固定するだけでは、この 2 つは切り分けられない。

そこで、原則としてパイプラインのすべての中間生成物を保存し、保存したどの段階からでも再開して、その後の段階だけを実行できるようにする。字幕と info.json は、すでにキャッシュとして保存・再利用されている（タスク `0002_ytdlp_transcript_source`）。

対応 issue: #213。関連: #145（0010）、PR [#217](https://github.com/isseis/yt2column/pull/217)、#186（同じ内容の変更を返す項目）、#185（誤認識の写し）。

要件レビューの過程で挙がった、設計で決める事項は [design_handoff.md](design_handoff.md) に申し送る。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   生成の出力（字数の調整の前の記事）、字数の調整の出力（検証・推敲の前の記事）、検証・推敲の一覧（適用の前）と適用後の記事を、保存できるようにする（F-001・F-002）。
-   各中間生成物に、生成したモデル名と ModelVersion、使ったテンプレート、入力の識別子を付け、どの実行から来たものかを後から確かめられるようにする（F-001）。
-   保存したどの段階からでも再開し、その後の段階だけを実行できるようにする。再開した段階より前の LLM は呼ばない（F-003）。
-   再開した段階より前の設定（`YT2COLUMN_MODEL` など）を、実行の必須条件から外す（F-003）。
-   再開の入力の中間生成物を検証し、壊れた入力・空の入力・入力が食い違う入力を拒否する（F-004）。
-   既存の最終字数の確認（0010 の F-001 の 4）を再開した実行にも適用する。検証・推敲を実行する再開（`--after generation`・`--after shorten`）では、検証・推敲の一覧（`--review-log`）も適用し、`--after review` では `--review-log` を受け付けない（F-003・AC-16）。
-   当初案の `--article <path>`（既存の記事ファイルを入力にする）と `--review-only`（生成をスキップする）を、この一般化の一部として置き換える（F-005）。
-   評価で、同じ生成の出力に別の字数の調整を当てる、同じ字数の調整の出力に別の検証・推敲を当てることができるようにする（F-008）。

### 2.2. スコープ (In Scope)

-   中間生成物の保存（保存する値、付ける来歴、保存の有効化と保存先）（F-001・F-002）。
-   保存した中間生成物からの再開（再開する段階の指定、実行する段階、設定の要否）（F-003）。
-   再開の入力の中間生成物の検証（F-004）。
-   CLI のフラグと出力（`--artifacts`・`--after`、既存フラグとの組み合わせ、`--out` の出力）（F-005）。
-   保存・読み込みの失敗の報告（F-006）。
-   ユニットテスト（F-007）。
-   文書（README・`project_overview.md`・`security.md`）と評価の手順の更新（F-008）。

### 2.3. スコープ外 (Out of Scope)

-   パイプラインの各段階（生成・字数の調整・検証・推敲）のプロンプト・モデル・振る舞いの変更（タスク 0010。本タスクは、0010 が定めた段階の入出力を保存・再利用するだけである）。
-   0010 の F-005（CLI のフラグ）のうち、`--no-shorten`・`--no-review`・`--review-log`・上書きテンプレートの既存の振る舞いの変更。本タスクは、0010 の F-005 に `--artifacts`・`--after` を加え、その組み合わせの規則を定める（要件定義書からの変更として、本書で扱う）。
-   中間生成物の自動削除・保存数の制限・世代管理。保存した中間生成物は、利用者が削除するまで残す（保存先は利用者が指定する）。
-   字幕・info.json の保存形式とキャッシュの変更。既存のキャッシュをそのまま使う。
-   検証・推敲の一覧の各項目の判定（0010 の F-008）。`--review-log` の Markdown の書式（0010 の AC-20）。
-   評価の再実行と `02_evaluation.md` の記録の更新。本タスクは、この仕組みで評価できるようにするだけであり、実際の評価は別に行う（F-008）。
-   ブラウザ拡張・localhost サーバ（#104・#109）。本タスクは CLI と `internal/` のパッケージだけを対象とする。
-   #186（同じ内容の変更を返す項目）・#185（誤認識の写し）への対処。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 保存する中間生成物と来歴

パイプラインは、次の 3 つの段階の出力を中間生成物として保存する。記事の中間生成物はタイトルと本文（出典のブロックを含まない、検証済みの生成テキストの形）とする。

-   **生成の出力:** 字数の調整の前の記事（タイトルと本文）。
-   **字数の調整の出力:** 検証・推敲の前の記事（タイトルと本文）。字数の調整が走ったときだけ存在する。
-   **検証・推敲の出力:** 適用の前の、修正の一覧そのもの（`writer.ReviewResult` の `Revisions`）と、適用した後の記事（タイトルと本文）。検証・推敲が走ったときだけ存在する。

各中間生成物は、次の来歴を記録する。これにより、保存した中間生成物がどの実行のどの入力から来たものかを、後から確かめられる。

-   段階の名前（生成・字数の調整・検証・推敲）。
-   生成したモデル名と ModelVersion（プロバイダが版を返さない場合は空）。
-   その段階が使ったテンプレートの識別子（system と user のテンプレート。既定の埋め込みか上書きファイルか、その内容）。
-   入力の識別子（その段階が消費した入力。生成では字幕とメタ情報、字数の調整では生成の出力、検証・推敲では検証の対象の記事と素材）。

`--review-log` が書き出す Markdown は、変更点を人が読むための表示であり、再利用の入力には使わない。検証・推敲の一覧は、再利用と検査に使える別の形式で保存する。

**Acceptance Criteria**:
- **AC-01**: `--artifacts <dir>` を付けた実行で生成・字数の調整・検証・推敲がすべて走ったとき、保存される中間生成物は、生成の出力・字数の調整の出力・検証・推敲の一覧・適用後の記事の 4 つである。生成の出力のタイトルと本文は、字数の調整の前の記事（生成の LLM の応答を検証した値）と一致する。字数の調整の出力のタイトルと本文は、検証・推敲の前の記事と一致する。適用後の記事のタイトルと本文は、公開した記事のものと一致する。検証・推敲の一覧は、適用に使った一覧と一致する。
- **AC-02**: 各中間生成物は、段階の名前と、モデル名・ModelVersion と、使ったテンプレートの識別子と、入力の識別子を記録する。生成の出力のモデル名と ModelVersion は生成の LLM の応答の値と、字数の調整の出力のそれは字数の調整の応答の値と、検証・推敲の一覧のそれは検証・推敲の応答の値とそれぞれ一致する（プロバイダが版を返さない場合は空である）。
- **AC-03**: 字数の調整が走らなかった実行では、字数の調整の出力を保存しない。検証・推敲が走らなかった実行では、検証・推敲の一覧と適用後の記事を保存しない。保存される中間生成物は、その実行で実際に走った段階のものだけである。
- **AC-04**: 各中間生成物は、その段階が完了した時点で保存される。後の段階が失敗して実行が記事を公開しなかった場合も、それより前の段階の中間生成物は保存される（生成と字数の調整の出力を、検証・推敲の失敗の後も確かめられる）。
- **AC-05**: `--artifacts` を付けない実行では、中間生成物を保存しない。
- **AC-06**: 中間生成物の保存に失敗した場合、実行はエラーで終わる。エラーから、失敗した段階が分かる。記事を公開しない。
- **AC-07**: 検証・推敲の一覧は、`--review-log` のファイルとは別に、再利用の入力になる形式で保存される。`--review-log` のファイルがあってもなくても、再開はその保存された一覧（F-003 では適用後の記事）を使い、`--review-log` のファイルを読み取りの入力にはしない。

#### F-002: 保存の指定と保存先

中間生成物の保存は、既定では行わない。`--artifacts <dir>` を指定したときだけ行う。理由は次のとおり。

-   中間生成物には記事の本文が入る。既定で保存すると、本番の実行のたびに、公開の有無にかかわらず記事と素材に由来する値（検証・推敲の一覧の根拠の引用）がディスクに残る。
-   保存先は実行ごとに利用者が選べる必要がある（評価では実行のたびに固定した中間生成物を使う）。

保存先は、キャッシュディレクトリの外とする（`--out`・`--review-log` と同じ規則）。キャッシュディレクトリの字幕と info.json は投稿の成功後に既定で削除されるので（[project_overview.md](../../dev/project_overview.md) の「前提・制約」）、その中に置くと中間生成物が消えるためである。

**Acceptance Criteria**:
- **AC-08**: `--artifacts <dir>` の dir がキャッシュディレクトリの中にある場合、CLI は yt-dlp と LLM を呼ぶ前に、使い方の誤りとしてエラーで終わる。
- **AC-09**: `--artifacts <dir>` の dir が存在しない場合、または使えない場合（ディレクトリでない、シンボリックリンクであるなど）、CLI は yt-dlp と LLM を呼ぶ前に、実行の失敗としてエラーで終わる（AC-30）。
- **AC-10**: 中間生成物は、動画 ID と段階の名前から決まる固定の名前で保存される。同じ動画 ID・同じ段階の保存は、前の実行のものを置き換える。動画 ID は検証済みのもの（`transcript` の検証を通ったもの）だけを使い、保存先のディレクトリの任意の名前を信用しない。
- **AC-11**: 中間生成物のファイルは、キャッシュと同じく所有者だけが読める権限（`0o600`）で作り、シンボリックリンクを辿らない。`--artifacts` のディレクトリは利用者が用意したものを使い、CLI は作らない（AC-09）。

#### F-003: 保存した中間生成物からの再開

`--after <stage>` を指定すると、`--artifacts <dir>` に保存された `<stage>` の出力を再利用し、その後の段階だけを実行する。`<stage>` は `generation`・`shorten`・`review` のいずれかとする。

-   `--after generation`: 保存された生成の出力を、字数の調整の前の記事として使う。字数の調整（本文が上限を超えるときだけ）・検証・推敲・最終の字数の確認・公開を行う。
-   `--after shorten`: 保存された字数の調整の出力を、検証・推敲の前の記事として使う。検証・推敲・最終の字数の確認・公開を行う。
-   `--after review`: 保存された適用後の記事を使って、最終の字数の確認と公開だけを行う。LLM を呼ばない。

再開した段階より前の LLM は呼ばない。再開で実行する段階が使うプロバイダの設定だけを検査し、それより前の段階の設定は必須にしない。字数の調整は生成の `LLMClient` を使う（0010 の F-001）ので、字数の調整を実行し得る `--after generation`（`--no-shorten` を指定しない場合）では、`YT2COLUMN_MODEL` と生成のプロバイダの API キーを必須とする。`--after shorten` では生成のモデルと API キーを必須にせず、`--after review` では LLM の設定を必須にしない。

再開した実行も、通常の実行と同じ規則で、字幕の取得・キャッシュ（必要なら yt-dlp の呼び出し）と最終の字数の確認を行う。検証・推敲を実行する再開（`--after generation`・`--after shorten`）では、検証・推敲の一覧（`--review-log`）も行う。`--after review` では検証・推敲を実行せず、`--review-log` を受け付けない（AC-16）。再開で実行した段階の出力も、`--artifacts` に保存する。

**Acceptance Criteria**:
- **AC-12**: `--after generation --artifacts <dir>` で、生成の LLM を呼ばず、保存された生成の出力をタイトルと本文として用い、本文が上限を超えていれば字数の調整を行い、検証・推敲を行い、最終の字数の確認を行い、公開する。生成の LLM の応答は使わない。
- **AC-13**: `--after shorten --artifacts <dir>` で、生成と字数の調整の LLM を呼ばず、保存された字数の調整の出力を検証・推敲し、最終の字数の確認を行い、公開する。
- **AC-14**: `--after review --artifacts <dir>` で、LLM を 1 つも呼ばず、保存された適用後の記事の最終の字数の確認を行い、公開する。
- **AC-15**: 生成の `LLMClient` を使う段階（生成・字数の調整）を実行しない再開（`--after shorten`・`--after review`、および `--no-shorten` を付けた `--after generation`）では、`YT2COLUMN_MODEL` が未設定でも設定の読み込みがエラーにならず、生成に使うプロバイダの API キー（`DEEPSEEK_API_KEY`・`ANTHROPIC_API_KEY` のうち生成のプロバイダのもの）が未設定でもエラーにならない。字数の調整を実行し得る `--after generation` では、生成のモデルと API キーを通常の実行と同じく検査する。実行する段階が使うプロバイダの設定だけを検査する（検証・推敲を実行するときは、そのプロバイダの設定を検査する）。
- **AC-16**: 再開した実行でも、最終の字数の確認と検証・推敲の一覧（`--review-log`）を、通常の実行と同じ規則で行う。検証・推敲を実行する再開（`--after generation`・`--after shorten`）では `--review-log` を使える。検証・推敲を実行しない `--after review` では `--review-log` を使えず、指定すると使い方の誤りとしてエラーで終わる。
- **AC-17**: どの段階から再開しても、字幕の取得・キャッシュは通常どおり行う。キャッシュの字幕と info.json が無ければ yt-dlp を呼び、エラーになった場合は再開を実行しない。成功した実行の後はキャッシュが既定で削除されるので（`--keep-cache` を付けない場合）、再開は字幕を取り直す。取り直した素材が保存時と異なれば、AC-21 で拒否する。
- **AC-18**: 再開した実行が走らせた段階の出力は、`--artifacts` に保存される（F-001 の規則に従う）。したがって、再開の実行を続けて行うことで、同じ動画の別の段階の組み合わせを保存できる。

#### F-004: 再開の入力の中間生成物の検証

再開の入力の中間生成物は、信頼できない入力として扱う（検証・推敲の応答から作られ、ディスクを経由して戻ってくるため）。規則に合わない入力は受理せず、部分受理もしない（[CLAUDE.md](../../../CLAUDE.md)「Empty is an error」「Reject, don't normalize」）。

-   指定した段階の中間生成物が無い場合は、エラーとする。
-   中間生成物が空、または壊れている場合は、エラーとする。
-   中間生成物の入力の識別子が、いまの入力（動画 ID・素材・前段の中間生成物）と一致しない場合は、エラーとする（別の実行の中間生成物を、別の素材や別の前段の出力に当てないため）。前段の照合は、その段階が実際に消費した中間生成物まで、生成の出力から順にたどって行う。後の段階が走らなかった実行（AC-03）は前の実行の後の段階の中間生成物を置き換えないので、古い実行の中間生成物が新しい生成の出力と混ざった状態を受理しない（[design_handoff.md](design_handoff.md) H-11）。
-   中間生成物の大きさと要素の数には、有限の上限を設ける。記事のタイトルと本文には生成テキストの上限を、検証・推敲の一覧には検証・推敲の応答の上限を再利用し、超える入力を拒否する。ファイル全体の大きさの上限は設計で定める。
-   再開で使うタイトルと本文は、生成テキストの検証（タスク `0004_article_writer` の F-005 と §3.2）を通す。ただし、生成テキストの検証が本文の先頭の U+FEFF を 1 個除去するのに対し、再利用の境界では正規化せず、先頭の U+FEFF を拒否する。規則に反する場合はエラーとする。
-   標準ライブラリが黙って修復・破棄・無視する入力（不正な UTF-8、対になっていないサロゲート、末尾に続く内容、未知の要素、重複した要素）は、受理せず拒否する。

**Acceptance Criteria**:
- **AC-19**: 指定した段階の中間生成物が `--artifacts` に無い場合、`errors.Is` で判定できる番兵エラーを返し、LLM を呼ばず、記事を公開しない。
- **AC-20**: 中間生成物が、空である、UTF-8 として不正である、本文の先頭に U+FEFF がある、タイトルまたは本文が空である、未知の要素または重複した要素を持つ、末尾に内容が続く、または上限（記事は生成テキストの上限、一覧は検証・推敲の応答の上限、ファイルは設計で定める上限）を超える場合、それぞれ `errors.Is` で判定できる番兵エラーで拒否し、LLM を呼ばず、記事を公開しない。部分受理はしない。本文の先頭の U+FEFF は、除去せず拒否する。
- **AC-21**: 中間生成物の入力の識別子が、いまの動画 ID・素材・前段の中間生成物の識別子と一致しない場合、`errors.Is` で判定できる番兵エラーで拒否し、LLM を呼ばず、記事を公開しない。生成からやり直した実行で字数の調整または検証・推敲が走らず、前の実行の字数の調整の出力または適用後の記事が残っている場合、それを使う再開（`--after shorten`・`--after review`）も、この番兵エラーで拒否する。
- **AC-22**: 再開で使うタイトルと本文が、生成テキストの検証（0004 の AC-22〜AC-24・AC-27・AC-31 の `Text`）で拒否される形である場合、または来歴のモデル名と ModelVersion が、応答のモデル名の検証（0004 の AC-25・AC-29・AC-31 の `Model`・`ModelVersion`）で拒否される形である場合、`errors.Is(err, writer.ErrMalformedOutput)` が真になるエラーで拒否し、記事を公開しない（来歴のモデル名は `--out` に書かれるため。AC-27）。
- **AC-23**: 中間生成物の読み込みで、標準ライブラリが黙って修復・破棄・無視すれば受理できてしまう入力は、受理せず拒否する（AC-20 の各例を、それぞれその入力だけで拒否する）。

#### F-005: フラグと出力

-   `--artifacts <path>`: 中間生成物を保存するディレクトリ。指定したときだけ保存する。`--after` と同時に指定した場合は、そのディレクトリを保存と再利用の両方に使う。
-   `--after <stage>`: `<stage>` の保存された出力から再開する。受理する値は `generation`・`shorten`・`review`。`--artifacts` を必須とする。
-   生成でしか使わない指定（`--system-prompt`・`--user-prompt`）は、生成を実行しない再開（`--after generation`・`--after shorten`・`--after review`）と同時に指定できない。
-   `--out` の出力は、実際に呼んだ段階に加えて、再利用した段階のモデル名と ModelVersion を、どの段階のものか分かる形で書く（F-001 の来歴を使う）。
-   CLI の使い方の表示と README に、新しいフラグと、再開の指定の規則を書く。

当初案の `--article <path>` と `--review-only` は、`--artifacts` と `--after` の一般化として置き換える（新たなフラグとしては設けない）。`--article <path>` は任意の記事ファイルを入力にするものだったが、本タスクでは、保存した中間生成物を動画 ID で選ぶ形にする。

**Acceptance Criteria**:
- **AC-24**: `--after` を `--artifacts` なしで指定した場合、CLI は yt-dlp と LLM を呼ぶ前に、使い方の誤りとしてエラーで終わる。
- **AC-25**: `--after` に `generation`・`shorten`・`review` 以外の値を指定した場合、CLI は yt-dlp と LLM を呼ぶ前に、使い方の誤りとしてエラーで終わる。
- **AC-26**: `--system-prompt` または `--user-prompt` を `--after` と同時に指定した場合、CLI は yt-dlp と LLM を呼ぶ前に、使い方の誤りとしてエラーで終わる。
- **AC-27**: `--out` の出力は、実際に呼んだ段階のモデル名と ModelVersion に加えて、再利用した段階のモデル名と ModelVersion を、どの段階のものか分かる形で含む。再利用した段階の来歴が空の ModelVersion を持つ場合、その段階の ModelVersion は無いものとして書く。
- **AC-28**: `-h`/`--help` の使い方の表示と README に、`--artifacts` と `--after` の説明と、`--after` が `--artifacts` を要すること、`--after review` が `--review-log` を使えないことが書かれている（静的な確認）。

#### F-006: 保存・読み込みの失敗の報告

保存または読み込みの失敗は、失敗した段階を示すエラーとして報告する。読み込みの失敗は、どの LLM も呼ばずに失敗する。再開の指定の誤り（F-005）は、使い方または設定の誤りとして、LLM を呼ぶ前に終わる。

**Acceptance Criteria**:
- **AC-29**: 中間生成物の保存に失敗した場合（F-001・AC-06）と、読み込みに失敗した場合（F-004）のエラーは、失敗した段階を示す。保存・読み込みの失敗では、記事を公開しない。
- **AC-30**: 再開のフラグの組み合わせの誤り（AC-24・AC-25・AC-26・AC-16 の `--after review` と `--review-log`）と、`--artifacts` のディレクトリがキャッシュディレクトリの中にあること（AC-08）は、LLM を呼ぶ前に使い方の誤り（終了コード 2）として終わる。`--artifacts` のディレクトリが存在しない・使えないこと（AC-09）と、中間生成物の不在・破損・食い違い（AC-19〜AC-22）は、実行の失敗（終了コード 1）として終わる。分け方は、引数の形だけで判定できる誤りを終了コード 2、ファイルシステムの状態を確かめて分かる誤りを終了コード 1 とするもので、`--out` の規則（キャッシュディレクトリの中は終了コード 2、親ディレクトリの不在は書き込むときに確かめて終了コード 1）と同じである。AC-09 の判定は、保存と読み込みに使うディレクトリを実際に開く処理で行い、事前の確認を別に設けない（事前の確認と使う時点の間でディレクトリが変わった場合に、同じ条件に 2 つの終了コードが付かないようにするため）。

#### F-007: テスト可能性

**Acceptance Criteria**:
- **AC-31**: 中間生成物の保存と再開のユニットテストは、LLM の API もネットワークも呼ばない。fake の `LLMClient`（生成・字数の調整・検証・推敲のそれぞれ）と、fake の `TranscriptSource` と `Publisher`（AC-17 の yt-dlp/キャッシュと、AC-19〜AC-22 の公開の有無を検証するため）、`t.TempDir` のディレクトリを使い、各 AC を検証する。
- **AC-32**: 既存の `ArticleWriter`・CLI のテストのうち、`--artifacts` を付けない既定の実行の振る舞いを検証するものは、本タスクの後もそのまま通る。

#### F-008: 文書と評価の手順の更新

**Acceptance Criteria**:
- **AC-33**: `project_overview.md` のパイプラインの説明と CLI の説明に、中間生成物の保存と再開を加える。`security.md` のキャッシュディレクトリと信頼できないテキストの節に、保存する中間生成物の権限・保存先・拒否の規則と、読み込みの境界を加える。README のフラグの表に `--artifacts` と `--after` を加える（静的な確認）。
- **AC-34**: この仕組みを使って評価を切り替える場合に備え、[0010 の 02_evaluation.md](../0010_post_generation_review/02_evaluation.md) の手順（§2）に、中間生成物を固定して段階だけを比べる方法（同じ生成の出力に別の字数の調整を当てる、同じ字数の調整の出力に別の検証・推敲を当てる）を加える。評価の再実行と §3 の記録の更新は、本タスクのスコープ外とする。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

本タスクが新たに扱う境界は、再開の入力の中間生成物（保存されたファイル。検証・推敲の応答と記事の本文を含む）と、`--artifacts` のディレクトリの読み込みである。字幕・info.json・検証・推敲の応答そのものの境界は、既存のタスク（`0002`・`0010`）のままとする。

| 境界 | 受理する形 | 上限 | 拒否時の扱い | 主な AC |
|---|---|---|---|---|
| 中間生成物のファイル | 所有者だけが読める通常のファイル。固定の名前（動画 ID と段階）で、シンボリックリンクでない | ファイル全体の有限の上限（値は設計で定める） | 番兵エラーで拒否し、LLM を呼ばず、公開しない | AC-10・AC-11・AC-19・AC-20 |
| 中間生成物の内容 | 宣言した要素だけを持つ、正しい UTF-8 の値。先頭に U+FEFF がなく、タイトルと本文は生成テキストの検証を通る | 生成テキストの上限と、検証・推敲の応答の上限（1 MiB・256 項目。`security.md` §6）を再利用する | 番兵エラーで拒否する。部分受理しない | AC-20・AC-22・AC-23 |
| 入力の識別子 | いまの動画 ID・素材・前段の中間生成物の識別子と一致する | - | 番兵エラーで拒否する | AC-21 |

-   標準ライブラリが黙って修復・破棄・無視すれば受理できてしまう入力は、受理せず拒否する（[requirements_process.md](../../dev/developer_guide/requirements_process.md) の「Untrusted input boundaries」）。具体的な構文と上限の値、不正な入力の検出方法は [`02_architecture.md`](02_architecture.md) で決める（[design_handoff.md](design_handoff.md) H-01・H-05）。
-   中間生成物の値によって実行する段階を選ばない。再開する段階は `--after` の値だけで決める（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   保存と読み込みの処理は、LLM の呼び出しに比べて無視できる時間で終わればよい。性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   再開では、呼ばない段階の LLM の時間と料金が減る。評価では、同じ生成の出力に別の段階を当てることで、生成の回数と料金を減らせる。

### 4.2. セキュリティ (Security)

-   中間生成物には、記事の本文（信頼できない LLM の出力）と、検証・推敲の一覧の根拠の引用（素材＝字幕などの信頼できないテキスト）が入る。API キー・Webhook URL・共有トークン・ローカルのパス（中間生成物の保存に使うパスを除く）を含めない（[security.md](../../dev/security.md) §2・§6）。
-   保存するファイルは `0o600` とし、シンボリックリンクを辿らない。保存先のディレクトリは利用者が用意したものを使い、CLI は作らない（AC-09・AC-11）。名前は検証済みの動画 ID と固定の段階名から組み立て、ディレクトリ内の任意の名前を信用しない（security.md §5）。
-   保存先がキャッシュディレクトリの中にある場合は拒否する（AC-08）。キャッシュの削除で中間生成物が消えるのを防ぎ、`--out`・`--review-log` と同じ規則にそろえる。
-   読み込みの失敗のエラーに、中間生成物の値（記事の本文・一覧の引用）を含めない。既存の生成テキスト・検証・推敲の応答の拒否と同じく、壊れた規則だけを示す。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   各中間生成物は、その段階の完了時に保存する（AC-04）。後の段階の失敗で、それより前の段階の出力を失わない。
-   保存または読み込みの失敗は、記事の失敗とする。保存した中間生成物と実際に公開した記事が食い違う状態を残さない（AC-06・AC-29）。
-   中間生成物の書き込みは、途中で中断した場合に、壊れた中間生成物を次の再開が受理しないようにする（壊れた中間生成物は F-004 で拒否する。書き込みの方法は [`02_architecture.md`](02_architecture.md) で決める。[design_handoff.md](design_handoff.md) H-03）。

### 4.4. 互換性 (Compatibility)

-   `--artifacts`・`--after` を指定しない実行の振る舞いは、本タスクの前と同じである（AC-32）。保存の既定は「保存しない」である（F-002）。
-   `--after shorten`（生成と字数の調整をスキップして検証・推敲を行う）は、当初案の `--review-only` に当たる。`--after generation`（生成をスキップして後の段階を行う）は、当初案の `--article <path>` に当たる（入力を任意のファイルではなく、保存した中間生成物から動画 ID で選ぶ）。
-   保存する中間生成物の形式は、本タスクの中で定める（同じバージョンの CLI での保存と再開を保証する。別のバージョンとの互換は対象外とする）。

### 4.5. 保守性 (Maintainability)

-   保存する中間生成物の値と来歴は、`writer` パッケージの既存の型（`Article`・`StepModel`・`ReviewResult`・`Revision`）から組み立てる。検証・推敲の応答の解析（`internal/strictjson`）と、生成テキストの検証（`0004`）を再利用し、複製しない（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   保存と読み込みの形式は 1 か所で定義し、保存と再開の両方が同じ定義を読む（片方だけを変えて食い違わないようにする）。
-   段階から実行する処理への対応は、網羅的な `switch`（`default` は拒否）で行い、保存した値から再開の段階を推測しない（「Declare, don't infer」）。
-   `writer.Article` の exported フィールドの集合を変える場合（中間生成物を保持するためなど）は、`internal/pipeline` の guard（`TestCommonTypesFieldSets`）を同じ変更で更新する（[AGENTS.md](../../../AGENTS.md)）。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」と [`CLAUDE.md`](../../../CLAUDE.md) に従う。外部ライブラリを追加しない。
-   本書は、0010 の F-005（CLI のフラグ）を変更する。0010 の要件定義書は `approved` であり、本書で `--artifacts`・`--after` とその組み合わせの規則を定め、0010 の F-005 を変更する要件定義書からの変更として扱う（同じ段階のフラグ `--no-shorten`・`--no-review`・`--review-log` の振る舞いは変えない）。
-   各段階の入出力と検証（0010 の F-001〜F-003）を変えない。本タスクは、その出力を保存・再利用するだけである。
-   字幕・info.json のキャッシュの形式と、キャッシュの削除の規則（`0005`）を変えない。
-   再開の入力の中間生成物は、信頼できない入力として扱う（F-004・§4.2）。
-   ユニットテストは、実際の `yt-dlp` も LLM の API も Webhook も呼ばない。fake の `LLMClient` と `t.TempDir` を使う（[CLAUDE.md](../../../CLAUDE.md)「Testing Strategy」）。
-   外部ライブラリは追加しない。保存の形式は Go の標準ライブラリ（`encoding/json` と `internal/strictjson`）で扱う。

## 6. 用語集 (Glossary)

-   **中間生成物:** パイプラインの各段階の出力のうち、後続の実行で再利用できるように保存するもの。生成の出力・字数の調整の出力・検証・推敲の一覧・適用後の記事を指す（F-001）。
-   **再開:** 保存した中間生成物を入力として、その段階より後の段階だけを実行すること（F-003）。
-   **来歴:** 中間生成物に付ける、段階の名前・モデル名と ModelVersion・使ったテンプレート・入力の識別子（F-001）。
-   **入力の識別子:** 中間生成物が消費した入力を示す値。再開のときに、いまの入力と一致するかを確かめる（F-004）。
-   **段階:** 生成（generation）・字数の調整（shorten）・検証・推敲（review）。`--after` の値はこの 3 つ（F-003・F-005）。
-   **素材:** 動画タイトル・チャンネル名・概要欄・字幕（0010 の用語と同じ）。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
