## 1. 概要 (Overview)

**目的:** 本書は、LLM の呼び出しのトークン数と公開の単価から、記事 1 本の生成にかかった料金の概算を算出し、CLI の標準エラーの要約・`--out` のファイル・Slack の投稿で利用者に示すための要件を定義する。

**背景:**
現在、1 回の実行にかかった料金は、各プロバイダのコンソールの利用履歴からしか分からない（[#99](https://github.com/isseis/yt2column/issues/99)）。

-   **トークン数はすでに得られる。** タスク `0019_token_usage`（#247）により、LLM の呼び出しごとに、プロバイダに依存しない 4 つの区分（入力・キャッシュから読んだ入力・キャッシュに書き込んだ入力・出力）のトークン数が、段階（生成・字数の調整・検証・推敲の 3 段階。検証・推敲は 1 つの段階。§6）ごとに `ArticleWriter` の結果として得られる。トークン数が分からない呼び出しは「不明」として、0 と区別して渡される。CLI の標準エラーには、段階ごとのトークン数の行（`yt2column: tokens: ...`）が出る。
-   **トークン数の合計からは料金が分からない。** 区分ごとに単価が異なり（DeepSeek はキャッシュの当たり・外れ、Claude はキャッシュの読み・書き）、モデルごとにも異なる。さらに DeepSeek には、時間帯によって単価が 2 倍になるピーク時間帯がある。トークン数の行を見ても、料金はすぐには分からない。
-   **開発時の記事の評価に使う。** 構成（テンプレートとモデル）を品質と料金の両方で比べるために、CLI の実行ごとに料金の概算を読めるようにする。評価は CLI の標準エラーを記録して読むので、CLI の出力は必須である。
-   **利用者にも示す。** 記事の利用者が、ブラウザ拡張から localhost サーバを経て Slack に投稿された記事を見たときに、その記事にかかった料金の目安を知れるようにする。
-   参考: `make test-integration-cli` の 1 回（2026-10-07）は、入力が約 8,000 文字（ユーザープロンプト 20 KB、大半が日本語）、出力が約 1,270 文字だった。

対応 issue: #99。先行: #247（0019、トークン数の段階ごとの記録と出力）、#213（0017、中間生成物の保存と再開）。後続: #248（0018、記事の品質の評価。基準の集合は本タスクの完了後に作る。§5）。関連: #11（thinking モードの切り替え）、#15（Gemini アダプタ）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   対象のモデルの区分ごとの単価を、出典と確認日とともにコードに持つ（F-001）。
-   段階ごとのトークン数・モデル名・呼び出しの時刻から、段階ごとの料金の概算を算出する。推測の値は出さない（F-002・F-003）。
-   この実行で発生した料金と、記事 1 本の料金（`--after` で再利用した段階を含む）の 2 つの合計を算出する（F-004）。
-   CLI の標準エラーの要約に、成功・失敗のどちらの実行でも、段階ごとの料金の概算と 2 つの合計を出す（F-005）。
-   `--out` のファイルと Slack の投稿（localhost サーバからの投稿を含む）の見出しのメタデータに、記事 1 本の料金の概算を出す（F-006）。
-   `--after` で再利用した段階の料金を算出できるよう、中間生成物の来歴に呼び出しの時刻を記録する（F-007）。
-   課金を伴う統合テストのログに、使用量と料金の概算を出す（F-008）。

### 2.2. スコープ (In Scope)

-   単価の表（コード内の定数）と、その出典・確認日・更新の手順（F-001・F-010）。
-   段階ごとの料金の概算の算出と、DeepSeek のピーク時間帯の判定（F-002）。
-   不明の扱い（トークン数が不明、単価が未知のモデル）（F-003）。
-   2 つの合計の算出（F-004）。
-   CLI の標準エラーの要約（成功と失敗）（F-005）。
-   `--out` と Slack の投稿の見出しのメタデータ（F-006）。
-   0017 の中間生成物の形式の変更（来歴への呼び出しの時刻の追加、形式の版、`id`）（F-007）。
-   統合テストのログ（F-008）。
-   ユニットテスト（F-009）。
-   文書（README・`project_overview.md`・`package_reference.md`）の更新（F-010）。

### 2.3. スコープ外 (Out of Scope)

-   トークン数の読み取り・検証・受け渡し（0019 で済んでいる）。
-   トークン数や料金による実行の制限（予算の上限など）。
-   日本円など、米ドル以外の通貨への換算。為替の取得は、外部の値への依存とネットワークの呼び出しを増やす。
-   単価の取得のためのネットワークの呼び出し（プロバイダの料金のページの取得など）。単価はコードに持つ（F-001）。
-   DeepSeek のピーク時間帯の、中国の祝日による除外の判定。祝日の暦を持たず、祝日もピーク時間帯として算出する（F-002 の「決定」）。
-   単価の表にないモデル（`deepseek-v4-pro`、`claude-fable-5-1` など）の単価。必要になったときに F-010 の手順で加える。
-   プロバイダの割引・特別な料金体系（DeepSeek の期間限定の値引き、Claude の Batch API・優先度の tier・データの所在地の指定（`inference_geo: "us"`）による 1.1 倍・fast mode）。本プロジェクトはこれらを使わず（Claude へのリクエストは `inference_geo`・`speed`・`service_tier` を送らない）、標準の料金で算出する。ただし、Claude Haiku 5.5 のプロンプトの長さによる単価の違いは、リクエストの指定ではなく入力の量で決まるので、スコープに含める（F-001・F-002）。
-   Claude のキャッシュの書き込みの TTL ごとの単価の区別。0019 と同じく、本プロジェクトはプロンプトキャッシュを指定していない（F-001）。
-   失敗の通知（タスク `0016_failure_notification`）の Slack の投稿に、料金の概算を書くこと。
-   localhost サーバのログや HTTP の応答に、料金の概算を出すこと。サーバの Slack の投稿は F-006 のとおり変わるが、それ以外の振る舞いは変えない。
-   料金の概算の機械可読な出力のための新しいフラグ。0019 と同じく、標準エラーの行の書式を固定することで足りるとする（F-005）。

## 3. 機能要件 (Functional Requirements)

### 3.1. 機能一覧

#### F-001: 単価の表

CLI は、対象のモデルの区分ごとの単価の表を、コード内の定数として持つ。表は、モデル名ごとに、0019 の 4 つの区分（入力・キャッシュから読んだ入力・キャッシュに書き込んだ入力・出力）それぞれの 100 万トークンあたりの単価（米ドル）を持つ。時間帯によって単価が変わるモデル（DeepSeek）は、ピーク時間帯とオフピーク時間帯の 2 組の単価を持つ。プロンプトの長さによって単価が変わるモデル（Claude Haiku 5.5）は、長さの閾値と、閾値以下・閾値超の 2 組の単価を持つ。

対象のモデルは次のとおりとする。

| プロバイダ | モデル名 | 時間帯による単価の違い | プロンプトの長さによる単価の違い |
|---|---|---|---|
| DeepSeek | `deepseek-flash` | あり（ピーク・オフピーク） | なし |
| Claude | `claude-opus-5-5`・`claude-sonnet-5-5` | なし | なし |
| Claude | `claude-haiku-5-5` | なし | あり（100,000 トークン以下・超） |

単価の出典は、DeepSeek は `https://api-docs.deepseek.com/quick_start/pricing`、Claude は `https://platform.claude.com/docs/en/about-claude/pricing` とし、どちらも 2026-10-16 に確認した。Claude の料金のページは、Claude 4.6 以降のモデルのうち Haiku 5.5 を除くものは文脈の長さによらず標準の単価とし、Haiku 5.5 はプロンプトが 100,000 トークンを超えるリクエストに高い単価を適用するとしている。

**決定（issue #99 の検討事項「単価の持ち方」）:** 単価は、設定ファイルや環境変数ではなく、コード内の定数として持つ。理由は次のとおり。

-   単価はモデルとプロバイダの公開の情報であり、利用者ごとに変える値ではない。
-   設定ファイルや環境変数で与えると、信頼できない入力の境界が 1 つ増え、その形の検証と拒否の規則が要る。
-   単価の変更は数か月に 1 回程度であり、コードの変更と PR で足りる。単価の出典と確認日を、変更の差分としてレビューできる。

単価の表は、各モデルの単価の出典（公式の料金のページの URL）と確認日を、コードのコメントに記録する。単価の値と出典・確認日の記録の具体的な形は、`02_architecture.md` で決める。

モデル名の照合は、0019 のトークン数の行に出るモデル名（応答の `model` の値で、0004 のモデル名の検証を通ったもの）と、表のモデル名の完全一致で行う。設定したモデル名（`YT2COLUMN_MODEL` など）ではなく、応答のモデル名を使うのは、料金はプロバイダが応答で報告したモデルに対してかかるからである。前方一致・大文字小文字の無視などの、ゆるい照合はしない（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。

DeepSeek にはキャッシュに書き込んだ入力の区分がなく、0019 のアダプタは常に 0 を返す（0019 の F-001）。表は、DeepSeek のその区分を「区分がない」ことを宣言する形で持つか、単価を 0 として持つかを、`02_architecture.md` で決める。Claude のキャッシュに書き込んだ入力の単価は、既定の TTL（5 分）の単価とする。

**Acceptance Criteria**:
- **AC-01**: 単価の表は、上の表の 4 つのモデルそれぞれについて、4 つの区分の単価を持つ。`deepseek-flash` は、ピーク時間帯とオフピーク時間帯の 2 組の単価を持つ。`claude-haiku-5-5` は、閾値（100,000 トークン）と、閾値以下・閾値超の 2 組の単価を持つ（静的な確認）。
- **AC-02**: 単価の表の各モデルについて、単価の出典の URL と確認日が、コードのコメントに記録されている（静的な確認）。
- **AC-03**: 単価の表は、実際の定義に対するユニットテストで形を確かめる。モデル名の重複、空のモデル名、負の単価、時間帯またはプロンプトの長さによる単価の違いがあるモデルでの 1 組だけの単価、0 以下の閾値は、テストを失敗させる（[CLAUDE.md](../../../CLAUDE.md)「Reject, don't normalize」）。
- **AC-04**: モデル名の照合は完全一致である。表にあるモデル名と、大文字小文字だけが異なるモデル名、接尾辞（`-latest` など）を加えたモデル名、前後に空白を加えたモデル名は、どれも表にないモデル名として扱う（F-003）。

#### F-002: 段階ごとの料金の概算の算出

CLI は、トークン数が分かった段階について、区分ごとのトークン数 × その区分の単価 ÷ 1,000,000 の和を、その段階の料金の概算とする。0019 で 1 つの段階が LLM を呼ぶのは 1 回なので、段階の料金は 1 回の呼び出しの料金である。

算出は、表示の精度より細かい誤差を生まない方法で行う。表示する値は、単価の出典の値から手で計算した正確な値を、表示の桁で四捨五入したものと一致する。算出の方法（整数の演算、小さい単位での計算など）は `02_architecture.md` で決める。

**決定（issue #99 の検討事項「DeepSeek のピーク時間帯の扱い」）:** 時間帯によって単価が変わるモデルは、その呼び出しの応答を受け取った時刻（CLI の時計の UTC）で、ピーク時間帯かオフピーク時間帯かを判定する。2026-10-16 に確認した DeepSeek の料金のページでは、ピーク時間帯は月曜から金曜の UTC 01:00〜04:00 と 06:00〜10:00（中国の祝日を除く）で、ピーク時間帯の単価はオフピーク時間帯の 2 倍である。判定の規則（曜日と時刻の範囲）も、単価と同じく出典と確認日とともにコードに持つ。

-   中国の祝日は判定しない。祝日の暦をコードに持つと、毎年の更新が要り、外れたときに誤りに気付けない。祝日の呼び出しは、オフピーク時間帯の単価で請求されるが、平日の時刻の範囲に入ればピーク時間帯として算出する。そのため、祝日の概算は実際より多くなり得る。これは、概算が実際より少なくならない向きの誤差であり、README に書く（F-010）。
-   時間帯の判定の結果（ピーク・オフピーク）は、CLI の標準エラーの段階の行に示す（F-005）。利用者は、コンソールの利用履歴と比べるときに、どちらの単価で算出したかを確かめられる。
-   ピーク時間帯の境界は、開始の時刻を含み、終了の時刻を含まない（01:00:00 はピーク時間帯、04:00:00 はオフピーク時間帯）。応答を受け取った時刻を判定に使うのは、それが CLI が観測できる時刻のうち、プロバイダが請求の対象とする処理の時刻に最も近いからである。プロバイダが請求に使う時刻（リクエストの受付か、処理の完了か）は文書化されていないので、境界をまたぐ呼び出しの判定は、プロバイダの判定と食い違い得る。

**プロンプトの長さによる単価の選択:** プロンプトの長さによって単価が変わるモデル（`claude-haiku-5-5`）は、その呼び出しの入力の 3 つの区分の和（入力・キャッシュから読んだ入力・キャッシュに書き込んだ入力）をプロンプトの長さとし、閾値（100,000 トークン）を超えれば閾値超の単価を、閾値以下なら閾値以下の単価を、4 つの区分すべてに適用する。Claude の料金のページは、プロンプトの長さをキャッシュの読み書きを含むすべての入力のトークン数とし、閾値を超えたリクエストは全体に高い単価を払うとしている。判定はトークン数だけから決まり、推測を含まない。トークン数が不明の段階は、F-003 のとおり料金が不明となる。

**Acceptance Criteria**:
- **AC-05**: トークン数が分かった段階の料金の概算は、各区分のトークン数とその区分の単価から手で計算した値と一致する。4 つの区分のトークン数がそれぞれ異なり、0 でない値で、区分の取り違えが値の違いとして現れる入力で、対象の 4 つのモデルのそれぞれについて確かめる。期待値は単価の出典の値から手で計算したものとし、算出のコードや単価の表の定数から導かない。
- **AC-06**: `deepseek-flash` の段階は、応答を受け取った時刻が月曜から金曜の UTC 01:00:00〜03:59:59 と 06:00:00〜09:59:59 ならピーク時間帯の単価で、それ以外（土曜・日曜の同じ時刻を含む）ならオフピーク時間帯の単価で算出される。境界の時刻（00:59:59・01:00:00・03:59:59・04:00:00・05:59:59・06:00:00・09:59:59・10:00:00）と、土曜・日曜の 01:00:00 で確かめる。時刻は UTC 以外の時間帯で表した値を与えても、UTC で判定する。
- **AC-07**: 時間帯によって単価が変わらないモデル（Claude）の段階の料金は、呼び出しの時刻によらない。
- **AC-07a**: `claude-haiku-5-5` の段階は、入力の 3 つの区分の和が 100,000 以下なら閾値以下の単価で、100,001 以上なら閾値超の単価で、4 つの区分すべてが算出される。和が 100,000 と 100,001 になる入力で確かめ、和の計算に 3 つの区分がそれぞれ含まれることを、1 つの区分だけで閾値を超える入力（区分ごとに 1 つずつ）で確かめる。プロンプトの長さによって単価が変わらないモデル（`claude-opus-5-5`・`claude-sonnet-5-5`・`deepseek-flash`）は、入力が 100,000 を超えても単価が変わらない。
- **AC-08**: トークン数がきわめて大きい段階（各区分が `int64` の上限に近い値）でも、算出は桁あふれを起こさず、桁あふれした値や負の値を出さない。表せない場合の扱い（不明とするか、別の表し方をするか）は `02_architecture.md` で決める。

#### F-003: 不明の扱い

段階の料金の概算は、次のいずれかの場合に「不明」とする。不明の段階には、0 を含め、推測の値を出さない。

| 理由 | 内容 |
|---|---|
| トークン数が不明 | 0019 でその段階のトークン数が不明（`unknown`）のとき |
| モデル名がない | 0019 でその段階のモデル名がない（`nomodel`）とき |
| 単価が未知のモデル | モデル名が単価の表にないとき（F-001 の完全一致） |

**決定（issue #99 の検討事項「トークン数が不明の段階を含む記事」）:** 合計（F-004）に含める段階のどれかが不明なら、その合計も不明とする。分かった段階だけの和や、下限（「$x 以上」）は出さない。理由は次のとおり。

-   部分的な和は、不明の段階の料金を 0 とみなした値であり、「推測の値を出さない」に反する。
-   不明は、プロバイダの仕様変更、新しいモデルへの切り替え、異常な応答のときにだけ起きる（0019 の F-002）。不明の段階の行は、理由とともに標準エラーに出る（F-005）ので、利用者は原因を確かめられる。

**Acceptance Criteria**:
- **AC-09**: トークン数が不明の段階、モデル名がない段階、単価の表にないモデル名の段階は、それぞれ料金が不明となり、数値（0 を含む）を出さない。3 つの理由は互いに区別できる（F-005 の書式で、固定の語で示す）。
- **AC-10**: 単価の表にないモデル名（例: `deepseek-v4-pro`、`claude-fable-5-1`、`gpt-5`）の段階では、表のほかのモデルの単価や、同じプロバイダのモデルの単価で代用した値を出さない。
- **AC-11**: 合計に含める段階のうち 1 つでも料金が不明なら、その合計は不明となり、数値を出さない。不明の段階を含まない合計は、不明の段階の影響を受けない（F-004 の「この実行の料金」は、不明の段階が再利用した段階だけなら数値を出す）。

#### F-004: 合計

CLI は、段階ごとの料金の概算から、次の 2 つの合計を算出する。

| 合計 | 含める段階 | 用途 |
|---|---|---|
| この実行の料金 | この実行で LLM を呼んだ段階（0019 の `run` の行） | この実行で実際に発生した料金。コンソールの利用履歴との照合 |
| 記事 1 本の料金 | この実行で呼んだ段階と、`--after` で再利用した段階（0019 の `run` と `reused` の行） | 記事 1 本を生成するのにかかった料金。構成の比較 |

**決定（issue #99 の検討事項「`--after` で再利用した段階の扱い」）:** 再利用した段階は、段階の行に再利用の印を付け（0019 の `reused`）、合計は上の 2 つを両方示す。開発時の評価（構成の比較）では記事 1 本の料金を、課金の確認ではこの実行の料金を使う。`--after` を使わない実行では、2 つの合計は等しいが、書式を固定するため両方を出す。

**Acceptance Criteria**:
- **AC-12**: 生成・字数の調整・検証・推敲がすべて走った実行の 2 つの合計は、3 つの段階の料金の和と一致する。
- **AC-13**: `--after` で再開した実行の「この実行の料金」は、この実行で呼んだ段階だけの料金の和であり、「記事 1 本の料金」は、再利用した段階を加えた和である。`--after generation` と `--after shorten` で確かめる。`--after review`（LLM を呼ばない）では、「この実行の料金」は 0 で、「記事 1 本の料金」は再利用した段階の和である。
- **AC-14**: LLM を呼ばなかった段階（字数の調整が走らなかった、`--no-review`）は、どちらの合計にも含めない（0 として足すのではなく、行がない）。

#### F-005: CLI の標準エラーの要約への出力

CLI は、0019 のトークン数の行を出す実行（成功した実行と、LLM を 1 つ以上呼んだ後か `--after` の入力を受理した後に失敗した実行。0019 の F-004・F-005・AC-20）で、標準エラーに、段階ごとの料金の行と、2 つの合計の行を出す。料金の行は、トークン数の行と同じく 1 段階 1 行とし、トークン数の行と同じ段階の名前・由来（`run`・`reused`）の並びを持つ。

各段階の行は、料金が分かった場合は米ドルの金額と、時間帯によって単価が変わるモデルではピーク時間帯・オフピーク時間帯のどちらで算出したかを示す。料金が不明の場合は、不明の印と、不明の理由（F-003 の 3 つ）を示し、数値を出さない。合計の行は、合計の種類（この実行・記事 1 本）と金額、または不明の印を示す。

**決定（issue #99 の検討事項「通貨と表示の形式」）:** 通貨は米ドルとする（両プロバイダの料金の通貨。2026-10-16 に人が確かめた）。標準エラーの金額は、小数点以下 6 桁の固定の桁数で出す（例: `usd=0.002345`）。記事 1 本の料金は 1 セントに満たないことが多く、評価で構成を比べるには細かい桁が要るためである。行の書式は 0019 と同じく固定し、README に書く。行の書式（行の接頭辞、語の並び、各語）は `02_architecture.md` で決める。

失敗した実行でも料金の行を出すのは、打ち切りなどで記事を公開しなかった実行でも、それまでに呼んだ LLM の料金はかかるからである（0019 の F-005 と同じ理由）。

**Acceptance Criteria**:
- **AC-15**: 生成・字数の調整・検証・推敲がすべて走って成功した実行の標準エラーに、3 つの段階それぞれの料金の行と、2 つの合計の行が出る。各金額は、F-002・F-004 で算出した値を小数点以下 6 桁に四捨五入したものである。
- **AC-16**: `deepseek-flash` の段階の行は、ピーク時間帯・オフピーク時間帯のどちらで算出したかを、行の固定の位置の固定の語で示す。Claude の段階の行は、時間帯を示さないことを固定の語で示すか、時間帯の語を持たない（`02_architecture.md` で決める）。
- **AC-17**: 料金が不明の段階の行は、不明の印と、F-003 の理由を示す固定の語を出し、数値を出さない。0019 のトークン数の行が不明の段階は、料金の行も不明になる。
- **AC-18**: `--after` で再開した実行では、再利用した段階の料金の行に、0019 のトークン数の行と同じ再利用の印が付く。再利用した段階の料金は、その中間生成物の来歴のトークン数・モデル名・呼び出しの時刻（F-007）から算出される。
- **AC-19**: 記事を公開せずに失敗した実行（0019 の AC-16〜AC-19 の各場合）でも、0019 のトークン数の行が出る段階について料金の行が出て、2 つの合計の行も出る。終了コードは本タスクの前と同じである。
- **AC-20**: 0019 のトークン数の行を出さない実行（0019 の AC-20）では、料金の行も合計の行も出さない。
- **AC-21**: 料金の行の書式（段階の名前・由来・時間帯の語・不明の印と理由の語・合計の種類の語・金額の桁数）は README に書かれている（静的な確認）。書式は、これらを行の固定の位置の固定の語で示し、モデル名などの値の内容から判定させない。
- **AC-22**: 既存の要約の行（公開先とモデル名、字数の調整が走ったこと、検証・推敲の項目数、0019 のトークン数の行）は変わらない。

#### F-006: `--out` と Slack の投稿への出力

`--out` のファイルと Slack の投稿の見出しのメタデータ（モデル名の行の並び。現在は `renderArticle` が両方に共通の本文を作る）に、記事 1 本の料金の概算を 1 行加える。行は、米ドルの金額と、概算であることを示す語を持つ。記事 1 本の料金が不明のときは、不明であることを示し、数値を出さない。

**決定（issue #99 の検討事項「Slack の投稿」）:** 料金の概算の行は、設定によらず常に載せる。有効・無効を切り替える設定は設けない（YAGNI）。localhost サーバ（タスク `0011_localhost_server`）からの Slack の投稿にも、同じ行が載る。

-   金額は、小数点以下 4 桁に四捨五入して出す（例: `$0.0023`）。記事の読者には目安で足り、標準エラーより粗い桁で読みやすくする。
-   載せるのは記事 1 本の料金だけとし、段階ごとの内訳とこの実行の料金は載せない。記事の読者に要るのは、その記事にかかった料金の目安である。段階ごとの内訳は CLI の標準エラーで見られる。
-   不明の理由は載せない。理由は CLI の標準エラー（F-005）で確かめる。サーバからの投稿で不明になった理由は、本タスクでは利用者に示さない（§2.3）。
-   行の文言は、既存の見出しのメタデータ（`- Model: ...`）と同じく英語とする。文言は `02_architecture.md` で決める。

**Acceptance Criteria**:
- **AC-23**: `--out` で書いたファイルの見出しのメタデータに、記事 1 本の料金の概算の行が 1 行あり、金額は F-004 の記事 1 本の料金を小数点以下 4 桁に四捨五入したもので、概算であることを示す語を持つ。
- **AC-24**: Slack の投稿（CLI からの投稿と、localhost サーバからの投稿の両方）の見出しのメタデータに、AC-23 と同じ行が載る。投稿が複数のメッセージに分かれる場合も、行は見出しのメタデータに 1 回だけ現れる。
- **AC-25**: 記事 1 本の料金が不明のとき、`--out` と Slack の投稿の行は不明であることを示し、数値（0 を含む）を出さない。記事は本タスクの前と同じく公開される。料金が不明であることは、公開の失敗の理由にならない。
- **AC-26**: 料金の概算の行を加えても、Slack の投稿の既存の検査（メッセージの分割、メンションの拒否、UTF-8 の検査）は本タスクの前と同じに働く。料金の概算の行は、Slack のメンションと解釈される文字を含まない。

#### F-007: 中間生成物の来歴への呼び出しの時刻

0017 の中間生成物は、0019 のトークン数に加えて、その段階の呼び出しの応答を受け取った時刻（UTC）を来歴に記録する。`--after` で再開した実行は、読み込んだ中間生成物の時刻を、再利用した段階の時間帯の判定（F-002）に使う。

**決定（中間生成物の形式の版）:**

-   中間生成物の形式の版（`version`）を 3 に上げる。版 2（0019 の CLI が保存したもの）の中間生成物は、再開の入力として受理せず、0017 の中間生成物の破損の番兵エラー（`artifact.ErrMalformed`）で拒否する。0019 の版 1 の拒否と同じ扱いである。時刻のない中間生成物を受理すると、再利用した DeepSeek の段階の料金を算出できない。
-   版 2 を受理する案（時刻なしとして扱い、再利用した DeepSeek の段階の料金を不明とする、ピーク時間帯の単価で算出する、幅で示すなど）は採らない。読み込みに版ごとの形の定義が 2 つ要り、再利用した段階の料金が不明か仮定の値になる。代わりに、0018 の基準の集合を本タスクの完了後に作る順序で、版 2 の中間生成物を再開に使う必要をなくす（§5）。2026-10-16 の時点で、0018 の基準の集合はまだ作られていない（0018 の `02_evaluation.md` のステップ 2 が未完了）。
-   呼び出しの時刻を中間生成物の `id` の計算に含める。0019 のトークン数と同じく、時刻も来歴の一部であり、どの呼び出しから来たものかを示す。
-   時刻を記録するのは、トークン数が分かった呼び出しに限らない。トークン数が不明でも、応答を受け取った呼び出しの中間生成物は時刻を記録する。時刻の表し方（形式、精度）は `02_architecture.md` で決める。

**Acceptance Criteria**:
- **AC-27**: `--artifacts` を付けた実行で保存した生成・字数の調整・検証・推敲の中間生成物は、それぞれ、その段階の呼び出しの応答を受け取った時刻を来歴に持ち、その値は F-002 の判定に使った時刻と一致する。
- **AC-28**: `--after` で再開した実行の、再利用した `deepseek-flash` の段階の料金は、中間生成物の時刻で判定した時間帯の単価で算出され、再開した実行の時刻によらない。ピーク時間帯の時刻を記録した中間生成物を、オフピーク時間帯の時刻に再開して確かめる（逆も確かめる）。
- **AC-29**: 中間生成物の時刻の要素が、ない、重複している、または `02_architecture.md` で定める形でない場合、その中間生成物は `artifact.ErrMalformed` で拒否され、LLM を呼ばず、記事を公開しない。要素ごと・不正な形ごとに、その入力だけで拒否することを確かめる。
- **AC-30**: 版 2 の中間生成物は、再開の入力として `artifact.ErrMalformed` で拒否される。
- **AC-31**: 時刻だけが異なる 2 つの中間生成物は、異なる `id` を持つ。中間生成物の時刻だけを書き換えたファイルは、記録した `id` と内容が一致しないものとして、`artifact.ErrMalformed` で拒否される。

#### F-008: 統合テストのログ

課金を伴う統合テストのログに、使用量と料金の概算を出す。

-   `make test-integration-cli`・`make test-integration-cli-slack`: CLI を実行して標準エラーをログに出しているので、F-005 の料金の行と合計の行がログに出る。
-   `make test-integration-deepseek`・`make test-integration-claude`: アダプタを直接呼ぶテストのログに、各呼び出しのトークン数（4 つの区分）と、F-002 の算出による料金の概算（`deepseek-flash` では時間帯を含む）を出す。

**Acceptance Criteria**:
- **AC-32**: `make test-integration-cli` のログに、F-005 の料金の行と 2 つの合計の行が出る。その値が、DeepSeek のコンソールの利用履歴の同じ実行の料金と一致することを、手動で確かめる（祝日の呼び出しを除く）。確かめた日時と結果は、`03_implementation_plan.md` に記録する。
- **AC-33**: `make test-integration-deepseek` と `make test-integration-claude` のログに、各呼び出しのトークン数と料金の概算が出る（手動の確認）。
- **AC-34**: 実際の Slack の投稿（`make test-integration-cli-slack`）で、見出しのメタデータに料金の概算の行が表示されることを、手動で確かめる。確かめた日時と結果は、`03_implementation_plan.md` に記録する。

#### F-009: テスト可能性

**Acceptance Criteria**:
- **AC-35**: 料金の算出（F-002〜F-004）のユニットテストは、期待値を単価の出典の値から手で計算したものとし、算出のコードや単価の表の定数から導かない。テストのコメントに、期待値の計算式を書く。
- **AC-36**: 時間帯の判定のユニットテストは、実際の時計に依存せず、テストが与えた時刻で確かめる。CLI と `ArticleWriter` のテストも、時刻を固定できる。
- **AC-37**: CLI の出力（F-005〜F-007）のユニットテストは、実際の API・`yt-dlp`・Webhook を呼ばず、段階ごとに異なるトークン数とモデル名を返す fake の `LLMClient`、fake の `TranscriptSource` と `Publisher`、`t.TempDir` を使う。
- **AC-38**: localhost サーバ（`internal/server`）の既存のテストは、Slack の投稿の本文に料金の概算の行が加わることへの追従を除き、本タスクの後もそのまま通る。
- **AC-39**: 既存のテストのうち、料金に関わらない振る舞い（記事の本文、モデル名の行、0019 のトークン数の行、検証・推敲の一覧、中間生成物の再開の規則）を検証するものは、`--out`・Slack の本文の料金の行と、中間生成物の時刻と形式の版への追従を除き、本タスクの後もそのまま通る。

#### F-010: 文書と単価の更新の手順

**Acceptance Criteria**:
- **AC-40**: README に、標準エラーの料金の行と合計の行の書式、各語の意味、2 つの合計の違い、`--out`・Slack の行、不明の理由、DeepSeek のピーク時間帯の判定（祝日を判定しないこと、境界をまたぐ呼び出しの判定がプロバイダと食い違い得ること）、料金は概算であり請求額はコンソールで確かめることが書かれている（静的な確認）。
- **AC-41**: 単価が変わったとき・対象のモデルを加えるときの更新の手順（出典のページで単価と時間帯の規則を確かめる、表と確認日を更新する、手で計算した期待値のテストを更新する）が、開発者向けの文書に書かれている。置き場所は `02_architecture.md` で決める（静的な確認）。
- **AC-42**: `project_overview.md` の CLI の出力の説明と中間生成物の形式の版、`package_reference.md` の料金の算出のパッケージが更新されている（静的な確認）。

### 3.2. 信頼できない入力の境界 (Untrusted Input Boundaries)

本タスクが新たに扱う境界は、中間生成物の呼び出しの時刻の要素だけである。応答の `usage` とモデル名、中間生成物のほかの要素の境界は、既存のタスク（0003・0004・0009・0017・0019）のままとする。単価の表はコード内の定数であり、入力の境界ではない（その形は AC-03 のテストで確かめる）。CLI の時計は外部の入力ではないが、テストでは固定できるようにする（AC-36）。

| 境界 | 消費する要素 | 受理する形 | 上限 | 拒否時の扱い | 主な AC |
|---|---|---|---|---|---|
| 中間生成物の呼び出しの時刻 | 応答を受け取った時刻 | `02_architecture.md` で定める 1 つの形だけ。1 回だけ現れる。0017 の中間生成物は、宣言していない要素を拒否する | 形で定める長さ（ファイル全体の上限は 0017 のとおり） | `artifact.ErrMalformed`。LLM を呼ばず、公開しない | AC-29〜AC-31 |

-   標準ライブラリが黙って修復・破棄・無視すれば受理できてしまう入力（時刻の解析で許される別の書き方、時間帯の差の付いた時刻、範囲を超えた日付の正規化など）は、受理する形を 1 つに定めたうえで、それ以外を受理しない。不正な形の検出方法は `02_architecture.md` で決める。
-   料金の値によって実行する処理を選ばない。料金は算出して出力するだけで、生成・字数の調整・検証・推敲・公開の振る舞いを変えない。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   料金の算出と出力は、LLM の呼び出しに比べて無視できる時間で終わればよい。性能のための仕組みは設けない（[CLAUDE.md](../../../CLAUDE.md)「Performance」）。
-   単価の取得や料金の確認のために、ネットワークの呼び出しを行わない。LLM の呼び出しの回数とリクエストの内容は変えない。

### 4.2. セキュリティ (Security)

-   料金の行とエラーメッセージに、API キー・Webhook URL・共有トークン・応答のテキスト・素材を含めない（[security.md](../../dev/security.md) §2・§6）。0019 のトークン数の行と同じく、標準エラーの行は `redact.Line` を通す。
-   Slack の投稿に加える行は、金額と固定の文言だけで作り、応答や素材の値を含めない。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   料金が不明であることで、記事の生成と公開を失敗させない（AC-25）。料金の把握は副次的な情報である（0019 の F-002 と同じ理由）。
-   失敗した実行でも、失敗までに呼んだ段階の料金の概算を失わない（AC-19）。

### 4.4. 互換性 (Compatibility)

-   CLI のフラグと終了コードは変えない。標準エラーには、料金の行と合計の行が加わる。`--out` のファイルと Slack の投稿には、見出しのメタデータに 1 行加わる。
-   中間生成物の形式の版を 3 に上げ、版 2 を拒否する（AC-30）。0017 の §4.4 のとおり、別のバージョンの CLI との互換は対象外とする。
-   `writer.Article` などの exported の型の形を変える場合は、`internal/pipeline` の guard（`TestCommonTypesFieldSets`）を同じ変更で更新する。

### 4.5. 保守性 (Maintainability)

-   単価の表と時間帯の規則は 1 か所に置き、CLI の要約・`--out`・Slack・統合テストのログが同じ算出を使う（[CLAUDE.md](../../../CLAUDE.md)「DRY」）。
-   プロバイダを加えるとき（#15 の Gemini など）は、そのアダプタが 0019 の 4 つの区分への対応を宣言し、単価の表にモデルを加えれば、本タスクの算出をそのまま使える。
-   標準エラーの料金の行の書式は 1 か所で定義し、成功と失敗の両方が同じ定義を使う。

## 5. 制約条件 (Constraints)

-   [project_overview.md](../../dev/project_overview.md) の「決定済みの方針」「前提・制約」と [CLAUDE.md](../../../CLAUDE.md) に従う。外部ライブラリを追加しない。
-   0019 の出力（段階ごとのトークン数・モデル名・由来・不明の理由）を入力にする。0019 のトークン数の行の書式と、`usage` の検証の規則は変えない。
-   本タスクは、0017 の中間生成物の形式（来歴）を変える。0017・0019 の要件定義書は `approved` であり、本書の F-007 を 0017 の F-001（来歴）への追加として扱う。0017 の再開の規則は変えない。

## 6. 用語集 (Glossary)

-   **料金の概算:** トークン数と、単価の表の公開の単価から算出した LLM の料金の推定値（米ドル）。プロバイダの請求額ではない。
-   **単価:** 区分ごとの 100 万トークンあたりの料金（米ドル）。
-   **ピーク時間帯・オフピーク時間帯:** DeepSeek が単価を変える時間帯。ピーク時間帯の単価はオフピーク時間帯の 2 倍（2026-10-16 の確認）。
-   **この実行の料金:** この実行で LLM を呼んだ段階の料金の概算の和（F-004）。
-   **記事 1 本の料金:** この実行で呼んだ段階と、`--after` で再利用した段階の料金の概算の和（F-004）。
-   **呼び出しの時刻:** CLI がその呼び出しの応答を受け取った時刻（UTC）。時間帯の判定に使う（F-002・F-007）。
-   **トークン数・区分・不明・再利用した値:** 0019 の用語と同じ。
-   **生成・字数の調整・検証・推敲:** パイプラインの 3 つの段階の名前。検証・推敲は 1 つの段階であり、0017 の `--after review` に対応して、1 回の LLM 呼び出しと 1 つの中間生成物を持つ。
-   **段階・中間生成物・来歴・再開:** 0017 の用語と同じ。
-   用語は [translation_glossary.md](../../translation_glossary.md) と統一する。
