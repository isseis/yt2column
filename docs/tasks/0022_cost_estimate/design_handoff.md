# 設計への申し送り：LLM の料金の概算の算出と、利用者への提示

本書は、[01_requirements.md](01_requirements.md) の作成で挙がった事項のうち、設計の段階で決めるものを集める。`02_architecture.md` は、各項目について、採った方針か、当てはまらない理由を記録する。

## H-01: 単価の表の置き場所と形

-   **事項:** 単価の表（モデル名・4 つの区分の単価・時間帯の規則・出典と確認日）を置くパッケージと、その型を決める。
-   **理由:** 単価はプロバイダ固有の情報だが、算出は CLI の要約・`Publisher`・統合テストのログが共有する（要件定義書 §4.5）。アダプタ（`internal/llm/<provider>`）に置くか、独立したパッケージに置くかで、依存の向きが変わる。DeepSeek のキャッシュに書き込んだ入力の区分の表し方（「区分なし」の宣言か、単価 0 か）もここで決める（要件定義書 F-001）。
-   **参考:** 2026-10-16 に DeepSeek の料金のページ（`https://api-docs.deepseek.com/quick_start/pricing`）で確かめた `deepseek-flash` の単価（100 万トークンあたり、オフピーク / ピーク）は、キャッシュに当たった入力 $0.003 / $0.006、当たらなかった入力 $0.15 / $0.30、出力 $0.60 / $1.20。ページは通貨の記号 `$` だけを示し、通貨の名前を書いていないので、設計の段階で米ドルであることを確かめる。Claude の単価は、設計の段階で公式の料金のページで確かめる。
-   **関連:** F-001、AC-01〜AC-04

## H-02: 算出の方法と桁あふれ

-   **事項:** 浮動小数点の誤差が表示の桁に現れない算出の方法（整数の演算、小さい単位での計算など）と、`int64` に近いトークン数での桁あふれの扱いを決める。
-   **理由:** 要件定義書 F-002 は、表示する値が手で計算した値の四捨五入と一致することを求める。`float64` の和は、0.5 の境界の四捨五入で結果が変わり得る。
-   **関連:** F-002、AC-05、AC-08、AC-15、AC-23

## H-03: 呼び出しの時刻の取得と受け渡し

-   **事項:** 応答を受け取った時刻を、どこで（アダプタ・`ArticleWriter`）取得し、どう段階ごとの結果と中間生成物に運ぶかを決める。テストで時刻を固定する方法（時計の注入）も含む。
-   **理由:** 時刻は 0019 のトークン数と同じ経路で、成功と失敗の両方の結果に載る必要がある（要件定義書 AC-19・AC-27）。実際の時計に依存しないテスト（AC-36）には、時計を差し替えられる必要がある。
-   **関連:** F-002、F-007、AC-27、AC-36

## H-04: 料金の概算の `Publisher` までの経路

-   **事項:** `--out` と Slack の見出しのメタデータ（`renderArticle`）に、記事 1 本の料金の概算をどう渡すかを決める。`writer.Article` に算出済みの値を持たせるか、`Publisher` が段階ごとのトークン数・モデル名・時刻から算出するか。localhost サーバの経路でも同じ値になること。
-   **理由:** `renderArticle` は `--out` と Slack で共有されている。0019 は、トークン数を `ArticleWriter` の結果から取り出せる形にした（0019 の §4.5）が、`Publisher` までの経路は作っていない。
-   **関連:** F-006、AC-23〜AC-26、AC-38

## H-05: 中間生成物の時刻の形

-   **事項:** 中間生成物に記録する時刻の形（RFC 3339 の UTC で `Z` の付いた形に限るなど）と精度、受理する形を 1 つに定めたうえでの拒否の規則を決める。
-   **理由:** `time.Parse` は、時間帯の差の付いた形や、小数の秒の桁数の違いなどを受理し得る。要件定義書 §3.2 は、受理する形を 1 つに定め、それ以外を拒否することを求める。
-   **関連:** F-007、AC-29〜AC-31
