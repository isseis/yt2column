## 1. 概要 (Overview)

**目的:** 本書は、ガードツール `fixprguard` がある書き込みを検出して止まるための要件を定義する（[#424](https://github.com/isseis/yt2column/issues/424)）。検出するのは、`/fixpr` の修正のフェーズで、git が無視するファイルのうちコマンドの実行に関わるファイルが作られた、書き換えられた、または削除された場合である。

**背景:**

`fixprguard` は、`/fixpr` と `/runpr` が信頼できないテキスト（PR のレビューのスレッド）を扱う間の守りとして、タスク 0030（[#395](https://github.com/isseis/yt2column/issues/395)）で作られた。`begin` は、作業ツリーが clean であることを確かめてから基準値を取る。`inspect`・`finish`・`push` は、git の状態を基準値と比べ、変更の集合を判定した集合と比べる。

これらの検査は、どれも git の目を通してファイルを見る。

-   clean の検査は、`git status --porcelain=v1 -z --untracked-files=all` の出力が空であることを確かめる（`internal/fixprguard/worktree.go:63-75`）。
-   commit の前の検査で、追跡されていないファイルを数えるのは `git ls-files --others --exclude-standard` である（`internal/fixprguard/worktree.go:351`）。
-   基準値が持つのは次の 7 つである（`internal/fixprguard/gitstate.go:103-120`）。HEAD、ブランチ、push 先のブランチの OID、hooks、git のディレクトリの場所と config のファイルの種類（内容は含まない）、git が読む config の値の一覧（ほかのブランチの `branch` の設定を除く）、info のファイル（`info/exclude`・`info/attributes`）。作業ツリーのファイルは入っていない。

このため、`.gitignore` が無視するファイルは、どの検査にも映らない。修正のフェーズのエージェント（信頼できないテキストを読んだ主体）が無視されるファイルに書き込んでも、ツールは止まらない。書き込まれたファイルは commit も push もされないので、利用者に報告されることもない。

このリポジトリでは `.claude/settings.local.json` が無視される（`.gitignore:3`）。issue #424 によれば、ここに `hooks` や `permissions.allow` を書かれると、次回以降の Claude Code のセッションで任意のコマンドが実行されるか、危険な操作が確認なしで許可される。`.envrc`・`.env` も無視される（`.gitignore:4-5`）ので、同じ経路になる。issue #424 によれば、`.envrc` については、内容が変わると direnv が再度の `allow` を求めるので、被害は少し緩和される。

同じ種類の経路はほかにもある。Go のツールがパッケージを探すときに除くのは、名前が `.` か `_` で始まるディレクトリと `testdata` だけである（`go help packages`）。`.gitignore` は参照しない。そのため、`go test ./...`（`make test`）は、無視されるディレクトリ（例: `build/`）の中の `.go` ファイルもコンパイルして実行する。無視される場所に置かれた `_test.go` は、それ以後に利用者が実行する `make test` で毎回実行される。

0030 のアーキテクチャ設計書は、無視されるファイルを残余のリスクとして記録した（0030 `02_architecture.md` 5.3「無視されるファイル」）。ただし、そこで想定したのは、build checks がその回の `make test` で無視される `_test.go` を実行することだけである。次のセッションや後の実行まで残る書き込みは想定していなかった。0030 の要件定義書は、「git が無視するファイル（`.envrc` など）を変えること」を残余のリスクとして受け入れている（0030 `01_requirements.md` 4.2）。

対応 issue: [#424](https://github.com/isseis/yt2column/issues/424)（関連: [#395](https://github.com/isseis/yt2column/issues/395)、タスク `0030_fixpr_untrusted_threads`）

**本書の記述範囲:** 本書は、観測できる振る舞いを定める。どのファイルの、どんな変化を、どのサブコマンドが検出し、止まったときに何を出力し、利用者がどう対処するかである。次のことは設計（`02_architecture.md`）で決める。

-   無視されるファイルを列挙する手段と、基準値にその状態を持たせる手段（トークンの形を含む）
-   比較の順序
-   シンボリックリンクのたどり方
-   上げた後の `protocol` の番号と、コマンド定義の文書が渡す `--protocol` の揃え方
-   テストの手段

要件のレビューで挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #424 で決めたこと:**

-   **止まり方:** 基準値に含めた無視されるファイルが基準値と違えば、既存の `git-state-changed` で止まる。新しい止まった種類は作らない。止まるのは `inspect`・`finish`・`push` である。理由: 修正のフェーズが git の状態を変えたときと同じく、ツールの外での変化を見つけたことを表すからである。
-   **最低限の対象:** `.claude/settings.local.json` は必ず対象に含める。存在しないことも状態として記録する。理由: このリポジトリで無視され、次のセッションでのコマンドの実行に直結するからである。
-   **文書を新しい保証に合わせる:** 0030 `02_architecture.md` 5.3「無視されるファイル」と `fixprguard_guide.md` 7 章を改める。理由: 古い保証の範囲のまま残すと、利用者がツールの守りを誤解するからである。
-   **完了条件:** `make test`・`make lint`・`doc-guard` が通る。テストが目的の理由で失敗できることは、`CLAUDE.md`「Testing Strategy」の手順で確かめる。

**要件定義の際に決めたこと（2026-10-22）:**

-   **対象を、コマンドの実行に関わるファイルの定義全体にする:** 基準値と比べるのは、git が無視するファイルのうち、コマンドの実行に関わるファイルの定義に当たるもの全部である。定義は `fixprguard_guide.md` 6 章にあり、`.go` の規則を含む。コードでは `internal/fixprguard/scope.go:36-54`・`:60-74`・`:103-128` である。issue が案として挙げた「`.claude/` の下とルートのドットファイル」は、この定義に含まれる。
    -   理由: `.claude/` の下とルートのドットファイルだけでは、無視される場所に置かれた `.go` ファイル（以後の `make test` で毎回実行される）が検出の対象にならない。
    -   この定義は範囲の規則のために既にあり、再利用すれば、定義を 1 か所に保てる（`CLAUDE.md`「DRY」）。
    -   定義に当たらないファイルは、実行に関わるものであっても対象の外である。それらは残余のリスクとして列挙する（4.2）。
-   **利用者自身の正当な書き込みでも止まる:** 修正のフェーズの間に、利用者が Claude Code の許可の確認に「今後は確認しない」と答えると、Claude Code が `.claude/settings.local.json` を書き換える。この場合も `git-state-changed` で止まり、ガイドの 8 章で対処の手順を案内する。理由: ツールには、この書き込みと攻撃による書き込みを区別できない。区別できない変化は安全側に倒す（0030 `01_requirements.md` 4.2 の方針）。
-   **止まったときの出力は部分の名前だけ:** `git-state-changed` の `parts` に新しい値 `ignored` を加える。どのファイルが違うかは出力しない。
    -   理由: 既存の `parts` も部分の名前だけを示す（`internal/fixprguard/gitstate.go:177-189`）。
    -   ファイル名は攻撃者が選べるので、出力に入れるとセッションに指示文を届ける経路になる（0030 `02_architecture.md` 5.3「ファイル名による出力の汚染」）。
    -   どのファイルが変わったかは、なくなったファイルを含め、利用者がガイドの手順で、ツールの外で調べる（AC-19）。

以下の決定は、要件定義書の作成の中で安全側の既定として選んだ。PR のレビューで確かめてほしい。

-   **古い基準値を受け付けない:** 本タスクの前の版が出力した基準値は受け付けない（AC-03）。理由: 受け付けると、対象のファイル（定義は 3 章）を比べないまま続ける経路が残るからである。
-   **通常のファイルでないものは止めずに記録する:** FIFO・デバイスなど通常のファイルでない対象のファイルは、内容を読まず、種類だけを記録する（AC-08・AC-16）。シンボリックリンクがたどる先が通常のファイルでない場合も同じである。理由: `begin` の時点でそのようなファイルがあるだけで、毎回 `begin` が止まることを避けるためである。種類の変化は検出する。
-   **読み取る内容の大きさに上限を設ける:** 上限は 2 つある。1 つの対象の通常のファイル（シンボリックリンクがたどる先を含む）の大きさの上限と、1 回の記録または比較で読み取る内容の合計の上限である。どちらかを超えると、内容を読み続けずに `git-failed` で止まる（AC-16）。
    -   理由: 上限がなければ、修正のフェーズのエージェントが巨大な疎ファイル（実際のディスクはほとんど使わない）を一瞬で作るだけで、以後の `inspect`・`finish`・`begin` が内容を読み終えられず、止まった種類を出力しないまま実行が進まなくなる。
    -   列挙の上限（AC-16）は、ファイルの数を抑えるが、内容の大きさは抑えない。1 つのファイルの上限だけでは、上限の内の 1 つの疎ファイルを指す対象のファイル（ハードリンクやシンボリックリンク）を短い名前で多数作るだけで、列挙の上限と 1 つのファイルの上限を守ったまま、同じ内容を何度も読ませられる。合計の上限は、この経路を塞ぐ。
    -   上限の値と合計の数え方は設計で決める（H-01）。
-   **ガイド 8 章と 0030 の要件定義書も改める:** issue が挙げた 0030 のアーキテクチャ設計書 5.3 とガイド 7 章に加えて、ガイド 8 章（止まったときの対処）と 0030 の要件定義書 4.2（残余のリスク）も改める（AC-19・AC-20・AC-20a）。理由: 新しい止まり方の対処がガイドになければ、利用者は止まった後に何をすればよいか分からない。0030 の要件定義書 4.2 は、本タスクが縮める残余のリスクそのものを記述している。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   修正のフェーズで、git が無視するコマンドの実行に関わるファイルが作られ、書き換えられ、または削除されたら、commit・push の前に `fixprguard` が止まる。
-   次のセッションや以後の `make test` まで残る書き込みが、利用者に知られないまま残ることを防ぐ。対象は、Claude Code のセッションの設定、環境変数のファイル、無視される場所の `.go` ファイルなどである。
-   止まったときに、利用者が原因を調べて取り除く手順を、ガイドで示す。

### 2.2. スコープ (In Scope)

-   `begin` が取る基準値に、対象のファイル（3 章）の状態を含めること（F-001）。
-   `inspect`・`finish`・`push` が、その状態を基準値と比べ、違えば止まること（F-002）。
-   止まったとき、記録や比較ができないときの出力（F-003）。
-   `fixprguard_guide.md`（日本語版・英語版）と、0030 の要件定義書・アーキテクチャ設計書の残余のリスクの記述を、新しい保証に合わせて改めること（F-004）。

### 2.3. スコープ外 (Out of Scope)

-   **コマンドの実行に関わるファイルの定義に当たらない、無視されるファイル。** 理由: 対象を定義と同じにすることは決定による（1 章）。定義の外には、実行に関わるものも含まれる。それらは残余のリスクとして列挙する（4.2）。
-   **コマンドの実行に関わるファイルの定義そのものの変更。** 定義は範囲の規則と共有し、本タスクでは変えない。
-   **この作業ツリーの外のファイル。** 同じリポジトリのほかの worktree や main のチェックアウトの中のファイル、`~/.claude/settings.json`、シェルの起動ファイルなどである。ただし、対象のファイルであるシンボリックリンクがたどる先は、作業ツリーの外にあっても状態に含める（3 章）。理由: ツールが守るのは、ツールを実行している作業ツリーとその git の状態である。これらのファイルを修正のフェーズのエージェントが書き換えられるかどうかは、Claude Code の権限の確認（利用者の設定）で決まる。git の設定のファイルは、既存の config の値の一覧の比較で検出できる（`internal/fixprguard/configlist.go:17-48`）。ただし、ほかのブランチの `branch` の設定は比べない。
-   **変えて元に戻すこと、確認と実行の間の書き換え。** 0030 と同じく、ある時点だけの確認である（0030 `02_architecture.md` 5.3「確認と実行の間のずれ」）。
-   **`head`・`list`・`fence`・`reply`・`edit-pr`。** 基準値を入力に持たないので、比較しない（0030 `02_architecture.md` 5.3「基準値を持たないサブコマンドの起動前の比較」）。`push` の後の書き込みは検出しない。
-   **`begin` の時点で既にある対象のファイルの内容の検査。** 利用者が自分で置いた `.claude/settings.local.json` や `.envrc` を、`begin` は拒否しない。記録するだけである。
-   **index の stat の偽造、hooks のディレクトリの外のコード。** 0030 の残余のリスクのまま変えない。

## 3. 機能要件 (Functional Requirements)

本書で「**対象のファイル**」とは、次の 2 つをともに満たすファイルをいう。

-   作業ツリーの中にあり、git が無視する。無視するのは `.gitignore`（入れ子のディレクトリのものを含む）、`info/exclude`、グローバルの除外のファイルのどれでもよい。
-   作業ツリーの最上位からのパスが、コマンドの実行に関わるファイルの定義（`fixprguard_guide.md` 6 章の表。`.go` の規則を含む）に当たる。同じ章の「パスの検査」は範囲の規則のためのものであり、ここでは当てはめない。

例: `.claude/settings.local.json`、ルートの `.envrc`・`.env`、`build/x_test.go`、`extension/node_modules/<pkg>/Makefile`。

この判定では、次の 2 点に注意する。

-   **パスで決める。** git がファイルを一つひとつ列挙するかどうかには依らない。無視されるディレクトリの中に入れ子のリポジトリがあり、git がその中身を個別に列挙しない場合でも、その中のファイルが定義に当たれば対象である。
-   **パスはバイト列のまま判定する。** 正規化はしない。不正な UTF-8 や制御文字を含むパスも、判定から外さない。理由: 名前は攻撃者が選べるので、判定から外す規則があれば、それが検出を逃れる経路になる。

対象のファイルの「**状態**」とは、どの対象のファイルがあるかと、各ファイルの次の性質をいう。

-   種類（通常のファイル・シンボリックリンク・FIFO など）
-   内容（通常のファイルの場合だけ）
-   実行の許可
-   シンボリックリンクの先（リンクの文字列）
-   シンボリックリンクがたどる先の種類・内容・実行の許可

シンボリックリンクがたどる先は、それ自身が対象のファイルでなくても（例: 無視されるが定義に当たらない `build/payload`）、作業ツリーの外にあっても、状態に含める。理由: コマンドやセッションが読むのはたどる先の内容である。リンクの文字列だけを記録すると、たどる先の内容を変えるだけで、リンクを変えずに読まれる内容を変えられる。たどる先が通常のファイルでない場合は、通常のファイルでない対象のファイルと同じく、種類だけを含める（1 章の決定）。たどれないリンク（たどる先が存在しない、リンクが循環する、途中のディレクトリを読めない）も読み飛ばさない。たどれないことを状態として記録して、後でたどれるようになったことやたどる先が変わったことを検出するか、AC-16 のとおり `git-failed` で止まる。どちらにするかは設計で決める（H-04）。

更新時刻・所有者・拡張属性は状態に含めない。理由: 更新時刻は、内容を変えなくても git やエディタの操作で日常的に変わり、変わっても実行される内容は変わらないからである。ディレクトリそのもの（空のディレクトリの作成や削除）は対象のファイルではない。その中のファイルが対象である。

### 3.1. 機能一覧

#### F-001: 基準値に対象のファイルの状態を含める

`begin` は、基準値を取るときに、対象のファイルの状態を記録する。`.claude/settings.local.json` は、存在しなくても「存在しない」という状態を記録する。

**Acceptance Criteria**:
- **AC-01**: `begin` の時点で対象のファイルがあっても、`begin` はそれを理由に止まらず、終了コード `0` で基準値を出力する。対象のファイルには、利用者が置いた `.claude/settings.local.json`・`.envrc` や、通常のファイルでないもの（FIFO など）を含む。ただし、読み取れない対象のファイルがある場合や、読み取る内容の大きさが上限（1 つのファイルの上限、または合計の上限）を超える場合は例外で、AC-16 のとおり止まる。比べられない状態を基準値に記録しないよう、安全側に倒すためである。
- **AC-01a**: `make ext-install` の後の作業ツリー（`extension/node_modules/` がある）でも、`begin` は列挙の上限、1 つのファイルの大きさの上限、読み取る内容の合計の上限のどれも理由にして止まらない。
- **AC-02**: `begin` の後に対象のファイルの状態が変わらなければ、`inspect`・`finish`・`push` は対象のファイルを理由に止まらない。終了コードと出力は、`protocol` の値を除いて本タスクの前と同じである。
- **AC-03**: 本タスクの前の版の `begin` が出力した基準値を渡すと、`inspect`・`finish`・`push` はそれを受け付けない。止まり方は、既存の基準値の形の誤りと同じで、終了コード `2` である。

#### F-002: `inspect`・`finish`・`push` が対象のファイルの変化を検出する

`inspect`・`finish`・`push` は、git の状態を基準値と比べるときに、対象のファイルの状態も比べる。違えば `git-state-changed` で止まる。変化を誰が起こしたか（エージェント、build checks、利用者の操作による Claude Code）は区別しない。

**Acceptance Criteria**:
- **AC-04**: `begin` のときに存在しなかった `.claude/settings.local.json` が `begin` の後に作られると、`inspect` は終了コード `1` で止まり、`stop` は `git-state-changed` になる。
- **AC-05**: `begin` のときに存在した `.claude/settings.local.json` の内容が `begin` の後に書き換えられると、書き換えの主体が何であっても、`inspect` は AC-04 と同じく止まる。
- **AC-06**: `begin` のときに存在した対象のファイルが `begin` の後に削除されると、`inspect` は AC-04 と同じく止まる。
- **AC-07**: `.claude/settings.local.json` 以外の対象のファイルについても、AC-04〜AC-06 と同じく止まる。少なくとも次の場合を含む。
    -   ルートの `.envrc`・`.env` が作られる、または書き換えられる。
    -   無視されるディレクトリ（例: `build/`）の中に `.go` ファイルが作られる。
    -   無視されるディレクトリの中の `Makefile` または `*.mk` が作られる、または書き換えられる。
    -   無視されるディレクトリの中に入れ子のリポジトリが作られ、その中に `.go` ファイルがある。
- **AC-08**: 対象のファイルの内容が同じでも、種類・実行の許可・シンボリックリンクの先が変わると、`inspect` は AC-04 と同じく止まる。例: 通常のファイルがシンボリックリンクや FIFO に置き換えられた場合、シンボリックリンクの先が変わった場合、実行の許可だけが変わった場合。
- **AC-08b**: 対象のファイルがシンボリックリンクで、リンクの文字列が変わらなくても、リンクがたどる先の種類・内容・実行の許可が変わると、`inspect` は AC-04 と同じく止まる。たどる先が対象のファイルでない無視されるファイルの場合（例: `.claude/settings.local.json` が `build/payload` を指し、`build/payload` の内容が書き換えられる）と、作業ツリーの外にある場合を含む。
- **AC-08a**: 対象のファイルの更新時刻だけが変わっても（内容・種類・実行の許可・リンクの先・リンクがたどる先が同じ）、`inspect` はそれを理由に止まらない。
- **AC-09**: `begin` の後、`finish` を呼ぶ前に対象のファイルが変わっていると、`finish` は `git-state-changed` で止まる。build checks（`make fmt`・`make test`・`make lint`）を 1 つも実行せず、commit を作らない。
- **AC-10**: build checks の実行中に対象のファイルが変わり（例: `make test` が実行したテストのコードによる）、build checks の後の比較の時点で基準値と違うと、`finish` は `git-state-changed` で止まり、commit を作らない。
- **AC-11**: `finish` の後、`push` を呼ぶ前に対象のファイルが変わっていると、`push` は `git-state-changed` で止まり、push しない。
- **AC-12**: 無視されるが対象のファイルではないファイル（例: ルートの `coverage.out`、`.vscode/settings.json`）が作られ、または書き換えられても、`inspect`・`finish`・`push` はそれを理由に止まらない。
- **AC-13**: `begin` の後に新しい `.gitignore`（入れ子のディレクトリのものを含む）が置かれるか、グローバルの除外のファイルが書き換えられ、それによって git が無視するようになった場所に、コマンドの実行に関わるファイルが作られると、AC-04 と同じく止まる。理由: 新しい `.gitignore` で新しいファイルを隠すことは、0030 が検出しないと記録した経路である（0030 `02_architecture.md` 5.3「無視されるファイル」）。

#### F-003: 止まったとき、記録や比較ができないときの出力

止まったときの出力は、どの部分が違うかだけを示し、対象のファイルの情報を含めない。状態を記録・比較できないときは、一部だけで続けずに止まる。

**Acceptance Criteria**:
- **AC-14**: 対象のファイルの状態だけが基準値と違うとき、AC-04〜AC-11・AC-13 で止まったときの出力では、`parts` は `ignored` だけである。
- **AC-15**: どのサブコマンドの標準出力・標準エラー・基準値にも、対象のファイルの情報を含めない。含めないのは、パス、ファイル名、内容、ファイルごとの digest である。
- **AC-16**: 次の場合、`begin`・`inspect`・`finish`・`push` は既存の `git-failed` で止まる。
    -   対象のファイルの列挙の結果が上限を超える。
    -   列挙の結果（git の出力）が期待する形でない。例: 区切りが壊れている、途中で終わっている、空の項目や重複したパスがある。補正や読み飛ばしはしない。
    -   対象の通常のファイルの内容を読み取れない（例: 読み取りの権限がない）。シンボリックリンクがたどる先の通常のファイルを含む。
    -   対象の通常のファイル（シンボリックリンクがたどる先を含む）の大きさが上限を超える。ツールは上限を超えて内容を読み続けない。
    -   1 回の記録または比較で読み取る内容の合計が上限を超える。同じ内容を指す対象のファイルが多数ある場合を含む。ツールは上限を超えて内容を読み続けない。
    -   対象のファイルがあるディレクトリを読めない。

    一部のファイルだけを記録した基準値を出力することはなく、一部だけを比べて続けることもない。通常のファイルでない対象のファイル（FIFO など）は内容を読まず、大きな通常のファイルや合計の大きな内容は上限で止まるので、ツールは読み取りで待ち続けない。

#### F-004: 文書を新しい保証に合わせる

ガイドと 0030 の文書の保証・残余のリスク・止まったときの対処の記述を、F-001〜F-003 の振る舞いに合わせる。利用者がツールの守りの範囲を誤解せず、止まったときに対処できるようにするためである。

**Acceptance Criteria**:
- **AC-17**: `fixprguard_guide.md` と `fixprguard_guide.ja.md` の 7.1「保証すること」に、次のことが書かれている。git が無視する、コマンドの実行に関わるファイルの作成・書き換え・削除を、`inspect`・`finish`・`push` が基準値と比べて検出する。
- **AC-18**: 同じガイドの 7.2「保証しないこと」の無視されるファイルの項目は、4.2 の「残余のリスク」の一覧と同じ範囲を示している。現在の項目は、無視されるファイル・`.gitignore` やグローバルの除外のファイルで隠したファイル・index の stat の偽造をまとめている。このうち隠したファイルは、対象のファイルについては検出するようになる（AC-13）。そのため項目を分け、隠したファイルのうち、対象のファイルでないものだけが残ることを示す。
- **AC-19**: 同じガイドの 8 章の `git-state-changed` の行は、`parts` の値に `ignored` を含み、その意味と次の対処を示している。
    -   対象のファイルを、ツールの外で一覧にする手順。手順は具体的なコマンドとして書く。ツールはどのファイルが変わったかを示さないので、一覧のすべてを確かめることを書く。更新時刻での絞り込みは、偽造できるので確認の手段にしない。
    -   `begin` の時点にあって、今はなくなった対象のファイルのパスを特定する手順。今の一覧には、なくなったファイルは現れない。そのため利用者は、`begin` の時点の対象のファイルのパスの記録で、修正のフェーズが書き換えられないものと今の一覧とを比べて、なくなったパスを特定できる。手順は具体的なコマンドとして書く。記録を誰が、いつ、どこに残すかは設計で決める（H-08）。記録の内容は、AC-15 のとおり標準出力・標準エラー・基準値に含めない。
    -   少なくとも `.claude/settings.local.json`（特に `hooks`・`permissions`）・`.envrc`・`.env` と、無視される `.go`・`Makefile`・`*.mk` の内容を確かめること。意図しない変更は取り除くこと。
    -   修正のフェーズが作業ツリーに残した変更の扱い。調べたうえで捨てて `/fixpr` をやり直すか、利用者が確かめて手で commit する。変更を残したまま `begin` を実行すると `dirty-work-tree` で止まる。
    -   修正のフェーズの間に利用者が許可の確認に答えたことが原因でも、内容を確かめてから続けること。やり直した `begin` は、その時点の対象のファイルを新しい基準値として受け入れる。
- **AC-19a**: 同じガイドの 8 章の `git-failed` の行は、AC-16 の原因（列挙の上限、1 つのファイルの大きさの上限、読み取る内容の合計の上限、対象のファイルやディレクトリを読み取れない）とその対処を示している。
- **AC-20**: 0030 `02_architecture.md` 5.3「無視されるファイル」の項目は、本タスク（0034）で検出するようになった範囲と、なお残る範囲を示している。残る範囲は、4.2 の「残余のリスク」の一覧と同じである。
- **AC-20a**: 0030 `01_requirements.md` 4.2 の残余のリスクのうち「git が無視するファイル（`.envrc` など）を変えること」の項目は、AC-20 と同じことを示している。

0030 の文書を書き換えるか、本タスクへの参照を追記するか、およびステータスの扱いは、設計で決める（H-06）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   新しい比較が加える時間は、1 回の `/fixpr` の実行時間に対して、利用者が気づかない程度に収める。実行の時間の大半は、LLM の修正のフェーズと、数十秒以上かかる build checks が占める。`CLAUDE.md`「Performance」に従い、数値の上限は定めない。設計で、実際の作業ツリー（`extension/node_modules/` があるもの）で測る（H-01）。

### 4.2. セキュリティ (Security)

-   条件付きのセキュリティガイド（`docs/dev/security.md`）のトリガーに該当する。本タスクは、秘密の値（API キー・Webhook の URL）が置かれる `.envrc`・`.env`（`security.md` §2）の内容を読み、その状態を基準値に含めるからである。同書 §2 の原則として、秘密の値を出力・ログ・エラーメッセージに含めないことを、次のとおり当てはめる。
    -   ツールは対象のファイルの内容を出力しない。ファイルごとの digest も、基準値や出力に含めない（AC-15）。基準値に置くのは、すべての対象のファイルの状態をまとめた値だけである。
    -   標準エラーの診断は、規則の名前だけを示す（`fixprguard_guide.md` 4 章）。
-   **信頼できない入力の境界:** 対象のファイルの名前・内容・種類は、修正のフェーズのエージェント（信頼できない主体）が書いたものでありうる。
    -   名前として受け付ける形: どんなバイト列も受け付け、正規化せずにそのまま定義と照らす（3 章）。判定から外すことはしない。名前は出力しない（AC-15）。
    -   内容として受け付ける形: ツールは内容を解析しない。状態として記録して比べるだけである。
    -   列挙の結果（git の出力）: 受理する形は設計で決める。その形に合わない出力は、補正も読み飛ばしもせずに `git-failed` で止まる（AC-16）。
    -   上限: 列挙の結果に上限があり、上限を超えた場合や読み取れない場合は `git-failed` で止まる。補正したり、一部だけを使ったりはしない（AC-16）。上限の値は設計で決める。1 つの対象の通常のファイル（シンボリックリンクがたどる先を含む）の大きさと、1 回の記録または比較で読み取る内容の合計にも上限があり、超えた場合は内容を読み続けずに `git-failed` で止まる（AC-16、1 章の決定）。これらの上限の値と合計の数え方も設計で決める（H-01）。
    -   シンボリックリンクがたどる先: 作業ツリーの外や、対象のファイルでない場所を指していても、たどる先の状態を記録する（3 章、AC-08b）。たどる先の名前は出力しない（AC-15）。
-   **残余のリスク:** 0030 の残余のリスクの「修正のフェーズのエージェントが、git が無視するファイルを変えること」（0030 `01_requirements.md` 4.2）は、本タスクの後は次の範囲に縮む。これらは引き続き、Claude Code の権限の確認（利用者の設定）に依存する。
    -   コマンドの実行に関わるファイルの定義に当たらない、無視されるファイルを変えること。その中には、後で実行されるか、設定として読まれるものがある。
        -   `build/` の下のバイナリ。たとえば `yt2column-nmhost install` が登録した Native Messaging host は、ブラウザが次の送信で起動する（manifest の `path` はホストの実行ファイルの絶対パス。`internal/nmhost/manifest.go:72-80`・`:265`）。
        -   `extension/node_modules/` の下の JavaScript。`make ext-check` が実行する。
        -   `.vscode/` の下の設定。
        -   無視されるディレクトリの中の `CLAUDE.md`、グローバルの除外のファイルで無視されたルートの `CLAUDE.local.md`。Claude Code が読み込む。
    -   この作業ツリーの外のファイル（2.3）を変えること。同じリポジトリのほかの worktree と main のチェックアウトを含む。
    -   対象のファイルを変えて、確認の前に元に戻すこと。
    -   `push` の後に変えること。
    -   検出の前に効く書き込み。`.claude/settings.local.json` への書き込みが、実行中のセッションに、ツールが止まる前から効く場合がある。ツールが検出するのは、その後の確認の時点である。
    -   まとめた値からの推測。ほかの対象のファイルの内容が分かっていて、`.env` の内容の候補が少なければ、まとめた値から内容を推測できる。基準値はセッションの会話とコマンドの引数に現れるが、それを読めるエージェントは `.env` を直接読むこともできる。
    -   止まった後のやり直しで、利用者が中身を確かめずに `begin` を実行すること。正当な書き込みで止まることがあるので、止まることに慣れて確かめなくなるおそれがある。やり直した `begin` は、その時点の対象のファイルを基準値として受け入れる（AC-19）。削除されたファイルを見落とさないよう、なくなったパスは、修正のフェーズが書き換えられない記録と比べて特定する（AC-19、H-08）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   対象のファイルの状態を記録・比較できないときは、安全側に倒して止まる（AC-16）。列挙の上限、1 つのファイルの大きさの上限、読み取る内容の合計の上限は、利用者の通常の作業ツリー（`extension/node_modules/` があるもの）で `begin` が止まらない値にする（AC-01a）。
-   利用者の正当な書き込み（許可の確認への回答）でも止まる。この場合の対処は、ガイドの 8 章が示す（AC-19）。

### 4.4. 互換性 (Compatibility)

-   古い版の基準値は受け付けない（AC-03）。ツールを変える PR のマージの後には再インストールが要る（`fixprguard_guide.md` 3 章・9 章）。
-   止まった種類の一覧は変えない。`git-state-changed` の `parts` の値に `ignored` が加わる。出力の契約が変わるので、`protocol` の番号を上げる（`fixprguard_guide.md` 9 章）。新しい番号と、コマンド定義の文書（`.claude/commands/`）が渡す `--protocol` をそれに揃える手段は、設計で決める（H-03）。
-   macOS と Linux で、同じファイルに対して同じ判定をする。定義の照合は、範囲の規則と同じく大文字と小文字を区別しない（`internal/fixprguard/scope.go:103-128`）。

### 4.5. 保守性 (Maintainability)

-   コマンドの実行に関わるファイルの定義は、範囲の規則と本タスクの比較とで 1 か所に保つ。
-   完了の時点で、`make test`・`make lint`・`doc-guard`（`go test -tags test ./cmd/yt2column ./cmd/yt2column-server ./cmd/fixprguard ./internal/pipeline`）が通る（issue #424 の完了条件）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   `CLAUDE.md` の「Reject, don't normalize」「Declare, don't infer」「Enforce invariants with the type, not with convention」に従う。基準値は厳密に解析し、補正しない（`internal/fixprguard/gitstate.go:128-145`）。
-   標準ライブラリ以外のモジュールを加えない（`CLAUDE.md`「Dependencies」）。
-   0030 の要件定義書とアーキテクチャ設計書は承認済みの文書である。改めるときは `docs/dev/developer_guide/requirements_process.md`「Editing an approved document」に従う（H-06）。

## 6. 用語集 (Glossary)

-   **基準値**（baseline）: `fixprguard begin` が出力する git の状態の識別子の組（`docs/translation_glossary.md`）。本タスクで、対象のファイルの状態を加える。
-   **コマンドの実行に関わるファイル**: build checks と CI が、設定として読む、またはコンパイル・実行するファイル。定義は `fixprguard_guide.md` 6 章と `internal/fixprguard/scope.go` にある（`.go` の規則を含む）。
-   **対象のファイル**: git が無視するファイルのうち、コマンドの実行に関わるファイルの定義に当たるもの（3 章の冒頭）。
-   **状態**: 対象のファイルの有無と、種類・内容・実行の許可・シンボリックリンクの先・シンボリックリンクがたどる先の種類と内容と実行の許可（3 章の冒頭）。
-   **修正のフェーズ**: `/fixpr` で、エージェントがスレッドの指摘に従ってリポジトリを編集する段階（0030 の用語）。
