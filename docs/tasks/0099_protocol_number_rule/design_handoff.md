# 設計への申し送り（0099）

要件定義の時点で挙がった、設計（`02_architecture.md`）で決める事項。`02_architecture.md` は、各項目にとった方針か、当てはまらない理由を記録する。

## H-01: マージの時点の確かめの置き場所と、`/runpr` で確かめる時点

**懸念:** F-003 の確かめを、Go の道具 `mergepr`（`prepare` か `merge`）に置くか、`/mergepr` と `/runpr` の手順に置くか。`/runpr` では、マージの質問の前に確かめるか、答えの後の `mergepr prepare` で確かめるか。

**なぜ重要か:** ADR-0014 は、決定的な判定をテストのある Go の道具に置くと定める。`/runpr` と `/mergepr` の両方の経路で止めるには、両方が通る `mergepr` に置くのが自然である。一方、`/runpr` の答えの後に止まると、人がマージの質問に答えた後で止まることになる。承認の commit（`/runpr` がマージの直前に行う、文書の `approved` への書き換え）との順序も決める必要がある。

**候補:** `mergepr prepare` で確かめ、`merge` でも `origin/main` が動いていれば確かめ直す。`/runpr` は、マージの質問の前に同じ確かめを読む。

**関連:** F-003（AC-06〜AC-14）

## H-02: 番号を変えた PR の見分け方

**懸念:** 「PR のコミットのどれかが番号を変えた」を、どう見分けるか。

**なぜ重要か:** ブランチに `main` を取り込んだ後は、`origin/main` との差分（3 点の差分）に番号の変更が残らないことがある（AC-08）。差分だけで見分けると、この場合を見落とす。また、番号を変えてから元の値に戻したブランチは、安全側に倒して止まる（AC-06 の「PR の値が `origin/main` の値と同じ場合」）。このとき、人がどう進めるかも決める。

**候補:** `git log origin/main..<head>` のコミットのうち、定数の行を変えたものがあるかを見る（`git log -L` や `-G`）。

**関連:** AC-06、AC-08、AC-09

## H-03: 対象の道具の一覧と、番号の読み方

**懸念:** 確かめの対象の道具（プロトコル番号の定数の場所）をどう持つか。定数をどう読むか。

**なぜ重要か:** 新しい道具を足したときに、対象から漏れないようにする（4.5）。定数が見つからないか読めないときは止まる（AC-13）。

**候補:** `internal/*/` の `const Protocol = <整数>` を探して一覧にする。一覧と、`cmd/*/main.go` の `--protocol` を持つ道具が合うことを、テストで確かめる。

**関連:** AC-01、AC-10、AC-13、4.5
