## 1. 概要 (Overview)

**目的:** 本書は、開発用ツールのプロトコル番号（`--protocol` の番号）を上げる変更について、番号の決め方と確かめ方の要件を定義する。並行するタスクが同じ番号を使い、違う約束が 1 つの番号を共有したまま `main` に入ることを防ぐ。

**背景:**

開発用ツールのうち 3 つは、道具を呼ぶ文書と道具の版が合っているかを、`--protocol` の番号で照合する。今の振る舞いは次のとおりである。

-   番号は、道具ごとの定数として次の場所にある。
    -   `fixprguard`: `internal/fixprguard/types.go:21`（今は `6`）
    -   `codexreview`: `internal/codexreview/types.go:15`（今は `1`）
    -   `chief`: `internal/chief/records.go:28`（今は `1`）
-   道具は、渡された `--protocol` が自分の番号と違えば、何もせずに拒む（`cmd/fixprguard/main.go:253`、`cmd/codexreview/main.go:83`、`cmd/chief/main.go:166`）。古い道具が新しい文書の想定で黙って判定しないようにするためである（[ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md) の「道具は `main` からインストールして使う」）。
-   文書が渡す番号と定数が等しいことは、道具ごとの文書のガードテストが確かめる（`cmd/fixprguard/docs_test.go:351`、`cmd/codexreview/docs_test.go:161`、`cmd/chief/docs_test.go:205` の `TestDocumentedProtocolMatches`）。
-   番号の決め方の規則は、`fixprguard` についてだけある。番号は上げるだけで、一度使った番号を再び使ったり下げたりしない。並行する 2 つのブランチは同じ番号を使わない（`docs/dev/guides/fixprguard_guide.md` §9）。この規則は、タスク 0036 が `3` を使ったため、タスク 0034 が `4` を使った経緯から来ている。マージの時点の確かめはない。
-   番号を上げる PR は、その PR の `/runpr` の前に、その PR のブランチで道具を入れ直す。1 つの道具がすべての worktree で共有されるので、マージまでの間、`main` を取り込んでいないほかの worktree の `/fixpr`・`/runpr` は番号の不一致で止まり、古い規則で判定しない（`docs/dev/guides/fixprguard_guide.md` §3、`docs/dev/guides/chief_guide.md` §2）。
-   2 つのブランチがどちらも番号を 1 から 2 に上げると、git は定数の行の同じ変更を衝突なしにまとめる。文書と定数の番号の照合（上のガードテスト）は、どちらのブランチでも合う。その結果、違う約束の 2 つの変更が、同じ番号 `2` のまま `main` に入る。後から入ったブランチで作った道具は、先に入ったブランチの文書の `--protocol` を受け付け、違う規則で黙って判定しうる。
-   2026-11-17 の時点で、chief の番号を上げる予定のタスクが 4 つある。0092 の PR-7（`docs/tasks/0092_chief_task_workspace/03_implementation_plan.md` §1.5 の決定 14）、0093（`docs/tasks/0093_chief_status_sheet/02_architecture.md` 1.2）、0095（`docs/tasks/0095_chief_transcript_report/02_architecture.md` 4.2）、0096（PR #921 で出している設計書。`main` にはまだない）である。0093 と 0096 は、文書に「2 に上げる」と書いている。
-   PR はすべて `/mergepr` で squash merge する（`.claude/commands/_context.md` の「PR merge method」）。`/runpr` も、マージには `/mergepr` の手順を使う（`.claude/commands/runpr.md` 910 行目の項 2）。`mergepr prepare` は、`origin` を fetch してから材料を作る（`.claude/commands/mergepr.md` 34 行目）。`mergepr merge` は、PR の base の名前が `prepare` のときと同じことだけを確かめ直し、`origin/main` が動いたかは見ない（`internal/mergepr/mergepr.go:249`）。

対応 issue: [#933](https://github.com/isseis/yt2column/issues/933)（関連: タスク [0092](../0092_chief_task_workspace/01_requirements.md)、[0093](../0093_chief_status_sheet/01_requirements.md)、[0095](../0095_chief_transcript_report/01_requirements.md)、[0096](../0096_chief_question_transcript/01_requirements.md)）

**本書の記述範囲:** 本書は、規則の中身、規則の対象、マージの時点の確かめで人が見る振る舞いを定める。次の事項は設計（`02_architecture.md`）で決める。

-   マージの時点の確かめを、Go の道具（`mergepr`）と `/mergepr`・`/runpr` の手順のどちらに置くか
-   番号を変えた PR（3 章）を見分ける方法と、定数の読み方
-   マージの直前の確かめ直しで止まったときの、`/runpr` の承認の commit の扱い
-   CLAUDE.md の中で規則を置く節
-   テストの手段

要件の段階で挙がった設計事項は [design_handoff.md](design_handoff.md) に申し送る。

**issue #933 で決めたこと:**

-   **タスク文書（要件定義書・設計書・計画書）には、上げた後の番号を書かず、「`main` の値 + 1」と書く（F-001）。** 先にマージされたタスクがその番号を使うと、後のタスクの文書と実装が食い違うためである。並行するタスクが増えるほど、この衝突は起きやすい。ADR: [ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md) を更新する（下の「要件定義の際に決めたこと」の ADR の項にまとめる）。
-   **番号は、実装の時点で `origin/main` の値に 1 を足して決める（F-002）。** 理由は上の項と同じである。ADR: ADR-0014 を更新する。
-   **マージの時点で、PR の番号が `origin/main` の値 + 1 になっているかを確かめ、食い違っていればマージせずに番号を直す（F-003）。** 実装の時点の後に、ほかのタスクが同じ番号でマージされうるためである。ADR: ADR-0014 を更新する。
-   **進行中の各タスク（0092・0093・0096）の文書は直さない。** それぞれのタスクで直すためである。ADR: なし（範囲の決定で、このタスクの中で閉じるため）。

**要件定義の際に決めたこと（2026-11-17）:**

-   **進め方は通常の進め方にする。対象外の判断は「対象外ではない」で、上書きはない。** ADR: なし（進め方の選択はこのタスクの中で閉じるため）。
    -   対象外ではない理由は 3 つある。(1) 開発用ツールの信頼の境界を変えない。(2) `docs/dev/security.md` の規則と前提を変えない。(3) 外部の依存を足さない（[requirements_process.md](../../dev/conventions/requirements_process.md) の「Simple Process」の「Excluded changes」）。
    -   通常の進め方にする理由は 3 つある。(1) 変更が CLAUDE.md、ADR-0014、`fixprguard_guide.md`、マージの経路（`/mergepr`・`/runpr`）に及ぶ。(2) ADR-0014 の決定を変える。(3) マージの時点の確かめを道具に入れれば、新しい仕組みになる。
-   **規則の対象は、道具とそれを呼ぶ文書の版を照合する番号（`--protocol` の番号）とする。今あるのは `fixprguard`・`codexreview`・`chief` の 3 つで、今後この番号を持つ道具にも当てはめる（F-001〜F-003）。** issue が挙げた番号と同じ性質を持ち、並行するタスクが上げうる番号だからである。ADR: ADR-0014 を更新する。
    -   中間生成物のファイル形式の版（`internal/artifact/artifact.go:30` の `artifactVersion`）は対象にしない。CLI の再開用の手元のファイルの版で、文書と道具の照合に使う番号ではないためである。
    -   Native Messaging のホストの返信の版（`internal/nmhost/relay.go:49` の `protocolVersion`、`extension/src/core/native.ts:18` の `hostReplyVersion`）は対象にしない。[ADR-0048](../../dev/adr/0048-extension-only-generation.md) で廃止が決まった経路の番号だからである。
-   **マージの時点の確かめは、人の手順に頼らず、マージが必ず通る経路に入れる。食い違えばマージせずに止まり、`origin/main` の値・PR の値・期待する値を示す。番号の直しは自動では行わない（F-003）。** 人の手順だけに頼ると、確かめを忘れたときに、上の「背景」の、気づかれない衝突が起きるためである。`/runpr` が番号と文書の `--protocol` を書き換えて自動で直す案は採らない。`/runpr` を受け持つのは OpenCode のモデルで（`_context.md` の「Command routing」の `runpr` の行）、複数の文書を書き換えさせると誤りうるためである。CLAUDE.md に人の手順として書くだけの案も採らない。忘れたときに防げないためである。ADR: ADR-0014 を更新する。
-   **確かめは、`/runpr` からのマージにも、`/mergepr` を単独で使うマージにも当てはめる（F-003）。** どちらの経路のマージでも同じ衝突が起きるためである。`/runpr` だけに当てはめる案は採らない。`/mergepr` を直接使うと確かめが抜けるためである。ADR: ADR-0014 を更新する。
-   **番号の決め方の正本は CLAUDE.md に置く。`fixprguard_guide.md` §9 は、番号の決め方を CLAUDE.md への参照に置き換え、`fixprguard` に固有の「いつ上げるか、上げなくてよい例外」を残す（F-004）。** 同じ規則を 2 か所に書かないためである。ガイドの文をそのまま残し、CLAUDE.md に規則を足すだけにする案は採らない。2 つの規則が離れて食い違いうるためである。ADR: ADR-0014 を更新する（決定の項に、正本の場所として書く）。
-   **実装の時点の決め方は CLAUDE.md の規則だけに書き、`/runplan` の定義（`.claude/commands/runplan.md`）には手順を足さない（F-002）。** `/runplan` は CLAUDE.md に従って動き、決め違えてもマージの時点の確かめで止まるためである。ADR: なし（コマンドの定義の細部のため）。
-   **ADR は新しく作らず、ADR-0014 を更新する。** `--protocol` の番号の扱いは、ADR-0014 の「道具は `main` からインストールして使う」の決定の一部だからである。開発の進め方の方針の ADR として新しく作る案は採らない。同じ主題の決定が 2 つの ADR に分かれるためである。ADR: [ADR-0014](../../dev/adr/0014-deterministic-checks-in-go.md) を本 PR で更新した。
-   **道具は、パッケージ `internal/<名前>` の `Protocol` 定数で見分ける。`origin/main` にその定数がなければ、期待する値は `1` とする。道具が新しい場合も、既存の道具に `--protocol` を足す場合も同じである（AC-10）。** 「`main` の値 + 1」の規則を、そのまま当てはめるためである。ADR: なし（規則の端の場合で、ADR-0014 の更新に収まるため）。
-   **「`main` の値 + 1」にすると、マージの前には、並行するブランチが同じ番号を共有する。この危険は受け入れて明記する。** 共有している間は、あるブランチから入れた道具が、ほかのブランチの文書の `--protocol` を受け付け、違う規則で黙って判定しうる。今の `fixprguard_guide.md` §9 の「並行する 2 つのブランチが同じ番号を使わない」は、これを防ぐ規則だった。危険が起きるのは、同じ道具の番号を上げる 2 本が同時にあり、片方の版を入れている間に限られる。ブランチごとに一意の番号を配る仕組みは、issue の範囲を超える。`fixprguard_guide.md` §3 の「古い規則で判定することはない（fail-closed）」の記述と、ADR-0014 の「結果」を、これに合わせて直す。ADR: ADR-0014 を更新する。
-   **確かめは、`gh pr merge` の直前に `origin` を取り直して、もう一度行う。残る数秒の時間差は受け入れて明記する。** `/runpr` では、人がマージの質問に答えるまで時間が空く。その間に別の PR が同じ番号でマージされると、最初の確かめだけでは防げないためである。CI の必須チェックと「ブランチを最新にする」設定で閉じる案は採らない。すべての PR で、マージの前に更新が要るためである。ADR: ADR-0014 を更新する。
-   **番号を上げてから元に戻した PR（履歴では変えたが、値は `origin/main` と同じ）は、安全側に倒して止める。直し方として、`origin/main` の上で履歴をまとめ直すことを示す。** `main` を取り込んで、上げた番号が吸収された PR と見分けにくく、めったに起きないためである。ADR: なし（規則の端の場合のため）。
-   **「一度使った番号」は、`main` で使った番号を指す。** マージされずに閉じた PR の番号は、再び使ってよい。ADR: なし（語の定義のため）。
-   **0095 の文書も、0092・0093・0096 と同じく、本タスクでは直さない。** issue の「含めない」は 3 つを挙げるが、0095 も `Protocol` を上げる設計を持ち、それぞれのタスクで直すという理由が同じだからである。ADR: なし（範囲の決定のため）。
-   **`/runpr` は、マージの質問の前に確かめる。そこで止まったときは、承認の commit も push もしない（AC-14）。** 人がマージの質問に答えた後で止まらないようにするためである。マージの直前の確かめ直し（AC-16）で止まったときの、すでに push した承認の commit の扱いは、設計で決める（design_handoff.md の H-01）。ADR: なし（`/runpr` の手順の細部のため）。
-   **`main` を取り込んだマージのコミットは、その結果の番号がどの親の番号とも違うときだけ、番号を変えたものとする（3 章の「番号を変えた PR」）。** ほかの PR が番号を上げた後に `main` を取り込んだだけの PR を、止めないためである（AC-09）。ADR: なし（語の定義のため）。
-   **PR の base が `main` でないときは、確かめられないものとして止める（AC-13）。** 本書の規則は `origin/main` と比べるもので、今のコマンドは `main` を base にした PR だけを作るためである（`.claude/commands/_lib/task-pr-handoff.md` の Part B の `--base main`）。ADR: なし（規則の端の場合のため）。

## 2. 目的とスコープ (Goals and Scope)

### 2.1. 目的 (Goals)

-   並行するタスクが同じプロトコル番号を使ったまま `main` に入ることを、マージの時点で止める。
-   タスク文書が、実装の前に、上げた後の番号を決め打ちしないようにする。
-   番号の決め方の規則を、3 つの道具に共通する 1 か所（CLAUDE.md）に置く。

### 2.2. スコープ (In Scope)

-   タスク文書の書き方の規則（F-001）
-   実装の時点の番号の決め方の規則（F-002）
-   マージの時点の確かめ（F-003）
-   CLAUDE.md への規則の記述、`fixprguard_guide.md` §9 の参照への置き換え（F-004）
-   ADR-0014 の更新（本 PR で行う）

### 2.3. スコープ外 (Out of Scope)

-   進行中の各タスク（0092・0093・0095・0096）の文書の直し。それぞれのタスクで行う（issue #933 の「含めない」）。
-   番号を上げるべき変更かどうかの判断（いつ上げるか）。道具ごとの今の規則のまま変えない（`fixprguard_guide.md` §9 の 3 つの条件など）。
-   番号を上げるべき変更なのに上げなかった PR を見つけること。issue #933 が扱うのは、上げた番号の衝突だけだからである。
-   中間生成物のファイル形式の版と、Native Messaging のホストの返信の版（「要件定義の際に決めたこと」）。
-   食い違ったときの番号の自動の直し（「要件定義の際に決めたこと」）。
-   CI で確かめること（「要件定義の際に決めたこと」の、マージの直前に確かめ直す項）。

## 3. 機能要件 (Functional Requirements)

本書では、次の用語を使う。

-   **プロトコル番号**: 開発用ツールと、それを呼ぶ文書の版を照合する番号。文書は `--protocol` で渡し、道具は自分の番号と違えば拒む。今は `fixprguard`・`codexreview`・`chief` の 3 つが持つ。
-   **道具**: プロトコル番号を持つ開発用ツール。パッケージ `internal/<名前>` の `Protocol` 定数で見分ける。
-   **PR のコミット**: PR のブランチにあり、マージの時点の `origin/main` にないコミット。ブランチに `main` を取り込んだマージのコミットも含む。
-   **番号を変えた PR**: ある道具のプロトコル番号を、PR のコミットのどれかが変えた PR。マージのコミットでないコミットは、親と番号が違えば変えたものとする。マージのコミットは、その結果の番号がどの親の番号とも違うときだけ、変えたものとする。定数が現れることと消えることも、変えたものに数える。
-   **期待する値**: マージの時点の `origin/main` の、その道具のプロトコル番号に 1 を足した値。`origin/main` にその道具の `Protocol` 定数がなければ、`1` とする。

### 3.1. 機能一覧

#### F-001: タスク文書の書き方

プロトコル番号を上げる変更のタスク文書には、上げた後の番号を書かない。

**Acceptance Criteria**:
-   **AC-01**: CLAUDE.md は、規則の対象を「道具と、それを呼ぶ文書の版を照合するプロトコル番号（`--protocol` の番号）」と性質で定め、今の対象として `fixprguard`・`codexreview`・`chief` の 3 つを挙げる。
-   **AC-02**: CLAUDE.md は、タスク文書（要件定義書・設計書・計画書・申し送りの文書）には上げた後の番号を書かず、「`main` の値 + 1」と書くと定める。今の値を、今の振る舞いとして `file:line` とともに挙げることは妨げない。
-   **AC-03**: CLAUDE.md は、今の仕様を持つ文書（コマンドの定義、`docs/dev/guides/` の手引き）には、今までどおり実際の番号を書くと定める。

#### F-002: 実装の時点の番号の決め方

プロトコル番号を上げる PR は、実装の時点の `origin/main` の値から番号を決める。

**Acceptance Criteria**:
-   **AC-04**: CLAUDE.md は、番号を上げる PR が、実装の時点の `origin/main` の値にちょうど 1 を足した値にすると定める。番号は上げるだけで、`main` で一度使った番号を再び使ったり下げたりしないことも定める。
-   **AC-05**: CLAUDE.md は、マージの時点の確かめ（F-003）があることと、止まったときの直し方（AC-12・AC-15）を挙げる。

#### F-003: マージの時点の確かめ

`/mergepr` でのマージは、`/runpr` から使うときも単独で使うときも、次のとおりに振る舞う。

**Acceptance Criteria**:
-   **AC-06**: 番号を変えた PR で、PR の head のその道具の番号が期待する値と違うとき、マージしない。食い違いには、PR の値が `origin/main` の値と同じ場合、期待する値より 2 以上大きい場合、小さい場合のすべてを含む。
-   **AC-07**: AC-06 で止まるとき、利用者に、道具の名前、マージの時点の `origin/main` の値、PR の head の値、期待する値、直し方（AC-12）を示す。
-   **AC-08**: 2 つのブランチが同じ番号に上げ、先に一方がマージされた後、もう一方のブランチに `main` を取り込んだ場合（`origin/main` との差分に番号の変更が残らない場合）も、AC-06 のとおりにマージしない。
-   **AC-09**: どの道具の番号も変えていない PR は、この確かめで止まらず、利用者に追加の操作を求めない。ほかの PR が番号を上げた後に、`main` を取り込んだだけの PR も含む。
-   **AC-10**: `origin/main` にその道具の `Protocol` 定数がない PR（道具を足す PR と、既存の道具に `--protocol` を足す PR）は、番号を期待する値 `1` と比べる。PR が `Protocol` 定数を消す道具は確かめない。
-   **AC-11**: 1 つの PR が 2 つ以上の道具の番号を変えたときは、道具ごとに確かめる。どれか 1 つでも食い違えばマージせず、食い違ったすべての道具について AC-07 の値を示す。
-   **AC-12**: 直し方として、次の手順を示す。PR のブランチに `origin/main` を取り込む。その道具の番号を期待する値にする。コマンドの定義と手引きに書いた番号（`--protocol` の値を含む）を同じ値にする。直したものを commit して push する。その PR のブランチで道具を入れ直す（`make install-<道具>`）。その後、マージをやり直す（`/runpr` から使ったときは `/runpr` を、単独のときは `/mergepr` を実行し直す）。
-   **AC-13**: 確かめに要るものを読めないときは、マージせずに止まり、読めなかったものを示す。読めないものとして扱うのは、次の場合である。(1) `origin/main` の取得に失敗した。(2) PR のコミットの読み取りに失敗した。(3) PR の head に `Protocol` 定数が見つからない（AC-10 の、PR が定数を消す場合を除く）。(4) 定数が、1 以上の 10 進の整数（先頭の `0` も区切りの `_` も持たない）として読めない。(5) 1 つの道具に定数が 2 つ以上ある。(6) PR の base が `main` でない。読めないものを、番号を変えていないものとして扱わない。
-   **AC-14**: `/runpr` は、マージの質問の前に確かめる。AC-06 か AC-13 で止まったとき、マージの質問をせず、承認の commit も push もしない。PR をマージせず、AC-07 または AC-13 の内容と、直した後に `/runpr` をもう一度実行することを報告する。
-   **AC-15**: 番号を変えた PR で、PR の head の値が `origin/main` の値と同じとき（上げた番号が `main` の取り込みで吸収された場合と、上げてから元に戻した場合）は、AC-12 の直し方に加えて、番号を上げないのであれば `origin/main` の上で PR の履歴をまとめ直す（番号を変えたコミットを残さない）直し方を示す。
-   **AC-16**: マージを GitHub に頼む直前に、`origin/main` を取り直し、AC-06〜AC-13 の確かめをもう一度行う。最初の確かめの後に `origin/main` が動いて食い違ったときは、マージせずに AC-07 の内容を示す。確かめ直しで AC-13 に当たったときも、マージせずに AC-13 の内容を示す。

#### F-004: 規則の置き場所

**Acceptance Criteria**:
-   **AC-17**: 番号の決め方（AC-02・AC-04）の正本は CLAUDE.md にある。
-   **AC-18**: `docs/dev/guides/fixprguard_guide.md` の差分は、次の 2 点に限る。(1) §9 で、番号の決め方を述べる文（番号は上げるだけで再び使ったり下げたりしないこと、並行する 2 つのブランチが同じ番号を使わないことと、その理由と経緯）を、CLAUDE.md の規則への参照に置き換える。(2) §3 の「どちらも、古い規則で判定することはない（fail-closed）」を、並行するブランチが同じ番号を共有する間はこの限りでないこと（AC-20）を述べる文に直す。
-   **AC-19**: `--protocol` を受け付ける道具のうち、マージの時点の確かめの対象にないものがあれば、`make test` が失敗する。
-   **AC-20**: CLAUDE.md は、受け入れた危険として次の 2 つを挙げる。(1) マージの前は、同じ道具の番号を上げる並行するブランチが同じ番号を共有し、片方のブランチから入れた道具が、もう片方の文書の `--protocol` を受け付けうること。(2) マージの直前の確かめ直し（AC-16）と GitHub のマージの間の数秒に、ほかの PR が同じ番号でマージされうること。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1. 性能 (Performance)

-   N/A。確かめが足すのは、マージのたびの数回の `git` の読み取りと取得だけである。

### 4.2. セキュリティ (Security)

-   N/A。条件付きの手引き（`docs/dev/security.md`）の対象（`yt-dlp` の起動、API キー、キャッシュのディレクトリ、LLM への送信、信頼できない文の埋め込み）に当たらない。確かめが読むのは、利用者自身の PR のブランチと `origin/main` である。`mergepr` は悪意のある PR の内容を防がない（`docs/dev/guides/mergepr_guide.md` §1）。ただし、読めない値は受け入れない（AC-13）。

### 4.3. 信頼性・可用性 (Reliability/Availability)

-   確かめは安全側に倒す。読めないか判断できないときは、マージしない（AC-13）。
-   受け入れる危険は AC-20 の 2 つである。
-   まだマージされていないブランチ A の上に作ったブランチ B は、A のコミットを PR のコミットとして持つ。A が squash merge された後、B は番号を変えていなくても止まりうる。今のコマンドは、ブランチを `origin/main` から作る（`.claude/commands/_lib/task-pr-handoff.md` の Part A）ので、めったに起きない。止まったときは AC-15 の直し方で進める。

### 4.4. 互換性 (Compatibility)

-   確かめを入れた版の道具がマージされた後、利用者は道具を入れ直す（ADR-0014 の「道具は `main` からインストールして使う」）。入れ直した後は、進行中のタスク（0092・0093・0095・0096）の PR も、番号を変えていればこの確かめを受ける。それらの文書の「2 に上げる」のような記述は、それぞれのタスクで直す（2.3）。

### 4.5. 保守性 (Maintainability)

-   プロトコル番号を持つ道具を新しく足したとき、その道具も確かめの対象になる（AC-19。仕組みは design_handoff.md の H-03）。

## 5. 制約条件 (Constraints)

-   `docs/dev/project_overview.md` の「決定済みの方針」「前提・制約」に従う。
-   判定は、テストのある Go の開発ツールに置くことを優先する（ADR-0014 の「決定的な判定はエージェントに任せず、テストのある Go の開発ツールに置く」）。
-   `/mergepr` のマージは、今までどおり利用者の明示的な承認を必要とする（CLAUDE.md の「Tool Execution Safety」）。
-   文書のテストは、値・構造・実行できる例だけを確かめる（ADR-0016）。CLAUDE.md の規則の文の意味は、PR のレビューで読む。
