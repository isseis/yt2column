## 1. 設計の全体像

本タスクでは、`internal/chief` のテストとサブテストのうち、互いに独立したものに `t.Parallel()` を入れ、同時に実行させる（[01_requirements.md](01_requirements.md) F-001）。テストの判定は変えない（F-002）。製品のコードも変えない（F-004）。変更前と変更後の比較は、本タスクの `_checks/` に置く一時スクリプトで行う（AC-01・AC-03・AC-05）。

**設計原則:**

-   **独立したテストだけを並列にする。** 独立したテストとは、次の 2 つを満たすテストである。
    -   プロセス全体の状態に結果が左右されず、その状態を書き換えもしない。プロセス全体の状態とは、環境変数、作業ディレクトリ、umask、パッケージの変数（代入と、スライスやマップの中身の書き換えの両方）である。
    -   ほかのテストと共有するファイルやディレクトリに書かない。
-   **確かめる内容を変えない。** 並列にするために変えてよいのは、テストの実行の仕方だけである。`t.Parallel()` の呼び出しを足すこと、親テストの共有の値をサブテストごとに作り直すこと、親の `defer` を `t.Cleanup` に移すことがこれに当たる。判定の式と入力の値は変えない。
-   **新しい仕組みを作らない。** テストのヘルパーの新しい部品（フィクスチャの複製など）は足さない。

**設計の際に決めたこと（2026-11-26）:**

-   速くする手段は `t.Parallel()` だけとする。テンプレートのリポジトリを複製してフィクスチャを速く作る仕組み（issue の改善方針 2）は採らない。
    -   理由: 要件書 1 章の計測では、パッケージ全体を並列にすると、最も長い 1 つのテスト（`TestReadClaudeReport`、約 22 秒）が時間の下限になる。変更前の 118.3 秒の 50% は約 59 秒なので、並列化だけで届く見込みがある。複製の仕組みは、テストのヘルパーに新しい部品を足し、その部品が正しく複製することにも責任を負うことになる（`CLAUDE.md`「YAGNI」）。
    -   AC-01 に届かなかったときは、その時点で決定の変更として人に相談する（`docs/dev/conventions/requirements_process.md`「Editing an approved document」）。
    -   採らなかった案: 並列化とフィクスチャの複製を両方行う案。
    -   2026-11-26 に人が選んだ。
    -   ADR: なし。本タスクの中で閉じる。
-   `t.Parallel()` は、issue が挙げた 6 つのファイルに限らず、パッケージ全体の独立したテストとサブテストに入れる。
    -   理由: issue の 6 つのファイル（`markers_parity_test.go`・`autosend_test.go`・`transcript_test.go`・`removal_test.go`・`snapshot_test.go`・`conflict_test.go`）の合計は約 67 秒で、残りの約 51 秒はほかのファイルにある（要件書 1 章の計測。`conflict_test.go` は 2.5 秒）。6 つのファイルだけを並列にすると、残りが直列のまま約 51 秒かかり、50% に届かない見込みが高い。

    -   採らなかった案: `privatefile` に排他を足して umask の変更を直列にする案（製品のコードを変え、F-004 を変えることになる）。`MkdirBelow` を呼ぶテストをすべて直列に残す案（fake の世界を使う大半のテストが直列に残り、50% に届かない見込み）。

### 3.2. 並列にするテストと直列に残すテスト

-   トップレベルのテストの関数の頭で `t.Parallel()` を呼ぶ。
-   表のテストの `t.Run` の中でも、サブテストが互いに独立なら `t.Parallel()` を呼ぶ。`go.mod` の Go の版は 1.26.5 である。Go 1.22 からは、ループ変数が繰り返しごとに別の変数になるので、ループ変数を写し直す必要はない。
-   **直列に残す**とは、そのテストも、その祖先のテストも `t.Parallel()` を呼ばないことである。並列の親の下で `t.Parallel()` を呼ばないサブテストは、ほかの並列のテストと同時に走りうるので、直列に残したことにならない（`go doc testing.T.Parallel` と、Go の `testing` パッケージの `checkParallel` のコメント）。
-   次のテストは直列に残す。
    -   **環境変数:** `t.Setenv` を直接呼ぶテストと、`repo.RealCommands()`（`internal/chief/test_helpers.go:134-137`）を通して呼ぶテスト。Go の `testing` パッケージでは、そのテストか祖先のどれかが `t.Parallel()` を呼んでいると、`t.Setenv` は panic する（`go doc testing.T.Setenv`）。
    -   **umask:** わざと `0o600`・`0o700` より広い権限でファイルかディレクトリを作るテストと、作ったものの権限を確かめるテスト（1 章の umask の決定）。これらのテストは、冒頭で umask を `0o022` にし、終わりに元へ戻す（1 章）。コミット `6c60f9f8` では、`grep -n '0o644\|0o755\|0o666\|Perm()'` が `records_test.go` の 4 行（`:285`・`:427`・`:945`・`:1107`）に合う。どれが umask に左右されるかは、実装の際に確かめる（`:285` は `os.Chmod` で、umask に左右されない）。
    -   **そのほかのプロセス全体の状態:** `os.Setenv`・`os.Chdir` を呼ぶテストと、パッケージの変数を書き換えるテスト。コミット `6c60f9f8` では、テストの中で `os.Setenv`・`os.Chdir`・`t.Chdir` を呼ぶ箇所はなかった（`grep`。`TestMain` の中の `isolateTestPath` を除く）。
    -   3.3 節で、並列にできないと判断したテスト。

Go の `testing` パッケージは、`t.Parallel()` を呼んだトップレベルのテストを一時停止させ、直列のトップレベルのテストがすべて終わってから再開する（`go doc testing.T.Parallel`）。そのため、直列に残したトップレベルのテストは、並列のテストと同時には走らない。`t.Setenv` が書き換えた環境変数を並列のテストが読むことも、並列のテストの umask の競合が直列のテストに及ぶこともない。

### 3.3. 並列にするときに確かめること

テストを並列にする前に、テストごとに次のことを確かめる。

-   **親テストの共有の値。** 親テストが作った値（一時ディレクトリ、レコーダ、fake の世界）を、サブテストが書き換えないか確かめる。書き換えるなら、その値をサブテストの中で作るよう移し、判定と入力はそのままにする。移せないなら、その親テストのサブテストは並列にしない。
-   **親の本体の順序。** サブテストが `t.Parallel()` を呼ぶと、親の関数は、サブテストが走る前に返る。親の `defer` と、`t.Run` のループの後のコードは、サブテストより先に走る。たとえば `TestReadClaudeReport` は、ループの後で共有の `config` に書き、判定を行う（`internal/chief/transcript_test.go:115-128`）。サブテストが頼る `defer` は `t.Cleanup` に移す。ループの後のコードがサブテストと同じ値を使うなら、サブテストを並列にしない。
-   **パッケージの変数の中身。** テストが、パッケージの変数のスライスやマップの中身を書き換えないか確かめる。
-   **決まった名前のファイル。** `os.TempDir()` の下の決まった名前など、テストの間で同じパスに書かないか確かめる。
-   **製品のコードが変えるプロセスの状態。** テストが呼び出す製品のコードが、プロセス全体の状態を変えないか確かめる。コミット `6c60f9f8` で見つかったのは `privatefile.MkdirBelow` の umask だけで、その扱いは 1 章と 3.2 節のとおりである。
-   **時間に依存する判定。** 実際の時間で待つテストが、並列の負荷で遅れて失敗しないか確かめる。失敗するなら、そのテストは直列に残す。判定の時間は変えない（F-002）。

直列に残したテストとその理由、共有の値を移したテストと `defer` を `t.Cleanup` に移したテストは、実装の計画書に記録する。後の 2 つは、`t.Parallel()` を足す以上の変更なので、PR のレビューで読む。

### 3.4. 共有の状態

-   `TestMain`（`internal/chief/main_test.go:12-24`）は、`isolateTestPath`（`internal/chief/test_helpers.go:43-75`）でプロセスの `PATH` を空のディレクトリに向けてから `m.Run` を呼ぶ。`testToolsDir` と `testBash`（`internal/chief/test_helpers.go:29-35`）は、その中で一度だけ書かれ、テストは読むだけである。
-   `newTestRepo`（`internal/chief/test_helpers.go:107-126`）は、テストごとの `t.TempDir()` の下にリポジトリと `HOME` を作る。git には `testEnv`（`internal/chief/test_helpers.go:85-96`）の環境だけを渡し、プロセスの環境変数を書き換えない。そのため、別々のテストのリポジトリは互いに独立である。

### 3.5. 比較の一時スクリプト

`docs/tasks/0128_chief_test_speedup/_checks/compare.sh` は、AC-01・AC-03・AC-05 を 1 回の実行で判定する。言語はシェル（bash）とし、`git`・`tar`・`go`・`jq`・`awk` を使う。`jq` は `make test` が前提にしている（`CLAUDE.md`「Development Notes」）。

-   **入力:** 引数はとらない。作業ツリーのトップレベルで、変更をコミットし終えた、きれいな作業ツリーで実行する。`git fetch origin main` は実行者が先に行う。root でない利用者で実行する（`transcript_test.go:72`・`maintask_test.go:313`・`trace_test.go:232` のテストは、root で実行すると `skip` になる）。
-   **変更前の木:** `git merge-base origin/main HEAD` のコミットを `git archive` で一時ディレクトリに展開する。`git worktree` は使わない。`internal/chief` のテストは、リポジトリのファイルを相対パスで読む（`internal/chief/task_test.go:34`、`internal/chief/markers_parity_test.go:17`、`internal/chief/runpr_next_doc_test.go:18` など）。`.git` のない展開した木でもテストが走ることを前提とし、走らなければ判定できないものとする。
-   **計測:** 変更前の木と作業ツリーの `HEAD` で、`go test -tags test -race -count=1 -json ./internal/chief` を続けて実行し、それぞれの出力を一時ディレクトリに保存する。
-   **判定:**
    -   AC-01: 2 つの出力から、パッケージの `pass` の行（`Test` を持たない行）の `Elapsed` を取り出し、変更後が変更前の 50% 以下であることを確かめる。
    -   AC-03: 2 つの出力から、`pass` のテストとサブテストの名前を並べて比べ、同じであることを確かめる。どちらかに `fail` か `skip` の行があれば、判定が通らないものとする。
    -   AC-05: `git diff --name-only <マージベース> HEAD` の各行が、要件書 AC-05 のパスに合うことを確かめる。
-   **出力:** 2 つの経過時間とその比、2 つのコミット、各判定の結果を表示する。表示は、計画書の検証の記録と PR の説明に写す（AC-02）。
-   **終了コード:**
    -   すべての判定が通れば 0、どれかが通らなければ 1 とする。
    -   `go test` がテストの失敗で 0 以外を返しても、出力にパッケージの `pass` か `fail` の行があれば、出力から判定する。テストの失敗は AC-03 の判定が通らないものとして 1 になる。
    -   判定できないとき（コマンドの失敗、パッケージの行のない出力、作業ツリーの変更）は 2 とする。判定できないときに 0 を返さない。
-   **後始末:** 一時ディレクトリは、終了の仕方によらず消す。作業ツリーとリポジトリには何も書かない。

このスクリプトは一時スクリプトであり、`docs/dev/conventions/requirements_process.md`「Temporary scripts (`_checks/`)」の 4 つの性質だけを持つ。それを超える備え（ほかの環境への対応、敵対的な入力への備え）は要らない。読む入力は、同じ実行者が同じ機械で作った `go test -json` の出力と `git` の出力だけである。実行するのは、PR を作る前の 1 回と、レビューでスクリプトかテストが変わったときだけである。
