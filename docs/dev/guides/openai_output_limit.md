# OpenAI の出力の上限の測り直し

リクエストが出力の上限をプロバイダに任せるとき（`MaxOutputTokens` が 0）、OpenAI のアダプタは自身の既定の `max_output_tokens`、すなわち `internal/llm/openai/request.go` の定数 `defaultMaxOutputTokens` を送る。この上限は推論と回答を合わせたトークン数にかかる。記事を書く 3 つの工程（生成、字数の調整、検証・推敲）は、どれもこの既定値を使う。値は、測定した出力の大きさと出力の速さに基づくので、出力を生み出す構成が変われば古くなりうる。本書では、いつ測り直すか、どう測るか、何を更新するかを説明する。値も測定値も本書には転記しない。それらはコードと、「現在の記録」で挙げる記録にある。

## 測り直すとき

OpenAI を使う構成の 3 つの工程のいずれかで、次のどれかが変わったときに測り直す。

- テンプレート。
- effort（`internal/config/config.go` の `defaultOpenAIEffort` の変更を含む）。
- モデル（料金表の候補の 2 モデル `gpt-6-astra`・`gpt-6.1-sol` の追加・削除を含む）。
- 処理方式（`service_tier`）とプロンプトキャッシュの保持期間。どちらも `internal/llm/openai/request.go` の定数で固定している。

ほかに、使う中で打ち切り（`llm.ErrTruncated`）や時間切れが続くときも、測り直して原因を確かめる。

## 費用と承認

測定は実際の OpenAI API を呼び、課金される。実行の前に、呼び出しの回数・予算の上限・使うキーを示して人間の承認を得る（`CLAUDE.md` の "Tool Execution Safety"）。以前の測定の承認は流用しない。キーは本番の `OPENAI_API_KEY` ではなく、利用上限を設けたテスト用のキーを使う。自動で送り直さない。

## 測り方

現在の記録は、製品のコードを変えずに測った。測定の時点のコミットの作業用のコピーに測定用の入口を置き、既存の字幕のパーサとプロンプトの検証・展開（`internal/writer`）を呼んで、アダプタと同じ要求本文（Standard、プロンプトキャッシュの保持 30 分、`store: false`、非ストリーミング）を 1 工程ずつ送った。測定用の入口・素材・生成した記事・生の応答はリポジトリにコミットしない。

- 素材は、既存の評価用キャッシュの公開動画を使い、字幕を取り直さない。40 分前後の動画を含める。動画の組は `docs/tasks/0008_column_prompt/02_evaluation.md` §3.2 にある。
- 出力の上限は、観測したい出力より十分大きい値（記録では 32,000）を送り、各呼び出しの期限は `provider.LLMTimeout` と同じにする。
- 字数の調整は、生成した本文が長さの上限を超えたときだけ走る。生成の結果が上限に収まったときは、同じ動画の既存の長い記事を入力にする。そのような記事のない動画では字数の調整を測らず、その旨を記録する。
- 検証・推敲は、字数の調整を測った動画ではその結果を、測らなかった動画では生成の結果を入力にする。
- 測定は逐次に行い、同時に送らない。

## 集めるもの

各呼び出しについて次を集める。

- 応答の `usage` の 4 区分（通常の入力、キャッシュの読み取り、キャッシュの書き込み、出力）。出力は推論を含む `output_tokens` である。
- 実時間。HTTP の要求を送る直前から、応答の本文を最後まで読み終えるまでを単調時計で測る。プロンプトの展開・起動・応答の解析は含まない。Claude の記録（CLI 全体の時間）より測る区間が狭いことを、記録に明記する。
- 応答の `status` と `incomplete_details.reason`（打ち切られたかどうか）、`service_tier`。
- モデル・effort・素材・工程・測った日付と、測定のもとにしたコミット。

## 判定の仕方

値を、`docs/tasks/0077_openai_llm_client/01_requirements.md` の AC-10 の 3 つの条件と照らす。

- (a) 値が、観測した最大の出力の 2 倍以上である。
- (b) 最も遅い速さでその値のトークン数を生成するのに要する時間が、`provider.LLMTimeout` の半分以下である。速さは、各呼び出しの出力のトークン数を実時間で割って求める。短い応答では通信の待ち時間の割合が大きいので速さは低く出るが、これは安全側の誤差である。
- (c) 対象のモデルがすべて、値を `max_output_tokens` として受け付ける。具体的には、値が OpenAI の文書に載るそのモデルの最大出力トークン数以下であり、測定でその指定が受理されたことを確かめる。

打ち切られた呼び出しの出力は、送った上限以上であることしか分からない。その旨を記録する。

3 つの条件を満たす整数の範囲がないときは、値を推測で増減しない。人間に相談し、呼び出しそのものの変更（ストリーミング、または `provider.LLMTimeout`）が要るなら、新しいタスクとして提起する。

## 更新するもの

値が条件を満たさなくなったときは、同じ変更の中で次をまとめて更新する。

1. `internal/llm/openai/request.go` の定数 `defaultMaxOutputTokens` と、その上のコメント。
2. `internal/llm/provider/provider_test.go` の、`TestOpenAIDefaultMaxTokensFitsBudget` が値と照らし合わせる測定値（`openAILargestObservedOutputTokens`・`openAISlowestRateTokens`・`openAISlowestRateDuration`・`openAIModelMaxOutputTokens`）と、その出どころを書いたコメント。
3. 根拠の記録: この変更を行うタスクのアーキテクチャ設計書（`02_architecture.md`）。
4. 下の「現在の記録」が、その記録を指すように直す。
5. 値を述べる文書: README の「設定」（日本語版を直してから `/mktrans README.md` で英語版をそろえる）と `docs/dev/project_overview.md`、`docs/dev/conventions/package_reference.md` の `internal/llm/openai` の行。

## 現在の記録

現在の根拠は `docs/tasks/0077_openai_llm_client/02_architecture.md` §1.4 に記録されている（2026-11-10 測定）。その節は、測った条件、各呼び出しの値、3 つの条件の判定、適用の限界（各条件 1 回の測定であること、測ったものより長い素材・ほかのモデル・既定以外の effort では打ち切りと時間切れが残ること）を記す。
