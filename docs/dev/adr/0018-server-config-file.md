# ADR-0018: サーバは設定を決まった場所の env-file 形式のファイルだけから読み、CLI は環境変数を読む

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

サーバ（`yt2column-server`）は、LLM の設定を環境変数から読んできた。エンドユーザー向けの配布では、サーバを `brew services`（macOS は launchd、Linux は systemd の user unit）で常駐させる（[#574](https://github.com/isseis/yt2column/issues/574)・[#578](https://github.com/isseis/yt2column/issues/578)）。そうして起動したサーバには、シェルで `export` した変数や `.envrc` が届かないので、サーバが自分で設定を読める場所が要る。

設計の前提が 3 つある。設定には API キーという秘密情報が含まれる。外部のモジュールは使わない方針である（[CLAUDE.md](../../../CLAUDE.md)「Dependencies」）。同一ユーザーのプロセスは信頼し、他のユーザーは排除する（[ADR-0006](0006-threat-model.md)）。

## 決定

-   **サーバは設定ファイルだけから設定を読み、CLI は今までどおり環境変数だけから読む。** 入口ごとに読む場所を 1 つに決め、どの値が効いているかを曖昧にしないためである。CLI を環境変数のままにするのは、設定ファイルが解く問題を CLI が持たないからである。CLI は利用者がシェルから実行するので、`.envrc` の値が毎回届く。CLI は開発の経路で、`YT2COLUMN_LLM=… yt2column …` のように実行ごとに値を変えて試す使い方があり、ファイルだけから読むとそれを失う。二系統を保つコストは、両方が同じキーの表と同じ値の検証（[ADR-0003](0003-llm-config-contract.md)）を通ることで小さく保つ。規則は [0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) の F-002、[project_overview.md](../project_overview.md) の「設定（環境変数）」、[security.md](../security.md) の §2「秘密情報（API キー・Webhook URL）」にある。
-   **サーバが環境変数から読むのは、パスを導出する `HOME` と、Go のランタイムが出す HTTP/2 のデバッグログについて警告するための `GODEBUG` だけである。** `GODEBUG` は Go のランタイム自身が環境から読む変数で、ファイルに書いても効かないためである。環境変数を読む場所の規則は [ADR-0024](0024-env-access-in-config.md) が定める。規則は 0066 要件定義書の F-002 と、security.md の §8.2「localhost サーバ（#109）」の「設定ファイル」にある。
-   **パスは `HOME` だけから導出し、macOS もその他の Unix も `$HOME/.config/yt2column/config.env` にする。** `XDG_CONFIG_HOME` は読まない。`HOME` だけから導出するのは、ソケットのパスと同じ考え方である（[ADR-0005](0005-server-architecture.md)）。macOS でも `~/Library/Application Support` に置かないのは、設定ファイルは利用者が端末から手で編集するもので、macOS の CLI でも `~/.config` が広く使われ、パスが 1 つなら案内が OS によらず同じになり、空白を含まないので案内のコマンドで引用が要らないからである。規則のない OS（Windows など）では、パスを導出せずに止まる。規則は 0066 要件定義書の F-001 と、project_overview.md の「設定（環境変数）」にある。
-   **書式は Docker の `--env-file` の規則を土台にした `KEY=VALUE` で、それより厳格にする。キーは CLI の環境変数と同じ名前の許可リストに限り、受理する形に合わないものは直さずに拒否する。ファイルはシェルとして実行しない。** Docker の env-file は文書化された規則を持ち、標準ライブラリだけで書け、キーを CLI の環境変数と同じ名前のままにでき、雛形に説明を書けるためである。直さずに拒否するのは、`.envrc` から写した誤りを黙って直さず、拒否で気づかせるためである。シェルとして実行しないのは、設定が検証をすり抜けるためである。受理する形と拒否するものの一覧は、0066 要件定義書の F-003 と、[README](../../../README.md) の「設定ファイル」にあり、OpenAI をサーバでも選べるようにするため、[0077 要件定義書](../../tasks/0077_openai_llm_client/01_requirements.md) F-001 で `OPENAI_API_KEY` を許可するキーに足した。Webhook への投稿の廃止に合わせて、[0083 要件定義書](../../tasks/0083_remove_slack_webhook/01_requirements.md) F-001 で `SLACK_WEBHOOK_URL` を許可するキーから除いた。除いたキーの行は、ほかの知らないキーと同じく拒否し、サーバは起動しない。黙って無視すると設定の誤りを隠すので、拒否する（0083 要件定義書「要件定義の際に決めたこと（2026-11-11）」）。
-   **空の値の行（`KEY=`）は書式としては受理し、環境変数の空の値と同じく値の検証で扱う。値の検証は環境変数のときと同じ規則を使う（[ADR-0003](0003-llm-config-contract.md)）。** 空の値の行は Docker の env-file でも正しい行で、書式の取り違えではなく値の問題だからである。こうすると、ファイルに固有の規則は書式だけになり、値の規則は `internal/config` の 1 か所に集まる。規則は 0066 要件定義書の F-003 にある。
-   **ファイルそのものを検査し、満たさなければ直さずに起動を止める。** 確かめる条件は 3 つで、自分が所有する通常のファイルであること、シンボリックリンクでないこと、モードがちょうど `0600` であることである。これらは、読むファイルそのものについて確かめる。親のディレクトリは検査しない。他人が読める、または差し替えられる状態のファイルを読まないためである。親を検査しないのは、サーバは設定ファイルの親に何も作らず、親を検査して守るものがないためである。規則は 0066 要件定義書の F-004 と、security.md の §8.2「localhost サーバ（#109）」の「設定ファイル」にある。
-   **ファイルがなければ、パスと雛形を作るコマンドを示して止める。** ファイルがなくても API キーがないので結局止まるが、ファイルがないことを専用のメッセージで示すほうが分かりやすいためである。規則は 0066 要件定義書の F-004 にある。
-   **ACL は検査せず、残余リスクとして受け入れる。** サーバは設定ファイルの ACL（macOS の拡張 ACL と Linux の POSIX ACL）を検査せず、`config init` も作ったファイルの ACL を変えない。README で、モードの検査が ACL を見ないことと、確かめ方と取り除き方を示す。ACL を扱うには OS に依存するコードが要り、そのコードは Linux だけで動く CI ではテストできないので、その実装と保守のコストを、防げるリスクと比べて対応しないことにしたためである。規則は 0066 要件定義書の F-004 と、README の「設定ファイル」にある。
-   **環境に残った設定の変数は無視する。** 許可するキーや廃止した LLM の変数がプロセスの環境にあっても、サーバは読まず、止まらず、警告もしない。読まない変数を検査するためだけのコードは持たない。止めると、CLI のために `.envrc` を読み込んだシェルからサーバを起動できなくなるためである。警告も含めて検査のためだけのコードを持たないのは、レビュアーの判断である。規則は 0066 要件定義書の F-002 にある。
-   **雛形はサーバのサブコマンド `yt2column-server config init` で作る。** モード `0600` で作り、既存のものは上書きしない。配布するバイナリを増やさないためである。雛形には許可するキーを並べ、`OPENAI_API_KEY` も入れる（[0077 要件定義書](../../tasks/0077_openai_llm_client/01_requirements.md) F-001）。規則は 0066 要件定義書の F-005 と、README の「設定ファイル」にある。

## 採らなかった案

-   **秘密情報を Keychain（Linux は libsecret）に置く。** 外部コマンドの呼び出しと OS ごとの実装が要る。平文のファイルが問題になったときに検討する（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **launchd の plist の `EnvironmentVariables` に書く。** `brew upgrade`・`brew services restart` で上書きされる（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **起動用のスクリプトで `.env` を `source` する。** 設定がシェルとして実行され、検証をすり抜ける（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **拡張の設定画面から送る。** API キーがブラウザを通る（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **TOML で書く。** 外部のモジュールが要り、標準ライブラリだけで書く方針を変えることになる。値は 7 つの平らな文字列で、TOML の表や型は要らない（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **JSON で書く。** コメントを書けないので雛形で各キーを説明できず、手で書くと誤りやすい（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **`export`・引用符を受け付けて取り除く。** 拒否せずに直すことになり、`.envrc` から写した誤りが見えなくなる（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **ファイルがなければ、空のファイルとみなして既定値で読む。** API キーがないので結局止まるが、ファイルがないことが利用者に分かりにくい（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **環境に残った変数でサーバを止める。** CLI のために `.envrc` を読み込んだシェルから、サーバを起動できなくなる（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **行末のコメントを値の一部として受け付ける（Docker の規則のまま）。** `KEY=value # comment` が書式も値の検証も通り、最初の LLM の呼び出しで初めて誤りが分かる（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **macOS の拡張 ACL を検査し、`config init` では継承した ACL を取り除く。** ACL を読み書きする macOS の API（`acl_get_fd`・`acl_set_fd` など）は libc の関数なので、呼ぶには CGO が要る。CGO を使わないなら、Apple が文書化していないシステムコール（`fchmod_extended` など）を `syscall` で直接呼ぶことになる。どちらでも OS に依存するコードが入り、そのコードは Linux だけで動く CI ではテストできない。一方、macOS の既定のホームディレクトリには読む権利を与えて継承される ACL がなく、ACL が付くのは利用者が付けた場合などに限られる。この実装と保守のコストと、防げるリスクを比べて、対応せず残余リスクとして受け入れた（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **環境に残った変数を名前だけ警告する。** 読まない変数を検査するためだけのコードを持たないことにした（レビュアーの判断）。効かない理由は README の説明で補う（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **CLI も設定ファイルだけから読む。** コードの変更は小さいが、実行ごとに環境変数で値を変えて試す使い方を失う。ファイルを読みつつ環境変数での上書きを許すと、どちらの値が効いているかが曖昧になる。CLI はシェルから実行するので、ファイルが解く問題をもともと持たない。
-   **設定ファイルでは、空の値の行をどのキーでも拒否する。** 空の値の行は Docker の env-file でも正しい行で、書式の取り違えではなく値の問題である。書式の段で拒否すると、ファイルにだけ値の規則が 1 つ増え、環境変数と規則がずれる。使うキーの空の値は値の検証で設定エラーになるので、拒否しなくても誤った値で動くことはない（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **CLI でも、使わないプロバイダの変数の空の値を拒否する。** 環境変数はほかのツールと共有する場所で（`ANTHROPIC_API_KEY` はほかの Anthropic のツールも読む）、読まない値を検査することになる（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **サーバがファイルと環境変数の両方を読む。** どちらの値が効いているかが曖昧になる（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **雛形を別のコマンドで作る。** 配布するバイナリが増える（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **macOS では `$HOME/Library/Application Support/yt2column/config.env` に置く。** 2026-11-06 の決定で、ソケットのディレクトリと親を共有していた。Apple の指針には沿うが、手で編集するファイルのパスに空白が入って案内のコマンドで引用が要り、README の案内と `config init` の作る親が OS ごとに分かれる。ソケットと親を共有することは、設定ファイルにとっての利点ではなかった（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) の実装の際に決めたこと）。
-   **ホーム直下のドットファイル（`~/.yt2column.env` など）に置く。** 古くからある形だが、ホームを散らかし、今の CLI の多くは `~/.config` の下に置く（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) の実装の際に決めたこと）。
-   **親のディレクトリも検査する。** 読むファイルそのものを検査するので、親の名前を入れ替えられても検査していないファイルは読まない。サーバは設定ファイルの親に何も作らないので、親を検査して守るものがない（[0066 要件定義書](../../tasks/0066_server_config_file/01_requirements.md) §1）。
-   **Webhook への投稿を廃止した後、設定ファイルに残った `SLACK_WEBHOOK_URL` の行を黙って無視する。** 設定の誤りを隠し、受理する形に合わないものを直さずに拒否する規則（CLAUDE.md「Reject, don't normalize」）に反する（[0083 要件定義書](../../tasks/0083_remove_slack_webhook/01_requirements.md)「要件定義の際に決めたこと（2026-11-11）」）。

## 結果

-   サーバは、シェルの環境を受け継がない起動（`brew services` など）でも同じ設定で動く。#578 の `service` ブロックは環境変数を渡さなくてよい。
-   CLI とサーバで設定の置き場所が分かれる。同じ API キーを `.envrc` と設定ファイルの 2 か所に書くことになる。CLI をエンドユーザーにも配るようになったとき、またはファイルと環境変数とで値の規則がずれる必要が出たときは、CLI も設定ファイルを読むかを見直す。
-   秘密情報は平文のファイルにあり、同一ユーザーのプロセスは読める。今の `.envrc` と同じ水準として受け入れる。
-   環境変数を設定したのに効かないとき、サーバは何も示さない。利用者は README の説明で、サーバが環境変数を読まないことを知る。
-   今の利用者は、更新後に設定ファイルを作るまでサーバを起動できない。互換の仕組みは設けず、README の移行の手順で移る。
-   macOS では、モードが `0600` でも、ACL が他のユーザーに読む権利を与えていれば、サーバはそのファイルを受理し、他のユーザーが秘密情報を読める。サーバはこれを示さない。利用者は README の説明で、ACL を確かめて取り除く。
