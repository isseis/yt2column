# ADR-0022: 料金の概算を internal/pricing に置き、単価の表から整数で正確に計算し、分かったか不明かを型で区別する

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

LLM の呼び出しは、応答が報告するトークン数から料金を概算できる。利用者は、記事 1 本の料金と実行全体の料金を、標準エラー出力と記事のメタデータで知りたい。料金は、モデルごとの単価、時間帯で変わる単価、プロンプトの長さで変わる単価で決まり、使ったモデルが単価の表になければ求められない。

料金を工程ごとにばらばらに求めると、同じ実行について CLI と記事のファイルで違う値が出る。金額を浮動小数で持つと、0.5 の境界の四捨五入で表示が手で計算した値と食い違う。単価の表と算出を 1 か所に置き、金額を整数で正確に持つ必要がある（[0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md) §1.1）。

## 決定

-   **単価の表・時間帯の規則・工程の料金の算出・2 つの合計・金額の書式は、新しいパッケージ `internal/pricing` の 1 か所に置く。** プロバイダのアダプタは単価を知らず、CLI・`Publisher`・統合テストが同じ関数を使う。CLI の要約・`--out`・統合テストのログが同じ算出を使うためである（[0022 要件定義書](../../tasks/0022_cost_estimate/01_requirements.md) §4.5「保守性 (Maintainability)」）。単価の表の置き場所と更新の手順は [pricing_update.md](../guides/pricing_update.md) にある。
-   **金額は整数で正確に持つ。** 単価は「100 万トークンあたりのマイクロ米ドル」の符号なし整数で持ち、単価とトークン数の積は 10^-12 米ドルの単位でちょうど整数になる。算出は `math/big` の整数で行い、表示の桁で四捨五入する。浮動小数では、0.5 の境界の四捨五入で表示が手で計算した値と食い違いうるためである。`math/big` を使うのは、桁あふれの分岐が要らないためである。規則は [0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md) の §1.1 と §3.3「段階の料金の算出（H-02）」にある。
-   **料金は「分かった（金額と適用した単価）」か「不明（理由つき）」のどちらかで、型で区別する。** `StageCost` と `Total` のゼロ値は不明であり、0 米ドルとは読めない。不明の理由と適用した単価は列挙型で表し、ゼロ値は「設定されていない」を意味する。不明の工程に、0 を含め推測の値を出さないためである（0022 要件定義書 F-003）。出力での表し方は [cli.md](../guides/cli.md) の「推定の料金」にある。
-   **単価の選び方は表で宣言し、モデル名の中身から推測しない。** 各モデルが「単価が 1 組」「時間帯で 2 組」「プロンプトの長さで 2 組」のどれかを宣言し、算出はその値で単価の組を選ぶ。モデル名は完全一致だけで照合する。表にないモデルは不明にする。呼び出し元の文字列の中身で振る舞いを選ばないためである（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。単価の組の選び方（方式）は pricing_update.md の「料金を出どころで確かめる」にある。
-   **呼び出しの時刻は `writer` が取得し、工程の使用量とともに運ぶ。** `Generate` が戻った直後の時刻を、成功では実行の使用量に、失敗ではエラーに、再開では中間生成物に持たせる。時刻は `id` の計算にも含める。アダプタが時刻を返す形にすると、`GenerateResponse` の形と 2 つのアダプタ、既存の fake を変えることになるためである。規則は 0022 設計書の §3.4「呼び出しの時刻の取得と受け渡し（H-03）」にある。中間生成物の形式は [ADR-0023](0023-artifact-resume.md) が定める。
-   **記事 1 本の料金は、`Publisher` が実行の使用量から求める。** `writer.Article` に料金のフィールドは加えない。記事のファイルのフロントマターは、この関数で求めた金額を書く。`writer` を単価の表に依存させず、`Article` の形を変えないためである。`Publisher` は実行の使用量から同じ値を求められる。出力の形は cli.md の「推定の料金」と、0022 設計書の §3.7「`--out` と Slack の見出しのメタデータ（H-04）」にある。
-   **料金は算出して出力するだけで、振る舞いを変えない。** 生成・字数の調整・検証・推敲・公開の分岐、リクエストの内容、呼び出しの回数、終了コードを料金で変えない。料金が不明でも記事は公開する。料金の値によって実行する処理を選ばず、料金の把握は副次的な情報だからである。規則は 0022 要件定義書の §3.2「信頼できない入力の境界 (Untrusted Input Boundaries)」と §4.3「信頼性・可用性 (Reliability/Availability)」にある。

-   **使用量が報告する料金の適用条件と、単価表の行が要求する条件が一致する場合だけ料金を求める。** 同じ4区分のトークン数でも、処理方式やキャッシュの保持期間が異なれば単価が変わるためである。追加の条件を要求しない既存の行の振る舞いは維持する。必要な条件を確認できない場合は、トークン数を保って料金だけを不明にする。条件の契約は [0077 設計書](../../tasks/0077_openai_llm_client/02_architecture.md) の「トークン数と料金の適用条件の分離」にある。

-   **拡張のビューアは、完成した記事の料金に加えて、失敗した実行の料金も示す。** 利用者が自分の API キーで支払うので、失敗した実行で使った額も分かるようにするためである。失敗した実行では、料金が分かった工程の料金を示し、分からない工程は不明と示す。工程ごとに示すのは、合計は 1 つの工程が不明なら不明になり、合計だけでは使った額が分からないためである。記事の生成を実行するページが閉じられるか再読み込みされて止まった実行の料金は、示さない。その使用量を受け取るページが残らないためである。規則は [0090 要件定義書](../../tasks/0090_extension_only_architecture/01_requirements.md) の F-001 にある。

トークン数の型と、失敗した呼び出しの使用量の返し方は [ADR-0021](0021-llm-client-contract.md) が定める。

料金の適用条件のコードへの反映は [#568](https://github.com/isseis/yt2column/issues/568) の実装で行う。

Slack の投稿の脚注は、まだコードに残っている。この差分は [#770](https://github.com/isseis/yt2column/issues/770) の実装で解消する。

失敗した実行の料金をビューアに示すことは、まだコードに反映していない。今のビューアが示すのは、完成した記事の料金だけである。この差分は [#773](https://github.com/isseis/yt2column/issues/773) の実装で解消する。

## 採らなかった案

-   **`float64` で算出する。** 0.5 の境界の四捨五入で、表示の値が手で計算した値と食い違い得る（[0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md) 付録 A）。
-   **`uint64` と `math/bits` で算出する。** 積と和のそれぞれで桁あふれの分岐と「表せない」場合の不明の理由が要る。`math/big` なら分岐がない（[0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md) 付録 A）。
-   **アダプタが呼び出しの時刻を返す。** `GenerateResponse` の形と 2 つのアダプタ、既存の fake を変えることになる（[0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md) 付録 A）。
-   **`writer.Article` に料金を持たせる。** `writer` が単価の表に依存し、`Article` の形と、そのフィールド集合を固定するテストが変わる。`Publisher` は実行の使用量から同じ値を求められる（[0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md) 付録 A）。
-   **合計の行を、工程の行と同じ接頭辞にする。** 行の種類を語の値で見分けることになる（[0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md) 付録 A）。
-   **ビューアが示す料金を、完成した記事のものだけにする。** 利用者が自分の API キーで支払う構成で、失敗した実行で使った額が利用者に分からない（0090 要件定義書「要件定義の際に決めたこと（2026-11-12）」）。
-   **生成の前に、字幕の長さから料金を見積もって示す。** 見積もりの仕組みを新しく作ることになり、実際の値との差も出る（0090 要件定義書「要件定義の際に決めたこと（2026-11-12）」）。

## 結果

-   同じ実行の料金が、標準エラー出力と記事のファイルで同じ値になる。
-   単価の表にないモデルや、使用量が不明な工程を含む実行は、料金を「不明」と表示する。記事の公開は止めない。
-   単価を変えるときは、表のエントリと、その出典と確認した日付を同じ変更で直す。算出と表示の書式は変わらない。
-   呼び出しの時刻を記録するので、時間帯で変わる単価を、呼び出した時刻で選べる。中間生成物を再開に使っても、その工程の料金を同じ時刻で求められる。

## 経緯

- 2026-10-16 料金の概算を `internal/pricing` に置き、単価の表から整数で正確に計算し、工程の料金と 2 つの合計を「分かった」か「不明」かで表すことにした（[0022 設計書](../../tasks/0022_cost_estimate/02_architecture.md)）
- 2026-10-25 既定のモデルを変えるとき、単価の表のモデル名を既定のモデルの定数とまとめず、別の役割の値として分けたまま保った（[0042 設計書](../../tasks/0042_default_llm_opus/02_architecture.md) §1.2）

- 2026-11-10 通常単価を適用できない OpenAI の応答を誤って価格付けしないため、単価表の行に必要な料金の条件を宣言し、使用量の条件と照合することにした（[0077 設計書](../../tasks/0077_openai_llm_client/02_architecture.md)）
- 2026-11-11 Webhook への投稿の機能の廃止に合わせて、料金を書く出力から Slack の投稿の脚注を除いた（[0083 要件定義書](../../tasks/0083_remove_slack_webhook/01_requirements.md) F-001）
- 2026-11-12 記事を拡張だけで作る構成に合わせて、拡張のビューアが失敗した実行の料金も示すことにした（[0090 要件定義書](../../tasks/0090_extension_only_architecture/01_requirements.md)「要件定義の際に決めたこと（2026-11-12）」）
