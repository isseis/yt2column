# ADR-0041: OpenAI は Responses API を応答の保存なしで呼び、出力上限は実測で決める

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

記事の生成と検証・推敲に別系統のモデルを組み合わせて評価するため、OpenAI のモデルを選べるようにする。既存の API との互換性を保つ必要はない。記事を書く各工程は独立した1回の要求であり、保存した会話を継続しない（[0077 要件定義書](../../tasks/0077_openai_llm_client/01_requirements.md)）。

生成が途中で終われば記事を公開できないため、出力上限には文面と推論の両方に余裕が要る。一方、各 LLM 呼び出しの期限は15分であり、上限だけを大きくしても期限に収まるとは限らない。既存の Claude の上限は、出力の長さと速さの実測を根拠に決めている（[claude_output_limit.md](../guides/claude_output_limit.md)）。

## 決定

- **OpenAI は Responses API を使い、1回ずつ非ストリーミングで呼ぶ。** 新規実装であり、issue の第一候補に合わせる。ツールと会話の継続は含めない。受理する応答と終了状態の契約は、0077 要件定義書 F-002・F-003 に従う。標準ライブラリと共有の送信経路を使う境界は [ADR-0001](0001-llm-adapter-stdlib.md) が定める。
- **すべての要求で応答の保存を無効にする。** 保存した応答を取得する用途がないため、`store: false` を固定し、切り替える設定は設けない。監視ログとプロンプトキャッシュの保持とは区別する。仕様は 0077 要件定義書 F-005・F-006 に従い、保持の説明は実装で [security.md](../security.md)「LLM プロバイダへ送るデータ」に加える。
- **出力上限は設計段階の実測から決める。** 推測で決めた値を後続の評価の前提にしないため、候補モデルを既定の effort で使って3工程を測り、出力の余裕、期限に対する余裕、モデルの受理範囲を両立する値を選ぶ。条件と記録する項目は 0077 要件定義書 F-002 が定める。実測には別途許可を得て、両立する値がなければレビュアーに再相談する。

- **処理方式とキャッシュの最低保持期間は固定する。** 通常単価で料金を求めるため、要求で Standard と30分を指定し、応答でも Standard を確認できた場合だけ通常単価を適用する。プロジェクトの既定に処理方式を任せず、保持期間を切り替える設定は設けない。確認できない場合も、本文が正常なら生成を続け、分かっている使用量を保ち、料金だけを不明とする。固定パラメータに未対応のモデルは API のエラーとして扱い、モデル名から要求の設定を変えない。仕様は [0077 設計書](../../tasks/0077_openai_llm_client/02_architecture.md) の「設計の際に決めたこと」と「使用量と料金」にある。

- **既定の出力上限は6,080トークンとする。** 2モデルの `medium` による3工程の出力と実時間から、要件の3条件を両立する範囲を求めて選んだ。測定値、区間の狭さと限界、更新する対象は 0077 設計書の「既定の出力上限と測定根拠」にある。

モデルの選択と effort は [ADR-0003](0003-llm-config-contract.md)、結果のモデル名と使用量は [ADR-0021](0021-llm-client-contract.md)、料金は [ADR-0022](0022-cost-estimate.md) に従う。コードと security.md への反映は [#568](https://github.com/isseis/yt2column/issues/568) の実装で行う。

## 採らなかった案

- **Chat Completions API を使う。** 既存の互換性に拘束されないため、issue の第一候補である Responses API を採る。
- **応答の保存を利用者の設定で切り替える。** 保存した応答を取得する必要がなく、設定とデータ保持の管理を増やすため採らない。
- **実測せず暫定の上限を置く、または上限を送らない。** 出力の長さと所要時間に対する余裕を確認できないため採らない。

- **処理方式をプロジェクトの設定に任せ、保持期間を選べるようにする。** 選択できる設定と単価の組を増やす必要がある。今回は要求を通常単価で求める範囲に固定し、その条件を確認できたかだけを共有の使用量と中間生成物に運ぶ。
- **Standard を確認できない応答を、料金のために拒否する。** 料金が不明でも生成・公開を続ける要件 AC-19 に反するため採らない。
- **Standard を確認できない応答でも通常単価を当てはめる。** 実際の処理方式と料金の前提が食い違うため採らない。

## 結果

- OpenAI の応答は既存の `LLMClient` の成功・失敗・使用量に対応させる。Responses API 固有の型を共有の結果に加えない。
- `store: false` はゼロデータ保持を意味しない。利用者には監視ログとキャッシュの保持も説明する必要がある。
- モデル・effort・テンプレート・処理方式・保持期間を変えるときは、許可を得て上限の根拠を測り直す。条件を両立できなければ再相談する。
- 固定の要求に未対応のモデルは API のエラーになる。Standard を確認できない応答は、そのことだけでは拒否せず料金を不明にする。料金の適用条件は共有の使用量と中間生成物で引き継ぐ。
- 既定の effort 以外の実行や、測定の対象を超える入力では打ち切りと期限切れが残りうる。本番の構成の変更は後続の評価で決める。

## 経緯

- 2026-11-10 Responses API を非ストリーミングかつ応答の保存なしで使い、既定の出力上限は設計段階で実測して決めることにした（[0077 要件定義書](../../tasks/0077_openai_llm_client/01_requirements.md)）

- 2026-11-10 通常単価と要求を一致させるため Standard と30分のキャッシュ設定に固定し、応答で Standard を確認できない場合は生成を続けて料金だけを不明とすること、実測の範囲から既定上限を6,080にすることを決めた（[0077 設計書](../../tasks/0077_openai_llm_client/02_architecture.md)）
