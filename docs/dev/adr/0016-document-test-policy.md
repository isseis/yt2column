# ADR-0016: 文書のテストは値・構造・実行できる例だけを確かめ、文の意味は PR のレビューで読む

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

リポジトリの文書には、コードや設定と一致していなければならない値がある。コマンドのフラグと終了コード、LLM のプロトコル番号、拡張の ID と権限、`make` の対象、拒否の理由の表などである。これらは、文書とコードのどちらかを変えたときに食い違いやすい。文書だけを変える PR でも、その食い違いを見つけられるようにしたい。

一方で、文書のテストは、文の意味を確かめられない。語を照合して文の意味を固定すると、言い換えのたびにテストを直すことになり、意味を反転させた文を見逃すこともある。テストの維持の費用が、防ぐ誤りを上回る確認を足すと、文書を直すたびにテストを直す手間だけが増える。

変更の前後の関係を述べる受け入れ基準は、PR ごとに 1 回だけ実行する `diff` の確かめで確かめる。この確かめはマージの後に保守しないので、費用は PR のレビューで読む量と書く作業である。ところが、確かめの作りの基準がなく、前のタスクの確かめを手本として写したため、確かめが変更に比べて大きくなりやすかった。差分が 2 行の ADR の直しに 547 行の確かめを書いたこともある（[0080 要件定義書](../../tasks/0080_diff_check_proportion/01_requirements.md) 1 章）。

## 決定

-   **文書のテストは、値・構造・実行できる例だけを確かめる。** 文の意味は、PR のレビューで読む。どの値・構造・例を確かめてよいか、直書きのリテラル・古い名前の不在・タスクの記録を扱わないこと、2 つの例外、同じ値を 2 つのテストで確かめないこと、廃止した仕様を残させるテストを足さないこと、維持の費用が防ぐ誤りを上回る確認を足さないことは、[CLAUDE.md](../../../CLAUDE.md) の「Testing Strategy」の「Document tests check values, structure, and executable examples, never prose」の段落と、その後の 3 つの規則に従う。語を照合して文の意味を固定すると、言い換えのたびにテストを直すことになり、意味を反転させた文を見逃すこともあるためである。この ADR は、その規則の理由と、採らなかった案を持つ。
-   **変更の前後関係（既存の見出しが変わっていないことなど）は、文書のテストにしない。** `diff` の確かめとして、マージの基点と PR の head を比べ、PR ごとに 1 回だけ実行する（[requirements_process.md](../conventions/requirements_process.md) §4）。前後の関係は PR ごとの性質なので、恒久的なテストにすると、文書を直すたびにテストを直すことになるためである。
-   **`diff` の確かめの作りは、確かめる差分の大きさに見合ったものにする。既定はタスクの `_checks/` に置くシェルスクリプトとし、ほかの言語はシェルで足りない理由を計画に書いたときに使う。** 確かめはマージの後に保守しないので、その費用を確かめる変更に見合ったものにするためである（[requirements_process.md](../conventions/requirements_process.md) の「4. Acceptance Tests」）。
-   **差分が小さい文書の変更では、記録した `git diff` の出力を PR のレビューで読むことも、`diff` の確かめとする。** 「小さい」かどうかは計画を書く者が判断し、レビュアーは異論を述べられる。数の閾値は設けない。差分が数行の変更では、差分そのものを読むほうが、それを確かめるスクリプトを読むより少なく済むためである。この形には壊して失敗を確かめる対象のコードがないので、その手順は要らない。レビュアーが異論を述べたときはスクリプトに替える（[requirements_process.md](../conventions/requirements_process.md) の「4. Acceptance Tests」）。
-   **前後の関係を述べる受け入れ基準は、「X の差分は Y と Z に限られる」の形で書き、守る部分を並べ挙げない。移動と分割だけは「A の内容が B に変わらずにある」の形で書いてよい。** 並べ挙げた部分の一つ一つを解析するコードが生まれるためである。移動と分割は、差分が限られる形では言い表せない（[requirements_process.md](../conventions/requirements_process.md) の「1. Requirements Document」）。
-   **計画は、前のタスクの `_checks/` を手本として写させず、壊し方は「チェックごとに少なくとも 1 つ」とだけ書いて並べ挙げない。** 前のタスクの大きなプログラムの構造が受け継がれ、計画に並べた壊し方がそのまま作業になるためである（[mkplan.md](../../../.claude/commands/mkplan.md)）。
-   **確かめる差分に比べて過大な `diff` の確かめを、計画のレビュー・フェーズのまとまりのレビュー・弱いモデルの作業のレビューで指摘する。** 大きさは計画を書くときに決まるので、実装の前にも見つけられるようにするためである（[mkplan.md](../../../.claude/commands/mkplan.md) の「Technical correctness checklist」、[runplan.md](../../../.claude/commands/runplan.md) の「Phase-group review checklist」、[_lib/opus-review.md](../../../.claude/commands/_lib/opus-review.md) の「Weak-model failure checklist」）。
-   **文書を読む Go の guard は、`doc-guard` の CI ジョブで、変更の種類にかかわらずすべての PR に実行する。** 対象のパッケージと、文書だけの変更で `make ext-test` を要求しない範囲は、[CLAUDE.md](../../../CLAUDE.md) の「Development Notes」と [.github/workflows/ci.yml](../../../.github/workflows/ci.yml) を正本とする。変えるときは、同じ PR で正本とこの ADR をそろえる。文書だけを変える PR でも、文書とコードの食い違いを同じ PR で見つけるためである。

## 採らなかった案

-   **文書のテキスト同期の guard を、拡張の node のテストに残す。** 文書だけの変更で node と `npm ci` を要求する。guard はテキストの同期だけで node を必要としない（[0012 要件定義書](../../tasks/0012_doc_sync_guards/01_requirements.md) §1）。
-   **文書だけの変更を CI で守らず、ローカルの `make test` に委ねる。** 手元でテストを実行しない経路（Web での編集、bot）で guard が壊れると、原因の PR と別の PR で初めて検出される（[0014 要件定義書](../../tasks/0014_doc_guard_ci/01_requirements.md) §1）。
-   **`doc-guard` で `go test -tags test ./...` を走らせる。** 文書だけの PR でも全パッケージのテストが走り、実行時間が延びる。対象を明示して列挙し、新しい文書の guard を足すときに更新する（[0014 設計書](../../tasks/0014_doc_guard_ci/02_architecture.md) §11）。
-   **`check-changes` の除外から `.md` と `docs/` を外す。** 文書だけの PR でも race 付きの全テストと lint が走る。実行時間が延び、分類の設計も変わる（[0014 設計書](../../tasks/0014_doc_guard_ci/02_architecture.md) §11）。
-   **`Makefile` に `test-doc-guard` の対象を足す。** 対象は 2 パッケージで固定であり、`ci.yml` に直接書けば足りる。同じコマンドを複数の手順から呼ぶ必要が出たときに検討する（[0014 設計書](../../tasks/0014_doc_guard_ci/02_architecture.md) §11）。
-   **タスクの文書の値をコードと照合する確認を残す。** タスクの文書は、その時点の記録であり、完了の後に変わらない。コードと照合すると、記録をコードに合わせて書き換えることになる（[0038 設計書](../../tasks/0038_doc_test_pruning/02_architecture.md) §1.2）。
-   **過去の 1 回の変更の性質を確かめるテストを `_checks/` へ移す。** 元のタスクはマージ済みで、`_checks/` はマージの基点と PR の head を比べて 1 回だけ実行するものなので、移しても実行する機会がない（[0052 要件定義書](../../tasks/0052_doc_test_pruning/01_requirements.md) §1）。
-   **`doctestutil` に同じ処理がある補助を置き換えず、使い手を失った補助を消すだけにする。** レビュアーは、重複する補助を `internal/doctestutil` の関数に置き換えることを選んだ。ただし `cmd/fixprguard` の `cutSection` は置き換えない。`doctestutil` の節を切り出す関数は見出しの全体の一致で探すので、見出しの題を言い換えるだけで複数の guard が落ちるようになる（[0052 設計書](../../tasks/0052_doc_test_pruning/02_architecture.md) §1.2）。

-   **記録した差分の読み取りを、行数の閾値の範囲だけで認める。** 閾値の値を根拠をもって決められず、差分の行数は読む手間の大きさと必ずしも一致しない（[0080 要件定義書](../../tasks/0080_diff_check_proportion/01_requirements.md)「要件定義の際に決めたこと（2026-11-10）」）。
-   **記録した差分の読み取りを認めず、`diff` の確かめをスクリプトだけにする。** 差分が数行の変更でもスクリプトが要り、作りの釣り合いが取れない（同）。
-   **スクリプトをシェルだけに限る。** 文書の構造を比べる確かめが書きにくくなる（同）。
-   **既定の言語を決めず、見合った作りにせよとだけ書く。** 基準がないまま、前のタスクの版を写す流れが残る（同）。
-   **受け入れ基準の書き方を勧めにとどめる。** 並べ挙げる書き方が残る（同）。
-   **移動と分割の書き方の例外を設けない。** 移動と分割の受け入れ基準の書き方が定まらないまま残る（同）。
-   **過大な確かめを指摘する観点を、フェーズのまとまりのレビューと弱いモデルの作業のレビューだけに置く。** 計画の段階で過大さを見逃し、実装の後に初めて見つかる（同）。
-   **受け入れ基準の並べ挙げを指摘する項目を、`/mkreq` のチェックリストに足す。** 人がこの案を選ばなかった。理由は記録されていない（同）。

## 結果

-   文書の値や構造を変えると、対応するテストが落ちる。文言だけを変えても、テストは落ちない。
-   文書だけを変える PR も、`doc-guard` のジョブで対象の guard が走る。node と `npm ci` は要らない（対象と例外は CLAUDE.md の「Development Notes」に従う）。
-   文書のテストは、文の意味の誤り（意味を反転させた文など）を見つけられない。それは PR のレビューで読む。
-   文書を直すときにテストを直す手間は、値・構造・実行できる例に限られる。新しい文書の guard を足すときは、`doc-guard` の対象にパッケージを足すか、既存のパッケージに置く。
-   `diff` の確かめは、PR ごとに 1 回だけ手で実行するか、記録した差分を PR のレビューで読む。`make test` と CI は実行しない。
-   記録した差分の読み取りを使うかどうかは人の判断なので、同じ大きさの変更でも、計画によって確かめの形が分かれうる。その判断の誤りは、PR のレビューで見つける。
