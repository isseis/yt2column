# ADR-0044: package_reference.md の行には責務の要約・主な公開の名前・仕様の置き場所だけを書き、挙動の詳細は doc コメントと仕様の文書に置く

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

`docs/dev/conventions/package_reference.md`（以下、パッケージの参照表）は、`cmd/`・`internal/` の下のパッケージと `prompts` パッケージを、責務とともに挙げる文書である。後の開発者は、変えようとするパッケージの責務と、詳しい仕様の置き場所を知るためにこの文書を読む。`/mkarch` も、パッケージを足すか変えるタスクの設計の前にこの文書を読む。

冒頭の運用の規則は、パッケージを足す・消す・責務を変えるコミットで更新することだけを定め、行に何をどこまで書くかの上限を定めていなかった。そのため、タスクごとに実装の詳細が書き足され、文書は 75,604 バイトにまで膨らんだ。数 KB に及ぶ行もある（[0085 要件定義書](../../tasks/0085_package_reference_summary/01_requirements.md) 1 章）。この文書を読むテストは、パッケージ名の列と `internal/strictjson` の利用者の一覧しか確かめない。行のほかの文は、PR のレビューで読む以外に古さを見つける手段がない。

## 決定

-   **行には、責務の要約、主な公開の名前、詳しい仕様の置き場所へのリンクだけを書き、実装の詳細（非公開の名前、数値、手順など）は書かない。** 実装の詳細はコードと二重になり、テストでは古さを見つけられないためである。書くものと書かないものの一覧は、[package_reference.md](../conventions/package_reference.md) の冒頭にある。
-   **挙動の詳細は、doc コメントか今の文書に置き、行からはリンクする。ほかの文書にすでにある詳細は写さず、どこにもない呼び出し側の契約は doc コメントへ移し、それ以外はコードを正本として行から削る。** 詳細の正本を 1 か所にし、コードの近くに置くためである。置き場所の一覧は [package_reference.md](../conventions/package_reference.md) の冒頭にある。
-   **表は、パッケージの種類ごとに分ける。** 1 つの表に全パッケージが並ぶと、目的のパッケージを探しにくいためである。種類とその定義は [package_reference.md](../conventions/package_reference.md) の冒頭にある。
-   **行の粒度の上限は、行ごとのバイト数やテストでは決めず、PR のレビューで読んで確かめる。** テストで止めると、正当に長い行があるたびに規則と衝突するためである。維持の費用が防ぐ誤りを上回る文書の確認は足さない（[ADR-0016](0016-document-test-policy.md)）。規則は [package_reference.md](../conventions/package_reference.md) の冒頭にある。

パッケージの参照表の冒頭は、まだこの規則を述べていない。行もまだ規則に従っておらず、表も種類ごとに分かれていない。この差分は [#817](https://github.com/isseis/yt2column/issues/817) の実装で解消する。

## 採らなかった案

-   **行には責務だけを書き、公開の名前も挙げない。** ADR が規則の置き場所として参照する番兵の名前などが行からなくなり、ADR の参照を張り替える箇所が増える（[0085 要件定義書](../../tasks/0085_package_reference_summary/01_requirements.md)「要件定義の際に決めたこと（2026-11-11）」）。
-   **行から外す詳細を、移さずにすべて削る。** 呼び出し側が頼る契約が、どこにも書かれなくなる（同上）。
-   **行から外す詳細を、すべてほかの文書へ移す。** コードを読めば分かる実装の細部まで文書に移すことになり、作業量が最も大きい（同上）。
-   **詳細の行き先を、`cli.md`・`development.md`・`security.md`・README・`production_profile.md`・タスクの設計書に限る。** guide にすでにある詳細を doc コメントに写すことになり、後のタスクが挙動を変えた古い設計書の節へのリンクも許してしまう（同上）。
-   **1 つの表のまま、行の中身だけを絞る。** 目的のパッケージを探しにくいままである（同上）。
-   **行ごとのバイト数の上限を冒頭に書き、Go の guard テストで超えた行を失敗にする。** 正当に長い行があるたびに規則と衝突する（同上）。

## 結果

-   行から外した実装の詳細は、doc コメント、仕様の文書、コードで読む。パッケージの参照表だけでは、パッケージの挙動の細部は分からない。
-   パッケージを足すか変えるタスクは、行を規則の粒度に保つ。規則を守っているかはテストで確かめず、PR のレビューで読む。
-   ADR は、パッケージの参照表の行を、その行が持つ内容（責務と公開の名前）の置き場所としてだけ参照できる。

## 経緯

- 2026-11-11 パッケージの参照表の行を、責務の要約・主な公開の名前・仕様の置き場所に限り、挙動の詳細を doc コメントと仕様の文書に置くことにした。表は種類ごとに分け、粒度の上限は PR のレビューで読むことにした（[0085 要件定義書](../../tasks/0085_package_reference_summary/01_requirements.md)「要件定義の際に決めたこと（2026-11-11）」）
