# ADR-0042: 実装モデル要件を opus・sonnet+opus-review・sonnet の 3 つにし、Opus 以外で実装した部分がある sonnet+opus-review・opus の PR は、開く前に Opus がレビューする

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

計画書は、PR ごとに `/runplan` を実行するモデルの目安（実装モデル要件）を持つ。人はこれを見て、セッションのモデルを選ぶ。Opus は Sonnet より誤りが少ないが、トークンあたりの単価は Sonnet の 2 倍である。Sonnet に任せられる PR を Sonnet で実装すれば、費用は下がる。ただし、Sonnet が落とした判断を誰かが見つけなければならない。

Codex の PR レビューは、PR を開いたときに 1 回だけ自動で行われる。それより後の変更はローカルの CLI レビューで見る（[ADR-0013](0013-review-setup.md)）。`/runplan` の中のサブエージェントのレビューは、セッションのモデルを引き継ぐ。そのため Sonnet のセッションでは、Opus によるレビューは行われない。1 つの PR は、複数の `/runplan` のセッションにまたがりうる。

過去の `/runplan` のセッション 123 件を Opus 5.5 の単価で換算すると、1 セッションの中央値は約 $13 だった。Opus のレビュー（二つのレビューと確認のレビュー）は約 $1.5〜4 と見込むが、PR のすべての commit を範囲とするので、これより大きくなりうる。Sonnet が使うトークンが Opus の約 1.4〜1.8 倍（Opus のレビューの費用によって変わる）を超えなければ、Sonnet で実装して Opus のレビューを足しても安くなる。この倍率は測っていない（[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md) の「費用の目安」）。

## 決定

以下の決定の仕様は、[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md) の機能要件と [0081 設計書](../../tasks/0081_implementation_model_choice/02_architecture.md)、値と読み替えを定める [_context.md](../../../.claude/commands/_context.md) の「PR marker conventions」が持つ。手順は、それを使うコマンドの定義（`mkplan2.md`・`mkplan.md`・`runplan.md`・`runpr.md`・`weakreview.md`）と、Opus のレビューの共通の手順（`_lib/opus-review.md`）が持つ。この決定のうち、値を読む側（`_context.md` の値の場所・読み方・読み替えの表、`runplan.md` の案内と実装の記録と PR を開く前の Opus のレビュー、`runpr.md` の示し方、共通の手順の要否の判断と記録の行）と、Opus のレビューの中身と `/weakreview` の振る舞いは、`_context.md`・コマンドの定義・共通の手順に反映されている。反映されていないのは、値を書く側の次のずれである。今の `mkplan2.md` は旧い値（`frontier-required`・`frontier-recommended`・`standard`）を定め、`mkplan.md` と `_lib/simple-process.md` は `mkplan2.md` の手順でその値を書かせる。`mkplan.md` は単一フェーズの計画書に値を書かず、`_context.md` も値を書く場面にそれを挙げない。このずれは [#760](https://github.com/isseis/yt2column/issues/760) の実装で扱う。

また、`sonnet` を OpenCode の DeepSeek V4.1 Flash で実装するという決定は、まだ `_context.md` の値とモデルの対応、`runplan.md` の案内、`runpr.md` の示し方に反映していない（どれも Sonnet を示す）。このずれは [#837](https://github.com/isseis/yt2column/issues/837)・[#838](https://github.com/isseis/yt2column/issues/838)（タスク 0088）の実装で扱う。`sonnet` の値については、値からセッションのモデルが直接分かり、名前がモデルのファミリー名を表すという下の 2 項目の理由が成り立たない。値の名前の見直しは #760 で扱う。

-   **実装モデル要件の値は `opus`・`sonnet+opus-review`・`sonnet` の 3 つとし、値はとるべき行動を表す。** `opus` は Opus で実装する。`sonnet+opus-review` は Sonnet で実装し、PR を開く前に Opus のレビューを行う。`sonnet` は OpenCode の DeepSeek V4.1 Flash で実装し、追加のレビューはしない（[ADR-0046](0046-chief-of-staff.md)）。値から、セッションのモデルと、追加のレビューの要否が直接分かるようにするためである（0081 要件定義書の F-001）。`sonnet` を Flash で実装するのは、Opus までは要らないと利用者が判断し、運用がすでにそうなっていたためである（[0088 要件定義書](../../tasks/0088_chief_of_staff/01_requirements.md)「要件定義の際に決めたこと（2026-11-11）」）。
-   **値の名前は、モデルのファミリー名だけを使い、版を含めない。** モデルの版が上がっても、値と計画書を書き換えずに済むためである（F-001）。
-   **当てはめる契機は、旧い区分の契機を引き継ぐ。判定理由には、Sonnet に任せると何が起きやすいかを書く。** 契機は設計の判断の材料として使われており、モデルを選ぶ人には Sonnet にしたときの危険が要るためである（F-001）。
-   **単一フェーズの計画書も、実装モデル要件の値を持つ。** PR マーカーがなくても、モデルを選び、Opus のレビューの要否を決める必要があるためである（F-002）。
-   **Opus のレビューは、`/runplan` が PR を開く前に行う。行うのは、値が `sonnet+opus-review` か `opus` で、かつ、PR のいずれかの phase group（`/runplan` が一度に実装するフェーズのまとまり）が Opus 以外で実装されているか、実装したモデルの記録がない場合である。各 phase group を実装したモデルは、その commit に記録する。** PR を開く前に直せば、最初の PR レビューが直した後のコードを見る。1 つの PR が複数のセッションにまたがっても、Sonnet が書いた commit をレビューなしで通さないためでもある。記録がないときは、安全側に倒す（F-005）。
-   **セッションのモデルと値が合わなくても、`/runplan` は止めずに案内する。** 値は案内であり、合わないときの不足は Opus のレビューで補うためである（F-004）。
-   **読めない値は、推し量って別の値として扱わず、止めずに Opus のレビューを行う側に倒す。値の欄がない計画書では、Opus のレビューを行わない。** 読めない値で止めると、計画書を直す PR が要るためである。欄がないのは、この決定の前に書かれた計画書の正しい形だからである（F-003）。
-   **Opus のレビューは、正しさのレビューと弱いモデルの失敗のレビューの二つを Opus で走らせ、指摘を統合する。cleanup（再利用・単純化・効率の指摘）は範囲に入れない。セッションは Critical と Major の指摘をすべて直し、確認のレビューも Opus で走らせる。指摘を自分の判断で退けず、誤りと考えるときは人に尋ねる。** 指摘は場所が決まっているので Sonnet でも直せ、直し方の誤りは Opus の確認で見つかるためである。Sonnet のセッションが Opus の指摘を退けられると、レビューを足す意味が失われるためでもある（F-005、F-006）。
-   **Opus で走らせられないときは、弱いモデルで代えずに止まり、PR を開かず何も push しない。** レビューが Opus で走ったと思い込んだまま PR を開かないためである（F-005、F-006）。
-   **`/weakreview` は同じ Opus のレビューを行い、既定で直して commit し、push はしない。`--no-fix` を付けたときだけ報告だけにし、`--fix` は何もしない引数として受け入れる。直すのは今 checkout しているブランチの範囲だけで、作業ツリーが clean でなければ止まる。** 同じレビューを行うのは、一つのコマンドで Opus のレビューを済ませられるようにするためである。既定で直すことの理由は記録されていない。`--fix` を受け入れるのは、旧い呼び方でも意図どおりに動くためである。範囲と作業ツリーの制限は、ほかのブランチや作業中の変更を書き換えないためである（F-006）。
-   **Opus のレビューの手順は、`/runplan` と `/weakreview` が共有する一つの共通の手順（`_lib/opus-review.md`）に置く。Opus のレビューを行うかの判断、記録の行の形、正しさのレビューのチェックリスト、弱いモデルの失敗のチェックリスト、決定的な事前の確かめも、この手順が持つ。正しさのレビューは、組み込みの `/code-review` スキルを呼ばず、リポジトリの中のチェックリストで行う。** 二つのコマンドが同じレビューを行い、定義を一か所に保つためである。組み込みのスキルは cleanup を含み、出力の形も決められず、リポジトリの外で変わりうるためでもある（0081 設計書）。
-   **Opus で走ったかは、レビューのサブエージェントが報告する自分のモデル ID で確かめる。Opus の ID でないとき、報告がないとき、呼び出しが失敗したときは、Opus で走らせられなかったものとして止まる。** Agent ツールの `model` の指定が効いたことを、レビューの結果と一緒に確かめるためである（0081 設計書）。
-   **phase group を実装したモデルと、Opus のレビューの結果は、commit メッセージの決まった形の行に記録する。実装の記録は phase group の commit の範囲とモデルを持つ。Opus のレビューを行わないのは、チェックボックスの commit、記録の行の commit、`README.en.md` の同期の commit を除くすべての commit が、Opus の実装の記録で覆われるときだけである。再び実行した `/runplan` は、Opus のレビューを終えた記録があり、その後の commit がチェックボックスの commit、記録の行の commit、`README.en.md` の同期の commit だけのときだけ、レビューを省く。この判断は、レビューを受けるセッションの解釈に任せず、決まったコマンドで行い、値は `origin/main` とブランチの計画書の両方から読み、どちらかがレビューを行うと判断すればレビューを行う。手で実行した `/weakreview` は、レビューを終えた記録を書かない。** 1 つの PR が複数のセッションにまたがっても、記録がブランチと一緒に残るためである。phase group の外の commit や、ブランチの上で下げられた値で、レビューが外れないようにするためでもある。`/weakreview` の範囲は自由に指定でき、PR の範囲と一致する保証がないためである（0081 設計書）。
-   **Opus のレビューの直しの commit は、PR を開く前にローカルの CLI レビューへかけ直さない。** 直しは PR を開く前に入るので、最初の Codex の PR レビューが必ず見るためである（0081 設計書）。
-   **単一フェーズの計画書の値は、計画書の「PR 構成」の節の終わりに書く。** 既存の単一フェーズの計画書がこの節を持ち、複数のフェーズの計画書の `### 3.2 PR 構成` と同じ節で値を見つけられるようにするためである（0081 設計書）。
-   **この決定の前に書かれた計画書の旧い値は書き換えず、`_context.md` の読み替えの表で新しい値として読む。** 承認済みの計画書の本文に触れずに済み、読み替えを 1 か所に集めるためである（F-003）。

## 採らなかった案

-   **`opus` と `sonnet` の 2 段階にする。** 仕組みは最も単純だが、大きくて誤りの入りやすい PR で、最も大きな節約を手放す（[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md)「要件定義の際に決めたこと（2026-11-10）」）。
-   **`opus` と `sonnet+opus-review` の 2 段階にし、Sonnet で実装するときは必ず Opus がレビューする。** 小さな PR では、レビューの費用が実装の費用と同じくらいになる（同上）。
-   **Opus のレビューを、PR を作った後、`/runpr` の前に人が `/weakreview` で実行する。** 直したものが最初の PR レビューに届かず、人の手順も増える（同上）。
-   **Opus のレビューを `/runpr` が最初に実行する。** 直したものが最初の PR レビューに届かない（同上）。
-   **Opus のレビューを省くかを、PR を開く時点のセッションのモデルで決める。** Sonnet が書いた commit が、レビューなしで PR に入りうる（同上）。
-   **Opus のレビューを、いつも省かずに行う。** Opus で実装したものに、同じ費用を二重に払う（同上）。
-   **`opus` の PR は、Sonnet で実装されても Opus のレビューを行わない。** 最もリスクの高い区分が、Opus の実装も Opus のレビューも受けなくなる（同上）。
-   **`opus` の PR を Opus 以外のセッションで実行したら、`/runplan` を止める。** 人が別のセッションを開き直す手間がかかる（同上）。
-   **読めない値で `/runplan` を止める。** 計画書を直す PR が要る（同上）。
-   **Opus のレビューの指摘を、Opus のサブエージェントが直す。** 費用が増える（同上）。
-   **Opus のレビューの指摘を報告だけにし、人が決める。** PR が直す前の状態で開かれる（同上）。
-   **セッションが、理由を添えて Opus の指摘を退けられるようにする。** Opus のレビューを足す意味が失われる（同上）。
-   **Opus で走らせられないときは、PR を開いて、Opus のレビューを行っていないことを記録する。** レビューが行われないまま PR が進みうる（同上）。
-   **`/weakreview` が直しを push まで行う。** push とその後のレビューの扱いは、利用者か `/runpr` に委ねる（同上）。
-   **cleanup（`/simplify` の範囲）も Opus のレビューに含める。** issue が求めるのは正しさのレビューで、Sonnet に直すか否かの判断が増え、統合と確認の費用も増える（同上）。
-   **進行中の計画書の値を、編集上の訂正として書き換える。** `frontier-recommended` の意味が変わるので、編集上の訂正と呼べるかに議論の余地がある（同上）。
-   **進行中の計画書の値を、決定の変更として書き換えて承認し直す。** 3 つの計画書の再承認を要する（同上）。
-   **単一フェーズの計画書には値を持たせない。** 理由は記録されていない。
-   **正しさのレビューで、組み込みの `/code-review` スキルをサブエージェントから呼ぶ。** cleanup の指摘を除けず、出力の形も固定できない。リポジトリの外でスキルが変わると、レビューの中身が黙って変わる（[0081 設計書](../../tasks/0081_implementation_model_choice/02_architecture.md)「設計の際に決めたこと（2026-11-10）」）。
-   **`/runplan` が `/weakreview` を呼ぶ。** 引数の解釈、範囲の確かめ、作業ツリーの確かめが、`/runplan` の手順と重なる（同上）。
-   **弱いモデルの失敗のチェックリストを `weakreview.md` に残し、共通の手順がそれを名指す。** Opus のレビューの定義が二つのファイルに分かれる（同上）。
-   **Opus のレビューの直しの commit を、PR を開く前にローカルの CLI レビューへかけ直す。** 最初の Codex の PR レビューが直しを見るので、CLI レビューの割り当てを使うほどの益がない（同上）。
-   **手で実行した `/weakreview` も、Opus のレビューを終えた記録を書く。** `/weakreview` の範囲は自由に指定でき、PR の範囲と一致する保証がない（同上）。
-   **単一フェーズの計画書の値を、フェーズの見出しの直後に書く。** PR マーカーのある計画書と、値を探す場所がそろわない（同上）。
-   **単一フェーズの計画書の値を、§3 の空いている番号の専用の節に書く。** 節の番号が計画書ごとに変わり、「PR 構成」の節と並んで値の置き場所が二つに見える（同上）。
-   **phase group の実装の記録をステップの ID で書き、PR のステップがすべて Opus の記録で覆われるかで判断する。** 記録を書いた後の commit と、phase group の外の commit を見落とす（同上）。
-   **DeepSeek V4.1 Flash など Claude 以外のモデルを、`opus`・`sonnet+opus-review` の実装モデルの候補にする。** 開発の道具に外部のサービスを加えることになり、確かめていない点も多い。PoC から始める別の issue（[#790](https://github.com/isseis/yt2column/issues/790)）で扱う（同上）。

## 結果

-   Opus のレビューを行う PR では、その分だけ費用と、PR を開くまでの時間が増える。Sonnet で実装して節約する額がそれより大きいという前提は、確かめていない。Sonnet の手戻りが多ければ、`opus` を選ぶほうが安い。
-   Opus のレビューの直しは、phase group ごとのローカルの CLI レビューの後に入る。Claude とは異なる系統のレビューがこの直しを見るのは、PR を開いたときの最初の Codex の PR レビューだけである。
-   Opus を使えない間は、Opus のレビューを要する PR を開けない。
-   計画書を書くコマンドは、新しい値だけを書く。旧い値を読むコマンドは、読み替えの表を使う。読み替えで、承認済みの計画書の `frontier-recommended` の PR は、「Opus が望ましい」から「Sonnet で実装し、Opus のレビューを足す」に意味が変わる。読み替えの表は、PR がまだ作られていない PR マーカーに旧い値を持つ計画書がなくなれば消してよい。
-   この決定の前に作られた phase group の commit には、実装したモデルの記録がない。そうした commit を含む `sonnet+opus-review`・`opus` の PR は、Opus のレビューを受ける。
-   値の名前 `sonnet` は、Sonnet ではなく DeepSeek V4.1 Flash を指す。`sonnet` の PR は Opus のレビューを受けないので、Flash の実装の誤りは、`/runplan` の中のレビュー、ローカルの CLI レビュー、Codex の PR レビューで見つける。リポジトリのコードは DeepSeek のサービスへ送られる。

## 経緯

- 2026-11-10 実装モデル要件を `opus`・`sonnet+opus-review`・`sonnet` の 3 つにし、Sonnet で実装した phase group を含む `sonnet+opus-review`・`opus` の PR では、`/runplan` が PR を開く前に Opus のレビューを行うことにした。`/weakreview` は同じレビューを Opus で行い、既定で直すことにした。旧い値は読み替えの表で読み、単一フェーズの計画書にも値を持たせることにした（[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md)）
- 2026-11-10 Opus のレビューの手順とチェックリストを `/runplan` と `/weakreview` が共有する共通の手順に置き、正しさのレビューをリポジトリの中のチェックリストで行うことにした。Opus で走ったかをサブエージェントの報告するモデル ID で確かめ、実装したモデルとレビューの結果を commit メッセージの行に記録することにした。直しの commit はローカルの CLI レビューにかけ直さず、単一フェーズの計画書の値は「PR 構成」の節に書くことにした（[0081 設計書](../../tasks/0081_implementation_model_choice/02_architecture.md)）
- 2026-11-11 実装モデル要件が `sonnet` の PR は、OpenCode の DeepSeek V4.1 Flash で実装することにした。DeepSeek V4.1 Flash を候補にしない案は、`sonnet` と `/runpr` については取り下げた（[0088 要件定義書](../../tasks/0088_chief_of_staff/01_requirements.md)「要件定義の際に決めたこと（2026-11-11）」、[ADR-0046](0046-chief-of-staff.md)）
