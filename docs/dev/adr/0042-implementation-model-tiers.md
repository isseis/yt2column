# ADR-0042: 実装モデル要件を opus・sonnet+opus-review・sonnet の 3 つにし、sonnet+opus-review の PR は開く前に Opus がレビューする

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

計画書は、PR ごとに `/runplan` を実行するモデルの目安（実装モデル要件）を持つ。人はこれを見て、セッションのモデルを選ぶ。Opus は Sonnet より誤りが少ないが、トークンあたりの単価は Sonnet の 2 倍である。Sonnet に任せられる PR を Sonnet で実装すれば、費用は下がる。ただし、Sonnet が落とした判断を誰かが見つけなければならない。

Codex の PR レビューは、PR を開いたときの 1 回だけである（[ADR-0013](0013-review-setup.md)）。PR を開いた後に直したものは、Codex に見てもらえない。`/runplan` の中のサブエージェントのレビューは、セッションのモデルを引き継ぐ。そのため Sonnet のセッションでは、指定しない限り Opus のレビューは行われない。

過去の `/runplan` のセッション 123 件を Opus 5.5 の単価で換算すると、1 セッションの中央値は約 $13 だった。レビューのサブエージェントは 1 回で中央値約 $0.5 だった。Sonnet が使うトークンが Opus の約 1.5 倍を超えなければ、Sonnet で実装して Opus のレビューを足しても安くなる。この倍率は測っていない（[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md) の「費用の目安」）。

## 決定

以下の決定の仕様は、[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md) と、値と読み替えを定める [_context.md](../../../.claude/commands/_context.md) の「PR marker conventions」が持つ。手順は、それを使うコマンドの定義（`mkplan2.md`・`mkplan.md`・`runplan.md`・`runpr.md`・`weakreview.md`）が持つ。

-   **実装モデル要件の値は `opus`・`sonnet+opus-review`・`sonnet` の 3 つとし、値はとるべき行動を表す。** `opus` は Opus で実装する。`sonnet+opus-review` は Sonnet で実装し、PR を開く前に Opus のレビューを行う。`sonnet` は Sonnet で実装し、追加のレビューはしない。値から、セッションのモデルと、追加のレビューの要否が直接分かるようにするためである。
-   **値の名前は、モデルのファミリー名だけを使い、版を含めない。** モデルの版が上がっても、値と計画書を書き換えずに済むためである。
-   **当てはめる契機は、旧い区分の契機を引き継ぐ。判定理由には、Sonnet に任せると何が起きやすいかを書く。** 契機は設計の判断の材料として使われており、モデルを選ぶ人には Sonnet にしたときの危険が要るためである。
-   **単一フェーズの計画書も、実装モデル要件の値を持つ。** PR マーカーがなくても、モデルを選び、Opus のレビューの要否を決める必要があるためである。
-   **`sonnet+opus-review` の PR では、`/runplan` が PR を開く前に Opus のレビューを行う。** Codex の PR レビューが、直した後のコードを見られるようにするためである。人が別のコマンドを実行する手順も増えない。
-   **Opus のレビューは、一般的な正しさのレビューと、能力の低いモデルの失敗を探すレビューの二つを Opus で走らせ、指摘を統合する。セッションが Critical と Major を直し、確認のレビューも Opus で走らせる。Opus で走らせられないときは、弱いモデルで代えずに止まる。** 指摘は場所が決まっているので Sonnet でも直せ、直し方の誤りは Opus の確認で見つかるためである。レビューが Opus で走ったと思い込んだまま PR を開かないためでもある。
-   **セッションが Opus で動いているときは、`sonnet+opus-review` の PR でも Opus のレビューを省く。セッションのモデルと値が合わなくても、`/runplan` は止めずに案内だけにする。** 実装もレビューも Opus になり、同じ費用を二重に払わないためである。
-   **`/weakreview` は同じ二つのレビューを行い、既定で直す。`--no-fix` を付けたときだけ報告だけにする。** 一つのコマンドで Opus のレビューを済ませられるようにするためである。既定で直すのは、利用者の選択である。
-   **この決定の前に書かれた計画書の旧い値（`frontier-required`・`frontier-recommended`・`standard`）は書き換えず、`_context.md` の読み替えの表で新しい値として読む。読めない値は推し量らずに止まる。** 承認済みの計画書に触れずに済み、読み替えを 1 か所に集めるためである。

## 採らなかった案

-   **`opus` と `sonnet` の 2 段階にする。** 仕組みは最も単純だが、大きくて誤りの入りやすい PR で、節約が最も大きい層の節約を手放す（[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md)「要件定義の際に決めたこと（2026-11-10）」）。
-   **`opus` と `sonnet+opus-review` の 2 段階にし、Sonnet で実装するときは必ず Opus がレビューする。** 小さな PR では、レビューの費用が実装の費用と同じくらいになる（同上）。
-   **Opus のレビューを、PR を作った後、`/runpr` の前に人が `/weakreview` で実行する。** 直したものが Codex の PR レビューに届かず、人の手順も増える（同上）。
-   **Opus のレビューを `/runpr` が最初に実行する。** 直したものが Codex の PR レビューに届かない（同上）。
-   **Opus のレビューの指摘を、Opus のサブエージェントが直す。** 費用が増える（同上）。
-   **Opus のレビューの指摘を報告だけにし、人が決める。** PR が直す前の状態で開かれる（同上）。
-   **Opus のセッションでも Opus のレビューを必ず走らせる。** 仕組みは単純だが、費用が二重になる（同上）。
-   **`opus` の PR を Opus 以外のセッションで実行したら、`/runplan` を止める。** 理由は記録されていない（利用者は、案内だけにする案を選んだ）。
-   **進行中の計画書の値を、編集上の訂正として書き換える。** `frontier-recommended` の意味が変わるので、編集上の訂正と呼べるかに議論の余地がある（同上）。
-   **進行中の計画書の値を、決定の変更として書き換えて承認し直す。** 3 つの計画書の再承認を要する（同上）。
-   **単一フェーズの計画書には値を持たせない。** 理由は記録されていない（利用者は、値を持たせる案を選んだ）。
-   **DeepSeek-V4.1-Flash など Claude 以外のモデルを、実装モデルの候補にする。** 開発の道具に外部のサービスを加えることになり、確かめていない点も多い。PoC から始める別の issue（[#790](https://github.com/isseis/yt2column/issues/790)）で扱う（同上）。

## 結果

-   `sonnet+opus-review` の PR では、Opus のレビューの分だけ費用と、PR を開くまでの時間が増える。Sonnet で実装して節約する額がそれより大きいという前提は、確かめていない。Sonnet の手戻りが多ければ、`opus` を選ぶほうが安い。
-   Opus のレビューの直しは、ローカルの CLI レビューの後に入る。異なる系統のレビューは、PR を開いたときの Codex の PR レビューが担う。
-   計画書を書くコマンドは、新しい値だけを書く。旧い値を読むコマンドは、読み替えの表を使い続ける。読み替えの表は、旧い値を持つ計画書が残る限り要る。
-   `/weakreview` の `--fix` は受け付けなくなる。直すのが既定になったためである。

## 経緯

- 2026-11-10 実装モデル要件を `opus`・`sonnet+opus-review`・`sonnet` の 3 つにし、`sonnet+opus-review` の PR では `/runplan` が PR を開く前に Opus のレビューを行うことにした。`/weakreview` は同じ二つのレビューを Opus で行い、既定で直すことにした。旧い値は読み替えの表で読み、単一フェーズの計画書にも値を持たせることにした（[0081 要件定義書](../../tasks/0081_implementation_model_choice/01_requirements.md)「issue #760 で決めたこと」「要件定義の際に決めたこと（2026-11-10）」）
