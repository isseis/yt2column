# ADR-0027: 記事の生成の状態と完成した記事を、拡張の SW だけが書くジョブの記録として chrome.storage.session に持つ

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

記事は、拡張のビューアのタブの中で生成する（[ADR-0009](0009-viewer-opening.md)・[ADR-0048](0048-extension-only-generation.md)）。ポップアップと、同じ記事のほかのビューアは、生成の状態と完成した記事を、生成を実行するページの外から知る必要がある。完成した記事は、ブラウザを終了するまで持ち、ディスクに書かない（[0090 要件定義書](../../tasks/0090_extension_only_architecture/01_requirements.md) F-001）。

利用者は、結果が分からないまま同じ入力で押し直すことがあり、同じ動画の記事を誤って二度依頼することもある。LLM の呼び出しには料金がかかるので、同じ記事を二度生成しないようにする必要がある。同じ記事を探すことと生成を始めることが別々に行われると、同時に押された 2 つの開始がどちらも記事を見つけず、二重に生成しうる。

拡張の Service Worker（SW）はいつでも停止されうるので、そのメモリだけを正しい値の置き場所にできない。記事を指す値を誰でも入力から計算できると、拡張のコードや利用者がその計算方法に依存しうる（[CLAUDE.md](../../../CLAUDE.md)「Keep internals unobservable」）。

## 決定

-   **生成の状態と完成した記事は、ジョブごとに 1 つのジョブの記録として `chrome.storage.session` に置き、書き込むのは SW だけにする。** 実行するビューアは、工程の進み具合と結果を SW へ知らせる。ポップアップとビューアは記録を読み、`chrome.storage.onChanged` で表示を更新する。`storage.session` はメモリだけにあり、正しい値を SW の停止で失わず、書き手を 1 つにして判定の排他を保つためである。記録の形は [0090 設計書](../../tasks/0090_extension_only_architecture/02_architecture.md) の「記録の形」にある。
-   **SW は、受け付けた求めを 1 つずつ直列に処理し、同じ入力・同じ動画の判定と記録の追加を、その 1 つの処理の中で行う。** 探すことと始めることを分けず、同時の 2 つの開始で二重に生成しないためである。規則は 0090 設計書の「SW の調停」にある。
-   **ジョブ ID は、予約のときに SW が作る 128 ビットの乱数とし、不透明な値にする。** ビューアの URL とページの間のメッセージに入る。同じ入力の判定は、WASM の入口が検査を通った入力から計算する SHA-256 の値（`inputDigest`）で行い、この値はジョブの記録の中にだけ置く。秘密を持つプロセスがなくなり、入力から計算した値を URL に置くと計算方法に依存されうるためである。規則は 0090 設計書の「ジョブ ID と、ジョブを見分ける値」にある。
-   **予約は、今の照会付きの開始と同じ順で判定する。** 同じ `inputDigest` の記録が処理中か完成ならそのジョブを示し、照会付きで同じ動画の別の記録が処理中か完成なら、受け付けた時点の最も新しいものを、記録を変えずに示し、それ以外は新しい実行を加える。失敗したか止まった記録は、同じジョブ ID のまま生成し直す。処理中の記録を使う前に、実行するページが生きていることを確かめる。同じ記事を二度生成せず、止まった実行を記事として示さないためである。規則は 0090 設計書の「SW の調停」と「止まった実行の判定」にある。
-   **生成の開始は送り方を宣言し、照会付きと照会なしを区別する。** 照会なしの開始は、同じ動画の別の記録があっても今の入力の記事を生成する。生成を始めるかどうかを、送り手が宣言した値で選ぶためである（[CLAUDE.md](../../../CLAUDE.md)「Declare, don't infer」）。規則は 0090 設計書の「SW の調停」にある。
-   **記録は件数 50・大きさの合計 8 MiB を上限とし、記事 1 つは 256 KiB まで、同時に走る実行は 2 つまでとする。** 上限を超えるときは、完成・失敗・止まった記録のうち終わった時点の最も古いものから捨て、処理中の記録は捨てない。捨てられる記録がないときと、処理中の実行が 2 つあるときは、開始を拒否する。`storage.session` の容量（約 10 MB）の中に収め、Worker のメモリと料金を一度に多く使わないためである。規則は 0090 設計書の「上限と捨てる記録」にある。
-   **記録は、コピーした字幕と概要欄を持たない。** 字幕は最大 4 MiB になりうるうえ、記事の表示にも同じ動画の照会にも要らないためである。規則は 0090 設計書の「記録の形」にある。
-   **完成した記事と、失敗と止まった実行の記録は、ブラウザを終了するまで、再読み込みと閉じたタブの復元の後も示す。** ブラウザの終了、拡張の再読み込みと更新、上限による捨てで、記録は失われ、ビューアは記事が失われたことを示す。これは受け入れる。料金のかかった記事と、料金のかかったかもしれない実行を見失わないためで、ディスクに書かないのは見た動画の記事を端末に残し続けないためである。規則は 0090 設計書の「記録が消えるとき」と「利用者に示す状態の種類」にある。
-   **前の版との互換の仕組みは作らない。** 記録は版の値を持つが、版の移行の仕組みは作らない。拡張の更新で `storage.session` は空になり、利用者は開発者 1 人であるためである。規則は 0090 設計書の「記録の形」にある。

この決定は、まだコードと仕様の文書（[development.md](../guides/development.md)・[security.md](../security.md)）に反映していない。今は、拡張とホストとサーバがジョブの API を使い、サーバが記事をメモリに持つ。この差分は [#773](https://github.com/isseis/yt2column/issues/773) の実装で解消する。

同じ動画の記事の有無を照会で返すことと、ジョブの記録を読める相手は [ADR-0006](0006-threat-model.md) が、拡張が保存するものは [ADR-0010](0010-extension-stores-nothing.md) が、自動で送り直さないことは [ADR-0028](0028-no-automatic-resend.md) が定める。

## 採らなかった案

-   **秘密を使わない SHA-256 で記事のキーを計算する。** 誰でもキーを計算できると、生成を始めずに記事の有無を知る手段になり、キーが不透明であることも保てない（[0044 設計書](../../tasks/0044_article_job_api/02_architecture.md) の Document Status の `Comments` と §3.2）。0058 は、このうち記事の有無を知る手段を作らないという理由を当てにしないとし、キーの計算方法に依存させないという理由だけを残した（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **受け取った文字列から記事のキーを計算する。** プロンプトと記事に届く値が同じ入力を、2 回生成しうる（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）。
-   **`net/http` の `ServeMux` のパターンでキーをパスから取り出す。** `ServeMux` はパスをデコードしてから照合するので、`%2F` を含むキーが別の形に読まれうる（[0044 設計書](../../tasks/0044_article_job_api/02_architecture.md) §3.1.1）。
-   **投稿の操作は、投稿の完了を待って応答する。** 記事は複数のメッセージに分けて 1 秒の間隔で送られ、1 通ごとに 30 秒で打ち切られるので、完了を待つとホストの 20 秒の打ち切りを超えることがある（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）。
-   **記事のキャッシュを永続化し、再起動をまたいで記事と投稿の状態を保つ。** 理由は記録されていない（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md) §2.3 は、親 issue #501 で永続化しないと決めたとだけ述べる）。
-   **再生成のフラグを設ける。** 理由は記録されていない（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md) §2.3 は、親 issue #501 で設けないと決め、作り直すにはサーバを再起動するとだけ述べる）。
-   **動画単位で記事の有無を問い合わせる操作を加える。** 生成の開始に照会の指定を加えれば、送るのが 1 回で済み、照会と開始の間に競合がなく、振る舞いを送り手が指定した値で選べる（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **照会の指定を新しいパスとホストのメッセージの新しい `op` で表す。** この案の利点は前の版との互換を求めるときにだけ要るもので、互換は求めない。ホストに版の扱いが、拡張に版の食い違いの判定と表示が要る。同じ入力・同じ検査・同じ結果の集合を持つ操作が 2 つの入口に分かれる（[0058 設計書](../../tasks/0058_same_video_article/02_architecture.md)「設計の際に決めたこと（2026-11-04）」）。
-   **旧 API を削除した後の `/articles` へのリクエストに、専用の拒否の理由を加える。** `/articles` を呼ぶのは手で送る `curl` くらいであり、専用の理由を加えると、拒否の理由の表とそのガードを変えることになるうえ、`/articles` のための分岐も残る（[0059 要件定義書](../../tasks/0059_remove_legacy_articles_api/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **照会の指定をクエリかヘッダで表す。** 本文と別に検査する場所が増える（[0058 設計書](../../tasks/0058_same_video_article/02_architecture.md)「設計の際に決めたこと（2026-11-04）」）。
-   **`mode` のない生成の開始を照会なしと解釈する。** 前の版の拡張が送る開始を受け付けられるが、互換を考えないので、その利点は要らない。補う解釈を持たないほうが、送り手が指定を書き忘れた誤りが拒否として表に出る（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「設計のレビューで決めたこと（2026-11-04）」）。
-   **前の版のホストやサーバに照会付きの開始を送ったとき、黙って生成しないようにする。** 前の版が受け取れば拒否する置き場所、版の食い違いの見分け方と専用の表示、前の版を相手にした確かめ方が要り、その費用は、利用者が開発者 1 人で害が生成 1 回分の料金にとどまることに見合わない（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「設計のレビューで決めたこと（2026-11-04）」）。
-   **字幕の差分や選択範囲の近さで同じ記事かを判定する。** issue のスコープ外であり、同じ動画かどうかだけで判定する（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」と §2.3）。
-   **同じ動画の記事が複数あるとき、一覧を示す。** 最近の記事の一覧の画面は issue のスコープ外であり、一覧を示すと実質的にその画面になる（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **同じ動画の応答に既存の記事の状態を入れる。** 状態の取得の応答の形を生成の開始の応答に重ねて持つことになる。状態の取得は応答の後すぐに送るので、1 回のやり取りを省く利点は小さい（[0058 設計書](../../tasks/0058_same_video_article/02_architecture.md)「設計の際に決めたこと（2026-11-04）」）。
-   **完成した記事を、ビューアのタブが開いている間だけ持つ。** 保存の仕組みは要らないが、再読み込みやタブを閉じる操作で記事を失い、作り直すと料金がもう一度かかる（0090 要件定義書「要件定義の際に決めたこと（2026-11-12）」）。
-   **完成した記事をディスクに保存し、ブラウザの再起動の後も残す。** 見た動画の記事が端末に残り、削除の操作と上限の設計が要る（0090 要件定義書「要件定義の際に決めたこと（2026-11-12）」）。
-   **ジョブ ID を、今のキーと同じく入力から計算した値にする。** 秘密を持つプロセスがなく、入力から計算した値を URL に置くと、計算方法に依存されうる（[0090 設計書](../../tasks/0090_extension_only_architecture/02_architecture.md)「ジョブ ID と、ジョブを見分ける値」）。
-   **処理中の状態を実行するページのメモリに持ち、ほかのページが `BroadcastChannel` で尋ねる。** ページの間の問い合わせが増え、判定の排他を保つのが難しい（0090 設計書「設計の際に決めたこと（2026-11-12）」）。
-   **完成した記事を `chrome.storage.local` か IndexedDB に置く。** ディスクに書くことになる（0090 設計書「記録が消えるとき」）。
-   **`onUpdateAvailable` で拡張の更新を遅らせ、記事を守る。** 遅らせてもブラウザの終了で記事は失われ、守れる時間が短い。開いている拡張のページがある間は、更新はもともと適用されない（0090 設計書「記録が消えるとき」）。

## 結果

-   ブラウザを終了するか、拡張のページを開いていない間に拡張が更新されると、記事は失われる。利用者は記事を作り直す。
-   同じ入力の判定は入力のすべての値から行うので、照会なしの開始では、選択範囲や動画メタデータが少しでも違えば別の記事として生成する。照会付きの開始は同じ動画の記事を示すが、記録は件数と大きさに上限があり、ブラウザの終了で消えるので、同じ動画の記事がないことは保証しない。
-   SW がジョブの記録の唯一の書き手なので、ポップアップとビューアは記録を直接書かない。実行するビューアの知らせは、記録の実行するページと一致しなければ捨てられる。
-   記事 1 つの大きさの上限（256 KiB）を超える記事は、失敗になる。
-   拡張のページは、`storage.session` の記録を読める。ジョブ ID と `inputDigest` は、拡張の外に出ない。
