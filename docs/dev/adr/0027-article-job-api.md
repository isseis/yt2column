# ADR-0027: 拡張とホストとサーバはジョブの API で生成と状態の取得を分け、記事をプロセスごとの秘密によるキーでサーバのメモリに持つ

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

ブラウザ拡張は、生成した記事をビューアに表示する必要がある（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md) §1）。そのためには、拡張が記事の生成を始め、その状態と記事を受け取る必要がある。拡張の Service Worker はいつでも停止されうるので、状態はサーバに問い合わせて知る。

拡張からサーバへの送信は、ブラウザが 1 つのメッセージごとに起動する Native Messaging のホストが中継し、1 回の中継は 20 秒で打ち切る（ホストの構成は [ADR-0005](0005-server-architecture.md)）。記事の生成は、この時間に収まらないことがある（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）。

利用者は、結果が分からないまま同じ入力を送り直すことがあり、同じ動画の記事を誤って二度依頼することもある。LLM の呼び出しには料金がかかるので、同じ記事を二度生成しないようにする必要がある。一方、記事を指す値をサーバの外の誰でも計算できると、拡張や利用者がその計算方法に依存しうる（[CLAUDE.md](../../../CLAUDE.md)「Keep internals unobservable」）。

## 決定

-   **拡張とホストとサーバは、ジョブの API だけを使う。** ジョブの API は、生成の開始（`POST /jobs`）と状態の取得（`GET /jobs/{key}`）の 2 つの操作である。この ADR で「生成の開始」「状態の取得」と書くときは、この 2 つの操作を指す。拡張の Service Worker が生成の開始を送り、ポップアップとビューアが状態の取得を繰り返す。拡張とホストとサーバの間の操作を、この 2 つに固定するためである。規則は [development.md](../guides/development.md) の「ジョブの API」と、[security.md](../security.md) §8.2「localhost サーバ」にある。
-   **ホストが受け付けるのは、版のメンバ `v` が `1` で、操作 `op`（`start`・`status`）を宣言したメッセージだけとする。** ホストは操作ごとに決めたメソッドとパスへ送り、それ以外のメッセージにはサーバへ何も送らずに `protocol_error` を返す。拡張が送り先のパスやメソッドを指定する手段はない。拡張に送り先を選ばせないためである。規則は security.md §8.2 にある。
-   **サーバは、この 2 つの操作のほかのリクエストのターゲットを `not_found` で拒否する。** 受け付ける操作を 2 つに限るためである。規則は security.md §8.2 にある。
-   **生成と状態の取得を別の操作にし、どの操作も長い処理を待たずに応答する。** 生成の開始は、記事のキーを返す。記事の状態は、状態の取得が、決まった値（`running`・`done`・`failed` など）で返す。完了した記事は、状態の取得の応答が、無効化した表示用の Markdown（`markdown`。記事の中のメンションを無効化した文字列、[ADR-0043](0043-copy-mention-neutralization.md)）と保存するファイルの中身（`file`）として持ち、無効化したかどうか（`mentionsNeutralized`）と、ビューアの見出しに使う無効化した動画のタイトルとチャンネル名（`videoTitle`・`channelName`）を添える。記録は、`videoTitle` を返すために、生成の開始が送った動画のタイトルを持つ。`file` は無効化しない。ファイルへの保存とクリップボードへのコピーはビューアが拡張のページで行い、サーバへの操作を持たない（[ADR-0010](0010-extension-stores-nothing.md)、コピーでのメンションの無効化は [ADR-0043](0043-copy-mention-neutralization.md)）。1 回の中継が 20 秒で打ち切られ、記事の生成はこの時間に収まらないことがあるためである（背景）。規則は development.md の「ジョブの API」にある。
-   **記事のキーは、検査を通った入力の値から、サーバのプロセスごとの秘密を鍵とする HMAC-SHA256 で計算する。** 計算に使うのは、生成の開始の入力の検査を通った後の 5 つの値（正規化した `videoUrl`、`transcript`、省略を空文字列とした `title`・`channelName`・`description`）である。受け取ったバイト列からは計算しない。送り方 `mode` と同じ動画の判定に使う動画 ID は、キーに入れない。秘密は `crypto/rand` の 32 バイトで、サーバの起動ごとに作り、メモリにだけ持ち、ログにも応答にも出さない。同じ入力には同じキーを返して記事を二度生成せず、誰でも計算できる値にはしないためである。規則は security.md §8「ブラウザ拡張と localhost サーバ」と §8.2 に、キーの計算の詳細は [0044 設計書](../../tasks/0044_article_job_api/02_architecture.md) §3.2「記事のキー」にある。
-   **記事のキーは不透明な値とする。** 拡張は、生成の開始が返したキーをそのまま送り返すだけで、その形にも計算方法にも依存しない。秘密を使う目的は、攻撃に対する防御ではなく、公開しないキーの計算方法に利用者と拡張を依存させないことである。サーバは、小文字の 16 進の 64 文字のほかのキーを、補正せずに `invalid_key` で拒否する。ホストはキーの形を検査せず、1 つのパスの部分としてエスケープしてから送る。規則は security.md の §8「ブラウザ拡張と localhost サーバ」と §8.2、0044 設計書 §3.2 にある。
-   **同じ入力では記事を作り直さない。** 生成の開始は、同じキーの記事が処理中か完了なら、LLM を呼ばずにそのキーを返す。失敗したキーは生成し直す。作り直したいときは、サーバを再起動する。LLM の呼び出しには料金がかかり、同じ記事を二度生成しないためである。規則は [0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」と security.md §8.2 にある。
-   **サーバの状態はメモリにだけ置く。** 記事のキャッシュはサーバのプロセスの中だけにあり、ディスクに書かない（サーバの構成は [ADR-0005](0005-server-architecture.md)）。サーバを再起動すると、記事の状態はすべて失われ、ビューアは記事が失われたことを示す。これは受け入れる。理由は記録されていない（0044 要件定義書 §2.3 は、親 issue #501 で永続化しないと決めたとだけ述べる）。規則は security.md §8.2 にある。
-   **記事のキャッシュは有限の件数だけを持ち、コピーした字幕を持たない。** 件数の上限を超えるときは、完了または失敗した古い記録から捨て、処理中の記録は捨てない。捨てた記録と再起動の前の記録のキーは、状態の取得で `unknown` になる。記事のキャッシュの記録は、コピーした字幕を持たない。生成中の字幕は、生成のジョブだけが持つ。サーバの停止では処理中の生成を取り消す。停止の後に完了した記事は、キャッシュとともに失われて誰も受け取れないためである。規則は security.md §8.2 にある。
-   **生成の開始は送り方 `mode` を必ず宣言する。** `mode` は `inquiry`（照会付き）か `plain`（照会なし）で、ない本文やほかの値は、どちらかに補わずに `invalid_body` で拒否する。生成を始めるかどうかを、送り手が宣言した値で選べるようにするためである。規則は [0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「設計のレビューで決めたこと（2026-11-04）」と security.md §8.2 にある。
-   **照会付きの開始は、同じ動画の最新の記事を示す。** 今の入力のキーの記事が処理中か完了ならそのキーを返す。そうでなく、同じ動画（動画 ID が同じ）の別のキーの記事が処理中か完了なら、生成を始めず、キャッシュも変えずに、そのうち最も新しく受け付けた 1 件のキーを同じ動画の応答で返す。同じ動画の応答は、記事の状態を持たない。同じ動画の記事を探すことと生成を始めることは、キャッシュの 1 回の排他制御の中で行う。同じ動画の記事を二度生成しないためである。規則は 0058 要件定義書「要件定義の際に決めたこと（2026-11-03）」、[0058 設計書](../../tasks/0058_same_video_article/02_architecture.md)「設計の際に決めたこと（2026-11-04）」、security.md §8「ブラウザ拡張と localhost サーバ」にある。
-   **照会なしの開始は、同じ動画の別のキーの記事があっても、今の入力の記事を生成する。** 今の入力のキーの記事が処理中か完了なら、照会なしの開始もそのキーを返す。利用者が今の入力の記事を求めたときは、同じ動画の別の記事があってもそれを作るためである。規則は 0058 要件定義書「要件定義の際に決めたこと（2026-11-03）」にある。
-   **前の版との互換の仕組みは作らない。** 拡張とホストとサーバは同じ版で使う。版の食い違いを見分ける仕組みと、そのための表示は設けない。利用者は開発者 1 人で、害は生成 1 回分の料金にとどまり、互換の仕組みの費用に見合わないためである。規則は 0058 要件定義書「設計のレビューで決めたこと（2026-11-04）」にある。

この決定のうち投稿の操作をなくす部分と、`markdown` を無効化した文字列にして `mentionsNeutralized` を添える部分は、まだコードと development.md・security.md に反映していない。いまのサーバとホストは投稿の操作を受け付け、記事のキャッシュは投稿の状態を持ち、`markdown` は無効化していない。この差分は [#770](https://github.com/isseis/yt2column/issues/770) の実装で解消する。

同じ動画の記事の有無を照会で返すことを、信頼の境界の内側で受け入れるリスクとする判断は [ADR-0006](0006-threat-model.md) が、拡張が何も保存せず状態の正しい値をサーバに置くことは [ADR-0010](0010-extension-stores-nothing.md) が定める。

## 採らなかった案

-   **秘密を使わない SHA-256 で記事のキーを計算する。** 誰でもキーを計算できると、生成を始めずに記事の有無を知る手段になり、キーが不透明であることも保てない（[0044 設計書](../../tasks/0044_article_job_api/02_architecture.md) の Document Status の `Comments` と §3.2）。0058 は、このうち記事の有無を知る手段を作らないという理由を当てにしないとし、キーの計算方法に依存させないという理由だけを残した（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **受け取った文字列から記事のキーを計算する。** プロンプトと記事に届く値が同じ入力を、2 回生成しうる（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）。
-   **`net/http` の `ServeMux` のパターンでキーをパスから取り出す。** `ServeMux` はパスをデコードしてから照合するので、`%2F` を含むキーが別の形に読まれうる（[0044 設計書](../../tasks/0044_article_job_api/02_architecture.md) §3.1.1）。
-   **投稿の操作は、投稿の完了を待って応答する。** 記事は複数のメッセージに分けて 1 秒の間隔で送られ、1 通ごとに 30 秒で打ち切られるので、完了を待つとホストの 20 秒の打ち切りを超えることがある（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）。
-   **記事のキャッシュを永続化し、再起動をまたいで記事と投稿の状態を保つ。** 理由は記録されていない（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md) §2.3 は、親 issue #501 で永続化しないと決めたとだけ述べる）。
-   **再生成のフラグを設ける。** 理由は記録されていない（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md) §2.3 は、親 issue #501 で設けないと決め、作り直すにはサーバを再起動するとだけ述べる）。
-   **動画単位で記事の有無を問い合わせる操作を加える。** 生成の開始に照会の指定を加えれば、送るのが 1 回で済み、照会と開始の間に競合がなく、振る舞いを送り手が指定した値で選べる（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **照会の指定を新しいパスとホストのメッセージの新しい `op` で表す。** この案の利点は前の版との互換を求めるときにだけ要るもので、互換は求めない。ホストに版の扱いが、拡張に版の食い違いの判定と表示が要る。同じ入力・同じ検査・同じ結果の集合を持つ操作が 2 つの入口に分かれる（[0058 設計書](../../tasks/0058_same_video_article/02_architecture.md)「設計の際に決めたこと（2026-11-04）」）。
-   **旧 API を削除した後の `/articles` へのリクエストに、専用の拒否の理由を加える。** `/articles` を呼ぶのは手で送る `curl` くらいであり、専用の理由を加えると、拒否の理由の表とそのガードを変えることになるうえ、`/articles` のための分岐も残る（[0059 要件定義書](../../tasks/0059_remove_legacy_articles_api/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **照会の指定をクエリかヘッダで表す。** 本文と別に検査する場所が増える（[0058 設計書](../../tasks/0058_same_video_article/02_architecture.md)「設計の際に決めたこと（2026-11-04）」）。
-   **`mode` のない生成の開始を照会なしと解釈する。** 前の版の拡張が送る開始を受け付けられるが、互換を考えないので、その利点は要らない。補う解釈を持たないほうが、送り手が指定を書き忘れた誤りが拒否として表に出る（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「設計のレビューで決めたこと（2026-11-04）」）。
-   **前の版のホストやサーバに照会付きの開始を送ったとき、黙って生成しないようにする。** 前の版が受け取れば拒否する置き場所、版の食い違いの見分け方と専用の表示、前の版を相手にした確かめ方が要り、その費用は、利用者が開発者 1 人で害が生成 1 回分の料金にとどまることに見合わない（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「設計のレビューで決めたこと（2026-11-04）」）。
-   **字幕の差分や選択範囲の近さで同じ記事かを判定する。** issue のスコープ外であり、同じ動画かどうかだけで判定する（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」と §2.3）。
-   **同じ動画の記事が複数あるとき、一覧を示す。** 最近の記事の一覧の画面は issue のスコープ外であり、一覧を示すと実質的にその画面になる（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）。
-   **同じ動画の応答に既存の記事の状態を入れる。** 状態の取得の応答の形を生成の開始の応答に重ねて持つことになる。状態の取得は応答の後すぐに送るので、1 回のやり取りを省く利点は小さい（[0058 設計書](../../tasks/0058_same_video_article/02_architecture.md)「設計の際に決めたこと（2026-11-04）」）。

## 結果

-   サーバを再起動すると記事の状態が失われる。利用者は記事を作り直す。
-   キーは入力のすべての値から計算するので、照会なしの開始では、選択範囲や動画メタデータが少しでも違えば別の記事として生成し直す。照会付きの開始は同じ動画の記事を示すが、キャッシュは件数に上限があり再起動で消えるので、同じ動画の記事がないことは保証しない。
-   秘密は起動ごとに作り直すので、再起動の前に得たキーは、再起動の後には同じ入力から得られない。キャッシュも起動ごとに空から始まるので、失うものはない。
-   キャッシュの件数の上限で、サーバを長く動かし続けてもメモリは増え続けない。捨てた記録のキーは `unknown` になり、同じ入力の開始は新しい生成になる。
-   ソケットに接続できる同じユーザーのプロセスは、照会付きの開始で、動画単位で記事の有無とキーを知れる（[ADR-0006](0006-threat-model.md)）。
-   拡張とホストとサーバの版がそろっていないと動かない組み合わせがある。前の版のサーバは `mode` を無視して生成しうる（害は生成 1 回分の料金）。新しいサーバは、前の版の拡張が送る `mode` のない開始を拒否する。利用者は 3 つを同じ版にそろえる。
-   サーバの停止で取り消した生成の記事は失われる。

## 経緯

- 2026-10-27 生成の開始・状態の取得・投稿の操作を別々の操作とする新しい API を加え、検査を通った入力の値から計算したキーで記事をサーバのメモリのキャッシュに持ち、同じ入力では作り直さないことにした。キャッシュは永続化せず、件数に上限を設ける。拡張が新しい API に移るまで旧 API（`/articles`）を今のまま残し、ホストは版のメンバ `v` の有無で旧形式と新形式のメッセージを見分けて、`v` のないメッセージを `/articles` へ中継した（CLAUDE.md「Declare, don't infer」の一時的な例外）（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）
- 2026-10-27 新しい API のパスを `POST /jobs`・`GET /jobs/{key}`・`POST /jobs/{key}/publish` とし、記事のキーを、秘密を使わない SHA-256 から、サーバのプロセスごとの秘密を鍵とする HMAC-SHA256 に改めた。生成を始めずに記事の有無を知る手段を作らないことと、キーを不透明に保つことが理由である。キャッシュを `internal/articlecache` に置き、件数の上限を 100 件にした（[0044 設計書](../../tasks/0044_article_job_api/02_architecture.md) §3.1・§3.2・§3.3.4）
- 2026-10-29 拡張を新しい API に全面的に移し、旧形式のメッセージ（`/articles` の経路）を送らなくした。`/articles` の削除は #526 に残した（[0050 要件定義書](../../tasks/0050_viewer_tab/01_requirements.md)「要件定義の際に決めたこと（2026-10-29）」）
- 2026-11-04 旧 API（`/articles`）とホストの旧形式の中継を削除し、サーバが受け付けるのをジョブの API だけにした。ホストは `v` を持たないメッセージを中継せずに `protocol_error` を返すようになり、`v` の有無で形を見分ける処理と CLAUDE.md の例外もなくなった（[0059 要件定義書](../../tasks/0059_remove_legacy_articles_api/01_requirements.md)「issue #526 で決めたこと」）
