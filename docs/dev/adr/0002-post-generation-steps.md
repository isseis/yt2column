# ADR-0002: 生成の後に字数の調整と検証・推敲の 2 つの工程を置き、検証・推敲は直す箇所の一覧だけを返す

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

記事を 1 回の LLM の呼び出しで生成する形では、0008 の評価で品質の目標を満たせなかった。残った問題は、素材にない知識の補足や意味の変わる言い換え、字幕の誤認識の写し、本文の字数の超過である（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) §1）。

生成とは別の LLM が記事と素材を突き合わせると、根拠のずれと誤認識の写しを見つけられた。字数は機械的に数えられる。そこで、生成の後に、字数を数えて超過したときだけ縮める工程と、記事を素材と突き合わせて直す工程を置く。

## 決定

-   **処理の順序は、生成、字数の調整、検証・推敲、最終の字数の確認、出典の付与とする。** 字数の調整を検証・推敲より前に置くのは、縮める際に混入したずれも検証・推敲で直せるようにするためである（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) F-001）。順序は [0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) の「F-001: 段階の順序と入出力」にあり、各工程の役割は [production_profile.md](../production_profile.md) の「パイプライン」にある。
-   **字数の調整は、本文が 4,000 字を超えたときだけ、生成と同じ `LLMClient` で縮める。** 生成と同じ `LLMClient` を使うのは、記事を書き直す作業であり、検証とは性質が違うためである（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) F-002）。上限と目標の字数は [project_overview.md](../project_overview.md) の「パイプライン」と [production_profile.md](../production_profile.md) の「パイプライン」にある。
-   **縮めた後も 4,000 字を超える記事と、検証・推敲の後で 4,000 字を超える記事は、もう一度縮めずに `ErrTooLong` で記事全体を失敗させる。** 超過した記事を成功として返さないためである（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) F-002）。規則は [0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) の「F-002: 字数の調整」にある。
-   **字数は、タイトルの行と出典のブロックを除いた本文の、改行を除くコードポイントの数とする（Markdown の記号は数える）。** 理由は記録されていない。数え方は [0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) の「F-001: 段階の順序と入出力」にある。
-   **`--no-shorten` と `--no-review` で工程を省ける。2 つのフラグは CLI だけが持ち、開発・検証のためのものであって、ブラウザ拡張ではサポートしない。** 工程の効果を比べる評価と、費用を抑えたい場合のためにある（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) F-005）。各フラグが省く工程は [cli.md](../guides/cli.md) の「使い方」と「生成の後の工程」にある。
-   **検証・推敲の LLM は、記事を書き直さず、直す箇所の一覧だけを返す。記事を直すのは `ArticleWriter` であり、一覧を当てはめて作る。** 各項目は、直す前の記述（記事からの一字一句そのままの引用）、直した後の記述（削った場合はそのことを示す印）、理由の種類、根拠となる素材の箇所を持つ。一覧に載っていない書き換えを起こさせないためである（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) F-003）。規則は [0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) の「F-003: 検証・推敲」にあり、応答の形は [0010 設計書](../../tasks/0010_post_generation_review/02_architecture.md) の「3.5.3. 応答の形と受理の規則（H-01）」にある。
-   **一覧は全部当てはめるか、全部拒否する。** 各項目の「直す前の記述」が記事の中にちょうど 1 回だけ現れ、異なる項目の範囲が重ならず、どちらの記述も改行を含まず、当てはめた後の `##` の見出しが数・文言・順序のすべてで変わらないときにだけ当てはめる。1 つの項目でも満たさなければ、一覧全体を拒否する。改行と見出しの条件は、段落と行の構成と、記事の構成を変えさせないためである（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) F-003）。規則は [0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) の「F-003: 検証・推敲」と、[0010 設計書](../../tasks/0010_post_generation_review/02_architecture.md) の「3.5.4. 当てはめの規則」にある。
-   **検証・推敲の応答は信頼できない入力として検証する。** 応答は 0 件以上の項目を持つ一覧 1 つだけからなり、各項目は 4 つの要素をちょうど 1 つずつ持つ。未知の要素・重複した要素・一覧の後に続く内容は拒否し、応答の大きさと項目の数には上限を置く。拒否は `ErrMalformedOutput` で、部分的な一覧を返さない。理由は記録されていない。規則は [0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) の「F-003: 検証・推敲」にあり、上限の値は [0010 設計書](../../tasks/0010_post_generation_review/02_architecture.md) の「3.5.3. 応答の形と受理の規則（H-01）」にある。
-   **無変更の項目（`before` と `after` が同じ項目）は受理する。** 記事の文面は変えず、`--review-log` の一覧には `No change.` と書く。拒否すると、無害な 1 項目のために記事全体が失敗し、生成と字数の調整の呼び出しも無駄になるためである（[0013 要件定義書](../../tasks/0013_identical_review_revisions/01_requirements.md) §1）。規則は [0013 要件定義書](../../tasks/0013_identical_review_revisions/01_requirements.md) の「F-001: 無変更の項目の受理」と「F-002: 一覧での無変更の印」にある。
-   **いずれかの工程の失敗は記事全体の失敗とする。** 前の工程の結果に戻したり、検証していない記事を返したりしない。理由は記録されていない。規則は [0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) の「F-006: 失敗の報告」にある。
-   **検証・推敲のプロバイダとモデルは生成と別に設定できる。** 未設定なら生成のプロバイダ・モデル・effort を受け継ぐ。理由は記録されていない。設定の仕様は [project_overview.md](../project_overview.md) の「設定（環境変数）」にある。

## 採らなかった案

-   **検証・推敲の LLM に記事を書き直させる。** 一覧に載っていない書き換えを起こさせるためである（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) F-003）。
-   **生成の前に字幕を整形し、その字幕で生成する。** 字幕を書き直して元の字幕を置き換える方法はとらない。採点は元の字幕を根拠に行うので、書き直しで入った誤りが観点「根拠」の不合格に直結し、しかも生成からは誤りと見分けられない。出力も字幕とほぼ同じ長さになり、長い動画では出力トークンが多くなる（[0018 要件定義書](../../tasks/0018_article_quality/01_requirements.md) F-008「試作 A」）。
-   **各工程を複数回繰り返す。** 各工程の呼び出しは、1 本の記事につき最大 1 回とした（[0010 要件定義書](../../tasks/0010_post_generation_review/01_requirements.md) 2.3）。理由は記録されていない。
-   **無変更の項目を拒否する。** 0010 の受理の規則と失敗の方針を変えることになり、無害な 1 項目のために記事全体が失敗し、生成と字数の調整の呼び出しも無駄になる（[0013 要件定義書](../../tasks/0013_identical_review_revisions/01_requirements.md) §1・2.3）。
-   **検証・推敲のテンプレートで、無変更の項目を返さないよう指示する。** モデルが守る保証がなく、無変更の項目が返る場合の扱いは別に要る（[0013 要件定義書](../../tasks/0013_identical_review_revisions/01_requirements.md) 2.3）。
-   **一覧から無変更の項目を取り除く、または応答を補正する。** 0010 の「補正しない」「一覧は変更の完全な記録になる」という方針に反する（[0013 要件定義書](../../tasks/0013_identical_review_revisions/01_requirements.md) 2.3）。

## 結果

-   記事 1 本につき、生成・字数の調整（走るときだけ）・検証・推敲の最大 3 回の LLM の呼び出しになる。どこかで失敗すれば記事は出ない。
-   記事の文面が変わるのは、一覧に挙がった箇所だけである。一覧は、その記事に何をしたかの完全な記録になる。
-   一覧の形で表せない直し（構成の変更など）は、この工程では行えない。構成や見出しのずれが残りうることは、[production_profile.md](../production_profile.md) の製品の制約に記録している。
-   プロバイダを足しても、この 2 つの工程のコードは変えない。変わるのは、使う `LLMClient` だけである。
