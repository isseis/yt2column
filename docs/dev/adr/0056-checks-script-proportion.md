# ADR-0056: タスクの _checks/ に置く一時スクリプトとそのテストは、本体の変更の規模・実行回数・想定運用環境に見合う作りにする

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

タスクは、`docs/tasks/NNNN_<name>/_checks/` にタスク専用のスクリプトを置く。例は、変更の前後の関係を確かめる `diff` の確かめ、移行の前提を確かめる移行ゲート、実装を始める前の前提の確認である。これらは 1〜2 回だけ手で実行する。`make test` も CI も実行せず、マージの後は保守しない。そのため、費用は主に、書く作業と、PR のレビューで読む量である。

ところが、作りとテストの規模に基準がないと、一時スクリプトにも常設の開発ツール並みの要求が積み上がる。設計書に常設のツール並みの防御を書くと、計画・実装・各レビューがそれを忠実に満たそうとして、テストと壊し確認をさらに広げる。

-   タスク 0078 では、差分が 2 行の ADR の直しに、547 行の確かめを書いた（[0080 要件定義書](../../tasks/0080_diff_check_proportion/01_requirements.md) 1 章）。
-   タスク 0121 では、本体の変更がコマンドの定義 3 ファイルと約 100 行のスクリプトとテストにとどまった。それに対し、2 回だけ実行する移行ゲートとそのテストは計 1,293 行になった（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) 1 章）。

## 決定

-   **一時スクリプトは置き場所で定める。用途によらず、タスクの `_checks/` に置くスクリプトをすべて対象にし、常設のツールと区別する。** 常設のツールとは、開発ツール、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテストである。`_checks/` という置き場所が、実行も保守もマージの後にしないことを意味しているので、判定がぶれないためである（[requirements_process.md](../conventions/requirements_process.md) の「4. Acceptance Tests」、[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) の F-001）。
-   **一時スクリプトとそのテストの設計と規模は、本体の変更の規模・実行回数・想定運用環境に見合ったものにする。`diff` の確かめのスクリプトの既定の言語はシェルとし、ほかの言語はシェルで足りない理由を計画に書いたときに使う。** マージの後に保守しないので、費用を確かめる変更に見合ったものにするためである（同）。
-   **一時スクリプトが必ず満たす核は 4 つとする。目的のものを検出すること、正常なときに検出しないこと、異常なときにフェイルクローズすること、呼び出し元を汚さないことである。核を超える防御は、設計書か計画が実運用上の具体的な必要性を書いたときだけ入れる。** 使われない環境への耐性や敵対的な入力への防御が、設計・テスト・レビューを膨らませたためである。判定できない状態を通ったと報告しないことは、核として残す（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) の F-002）。
-   **想定運用環境の既定は、スクリプトを実行する人の、このリポジトリのふだんの作業ツリーとする。ほかの環境への耐性は、その環境で実際に実行することを設計書か計画が書いたときだけ求める。** 既定がないと、何が過剰かの判断が人と文書によって分かれるためである（同）。
-   **一時スクリプトのテストは、既定ではコミットしない。壊し確認は 1 回行い、その結果を計画に記録する。コミットするのは計画が具体的な理由を書いたときだけとし、その場合も核の代表ケースに限る。** 1〜2 回しか実行しないスクリプトでは壊し確認の結果が残れば足り、コミットしたテストはレビューで読む量を増やすためである（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) の F-003）。
-   **計画は、前のタスクの `_checks/` を手本として写させず、壊し方は「チェックごとに少なくとも 1 つ」とだけ書いて並べ挙げない。** 前のタスクの大きなプログラムの構造が受け継がれ、計画に並べた壊し方がそのまま作業になるためである（[mkplan.md](../../../.claude/commands/mkplan.md)）。
-   **過剰な一時スクリプトとそのテストを、要件・設計・計画・フェーズのまとまり・弱いモデルの作業の各レビューで指摘する。** 上流の過剰な仕様は下流で膨らむので、最も上流から各段で止めるためである（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) の F-004）。
-   **この基準は、決めた変更が `main` に入った後に書く文書と、その `_checks/` だけに当てはめる。** 承認済みの文書に後から当てはめると、計画と実装が食い違うためである（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) の F-005）。
-   **一時スクリプトの設計水準の基準は、エージェントの操作の規則を緩めない。** 出力を GitHub に投稿するときのメンションの検査と、ネットワークの操作の承認（[CLAUDE.md](../../../CLAUDE.md) の「Tool Execution Safety」）が当たる。これらはスクリプトの作りではなく、エージェントが何をしてよいかの規則だからである（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) の F-002）。

## 採らなかった案

-   **`diff` の確かめのスクリプトをシェルだけに限る。** 文書の構造を比べる確かめが書きにくくなる（[0080 要件定義書](../../tasks/0080_diff_check_proportion/01_requirements.md)「要件定義の際に決めたこと（2026-11-10）」）。
-   **既定の言語を決めず、見合った作りにせよとだけ書く。** 基準がないまま、前のタスクの版を写す流れが残る（同）。
-   **過大な確かめを指摘する観点を、フェーズのまとまりのレビューと弱いモデルの作業のレビューだけに置く。** 計画の段階で過大さを見逃し、実装の後に初めて見つかる（同）。
-   **計画が「一時スクリプト」と宣言したものだけを対象にする。** 宣言を書き忘れると、基準がない状態に戻る（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md)「要件定義の際に決めたこと（2026-11-24）」）。
-   **想定運用環境の既定を置かず、実運用上の具体的な必要性だけを求める。** 必要性があるかの判断が人と文書によって分かれる（同）。
-   **一時スクリプトのテストを、理由がなくてもコミットしてよいことにし、代表ケースに限るだけにする。** コミットが既定になり、規模を抑える歯止めが弱い（同）。
-   **一時スクリプトのテストを一切コミットしない。** テストを残す具体的な理由がある場合に対応できない（同）。
-   **観点を置く場所を、設計・計画・フェーズのまとまり・弱いモデルの作業の 4 か所に限る。** 要件の段階で入った過剰な仕様を、設計のレビューまで見つけられない（同）。
-   **承認済みでも、まだ実装していない PR の `_checks/` には新しい基準を当てはめる。** 承認済みの計画と実装が食い違う（同）。
-   **この決定を ADR-0016 に書き足す。** 移行ゲートや前提の確認は文書のテストではなく、ADR-0016 の主題からはみ出す（同）。

## 結果

-   一時スクリプトの規模の判断は、規約の基準に照らした人とレビュアーの判断であり、数の上限はない。同じ種類の変更でも、計画によって作りが分かれうる。その判断の誤りは、PR のレビューで見つける。
-   核を超える防御を書かなかった一時スクリプトは、想定運用環境の外では誤った結果を出しうる。核に異常なときのフェイルクローズを残し、1〜2 回だけ手で実行するものなので、受け入れる。ほかの環境で実行するときは、設計書か計画にそう書く。
-   コミットしないテストは、マージの後に再実行できない。一時スクリプトはマージの後に実行しないので、壊し確認の記録で足りるとする。
-   この決定より前に承認された文書の `_checks/`（タスク 0121 を含む）は、元の規模のまま残る。
-   `diff` の確かめに固有の規則（記録した差分の読み取り、前後の関係を述べる受け入れ基準の書き方）は、[ADR-0016](0016-document-test-policy.md) にある。

## 経緯

- 2026-11-24 比例原則の対象を、`diff` の確かめから `_checks/` の一時スクリプト全般とそのテストに広げ、この ADR に分けた。核の 4 つ、想定運用環境の既定、テストを既定でコミットしないこと、観点を置く 5 か所、適用の範囲を定めた（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md)「issue #1132 で決めたこと」「要件定義の際に決めたこと（2026-11-24）」）
