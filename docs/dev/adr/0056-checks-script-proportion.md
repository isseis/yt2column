# ADR-0056: タスクの _checks/ に置く一時スクリプトとそのテストは、本体の変更の規模・実行回数・想定運用環境に見合う作りにする

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

タスクは、`docs/tasks/NNNN_<name>/_checks/` にタスク専用のスクリプトを置く。例は、変更の前後の関係を確かめる `diff` の確かめ、移行の前提を確かめる移行ゲート、実装を始める前の前提の確認である。これらは 1〜2 回だけ手で実行し、`make test` も CI も実行しない。そのため、費用は主に、書く作業と、PR のレビューで読む量である。

ところが、作りとテストの規模に基準がないと、一時スクリプトにも常設の開発ツール並みの要求が積み上がる。設計書に常設のツール並みの防御を書くと、計画・実装・各レビューがそれを忠実に満たそうとして、テストと壊し確認（確かめの対象を壊して、確かめが失敗することを確かめること）をさらに広げる。

-   タスク 0078 では、差分が 2 行の ADR の直しに、547 行の確かめを書いた（[0080 要件定義書](../../tasks/0080_diff_check_proportion/01_requirements.md) 1 章）。
-   タスク 0121 では、本体の変更がコマンドの定義・スクリプト・テストの約 100 行の追加にとどまった。それに対し、2 回だけ実行する移行ゲートとその補助とテストは、計 1,293 行になった（[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) 1 章）。

## 決定

各項目の仕様の正本は、[requirements_process.md](../conventions/requirements_process.md) の「4. Acceptance Tests」と、各項目が挙げるコマンドの定義に置く。要件は [0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md) の各機能要件（F-001〜F-006）にある。

-   **一時スクリプトは置き場所で定める。用途によらず、タスクの `_checks/` に置くスクリプトとその補助のファイルをすべて対象にし、常設のツールと区別する。** 常設のツールとは、開発ツール、CI のスクリプト、`.claude/commands/_lib/` のスクリプト、`make test` で実行するテストである。`_checks/` という置き場所そのものが、`make test` も CI も実行しないことを意味するので、用途で分けるより判定がぶれないためである（0124 要件定義書の F-001）。
-   **一時スクリプトとそのテストの設計と規模は、本体の変更の規模・実行回数・想定運用環境に見合ったものにする。`diff` の確かめのスクリプトの既定の言語はシェルとし、ほかの言語はシェルで足りない理由を計画に書いたときに使う。ほかの用途の一時スクリプトの既定の言語は定めない。** マージの後に保守しないので、その費用を、確かめる変更の規模に見合う範囲に抑えるためである（0124 要件定義書の F-001。シェルの既定は [0080 要件定義書](../../tasks/0080_diff_check_proportion/01_requirements.md) の F-001）。
-   **一時スクリプトが必ず満たす核は 4 つとする。目的のものを検出すること、正常なときに検出しないこと、異常なときにフェイルクローズすること、呼び出し元を汚さないことである。他者が書いた入力が読めないとき、または受け入れる形に合わないときに、通ったと報告しないことは、フェイルクローズの性質に含まれる。細工された入力への防御は核に含めない。核を超える防御は、設計書か計画が実運用上の具体的な必要性（どの実行で、どの状況や脅威が起きるか）を書いたときだけ入れる。** 使われない環境への耐性や敵対的な入力への防御が、設計・テスト・レビューを膨らませたためである。判定できない状態を通ったと報告しないことは、核として残す（0124 要件定義書の F-002）。
-   **想定運用環境の既定は、スクリプトを実行する人またはエージェントの、手元の機械にあるこのリポジトリの作業ツリー（`main` のチェックアウトか linked worktree）とする。クラウドのセッションは既定に入れない。ほかの環境への耐性は、その環境で実際に実行することを設計書か計画が書いたときだけ求める。** 既定がないと、何が過剰かの判断が人と文書によって分かれるためである（0124 要件定義書の F-002）。
-   **一時スクリプトの出力を GitHub に投稿するときの守りは、エージェントの操作の既存の規則に任せ、基準はそれらを緩めない。出力をコミットするときは、PR のレビューで読む。** 当たる規則は、メンションの検査と、ネットワークの操作の承認（[CLAUDE.md](../../../CLAUDE.md) の「Tool Execution Safety」）である。投稿する文の守りはそれらがすでに担っており、スクリプトの側の網羅的なエスケープは重ねた守りになるためである（0124 要件定義書の F-002）。
-   **一時スクリプトのテストは、既定ではコミットしない。壊し確認を行い、その結果を計画に記録する。コミットするのは計画が具体的な理由を書いたときだけとし、その場合も核の代表ケースに限る。「レビューの修正の後に再実行するため」だけでは理由にならず、修正の後は壊し確認をやり直して記録し直す。** 1〜2 回しか実行しないスクリプトでは壊し確認の結果が残れば足り、コミットしたテストはレビューで読む量を増やすためである。どのスクリプトもレビューで直されるので、再実行を理由に認めると、テストのコミットが既定になる（0124 要件定義書の F-003）。
-   **計画は、前のタスクの `_checks/` を手本として写させず、壊し方は「チェックごとに少なくとも 1 つ」とだけ書いて並べ挙げない。これは一時スクリプトのすべてに当てはまる。** 前のタスクの大きなスクリプトの構造が受け継がれることも、計画に並べた壊し方がそのまま作業になることも、用途によらず起こるためである（[mkplan.md](../../../.claude/commands/mkplan.md)、0124 要件定義書の F-004）。
-   **過剰な一時スクリプトとそのテストを、要件・設計・計画・フェーズのまとまり・テスト・弱いモデルの作業の各レビューで指摘する。CLI レビューとクロスチェックの部分レビューが、必要性の書かれていない核を超える防御を求めたときは、その指摘を実害のないものとして扱う。** 上流の過剰な仕様は下流で膨らみ、各レビューの指摘もそれを広げるので、最も上流から各段で止めるためである（0124 要件定義書の F-005）。
-   **この基準は、この決定を入れた変更が `main` に入った後に承認される文書に、文書ごとに当てはめる。それより前に承認された文書とその `_checks/` は変えず、そうした文書が求めることを過剰とは指摘しない。** 承認済みの文書に後から当てはめると、文書の間や計画と実装が食い違うためである（0124 要件定義書の F-006）。

## 採らなかった案

-   **`diff` の確かめのスクリプトをシェルだけに限る。** 文書の構造を比べる確かめが書きにくくなる（[0080 要件定義書](../../tasks/0080_diff_check_proportion/01_requirements.md)「要件定義の際に決めたこと（2026-11-10）」）。
-   **`diff` の確かめの既定の言語を決めず、見合った作りにせよとだけ書く。** 基準がないまま、前のタスクの版を写す流れが残る（同）。
-   **過大な確かめを指摘する観点を、フェーズのまとまりのレビューと弱いモデルの作業のレビューだけに置く。** 計画の段階で過大さを見逃し、実装の後に初めて見つかる（同）。
-   以下は、[0124 要件定義書](../../tasks/0124_checks_proportion/01_requirements.md)「要件定義の際に決めたこと（2026-11-24）」による。
    -   **計画が「一時スクリプト」と宣言したものだけを対象にする。** 宣言を書き忘れると、基準がない状態に戻る。
    -   **想定運用環境の既定を置かず、実運用上の具体的な必要性だけを求める。** 必要性があるかの判断が人と文書によって分かれる。
    -   **クラウドのセッションの作業ツリーも、想定運用環境の既定に含める。** 実行しない環境への耐性まで既定で求めることになる。
    -   **他者が書いた入力を読むか、出力を投稿・コミットするスクリプトでは、核を超える防御を常に必要とする。** 0121 と同じ規模の防御が、移行ゲートのたびに既定で入る。
    -   **一時スクリプトのテストを、理由がなくてもコミットしてよいことにし、代表ケースに限るだけにする。** コミットが既定になり、規模を抑える歯止めが弱い。
    -   **一時スクリプトのテストを一切コミットしない。** テストを残す具体的な理由がある場合に対応できない。
    -   **テストをコミットする理由の中身を定めず、計画とレビューの判断に任せる。** 再実行のためという理由がそのまま通る。
    -   **計画の 2 つの規則を `diff` の確かめだけに残す。** 移行ゲートなどで、前のタスクの写しと壊し方の並べ挙げが起きうる。
    -   **一時スクリプト全般の既定の言語をシェルにする。** issue が求めておらず、0121 では言語より網羅的なエスケープが規模を膨らませた。
    -   **観点を置く場所を、設計・計画・フェーズのまとまり・弱いモデルの作業の 4 か所に限る。** 要件の段階で入った過剰な仕様と、CLI レビューなどから来る過剰な要求を止められない。
    -   **承認済みでも、まだ実装していない PR の `_checks/` には新しい基準を当てはめる。** 承認済みの計画と実装が食い違う。
    -   **最初の文書がこの変更より前に承認されたタスクには、後の文書も含めて新しい基準を当てはめない。** 長いタスクで、古い基準が残り続ける。
    -   **この決定を ADR-0016 に書き足す。** 移行ゲートや前提の確認は文書のテストではなく、ADR-0016 の主題からはみ出す。

## 結果

-   一時スクリプトの規模の判断は、規約の基準に照らした人とレビュアーの判断であり、数の上限はない。同じ種類の変更でも、計画によって作りが分かれうる。その判断の誤りは、PR のレビューで見つける。
-   核を超える防御を書かなかった一時スクリプトは、想定運用環境の外では誤った結果を出しうる。核に異常なときのフェイルクローズが残り、しかも 1〜2 回だけ実行するものなので、この誤りは受け入れる。ほかの環境で実行するときは、設計書か計画にそう書く。
-   コミットしないテストは、マージの後に再実行できない。一時スクリプトはマージの後に実行しないので、壊し確認の記録で足りるとする。
-   この決定より前に承認された文書の `_checks/`（タスク 0121 を含む）は、元の規模のまま残る。
-   `diff` の確かめに固有の規則（記録した差分の読み取り、前後の関係を述べる受け入れ基準の書き方）は、[ADR-0016](0016-document-test-policy.md) にある。記録した差分の読み取りは、`diff` の確かめにだけある、規模を抑える手段である。
