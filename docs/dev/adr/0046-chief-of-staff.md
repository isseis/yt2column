# ADR-0046: chief は人の判断を待つものを示し、決まった入力だけをほかのエージェントに送り、マージの後の次のコマンドを自動で送り、タスクの workspace を issue から作って、終わったら確かめて消す

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

タスクは、Herdr の workspace（タスクごとの git の worktree）で、Claude Code と OpenCode のエージェントが並行して進める。各タスクは `/mkreq`・`/mkarch`・`/mkplan`・`/runplan` が PR を作り、人がレビューしてから `/runpr` を実行し、`/runpr` がマージの確認を人に尋ねてマージする。workspace が増えると、人を待っているものが見えず、マージの後に次のコマンドを決まったモデルで走らせる操作にも人の手がかかる。

タスクを始めるたびに、人が手で worktree と workspace を作ってエージェントを起動し、終わった workspace も人が片付けている。

これらを chief というコーディネーターに任せる。chief はほかのエージェントのセッションに入力を送り、worktree と workspace を作って消すので、開発用の道具の信頼の境界になる。chief が誤った入力を送ると、人が選んでいない答えが送られたり、違うモデルでコマンドが走ったりする。エージェントの画面、PR の説明、レビューは、ほかのエージェントや外部が書いた信頼できない文字列である（[security.md](../security.md) §6）。

Herdr はリポジトリの外の道具で、chief はその CLI の出力に依る。OpenCode はコマンドでモデルを切り替えられず、質問を示しても Herdr に `blocked` と報告されない。

## 決定

chief は人の代わりに判断せず、人が選んだ答えと決まった範囲の入力だけを、Go の道具 `chief` が確かめてからほかのエージェントへ送る。マージの後の次のコマンドと、マージコンフリクトになった PR の解消のコマンドは、GitHub と git の状態を引き金に自動で送り、タスクの workspace は issue から作って、完了を確かめてから人の確認で消す。

以下の決定の仕様は [chief_architecture.md](../chief_architecture.md) が持ち、決定の出典は [0088 要件定義書](../../tasks/0088_chief_of_staff/01_requirements.md) の機能要件である（以下、番号だけで書いた F-NNN は、その機能要件を指す）。

### 人の判断の中継

-   chief は、人の代わりに判断しない。止まっているエージェントの質問には、人が chief の選択肢で選んだ答えだけを中継し、送る直前に質問と選択肢が人に示したときと同じであることを確かめる。中継するのは 1 つを選ぶ問いの選択肢だけで、権限の確認、自由に書く答え、複数を選ぶ問いは中継しない。質問と選択肢は画面のとおりに示す。
    -   理由：人の判断であることを保ったまま、pane を移る手間をなくすためである。権限の確認を中継しないのは、実行されるコマンドを見ないまま許可しやすくなるためである。自由に書く答えを中継しないのは、chief が送る入力が人の書いた任意の文まで広がるためである（0088 要件定義書の F-005）。
    -   `/runpr` のマージの質問には、次のコマンド（NEXT）をそのセッションで実行する答えはない（[ADR-0047](0047-runpr-merge-question.md)）。
-   画面は、実画面のサンプルで確かめた形だけを受け付ける。答えを中継するときは、人に示した質問と選択肢から作った照合値を、送る直前に読み直した画面から作った照合値と比べ、一致したときに、選択肢の番号から決まったキー入力だけを送る。
    -   理由：確かめていない形の画面で、人が選んでいない答えを送らないためである（0088 設計書の 3.4・3.6）。
-   レビュー待ちの PR への `/runpr` は、人が PR の詳細を見てから選んだときだけ送る。
    -   理由：人がレビューした後に `/runpr` を実行するという流れを保つためである（F-004）。
-   人が選んで送るタスクのコマンドの提案（`/mkarch`・`/mkplan`・`/runplan`、引き継ぎの `/runplan` を含む）は、人が選んだ項目の ID を道具が受け取り、送る直前に作り直した行が同じ項目を提案しているときだけ送る。項目の ID は、コマンドの文（タスクを含む）から作られる。
    -   理由：人が見た後に行のタスクが変わっても同じ種類のコマンドであれば送信が通り、人の選んでいないタスクへ送ってしまうためである。自動送信の提案が行と別のタスクを示すこともあるので、行のタスクではなく、人が選んだ項目で縛る（[0105 設計書](../../tasks/0105_chief_post_merge_next_command/02_architecture.md)「設計の際に決めたこと（2026-11-19）」）。

### 送る入力と送り先

-   chief がタスクの workspace へ送る入力は、次のものだけにする。`git` のコマンド、`gh pr merge`、自由な文、`/weakreview` は送らない。自分の workspace のエージェントには何も送らない。
    -   `/clear`・`/model`（Claude Code）、`/new`（OpenCode）
    -   `/mkreq`・`/mkarch`・`/mkplan`・`/runplan`・`/runpr`・`/mergemain`
    -   1 つを選ぶ問いの選択肢を選ぶ入力
    -   理由：送る入力の範囲を決めておけば、chief の誤りで送られうるものも、その範囲に限られるためである。`/weakreview` を送らないのは、上位モデルのレビューを `/runplan` が PR を開く前に行う（[ADR-0042](0042-implementation-model-tiers.md)）からである（F-006）。`/mergemain` は、コンフリクトの解消を自由な文ではなく決まった形のコマンドで送るために足した（[0115 要件定義書](../../tasks/0115_chief_conflict_resolution/01_requirements.md) の F-006）。
-   コマンドごとのエージェントとモデルは、次のとおりとする。モデルが切り替わったこと（OpenCode では、モデルが合っていること）を確かめてからコマンドを送り、確かめられなければ送らない。値が読めないときと、値がないときは、推し量らず、コマンドを送らない。`chief` 自身の Antigravity 操作対応（pane・記録の読み取りや送信）は対象外であり、送り先は現行の Claude Code と OpenCode のままとする。`_context.md` の送り先の表（`Command routing` 表）における `/runplan` 用の行キーは `runplan-high`・`runplan-standard+high-review`・`runplan-low` とする（[ADR-0055](0055-harness-independent-commands.md)）。
    -   `/mkreq`・`/mkarch`・`/mkplan`：Claude Code・Opus
    -   `/runplan`：実装モデル要件の値（[ADR-0042](0042-implementation-model-tiers.md)）に従う。`high`（旧 `opus`）は Claude Code・Opus、`standard+high-review`（旧 `sonnet+opus-review`）は Claude Code・Sonnet、`low`（旧 `sonnet`）は OpenCode・DeepSeek V4.1 Flash
    -   `/runpr`：OpenCode・DeepSeek V4.1 Flash
    -   `/mergemain`：Claude Code・Opus
    -   理由：送り先とモデルの取り違えをなくすためである。`/mergemain` に Opus を使うのは、文書の衝突を、両側の変更を保てるかどうか判断しながら解消させるためである（0115 要件定義書「要件定義の際に決めたこと（2026-11-19）」）。`/runpr` と `low`（旧 `sonnet`）の `/runplan` に Flash を使うのは、これらに Opus までは要らないと利用者が判断し、2026-11-11 の時点で運用がすでにそうなっていたためである。`low` の対応は ADR-0042 が持つ（F-006）。
-   実装モデル要件の値ごとの送り先とモデルは 1 か所に置き、そこを直すだけで差し替えられるようにする。`standard+high-review`（旧 `sonnet+opus-review`）を OpenCode に差し替えた後は、OpenCode のセッションが上位モデルのレビューを走らせられないため PR を開かずに止まるので、chief は同じ workspace の Claude Code・Sonnet へ同じ `/runplan` を送ることを提案し、Claude Code が上位モデルのレビューと PR の作成を行う。
    -   理由：`standard+high-review` を DeepSeek V4.1 Flash で実装して上位モデルのレビューを受ける形と、今の Sonnet の形の成果物の品質を、別の issue で比べてからどちらにするかを決めるためである（0088 要件定義書の F-006）。
-   コマンドごとの送り先のエージェントとモデルは、`_context.md` の送り先の表 1 か所に置き、chief は `origin/main` の版から読む。
    -   理由：人への案内と chief が同じ表を読み、値ごとの送り先を 1 行の直しで差し替えられるようにし、ブランチで表を書き換えても送り先が変わらないようにするためである。表は [_context.md](../../../.claude/commands/_context.md) が持つ（0088 設計書の 3.3）。
-   `/runpr` と `low`（旧 `sonnet`）の `/runplan` は、OpenCode を通して DeepSeek のサービスにリポジトリのコード、レビューのスレッド、コマンドの定義を送る。この送り先を選ぶことを受け入れる。
    -   理由：上の項のとおり Flash を使うと決めたことに伴うものである。DeepSeek V4.1 Flash が手順を守れるかは、[#790](https://github.com/isseis/yt2column/issues/790) で確かめていない（0088 要件定義書の 4.2）。

### マージの後の自動送信

-   `/runpr` がマージを終えたら、chief は次のコマンド（`/mkarch`・`/mkplan`・`/runplan`）を人に尋ねずに送る。人がマージの確認に答えたことを、次のコマンドを送ることの承認とみなす。
    -   引き金は画面ではなく、GitHub の PR の状態（`MERGED`）と git の状態（`origin/main` に対して未コミットの変更も先のコミットもなく、次のブランチか `origin/main` を指している）で確かめる。画面と transcript から読み取った判断は、送信を止めるか条件を狭めるためだけに使う。
    -   自動送信は、chief が待ち受けの中で PR が開いている状態から `MERGED` になったのを見たときだけ、マージした PR 1 件につき 1 回までとし、chief を起動し直しても変わらない。chief が動いていなかった間のマージは、提案として示す。
    -   理由：マージの後の操作には人の判断が要らないためである。引き金を画面に頼らないのは、人に尋ねずに入力を送る判断を、信頼できない文字列に委ねないためである。1 回に限り、見たマージだけを対象にするのは、送ったコマンドが失敗して条件がまた満たされても、人が手で走らせた次のコマンドや古いマージがあっても、同じコマンドを 2 回走らせないためである（F-007）。
-   自動送信を止める例外は、実装計画書の PR マーカーの欄に「この PR を作る `/runplan` を自動で送ってよいか」として宣言する。この欄は `/mkplan` が書く。欄がない計画書は、自動送信してよいものとして扱う。
    -   理由：途中で対話のセッションを挟むことは計画を作るときに決まり、計画書に置けば別の場所に書き写さずに済むためである（CLAUDE.md の「Declare, don't infer」）。欄を PR を作る側に付けるのは、計画書のマージの後・PR-1 の前で止めることも表せるためである。欄がない計画書を自動送信してよいものとして扱うのは、欄がないことが、この決定の前に書かれた計画書の正しい形だからである（F-008）。
-   自動送信の欄は `**自動送信**` とし、値は `auto` と `hold` にする。PR マーカーのない計画書では「PR 構成」の節に書く。
    -   理由：値を ASCII にして、似た文字による読み違いをなくすためである。形は `_context.md` の「PR marker conventions」が持つ（0088 設計書の 3.8）。
-   送れたかが分からない送信は送り直さず、その workspace への送信を、人が解除するまで止める。
    -   理由：同じコマンドを 2 回走らせるより、人に示して止まるほうを選ぶためである（F-006）。
-   次のコマンドを `/runplan` と決めるために読む計画書のステップは、受け入れる 3 つの書き方（チェックボックスの行、2 章の見出し、2 章の 1 行の太字の段落）からだけ読む。2 章の中のステップに似た行（書き方 A（`- [ ] **ステップ N-M**`）に似たチェックボックスの行を含む）や、チェックボックスのないステップがあれば、ステップを読めないものとし、推し量らずに要確認にして送らない。すべての PR がマージ済みの計画書は、ステップを読めるかどうかにかかわらず完了とする。今の仕様は [chief_architecture.md](../chief_architecture.md) の 3.5（判定と副作用の条件）にあり、決定の出典は [0113 要件定義書](../../tasks/0113_plan_step_reading/01_requirements.md) の 3 章である。
    -   理由：規約はステップをチェックボックスで書くことだけを求め、`main` の計画書は見出しと太字の段落でもステップを書いている。それを読まないと、PR が残るタスクの次のコマンドが決まらない。似た行を読み替えないのは、残りのステップを見落として「残りなし」と誤って読まないためである（[0113 要件定義書](../../tasks/0113_plan_step_reading/01_requirements.md)「要件定義の際に決めたこと（2026-11-19）」）。

### マージコンフリクトの解消の自動送信

仕様は [0115 要件定義書](../../tasks/0115_chief_conflict_resolution/01_requirements.md) の F-001〜F-007 にある。

-   chief は、ラウンドごとに、開いている PR の GitHub の `mergeable` を読む。`CONFLICTING` の PR の行をコンフリクトとして示し、`UNKNOWN` はコンフリクトとして扱わない。受け付けない値を読んだときは、その行を「要確認」にする。
    -   理由：コンフリクト中の PR では CI が走らず、人が気づくまで止まるためである。`UNKNOWN` を扱わないのは、GitHub が計算を終えていない値から推し量って送らないためである（0115 要件定義書の F-001）。
-   待ち受けのラウンドで PR が `CONFLICTING` なら、chief はその workspace の Claude Code へ `/mergemain <PR>` を人に尋ねずに送る。状態が変わるところを見ることは条件にしない。`once` では送らない。
    -   引き金は GitHub と git の状態である。PR の base が `main` で、head がこのリポジトリのブランチで、worktree が PR の head ブランチにあって HEAD が PR の head と同じで変更がなく、そのラウンドの `main` の取得が成功したときだけ送る。
    -   画面と transcript は送ることを止める向きにだけ使う。workspace のエージェントがすべて入力を待ち、Claude Code の pane の transcript があって、人の最後のタスクのコマンドの後に人の入力がなく、送信が止まっていないときだけ送る。`/runpr` の実行中は送らない。
    -   PR のブランチの `/mergemain` のコマンドの定義が `origin/main` のものと同じときだけ送る。人が選んで送るときも同じである。
    -   自動送信は PR の head のコミットごとに 1 回までとし、chief を起動し直しても変わらない。
    -   理由：マージと違い、コンフリクトは今の状態そのものが解消すべきものなので、chief が見ていなかった間に起きたものでも送ってよい。git の状態を確かめるのは、`/mergemain` の前提を満たさない状態の pane に `/clear` を送って、その文脈を消さないためである。定義を比べるのは、Claude Code がコマンドの定義を PR のブランチから読むので、人に尋ねずに送るコマンドを `main` でレビューされた定義で動かすためである。head ごとに 1 回にするのは、失敗した解消を、人が手を入れるまで繰り返さないためである。人の後の入力を条件にするのは、送る前の `/clear` で人の会話の文脈を黙って消さないためである（0115 要件定義書の F-002）。
-   `/mergemain` は、PR のブランチに `origin/main` を merge で取り込む（rebase はしない）。取り込みのたびに README・ADR・プロトコル番号の「Taking in `main`」の規則を当てる。内容の衝突のうち解消するのは、`.md` のファイルの衝突と、プロトコル番号の宣言の行だけの衝突に限る。それ以外の衝突、両側の変更を保てない文書の衝突、ADR の番号か主題が `main` とぶつかる取り込みでは止まる。止まるときは作業の前の状態に戻して、理由の種類と衝突したファイルを報告する。`gh pr merge`、PR レビューの依頼、ローカルの CLI レビュー、`numreserve` は行わない。戻すのは自分が作ったものだけで、ほかの変更があれば戻さずに止まる。`/mergemain` を実行することは、人が打っても chief が送っても、その PR についての `gh pr view`・`git fetch origin`・PR の head ブランチへの push を承認する。この承認は CLAUDE.md の「Tool Execution Safety」が持つ。手順は `.claude/commands/mergemain.md` が持つ。
    -   理由：Go・TypeScript のロジックの衝突を自動で解消して誤りを push しないためと、最初は狭く始めて実績を見て広げるためである。文書の衝突まで含めるのは、多くのタスクが同時に変える `CLAUDE.md` やコマンドの定義でも衝突が起きるためである。ADR の番号を振り直さないのは、人に尋ねずに送ったコマンドに、戻せない記録のタグと PR への書き込みをさせないためである。承認を CLAUDE.md に書くのは、人に尋ねずに送るコマンドには、ネットワークの操作を承認する人の行為がなく、`/chief` の起動が承認するのは道具の読み取りだけだからである。解消の結果は、その後の `/runpr` とマージの質問で人の判断を通る（0115 要件定義書の F-005）。
-   解消できなかったことは、chief が GitHub の状態から判定する。送った後に pane が動き、その後エージェントがすべて入力を待つ状態に戻ったことを確かめ、PR が同じ head のまま `CONFLICTING` なら、「解消できず」として人の判断を待つ行にする。chief は `/mergemain` の報告を読まない。コンフリクトの行では、人が `/mergemain` を選んで送ることもできる。
    -   理由：報告の形を足して transcript から読むと、画面と transcript の読み取りの例外が広がるためである（0115 要件定義書の F-003・F-004）。
-   送る前に PR を作ったコマンドの報告を読めれば、その控えを作る。`/mergemain` の merge コミットで head が変わったときは、控えを新しい head に引き継ぐ。読めなければ、控えを作らずに送る。
    -   理由：送る前の `/clear` で消える報告を PR の詳細に残しつつ、控えを作れないことで自動送信を止めないためである（0115 要件定義書の F-002）。

### 記録

-   自動送信の記録、送信の記録、送信の停止、chief の待ち受けで PR を見た記録、worktree ごとの履歴の記録、ロックなどは、リポジトリの外の状態のディレクトリに、同名のものがすでにあれば作らず、上書きしない形で置く。判定にはそれを読み返す。入力を送る前に送信の記録を作り、終わりの記録のない送信は、送れたかが分からないものとしてその workspace への送信を止める。
    -   理由：起動し直しても 2 回送らず、同時に動く 2 つの chief の一方だけが送り、途中で止まった送信を送り直さないためである。ADR-0014 の例外である（0088 設計書の 3.5）。
-   記録は、送るコマンドとタスクを決めるためには使わない。例外は、下の「ブランチ `main` をチェックアウトした worktree のタスク」だけである。送ることについて使うのは、この例外のほかは、次の 3 つだけである。
    -   送ることを止める条件（リセットの候補を狭める PR の詳細の控えと報告の控えを含む）。
    -   自動送信の候補の workspace を名指す条件。名指された workspace は、Herdr・git・GitHub で確かめ直す。
    -   人に示すリセットの候補を名指す条件（報告が読めずに見送ったリセットの記録）。名指されたリセットの候補は、Herdr と transcript で確かめ直す。見送りの記録は、その pane へコマンドかリセットを送れたときと、14 日の後に消す。
    -   理由：PR を見た記録は、自動送信を可能にする条件の 1 つである。この記録が偽られると、chief が見ていないマージでも自動送信が起きうる。ただし送られるのはその workspace の正しい次のコマンドだけなので、これを残る危険として受け入れる。
-   このほかに、chief が workspace を作ったときに残す記録（worktree のパスと issue 番号）を、削除の候補を名指すことと、その行に示すタスクを探す手がかりに使う。この記録は送るコマンドと送り先を決めない。
    -   名指された workspace は、Herdr・git・`origin/main` の文書で確かめ直し、記録のパスはその issue 番号から決まるパスと等しくなければならない。
    -   worktree ごとの記録は、同じパスに作り直す前と、workspace を消し終えた後に、そのパスの分をすべて消す。
-   通知の記録は通知の重複の防止と待っている時間による並べ方に、送信の記録は送った入力の履歴と、「実行中」の行と、作業項目の表示と状態の詳細の表示にだけ使い、どちらも送る中身を左右しない。

### ブランチ `main` をチェックアウトした worktree のタスク

-   chief の待ち受けの worktree ごとの履歴の記録（下の項）のうち、同じセッションが、PR が開いていることを確かめ、その後に同じ PR がマージされたことを確かめた記録を、チェックアウトされたブランチの名前がちょうど `main` の worktree のタスクを決めるために使う。次のすべてを満たすときだけ、それをその worktree のタスクとする。
    -   それらの PR のブランチ名から抽出したタスクが 1 つに決まる。
    -   そのセッションが、その worktree のブランチの PR として、ほかのタスクの PR も、機能ブランチの名前の規則に合わないブランチ（`main` を除く）の PR も確かめていない。
    -   最後にマージを確かめたそのタスクの PR の後に、その worktree がほかのタスクの機能ブランチにいることを確かめていない。
    -   開いていることを確かめた後にマージも閉じたことも確かめていない PR がない。
-   自動送信の 15 分の窓と 10 分の引き継ぎの期限は、この特定には当てない。記録がないか食い違うか読めなければ、detached HEAD と同じく要確認として `/mkreq` を示さない。
-   そのタスクの次のコマンドは `origin/main` の文書から決め、人が選んだときだけ送り、自動送信はしない。
-   特定に使うのは、chief の pane のセッションに属する、worktree ごとの履歴の記録である。PR が開いていること、マージされたこと、閉じられたことと、worktree がいる機能ブランチのタスクが変わったことを、変わったときに 1 件ずつ追記し、書き換えない。今のセッションの記録だけを読み、ほかのセッションの記録は chief の起動のときに消す。その worktree の履歴の記録は、同じパスに worktree を作り直す前と、workspace を消し終えた後にも消す。
-   履歴の最後の状態が開いている PR のうち、そのラウンドで開いているのを見なかったものは、自動送信の窓の外でも、自動送信と同じ GitHub の読み取りで状態を確かめる。同じラウンドで同じ PR を 2 回読まない。
-   理由：PR を見た記録はラウンドごとに消えるので、ラウンドをまたぐ特定には使えない。変化だけを追記すれば書き換えずに済み、作り直したパスの記録は今の規則で消える。窓の外でも状態を読まなければ、15 分以上あいた後のマージで特定できない（[0105 設計書](../../tasks/0105_chief_post_merge_next_command/02_architecture.md)「設計の際に決めたこと（2026-11-19）」）。
-   detached HEAD の worktree と、`main` でも機能ブランチでもないブランチの worktree には使わない。
-   理由：`main` をチェックアウトした worktree に chief の待ち受けの記録を使うのは、マージの後に `mergepr` が worktree を `main` に置くと、ブランチからタスクを読めず、続けるべきタスクがあるのに `/mkreq` を示していたためである。人が選ぶ送信に限るのは、人が行のタスクを見てから選べるようにするためである（[0105 要件定義書](../../tasks/0105_chief_post_merge_next_command/01_requirements.md)「要件定義の際に決めたこと（2026-11-18）」）。

### 画面と transcript の読み取り

報告を transcript から読む今の仕様は [chief_architecture.md](../chief_architecture.md) の 3 章にあり、決定の出典は [0095 要件定義書](../../tasks/0095_chief_transcript_report/01_requirements.md) の F-001〜F-003 に、PR の記録の確かめの結果は [0095 設計書](../../tasks/0095_chief_transcript_report/02_architecture.md) の 1.2 にある。

-   pane の画面とセッションの記録の文字列から判断することは、CLAUDE.md の「Declare, don't infer」の例外とする。対象は、エージェントが質問で止まっているかどうか、その質問が 1 つを選ぶ問いかどうか、権限の確認で止まっているかどうか、`/runpr` の報告の次のコマンド、モデル、入力欄に残っている文字、PR を作ったコマンドの報告の要約である。
    -   合わない画面とセッションの記録は広く解釈せず、「要確認」か「送らない」にする。transcript の行も、サンプルで確かめた形に合わなければ広く解釈しない。
    -   ただし、Claude Code の transcript の値や種類の名前だけが変わったときと、transcript のファイルがないときは、その pane に報告がないものとして読み、自動送信の前の NEXT の照合は通る（「結果」）。
    -   状況の表を組むときの、文字ごとの表示幅の数え方と、折り返しと切る位置も、表に入る外から来る値の中身から決めるので、同じく例外とする。その結果は表の配置にだけ使い、何を送るか、行の状態、急ぎの度合いを左右しない（[0102 要件定義書](../../tasks/0102_chief_text_table/01_requirements.md) の AC-28）。
    -   理由：画面は Claude Code と OpenCode が描く外部の値で、セッションの記録は Claude Code が書く外部の値で、どちらも型で表せず、OpenCode の質問の画面は変えられないためである。範囲と境界の出典は 0088 要件定義書の 5 章と、報告を transcript から読むように変えた [0095 要件定義書](../../tasks/0095_chief_transcript_report/01_requirements.md) の 5 章にある。今の範囲と境界は CLAUDE.md の例外の一覧に書く。
-   Claude Code の pane の最後の報告（`/runpr` の報告と、PR を作ったコマンドの報告）は、画面ではなく、そのセッションの transcript で最後に終わった応答の本文から読む。OpenCode の pane の報告は画面から読む。transcript を読めないときは画面に戻らず、送らないか、空にしないか、PR の説明から要約する。
    -   理由：Herdr は pane の高さの分の行しか返さない。そのため、画面より長い報告や、折り返しと描き直しで切り出せない報告があると、送るべきものが止まり、PR の詳細とリセットが働かなかった。transcript には報告の全文が折り返しなしで残る。画面に戻らないのは、壊れやすい経路を残さないためである。
-   報告を使う確かめ（`/runpr` の報告の NEXT の照合、ブランチのない状態での自動送信と `/runpr` の pane のリセットでの NEXT と PR 番号、PR を作った pane のリセットの前の確かめ）は外さない。ただし、Claude Code の pane の NEXT の照合は、最後の報告だけを対象にする。
    -   理由：確かめを外さないのは、NEXT の照合が chief 自身の判定の誤りや古い状態を拾える唯一の照合であり、情報源を替えても負担がほとんどないためである。NEXT の照合を最後の報告に限るのは、transcript には人が見ていない古い報告まで残り、それで送信が止まるためである。
-   PR を作ったセッションは、報告の本文の URL ではなく、transcript に Claude Code が残す PR の記録（`pr-link` の行）で見分ける。
    -   この記録は、PR を作ったコマンドの実行では、PR を作った後に書かれる。ただし、PR を作らずにその PR に関わったセッション（`gh pr checkout`、PR のあるブランチへの `git push` など）にも書かれるので、「そのセッションが関わった PR」の記録として扱う。
    -   PR を作った pane のリセットは、人の最後の入力が PR を作ったコマンドであることの確かめで守る。
    -   理由：PR の記録で見分けるのは、transcript が宣言する値があるのに本文から推し量らないためである（CLAUDE.md の「Declare, don't infer」）。
-   transcript のファイルがまだないセッションは、報告がないものとする。
    -   理由：`/clear` の直後のように応答をまだ書いていないセッションには実際に報告がないためである。そう扱わないと、chief 自身が空にした pane のせいで自動送信が止まってしまう。
-   `/runpr` の最後の報告は、NEXT を chief の今の文法で読める 1 行（`NEXT: /runplan 0015`、`NEXT: なし（理由）`）で書く。その形は [runpr.md](../../../.claude/commands/runpr.md) の step 5 が定め、chief は文法を広げない。
    -   理由：NEXT の照合が、報告の書き方の偶然に頼らずに働くようにし、報告の本文の中身から推し量る範囲を広げないためである（CLAUDE.md の「Declare, don't infer」、[0095 要件定義書](../../tasks/0095_chief_transcript_report/01_requirements.md)「実装の際に決めたこと（2026-11-17）」）。

### pane の選び方とリセット

-   送り先の pane は、workspace の中に、送り先の種類のエージェントの pane がちょうど 1 つあるときだけ選ぶ。画面の文字列では選ばない。リセットする pane も同じ規則で候補を決め、次のすべてを満たすときだけリセットする。
    -   そのコマンドの報告が pane の最後の報告として残っている。
    -   その後エージェントが動いていない。
    -   Claude Code の transcript で人が最後に入力した行がそのコマンドである。
    -   Claude Code の pane では、最後の報告と PR の記録と人の最後の入力を、画面ではなく transcript から読む（入力を送る直前の、問いと入力欄の確かめは画面で行う）。
    -   理由：送るたびに文脈を空にするので、人が対話に使っている pane の文脈を、黙って失わないようにするためである。画面と transcript は、送ることについては候補を狭めることにだけ使い、人の入力は transcript が宣言する値で見分ける（0088 設計書の 3.1.3）。
-   報告が見つからないか読めないことで見送ったリセット（`no_report` の一部）は、黙って捨てずに人の選択肢として示す。
    -   対象は、Claude Code で PR を作った pane のリセットと、`/runpr` の pane のリセット（Claude Code・OpenCode）で、見送ったときにほかの条件（状態が変わっていないこと、入力を待っていること、Claude Code の pane では人の最後の入力）をすべて満たしていたものに限る。人が選んだときだけ、それらの条件を確かめ直してから送る。
    -   OpenCode の `/runpr` の pane のリセットでは、最後のメッセージの始まりが画面の外に出ていて PR を名指さない場合も、報告が読めないものとする。
    -   Claude Code の pane の transcript を読めずに見送ったリセット（`no_transcript`・`unsupported_path`）は示さない。
    -   報告は読めたが別のものだった見送り（別の PR、違う NEXT、別の pane から控えた報告）、OpenCode で PR を作った pane のリセット、人の入力があったことによる見送り（`other_input`）などは選択肢にしない。
    -   理由：報告が読めないというだけの理由で、pane が前のコマンドの文脈を持ったまま残らないようにするためである。報告が別のものだと読めたことは、pane が別の作業に移った証拠である。人の会話を守るため、それは選択肢にしない（[0097 要件定義書](../../tasks/0097_chief_reset_offer/01_requirements.md) の F-001・F-002）。

### 道具と実行の枠組み

-   chief の判定と送信は、Go の開発用の道具 `chief`（`cmd/chief`・`internal/chief`）に置く。`/chief` のコマンドの定義は、道具の呼び出し、人への問い、報告の要約だけを持つ。道具は送る入力を、コマンドの種類と検証した引数から型で組み立て、文字列の入力を受け取らない。
    -   理由：エージェントが手順を読み違えても、決まった範囲の外の入力が送られないようにし、判定をテストで確かめるためである（[ADR-0014](0014-deterministic-checks-in-go.md)）。構成は [chief_architecture.md](../chief_architecture.md) の 1 章と 2 章にある。
-   自動の進行と通知は、chief のセッションが待ち受けている間だけ行い、セッションと別に常駐するプロセスを置かない。chief は同時に 1 つだけ動かす。chief の読み取り専用のネットワークの操作（PR・CI・レビューの状態の取得、`git fetch`、workspace を作る前の issue の取得）は、chief を起動したことで承認したものとする。
    -   理由：常駐のプロセスは、エージェントのいないところでほかのセッションへ入力を送ることになり、信頼の境界が広がるためである。1 つに限るのは、2 つの chief が同じコマンドを送らないためである。読み取りの承認は、人がいないときにも状態を読む必要があるためで、書き込みの操作は含めない。規則は CLAUDE.md の「Tool Execution Safety」に書く（F-010）。
-   chief は Herdr の中でだけ動き、Herdr の出力を読めないときは状態を推し量らずに「要確認」とする。
    -   理由：Herdr の出力の形はリポジトリの外で変わりうるためである（F-001）。
-   chief のセッションが道具を通さずに入力を送らないよう、リポジトリの `.claude/settings.json` で、次の herdr と git の呼び出しを拒む。読み取りの呼び出しは拒まない。worktree と workspace の作成と削除、エージェントの起動は道具が行い、この拒否は緩めない。
    1.  pane へ入力を送るか、pane でコマンドを走らせるか、pane の入力の経路を変える呼び出し。
    2.  エージェントの状態とセッションを Herdr に報告する呼び出し。
    3.  pane・タブ・workspace・セッション・worktree を閉じるか消す呼び出し、エージェントの連携を変える呼び出し、Herdr を止めるか入れ替える呼び出し。
    4.  サブコマンドの前に、別のセッションか別の機械を指す引数を書いた呼び出し。
    5.  workspace・タブ・pane・worktree を作る呼び出し。
    6.  `git worktree` で worktree を足す、消す、動かす呼び出し。

    道具の削除のサブコマンドは、確認なしに許す道具の呼び出しから外し、呼ぶたびに Claude Code の許可の確認を出させる。
    -   理由：画面や PR の説明の指示に従ったセッションが、任意の入力を送ること、chief の確かめが頼る状態とセッションの値を偽ること、タスクの pane を閉じるなどして作業を失わせること、道具を通さずに worktree と workspace を作るか消すことを防ぐためである。削除のサブコマンドに許可の確認を出させるのは、消すかどうかの人の確認を、セッションの外でも求めるためである。読み取りは、ほかのセッションが使うことがあり、送ることも偽ることもできないので、拒まない。
    -   拒む呼び出しの一覧は [chief_guide.md](../guides/chief_guide.md) の 6 章にあり、決定の出典は [0088 実装計画書](../../tasks/0088_chief_of_staff/03_implementation_plan.md) の「計画の際に決めたこと」と [0092 設計書](../../tasks/0092_chief_task_workspace/02_architecture.md) の 3.8 である。パスで書いた呼び出しなど、規則の外の書き方は残る危険とする（0088 設計書の 5.2）。

### 今の仕様の文書とプロトコル番号

-   chief の今の仕様は、`docs/dev/` の直下の開発者向けの文書 [chief_architecture.md](../chief_architecture.md) が持つ。持つのは、構成要素と信頼の境界、`/chief` の定義と道具の契約、状態のディレクトリ・ロック・記録、道具が書き出すもの（中身・書き出す先・残る期間・信頼できない文字列を含むか）、画面と transcript の読み取りの扱い、判定と副作用の条件の要約（判定ごとに、読むもの、副作用の条件にあたるか、細部の置き場所を示す）、プロトコル番号を上げる基準、テストのしかたである。読み取りの範囲は CLAUDE.md の例外の一覧が持つ。この文書が述べる事柄を変える PR は、同じ PR でこの文書を直す。
    -   理由：今の仕様が 10 本のタスクの設計書に分かれ、後のタスクが上書きした部分を読む人が自分で差し引く必要があったためである。同じ PR で直さなければ、文書はまた古くなる（[0117 要件定義書](../../tasks/0117_chief_architecture_doc/01_requirements.md)「要件定義の際に決めたこと（2026-11-20）」）。
-   chief のプロトコル番号は、道具と `/chief` の定義の間の約束を変える PR と、pane へ送る・自動で送る・workspace と worktree を作る・消すといった副作用の条件を変える PR で上げる。約束を変える追加でも、古い道具と新しい定義、新しい道具と古い定義のどちらの組み合わせも黙って誤らないことを示す 3 つの条件がすべて成り立てば、上げなくてよい。状況の表の分類など、副作用の条件でない判定だけを変える PR は上げない。定義だけを変える PR も、定義が読まなかった出力の項目を読み始めるか、示すだけだった項目で分岐し始めるときは上げる。約束と 3 つの条件の一覧は [chief_architecture.md](../chief_architecture.md) のプロトコル番号の章にあり、番号の決め方とマージの時点の確かめは CLAUDE.md の「Protocol numbers」にある。
    -   理由：古い定義と新しい道具の組み合わせが黙って誤ることと、入れ直しを忘れた古い道具が取り消せない副作用を古い条件で起こし続けることを防ぎ、害のない追加では番号を上げないためである。上げるたびに道具の入れ直しが要り、並行するタスクとの番号の衝突も増える。`fixprguard` の基準の形にそろえ、判定の変更は副作用の条件に絞る（[0117 要件定義書](../../tasks/0117_chief_architecture_doc/01_requirements.md)「要件定義の際に決めたこと（2026-11-20）」）。

### workspace の作成と削除

-   人が chief で issue 番号を答えると、道具は次の順に workspace を作る。
    1.  GitHub から issue を読み、存在しない issue、閉じた issue、ラベル `draft` が付いた issue（下書きの issue）、PR の番号を拒む。下書きの issue の方針は [ADR-0053](0053-draft-issue-label.md) にあり、`/mkreq` と同じ判定にする。
    2.  通れば、`~/.herdr/worktrees/yt2column/issue-<N>` に `origin/main` から detached の worktree を作る。
    3.  それを開いた `issue-<N>` という名前の workspace に、シェル・OpenCode・Claude Code の pane を作ってエージェントを起動し、Claude Code の pane に `/mkreq <N>` を送る。

    作るときの規則は次のとおりである。
    -   エージェントは、人の代わりに許可や信頼を与える引数を付けずに起動し、フォルダの信頼を問う画面などが出たら送らずに人が答えるよう示す。
    -   パスと名前は issue 番号だけから決める。同じパスの worktree か workspace がすでにあれば作らない。
    -   途中で失敗したら、そこで止まって人に示し、作ったものは消さない。
    -   理由：人が issue 番号を答えるだけでタスクを始められるようにし、タスクにならない番号（存在しない issue、閉じた issue、下書きの issue、PR）で、片付けられずに残る workspace を作らないためである。許可や信頼を与える引数を付けないのは、chief が人の代わりにリポジトリの hooks や設定を信頼しないためである。名前を issue 番号だけから決めるのは、issue の題名などの中身で振る舞いを選ばず（CLAUDE.md の「Declare, don't infer」）、chief が入力を送れなくなる文字をパスに入れないためである。detached にするのは、`/mkreq` がタスクのブランチを作った後に一時的なブランチを残さないためである。今の仕様は [chief_architecture.md](../chief_architecture.md) の 3.5 にあり、決定の出典は [0092 要件定義書](../../tasks/0092_chief_task_workspace/01_requirements.md) の F-001〜F-004 である。
-   chief が削除を提案するのは、chief が作った workspace のうち、記録した issue を `対応 issue` とするタスクが `origin/main` でちょうど 1 つあり、完了したものだけにする。人が選び、消すかどうかの問いに答えたときだけ、消す直前に次を確かめ直し、通ったときだけ workspace を閉じて worktree を消す。
    -   追跡していないファイルを含めて変更がないこと。
    -   HEAD が `origin/main` から届くこと。
    -   どのエージェントも実行中でも質問で止まってもいないこと。
    -   エージェントでない pane の前面のプロセスがその pane のシェル自身であること。

    worktree は、変更があれば git が拒む形で消す。ブランチなど、ほかのものは消さない。
    -   理由：作業を失わずに、終わった workspace を人の確認だけで片付けるためである。シェルの pane を確かめるのは、workspace を閉じると、そこで動いているビルドやエディタも終わるためである（[0092 設計書](../../tasks/0092_chief_task_workspace/02_architecture.md) の 3.4.2）。完了したタスクの worktree は `origin/main` で detached になり、ブランチからタスクを読めないので、作ったときの記録から issue を読む。人が手で作った workspace は、作ったときの issue が分からないので対象にしない（0092 要件定義書の F-005・F-006）。

### 状況の表

今の仕様は [chief_architecture.md](../chief_architecture.md) の 3.5 にあり、決定の出典は [0093 要件定義書](../../tasks/0093_chief_status_sheet/01_requirements.md) の F-001〜F-006 と、表の形については [0102 要件定義書](../../tasks/0102_chief_text_table/01_requirements.md) の F-001〜F-005 である。

-   状況の表の各行に、急ぎの度合いの印（すぐ 🛑・あとで 🔶・待つ 🟢。色だけでなく形でも区別でき、表の上の凡例で意味を示す）と、タスクの作業項目の表示（`origin/main` の文書から決まる）と状態の詳細を示し、行を急ぎの度合いの順に並べる。次に動くのが人か AI か（番）も道具が決めて出力に含めるが、表には示さない。これらは道具が決める。
    -   理由：人が表を一目見て、何から手を付ければよいかを分かるようにするためである。道具が決めるのは、セッションに判断を残さず、判定をテストで確かめるためである。番を表に示さないのは、表を pane の幅に収めるためで、番は状態から分かる。印の形を変えたのは、色だけに頼らないためと、「待」が「人の対応を待っている」とも読めたためである。
-   表そのものも道具が等幅のテキストとして組んで出力に含め、`/chief` のセッションは code block にそのまま貼り、値を写したり切ったりしない。
    -   表は列を罫線で区切らず、表示幅でそろえ、workspace ごとに 2 行で示す。
    -   1 行を、chief の pane の幅（Herdr から読む）から Claude Code の code block の余白（chief のタブを分割していれば、Herdr が分割した pane に描く枠も）を引いた幅に収める。pane の幅を読めなければ 80 桁とみなし、内容の列が最小の幅を取れなければはみ出しを受け入れる。
    -   表のために読む Herdr のタブの一覧と pane の配置は、表示にだけ使う。
    -   理由：Claude Code が描く Markdown の表では、行ごとに罫線が引かれ、セルの中で改行できず、1 行に収まらない値が意図しない形で折り返すためである。
-   状態の詳細と「実行中」の行に示す実行中のコマンドは、Claude Code の pane ではセッションの記録で人が最後に入力したタスクのコマンドから、OpenCode の pane では chief の送信の記録から決め、画面からは決めない。これらは表示にだけ使い、何を送るかを左右しない。
    -   Claude Code の pane で、そのコマンドの後に人の入力があれば、そのことだけを添えて示し、後の入力の中身は読まない。
    -   例外として、人の最後のタスクのコマンドの後に人の入力があるかどうかは、`/mergemain` の自動送信を止める条件にも使う（上の「マージコンフリクトの解消の自動送信」）。送ることを止める向きにだけ使い、何を送るかは左右しない。
    -   実行中のコマンドが 1 つに決まらなければ、推し量らず、決まらない理由を示す。
    -   理由：Claude Code の pane でセッションの記録を使うのは、次の 2 つのためである。chief が打った入力も人の入力としてセッションの記録に残るので、送信の記録との優先を決めずに済む。また、人が自分で打ったコマンドも示せる。後の入力があっても最後のタスクのコマンドを示すのは、人が自由な文で指示を足したセッションでも、何の作業をしているかを示すためである。読むのは画面の読み取りの例外の範囲（人の最後のコマンド）に収まる。

## 採らなかった案

退けた案の多くは、人の確認や確かめを減らす案、信頼できない文字列や記録から推し量る範囲を広げる案、規則と作る量を増やす案である。決定の節と同じ見出しで分け、各案の下に採らなかった理由を書く。

### 人の判断の中継

-   質問には一切触れず、中身を示すだけにする（試作の形）。
    -   理由：人が答えるたびに pane を移る手間が残り、選択式で次の操作をとれるようにするという要求に合わない（0088 要件定義書「要件定義の際に決めたこと（2026-11-11）」）。
-   権限の確認、自由に書く答え、「NEXT をこのセッションで実行する」答えも中継する。
    -   理由：実行されるコマンドを見ないまま許可しやすくなり、chief が送る入力が人の書いた任意の文まで広がり、コマンドごとのモデルの決まりを chief 自身が破る（同上）。
-   エージェントの側に、待っていることを示す決まった形の合図を要件として求める。
    -   理由：OpenCode の質問の画面は変えられない（同上）。
-   人が選ぶ送信で、人に示した行のタスクを受け取らず、送る直前に作り直した行のコマンドの種類だけを比べる（[0105 設計書](../../tasks/0105_chief_post_merge_next_command/02_architecture.md)「設計の際に決めたこと（2026-11-19）」）。
    -   理由：人が見た後に行のタスクが変わったことに、道具が気付けない。
-   人が選ぶ送信で、行のタスクを道具に渡して照合する（同じ出典）。
    -   理由：自動送信の提案が行と別のタスクを示すとき、人が見ていない行のタスクへ送りうる。

### 送る入力と送り先

-   `/runpr` も Claude Code で走らせる。
    -   理由：`/runpr` には Opus までは要らないと利用者が判断した（0088 要件定義書「issue #836・#837・#838 で決めたこと」）。
-   `sonnet` の `/runplan` を Claude Code・Sonnet で走らせる（ADR-0042 のまま）。
    -   理由：`sonnet` の実装には Opus までは要らないと利用者が判断し、運用がすでに Flash だった（0088 要件定義書「要件定義の際に決めたこと（2026-11-11）」）。
-   送り先の表を Go のコードに持ち、`_context.md` との一致をガードのテストで確かめる。
    -   理由：値ごとの送り先を差し替えるのに 2 か所を直すことになる（[0088 設計書](../../tasks/0088_chief_of_staff/02_architecture.md)「設計の際に決めたこと（2026-11-11）」）。

### マージの後の自動送信

-   自動送信の例外を、chief の手元のファイルに人が書く（試作の形）。
    -   理由：計画書がすでに決めている事柄を、別の場所に書き写すことになる（0088 要件定義書「要件定義の際に決めたこと（2026-11-11）」）。
-   自動送信の例外を、「この PR のマージの後」に付ける。
    -   理由：実装計画書そのものの PR にはマーカーがなく、計画書のマージの後・PR-1 の前で止めることを表せない（同上）。
-   自動送信の欄がない計画書は、自動送信しない。
    -   理由：進行中のタスクを、最後まで人の手で進めることになる（同上）。
-   自動送信の引き金を、`/runpr` の報告の画面で確かめる。
    -   理由：人に尋ねずに入力を送る判断を、信頼できない文字列に委ねることになる（同上）。
-   セッションと別に常駐するプロセスを置き、セッションがなくてもマージの後の送信を行う。
    -   理由：信頼の境界が広がり、作る量も大きくなる（同上）。
-   計画書のステップを書き方 A（`- [ ] **ステップ N-M**`）だけから読み、ほかの書き方の計画書を書き直して、`/mkplan` に書き方 A を指示させる。
    -   理由：見出しと太字の段落で書いた既存の計画書を救えない（[0113 要件定義書](../../tasks/0113_plan_step_reading/01_requirements.md)「要件定義の際に決めたこと（2026-11-19）」）。
-   書き方 A に似たチェックボックスの行（`**ステップ N-M（…）**`）を、4 つ目の書き方として読む。
    -   理由：受け入れる書き方を少なく保ち、似た行は読み替えずに、見える形で止めるためである（同上）。
-   2 章の中のステップに似た行を無視する。
    -   理由：未着手のステップを見落とし、「残りなし」や「対象ステップが済んだ」と誤って読みうる（同上）。

### マージコンフリクトの解消の自動送信

-   自動で解消してよい衝突を、既存の規則があるもの（README の同期、ADR の番号、プロトコル番号）だけに限る。
    -   理由：多くのタスクが同時に変える `CLAUDE.md` やコマンドの定義の衝突が残り、効果が小さい（[0115 要件定義書](../../tasks/0115_chief_conflict_resolution/01_requirements.md)「要件定義の際に決めたこと（2026-11-19）」）。
-   検査が通れば、どの衝突も解消する。
    -   理由：Go・TypeScript のロジックの衝突の誤った解消を push しうる（同上）。
-   ADR の番号の重なりでは、`numreserve adr` で番号を振り直す。
    -   理由：人に尋ねずに送ったコマンドが、戻せない記録のタグを作り、PR の説明に訂正の段落を書くことになる（同上）。
-   `/mergemain` が決まった形の報告の行を書き、chief が transcript から失敗の理由を読んで表に示す。
    -   理由：画面と transcript の読み取りの例外が広がる（同上）。
-   PR の head と `origin/main` の組ごとに 1 回送る。
    -   理由：`main` が進むたびにやり直し、続けて失敗する回数の上限も別に決めることになる（同上）。
-   前のラウンドで `CONFLICTING` でなかった PR にだけ送る。
    -   理由：chief が見ていなかった間に起きたコンフリクトが、解消されずに残る（同上）。
-   `/runpr` に、コンフリクトを解消する段を足す。
    -   理由：範囲が広がる。`/runpr` の中で `main` を取り込むときは、今の「Taking in `main`」の規則で足りる（同上）。
-   `/mergemain` が、解消の差分（`git diff --cc` の範囲）をローカルの CLI レビューにかける。
    -   理由：CodeRabbit の割り当てを使う。解消の結果は `/runpr` とマージの質問で人の判断を通る（同上）。
-   `/mergemain` を Claude Code・Sonnet で走らせる。
    -   理由：文書の衝突の判断の質が下がりうる（同上）。
-   PR のブランチに `/mergemain` の定義があれば、`origin/main` と違っても送る。
    -   理由：古い定義で動き、`main` で広げた規則や直した手順が当たらない（同上）。
-   送る前に報告の控えを作れなければ、送らない。
    -   理由：送る前の pane の最後の報告は、リセットや人の会話の後にはこの PR の報告でないことが多く、そのたびに自動送信が止まる（同上）。
-   `/mergemain` がたどる規則のファイル（`mktrans.md`・`adr.md`・CLAUDE.md・settings・skill）をブランチが変えていれば、自動では送らない。
    -   理由：衝突しやすい PR ほど対象から外れる（同上）。
-   `/mergemain` は `git fetch` と `gh pr view` を使わず、chief が取得した `origin/main` と送る直前の確かめに頼る。
    -   理由：人の答えで、承認を CLAUDE.md に書き足すことにした（同上）。
-   transcript のファイルがまだない pane を、人の入力がないものとして送る。
    -   理由：Claude Code が transcript の置き場所を変えると、会話中の pane も人の入力がないものと読める（同上）。
-   `/mergemain` で head が変わった後は、PR を作ったコマンドの報告を失うのを受け入れる。
    -   理由：解消が成功したときに、PR の詳細から報告が消える（同上）。

### 記録

-   自動送信の記録とロックを git の共通ディレクトリに置く。
    -   理由：worktree のエージェントが書ける点で、リポジトリの外の状態のディレクトリより守りが強くなるわけではない。置き場がリポジトリの clone ごとに分かれるだけである（[0088 設計書](../../tasks/0088_chief_of_staff/02_architecture.md)「設計の際に決めたこと（2026-11-11）」）。

### ブランチ `main` をチェックアウトした worktree のタスク

出典はいずれも [0105 要件定義書](../../tasks/0105_chief_post_merge_next_command/01_requirements.md)「要件定義の際に決めたこと（2026-11-18）」である。

-   ブランチ `main` をチェックアウトした worktree は、chief がマージを確かめた PR の記録がなければ、今までどおりタスクのない workspace として `/mkreq` を示す。
    -   理由：マージの後に `mergepr` が worktree を `main` に置くので、続けるべきタスクがありうる worktree に `/mkreq` を示しうる。
-   ブランチ `main` をチェックアウトした worktree を、記録を使わずに要確認とするだけにする。
    -   理由：マージの後に、そのタスクの次のコマンドを示せない。
-   ブランチ `main` をチェックアウトした worktree で、PR のブランチ名から抽出したタスクが食い違えば、最後に見た PR のタスクを採る。
    -   理由：worktree を使い回したときに、推し量ってどれかを選ぶことになる。
-   ブランチ `main` をチェックアウトした worktree のタスクを、chief のセッションを越えて保つ記録を足す。
    -   理由：セッションに属さない記録と、それを消す規則が要る。
-   ブランチ `main` をチェックアウトした worktree のタスクを、開いていることを確かめただけで、マージを確かめていない PR の記録からも決める。
    -   理由：その PR を作ったコマンドを、次のコマンドとしてもう一度示しうる。
-   detached HEAD の worktree のタスクも、chief がマージを確かめた PR の記録から決める。
    -   理由：0088 の決定を変え、完了したタスクの行や削除の提案の扱いにも及ぶ。
-   ブランチ `main` をチェックアウトした worktree の、記録から決めたタスクの次のコマンドを、表示だけにして送れなくする。
    -   理由：提案を chief から送れず、人が pane で打つことになる。
-   ブランチ `main` をチェックアウトした worktree へも、マージの後の次のコマンドを自動で送る。
    -   理由：自動送信の条件が広がる。
-   履歴の記録を、毎ラウンド履歴全体を新しい記録に書き写し、古いラウンドの分を消す形にする（[0105 設計書](../../tasks/0105_chief_post_merge_next_command/02_architecture.md)「設計の際に決めたこと（2026-11-19）」）。
    -   理由：書き込みの失敗と空の履歴を見分けられず、作り直したパスの記録を消す規則も別に要る。
-   マージを確かめるのを、自動送信の窓の中だけにする（同じ出典）。
    -   理由：15 分以上あくと、セッションが続いても特定できない。
-   機能ブランチの名前の規則に合わないブランチの PR を、履歴に残さない（同じ出典）。
    -   理由：タスクの分からない仕事に使い回した worktree が `main` に戻ったとき、前のタスクを誤って特定しうる。

### 画面と transcript の読み取り

-   Claude Code の pane の報告を、画面から読み続ける。
    -   理由：Herdr は pane の高さの分の行しか返さず、長い報告を読めずに、PR の詳細とリセットが働かない（[0095 要件定義書](../../tasks/0095_chief_transcript_report/01_requirements.md) の 1 章の背景）。
-   Claude Code の pane の報告でも、NEXT の照合を外す。
    -   理由：NEXT は計画書と GitHub から決まる値と重なるが、chief 自身の判定の誤りや古い状態を拾える唯一の照合がなくなり、送る条件が緩む（[0095 要件定義書](../../tasks/0095_chief_transcript_report/01_requirements.md)「要件定義の際に決めたこと（2026-11-16）」）。
-   NEXT の照合に加え、PR を作った pane のリセットの前の報告の確かめも外す。
    -   理由：空にする条件が緩む。確かめは、人の最後の入力のために読む transcript で済み、残しても負担がほとんどない（同上）。
-   transcript のすべての報告の NEXT を照合する。
    -   理由：人が見ていない古い報告で送信が止まる（同上）。
-   chief の NEXT の文法を広げ、見出しやコードブロックに書かれた次のコマンドも読む。
    -   理由：本文の中身から推し量る範囲が広がり、報告の書き方が変わるたびに壊れる（[0095 要件定義書](../../tasks/0095_chief_transcript_report/01_requirements.md)「実装の際に決めたこと（2026-11-17）」）。
-   NEXT の行のない今の Claude Code の `/runpr` の報告のまま、NEXT の照合が照合せずに通ることを受け入れる。
    -   理由：Claude Code の pane で NEXT の照合を実質的に外すことになる（同上）。
-   PR を作ったセッションを、報告の本文の PR の URL で見分ける。
    -   理由：transcript が宣言する PR の記録があるのに、本文から推し量ることになる（同上）。
-   transcript のファイルがまだないセッションを、読めないものとする。
    -   理由：chief 自身が `/clear` で空にした pane のせいで、次のマージの自動送信が止まる（同上）。
-   transcript を読めないときは、画面の読み取りに戻る。
    -   理由：壊れやすい経路が残り、判定の情報源を画面から移す方針（[#902](https://github.com/isseis/yt2column/issues/902)）に反する（同上）。
-   Claude Code が値や種類の名前を変えたことを拾うために、応答の行が 1 つもない transcript などを読めないものとする。
    -   理由：`/clear` の直後のセッションも同じ形になり、chief 自身が空にした pane のせいで自動送信が止まる（[0095 設計書](../../tasks/0095_chief_transcript_report/02_architecture.md)「設計の際に決めたこと（2026-11-17）」）。
-   PR を作った報告を示すときにも、人の最後の入力が PR を作ったコマンドであることを確かめる。
    -   理由：示すだけの用途で、PR に関わった pane の報告を示しても実害がない（同上）。
-   遅れて書かれた報告に、PR の詳細の控えだけで備えるか、短い間を置いて読み直して備える。
    -   理由：控えだけでは、その head の間ずっと PR の説明を示し、PR を作った pane を空にしない。間を置く案では、報告がもともとない pane でも、PR の詳細を読むたびに待つ（同上）。

### pane の選び方とリセット

-   報告が読めずに見送ったリセットを、これまでどおり黙って見送る。
    -   理由：長い報告の後に、pane が前のコマンドの文脈を持ったまま残り、人が手で空にすることになる（[0097 要件定義書](../../tasks/0097_chief_reset_offer/01_requirements.md) の 1 章の背景）。
-   人の入力があったことで見送ったリセット（`other_input`）も、人の選択肢にする。
    -   理由：人が同じ pane で始めた会話を守る規則を、人の選択で越えることになる（[0097 要件定義書](../../tasks/0097_chief_reset_offer/01_requirements.md)「issue #919 で決めたこと」）。
-   `no_report` で見送ったリセットをすべて選択肢に出し、送る直前にだけほかの条件を確かめる。
    -   理由：送れない項目が選択肢に混ざり、人が選んだ後で道具が断ることになる（同「要件定義の際に決めたこと（2026-11-17）」）。
-   報告は読めたが別のもの（別の PR、違う NEXT、別の pane から控えた報告）だった見送りも選択肢にする。
    -   理由：pane が別の作業に移った証拠があるのに、その文脈を消す方へ人を誘う（同上）。
-   OpenCode で PR を作った pane のリセットも選択肢にする。
    -   理由：その pane で PR を作ったコマンドが走った証拠も、人の会話を確かめる手段もない（同上）。
-   OpenCode の `/runpr` の pane のリセットを選択肢にしない。
    -   理由：報告が長いのか人が会話を続けたのかを機械で区別できないが、除くと、報告の読めない OpenCode の pane がいつまでも空にされない（同上）。

### 道具と実行の枠組み

-   chief の判定と送信を、コマンドの定義と bash スクリプトに置く（試作の形）。
    -   理由：判定と副作用を持ち、JSON を読み、状態を持つので、テストで確かめられる道具が要る（[0088 設計書](../../tasks/0088_chief_of_staff/02_architecture.md)「設計の際に決めたこと（2026-11-11）」）。
-   `.claude/settings.json` の拒否を緩め、chief のセッションに herdr を直接呼ばせる。
    -   理由：セッションが信頼できない文字列に従ったときに、決まった範囲の外の操作をしうる（[0092 要件定義書](../../tasks/0092_chief_task_workspace/01_requirements.md)「要件定義の際に決めたこと（2026-11-16）」）。
-   作る呼び出しを拒否に足さないか、足しても削除のサブコマンドを確認なしに許したままにする。
    -   理由：人の確認を `/chief` のセッションだけに任せることになる（[0092 設計書](../../tasks/0092_chief_task_workspace/02_architecture.md)「設計の際に決めたこと（2026-11-16）」）。

## 結果

自動の進行は chief のセッションの間だけで、chief は Herdr・Claude Code・OpenCode の出力の形に依るので、それらが変わると直すかサンプルを採り直すまで止まる。同じ利用者のプロセスが書ける記録が偽られる危険は、人の選択と確かめ直しを条件に受け入れる。

### 運用と人の手

-   chief のセッションが止まると、自動の進行と通知も止まる。利用上限などでセッションが止まっている間にマージされた PR の次のコマンドは、自動では送られず、次に状況の表（0088 要件定義書の F-001）を出したときに提案として示され、人が選んで送る。
-   OpenCode のモデルが合わないときは、人がその pane で切り替える。
-   `/mergemain` が解消しない衝突（Go・TypeScript などのロジック、内容以外の衝突、ADR の番号と主題の重なり）と、解消できなかった衝突は、人が pane で解消する。`/mergemain` の定義を持たないか古いブランチの PR も同じである。失敗の理由は表に出ず、人が pane の報告で読む。コンフリクトに気づくのは次のラウンドで、待ち受けの制限時間の分だけ遅れうる。`/mergemain` を送ると、Claude Code の pane の文脈は消え、PR を作ったコマンドの報告は控えがなければ PR の詳細に出なくなり、`/runpr` の後のその pane のリセットは見送られる。merge コミットは `main` の変更を差分に含むので、`/runpr` で PR レビューの再依頼か、マージの質問での確認が増えうる。
-   `/mergemain` の定義だけを `origin/main` と比べるので、ブランチが `mktrans.md`・`adr.md`・CLAUDE.md・settings を変えていたり、同じ名前の skill を足していたりすれば、`/mergemain` は `main` でレビューされていない規則で動く。`/clear` の直後で transcript のファイルがまだない pane には自動では送らないので、人が選んで送る。
-   実装計画書の PR マーカーの欄が 1 つ増え、`/mkplan` はその値を決める。
-   計画書のステップは、受け入れる 3 つの書き方のどれかで書く必要がある。ほかの書き方の計画書は、マージの後に要確認で止まり、自動送信されない。`/mkplan` と規約は、この書き方を指示していない。
-   権限の確認、自由に書く答え、複数を選ぶ問いには、人がその pane へ移って答える。
-   chief は `make install-chief` で `main` から入れ、道具を変えたマージの後は入れ直す。
-   chief_architecture.md が述べる事柄を変える PR は、同じ PR でその文書も直す。プロトコル番号を上げるかどうかは、その文書の基準で決める。副作用の条件を変える PR は番号を上げるので、利用者は入れ直しが要る。
-   作った worktree は、`/mkreq` がタスクのブランチを作るまで detached で、「要確認」として表の最後に並ぶ。作った後に `/mkreq` を送れなかったときは、人がその pane で `/mkreq` を打つ。
-   人が手で作った workspace と、chief が作ったがタスクのない workspace は、人が端末で片付ける。
-   人が Claude Code に、Herdr の workspace・タブ・pane や git の worktree を作らせると拒まれる。その操作は人が端末で直接行う。
-   ブランチ `main` をチェックアウトした worktree のタスクは、chief の pane の Claude Code のセッションが変わる（`/clear` か起動し直し）と分からなくなり、その行は要確認になる。`tick` を走らせずに `snapshot` だけを走らせたときも、chief がマージを確かめないので要確認になる。そこへは chief から `/mkreq` を送れず、人がその pane で打つ。
-   急ぎの度合いと番の対応、表の語と組み方は道具の中にあり、変えるには道具を直して入れ直す。ラウンドごとに、Herdr のタブの一覧と chief の pane の配置を読む。

### モデルと送り先

-   リポジトリのコードとレビューのスレッドが DeepSeek のサービスへ送られる。`low`（旧 `sonnet`）の PR は上位モデルのレビューを受けないので、Flash の実装の誤りは、`/runplan` の中のレビューとローカルの CLI レビュー（および利用者が選んだときの手動の PR レビュー。[ADR-0013](0013-review-setup.md)）で見つける。

### 外の道具の形への依存

-   chief は Herdr の CLI の出力の形に依り、Herdr の変化に合わせて直す必要がある。
-   Claude Code か OpenCode の版が上がって画面の形が変わると、実画面のサンプルを採り直すまで、その画面は「要確認」になり、答えの中継もできない。
-   Claude Code の版が上がって transcript の形が変わったときの影響は、変わり方で分かれる（[0095 設計書](../../tasks/0095_chief_transcript_report/02_architecture.md) の 1.2）。
    -   使う項目がなくなるか型が変わると、サンプルを採り直すまで Claude Code の pane の報告は読めない。そのため、自動送信とリセットは止まり、PR の詳細は PR の説明から要約される。
    -   値や種類の名前だけが変わると（応答の終わりを示す値や、本文の部分の種類の名前など）、報告がないものとして読まれ、NEXT の照合は止まらずに通る。
-   Claude Code の pane の NEXT の照合は最後の報告だけを見るので、それより前の報告の NEXT が違っても、報告の後に人が次の作業を始めて報告がなくなっても、自動送信は止まらない。Claude Code が transcript の置き場所を変えると、ファイルがないものとして NEXT の照合は通る。
-   workspace に transcript を読めない Claude Code の pane があると、OpenCode へ送るコマンドを含め、その workspace の自動送信は止まる。
-   PR の記録は PR を作らなかったセッションにも書かれるので、PR の詳細は、その PR に関わった Claude Code の pane（同じ pane で `/fixpr` を走らせた後など）の最後の報告を、PR を作ったコマンドの報告として示すことがある。
-   Claude Code が code block の左に取る余白や、Herdr が分割した pane に描く枠の幅が変わると、表が pane の幅を超えて折り返しうる。chief のタブを拡大したときは、表が分割したときの幅で組まれ、画面より狭くなる。表を人に示すのはセッションで、道具はセッションが表を変えずに写したかを確かめられず、写し違いは機械的には防げない。セッションの記録のない OpenCode の pane で人が打ったコマンドは、実行中のコマンドとして示されない。

### 記録と残る危険

-   自動送信の記録を、chief のセッションの外（リポジトリの外の状態のディレクトリ）に残す。その記録を消しても、chief が待ち受けの間に PR が開いているのを見ていないマージについては、自動送信は行われない。
-   PR を見た記録と履歴の記録は同じ利用者のプロセスが書けるので、偽られた記録が `main` をチェックアウトした worktree に別のタスクを示しうる。送るには人の選択が要り、送られるのもそのタスクの `origin/main` の文書が示す次のコマンドだけなので、これを残る危険として受け入れる。
-   履歴の記録を書けなかったときは、その worktree がほかのタスクのブランチにいたことを知らないまま `main` に戻り、古いタスクを示しうる。書けなかったことはラウンドの問題に示され、送るには人の選択が要るので、これも残る危険として受け入れる。読めない履歴の記録が 1 つでもあると、そのセッションのすべての `main` の worktree が要確認になる。chief の pane のセッションを変えれば戻る。中身の分からない記録のファイルだけを消すと、ほかのタスクを示す事象を失いうるので、その戻し方は採らない。
-   消すかどうかを人に尋ねるのは `/chief` のセッションで、道具はその確認が行われたかを確かめられない。
    -   削除のサブコマンドには Claude Code の許可の確認が出るので、消すたびに人は 2 回答える。auto mode でもその確認が出ることを確かめた（[0092 計画書](../../tasks/0092_chief_task_workspace/03_implementation_plan.md) の「PR-1 の実行の記録」）。
    -   道具が確かめるのは、次の条件だけである。chief が作ったこと、タスクが完了していること、変更がないこと、HEAD が `origin/main` から届くこと、エージェントが動いていないこと、エージェントでない pane の前面にシェル以外のプロセスがないこと。

    -   人が選んだリセットも送信の記録に残るので、マージを見た後に選ぶと、その workspace の次のコマンドは自動では送られず、提案として示される。
