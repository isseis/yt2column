# ADR-0040: 小さな変更のタスクは、人の判断で 3 文書を簡易な内容にして 1 本の PR で作れるようにし、機械的な判定は設けない

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

タスクの開発文書（要件定義書・設計書・計画書）は、1 本ずつ別の PR で作り、前の文書が承認されてから次の文書を書く（[requirements_process.md](../conventions/requirements_process.md) の「LLM Constraints」と「Review Flow」）。PR ごとに、Codex の PR レビュー、CI、`/runpr` の往復がかかる。小さな変更でも、3 文書の分量と 3 回の PR の往復の負荷は変わらない。タスク 0069 と 0071 は文書の内容を簡易にとどめたが、コマンドの定義にその手順はなく、その場の判断に頼った（[0072 要件定義書](../../tasks/0072_simple_task_documents/01_requirements.md) §1）。

負荷を減らすために導入した軽量プロセスは、適用の条件が実際の変更にほとんど当てはまらず、一度も使われていない。一方で、条件を機械的に判定するスクリプトとそのテストが、維持のコストの大半を占めた（[#743](https://github.com/isseis/yt2column/issues/743)、[ADR-0012](0012-lightweight-check-in-bash.md)）。

## 決定

-   **タスクは、通常の進め方か、簡易な進め方のどちらかで進める。`/mkreq` が要件定義書を書くたびに人に尋ね、選んだ進め方を要件定義書に記録する。** 文書の分量を変更の規模に合わせる判断を、その場の判断ではなく決まった手順にするためである。手順の正本は [requirements_process.md](../conventions/requirements_process.md) と `/mkreq` の定義に置く。手順をそこに足すことは、タスク 0072 の実装で扱う。
-   **簡易な進め方では、`/mkreq` が 3 文書を簡易な内容で書き、1 本の PR で開く。人は 3 文書を 1 回のマージの質問で承認し、実装は別の PR で行う。** PR の往復の待ちを減らし、実装の前に人が承認する関門は残すためである。
-   **簡易な進め方でも、受け入れ基準、受け入れ基準ごとの確かめ方、ADR の判断、`docs/dev/security.md` が当てはまるかの判断、日本語の推敲は省かない。当てはまらない節の本文、設計書の Mermaid 図、設計書のレビューの panel は省いてよい。** 実装を縛る内容と承認の判断を支える内容を残し、書く負荷の大きいものだけを省くためである。
-   **簡易な進め方を選ぶかは人が判断し、行数・ファイル数の上限や判定のスクリプトは設けない。ただし、セキュリティの前提か信頼の境界を変える変更と、外部への依存を足す変更は、簡易な進め方を選べない。この除外も読んで判定する。** 軽量プロセスで維持のコストの大半を占めた機械的な判定を作らず、誤ると影響の大きい変更だけを通常の進め方に残すためである。
-   **3 文書の PR をマージする前なら、レビュアーの判断で通常の進め方へ戻せる。マージの後は戻さない。** レビューの済んだ要件定義書を無駄にしないためである。
-   **簡易な進め方でも、実装の PR の数は限らない。計画書が PR の境界を決める。** 機械的な上限を設けない方針に合わせるためである。

## 採らなかった案

-   **3 文書を別々の PR のまま、内容だけを簡易にする。** PR の往復の待ちが減らない（[0072 要件定義書](../../tasks/0072_simple_task_documents/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **文書と実装を 1 本の PR にする。** 計画の承認の前に実装を書くことになり、文書を差し戻すと実装も無駄になる（同上）。
-   **人が同じブランチで `/mkreq`・`/mkarch`・`/mkplan` を続けて走らせ、`/mkplan` が PR を開く。** 人の操作が 3 回のまま残る（同上）。
-   **簡易な進め方を選べない変更を設けない。** 誤ると影響の大きい変更が簡易な設計で通りうる（同上）。
-   **日本語の推敲も省いてよいものにする。** 文が読みにくいと承認の判断を誤らせる（同上）。
-   **エージェントが簡易で足りると判断したときだけ提案する。** 提案しなかった変更について人が選ぶ機会がない（同上）。
-   **通常の進め方へ戻さず、タスクを取り下げて作り直す。** レビューの済んだ要件定義書を捨てることになる（同上）。

## 結果

-   簡易な進め方では、要件定義書の承認の前に設計書と計画書を書く。これは [requirements_process.md](../conventions/requirements_process.md) の「LLM Constraints」の例外で、簡易な進め方を記録したタスクに限る。要件の誤りが設計と計画に及ぶと、3 文書を書き直すことになる。小さな変更ではその費用が小さいと見込んで受け入れる。
-   簡易な進め方の設計書は、panel ではなく 1 人のレビュアーが見る。運用の観点の見落としが増えうる。セキュリティの前提と信頼の境界を変える変更を除外して、影響を抑える。
-   簡易な進め方を選ぶかと除外に当たるかは、人とエージェントが読んで判定する。判定を誤っても機械的には検出されず、PR のレビューで見つける。
-   簡易な進め方は、この決定の後に `/mkreq` で要件定義書を書くタスクだけに当てはまる。進行中のタスクは通常の進め方のまま進む。
-   軽量プロセスは、[#744](https://github.com/isseis/yt2column/issues/744) で削除するまで、簡易な進め方と並んで残る。

## 経緯

- 2026-11-09 小さな変更のタスクは、人の判断で 3 文書を簡易な内容にして `/mkreq` が 1 本の PR で作れるようにし、機械的な判定を設けず、セキュリティの前提・信頼の境界・外部への依存を変える変更を除外した（[0072 要件定義書](../../tasks/0072_simple_task_documents/01_requirements.md)「issue #743 で決めたこと」「要件定義の際に決めたこと（2026-11-09）」）
