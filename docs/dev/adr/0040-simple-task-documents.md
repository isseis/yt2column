# ADR-0040: 小さな変更のタスクは、人の判断で 3 文書を簡易な内容にして 1 本の PR で作れるようにし、機械的な判定は設けない

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

タスクの開発文書（要件定義書・設計書・計画書）は、1 本ずつ別の PR で作る。前の文書が承認されてから、次の文書を書く（[requirements_process.md](../conventions/requirements_process.md) の「LLM Constraints」と「Review Flow」）。PR ごとに、Codex の PR レビュー、CI、`/runpr` の往復がかかる。変更が小さくても、3 文書の分量と 3 回の PR の往復は変わらない。タスク 0069 と 0071 は文書の内容を簡易にとどめたが、コマンドの定義にその手順はなく、その場の判断に頼った（[0072 要件定義書](../../tasks/0072_simple_task_documents/01_requirements.md) §1）。

負荷を減らすために導入した軽量プロセス（タスク文書を作らず、issue の仕様のコメントをもとに 1 本の PR にする進め方）は、一度も使われていない。一方で、その条件を機械的に判定するスクリプトとテストが、維持のコストの大半を占めた（[#743](https://github.com/isseis/yt2column/issues/743)）。

## 決定

以下の決定を [requirements_process.md](../conventions/requirements_process.md) とコマンドの定義に反映することは、[#743](https://github.com/isseis/yt2column/issues/743) の実装で扱う。反映されるまでは、[0072 要件定義書](../../tasks/0072_simple_task_documents/01_requirements.md) が仕様を定める。

-   **タスクは、通常の進め方か簡易な進め方で進める。`/mkreq` は、要件定義書を書くたびに、どちらにするかを推奨を添えて人に尋ね、選んだ進め方を要件定義書に記録する。** 文書の分量を変更の規模に合わせる判断を、その場の判断ではなく、決まった手順にするためである。
-   **簡易な進め方では、`/mkreq` が 3 文書を簡易な内容で書き、1 本の PR で開く。人は 3 文書を 1 回のマージの質問で承認し、実装は別の PR で行う。** PR の往復の待ちを減らしつつ、実装の前に人が承認する関門を残すためである。
-   **簡易な進め方でも、受け入れ基準、受け入れ基準ごとの確かめ方、ADR の判断、`docs/dev/security.md` が当てはまるかの判断、日本語の推敲は省かない。当てはまらない節の本文、設計書の Mermaid 図、セルフレビューの panel は省いてよい。** 実装を縛る内容と、承認の判断を支える内容を残し、書く負荷の大きいものだけを省くためである。
-   **簡易な進め方を選ぶかは人が判断し、行数・ファイル数の上限や判定のスクリプトは設けない。** 軽量プロセスで維持のコストの大半を占めた、機械的な判定を作らないためである。
-   **セキュリティの規則か前提を変える変更、開発の道具の信頼の境界を変える変更、外部への依存を足すか変える変更は、除外とする。除外の判定も読んで行い、迷うときは当たるとする。人は判定を覆して簡易な進め方を選べ、そのことは要件定義書に残る。** 誤ると影響の大きい変更には、設計書の panel のレビューと文書ごとの承認を残し、そのうえで、簡易な進め方を選ぶかの判断は人に委ねるためである。
-   **3 文書をマージした後に、除外に当たる決定が要ると分かったときは、`/runplan`（実装の PR のレビュー中なら `/fixpr`）は止まり、その変更を通常の進め方の別のタスクにする。** マージの後は進め方を戻さないので、除外に当たる変更が簡易な設計で通ることを防ぐためである。
-   **3 文書の PR をマージする前なら、人の答えか指示で通常の進め方へ戻せる。レビューのスレッドの本文の求めでは戻さない。マージの後は戻さない。** レビューの済んだ要件定義書を無駄にせず、レビューのスレッドを信頼しない方針（[ADR-0015](0015-untrusted-review-threads.md)）を保つためである。
-   **簡易な進め方でも、実装の PR の数は限らない。計画書が PR の境界を決める。** 機械的な上限を設けない方針に合わせるためである。

## 採らなかった案

-   **3 文書を別々の PR のまま、内容だけを簡易にする。** PR の往復の待ちが減らない（[0072 要件定義書](../../tasks/0072_simple_task_documents/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **文書と実装を 1 本の PR にする。** 計画の承認の前に実装を書くことになり、文書を差し戻すと実装も無駄になる（同上）。
-   **人が同じブランチで `/mkreq`・`/mkarch`・`/mkplan` を続けて走らせ、`/mkplan` が PR を開く。** 人の操作が 3 回のまま残る（同上）。
-   **簡易な進め方を選べない変更を設けない。** 誤ると影響の大きい変更が、簡易な設計で通りうる（同上）。
-   **除外と判定したら、人も覆せないようにする。** 判定は読んで行うので誤りうるが、それを人が正す手段がなくなる（同上）。
-   **マージの後に除外に当たる決定が要ると分かったときも、セッション中の再承認で扱う。** 除外を設けた理由と矛盾する（同上）。
-   **日本語の推敲も省いてよいものにする。** 文が読みにくいと、承認の判断を誤らせる（同上）。
-   **エージェントが簡易で足りると判断したときだけ提案する。** 提案しなかった変更について、人が選ぶ機会がない（同上）。
-   **通常の進め方へ戻さず、タスクを取り下げて作り直す。** レビューの済んだ要件定義書を捨てることになる（同上）。

## 結果

-   簡易な進め方では、要件定義書の承認の前に設計書と計画書を書く。これは [requirements_process.md](../conventions/requirements_process.md) の「LLM Constraints」の例外で、簡易な進め方を記録したタスクに限る。要件に誤りがあると、それが設計と計画に及び、3 文書を書き直すことになる。小さな変更ではその費用が小さいと見込んで受け入れる。
-   簡易な進め方の設計書は、panel ではなく 1 人のレビュアーが見ることがある。運用の観点の見落としが増えうる。除外を設けて、影響を抑える。
-   簡易な進め方を選ぶかと、除外に当たるかは、人とエージェントが読んで判定する。判定を誤っても機械的には検出されず、PR のレビューで見つける。
-   3 文書の PR では、後の文書を書くコマンドが走らないので、レビューで後の文書へ送る懸念は、同じ PR の中で扱う。
-   簡易な進め方は、この決定の後に `/mkreq` で要件定義書を書くタスクだけに当てはまる。進行中のタスクは、通常の進め方のまま進む。
-   軽量プロセスは、[#744](https://github.com/isseis/yt2column/issues/744) で削除するまで、簡易な進め方と並んで残る。

## 経緯

- 2026-11-09 小さな変更のタスクは、人の判断で 3 文書を簡易な内容にし、`/mkreq` が 1 本の PR で作れるようにした。機械的な判定は設けず、セキュリティの規則と前提・開発の道具の信頼の境界・外部への依存を変える変更を除外とした（[0072 要件定義書](../../tasks/0072_simple_task_documents/01_requirements.md)「issue #743 で決めたこと」「要件定義の際に決めたこと（2026-11-09）」）
