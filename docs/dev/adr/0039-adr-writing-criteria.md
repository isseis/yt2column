# ADR-0039: ADR の背景には決定が答える問題と前提だけを、決定には守るべき規則を理由と正本の場所とともに書き、決定を変えない直しは編集上の訂正として認める

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

ADR は、後の開発者が、変えようとしている主題の決定とその理由を知るために読む文書である。規約の「Writing an ADR」が各節の用途を 1 行ずつ述べるだけで、何をどの詳細度で書くかの基準がないと、「背景」には前の規則の経緯や調査の数字が時系列で並び、「決定」には正本の文書の一覧の写しや腐りやすい実装の細部が入りやすい（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md) §1）。

規約は、ADR を変えてよいのは、その決定を下すか変える PR だけだと定めていた。そのため、決定を変えずに ADR を直す変更（正本の文書とコードの食い違いを述べる記述（以下「ずれの記述」）を、食い違いが直った後に消すことや、既存の ADR を基準に合わせる見直し）を、決定を変えない PR が行うには、規約の例外が要った（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md) §1）。

## 決定

-   **「決定」は今効いている決定だけを書き、正本の文書がある主題では要約して正本へリンクする。** 仕様の正本を 1 つにするためである。規則は [adr.md](../conventions/adr.md) の「Writing an ADR」にある。
-   **「背景」には、決定が答えている問題と、決定を縛る前提だけを書く。** 決定の根拠そのものである数字は残す。前の決定は「経緯」に、退けた形は「採らなかった案」にあり、「背景」に重ねると今の決定が読み取りにくくなるためである。基準を規約の「Writing an ADR」に足すことは、[#728](https://github.com/isseis/yt2column/issues/728) で扱う。
-   **「決定」には、後の変更が守るべき規則を 1 項目ずつ、短い理由と、正本の文書かコードの場所とともに書く。** 正本の文書の一覧と腐りやすい実装の細部は書かない。正本とのずれの記述と、その issue へのリンクは残す。ADR を、決定が変わらない限り古くならない文書にするためである。基準を規約の「Writing an ADR」に足すことは、[#728](https://github.com/isseis/yt2column/issues/728) で扱う。
-   **ADR を作るか変えるのは、その決定を下すか変える PR である。ただし、決定を下しも変えもしない PR も、ADR に編集上の訂正を加えてよい。** 訂正は、決定を変えない決まった種類の直しに限る。訂正はコミットメッセージと PR の説明に記録し、「経緯」には項目を足さない。タスク文書の編集上の訂正（[requirements_process.md](../conventions/requirements_process.md) の「Editing an approved document」）と記録の置き場所をそろえ、例外を作らずに ADR を直せるようにするためである。直した結果が今の決定と食い違う変更と、訂正か迷う変更は、決定の変更として扱う。記録を失わない側に倒すためである。PR を作った後は、その PR が決定を下すか変える ADR 以外の ADR に訂正を加えない。PR を作った後の修正では、コマンドが ADR の訂正を記録せず、レビュアーが分類を確かめられないためである。レビュアーが分類に異を唱えた変更は決定の変更として扱い、タスク文書のない PR では、決定を PR の説明に記録し、「経緯」の項目からその PR へリンクする。規則を規約に足すことは、[#728](https://github.com/isseis/yt2column/issues/728) で扱う。
-   **ずれの記述は、ずれを直す PR が同じ PR で消す。** ずれの記述が事実でない期間を作らないためである。ずれを直す人が記述を見つけられるように、issue から ADR を、ADR から issue をたどれるようにする。ずれの記述を足す PR は、マージを頼む前に、最新の `main` に照らして、そのずれの記述がまだ事実かどうかを確かめ直す。規則を規約に足すことは、[#728](https://github.com/isseis/yt2column/issues/728) で扱う。
-   **`main` の上で `TestADRRecords` が失敗したときの、番号を付け替える直しは、その直しだけの PR で行う。** 番号の付け替えは ADR の識別子を変え、ほかの文書の参照にも及ぶ。関係のない PR のレビュアーは、これを承認する立場にないためである。規則は [adr.md](../conventions/adr.md) の「Taking in `main`」にある。

## 採らなかった案

-   **編集上の訂正にも「経緯」の項目を足す。** 「経緯」の定義を変え、決定の変遷の中に書き方の直しが混ざる（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **決定を変えない直しを認めず、タスクごとの例外で扱い続ける。** 既存の ADR の見直しのたびに例外が要る（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **編集上の訂正を、基準に合わせる書き直しと、ずれの記述の削除に限る。** 古くなったリンクを直すのにも決定を下す PR が要り、ADR に誤った参照が残る（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **基準に合わせる書き直しを同じ節の中に限り、節をまたぐ移動と題名の変更を認めない。** 基準に合わせられない ADR が残る（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **決定を変える PR が、触れた古い ADR の全体を基準に合わせる。** その PR の範囲とレビューが広がる（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **番号を付け替える直しも、どの PR でも行えるようにする。** 関係のない PR のレビュアーが ADR の識別子の変更を承認することになる（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **ADR の仕組み全体（0060 の決定）を主題とする ADR を作る。** issue の範囲を超える（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **規約そのものが正本の文書なので、この主題の ADR を作らない。** 正本の文書がある主題でも、ADR が理由・採らなかった案・経緯を持つという規約の分担と合わない（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **CLAUDE.md の「Design decisions (ADR)」にも、編集上の訂正を認める文を足す。** 同じ規則を 2 か所で持つことになり、そろえる手間が増える（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **ADR の編集上の訂正を運ぶように、コマンドの定義と `requirements_process.md` も同時に変える。** 範囲が広がる（[0070 要件定義書](../../tasks/0070_adr_writing_criteria/01_requirements.md)「要件定義の際に決めたこと（2026-11-09）」）。
-   **ずれの記述を足す PR が、ずれの記述がリンクする issue が閉じたかを `gh issue view` で確かめる。** issue が閉じてもずれが直ったとは限らない（[0070 設計書](../../tasks/0070_adr_writing_criteria/02_architecture.md)「1.2. 設計の際に決めたこと（2026-11-09）」）。
-   **ずれの記述の探し方だけを規約に書き、ずれの記述を足す PR の確かめ直しを求めない。** ずれを直す PR より後に `main` に入った ADR では、そのずれの記述が事実でないまま残る（[0070 設計書](../../tasks/0070_adr_writing_criteria/02_architecture.md)「1.2. 設計の際に決めたこと（2026-11-09）」）。
-   **ずれの記述を足す PR は、`main` を取り込むたびに確かめ直す。** このリポジトリで `main` を取り込むのは衝突を解くときだけで、squash マージは取り込まずに行うので、確かめ直しがほとんど起きない（[0070 設計書](../../tasks/0070_adr_writing_criteria/02_architecture.md)「1.2. 設計の際に決めたこと（2026-11-09）」）。
-   **PR を作った後の修正でも、ADR に編集上の訂正を加えてよいとする。** 今のコマンドは PR を作った後の訂正を ADR について記録しないので、分類がレビュアーの目に入らない（[0070 設計書](../../tasks/0070_adr_writing_criteria/02_architecture.md)「1.2. 設計の際に決めたこと（2026-11-09）」）。
-   **異論の出た訂正を、タスク文書のない PR では差分から戻す。** 要件が定める「決定の変更として扱う」に反する（[0070 設計書](../../tasks/0070_adr_writing_criteria/02_architecture.md)「1.2. 設計の際に決めたこと（2026-11-09）」）。

## 結果

-   ADR を書くタスクは、「背景」と「決定」を規約の基準に合わせて書く。基準に合っているかは文の意味の問題なので、テストでは確かめず、PR のレビューで読んで確かめる（[ADR-0016](0016-document-test-policy.md)）。
-   ADR-0001〜0030 は、基準ができる前に書かれ、基準に合っていない記述を含みうる。それらは [#729](https://github.com/isseis/yt2column/issues/729) で、編集上の訂正として見直す。決定を変える PR は、触れた古い ADR のうち自分が変える部分だけを基準に合わせればよい。
-   ずれを直す PR は、そのずれを述べる ADR の記述を同じ PR で消す負担を負う。
-   編集上の訂正は「経緯」に残らない。squash マージの後は PR のコミットが `main` から辿れなくなるので、ADR がいつ、なぜ直されたかは、squash の件名にある PR 番号から開く PR の説明でしか分からない。決定の変更を編集上の訂正と誤って分類すると、「経緯」に残らない。PR の説明で訂正であると明示し、レビュアーが分類を確かめ、異を唱えたときは決定の変更として扱うことで防ぐ。
-   `/fixpr`・`/runplan`・ローカルの CLI レビューの記録の手順は、タスク文書の訂正だけを運び、ADR の訂正をまだ運ばない。ADR の訂正の行は、エージェントが規約に従って書く。タスク文書の記録の置き場所は [ADR-0036](0036-task-document-status-records.md) にある。
-   ずれの記述を足す PR の確かめ直しと、ずれを直す PR の検索は、コマンドの手順にない。ずれを直す PR は PR を作る前に探すので、PR を作った後に `main` に入ったずれの記述は消せない。このため、確かめ直しが行われなかったずれの記述や、ずれを直す PR を作った後に別の PR が `main` へ足したずれの記述は、事実でなくなっても、後の PR が編集上の訂正として消すまで `main` に残る。ずれの記述を足すことは編集上の訂正ではないので、ADR の決定を変えない PR は、見つけたずれを issue にするだけで、ADR には書けない。
