# ADR-0033: 字幕のキャッシュを 2 つのスロットとポインタで持ち、記事を出した後は既定で消す

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

CLI は字幕と動画の情報（`info.json`）を `yt-dlp` で取得する。失敗した後の再実行やプロンプトの調整のたびに `yt-dlp` を起動し直すのは無駄なので、字幕と `info.json` を動画 ID ごとにキャッシュする（[0002 要件定義書](../../tasks/0002_ytdlp_transcript_source/01_requirements.md) §2.1）。

1 回の取得は 2 つのファイルからなり、1 回のリネームでは置き換えられない。置き換えの途中で失敗したりプロセスが終わったりすると、新旧のファイルが混ざり、揃ったキャッシュに見えてしまう（[0002 の design_handoff.md](../../tasks/0002_ytdlp_transcript_source/design_handoff.md) H-07）。取り直しに失敗したときに、有効なキャッシュを失わないことも求められる（[0002 要件定義書](../../tasks/0002_ytdlp_transcript_source/01_requirements.md) F-005）。

一方で、処理を終えた動画の文字起こしをローカルに残し続けることは望ましくない（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md)「付録A: 決定履歴」）。また、中断で残ったエントリの掃除は、同じキャッシュディレクトリで動く別の実行の書きかけのエントリを消しうる（[0005 要件定義書](../../tasks/0005_cli_assembly/01_requirements.md) §1）。

## 決定

-   **字幕のキャッシュは、CLI の `yt-dlp` の経路だけが、動画 ID をキーとしてファイルにだけ持つ。** プロセスのメモリには持たない。localhost サーバは `yt-dlp` を呼ばないので、このキャッシュを使わない（[ADR-0005](0005-server-architecture.md)）。サーバがメモリに持つ記事のキャッシュは別のもので、[ADR-0027](0027-article-job-api.md) が定める。
-   **1 本の動画のキャッシュは、2 つのスロットと、有効なスロットを示すポインタで持つ。** 取得は、ポインタが指していない側のスロットに書き、検証して同期した後、ポインタのリネーム 1 回で切り替える。切り替えの前に失敗しても既存のキャッシュは変わらないので、元へ戻す操作を持たない。保証すること（G1〜G6）とその前提（P1〜P4）、中断の時点ごとの状態、キャッシュのコードを変えるときのチェックリストは [cache_consistency.md](../cache_consistency.md) に従う。パーミッションと、名前を検証済みの動画 ID から組み立てる規則は [security.md](../security.md) §5「キャッシュディレクトリ」に従う。
-   **CLI は、記事を `--out` に書いた後、既定でその動画のキャッシュを消す。** `--keep-cache` を付けた実行と、記事を書く前に失敗か中断した実行は、キャッシュを残す。削除の失敗は警告にとどめる。
-   **キャッシュの削除は、検証・推敲のログを書く前に行う。** 記事はもう出してあるからである。そのため、ログを書けずに終了コード `1` で終わった実行でも、キャッシュは消えている。
-   **CLI は、実行のたびに、パイプラインの前にキャッシュディレクトリ全体を掃除する。** 前の実行が中断で残したエントリを、今回の実行の成否によらず回収するためである。掃除の失敗は警告にとどめる。
-   **同じキャッシュディレクトリに書くのを 1 つの実行に保つ前提（P1）は、CLI がキャッシュディレクトリの排他で守る。** `internal/transcript` は排他を持たず、呼び出し側に直列化を求める。CLI は排他を待たずに取り、取れなければすぐに失敗する。排他は `yt-dlp` にも引き継ぐ。利用者から見た振る舞いは [cli.md](../guides/cli.md) の「キャッシュと同時実行」に従う。

## 採らなかった案

-   **2 つの正規のファイルを退避名へリネームしてから新しいファイルを置き、失敗したら元に戻す。** 0002 の当初の方式である。2 つのファイルを 1 回のリネームで置き換えられないため、新旧の混在を防ぐ順序の不変条件と、ロールバック自体の失敗の扱いが要り、手順とテストが複雑になった（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md)「付録A: 決定履歴」）。
-   **字幕と `info.json` を 1 つのファイルにまとめる。** コミットは 1 回のリネームで済むが、要件が 2 つのファイルを前提としており（AC-29 の「一部だけ存在」など）、要件の変更が要る（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md)「付録A: 決定履歴」）。
-   **スロットを一意の名前（`os.MkdirTemp`）で作る。** ポインタの内容が任意の名前になり、ディレクトリ内の文字列を信用しない規則（AC-20）に反する。固定名の 2 つのスロットなら、ポインタは `a`・`b` の 2 値だけを受理すればよく、掃除も命名規則で不要なエントリを判定できる（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md)「付録A: 決定履歴」）。
-   **`<動画 ID>.` の接頭辞でその動画のエントリを識別して、残ったエントリを消す。** 利用者が置いた `<動画 ID>.notes` などの無関係なファイルまで消し、AC-59 に反する（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md)「付録A: 決定履歴」）。
-   **キャッシュをプロセスのメモリにも持つ。** 利用者がキャッシュのファイルを消せば、次の `Fetch` がキャッシュミスとして取り直す。これを成り立たせるため、キャッシュはファイルだけとした（[0002 要件定義書](../../tasks/0002_ytdlp_transcript_source/01_requirements.md) F-005）。メモリのキャッシュは、必要になった時点で加える（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md) §9）。
-   **既存のキャッシュディレクトリとファイルのパーミッションを検査して、厳しくするか拒否する。** キャッシュの中身は公開動画の字幕とメタ情報であり、利用者が用意したディレクトリのパーミッションを変えたり拒否したりしても、機密性は上がらず、利用者の設定を上書きするだけである（[0002 の design_handoff.md](../../tasks/0002_ytdlp_transcript_source/design_handoff.md) H-11）。
-   **掃除と `Fetch` の排他を、`internal/transcript` の中のロックファイルや経過時間のしきい値で行う。** YAGNI として設けず、単一ライターの前提をキャッシュディレクトリ全体に広げて、呼び出し側に任せた（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md)「付録A: 決定履歴」）。
-   **同時実行を排他せず、利用者への注意にとどめる。** cron などで実行が重なると、一方の掃除が他方の書き込み中のエントリを消しうる（[0005 要件定義書](../../tasks/0005_cli_assembly/01_requirements.md) F-007）。
-   **排他を `internal/transcript` に置く。** 排他は、掃除・字幕の取得・記事の生成・公開・キャッシュの削除からなる 1 回の実行の全体にかかるので、呼び出し側の部品とした（[0005 設計書](../../tasks/0005_cli_assembly/02_architecture.md) §3.7）。
-   **`fcntl` のレコードロック（POSIX ロック）を使う。** プロセスに結び付き、子プロセスに引き継がれず、同じプロセスの別の記述子を閉じただけで解放される（[0005 設計書](../../tasks/0005_cli_assembly/02_architecture.md) §3.7）。
-   **使い終わった排他のファイルを消す。** 消してから作るまでの間に、別のプロセスが別の inode に排他を取る競合が生じる（[0005 設計書](../../tasks/0005_cli_assembly/02_architecture.md) §3.7）。
-   **CLI の終了時に `yt-dlp` のプロセスグループを止めて、SIGKILL の後に `yt-dlp` が残らないようにする。** SIGKILL では CLI が後始末を実行できない。Linux の `Pdeathsig` は macOS にない（[0005 の design_handoff.md](../../tasks/0005_cli_assembly/design_handoff.md) H-02）。
-   **同時の書き込みを防がずに、壊れたキャッシュを検出する。** 2 つのプロセスが同じファイルに書くと、2 回分の取得が混ざったまま JSON として正しいファイルが残りうる。厳格な解析では見分けられない（[0005 の design_handoff.md](../../tasks/0005_cli_assembly/design_handoff.md) H-02）。

## 結果

-   キャッシュは、障害や電源断の後も、旧世代・新世代・キャッシュミスのどれかになる。壊れた内容や新旧が混ざった内容を、有効な世代として読まない。ただし、同時の書き込み、他者による変更、ネットワークファイルシステム、`fsync` を守らないストレージは保証の外にある（[cache_consistency.md](../cache_consistency.md)「保証しないこと」）。
-   キャッシュのコードを変えるときは、[cache_consistency.md](../cache_consistency.md) の「変更時のチェックリスト」を確かめる。
-   記事を出した後の再実行は、字幕を取り直す。同じ動画を何度も処理する評価などでは、すべての実行に `--keep-cache` を付ける必要がある。
-   CLI が書くほかのファイルは、キャッシュの削除や掃除で消えないよう、キャッシュディレクトリの外に置く。`--out` と `--review-log` はキャッシュディレクトリの中を拒否し（[cli.md](../guides/cli.md) の「使い方」、[0010 設計書](../../tasks/0010_post_generation_review/02_architecture.md) §3.9）、`--artifacts` も同じく拒否する（[ADR-0023](0023-artifact-resume.md)）。
-   同じキャッシュディレクトリを使う CLI は 1 つずつしか動かない。SIGKILL の後に残った `yt-dlp` が止まったままだと、利用者が止めるまで後の実行は失敗し続ける。これは残るリスクとして受け入れた（[0005 設計書](../../tasks/0005_cli_assembly/02_architecture.md) §3.7）。
-   大文字と小文字を区別しないファイルシステムでは、大文字と小文字だけが異なる 2 つの動画 ID が同じエントリに当たる。`info.json` の `id` の照合で別の動画の字幕は返さないが、そのキャッシュは使えない。衝突の確率は無視できるので対処しない（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md) §3.5）。

## 経緯

- 2026-09-30 字幕と `info.json` のキャッシュを、動画 ID ごとの 2 つの固定名のスロットとポインタで持ち、ポインタのリネーム 1 回でコミットすることにした。退避とロールバックの方式はやめた。中断で残ったエントリは `Fetch` の終了時と掃除で消し、動画 1 本のキャッシュの削除を `YtDlpSource` の具体型のメソッドとして設けて、投稿の成功後に既定で呼ぶことを呼び出し側（#6）に求めた（[0002 設計書](../../tasks/0002_ytdlp_transcript_source/02_architecture.md) §3.5・付録A）
- 2026-10-05 CLI の 1 回の実行は、キャッシュディレクトリの `flock` の排他を待たずに取り、`yt-dlp` に引き継ぐことにした。排他の後にキャッシュを掃除し、投稿に成功して `--keep-cache` がなければその動画のキャッシュを消す。掃除と削除の失敗は警告にとどめる（[0005 設計書](../../tasks/0005_cli_assembly/02_architecture.md) §3.4・§3.7）
- 2026-10-10 検証・推敲のログを加えるとき、キャッシュの削除をログの書き出しの前に行うことにした。記事は投稿済みで、キャッシュは要らないためである（[0010 設計書](../../tasks/0010_post_generation_review/02_architecture.md) §3.9）
