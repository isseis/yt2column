# ADR-0006: ブラウザ拡張と localhost サーバの脅威モデルは、同一ユーザーを信頼し、他のユーザーを排除する

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

サーバは、拡張から送られた字幕と動画メタデータを受け取り、LLM の API キーと Slack の Webhook URL を使って記事を作る。記事の本文は LLM の出力で、字幕とメタデータへのプロンプトインジェクションで操作されうる。サーバの入口をどこまで限定するかは、どの相手を排除し、どの相手を信頼するかで決まる。

当初は loopback の TCP と共有トークンで入口を限定していたが、0026 で待ち受けを UDS だけに変えた。排除する相手ごとに根拠が異なるので、混同しないように書き分ける（[security.md](../security.md) §8）。

## 決定

-   **同一ユーザーのフル権限プロセスは信頼する。** サーバや拡張と同じ OS ユーザーとして動き、ファイルの読み書きとプロセスの起動ができるプロセス（AI Agent を含む）は、`.envrc`・API キー・Webhook URL を読め、サーバを経由せずに LLM API や Slack を直接使える。サーバの入口をどう限定しても、これらの資産は守れないので、この相手は排除しない。
-   **排除する相手ごとに根拠を分ける。** 他のユーザーのプロセスはソケットの権限で排除する。ウェブページは、サーバが TCP を待ち受けないので経路がない。サンドボックス化された Agent を排除しているのはサンドボックスのポリシーであり、UDS の権限ではない。それぞれの仕組みは [security.md](../security.md) §8「ブラウザ拡張と localhost サーバ」と §8.2「localhost サーバ」に従う。
-   **UDS の権限は同じ uid のプロセスを区別しない。** サーバは `Host`・`Origin`・`Content-Type`・`Authorization` を検査せず、パスとメソッドだけを検査する。共有トークンは、同じユーザーのフル権限プロセスを防げず、他のユーザーとウェブページは UDS で排除できるので、削除した。
-   **Native Messaging のホストを起動できる拡張を固定し、秘密は `secret.Secret` で持つ。** ホストの `allowed_origins` は固定した拡張 ID のオリジンだけとし、API キーと Webhook URL は、送信先へのリクエストを除き、エラーやログを含むどの出力にも漏らさない。

この決定の仕様の正本は [security.md](../security.md) の §8「ブラウザ拡張と localhost サーバ」、§8.1「ブラウザ拡張」、§8.2「localhost サーバ」である。

## 採らなかった案

-   **共有トークンを残して認証を続ける。** 同一ユーザーのフル権限プロセスはトークンも `.envrc` も読めるので、トークンを残しても防げない（[0026 要件定義書](../../tasks/0026_native_messaging_relay/01_requirements.md) §4.2）。
-   **`Host`・`Origin` の検査を残し、ホストに `Origin` を付けさせる。** UDS ではソケットに接続できる相手なら誰でも偽れるので、検査しても排除できる相手がいない（[0026 設計書](../../tasks/0026_native_messaging_relay/02_architecture.md) §3.4）。
-   **別ユーザー分離、launchd によるソケットの保護、拡張のエクスポートできない鍵によるリクエストの署名、リクエストごとの利用者の承認を行う。** 同一ユーザーのフル権限プロセスへの防御は本タスクの範囲外とし、必要になった場合は別のタスクとする（[0026 要件定義書](../../tasks/0026_native_messaging_relay/01_requirements.md) §2.3・§4.2）。
-   **拡張がサーバを認証する（サーバが本物であることを確かめる）。** 同じマシンの他の利用者がポートを先に使うリスクは受け入れる（[0020 要件定義書](../../tasks/0020_extension_send/01_requirements.md) §2.3、[0011 設計書](../../tasks/0011_localhost_server/02_architecture.md) §5.4）。
-   **共有トークンを自動でローテーションする。** 漏洩時の作り直しは、利用者がトークンのファイルを削除してサーバを再起動する手動の手順とする（[0011 要件定義書](../../tasks/0011_localhost_server/01_requirements.md) §2.3）。

## 結果

-   サーバの入口を守る境界は、OS のファイルの権限と、TCP を待ち受けないことである。同じユーザーのプロセスは、サーバを経由せずに秘密を使える。
-   同じユーザーは、サーバの稼働中でもソケットのパスを `unlink` して自分のソケットを同じパスに bind でき、以後の字幕を受け取れる。サーバの停止中にソケットを先に bind することもできる。起動のロックは、ロックを取らない相手を止めない。
-   ソケットのディレクトリの祖先は検査しない。macOS の拡張 ACL は、モードのビットと独立に他ユーザーに検索を許しうる。これらは利用者 1 人の macOS を前提に受け入れる。
-   ホストのバイナリと manifest は同一ユーザーが置き換えられる。`allowed_origins` は、同じ `key` を使えば誰でも同じ ID を名乗れるので、同じ ID の拡張を読み込める同一ユーザーを排除しない。
-   ウェブページからの経路はないので、以前の TCP のサーバが前提にしていた DNS rebinding と preflight の対策は要らない。

## 経緯

- 2026-10-13 localhost サーバを loopback にだけ bind し、`Host`・`Origin`・`Content-Type`・共有トークンで入口を限定した。同一ユーザーとして動くプロセスは信頼し、トークンのファイルを読めることと、停止中に他の利用者がポートを先に使えることを残余のリスクとして受け入れた（[0011 設計書](../../tasks/0011_localhost_server/02_architecture.md) §5.1・§5.2・§5.4）
- 2026-10-16 拡張は共有トークンを `chrome.storage.local` に保存して送信に使い、サーバを認証しないこと（ポートを先に使うプロセスへの送信）を残余のリスクとして受け入れた。偽のサーバがありうるので、応答を信頼できない入力として検査する（[0020 設計書](../../tasks/0020_extension_send/02_architecture.md) §5.1・§5.4）
- 2026-10-19 待ち受けを TCP から UDS に変え、ソケットのディレクトリの `0700` とソケットの `0600` で他のユーザーを排除し、共有トークン・ポート設定・`Host`/`Origin` の検査を削除した。排除する相手ごとに根拠（他のユーザー・ウェブページ・サンドボックス化された Agent）を書き分けた（[0026 設計書](../../tasks/0026_native_messaging_relay/02_architecture.md) §5.1〜§5.4）
