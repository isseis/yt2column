# ADR-0006: ブラウザ拡張と localhost サーバの脅威モデルは、同一ユーザーを信頼し、他のユーザーを排除する

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

サーバは、拡張から送られた字幕と動画メタデータを受け取り、LLM の API キーを使って記事を作る。記事の本文は LLM の出力で、字幕とメタデータへのプロンプトインジェクションで操作されうる。サーバの入口をどこまで限定するかは、どの相手を排除し、どの相手を信頼するかで決まる。

## 決定

-   **同一ユーザーのフル権限プロセスは信頼する。** サーバや拡張と同じ OS ユーザーとして動き、ファイルの読み書きとプロセスの起動ができるプロセス（AI Agent を含む）は、`.envrc` と API キーを読め、サーバを経由せずに LLM API を直接使える。サーバの入口をどう限定しても、これらの資産は守れないので、この相手は排除しない。規則は [security.md](../security.md) の §8「ブラウザ拡張と localhost サーバ」にある。
-   **排除する相手ごとに根拠を分ける。** 他のユーザーのプロセスはソケットの権限で排除する。ウェブページは、サーバが TCP を待ち受けず、ブラウザもページから UDS へ接続できないので経路がない。サンドボックス化された Agent を排除しているのはサンドボックスのポリシーであり、UDS の権限ではない。理由は記録されていない。規則は security.md §8「ブラウザ拡張と localhost サーバ」と §8.2「localhost サーバ」、[0026 要件定義書](../../tasks/0026_native_messaging_relay/01_requirements.md) §4.2「セキュリティ (Security)」にある。
-   **UDS の権限は同じ uid のプロセスを区別しない。** サーバは `Host`・`Origin`・`Content-Type`・`Authorization` を検査せず、パスとメソッドだけを検査する。共有トークンによる認証も行わない。共有トークンは同じユーザーのフル権限プロセスを防げず、他のユーザーとウェブページは UDS で排除できるので、要らない。規則は security.md §8 と §8.2 にある。
-   **Native Messaging のホストを起動できる拡張を固定する。** ホストの `allowed_origins` は固定した拡張 ID のオリジンだけとする。ブラウザはページから UDS へ接続できず、拡張以外の相手にホストを起動させないためである。拡張の ID を manifest の `key` で固定することは [ADR-0026](0026-extension-platform.md) が定め、規則は [security.md](../security.md) §8.1「ブラウザ拡張」と、0026 要件定義書 §4.2「セキュリティ (Security)」にある。
-   **拡張 ID は送り元の認証にならない。** 同じ `key` を使えば誰でも同じ ID の拡張を読み込めるので、`allowed_origins` は同じ ID の拡張を読み込める同一ユーザーを排除しない。規則は security.md §8.1 と §8.2 にある。秘密の持ち方と、秘密を出力に流さないことは [ADR-0031](0031-secret-closure.md) が定める。

Webhook URL と Slack への投稿は、まだコードと security.md に残っている。この差分は [#770](https://github.com/isseis/yt2column/issues/770) の実装で解消する。

## 採らなかった案

-   **共有トークンで認証する。** 同一ユーザーのフル権限プロセスはトークンも `.envrc` も読めるので、トークンを残しても防げない（[0026 要件定義書](../../tasks/0026_native_messaging_relay/01_requirements.md) §4.2）。
-   **`Host`・`Origin` の検査を残し、ホストに `Origin` を付けさせる。** UDS ではソケットに接続できる相手なら誰でも偽れるので、検査しても排除できる相手がいない（[0026 設計書](../../tasks/0026_native_messaging_relay/02_architecture.md) §3.4）。
-   **別ユーザー分離、launchd によるソケットの保護、拡張のエクスポートできない鍵によるリクエストの署名、リクエストごとの利用者の承認を行う。** 同一ユーザーのフル権限プロセスへの防御は本タスクの範囲外とし、必要になった場合は別のタスクとする（[0026 要件定義書](../../tasks/0026_native_messaging_relay/01_requirements.md) §2.3・§4.2）。
-   **拡張（ホスト）がサーバを認証する（接続先が本物のサーバであることを確かめる）。** 他のユーザーは、ソケットのディレクトリの `0700` と所有者の検査によって、ソケットのパスに名前を作れない。同じユーザーは、ファイルの権限でも uid でも区別できず、信頼の範囲に含める。認証で新たに排除できる相手が残らないので、行わない（[security.md](../security.md) §8.2）。ただし、ソケットのディレクトリがまだなく、その親に他ユーザーが書き込める既定でない設定では、ホストが接続先を検査しないので隙間が残る。これは [#678](https://github.com/isseis/yt2column/issues/678) で扱う。
-   **共有トークンを自動でローテーションする。** 漏洩時の作り直しは、利用者がトークンのファイルを削除してサーバを再起動する手動の手順とする（[0011 要件定義書](../../tasks/0011_localhost_server/01_requirements.md) §2.3）。

## 結果

-   サーバの入口を守る境界は、OS のファイルの権限と、TCP を待ち受けないことである。同じユーザーのプロセスは、サーバを経由せずに秘密を使える。
-   同じユーザーは、サーバの稼働中でもソケットのパスを `unlink` して自分のソケットを同じパスに bind でき、以後の字幕を受け取れる。サーバの停止中にソケットを先に bind することもできる。起動のロックは、ロックを取らない相手を止めない。
-   ソケットのディレクトリの祖先は検査しない。macOS の拡張 ACL は、モードのビットと独立に他ユーザーに検索を許しうる。これらは利用者 1 人の macOS を前提に受け入れる。
-   ホストのバイナリと manifest は同一ユーザーが置き換えられる。`allowed_origins` は、同じ `key` を使えば誰でも同じ ID を名乗れるので、同じ ID の拡張を読み込める同一ユーザーを排除しない。
-   ウェブページからの経路はないので、DNS rebinding と preflight の対策は要らない。
-   同じ動画の記事の有無と、その記事のキーは、照会付きの生成の開始で、生成を始めずに分かる。照会できるのはソケットに接続できる同じユーザーのプロセスだけで、その相手は生成の開始でキーを得て記事を受け取れ、ブラウザの履歴も読めるので、記事の有無を動画単位で知る手段は増えるが、守る資産は変わらない。この記事の有無の照会は、排除する脅威ではなく、信頼の境界の内側で受け入れるリスクとする（[security.md](../security.md) §8）。

## 経緯

- 2026-10-13 localhost サーバを loopback にだけ bind し、`Host`・`Origin`・`Content-Type`・共有トークンで入口を限定した。同一ユーザーとして動くプロセスは信頼し、トークンのファイルを読めることと、停止中に他の利用者がポートを先に使えることを残余のリスクとして受け入れた（[0011 設計書](../../tasks/0011_localhost_server/02_architecture.md) §5.1・§5.2・§5.4）
- 2026-10-16 拡張は共有トークンを `chrome.storage.local` に保存して送信に使い、サーバを認証しないこと（ポートを先に使うプロセスへの送信）を残余のリスクとして受け入れた。偽のサーバがありうるので、応答を信頼できない入力として検査する（[0020 設計書](../../tasks/0020_extension_send/02_architecture.md) §5.1・§5.4）
- 2026-10-19 待ち受けを TCP から UDS に変え、ソケットのディレクトリの `0700` とソケットの `0600` で他のユーザーを排除し、共有トークン・ポート設定・`Host`/`Origin` の検査を削除した。排除する相手ごとに根拠（他のユーザー・ウェブページ・サンドボックス化された Agent）を書き分けた（[0026 設計書](../../tasks/0026_native_messaging_relay/02_architecture.md) §5.1〜§5.4）
- 2026-11-03 照会付きの生成の開始で、同じ動画の記事の有無とキーを生成を始めずに返すことにした。0044 が排除する脅威とした、生成を始めずに記事の有無を知ること（T-10）を、ソケットに接続できる同じユーザーのプロセスは信頼するので、信頼の境界の内側で受け入れるリスクとして再評価した。キーをプロセスごとの秘密から計算することは、キーの計算方法に依存させないために保った（[0058 要件定義書](../../tasks/0058_same_video_article/01_requirements.md)「要件定義の際に決めたこと（2026-11-03）」）
- 2026-11-11 Webhook への投稿の機能の廃止に合わせて、同一ユーザーのプロセスが読める資産から Webhook URL を、直接使えるサービスから Slack を除いた（[0083 要件定義書](../../tasks/0083_remove_slack_webhook/01_requirements.md) F-001）
