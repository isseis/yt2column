# ADR-0050: タスクの PR を開く前にクロスチェックの部分レビューを範囲を絞って行い、走らないときは止めずに記録する

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

**問題：** タスクの PR は、開く前にサブエージェントのセルフレビューとローカルの CLI レビューを受け、開いたときの PR レビューはない（[ADR-0013](0013-review-setup.md)）。PR を開いた後に見つかった問題を直すと、人のレビューが始まった後に PR が変わる。この ADR を決めた時点では、開いたときに Codex の PR レビューを 1 回だけ受け、PR を開いた後の修正は Codex の PR レビューに見られなかった。

**実績：** 開く前のレビューを通った PR に、作った後で Fable のサブエージェントのレビューを手作業で頼んだ。7 件のうち 6 件で、マージの前に直すべき Major 級の問題が見つかった。Codex の最初の PR レビューが指摘 0 件を返した PR もあった。

-   **効いた条件：** 成果が大きかったのは、範囲を絞って役目を狭めた回と、文書の PR である。承認済みの設計を写した実装では、効果が薄かった。
-   **弱点：** 受け取る側のトリアージで、正しい指摘を誤って却下した。その 1 件は、ローカルの CLI レビューの指摘を誤って却下したものと同じだった（[0098 要件定義書](../../tasks/0098_fable_partial_review/01_requirements.md) §1）。

**制約：** Fable は Claude Code の Agent ツールで選べるモデルの 1 つで、OpenCode からは呼べない。1 回の費用は、これまでの実績で 2〜16 分、出力 2k〜260k トークンである。また、Antigravity CLI（[ADR-0055](0055-harness-independent-commands.md)）では `invoke_subagent` で具体的なモデルを固定できず、サブエージェントもシステムプロンプトから自身のモデルの ID を読めない。モデルを固定して検証できるのは `swarm` ツールだけである。

**決めることと選択肢：** この問題に対して、次の 6 つを決める必要があった。

1.  **いつ見せるか：** PR を作った後（これまでの手作業の形）か、PR を開く前か。
2.  **何を見せるか：** PR の全体か、効果の大きかった箇所に絞るか。
3.  **指摘をどう扱うか：** 部分レビューの指摘だけを別に扱うか、ローカルの CLI レビューの指摘とまとめるか。誤った却下をどう防ぐか。
4.  **ハーネスごとのモデル検証と未実行時の扱い：** PR を止めるか、ほかのモデルで代えるか、止めずに記録するか。
5.  **見た後に足された commit をどうするか：** 直しや `main` の取り込みは、部分レビューの後にも起こる。それをすべて見直すか、見直さない commit を決めるか。
6.  **記録行の形式：** モデル固有名を残すか、役割名に改めて新旧両方を読むか。

## 決定

PR を開く前に、ハーネスごとに `_context.md` が定めるクロスチェック役割のモデルによる部分レビューを、4 つの基準に当たる箇所に絞って 1 回行う。起動・モデル検証・タイムアウト・終了処理はハーネスのアダプタ（[ADR-0055](0055-harness-independent-commands.md)）に委譲し、指摘はローカルの CLI レビューの指摘とまとめてトリアージし、却下には根拠を確かめる。走らないときは、止めずに `not run` と記録する。見た後に足された commit は、記録を無効にするものとしないものを判定のスクリプトが分け、push の直前に確かめ直す。

仕様は [0098 要件定義書](../../tasks/0098_fable_partial_review/01_requirements.md) の機能要件と [0120 要件定義書](../../tasks/0120_harness_independent_commands/01_requirements.md) の F-005・F-008 が持つ。記録の後、push の前にできた commit の扱いは、[0114 要件定義書](../../tasks/0114_fable_record_after_merge/01_requirements.md) の F-001・F-002・F-005 が持つ。手順は `.claude/commands/_lib/` のクロスチェック部分レビューの共有手順（現在は `.claude/commands/_lib/fable-review.md`）とハーネスのアダプタにあり、ハーネス別のモデル対応表は [_context.md](../../../.claude/commands/_context.md) にある。

**食い違い：** 共有手順のファイル名と本文（`.claude/commands/_lib/fable-review.md`）および呼び出し元の入力名は、まだ `Fable` の固有名・Claude Code の `Agent` ツール・`claude-fable-...` のモデル ID・`Fable review:` の記録行だけを前提としている。この食い違いは https://github.com/isseis/yt2column/issues/1072 の実装で解消する。

### 1. PR を開く前に、1 つの PR につき 1 回行う

-   **選んだもの：** タスクの PR を開くコマンド（`/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2`・`/runplan`）は、PR を開く前に、ローカルの CLI レビューと並列にクロスチェックの部分レビューを行う。
-   **理由：** PR を開く前に直せば、直しがローカルの CLI レビューを通り、人のレビューは直した後の PR から始まるためである。PR を開いたときの PR レビューはない（[ADR-0013](0013-review-setup.md)）。この理由は [0118 要件定義書](../../tasks/0118_codex_removal/01_requirements.md) で改めたもので、それまでは Codex の最初の PR レビューが修正を見ることを理由にしていた。
-   **回数：** `/runplan` でも phase group ごとではなく、PR につき 1 回とする。費用が phase group の数だけ増えるためである。
-   **`/mkplan2` も含める：** PR の境界などを人に問わずに決めるためであり、共有の手順に置けば例外が要らないためでもある（0098 要件定義書の F-001）。

### 2. 見る箇所を 4 つの基準に絞る

-   **選んだもの：** 範囲は、信頼の境界・先行文書との照合・外部の振る舞いについての技術的な主張・人に問わずに決めたこと、の 4 つの基準に当たる箇所に限る。
-   **理由：** 範囲を絞った回の成果が大きかったためである。
-   **実装の PR：** 先行文書との照合は、文書の決めていない点・文書を解釈した点・文書と違えた点に限る。実装の PR には必ず先行文書があり、設計を写した実装では効果が薄かったためである。
-   **3 文書の PR：** 3 文書をまとめて 1 回行い、3 文書どうしの食い違いを照合に含める（0098 要件定義書の F-002）。
-   **外した箇所も確かめさせる：** 外した箇所とその理由をクロスチェックのモデルに渡す。外した箇所が基準に当たるとモデルが判断したら、その箇所もレビューさせ、外した判断の誤りを指摘として返させる。当たる箇所がないと書き手が判断したときも、除外の一覧だけを確かめさせ、モデル側も当たる箇所を見つけなければ `not run` と記録する。外した箇所は PR の説明にも残す。書き手のセッションが自分の盲点を外さないようにするためである。当たる箇所がないときに呼ばないと、すべてを外した判断を誰も確かめない（0098 要件定義書の F-002、F-003）。
-   **既出の指摘：** 却下した指摘と決着済みの論点は、セッション自身の言葉で渡し、具体的な筋書きがあるときに限って再提起させる。重複を避けるためである。指摘の本文は渡さない。信頼しないテキストの扱い（[ADR-0015](0015-untrusted-review-threads.md)）を変えないためである（0098 要件定義書の F-003）。

### 3. 指摘はまとめてトリアージし、却下には根拠を確かめる

-   **選んだもの：** 部分レビューの指摘とローカルの CLI レビューの指摘を 1 回のトリアージにまとめる。却下するときは、該当箇所を読むか実験で根拠を確かめ、確かめた方法と結果を理由として記録する。この規則は、ローカルの CLI レビューの指摘だけのトリアージにも当てはめる。
-   **理由：** 誤った却下が、部分レビューの指摘とローカルの CLI レビューの指摘の両方で起きたためである。上位モデルのレビューの指摘は、もともと人に尋ねる（[ADR-0042](0042-implementation-model-tiers.md)）ので対象にしない（0098 要件定義書の F-004）。
-   **直しの確かめ：** 部分レビューの指摘の修正は、ローカルの CLI レビューの 2 回目の試行で確かめ、部分レビューをもう一度は走らせない。部分レビューの指摘だけを直したときも、最初の試行がどの CLI もレビューしなかったときも、2 回目の試行を行う。修正を確かめずに push しないためであり、費用を 1 回分に抑えるためでもある（0098 要件定義書の F-004）。

### 4. ハーネスごとにモデルを固定・検証し、走らないときは止めずに記録する

-   **選んだもの：** 担当モデルは `_context.md` の対応表にハーネスごとに定める（Claude Code は `fable`、Antigravity は組み込みの `claude-opus-5-5-medium`）。基準に当たる箇所がない、エラーや利用上限に達した、走ったモデルが指定モデルでない、エージェントがクロスチェックモデルを呼べない、のどれかのときは、止めずに `not run` とその理由を記録して進む。
-   **理由：** 部分レビューは追加のレビューであり、使えないことで PR を止めないためである。Antigravity に `claude-opus-5-5-medium` を選んだのは、136 PR の実運用で `gemini-4-argon-medium` / `high` が延べ 9 回すべて指摘 0 件と検出力に欠け、`gemini-4-carbon-medium` と `gemini-4-neon-xhigh` は実測で 10 分超タイムアウトかつ割り当て消費が大きかったためである。一方、`claude-opus-5-5-medium` は実 PR `#1076` を 4 分 19 秒で完了し、4 つの範囲基準と `exclusion-error` の計 5 区分すべてにわたって 6 件の具体的な指摘を厳密形式で返し、通常セッションの Gemini 4 Neon に対する異系統クロスチェックとして機能した（[0120 設計書](../../tasks/0120_harness_independent_commands/02_architecture.md)「設計の際に決めたこと（2026-11-22）」）。
-   **ハーネス別の起動とモデル検証：** ほかのモデルで代えず、指定モデルで走ったかを検証する。
    -   **Claude Code：** `Agent` ツールで起動し、サブエージェントが出力 1 行目に報告するモデルの ID で確かめる。
    -   **Antigravity：** `invoke_subagent`（`Model: "pro"` を含む）は使わず、プロンプトに `Model:` 行の出力も求めない。起動前に `swarm(action: "models", all: true)` で指定モデルの存在と割り当ての残りを確かめ、利用不可なら別モデルで代えず `not run`（`unavailable`）とする。利用可能ならメインセッションが起動前状態チェックより前に差分・ログ・変更ファイル一覧をスクラッチパッドへ直接リダイレクトして書き出し、`swarm(action: "add", ...)` でモデルを固定して起動し、ワーカーは `git` を実行せず `read_file` でそれを読む。モデル検証はサブエージェント本文の自己申告ではなくハーネス返却 JSON の `"model"`（欠落時のみ起動直後の `status` を 1 回予備参照）が指定モデルの ID と完全一致することで確かめ、不一致なら即座に `swarm(action: "kill")` と終了時状態チェックを行い、モデル不一致の `not run`（`wrong-model`）とする。起動後は完了を待機し（並列タスクで早期解除されない `schedule` で 30 分のタイムアウトを設ける）、結果は `read_board` で取得し、終了時に `swarm(action: "kill")` でワーカーを終了させる（[0120 要件定義書](../../tasks/0120_harness_independent_commands/01_requirements.md) の F-005、[0120 設計書](../../tasks/0120_harness_independent_commands/02_architecture.md) 1.4「実測検証の結果（H-01・H-04）」）。
    -   **理由：** Antigravity の `invoke_subagent` は具体的なモデルを固定できず、サブエージェントはシステムプロンプトから自身のモデルの ID を読めないため本文の自己申告が検証にならないからである。
-   **OpenCode で動く `/runplan`：** `not run`（`agent-cannot-call`）とする。chief の送り先（[ADR-0046](0046-chief-of-staff.md)）を変えないためである（0098 要件定義書の F-005）。
-   **待つ時間：** 30 分までとし、超えたら `not run`（時間切れ）とする。呼び直しは 1 回とする。上限がないと、応答が返らないときに PR を開けないためである。30 分は、これまでの実績の最長（16 分）のおよそ 2 倍である（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 4）。

### 5. 見た後に足された commit は、判定のスクリプトが分け、push の直前に確かめ直す

部分レビューが見た範囲の後にも、直し・チェックポイントの commit・`main` の取り込みなどの commit が足される。すべてを見直すと費用が繰り返しかかり、何も見直さないと誰も見ていない変更のまま PR が開く。そこで、記録を無効にしない commit を決め、それ以外の commit があれば見直す。

-   **記録を無効にしない commit：** 中身のない commit（空の commit、`README.en.md` だけを変える commit、計画書の PR の進み具合のチェックボックスの行だけを変える commit）、同じ実行の直しの commit、チェックポイントの印の後の commit（green gate の直し、上位モデルのレビューの直しなど、PR のチェックポイントの実行が PR を作るまでに作った commit）である。直しの commit を含めるのは、部分レビューと上位モデルのレビューが互いの直しのたびに繰り返されないようにするためである（0098 要件定義書の F-001、0114 要件定義書の F-002）。
-   **計画書のほかの行を変える commit は、中身のある commit とする：** `_lib/opus-review.md` の除外できる commit は使わない。計画書は、タスク文書の PR ではレビューされる中身であり、実装の PR でも実装モデル要件や自動送信の値は中身であるためである（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 11）。
-   **チェックポイントの印：** チェックポイントの入口で記録が有効なら、空の commit に印を残し、印より後の commit を記録を無効にしない commit とする。
    -   **理由：** チェックポイントの commit は別々の手順が作るので、commit ごとに見分ける行を書かせると、それらの手順のすべてに手が入るためである（0098 設計書 1.2 の決定 3）。タスク文書の PR の CHECKS の直しも、`/runplan` の green gate の直しと同じく印で扱う。commit のデータだけでは CHECKS の直しをほかの commit と見分けられないためである（0114 要件定義書の F-002）。
    -   **使う入口：** `/runplan` のチェックポイントの入口（green gate より前）に加え、タスク文書の PR でも、同じ入口を Part B step 2（CHECKS）の前に走らせて印を残す。入口は、記録が有効でなければ見直してから印を残すので、印を残せないまま CHECKS の直しが記録を無効にすることがない（[0114 設計書](../../tasks/0114_fable_record_after_merge/02_architecture.md) 1.2 の決定 4）。
    -   **例外：** 印より後に phase group の実装の記録があるときは、その印を使わない。印の後の merge commit も、merge の後の確認の記録がない限り記録を無効にする。
    -   **受け入れる危険：** やり直しの前などに、人やほかのセッションが印の後に手で足した commit は、部分レビューが見ない。この危険は、`/runplan` のチェックポイントでもタスク文書の PR でも同じく受け入れる（0098 設計書 1.2 の決定 3、0114 要件定義書の F-002）。
-   **push の直前にもう一度判定する：** 記録が有効かを、起動とチェックポイントの入口に加えて、push の直前（`_lib/task-pr-handoff.md` Part B の CHECKS の後）にも判定する。有効でなければ、足りない commit について部分レビューを単独で行ってから push する。push するのは判定した commit である。入口でしか判定しないと、その後、push までにできた commit を誰も見ないまま PR が開くためである（PR #987 で merge commit について起きた。0114 要件定義書の F-001）。
-   **merge commit に対する merge の後の確認：** 記録の後の merge commit は、ハーネスの `high` 役割のモデル（Claude Code では Opus、Antigravity では `swarm` で固定した `high` 役割モデル。[ADR-0042](0042-implementation-model-tiers.md)）のサブエージェント／ワーカーが、merge で手で解いた箇所（衝突の解決）と、`main` から入った ADR・先行のタスク文書・コマンドの定義の変更を PR の文書やコードが参照している箇所だけを確かめる（merge の後の確認）。確認の記録がある merge commit だけが、部分レビューの記録を無効にしない。
    -   **理由：** merge で新しく見るべきものは、merge commit 自身の変更と、`main` で変わった文書との整合だけで、PR のほかの箇所は部分レビューの記録がすでに見ているためである。範囲が決まった確認なので `high` 役割モデルで足り、部分レビュー 1 回分より費用が小さい。確認は、衝突を解いたセッション自身ではなく、別のサブエージェント／ワーカーにさせる。これは部分レビューの代わりではなく、merge commit だけを受け持つ別のレビューである（0114 要件定義書の F-002、F-005、0120 要件定義書の F-005）。
    -   **確認の単位と時点：** 確認は merge commit 1 つにつき 1 回行い、その merge commit だけを名指しした記録を残す。数え方が単純になるためである（0114 設計書 1.2 の決定 7）。push の直前に加えて、チェックポイントの入口でも行う。`/runplan` のチェックポイントの入口は上位モデルのレビューより前に走るので、確認の直しが上位モデルのレビューの範囲に入り、上位モデルのレビューが 2 回走らずに済むためである（同 1.2 の決定 1）。
    -   **確認できない merge commit は部分レビューに回す：** 確かめるのは、確認できる merge commit（親が 2 つで、第 1 親がブランチ側、第 2 親が `origin/main` にあるもの）だけとする。ほかの merge commit（親が 3 つ以上のもの、`main` の側で merge したものなど）と、範囲を求める git が失敗した merge commit は、部分レビューが PR の全体を見る。ほかの形では手で解いた箇所と `main` から入った変更を正しく求められず、誰も merge を見ないまま確認済みに数えることになるためである。止めないのは、止まった後の再開の手段がないためである（0114 要件定義書「要件定義の際に決めたこと」の「確かめられない merge commit」、0114 設計書 1.2 の決定 12）。
    -   **確認が走らないとき：** `high` 役割モデルを呼べない、エラー、利用上限などのときは、部分レビューと同じく止めずに `not run` と記録して進む。
    -   **部分レビューを走らせ直す範囲：** 記録の後に merge commit 以外の中身のある commit があって部分レビューを走らせ直すときは、範囲に merge commit があれば、PR の全体（新しい merge-base から HEAD まで）を見る。merge の前の記録から範囲を決めると、`main` 側の変更が範囲に入り、指摘が捨てられるノイズになるためである。merge の前の merge-base を START に持つ記録は、merge の後も記録として読む。
-   **有効かは、判定のスクリプトが決める：** 部分レビューの記録が有効かどうか（PR を開いてよいか）は、`origin/main` から取り出す判定のスクリプト `.claude/commands/_lib/review-records.sh` が決め、失敗したときは「有効でない」とする。誤って有効と判定すると部分レビューを飛ばして PR が開かれるので、レビューを受ける側のセッションの解釈に任せないためである（0098 設計書 1.2 の決定 10）。

### 6. サブエージェント／ワーカーを指示で縛り、状態を比べて書き込みを見つける

-   **選んだもの：** クロスチェックのサブエージェント／ワーカーには、作業ツリーとリポジトリの状態を変えないこと、push・GitHub への書き込み・ほかの pane への入力をしないこと、ネットワークや本物のサービスを使わないこと、秘密のファイルを読まないことを指示で求める。セッションは、起動の前と、終えるすべての出口で、この worktree の状態（git が無視する `.claude/`・`.agents/` 配下や `CLAUDE.md`・`AGENTS.md`・`GEMINI.md` 等の指示ファイルを含む。[ADR-0055](0055-harness-independent-commands.md)）を比べ、変わっていれば結果を使わずにコマンドを止める。出口の後も、commit を作るたびにその直前に比べる。比べる状態の一覧は共有手順の「The state check」にある。
-   **理由：** レビューに使えるサブエージェントや `swarm` ワーカーはコマンド実行機能を持ち、種類の選び方では書き込みを防げないためである。止めるのは、変わった状態の上では、並列のローカルの CLI レビューの結果とこれから作る commit を信頼できないためである。並列のローカルの CLI レビューは、作業ツリーが変わると止まる（0098 要件定義書の F-001）。
-   **比べないもの：** ほかの worktree と共有する ref・stash・worktree の一覧は比べない。ほかのセッションの作業によって部分レビューの実行中にも変わり、ほとんど毎回止まるためで、`codexreview` が比べるものを絞ったのと同じ理由である。基準のハッシュはセッションの文脈に持つ。スクラッチパッドをサブエージェントやワーカーも書けるためである。
-   **受け入れる危険：** ネットワークと秘密のファイルについては、Claude Code では道具で制限する手段がなく指示で求めるだけになる（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 5・20）。

### 7. 役割名に基づく記録と新旧両読み、共有の手順への配置

-   **記録と新旧両読み：** 部分レビューの実施と、指摘の却下・`deferred`・`unclear`、およびすべての指摘の明細と費用を、コミットメッセージの決まった形の行と PR の説明に記録する。新しく書く記録行（実施・未実施・範囲・指摘・チェックポイント）の接頭辞、モデル不一致の理由コード、PR の説明の見出しはモデル固有名（`Fable`・`not-fable`）を含まない役割名に基づく形にする。`review-records.sh` と PR の説明・`/runpr` の読み取りは、`_context.md` が認めるすべてのクロスチェックモデルの ID と、新旧両方の記録行・理由コードを同じ意味で読む。
    -   **理由：** 1 つの PR が複数のセッションやハーネスにまたがっても記録がブランチと一緒に残り、効果を後から測れるようにするためである。あわせて、既存のブランチや過去のコミットとの互換性を保ち、別ハーネスのモデルで走った記録に `Fable` の名前が残らないようにする（0098 要件定義書、0120 要件定義書の F-005）。記録の分類と集計は [#936](https://github.com/isseis/yt2column/issues/936) で扱う。
    -   **マージの質問：** `/runpr` のマージの質問の要約に、PR を開いた後の変更をローカルの CLI レビューが見たかと、部分レビューの記録を 1 行で示す。人が PR レビューを追加で頼むかを決める材料にするためである。部分レビューは PR を開く前のものなので、PR を開いた後の変更は見ていないと分かる形で示す（0098 要件定義書の F-006、F-008）。
-   **手順の置き場所：** 部分レビューの共通規則は 1 つの共有手順に置き、起動・モデル検証・タイムアウト・停止だけをハーネスのアダプタへ委譲し、ローカルの CLI レビューの手順（`_lib/local-cli-review.md`）から最初の試行と並列に起動して最初の試行のトリアージで結果をまとめる。まとめたトリアージと 2 回目の試行の条件はローカルの CLI レビューの手順にしか置けず、有効かの判定の規則の正本と記録の行の定義も 1 か所に保つためである（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 1、[0114 設計書](../../tasks/0114_fable_record_after_merge/02_architecture.md) 1.2 の決定 3、0120 要件定義書の F-005）。

## 採らなかった案

### いつ・何を見せるか（決定 1・2）

-   **PR を作った後のレビュー：** PR を作った後に部分レビューを行う（これまでの手作業の形）。人のレビューが始まった後に修正が入る（0098 要件定義書の「issue #924 で決めたこと」）。
-   **`/mkplan2` の除外：** `/mkplan2` を対象から外す。共有の手順に例外が要り、`/mkplan2` が人に問わずに決めたことが見られない（0098 要件定義書「要件定義の際に決めたこと（2026-11-17）」）。
-   **上位モデルのレビューとの排他：** `/runplan` では、上位モデルのレビューが走る PR で部分レビューを走らせない。信頼の境界と技術的な主張は、上位モデルのレビューのチェックリストの役目と違う（同上）。
-   **`/runplan` での字面どおりの照合：** `/runplan` で、先行文書との照合を字面どおりに当てはめる。実装の全体が毎回範囲に入る（同上）。
-   **文書ごとの実行：** 3 文書の PR で、文書ごとに 3 回走らせる。費用が 3 倍になる（同上）。
-   **外した箇所の扱いの別案：** 外した箇所を PR の説明に残すだけにする、または範囲を別のサブエージェントに選ばせる。前者は、人が PR の説明を読むまで盲点に気づけない。後者は、サブエージェントが 1 つ増え、その選び方を確かめる者がいない（同上）。

### 指摘の扱い（決定 3）

-   **部分レビューの指摘だけへの却下の規則：** 部分レビューの指摘だけに、却下の根拠を確かめる規則を当てはめる。同じトリアージの中で却下の基準が 2 つになり、ローカルの CLI レビューの指摘の誤った却下を防げない（0098 要件定義書「要件定義の際に決めたこと（2026-11-17）」）。
-   **却下の規則の `/fixpr` への拡大：** 却下の根拠を確かめる規則を、`/fixpr` の PR のスレッドとセルフレビューの指摘にも広げる。`/fixpr` を変えないという issue の範囲を超える（同上）。
-   **マージの質問での当否：** マージの質問で、人に部分レビューの指摘の当否を尋ねる。人の手間が増える。PR を開いた後の指摘との突き合わせで代える（同上）。

### モデル検証と走らないとき（決定 4）

-   **ほかのモデルでの代替：** 指定されたクロスチェックモデルで走らせられないときに、上位モデルかセッションのモデルで代える。上位モデルのレビューと役目が重なり、記録の意味も曖昧になる（0098 要件定義書「要件定義の際に決めたこと（2026-11-17）」）。
-   **モデルの ID を確かめない案、または Antigravity で本文の自己申告を使う案：** 指定が効いたことが分からず、Antigravity ではサブエージェントがプロンプト中の語をオウム返しして検査を素通りしうる（同上、[0120 要件定義書](../../tasks/0120_harness_independent_commands/01_requirements.md)「issue #1072 で決めたこと」）。
-   **Antigravity で `invoke_subagent`（`Model: "pro"`）を使う案：** `invoke_subagent` は 4 段階の列挙しか持たず、指定した具体的なクロスチェックモデルのプールに固定できない（0120 要件定義書「issue #1072 で決めたこと」）。
-   **Antigravity で `gemini-4-argon-medium` / `high` を選ぶ案：** 136 PR の実運用（7 日間）で延べ 9 回すべて指摘 0 件であり、上位モデルのレビューがない文書 PR でも問題を検出できなかった（[0120 設計書](../../tasks/0120_harness_independent_commands/02_architecture.md) 1.4「実測検証の結果（H-01・H-04）」）。
-   **Antigravity で `gemini-4-carbon-medium` または `gemini-4-neon-xhigh` を選ぶ案：** 実測でどちらも 10 分以内に完了せず（Carbon は小規模パッチでも 3 分超で無応答）、Gemini の割り当て消費も大きかった（同上）。
-   **Antigravity からローカルの Claude Code CLI（`claude -p --model fable`）を本タスク内で直接呼び出す案：** `--restricted`・`--output-format json` の実挙動確認および `BypassSandbox: true` 下の実行境界（固定フラグを強制するラッパーの要否など）の設計が別途要るため（ログイン済み `claude` CLI の利用を前提とし、認証自体の設計は不要）、後続 issue（[#1082](https://github.com/isseis/yt2column/issues/1082)、`#1072` が前提）へ分離した（[0120 設計書](../../tasks/0120_harness_independent_commands/02_architecture.md)「設計の際に決めたこと（2026-11-22）」）。
-   **Antigravity で部分レビューを行わない案、またはメインセッションと別系統モデルの利用を毎回確認・強制する案：** 前者は信頼の境界と暗黙の選択を PR の前に見る層を失い、後者は毎回の確認やモデル選択制約を増やす（0120 要件定義書「要件定義の際に決めたこと（2026-11-21）」）。
-   **OpenCode からの引き継ぎ：** OpenCode で動く `/runplan` では、PR を開く前に Claude Code に引き継いで部分レビューを走らせる。`runplan-takeover` の行の役目を広げることになり、chief の動きが変わる（0098 要件定義書「要件定義の際に決めたこと（2026-11-17）」）。
-   **待つ時間の別案：** 待つ時間の上限を 20 分にする、または上限を設けない。前者は、これまでの最長（16 分）に近い回が時間切れになりうる。後者は応答が返らないときに PR を開けない（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 4）。

### 見た後に足された commit（決定 5）

-   **commit ごとの行：** チェックポイントの commit のそれぞれに、記録を無効にしないことを示す行を書かせる。ブランチのレビューや上位モデルのレビューの手順の中の commit にも手が入る（0098 設計書 1.2 の決定 3）。
-   **除外できる commit の流用：** 記録を無効にしない commit に、除外できる commit（計画書だけを変える commit のすべて）を使う。計画書の中身を変える commit を見ないまま PR が開きうる（0098 設計書 1.2 の決定 11）。
-   **セッションによる判定：** 記録が有効かを、セッションが手順の文に従って判定する。誤って有効と判定する危険な側の誤りが残る（0098 設計書 1.2 の決定 10）。
-   **CHECKS の直しのたびに走らせ直す案（印を使わない案）：** タスク文書の PR の CHECKS の直しにも、部分レビューを走らせ直す。CHECKS の直しのたびに 1 回分の費用がかかる（[0114 要件定義書](../../tasks/0114_fable_record_after_merge/01_requirements.md)「要件定義の際に決めたこと（2026-11-19）」）。
-   **止めて人に問う案：** push の直前の判定で記録が有効でなければ、自動では走らせずに止め、人に問う。人の手間が増え、人が選べるのは走らせることだけである（同上）。
-   **merge の前の記録から範囲を決める案：** merge の後の範囲を、今のまま merge の前の記録から決める。記録の START によっては、範囲に merge で入った `main` 側の変更が入り、指摘が捨てられるノイズになる（同上）。
-   **merge の後に PR の全体を見直す案：** 記録の後の merge commit で部分レビューを走らせ直し、PR の全体を見せる。費用の大部分が、すでに見た箇所の読み直しになる（同上）。
-   **merge に関わる箇所に絞って部分レビューを走らせ直す案：** 判定のスクリプトは変えずに済むが、費用は 1 回分かかる（同上）。
-   **merge commit を記録を無効にしない commit に数え、Codex の PR レビューに任せる案：** PR #987 の穴が残る（同上）。
-   **先に `main` を取り込む案：** 部分レビューの前に `main` を取り込む手順を足し、記録の後の merge を減らす。merge の要る理由（衝突など）は記録の後にも起こりうるので、減らしても、記録の後の merge の扱いは別に要る（同上）。
-   **どの merge commit も確認に回す案：** 親が 3 つ以上の merge commit なども merge の後の確認に回し、範囲を求める git の失敗は `not run` と記録して進む。手で入れた変更を誰も見ないまま、merge commit が確認済みに数えられる（0114 要件定義書「要件定義の際に決めたこと」）。
-   **merge の後の確認を push の直前だけで行う案：** チェックポイントの入口では確認せず、push の直前だけで確認する。`/runplan` で確認が直しを作ると、上位モデルのレビューの判断をやり直し、PR の全体に上位モデルのレビューがもう 1 回走りうる（[0114 設計書](../../tasks/0114_fable_record_after_merge/02_architecture.md) 1.2 の決定 1）。
-   **1 回の確認で複数の merge commit を見る案：** 記録の後の merge commit をまとめて 1 回で確かめる。記録の行に merge commit の一覧を持たせることになり、読み方が増える（0114 設計書 1.2 の決定 7）。

### 書き込みの防ぎ方（決定 6）

-   **読み取り専用のサブエージェント：** 読み取りの道具だけを持つ種類のサブエージェントで呼び、書き込みを防ぐ。Claude Code ではレビューに使える種類はどれも Bash を持ち、Bash を持たない種類は git を読むことも実験もできない（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 5）。
-   **共有の状態の比較：** ほかの worktree と共有する ref・stash・worktree の一覧も比べる。ほかのセッションの作業によって部分レビューの実行中にもほとんど毎回変わり、止まる（0098 設計書 1.2 の決定 20）。

### 記録と置き場所（決定 7）

-   **記録行の接頭辞を `Fable review:` のまま固定する案：** Antigravity のクロスチェックモデルで走った記録にも `Fable` の名前が残り続ける（[0120 要件定義書](../../tasks/0120_harness_independent_commands/01_requirements.md)「要件定義の際に決めたこと（2026-11-21）」）。
-   **一部の指摘だけの記録：** 却下・`deferred`・`unclear` の指摘だけを記録する。当たった指摘が分からず、効果を測れない（0098 要件定義書「要件定義の際に決めたこと（2026-11-17）」）。
-   **部分レビューの手順を親にする案：** 部分レビューの手順を親の手順とし、そこからローカルの CLI レビューの手順を呼ぶ。まとめたトリアージと 2 回目の試行の規則が 2 つのファイルにまたがる（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 1）。
-   **merge の後の確認を別のファイルに置く案：** 確認の手順を新しい `_lib/merge-check.md` に置く。共有する部品への参照が 2 つのファイルにまたがり、記録の行の表も 2 か所に分かれる（[0114 設計書](../../tasks/0114_fable_record_after_merge/02_architecture.md) 1.2 の決定 3）。

## 結果

-   **PR を開くまでの時間：** クロスチェックの部分レビューとローカルの CLI レビューのうち、長い方の分だけ延びる。
-   **記録の後に `origin/main` を merge した PR：** merge の後の確認（`high` 役割モデルでの 1 回）と、その直しの確かめ、CHECKS の走り直し、`/runplan` では上位モデルのレビューの判断のやり直しの分だけ、PR を開くまでの時間が延びる。記録の後に merge commit 以外の中身のある commit もあれば、部分レビューが PR の全体を見る 1 回分が加わる。
-   **merge の後の確認が見ないもの：** 範囲の外にある merge の意味の衝突（コードの振る舞いの食い違い）は見ない。それは CHECKS だけに任せる。この危険は受け入れる（[0118 要件定義書](../../tasks/0118_codex_removal/01_requirements.md)「要件定義の際に決めたこと（2026-11-20）」）。確認が `not run` のとき（OpenCode で動く `/runplan` では、いつも）は、merge を PR の前に見るのは CHECKS だけである。
-   **Antigravity での Claude 割り当て枠の消費とモデル系統の重なり：** Antigravity 組み込みの `claude-opus-5-5-medium` は週次リセットの Claude 枠を 1 PR あたり数 % 消費するため、枠が尽きたときは `not run`（`unavailable`）として PR を止めずに進む。また、通常のメインセッション（Gemini 4 Neon）とは異系統になる一方、メインセッションのモデルの ID をセッション側から検証できないため、利用者が手動で Claude 系をメインセッションに選んだ場合は同系統または同一モデルになりうる。別ワーカーの独立した文脈での検証と CodeRabbit CLI のレビューがあることを踏まえ、この危険を受け入れる（[0120 要件定義書](../../tasks/0120_harness_independent_commands/01_requirements.md)「要件定義の決定変更（2026-11-22）」）。
-   **OpenCode：** `low`（旧 `sonnet`）の PR を OpenCode で実装すると、部分レビューは走らない。
-   **却下の手間と両読み保守：** トリアージの却下には確かめた方法と結果が要り、判定のスクリプトと読み取り手順は新旧 2 系統の記録行を扱う。
-   **出力の扱い：** 部分レビューの出力の文は、コミットメッセージにも PR の説明にも写さない。出力は、差分にある秘密やメンションを引用しうるためである。指摘は、場所とセッション自身の要約で記録する。
-   **マージの質問：** `/runpr` のマージの質問の要約は、部分レビューの記録を読む。マージの質問の形は [ADR-0047](0047-runpr-merge-question.md) が決める。
