# ADR-0050: タスクの PR を開く前に Fable の部分レビューを範囲を絞って行い、走らないときは止めずに記録する

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

タスクの PR は、開く前に、サブエージェントのセルフレビューとローカルの CLI レビューを受け、開いたときに Codex の PR レビューを 1 回だけ受ける（[ADR-0013](0013-review-setup.md)）。PR を開いた後に見つかった問題を直すと、その修正は Codex の PR レビューに見られない。

PR を作った後に Fable のサブエージェントのレビューを手作業で頼んだ 7 件では、6 件で、マージの前に直すべき Major 級の問題が見つかった。Codex の最初の PR レビューが指摘 0 件を返した PR もあった。成果が大きかったのは、範囲を絞って役目を狭めた回と、文書の PR である。承認済みの設計を写した実装では、効果が薄かった。弱点は受け取る側のトリアージで、正しい指摘を誤って却下した。その 1 件は、ローカルの CLI レビューの指摘を誤って却下したものと同じだった（[0098 要件定義書](../../tasks/0098_fable_partial_review/01_requirements.md) §1）。

Fable は、Claude Code の Agent ツールで選べるモデルの 1 つで、OpenCode からは呼べない。

## 決定

以下の決定の仕様は、[0098 要件定義書](../../tasks/0098_fable_partial_review/01_requirements.md) の機能要件が持つ。記録の後、push の前にできた commit の扱いは、[0114 要件定義書](../../tasks/0114_fable_record_after_merge/01_requirements.md) の F-001 と F-002 が持つ。

-   **PR を開く前のレビュー：** タスクの PR を開くコマンド（`/mkreq`・`/mkarch`・`/mkplan`・`/mkplan2`・`/runplan`）は、PR を開く前に、Fable の部分レビューを 1 つの PR につき 1 回行う。ローカルの CLI レビューと並列に走らせる。PR を開く前に直せば、Codex の最初の PR レビューが修正を見るためである。`/runplan` で phase group ごとに走らせないのは、費用が phase group の数だけ増えるためである。`/mkplan2` を含めるのは、PR の境界などを人に問わずに決めるためであり、共有の手順に置けば例外が要らないためでもある（F-001）。
-   **範囲：** 範囲は、信頼の境界・先行文書との照合・外部の振る舞いについての技術的な主張・人に問わずに決めたこと、の 4 つの基準に当たる箇所に限る。当たる箇所がないと書き手が判断したときは、除外の一覧だけを Fable に確かめさせ、Fable も見つけなければ `not run` と記録する。範囲を絞った回の成果が大きかったためである。`/runplan` では、先行文書との照合を、文書の決めていない点・文書を解釈した点・文書と違えた点に限る。実装の PR には必ず先行文書があり、設計を写した実装では効果が薄かったためである。3 文書の PR では、3 文書をまとめて 1 回行い、3 文書どうしの食い違いを照合に含める（F-002）。
-   **範囲から外した箇所：** 範囲から外した箇所とその理由を Fable に渡し、外した箇所が基準に当たると Fable が見たら、その箇所もレビューさせ、外した判断の誤りを指摘として返させる。どの基準にも当たる箇所がないと書き手が判断したときも、Fable に除外の一覧だけを確かめさせる。外した箇所は PR の説明にも残す。書き手のセッションが自分の盲点を外さないようにするためである。当たる箇所がないときに Fable を呼ばないと、すべてを外した判断を誰も確かめない（F-002、F-003）。
-   **既出の指摘：** Fable には、却下した指摘と決着済みの論点を、セッション自身の言葉で渡し、具体的な筋書きがあるときに限って再提起させる。Codex CLI の指摘の本文は渡さない。既出の指摘との重複を避けるためである。本文を渡さないのは、信頼しないテキストの扱い（[ADR-0015](0015-untrusted-review-threads.md)）を変えないためである（F-003）。
-   **トリアージ：** Fable の指摘とローカルの CLI レビューの指摘を 1 回のトリアージにまとめる。このトリアージで却下するときは、該当箇所を読むか実験で根拠を確かめ、確かめた方法と結果を理由として記録する。この規則は、ローカルの CLI レビューの指摘だけのトリアージにも当てはめる。誤った却下が、Fable の指摘とローカルの CLI レビューの指摘の両方で起きたためである。Opus のレビューの指摘は、もともと人に尋ねる（[ADR-0042](0042-implementation-model-tiers.md)）ので対象にしない（F-004）。
-   **直しの確かめ：** Fable の指摘の修正は、ローカルの CLI レビューの 2 回目の試行で確かめ、Fable をもう一度は走らせない。Fable の指摘だけを直したときも、最初の試行がどちらの CLI もレビューしなかったときも、2 回目の試行を行う。修正を確かめずに push しないためであり、費用を 1 回分に抑えるためでもある（F-004）。
-   **サブエージェントがしないこと：** Fable のサブエージェントは、作業ツリー・index・HEAD・ref を変えず、push・GitHub への書き込み・ほかの pane への入力もせず、実験は作業ツリーの外で行う。並列に走るローカルの CLI レビューは、作業ツリーが変わると止まるためである（F-001）。
-   **記録の後の commit：** Fable が見た範囲の後に commit が足され、その中に、記録を無効にしない commit のどれにも当たらないものがあるときは、その commit について Fable の部分レビューをもう一度行う。ただし、そのような commit が merge commit だけのときは、Fable ではなく merge の後の確認を行う（「merge commit の扱い」）。Fable が PR の実装の全体を見ていないまま PR を開かないためである。記録を無効にしない commit は、中身のない commit（空の commit、`README.en.md` だけを変える commit、計画書の PR の進み具合のチェックボックスの行だけを変える commit）、同じ実行の直しの commit、PR のチェックポイントの実行が PR を作るまでに作った commit（green gate の直し、Opus のレビューの直しなど）、タスク文書の PR で Part B step 2（CHECKS）の前に残す印の後の commit である。直しの commit で記録を無効にしないのは、Fable と Opus のレビューが互いの直しのたびに繰り返されないようにするためである。タスク文書の PR の CHECKS の直しも、`/runplan` の green gate の直しと同じく印で扱う。commit のデータだけでは CHECKS の直しをほかの commit と見分けられないためである。印の後に人やほかのセッションが手で足した commit は Fable がレビューしないが、この危険は `/runplan` のチェックポイントと同じく受け入れる（0098 要件定義書 F-001、0114 要件定義書 F-002）。
-   **push の直前の判定：** タスクの PR は、記録が有効かを、起動とチェックポイントの入口に加えて push の直前（`_lib/task-pr-handoff.md` Part B の CHECKS の後）にも判定し、有効でなければ、足りない commit について Fable の部分レビューを単独で行ってから push する。入口でしか判定しないと、その後、push までにできた commit（PR #987 では merge commit）を、Fable も merge の後の確認も見ないまま PR が開くためである（PR #987 で起きた。0114 要件定義書 F-001）。push するのは判定した commit である。判定が、記録を無効にしているのが未確認の merge commit だけだと示したときは、push の直前に加えて、チェックポイントの入口でも merge の後の確認を行う。`/runplan` のチェックポイントの入口は Opus のレビューより前に走るので、確認の直しが Opus のレビューの範囲に入り、Opus のレビューが 2 回走らずに済むためである（[0114 設計書](../../tasks/0114_fable_record_after_merge/02_architecture.md) 1.2 の決定 1）。
-   **merge commit の扱い：** 記録の後の merge commit は、Fable を走らせ直さず、Opus のサブエージェントが確かめる（merge の後の確認）。範囲は、merge で手で解いた箇所（衝突の解決）と、merge で `main` から入った ADR・先行のタスク文書・コマンドの定義の変更を、PR の文書やコードが参照している箇所に限る。merge の前の merge-base を START に持つ Fable の記録も、merge の後に記録として読む。確認は merge commit 1 つにつき 1 回行い、その merge commit だけを名指しした記録を残す。その記録がある merge commit だけが Fable の記録を無効にしない。1 つの記録が 1 つの merge commit だけを名指しすれば、数え方が単純になるためである（0114 設計書 1.2 の決定 7）。確認が走らない（Opus を呼べない、エラー、利用上限など）ときは、止めずに `not run` と記録して進む。記録の後に merge commit 以外の中身のある commit があって Fable を走らせ直すときは、範囲に merge commit があれば、Fable は PR の全体（新しい merge-base から HEAD まで）を見る。merge で新しく見るべきものは、merge commit 自身の変更と、`main` で変わった文書との整合だけで、PR のほかの箇所は Fable の記録がすでに見ているためである。範囲が決まった確認なので Opus で足り、Fable の 1 回分より費用が小さい。確認は、衝突を解いたセッション自身ではなく、別のサブエージェントにさせる。これは Fable の代わりではなく、merge commit だけを受け持つ別のレビューなので、Fable を Opus で代える案（採らなかった案）とは別である（0114 要件定義書 F-002、F-005）。
-   **計画書を変える commit：** 中身のない commit に、計画書のほかの行を変える commit は含めない（`_lib/opus-review.md` の除外できる commit は使わない）。印の後の commit は、計画書を変えるものも含めて、印の規則（「記録の後の commit」）による。タスク文書の PR では計画書そのものがレビューされる中身であり、実装の PR でも実装モデル要件や自動送信の値は中身なので、記録の後にそれを変える commit を無視すると、Fable が見ないまま PR が開くためである（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 11）。
-   **行わないとき：** Fable の部分レビューを行わないとき（基準に当たる箇所がなく、除外の一覧を確かめた Fable も見つけなかった、エラーや利用上限、走ったモデルが Fable でない、エージェントが Fable を呼べない）は、止めずに `not run` とその理由を記録して進む。ほかのモデルで代えない。Fable で走ったかは、サブエージェントが報告するモデル ID で確かめる。Fable は追加のレビューであり、使えないことで PR を止めないためである。代えないのは、Fable で走ったつもりの記録を残さないためである。OpenCode で動く `/runplan` も `not run` とするのは、chief の送り先（[ADR-0046](0046-chief-of-staff.md)）を変えないためである（F-005）。
-   **記録：** Fable の部分レビューの実施と、指摘の却下・`deferred`・`unclear` を、コミットメッセージの決まった形の行と PR の説明に記録する。既存の記録の行の読み方は変えない。効果を後から測れるように、指摘のすべて（直した指摘を含む）について、場所・範囲に入れた基準・ファイルの種類・重大度・ローカルの CLI レビューが同じ問題を挙げたか・扱いを、1 回ごとの費用とともに、PR の説明に決まった形で残す。`/runpr` のマージの質問の要約には、Codex が見ていない変更をローカルの CLI レビューが見たかと、その PR の Fable の部分レビューの記録を 1 行で示す。Fable の部分レビューは PR を開く前のものなので、PR を開いた後の変更は見ていないと分かる形で示す。1 つの PR が複数のセッションにまたがっても、記録がブランチと一緒に残るためである。指摘のすべてを残すのは、範囲の基準やレビューさせるファイルの種類を見直すには、どこでほかが見つけなかった指摘が出たかが要るためである。その記録を PR の説明に置くのは、squash でマージしてブランチを消すと、ブランチのコミットメッセージは後から集めにくいためである。記録の分類と集計は [#936](https://github.com/isseis/yt2column/issues/936) で扱う。要約に示すのは、人が PR レビューを追加で頼むかを決める材料にするためである（F-006、F-008）。
-   **手順の置き場所：** Fable の部分レビューの規則は共通の手順 `_lib/fable-review.md` に置き、ローカルの CLI レビューの手順（`_lib/local-cli-review.md`）に任意の入力 FABLE を足して、最初の試行と並列に起動し、最初の試行のトリアージで結果をまとめる。まとめたトリアージと 2 回目の試行の条件はローカルの CLI レビューの手順にしか置けず、Fable の手順をその外側に置くと規則が 2 つのファイルにまたがるためである（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 1）。push の直前の入口と merge の後の確認も `_lib/fable-review.md` に置き、状態の確かめ・出力の確かめ・トリアージ・記録の commit の部品を Fable の部分レビューと共有する。有効かの判定の規則の正本もこのファイルにあり、別のファイルに置くと、共有する部品と記録の行の表が 2 か所に分かれるためである（0114 設計書 1.2 の決定 3）。
-   **`/runplan` のチェックポイント：** `/runplan` のチェックポイントでは、その入口（green gate より前）で Fable の記録が有効かを判定し、有効なら空の commit にチェックポイントの印を残す。印より後の commit は、チェックポイントの実行が作った commit として記録を無効にしない。ただし、印より後に phase group の実装の記録があるときは、その印を使わない。印より後の merge commit も、merge の後の確認の記録がない限り記録を無効にし、push の直前の判定で見つかる（「push の直前の判定」と「merge commit の扱い」）。タスク文書の PR の印も、同じチェックポイントの入口を Part B step 2（CHECKS）の前に走らせて残す。入口が、記録が有効でなければ救済してから印を残すので、印を残せないまま CHECKS の直しが記録を無効にすることがないためである（0114 設計書 1.2 の決定 4）。チェックポイントの commit は別々の手順が作るので、commit ごとに見分ける行を書かせると、それらの手順のすべてに手が入るためである。やり直しの前に人やほかのセッションが印の後に足した commit は Fable がレビューしないが、この危険は受け入れる（同 1.2 の決定 3）。
-   **待つ時間：** Fable の結果を待つのは 30 分までとし、超えたら `not run`（時間切れ）とする。呼び出しが失敗したときの呼び直しは 1 回とする。上限がないと、Fable が返らないときに PR を開けないためである。30 分は、これまでの実績の最長（16 分）のおよそ 2 倍である（同 1.2 の決定 4）。
-   **状態の確かめ：** Fable のサブエージェントには、作業ツリーとリポジトリの状態を変えないこと、ネットワークや本物のサービスを使わないこと、秘密のファイルを読まないことを指示で求める。セッションは、Fable の部分レビューを起動する前と、終えるすべての出口（結果が返ったとき・時間切れ・エラー・呼び直しの前）で、この worktree の状態（作業ツリー、HEAD とそのブランチ、フラグの付いた index のパス、ほかのブランチの `branch.*` を除いた設定、info、hooks、`fixprguard` の監視の一覧に当たる無視されるファイルと `.claude/settings.local.json`）を比べ、変わっていれば結果を使わずにコマンドを止める。出口の後も、セッションが commit を作るたびに、その直前に、セッション自身が変えるはずのない状態（index のフラグ、設定、info、hooks、`.claude/settings.local.json` を除く監視するファイル）を比べる。基準はハッシュでセッションの文脈に持つ。ほかの worktree と共有する ref・stash・worktree の一覧は比べない。レビューに使えるサブエージェントの種類はどれも Bash を持ち、種類の選び方では書き込みを防げないためである。止めるのは、変わった状態の上では、並列のローカルの CLI レビューの結果とこれから作る commit を信頼できないためである。共有の状態を比べないのは、ほかのセッションの作業で Fable が走る間にも変わり、ほとんど毎回止まるためで、`codexreview` が比べるものを絞ったのと同じ理由である。基準を文脈に持つのは、スクラッチパッドをサブエージェントも書けるためである。ネットワークと秘密のファイルについては、道具で制限する手段がなく、指示で求めるだけになる。この危険は受け入れる（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 5・20）。
-   **有効かの判定：** Fable の記録が有効かどうか（PR を開いてよいか）は、`origin/main` から取り出す判定のスクリプト `.claude/commands/_lib/review-records.sh` が決め、失敗したときは「有効でない」とする。誤って有効と判定すると、Fable を飛ばして PR が開かれてしまうので、レビューを受ける側のセッションの解釈に任せないためである（同 1.2 の決定 10）。

上の「記録の後の commit」（タスク文書の PR の印）・「push の直前の判定」・「merge commit の扱い」（merge の後の確認と、Fable を走らせ直す範囲）は、まだ手順と判定のスクリプトに入っていない。今の手順は、有効かを起動とチェックポイントの入口でしか判定せず、merge の後の確認を持たない。タスク文書の PR は、チェックポイントの入口を走らせない。判定のスクリプトは、タスク文書の PR の CHECKS の直しで記録を無効にし、merge commit をいつも記録を無効にする commit とし、merge で merge-base が動くと START が古い merge-base の記録を無視し、merge の後の START を記録によって merge commit の第 1 親にする。この差分は [#988](https://github.com/isseis/yt2column/issues/988) の実装で解消する。

## 採らなかった案

-   **PR を作った後のレビュー：** PR を作った後に Fable のレビューを行う（これまでの手作業の形）。修正が Codex の PR レビューに見られない（0098 要件定義書の「issue #924 で決めたこと」）。
-   **ほかのモデルでの代替：** Fable で走らせられないときに、Opus かセッションのモデルで代える。Opus のレビューと役目が重なり、記録の意味も曖昧になる（0098 要件定義書「要件定義の際に決めたこと（2026-11-17）」）。
-   **モデル ID を確かめない案：** モデル ID を確かめない。Agent ツールの `model` の指定が効いたことが分からない（同上）。
-   **Fable の指摘だけへの却下の規則：** Fable の指摘だけに、却下の根拠を確かめる規則を当てはめる。同じトリアージの中で却下の基準が 2 つになり、ローカルの CLI レビューの指摘の誤った却下を防げない（同上）。
-   **却下の規則の `/fixpr` への拡大：** 却下の根拠を確かめる規則を、`/fixpr` の PR のスレッドとセルフレビューの指摘にも広げる。`/fixpr` を変えないという issue の範囲を超える（同上）。
-   **`/mkplan2` の除外：** `/mkplan2` を対象から外す。共有の手順に例外が要り、`/mkplan2` が人に問わずに決めたことが見られない（同上）。
-   **OpenCode からの引き継ぎ：** OpenCode で動く `/runplan` では、PR を開く前に Claude Code に引き継いで Fable を走らせる。`runplan-takeover` の行の役目を広げることになり、chief の動きが変わる（同上）。
-   **外した箇所の扱いの別案：** 外した箇所を PR の説明に残すだけにする、または範囲を別のサブエージェントに選ばせる。前者は、人が PR の説明を読むまで盲点に気づけない。後者は、サブエージェントが 1 つ増え、その選び方を確かめる者がいない（同上）。
-   **Opus のレビューとの排他：** `/runplan` では、Opus のレビューが走る PR で Fable を走らせない。信頼の境界と技術的な主張は、Opus のレビューのチェックリストの役目と違う（同上）。
-   **`/runplan` での字面どおりの照合：** `/runplan` で、先行文書との照合を字面どおりに当てはめる。実装の全体が毎回範囲に入る（同上）。
-   **文書ごとの実行：** 3 文書の PR で、文書ごとに 3 回走らせる。費用が 3 倍になる（同上）。
-   **一部の指摘だけの記録：** 却下・`deferred`・`unclear` の指摘だけを記録する。当たった指摘が分からず、効果を測れない（同上）。
-   **マージの質問での当否：** マージの質問で、人に Fable の指摘の当否を尋ねる。人の手間が増える。PR を開いた後の指摘との突き合わせで代える（同上）。
-   **Fable の手順を親にする案：** Fable の手順を親の手順とし、そこからローカルの CLI レビューの手順を呼ぶ。まとめたトリアージと 2 回目の試行の規則が 2 つのファイルにまたがる（[0098 設計書](../../tasks/0098_fable_partial_review/02_architecture.md) 1.2 の決定 1）。
-   **commit ごとの行：** チェックポイントの commit のそれぞれに、Fable の記録を無効にしないことを示す行を書かせる。ブランチのレビューや Opus のレビューの手順の中の commit にも手が入る（同 1.2 の決定 3）。
-   **待つ時間の別案：** 待つ時間の上限を 20 分にする、または上限を設けない。前者は、これまでの最長（16 分）に近い回が時間切れになりうる。後者は Fable が返らないときに PR を開けない（同 1.2 の決定 4）。
-   **読み取り専用のサブエージェント：** 読み取りの道具だけを持つ種類のサブエージェントで呼び、書き込みを防ぐ。レビューに使える種類はどれも Bash を持つので防げない。Bash を持たない種類は、git を読むことも実験もできない（同 1.2 の決定 5）。
-   **共有の状態の比較：** ほかの worktree と共有する ref・stash・worktree の一覧も比べる。ほかのセッションの作業で、Fable が走る間にもほとんど毎回変わり、止まる（同 1.2 の決定 20）。
-   **除外できる commit の流用：** Fable の記録を無効にしない commit に、除外できる commit（計画書だけを変える commit のすべて）を使う。計画書の中身を変える commit を Fable が見ないまま PR が開きうる（同 1.2 の決定 11）。
-   **セッションによる判定：** Fable の記録が有効かを、セッションが手順の文に従って判定する。誤って有効と判定する危険な側の誤りが残る（同 1.2 の決定 10）。
-   **CHECKS の直しのたびに走らせ直す案（印を使わない案）：** タスク文書の PR の CHECKS の直しにも、Fable を走らせ直す。CHECKS の直しのたびに、Fable の 1 回分の費用がかかる（[0114 要件定義書](../../tasks/0114_fable_record_after_merge/01_requirements.md)「要件定義の際に決めたこと（2026-11-19）」）。
-   **止めて人に問う案：** push の直前の判定で記録が有効でなければ、Fable を自動では走らせずに止め、人に問う。人の手間が増え、人が選べるのは Fable を走らせることだけである（同上）。
-   **merge の前の記録から範囲を決める案：** merge の後の範囲を、今のまま merge の前の記録から決める。記録の START によっては、範囲に merge で入った `main` 側の変更が入り、Fable の指摘が捨てられるノイズになる（同上）。
-   **merge の後に Fable が PR の全体を見直す案：** 記録の後の merge commit で Fable を走らせ直し、PR の全体を見せる。費用の大部分が、すでに見た箇所の読み直しになる（0114 要件定義書「要件定義の際に決めたこと（2026-11-19）」）。
-   **Fable を merge に関わる箇所に絞って走らせ直す案：** 判定のスクリプトは変えずに済むが、費用は Fable の 1 回分かかる（同上）。
-   **merge commit を記録を無効にしない commit に数え、Codex の PR レビューに任せる案：** PR #987 の穴が残る（同上）。
-   **merge の後の確認を push の直前だけで行う案：** チェックポイントの入口では確認せず、push の直前だけで確認する。`/runplan` で確認が直しを作ると、Opus のレビューの判断をやり直し、PR の全体に Opus のレビューがもう 1 回走りうる（[0114 設計書](../../tasks/0114_fable_record_after_merge/02_architecture.md) 1.2 の決定 1）。
-   **merge の後の確認を別のファイルに置く案：** 確認の手順を新しい `_lib/merge-check.md` に置く。共有する部品への参照が 2 つのファイルにまたがり、記録の行の表も 2 か所に分かれる（同 1.2 の決定 3）。
-   **1 回の確認で複数の merge commit を見る案：** 記録の後の merge commit をまとめて 1 回で確かめる。記録の行に merge commit の一覧を持たせることになり、読み方が増える（同 1.2 の決定 7）。
-   **先に `main` を取り込む案：** Fable の部分レビューの前に `main` を取り込む手順を足し、記録の後の merge を減らす。merge の要る理由（衝突など）は記録の後にも起こりうるので、減らしても、記録の後の merge の扱いは別に要る（同上）。

## 結果

-   タスクの PR を開くまでの時間は、Fable の部分レビューとローカルの CLI レビューのうち長い方の分だけ延びる。Fable の 1 回の費用は、これまでの実績で 2〜16 分、出力 2k〜260k トークンである。
-   記録の後に `origin/main` を merge したタスクの PR は、merge の後の確認（Opus のサブエージェント 1 回）と、その直しの確かめ、CHECKS の走り直し、`/runplan` では Opus のレビューの判断のやり直しの分だけ、PR を開くまでの時間が延びる。記録の後に merge commit 以外の中身のある commit もあれば、Fable が PR の全体を見る 1 回分が加わる。
-   merge の後の確認は、範囲の外にある merge の意味の衝突（コードの振る舞いの食い違い）を見ない。それは CHECKS と Codex の PR レビューに任せる。確認が `not run` のとき（OpenCode で動く `/runplan` では、いつも）は、merge を PR の前に見るのは CHECKS だけである。
-   `sonnet` の PR を OpenCode で実装すると、Fable の部分レビューは走らない。
-   トリアージの却下には、確かめた方法と結果が要る。却下の手間が増える。
-   Fable の出力の文は、コミットメッセージにも PR の説明にも写さない。出力は、差分にある秘密やメンションを引用しうるためである。指摘は、場所とセッション自身の要約で記録する。
-   `/runpr` のマージの質問の要約は、Fable の部分レビューの記録を読む。マージの質問の形は [ADR-0047](0047-runpr-merge-question.md) が決める。
