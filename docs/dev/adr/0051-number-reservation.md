# ADR-0051: タスク番号と ADR 番号は GitHub の上で重複しないように道具で決め、決められなければ止め、ADR 番号の欠番を許す

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

タスクと ADR は、複数のセッションで並行して作られる。セッションは、ローカルの worktree だけでなく、別のクローンで動く cloud のセッション（claude.ai/code）でもある。タスク番号は `/mkreq` が「使用中の最大値 + 1」として計算し、ADR 番号は「`main` とその PR のブランチの最大値の次」として決めている。どちらも、計算してから番号を使うまでの間に排他がない。同じ時点の状態から計算した 2 つのセッションは、同じ番号を取る。ADR-0050 を別の PR が使っていたために、空いている番号を手で確かめ直した例がある（[0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) §1）。

## 決定

-   **タスク番号と ADR 番号は、別のクローンや cloud のセッションの間でも重複しないことを、サーバ側（GitHub）で保証する。** ローカルのロックやファイルは、別のクローンからは見えないためである。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の F-001・F-002 にある。
-   **番号ごとに 1 つの tag を GitHub の REST で作り、作れた番号だけを使う。** 名前はタスク番号なら `refs/tags/task-number/NNNN`、ADR 番号なら `refs/tags/adr-number/NNNN` である。作成が失敗したときは、同じ名前の ref がすでにあることを読み直して確かめた場合だけ次の番号を試し、そのほかは止める。同じ名前の ref は GitHub の上で 2 つ作れないので、どのクローンからでも排他が効くためである。また、成否を HTTP の状態コードという宣言された値で判定できる。この方式は、すでにある ref の作成を GitHub が成功として受けないことを前提にし、道具を使い始める前にその前提を確かめる。方式と、使用中の番号の集め方・上限は [0100 設計書](../../tasks/0100_number_reservation/02_architecture.md) の「使用中の番号の集め方」「記録の tag」「候補の番号と上限」にある。
-   **記録の tag は、削除と更新を禁じ、誰も迂回できない tag 用の ruleset で守る。** 記録が消えると番号が使い回されるうえ、エージェントは利用者の資格で `git push` できるので、文書の規則だけでは消すことを止められないためである。ruleset を変える・無効にすることは、利用者の承認を要る。設定と、誤った tag を消す手順は [0100 設計書](../../tasks/0100_number_reservation/02_architecture.md) の「記録の ruleset と記録の tag の名前」にある。
-   **番号を決める道具は Go の `numreserve` とし、[ADR-0014](0014-deterministic-checks-in-go.md) の開発の道具として `main` から入れる。** 判定をテストで壊して確かめるためである。呼び出しの形と止める理由は [0100 設計書](../../tasks/0100_number_reservation/02_architecture.md) の「道具 `numreserve` の呼び出しと出力」と「止める理由」にある。
-   **番号は道具が決め、エージェントは道具が返した番号だけを使う。** 番号の判定が、エージェントの読み違いで変わらないようにするためである。タスク番号と ADR 番号は、互いに影響しない別々の番号の空間に持つ。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の AC-05・AC-15 にある。
-   **番号を決められなければ止め、理由の種類を示す。従来の計算に戻して続けない。** 目的は重複を防ぐことであり、代わりの計算で続けると重複の余地が戻るためである。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の AC-06・AC-14 にある。
-   **一度決めた番号の記録は残し、番号を使い回さない。** 中断したタスクや PR の番号は欠番になる。記録を消すと、同じ番号を再び使う余地が生まれるためである。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の AC-03・AC-11 にある。
-   **ADR 番号の欠番を許し、重複だけを禁じる。** 番号を決めた順とマージの順が違うと、`main` で間の番号が一時的に欠ける。取り下げた PR の番号は欠けたまま残る。欠番を禁じると、そのたびにすべての PR の `TestADRRecords` が失敗するためである。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の F-003 にある。
-   **ADR 番号を決める手順は ADR の規約に書き、コマンドが作る PR にも手で作る PR にも当てはめる。付け替えた後の番号も同じ手順で決める。** ADR はどのコマンドの PR でも作られうるうえ、手で選んだ番号は、ほかの PR が決めてまだマージしていない番号と重なりうるためである。規則の置き場所は [adr.md](../conventions/adr.md) の「Location and naming」と「Taking in `main`」である。
-   **使用中とみなす PR は、このリポジトリの中にヘッドがあるものに限る。** fork の PR のブランチ名はリポジトリの外の人が付けられ、数えると番号を押し上げられるためである。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の AC-02・AC-11 にある。
-   **番号を決める道具の呼び出しは、決まった形で行う限り、利用者に確かめずに実行してよい。** ADR 番号はどの PR でも決めるので、コマンドごとの承認では足りないためである。規則の置き場所は [CLAUDE.md](../../../CLAUDE.md) の「Tool Execution Safety」である。
-   **番号の記録を、道具を介さずに作る・変える・消すことは、利用者の承認を要る。`git push` を承認なしで認める規則の例外とする。** エージェントは利用者の資格で動き、`git push` は承認なしで実行できるので、道具が止まった後に手で記録を作れば重複が戻り、記録を消せば番号が使い回されるためである。規則の置き場所は [CLAUDE.md](../../../CLAUDE.md) の「Tool Execution Safety」である。
-   **次に試す番号が、`main` にある番号と記録の最大値から決めた幅を超えて離れるときは、番号を決めずに止める。** 迷い込んだブランチや打ち間違えたファイル名が 1 つあるだけで、番号が黙って跳び、記録に残って戻せなくなるためである。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の AC-09 にある。
-   **PR が加える番号に記録があることと、`main` とほかのブランチで別のものに使われていないことを、マージの前に `mergepr` で確かめる。この仕組みの導入より前からある番号は、番号の空間ごとのしきい値以下として、記録があるかの確かめから外す。** 古い手順を持つ作業中のブランチが手で選んだ番号は、`numreserve` による予約では見つけられないためである。`mergepr` に置くのは、マージの方法が `/mergepr` と決まっており、マージの直前の最新の `main` と比べられるためである。要件は [0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md) の F-007 に、確かめ方は [0100 設計書](../../tasks/0100_number_reservation/02_architecture.md) の「マージの前の確かめ（`mergepr`）」と「しきい値」にある。
-   **食い違い:** 番号を決める道具 `numreserve`、記録の ruleset、`mergepr` によるマージの前の確かめはまだない。[adr.md](../conventions/adr.md) の「Location and naming」と `TestADRRecords` は欠番を誤りとし、「Taking in `main`」は付け替えの番号を手で選び、「Index」は新しい行を表の末尾に足すとしている。[CLAUDE.md](../../../CLAUDE.md) の「Tool Execution Safety」には、道具の常設の承認も、記録の書き換えの例外もない。[mkreq.md](../../../.claude/commands/mkreq.md) の step 2 は、エージェントが番号を計算し、fork の PR のブランチも数える。どれもこの ADR の決定に合っていない（[#917](https://github.com/isseis/yt2column/issues/917)）。

## 採らなかった案

-   **タスク番号を issue 番号にする（issue #917 の案 B）。** 同じ issue に 2 つの `/mkreq` を走らせると同じ番号になり、中断した issue からはタスクを作れなくなる。ADR 番号には使えないので、仕組みが 2 つになる（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md) の 1.4）。
-   **番号を計算した後に使用中かを確かめ直す（issue #917 の案 D）。** 2 つのセッションが同時に確かめ直すと、重複が残る（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md) の 1.4）。
-   **記録の tag を `git push` で作る。** 同じ commit を指す同じ名前の tag の 2 回目の push も終了コード 0 で終わるので、作れたかを終了コードで判定できない（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md)「設計の際に決めたこと（2026-11-17）」）。
-   **記録を独自の名前空間（`refs/number-reservations/...`）やブランチに置く。** 独自の名前空間は ruleset で守れない。ブランチは、`chief` と `/mkreq` が読むブランチの一覧に混ざる（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md)「設計の際に決めたこと（2026-11-17）」）。
-   **マージの前の確かめを CI に置く。** CI は PR の時点の `main` としか比べられず、記録の tag を読むネットワークの処理も CI に要る（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md)「設計の際に決めたこと（2026-11-17）」）。
-   **記録の tag に PR の情報を持たせ、マージの前に PR と結びつけて確かめる。** 注釈付きの tag と ref の 2 段の作成が要り、途中で失敗したときの扱いが増える。ほかのブランチを見る確かめなら、手で選んだ番号の重なりも見つけられるので、この案は要らない（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md)「設計の際に決めたこと（2026-11-17）」）。
-   **仕組みの導入より前に作った PR を、PR の作成日時で記録があるかの確かめから外す、または使用中の番号の記録をまとめて作る。** 作成日時で分けると、導入より前に作った PR が導入の後に加えた番号を見逃す。まとめて作ると、そのための経路が道具に要る（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md)「設計の際に決めたこと（2026-11-17）」）。
-   **ローカルのロック（git の共通ディレクトリでの `mkdir` によるロック）。** 同じマシンの worktree の間でしか効かず、別のクローンや cloud のセッションには効かない。エージェントが複数のツールの呼び出しにまたがってロックを持つのも壊れやすい（[0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md)「issue #917 で決めたこと」）。
-   **番号を決められないとき、従来の計算で続けて警告する。** 重複の余地が残り、マージの前に確かめる仕組みが別に要る（[0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md)「要件定義の際に決めたこと（2026-11-17）」）。
-   **ADR 番号の欠番を禁じたままにする。** マージの順を予約の順にそろえる運用と、取り下げた番号を別の ADR で埋める運用が要る（[0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md)「要件定義の際に決めたこと（2026-11-17）」）。
-   **使い終わった番号の記録を消す。** 消す手順が要り、消した番号を再び使う余地が生まれる（[0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md)「要件定義の際に決めたこと（2026-11-17）」）。
-   **ADR 番号の決定だけは、その都度利用者に確かめる。** ADR は手で作る PR でも作られ、コマンドごとの承認では扱えない（[0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md)「要件定義の際に決めたこと（2026-11-17）」）。

## 結果

-   番号を決めるには GitHub に届くことが要る。番号を決められない環境では、`/mkreq` と ADR の作成と付け替えが止まる。
-   中断したタスクや PR の番号は欠番として残る。番号の並びから、作られたタスクや ADR の数は分からない。
-   ADR の規約と `TestADRRecords` は、欠番を誤りとしない形に変わる。重複の検査と、`main` を取り込むときの付け替えの規則は残る。
-   記録の tag は `git fetch` の tag の自動追従で各クローンに入り、`git tag` の一覧に並ぶ。
-   記録の ruleset はリポジトリの外にあり、利用者が設定する。設定する前は、記録の tag の削除を止めるのは [CLAUDE.md](../../../CLAUDE.md) の規則だけである。
-   `/mergepr` を通らない手作業のマージは、マージの前の確かめを通らない。
-   記録の tag は誰も迂回できずに残るので、誤って作られた tag があると、利用者がその tag だけを ruleset の対象から一時的に除いて消すまで、その番号の空間では番号を決められなくなる。手で作られた大きな番号の tag は、跳びの基準を押し上げ、番号を使い切らせうる。
-   エージェントは利用者の管理者の資格で動くので、記録の ruleset を変える・無効にすることができる。これを止めるのは [CLAUDE.md](../../../CLAUDE.md) の規則だけである。
-   すでにある ref の作成を GitHub が成功として受けないことは、決めた時点では確かめていない。この前提が崩れると、一意性が崩れる。
-   古い `mergepr` のバイナリは、確かめなしにマージする。cloud のセッションで番号を決められるかは、決めた時点では確かめていない。
-   2 つの `/mergepr` が同時に確かめると、どちらも重複の確かめを通りうる。古い手順のセッションが、中断されてブランチが消えた番号を手で選ぶと、使い回しは見つからない。

## 経緯

- 2026-11-17 タスク番号と ADR 番号を GitHub の上で重複しないように道具で決め、決められなければ止め、番号の記録を残して使い回さず、ADR 番号の欠番を許し、道具の呼び出しを常設の承認にすると決めた。タスク番号と ADR 番号を別の空間に持ち、ADR 番号を決める手順（付け替えを含む）を ADR の規約に書き、使用中とみなす PR をこのリポジトリの中にヘッドがあるものに限り、番号の記録の道具以外での書き換えに承認を要ることにし、番号が不自然に跳んだら止め、マージの前に番号を確かめることにした（[0100 要件定義書](../../tasks/0100_number_reservation/01_requirements.md)「要件定義の際に決めたこと（2026-11-17）」）
- 2026-11-17 番号ごとに 1 つの tag（`refs/tags/task-number/NNNN`・`refs/tags/adr-number/NNNN`）を GitHub の REST で作る方式にし、記録の tag を削除と更新を禁じる ruleset で守り、道具を Go の `numreserve` にし、マージの前の確かめを `mergepr` に置いてほかのブランチも見ることにし、仕組みより前の番号をしきい値で記録の確かめから外すことにした（[0100 設計書](../../tasks/0100_number_reservation/02_architecture.md)「設計の際に決めたこと（2026-11-17）」）
