# ADR-0038: make deadcode はモジュール全体とテストから届かない関数を報告して失敗し、テストの時間の判定は -race なしのビルドだけで行う

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

この ADR は、開発の確認の範囲についての 2 つの決定を持つ。到達できない関数を報告する `make deadcode` が何を解析し、いつ失敗するかと、テストの時間の判定（コピーした字幕のパーサの時間の期限と、表示用の Markdown の無害化の線形時間の判定）をどのビルドで行うかである。

到達できない関数の報告は、ほかの `main` パッケージやほかのパッケージのテストから届く関数まで含むと数百件のノイズになり、本当に到達できない関数を見逃す。報告があっても失敗しなければ、タスクの完了の条件に使えない（[0047 要件定義書](../../tasks/0047_deadcode_scope/01_requirements.md) §1）。

コピーした字幕のパーサには、記事の生成を始める前の入力の検査の中で解析を終えるための予算がある（[0015 設計書](../../tasks/0015_copied_transcript_source/02_architecture.md) §7.3）。`make test` と CI の `Test` ジョブは全パッケージを `-race` 付きで実行するが、`-race` 付きのビルドでは長い入力の解析が手元の計測で約 23〜31 倍遅くなる。本番の CLI と拡張の記事生成モジュールは `-race` なしでビルドされる。WASM は `-race` でビルドできない（[0039 要件定義書](../../tasks/0039_large_input_test_timeout/01_requirements.md) §1、[0090 設計書](../../tasks/0090_extension_only_architecture/02_architecture.md)）。issue #1166 の計測では、`go test -race ./...` の全体の実行の中で、4 MiB の入力 7 つを `-race` 付きのビルドで解析するテストに約 101 秒かかり、`-race` 付きの実行で最も時間のかかるテストの 1 つである（[0129 要件定義書](../../tasks/0129_race_test_speedup/01_requirements.md) §1）。

表示用の Markdown の無害化には、入力を 4 倍にしたときの処理時間の比が 8 未満であることを確かめる線形時間のテストがある。このテストは、`-race` 付きと `-race` なしの全体の実行の中で、ほかのパッケージのテストと並行に走っていた。#1166 の並列化で同時に走るパッケージが増え、`-race` 付きの全体の実行で、CPU の競合のために時間比（4 倍の入力と元の入力の処理時間の比）が 11.3 になって失敗した。時間比の余裕は、線形の処理で期待される約 4 倍に対して 8 倍で、約 2 倍しかない（[0133 要件定義書](../../tasks/0133_linear_time_test_norace/01_requirements.md) §1）。

## 決定

-   **`make deadcode` は、モジュール全体と、`test`・`integration` のタグのテストを起点に、到達できない関数を報告する。出力があれば失敗する。** どの `main` パッケージから届く関数も、どのテストから届く関数も到達できると数え、本当に到達できない関数をノイズに紛れさせないためである。失敗させるのは、報告の有無を終了コードで示し、タスクの完了の条件に使えるようにするためである（[0047 要件定義書](../../tasks/0047_deadcode_scope/01_requirements.md)「issue #361 で決めたこと」「要件定義の際に決めたこと（2026-10-28）」）。合否は終了コードと出力の有無だけで決め、出力の中身を読まない。解析の範囲と失敗の条件は、[CLAUDE.md](../../../CLAUDE.md) の「Code Quality」の `make deadcode` の項に従う。
-   **`make deadcode` は手元で実行するターゲットで、CI では実行しない。** CI で実行するには、CI の環境に `deadcode` コマンドを入れる手順とその版の固定が要り、issue がそれを求めていなかったためである（0047 要件定義書「要件定義の際に決めたこと（2026-10-28）」）。
-   **パーサの時間の期限は、`-race` なしのビルドだけで確かめる。** `make test` は、`-race` 付きの実行の後に `make test-parse-norace` を実行し、そこで時間を確かめる。CI の `Test` ジョブも別の手順として同じターゲットを実行する（[.github/workflows/ci.yml](../../../.github/workflows/ci.yml)）。期限が守るのは本番の解析（拡張の記事生成モジュールと CLI）で、本番は `-race` なしでビルドされ、`-race` 付きのビルドの時間は本番のパーサの性能を表さないためである（[0039 要件定義書](../../tasks/0039_large_input_test_timeout/01_requirements.md)「要件定義の際に決めたこと（2026-10-23）」）。`make test` と `make test-parse-norace` の振る舞いは、[CLAUDE.md](../../../CLAUDE.md) の「Test Commands」の `make test` と `make test-parse-norace` の項に従う。
-   **線形時間のテストの時間比は、`make test-parse-norace` の実行だけで判定する。** 判定は、`-race` なしのビルドで、テストの環境変数が判定を求めるときだけ行い、その環境変数はこのターゲットだけが設定する。ターゲットは、時間を確かめる 2 つのテストを、ほかのテストと並行に走らせずに 1 つずつ走らせる。全体の実行（`-race` 付きと `-race` なし）では、同時に走るほかのパッケージとの CPU の競合で時間比がぶれ、テストの並列化を進めるほど競合が強まるためである。ビルドタグだけで切り替えると、`-race` なしの全体の実行（`go test ./...` や `make coverage-compare`）で判定し続けてしまう（[0133 要件定義書](../../tasks/0133_linear_time_test_norace/01_requirements.md)「要件定義の際に決めたこと（2026-11-28）」）。環境変数の名前と値、ターゲットのレシピは、[0133 設計書](../../tasks/0133_linear_time_test_norace/02_architecture.md)「設計の際に決めたこと（2026-11-28）」に定める。
-   **`-race` 付きのビルドでも、時間以外は確かめ続ける。** パーサのテストは、どちらのビルドでも、解析の成功、セグメントの数、メモリの確保量の上限を確かめる。ビルドごとに違う値は、ビルドタグ `race` と `!race` のテストのファイルに置く。手元の計測ではメモリの確保量が単独の実行と並行の実行で 1% 未満しか違わず、0015 が確かめようとした性質（メモリの確保量が入力の長さに比例すること）を、時間の上限を持たずに確かめ続けられるためである（0039 要件定義書「要件定義の際に決めたこと（2026-10-23）」）。
-   **線形時間のテストは、時間比を判定しないときも、無害化が成功することと出力の契約を確かめる。** `-race` 付きのビルドと、環境変数のない `-race` なしの実行でも、意味のある確認を残すためである（[0133 要件定義書](../../tasks/0133_linear_time_test_norace/01_requirements.md)「要件定義の際に決めたこと（2026-11-28）」）。
-   **`-race` 付きのビルドでは、4 MiB より小さい入力で確かめる。** 4 MiB の入力での確認は `-race` なしのビルドだけが行う。入力の大きさは、確保量が入力の長さの 2 乗に比例するように解析を壊したとき、4 MiB の入力と同じく確保量の上限を超えて失敗する大きさにする。実際に解析を壊して、失敗することを確かめる（[0129 要件定義書](../../tasks/0129_race_test_speedup/01_requirements.md) の AC-03）。`-race` 付きのビルドの時間は本番の性能を表さない。また、4 MiB の入力での確保量は `-race` なしのビルドがより厳しい上限で確かめ続けるので、`-race` 付きのビルドで 4 MiB の入力を解析しても、その時間に見合う確認は得られないためである（[0129 要件定義書](../../tasks/0129_race_test_speedup/01_requirements.md)「要件定義の際に決めたこと（2026-11-26）」）。
-   **食い違い:** 線形時間のテストはまだ、全体の実行（`-race` 付きと `-race` なし）で時間比を判定し、判定しないときの出力の契約も確かめていない。`make test-parse-norace` もまだパーサのテストだけを走らせる。この食い違いは https://github.com/isseis/yt2column/issues/1206 の実装で解消する。

## 採らなかった案

-   **`make deadcode` の解析の起点を CLI の `main` パッケージ（`./cmd/yt2column`）とそのテストに限る。** ほかの `main` パッケージかほかのパッケージのテストから届く関数まで報告し、本当の候補を数百件の報告から探すことになる（[0047 要件定義書](../../tasks/0047_deadcode_scope/01_requirements.md) §1）。
-   **`-test` を外し、テストを解析の起点に含めない。** `test` のタグの付いたテストヘルパーが到達できないと数えられ、422 件の報告が出た。タグも外すと、意図した足場とテストが使う公開関数の 44 件が報告された（[0047 要件定義書](../../tasks/0047_deadcode_scope/01_requirements.md)「要件定義の際に決めたこと（2026-10-28）」）。
-   **報告があっても `make deadcode` を終了コード 0 で終わらせる。** 報告の有無が終了コードに現れないので、完了の条件に使えない（[0047 要件定義書](../../tasks/0047_deadcode_scope/01_requirements.md) §1・「要件定義の際に決めたこと（2026-10-28）」）。
-   **CI で `make deadcode` を実行する。** CI の環境に `deadcode` コマンドを入れる手順と、その版の固定が要る。issue はそれを求めていない（[0047 要件定義書](../../tasks/0047_deadcode_scope/01_requirements.md)「要件定義の際に決めたこと（2026-10-28）」）。
-   **`make test` の中で、このリポジトリ自身に `make deadcode` を走らせるテストを置く。** 検査が働くのは `deadcode` コマンドのある手元だけで、`deadcode` コマンドのない CI との差が大きくなる（[0047 設計書](../../tasks/0047_deadcode_scope/02_architecture.md)「1.2. 設計の際に決めたこと（2026-10-28）」）。
-   **時間の期限を `-race` 付きのビルドの `make test` で確かめる。** 0015 の決定である。0015 の予算が守るのは本番のサーバの解析で、本番は `-race` なしでビルドされる。`-race` 付きのビルドでは、データ競合の検出器の負担のため、解析が手元の計測で `-race` なしの約 23〜31 倍かかり、本番のパーサの性能を表さない（[0039 要件定義書](../../tasks/0039_large_input_test_timeout/01_requirements.md)「要件定義の際に決めたこと（2026-10-23）」）。
-   **原因を調べずに、時間の上限だけを変える。** 原因が分からないまま上限だけを変えると、本当の劣化を見逃すおそれがある（[0039 要件定義書](../../tasks/0039_large_input_test_timeout/01_requirements.md)「issue #463 で決めたこと」）。
-   **`-race` 付きのビルドでも 4 MiB の入力のままにする。** このテストが、`-race` 付きの実行で最も時間のかかるテストの 1 つであり続ける（[0129 要件定義書](../../tasks/0129_race_test_speedup/01_requirements.md)「要件定義の際に決めたこと（2026-11-26）」）。
-   **`-race` 付きのビルドから、コピーした字幕の大きな入力のテストを外す。** `-race` 付きのビルドが、解析の成功・セグメントの数・確保量を確かめなくなり、「`-race` 付きのビルドでも、時間以外は確かめ続ける」に反する（[0129 要件定義書](../../tasks/0129_race_test_speedup/01_requirements.md)「要件定義の際に決めたこと（2026-11-26）」）。
-   **4 MiB の入力を、`make test-parse-norace` だけが実行する別のテストに移す。** 7 つの入力を作る処理と解析を、2 つのテストで二重に持つことになる（[0129 要件定義書](../../tasks/0129_race_test_speedup/01_requirements.md)「要件定義の際に決めたこと（2026-11-26）」）。
-   **パーサを改善する。** CI で上限を超えた原因は `-race` 付きのビルドの時間で、本番の解析の時間ではない。改善しても本番の時間はほとんど変わらず、受理と拒否の規則を保つことを新たに保証する負担が加わる（[0039 調査の記録](../../tasks/0039_large_input_test_timeout/04_investigation.md) §7.2）。
-   **`-race` なしの確認を、CI の `doc-guard` ジョブに加える。** `doc-guard` は文書だけの PR でも走り、`Test` ジョブとは走る条件が違う（[0039 設計書](../../tasks/0039_large_input_test_timeout/02_architecture.md)「1.2. 設計の際に決めたこと（2026-10-23）」）。
-   **`test-parse-norace` を `make test` の前提条件（prerequisite）にする。** `make -j` では `-race` 付きの実行と並行に走り、時間の確認がその負荷を受ける（[0039 設計書](../../tasks/0039_large_input_test_timeout/02_architecture.md) §3.2）。
-   **線形時間のテストも、パーサの期限と同じくビルドタグだけで切り替える。** `-race` なしの全体の実行で、ほかのパッケージと並行に走る中で時間比を判定し続け、そこで失敗しうる。`make coverage-compare` はその失敗で止まる（[0133 要件定義書](../../tasks/0133_linear_time_test_norace/01_requirements.md)「要件定義の際に決めたこと（2026-11-28）」）。
-   **線形時間のテストの `-race` 付きのビルドでは、成功だけを確かめる。** 時間以外の確認が成功だけになり、同じファイルにある出力の契約の確認を長い入力に当てられるのに当てない（[0133 要件定義書](../../tasks/0133_linear_time_test_norace/01_requirements.md)「要件定義の際に決めたこと（2026-11-28）」）。
-   **`test-parse-norace` を、`test-timing-norace` のような汎用の名前に変える。** `CLAUDE.md`、この ADR、ガードのテスト、CI の手順の名前をまとめて変えることになる（[0133 要件定義書](../../tasks/0133_linear_time_test_norace/01_requirements.md)「要件定義の際に決めたこと（2026-11-28）」）。
-   **時間の確認を別のテスト関数に分ける。** 7 つの入力を作る処理と解析を、2 つのテストで重複させる（[0039 設計書](../../tasks/0039_large_input_test_timeout/02_architecture.md)「1.2. 設計の際に決めたこと（2026-10-23）」）。

## 結果

-   `make deadcode` は、どの `main` パッケージからもどのテストからも届かない関数だけを報告する。新しい `main` パッケージやパッケージを加えても、ターゲットを変えずに解析の範囲に入る。
-   テストだけが呼ぶ本番のコードは報告されない。後の PR が呼ぶ予定の足場は、テストから届くようにするか、使う PR まで加えない。
-   `make deadcode` は CI で実行されないので、手元で実行しなければ検査は働かない。`deadcode` コマンドの版は固定していない。解析の範囲を確かめるテストは、`deadcode` コマンドがないとスキップされ、CI ではスキップされる。
-   `-race` 付きのビルドでは解析の時間を比べないので、解析が止まらないときは `go test` のパッケージのタイムアウトで失敗する。時間の劣化は `-race` なしの確認で見つける。
-   `-race` 付きのビルドは 4 MiB の入力を解析しないので、4 MiB の入力でだけ現れる問題は `-race` なしの確認だけが見つける。データ競合の検出器は、4 MiB の入力の解析を一度も調べない。
-   `make test-parse-norace` が担う時間の確認（パーサの期限と線形時間の時間比）は、`-run` で絞り、`-p 1` で 2 つのパッケージのテストを 1 つずつ走らせる 1 回の `go test` だけで行われる。テストの名前、`-race` の有無、`-count=1`、`-p 1`、渡すパッケージ、判定を求める環境変数の設定、`make test` と CI からの呼び出しが変わると、確認が黙って行われなくなるか、ほかのパッケージのテストと並行に走る。これを `internal/transcript` と `internal/publisher` のレシピのガードのテストが確かめる（[0133 設計書](../../tasks/0133_linear_time_test_norace/02_architecture.md)「設計の際に決めたこと（2026-11-28）」）。
-   期限は 7 つの入力に共通の 1 つの値で、入力の長さの 2 乗に比例するような桁の違う劣化だけを見つける。手元で `make test` をほかの重い処理と同時に実行すると、パーサの期限と線形時間の時間比の判定は、どちらもその負荷を受けうる。
-   表示用の Markdown の無害化が入力の長さの 2 乗に比例する時間に劣化しても、全体の実行では見つからない。`make test-parse-norace` の実行だけが見つける。
-   パーサの期限はビルドタグだけで切り替えるので、`-race` なしの全体の実行でも確かめ続ける。線形時間の時間比とは、判定する実行が違う。
-   期限はネイティブのビルドで確かめる。拡張の記事生成モジュールでの解析の時間は測っていない。WASM の解析はネイティブより遅くなりうるが、桁の違う劣化を見つけるという期限の目的は変わらない。
