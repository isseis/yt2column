# ADR-0028: 結果が分からないときも、止まった実行も、記事の生成を自動で始め直さない

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

拡張の中のやり取りでは、頼んだ側が結果を知れないことがある。ポップアップは、Service Worker（SW）が予約の結果を返す前に止まったときや、時間の上限までに結果が届かなかったときに、生成が始まったかどうかを知れない（[0090 設計書](../../tasks/0090_extension_only_architecture/02_architecture.md)「SW の調停」）。生成を実行するビューアのタブが閉じられるか読み込み直されると、その実行は途中で止まる。

結果が分からないまま、または止まった実行を見て、自動で始め直すと、同じ記事が二重に生成されうるうえ、利用者の意図しない料金がかかる。生成には LLM の料金がかかり、利用者が自分の API キーで支払う。

## 決定

-   **生成の開始と予約は、どの結果でも自動では送り直さない。** ポップアップが結果を受け取れない場合、SW が止まった場合、応答が想定外の場合も送り直さない。結果が分からないまま送り直すと、同じ記事が二重に生成されうるためである。規則は [0090 設計書](../../tasks/0090_extension_only_architecture/02_architecture.md) の「SW の調停」と「利用者に示す状態の種類」にある。
-   **生成の開始は、利用者の 1 回の操作につき 1 回だけ頼む。** もう一度頼むのは、利用者がポップアップのボタンを押したときだけである。利用者の操作だけを、料金のかかる生成の契機にするためである。規則は 0090 設計書の「生成の開始と予約」と [ADR-0008](0008-launch-path.md) にある。
-   **止まった実行と失敗した実行は、自動で生成し直さない。** 実行するビューアを読み込み直しても、閉じたタブを復元しても、履歴から開いても、生成は始まらない。生成し直すのは、利用者が同じ入力で開始を押したときだけで、そのときは同じジョブのまま生成し直す。ページを開く操作で料金をかけないためである。規則は 0090 設計書の「止まった実行の判定」と [0090 要件定義書](../../tasks/0090_extension_only_architecture/01_requirements.md) AC-07 にある。
-   **ポップアップが 60 秒たっても予約の結果を受け取れないときは、結果不明として示す。** 示すのは、ビューアで状態を確かめる手順と、もう一度押しても、同じ入力の記事が処理中か完成なら二重には生成されないことである。同じ入力の判定（[ADR-0027](0027-article-job-api.md)）が、利用者の押し直しを安全にするためである。規則は 0090 設計書の「利用者に示す状態の種類」にある。
-   **自動で繰り返すのは、生成を始めない表示の更新と、実行するページの生存の確認だけにする。** 表示の更新は `chrome.storage.onChanged` の通知で行い、生存の確認は LLM を呼ばない。規則は 0090 設計書の「止まった実行の判定」にある。

この決定のうち、拡張の中の予約と止まった実行の扱いは、まだコードに反映していない。今は、拡張が Native Messaging のホストを通してサーバへ生成の開始を送り、ホストもサーバへ 1 回だけ接続して再送しない。この差分は [#773](https://github.com/isseis/yt2column/issues/773) の実装で解消する。

## 採らなかった案

-   **投稿を自動でリトライする（HTTP 429 の `Retry-After` に従う待機を含む）。** Incoming Webhook への投稿は冪等ではなく、応答を受け取れなかったメッセージを再送すると、同じメッセージが重複して投稿されうる（[0006 要件定義書](../../tasks/0006_slack_webhook_publisher/01_requirements.md) §2.3）。
-   **応答を受け取れなかった送信を、拡張が自動で再送する。** サーバは `202` が届かなくてもジョブを続けるので、再送すると記事が二重に投稿される（[0020 要件定義書](../../tasks/0020_extension_send/01_requirements.md) §1、[0011 設計書](../../tasks/0011_localhost_server/02_architecture.md) §3.8.1）。
-   **クライアントが付けるリクエスト ID で重複を除き、再送しても二重にならないようにする。** 理由は記録されていない（[0026 要件定義書](../../tasks/0026_native_messaging_relay/01_requirements.md) §2.3 は、送信は 1 回だけとし、二重の投稿の検出は別のタスクとするとだけ述べる）。
-   **投稿に失敗した記事のやり直しで、最初のメッセージから送り直す。** 届いたメッセージがすべて重複する（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）。
-   **生成の開始の結果不明で、送り直す前に Slack を確かめるよう案内する。** 0020 から 0050 までの案内である。生成の開始は、同じ入力に対して処理中または完了した記事のキーを返し、LLM を呼ばない。投稿も利用者の操作になったので、Slack を確かめる必要がなくなった（[0050 要件定義書](../../tasks/0050_viewer_tab/01_requirements.md) §5）。
-   **止まった実行を、実行するビューアの再読み込みで自動で始め直す。** ページを開く操作で料金がかかり、利用者の明示の操作のときだけ生成を始める決定（[0090 要件定義書](../../tasks/0090_extension_only_architecture/01_requirements.md) AC-07）に反する（[0090 設計書](../../tasks/0090_extension_only_architecture/02_architecture.md)「止まった実行の判定」）。

## 結果

-   結果不明のとき、拡張は自動で回復しない。利用者がビューアで状態を確かめるか、同じ入力で押し直す。同じ入力の記事が処理中か完成なら、作り直さずにそのジョブが示される（[ADR-0027](0027-article-job-api.md)）。
-   実行するビューアを閉じるか読み込み直すと、その実行は止まったまま残り、料金は不明と示される。利用者が押し直すまで、記事はできない。
-   拡張に頼みの経路を足すときも、1 回だけ頼み、結果不明では頼み直さない形を保つ。

## 経緯

- 2026-10-07 CLI の Webhook への投稿を自動でリトライしないことにした。Incoming Webhook への投稿は冪等ではないので、HTTP 429 も投稿の失敗とし、分割した投稿の途中で失敗しても続きから再開しない（[0006 要件定義書](../../tasks/0006_slack_webhook_publisher/01_requirements.md) §2.3）
- 2026-10-13 サーバは `202` の書き込みに失敗してもジョブを続け、拡張にはネットワークの誤りの後に自動で再送しないことを求めた（[0011 設計書](../../tasks/0011_localhost_server/02_architecture.md) §3.8.1）
- 2026-10-15 拡張は、応答を受け取れない場合と想定外の応答の場合に自動で再送せず、結果が分からないことを示して、送り直す前に Slack を確かめるよう案内することにした（[0020 要件定義書](../../tasks/0020_extension_send/01_requirements.md) F-003・F-007）
- 2026-10-19 Native Messaging のホストを足すとき、ホストは接続にも送信にも再試行を持たないことにした。拡張はホストへ 1 回だけ送り、未送信と確定しない失敗を結果不明として扱う（[0026 設計書](../../tasks/0026_native_messaging_relay/02_architecture.md) §1.1・§3.5.2）
- 2026-10-27 生成と投稿を分けたジョブの API で、投稿中または投稿済みの記事への投稿の操作を投稿し直さない（冪等）ことにした。分割した投稿の一部が失敗した記事のやり直しは、届かなかった最初のメッセージから送り、失敗した 1 通の重複を許す（[0044 要件定義書](../../tasks/0044_article_job_api/01_requirements.md)「要件定義の際に決めたこと（2026-10-27）」）
- 2026-10-29 拡張を新しい API に移し、生成の開始と投稿の操作を自動で送り直さず、状態の取得だけを繰り返すことにした。生成の開始の結果不明では Slack を確かめる案内をやめ、同じ入力の記事が処理中か完了していれば二重には生成されないことを示す（[0050 要件定義書](../../tasks/0050_viewer_tab/01_requirements.md)「要件定義の際に決めたこと（2026-10-29）」）
- 2026-11-11 Webhook への投稿の機能の廃止に合わせて、次の 4 つの決定をなくした。投稿の操作を自動で送り直さないこと、サーバが Webhook への投稿を送り直さないこと、投稿の冪等性、届かなかった最初のメッセージからのやり直しである。自動で送り直さない規則は生成の開始に残る（[0083 要件定義書](../../tasks/0083_remove_slack_webhook/01_requirements.md) F-001）
- 2026-11-12 localhost サーバと Native Messaging のホストの廃止に合わせて、ホストの接続と未送信の確定の規則をなくした。生成の開始と予約を自動で送り直さないこと、止まった実行を自動で生成し直さないこと、60 秒で結果不明とすることにした（[0090 設計書](../../tasks/0090_extension_only_architecture/02_architecture.md)）
