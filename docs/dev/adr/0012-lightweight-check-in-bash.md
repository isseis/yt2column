# ADR-0012: 軽量プロセスの確かめ直しは、origin/main の版の bash スクリプトで行い、Go のツールにしない

## 状態

| 項目 | 値 |
|---|---|
| 状態 | `有効` |

## 背景

軽量プロセスでは、エージェントが要件・設計・計画の文書を作らずに 1 本の PR を作る。そのため、変更が軽量プロセスの条件を満たすかを、エージェントの申告ではなく、ブランチの実際の diff で確かめ直す必要がある。条件は、行数・ファイル数・除外するパス・道具のコミット（条件の表が許可したコマンド、つまり道具のコマンドが生成したコミット）についてのものである（[requirements_process.md](../conventions/requirements_process.md) の「Lightweight Process」）。確かめ直しの結果が `FAIL` なら変更を戻すので、確かめ直しは信頼境界にある。

決定を縛る前提は次のとおりである。

-   確かめ直す仕組みは、確かめられる側のブランチから変更できてはならない。ブランチがその仕組みを書き換えれば、どの変更も通せる。
-   エージェントがコマンドを打ち直して実行すると、テストが走らせるものと実際に走るものが同じだと保証できない。PTY（疑似端末）は約 4000 バイトを超える入力を黙って切り詰めることがある。
-   タスク 0054 では、確かめる仕組みの方が、確かめる対象の変更より大きくなった。軽量プロセスの仕組みは、軽量に保つ。
-   bash では、単語分割・glob・`eval`・算術展開・呼び出し元の環境（エクスポートされた関数、`SHELLOPTS` など）によって、意図しないコマンドが動きやすい。

## 決定

-   確かめ直しは、リポジトリのファイル `.claude/commands/_lib/lightweight-check.sh` の bash スクリプト（bash 3.2 で動く書き方）で行い、Go のツールは作らない。`/runissue` は、`git show origin/main:` で書き出した版を `bash` で実行し、作業ツリーの版は実行しない。入力・出力・判定の取り決めは [0061 設計書](../../tasks/0061_lightweight_process/02_architecture.md) の 3.5.6 にある。
-   bash の落とし穴への守りはスクリプトの本体にあり、その取り決めは冒頭のコメントに書いてある（[lightweight-check.sh](../../../.claude/commands/_lib/lightweight-check.sh)）。要旨は次のとおりである。
    -   `PATH`・`HOME`・`TMPDIR` だけを残した `env -i` で自分を起動し直し、呼び出し元の環境を持ち込まない。
    -   `eval` を使わない。外部から受け取った値を、算術展開に入れる前に数字だけだと確かめる。
    -   道具のコマンドは shell を通さず、語の配列として実行する。git の出力は `-z` で読む。
    -   一時的なファイルと worktree は `trap` で消す。
-   git の設定・属性に左右されないための守り（設定の上書き、属性を空の tree から読むこと）は、bash に限らず Go でも要る守りで、同じスクリプトが持つ。

### 見直しの条件

次のどれかに当たったら、bash スクリプトのままにするか、Go のツールに移すかを決め直す。

1.  スクリプトの、空行とコメントの行を除いた行数が、テストの上限を超える。
2.  スクリプトが `eval` を使う。
3.  bash に特有の欠陥（単語分割・glob・`eval`・算術展開による注入、失敗の取りこぼし、bash の版による違い）が、レビューか実際の使用で見つかる。
4.  確かめ直しが、構造を持つ新しい種類の入力（JSON など）や、条件の表（軽量プロセスの条件を並べた表）の新しい種類の行を読む必要が出る。
5.  `origin/main` の版の Go のツールを、インストールの手順なしに、今と同じ程度の時間で動かせる方法が見つかる。

1 と 2 は、`make test` の `TestLightweightCheckRevisitConditions`（[lightweight_docs_test.go](../../../cmd/yt2column/lightweight_docs_test.go)）が、変更のたびに確かめる。行数の上限の値は、このテストの定数が持つ。3〜5 は数えられないので、テストにはしない。

決め直した結果、bash スクリプトのままにするときは、その理由をこの ADR の経緯に書く。1 に当たって bash スクリプトのままにするときは、同じ PR でテストの上限を上げる。Go に移すときは、条件の表と出力の形（0061 設計書 3.5.6）を保てば、`runissue.md` の手順は変わらない。

## 採らなかった案

-   **Go のツールにする（`fixprguard` と同じ形）。** パッケージ・テスト・インストールの手順が増え、タスク 0054 で問題になった「確かめる仕組みの方が変更より大きい」状態を繰り返すため、採らなかった（0061 設計書 1.2 の H-01）。2026-11-05 に比べ直したところ、Go にすれば bash に特有の落とし穴（上の背景の最後の項目）はなくなる。一方で、次の 2 つがわかった。
    -   守りの大半（git の設定・属性への守りと、道具のコミットを worktree で再現すること）は git を呼ぶ側の守りで、Go でも同じだけ要る。
    -   `origin/main` の版を動かすという保証を維持するには、`origin/main` の worktree でのビルドか、利用者によるインストールが要る。インストールにすると、`origin/main` より古い版が動くことがある。

    そのため、今は移さず、見直しの条件を置いた。
-   **`runissue.md` のコードブロックに書く。** エージェントが打ち直して実行するので、テストが走らせるものと実際に走るものが同じだと保証できない。コマンドが長く、PTY の切り詰めのおそれもある。そのため採らなかった（0061 設計書 1.2 の H-01）。

## 結果

-   スクリプトは bash 3.2 で動く書き方に限られる。テストは、`PATH` 上の bash と macOS の `/bin/bash` の両方で走らせる。
-   `make test` は `bash` と、`--attr-source` を受け付ける `git` を要する（`CLAUDE.md` の「Development Notes」）。
-   スクリプトとそのテストには、仕様の見出しのための日本語のリテラルの例外がある（`CLAUDE.md` の「Go Idioms」）。
-   bash に特有の守りは、テストで支えるしかない。`TestLightweightCheck` は、fixture のリポジトリでスクリプトを実際に動かすので、時間がかかる（手元の開発環境では 30〜50 秒）。
-   スクリプトを変える PR は、見直しの条件に当たらないかを確かめる。数えられる条件はテストが確かめ、数えられない条件はスクリプトを読んで確かめる。

## 経緯
