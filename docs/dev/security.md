# セキュリティ考慮事項

yt2column の設計・実装・レビューで確認するセキュリティ上の観点をまとめる。`mkarch` / `weakreview` などのコマンドは、機能が `.claude/commands/_context.md` の "Conditional-guide trigger" に該当するとき本書を参照する。

yt2column はローカルで実行する CLI であり、利用者本人が入力（動画 URL）を与える。ただし、字幕・動画タイトル・概要欄・LLM の応答・外部サーバーのレスポンスは**信頼できない入力**として扱う。

## 1. 外部コマンド（yt-dlp）の起動

- `exec.CommandContext` に引数を配列で渡す。シェル（`sh -c`）を経由しない。
- 子プロセスへ渡す環境変数は allowlist に限定し、設定されている変数のみを渡す（例: `PATH`・`HOME`・`TMPDIR`・`XDG_CONFIG_HOME`・`XDG_CACHE_HOME`・proxy 関連・locale・`SSL_CERT_FILE` / `SSL_CERT_DIR`）。`exec.Cmd.Env` を nil のままにせず、API キーや Webhook URL などの秘密情報を子プロセスへ引き継がない。ブロックリスト（既知の秘密情報だけを除く）ではなく allowlist にして、秘密情報を追加したときに漏れないようにする。
- URL は引数として渡す前に検証する。YouTube の動画 URL 形式から動画 ID を取り出し、yt-dlp には正規化した URL を渡す。`-` で始まる値がオプションとして解釈されないよう、URL の直前に `--` を置く。
- 出力先のディレクトリは `-P`（`--paths`）の値として渡し、`-o` の出力テンプレートは動画 ID のフィールド（`%(id)s`）に基づく固定の文字列とする。yt-dlp は `-o` の値をテンプレートとして展開するため、`%` を含むキャッシュディレクトリのパスなど、呼び出し元が与えたパスを `-o` に含めない。動画 ID は `[A-Za-z0-9_-]{11}` に一致することを確認し、パス区切りや `..` を含む値を拒否する。
- `context` によるタイムアウトを設定する。
- yt-dlp の標準エラー出力をエラーメッセージに含める場合は長さを制限する。

## 2. 秘密情報（API キー・Webhook URL）

- `DEEPSEEK_API_KEY` などの API キーと `SLACK_WEBHOOK_URL` は環境変数からのみ読み込む。リポジトリ内のファイルに書かない（`.envrc` / `.env` は `.gitignore` 済み）。
- Webhook URL は URL 自体が秘密情報である。ログ・エラーメッセージに含めない。`*url.Error` など、URL を含む値をラップしたエラーをそのまま出力しない。
- テストでは、本番の API キー（`DEEPSEEK_API_KEY`・`ANTHROPIC_API_KEY` に設定するもの）と本番の Webhook URL を使わない。ただし、実 API を呼ぶ統合テストに限り、本番とは別に用意した**テスト用の API キー**を使う例外を設ける（`docs/tasks/0003_deepseek_llm_client/02_architecture.md` §5.2）。テスト用の API キーは、DeepSeek API・Anthropic API に実際に通る有効なキーであり、使えば料金が発生する。
  - ユニットテストは、本番のキーもテスト用の API キーも使わない。偽の値だけを使い、Webhook URL も偽の値だけを使う。どのテストも API キーをコードやテストデータに書かない。
  - テスト用の API キーは、テスト専用の環境変数 `YT2COLUMN_TEST_DEEPSEEK_API_KEY` からだけ読む。統合テストは、本番の `DEEPSEEK_API_KEY` を、設定されていても読まない。テスト用の API キーには、本番と別のキー（利用上限を設けたものなど）を割り当てる。
  - Claude の統合テストも同じ方針で、テスト専用の `YT2COLUMN_TEST_ANTHROPIC_API_KEY` からだけ API キーを読み、本番の `ANTHROPIC_API_KEY` は設定されていても読まない。ワークスペース ID もテスト専用の `YT2COLUMN_TEST_ANTHROPIC_WORKSPACE_ID` からだけ読み、本番の `ANTHROPIC_WORKSPACE_ID` は読まない。テスト用の API キーには、利用上限を設けたワークスペースのものを割り当てる。
  - テスト用の API キーを使うのは、`//go:build integration` の次の 3 つの統合テストだけである。どれも、対応する make のターゲットだけがエクスポートするオプトインの変数の値がちょうど `1` でなければスキップする。各ターゲットは自分のオプトインだけをエクスポートし、他のオプトインはエクスポートしない。テスト用の API キーが `.envrc` などで常にエクスポートされていても、`go test -tags integration ./...` や IDE からの実行で料金が発生しない。

    | 統合テスト | make のターゲット | オプトインの変数 | テスト用の API キーがない場合 |
    |---|---|---|---|
    | `internal/llm/deepseek/integration_test.go`（DeepSeek のアダプタ） | `make test-integration-deepseek` | `YT2COLUMN_DEEPSEEK_INTEGRATION=1` | スキップする |
    | `internal/llm/claude/integration_test.go`（Claude のアダプタ） | `make test-integration-claude` | `YT2COLUMN_CLAUDE_INTEGRATION=1` | スキップする |
    | `cmd/yt2column/integration_test.go`（CLI の組み立てで testdata の字幕からファイル出力まで） | `make test-integration-cli` | `YT2COLUMN_CLI_INTEGRATION=1` | 失敗する（本番の `DEEPSEEK_API_KEY` だけがある場合も、それを代わりに使わない） |

  - 実行するかどうかの判定とテスト用の API キーの読み込みは、DeepSeek の 2 つのテストが `internal/llm/deepseek/testutil` の `SettingsFrom` で、Claude のテストが `internal/llm/claude/testutil` の `SettingsFrom` で行う。
  - CLI は API キーを `DEEPSEEK_API_KEY` という名前で受け取るので、CLI の統合テストは、読み込んだテスト用の API キーを、テストが組み立てて CLI に与える環境の中で `DEEPSEEK_API_KEY` という名前で渡す。プロセスの環境変数は変えない。名前は本番と同じだが、値はテスト用の API キーである。
  - テストの出力（ログ・失敗メッセージ・スキップの理由）に API キーもその一部も書かない。
- 本番の `SLACK_WEBHOOK_URL` は、本番の API キーと同様、テストでは使わない。統合テストは、テスト専用の環境変数 `YT2COLUMN_TEST_SLACK_WEBHOOK_URL` からだけ Webhook URL を読む。本番の `SLACK_WEBHOOK_URL` は、設定されていても読まない。テスト用の Webhook は、本番とは別の Mattermost のテスト用チャンネルに投稿するものを用意する。テスト用の Webhook URL を使うのは `//go:build integration` の次の 2 つのテストであり、対応するオプトインの変数の値がちょうど `1` でなければスキップする。値 `1` は、対応する make のターゲットからでも、IDE や `go test -tags integration` を起動した環境からでも、どこから渡されてもテストを実行する。各ターゲットは自分のオプトインだけをエクスポートし、他方のオプトインはエクスポートしない。テスト用の Webhook URL がない場合と、HTTP/2 のデバッグ（下記の `GODEBUG`）が有効な場合は、スキップせずに失敗し、Webhook に送らない。

    | 統合テスト | make のターゲット | オプトインの変数 | テスト用の Webhook URL がない場合 |
    |---|---|---|---|
    | `internal/publisher/slack_integration_test.go`（`SlackWebhookPublisher` が固定の記事を投稿） | `make test-integration-slack` | `YT2COLUMN_SLACK_INTEGRATION=1` | 失敗する（本番の `SLACK_WEBHOOK_URL` だけがある場合も、それを代わりに使わない） |
    | `cmd/yt2column/integration_slack_test.go`（CLI の組み立てで生成した記事を投稿） | `make test-integration-cli-slack` | `YT2COLUMN_CLI_SLACK_INTEGRATION=1` | 失敗する（テスト用の API キーも要る） |

- `GODEBUG` に `http2debug=1` または `http2debug=2` を含めると、Go の HTTP/2 の Transport は送信するリクエストヘッダーを値ごと標準エラー出力に記録する。`Authorization`・`x-api-key` などの API キーのヘッダーもそのまま出力される。`--slack` の Webhook への送信では、リクエストのパス、すなわち Webhook URL のパスも書かれうる。この設定で通信を調査するときは、無効な API キー（本番のキーでもテスト用のキーでもないもの）を使う。`GODEBUG` はプロセスの開始時に一度だけ読まれ、実行中に取り除いても効かないため、統合テストは、API を呼ぶものも Webhook に投稿するものも、送信の前にこれらの設定を検出して失敗する。
- 本番の CLI は `GODEBUG` の `http2debug` を拒否せずに読み込み、利用者が明示的に指定したものとしてデバッグを優先する。その代わり、LLM API を呼ぶ前に、`http2debug` により API キーが標準エラー出力に書かれうることを警告する（`--slack` の場合は Webhook URL のパスも書かれうることも警告する）（F-001・F-007・F-008）。

## 3. ネットワーク通信

- HTTP クライアントにはタイムアウトを設定する（`http.DefaultClient` をそのまま使わない）。Webhook への送信では、メッセージごとに 30 秒のタイムアウトを `context.WithTimeoutCause` で与え、`http.Client.Timeout` は使わない。
- **レスポンスサイズの上限**: 外部サーバーのレスポンスを読むときは `io.LimitReader` などで上限を設ける。上限なしの `io.ReadAll` / `json.Decoder.Decode` は指摘対象とする。Webhook の応答の本文は 8,193 バイトまで読む（8,192 バイトを超える本文を検出するため、上限より 1 バイト多く読む）。
- リトライする場合は回数または経過時間の上限を設ける。Webhook への送信は自動でリトライしない（分割投稿の途中で失敗しても、続きからの再開もしない）。
- **リダイレクトに従わない**: Webhook への送信では `http.Client.CheckRedirect` が `http.ErrUseLastResponse` を返し、3xx の応答に従わない。リダイレクト先が Webhook URL を別のホストへ送ることを防ぐ。
- **応答から取り出すものを限定する**: `200` 以外の応答からは、エラーの識別子（`id`・`request_id`）だけを取り出し、`message` などの自由文は読まない・表示しない。`200` の応答は、本文がちょうど `ok` のときだけ成功とする。
- Webhook 送信の失敗は、分割投稿の途中で失敗した場合も含め、どこまで投稿済みかが分かるエラーにする。

## 4. LLM プロバイダへ送るデータ

- DeepSeek の API への入力は中国で処理・保存され、プライバシーポリシー上はデフォルトでモデルの学習に使われる（オプトアウトあり）。運用開始前にオプトアウトの設定を確認する。
- Anthropic の Messages API へ送る入力と出力は、商用製品の既定では Anthropic のモデルの学習に使われない（利用者がフィードバックを明示的に送った場合や、利用者が許可した場合を除く）。Anthropic API の入力と出力は、受け取りまたは生成から 30 日以内にバックエンドから自動的に削除される。利用者側で保持期間を延ばす機能を使う場合、別途合意した場合（ゼロデータ保持など）、利用ポリシー違反の調査、法令上の保持は例外である。出典: Anthropic Privacy Center [「Is my data used for model training?」](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training)・[「How long do you store my organization's data?」](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)（2026-10-12 確認）。
- 字数の調整の段階は生成した文面（タイトルと本文）も LLM に送る。検証・推敲の段階は、生成した文面に加えて素材（字幕・概要欄・動画タイトル・チャンネル名）も送る。検証・推敲のプロバイダを生成と別にする（`YT2COLUMN_REVIEW_PROVIDER`）と、送り先の事業者が増える。
- LLM に送るのは、生成では公開動画の字幕・メタ情報、字数の調整では生成した文面、検証・推敲では生成した文面と素材、そしていずれの段階でもプロンプトテンプレートだけにする。API キー、Webhook URL、ローカルのファイルパス、利用者の個人情報をプロンプトに含めない。

## 5. キャッシュディレクトリ

- ディレクトリは `0o700`、ファイルは `0o600` で作成する。
- キャッシュの読み込み時も、ファイル名を動画 ID から組み立てる（ディレクトリ内の任意のファイル名を信用しない）。
- ディレクトリを列挙する必要がある場合（dangling なエントリの掃除など）は、自分の命名規則に完全に一致し、動画 ID の検証を通った名前だけを扱う。操作するパスは検証済みの動画 ID から組み立て直し、シンボリックリンクを辿らない。
- 中間生成物（`--artifacts` の成果物）も `0o600` で作り、キャッシュの外の利用者が指定したディレクトリに置く（CLI はディレクトリを作らない）。名前は検証済みの動画 ID と固定の段階名から組み立てる。読み書きは `os.Root` のハンドルを基準に行い、読み込みでは `Lstat` で通常のファイルに限ることを確かめ、開いた記述子が同じファイルであること（`os.SameFile`）と大きさの上限を確かめてから読む。シンボリックリンク（ルート内を指す相対のものを含む）と FIFO は拒否し、`--artifacts` がキャッシュディレクトリの中にある場合は拒否する。

## 6. 信頼できないテキストの取り扱い

- 字幕・タイトル・概要欄はプロンプトに埋め込まれる。プロンプトインジェクションによって生成記事の内容が操作されうることを前提とし、生成結果を他のコマンドやコードとして実行しない。
- 生成記事を Slack に投稿する前に、出典リンクがコード側で付与されていること（LLM の出力に依存しないこと）を確認する。
- LLM の空応答・途中打ち切り（`finish_reason` が `stop` 以外）はエラーとして扱い、不完全な記事を投稿しない。
- 推論モデルの推論過程（DeepSeek の `reasoning_content`）は記事に含めない。
- **Webhook への投稿で、記事によるメンションの通知を抑止する。** 2 つの層を併用する（F-006）。全メッセージに `silent`（真）を付けて通知・未読の表示を抑止し、`silent` に対応しない版のサーバにも備えて、メンションとして解釈されうる記法（`@` の後に名前の文字が続く語、`<!`・`<@`、文字参照、`<a|b>` の形）を含む記事は、1 つのメッセージも送らずに拒否する。`silent` に対応しない版では、拒否の層だけが通知を防ぐ。
- **検証・推敲の応答を信頼しない。** 応答は LLM が書いた JSON であり、信頼できない入力として扱う。応答全体の大きさ（1 MiB）と項目の数（256）に上限を設け、正しい UTF-8・対になっていないサロゲート・末尾に続くデータ・未知のキーと重複したキー・値の型・制御文字（タブ以外を拒否し、`before`・`after` は改行 `\n` も拒否、`evidence` の `\n` だけを認める）を検査し、規則に反する応答は補正・部分受理せずに拒否する。直す前と直した後の記述は、記事の中にちょうど 1 回だけ現れ、範囲が重ならず、見出しの構成を変えないことを確かめてから当てはめる。拒否のエラーには応答の値を含めない。
- **LLM の応答の `usage` を信頼しない。** 応答の `usage` もネットワークから受け取る信頼できない入力である。規則に合わない値（要素の不在・重複、値が負でない整数でない：負数・`-0`・小数・指数・`int64` を超える数・文字列・真偽値・`null`・配列・オブジェクト）は受理せず、その呼び出しのトークン数を「不明」とする。`usage` の不正で応答を拒否せず、記事の生成も失敗させない（副次的な情報のために本来の機能を失わない）。不明の理由は壊れた規則と要素の名前（アダプタの定数）だけから作り、応答のテキストと `usage` の値を含めない。トークン数の行は `redact.Line` を通る。ただし Claude の `cache_read_input_tokens`・`cache_creation_input_tokens` の `null` だけは、文書化された値として 0 とする（プロンプトキャッシュを指定していないため）。
- **一覧のファイル（`--review-log`）に入る値**は、記事の値と検証・推敲の応答の値だけから作り、設定の値（API キー・Webhook URL）を含めない。検証・推敲の応答から来る値は Markdown の引用ブロックの中に置き、値の中の見出し記号などがファイルの見出しの構造を壊さないようにする。記事のタイトルとモデル名・モデルの版は制御文字と改行を拒否する検査を通り、出典 URL は検証済みの動画 ID から組み立てるので、箇条書きの行も見出しの構造を変えない。投稿と同じく、書き出す前に記事の値を `CheckPublishable` で検査する。
- **中間生成物（`--artifacts`）に入る値**は、段階の出力（記事のタイトルと本文、検証・推敲の一覧）と来歴（段階・モデル名とモデルの版・トークン数・呼び出しの時刻・テンプレートの内容のダイジェスト・入力の識別子）だけとし、API キー・Webhook URL・上書きテンプレートのローカルのパス・設定の値を含めない。読み込みは信頼できない入力として境界で検査し、未知のキー・重複したキー・末尾の内容・上限（ファイル 4 MiB・文面 1 MiB・一覧 256 項目）の超過・本文の先頭の U+FEFF を拒否し、入力の識別子を生成の出力まで順にたどって照合する。`usage` 要素も検査し、4 つの区分のオブジェクトか不明を表す `null` だけを受理し、宣言していない要素・要素の欠け・重複・負数や範囲外の数は拒否する。トークン数と呼び出しの時刻は来歴の一部として `id` の計算に含め、書き換えたファイルを拒否する。呼び出しの時刻（`call_time`）は `YYYY-MM-DDTHH:MM:SSZ` の 20 バイトの文字列だけを受理し、`time.Parse` の後に同じ書式で書き直した文字列とのバイト単位の一致でほかの書き方を拒否する。ゼロの時刻と UTC でない時刻も拒否する（`TestParseRecordRejectsCallTime`）。ただし `id` は秘密の鍵を使わない識別子なので、トークン数や呼び出しの時刻を書き換えたうえで `id` を計算し直したファイルは検出できない（残余のリスクであり、改ざんの影響は、再利用した段階のトークン数の表示と、料金の行の適用した単価・`at=` の時刻・推定コストを誤らせることに限られる）。壊れた入力は補正も部分受理もしない。拒否のエラーには成果物の値を含めない。

## 7. リポジトリに保存する実データ

テスト用に実際の取得結果（`yt-dlp` の出力、YouTube のページの HTML など）を `testdata/` に保存するときは、次を守る。個々のファイルの出典・加工内容・作り直し方は [testdata/README.md](../../testdata/README.md) に記録する。

- 保存してよいのは、再配布が許諾されたライセンス（CC BY など）の動画から取得したものだけにする。出典とライセンスを `testdata/README.md` に明記する。
- 取得者を特定できる情報は、コミットする前に取り除く。`yt-dlp` の info.json は署名付き URL に取得者の IP アドレスを埋め込むので、該当する値を置き換える。ブラウザで保存したページの HTML は、ログインした状態で保存するとアカウントの情報（アバター、登録チャンネルの一覧、視聴履歴に基づくおすすめなど）を含む。ログインしていない状態で保存し、さらに必要な要素だけを切り出す。
- ページ全体のスナップショットはコミットしない。YouTube 自身のマークアップ・スクリプト、他チャンネルの動画の情報を含み、ログインした状態で保存した場合はアカウントの情報も含むためである。スナップショットは、どの worktree からも参照できるように、リポジトリの外の `${YT2COLUMN_SNAPSHOT_DIR:-${XDG_DATA_HOME:-$HOME/.local/share}/yt2column/snapshots}` に置く。`.envrc` は worktree に複製されないので、この環境変数は任意とし、設定しなければ既定のパスを使う。テストはこのディレクトリを参照しない。

## 8. ブラウザ拡張と localhost サーバ（#43）

ブラウザ拡張（#110・#111）は、収集した字幕と動画ページの URL を、利用者のマシンで動く localhost のサーバ（#104・#109）へ送る。#170 から、動画ページの DOM から読んだ動画タイトル・チャンネル名・概要欄も任意のメンバとして送る（§8.1）。タブのタイトルは送らない。#272 から、サーバは TCP を待ち受けず、Unix ドメインソケット（UDS）だけを待ち受ける。拡張からの送信は、ブラウザが起動する Native Messaging のホストが UDS へ中継する。

- **同一ユーザーのフル権限プロセスは信頼する。** サーバや拡張と同じ OS ユーザーとして動き、ファイルの読み書きとプロセスの起動ができるプロセス（AI Agent を含む）は、`.envrc`・API キー・Webhook URL を読め、サーバを経由せずに LLM API や Slack を直接使える。サーバの入口をどう限定しても、これらの資産は守れないので、この相手は排除しない。
- **排除する相手ごとに根拠が異なる。** 混同しない。
  - 他ユーザーのプロセス: ソケットのディレクトリの `0700`（主な防御）とソケットの `0600`（2 つ目の防御）、ディレクトリとソケットの所有者の検査で排除する（§8.2）。
  - ウェブページ: サーバは TCP を待ち受けないので、ページからサーバへ届く経路がない。ブラウザには、ページから UDS へ接続する手段がない。DNS rebinding や preflight の不要な `POST` でページが loopback のサーバへ届く問題（以前の TCP のサーバの前提）は、待ち受けそのものがなくなったことで生じない。
  - サンドボックス化された Agent: 排除しているのはサンドボックスのポリシーであり、UDS の権限ではない。ファイルのモードは同じ uid のプロセスを区別しないので、ポリシーが Unix ソケットへの接続を許可していれば、Agent はサーバに到達できる。UDS への移行によって、この点が後退することはない。
- **UDS の権限は同じ uid のプロセスを区別しない。** ソケットに接続できる相手は、同一ユーザーのどのプロセスでもありうる。サーバは、この相手が付けられる `Host`・`Origin`・`Content-Type`・`Authorization` のヘッダを検査しない（誰でも偽れるので、検査しても排除できる相手がいない）。検査するのはパスとメソッドだけである。
- **共有トークンを削除した理由。** 以前の共有トークンは拡張の認証ではなく、トークンのファイルを読める相手だけが示せる秘密の値で、ファイルを読めない相手を排除するものだった。同一ユーザーのフル権限プロセスはトークンのファイルも `.envrc` も読めるので、トークンを残してもこの相手は防げない。他ユーザーとウェブページは上のとおり UDS で排除できるので、トークンが排除する相手は残らない。そのため削除した。

### 8.1. ブラウザ拡張（#110）

本タスクの拡張（#110）は、開発環境と、選択範囲・タブの URL・タブのタイトルの収集と表示、および選択範囲と URL のサーバへの送信を行う。#170 で、動画ページの DOM から動画タイトル・チャンネル名・概要欄（以下、動画メタデータ）を読み、表示し、本文に加えて送るようになった。

**移行中の注記（#272）。** この節は、`127.0.0.1` へ HTTP と共有トークンで送る現行の拡張を述べる。サーバは既に UDS だけを待ち受け、共有トークンを持たない（§8・§8.2）ので、現行の拡張はサーバに届かない。拡張を Native Messaging のホストへ切り替えるときに、この節を改め、この注記を削除する（`docs/tasks/0026_native_messaging_relay` のフェーズ 3）。

- **要求する権限**（設計書 3.1 の manifest）: `activeTab`（利用者が起動したタブに限り、そのタブの URL・タイトルを読み、スクリプトを注入することを許す）、`scripting`（起動したタブに、選択範囲と動画メタデータを読む関数を注入する）、`storage`（オプションページで設定（共有トークンとポート）を `chrome.storage.local` に保存する）。閲覧内容全般に及ぶ権限（すべてのサイトへのホストの権限、`tabs`、`history`、`cookies`、`webRequest` など）は要求しない。
- **ホストの権限（`host_permissions`）:** `http://127.0.0.1/*` を宣言する。送信先は loopback のサーバだけで、宣言しないと `Content-Type: application/json` の `POST` が preflight（`OPTIONS`）になり、サーバは `OPTIONS` を拒否するためである。この権限は、送信のほかに、`127.0.0.1` の任意のポートへの要求と、`scripting` と合わせた `127.0.0.1` のタブへの注入も許す。拡張のコードは送信先を `/articles` に限り、注入は `activeTab` で起動したタブに対してだけ行う（残余のリスクは設計書 5.4 のとおり受け入れる）。
- **共有トークンをログ・表示・本文に出さない。** トークンは送信の `Authorization` ヘッダと保存先にだけ置き、開発者向けのログ・利用者への表示・送る本文には入れない。
- **トークンの保存先の理由と残余のリスク。** トークンは `chrome.storage.local` に保存する（ブラウザを再起動しても貼り直さずに済み、`chrome.storage.sync` と違ってブラウザの外へ同期されない）。ただしプロファイルのディレクトリに暗号化されずに保存され、同じ OS の利用者として動くプロセスは読める（サーバのトークンのファイルや `.envrc` の秘密と同じ信頼の範囲）。このリスクは受け入れる（設計書 5.4）。
- **API キーと Webhook URL を持たない。** 拡張はこれらを保持も入力も保存も表示もしない。
- **応答を受け取れない場合は自動で再送しない。** 生成と投稿の結果は Slack だけで知らせ、サーバは `202` の後の結果を返す API を持たない。応答を受け取れない場合と想定外の応答の場合は、送り直す前に Slack を確かめるよう案内し、自動では再送しない。
- **応答を受理する形で検査し、本文の文字列を表示しない。** 応答の本文は信頼できない入力として受理する形だけを読み、状態コード・`status`・`reason`・`requestId` の組が合わなければ想定外の応答とする。応答の本文の文字列は表示に使わない（`reason` は固定の文言に、`requestId` は 16 進 16 文字に限る）。
- **利用者が起動するまでページを読まない。** `content_scripts` を宣言せず、ページの読み込み時に自動で実行されるコードを持たない。起動で読むのは起動したタブだけである（`activeTab`）。選択範囲はページの DOM の構造に依存せず、ブラウザの選択の API（`window.getSelection()`）で取得する。
- **動画メタデータは DOM から読むだけで、ページを操作しない。** 動画タイトル・チャンネル名・概要欄は、収集が成功したときだけ、起動したタブの動画ページの DOM から読む。新しい権限を加えず、既存の `scripting` の注入で DOM を読むだけで、クリック・フォーカス・入力などページを操作するコードを持たない（概要欄の「…もっと見る」も開かない）。読む時点のページの URL が収集した URL と一致しない場合は、別の動画の値を混ぜないよう 3 つの値をすべて省略する。DOM の構造は YouTube が独自に定義したもので変わりうるため、取得に失敗しても起動を失敗させず、拒否の理由にもしない（値を省略して選択範囲と URL を送る）。開発者向けのログにはフィールドの名前・省略の理由・失敗した検査の種類・折りたたみの状態だけを残し、読み取った値は残さない。
- **動画メタデータを untrusted テキストとして扱う。** 読み取った結果は信頼できない入力であり、受理する形（決めたメンバと値の型）に合うものだけを受け入れる。値は HTML として解釈せず `textContent` だけで表示し、双方向の制御文字で表示順が変わらないよう `dir="auto"` と `unicode-bidi: plaintext` で分離する。本文へは JSON の文字列として入れる。値の大きさは本文の上限（4 MiB）の判定に含める。
- **読み取った文字列をテキストとして表示する。** 選択範囲とタブのタイトルは信頼できない入力であり、HTML やほかのマークアップとして解釈せず、`textContent` だけで表示する。`eval`・`new Function` と HTML を解釈する API は lint で禁止し、Manifest V3 の既定の Content Security Policy を緩めない（lint とは独立した 2 つ目の防御）。
- **秘密鍵をリポジトリに含めない。** 拡張 ID の固定には manifest の `key`（公開鍵）だけを使い、生成した RSA の秘密鍵は生成直後に削除する。固定した拡張 ID は `clfmbbcdpnjcefbdihdoahomaifbabkk`。拡張 ID は秘密ではなく、`key` は公開情報なので誰でも同じ ID の拡張を読み込んで名乗れる。したがって `Origin` ヘッダは送り元の認証にならない（前段と設計書 3.12.1）。
- **依存パッケージは lockfile で版を固定し、開発用に限る。** 拡張の実行時に読み込む npm の依存パッケージはなく、`dist/` に含まれるのは本リポジトリで書いたコードだけである。インストールは `npm ci --ignore-scripts` で行い、依存パッケージのインストール時のスクリプト（`postinstall` など）を実行しない。

### 8.2. localhost サーバ（#109）

サーバ（`cmd/yt2column-server`・`internal/server`・`internal/serversock`）は、拡張から送られた字幕をもとに記事を生成し Slack へ投稿する。§8 の方針に加え、次を守る。

- **UDS だけを待ち受ける。** ソケットのパスは `HOME` だけから導出する（macOS は `$HOME/Library/Application Support/yt2column/run/server.sock`、他の Unix は `$HOME/.local/state/yt2column/run/server.sock`）。`XDG_*`・`TMPDIR` などほかの変数は読まない。ブラウザが起動するホストは利用者のシェルの環境変数を引き継がないので、ほかの変数を読むと、サーバとホストが別のパスを導出しうるためである。導出したパスが OS の上限（Linux は 107 バイト、macOS と他の Unix は 103 バイト）を超えれば、値を含めずに `HOME` を名指して起動を中止する（終了コード `2`）。
- **ソケットのディレクトリ（`run`）は `0700`、ソケットは `0600`。** 他ユーザーを排除する主な防御は、ディレクトリの `0700` である。起動時に、ディレクトリの親が symlink でないディレクトリで、所有者が自分で、グループとその他の書き込みのビット（`0022`）が立っていないことを確かめる（親に他人が書き込めると、検査の後に `run` の名前を入れ替えられる）。`run` がなければ `0700` で作り、symlink でないディレクトリで、所有者が自分で、権限がちょうど `0700`（setuid・setgid・sticky のビットもなし）であることを確かめる。bind の直後、ソケットは umask に従う広い権限で存在しうるが、その間も他ユーザーはディレクトリを検索できない。bind の後に `chmod` で `0600` にし、`Lstat` でソケットであること・所有者が自分であること・権限がちょうど `0600` であることを確かめ直す（2 つ目の防御）。プロセス全体の umask は変えない。
- **修復せずに拒否する。** ディレクトリ・親・ソケットのパスが受理する形でなければ、権限を変えず、何も削除せずに起動を中止する（終了コード `1`）。エラーはパスと固定の理由を示し、利用者が手で直す（CLAUDE.md「Reject, don't normalize」）。
- **起動のロック。** ディレクトリの検査の後、ソケットのディレクトリのロックのファイル（`.yt2column.lock`。`internal/cachelock` を使う）に、待たずに排他の `flock` を取る。stale の判定・`unlink`・bind をサーバの間で直列化し、2 つのサーバが互いのソケットを消し合わないようにするためである。取れなければ、別のサーバが動いているとして起動を中止する（終了コード `1`）。サーバは、`Serve` が返る（シャットダウン中のジョブと失敗の通知の完了を待つ）までロックを持ち続けるので、シャットダウン中に起動した次のサーバも中止する。2 つのサーバが同時にジョブを処理し、同時実行の枠の上限がサーバ全体で効かなくなることはない。ロックはプロセスの終了（`SIGKILL` を含む）で解放され、ロックのファイルは削除しない。
- **stale の判定。** ソケットのパスに既にある名前は、自分の所有のソケットで、接続が拒否される（`ECONNREFUSED`）場合だけ、異常終了したサーバが残した stale なソケットとして削除し、bind し直す。接続できるソケット（ロックを取らずに待ち受ける別のプロセス）は削除せずに中止する。他人の所有のソケット、接続の試みがほかの理由で失敗するソケット、通常ファイル・ディレクトリ・symlink・FIFO も、削除せずに中止する。正常に終了すると、リスナーを閉じたときにソケットを削除する。
- **ヘッダの検査はパスとメソッドだけ。** リクエストは、パス（`/articles`）、メソッド（`POST`）、同時実行の枠（`2`）の順に検査する。パスとメソッドの不一致（`not_found`・`method_not_allowed`）は、本文を 1 バイトも読まず、枠を取らず、記事の生成も失敗の通知もしない。HTTP として読めないバイト列には `net/http` が自分で `400` を返し、ハンドラは呼ばれない。枠（`2`）を超えるリクエストは、本文を読まずに `too_many_requests` で拒否する。未完了のリクエストの資源消費は、本文を読まないこと、枠を取らないこと、`Connection: close`、ヘッダの大きさとタイムアウトの上限で抑える。
- **受け取る入力の境界。** 本文は 4 MiB を上限とし、`Content-Length` の事前検査と `http.MaxBytesReader` で読む。`Content-Length` が上限を超えれば本文を読まずに `body_too_large` で拒否するので、`Expect: 100-continue` を付けたクライアントは本文を送らずに拒否の応答を受け取る。本文全体の UTF-8・対になっていないサロゲート・1 つのオブジェクト・末尾の余分な値・宣言したメンバの重複を厳格に検査し（`internal/strictjson`）、`videoUrl` は `transcript.ValidateVideoURL` で、`transcript` は `transcript.NewCopiedSource` で検査する。合わない入力は補正せず拒否する。
- **秘密と字幕の本文を出力に流さない。** API キー・Webhook URL は `secret.Secret` で持つ。応答と失敗の通知は、拒否の理由・失敗の種類・リクエスト ID・検査済みの動画 ID という固定の値だけで組み立てる。ログは `redact.Writer` を必ず通し、`redact.SecretStrings` が返す文字列を伏せ字にする。`server.New` がロガーと `http.Server` の `ErrorLog` を `redact.Writer` の上に作るので、呼び出し側が伏せ字の処理を忘れても漏れない。サーバは標準出力に何も書かず、ログ・案内・エラーは標準エラー出力に書く。起動のログにはソケットのパスを記録する（秘密ではない）。
- **残余のリスク（許容する）。**
  - 同一ユーザーは、サーバの稼働中でもソケットのパスを `unlink` して自分のソケットを同じパスに bind でき、以後の字幕を受け取れる。起動のロックは、ロックを取らない相手を止めない（`flock` は助言的なロックである）。
  - サーバの停止中に、同一ユーザーがソケットのパスを先に bind して、字幕を受け取れる（以前の TCP のサーバの残余リスクと同じ種類で、他ユーザーにはできなくなった）。
  - ソケットのディレクトリの祖先（`HOME`・`Library/Application Support`・`.local/state`）は検査しない。他ユーザーがこれらに書き込めないことを前提とする（macOS の既定）。
  - macOS の拡張 ACL（アクセス制御リスト）は、モードのビットと独立に他ユーザーに検索や追加を許しうる。継承される ACE が祖先にある場合や、`chmod +a` で `run` に付けた場合、`Lstat` のモードは `0700` のままで検査を通る。標準ライブラリでは ACL を読めないので、ソケットのディレクトリとその親に他ユーザーを許す ACE がないことは、確かめていない前提である。Linux では、モード `0700` のとき POSIX ACL のマスクが `---` になるので、この問題はない。
  - macOS では、待ち行列が満杯の稼働中の待ち受けへの接続も `ECONNREFUSED` になりうるので、ロックを取らずに同じパスで待ち受ける同一ユーザーのプロセスを、stale と見なして削除することがある。同一ユーザーの信頼の範囲に含める。
  - サーバがシャットダウンを始めた瞬間に待ち行列にあった接続は、処理されずに切られる。
  - `202` が届かずに利用者が送り直すと、同じ記事が二重に生成・投稿されうる。
  - 利用者 1 人の macOS を前提に、これらは受け入れる。
